# 音声バージョンの作成

**引数**: $ARGUMENTS（オプション: ニュースレターのファイル。省略時は `newsletters/` の最新）

## この番組について

台本を書くときも、見直しを頼むときも、この前提に立つ。

```
「UXエンジニアリング・マガジン」は、UX・フロントエンド・デザインシステム・アクセシビリティ・AI を使った開発などの、国内外の技術記事やデザインの記事を毎号選んで紹介する日本語のニュースレターです。この番組はその音声バージョンで、1号ごとに10〜15分です。
聞く人は、UXエンジニア、フロントエンドエンジニア、デザイナーなど、作る側の人たちです。通勤中や作業の合間に、画面を見ずに耳だけで聞きます。
落ち着いた案内役（Aoi）と、気さくな聞き手（Ren）の2人が、です・ます調で話します。記事ごとに、何の記事か・いちばん大事な点・作る人にとっての意味を伝え、聞いた人が気になったら元の記事を読みに行ける手がかりを残します。
CSS のプロパティ名や製品名などの技術名は、英字のまま読み上げます。聞く人はこうした名前を知っている、または調べられる前提です。
```

## 1. 対象を決める

```bash
NEWSLETTER=${ARGUMENTS:-$(ls newsletters/[0-9]*.md | sort | tail -1)}
EPISODE=$(basename "$NEWSLETTER" .md)
SCRIPT="podcasts/scripts/${EPISODE}.json"
```

`podcasts/audio/${EPISODE}.mp3` がすでにあれば、台本と生成は飛ばして手順7から行う（Release に MP3 がもうあれば、Release へのアップロードは飛ばして、カバー画像と手順8の動画を作る）。

## 2. 台本を書く

ニュースレターを読み、耳で聞く2人の会話台本を `$SCRIPT` に書く。

- A（Aoi）は記事を紹介する案内役、B（Ren）は聞き手。B は短い相づちや質問で話を進める
- **長さは最大 15 分（本文 5,000 字まで）**。5,500 字を超えると生成側で止まる
- 構成: オープニング → 詳細掲載の記事を1本ずつ → エンディング（100字ほど）。「その他の記事」は読まない
- オープニングで言うのは、番組名・何月何日号・本数の3つだけ。その号の話題をまとめて紹介しない（まとめると抽象的になって、毎回同じような言い方になる）
- 記事1本は 300〜400 字が目安。15本の号はそれでちょうど15分前後になる。記事が少ない号は短くてよく、15分に届かせるための水増しはしない
- 記事ごとに、何の記事か・いちばん大事な点・UXエンジニアにとっての意味を話す。3行まとめと詳細解説から選び、全部は読まない
- 文体は `ai/docs/style-guide.md` に従う。話し言葉なので1文を短くする

耳で聞くための書き換え（TTS はそのまま読むので、台本の段階で直す）:

- 英語のタイトルはそのまま読まず、日本語で内容を言う（例: 「Design systems should be fast by default」→「デザインシステムは最初から速くあるべき、という記事」）
- **技術の名前はぼかさない**。記号やかっこを外して英字のまま書く（`:has()` →「has セレクター」、`text-wrap: pretty` →「text-wrap の pretty」、`sibling-index()` →「sibling-index 関数」）。「親を選べるセレクター」「新しい CSS の関数」のように名前を消して説明だけにしない。説明は名前のあとに足す
- 製品名・人名・サービス名も英字のまま書いてよい（Figma、Claude、WCAG、Lighthouse、PageSpeed Insights は正しく読める）
- 1文字ずつ読まれてしまう名前はカタカナにする（`nth-child` は「エヌティーエイチ・チャイルド」と読まれたので「エンスチャイルド」）
- URL、カラーコード（`#4f46e5` は「藍色」などに）、絵文字、関数の引数のような記号の並びは書かない
- 出典名は「Zennの記事」「Smashing Magazine の記事」くらいに短く言う
- 読みが分かれる漢字は言い換える（実際に「一行」が「いってん」、「全文」が「ぜんぶ」と読まれた）
- 3桁以上のバージョン番号は小数のように読まれることがある（「Chrome 156」が「いってんごろく」になった）。「バージョン百五十六」のように書く
- 本数などの数え方は数字で書く（「九本でした」が崩れて読まれたことがある。「9本」は正しく読めた）

形式:

```json
{
  "episode": "2026-11-06-150018",
  "newsletter": "newsletters/2026-11-06-150018.md",
  "segments": [
    { "id": "opening", "title": "オープニング", "lines": [{ "speaker": "A", "text": "..." }] },
    { "id": "a01", "title": "記事の短い題", "lines": [...] },
    { "id": "ending", "title": "エンディング", "lines": [...] }
  ]
}
```

記事のセグメントは `a01`, `a02`, ... と順に振る。1セグメントが1回の TTS リクエストになる。

## 3. 台本をチェックする

書き終えたら、記事の中身がちゃんと伝わる台本になっているかを確かめて直す。

まず、3行まとめに出てくる名前が台本から抜けていないかを機械的に調べる:

```bash
pnpm run podcast:check "$SCRIPT"
```

同じコマンドで、`ai/docs/style-guide.md` の禁止語（「版」など）が台本に入っていないかも出る。別の語の一部に当たっただけのもの（「出版」など）でなければ直す。

挙がった名前は、1つずつ「台本に足す」か「言わなくても記事の中身は伝わる」かを決める。記事の主役の技術・製品・手法なら足す。例として出てくる値（`:nth-child(5)` や `light only` など）や、記事の要点に関わらない名前なら足さなくてよい。

次に、記事のセグメントを1本ずつ、ニュースレターの3行まとめと詳細解説に照らして読み直す:

1. **名前**: 記事の主役の技術・製品・手法を、名前で言っているか。「こういう技術」「新しい機能」「ある関数」で済ませていないか
2. **中身**: それが何をするもので、記事で何が分かったか（数字や結論があれば）を具体的に言っているか。聞いた人が自分で調べ始められるだけの手がかりがあるか
3. **正しさ**: 3行まとめや詳細解説と食い違う内容、言いすぎがないか
4. **読み**: 耳で聞いて読めるか（記号、URL、カラーコード、読みが分かれる漢字、1文字ずつ読まれる名前が残っていないか）

直したら `pnpm run podcast:check` をもう一度実行する。直した箇所と、足さないと決めた名前は手順9の報告に書く。

## 4. 日本語を見直す

英語の記事が多いので、英語の言い回しを日本語に置き換えただけの、不自然な表現が混ざりやすい。書いた本人は自分の文の不自然さに気づきにくいので、**台本の日本語だけを、別のエージェント（Agent ツール、ほかの文脈を持たない新しいエージェント）に読ませて**候補を挙げさせる。

台本の文を書き出す:

```bash
python3 -I -c "import json,sys; d=json.load(open(sys.argv[1])); [print(f\"[{s['id']}] {l['speaker']}: {l['text']}\") for s in d['segments'] for l in s['lines']]" "$SCRIPT"
```

「この番組について」の文と台本の出力を添えて、次の依頼をそのまま渡す:

```
添えた「この番組について」がこの台本の前提です。以下は、その番組の台本です。もとの記事には英語のものが多いので、英語の言い回しを日本語に置き換えただけの不自然な表現が混ざっているかもしれません。日本語として不自然なところを挙げてください。

見るところ:
- 英語の語をそのまま訳した言い方（例: owner →「持ち主」、moment →「瞬間」、shared context →「共有の文脈」、give a shift →「切り替えをくれる」、lean toward →「〜の方向に寄る」、real tables →「本当の表」）
- 人ではないものが主語の「〜が〜をくれる」「〜が〜を可能にする」のような、日本語の会話では言わない言い方
- 名詞を重ねた硬い言い方や、一度聞いただけでは意味が取りにくい文

見ないところ: 英字のまま書いた技術名・製品名（これは意図して残している）、内容の正しさ、長さ。

出力: 1件ずつ「[セグメントid] 元の文の該当部分 → 言い換え案（なぜ不自然か）」の形で。言い換え案は、技術名と意味を変えないこと。不自然なところがなければ「なし」とだけ書く。
```

返ってきた候補は、1つずつ読んで判断する。もっともだと思うものは直し、技術名が消える・意味が変わる言い換えは採らない。直したら `pnpm run podcast:check` をもう一度実行する。直した箇所は手順9の報告に書く。

## 5. 字数と予算を確かめる

```bash
pnpm run podcast "$SCRIPT" --dry-run
```

`NG:` が出たら台本を直してもう一度確かめる。予算や1日の本数で止まった場合は、作らずにその理由を報告して終える。

## 6. 音声を作る

```bash
pnpm run podcast "$SCRIPT"
```

途中で失敗しても、作り終えたセグメントは `podcasts/audio/${EPISODE}/` に残っているので、同じコマンドで続きから作れる（二重に払わない）。

## 7. カバー画像を作って Release に上げる

号ごとのカバー画像（3000×3000 の JPEG）を作る。通し番号・日付・記事の本数が入る:

```bash
pnpm run podcast:cover "$SCRIPT"
```

カバー画像はスタイルを試している途中なので、手元（`podcasts/audio/`）に置くだけにして、Release には上げない。

MP3 はリポジトリに入れず、GitHub の Release `podcast` に置く。公開リポジトリなので、誰でもダウンロードできる。

```bash
gh release upload podcast "podcasts/audio/${EPISODE}.mp3" --clobber
```

## 8. 動画を作る

X には音声だけでは投稿できないので、全編を1本の MP4 にする。エンコードは reel の talk-lab（`config/podcast.yml` の `video.appUrl`）がブラウザの中で行い、このコマンドはヘッドレスブラウザで MP3 を渡して書き出された MP4 を受け取る。

```bash
pnpm run podcast:video "$SCRIPT"
```

- `podcasts/video/${EPISODE}/full.mp4` に書き出す。10分ほどの号で、書き出しは2分弱、大きさは 300MB 前後になる
- 記事ごとのクリップ（`a01.mp4` など）も欲しいときは `--clips` を付ける。特定のものだけなら `--only full,a03`
- h264 + aac か、長さがタイムラインと 0.2 秒以内で合うか、X の上限（`config/podcast.yml` の `video.maxDurationSec` / `maxSizeMb`。X Premium に合わせてある）に収まるかを ffprobe で確かめ、外れたら止まる
- 作り終えた MP4 は飛ばすので、途中で止まっても同じコマンドで続きから作れる。MP3 かタイムラインのほうが新しい MP4 は作り直す。`--only` で挙げたものは必ず作り直し、全部作り直すなら `--force`
- タイムライン（`podcasts/audio/${EPISODE}.timeline.json`）は `pnpm run podcast` で MP3 を作ったときにだけ書き出される。ない場合は動画を作らずに、そのことを報告する
- 動画は git にも Release にも入れない。X への投稿は手で行う

## 9. 報告

- MP3 の長さと公開 URL（`https://github.com/uto-usui/magazine/releases/download/podcast/${EPISODE}.mp3`）と、カバー画像のパス（`podcasts/audio/${EPISODE}.jpg`）
- 動画の本数と、1本ずつのパス・長さ・大きさ（`pnpm run podcast:video` の最後に出る一覧）
- X に投稿するときのタイトルと話題の一覧（`pnpm run podcast:video` の最後に「投稿用:」として出る）
- この回の料金と、今月の使用額（`pnpm run podcast:usage` の出力）
- 手順3のチェックで直した箇所と、足さないと決めた名前
- 手順4で直した日本語（元の文 → 直した文）

コミットはしない。台本（`podcasts/scripts/`）と使用量の記録（`state/tts-usage.json`）はコミット対象、MP3 と MP4 は `.gitignore` 済み。
