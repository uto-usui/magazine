# ニュースレター自動作成（非対話バージョン）

このコマンドは `/create-newsletter` の非対話バージョンです。
ユーザー確認なしで自動的にニュースレターを作成し、コミットまで行います。pushは呼び出し元が担当します。

## 処理手順

### 0. 対象日付の決定

**引数**: $ARGUMENTS（オプション: 対象の日付フォルダ名 例: `2026-01-20`）

1. **引数がある場合**: 指定された日付フォルダを使用
2. **引数がない場合**: 最新の日付フォルダを自動検出
   ```bash
   ls -d articles/[0-9][0-9][0-9][0-9]-[0-9][0-9]-[0-9][0-9] 2>/dev/null | sort -r | head -1
   ```

3. **生成済みチェック**: 対象日付のニュースレターが既に存在するか確認
   ```bash
   ls newsletters/${TARGET_DATE}-*.md 2>/dev/null
   ```

4. **生成済みの場合**: **スキップして終了**（再生成しない）
   - 「既に YYYY-MM-DD のニュースレターが存在します。処理をスキップします。」と報告

### 1. 記事一覧の取得

`articles/YYYY-MM-DD/` ディレクトリ内の記事を検索し、各記事のタイトル・カテゴリ・publishedDateを読み取ります。

**記事がない場合**: エラーメッセージを表示して終了

### 2. 記事選定（自動）

**`ai/docs/selection-rubric.md` を読み込み、その手順（足切り → 採点 → 並べて選ぶ → 記録）で選ぶ。** 記事数にかかわらず全記事を採点して記録する。

- 詳細掲載は最大15件。足切りと「A が 0 点」を除いた記事が15件に届かなければ、届いた分だけ載せる（数合わせで基準を下げない）
- 足切りした記事と、選ばれなかった記事は「その他の記事」に載せる

### 3. 記事の要約生成

選択された各記事について：

1. **記事本文を読み込む**
2. **3行まとめを生成**（1行1文を基本にし、です・ます で終える。体言止めや「〜する。」で終えない）
3. **詳細解説を生成**（長さは中身に合わせる）
   - 記事の背景・文脈を説明
   - 技術的なポイント、アーキテクチャ、実装の詳細を解説
   - **UXエンジニアの仕事につなげて解釈を加える**（書き方は `ai/docs/editor-voice.md`）。ただし「UXエンジニアの視点では」「UXエンジニアにとって」と前置きせず、どの場面で何に使えるかを具体的に書く。具体的に言えることがなければ書かない（感想や一般論で埋めない）
   - 中身の薄い記事は短くてよい。字数を埋めるために要約の言い換えや一般論を足さない。元記事が短い記事（3行まとめで主な中身を言い尽くせる記事）は、3行まとめにない情報だけを2〜3文で書く
   - 記事の限界点や注意点があれば言及
   - 関連するトピックや発展的な内容への言及

### 4. ニュースレター生成

以下のフォーマットでMarkdownファイルを生成：

```markdown
# ニュースレター

**発行日**: YYYY-MM-DD

---

## ハイライト

### [記事タイトル](元記事URL)

> **出典**: フィード名 | **公開日**: YYYY-MM-DD | **カテゴリ**: xxx

**3行まとめ**
- ポイント1
- ポイント2
- ポイント3

**詳細解説**

[解説文]

---

（詳細掲載記事ごとに繰り返し）

---

## その他の記事

- [記事タイトル](元記事URL) - カテゴリ / フィード名
- ...

---
```

### 5. ファイル出力

- **出力先**: `newsletters/${TARGET_DATE}-HHmmss.md`
- 日付は**実行日ではなく `TARGET_DATE`（対象 `articles/` の日付）**。日跨ぎ実行でも poller の重複チェックと整合させるため
- `HHmmss`: 同日再生成時の衝突防止

```bash
NEWSLETTER_FILE="newsletters/${TARGET_DATE}-$(date "+%H%M%S").md"
SCORES_FILE="newsletters/scores/$(basename "$NEWSLETTER_FILE" .md).tsv"
```

採点表は `$SCORES_FILE` に書く（形式は `ai/docs/selection-rubric.md` の「記録」）。

### 6. 校正

**`ai/docs/proofreading.md` の手順で校正する。** 機械チェックのあと、書いた経緯を知らないサブエージェント2つ（文の校正・読み物としての通読）に読み直させ、指摘を反映し、機械チェックがすべて `OK` になるまで直す。サブエージェントを使わずにこの手順を済ませない。

### 7. コミット

```bash
git add "$NEWSLETTER_FILE" "$SCORES_FILE"
git commit -m "docs: Add newsletter for ${TARGET_DATE}" -- "$NEWSLETTER_FILE" "$SCORES_FILE"
```

### 8. 完了報告

- 作成したファイルのパス
- 含まれる記事数
- 校正の指摘の数・反映した数・採らなかった指摘とその理由

## 文体・表記ルール

**書き始める前に `ai/docs/editor-voice.md`（編集部としての書き方と、解釈の着眼点）を読み、解釈はその書き方で書くこと。**

**必ず `ai/docs/style-guide.md` を読み込み、スタイルガイドに従って文章を生成すること。**

## 注意事項

- 記事が存在しない場合はエラー終了
- 既存のニュースレターがある場合はスキップ
- 要約は原文の意図を損なわないよう正確性を重視
- 技術用語は可能な限り日本語で解説
- 記事のカテゴリで絞り込まない（全カテゴリ対象）
- 詳細解説は要約で終わらせない（3行まとめに入らなかった中身と、具体的に言える解釈を書く。長さは中身に合わせる）
- 校正はサブエージェントに任せる（`ai/docs/proofreading.md`）
