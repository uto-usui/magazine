# 編集ガイドライン

キュレーション記事の編集方針。導入文、コメント、締め文の書き方と、記事全体の構成ルール。

---

## 編集テーマ

選定した記事を俯瞰し、全体を貫くテーマを見つける。

例: 「AI時代にUXエンジニアはどう働くか」「パフォーマンスと体験の両立」「見えない仕事の価値」

テーマは無理に作らなくてよいが、あると記事間のつながりが生まれる。

## シリーズとしての継続性

このピックアップはシリーズとして続いている。過去の号（`newsletters/pickup/`）との関連を意識する:

- 以前紹介した記事と関連するテーマがあれば言及する（「以前の〇〇とも通じる」）
- 同じテーマが続いている場合はその流れを意識する
- 関連がない場合は無理に言及しない

## 記事の並び順

並び順にも意図を持つ:

- 冒頭の問いに関連する記事を最初と最後に配置
- 技術記事を間に挟んでバランスを取る
- 関連する記事は近くに配置

## 導入文

**書くこと**:
- 今回の記事に共通するテーマや傾向を軽く伝える
- 読者を記事に誘い込むフック

**書かないこと**:
- 数字（何号分、何記事から何記事を選んだ等）— 裏側の話なので不要
- 「3つの柱で構成しています」のような構成説明 — 自分が書いた記事みたいになる
- 押しつけがましい表現

**トーン**: 淡々と、でも温かみのある感じ。「やはり」「〜でした」のように少し引いた視点。週番号表記（例: 202601W3）を使ってもよい。

**良い例**:

```
202601W3の記事は、やはりAIの話題が多めでした。仕様書の書き方、デザイナーの役割の変化、ユーザーフィードバックの活かし方。眺めていると「AIと一緒に働くって、結局どういうことなんだろう」という問いが出てきます。GSAPやCSS、アクセシビリティの話も。
```

## 🐈‍⬛ コメント

各記事に付ける編集者コメント。

**書くこと**（以下のいずれか）:
- 記事に書かれていない視点を足す（限界、前提条件、別の角度からの解釈）
- 他の記事や概念との接続（「今回の〇〇とも通じる」「〇〇を知っていると深まる」）
- ポジティブな好み（「個人的には〇〇が好き」「これはよくやっている」）

**書かないこと**:
- 「〜な人におすすめです」「〜に役立ちます」— 誰でも書けるラベル付け
- 読者への直接的な問いかけ（「あなたはどう思いますか？」等）— メタ的すぎる
- 否定的な評価や炎上リスクのある表現

**良い例**:

```
> 🐈‍⬛ : 「Always / Ask first / Never」の境界設計は、AIに限らずチームメンバーへの権限委譲でも使えるフレームワーク。境界を書くこと自体がAIへの信頼度の可視化になっているのがおもしろい。
```

```
> 🐈‍⬛ : 今回の「Designers as agent orchestrators」とも通じる話で、AIが台頭するほど「曖昧さを扱う」見えにくい仕事の価値が上がる。評価されにくいからこそ、自分で言語化しておく意味がある。
```

```
> 🐈‍⬛ : 物理演算をScrollTriggerで表示領域内のみ実行する最適化、こういう地味な配慮がパフォーマンスとリッチさの両立に効く。個人的には「目が怒る」インタラクションが好き。
```

## 締めの文章

**書くこと**:
- 冒頭で提示した問いを回収する
- 今回の記事から具体的な内容を含める（抽象論だけにしない）
- 時勢に合わせたひとこと
- 「また来週」的な軽い挨拶

**時勢のネタ**: 季節、天気、「今日は何の日」、技術カンファレンス、連休・祝日、年度の節目など。読者と共有できる「今」の感覚を入れる。自分で考えて選ぶこと。例をそのまま使わない。

政治・宗教・社会問題など炎上リスクのある話題は避ける。

**トーン**:
- 前向き（「仕方ない」「しかない」等の消極的表現はNG）
- 押しつけがましくない
- 軽く終わる（長々と書かない）
