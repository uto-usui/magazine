# 編集部としての書き方

詳細解説の解釈を、どこに目を付けて、どんな言い方で書くかの資料です。**書き始める前に読みます。** 表記の決まりは `style-guide.md`、書いたあとの検査は `proofreading.md` が受け持ちます。

ここに書いた言い方や締め方を、全記事に同じように当てはめないでください。同じ形を並べると、それ自体が新しい癖になります。記事ごとに選びます。

## 立場

ニュースレターは、編集部が記事を紹介するものです。個人が自分の知識や体験を伝えるものではありません。主役は元記事の中身で、編集部の役目は、その中身を読者が自分の仕事のどこで使えるかまで紹介することです。

読者は、デザインシステム、アクセシビリティ、デザインとコードの行き来、AI との協働に関わるエンジニアやデザイナーです。

- 個人の好みや願望、気持ちは書かない。「〜を試してみたい」「〜がすきです」「うれしい」「ありがたい」「しんどい」は使わない
- 一人称（私・ぼく）も「編集部では」も出さない
- 解釈は、読者の仕事にどう当てはまるかで書く（「〜の場面で使えます」「〜できそうです」）
- 読者への提案は書いてよい。「まず〜から取り入れると手軽です」「〜と見比べてみてください」「〜の仕様に一緒に書いておくと、実装とずれにくくなります」のように、読者が次に何をするかを示す。「〜てみたい」は書き手の願望なので使わず、読者に向けた提案の形にする

## どこに目を付けるか

解釈は、次のような着眼点から出てきます。記事ごとに、当てはまるものが 1 つあれば十分です。当てはまるものがなければ、解釈は書きません。

- **デザインとコードの両側から見る**: CSS の新しい機能なら、Figma の側でどう設計できるか。デザインの話なら、コードでどう保つか
- **本番のコードを正とする**: 仕様書や静的なモックが実物とずれる話
- **人の注意に頼らず、仕組みで質を守る**: 目視や気づきに頼っている確認を、テスト・lint・型・部品に移せるか
- **誰かの手間が減るか**: チームの誰かが何かをしなくてよくなるか
- **ほかの人も使える形か**: 一部の人しか扱えない技術か、チームに広げられるものか
- **AI の出力をどう確かめるか**: AI に任せる前に、確かめる仕組みを置けるか
- **保ち続ける手間**: 入れやすさだけでなく、運用し続けるコスト
- **見た目と機能の両方**: 見た目の工夫も、根拠があれば取り上げる。根拠のない飾りは持ち上げない

## 書き方

- **記事を評価せず、中身を紹介する。** 「〜な記事です」「〜を促す記事です」と記事を性格づけしない。勧めるなら、何がいいかを 1 点だけ言う（「よい例と悪い例が並んでいて、直し方がつかみやすい」）
- **何に使えるかを名詞で言う。** 「参考になる」「発想が広がる」はどの記事にも付けられる。「まず reset と utility の層で使うと、`!important` を減らせそうです」のように、どこで何をするかを書く
- **前のやり方と比べる。** 「これまでは scroll イベントを間引いていたところが、CSS だけで済むかもしれません」のように、何の手間が減るかで書く
- **確度を使い分ける。** 記事に書かれた事実や結果は言い切る。読者の仕事に当てはめるところは「〜できそうです」「〜かもしれません」
- **欠点も短く言う。** 「ドキュメントはやや難しめです」「運用の手間は大きそうです」。そのあとに、どんな場面なら向いているかを書く。元記事が自分で書いている限界は、記事の事実として伝える
- **合わないものはけなさない。** どんなチームや場面なら合うかを書く
- **薄い記事は短く。** 詳細解説を 2〜3 文にするときは、解釈もそのなかの 1 文に含める
- **解釈の置き場所は決めない。** 事実の段落のなかに 1 文混ぜてもよい。毎回いちばん最後に解釈の段落を置くと、全記事が「事実 → 解釈」の同じ形になる
- **締めは、使う場面や読者への提案にする。** 最初に取り入れやすいところや、手元で確かめる方法を示す。教訓や格言で締めない。締めの文がなくてもよい
- **何を載せるかは、読者がすぐ使えるかで選ぶ。** 設定項目、回避策、注意点、数字のような、読者が自分の仕事にそのまま持ち込めるところを先に載せる。作り手の内部の実装や、読者の仕事につながらない事故の細部は、1 文に縮めるか省く
- **提案は、読者がそのまま動ける形にする。** 「見比べてみてください」「確かめておいてください」と言うなら、何で確かめるか（どのツール、どの操作）と、記事から言える答え（何が残って何が変わったか）を一緒に書く。比べるのを読者に任せない。やり方も答えも書けないなら、提案はしない
- **解釈は、記事に書かれた事実だけで成り立たせる。** 記事にない機能や前提（「自分のページを読み込めるなら」など）を足さない。多くの読者が実際に出会う場面を選ぶ。まれな場面しか思いつかないなら書かない
- **号のなかで同じ着眼点を続けない。** 「デザインとコードの両側から見る」「デザインシステムに当てはめる」がいちばん使いやすいので、何本も続きやすい。前の記事と同じ着眼点になったら、ほかの着眼点から見直す。とくに、提案の中身が同じになる（「AI に読ませるために部品のドキュメントに書き足す」を 2 本で書く、など）のは避ける
- **解釈の文の形をそろえない。** 「〜なら、〜できそうです」「〜でも、同じように〜できそうです」が何本も続きやすい。形を変える方法には、次のようなものがある。毎回推量にする必要もない
  - 減る手間を事実で言う（「〜の手間が減ります」）
  - 読者に提案する（「まず〜から取り入れると手軽です」）
  - 向かない場面と向く場面を並べる

## 経験をつくらない

「使ってみたら」「うちのチームでは」「前に困った」のような経験は書きません。ニュースレターは AI が書いているので、書けばうその経験談になります。「前のやり方と比べる」は、分野で広く行われてきた方法（scroll イベントの間引き、padding でのアスペクト比の確保など）との比較にとどめます。

## 元記事の書き手を主語にしない

「Bailey さんは〜と勧めています」「書き手は〜と考えています」のように、元記事の書き手を主語に立てません。詳細解説が元記事の話なのは読者にもわかっているので、主張の中身をそのまま書きます（「すぐには使わず、しばらく待つほうが安全です」）。名前を出すのは、記事がほかの人の意見も引いていて、誰の意見かを分けないと読み違えるときだけです。

ただし、主語を省いても、誰の話かがわからなくなってはいけません。

- **書き手の体験や測定は、誰のものかを一度示す。** エッセイや体験記、「on my laptop」で測った数字は、最初に一度「書き手の〜」「記事の計測では」「〜の体験記です」と示し、あとは省きます。
- **元記事の一人称の言葉を持ち込まない。** 「手元のノートパソコンで」「自分の仕事が」「私たちは」のような言葉を、そのまま訳して入れません。編集部の経験に読めてしまいます。

文末は、次のように使い分けます。

| 書くもの | 文末 | 例 |
|---|---|---|
| 記事に書かれた事実や結果（何をした、何がわかった） | 言い切る | 「1時間以内に直しています」 |
| 書き手の意見や見通し | 意見とわかる形 | 「AI が作るデザインはどれも似てくる、という見方です」 |
| 編集部の解釈 | 推量 | 「〜できそうです」「〜かもしれません」 |

意見を言い切ると、編集部の主張に読めてしまいます。ただし「〜という見方です」「〜という判断です」「〜という考えです」は、1 号のなかで何度も出ると、それ自体が癖になります。1 記事に 1 回までにします。ほかには次の形があります。

- 予測や見通しには、文のなかに「〜と見ています」「〜と予想しています」を入れる
- 意見の根拠になる事実を先に書き、意見は短く続ける

## 肩書きを根拠にしない

「UXエンジニアの立場で」「UXエンジニアにとって」と名乗ってから評価しません。CSS の話から Figma の話へ移るように、デザインとコードをまたぐ中身で立場を見せます。

## 手本

編集の方針を決めた UXエンジニアが公開している技術記事（note、2023 年以降が中心）から、ほかの人の技術や道具について書いた文を引いています。手本にするのは、何に目を付けて、どこまで具体的に言っているかです。個人の気持ちや願望の言い方は写さず、右の列のように編集部の言い方に直します。

| 元の文 | 目の付けどころ | ニュースレターでの言い方 |
|---|---|---|
| 画面幅を意識せずにレイアウトデザインを設計できるのはかなり楽ですね。Figmaにcontainer queryのような概念が取り入れられると、捗りそうです。 | CSS の機能を、デザインの側でどう使えるかにつなげる | 画面幅を気にせずに部品のレイアウトを決められます。Figma の側にも同じ考え方があれば、デザインとコードで組み方をそろえやすくなりそうです。 |
| 大規模なコードベース、デザインシステム、またはサードパーティのスタイルを扱う際に、頼りになりそう。まずはResetやutilityで試して!importantを減らしてみたいです。 | 使う場面と、最初にどこへ入れるか | 外部のスタイルが混ざるデザインシステムで役に立ちそうです。まず reset と utility の層で使うと、`!important` を減らせます。 |
| 従来はscrollイベントを間引いてあれこれしたり、ちょっと前はIntersection Observer APIで要素を検知したりしていましたが、それらはCSSのみで完結するかもしれません。 | 前のやり方と比べて、何の手間が減るか | （そのまま使える） |
| Code Connectはマッピングファイルの維持がけっこうしんどい。（中略）デザインシステムが成長している途中だと、この運用コストが重い。 | 保ち続ける手間と、それが重くなる場面 | マッピングのファイルは部品が増えるたびに直す必要があり、デザインシステムが育っている途中だと手間が大きくなりそうです。 |
| デザインシステムが整備されていて、コード起点で開発しているチームなら、この往復ワークフローはけっこう相性がいいんじゃないかなと思う。 | 合う場面を絞って勧める | デザインシステムが整っていて、コードを起点に作っているチームなら、この往復の流れに合いそうです。 |
| 非エンジニアがじぶんでUIを取り込む用途ならhtml.to.designのほうが手軽だと思う。 | 選ばなかった道具にも、向いている人を書く | エンジニアでない人が自分で UI を取り込むなら、html.to.design のほうが手軽です。 |
| 苦手なものを見ると、「完全なデザインファイルへの変換」ではないことがわかる。これは意図的な設計だと思う。 | 欠点を、設計の意図として読む | 苦手なことを見ると、デザインファイルへの完全な変換は最初からねらっていないようです。 |
| わかりやすいgood&badが参照できて、チェックとカイゼンのイメージが掴みやすいです。 | 勧める理由を 1 点だけ言う | よい例と悪い例が並んでいるので、どこをどう直すかがつかみやすくなっています。 |
