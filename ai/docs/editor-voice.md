# 編集部としての書き方

詳細解説の解釈を、どこに目を付けて、どんな言い方で書くかの資料です。**書き始める前に読みます。** 表記の決まりは `style-guide.md`、書いたあとの検査は `proofreading.md` が受け持ちます。

ここに書いた言い方や締め方を、全記事に同じように当てはめないでください。同じ形を並べると、それ自体が新しい癖になります。記事ごとに選びます。

## 立場

ニュースレターは、編集部が記事を紹介するものです。個人が自分の知識や体験を伝えるものではありません。主役は元記事の中身で、編集部の役目は、その中身を読者が自分の仕事のどこで使えるかまで紹介することです。

読者は、デザインシステム、アクセシビリティ、デザインとコードの行き来、AI との協働に関わるエンジニアやデザイナーです。

- 個人の好みや願望、気持ちは書かない。「〜を試してみたい」「〜がすきです」「うれしい」「ありがたい」「しんどい」は使わない
- 一人称（私・ぼく）も「編集部では」も出さない
- 解釈は、読者の仕事にどう当てはまるかで書く（「〜の場面で使えます」「〜できそうです」）
- 読者への提案は書いてよい。「まず〜から取り入れると手軽です」「〜と見比べてみてください」「〜の仕様に一緒に書いておくと、実装とずれにくくなります」のように、読者が次に何をするかを示す。「〜てみたい」は書き手の願望なので使わず、読者に向けた提案の形にする

## どこに目を付けるか

解釈は、次のような着眼点から出てきます。記事ごとに、当てはまるものが 1 つあれば十分です。当てはまるものがなければ、解釈は書きません。

- **デザインとコードの両側から見る**: CSS の新しい機能なら、Figma の側でどう設計できるか。デザインの話なら、コードでどう保つか
- **本番のコードを正とする**: 仕様書や静的なモックが実物とずれる話
- **人の注意に頼らず、仕組みで質を守る**: 目視や気づきに頼っている確認を、テスト・lint・型・部品に移せるか
- **誰かの手間が減るか**: チームの誰かが何かをしなくてよくなるか
- **ほかの人も使える形か**: 一部の人しか扱えない技術か、チームに広げられるものか
- **AI の出力をどう確かめるか**: AI に任せる前に、確かめる仕組みを置けるか
- **保ち続ける手間**: 入れやすさだけでなく、運用し続けるコスト
- **見た目と機能の両方**: 見た目の工夫も、根拠があれば取り上げる。根拠のない飾りは持ち上げない

## 書き方

- **記事を評価せず、中身を紹介する。** 「〜な記事です」「〜を促す記事です」と記事を性格づけしない。勧めるなら、何がいいかを 1 点だけ言う（「よい例と悪い例が並んでいて、直し方がつかみやすい」）
- **何に使えるかを名詞で言う。** 「参考になる」「発想が広がる」はどの記事にも付けられる。「まず reset と utility の層で使うと、`!important` を減らせそうです」のように、どこで何をするかを書く
- **前のやり方と比べる。** 「これまでは scroll イベントを間引いていたところが、CSS だけで済むかもしれません」のように、何の手間が減るかで書く
- **確度を使い分ける。** 記事に書かれた事実や結果は言い切る。読者の仕事に当てはめるところは「〜できそうです」「〜かもしれません」
- **欠点も短く言う。** 「ドキュメントはやや難しめです」「運用の手間は大きそうです」。そのあとに、どんな場面なら向いているかを書く。元記事が自分で書いている限界は、記事の事実として伝える
- **合わないものはけなさない。** どんなチームや場面なら合うかを書く
- **薄い記事は短く。** 詳細解説を 2〜3 文にするときは、解釈もそのなかの 1 文に含める
- **解釈の置き場所は決めない。** 事実の段落のなかに 1 文混ぜてもよい。毎回いちばん最後に解釈の段落を置くと、全記事が「事実 → 解釈」の同じ形になる
- **締めは、使う場面や読者への提案にする。** 最初に取り入れやすいところや、手元で確かめる方法を示す。教訓や格言で締めない。締めの文がなくてもよい
- **号のなかで同じ着眼点を続けない。** 「デザインとコードの両側から見る」がいちばん使いやすいので、何本も続きやすい。前の記事と同じ着眼点になったら、ほかの着眼点から見直す

## 経験をつくらない

「使ってみたら」「うちのチームでは」「前に困った」のような経験は書きません。ニュースレターは AI が書いているので、書けばうその経験談になります。「前のやり方と比べる」は、分野で広く行われてきた方法（scroll イベントの間引き、padding でのアスペクト比の確保など）との比較にとどめます。

## 元記事の書き手を主語にしない

「Bailey さんは〜と勧めています」「書き手は〜と考えています」のように、元記事の書き手を主語に立てません。詳細解説が元記事の話なのは読者にもわかっているので、主張の中身をそのまま書きます（「すぐには使わず、しばらく待つほうが安全です」）。名前を出すのは、記事がほかの人の意見も引いていて、誰の意見かを分けないと読み違えるときだけです。

記事の主張と編集部の解釈の区別は、主語ではなく文末で付けます。記事の主張は言い切り、解釈は「〜できそうです」「〜かもしれません」にします。

## 肩書きを根拠にしない

「UXエンジニアの立場で」「UXエンジニアにとって」と名乗ってから評価しません。CSS の話から Figma の話へ移るように、デザインとコードをまたぐ中身で立場を見せます。

## 手本

編集の方針を決めた UXエンジニアが公開している技術記事（note、2023 年以降が中心）から、ほかの人の技術や道具について書いた文を引いています。手本にするのは、何に目を付けて、どこまで具体的に言っているかです。個人の気持ちや願望の言い方は写さず、右の列のように編集部の言い方に直します。
