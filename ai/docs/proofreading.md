# ニュースレターの校正手順

書き上げたニュースレターを保存したあと、コミットの前にこの手順で読み直して直す。`/create-newsletter` と `/create-newsletter-auto` の両方で行う。

書いた本人が読み直すと、書いたときの意図で読んでしまい、癖や不自然さに気づきにくい。そのため読み直しは、書いた経緯を知らないサブエージェントに任せる。サブエージェントを使わずに校正を済ませてはいけない。

## 1. 機械チェック

```bash
scripts/check-newsletter-style.sh "$NEWSLETTER_FILE"
```

癖になりやすい表現を数え、1号あたりの上限を超えたものを `NG` として該当行と一緒に出す。上限は、2026年10〜11月の号で数えた回数をもとに決めた（たとえば「〜のは、〜です」は1号に6〜17回、「UXエンジニアの視点で／にとって」は5〜15回出ていた）。

この出力は 2 のサブエージェントに渡す。

## 2. サブエージェントによる読み直し

Agent ツール（`subagent_type: general-purpose`）で、次の2つを**並行して**起動する。どちらにも、記事の選び方や書いたときの考えは渡さない。渡すのはファイルのパスと読むべきガイドだけにする。サブエージェントはファイルを編集せず、指摘を返すだけにする。

### A. 文の校正

```
newsletters/<ファイル名>.md はUXエンジニア向けの日刊ニュースレターです。
書いた経緯は知らない読み手として、文の自然さを校正してください。ファイルは編集せず、指摘だけを返してください。

先に ai/docs/style-guide.md を全部読んでください。とくに「7. 自然な日本語で書く」を基準にします。

見るところ:
1. 英語を直訳したような文（「〜のは、〜です」、物や記事が主語の文、「〜を促す」「〜を持つ」「〜にとって」、「A ではなく B」の言い切り、抽象名詞の主語など）
2. 意味のぼやけた評価の言葉（納得感、示唆、価値を上げる など）、格言めいた締めの一文
3. スタイルガイドの NG ワード、漢字の開き、冗長な表現
4. 書き手の経験をつくっている文（「使ってみたら」「ぼくのチームでは」、一人称）。ai/docs/editor-voice.md の「経験をつくらない」を基準にします
5. 下の機械チェックで上限を超えた表現。どれを残し、どれを言い換えるかまで決めてください

機械チェックの結果:
<scripts/check-newsletter-style.sh の出力を貼る>

返し方: 記事の見出しごとに「原文 / 何が問題か / 書き換え案」を並べてください。
書き換え案で事実・数字・固有名詞・リンクを変えないこと。元記事に書いていないことを足さないこと。
問題がない文は挙げなくてかまいません。
```

### B. 読み物としての通読

```
newsletters/<ファイル名>.md はUXエンジニア向けの日刊ニュースレターです。
毎日これを受け取っている読者のつもりで、号を最初から最後まで通して読み、読み物として続けて読めるかを評価してください。ファイルは編集せず、指摘だけを返してください。

先に ai/docs/style-guide.md の「8. 毎号続けて読まれる読み物として」と、ai/docs/editor-voice.md を読んでください。

見るところ:
1. 記事どうしで書き出しや締めの型が同じになっていないか（同じ型の箇所をすべて挙げる）
2. 全記事が同じ構成をなぞっていないか
3. 書き出しの1〜2文で何の記事かわかるか
4. 3行まとめの言い換えや一般論で字数を埋めている段落がないか（削ってよい段落を挙げる）。元記事が短い記事は、詳細解説が3行まとめにない情報だけになっているか
5. 感想・私見の文（「おもしろい」「参考になる」「〜として使える記事です」など）で、どの場面で何に使えるかまで書いていないもの。削る前提で挙げる。残す感想は editor-voice.md の書き方（中身について書く、名詞で言う、確度の使い分け）になっているか
6. 褒め言葉や「UXエンジニアの視点では」のような前置きが繰り返されていないか。感想が号のなかで同じ関心（editor-voice.md の「感想の出どころ」）ばかりになっていないか
7. 途中で読むのをやめたくなる箇所があれば、どこで、なぜか

比較のため、前の号を1つ（newsletters/ のなかでこのファイルの直前のもの）も読み、号をまたいで同じ型が続いていないかも見てください。

返し方: 号全体の所見を3〜5行で書いたあと、直す箇所を記事の見出しごとに「箇所 / 何が問題か / 直し方」で並べてください。
直し方で事実・数字・固有名詞・リンクを変えないこと。
```

## 3. 反映

2つの指摘をまとめて、メインのエージェントがファイルを直す。

- 指摘は原則すべて反映する。採らないのは、書き換えで意味が変わる・事実と合わなくなる場合だけ
- 書き換えるときも、事実・数字・固有名詞・リンクは変えない。迷ったら元記事（`articles/` の Markdown）を開いて確かめる
- A と B の指摘が同じ箇所でぶつかったら、B（号全体の読みやすさ）の方針に合わせて、A の基準を満たす文にする

## 4. 再チェック

```bash
scripts/check-newsletter-style.sh "$NEWSLETTER_FILE"
```

`NG` が残っていたら言い換えて、すべて `OK` になるまで繰り返す。

## 5. 報告

完了報告に、A・B それぞれの指摘の数、反映した数、採らなかった指摘とその理由を書く。
