# 文体・表記スタイルガイド

このドキュメントは、AI生成文章（ニュースレター、記事キュレーション、要約など）における文体・表記ルールを定義します。

## 基本姿勢

- **柔らかく、自然体で** - 硬い言葉や気取った表現は避ける
- **押しつけない** - 読者に判断を委ね、煽らない
- **誠実に、等身大で** - 大げさに盛らない、賢く見せようとしない

## 2. トーンの使い分け・文脈に応じた表現

文脈と組み合わせる言葉によって、適切な表現を選ぶ。

### 肯定的な形容

| 表現 | 使う場面 | 例 |
|------|----------|-----|
| 優れた | 堅い名詞と組み合わせる | 優れたUX、優れた組織、優れた設計 |
| いい | 柔らかい名詞と組み合わせる | いい雰囲気、いい温度感、いいバランス |
| すごい・すばらしい・最高 | 編集部コメントなど口語調パート | 「これはすごい」「すばらしい記事」 |

※ 本文では「すごい」「最高」などカジュアルな表現は避ける。ニュースレターの感想・私見は「優れた」「効果的な」より、`editor-voice.md` の気持ちの言葉（楽、ありがたい、すき）を先に考える

## 3. 文体ルール

### 基本スタイル

- **文末**: 「です・ます」調（敬体）を基本とする
- **トーン**: 親しみやすく、専門的すぎない
- **主語**: 「私」「私たち」「筆者」「著者」は使わない。文脈で理解できる主語は省略する
- **元記事の書き手も主語にしない**: 「Bailey さんは〜と勧めています」「書き手は〜と考えています」と書かず、主張の中身をそのまま書く。詳細解説は元記事の話だと読者はわかっている。英語の記事は He argues / She recommends と書き手を主語に立てるので、そのまま訳すと同じ主語が何度も出る。名前を出すのは、記事がほかの人の意見も引いていて、誰の意見かを分けないと読み違えるときだけ

### 語尾のバリエーション

単調な文章を避けるため、語尾を適度に変化させる。

```
✅ 良い例:
- 〜です。
- 〜ます。
- 〜でしょう。
- 〜かもしれません。
- 〜ですね。
- 〜になります。
- 〜といえます。

❌ 避ける:
- 同じ語尾が3回以上連続
```

### 一文の長さ

- 一文は **60〜80文字程度** を目安に
- 長くなる場合は文を分割する

### 段落構成

- 一段落は **2〜4文** を目安に
- 話題が変わるときは段落を分ける

## 4. 用語・表記統一

### 記号・句読点

| 用途 | 使用する | 使用しない |
|------|----------|------------|
| 句点 | 。 | ．（ピリオド） |
| 読点 | 、 | ，（カンマ） |
| 括弧 | 「」（引用・強調） | ""（ダブルクォート） |
| 括弧 | （）（補足） | ()（半角） |
| 三点リーダー | …（1文字） | ...（ピリオド3つ） |
| 中黒 | ・ | ･（半角） |
| ダッシュ | ー（長音） | −（マイナス） |

### 数字

- 桁数の多い数字: **半角数字 + カンマ区切り**（例: 1,000人）
- 日付: **YYYY/MM/DD**
- 時刻: **HH:MM**（24時間表記）
- 割合: **〇〇%**（半角）

## 5. NGワード・禁止表現

### 絶対に使わない表現

| NGワード | 理由 | 代替表現 |
|----------|------|----------|
| 「革命的」「画期的」 | 大げさ・陳腐 | 「新しいアプローチ」「注目の手法」 |
| 「爆速」「爆上げ」 | カジュアルすぎる | 「高速」「大幅に向上」 |
| 「神」「最強」 | カジュアルすぎる | 「優れた」「強力な」 |
| 「ぶっちゃけ」 | 口語的すぎる | 「実際のところ」「正直なところ」 |
| 「めっちゃ」 | 口語的すぎる | 「非常に」「とても」 |
| 「いわゆる」の多用 | 冗長 | 必要なときのみ使用 |
| 「基本的に」の多用 | 冗長 | 削除するか具体化 |
| 「必見」 | 煽り・押しつけがましい | 「注目」「おすすめ」「参考になる」 |
| 「劇的」 | 大げさ・広告的 | 「大きく」「明確に」 |
| 「核心」 | 硬い・仰々しい | 「ポイント」 |
| 「特筆」 | 硬い・堅苦しい | 「とくに」「際立つ」 |
| 「懸念」 | 硬い・ネガティブ | 「課題」「気になる点」 |
| 「執着」 | 強すぎる・ネガティブ | 「こだわり」「重視」 |
| 「慧眼」 | 気取っている・硬い | 「鋭い視点」「よく見ている」 |
| 「注目すべき」 | 押しつけがましい | 「注目の」「興味深い」 |
| 「劣悪」 | 強すぎる・ネガティブ | 「良くない」「問題がある」 |
| 「〜すべき」 | 押しつけがましい・ネット民的 | 「〜するとよい」「〜がおすすめ」 |
| 「版」（「新しい版」「ベータ版」「音声版」など） | 硬い・耳で聞くと伝わりにくい | 「バージョン」（「新しいバージョン」「ベータバージョン」） |

### 避けなければいけない表現

| 避ける表現 | 理由 | 代替表現 |
|------------|------|----------|
| 「〜することができます」 | 冗長 | 「〜できます」 |
| 「〜を行う」 | 冗長 | 動詞に置き換え（「実行する」「作成する」） |
| 「〜という形になります」 | 冗長 | 「〜になります」「〜です」 |
| 「〜させていただきます」 | 過剰敬語 | 「〜します」「〜いたします」 |
| 「〜の方」（不要な場合） | 冗長 | 削除 |
| 「現時点では」 | 冗長な場合が多い | 「現在」「今は」 |
| 二重敬語 | 不自然 | 適切な敬語に |

### 注意が必要な表現

| 表現 | 注意点 |
|------|--------|
| 「簡単」「容易」 | 読者によっては難しい場合も。「比較的」を付けるか具体化 |
| 「誰でも」「すべての人」 | 実際には例外がある場合が多い |
| 「必ず」「絶対に」 | 例外がある場合は避ける |
| 「最新」 | 公開時点では最新でも、すぐ古くなる可能性 |
| 「完全」「完璧」 | 実際には制限がある場合が多い |

## 6. 文章構成のガイドライン

### 導入文

- 記事の概要や読むメリットを簡潔に示す
- 2〜3文程度で完結させる

### 本文

- 見出しを適切に使い、構造を明確にする
- 箇条書きを活用して可読性を高める
- コードや具体例を交えて説明する

### 結び

- 記事のポイントを簡潔にまとめる
- 次のアクションや関連情報への誘導を含める

## 7. 自然な日本語で書く（直訳調を避ける）

元記事の多くは英語です。英語の文の組み立てをそのまま日本語に移すと、意味は通じても硬く、読みにくい文になります。日本語の文として書き直し、声に出して読んで引っかからないかを確かめます。

| 直訳調の形 | 例（実際に出た文） | 書き直しの例 |
|------------|------------------|--------------|
| 「〜のは、〜です」（What's X is Y） | UXエンジニアの立場で参考になるのは、後半のテストの書き方です。 | 後半のテストの書き方は、手元のプロジェクトでもそのまま試せます。 |
| 物や記事が主語になって何かをする | 測り方の失敗を隠さずに書いている点も、この記事の価値を上げています。 | 測り方の失敗も隠さずに書いているので、結果を信用しやすくなっています。 |
| 抽象名詞を主語にする | この記事のいちばんの視点は、スキルの使い手が2種類いるという指摘です。 | スキルの使い手は2種類います。 |
| 元記事の書き手を主語にする（He argues / She recommends） | CSS のレイアウトについて多くの記事を書いてきた Ahmad Shadeed さんは、それだけでは足りないと指摘します。 | でも、それだけでは足りません。 |
| 〃 | この記事の書き手はその処理を飛ばして、フォント自体に区切りを判定させました。 | ここではその処理を飛ばして、フォント自体に区切りを判定させています。 |
| 「〜を促す」「〜を可能にする」「〜を提供する」 | 視点の切り替えを促す記事です。 | 新しい手法の話というより、ものの見方の話です。 |
| 「〜を持つ」（have） | 必要以上の権限を持つキー | 必要以上の権限があるキー |
| 「〜にとって」（for） | UXエンジニアにとって身近なものです。 | UXエンジニアもよく出会う課題です。 |
| 「A ではなく B」で言い切る（not A but B） | 仕様書は「品質を上げる道具」ではなく「ブレを消す道具」だ | 仕様書の役目は、品質を上げることより、出力のブレをなくすことにある |
| 「〜することで」「〜によって」の連鎖 | 〜することで〜が可能になり、それによって〜 | 文を分ける。「〜すると〜できます。そのため〜」 |

あわせて次のことを守ります。

- 英語の単語を辞書どおりの訳語に置き換えて終わりにしない。「insight」を「洞察」、「takeaway」を「学び」と機械的に訳さず、何がわかったのかを普通の言葉で書く
- 「納得感がある」「示唆に富む」「価値を上げる」のような、意味のぼやけた評価の言葉を使わない。何がどうよいのかを書く
- 格言めいた一文で段落を締めない（「揺れないほうが怖い」「AI はまだ道具にすぎない」など）
- カタカナ語は、日本語の言葉で言えるなら日本語にする。製品名・技術用語・定着した語（UI、API、コンポーネントなど）はそのままでよい

## 8. 毎号続けて読まれる読み物として

ニュースレターは同じ読者が毎日のように受け取ります。1本ずつはよく書けていても、同じ型が続くと読み飛ばされます。

- **書き出しで何の記事かわかるようにする**: 最初の1〜2文で、何についての記事かを伝える（誰が書いたかは出典の行にある）。「記事は〜から始まります」で毎回始めない
- **締めを型にしない**: 「UXエンジニアの視点では、〜という指摘が参考になります」のような決まった締めを置かない。言うことがなければ締めの段落は要らない。実務での使い道を書くなら、どの場面で何に使えるかを具体的に書く
- **構成を記事に合わせる**: 「背景 → 仕組み → おもしろい点 → UXエンジニアの視点 → 限界」を全記事でなぞらない。調査記事なら結果から、ツール紹介なら使い方から、と記事の性質で変える
- **感想・私見は、具体的に言えるときだけ書く**: 解説の中心は記事の中身（何をして、何がわかり、何を主張しているか）。「おもしろい」「参考になる」「〜のきっかけになる」「〜として使える記事です」のような感想は、それだけでは読者に何も足さない。書くなら、どんな場面で何をするときに記事のどの部分が使えるかまで書く。そこまで言えないなら書かない。UXエンジニアの仕事へのつなげ方も同じで、「ユーザー体験の向上につながる」のような一般論なら書かない
- **長さは中身に合わせる**: 中身の薄い記事は短くてよい。字数を埋めるために要約の言い換えや一般論を足さない。元記事が短く、3行まとめでほぼ言い尽くせる記事は、詳細解説を3行まとめにない情報だけの2〜3文にとどめる
- **持ち上げすぎない**: 「ていねい」「具体的」「正直に」「実用的」のような褒め言葉を号のなかで繰り返さない。褒めるなら、何がどうよいかを書く
- **段落の頭に褒め言葉を置かない**: 「実験の組み方がていねいです。」「事例の紹介も具体的です。」のように評価を1文置いてから中身に入らず、中身から書き始める
- **山場を予告しない**: 「いちばんおもしろいのは〜」「この記事のいちばんの視点は〜」と前置きせず、その結果や主張をそのまま書く
- **最後の1文で記事の読み方を決めない**: 「チェックリストとして使える記事です」「読み物として楽しむのがよいでしょう」で毎回締めない。事実や記事の主張で段落を終えてよい
- **「限界がある。それでも〜」で救わない**: 「使う場面は限られるでしょう。それでも〜発想が広がります」のように、弱い記事を一般論で持ち上げて締めない。短い記事は短く書く
- **前の号と同じ文を使わない**: 似た記事が続く日は、書き出しや締めが前の号と同じ文になりやすい。前の号の同じ種類の記事と見比べる
- **3行まとめと詳細解説で同じことを言わない**: 詳細解説は3行まとめの言い換えではなく、まとめに入らなかった中身と解釈を書く
