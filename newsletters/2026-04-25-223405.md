### [The end of responsive images](https://piccalil.li/blog/the-end-of-responsive-images/?ref=main-rss-feed)

> **出典**: Piccalilli | **公開日**: 2026-04-23 | **カテゴリ**: css

**3行まとめ**
- 14年間悩まされてきた `sizes` 属性の手書き問題が、ようやく決着しつつあります。
- Gecko・WebKit・Blink すべてで `sizes="auto"` がサポートされ、`loading="lazy"` と組み合わせれば描画後のレイアウト情報を使ってブラウザーが自動でソース選択できるようになりました。
- 著者の Mat Marquis は元 RICG（レスポンシブ画像コミュニティグループ）のチェアで、自ら推進した仕様の負債を、自身の手で解消しに来た格好です。

**詳細解説**

レスポンシブ画像の苦労を一度でも味わったことがあれば、`sizes` 属性のしんどさは身に染みているはずです。`(min-width: 1340px) 257px, (min-width: 1040px) calc(24.64vw - 68px), …` のような呪文をブレイクポイントごとに手で組み立てるあの感覚です。Mat はこの記事で、「`srcset` と `sizes` を記述的構文として標準化したのは正しかったが、`sizes` だけは最後まで好きになれなかった」と告白しています。

`sizes` がつらいのは、ビルド時点ではレイアウトが分からないという根本制約のせいでした。レイアウトを実測しないと値が決まらないのに、HTML 属性として手書きする必要があった、というねじれ構造です。今回追加された `auto` 値は、この前提を `loading="lazy"` の存在で覆します。遅延読み込みされる画像はビューポートに入る瞬間にリクエストが走るので、その時点ではレンダリング後のサイズが分かっており、ブラウザーが自前で最適なソースを選べる、というシンプルな発想です。

UXエンジニアリングの観点で重要なのは、ここで「制御を諦めた方が良い」という判断が改めて肯定されたことだと思います。接続速度や端末特性まで含めた最適化は、開発者ごとに方針が割れると最終的に損をするのはユーザーです。ブラウザーに丸投げすることでサイトをまたいだ一貫性が生まれ、ユーザーの体験が個別最適化の犠牲にならずに済みます。一方で LCP 候補となるヒーロー画像など、`loading="lazy"` を付けたくないケースでは引き続き手書きの `sizes` が必要なので、完全な置き換えではない点には注意が必要です。

WordPress はすでに `auto` への移行を進めており、CMS や静的サイトジェネレーターを使っている場合はテンプレートに `sizes="auto, ..."` を仕込むだけで恩恵を受けられます。サポート外のブラウザーは `auto,` の部分を黙って捨ててくれるので、リスクなく今日から導入できます。

### [fetchのキャンセルだけじゃない！　AbortSignalで実現するクリーンなJS非同期処理](https://ics.media/entry/260423/)

> **出典**: ICS MEDIA | **公開日**: 2026-04-22 | **カテゴリ**: frontend

**3行まとめ**
- `AbortSignal` は `fetch` のキャンセル専用ではなく、非同期処理全般のクリーンアップを統一的に扱うための仕組みです。
- `addEventListener` の `signal` オプションや `AbortSignal.any()`・`AbortSignal.timeout()` を組み合わせると、レースコンディション対策やタイムアウトを宣言的に書けます。
- 自作の非同期関数も `signal` を受け付ける形にしておくと、標準 API と同じ片付け方法に乗せられて運用が楽になります。

**詳細解説**

`AbortController` は知っていても、その応用範囲を最大限に活かしているチームは意外と少ない印象です。記事では `fetch` のキャンセルから始めて、インクリメンタルサーチでよくあるレースコンディションをひとつの `signal` で解消するパターン、`AbortSignal.any()` で「ユーザー操作・タイムアウト・コンポーネントのアンマウント」を1つにまとめるパターンまで、実務にそのまま使える書き方が紹介されています。

とくに価値が高いのは、React の `useEffect` でのクリーンアップを `controller.abort()` 一発に統一する例です。複数の `addEventListener` と `fetch` をすべて同じ `signal` に紐付けておけば、コンポーネントのライフサイクルと `AbortSignal` のライフサイクルを1対1で対応させられます。`removeEventListener` への参照ズレや解除漏れといった、地味だが厄介なバグの温床を構造的に消せる設計です。

UXエンジニアリングの視点では、「ユーザー操作のキャンセル可能性をプロダクト全体で一貫して扱えるか」が大きな差別化になりつつあります。タブ切り替え時の古いリクエストが新しい画面を上書きする問題は、UXの不快感を生む典型例です。`AbortSignal` を共通の合言葉にすることで、フロントエンド全体のクリーンアップ戦略をひとつに揃えられます。AIエージェントとの連携が増える時代には、長時間動く処理を外から止められる設計が一層重要になるはずなので、自作ライブラリを設計するときは独自のキャンセル方式を再発明せず、`signal` を受け取るインターフェースを基本にしておくとよいでしょう。

`AbortSignal.any()` と `AbortSignal.timeout()` のみ Baseline 2024 Newly available（Safari 17.4 以降）である点だけ、互換性の制約として頭に入れておくと安心です。

### [A reimagining of JSX from a React core alum](https://react.statuscode.com/issues/471)

> **出典**: React Status | **公開日**: 2026-04-24 | **カテゴリ**: frontend

**3行まとめ**
- React の元コアメンバー Dominic Gannaway による TSRX という言語拡張が話題で、JSX の精神的後継を名乗っています。
- TSRX は React・Preact・Solid・Ripple へコンパイルでき、制御フロー、スコープ付きスタイル、ローカル変数を言語レベルで持ちます。
- React Miami 開催中の React Status 号では、TSRX のほかに Rspack 2.0、TypeScript 7.0 Beta、Expo の Series B など、エコシステム全体の地殻変動が一気に並んでいます。

**詳細解説**

JSX は React の象徴ですが、ループや条件分岐を JavaScript の式で書くアプローチには限界もありました。TSRX は宣言的 UI のための TypeScript 言語拡張として、その不満を真正面から扱おうとしている試みです。React 公式というより React 出身者の挑戦で、複数フレームワークへのコンパイル先を持つ点が特徴的です。

UXエンジニアリングの視点で見ると、この種の言語拡張は「フレームワーク横断のコンポーネント記述」を実現するための布石でもあります。同じソースから React と Solid と Preact 向けの実装を吐ける構造は、デザインシステムの実装コストを抑えるうえで魅力的です。一方で言語拡張は学習コストと長期保守の負担も大きいので、TSRX が JSX のように普及するかは、エコシステム側のサポートと実プロダクトでの採用例次第になります。

同号で取り上げられている Mark Erikson のスライド「A Guide to React Compiler Rendering」も、React Compiler の挙動を体系的に整理した資料として参考になります。Rspack 2.0 が RSC をサポートしたこと、TypeScript 7.0 Beta（Go 製ネイティブ実装、コンパイル10倍）の登場、Expo が Series B で4,500万ドル調達した話と合わせて、React 周辺のツールチェーンが今年大きく塗り替わる予感があります。短いリンク集ですが、UXエンジニアが追っておきたい変化が一気にまとめて確認できる構成です。

### [Attention Engineering: Why Users Ignore Even the Most Important Elements](https://uxmag.com/articles/attention-engineering-why-users-ignore-even-the-most-important-elements)

> **出典**: UX Magazine | **公開日**: 2026-04-23 | **カテゴリ**: ux-research

**3行まとめ**
- ユーザーが大切な要素を見落とすのは怠慢ではなく、脳が情報の95%を意識前にフィルタリングしているからだ、という前提から議論が始まります。
- 注意は認知・視覚・行動・感情の4つの層から成り、ひとつでも設計とずれると注意は崩壊する、という見立てです。
- 大切なのはコントラストやサイズではなく、ユーザーの目的・メンタルモデル・習慣・感情と整合させる設計、という結論です。

**詳細解説**

「重要な要素なのに、なぜか見られない」という現象は、UI改修の現場でよく遭遇します。著者の Tushar Deshmukh はこれを Attention Engineering（注意工学）と呼び、注意を「スポットライト」ではなく「ゲートキーパー」として捉え直すよう主張します。脳は意味・安全・期待・関連性を瞬時に判定し、それに合わないものは意識に上る前に弾く、という構造です。

実例も示唆に富んでいます。健康診断ポータルで「Confirm Appointment」ボタンが画面上部にあったのに、ユーザーがスクロールして「確認ボタンが無い」と言い張るケースは、メンタルモデル（最終操作はページ下部にある）が視覚情報を打ち消した典型です。E コマースの「Size Guide」を完全にスルーするのも、その位置のテキストは些末なものという過去の習慣が働いた結果だと整理しています。

UXエンジニアリングの観点で重要なのは、「コントラスト調整やコピー書き直しは症状対処にすぎない」という指摘です。本当に効くのは、ユーザーが認知的に進みたい流れに沿った構造を作ること、不安を抱えている瞬間に余計な情報を増やさないこと、そして習慣を上書きしようとせず尊重することです。フロントエンド側でA/Bテストを回すときも、変数を「色やサイズ」だけでなく「文脈との整合性」「タイミング」「直前の感情負荷」まで広げると、より本質的な学びが得られるはずです。

「Users see what they need, not what you want them to see.」という Jakob Nielsen の引用が記事を貫いています。ユーザー心理シリーズの第5回として、設計の前提そのものを問い直す内容になっています。

### [Why Research also needs to research itself](https://medium.com/researchops-community/why-research-also-needs-to-research-itself-b70fe1ee7c8e)

**3行まとめ**
- メタリサーチ（リサーチ自体を対象とするリサーチ）は科学の世界では定着しつつあるのに、企業のユーザーリサーチではまだ十分扱われていない、という問題提起です。
- 「いつもこのやり方だから」で手法が固定化すると、リサーチは探索ツールから単なるプロトコルへ後退してしまいます。
- AI が分析を加速する時代だからこそ、方法そのものを継続的に見直す批判的な羅針盤としてメタリサーチが必要だ、と著者は主張しています。

**詳細解説**

著者の Alessandra Gomiero は2018年から各業界の定性調査に関わってきたリサーチャーです。彼女が一貫して感じてきたのは「方法の結晶化」、つまり問題から手法を選ぶのではなく、すでに馴染んだ手法に問題を押し込める文化への違和感です。定性のほうが深い洞察を得られる場面でも、ダッシュボードと数値が要求される――この構造の根本にあるのは、技術的というより文化的な抵抗だ、と整理されています。

メタリサーチが提供するのは、リサーチを「固定されたプロトコル」ではなく「学習と進化の対象」として扱う姿勢です。製品・ユーザー・市場が変わり続けているのに、研究方法だけが10年前のまま固定されていれば、得られるエビデンスの質も劣化していきます。記事はリサーチプロジェクトの最後に「lessons-learned」を儀式化することを提案します。これはバイアスや前提を文書化し、組織のナレッジとして蓄積する装置です。

UXエンジニアリングの観点では、この発想はリサーチに限らず、デザインシステムや実装のレトロスペクティブにも応用できます。コンポーネントの設計判断、計測の取り方、ユーザビリティテストの設計まで、自分たちの方法そのものを定期的に検査する仕組みを持っているか――そう問い直すための補助線になります。AI が高速にデータを比較・要約できる時代だからこそ、「どの問いを立てるか」「何を信頼するか」という判断は人間に残ります。メタリサーチはその判断を下すための足場を与える、と捉えると腑に落ちます。

「データが豊富で信頼が乏しい世界では、信頼には方法、記憶、継続的な見直しが要る」という締めの一文が、記事全体を象徴しています。

### [10 Guidelines for Designing Your Site’s AI Chatbots](https://www.nngroup.com/articles/ai-chatbots-design-guidelines/)

> **出典**: Nielsen Norman Group | **公開日**: 2026-04-24 | **カテゴリ**: design

**3行まとめ**
- NN/g がサイト固有の AI チャットボットを実ユーザー観察し、10個の実践的ガイドラインに整理しました。
- 「複数のチャットを並列させない」「全ページで使えるようにする」「できることを冒頭で示す」「サジェスト質問はテキストではなくボタンで出す」など、設計判断のチェックリストとして直接使えます。
- ストリーミング応答の自動スクロール、画像なしの推薦、共有・保存できない会話など、よく見る悪手も具体例で批判されています。

**詳細解説**

NN/g らしく、Home Depot の Magic Apron と Live Chat が併存して混乱を生んでいる例、Williams Sonoma の AI Sous Chef がページを横断して追従する良例、Amazon の Rufus が見ているページを認識して提案を変える例など、実プロダクトのスクリーンショット付きで議論されています。とくに第1ガイドライン「複数のチャットを統合する」は、社内のシステム構成をユーザーに理解させてはいけない、というシンプルな原則の再確認として効きます。

第3ガイドラインの「できることを示す」は、AIプロダクトでよく抜け落ちる視点です。「Ask me anything」は一見親切ですが、実際にはチャットボットの能力を超えた期待を生み、失敗体験を量産します。Magic Apron が閲覧履歴を記憶できるのに、UI 上はその能力を一切示していなかったため、ユーザーが商品名をコピペしてしまう例は印象的です。「能力を持っているだけでは不十分で、その能力を使えると気づかせる UI が必要」という、UXエンジニアリング的な原則の好例です。

第6・第7ガイドラインの「プログレッシブディスクロージャー」と「自動スクロールしない」も実装に直結します。ストリーミング中に勝手に末尾まで飛ばすチャットボットは、読み始めた瞬間にユーザーを置き去りにします。新しいメッセージが来ても、ユーザーのスクロール位置はメッセージの先頭で止めるべきだ、という指針は実装側で確実に反映できます。

AI チャットボットを「サイトの一部」として設計するとき、機能の派手さより「複数チャネルとの整合」「文脈の保持」「能力の可視化」「画面操作との親和性」のほうが体験を左右します。今後ボイス入力や保存・共有機能まで含めて設計する際の、共通言語として参照できる文書です。

### [Why User Panels Fail](https://www.nngroup.com/articles/user-panels-fail/)

> **出典**: Nielsen Norman Group | **公開日**: 2026-04-24 | **カテゴリ**: design

**3行まとめ**
- 自社のユーザーパネルは時間とともに3つの典型パターンで劣化する、と整理した記事です。
- データの陳腐化（静的データベース化）、サンプリングバイアス（ロイヤルユーザーへの偏り）、事業現実からの乖離（成長した事業に追随しないパネル構成）が3大要因です。
- 健全なパネルは「資産」ではなく「継続運用するシステム」として、責任者・更新頻度・バランス監査をルール化する必要があります。

**詳細解説**

社内パネルは立ち上げ時こそ「これで募集の悩みから解放される」と歓迎されますが、半年経つとリクルート効率が下がり、外部リクルートで補わざるを得なくなる――この「ゆっくりとした崩壊」を、NN/g は3つの構造的失敗として明文化しました。第1の Static-Database 問題は、データが更新されないまま蓄積されていくことでの劣化、第2の Panel-Sampling Bias はブランド愛着の高い人ばかりが集まることで生まれるエコーチェンバー、第3の Deviation from Business Realities は事業が広がってもパネルが旧来の顧客構成のまま残るギャップです。

UXエンジニアリングの視点だと、これは検索インデックスや A/B テストの対象セグメントの劣化と同じ構造に見えます。仕組みを作って終わりではなく、四半期ごとの監査・参加履歴のトラッキング・接触頻度の上限設定など、運用ガバナンスがあって初めて意味を持ちます。記事の最後にある「Self-Diagnose Your Panel」表は、症状（応答率の低下、フィードバックの均質化、要件に合う参加者が見つからない）から原因へ素早く戻れる導線として実用的です。

「パネルがあること自体は成熟の指標ではない。運用の規律こそが成熟だ」という締めの一文が刺さります。リサーチ運用を社内システムとして設計するとき、ジョブを誰が持ち、どの周期で何を確認するかを必ず仕様に含めるべきだという話です。

### [GPT image gen prompting guide](https://developers.openai.com/cookbook/examples/multimodal/image-gen-models-prompting-guide)

> **出典**: Sidebar 経由（OpenAI Developers Cookbook） | **公開日**: 2026-04-23 | **カテゴリ**: design

**3行まとめ**
- OpenAI 公式の `gpt-image-2` 用プロンプトガイドで、生成・編集の現場で使えるパターンが体系化されています。
- プロンプトは「背景・主体・詳細・制約」の順、テキストは引用符かオールキャップス、人物編集は「変えない部分」を明示するなど、実用的な指針が並びます。
- 編集系では preserve リストを毎イテレーションで再宣言する、style 転送・try-on・コンポジット・天候差し替えなど用途別のテンプレが用意されています。

**詳細解説**

`gpt-image-2` は `outputQuality` の low/medium/high で速度と品質をトレードオフでき、最大3,840px・8,294,400ピクセルまでの自由な解像度を扱えます。低クオリティでも従来モデルより上の品質が出るので、バッチ生成や試作には `low` を、テキスト多用やポートレートには `medium` 以上を、というガイドラインが明確に書かれています。

UXエンジニアリングの観点で参考になるのは、「プロンプトを仕様書として扱う」発想です。マーケ用クリエイティブやプロダクトのモックアップ、教育コンテンツ、コミック、ロゴ、ピッチデックスライドなど、用途ごとに「ブランドの位置付け」「ターゲット」「コピーの正確な文言」「許容しない要素」をまとめて渡す書き方が紹介されています。とくに編集ワークフローでは「change only X / keep everything else the same」と invariant を毎回繰り返す方針が示されており、ドリフトを抑えるテクニックとしてそのまま使えます。

文字を入れたい場合は引用符かオールキャップスで囲い、ブランド名のような難しい単語は1文字ずつ書く、長文プロンプトより短い base prompt + 単一変更のリファインを重ねる、複数画像入力は「Image 1: …」とインデックスで参照する、といった注意点も実務向けです。Virtual try-on や Sketch-to-render、コンポジット、季節差し替えなどのテンプレを社内のデザインオペレーションに組み込めば、AI を使ったビジュアル制作のばらつきを抑えられます。

公式の Cookbook 形式で Python サンプル付きなので、自社のデザインパイプラインに統合する際の起点として最適です。

- フロントエンドは犠牲財ではなく、ブランドや雰囲気を伝える役割が一層重要になる、という見立てです。

**詳細解説**

MCP に加え、Google Workspace CLI、Obsidian CLI、Salesforce CLI、コードベースから自動で CLI を生成する CLI-Anything など、AI に渡す前提のコマンドラインツールが急増しています。Webb の主張は、「AI が叩くなら API より CLI のほうが向く」というシンプルな事実認識から始まります。CLI はユーザーの PC 上で他ツールと組み合わせやすく、セキュリティ的にも UI を持たないぶん攻撃面が狭い、というメリットが整理されています。

UXエンジニアリングの観点で響くのは、「ユーザージャーニー設計の限界」をはっきり言語化している点です。ユーザーは ホテル検索→予約→滞在→レビュー という直線では生きていない。家族グループに送り、2日後に戻ってきて、別アプリで補足を取る、という非線形な動きをします。CLI の組み合わせ可能性はその現実に合っており、Airbnb の検索結果を WhatsApp に投げる、Notion で確認しながら Obsidian で書く、という流れが摩擦なく繋がります。

ではフロントエンドはどうなるか。Webb は「使い勝手の最適化」という従来の主軸から、「ブランドと vibe を伝える」役割へ重心が移る、と予想します。ユーザーは初回だけアプリを触り、以後はパーソナル AI に橋渡しするだけ、というシナリオです。つまりトップページは「AI に伝えるための名刺」になります。エージェント時代の権限管理、隣接サービスへの誘導（バンク連携の例が示されています）など、まだ未解決の論点も提示されており、近未来のサービス設計を考える起点として有用です。
