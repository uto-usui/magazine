### [The web is losing its personality](https://ishadeed.com/article/web-personality/)

> **出典**: Ahmad Shadeed | **公開日**: 2026-11-26 | **カテゴリ**: css

**3行まとめ**
- AI に一度で作らせたランディングページは、色と文言を変えるとどれも同じに見えます。AI が学んだのが、テンプレートや UI キット、shadcn のような部品集、Linear に似せたサイトだからです
- 一度で作らせた画面の目印として、見出しの上のピル型のラベル、グラデーションの見出し、背景のぼかし、見出しのぼかしアニメーション、「No fluff」のように否定を重ねる言い回し、`overflow` で切れた影を挙げています
- 似たデザインは Bootstrap やテーマ販売の時代にもありましたが、AI で広がる速さはそのころとは比べものにならない、と見ています

**詳細解説**

作り直しの例は、カフェのランディングページです。仕上がって見える画面から始めると、そこから離れて考えにくくなります。そこで、まず載せる内容だけのワイヤーフレームを作り、文言も AI に任せずに書きます。次に、ブランドを人に見立てたらどうか、店に入ったときの雰囲気はどうか、豆の袋の素材は何か、と問いを立てます。そこから、店の壁に合わせた紙の質感の背景と、ヘッダーとヒーローをまとめて豆の袋に見立てる案をスケッチで起こしています。Figma での作業は1時間かからなかったそうです。

書体・画像・イラストのようなブランドの表現で違いを出し、ナビゲーションや CTA のような見慣れたパターンは変えない、と線を引いています。AI はプロジェクトの初期設定や依存関係の追加、内容のデータ化、最初の簡単な組み立てに使い、CSS は手で書く、という分け方です。

### [I’m a 100x engineer now](https://veszelovszki.com/a/tpe/)

> **出典**: Sidebar | **公開日**: 2026-11-27 | **カテゴリ**: design

**3行まとめ**
- 36年コードを書いてきた David Veszelovszki さんが、macOS のファイルマネージャー Cmdr を一人で作りました。10か月で140万行になり、Copilot だけのころの約60倍、AI なしのころの80〜100倍の速さと見積もっています
- コードは読まず、レビューもしません。代わりに、テスト・lint・複雑さの上限など159のチェックを置き、バグを直すたびに同じ種類のバグが起きないようチェックを足しています
- UI の文言、色、余白、エラーメッセージなど、人が目にするものはすべて人が書くか確かめる、と決めています

**詳細解説**

時間の40〜50%は、チェックとコードの構成の手入れに使っています。チェックには、TypeScript と Rust の型の対応が最新か、新しい文字列が15言語に訳されているか、`CLAUDE.md` が600語を超えていないか、なども含まれます。全部で約20分かかるので、約20秒と約5分の短い組も用意しています。9月だけでエージェントは10万4,000回チェックを走らせ、2,200回の失敗のほとんどを CI の前で止めました。

`CLAUDE.md` はコードの近くに分散して置いています。長くなったら、自動で読まれる `CLAUDE.md`（600語まで）と、必要なときに検索して読む `DETAILS.md` に分けます。ときどきエージェントにバグを1つ直させ、読んだ情報のうち余計なもの・古いもの・足りないものを記録させて、文書を直します。

UI の文言が絡む課題では、Claude が書いた新しい文字列を、人が5分ほどかけて直してから出しています。訳文が人の確認を通ったかを文字列ごとに記録する仕組みもすでにあり、確認が済んだ割合は今はどの言語も0%です。Pull Request で増えた UI の文字列だけを抜き出して人が見る運用なら、チームの開発にも持ち込めそうです。

この速さは一人で作っているから出るもので、チームでは調整に時間がかかる、と断っています。車やペースメーカーのような重要なシステムには勧めないことと、睡眠を削りがちになることにも触れています。

### [Verifiable Credentials による個人情報収集の最小化](https://blog.jxck.io/entries/2026-11-27/verifiable-credentials.html)

> **出典**: blog.jxck.io | **公開日**: 2026-11-27 | **カテゴリ**: web-standards

**3行まとめ**
- 年齢の確認に要るのは「18歳以上か」の真偽値だけなのに、今は生年月日まで集めています。必要な事実だけを証明として受け取る方法が Verifiable Credentials（VC）です
- マイナンバーカードの基本4情報は、J-LIS の署名付きで Wallet に入れられます。項目ごとに salt 付きのハッシュへ署名しておくと、生年月日だけを開示しても、改ざんがないことを確かめられます（選択的開示）
- 生年月日も見せずに済ませるには、発行する側が `over 18` の項目を足すか、ゼロ知識証明を使います。どちらもまだ普及の途中です

**詳細解説**

11月25日の eKYC の記事の続きです。年齢のほかに、学割の「学生である」、マッチングアプリの「未婚である」も、真偽値で足りる例として挙がっています。20歳以上かどうかだけを確かめる方法は、デジタル庁のマイナンバーカード対面確認アプリが、対面に限って提供しています。オンラインの eKYC で `over 18` だけを受け取る使い方は、まだありません。ゼロ知識証明は、証明のしかた自体は確立していますが、こうした用途に向けた標準化はまだ途中です。

VC は誰が発行してもかまいません。大学が卒業を、試験ベンダーが資格を、イベントサイトがチケットを VC にする例が挙がっています。卒業年を隠して「卒業した」事実だけを開示できるようにするかは、発行する大学が決められます。身元確認を代行するベンダーが `over 18` の VC を出せば、生年月日はそのベンダーに集まり、受け取る側は持たずに済みます。

券面の画像と違って、VC には Holder Binding があります。持ち主以外が盗んで提示すると、それがわかる仕組みです。事業者から VC が漏れても、それで年齢や学歴を偽ることはできません。

### [High fidelity, low definition](https://www.seangood.win/articles/high-fidelity-low-definition)

> **出典**: Sidebar | **公開日**: 2026-11-26 | **カテゴリ**: design

**3行まとめ**
- AI で本物らしいプロトタイプが数分で作れるようになり、問題をどこまで定義できているか（definition）と、プロトタイプの作り込み（fidelity）が、一緒に進まなくなりました
- AI を前提にしたチームは、問題の定義を飛ばして作り込んだプロトタイプから始めがちで、案ごとに入り込んだ前提をあとから洗い出すのに時間を取られている、と見ています
- プロトタイプを作る前に、何を決めたいか、何を知りたいかを考え、それに合う作り込みの度合いを選ぶよう勧めています

**詳細解説**

これまでは、ホワイトボードから作り込んだモックへ時間をかけて進むあいだに、チームのなかで問題の理解がそろっていきました。作り込んだモックは時間がかかるぶん、コードを書く前に合意できた印にもなっていました。今は作るのが速くなったぶん、評価するところで詰まります。作り込んだ案はどれも完成して見えるので、その裏にある前提が試されないまま、最初の案に引っぱられます（アンカリング）。

ユーザーフローやスケッチのようなラフな表現を見せると大きな方向について、作り込んだものを見せると細部について、意見が集まります。範囲が狭く決まっている変更なら、最初から作り込むほうが速いこともある、と使い分けも示しています。Shape Up の「抽象度をちょうどよくする」という考えも引いています。方向がはっきりしないまま作り込んだプロトタイプが届いたら、それで何を決めるのかを聞き返し、必要ならユーザーフローやホワイトボードに戻るよう勧めています。

### [Freeze And Resume Network Calls In Cypress](https://glebbahmutov.com/blog/freeze-network-calls/)

> **出典**: Gleb Bahmutov | **公開日**: 2026-11-26 | **カテゴリ**: testing

**3行まとめ**
- 読み込み中の表示を E2E テストで確かめるとき、`cy.intercept` で通信を2秒遅らせる方法では、テストがその分だけ遅くなります
- 遅らせる代わりに、返す Promise の `resolve` を取っておきます。通信を止めたまま表示を確かめ、そのあと `resolve` を呼んで再開します。テストは2秒から96ms になりました
- `cy.freeze` と `cy.resume` のカスタムコマンドにまとめると、エイリアスごとに止めたり再開したりできます

**詳細解説**

止めているあいだにリクエストのメソッドと URL を確かめ、2秒待っても「loading...」が残っていることも検証しています。同じエイリアスで止め直すと前の Promise を先に解決し、止めていないエイリアスを再開しようとするとエラーにします。時間や順番に関わる不具合を調べるのにも向く、としています。

### [Confetti + Shapes + random(): A Fun Combination!](https://blog.master.dev/confetti-shapes-random-a-fun-combination/)

> **出典**: Frontend Masters Blog | **公開日**: 2026-11-27 | **カテゴリ**: css

**3行まとめ**
- CSS の新しい `random()` 関数に `shape()` や `sibling-index()` を組み合わせて、ホバーで図形が紙吹雪のように散る効果を CSS だけで作っています
- 要素を `offset-path` の図形の上に、`sibling-index()` と `sibling-count()` の割合で等間隔に並べ、`translate` と色に `random()` を入れて散らします
- 範囲を決める変数を2つ足すと、図形の一部だけを散らし、ホバーでその範囲を一周させることもできます

**詳細解説**

要素の数は決めておく必要がなく、10個でも1,000個でも動きますが、増やしすぎると描画が重くなります。Firefox では不具合のため、アニメーションが正しく動きません。

疑似要素で紙吹雪を2倍にするときは、`sibling-index()` と `sibling-count()` の値を子に受け継がせるために、変数を `@property` で登録する必要があります。ホバーしていないときは散らす距離を `0px` にして色もそろえておき、ホバーで散らします。一周させる動きは、`mod()` で値を0〜1に折り返して作っています。角度を 45deg から 405deg に回すのと同じ考え方です。

- 描画用の canvas は本物の DOM のテキストの上に重ねるので、文字は選択もコピーもでき、スクリーンリーダーでも読み上げられます
- 時間を秒・割合・CSS の変数 `--tegaki-progress` で渡せるので、スクロールやスライダー、動画のフレームに合わせて描けます

### [Lighting that feels just right](https://blog.maximeheckel.com/posts/lighting-that-feels-just-right/)

> **出典**: Sidebar | **公開日**: 2026-11-26 | **カテゴリ**: design

**3行まとめ**
- 書き手のシェーダーの絵が物足りない原因は間接光（グローバルイルミネーション、GI）だった、と気づいたところから、ブラウザでリアルタイムに GI を近似する方法を順に作って解説しています
- 最初は、画面に映っている画素だけで光の跳ね返りを探す Screen-Space GI です。1画素8本のレイではノイズが多いので、前のフレームの結果を足していく時間方向の蓄積で滑らかにします
- 次に、空間に並べたプローブで光を集める方法に移り、カメラを動かしても結果が消えないようにしています。光源が動いたときは、前の結果をどれだけ残すか（hysteresis）で調整します

**詳細解説**

Screen-Space GI は画面の外のものを扱えず、反射でもカメラから見えない物の裏側が黒く抜けるため、プローブを使う方法に移っています。本番向けの実装ではないとして、使うなら Three.js に入っているプローブ式の GI を勧めています。手順の多くは、1段ずつ進められる図と、パラメータを動かせるデモで確かめられます。

### [SmartHRの「フロントシステム」の品質保証は、なぜ一言で語れないのか —— むずかしさに向き合う現場の取り組み](https://tech.smarthr.jp/entry/2026/11/27/120641)

> **出典**: SmartHR Tech Blog | **公開日**: 2026-11-27 | **カテゴリ**: design

**3行まとめ**
- SmartHR の「フロントシステム」は、入社手続き、従業員情報の更新申請、給与明細など、目的も利用者も違う機能の集まりです。そのため QA リードは、エリアとして守る品質を一言で言えずにいます
- 軸がないままチームごとに最適化が進むと、品質保証のやり方やリスクの見方がばらつき、異動したときに慣れるまで時間がかかります。不具合のデータを集めても、エリアとしての傾向が見えません
- エリアの EM・PO と品質保証の方針を合意して行動計画に入れる体制づくりと、テストケースを Notion に集めて AI で考慮漏れを見つける仕組みを進めています

**詳細解説**

決まった形式を押しつけず、外してはいけないところをガードレールとして示す方向で整えています。機能に詳しい人が探索的にテストするほうが不具合を見つけやすい開発もあるので、やり方はチームに任せています。そのうえで「テスト戦略」と「テスト計画」を分けて広めようとしています。戦略は開発のできるだけ早い段階でリスクを洗い出すため、計画は開発ごとに合ったテストを選ぶためのものです。

AI の仕組みでは、集めたテストケースにインシデント、不具合、仕様書のデータも合わせて参照させています。点で存在していた機能を線でつなぐ開発が増え、互いの仕様を把握しきれずに想定外の不具合が出る場面もある、と書いています。

### [Usability Testing 101](https://www.nngroup.com/articles/usability-testing-101/)

> **出典**: Nielsen Norman Group | **公開日**: 2026-11-27 | **カテゴリ**: design

**3行まとめ**
- ユーザビリティテストは、現実的なタスクに取り組む人を観察して、問題と改善できるところを見つける調査の方法です。進行役、タスク、デザイン、参加者の4つでできています
- 1つの利用者グループの定性的なテストなら、5人で主な問題の多くが見つかるとしています。いちばん簡単な形なら、計画・5人のテスト・分析の3日で済みます
- AI は文字起こしやハイライト動画づくり、分析の手助けに使えますが、解釈は元のデータで確かめる必要があります。AI の進行役は、今は簡単な調査に向く、としています

**詳細解説**

タスクの書き方で結果が変わります。言い回しの小さな誤りで、参加者がタスクを取り違えたり、行動を誘導されたりします（プライミング）。参加者にタスクを声に出して読んでもらうと、読み飛ばしが防げ、観察する人もどのタスクの途中かがわかります。AI でインターフェースを速く作り変えられるようになったぶん、テストの回数を増やす必要が出てくるかもしれない、とも書いています。できれば、スクリーンリーダーなどの支援技術を使う人も参加者に入れるよう勧めています。
