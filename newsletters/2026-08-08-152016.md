### [Dark mode toggles: two states are enough](https://lea.verou.me/blog/2026/dark-mode-toggles/)

> **出典**: Lea Verou | **公開日**: 2026-08-06 | **カテゴリ**: css

**3行まとめ**
- ヘッダーに常設するテーマ切り替えは Light / Dark の2状態で足りる。System を並べた3状態は、データモデルがそのままUIに漏れ出した形
- 内部の状態は3つのままでよく、画面に出すのは「いま見えている値」と「その反対」の2つだけ。それで3状態すべてを表現できる
- 保存値を消す判定は、ユーザーが押した瞬間にだけ走らせる。OS側の変更に反応して消すと、テーマを固定したい人が固定できなくなる

**詳細解説**

Tailwind、Ant Design、Excalidraw、Astro と、テーマ切り替えを3状態で持つ実装は今も広く見かけます。「System はポリシーで、Light / Dark は値だから、意図としては別物だ」という説明はもっともらしく響きます。この記事はそこに切り込み、ユーザーがテーマ切り替えを探すのは「いま眩しい」「いま暗すぎて読めない」ときだけだと指摘します。ベッドで読んでいて画面が閃光弾になった、屋外のノートPCでダークテーマが判読できない。状況的で、即時的で、色の好みというより環境の話です。

そのうえで、良くない2状態トグルの問題も認めています。一度切り替えると System に戻れなくなる実装は、選択が不可逆になり「ユーザーの自由」というユーザビリティ原則を壊します。だから2状態は「3状態を表現できる2状態」でなければなりません。押すと現在の解決値の反対を保存し、もう一度押すと保存値を削除してシステム既定へ戻る。この後半を落としている実装が多い、という指摘です。

実装上でいちばん間違えやすいのは、保存値の掃除のタイミングでしょう。OSの設定が時間帯で自動的に切り替わる環境は珍しくありません。保存値がたまたまOS設定と一致したからといって消してしまうと、明示的な選択が、ユーザーの関与していないイベントによって黙って既定値へ降格します。評価はユーザー操作のときにだけ行う、という一行のルールがここを守ります。

UXエンジニアリングの視点で読むと、これはトグルの話というより「状態機械のすべての状態にUIを与えなくてよい」という設計判断の話です。記事自身も、引数を大量に要求する信号対雑音比の低いAPIと同じ構図だと書いています。デザインシステムのコンポーネントとして常設トグルを提供する側なら、`localStorage` に何を書くか・いつ消すかまでを仕様に含めておくと、利用側での取りこぼしが減ります。

適用範囲もはっきり区切られています。設定パネルの中に置くテーマ設定なら、ユーザーはすでに将来の決定をする気持ちでいるので3状態が妥当です。また、ライトモードをOSの状態に応じて出し分ける（暗いOSでは控えめなライト）実装をしているなら、3状態を出す資格がある、とも書かれています。常設トグルという特定の文脈への主張だと理解して読むのがよさそうです。

### [How Baseline Can Help You Ship Less JavaScript](https://smashingmagazine.com/2026/08/how-baseline-can-help-ship-less-javascript/)

> **出典**: Smashing Magazine | **公開日**: 2026-08-07 | **カテゴリ**: design | **著者**: Jad Joubran

**3行まとめ**
- 中規模のJavaScriptアプリなら、ブラウザが自前で処理できるようになった依存が gzip 後で 60〜90KB ほど眠っていることが多い
- 依存を1つずつ見るのではなく、国際化・HTTPクライアント・UIプリミティブ・Lodash という塊で棚卸しする
- 判断は3つの問いで行う。自分の利用者にとってBaseline安全か、置き換えの費用はいくらか、実際の使い方をカバーできるか

**詳細解説**

`npm audit` はセキュリティのために回すのに、「このライブラリはまだブラウザにできないことをしているか」は誰も聞かない。だから残り続ける。この記事の出発点はその観察です。Baseline の3段階（Limited / Newly available / Widely available）を土台に、置き換えの安全度を判定していきます。Widely available は全エンジンに載って30か月経った状態で、ここに達していれば今日置き換えられる目安になります。

いちばん取りやすいのは国際化の塊です。`timeago.js` は `Intl.RelativeTimeFormat`、`pluralize` は `Intl.PluralRules`、`numeral` は `Intl.NumberFormat`、配列を文章に繋ぐヘルパーは `Intl.ListFormat` に置き換わります。合わせて gzip で 14KB ほど。ただし `Intl.DurationFormat` は Newly available どまりなので、広い読者を相手にするなら機能検出を挟むか、もう1年待つ判断になります。

UIプリミティブの節がとくにおもしろいところ。`<dialog>` の `showModal()` は、フォーカスの閉じ込め、背景の inert 化、Escape での閉じ、開いた要素へのフォーカス復帰までを引き受けます。つまりモーダルライブラリと `focus-trap` が1要素に畳まれます。残る背景スクロールの固定は `body:has(dialog:modal) { overflow: hidden; }` の1行。`dialog[open]` ではなく `:modal` を使う理由（`show()` の時点で `open` は立つが、まだモーダルではない）まで説明されていて、こうした細部が実務では効いてきます。

逆に「まだ置き換えない」判断の例として Temporal が挙げられているのが誠実です。Safari の安定版が未対応でBaselineに達しておらず、公式ポリフィルは gzip で 44KB。`dayjs` の 3KB と入れ替えると、条件付き読み込みをしない限りバンドルは 41KB ほど増えます。フレームワークが「待て」と言う側の事例を1つ置くことで、3つの問いが単なる削除の口実になっていないことが示されます。

UXエンジニアリングの視点では、置き換えの副産物としてアクセシビリティの既定値が上がる点が見逃せません。手書きのモーダルやツールチップが抱えがちなフォーカス管理やキーボード操作の不備は、プラットフォーム機能に寄せるだけで解消されることが多いからです。バンドルサイズの話として始まって、実装品質の話に着地します。四半期に一度、`npm ls --omit=dev --depth=0` から棚卸しを回す習慣として持つのがよさそうです。

### [Working with ::highlight() using progressive enhancement](https://piccalil.li/blog/working-with-highlight-using-progressive-enhancement/)

> **出典**: Piccalilli | **公開日**: 2026-08-06 | **カテゴリ**: css | **著者**: Sunkanmi Fafowora

**3行まとめ**
- CSS Custom Highlight API と `::highlight()` を使うと、DOMを分割せずに任意のテキスト範囲へスタイルを当てられる
- 手順は4つ。`Highlight()` のインスタンスを作り、`CSS.highlights` に登録し、`Range()` を作って追加し、`::highlight()` で装飾する
- この機能はJavaScriptに全面的に依存する。`<mark>` によるフォールバックを先に書き、`@supports selector()` で囲うのがプログレッシブエンハンスメント

**詳細解説**

`::selection` や `::target-text` のようなハイライト用の擬似要素は以前からありましたが、任意の範囲に自前のハイライトを当てる手段はありませんでした。そこを埋めるのが CSS Custom Highlight API です。JavaScriptで範囲を作り、CSSで見た目を決める。役割分担としてはきれいな形をしています。

記事の進め方が良いのは、実装手順に入る前に「JSが落ちたらどうなるか」を先に問うところです。デモでは対象の単語をあらかじめ `<mark class="gold">` `<mark class="ice">` で囲い、`mark { background: none; }` を土台に `oklch()` の文字色と `text-shadow` でスタイルを当てています。この時点でJSなしでも意図した見た目が出ます。同じ `<mark>` に `id` も振っておき、JSが動く環境ではそこから `firstChild` を取って範囲を作る、という二段構えです。

`Range()` の扱いには少し癖があります。`setStart(node, 0)` と `setEnd(node, node.textContent.length - 1)` で範囲を決めるのですが、記事のコードは終端に `- 1` を置いているため、実際には末尾の1文字が範囲から外れます。単語全体を対象にしたい場合は `- 1` を外すのが正しい書き方なので、写経するときは手元で確認してみてください。

仕上げは `@supports selector(::highlight(hl-gold))` で `::highlight()` のブロックを囲むところです。未対応ブラウザではこのブロックごと無視され、`<mark>` のスタイルだけが残ります。JSが動く環境では両方が当たりますが、見た目を揃えてあるので破綻しません。

UXエンジニアリングの視点では、この形は「装飾のためにマークアップを壊さない」手段として価値があります。検索語のハイライトやコードエディタのシンタックス装飾のように、範囲が動的に変わる用途では、`<span>` を差し込む従来のやり方がDOMを汚し、テキスト選択やスクリーンリーダーの読み上げにも影響しました。`::highlight()` はDOMに触れずに済みます。裏を返すと、意味づけとしてのハイライトは残らないので、意味を持たせたいなら `<mark>` を併用する今回の構成がそのまま答えになります。

### [Storybookとは？ UIコンポーネントを効率よく開発・確認するウェブのツール](https://ics.media/entry/260806/)

> **出典**: ICS MEDIA | **公開日**: 2026-08-05 | **カテゴリ**: frontend | **著者**: nohara

**3行まとめ**
- 0件・大量件数・極端に長い文言といった状態は、普段の開発用データでは見つからない。それを画面遷移なしで並べるのがStorybook
- Storyに登録する観点を「最小と最大 / 空や0件 / 読み込み状態 / 並び順 / 文字種の違い」としてルール化している
- StoryのURLを共有すればデザイナーやディレクターに見てもらいやすく、コーディングエージェントへ期待する見た目を伝える手段にもなる

**詳細解説**

Storybook 10.5 / Vite 8.1 / Node.js 24 を前提にした導入記事です。`npm create storybook@latest` を叩くと構成を自動検出して設定が入る、という導入の軽さから、`NoticeList` という小さなお知らせ一覧を題材にStoryを4つ（Default / Loading / Empty / Scroll）作るところまでを追います。入門として読みやすい一方で、中身はかなり実務寄りです。

読みどころは、ICSが社内でルール化しているというStoryの観点リストでしょう。最小と最大、空や0件、読み込みなどの状態、並び順、文字種の違い。前半3つはユニットテストで境界値や空値を確かめるときと同じ発想で、そこに「描画してはじめて確認できる」観点が乗っている構成になっています。文字種の違いは日本語のUIではとくに効きます。同じ文字数でも半角英字・全角英数・和文でラベルの幅が変わるからです。

デモの作り方も具体的です。記事ランキングでは［Japanese］と［English］を切り替えると三点リーダーの省略開始位置が変わり、同着順位は［TiedRanks］、空文字のタイトルは［EmptyTitle］として登録されています。サイドメニューでは、日本語なら5項目とも1行に収まるラベルが英語では2項目で2行になり、高さがずれる様子を見比べられます。バッジがラベル側の幅を奪う挙動も別Storyとして切り出されています。

Storyに載せるのはプレゼンテーショナルコンポーネントに寄せる、というコラムも実務的な判断です。API通信や画面遷移を持ち込まず、Propsで見た目に必要な値だけを受け取る形にしておくと、状態を外から与えるだけで全パターンを並べられます。ControlsとStoryの使い分けも整理されていて、あとから見返したい状態はStory、その場かぎりの確認はControls、という線引きになっています。

UXエンジニアリングの視点では、`@storybook/addon-mcp` の存在が今の文脈で効いてきます。Storyが「このコンポーネントが取りうる状態の一覧」として整備されていれば、それはそのままコーディングエージェントへの仕様書になります。デザイナーとの合意形成、視覚回帰テスト、エージェントへの入力という3つの用途が同じ資産に載る構図で、Storyを書く動機がまた1つ増えたといえます。

### [The last product design tool](https://writing.mariusz.cc/ultimate-product-design-tool/)

> **出典**: Sidebar | **公開日**: 2026-08-06 | **カテゴリ**: design

**3行まとめ**
- デザインシステムがコードとして確立していれば、四角と矢印のワイヤーからAIが実装可能なインターフェースを組み立てられる
- そのため、インターフェース設計の道具として tldraw が Figma より出番の多い場面が出てきている
- エージェントに任せるのはインターフェースの発明ではなく、ホワイトボードとコードベースという2つの語彙のあいだの翻訳

**詳細解説**

「ワイヤーフレームなんて誰が必要とするのか」から「tldraw が第一の道具になった」への転向を書いた短い記事です。磨かれた画面、丁寧なタイポグラフィ、細かく調整された余白を製品デザインツールの条件とするなら、四角と矢印と落書きしか出せない tldraw は物足りなく見えます。それが機能なのだ、というのが主張です。

理屈は明快です。デザインシステムがコードとして確立していれば、ボタンにはサイズも状態も強弱もすでに定義されています。ダイアログには構造があり、コンポーネントの契約とスロットが、渡せるプロパティと組み合わせ方を決めています。だから「Dialog」と書かれた四角を置いた時点で、それがどう見えてどう動くかは確定しています。決めているのは、フローのこの地点にダイアログが要るかどうかだけです。

エージェントに与えている仕事の切り取り方も参考になります。スクリーンショットやプロンプトからインターフェースを発明させるのではなく、ホワイトボード側の語彙（画面・ラベル・関係・メモ）とコードベース側の語彙（名前のついたコンポーネントと明示的な契約）を対応づけるだけ。契約が明確なほどエージェントが間違える余地は減り、もっともらしい誤りを直す時間も減ります。

UXエンジニアリングの視点では、この記事はデザインシステム投資の回収先が1つ増えたことを示しています。従来はコードの再利用性や一貫性が主な効能でしたが、ここでは「エージェントに渡せる語彙」として機能しています。裏を返せば、デザインシステムがコード側に確立していないチームがこのループを真似ても、エージェントは毎回インターフェースを発明することになり、レビューの手間が増えるだけになりそうです。

一方で、この方法が効く範囲は限定的だという点も押さえておきたいところ。既存コンポーネントの組み合わせで表現できる画面には強い反面、新しいインタラクションそのものを設計する場面では、四角と矢印は解像度が足りません。記事も最終的なインターフェースはブラウザに宿ると書いていて、判断と実験の場をコードへ移す話として読むのが妥当でしょう。

### [Introducing Agent Plugins](https://vercel.com/blog/introducing-agent-plugins)

> **出典**: Vercel | **公開日**: 2026-08-06 | **カテゴリ**: frontend | **著者**: Jonathan Hefner

**3行まとめ**
- Agent Skills と MCP サーバーを1つのプラグインとして配布するための、ベンダー中立な標準 Agent Plugins 1.0.0 が公開された
- 仕様は `plugin.json` と `skills/` `mcp.json` という固定の置き場所だけ。インストール・配布・ポリシー・UXは各クライアントに委ねる
- ChatGPT / Codex、Cursor、GitHub Copilot、Kiro、VS Code が launch 時点で対応。AWS・Anysphere・GitHub・Microsoft・OpenAI・Vercel が策定に参加

**詳細解説**

同じ Skill や MCP サーバーなのに、クライアントごとにメタデータの形も探索パスもMCPの設定方法も違う。拡張の作者はその都度パッケージし直すことになります。Agent Plugins はその重複を1つの構造に畳む提案です。ルートに `plugin.json` を置き、Skill は `skills/` の下、MCPサーバーの設定は `mcp.json`。対応クライアントはこの場所だけを見ればよいことになります。

マニフェストの最小構成が `$schema` と `name` の2フィールドだけ、という思い切りが仕様の性格をよく表しています。残りの契約はディレクトリ構造そのものが担う設計です。マニフェストを検証したあと、各コンポーネントは独立して検証されるので、1つ壊れていても無関係なコンポーネントまで無効にはなりません。

範囲を意図的に小さく保っている点も明示されています。バージョン1が扱うのは Agent Skills と MCP サーバーの2種類だけ。コマンド、フック、エージェントといった要素はクライアント側に残されています。すでに仕様と普及があるものだけを対象にし、意味が収束してから portable な面積を広げる、という順序です。クライアント固有のデータには名前空間つきの拡張機構が用意されていて、他のクライアントはそれを無視します。

UXエンジニアリングの視点では、これはデザインシステムのトークン配布と似た構図に見えます。中身（Skill の内容、コンポーネントの見た目）は変わらないのに、配布経路がクライアントごとに分断されていると、作る側は同じものを何度も梱包し、使う側は見つけられません。Agent Plugins が定義しているのは中身ではなく、発見と読み込みの契約です。標準化の対象を「探し方」に絞ったところが要点でしょう。

気になる点を挙げるなら、Vercel が提案を始めた仕様であること、そしてどのクライアントも実装は任意である以上、対応の深さにばらつきが出うることでしょうか。とはいえ Technical Steering Committee に AWS・Cursor・Microsoft・OpenAI・Vercel の Core Maintainer が並び、単一企業のロードマップが方向を決めない形になっているのは、こうした標準としては良い出発点です。社内でスキルやMCPサーバーを配っているチームなら、梱包の形を寄せておく価値はありそうです。

### [ICML 2026で分かった本番エージェント86システムの「地味な設計」という解](https://tech.layerx.co.jp/entry/icml-2026)

> **出典**: LayerX エンジニアブログ | **公開日**: 2026-08-07 | **カテゴリ**: engineering | **著者**: tosho_layerx

**3行まとめ**
- 本番稼働中のLLMエージェント86システムの調査では、追加学習なし70%、人の確認までの自律ステップ10未満68%、事前に決めた手順に沿わせる80%という「地味な設計」が並んだ
- 記憶の研究では、同じ方式のままモデルを大きくしても平均 +0.038 しか改善しないのに対し、記憶の設計を変えると 0.45 の差が出た
- 検索の窓口しか触れない立場から知識ベース全体を復元する攻撃は、4分野混在で45〜49%に届く。文書の閲覧権限と検索索引の権限は別々に管理されがち

**詳細解説**

「もっと賢いエージェントの作り方」を探しにICML 2026へ行ったところ、いちばん残ったのは本番運用の実態調査だった、という導入から始まります。20件の詳細インタビューと306名のアンケートから、26業種86システムを分析した研究です。並んでいたのは、既製モデルとプロンプトで作る、人が確認するまでの自律ステップを10未満に抑える、開放的な自律計画ではなく事前に決めた手順に沿わせる、という設計でした。

理由の部分が読みどころです。追加学習を避けるのは技術力の問題ではなく、そのほうがモデル更新で壊れにくく開発サイクルも速いから。最大の壁は能力ではなく信頼性で（38%で首位）、その解決策もアルゴリズムではなく、読み取り専用で動かす・隔離環境に置く・権限を役割ごとに絞るというシステム設計の側にありました。「7割が追加学習をしていない」は「3割はしている」でもある、という補足も丁寧です。

人の確認を外せている少数派の分析も具体的です。本番31件のうち人の確認を使わないのは8件で、そのうち評価手法を持たないのは1件だけ。分かれ目は業界でも規模でもなく、正しさを機械が数秒で判定できるかどうかでした。コーディングエージェントはコンパイルとテストで検証できる稀なケースだと論文は書いています。LLMを採点役に使うチームは20件すべてが人のレビューと併用していて、単独運用はゼロだったという数字も添えられています。

「手順に沿わせる80%」の中身の読み替えには意表を突かれます。これは設計思想の選択ではなく、既存の業務プロセスをそのままエージェントのワークフローに写した結果だ、という解釈です。保険査定のエージェントが固定の順序なのは、査定業務がその順序だからにすぎません。裏返すと「うちの業務は、もう手順として書けているか」が先に問われます。TG-RAG の話（手順をプロンプトに書くか推論の途中に差し込むかで12ポイント変わる、強制しているのは「選択肢」であって「選択」ではない）も、この延長として読めます。

UXエンジニアリングの視点では、この記事全体が「どこまでを機械に任せ、どこから人に戻すか」という線の引き方の議論として読めます。人間による確認は、いま最も効いている方法論であると同時に、エージェントの数が1桁増えたときに真っ先に回らなくなる方法論でもある。この二面性を正面から書いているのが誠実です。数字の限界（86システムの「成功」は本番に到達したことだけを指し、投資対効果も継続率も測っていない）まで自分で割り引いている点も、信頼して読める理由になっています。

### [How to Decide When an AI Tool Is Worth Keeping](https://www.nngroup.com/articles/prove-framework/)

> **出典**: Nielsen Norman Group | **公開日**: 2026-08-07 | **カテゴリ**: design | **著者**: Caleb Sponheim

**3行まとめ**
- AIツールの評価は「1回試して良さそうだから採用」か「変な使い方をして見限る」のどちらかに転びやすい

**詳細解説**

**詳細解説**

PX PUSH は分散型・オープン経済の領域に特化したサブスクリプション型デザインスタジオです。この分野のチームは速く動き公開の場で出荷するのに、周囲の代理店やスタジオはその言語を話さない。だからサイト自体を、その事業の動き方（構造的で、説明責任があり、その全部について少し無表情）に合わせた、と説明されています。1988年の画面ならこう見えるはず、という問いを全要素に通しています。

CRT効果の作り方が明快です。`Wrapper.vue` という1つのコンポーネントの中に、固定配置のオーバーレイを重ねるだけ。8秒ループで下から上へ走る走査線バー、リフレッシュ線を模した細かい繰り返しパターン、古いガラスの発光を作る `backdrop-filter: blur` の層、画面全体に伸ばして端を暗く歪ませる `crt.png`、そして控えめなノイズテクスチャ。CSSと画像2枚で、セッション中ずっと動き続けます。

Three.js を3つ別々のビルドに分けているのも判断として明確です。SVGを `SVGLoader` で読んで押し出し、ベベルを付け、PMREM環境光の下でメタルネスとクリアコートを当てたクロームのロゴ。約8,000枚の雲プレーンを1つの buffer geometry にまとめ、カスタムGLSLで縁をフェードさせる雲飛行のヒーロー。実行時にキャンバス上で光沢マップを再着色するフロッピーディスク。ヒーローでは「speed」という単語にホバーすると飛行速度の倍率が0.2から2へ上がるイースターエッグまで仕込まれています。

エンジニアリングの労力が注がれたのは、実はそこではありません。Nuxt のページフックはコンポーネントがマウントされたことは教えてくれますが、シーンがアセットを読み終えて最初のフレームを描いたかどうかは教えてくれない。そこで `prepared → revealed → ready` という小さなライフサイクルを、window イベントによる素朴な pub/sub として自作しています。各コンポーネントが `registerPageTask()` で Promise を登録し、ページはすべてが決着するかハードタイムアウトまで待つ。3つのシーンが互いを知らないまま協調できる構造です。

UXエンジニアリングの視点で拾いたいのは、Journal のドロワー実装でしょう。記事一覧の上にオフィス用紙を模したドロワーをスライドさせ、左端はCSSマスクで穴を開けています。見た目としては大胆な逸脱ですが、各記事は自分のスラッグ、正規URL、OGタグ、`BlogPosting` スキーマを保持したまま。ドロワーは記事の見え方を変えるが、ルーティングやインデックスのされ方は変えていない、と明記されています。演出とWeb標準の両立をどこで線引きするかの、良い実例です。

### [Garden Anomaly: A Tiny WebGPU and TSL Experiment](https://tympanus.net/codrops/2026/08/06/garden-anomaly-a-tiny-webgpu-and-tsl-experiment/)

> **出典**: Codrops | **公開日**: 2026-08-06 | **カテゴリ**: design | **著者**: Frank Reitberger

**3行まとめ**
- WebGPURenderer と TSL（Three Shading Language）のノードマテリアルだけでシーン全体を構成した実験作
- 物理はCPU上のPosition Based Dynamics。壁への衝突が一定速度を超えたときだけガラスに膨らみができ、同時に音が鳴る
- 音はWeb Audio APIで完全に手続き的に生成。泡の半径がペンタトニックスケール上の音高を決めるので、同時ヒットが自然に和音になる

**詳細解説**

Three.js Conference に向けたCodropsのシリーズの1本で、ガラス球のなかで泡が跳ねる小品の解説です。TSLやWebGPUをどこから始めればいいかとよく聞かれるが、正直あまり助言できることはない——Three.jsのサンプルをいくつか見て、TSLのWikiを読んで、あとは実験を始めただけだ、という書き出しが率直で好ましいところ。

レンダリング構成が細かく列挙されています。透過シェルは `MeshPhysicalNodeMaterial` で、transmission、thickness、IOR、iridescence（0.90 / IOR 1.55）、clearcoat、青系の減衰色と距離。衝突による膨らみはカスタムの `positionNode` で、方向と振幅のベクトルを持つ8スロットの `uniformArray` が頂点変位を駆動します。法線は解析的な摂動と、球用の接空間フレームから作った法線マップの組み合わせ。発光は、キャンバスで生成した走査線ストリップをUVオフセットのuniformでシームレスにスクロールさせています。

物理はPosition Based Dynamics（PBD）で、すべてCPU上で走ります。重力と空気抵抗を半陰的オイラーで速度に積分し、位置を進める。3回の反復で球同士の衝突を解き、質量は半径の3乗で重み付けするので小さい泡が大きい泡に自然に譲ります。速度を積分値ではなく位置の変化から `v = (x − x_prev) / dt` で導き直すのがPBDの決定的な特徴で、これによって山が絶えず暴れずに落ち着く、と説明されています。ただし200ms静止した泡には上向きの弾みを与えて、系全体を穏やかに沸騰させ続けています。

音の設計がいちばんおもしろいところ。サンプル音源は一切なく、Web Audio APIで手続き的に生成しています。鳴るのは泡がガラスに当たって膨らみを作ったときだけで、泡同士の衝突は無音。つまり音は常に、目に見えるガラスの変形と直接結び付いています。音高は2オクターブのCメジャーペンタトニック（C4〜A5）から選ばれ、泡の半径が決めます。ペンタトニックなので重なっても心地よい和音になる、という設計です。1音は4つのサイン波オシレータの積み重ねで、それぞれに独立したゲインエンベロープを持たせ、明るく開いてから純粋なサイン波の尾へ消えていきます。

UXエンジニアリングの視点で見ると、音の実装まわりの丁寧さが参考になります。`AudioContext` は最初のポインタ操作で生成・再開してブラウザの自動再生ポリシーに従い、レートリミッタで最短間隔と8ボイスの上限を設け、終わったボイスは自分で片付ける。既定音量は環境音として成立するよう意図的に低く設定されています。演出としてのオーディオを本番のUIに載せるときに必要な配慮が、そのまま揃っている実装例です。

### [Drawesome](https://benji.org/drawesome)

> **出典**: Sidebar | **公開日**: 2026-08-06 | **カテゴリ**: design

**3行まとめ**
- React用の描画ツールバー。7種類のペンと消しゴム、SVG / PNG書き出しつきで、依存はReactのみ
- ツールバーはパネルを差し替えるのではなく形そのものが変わる。色を選ぶとペンの列がパレットになり、最小化すると手にしている道具を抱えたまま円盤に丸まる
- 意見の強さが売りで、既定値がそのまま出荷版になるよう作られている。カスタマイズは「切る・並べ替える」であって「作り直す」ではない

**詳細解説**

スクリーンショットへの注釈、フレームへの書き込み、おかしい箇所を丸で囲む。制作ツールを作っているとこの手の描画機能が何度も必要になるので、毎回作らずに済むようにした、というのが出発点です。`npm install drawesome` して、高さを持つ親要素のなかに `<Draw />` を置く。導入は2行で済みます。

作り込みの大半はツールバーに費やされたと書かれています。パネルを差し替えるのではなく、バーそのものが形を変える。色を選べばペンの列がパレットになり、サイズ調整を開けば2本のスライダーになり、最小化すれば手にしている道具を抱えたまま円盤に丸まる。すべての状態が次の状態へ滑らかに変形します。脚注に、Appleのマークアップツールとそのスキューモーフィズムの徹底ぶりから着想を得た、トレイに並んだペンはアイコンの列に勝る、とあるのが設計の芯です。

ペンの挙動も名前どおりに作り分けられています。鉛筆・ペン・ブラシは速く動かすほど細くなり、ファインライナーと蛍光ペンは何をしても一定の幅を保ち、万年筆は速度ではなく方向で決まって一方向には太く逆方向には髪の毛のように細くなる。消しゴムはストローク単位ではなく面積を消すので、線の一部だけを消して残りを保てます。

APIの切り方が実務的です。`tools` で並べるペンと順序を決め、`controls` で undo や clear を落とす。`theme` は `light` / `dark` / `auto`、`placement` と `inset` と `align` で配置を決める。`background` を `transparent` にすればコンポーネントは何も塗らず、背後がそのまま透けます。680px 未満ではバーを縦に立ててツールを減らす、というレスポンシブ対応も実際のコードで示されています。`chrome={false}` でツールバーを外し、`DrawSurface` / `Toolbar` / `useDrawing` を個別に組み直す逃げ道も用意されています。

UXエンジニアリングの視点で拾いたいのは、「意見の強さが要点だ」という宣言です。既定値は出荷する版そのもののつもりで作ってあるので、見た目や手触りを考えなくても正しいものになる。設定でできるのは切ることと並べ替えることだけ、という線引きは、汎用性を求めて設定項目が膨らむコンポーネントとは逆の方向です。部品から組み立てたいなら tldraw や Excalidraw のほうが向いている、と脚注で自ら書いているのも潔いところ。ライブラリのAPI設計として、どこまでを決め打ちにするかの参考になります。
