### [How employment is changing at Anthropic](https://www.anthropic.com/research/employment-at-anthropic)

> **出典**: Sidebar | **公開日**: 2026-10-22 | **カテゴリ**: design

**3行まとめ**
- Anthropic が社内の雇用・AI 利用・成果・カレンダー・採用記録のデータと、17人へのインタビューをもとに、AI で仕事がどう変わったかをまとめた調査レポートです
- 技術部門のジュニア層の採用比率は27%から9%に下がり、社員が動かすエージェントの稼働時間は人の6倍になりました
- エージェントの出力を読む人の注意が新しいボトルネックになり、エージェントを管理するための仕事（メタワーク）が増えていると報告しています

**詳細解説**

AI の導入がもっとも進んだ会社のひとつで、仕事と雇用に何が起きているかを数字で示したレポートです。2025年初めから、技術部門に占めるジュニア層の割合は21%から14%に、ジュニアの採用比率は27%から9%に下がりました。一方で営業や財務、採用の人員は技術部門より速く増えています。コードを書いていなかった非技術職のコーディング系エージェントのセッションは、月2回から90回に増えたそうです。

生産性については、エージェントを使い始めた192人のエンジニアと、使っていない74人を同じ月どうしで比べています。導入後に追加されるコードの量ははっきり増えました。同じ人が同じ月・同じディレクトリで書いたコードを比べると、エージェントが書いたコードのほうが後で消されたり戻されたりしやすい、という差は見られなかったそうです。ただし、導入のタイミングはランダムではないので、推定に偏りがありうることも明記されています。

UXエンジニアリングの視点で興味深いのは、人の注意がボトルネックになっているという指摘です。対話型セッションの約80%は、エージェントが人の入力を待っている時間でした。非技術職でも、エージェントの出力をすべて読むと勤務時間の半分以上かかる量になっています。その結果、エージェント向けの常設の指示は1年で数百件から8,500件に増え、メタワークはセッション全体の10%から22%に増えました。エージェントの成果を人がどう確認し、どこで判断するかという画面や仕組みの設計が、これからの大きなテーマになりそうです。

ほかにも、Claude.ai のあいさつ文などを書いていたライターのチームが、エージェント向けのプロンプトや評価（eval）を書く仕事に移った話が紹介されています。「人の行動を動かすために言葉を使っていたライターが、いまは Claude の行動を動かすために言葉を使っている」という一文は、UX ライティングの今後を考えるうえで参考になります。また、口頭で決めたことが記録に残らないとエージェントが文脈を失うため、仕事を見える場所で進める圧力が強まっているそうです。採用面接では、AI ツールを工夫して使えるか、自律性や判断力があるかへの言及が増えています。

最後に、会社としての対応として、株式の保有による利益の共有、影響を受けそうな職種を早めに見つける仕組み、社内での配置転換の3つが挙げられています。ただし、こうした対応はジュニア採用の減少そのものには効かないと、レポート自身が認めています。1社の、それも AI を作っている会社の事例なので、そのままほかの組織に当てはめることはできません。それでも、変化の先行例として読む価値は大きいでしょう。

### [AI Writes, Reviews, and Tests My Code. My Job Now Is to Taste It](https://tech.layerx.co.jp/entry/engineer-as-director-en)

> **出典**: LayerX エンジニアブログ | **公開日**: 2026-10-21 | **カテゴリ**: engineering

**3行まとめ**
- LayerX の Ai Workforce チームのエンジニアが、チケットからマージ、開発環境での QA までをほぼ AI に任せている働き方を紹介した記事です
- 16営業日で211件の PR がマージされ、本人はコードを1行ずつ読むのをやめ、AI が何を読み、何をコミットしたかを見るようにしています
- ゲーム監督の小島秀夫さんの「料理長が味見をする」というたとえを借りて、作ったものを実際に使って確かめることを自分の仕事と位置づけています

**詳細解説**

使っているのは Claude Code の4つの skill です。チケットからマージまでを担う `/ship`、難しいチケットで先に実装計画を書いてレビューする `/plan-checker`、複数の観点で PR をレビューし、指摘ごとに別のエージェントが「本当に起きるか」を問い直す `/pr-checker`、マージ後に QA のシナリオを流す `/devqa` です。`/devqa` は10月上旬の9日間で、リリース前に7件の問題を見つけたそうです。

`/ship` の設計で参考になるのは、仕様だけは AI に決めさせない点です。受け入れ条件を満たせない、既存の設計とぶつかる、お客様に見える振る舞いに選択肢があるといった場合は、途中でも PM に返して止まります。迷ったときは「PM がこの PR を見て『そんなこと決めていない』と言わないか」を自分に問うそうです。AI に任せる範囲と、人が決める範囲の線引きを具体的に言葉にしている例として、ほかのチームでも応用しやすいでしょう。

一方で、コードを読まないことによる失敗も正直に書かれています。git worktree の扱いで、ほかのセッションがメインの作業ツリーのブランチを切り替えてしまい、レビュー役と検証役の6つのエージェントが、変更を1行も含まないコードを読んで、もっともらしい結果を返しました。それ以来、長いタスクは最初から専用の worktree で動かし、コミットのたびに `git show --stat` でファイル名と行数を確認しています。「見ているのはコードではなく、AI が何を読み、何をコミットしたか」という言い方は、AI と働くときの確認ポイントをうまくまとめています。

UXエンジニアリングの視点では、テストがすべて通っていた機能を、PM が実際に触って作り直した話がとくに興味深いところです。初期設定を案内するエージェントは、思いついた機能がすべて入っていて、何のためのものか分からなくなっていました。自動の確認が増えるほど、人が使ってみて違和感に気づく役割の価値は上がりそうです。なお、この働き方は同僚のレビューと QA チームがいる前提で成り立っていて、すべてのチームにすすめるものではないと、著者自身が断っています。

### [内製 Background Coding Agent “haro” で拓く未来の開発体験](https://tech.layerx.co.jp/entry/why-we-built-our-background-agent)

> **出典**: LayerX エンジニアブログ | **公開日**: 2026-10-22 | **カテゴリ**: engineering

**3行まとめ**
- LayerX のバクラク事業部が、クラウド上で Claude Code などを動かすコーディングエージェント基盤「haro」を内製した理由と、その使われ方を紹介しています
- 開発開始から約3か月で、1日の PR の55〜60%（200件弱）が haro 経由で作られ、利用者はエンジニアの半数を超える58人になりました
- デザイナーによる UI の修正や QA による観点出しなど、エンジニア以外の使い方も広がっています

**詳細解説**

内製した理由は、ローカル開発の限界と、既製品では自社の monorepo を快適に動かしきれないことの2つです。大きな monorepo では Language Server やエージェントのプラグインがメモリを大量に使い、git worktree で並列に開発すると、人の認知より先にマシンが限界を迎えるといいます。構成は、エージェントの制御を TypeScript（Temporal Workflow と AI SDK の `HarnessAgent`）、実行環境を Go（EKS 上の CRD とカスタムコントローラー）で管理する形です。

haro のエージェントには Slack、Notion、Linear、Datadog、Snowflake などの MCP がつながっていて、利用者は鍵の管理をせずに自分のアカウントで使えます。モバイルアプリチームでは PR の75%ほどが haro で作られています。haro の環境では Android エミュレーターが動くので、実機の数が並列開発のボトルネックにならず、小さな UI 変更なら実装からスクリーンショット付きの PR 作成まで任せられるそうです。

UXエンジニアリングの視点では、「コードを読み書きでき、動作確認もできる環境」を気軽に用意できることで、デザイナーが自分で UI の実装を直せるようになった点が大きいでしょう。デザインと実装の間の受け渡しが減ると、細かい調整のやり取りの形も変わりそうです。また、セッションは原則として社内に公開されていて、上手な人の使い方を見て取り入れられます。使い方そのものが共有される仕組みは、ツールの定着にも効いているようです。

記事の後半では、最近よく話題になる「Software Factory」についての考えが書かれています。作るものがはっきりしていれば工場のように型にはめて流すと効率がよい一方で、お客様の課題を深掘りして解き方から考える開発では、仕様を決めるところに何度も戻ることになります。「速く作る」だけでなく「価値を速く作る」ことが必要だという指摘は、前の記事で PM が機能を作り直した話ともつながっています。

### [The fastest gun in UX](https://www.doc.cc/articles/fastest-gun)

> **出典**: Sidebar | **公開日**: 2026-10-22 | **カテゴリ**: design

**3行まとめ**
- スピードを求められたデザイナーがプロセスを省くほど、根拠の弱いアイデアを通したい人に利用されてしまう、という構造を論じたエッセイです
- Stack Overflow で最初に投稿された回答が質に関係なく票を集める現象になぞらえ、プロダクト組織の「早撃ちガンマン」を描いています
- 対抗するには速さで競うのではなく、ストーリーボードや PRFAQ のような低精度の道具で、前提そのものを議論できる状態を作るとよいと提案しています

**詳細解説**

ZIRP（ゼロ金利時代）が終わってから、「デザインの ROI」が再び問われ、デザイナーは成果を速く出すことを求められています。一部のデザイナーはプロセスを短くして応えていますが、それでも「作って、測って、学ぶ」は「作って、作って、作る」のままだと著者は言います。理由として挙げているのが、計画の場で最初に出たアイデアが場の議論を決めてしまう「早撃ちガンマン」の存在です。

この人物は、反対意見を解消するのではなく、わざとあいまいにしたまま、アイデアがロードマップに載るまで時間を稼ぎます。そのときユーザーリサーチは時間のむだどころか、脅威になります。さらに、ペルソナや JTBD のテンプレートを自分の思い込みや LLM の出力で埋め、本物のプロセスを経たように見せる「ポチョムキン・デザイン」という言い方も出てきます。早撃ちガンマンが自分で作れないのは高精度のモックアップだけなので、デザイナーに強い圧力がかかる、という見立てです。

UXエンジニアリングの視点では、AI でモックアップやプロトタイプがすぐ作れるようになった今、この指摘はいっそう重みを持ちます。見た目の完成度が高いものは、前提への疑問を細部の議論で覆い隠してしまいます。著者が「UI はプロダクトではない」と書いているように、モックアップは解決策を見せる道具であって、その前提が正しいかは教えてくれません。

ただし、組織の問題を「ひとりの悪役」に集約する書き方なので、読む側は少し割り引いて受け取るとよいでしょう。実際には、計画の仕組みや評価制度が同じ振る舞いを生んでいることも多いはずです。次に紹介する、リサーチの根拠と意思決定のつながりを残す記事とあわせて読むと、具体的な打ち手も見えてきます。

### [When Research Evidence Stops Surviving Product Decisions](https://medium.com/researchops-community/when-research-evidence-stops-surviving-product-decisions-183579089904)

> **出典**: ResearchOps Community | **公開日**: 2026-10-22 | **カテゴリ**: ux-research

**3行まとめ**
- リサーチのリポジトリに調査結果は残っていても、「なぜこれを作ると決めたのか」というつながりは失われやすい、という問題を扱った記事です
- 根拠、解釈、反証、決定、現在の状態の5つを残す「最小限の系譜（lineage）」を提案しています
- すべてを記録するのではなく、影響の大きい決定だけに絞ること、ツールより運用と担当者が大事なことを強調しています

**詳細解説**

調査の結果は、ロードマップの一文、チケット、スライドへと渡るたびに要約されていきます。記事の例では、「5人の参加者がこの画面で A と B の違いを理解しにくそうだった」が、「ユーザーは B を理解していない」、「B は分かりにくい」、「B を削除する」へと変わっていきます。観察、解釈、一般化した主張、決定は本来別のものですが、受け渡しのたびに前提の条件が落ちてしまう、という指摘です。

提案されている5つの要素のうち、とくに重視されているのが反証（counterevidence）です。支持する根拠は決定と一緒に運ばれやすい一方、合わない根拠は最初の要約で落ちやすいので、専用の欄を設けておくとよいといいます。状態には「現行・反証あり・置き換え済み・古い・未解決」などを付け、古い結論がいちばん見つけやすいまま残る問題を防ぎます。根拠が割れていても決定はできますが、割れていたことが後から分かるようにしておく、という考え方です。

UXエンジニアリングの視点では、AI 時代の意思決定にもそのまま当てはまる話です。エージェントに渡す文脈やスペックが、どの観察から来たのかたどれないと、誤った前提が大量の出力に広がってしまいます。記事には、直近6〜12か月の重要な決定を5つ選び、根拠をたどれるか、決定が今も有効か、といった項目で点検するチェックリストも付いています。新しいツールを入れる前に試せる内容です。

著者は Validation Ledger というプロトタイプを作っていますが、自分が作者なので独立した根拠にはならない、実務での評価もまだしていない、と明記しています。結論が「この製品が必要だ」ではなく「まずツールなしで実践を試せるとよい」になっているのも誠実です。リンク付きの簡単な決定ログで解決するならそれでよく、リンクが保たれないなら、どのツールを買うかではなく、なぜ保たれないのかを考えるとよい、という締めくくりです。

### [How Lufthansa Systems prototypes realistic maps for the cockpit with Figma Make](https://www.figma.com/blog/lufthansa-figma-make/)

> **出典**: Figma Blog | **公開日**: 2026-10-22 | **カテゴリ**: design

**3行まとめ**
- 10万人以上のパイロットが使うコックピット用 iPad アプリ「Lido」のデザインチームが、Figma Make で動く地図のプロトタイプを作った事例です
- 社内の Mapbox ベースの地図や OpenSky Network の航空交通データをつなぎ、本物に近い状態でパイロットに試してもらえるようになりました
- 専門家を相手にするなら、ドメイン知識に投資し、ユーザーと定期的に接するとよい、という助言も語られています

**詳細解説**

Lufthansa Systems は、飛行計画から離陸、巡航、着陸までを支える Lido 製品群を作っています。中心にあるのは、航路やウェイポイント、代替空港、乱気流の層などを表示する動的な地図です。ところが、これまでのプロトタイプは Sketch、XD、Framer と道具を替えても静的なものが中心で、スクリーンショットを見せてもらうフィードバックは「本物らしさ」に欠けていたそうです。

社内ハッカソンで、Mapbox を使った社内の Web 版地図を Make に読み込ませたところから試行が始まりました。さらに OpenSky Network のデータで、現在地から500海里以内の航空機を表示し、タップするとコールサインや機種、相対高度が出るようにしています。パイロットから「フライトトラッカーのようにサイズを変えてほしい」と言われると、FAA の重量区分（super、heavy、large、small）を当てはめるよう指示するだけで反映できたそうです。

UXエンジニアリングの視点では、動的なふるまいを検証できるようになった点が大きいでしょう。どのズーム倍率で交通情報を出せば地図が散らからないかは、静止画では確かめられません。空港内の地図で、離陸した瞬間に機体の色が変わるという規制上の要件も、実際に動くところを見る必要があります。本番は SwiftUI で作られているため、実装の前に何度もパイロットに試してもらえることで、開発に渡す内容の精度が上がったといいます。

チームの取り組みとして、デザイナーは年に1回以上、通常の運航便のコックピットに同乗して観察調査をしているそうです。「専門家と話すには自分も専門家でなければならない」という言葉は、ドメインの深いプロダクトに関わる人には実感があるでしょう。なお、Figma 公式ブログの導入事例なので、ツールの限界や移行の苦労についてはあまり触れられていません。その点は割り引いて読むとよさそうです。

### [How to put your design system to work with the Figma agent](https://www.figma.com/blog/how-to-put-your-design-system-to-work-with-the-figma-agent/)

> **出典**: Figma Blog | **公開日**: 2026-10-23 | **カテゴリ**: design

**3行まとめ**
- Figma エージェントに自社のデザインシステムを正しく使わせるための、文脈の与え方を整理した記事です
- ライブラリの接続、ガイドライン、実例、skill の4種類の文脈を使い分けるとよいと説明しています
- エージェントが同じ間違いをくり返すなら、ガイドラインやライブラリを見直すきっかけにするとよいとしています

**詳細解説**

まずは公開済みのライブラリをエージェントに接続し、承認済みのコンポーネントや変数を使わせます。そのうえで、ライブラリだけでは分からない判断を「ガイドライン」として書きます。ガイドラインはライブラリに添付する指示ファイルで、そのライブラリを有効にしたプロンプトには自動で含まれます。たとえば「チェックアウト画面の『注文を確定』には必ずプライマリボタンを使う」といったルールです。現在は新しくデザインを作るときに効きやすく、既存デザインの編集ではまだ一貫しない場合があると明記されています。

次に、組み合わせ方の実例を見せます。`Examples` というページに置くか、名前の末尾に `_example` を付けたコンポーネントは、エージェントが参照する実例として扱われます（大文字小文字を区別します）。配送先フォームで、どの項目を同じ行に並べるか、任意項目をどう見せるかは、部品だけでは伝わりません。くり返す作業は skill にして、`/design-system-audit` のようにスラッシュで呼び出せます。

UXエンジニアリングの視点では、コーディングエージェントでの CLAUDE.md や skill の使い方と、ほぼ同じ構造になっている点が興味深いところです。命名、プロパティ、バリアント、変数の適用といった、これまで「人が分かりやすいように」整えてきたことが、そのままエージェントへの手がかりになります。デザインシステムのドキュメントを、人とエージェントの両方が読むものとして書き直す時期に来ているのかもしれません。

### [Your product is not the center of the universe](https://apeatling.com/2026/10/19/your-product-is-not-the-center-of-the-universe/)

> **出典**: Sidebar | **公開日**: 2026-10-21 | **カテゴリ**: design

**3行まとめ**
- 自社プロダクトを中心に考え、ユーザーに来てもらうことを前提にする「プロダクト中心」の考え方には期限がある、と論じた短いエッセイです
- これからは、ユーザーと、その人が選んだエージェントを中心に置く「人中心」の考え方が残ると主張しています
- 人中心になってもプロダクトが単なる道具になるわけではなく、UI、専門知識、独自のデータ、実行と運用で価値を出せると述べています

**詳細解説**

### [A simple guide to calm UI](https://maxschmitt.me/posts/calm)

> **出典**: Sidebar | **公開日**: 2026-10-21 | **カテゴリ**: design

**3行まとめ**
- 項目の追加や削除のような普通の UI を「落ち着いた」印象にするための、すぐ使えるルールを、動く例と一緒に紹介した記事です
- ローディング表示を段階的に出し分けないこと、トーストを使わず操作の結果そのものを見せることの2つが基本ルールです
- エラーもトーストで出さない、高さが変わるモーダルは上端に固定する、Enter で送信できるようにする、などの追加ルールもあります

**詳細解説**

1つ目のルールは、ローディング表示を連鎖させないことです。保存ボタンでローディングを出し、ダイアログを閉じてから背景のリストで別のローディングを出すと、画面が何度も落ち着かない状態になります。そこで、背景のリストの再取得が終わるまで保存ボタンのローディングを続け、終わったら一度に反映します。2つ目は、成功を知らせるトーストを出さず、リストに項目が増えたこと自体を確認の代わりにすることです。

追加ルールも実用的です。エラーのトーストはクリックした場所から遠くに出て、しばらくすると消えるので、見逃したユーザーを混乱させます。中央寄せのモーダルは、エラー文が出たり消えたりすると送信ボタンの位置がずれるので、上端に固定するとよいそうです。React なら `<button onClick>` ではなく `<form onSubmit>` を使えば Enter での送信が自然に動きます。ダイアログを開いたら最初の入力欄にフォーカスを当てる、というのも基本ですが見落とされがちです。

UXエンジニアリングの視点では、どれも追加の工数をほとんどかけずに体験を良くできる点がよいところです。ただ、トーストをなくす場合は、スクリーンリーダーの利用者に成功や失敗がどう伝わるかを別に考えておく必要があります。`aria-live` の領域で結果を知らせる、エラーは入力欄のそばに関連付けて出す、といった対応とあわせて取り入れるとよいでしょう。著者も、楽観的更新やアニメーションでさらに磨けると書いていて、ここで紹介しているのは土台にあたる部分です。

### [Native masonry layouts with CSS grid lanes](https://piccalil.li/blog/native-masonry-layouts-with-css-grid-lanes/)

> **出典**: Piccalilli | **公開日**: 2026-10-22 | **カテゴリ**: css

**3行まとめ**
- 長く議論されてきた CSS のメイソンリーレイアウトが、`display: grid-lanes` として形になった経緯と使い方を解説した記事です
- Grid のトラック定義をそのまま使い、ブラウザが各レーンの埋まり具合を見ながら、もっとも空いているレーンへ順に配置します
- 似た高さのレーンをどう選ぶかを決める `fit-tolerance` や subgrid との組み合わせも紹介されています。対応は現在 Safari 26.4 以降のみです

**詳細解説**

議論の始まりは、2017年に Rachel Andrew さんが CSSWG に立てた issue です。その後、Mozilla と WebKit は Grid の拡張として `grid-template-rows: masonry` を、Chromium は独立したレイアウトとして `display: masonry` を提案し、長く平行線が続きました。2025年1月に Grid のトラック定義と配置のプロパティを再利用することで合意し、同年12月に `grid-lanes` という名前に決まった、という流れです。

使い方は通常の Grid とほぼ同じで、`grid-template-columns: repeat(auto-fill, minmax(14rem, 1fr))` のように列を決めれば、行の高さをそろえずに縦に詰めて並びます。`grid-template-rows` を決めると、横方向に詰めるレンガ状の配置になります。`grid-column: span 2` のように複数列にまたがる項目は先に配置され、そのあとで残りが詰められます。Grid の一部として扱うことで、カードの中身を `subgrid` で親のトラックにそろえられる点も、Grid 案が選ばれた理由のひとつだそうです。

UXエンジニアリングの視点では、`fit-tolerance` がおもしろいところです。400px と 398px のレーンがあるとき、2px 短いほうに必ず入れると、ソース順で後の項目が前に飛び出すことがあります。初期値は 1em で、その範囲の差なら同じ高さとみなし、ソース順を保ちやすいレーンを選びます。`infinite` にすると、すき間ができてもソース順を優先します。見た目の順番と DOM の順番がずれるとスクリーンリーダーやキーボード操作で違和感が出るので、詰め具合と読み順のバランスを調整できるのはありがたい設計です。

仕様はまだ Editor's Draft で、細部は変わる可能性があります。今のところ Safari 26.4 以降でしか動かないので、使うなら通常の Grid などをフォールバックとして用意しておくとよいでしょう。WebKit チームの Field Guide to Grid Lanes には、試せるプレイグラウンドとデモがあるので、手を動かして確かめるならそちらも便利です。
