### [Web-Perf Wednesday 018 – Soft Navigations Lift the CrUX Pass Rate](https://csswizardry.com/2026/11/web-perf-wednesday-018-soft-navigations-lift-the-crux-pass-rate/)

> **出典**: CSS Wizardry | **公開日**: 2026-11-18 | **カテゴリ**: css

**3行まとめ**
- 2026年10月の CrUX（Chrome の実際のユーザーから集めた計測データ）で、SPA の画面の切り替わり（ソフトナビゲーション）も数えると、Core Web Vitals の3指標すべてに合格するオリジンの割合が 56.3% から 60.3% に上がります
- サイトが速くなったわけではありません。1つの長いドキュメントを、ユーザーが別のページだと感じる画面ごとに分けて数えるようになったためです
- Google はこの実験的な指標を 2027年5月に正式なものにする予定で、そのあとは Search Console もこちらを使う見込みです

**詳細解説**

指標ごとに見ると、LCP は 68.8% から 73.6%、CLS は 81.6% から 85.0%、INP は 85.2% から 87.0% に変わります。2つめ以降の画面は、最初の読み込みで取ったリソースやアプリの状態を使い回せます。CLS と INP も、セッション全体ではなく画面ごとに評価されます。そのため、実験的な数字と今の数字は別のものを測っている、と整理しています。

今月から CrUX API に `experimental_first_contentful_paint_with_softnavs` と `experimental_navigation_types_with_softnavs` が加わり、CrUX Vis でも同じものが見られます。ナビゲーションの種類の内訳を見れば、数字のうちどれだけがソフトナビゲーションによるものかがわかります。BigQuery には次の月次リリースで入る予定です。

同じ URL・同じデバイスの区分で2つの系列を取り、差の大きさと向きを記録して、差が出ているルートを探すよう勧めています。RUM のツールが同じ画面の切り替わりをナビゲーションとして数えているかも、確かめておくよう書いています。5月に数字が動いたとき、サイトが変わったのか、測り方が変わったのかを見分けられるようにするためです。

同じ号では、Firefox 161 で `NavigationTransition.to` が使えるようになる話も取り上げています。`navigateerror` の処理のなかでも、ユーザーが向かおうとしていた URL を取れるので、失敗したルートの切り替えを行き先ごとに記録できます。

### [Design writing: working with AI agents](https://automattic.design/2026/11/16/design-writing-working-with-ai-agents/)

> **出典**: Sidebar | **公開日**: 2026-11-18 | **カテゴリ**: design

**3行まとめ**
- Automattic のデザインライティングのチームが、UI の文言を書くスキル「agentic-ux-copy」と、AI 動画や読み上げのナレーションを書くスキル「voiceover-scriptwriting」を作りました
- どちらのスキルも、エージェントが書く前に、読み手・声のトーン・制約について質問します。そのうえで、禁止語のリンター（47語と33パターン）と人の判断を組み合わせています
- 裏づけの調査には Jakob Nielsen さんのものもあります。ChatGPT の文章は米国の学年でいう16年生（大学4年）向けの難しさで、8年生向けを頼んでも10年生向けになりました

**詳細解説**

UI の文言のスキルでは、おもに次の3つを守らせます。見出しや機能名、ユーザーの入力をなぞるだけの説明を書かないこと。くり返しを避け、単語だけでなく文の組み立てにも変化をつけること。抽象的なものに具体的な動詞を付けないことです。ブランドの文書があれば、形容詞を並べず、実際の文言の例をもとにした短いブランドファイルにまとめ直します。長い文書だとエージェントは一部しか守らず、語り口はトーンの指示より例のほうが伝わりやすいからです。

ナレーションのスキルは、話す速さを1分130〜150語として、15秒の枠なら30〜40語に収めます。長すぎたら読む速さを上げず、話す中身を1つ削ります。数字は話すとおりに書き直します。「11」は英語なら eleven、スペイン語なら once、ドイツ語なら elf です。

主張や数字は、一字一句そのまま残す決まりです。「2005年から稼働率99.99%以上」を「99.999%を保証」と言い換えると、好みの問題では済まず、法律の問題になるからです。禁止語のリストはモデルの世代とともに古くなるので、管理する人と見直す人を決めておくことも挙げています。

研究にもとづく指針と禁止語の一覧は、Automattic Design System のサイトで公開されています。禁止語のリンターは、エージェントの出力だけでなく、人が書いた文言のレビューにも当てられそうです。

### [Glimm](https://glimm.dev/)

> **出典**: Sidebar | **公開日**: 2026-11-18 | **カテゴリ**: design

**3行まとめ**
- glimm は、React と Next.js のアプリで、画面が切り替わるときに WebGL の光の帯を走らせるライブラリです。約 11 KB で、最初に帯が走るまで WebGL のコンテキストを作りません
- リンクを置き換える `TransitionLink`、コードから画面を移る `useTransitionRouter()`、すべての内部リンクに効く `<InterceptLinks />` の3つのきっかけを組み合わせて使います
- Chrome 157 以降では HTML-in-Canvas を使い、帯に合わせてページそのものも動かします。この部分は実験的な機能で、ほかのブラウザでは通常の帯だけが走ります

**詳細解説**

ドキュメントは、公開や送信が終わったとき、チェックアウトのように画面全体が変わるモード、はっきり別の区域へ移るときに使うとしています。ホバーやメニュー、行の追加のような繰り返しの操作、読み込み中の表示には使いません。迷ったら「changelog や告知で触れるほどの変化か」で決めるよう勧めています。

HTML-in-Canvas を使う部分では、古いページを帯の手前、新しいページを奥に置くので、帯が中身を塗りつぶしません。カード1枚の更新なら、帯はカードのなかだけを走ります。リクエストの最中はページの中身が寄り集まり、結果が返った時点で帯が離れていくので、待ち時間は増えません。失敗したときは帯を出しません。

`pageEffect={false}` でページの動きを止められ、`usePageEffect()` を使えば、ユーザーが切り替えるスイッチも置けます。OS で動きを減らす設定にしている人には、帯そのものを出しません。デザインシステムのモーションの指針に「changelog や告知で触れるほどの変化か」という問いを書いておくと、画面遷移のアニメーションを足すかどうかを、部品ごとに話し合わずに決められそうです。性能の計測値は載っていません。

### [Nudeps: bundler-like imports, none of the baggage](https://lea.verou.me/blog/2026/nudeps/)

> **出典**: Lea Verou | **公開日**: 2026-11-19 | **カテゴリ**: css

**3行まとめ**
- Lea Verou さんが、バンドラーを使わずに、npm で入れたパッケージを `import { createApp } from "vue"` のように名前で読み込めるツール「Nudeps」を公開しました
- `npx nudeps install` を一度実行し、HTML に `<script src="/importmap.js"></script>` を足せば、あとは `npm install` のたびに自動で更新されます
- 依存パッケージにだけ手を加え、アプリのコードは書き換えません。開発中に変更を見張るプロセスも動かしません

**詳細解説**

`npm install` のたびに、必要なファイルを `node_modules/` から `client_modules/` にコピーし、`vue@3.5.45` のようにバージョンを入れたディレクトリ名で平らに並べます。依存関係をたどるのには JSPM のエンジンを使い、import map を差し込むスクリプトを作ります。再実行には npm の `dependencies` フックを使うので、手で動かすコマンドはありません。

Vue、Lit、Three.js、D3、Floating UI などはそのまま動き、Open Props や Bootstrap Icons のような CSS やアイコンのパッケージも使えます。ただし CSS は名前では読み込めないので、URL で指定します。プロトタイプ用の HTML に gsap や Floating UI を足したいときも、バンドラーの設定から始めずに済みます。

JSX や TypeScript の変換には別のツールが要り、対応しているパッケージマネージャーは今は npm だけです（pnpm と yarn への対応が次の予定です）。小さなモジュールが多いパッケージは最初の読み込みが遅くなることがあり、バンドラーとの速さの比較もまだありません。

### [Understanding CSS random()](https://piccalil.li/blog/understanding-css-random/)

> **出典**: Piccalilli | **公開日**: 2026-11-18 | **カテゴリ**: css

**3行まとめ**
- 使えるようになったばかりの CSS の `random()` 関数を、ブログの欄外のメモを1枚ずつ少し傾ける実装を例に解説しています
- `random(-2.5deg, 2.5deg)` のように最小値と最大値を渡すと、その範囲のランダムな値になり、3つめの引数で刻み幅も指定できます
- 乱数の元になる値（シード）は、既定では「要素・プロパティ・その値のなかで何番目の `random()` か」の組ごとに共有されます

**詳細解説**

この共有のしかたのおかげで、メディアクエリで `transform` を上書きしても、`@keyframes` のなかで同じ `rotate(random(...))` を書いても、1枚のメモの傾きは変わりません。逆に、`transform` を上書きするときに `rotate()` を書き忘れると傾きが消えるので、同じ記述を何か所にも繰り返すことになります。

「何番目か」の部分でもつまずきやすくなります。`margin-block: random(1rem, 5rem)` をメディアクエリで `random(1rem, 5rem) random(1rem, 5rem)` に書き換えると、2つめの値には新しい乱数が使われます。

最初の引数に `--random-margin property-scoped` のように名前と範囲を書けば、プロパティ単位で値を共有できます。`element-scoped` は要素ごと、名前だけなら一致するすべての要素で同じ値になります。`fixed 0.5` はシードを手で決める指定で、範囲の端がどう見えるかを確かめるときに使います。名前と範囲のキーワードで1つの引数なので、あいだにカンマを入れない点にも注意が要ります。

ページを読み込むたびに傾きが変わるので、スクリーンショットを比べるテストでは毎回差分が出ます。テストのときだけ値を固定する方法を先に決めておくと、誤検知を避けられます。

### [漠然とした不安を見える形に —— System Risk Recordsを導入して得た3つの安心](https://tech.smarthr.jp/entry/2026/11/19/113553)

> **出典**: SmartHR Tech Blog | **公開日**: 2026-11-19 | **カテゴリ**: design

**3行まとめ**
- SmartHR の届出書類チームは、気になっているリスクを一覧にして優先度を点数で出す「System Risk Records」を、担当の SRE と一緒に導入しました
- 優先度は「インパクト × 発生可能性 × 影響範囲 ÷ 対応工数」で出します。インパクトは、ユーザーに欠かせない一連の操作（CUJ）ができなくなるかどうかを基準に5段階でつけます
- 付箋で書き出したリスクは22件になり、そのうち1件の対応を終え、2件が対応中です

**詳細解説**

付箋に書き出すと、記事を書いた開発者が忘れていたリスクを、ほかのメンバーが挙げていたり、同じリスクを何人もが書いていたりしました。一覧には、問題とあわせて、それで何が起きうるかも書きます。「切り戻しの手順が整っていない」で止めず、「そのため復旧に時間がかかり、使いづらい状態が長引く」まで続けます。

式はユーザー体験への影響が中心なので、点数は低く出ても、話し合いで順位を上げたリスクが2種類あります。1つは、ユーザー体験には影響しなくても、セキュリティの心配が大きいものです。もう1つは、影響するのは一部のユーザーでも、インフラの負荷を通じてほかのユーザーにも広がりうるものです。インパクトの段階は「CUJ の操作ができなくなる」「CUJ の操作でユーザーが不便に感じる」のようにユーザーの操作で書かれているので、デザイナーや PM も同じ表で点数をつけられそうです。

対応はまだ、その開発者と担当の SRE が中心で、スプリントに組み込む流れも決まっていない、と課題を挙げています。

### [5 CSS Values for Easier Text Styling](https://blog.master.dev/5-css-values-for-easier-text-styling/)

> **出典**: Frontend Masters Blog | **公開日**: 2026-11-18 | **カテゴリ**: css

**3行まとめ**
- 文字まわりのスタイルを書くときに役立つ CSS の値として、`unset`、`AccentColor`、`ch`、`from`、`revert-layer` の5つを紹介しています
- `unset` は、継承するプロパティなら親の値を、継承しないプロパティなら初期値を使うので、`h1` などにブラウザが付けているスタイルを打ち消すときに使えます
- `revert-layer` は、上のレイヤーで当てた値を捨てて、下のレイヤーの値に戻します

**詳細解説**

`AccentColor` は本来 OS のアクセントカラーを返すシステムカラーですが、フィンガープリントに使われないよう、ブラウザは標準の青を返します。試作や、OS に似せた飾りの少ない見た目に向いています。`ch` は数字の「0」の幅で、等幅フォントなら `width: 10ch` で10桁の入力欄にちょうど合います。`padding` や `gap` に使えば、文字の大きさに合わせた余白になります。`from` は相対色の構文で、`hsl(from currentcolor h s 45)` のように、元の色をどの表記で書いていても、別の色空間で調整できます。

`revert-layer` の例は、記事本文の見出しを `feature` レイヤーで太く大きくし、引用のなかの見出しだけを `base` レイヤーの既定値に戻すものです。これまでなら、引用のなかの見出しに base の値をもう一度書き写していました。`revert-layer` を使えば、base の値を変えたときに、書き写した側を直し忘れることがありません。
