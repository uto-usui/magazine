### [The Slopnami is an accessibility problem](https://www.soren.work/writing/the-slopnami-is-an-accessibility-problem/)

> **出典**: Sidebar | **公開日**: 2026-11-25 | **カテゴリ**: design

**3行まとめ**
- AI でメッセージや文章、コードを量産すると、送る側の手間は減りますが、そのぶん受け取る側に、読む・見分ける・直す手間が回ってきます。障害のある人ほど、その負担が大きくなります
- 迷惑な連絡、水増しされた文章、見せかけのアクセシビリティ、人にたどり着けない窓口、誤った情報、障害が描かれなくなること、の6つに分けて、障害のある利用者への影響を表にしています
- WebAIM Million の 2026 年の調査では、6年続いた改善が止まりました。1ページあたりの検出エラーは 51 件から 56.1 件に増え、原因の候補に AI を使ったコーディングが挙がっています

**詳細解説**

見せかけのアクセシビリティの例には、自動生成の代替テキスト、確認していない自動字幕、「AI アクセシビリティ」をうたうオーバーレイ、支援技術で確かめずに出した AI 生成の UI が並びます。「笑っている人」のような代替テキストでも属性は埋まるので、監査やコードレビューでは問題なく見えますが、スクリーンリーダーの利用者には何も伝わりません。オーバーレイについては、WCAG に準拠できるとうたった accessiBe に、FTC が 100 万ドルの支払いを命じた件も引いています。

WebAIM Million では、ARIA 属性が1ページ平均 106 から 133 に増えました。ARIA を使うページのエラーは平均 59.1 件で、使わないページは 42 件です。WebAIM 自身は ARIA がエラーの原因だとは言っていませんが、この記事ではこれも「アクセシビリティらしく見えるだけのマークアップ」の例に入れています。エラーの 96% は、7年続けて上位にある6種類（低いコントラスト、ラベルのないフォーム、空のリンクや空のボタンなど）に入ります。

AI が生成したコードについては、支援技術を使うテスターに渡す前に、キーボードとスクリーンリーダーで操作して確かめるよう勧めています。axe のような自動チェックで拾えるのは一部だけ、とも書いています。ただ、上位6種類のような基本のエラーは自動チェックでも見つかります。まず自動チェックを Pull Request に組みこんで基本のエラーを止めておけば、人の時間はキーボードとスクリーンリーダーでの確認に回せます。

### [Mirror mode](https://mattstromawn.com/writing/mirror-mode/)

> **出典**: Sidebar | **公開日**: 2026-11-25 | **カテゴリ**: design

**3行まとめ**
- デザイナーが本番のコピーで作業する「mirror mode」は、本番のコードで作業するやり方と、別にプロトタイプ用の環境を用意するやり方の両方を兼ねます
- `prototype` のような長く続くブランチを本番から切り、定期的に main から rebase します。このブランチ自体はマージせず、できたところから小さな Pull Request に分けて main に送ります
- まだない API は shim（本番のエンドポイントをまねたモックの API）で補います。ある 0→1 の開発では、6か月でモック 100% から本物の API 100% に置き換わりました

**詳細解説**

本番のコードのコピーなので、本番で読み込みが遅い画面はプロトタイプでも遅く、実物に近い条件で試せます。出荷しないブランチなので、コードレビューも CI も通さず、雑なコードのままでかまわない、としています。モバイルアプリの例では、TestFlight で配るプロトタイプにデモ用の切り替えを何十も入れています。認証やオンボーディングを飛ばして利用初日や 100 日目の画面を出したり、エラーの状態にしたり、アカウントを消して退会の流れを見たりできます。デモ用の切り替えだけなら、ブランチの運用まで変えなくても、今あるプレビュー環境に足せます。空の状態やエラーの状態も、実際の画面で触りながらレビューできそうです。

欠点も6つ挙げています。キャンバスの代わりにプロンプトとコードで作業することになり、よく動くぶん、一部がモックだと忘れられやすくなります。本番から遅れると信用を失い、本番のデータへのアクセスを広げるのを嫌がる組織もあります。ほかに、どこまでを実装に回せるのかを示しにくいこと、経営陣が通りがかりに口を出しやすいことも挙げています。デザイナーが事実上エンジニアの組織に入っている小さなチームに向く、としています。記事の最後には、このブランチを用意させるためのエージェント向けのプロンプトも載っています。

### [Web-Perf Wednesday 019 – Firefox Ships Dictionary Compression](https://csswizardry.com/2026/11/web-perf-wednesday-019-firefox-ships-dictionary-compression/)

> **出典**: CSS Wizardry | **公開日**: 2026-11-25 | **カテゴリ**: css

**3行まとめ**
- Firefox 161 が Compression Dictionary Transport に対応しました。ブラウザに前のバージョンのファイルが残っていれば、サーバーはそれを辞書にして、変わった部分を中心に送れます
- 公開されている例では、Brotli だけで圧縮した場合と比べて、1週間分の更新があった YouTube のプレイヤーのバンドルが 90%、CNN の古い React のバンドルが 63% 小さくなっています
- 大きくて更新が多く、再訪も多く、バージョン間の差が小さいファイルに向いています。一度きりのキャンペーン用のバンドルや、毎回作り直されるファイルでは効きません

**詳細解説**

サーバーは、最初に返すファイルのレスポンスに `Use-As-Dictionary` を付けて、辞書として使えることを示します。次に対応するファイルを取りにいくとき、ブラウザは辞書のハッシュを `Available-Dictionary` に入れ、`dcb`（Brotli）か `dcz`（Zstandard）に対応していると伝えます。使える辞書がなければ、これまでどおりの圧縮で返ります。

辞書を使うには安全なコンテキストが必要で、`no-store`、`no-cache`、`max-age=0, must-revalidate` のレスポンスは辞書になりません。キャッシュするレスポンスは `Accept-Encoding` と `Available-Dictionary` で Vary させ、CDN がこのヘッダーを転送してキーに含めるかも確かめる必要があります。MDN ではまだ実験的な機能の扱いです。そのため、段階的な改善として入れ、まずは同じオリジンの大きなファイル1つで、再訪時の転送量と時間を比べるよう勧めています。

ファイル名にハッシュを付けて配るやり方では、1行直しただけでもバンドル全体を取り直すことになります。辞書圧縮があれば、差分を小さくするためにチャンクを細かく分ける工夫を、いくらか減らせるかもしれません。

ほかに、Safari Technology Preview 257 が、広い範囲を覆う `will-change` の要素で作られる合成レイヤーのメモリに上限を設けたことも取り上げています。ブラウザの上限は安全網にすぎないので、あとに実際のアニメーションが続かなくなった `will-change` は消すよう勧めています。

### [タイムズはどうすべきだったのか、JPKI を用いた eKYC の今後](https://blog.jxck.io/entries/2026-11-25/ekyc-over-jpki.html)

> **出典**: blog.jxck.io | **公開日**: 2026-11-25 | **カテゴリ**: web-standards

**3行まとめ**
- タイムズカーの情報漏洩をきっかけに、運転免許証の券面を撮って送る eKYC（オンラインの本人確認）の問題を、関係する法令から整理しています
- タイムズはもともと犯収法の対象外です。券面画像を退会後7年残していたのも、法令ではなく、なりすまし対策と問い合わせ対応のためでした
- マイナンバーカードの JPKI と、免許を統合したマイナ免許証の IC を読めば、本人確認と免許の確認が1枚で済み、券面画像を保存しなくてよくなります

**詳細解説**

券面とセルフィーを送る方式（現行ホ方式）は、犯収法の施行規則で 2027 年に廃止され、IC チップを読む方式に移ります。免許証にはもともと IC チップがあり、スマートフォンでも読めます。それでも広まらなかった理由に、免許の暗証番号を覚えている人が少ないことを警察庁が 2021 年に挙げています。タイムズは券面を撮る方式だったため、マイナ免許証にした人はしばらく借りられませんでした。対応したあとも、警察庁のアプリで読み出した免許情報を画像にして送る、間に合わせのやり方です。

漏洩のあと、タイムズは本人確認書類の画像を全件削除すると発表しました。個人情報保護委員会も、要らなくなった個人データを消すよう注意喚起しています。ほかの事業者にも、慣習で住所や生年月日、電話番号を集めていたフォームを見直す動きがあります。

JPKI を使うには、認定を受けたプラットフォーマーに頼むか、自社で認定を取る必要があります。また、JPKI で取った基本4情報もデータベースに保存すれば、漏れるリスクは残ります。続きの記事では、情報を持たずに確認するための Verifiable Credentials とゼロ知識証明を扱う予定だそうです。

### [AIが速く作っても人の待ちが残っていた —— 開発プロセス全体で減らした合意と、残した確認](https://tech.smarthr.jp/entry/2026/11/25/182704)

> **出典**: SmartHR Tech Blog | **公開日**: 2026-11-25 | **カテゴリ**: design

**3行まとめ**
- AI で実装が速くなっても、人の合意や受け渡しを待つ時間は残っていました。そこで SmartHR のあるチームが、AI の活用をチケットの起票からふりかえりまで広げた記録です
- 全員で合意していた判断と確認を、担当者・AI・レビュアーに分け直しました。1チケットの完了責任を1人に置き、サブタスクとプランニングポーカーをやめ、PBR はスプリントプランニングにまとめています
- 1週あたりの開発に使える時間は約69時間から約93時間に増えましたが、時間あたりの完了 SP は約0.14のまま変わっていません

**詳細解説**

会議を減らす前に、土台を3つ整えています。チケットは What・Why・受け入れ条件・前提条件・やること・やらないこと・検討事項・参考リンクに分けて書き、口頭で決めたことも理由と一緒に本文に残します。着手できる状態（DoR）、完了した状態（DoD）、粒度、SP の基準は文書にしてリポジトリに置き、起票用と詳細化用の Claude Code のスキルが実行時に読みます。AI が案を出し、人が確認して承認する流れです。

QA では、実装者が AI にテストさせ、テストケースと操作前後のスクリーンショットを Pull Request に残します。レビュアーはその証跡を確かめ、足りないときだけ自分で操作します。権限や設定によって結果が変わる、条件の組み合わせが多い変更では、レビュアーがテスト設計を見ます。AI が「成功」を返しても、それだけで完了にはしない、とも断っています。

開発に使える時間が増えたのは、人数より会議が減った影響が大きいと見ています。ただ、人数の増減があり、改善後の期間も4週と短いので、単純には比べられません。品質の前後比較もまだありません。取り入れるなら、減らしたい待ちを1つ選び、やめることと残す確認を先に決めるよう勧めています。

### [Style Queries as Conditional Modifiers](https://css-tricks.com/css-style-queries-as-conditional-modifiers/)

> **出典**: css-tricks | **公開日**: 2026-11-25 | **カテゴリ**: css

**3行まとめ**
- Baseline の Newly Available になった container style queries を、BEM のような修飾クラスの代わりの「条件つきの修飾」として使う方法です。Kevin Powell さんの講座の一部を記事にしています
- コンポーネントに修飾クラスを付ける代わりに、祖先にカスタムプロパティ（`--card-density: compact` など）を置き、コンポーネントの側が `@container style()` でその値を読み取り、見た目を変えます
- 切り替えは、media query、container query、`:has()`、CMS の設定など、カスタムプロパティを置けるものなら何からでもできます

**詳細解説**

例は、サイドバーに並べた関連記事のカードです。テンプレートのループで `card--compact` を付けると、ページの下のほうでも詰まった見た目になり、デザインチームから「そこでは余白を詰めなくていい」と言われます。style query なら、`@media (width > 700px)` のなかで `.sidebar` に `--card-density: compact` を置くだけで、サイドバーが横に並ぶときだけカードを詰められます。Figma のコンポーネントのプロパティも、`--card-density: compact` と同じ名前と値でそろえておくと手軽です。デザインで選んだ「compact」がコードのどの設定に当たるかを、受け渡しのたびに説明しなくて済みます。

横スクロールのグリッドの例もあります。ヒーローが2列になったら、外側のレイアウトで `--overflow-grid-direction: row` を置くだけです。グリッドはその値を style query で読み取り、1列の縦スクロール（`max-block-size: 50vb`）に変わります。外側から子の見た目を直接書き換えないので、レイアウトとコンポーネントが互いに壊しあいにくくなります。

要素は自分自身の値を問い合わせられないので、カスタムプロパティは祖先に置きます。今のところ問い合わせられるのはカスタムプロパティだけです。ボタンをアクセントの色にする程度なら、修飾クラスのほうが向いています。条件とスタイルを別々の場所に置きたいときや、1つの条件で複数のものを変えたいときには、style query が役に立ちます。

### [Motion Design with CSS Anchors](https://blog.master.dev/motion-design-with-css-anchors/)

> **出典**: Frontend Masters Blog | **公開日**: 2026-11-25 | **カテゴリ**: css

**3行まとめ**
- CSS のアンカー位置指定で、要素を結びつけるアンカーを途中で付け替えると、別の場所へ移動するアニメーションを作れます
- ロゴの例では、`@keyframes` のなかで `anchor(--taglineAnc left)` のようにアンカーを指定して、ロゴを見出しの文字のそばからタグラインの両端を通って元の位置まで動かしています
- チェックした ToDo がごみ箱のアイコンへ飛んでいく例や、選んだ時間帯へ赤い点が動く例では、`transition` と `inset` で同じことをしています

**詳細解説**

アンカーがなかった頃は、単語やタグラインの位置と大きさを測り、その座標のあいだを動かす必要がありました。今は、通り道になる要素にアンカー名を付けておけば、どこにあるかはブラウザが計算します。

ToDo の例では、各 `li` に `anchor-name: --todoAnc` と `anchor-scope: --todoAnc` を付けて、項目が自分の `li` にだけ結びつくようにしています。チェックされると `inset: anchor(--trashAnc inside)` と `scale: 0` に切り替わり、縮みながらごみ箱へ向かいます。時間帯の例は逆で、`li:has(:checked)` にアンカー名を付け、アンカーのほうを移しています。

執筆時点の Firefox は、アンカー名の付け替えはできますが、`inset` を滑らかに変化させることはまだできません。用途としては、データの流れ、タイムライン、並べ替え、オンボーディングでマスコットを動かす場面を挙げています。
