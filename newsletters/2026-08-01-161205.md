今回は「やめる」判断が並びました。GitHub の case folding は非 ASCII のバイトで早期脱出する処理を消したら15倍速くなり、TanStack は計測にもとづいて自分のサイトから React Server Components を外しています。NN/g の調査は、UX という名前を付け替える動きに対して代案が育っていないことを示しました。Brad Frost は即時性への期待そのものを手放す話を書き、cassidoo は AI を使わずに自分でアルゴリズムを書いています。21本のなかから15本を詳しく紹介します。

## ハイライト

### [Don't stop early: Case-folding source code at memory speed](https://github.blog/engineering/architecture-optimization/dont-stop-early-case-folding-source-code-at-memory-speed/)

> **出典**: GitHub Engineering | **公開日**: 2026-07-31 | **カテゴリ**: engineering

**3行まとめ**
- ASCII の高速パスでもっとも効いたのは、最適化を足すことではなく「非 ASCII のバイトで早期脱出する」処理を消すこと。3.1 GiB/s から45 GiB/s 超へ
- データ依存のループ脱出が1つあるだけでベクトル化が止まる。本体を分岐なしにしても break が残ると2.6 GiB/s と、かえって遅くなる
- Unicode の折り畳み表は64コードポイント単位のページビットマップとランの区間圧縮で1,776バイトに収まり、UTF-8 をデコードせずバイト空間の加算だけで畳める

**詳細解説**

case folding は、大文字小文字の違いを消して比較できる形に揃える操作です。表示のための小文字化とは目的が違い、ロケールにも文脈にも依存しません。記事はこの区別から入ります。ギリシャ語の語末シグマやトルコ語の I は小文字化の結果が変わるため、`to_lowercase` を代用すると静かに誤った一致が生まれる、という説明が丁寧でした。

GitHub のコード検索エンジン Blackbird は1億8,000万を超えるリポジトリ、480TB 以上のソースコードを索引しています。索引を作る前に全バイトを畳み、検索結果の候補ごとにもう一度畳む。この規模だと、基本操作の速度そのものが問題になります。

読みどころは、素朴な実装から分岐を1つずつ削っていく過程です。非 ASCII を見つけたら `break` する、`A..=Z` の範囲を `if` で判定する、該当したときだけ書き込む——この3つを、アキュムレータへの `OR`、`wrapping_sub` による算術判定、マスクを畳み込んだ無条件ストアに置き換えます。分岐が消えたループは自動でベクトル化され、メモリ帯域に張り付きました。

おもしろいのは、途中の計測が素直に上がらないところです。break を残したまま本体だけを分岐なしにすると3.1 GiB/s から2.6 GiB/s へ落ちます。分岐のある版は書き換えが必要なバイトにしか書き込まないのに対し、分岐なし版は毎回書き戻すからです。「分岐レスはベクトル化の前提としてのみ価値があり、スカラーコードでは悪化しうる」と明記されていて、ここは持ち帰りたい教訓でした。標準ライブラリが採る中間の解——ワード単位で ASCII を走査してから変換する2パス——が23 GiB/s、それを1パスに融合すると8.7 GiB/s まで落ちる、という比較も載っています。

テーブル設計のほうも読ませます。非 ASCII のパスであっても、大半の文字は畳まれません。だから本当に速くしたいのは「畳むかどうか」の否定判定であって、畳む処理そのものではない。ハッシュマップはヒットに最適化された構造なので、ミス主体のこのワークロードには形が合わない、という指摘が的確です。ページビットマップで1ビット照会し、立っていたときだけラン表を引く。ランの並びは SWAR で8バイト同時に比較する。折り畳みはリトルエンディアンのバイト加算1回で済ませる。合計1,776バイト、1エントリあたり9.6ビットに収まりました。

UXエンジニアリングの視点では、これは検索の待ち時間を支える基盤の話です。体感に出るのは索引の鮮度と結果の速さで、そこに至るまでの層は普段見えません。ただ、この記事の構図——「速くするために足す」のではなく「早めに止める判断をやめる」——は、上のレイヤーでも見かける形だと思います。前提条件（well-formed で最短形の UTF-8 であること）を明示している点も誠実でした。数値は Apple M4 での測定で、マイクロアーキテクチャが変われば比率ごと動きうる、と自分で断っています。

### [No New Name Has Replaced "UX"](https://www.nngroup.com/articles/no-new-name-ux/)

> **出典**: Nielsen Norman Group | **公開日**: 2026-07-31 | **カテゴリ**: design

**3行まとめ**
- 定義文だけを見せて分野名を答えてもらう間接的な聞き方で、604人の70%が UX 系の言葉を使った。「UX」単独で47.8%
- 代案として語られる「experience design」を含む回答は4件、「human」を含む回答は5件。代替ラベルは分散したまま
- 「product」を使うかどうかは職種に強く依存する。プロダクトマネージャーの38%に対し、UX 実務者は10%

**詳細解説**

レイオフ、予算の縮小、価値を証明し続ける圧力。そうした状況のなかで「UX という呼び名がもう役に立っていないのでは」という議論が続いています。NN/g はこれを、2026年4月に604人へ聞いた調査で確かめました。

調査手法の工夫がこの記事の見どころです。「この分野をどう呼びますか」と聞くと、流行の言葉を復唱させてしまう。そこで UX という語を出さずに定義文だけを提示し、「これはどの職種・分野の仕事だと思いますか」と1つだけ答えてもらいました。思い浮かぶ言葉を拾う設計です。

結果として、UX 系の語が70%を占めました。対抗する語は見当たらず、UX 以外の回答も「consumer-behavior research」「digital-experience strategy」「journey management」といった具合に散らばっています。まとまった代案が育っていない、というのが結論でした。

職種による差の分析も収穫があります。「product」を使ったのは全体の12%ですが、プロダクトマネージャーでは38%、プロダクトデザイナーでは27%、UX 実務者では10%。統計的に有意な差だと書かれています。自分の肩書きに入っている言葉で仕事を説明する、という当たり前の傾向が数字で出た形でしょう。

UXエンジニアリングの視点だと、この職種差はそのまま職能横断チームの摩擦です。同じ画面について話しているのに、ある人は「プロダクトの判断」と呼び、別の人は「UX の課題」と呼ぶ。呼び名が違うだけなら実害は小さいのですが、責任範囲の認識までずれていることがあります。記事の提案——名前を探すより、どの意思決定を良くしてどのリスクを避けたかを示す——は、その摩擦への現実的な答えだと思います。

限界も自分で挙げています。NN/g のチャネルで集めた回答者は UX 寄りに偏りうること、地域の代表性がないこと。そして「思い浮かぶ言葉」を測っただけで、「どの言葉がもっともよく伝わるか」は別の調査が要る、という区別も明確でした。

### [AI fluency isn't the finish line](https://www.figma.com/blog/ai-fluency-isnt-the-finish-line/)

> **出典**: Figma Blog | **公開日**: 2026-07-31 | **カテゴリ**: design

**3行まとめ**
- ツールの習熟は入場料であって到達点ではない。差が付くのは共有できる仕組みを作る力、意思決定へ導く力、チームで学び合う力
- 社内向けの道具を作れる人が増えた。一人が10倍速くなるより、チーム全体が10倍速くなるほうが効く
- 回答者の47%が、チームとリーダーの導入速度のずれを挙げた。20%は現場が先行、27%はリーダーが押しているが現場が追えていない

**詳細解説**

「ツールを学ばないと取り残される」という投稿がタイムラインに溢れている、という書き出しから始まります。Figma の2026年 AI レポートでも、大多数がツールの習熟を重要だと答えている。そのうえで、ツール以外の部分はどうなのか、という問いを立てた記事です。

具体例が地に足がついています。AI レポートを作ったとき、研究者の Shane Johnston は調査データを載せた対話的なサイトを vibe-coding しました。「文脈とデータが自分の頭とマシンに閉じずに済んだ」という言葉が引かれています。Brand Studio は Figma Make で画像エフェクトの生成器を作り、チームの誰でもワンクリックでブランドに沿ったテクスチャを当てられるようにしました。共有プロトタイピング環境を作った例も出てきます。

意思決定の話も具体的でした。方向性を何十本も生成できるようになったからこそ、そこから1つに決めるファシリテーションの重みが増している。誰を呼ぶかの基準として、反対意見を持つ人、経緯を知っていて選択肢を1つ消せる人、リスクを先に見つけられる人が挙がります。内製アプリを作ったチームが、公開範囲外の社内プロジェクトを従業員が知っていることに気づき、そこで初めて情報が漏れていたと分かった、という例も出てきます。データガバナンスの担当を先に呼んでいれば防げた話です。

会議の前に文脈を渡す工夫も紹介されています。Figma の PM はプロトタイプの各フローを Loom で録画するか、注釈を付けた FigJam を共有しておく。会議の時間を説明ではなくトレードオフの検討に使うためです。

UXエンジニアリングの視点で刺さるのは、「一人が10倍」と「チームが10倍」の対比でしょう。プロンプトライブラリや社内エージェントは、個人の勘所をチームが読める形に変える手段です。作れる人が増えたぶん、その投資判断が現場に降りてきたともいえます。摩擦を見つけて取り除く、という感覚はプロダクトの仕事そのもので、対象が自分たちのワークフローになっただけ、という整理も納得がいきました。

ただし、根拠として引かれているのは Figma 自身のレポートです。ツールを売る側の立場が混じることは割り引いて読みたいところ。とはいえ、導入速度のずれを47%が挙げたという数字は、押す側と押される側のどちらから見ても心当たりがある話だと思います。

### [The AI aesthetic](https://blog.jim-nielsen.com/2026/ai-aesthetic/)

> **出典**: Sidebar | **公開日**: 2026-07-31 | **カテゴリ**: design

**3行まとめ**
- ✨ は AI を意味する記号になった。時代ごとに固有の UI 語彙が生まれ、一部はハンバーガーメニューのように定着していく
- ストリーミングテキストはチャットに固有だが、「シマーするテキスト」は非同期処理一般の表現として広がり始めている
- AI アプリのアイコンは OS 標準より小さく細い。macOS の Finder や Mail と並べると粒立ちの違いがはっきり出る

**詳細解説**

Jim Nielsen による短いエッセイですが、視点が良いので取り上げます。時代ごとの制約から生まれた UI の言い回しには、流行とともに消えるものと、既存の相互作用のパターンに溶け込むものがある。ハンバーガーメニューは後者で、画面サイズの制約から広がったあと、「ここにメニュー的な何かがある」を短く示す記号として残りました。

AI の時代に生まれた語彙も同じ分岐点にいる、というのがこの記事の見立てです。ストリーミングテキストはチャットのために作られ、チャットで洗練された表現なので、ほかへの転用は効きにくい。一方、シマー（きらめきが左から右へ流れる）は AI の文脈では「考えている」を意味していたのに、いまや取得中・計算中といった非同期処理一般の表示に使われ始めている。

無意識に拾っているものとして挙げられるのが、アイコンの小ささです。Claude、Codex、Cursor のサイドバーと、Finder、Photos、Mail を並べたスクリーンショットが載っていて、AI 側だけ明らかに細く小さい。Electron アプリだとシステムの粒立ちとぶつかるので目立つ、という説明でした。ベージュとクリーム、オレンジのアクセント、セリフ体という配色・書体の傾向にも触れています。

もう1つ挙がっているのが、トグルを押すと UI 全体が再描画されて、もう一度押すにはマウスを動かし直さないといけない、というもぐら叩きのようなコントロールです。「AI の非決定性が UI/X にも染み出している」という書き方が的確でした。

UXエンジニアリングの視点でいうと、この記事は自分たちの語彙を点検するきっかけになります。シマーを「AI 機能だから」使っているのか、「非同期だから」使っているのか。デザインシステムに AI 専用のトークンを足すのか、非同期状態の表現として一般化するのか。実装の分岐点としてはっきりしています。アイコンの大きさも、ブランドの一貫性とプラットフォームへの適合のどちらを取るかという、昔からある判断の新しい現れ方でしょう。

### [Things Take the Time They Take: A 42nd Thought at 42](https://bradfrost.com/blog/post/things-take-the-time-they-take-a-42nd-thought-at-42/)

> **出典**: Brad Frost | **公開日**: 2026-07-30 | **カテゴリ**: design-systems

**3行まとめ**
- 「9人集めても1か月で赤ちゃんは作れない」。good, fast, cheap から2つを選ぶという三角形はいまも成り立つ
- 生成の道具で作ることが即時になるほど、即時性への期待も上がる。そのずれが焦りや罪悪感を生む
- 前のコンロと後ろのコンロ。大きなアイデアは弱火でゆっくり煮て、ときどきかき混ぜる。週次や月次のリズムが効く

**詳細解説**

Brad Frost が誕生日ごとに書いている連作の42番目です。R/GA 時代に聞いた言葉から始まります。人を増やしても縮まらない時間がある、という当たり前の話に、多くの人が賢い抜け道を探し続けてきた。どれもうまくいかなかった、と。

そのうえで、体感の変化を書いています。デジタルが即時の豊かさをもたらし、配送にかかる時間の期待値も、待つ意思そのものも変えてしまった。生成の道具が加わって、作ることまで即時になった。便利さは本物で、新しい可能性も開くけれど、代償もある——という書き方で、道具そのものを否定してはいません。

品質のつまみを下げられない、と自分について書いているところが率直でした。「今回は手を抜いて早く出す」と宣言した仕事でも、結局できない。人によっては時間とお金の制約に合わせて調整できるのだろうけれど、自分には無理らしい、と。

いちばん実用的なのは、前のコンロと後ろのコンロという語彙でしょう。前のコンロは請求書を払っている大きな仕事で、注意の大半を持っていく。後ろのコンロには、じっくり煮ておけばいい大きなアイデアが載っていて、ときどきかき混ぜる。週ごと、月ごとの拍を作ると、その軽い接触の積み重ねがアイデアを形にしていく。

UXエンジニアリングの視点では、デザインシステムや基盤の整備が典型的な後ろのコンロだと思います。四半期の目標に正面から載せると窒息するのに、完全に降ろすと消えてしまう。週に一度だけ手を入れる、という進め方は実際に運用できる形です。そして、生成 AI で試作が数分で作れるようになったいまのほうが、「作れた」と「使えるようになった」の距離はむしろ開いている気がします。時間をかけたと分かるものを評価したい、という結びは、その距離を意識した言葉として読めました。

### [Why You Need Mentorship and How to Get It Right](https://www.nngroup.com/articles/mentorship/)

> **出典**: Nielsen Norman Group | **公開日**: 2026-07-31 | **カテゴリ**: design

**3行まとめ**
- メンターシップは若手のものではない。昇進、報酬、キャリア満足度、燃え尽きの少なさに、研究で裏付けのある効果がある
- 上司をメンターにしない。キャリアを握られている相手には率直になれず、得られるものが目減りする
- 毎回1つのアクションアイテムを持ち帰り、次回の冒頭で結果を報告する。この2つを飛ばすと関係が続かない

**詳細解説**

著者の実体験から始まります。UX 成熟度の低い組織で一人デザイナーとして働いていたころ、開発者たちがユーザー調査を止め、納期のためにデザインを削っていくことに腹を立てていた。協力者ではなく障害物として見るようになっていた、と。数年後、同じ会社を離れた開発リーダーにメンタリングを受けて、実は開発者たちも決定権を持たず、経営から強い圧力を受けていたと知ります。もっと早く聞いていれば、関係も成果も何年か早く良くなっていた——この導入が効いています。

定義としては、経験のある人が長期にわたってキャリアの指針や組織の見取り図を提供する一対一の関係です。年数が上とは限らず、新しい潮流について若手が年長者を導くリバースメンタリングもある、と補足されています。

効果は研究で裏付けられていて、昇進の増加、キャリア満足度と定着意欲の向上、報酬の伸び、燃え尽きの減少が挙がっています。メンター制度を持つ組織では、周縁化されがちなグループの昇進・定着・管理職比率が最大24%上がるという研究も引かれていました。

うまくいかない理由も列挙されています。率直に話せない相手を選ぶ、助言を実行に移さない、頻度がばらつく、メンター側に必要な知識や人脈がない、目標を伝えていないので助言の方向が定まらない。選び方の基準は、2〜3段階上の役職、業界や自社を理解している、メンタリングの実績がある、そして同時に抱えるメンティーが1〜2人までであること。有料の短期セッションはコーチングであってメンターシップとは別だ、という線引きも明快でした。

内部か外部かの整理も実用的です。社内のメンターは政治的な読みや組織固有の知識を渡せるけれど、強い信頼が要る。数年以内に円満に辞めた元同僚のような「自社を知る外部」は、率直さと文脈のバランスが良く、信頼の薄い職場でとくに効く。まったく縁のない外部は視野の広さで勝る、という具合です。

UXエンジニアリングの視点でいうと、デザインとエンジニアリングを行き来する立場は、社内に同じ経路を通った人がいないことがよくあります。そのぶん外部メンターの相対的な価値が高い領域だと思います。「上司をメンターにしない」は 1on1 の設計と衝突するように見えますが、役割が違うだけでしょう。1on1 は評価と実務の場、メンターシップは評価から切り離して率直に話せる場です。セッションの5ステップ（近況、事前のアジェンダ共有、記録、1つのアクションアイテム、次回冒頭での報告）は、そのまま持ち帰れる形になっています。

### [A simple clustering algorithm for lists](https://cassidoo.co/post/clustering-tiles/)

> **出典**: Sidebar | **公開日**: 2026-07-31 | **カテゴリ**: design

**3行まとめ**
- 子どものマグネットタイルを仕分けているうちに見つけた手法。末尾と同じ値を右から探し、その間を反転する操作を繰り返してグループ化する
- pancake sort に近いが、こちらは整列ではなくクラスタリングが目的。入れ子の while で書いたので O(n^2) の貪欲法
- AI を使わずに手で書いたと明記されている。人間なら一目で掴んで一手でひっくり返せることが、計算機には易しくない

**詳細解説**

Cassidy Williams が、子どもと Magna-Tiles で遊びながら見つけた並べ替えの手つきを、そのままアルゴリズムに起こした記事です。

手順はこうです。`bgogbrbroorrgbgorrbggo` のようなリストがあるとき、末尾の値（この場合 `o`）を見て、それと同じ値で末尾にいちばん近いものを探し、その間を反転する。すると `o` が末尾にまとまります。次は末尾に来た `r` について同じことをする。右端のクラスタが完成したら、右から見て未完成の次のグループへ移り、また反転する。これを繰り返すと `bbbbbrrrrrrggggggooooo` に収束します。記事には各ステップの状態が全部書き出されていて、追いかけやすい構成でした。

コードも載っています。最初は再帰で試して（マージソートに似た形になりそうだと思ったそうです）、結局は入れ子の while ループのほうが素直に書けた、と。手作業での試行錯誤が要って疲れた、という感想も添えられています。

いちばんおもしろいのは最後の節でしょう。この問題は、目の前に実物がある人間のほうが計算機より簡単に解ける。人間の目は状態を `O(1)` で読み取れるし、群れをまとめて掴んで一手でひっくり返せる。計算機にとってはどちらも自明ではない、という指摘です。

UXエンジニアリングの視点だと、この非対称性は直接操作の UI を設計するたびに出てきます。物理的に「まとめて掴む」動作を画面に翻訳しようとすると、選択、範囲の指定、順序といった余分な段が挟まる。人間には易しく計算機には難しいものを、そのまま計算機の手順に写さずに済むインタラクションを探すのが仕事の一部だ、とも読めました。

効率的でも実用的でもない、と著者自身が認めています。アルゴリズムの実用性を目当てに読むものではありません。それでも、AI に書かせずに手で考える時間の価値を思い出させてくれる記事でした。

### [Vercel Passport is now generally available](https://vercel.com/changelog/vercel-passport-generally-available)

> **出典**: Vercel | **公開日**: 2026-07-31 | **カテゴリ**: frontend

**3行まとめ**
- 自社の ID プロバイダ（Okta、Microsoft Entra ID、任意の OIDC）でデプロイを保護し、検証済みの ID トークンをアプリに渡す機能が一般提供に
- `getIdentity()` で訪問者を読める。ローカル開発では設定可能な開発用 ID が返るので、同じコードパスがそのまま動く
- グループ所属などのクレームを載せられるようになった。下流のサービスへ転送して `verifyIdentity()` で検証でき、JavaScript 以外からは JWKS を使って標準的な JWT として扱える

**詳細解説**

デプロイの保護を、共有パスワードではなく既存の ID 基盤に寄せる機能です。訪問者はアプリに到達する前にプロバイダで認証し、Vercel が署名済みの ID トークンをデプロイへ転送します。

設計で目を引くのは、クライアントが送ってきた `x-vercel-oidc-passport-token` ヘッダーの値を剥がしたうえで、検証後のトークンを注入する点です。アプリのコードが受け取る時点で検証は済んでいる、という保証になります。`subject` はチームと Vercel Connect アプリにスコープされた安定 ID、`externalSubject` はプロバイダ側の ID、と役割が分かれているのも扱いやすそうです。

認可の材料としては、`groups` スコープを要求してクレームを許可リストに入れると、所属グループがトークンに載ります。下流のサービスへベアラートークンとして転送する場合は `verifyIdentity()` が署名とクレーム、そして期待するプロジェクトと環境から来たものかを確認します。JavaScript 以外の言語からは公開された JWKS を使えるので、言語をまたいだ構成でも組めます。

運用まわりも一通り揃っています。認証が成功するたびに `passport-access-granted` イベントが Activity Log と Audit Logs に残り、訪問者と保護対象のホスト名、プロジェクトが記録される。Webhook や cron、CI からのアクセスは Protection Bypass for Automation か Trusted Sources で迂回できます。ここで注意が要るのは、Passport がデプロイのルートより手前、Vercel のネットワーク側で動くため、バイパス用のシークレットは元のリクエストに含まれている必要があること。自分のミドルウェアで後から足すのでは間に合いません。staging や qa といったカスタム環境にも対応しました。

UXエンジニアリングの視点では、プレビュー環境の共有が地味に困る領域だったことを思い出します。パスワードを共有するか、リンクを知っていれば誰でも見られる状態にするか。前者は流出したら終わりで、後者は検索に載る事故が起きる。IdP で認証したうえで「誰が見ているか」がアプリまで届くなら、プレビュー環境で役割別の表示を試すこともできそうです。ステークホルダーに見せるときの体験そのものを設計できる、という意味では効きます。ただし Enterprise プラン限定なので、選択肢に入るチームは限られます。

UXエンジニアリングの視点でいうと、この種の調査は結果が出たときの使い道がはっきりしています。自分の職場で感じている息苦しさや変化が、業界全体で起きていることなのか、それとも自分たちの組織に固有の問題なのか。それを切り分ける材料になります。とくに AI 導入の速度差やそれによる負荷は、社内だけを見ていると個人の適応の問題に見えてしまいがちです。

設計として妥当だと思うのは、全設問を任意にして匿名参加も選べるようにしている点でしょう。健康や世界観まで踏み込む以上、答えたくない項目を飛ばせることは前提になります。回答者の層が偏る（こうした調査に届く人は限られる）という限界は毎回付いて回りますが、同じ設問で経年比較ができることに価値があります。まだ回答を受け付けている段階なので、関心があれば参加してみるのも良さそうです。
