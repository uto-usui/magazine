### [Better code, fewer tokens: The benefits of Code Connect in MCP](https://www.figma.com/blog/the-benefits-of-code-connect-in-mcp/)

> **出典**: Figma Blog | **公開日**: 2026-08-05 | **カテゴリ**: design

**3行まとめ**
- Code Connect を設定した状態で Figma MCP を使うと、コーディングエージェントの出力品質が 1〜4 の Likert 尺度で 1 段階上がった
- トークン使用量は中央値で 29.5% 減、所要時間は 19.6% 減。27 のテストケースで検証している
- 効果の大きさを決めるのは Code Connect のカバレッジ。デザインのうちどれだけがデザインシステムのコンポーネントで、そのうちどれだけが接続済みかで結果が変わる

**詳細解説**

Figma MCP の `get_design_context` が返すのは、キャンバス上の見た目を React で記述したものです。視覚的には正しいのですが、それが自社コードベースのどのコンポーネントに対応するのかをエージェントは知りません。結果として、自前でコンポーネントを作る、デザインシステムから違うものを選ぶ、正しいものを見つけるまで探し回ってトークンを消費する、といったことが起きます。

Code Connect のテンプレートがあると、生成される React の一部が本番コードのスニペットに置き換わります。記事の例では、`div` と `button` を並べた tablist が `<SegmentedControl value="design" options={["Design", "Code"]} />` の一行になります。どのコンポーネントを import し、どのプロパティに何を渡すかまで指定された状態でエージェントに届くわけです。

評価の作り方も参考になります。Figma の例示用デザインシステム SDS（MCP 応答の 20% が Code Connect スニペット）と、社内の大きめなデザインシステム FPL（同 6%）の2つを用意し、correctness / code quality / maintainability / completeness / best practices の観点で LLM を判定役に据えました。モデルは Claude Sonnet 4.5 と Claude Opus 4.7、外れ値をならすため複数回実行し、一部のランは 24 時間を超えたそうです。

品質の中身がとくにおもしろいところ。Code Connect なしのランでは、見た目は近いのにタブが動きません。選択状態がハードコードされていて、インタラクションが存在しないのです。エージェントは `node_modules` を漁り、アイコン名を広く grep し、300 行ほどの CSS を書いていました。ありの場合は本物の Tabs と Button に直接手を伸ばし、77% の時間・62% のトークンで終わっています。

UXエンジニアリングの視点では、「見た目は合っているのに動かないタブ」はデザインとコードの対応関係が失われたときに出る典型的な劣化で、スクリーンショットのレビューでは見落としやすい種類のものです。Code Connect はエージェント向けの投資というより、デザインシステムの意味をコード側に書き戻す作業といえます。カバレッジが効くという結果は、部分的な整備でも比例して効くことを示す一方、デザインシステムのコンポーネント比率が低い画面では効果が薄いことも意味します。数字は Figma 自身の評価なので、自分たちのデザインシステムで測り直す前提で読むのがよいでしょう。

### [Claude Skills for content design: inside Intuit's AI build](https://uxcontent.com/claude-skills-for-content-design-inside-intuits-ai-build/)

> **出典**: UX Content Collective | **公開日**: 2026-08-05 | **カテゴリ**: ux-writing | **著者**: Sarah Mohs

**3行まとめ**
- 社内調査では、デザイナーが1つのフローをAIで設計するのに 30〜50 回プロンプトを繰り返し、文言は最後に回されていた
- コンテンツ標準を Claude の skill 群として束ね、共有リファレンスを1つ持つ「ハブ」型のプラグインに再設計した
- 社内AIマーケットプレイスで公開 24 時間後にインストール数2位。PRレビュー用のエージェントに組み込む使い方も出ている

**詳細解説**

問いの立て方が鋭い記事です。Intuit のコンテンツシステムチームは、AI支援のデザインワークフローを観察して、デザイナーが構造・インタラクション・トークンを何十回も直したあと、最後に「このカードには何と書く?」と考えていることを見つけました。そこから「コンテンツが生成される層に標準が置かれていないなら、それはまだシステムの一部なのか」という問いに至ります。

すでにサイトを Markdown 化し、Cursor や Claude 向けの skill も試していましたが、見つけてもらえない・バージョン管理ができないという壁がありました。転機になったのは、社内で検証済みの skill を登録・検索・インストールできるディレクトリが作られていたことです。更新が自動で配布される仕組みがあるなら、プラグインにする価値があります。

アーキテクチャの検討過程が読みどころです。当初は skill ごとにリファレンスのフォルダを持たせていましたが、それでは source of truth が分裂し、標準が変わるたびに重複ファイルを更新することになります。FigJam で複数のモデルを比較し、共有リファレンスを持つ1つの「ハブ」から専門 skill に自動ルーティングする形に落ち着きました。retrieval の精度、トークン消費、保守の手間の3点でこれが有利だったといいます。

ロジック側は人の手で棚卸ししました。skill 同士の重複や、同じ条件を取り合っている箇所を洗い出し、skill の description も書き直しています。トリガーとなる表現を、コンテンツデザイナーが自分の仕事を語るときの語彙ではなく、デザイナーが実際に使う言い方に合わせた、という判断が効いています。skill の description は実質的に検索インターフェースなので、ここは使う人の言葉で書くのが理にかなっています。

効果の実例も具体的です。プラグインなしのモデルは、あるトースト表示を「すべての標準を満たしている」と誤って判定しました。プラグインを有効にすると toast-writer skill が走り、必要なリファレンスを読み込んで、確認系のガイドラインに沿った指摘を返します。「Claude が style guide に反することを本当にやりたいのか聞いてくるようになった」というフィードバックが微笑ましいところ。

いちばん厄介だったのはパッケージングで、社内ガイドが開発者向けに書かれていたため読み解くのに苦労し、179 回のコミットと大量の Slack のやりとりを要したと正直に書かれています。もっとも役に立ったリソースは人間だった、という結びも誠実です。そして著者自身が「このプラグインはシステムをスケールさせるが、craft はスケールさせない」と書き添えています。ガイドラインの配布経路を設計する話として、デザインシステムのドキュメントを持つチームには直接刺さる内容でしょう。

### [Developers are attached to tools because tools encode trust](https://stackoverflow.blog/2026/07/29/developers-are-attached-to-tools-because-tools-encode-trust/)

> **出典**: Sidebar | **公開日**: 2026-08-05 | **カテゴリ**: design

**3行まとめ**
- Stack Overflow の Developer Survey では、AIの利用率が 76% から 84% に上がる一方、信頼は 40% から 29% に下がった
- ツールはプロセスを符号化したものにすぎず、プロセスそのものではない。エージェントは既存プロセスの欠陥を露出させた
- 新しいボトルネックはコードレビュー。責任の所在を人に置き、暗黙知を context として明示していく方向

**詳細解説**

導入は Vim と Emacs の話から始まります。初心者には秘密の呪文を覚えないと使えない端末プログラムに見えても、習熟した人には考えるのと同じくらい自然に感じられる。『達人プログラマー』が言う「手の延長のように感じられる鋭い道具」です。ここに信頼が宿る理由として、記事は予測可能性を挙げます。包丁の形と重さと刃の付き方が毎回変わるなら、そのつど覚え直すことになり、信頼は育ちません。

対比として引かれる Bjarne Stroustrup の言葉が効いています。「コードは解の正確な記述だ」「英語は、曖昧であってはならないものを表現するには出来の悪い言語だ」。IDE やコンテナ、静的解析には役割の境界がありましたが、AIはソフトウェア開発ライフサイクル全体に入り込みます。だから不信も全体に及ぶ、という整理です。コードの生産は速くなっても、本番障害を起こさないと信じられる状態まで持っていく検証のほうが時間を食うようになりました。

そのうえで記事は、リンターやユニットテスト、CI/CD といった既存の道具が「プロセスを符号化していただけで、プロセスそのものではなかった」と指摘します。優れた CI/CD があってもリリースが速くなるとは限らず、優れた IDE が良いコードを保証したわけでもない。プロセスの一部は文化として、つまり人の振る舞いや規範として存在していました。壊れたプロセスに良い道具を足しても、やはり壊れたままです。

責任の話では Honeycomb の CTO、Charity Majors の発言が痛快です。「human-in-the-loop なんて、お情けで呼ばれた客みたいな響きだ。ループを作ったのは私で、私が持ち主で、そのループが存在する理由も私だ」。コミットを push した人がそのコードを持ち、PR を承認した人がその承認を持つ。金曜に本番を壊してもIDEのせいにしなかったのだから、いまエージェントのせいにするのも筋が通らない、という整理です。

デザインシステムを持つチームに直接刺さるのは、Bit の Laly Bar-Ilan の指摘でしょう。「DRY が私たちの主要な原則なのに、今のAIは本質的に WET だ。あるデベロッパーが『ボタンを作って』と言えば喜んで作り、別のチームの誰かが頼めばコードベースにまたボタンが増える」。前述の Figma の記事と同じ問題を、別の角度から言い当てています。最後に Anil Dash の「6年動いている質素な bash スクリプトで十分だ」という一言で、非決定的な仕組みを何にでも当てはめようとする空気を冷ましています。なお記事は Stack Overflow 自社製品への導線を含むので、そこは割り引いて読むとよさそうです。

### [The AI productivity gap](https://bjorg.bjornroche.com/management/ai-productivity-gap/)

> **出典**: Sidebar | **公開日**: 2026-08-05 | **カテゴリ**: design

**3行まとめ**
- シニアの1日を作業別に分解すると、コーディングが3倍速くなっても短縮は 1.25 時間、約 15% にとどまる
- ジュニアはコーディングの比率が高いぶん恩恵が大きく約 25%。「AIがジュニアの仕事をするから」という採用判断とは逆の結果
- AIが書いたPRDやチケットを読むほうがかえって時間がかかる、という逆効果にも触れている

**詳細解説**

「AIでプロトタイプ並みの速さで本番機能が出てくるはず」という経営側の期待と現実のズレを、時間の内訳で説明した記事です。シニア開発者の8時間を分解すると、新規コードを書く時間は 1.5 時間しかありません。ここが 0.5 時間になっても、設計とアーキテクチャの 1.0 時間、コードレビューの 0.75 時間、ドキュメントと管理業務の 0.75 時間、会議の 1.5 時間はそのままです。

おもしろいのは、増える項目も見積もっているところ。新しいコードが増えるぶん、テストやCI/CD、デプロイの時間は 0.5 時間から 0.75 時間に増えると置いています。合計は 8.0 時間から 6.75 時間、短縮は約 15%。ジュニアは新規コードに 2.75 時間を使っているので、同じ計算で 8.0 時間が 6.0 時間になり、約 25% の改善になります。

この非対称性から出てくる示唆が本題です。「AIがジュニアの仕事をするようになったので、シニアしか採らない」という判断は、恩恵の大きさの順序と逆を向いていることになります。とくにAIを学習の道具として使えるジュニアほど伸びしろがある、という指摘です。著者は doorman fallacy（ドアマンの職務をドアを開けることだと誤認する誤り）にも触れ、良いコードを書けることは前提条件にすぎず、システムについて考えられること、難しい問題を人と一緒に解けること、曖昧な要求を具体的な作業に分解できることのほうが仕事の中心だと述べています。

フロントエンドの仕事でも構造は同じでしょう。実装そのものよりも、どの状態を用意するか、既存のどのコンポーネントに寄せるか、アクセシビリティの扱いをどうするかといった判断に時間が溶けます。生産性を測るなら、書いた量ではなく仕様の曖昧さがどれだけ減ったかを見るほうが実態に合います。数字は著者の経験に基づく試算で、注記でも「具体的な値には議論の余地がある」と認めているので、構造の議論として読むのが妥当です。

### [This Week In React #293](https://thisweekinreact.com/newsletter/293)

> **出典**: This Week In React | **公開日**: 2026-08-05 | **カテゴリ**: frontend

**3行まとめ**
- Next.js 16.3 が正式リリース。App Router に Instant Navigations が入り、開発サーバーのメモリ使用が最大 90% 減
- TanStack Table V9 が2年越しで到達。tree-shakable なプラグイン構成と TanStack Store ベースの状態管理に置き換わった
- GitHub の stacked PR が public preview に。base の自動付け替えと gh-stack CLI が付く

**詳細解説**

Next.js 16.3 は中身が濃い回です。長時間の開発セッションでのメモリ使用が最大 90% 減り、Turbopack が Vite ライクな `import.meta.glob()` に対応、artifact caching でリビルドが速くなりました。SSR の処理能力は最大 22% 向上、TypeScript 7 は `experimental.useTypeScriptCli` 経由で使えます。カスタムのエラーバウンダリを作る `catchError` や、i18n に使える `next/root-params` といったAPIも増えました。

中心にあるのは Cache Components の上に構築された Instant Navigations で、サーバー駆動のアプリにSPA並みの反応を持たせるものです。ニュースレターはこれを「dynamic-by-default に戻り、キャッシュは完全に明示的で予測可能にする」というアーキテクチャの方針転換だと読んでいます。キャッシュの暗黙的なふるまいに振り回された経験がある人には、方向として歓迎しやすい変化でしょう。

TanStack Table V9 は2年以上かけた基盤の作り直しです。framework-agnostic な設計でアダプタ群も刷新され、React では 18 以降に対応し、React Compiler と併用できます。atom や selector 単位で細かく読めるので、無駄な再レンダーを避けられるようになりました。テーブルは状態の絡み合いが激しく再描画のコストが出やすい部品なので、粒度の細い購読は素直にありがたいところです。

UIまわりでは React Aria 1.20 が PreviewTrigger のポップオーバー、インラインタグ用の TokenField、ネイティブのコンテキストメニュー、行がインタラクティブなテーブル、Next.js 16 の RSC collection 対応を追加しました。どれも自前で作るとアクセシビリティを落としやすい領域なので、ライブラリ側に寄せられるのは実務的な利点です。ほかに MobX 7.0、SWR 2.5（RSC のデータプリロードと `unload()`）、Base UI 1.7、Styled Components 6.5 が並びます。

エコシステム側の話題としては、Chrome チームの実験的な `use-webmcp-tool` が目を引きます。WebMCP 経由でクライアント側のツールをブラウザのAIエージェントに公開する React 抽象で、UIを「エージェントから操作できる対象」として設計する流れにつながります。CSS 側では、ルートに応じた View Transition のロジックをJSから追い出す W3C 提案「Declarative Route and Navigation Matching in CSS」も紹介されています。pnpm 11.20 が複数レジストリでのパッケージ置き換えの脆弱性を修正した件も、サプライチェーン周りの動きとして押さえておきたいところです。

### [Web-Perf Wednesday 003 – Native SPA Metrics Have Arrived](https://csswizardry.com/2026/08/web-perf-wednesday-003-native-spa-metrics-have-arrived/)

> **出典**: CSS Wizardry | **公開日**: 2026-08-05 | **カテゴリ**: css

**3行まとめ**
- Chrome 151 が stable に到達し、`soft-navigation` と `interaction-contentful-paint` が Performance Timeline に入った
- web-vitals v6 が対応。ただし既存の virtual page との二重計上や母集団の変化が起きるため、並走させて比べるのが安全
- Chrome 152 Beta には CPU Performance API（デバイス性能のティア）と Connection Allowlists が入っている

**詳細解説**

春はオリジントライアル、7月はベータ機能だったものが、7月28日から stable の Chrome 151 に載りました。ブラウザが操作起点の同一ドキュメント内ルート変更を認識し、新しい時間原点を作って、以降の性能データを元のドキュメントではなく現在のルートに紐づけられるようになります。web-vitals は7月21日の v6 でこれに対応しました。

大事なのは、これが既存イベントへのフィールド追加ではないという点です。1つのドキュメントが複数のメトリクスのライフサイクルを持つようになります。カタログ、商品ページ、カート、アカウント画面が個別に観測できるようになり、優秀な初期LCPが何年も隠してきた遅いルートが見えてきます。

同時に、二重計上と不連続も持ち込まれます。RUM製品が独自の virtual page と Chrome のネイティブな soft navigation を両方出すかもしれない。INP の attribution がルート境界をまたぐ挙動も変わりえます。さらに v6 は `requestIdleCallback` の待ちを1秒で打ち切るようになったため、これまで報告に至らなかった忙しいセッションがデータセットに入り、カバレッジが改善した結果としてパーセンタイルが悪化して見えることがあります。アプリが何も変わっていないのにグラフが動く、というのがいちばん厄介な状態です。

対処の手順が具体的で実用的です。本番の系列をその場で置き換えず、v5 と v6、既存モデルとネイティブモデルを並走させます。比べる順序も指定されていて、1,000 セッションあたりの報告率、メトリクスの完了率、ブラウザとデバイスの構成、ルート検出、bfcache の母集団、インタラクションの分布を先に見て、ヘッドラインのパーセンタイルは最後に比べます。RUMベンダーには、hard と soft のナビゲーションを統合するのか、独自ルートの重複をどう防ぐのかを確認します。

比較はユーザーのジャーニー単位で組むのがよいという指摘も的確です。「ルート遷移は正しく検出されたが、間違ったページに紐づけられた」状態は、技術的には成功していて分析的には無意味です。起点となった操作、遷移前のルート、遷移先、visibility state、続く描画のマイルストーンをひとまとめに保持し、速いルート・データ取得の重いルート・リダイレクト・モーダル的なURL変更・履歴からの復元・中断された遷移といった端のケースをサンプリングします。実装そのものをデータスキーマの一部として扱い、ブラウザ、web-vitals のバージョン、RUM SDK、attribution のビルド、アプリのリリース、ナビゲーションの分類を残しておく、という助言が締めです。

Chrome 152 Beta の CPU Performance API は、ビューポート幅やユーザーエージェント、デバイスメモリよりも INP や long task の悪化を説明しやすい可能性があります。ただしユーザーや管理者が値を上書きできるので、ハードウェアの真実ではなく capability hint として扱い、既存の次元と並べて記録して分散を説明できるか検証してから体験を変えるのが順序です。Connection Allowlists はサーバーが許可した接続先以外をブラウザが遮断する仕組みで、本来はセキュリティ機能ですが、サードパーティの一覧表を「監査時点の記録」から「強制される契約」に変える力があります。ベンダーがCDNやテレメトリの送信先を変えれば本番が壊れるので、所有者と有効期限、失敗時のテストまで設計に含める必要があります。

### [Web-Perf Wednesday 002 – The Metrics Don't Tell the Whole Story](https://csswizardry.com/2026/07/web-perf-wednesday-002-the-metrics-dont-tell-the-whole-story/)

> **出典**: CSS Wizardry | **公開日**: 2026-07-29 | **カテゴリ**: css

**3行まとめ**
- CrUX の 2026年6月版で good LCP 67.7%、good INP 85.9%、CWV 全項目通過 55.3% と全体が後退。Google は季節性と説明した
- 「ウェブ全体が遅くなった」は「直近のデプロイのせい」と同じくらい雑な説明。全体の変化量と自サイトの変化量を比べる
- Safari 27 Beta の scroll anchoring は見えるズレを補償するが、レイアウトの原因は直さない

**詳細解説**

比較の作り方が明確です。今月と先月ではなく、自サイトの変化量を全体の変化量と比べる。モバイルとデスクトップを分け、LCP と INP を別々に見て、オリジン全体ではなく主要なテンプレート単位で確認します。全体が 1.2 ポイント下がって自サイトが4ポイント下がったなら、全体の傾向は差分を説明していません。逆にブラウザとデバイスを通して市場とほぼ一致しているなら、慌ててコード調査を始めるのは全員の時間の無駄になります。週次の History API のデータで、28日のローリングウィンドウの中にリリースやキャンペーンの日付を置くのも有効です。これがないと、見かけの回復が「いちばん悪い日が窓から抜けただけ」なのか区別できません。

INP の節は、計測を製品の言葉に翻訳する話です。INP が悪いかどうかは多くのチームが言えるようになりましたが、どの操作が原因で、ジャーニーのどこで起き、何が遅延させたかを言えるチームは少ない。入力遅延・処理時間・表示遅延に分けるガイダンスはあっても、その数字に製品としての身元が必要です。コンポーネント、ルート、インタラクションの種類、アプリの状態、実験、ジャーニーの重要な段階を一緒に記録する。「INP は 240ms」は閾値の問題を指すだけですが、「リピート顧客が決済手段のセレクタを開くと 240ms になる」は優先順位を付けられる情報になります。

最後の「サードパーティも老いる」が地味に効きます。Safari 27 は `ResizeObserver` と `IntersectionObserver` が次第に遅くなる問題、多数の要素を監視したときの O(n²) の反復を修正しました。ここから引き出される教訓は、コストの一部はページの寿命とともに積み上がるのに、合成監視の多くは数秒で止まるということです。繰り返し登録されるリスナー、残り続ける iframe、広告のリフレッシュループ、ルート単位の再初期化、切断されないオブザーバーは初期バイト数や起動時CPUには現れません。初期ロード時、通常の操作の後、ルート遷移を繰り返した後で、メモリ・タスク・フレーム・オブザーバーを比べる、という提案は長寿命のダッシュボードやSPAを作っている人ほど響くはずです。scroll anchoring も同じ構図で、ブラウザが見えるズレを補償してくれるぶん、寸法指定のない画像やリサイズする広告といった原因が見えにくくなります。

### [From User Sequences to Scaling Laws: A Multi-Stage Architecture for Meta's Ads Ranking](https://engineering.fb.com/2026/08/05/ml-applications/from-user-sequences-to-scaling-laws-a-multi-stage-architecture-for-metas-ads-ranking/)

> **出典**: Meta Engineering | **公開日**: 2026-08-05 | **カテゴリ**: engineering

**3行まとめ**
- ユーザー履歴を扱う重いモデルをオフラインに、ランキングをオンラインに分ける多段構成で、LLM に似たスケーリング則が現れた
- dense tokenization と target-aware attention により、手作りの交差特徴に頼らず相互作用をデータから学習する
- Instagram のコンバージョンが 6%、Facebook が 3%、Facebook の広告クリックが 3.5% 向上した

**詳細解説**

広告のレコメンドは、数千の広告を数ミリ秒で取得してランク付けし、毎秒数百万の候補を処理する世界です。この規模に合わせるため、ユーザーのイベント列を扱うモデルと疎な特徴の相互作用を扱うモデルを分けるハイブリッド構成が使われてきました。要求は満たせるものの、コンポーネント間の知識転移が失われやすく、手作業の特徴量設計が残り、ランキング側とシーケンス側の干渉がスケールの上限になります。

多段構成の分け方が明快です。1段目のオフラインのユーザーモデルは、数千の長さの履歴を非同期で処理し、深い行動パターンを捉えた埋め込みをユーザー単位で事前計算してキャッシュします。ここでユーザーの特徴を広告や文脈の特徴から厳密に切り離し、埋め込みが特定の広告候補に依存しないようにしている点が鍵です。2段目のオンラインのランキングモデルは、そのキャッシュ済み表現に新鮮なユーザーシグナルと広告候補の情報を足して、厳しいレイテンシ予算のなかで速度に最適化されます。

学習側の工夫は2つ。dense tokenization は疎な特徴と系列的な行動データを1つの密な語彙に統合し、attention が相互作用を自力で見つけられるようにします。target-aware multi-head attention は、トークン化した疎な特徴と広告候補の情報をユーザーの行動列と融合し、各層がスコアリング対象の広告に対して過去の行動を重み付けできるようにします。層を積むことで高次の相互作用を捉えつつ、長い系列をコンパクトな表現に落としていきます。

そして FLOPs と性能（normalized entropy）の関係が対数線形になり、モデルの深さ・幅・系列長・意味的な情報の各軸でスケーリング則が観測されました。フロンティアを押し広げる4つのレバーが挙げられています。1つは形のバランスで、単一の軸だけを伸ばすと他の軸がボトルネックになるという scaling synergy principle。2つ目は多段構成のチューナビリティで、オンライン側は計算あたりの改善が急ですがリクエスト時間の制約を受け、オフライン側は緩やかでも非同期なので制約なく伸ばせます。3つ目は系列の構成で、長さは効き続けるものの、同質な系列より多様な系列が勝つという知見が重要です。閲覧・クリック・コンバージョンが混ざったほうが、シグナルの強い行動だけを並べるより豊かな表現になります。4つ目は基盤モデル由来の意味的特徴で、新しい広告や履歴の少ない広告主の cold-start に効きます。

UXエンジニアリングの視点で読むと、「事前計算してキャッシュできる重い部分」と「リクエスト時に決めるしかない軽い部分」を切り分ける発想は、レンダリング設計とそのまま同じ形をしています。Next.js の Cache Components をめぐる議論と構造が重なるのはおもしろいところ。系列の多様性が効くという知見は、行動ログの設計にも跳ね返ります。クリックだけでなく閲覧まで残すかという判断が、後段のモデルの質を左右するわけです。詳細は「LLaTTE: Scaling Laws for Multi-Stage Sequence Modeling in Large-Scale Ads Recommendation」という論文で公開されています。

- 登録に失敗したときは、何が起きたかと返金の状態を同じ画面で見せる
- メール設定は Google Workspace / Outlook / iCloud / Proton Mail / Zoho / Mailgun / ImprovMX の DNS プリセット。Bluesky のハンドル用プリセットもある

**詳細解説**

changelog としては小さな項目ですが、待ち時間の設計として読むとよくできています。ドメインの登録には数分かかります。その間ユーザーを待たせるのではなく、選べる行動を先に並べます。新しいプロジェクトをデプロイする、既存のプロジェクトに接続する、すでに運用しているサイトをプロキシまたはリダイレクトする、メールを設定する。そして各アクションはドメインの準備ができ次第、順に有効になります。

プロキシを選ぶと、オリジンを入力するだけでトラフィックが Vercel の CDN とファイアウォールを経由して既存サイトに流れ、そのための routing 用プロジェクトを Vercel が作って設定まで済ませます。ユーザーがやることは「何をしたいか」を選ぶところまでで、そのために必要な構成物は裏で用意される、という分担です。

UXエンジニアリングの観点では、非同期処理の待ちをどう扱うかの教科書的な例です。進行状況を出すだけでなく、待っている間に価値のある選択肢を置き、失敗時には次の行動につながる情報まで見せています。とくに「何が起きたか」と「お金がどうなるか」を同じ画面に出すのは、決済を含むフローを作るときに真似したい設計です。DNS プリセットも、レコードという実装の語彙ではなく、ユーザーが持っている語彙（使っているメールサービスの名前）を入口にしている良い例といえます。

### [A Canvas for Individuality: Creating Websites That Feel Unmistakably Human with Readymag](https://tympanus.net/codrops/2026/08/05/a-canvas-for-individuality-creating-websites-that-feel-unmistakably-human-with-readymag/)

> **出典**: Codrops | **公開日**: 2026-08-05 | **カテゴリ**: design

**3行まとめ**
- 「トレンドではなく個性が記憶に残る体験を作る」という切り口で、Readymag 製のサイト 14 件を紹介するショーケース
- 画像を一切使わず文字だけで、完成物ではなくその裏の思考を見せる Artem Matyushkin のポートフォリオなど、振り切った例が並ぶ
- Readymag とのパートナーシップ記事（プロモコード付き）である点は踏まえて読むのがよい

**詳細解説**

具体例が並ぶタイプの記事なので、眺めて手が動くほうを拾うのが向いています。Brian Lim のポートフォリオは editorial で整った構成に、回転するプロジェクトカードと下端のグラデーションという遊びを差し込んでいます。Dinette は一点物のラグの陽気さに合わせて、買い物の体験そのものをブランドの延長にしています。melt dome は固定した黄色い枠と切り抜きの人物写真で、フレーミングを設計の言語に変えています。Anton Tvinenko はインターネット的な懐かしさをデスクトップ風の世界に組み替えていて、誰のものか間違えようがない見た目です。

いちばん示唆的なのは Artem Matyushkin の例でしょう。一見すると文字の壁にしか見えないのですが、画像をすべて落としたことで焦点が「完成した仕事」から「その裏にある思考」へ移ります。優れたデザインは視覚的な流行を追うことではなく、ある考えを明快に、確信をもって表現することだという主張が、サイトの構造そのもので示されています。

デザインシステムやトークンで揃えていく仕事とは反対側にある話です。一貫性は手段であって、目的はその制作物がその人のものだと伝わること。ノーコードのキャンバスでここまで振り切れるという事例は、実装の自由度と表現の自由度が別の問題であることも示しています。ただしスポンサード記事なので、ツールの評価としては割り引いて、ショーケースとして眺めるのが妥当です。
