### [AIでReactのUIを作るとデザインがぶれる。DESIGN.mdとCSSトークンでどこまで防げるか](https://zenn.dev/howmanydesigns/articles/e8708fa1f4627b)

> **出典**: Zenn designsystem | **公開日**: 2026-11-03 | **カテゴリ**: design-systems

**3行まとめ**
- 同じ「チーム設定」画面を、画面要件だけ・DESIGN.md を追加・CSS トークンまで追加、の3条件で各3回、計9回 AI に作らせて比べた検証です
- DESIGN.md を渡すと見出しサイズ・入力欄の高さ・角丸がそろい、トークンを加えると見出しの文字色も定義どおりの値にそろいました
- 見た目とは別に、9画面すべてで「リセットすると役割が初期値に戻らない」同じ不具合が見つかり、原因と修正まで追っています

**詳細解説**

AI に画面を作り直させるたびに、見出しが少し大きくなったり、主役の色が青から緑に変わったりする。多くの人が感じているこのぶれを、条件をそろえて数字で確かめた記事です。モデルや推論設定、React と Vite の版、画面幅を固定し、試行ごとに新しいセッションで生成しています。生成し直してよい結果を選ぶこともせず、9件すべてを評価しています。

測り方がていねいです。見出しや入力欄に `data-probe` 属性を付けるよう要件に入れておき、`getComputedStyle()` で値を取っています。条件 A（資料なし）では見出しが 27/30/29px とばらつき、入力欄も 43〜44px でした。DESIGN.md を渡した B と、トークンも渡した C では、見出し 24px、入力欄 40px、角丸 8px にそろっています。違いが出たのは見出しの文字色で、B は2種類に分かれ、C は3回とも `--color-text` の `#18181b` と一致しました。

ここから導いている使い分けは、実務でそのまま使えます。DESIGN.md には余白のスケールや装飾をどこまで抑えるかといった「判断の基準」を書き、トークンには「実装で参照できる値」を渡す、という分担です。ただし記事は「トークンを渡せばデザインを強制できる」とは言っていません。CSS 変数があっても別の値を直接書けるので、任意の値を禁じる検査はまた別に必要です。

UXエンジニアの立場で一番おもしろいのは後半の不具合です。`<form onReset>` で React の状態を戻していたものの、ブラウザ標準のリセットを止めていなかったため、`select` が先頭の「管理者」に戻っていました。最初の検査は表示名が戻ることしか見ておらず、テストは通っていたそうです。見た目がそろうことと、操作が正しく動くことは別の問題だと、具体的な例で示しています。

限界もはっきり書かれています。1画面・1モデル・各3回の観察で、seed は固定できず、評価者も条件を知っていました。B の DESIGN.md には具体的な数値も含まれていたので、抽象的な方針だけの効果とは分けられていません。それでも、自分のチームで同じ比較を試すときの手順書として、十分に参考になる内容です。

### [Creating tools for scaling generated content](https://designnotes.blog.gov.uk/2026/11/03/creating-tools-for-scaling-generated-content/)

> **出典**: GOV.UK Design Notes | **公開日**: 2026-11-03 | **カテゴリ**: design

**3行まとめ**
- GOV.UK の AI チームが、利用者の状況に合わせて生成する「行動プラン」の文章の質を、大量の出力で確かめるテストの仕組みを作りました
- シナリオ集・プロンプト・一括生成・評価基準の4つで回し、コンテンツのルールを評価項目にして毎回すべてのプランに当てています
- 機械的に判定できる項目はコードで、判断が要る項目はモデルに判定させ、人のラベルと照らし合わせて調整しています

**詳細解説**

出産や失業といった出来事に合わせて、行政手続きの手順を利用者ごとに組み立てる取り組みの続報です。生成される文章は利用者が求めたときに初めてできるので、事前に1つずつ確認できません。承認が必要な文面は何千通りにもなり、1つの出力がよくても次の100件がよいとは限らない。記事はこの状況を「作っているのは文章そのものではなく、文章を作る指示だ」と言い表しています。

仕組みは4つの部品でできています。現実的な状況を集めたシナリオ集、プラン・ステップ・タスクごとに分けて版を管理するプロンプト、全シナリオをまとめて流す生成、そして評価基準です。評価基準には「タイトルは -ing 形か」「法的な義務を "you must" で書いているか」「期限をカレンダーの日付ではなく出来事を起点に書いているか」といった項目が並びます。正確さや根拠の確認は別の仕組みで扱い、ここでは文章の設計だけを見ている点も整理されています。

運用から得た知見が具体的です。タイトルの長さのような機械的な項目は、モデルに判定させるよりコードで調べるほうが安くて確かだそうです。判断の要る項目でモデルを審査役にするときは、人が付けたラベルと一致するかを確かめています。評価は5段階ではなく合否の2択にしていて、5段階だと誰もが無難な「3」に落ち着いてしまうからだと説明しています。全体の平均点より、1つの項目がシナリオ全体で何割通ったかを見るほうが、プロンプトのどの行を直せばよいかに直結する、という指摘も実践的です。

UXエンジニアの視点では、コンテンツデザインのルールをテストに変えている点に注目したいところです。「余計なものがないか」も測れるようになり、すでに画面に出ている期限をくり返す、頼まれていない注意書きを足す、といった生成文章のくせを数百件の中で見つけられます。1か所を直したら別の場所のタイトルが長くなった、という回帰にもすぐ気づけます。

ただし、数字の成果はまだ書かれておらず、本人たちも「開かれた実験」と位置づけています。評価を見ながらプロンプトだけでなく、情報設計や画面のデザイン、モデルに渡すデータの形まで見直すきっかけにしているそうです。デザインシステムの文章ガイドラインを AI に守らせたいチームには、そのまま応用できる考え方です。

### [Introducing Adaptive Dark Mode](https://webkit.org/blog/18541/introducing-adaptive-dark-mode/)

> **出典**: WebKit Blog | **公開日**: 2026-11-03 | **カテゴリ**: web-standards

**3行まとめ**
- Safari 27.3 beta に、ダークモードに対応していない明るいサイトをブラウザが暗く変換して表示する Adaptive Dark Mode が入りました（ユーザーが有効にしたときだけ動きます）
- 色相を保ったまま明度を反転させ、文字は WCAG の 4.5:1 のコントラストを目安にし、SVG やモノクロのロゴも必要に応じて変換します
- `color-scheme: light dark` を宣言したサイトは変換されず、`light only` で断ることもできます。変換されたかどうかはサイト側から検出できません

**詳細解説**

背景にある数字は、ページの読み込みのおよそ40%がダークモードの利用者からなのに、ダークモードに対応したページは10%ほどにとどまる、というものです。夜に真っ白なサイトを開いてまぶしい思いをする、その差を埋めるための機能です。ページを読み込むと色を調べ、おもに明るいページだと判断したときだけ暗く変換します。

変換の中身に設計の判断が詰まっています。色相を保ったまま明度を反転させる行列を作り、背景を暗く、文字を明るくしています。ボタンと背景のコントラストや、画像の上の文字、ホバーメニューの見やすさにも気を配っているそうです。画像は基本的にそのまま残し、背景が反転すると見えにくくなるアイコンやロゴだけを変換します。SVG は中身を調べ、ビットマップは画素のヒストグラムを見て単純な白黒のロゴだけを反転させています。`mix-blend-mode` やマスクは場合によって無効にし、`<canvas>` は中身が予測できないので触らない、という線引きも書かれています。

サイトを作る側が持ち帰れることも明確です。ロゴやアイコンはビットマップより SVG にする、タイル状の背景画像より CSS の色やグラデーションを使う、画像にページの背景色を焼き込まず透過にする、といった対策が挙がっています。`color-scheme` の宣言は JavaScript で後から入れず、HTML か CSS に最初から書くよう勧めています。そうすれば最初の描画から正しく表示されるからです。

UXエンジニアとして気になるのは、ブランドの色や意味を持つ色がブラウザ側で変わりうることです。変換されたかどうかは指紋採取（fingerprinting）を防ぐために検出できず、JavaScript で色を読んでも元の値が返ります。つまり「変換されたときだけ直す」ことはできません。`light only` は最初の beta ではまだ効かないので、実際に beta で自分のサイトを開き、ロゴ・グラデーション・ブレンド・コントラストを確かめておくのがおすすめです。

いちばんの対策は、自分でダークモードに対応することだと記事も書いています。`light-dark()` や `prefers-color-scheme`、`<picture>` の切り替えはすでに広く使えます。デザインシステムで色をセマンティックなトークンにしてあれば、対応の手間はかなり小さくなるでしょう。

### [Do AI Moderators Uncover as Much as Human Moderators?](https://measuringu.com/do-participants-provide-the-same-depth-of-insight-to-human-and-ai-moderators/)

> **出典**: MeasuringU | **公開日**: 2026-11-04 | **カテゴリ**: ux-research

**3行まとめ**
- 20人を AI と人のモデレーターに無作為に割り振ったインタビュー実験で、引き出せたテーマの数を比べた連載の2本目です
- 8つのテーマのうち7つは両方で見つかりましたが、1セッションあたりのテーマ数は人が6.9、AI が5.0で、人のほうが多くなりました
- 差が大きかったのはインタビューガイドに書いていない話題で、人は台本から少し外れて質問し、AI はほとんど拾えませんでした

**詳細解説**

MeasuringU は Gemini 3 Flash で AI モデレーターを作り、写実的なアバターと研究員の声で、起床や睡眠に関する探索的なインタビューを実施しました。前の記事では、AI 相手だと参加者の発話が45%少ないという結果でした。今回は「話す量が少なくても、同じ深さの気づきが得られるのか」を、テーマの重なりで確かめています。

分析の手順は手堅いものです。インタビューに関わっていない研究員2人が、あらかじめテーマを決めずに20本の記録を別々にコード化し、さらに Claude にも確認させています。人どうしの一致は κ=.38 で、まずまずの水準です。条件が伏せられていても、コーダーには AI のセッションだとだいたい分かったそうで、そうした限界も記事に書かれています。

いちばんの発見は「睡眠の環境」というテーマです。室温や騒音の話は人のセッションの10件中6〜9件に出てきたのに、AI のセッションでは0〜1件でした。ガイドには部屋の環境を聞く項目がなく、人のモデレーターは「部屋の温度はどうですか」と自分から聞いていました。AI も部屋のことに触れてはいますが、「理想の起き方」の質問の中で仮定として聞いただけで、具体的な行動は引き出せていません。

ガイドに書かれた話題では、AI と人の差は平均で約8ポイントにとどまりました。ガイドにない2つのテーマでは、差が30ポイントと73ポイントに広がっています。記事の実用的な結論は「よい台本を書く」ことです。ただ、探索的なリサーチは聞くべきことが事前に分からないからこそ実施するものなので、この結論には矛盾も含まれています。

UXリサーチを AI に任せる場面が増えるなかで、どこまで任せられるかの手がかりになる結果です。調べたいことが決まっている検証的な調査なら AI でもかなり拾えそうです。逆に、新しい機会を探す段階では、人のモデレーターの「脱線」に価値がある、と読めます。1つの研究・1つの台本での結果なので、次回以降の連載も合わせて見ていきたいところです。

### [Modern CSS Might Make Your Front-End More Complex](https://smashingmagazine.com/2026/11/modern-css-might-make-your-front-end-more-complex/)

> **出典**: Smashing Magazine | **公開日**: 2026-11-03 | **カテゴリ**: design

**3行まとめ**
- JavaScript をコンテナクエリや `:has()` に置き換えると、そのファイルは短くなっても、アプリ全体は理解しにくくなることがある、という指摘です
- 古い実装が残って振る舞いの持ち主が2人になる、`container-type` でカードの幅が0pxになる、`:has()` の詳細度で別の部品の余白が消える、といった4つの場面をデモで示しています
- 5,000行の表では `:has()` のルールの組み合わせで再計算の範囲が大きく広がることを計測し、移行のチェックリストにまとめています

**詳細解説**

記事は「局所的な単純さ」と「システムの複雑さ」を分けて考えます。差分が赤ばかりの PR は前者を示すだけで、後者、つまり安全に変更するまでに理解しなければならない相互作用の数は分かりません。モダン CSS を否定しているのではなく、「元の実装を本当に置き換え、周りを乱さないときだけ複雑さが減る」という狭い主張です。

1つめの場面は、`ResizeObserver` でクラスを付けていたカードをコンテナクエリに移したのに、Observer と古いクラスのルールが別ファイルに残っていたケースです。どちらも 480px で一致しているうちは問題が見えません。デザイナーの依頼でブレークポイントを 600px に変えたとたん、480〜600px の間に誰も書いていない状態が生まれます。記事は「サイズや DOM 構造で決まる見た目は CSS、アプリの状態と非同期処理は JavaScript」と持ち主を分け、移行したら古い実装を最後まで消すように勧めています。

2つめは、`container-type: inline-size` が新しいブロック整形コンテキストを作ることです。マージンの相殺が止まって余白が増え、float の横に押し出されます。さらに、中身から幅を決めていたカードは幅が 0px になって消えます。flex アイテム、`inline-block`、`fit-content` などで同じ結果になったと確かめています。付ける前に「幅はどこから来るか」「最初と最後の子にマージンはあるか」「実際にどこで使われているか」を確認する、という3つの問いはすぐに使えます。

3つめの `.card:has(img) p` は、コメント欄のアバター画像にも当たってしまい、詳細度でもコメント部品のルールに勝ってしまう例です。`>` で範囲を絞り、`:where()` で詳細度を 0 にし、カスケードレイヤーを確かめる、という対処が挙がっています。4つめは性能の話で、`body` に付けた `:has()` 単体は 1.5ms ほどの差でした。ところが別の無害なルールと組み合わさると、行を選ぶたびに5,000行すべてのスタイルが再計算され、1回あたり約7msかかっています。

UXエンジニアには、デザインシステムの部品にコンテナクエリを入れるときの確認項目として役立ちます。部品を単体で見る Storybook では問題が見えず、実際の画面に置いて初めて壊れる、というのがこの記事に出てくるバグの共通点です。最後のチェックリスト（持ち主・範囲・カスケード・移行・性能・保守性）は、PR テンプレートに入れておいてもよさそうです。

### [Building an AI-ready design system library](https://uxdesign.cc/building-an-ai-ready-design-system-library-code-figma-with-mcp-ec5d9e8c90d2)

> **出典**: Sidebar | **公開日**: 2026-11-04 | **カテゴリ**: design

**3行まとめ**
- Figma からコードを AI に作らせると、フォーカス順やエラー状態など Figma に書けないことを AI がもっともらしく作ってしまう、という問題から出発しています
- そこで向きを逆にし、コードを正としてトークンとコンポーネントを MCP 経由で Figma に写し、写せなかったことを `GAPS.md` に毎回書き出させています
- Storybook の manifest と Figma 側の JSON を突き合わせる parity check で、名前・プロパティ・既定値のずれを確かめています

**詳細解説**

書き手はデザイナーで、本番のコードは書かない立場です。React のコンポーネントが表現できることと Figma のコンポーネントが表現できることを比べたところ、Figma で表せるのは約17%だったそうです（本人による概算と断っています）。以前はその差を開発者が質問して埋めていましたが、AI はファイルを完全な指示として読み、足りないところを推測で埋めます。スクリーンショットでは見えないフォーカス順や読み上げ内容、空の状態が作られてしまう点を心配しています。

そこで「コードが正で、Figma は鏡」という方針をとっています。手順は具体的です。安全な複製リポジトリを用意し、Storybook を立ち上げ、空の Figma ファイルを開きます。まずトークンとテキストスタイルを、コードと同じ名前・同じ階層（primitive と semantic）で写します。次に Button と Alert のような易しい部品と厄介な部品を1つずつ試し、それがうまくいってから全体を流します。使ったプロンプトもそのまま載っています。

いちばんのアイデアは `GAPS.md` です。Figma で表せなかったこと、AI が自信のなかったこと、人が確かめるべきことを毎回書き出させます。単位のない line-height を px にしなければならない、振る舞いの中にしかない状態がある、Figma に対応するもののないレイアウトのルールがある、といった項目が並ぶそうです。差分を見えるようにしておけば、開発者と一緒にひとつずつ片づけられます。

UXエンジニアとして参考になるのは、文脈を Markdown に手書きするのではなく、トークンやコンポーネントそのものに持たせるという考え方です。名前、許される値、既定値、コードでの変数名、Storybook へのリンクを要素ごとに付けておけば、コードと食い違うことがありません。DESIGN.md には「なぜ」と「いつ」だけを書く、という分担は、今号の1本目の検証結果ともよく合います。

注意点も書かれています。依存されているライブラリで作業するときは必ず複製してから試すこと、variant を消して作り直してもインスタンスはつながらないので名前を直すこと、といったものです。iOS・Android・Web と複数のソースがある場合は単純にはいかず、Nathan Curtis の「コンポーネントをデータで定義する」案に触れています。parity check は今は構造だけで見た目は比べていない、という限界も正直に書かれています。

### [CSSだけで横スクロールと見出し固定を両立！ 単一軸スクロールコンテナー](https://ics.media/entry/261104/)

> **出典**: ICS MEDIA | **公開日**: 2026-11-03 | **カテゴリ**: frontend

**3行まとめ**
- Chrome・Edge 156 で、`overflow` の片方の軸にだけ `clip` を指定すると、その要素は指定した軸だけのスクロールコンテナーになるよう仕様が変わりました
- これで「表の中は横スクロールして左の見出しを固定し、上の見出しはページの縦スクロールに合わせて画面上部に固定する」が CSS だけで書けます
- 未対応のブラウザでは片軸の `clip` が `hidden` 扱いになる点に注意が必要で、`scroll-state()` と組み合わせたデモも紹介されています

**詳細解説**

横に長い表を `overflow-x: auto` で横スクロールさせると、縦にスクロールしていなくても縦方向までスクロールコンテナーとして扱われていました。`position: sticky` は一番近い祖先のスクロールコンテナーを基準にするので、上の見出しはページのスクロールについてこられません。工程表や比較表で、上の見出しが画面の外に流れてしまうのはこのためでした。

新しい仕様では、`overflow: auto clip;`（`overflow-x: auto; overflow-y: clip;` と同じ）と書くと、横だけのスクロールコンテナーになります。縦方向にはスクロールコンテナーができないので、`thead th` の sticky はページ全体のスクロールを基準に画面上部へ固定されます。記事の図は、`overflow-y` が `hidden` の場合と `clip` の場合で縦横の基準がどう変わるかを示していて、理解の助けになります。

デモの1つめは工程表で、行見出しを2列にして2列目を `left: 160px` で固定し、重ならないようにしています。`scope="rowgroup"` と `scope="row"` も付けています。2つめの国別比較表は `scroll-state()` と組み合わせたものです。見出しが固定されたら国旗の並びを変え、右にまだスクロールできるときだけ影を出しています。

UXエンジニアの視点では、表の「どこを見ているか分からなくなる」問題を CSS だけで解決できるのはうれしいところです。これまでは JavaScript で見出しを複製したり、表に高さを付けて内側でスクロールさせたりしていました。内側のスクロールはページのスクロールと二重になり、特にスマートフォンでは操作しにくくなりがちです。

ただし、未対応のブラウザでは片軸の `clip` が `hidden` とみなされ、指定どおりには動きません。執筆時点で使えるのは Chrome・Edge 156 以上です。それ以外のブラウザでは見出しが固定されないだけ、という段階的な強化として入れられるかを、表ごとに確かめるとよいでしょう。

### [Re-Implementing :nth-child() With Modern CSS](https://css-tricks.com/re-implementing-nth-child-with-modern-css/)

> **出典**: css-tricks | **公開日**: 2026-11-03 | **カテゴリ**: css

**3行まとめ**
- `:nth-child(An + B)` の A と B を CSS 変数で変えられるよう、`sibling-index()` と `if()` を使って同じ選択を作り直す練習問題のような記事です
- `:nth-child(5)` なら `if(style(sibling-index() = --B): red)` のように書け、`n + B` や `-n + B` は比較演算子を変えるだけで表せます
- `An + B` の一般形では `mod()` を使い、A が0のときに `NaN` になる問題を `sign()` を組み合わせて回避しています

**詳細解説**

Temani Afif によるこの記事は、本人も認めるとおり、実務でそのまま使うためのものではありません。セレクタの引数は変数にできないので、`5n + 8` の数字を変えたいときは毎回セレクタを書き直すしかありません。そこで、要素の側で自分が何番目かを `sibling-index()` で調べ、条件に合えばスタイルを当てる、という逆向きの発想で同じことを実現しています。

段階を追って説明しているので、新しい関数の練習になります。`if()` の中の `style()` では、`sibling-index() = --B` のようにカスタムプロパティと比べられ、書き方にもいくつかの変形があります。`n + B` は `>=`、`-n + B` は `<=` に変えるだけです。一般形では「(index − B) を A で割った余りが0で、商が0以上」という条件を `mod()` と `calc()` で書いています。A が0だと `mod()` の結果が `NaN` になって条件が崩れるので、`sign()` を使った補助変数で場合分けしています。

UXエンジニアの視点では、`if()` と `sibling-index()` が登場したことで、CSS の中で「自分の位置に応じて見た目を変える」表現が書きやすくなった点が大事です。たとえば、何番目ごとに色を変えるかをユーザーの設定や画面幅に合わせて切り替える、といった使い方が考えられます。同じ条件をプロパティごとに書く必要があり、冗長になりやすいことは記事でも欠点として挙げています。

対応ブラウザはまだ限られているので、すぐに本番で使う場面は少ないでしょう。それでも、新しい CSS の関数をどう組み合わせると条件分岐が書けるのかを手を動かして学ぶには、ちょうどよい題材です。最後に `:nth-last-child()` への応用を宿題として出しているので、`sibling-count()` と合わせて試してみるのもおもしろそうです。

### [Multi-Column Different-Speed Scrolling](https://blog.master.dev/multi-column-different-speed-scrolling/)

> **出典**: Frontend Masters Blog | **公開日**: 2026-11-03 | **カテゴリ**: css

**3行まとめ**
- 写真ギャラリーの2列を、スクロール駆動アニメーションで違う速さに動かす実装を、JavaScript を使わずに作っています
- 右の列に `animation-timeline: scroll(root block)` で `translateY` を当て、各写真には `view()` で拡大と移動を付けています
- 右の列だけ逆向きに流れて見える版も作っていて、こちらは sticky や個別の計算が要り、かなり手間がかかると書いています

**詳細解説**

Chris Coyier による、ギャラリーのように「見て回る」ためのページなら、スクロールの見え方はもっと自由でよいのでは、という思いつきから始まった実験です。スクロールそのものはいじらず、スクロール量に合わせて列を `transform` で動かし、速く流れているように見せています。スクロールバーは残すので、「あとどれくらいあるか」という手がかりは失われません。

実装の要点は短くまとまっています。2列のグリッドを作り、右の列に `scroll(root block)` をタイムラインにしたアニメーションを当て、`translateY(12vh)` から `-20vh` まで動かします。`@supports` で囲み、狭い画面では1列に戻しています。各写真には `view()` のタイムラインで、画面に入ってから出るまでの間に少し縮みながら動く効果を付けています。`@custom-media` を LightningCSS で変換して使っている点も、さりげなく紹介されています。

UXエンジニアとして押さえておきたいのは、記事中でも触れている `prefers-reduced-motion` への配慮です。列が違う速さで動く表現は、動きに敏感な人には負担になりえます。記事の数値は「感覚でよさそうに見えた値」と本人が書いているとおり、試しながら決めたものです。採用するなら、動きを減らす設定のときは止める、動きの幅を小さくする、といった対応を最初から入れておくとよいでしょう。

あくまで遊び心のある段階的な強化として紹介されており、重要な機能に使うものではない、と本人も書いています。スクロール駆動アニメーションと `popover` で、以前なら JavaScript が必要だった演出がここまで書けるようになった、という現在地を知るにはよい記事です。
