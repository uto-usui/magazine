### [The default is not a design decision](https://www.hipuku.dev/writing/the-default-is-not-a-design-decision)

> **出典**: Sidebar | **公開日**: 2026-09-29 | **カテゴリ**: design

**3行まとめ**
- ここ数年の SaaS がロゴを外すと見分けがつかないほど似ている理由を、プラットフォーム・ツール・評価文化・自動化という4つの変化から説明するエッセイです
- どの変化もそれぞれは合理的な判断でしたが、重なった結果として「機能としての一貫性」が「見た目の画一化」を正当化する理屈にすり替わった、と整理しています
- AI デザインツールは最初の案が意見より先に出てくるため、美的な判断はプロンプトを打つ前に済ませておく必要がある、というのが結論です

**詳細解説**

出発点は、2003〜2019年のウェブをコンピュータビジョンで分析した2021年の研究です。2007年以降にページレイアウトが目に見えて似ていき、サイト間の平均的な距離は30%以上縮んだと報告されています。著者はこれを偶然ではなく構造の問題だと見て、その流れを順番にたどっていきます。

1つめはプラットフォームです。1987年の Apple Human Interface Guidelines、2008年の App Store、2014年の Material Design と続くなかで、慣習から外れることのコストが上がっていきました。2つめはツールで、Figma のコミュニティライブラリによって、他人の美的な判断が「すでに読み込まれた状態」で手に入るようになります。3つめは Dribbble に代表される評価文化で、400×300のサムネイルで映える仕上がりが「良いデザイン」の定義になりました。そして4つめが自動化です。「クリーンでミニマルな SaaS ダッシュボード」と頼むと、モデルはもっとも確率の高い、つまりもっともありふれた答えを返します。

おもしろいのは、Hick の法則や Norman のアフォーダンス、Nielsen の議論を否定していない点です。クリックできる場所が分かる、ボタンが押せそうに見える、といった機能面の一貫性には価値があると認めています。そのうえで、その研究が「同じ空間の使い方、同じ文字の階層、同じ温度感」まで正当化する根拠として引用されるようになった、とずれを指摘しています。デザインシステムが「チームが下した判断の記録」から「チームに渡された判断」へ役割を変えた、という一文は、システムを運用している立場からするとかなり刺さります。

AI ツールの節では、Figma の Make Designs が Apple の天気アプリとほぼ同じ画面を出して取り下げられた件や、Claude Design のオンボーディングの仕組みが例に挙がっています。既存のコードとデザインファイルを読んでシステムを組み立てる仕組みは便利ですが、そのシステムがテンプレートの寄せ集めだった場合、意図した判断と受け継いだだけの判断を区別できないまま広げてしまいます。Claude Design の公開後、関係のないクリエイターのカルーセル投稿が同じレイアウトで並んだ観察も、既定値の影響がよく見える例です。

UXエンジニアリングの視点では、「既定値もまた誰かが下したデザインの判断だ」という見方が持ち帰りやすいと感じます。コンポーネントの余白や密度、色、動きには、それを最初に作った人の文脈があります。理由を問わずに採用すると、その判断を上流に預けたまま追認することになります。楽天や Yahoo! JAPAN の情報密度を、漢字の構造から生まれた別の伝統として紹介しているのも、日本の読者には興味深いところです。見た目での差がつかなくなると、競争の場は文章やブランドの声、振る舞いに移る、という指摘もあわせて読んでおきたい部分です。

### [Plan mode is dead](https://www.aymannadeem.com/artificial/intelligence,/developer/tools/2026/09/24/plan-mode-is-dead.html)

> **出典**: Sidebar | **公開日**: 2026-09-29 | **カテゴリ**: design

**3行まとめ**
- 計画をファーストクラスの機能にしたデスクトップのコーディングアプリ「Nuanced」を作り、うまくいかなかった創業者による振り返りです
- 失敗の理由として、「計画すること」と「計画書」を混同したこと、モデルが賢くなったこと、AI が書いた長い文章は読まれないこと、計画と実装を分けすぎたことの4つを挙げています
- 人間がシステムの全体像を理解し続ける問題は残っていて、計画モードはその解決に合った抽象ではなかった、という結論です

**詳細解説**

Nuanced は、AI によるコード生成の速さに人間の理解が追いつかない、という問題意識から作られたアプリです。チャットで作りたいものを話すと、曖昧な点や判断が必要な点をシステムが提示し、合意した計画を永続的なドキュメントとして残してから実装に入ります。書き捨てのチャットに埋もれていく計画に「居場所」を与えたい、という動機はとても共感しやすいものです。

ところが初期ユーザーは、残された仕様書にほとんど関心を示しませんでした。仕様書は長く、情報量は多いのに分かりやすさにつながらない。AI が書いた文章特有の、構造化されすぎたリズムが読みにくさの原因だと著者は見ています。これに対して要点を案内する「Spec Tour」を作りましたが、画面上のテキストがさらに増えただけでした。「仕様書を使えるようにするために短い版を生成する必要があるなら、そもそも完全な仕様書は何のためにあったのか」という自問は、ドキュメント生成まわりの機能を作っている人にとって重い問いです。

もうひとつの学びは、工程を分けたことの弊害です。「チャット → 質問に答えて曖昧さを解消 → 仕様書生成 → レビュー → 修正 → 承認 → 実装 → コードレビュー」という直線的な流れは、実際の考え方と合っていませんでした。試してみて初めて分かることがあり、その結果で考えが変わるのが普通です。現在のエージェントは「理解 → 実行 → 確認 → 明確化 → 調整 → 再実行」のループで動いており、計画はそのループのなかに溶け込んでいる、と整理しています。

UXエンジニアリングの視点では、計画モードとビルドモードの切り替えが「このタスクは計画に値するか」というメタな判断をユーザーに求めていた、という指摘がおもしろいところです。文脈を持っているのは AI 側なので、その判断こそ AI に任せたほうがよいものでした。モード設計全般に通じる教訓といえます。一方で、何百ものエージェントが同時にシステムを変えていくなかで、人間の注意をどこに向けてもらうかは未解決のまま残っています。後述の「A eulogy for the software engineer」にある「完了の定義を先に書いておく」という考え方と並べると、計画書ではなく判断基準を残す、という方向性が見えてきます。

### [コーディングエージェントはスプレッドシートをどう操作しているか](https://tech.layerx.co.jp/entry/coding-agent-for-spreadsheet)

> **出典**: LayerX エンジニアブログ | **公開日**: 2026-09-28 | **カテゴリ**: engineering

**3行まとめ**
- OpenAI が提供する Spreadsheets skill の中身を読み解き、Codex がコードから XLSX を読み書きする流れを実際のタスクで観察した記事です
- skill には「数値を式に直接書かずセル参照を使う」「編集処理を1つのスクリプトに集約する」「エージェント前提の Artifact Tool を使う」といったルールがあります
- 実行は「探索 → 編集 → 画像での確認 → 保存ファイルの照合」の4段階で、画像化によって表示形式の抜けを自分で見つけて直していました

**詳細解説**

バクラクのようなバックオフィス業務ではスプレッドシートが至るところで使われていて、その操作をエージェントに任せる選択肢が現実的になってきました。ただ、ユーザーから見えるのは指示と成果物だけで、内部で何をしているかは分かりにくいままです。この記事は GUI 操作ではなく、コードからファイルを編集する方式に絞って、そのなかを覗いています。

skill のルールで印象的なのは、計算結果が正しいことに加えて「あとから人が計算過程を追え、前提を変えられること」を重視している点です。成長率5%を `=A5*1.05` と書かず、入力セルに置いて `=A5*(1+$A$6)` と参照します。複雑な式を1セルに押し込まず、意味のある中間計算をセルに分けて残します。エージェントが作った成果物を人が引き継ぐことを前提にした設計で、スプレッドシートに限らず AI の出力全般に当てはまる考え方です。

実験では SpreadsheetBench2 から、4年間の売上予測モデルの空欄を数式で埋めるタスクを使っています。編集スクリプトには、書き込み前に対象範囲が空であることを確かめ、既存のセルを上書きしそうなら処理を止めるガードが入っていました。さらにおもしろいのが画像による確認です。最初のレンダリングで、追加したセルが `General` のままになっていて、割合が `3.10%` ではなく `0.031` と表示されていることに気づき、表示形式を追加して再実行しています。値と数式の検査だけでは見つけにくい問題を、見た目の確認で補った例です。

UXエンジニアリングの視点では、「コードで編集するだけでは、値がどう表示されるかまでは分からない」という点が、フロントエンドの E2E テストやビジュアルリグレッションテストとまったく同じ構図なのが興味深いところです。エージェントに `render` という目を持たせることで、人がふだん画面で確かめていることを検証ループに組み込めます。一方で、1シートの簡単なタスクでも15ターン・約3分32秒かかったこと、複数シートや外部参照を含む難しいケースでは失敗例もあることが正直に書かれています。最後の「目指すのは複雑なスプシを解けることではなく、お客様の業務が楽になること」という一文も、プロダクトとして AI を組み込む側の姿勢としていいバランスだと感じます。

### [12 CSS features you can use today with no build step](https://flaviocopes.com/modern-css-features/)

> **出典**: Sidebar | **公開日**: 2026-09-28 | **カテゴリ**: design

**3行まとめ**
- Sass や PostCSS、JavaScript のハックで補っていた機能を置き換えられるモダン CSS を12個、置き換え前の回避策とあわせて紹介する記事です
- ネスト、`:has()`、コンテナクエリ、subgrid、`oklch()` と `color-mix()`、カスケードレイヤー、`dvh`/`svh`、`@starting-style` などを取り上げています
- 対応状況は2026/09/21時点の MDN と web-features のデータで確認していて、Baseline ではないスクロール駆動アニメーションだけはその旨を明記しています

**詳細解説**

この記事の良いところは、機能ごとに「それが何を置き換えるのか」と「どこでつまずくか」がセットで書かれている点です。たとえばネストでは、`&__title` と書いても `.card__title` というクラス名は作られないことが注意点として挙がっています。`&` は文字列の連結ではなくセレクタだからです。親がセレクタリストの場合に `:is()` と同じ詳細度の扱いになり、ID の強さが意図せず乗ってしまう点も、Sass から移行するときに見落としやすいところです。

実務で役立ちそうな注意点がほかにも多くあります。`:has()` は `body:has(.menu-open)` のように対象を広く取ると、`body` 内のあらゆる変化で再評価が走ります。`container-type: inline-size` は中身で幅が決まる要素に付けるとつぶれてしまいます。`aspect-ratio` は比率を固定するものではなく希望値なので、中身が多ければ箱は伸びます。どれも一度はまると時間を取られる類の話です。

アニメーションまわりの記述も丁寧です。スクロール駆動アニメーションは `@supports` で囲み、`animation` の一括指定が `animation-timeline` をリセットするので順番に気をつける必要があります。著者自身が macOS で「視差効果を減らす」を有効にしていることにふれ、`prefers-reduced-motion: no-preference` のなかに入れるよう勧めているのも好感が持てます。`@starting-style` は、Firefox では `display` の遷移に未対応なので、フェードインは効いてもフェードアウトは一瞬で消える、といった差分まで書かれています。

UXエンジニアリングの視点では、ビルドの仕組みを減らせること以上に、「コンポーネントが自分の置かれた場所に応じて振る舞える」機能がそろってきたことに価値があると感じます。コンテナクエリと `cqi`、subgrid、論理プロパティは、デザインシステムのコンポーネントを文脈に強くする道具です。`dvh` はツールバーの出入りに合わせてサイズが変わるので、レイアウトには `svh` を基本にする、という著者の方針もそのまま参考にできます。最後の「分からないときは MDN の Baseline バッジを見て、危ない部分は `@supports` で包む」という手順は、チームの判断基準としても使いやすいでしょう。

### [Is your app ready for iPhone Duo?](https://codewithbeto.dev/blog/is-your-app-ready-for-iphone-duo)

> **出典**: Sidebar | **公開日**: 2026-09-28 | **カテゴリ**: design

**3行まとめ**
- 初の折りたたみ iPhone「iPhone Duo」に向けて、既存アプリをどう見直すかをまとめた実践的なガイドです
- まず Xcode 27.1 と iOS 27.1 SDK でリビルドし、そのうえでサイズクラスで空間の変化に追従させ、セーフエリアと折り目を意識するよう勧めています
- システム標準のコンポーネントを使うと、ツールバーの縦配置やシートの位置調整などを iOS が自動で面倒を見てくれます

**詳細解説**

最初の一歩はとても具体的です。古い SDK でビルドしたアプリは内側のディスプレイの狭い範囲に収まり、周りに大きな余白が残ってしまいます。新しい SDK でリビルドするだけで全画面を使えるようになり、思ったより手間がかからないと分かるかもしれません。そのうえで「広がった空間で何をするか」を考えるのが、本当のデザインの仕事だという流れです。

記事が繰り返し強調しているのは、空間が常に変わり続けるという点です。回転、半分だけ折る、Split View で隣に別のアプリを開く、といった操作で、アプリが使える領域の大きさも形も変わります。端末は同じ iPhone Duo でも、アプリが持っているウィンドウは同じではありません。メールアプリの例では、狭い画面では受信箱とメッセージを順番に見せ、広ければ横に並べます。プロダクトそのものは変わらず、不要になった画面遷移がなくなるだけ、という説明が分かりやすいところです。

折りたたみ端末ならではの論点は折り目です。半分折った状態では画面中央が見えにくく操作しにくい領域になるため、大事な操作要素はそこから離しておくのがよいとされています。一方、記事やフィード、リストのようにスクロールする内容は、中央の固定要素を操作するわけではないので自然に通過できます。カメラや操作部によるセーフエリアが辺ごとに違い、回転でも変わること、ConcentricRectangle のような API で画面の角のカーブに合わせられることにもふれています。

UXエンジニアリングの視点では、この記事の考え方はウェブのレスポンシブデザインとそのまま重なります。「折りたたまれていることを知る必要が本当にあるのか」を問い、空間に応じて振る舞うレイアウトなら特別な設計なしで適応できる、という指摘は、前述の CSS 記事にあるコンテナクエリの考え方と同じです。テストの節にある「サイドバーが空間を失ったあとも残る」「技術的には収まっているのに大きな空白がある」といった観点は、見た目の崩れではなく体験の違和感を探すためのチェックリストとして使えます。React Native なら Expo Router や Expo UI がすでに対応している、という補足もあります。

### [The age of the soft skill](https://rudyfaile.com/2026/09/24/the-age-of-the-soft-skill/)

> **出典**: Sidebar | **公開日**: 2026-09-29 | **カテゴリ**: design

**3行まとめ**
- 技術的な能力が希少でなくなった今、「扱いにくいけれど替えがきかないエンジニア」という取引は終わった、と論じるエッセイです
- 希少になったのは判断力で、正確さ、反応の速さ、問いの背景まで考えているか、一緒に働きやすいか、が見られていると整理しています
- AI の回答をそのまま貼り返す「meat proxy」や、長い AI 文書を読ませることを、相手の時間を奪う行為として強く批判しています

**詳細解説**

著者は1年半前に「Claude はいまいち」と書き、9か月前に「まあまあ良い」と書いた人です。いまは、自分がよく知っているシステムの制約を渡すと、モデルが返す設計のほうが実際に出荷したものより良いことが多い、と認めています。ただしモデルにできないのは、そもそもの制約を知ることです。誰のためのものか、何を壊してよいか、前回試したときに何が起きたか。その部分は人が担う、という前提から話が始まります。

いちばん読まれてほしいのは、書くことと読むことのコストが逆転したという指摘です。以前は3ページ書くほうが3ページ読むより大変だったので、長い文書は少なくとも誰かが手を動かした証拠でした。今は書くコストはほぼゼロで、読むコストは変わりません。圧縮していない AI 文書を渡すのは、作業を共有しているのではなく相手に移しているだけだ、という整理です。Pascal の「短い手紙を書く時間がなかった」という言葉を引いて、短くすることこそが仕事だったと述べています。

「meat proxy」の節もよく書けています。AI を使うこと自体は前提として認めたうえで、なぜ自分ではなく「あなた」に聞いたのか、その理由を分かっているかを問うています。「Claude はこう考えている」という返事には興味がなく、知りたいのは Brian がどう考えるかだ、という一文が端的です。「X を試して Y だと思ったが、まだ分からない」という質問は歓迎される、という線引きもはっきりしています。

UXエンジニアリングの視点では、この話はチーム内のコミュニケーションだけでなく、AI を組み込んだプロダクトの出力設計にも当てはまります。長くて構造化された生成テキストは、読む側の注意というもっとも高いコストを消費します。前述の「Plan mode is dead」で仕様書が読まれなかった話とも同じ根を持っています。ただし記事全体はかなり強い口調で、「曖昧さはもう止まる理由にならない」といった主張は、組織やタスクの性質によっては当てはまらない場面もあるでしょう。読む人の立場によって受け取り方が大きく変わる記事です。

### [A eulogy for the software engineer](https://davekiss.com/blog/eulogy-for-the-software-engineer/)

> **出典**: Sidebar | **公開日**: 2026-09-28 | **カテゴリ**: design

**3行まとめ**
- 「ソフトウェアエンジニア 1968–2026」の葬儀という形式で、AI によって変わった仕事への喪失感と、それでも残るものを語るエッセイです
- ヘッドホン（没頭）、ノート（完了の定義を描くこと）、キーボード（出荷物への責任）の3つを棺に納め、最後にそれがそのまま新しい仕事の形だと気づく構成になっています
- 失われたのはエンジニアではなく「苦労する道が唯一の道だったこと」で、だからこそ意図して技術と審美眼を次の世代に手渡す必要がある、と結んでいます

**詳細解説**

著者は学位なしで独学し、Google や Stack Overflow を頼りにこの業界に入った人です。誰の許可もいらず、中にいる人が知っていることを惜しみなく公開してくれたから入れた、という経験が全編の土台になっています。Grace Hopper、Tim Berners-Lee、Linus Torvalds、Ryan Dahl、_why the lucky stiff と「祖先」の名前を挙げていく部分は、この文化への愛情がよく伝わってきます。

中盤で、この変化を起こしたのは自分たち自身だと認めています。コミット、回答、レビュー、ドキュメント、夜中にフォーラムで書いた丁寧な返信が、すべて学習データになりました。そのうえで、公開されなかったものに目を向けます。修正が見つかるまでの3時間の格闘、出荷しないと決めた間違った案、行き詰まったときに一緒に考えた相手、そして審美眼です。それらはスクレイピングできない、という指摘が記事の転換点になっています。

各イベントの発表紹介にも参考になる話が多く含まれています。マルチテナント SaaS での SLO の実装経験、6か月で3件の重要なサービス劣化を SLO 監視で検知した事例、「越境するなら専門用語を使うな」という発表などです。YOUTRUST の、ライブラリのアップグレード状況をバージョン種別でスコア化し、「アルバイト募集」という形で自発的な参加者を集めた取り組みも、地道な改善に人を巻き込む方法として参考になります。

いちばんの収穫として挙げられているのが End-to-End SLO です。CUJ（Critical User Journey）を起点にし、「サービスごとの SLO を積み上げるだけでは、ユーザーの『商品を買って受け取る』という目的は守れない」という考え方です。もうひとつの Implicit SLOs は、これまでプロダクトが提供してきたサービスの質が、顧客のなかに暗黙の「信頼性の期待」を作っている、という概念です。

UXエンジニアリングの視点では、どちらの概念もユーザー体験の品質をどう測るか、という問いに直結しています。個々の API が SLO を満たしていても、ユーザーが目的を達成できなければ意味がありません。以前は速かった画面が遅くなれば、仕様上の基準を満たしていても信頼は下がります。前述の Apollo Router の記事で分散トレースがつながったことは、まさにこうした端から端までの計測の土台になるものです。記事自体はイベントレポートなので、概念の詳細は紹介されている資料をたどるとよいでしょう。

### [How to scale intent, quality, and artistry with AI](https://www.youtube.com/watch?v=GLvFTMtw4Jk)

> **出典**: Sidebar | **公開日**: 2026-09-29 | **カテゴリ**: design

**3行まとめ**
- Lenny and Friends Summit（2026/09/10、サンフランシスコ）での、Stripe の Katie Dill による講演の動画です
- AI で作ることが簡単になるなか、プロダクトが没個性な「ゾンビ UI」にならないために何が必要かを語っています
- 明確な視点、ユーザーへの理解、細部へのこだわりをどう AI ツールに組み込むか、最初の案の先まで手を入れること、AI をより独自性のあるプロダクトづくりに使うことが論点です

**詳細解説**

この項目は YouTube の動画で、手元にあるのは概要欄の説明だけです。そのため内容の紹介は概要欄の範囲にとどめます。Katie Dill は Stripe のデザインを率いてきた人で、細部まで作り込まれたプロダクトで知られる会社の視点から話している点が興味深いところです。

概要欄によると、講演の中心は「優れたデザインは今も明確な視点、ユーザーの理解、細部への気配りに支えられている」という主張です。そのうえで、それらの基準を AI ツールのなかに組み込む方法、最初の出力で止めずに編集を重ねること、AI を使ってより独自性のあるプロダクトを作ることが語られているようです。

今号では、同じ問題意識を持つ記事がいくつも並びました。「The default is not a design decision」は、AI の最初の案が意見より先に出てくることで美的な判断の場所がずれる、と指摘しています。「A eulogy for the software engineer」は、平均値は出発点として悪くないが、あなたは平均に混ざらない部分だ、と語っています。「最初の案の先まで手を入れる」というこの講演の論点は、そのどちらにも対する実践的な答えになりそうです。

UXエンジニアリングの視点では、「基準を AI ツールに組み込む」という部分がとくに気になります。デザインシステムのトークンやコンポーネント、リポジトリに置くガイドラインを通じて、チームの視点を AI の出力に反映させる取り組みは、エンジニアが担える領域です。今号の記事を読んでから動画を見ると、論点がつかみやすいでしょう。
