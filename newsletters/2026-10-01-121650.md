### [Why has Shopify dropped React Native?](https://newsletter.pragmaticengineer.com/p/shopify-native-mobile)

> **出典**: The Pragmatic Engineer | **公開日**: 2026-09-29 | **カテゴリ**: engineering

**3行まとめ**
- 6年前に React Native へ全面移行した Shopify が、すべてのアプリを Swift と Kotlin のネイティブ実装に戻すと発表しました。その背景を Gergely Orosz さんが関係者への取材をもとに整理した記事です
- 理由は、コーディングエージェントのおかげで同じ機能を2つのプラットフォームで作るコストが下がったことです。Shop アプリはすでに12週間でネイティブ化を終えています
- 2つの実装のずれを防ぐために、Swift と Kotlin の両方を同じテストで検証する共通のテストスイートを用意している点が、この移行を支えています

**詳細解説**

2020年に Shopify が React Native を選んだ理由は、Android 版の開発が遅れがちだったことです。記事では、iOS 版のヒットから Android 版のベータまで14か月かかり、成長の波を逃した Clubhouse の例を挙げています。「一度書けば両方で動く」「Web とモバイルを行き来できる人材」「機能の差を埋める作業を減らす」という狙いは実際に当たりました。2025年の時点でも、画面表示は500ms未満、クラッシュなしのセッションは99.9%超と、成功を宣言していたほどです。

それでも方針を変えたのは、判断の前提が動いたからです。モバイル責任者の Mustafa Ali さんは「エージェントが実装・移植・テスト・レビューの作業を十分にこなせるようになり、2つのプラットフォームで作るコストが決め手ではなくなった」と話しています。New Architecture への移行で得られた改善は、起動時間で Android が約10%、iOS が約3%と小さいものでした。共有の利点が小さくなる一方で、プラットフォームの機能や純正のツールに近いというネイティブの利点は残ります。エンジニアリング責任者の Farhan Thawar さんの「共通言語だった React が、LLM のおかげで英語に置き換わった」という言葉が、変化をよく表しています。

運用面でおもしろいのは、検証の仕組みです。Swift と Kotlin で書いたビジネスロジックを1つのテストスイートで検証し、両方で同じテストに通らないと出荷できません。このテストはデスクトップ上でヘッドレスに動くので、エージェントが素早く試行錯誤できます。チームも iOS と Android で分けず、同じ開発者が両方を担当する体制を続けるそうです。

UXエンジニアリングの視点では、「作り直しはパフォーマンス、安定性、アクセシビリティ、品質のすべてで今を上回ること」という条件を最初に置いている点が参考になります。ただ、共通テストで確かめられるのはおもにビジネスロジックです。画面の触り心地やアニメーション、プラットフォームごとの UI の慣習がそろっているかは、別に見ていく必要があるでしょう。Shopify ほどの規模と検証基盤がないチームで同じ判断が成り立つかも、慎重に考えたいところです。Airbnb の2年での撤退や、7年かけてネイティブ化を進める Notion の例もあわせて紹介されていて、行ったり来たりの歴史として読むこともできます。

### [How to keep enjoying programming in a world of LLMs](https://discourse.haskell.org/t/how-to-keep-enjoying-programming-in-a-world-of-llms/14705)

> **出典**: Sidebar | **公開日**: 2026-09-30 | **カテゴリ**: design

**3行まとめ**
- Haskell プログラマが、LLM の時代にプログラミングの楽しさを手放さず、ほどほどに生産性を上げるための働き方をまとめた投稿です
- 中心にあるのは「計画はエージェントと一緒に立て、コードは自分で書く」という方針です。エージェントには調査、計画の記録、周辺作業、レビューを任せ、大事な判断は自分に質問させます
- トークン切れを「買い足りなかった」ではなく「サービス障害」として扱うこと、生成された PR 本文はコミュニケーションではなくツールの出力だ、という指摘もあります

**詳細解説**

著者は、自分でコードを書き続ける理由を3つ挙げています。コードベースを自分のものとして保つため、腕を落とさないため、そして LLM が人間に読みやすいコードを書くのは宣伝されているほど得意ではないためです。全部を生成に任せると、エージェントしか住めない「荒れ地」になってしまう、という表現は実感がこもっています。

そのうえで、エージェントの役目を具体的に分けています。調査を任せたら、自分も並行して検索し、エージェントが知ることをだいたい把握しておく。調査結果はリンク付きで書き残させ、変な提案が出てきたら「調査ではどう書かれていたか」と聞き返す。エージェントにコーディングを任せるのは、後片付けや定型作業、リスクの低いリファクタリングくらいに絞ります。「おもしろいケースを3つ書いて残り7つを任せたくなったら、抽象化するべきところかもしれない」という注意は、Haskell らしい視点です。

もうひとつの柱がレビューの自動化です。生成器と識別器を組み合わせる GAN になぞらえて、レビュー用のエージェントが指摘を出さなくなるまでは、生成物を読まないと決めています。対象はコードだけではありません。計画にもレビューをかけ、手順2で直す予定の関数が手順7で書かれる、といった矛盾を人間が探さなくて済むようにしています。

UXエンジニアリングの視点では、「エージェントを自分の働き方に合わせる。その逆ではない」という一文が残ります。いまのコーディングツールが標準にしている「計画を立てたらエージェントが実装する」流れも、ひとつの設計上の選択にすぎない、と気づかされます。生成した PR 本文は `<details>` に入れて手書きの本文に添える、という作法もすぐ試せます。一方で、生産性は「2倍くらい」という本人の感覚で、チームや会社がもっと速さを求める場面でこのやり方を通せるかは、環境しだいでしょう。

### [Claude Sonnet 5.5がReact習熟度ベンチマークで見せた一風変わった性質](https://zenn.dev/uhyo/articles/react-profession-bench-18)

> **出典**: uhyo | **公開日**: 2026-09-30 | **カテゴリ**: frontend

**3行まとめ**
- React 習熟度ベンチマークの第18回です。Sonnet 5.5 は effort=high で81.08点、max で91.74点で、一段の差（+10.67）はこのベンチの全モデルのなかでもっとも大きくなりました
- max ではコンポーネント設計（+0.95）、アクセシビリティ（+0.77）、パフォーマンス意識（+0.59）が大きく伸び、`useId` の使用は6回から35回に増えました
- high は3サンプルを約1時間45分で終えるほど速い一方、max は約28時間かかります。著者は high での性能が大事だとして、Sonnet 5.5 は実装役として使うのがよいかもしれない、と考えています

**詳細解説**

このベンチは13種類の仕様をモデルに実装させ、評価役のモデル（Sonnet 4.6 に固定）が状態設計や Effect の扱い、アクセシビリティなど6つのカテゴリに分けて採点するものです。各条件3サンプル、今回は合計78実装です。これまでの Claude モデルでは high と max の差は3〜5点ほどでしたが、Sonnet 5.5 だけが10点以上離れました。max の91.74点は Opus 5 max（90.28）を上回り、Opus 5.5 high（90.79）とも並びます。

おもしろいのは、点数だけでなくコードの形まで変わることです。high では1実装あたりの `.tsx` ファイルが5.7個、`App.tsx` が平均109行と、前世代の Sonnet 5（7.7個、89行）より1ファイルに詰め込む書き方に戻っています。max では10.7個、57行になり、Opus 5.5 max（12.0個、51行）に近づきます。`useSyncExternalStore` や `useTransition`、`useOptimistic` といった新しめのフックも、max でだけ使われるようになりました。13の仕様すべてで max が high を上回っていて、効き方は全体に及んでいます。

記事の後半は、分析を担当した AI によるレポートです。運用の記録として、エージェントが自分の成果を確かめるために起動した開発サーバが残り続け、7つの vite が約1GBを使っていた話も出てきます。エージェントにブラウザで確認させる仕組みを組むときに、そのまま参考になる失敗例です。

UXエンジニアリングの視点では、アクセシビリティの点数と `useId` の使用回数がそろって動いている点が気になりました。ラベルと入力欄をきちんと結び付けるかどうかが、モデルの性能というより effort の設定ひとつで変わる、ということです。既定の設定で評価して「このくらい」と判断すると、見落とすものがありそうです。採点は LLM によるもので、作業時間やコストは点数に入っていない点は、読むときに頭に置いておくとよいでしょう。

### [Sidenotes with CSS anchor positioning](https://vincent.bernat.ch/en/blog/2026-css-sidenotes)

> **出典**: Sidebar | **公開日**: 2026-09-30 | **カテゴリ**: design

**3行まとめ**
- CSS のアンカー位置指定（anchor positioning）を使い、JavaScript なしでサイドノート（余白の注釈）を実装する方法を紹介した記事です
- 注釈は参照している段落の直後に `<aside role="note">` として置くので、テキストブラウザやスクリーンリーダー、リーダーモードでも読む順番が自然になります
- 画面が広く、ブラウザが対応していれば右の余白に移し、参照記号と同じ高さにそろえます。前の注釈と重なりそうなときは、自動で下にずらします

**詳細解説**

サイドノートを JavaScript なしで描画する方法としては Tufte CSS が知られていますが、中身はインライン要素に限られます。この記事のやり方は、2023年に Eric Meyer さんが示した手法をもとにしていて、注釈に段落を複数入れられます。HTML 上の位置も自由です。

仕組みはこうです。参照記号の `<sup>` と注釈の `<aside>` の両方に `data-anchor="--lf-sn-YYY"` のような属性を持たせます。CSS で `attr(data-anchor type(<custom-ident>))` と書くと、その値をアンカー名として読み取れます。参照記号側は `anchor-name` に、注釈側は `position-anchor` に指定し、注釈を `position: absolute` と `left: 100%` で本文の右側に出します。インラインスタイルを書かずに済ませたかった、というのが `attr()` を使った理由だそうです。

重なりの回避もうまくできています。各注釈は `--lf-sidenote` という共通のアンカー名も持っていて、`anchor(--lf-sidenote bottom)` で直前の注釈の下端を参照できます。`top: max(anchor(top), anchor(--lf-sidenote bottom, -1rlh) + 1rlh)` と書けば、参照記号の高さと、直前の注釈の1行下のうち、低いほうの位置に置かれます。最初の注釈ではフォールバック値が効くので、参照記号の高さにそろいます。

UXエンジニアリングの視点では、DOM の順番を読む順番のまま保ち、見た目の位置だけを CSS で動かしている点がよい設計です。`@supports` で `attr()` の型指定まで含めて判定し、`min-width: 72rem` のメディアクエリと組み合わせているので、条件に合わない環境では段落の下に控えめな色で表示されます。注釈が下にあるときは「↓」、余白にあるときは「→」と参照記号を切り替える工夫もあります。同じ週の Frontend Focus で紹介された、アンカー位置指定を使って要素の重なりを検出する Ahmad Shadeed さんの記事とあわせて読むと、アンカー位置指定の使いどころが広がって見えます。

### [Web-Perf Wednesday 011 – SpeedCurve’s INP Observer Missed Its Threshold](https://csswizardry.com/2026/09/web-perf-wednesday-011-speedcurves-inp-observer-missed-its-threshold/)

> **出典**: CSS Wizardry | **公開日**: 2026-09-30 | **カテゴリ**: css

**3行まとめ**
- Harry Roberts さんが、SpeedCurve の計測ライブラリ lux.js で、Event Timing の `durationThreshold: 0` がブラウザに届いていなかったバグを見つけました
- ラッパー関数がオプションを入れ子の `options` プロパティに入れていたため、ブラウザは既定の104msのしきい値を使っていました。104ms未満の操作が記録されず、INP の値や原因の特定に影響していた可能性があります
- 報告から1時間ほどでパッチが出て、修正は lux.js 4.5.3 に入りました。修正の前後で INP の分布が変わっても、それはアプリではなく計測側の変化かもしれない、と注意を促しています

**詳細解説**

バグの中身は、オブジェクトの形のちょっとした違いです。`PerformanceObserver` を包むラッパーは、エントリの種類とコールバック、追加のオプションを受け取ります。ところが追加のオプションを最上位に展開せず、`options` という入れ子のプロパティに入れて渡していました。2023年3月の時点ではスプレッド構文で正しく書かれていて、同年5月の無関係な変更で入れ子になったそうです。2024年5月に INP 用にしきい値0を明示するようになってからも、その値はブラウザに届かず、3年以上そのままでした。

修正は素早く、SpeedCurve の Joseph Wynn さんが報告の1時間ほど後にパッチを出し、9月24日にマージされました。104ms未満の操作が記録されるかを確かめるブラウザ統合テストも追加されています。Web API の受け渡しのような問題は、ブラウザ上で動かさないと見つけにくいので、テストの置き場所として妥当です。リリースノートでは、影響はおもにソフトナビゲーション（SPA 内の画面遷移）だったと説明されています。

記事の後半では、Safari Technology Preview 253 の変更にも触れています。Web Inspector にネットワークのスロットリング機能が入り、`IntersectionObserver` の対象が多いページでの CPU や電力の使いすぎ、`scroll-timeline` の名前を共有したときに数秒メインスレッドが止まる問題などが直りました。Firefox 157 では WebGPU の `TRANSIENT_ATTACHMENT` が使えるようになっています。

UXエンジニアリングの視点では、「サイトと同じくらい丁寧に計測の仕組みもテストする」という締めの言葉がすべてを言い表しています。INP は操作への反応の良さを表す指標で、その値をもとにリリースの良し悪しや目標が決まります。lux.js のバージョンを RUM のデータ期間と一緒に記録しておく、展開のタイミングに注釈を残しておく、といった手順はすぐ真似できます。どの程度の影響があったかは記事からは分からないので、自分のデータで前後を比べて確かめることになります。

### [Why GitHub now ships more CSS, not less](https://frontendfoc.us/issues/760)

> **出典**: Frontend Focus | **公開日**: 2026-09-30 | **カテゴリ**: frontend

**3行まとめ**
- GitHub が3年かけて github.com から styled-components などの CSS-in-JS を取り除き、CSS Modules へ移行した事例が筆頭です。配信する CSS は増えましたが、サーバーサイドレンダリングの時間は55%短くなりました
- Anthropic による claude.ai の高速化の話も紹介されています。入力できるようになるまでの時間（p75）が3.1秒から0.55秒に縮みました
- そのほか、CSS だけで要素の重なりを検出する手法、CSS でグリッドの情報を取り出す手法、流体タイポグラフィについての議論などが並ぶ号です

**詳細解説**

CSS Modules はブラウザの標準機能ではなく、バンドラーの慣習です。`.module.css` のクラス名をファイルごとに一意な名前へ書き換えることで、実行時のコストなしにスタイルの影響範囲を閉じ込めます。GitHub の事例は「CSS を減らす」のではなく「実行時にスタイルを組み立てる処理をなくす」ことで速くした話で、バイト数だけを見ていると気づけない改善です。This Week In React でも、何年もかけて少しずつ移行した話として取り上げられていました。

claude.ai の高速化では、CLS では拾えないほど小さなレイアウトシフトまで追いかけたこと、DOM が変わるたびに24msかかっていた `:root:has()` セレクタ、Chrome のプリレンダリングが間違った高さでページを描いていた問題などが紹介されています。This Week In React の紹介によると、React が初期化される前から静的な入力欄を表示して、すぐに文字を打てるようにしたそうです。作業の多くは Claude が担い、React のコミット回数などをエージェント向けの決まった指標として使ったとのことです。

ほかの記事では、Ahmad Shadeed さんのアンカー位置指定、スタイルのコンテナクエリ、スクロール駆動アニメーションを組み合わせて重なりを検出する手法が目を引きます。Donnie D'Amato さんは、コンテナの幅は予測しにくいので、流体タイポグラフィにはコンテナクエリより viewport 単位のほうが向いている、と論じています。UI の細かな助言をイラスト付きでまとめた「The Interface Cheat Sheet」も、デザインとの会話に使えそうです。

UXエンジニアリングの視点では、「入力できるようになるまでの時間」という指標の立て方が参考になります。チャット UI にとって、利用者が最初にしたいのは文字を打つことです。汎用の指標ではなく、その画面の目的に沿った指標を置くことで、直すべき場所がはっきりします。この号は短い紹介の集まりなので、気になった記事は原文で確かめるのがおすすめです。

### [他職種の専門性を開発プロセスにつなぐ —— QAエンジニアとカスタマーサポートの協業で見えた、工程に応じた関わり方](https://tech.smarthr.jp/entry/2026/09/29/142202)

> **出典**: SmartHR Tech Blog | **公開日**: 2026-09-29 | **カテゴリ**: design

**3行まとめ**
- QA エンジニア（QAE）とカスタマーサポート（SP）が、仕様レビューで協業してきた取り組みの続報です
- レビュー観点のリストを渡すだけでは SP の知見を活かしきれず、工程ごとに「SP が出せる情報」と「確認する内容」を整理する必要があると分かりました
- 指摘を他の仕様にも使える問いへ置き換え、運用は SP 主体に移っています。指摘のその後を記録するデータベースも作りましたが、仕様への反映やリリース後の問い合わせへの影響はまだ追えていない、と正直に書いています

**詳細解説**

具体例として紹介されているのは、承認済みの申請を取り消せる機能のレビューです。当時の仕様には、取り消しが必要な申請を管理者に事前に知らせる仕組みがなく、問題が起きた後も対象の申請を探しにくい状態でした。SP は、管理者が気づかないまま取り消しの期限を過ぎるおそれを指摘し、似た問い合わせの実績をもとにアラート通知を提案しました。開発チームからは「ユーザーのニーズが具体的に見えた」という声があったそうです。

協業してみて分かったのは、SP の知見が問い合わせの情報だけではないことです。顧客の声から整理したインサイト、仕様のナレッジ、問い合わせ件数のような数字、顧客への案内文の案まで蓄積されていました。さらに、機能を使う前後の操作をたどり、連携先や周辺機能まで見ながら、どこで問題が起きるかを予測する力そのものが専門性だった、と書かれています。

そこで、PRD 作成、PRD レビュー、仕様の具体化、リリース後の4つの工程について、SP が出せる情報と確認する内容を表にまとめました。指摘は案件ごとに終わらせず、「期限のある操作について、対象者が期限切れに気づけるか」「データ出力、一括更新、権限の違いが考慮されているか」のような問いに置き換えています。これらは Notion AI のスキルにもまとめられ、SP のメンバーが短時間で観点を増やすのに使われています。

UXエンジニアリングの視点では、サポート部門を「ユーザーリサーチの蓄積を持つチーム」として開発の上流に招いている点が興味深いです。問いのリストは、そのまま UI のヒューリスティック評価にも使えそうな内容です。ツールがフィードバックの質にどれだけ効いたかは切り分けられていないため、経験のあるメンバーの判断と組み合わせて使う、という慎重さもよいバランスです。

- 該当するレスポンスは `x-vercel-cache` が `MISS` になり、Runtime Logs には `vary_key_denied:cookie` と記録されます

**詳細解説**

`Vary` は、どのリクエストヘッダーによってレスポンスが変わりうるかをキャッシュに伝えるヘッダーです。`Vary: Cookie` は「Cookie が違えば別のレスポンスとして扱ってほしい」という意味になります。Cookie の値は訪問者ごとに違うことが多いので、共有キャッシュではほぼヒットしないエントリが増えるだけになりがちです。今回の変更でも、レスポンス自体はふつうに返され、保存されないだけです。

対応の方針は2つに分かれます。Cookie によって中身が変わらないなら、`Vary` から `Cookie` を外せば、ほかの条件を満たす限り CDN でキャッシュされます。中身が Cookie によって変わるなら、`Cookie` を残したうえで `Cache-Control: private` を付け、個人向けのレスポンスが共有キャッシュに入らないようにします。`Cookie` 以外の `Vary` ヘッダーの扱いは変わりません。

UXエンジニアリングの視点では、キャッシュされているつもりだったページが、気づかないうちに毎回オリジンへ行くようになる可能性がある点に気をつけたいところです。表示までの時間が延びれば、利用者の体感に直接響きます。自分で `Vary: Cookie` を付けた覚えがなくても、ミドルウェアやライブラリが付けていないか、ログで `vary_key_denied:cookie` を一度確かめておくと安心です。個人向けの内容を共有キャッシュに載せない、という本来の安全面の考え方を見直すきっかけにもなります。
