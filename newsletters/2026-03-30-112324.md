### [The three thirds](https://uxdesign.cc/the-three-thirds-2fba0a893a85)

> **出典**: Sidebar | **公開日**: 2026-03-27 | **カテゴリ**: design

**3行まとめ**
- デザイナーという職業が、うまくいっている人（36%）、苦しんでいる人（35%）、どちらでもない人（29%）にほぼ均等に分裂している
- この三等分は単なる景気の波ではなく、職業としてのアイデンティティ危機を示している
- キャリアの方向性として「役割の再定義」「ポートフォリオキャリア」「完全な転身」「内面的な再交渉」の4つが観察されている

**詳細解説**

Figmaの「State of the Designer 2026」レポートが明らかにした数字は、デザイン業界に静かな衝撃を与えています。デザインが良くなったか悪くなったかを問われ、ほぼ均等に三分割された回答は、業界に共通の物語がないことを意味しています。

著者のVlad Derdeicea氏は、ヨーロッパの銀行で7人のデザイナーを率いる管理職です。15年のキャリアを持ちながら、何ヶ月もFigmaを開いてデザインをしていないと告白します。ステークホルダーとの調整、チームコーチング、ロードマップの交渉。デザイナーになった理由とは異なるものに日々を費やしている、という感覚は多くの中堅デザイナーに共感を呼ぶでしょう。

興味深いのは「第三の三分の一」、つまり「変わらない」と答えた29%への分析です。燃え尽きてもいないし、成功してもいない。ただ出勤し、仕事をこなし、給料をもらう。著者はこれを無関心ではなく、明確なシグナルを出さなくなった業界への合理的な対応だと見ています。しかし、次のレイオフやAIの進化が来たとき、もっとも準備ができていないのはこのグループだとも指摘します。

UXエンジニアリングの視点から見ると、この記事は「つくること」と「つくることについて考えること」の間にある緊張関係を浮き彫りにしています。デザインとエンジニアリングの境界が曖昧になるなかで、手を動かすクラフトから離れていくキャリアパスにどう折り合いをつけるか。答えはまだ出ていませんが、その問い自体に向き合うことの価値を、この記事は丁寧に描いています。

### [The evolution of craft](https://carlsz.dev/posts/evolution-of-craft)

> **出典**: Sidebar | **公開日**: 2026-03-27 | **カテゴリ**: design

**3行まとめ**
- AIの登場でUX専門家やエンジニアの役割が「Operator（実行者）」から「Intent Architect（意図の設計者）」へ変化している
- ソフトウェア開発にInner Loop / Outer Loopに加え、AIの出力を監督・評価する「Middle Loop」が出現している
- テイストや設計意図を機械可読な形式で明文化する「プログラマブルインフラ」が新しいキャンバスになる

**詳細解説**

Jakob Nielsenが指摘するように、AIは従来のクリエイティブワークフローを反転させています。ラフスケッチから始めて何週間もかけて最終成果物に近づけるのではなく、AIが数分で高忠実度の成果物を生成し、そこから人間が反復・レビュー・精緻化する流れです。

この記事が提示する「Middle Loop」という概念は注目に値します。Inner Loop（コードを書いてテストする個人のサイクル）とOuter Loop（CI/CDとデプロイの全体サイクル）の間に、AIエージェントの出力を指示・評価・改善する監督レイヤーが生まれているという考え方です。ThoughtWorksの調査によれば、もっとも効果的なエンジニアは、タイピングの速さや構文の暗記ではなく、システム思考、問題分解、仕様の明確さで定義されるようになっています。

具体的な実践例として、Anthropicの`frontend-design skill`が挙げられています。これはビジュアルモックアップではなく、プレーンテキストのMarkdownファイルとしてAIエージェントに対して美的方向性やアンチパターンを明示的に指示するものです。デザイナーがインターフェースを描くのではなく、意図を設計している。まさに「Intent Architect」の具体像といえます。

前述の「The three thirds」と合わせて読むと、デザイナーのキャリア危機に対するひとつの方向性が見えてきます。手を動かすクラフトから離れることは終わりではなく、クラフトの定義そのものが進化しているのだ、という視座です。

### [GenUI vs. Vibe Coding: Who's Designing?](https://www.nngroup.com/articles/genui-vs-vibe/?utm_source=rss&utm_medium=feed&utm_campaign=rss-syndication)

> **出典**: Nielsen Norman Group | **公開日**: 2026-03-27 | **カテゴリ**: design

**3行まとめ**
- 生成UI（GenUI）はAIがUI要素の生成を自ら判断し、Vibe CodingはユーザーがAIにビルドを指示するもので、デザインの責任の所在が異なる
- Vibe Codingは「何をつくるか」を明確に表現できるユーザーを前提としており、そのスキルを持たない大多数のユーザーにはGenUIが有効
- 両者の失敗モードは根本的に異なり、Vibe Codingは実行品質、GenUIはデザイン判断で評価される

**詳細解説**

NNGroupのKate Moranによるこの記事は、混同されがちな2つの概念を明確に区別しています。Vibe Codingでは「旅行プランナーアプリをつくって」とユーザーが指示します。GenUIでは「旅行の計画を手伝って」とユーザーが言ったとき、AIが自らチェックボックスやインタラクティブなチャートを生成すべきだと判断します。

とくに示唆に富むのは、Vibe Coding内部にも仕様の詳細度というスペクトラムがあるという指摘です。「旅行プランナーをつくって」という曖昧なプロンプトと、3カラムレイアウトやMapboxのカラーコードまで指定する詳細なプロンプトでは、AIに委ねられるデザイン判断の量がまったく異なります。

「誰もが自分専用のソフトウェアをAIでつくる時代」という楽観論に対する批判も的確です。何百ものユーザーリサーチセッションを通じて、ほとんどの人はデジタルプロダクトに何を求めているかを特定し言語化する能力を持っていないことを、著者は経験的に知っています。Slackの代替品をVibe Codingでつくれるという議論は、専門企業が何年もかけて蓄積してきたユーザーリサーチと反復改善の制度的知識を見落としています。

UXエンジニアにとって、この区別は重要な設計指針になります。GenUIを組み込むシステムでは、UIの生成判断そのものが設計対象になるからです。従来のユーザビリティテストのように、タスク完了率や満足度シグナルで評価する必要があるでしょう。

### [The Code Agent Orchestra - what makes multi-agent coding work](https://addyosmani.com/blog/code-agent-orchestra/)

> **出典**: Addy Osmani | **公開日**: 2026-03-26 | **カテゴリ**: performance

**3行まとめ**
- AI支援コーディングには8つのレベルがあり、レベル6以降のオーケストレーション層はレベル5までとは根本的に異なるスキルが必要
- サブエージェント（手動調整の並列実行）とAgent Teams（共有タスクリストとピアメッセージングによる協調実行）の2つのパターンがある
- 3〜5人のチームメイトが適正規模で、検証（verification）がコード生成ではなくボトルネックになっている

**詳細解説**

Addy OsmaniがO'Reilly AI CodeConで発表したこの内容は、マルチエージェントコーディングの実践的なガイドです。半年前、ほとんどの開発者はひとつのAIアシスタントと同期的にやりとりしていました。今日、もっとも生産性の高い開発者は複数のエージェントを非同期で調整しています。

核となるメンタルモデルの変化は、「ペアプログラミング」から「チームマネジメント」への移行です。Conductor（指揮者）モデルでは、ひとつのエージェントをリアルタイムで導きます。Orchestrator（オーケストレーター）モデルでは、複数のエージェントが各自のコンテキストウィンドウで非同期に作業し、開発者は計画と確認を担います。

実践的なパターンとして、サブエージェントではデータ層、ビジネスロジック、APIルートを独立したエージェントに委譲し、依存関係のあるタスクはレポートファイルを待って順次実行します。Agent Teamsでは共有タスクリストと依存関係の自動解決、ピアツーピアメッセージングにより、バックエンドエージェントがフロントエンドエージェントにAPI仕様を直接伝えることもできます。

組織構造の比喻も実用的です。VPがエンジニア個人にタスクを割り当てないように、オーケストレーターは6つのサブエージェントを直接管理するのではなく、2つのフィーチャーリードを経由し、各リードが自分の配下のスペシャリストを管理します。コンテキストの汚染を防ぎながら、深い分解を実現する手法です。

### [AIの提案が正しそうなのに動かない理由を、uvicornのソースコードを読んで理解した話](https://tech.layerx.co.jp/entry/debugging-ai-code-uvicorn)

> **出典**: LayerX エンジニアブログ | **公開日**: 2026-03-27 | **カテゴリ**: engineering

**3行まとめ**
- Coding Agentが提案した`on_event("shutdown")`によるSSE接続の終了は、シャットダウンの順序を考慮すると到達不能なステップだった
- uvicornのソースコードを読むことで、シグナル受信 → リクエスト停止 → 接続待ち → lifespanシャットダウンという順序を理解し、問題の本質を特定できた
- AIの提案が「もっともらしい」からこそ判断が難しく、原理の理解がAIの出力を評価・修正するための鍵になる

**詳細解説**

LayerXのインターンエンジニアが、FastAPI/uvicornのホットリロード問題に取り組んだ実体験のレポートです。Coding Agentに相談したところ、`on_event("shutdown")`でSSE接続を閉じるという「もっともらしい」提案を受けました。しかし実装してもうまくいかない。

uvicornのソースコードを読むと、シャットダウンの処理順序が明確になります。SIGTERMを受信し、新規リクエストを停止し、アクティブな接続が閉じるのを待ち、最後にlifespanのshutdownが呼ばれる。AIが提案したのはステップ4の処理ですが、問題はステップ3で起きていました。SSE接続が無限ループで生き続けているため、ステップ4には到達しないのです。

解決策は、SIGTERMを受け取った時点でSSEのループに終了通知を送ること。シグナルハンドラの前段に処理を挟むだけの、数十行程度の修正でした。

この記事の価値は技術的な解決策そのものよりも、AIとの協働における「理解」の位置づけにあります。シャットダウンの順序というひとつの知識があれば、AIの提案の正否を判断でき、正しい指示を出すこともできます。AIがコード生成を担う時代においても、システムの原理を理解する姿勢が人間側の差別化要因になるという教訓は、前述のマルチエージェント記事やクラフトの進化と通底するテーマです。

### [What Is CSS Containment and How Can I Use It?](https://csswizardry.com/2026/04/what-is-css-containment-and-how-can-i-use-it/)

> **出典**: CSS Wizardry | **公開日**: 2026-04-02 | **カテゴリ**: css

**3行まとめ**
- CSS Containmentは、DOMのサブツリーが独立していることをブラウザに宣言し、再計算の範囲を限定するパフォーマンス最適化手法
- layout、paint、size、styleの4種類があり、ショートハンドとして`content`と`strict`が使える
- OpenTableのモバイルドロワーでの事例では、containmentの適用によりレイアウト再計算のコストが大幅に削減された

**詳細解説**

Harry Robertsによる、CSS Containmentの決定版ともいえる解説記事です。モダンなUIはヘッダー、無限スクロールフィード、カートサマリー、サードパーティウィジェットなど多くの要素で構成されています。何かが変わるたびに、ブラウザはページのどの部分を再計算すべきかを判断しなければなりません。デフォルトでは安全側に倒し、必要以上に広い範囲を処理します。

Containmentはその境界を明示する手段です。4つの基本型は、レイアウト（フロートやカウンターの漏れ防止）、ペイント（要素外への描画の切り詰め）、サイズ（子要素に依存しない固定サイズの宣言）、スタイル（カウンターのスコープ制限）です。

実用面で注目すべきは`content-visibility: auto`との組み合わせです。画面外のコンテンツのレンダリングを完全にスキップできるため、長いリストや記事ページでの効果は大きいでしょう。ただし、`contain: size`を不用意に使うと要素がゼロサイズになったり、`contain: paint`で意図しないクリッピングが発生するなど、副作用への注意も丁寧に解説されています。

デザインシステムの文脈では、カード、モーダル、サイドバーといった自己完結型のコンポーネントに`contain: content`を適用することが、INP（Interaction to Next Paint）の改善に直結します。

### [When All You Can Do Is All or Nothing, Do Nothing](https://csswizardry.com/2026/03/when-all-you-can-do-is-all-or-nothing-do-nothing/)

> **出典**: CSS Wizardry | **公開日**: 2026-03-30 | **カテゴリ**: css

**3行まとめ**
- デザインシステムが`loading=lazy`や`fetchpriority=high`をいつ適用すべきか判断できない場合、何もしないほうが安全
- すべてに高優先度をつけると何も優先していないのと同じになり、ブラウザのデフォルトヒューリスティクスに勝てない
- 取りこぼしの機会損失より、誤った最適化による悪影響のほうがリスクが大きい

**詳細解説**

CSS Wizardryの同じHarry Robertsによる、デザインシステムにおけるパフォーマンスヒントの扱い方についての記事です。コンポーネントがページのどこに配置されるかをデザインシステムが知らない場合、`loading=lazy`をつけるべきかどうかは判断できません。

CMSの自由度が高い環境では、同じカードコンポーネントがヒーロー画像として使われることも、ページ下部のグリッドに使われることもあります。すべてに`loading=lazy`をつければ、LCP候補の画像まで遅延読み込みしてしまう。すべてに`fetchpriority=high`をつければ、優先度が均一になり、ブラウザにとってはノイズでしかありません。

「何もしない」はサボりではなくデフォルトへの回帰です。`loading=lazy`や`fetchpriority=high`は数年前まで存在しなかった機能であり、それらを省略してもブラウザは独自のヒューリスティクスでリクエストを優先付けします。確信を持てる文脈（カルーセルの2枚目以降、3段落目以降の記事内画像など）でだけヒントを適用し、それ以外は意図的にブラウザに委ねる。このシンプルな原則は、デザインシステムの設計指針として非常に明快です。

### [Minimum Viable Product (MVP): Definition](https://www.nngroup.com/articles/mvp-definition/?utm_source=rss&utm_medium=feed&utm_campaign=rss-syndication)

> **出典**: Nielsen Norman Group | **公開日**: 2026-03-27 | **カテゴリ**: design

**3行まとめ**
- MVPは「価値提案仮説」と「ソリューション仮説」の2つを段階的に検証する構造化された実験である
- プロトタイプMVPとライブコードMVPの選択は、リスク×リワードのマトリクスで判断する
- AIツールが開発スピードを上げても、「間違ったアイデアを追求するコスト」は変わらないため、MVPの価値は失われない

**詳細解説**

NNGroupのSara Paulによる、AI時代におけるMVPの再定義です。ローコードプラットフォームやAI支援デザインツールで新しいプロダクトをつくるスピードは上がりましたが、「正しいものをつくっているか?」という問いの重要性はむしろ増しています。

記事の核心は、MVPを2段階の仮説検証として構造化している点です。第1段階の「価値提案仮説」は、ユーザーがそのアイデアに価値を感じるかどうかを検証します。第2段階の「ソリューション仮説」は、特定の実装がその価値を提供できるかを検証します。

リスク×リワードのマトリクスは判断のフレームワークとして実用的です。ハイリスク・ハイリワードのアイデアはプロトタイプMVPで不確実性を下げ、ローリスク・ハイリワードのアイデアはライブコードMVPで実世界のデータを集めます。AIがコードMVPの構築コストを下げたとしても、プロダクトリスクは開発コストではなく「間違ったときのコスト」で決まるという指摘は、Vibe Codingで簡単にプロダクトがつくれる時代だからこそ響きます。

ステークホルダーへの伝え方として、MVPを「ローンチ」ではなく「実験」としてフレーミングすることの重要性も具体的です。

### [The curse of the cursor](https://unsung.aresluna.org/the-curse-of-the-cursor/)

> **出典**: Sidebar | **公開日**: 2026-03-27 | **カテゴリ**: design

**3行まとめ**
- 現在のマウスポインタの非対称な矢印形状は、1970年代にAlan Kayが16x16ピクセルグリッドで表現するために考案したもの
- Appleは2020年にiPad向けに円形ポインタへの大胆なリデザインを試みたが、2025年に従来の矢印形状に戻した
- Retinaディスプレイの時代でも形状が変わらないのは、ポインタが「矢印」ではなく「マウスポインタという固有の形」として定着しているため

**詳細解説**

Doug Engelbartの1968年「Mother Of All Demos」で最初に登場したマウスポインタは、上向きの対称な矢印でした。しかしAlan Kayは、16x16の1ビットピクセルグリッドでは対称な矢印の両辺がジャギーになることに気づき、左辺を垂直に揃えた非対称なデザインを採用しました。この形がXerox Altoに搭載され、Lisa、Mac、Windows 1.0と引き継がれていきます。

Appleの2020年のリデザインは興味深い実験でした。iPadのトラックパッド導入に合わせ、円形のポインタへと変更し、ホバーしたオブジェクトにモーフィングする振る舞いを加えました。しかし実際に使ってみると「革命」というほどの印象はなく、2025年には従来の形状に戻されています。

2020年と2025年のWWDCビデオを並べたときの矛盾が、著者の指摘どおりおもしろいものです。2020年には「精密なポインタをiPadOSに持ってくるのは適切ではないと感じた」と語り、2025年には「新しいポインタはどういうわけかより精密で応答性が高く感じる」と語っています。

記事の結論として引用されるYouTubeコメントが印象的です。「マウスカーソルを矢印だと思ったことがなかった。ずっとそれ自体が固有の形だと思っていた」。フロッピーディスクのアイコンがオブジェクトの記憶を超えてインターフェースの記号として定着したように、マウスポインタもまた、その起源を超えた固有の存在になっているのかもしれません。

### [現場の暗黙知を仕組みに変えるプロダクト開発の第一歩 —— カスタマーサクセス×開発チーム ワークショップレポート](https://tech.smarthr.jp/entry/2026/03/27/120000)

> **出典**: SmartHR Tech Blog | **公開日**: 2026-03-27 | **カテゴリ**: design

**3行まとめ**
- CS（カスタマーサクセス）と開発チームが半日ワークショップを実施し、顧客のペルソナや活用定着のつまずきポイントを共同で整理した
- 開発チームが想定していた「専任担当者が自走できる」というペルソナと、「兼務で余裕がなく他社事例を参考にしたい」という実態に大きなギャップがあった
- 当初想定していた管理ツール開発から、CSの暗黙知を仕組み化する方向へとアプローチが転換した

**詳細解説**

SmartHRの社内ツールユニットの取り組みレポートです。タレントマネジメント機能の活用定着率を上げることがミッションですが、開発チームだけの仮説で進めると現場の実態とずれるリスクがありました。

ワークショップで明らかになったのは3つの課題です。第1に、ペルソナのずれ。開発チームはヘルプページを読んで自走できる専任担当者を想定していましたが、実際は給与計算や入退社手続きの合間にSmartHRを触っている兼務の担当者がほとんどでした。第2に、CSの情報が複数の社内システムに断片化しており、状況把握にタイムラグが生じていたこと。第3に、プロダクトごとにつまずきポイントがまったく異なること。初期設定で止まるもの、社内合意形成に時間がかかるもの、数値は出ているが次のアクションにつなげられないものなど、停滞の構造は一様ではありませんでした。

開発チームがもっとも手応えを感じたのは、CSが現場で培ってきたノウハウの厚みに触れたことだそうです。顧客対応のなかで磨かれたトークや手順を、個人の力量ではなく再現可能な仕組みに落とし込んでいく。プロダクトの外側にある運用の知見が、プロダクト開発の方向性を変えたという事例は、UXリサーチの効用を実感できる良いレポートです。

### [Pell Mell: Crafting a Visual Exploration Platform with Editorial Rhythm](https://tympanus.net/codrops/2026/03/27/pell-mell-crafting-a-visual-exploration-platform-with-editorial-rhythm/)

> **出典**: Codrops | **公開日**: 2026-03-27 | **カテゴリ**: design

- UIを極限まで削ぎ落とし、スクロール駆動のフローとタイポグラフィで体験のリズムを構築している
- Intersection Observerを活用した軽量なアニメーションと、制約付きCMSブロックで拡張性とデザインの一貫性を両立させている

**詳細解説**

Le Fruit StudioによるPell Mellの再設計は、ポートフォリオサイトの典型的なパターンへの問い直しです。きれいなグリッド、フィルター、カテゴリ分け。多くのポートフォリオサイトは同じように構築されていますが、そこには「感覚」がほとんどないと著者は指摘します。

技術的な特徴は、重いアニメーションフレームワークに依存せず、Intersection Observerとシンプルなトランジションで体験を構築している点です。要素の出現はスクロールに連動し、ホバーは控えめなスケールとオパシティの変化だけ。このミニマルなアプローチが、コンテンツ自体を主役にしています。

ナビゲーションの設計思想も明快です。「ユーザーがナビゲーションに頼りすぎるなら、フローに問題がある」という考え方で、メニューは存在するものの体験を中断しません。モバイル版も「デスクトップの軽量版」ではなく、同等に完全な体験として設計されています。

### [New to the web platform in March](https://web.dev/blog/web-platform-03-2026?hl=en)

> **出典**: web.dev | **公開日**: 2026-03-27 | **カテゴリ**: web-standards

**3行まとめ**
- Chrome 146でスクロールトリガーアニメーションと`trigger-scope`プロパティが追加され、CSSだけでスクロール連動の演出を実現できるようになった
- Firefox 149とSafari 26.4で条件なしの`@container`クエリがサポートされ、名前だけでコンテナにマッチ可能に
- Safari 26.4の`display: grid-lanes`でMasonryレイアウトがネイティブに利用可能になった

**詳細解説**

2026年3月のWebプラットフォーム新機能まとめです。Chrome 146、Firefox 149、Safari 26.4のリリースにより、複数の注目機能が安定版に到達しました。

スクロールトリガーアニメーションは、JavaScriptのIntersection Observerに頼ることなく、CSSだけで宣言的にスクロール連動のインタラクションを実装できる機能です。ワーカースレッドにオフロードできるためパフォーマンス面でも有利です。合わせて追加された`trigger-scope`プロパティにより、アニメーショントリガー名のスコープを限定でき、グローバルな名前衝突を防げます。

Safari 26.4の`display: grid-lanes`によるMasonryレイアウトのネイティブサポートも大きな動きです。これまでJavaScriptライブラリに頼っていたレイアウトパターンが、CSS Gridの拡張として宣言的に記述できるようになります。

ベータ版では、Chrome 147に`contrast-color()`関数が搭載される予定です。引数の色に対してもっともコントラストの高い黒か白を返す関数で、アクセシビリティ対応のテキスト色の自動選択に直接活用できます。

### [Why test IDs are an accessibility code smell](https://react.statuscode.com/issues/468)

> **出典**: React Status | **公開日**: 2026-03-27 | **カテゴリ**: frontend

**3行まとめ**
- `data-testid`はアクセシビリティのコードスメルであり、ロールベースのセレクターに切り替えることでアクセシビリティチェックが「ほぼ無料で」手に入る
- Next.js 16.2のAdapter APIが安定版となり、Netlify、Cloudflare、AWSアダプターが年内に予定されている
- TanStack DB 0.6がSQLiteベースの永続化とオフラインサポートを追加し、ローカルファーストなアプリ開発の選択肢が広がっている

**詳細解説**

React Status #468の注目トピックは、TKDodoことDominik Dorfmeisterの記事です。テストで`data-testid`を使うのはベストプラクティスではなくコードスメルであると主張し、ロールベースのセレクター（`getByRole`、`getByLabelText`など）への切り替えを提案しています。ロールベースのセレクターを使えば、テストを書くこと自体がアクセシビリティの検証を兼ねるようになります。

ほかの注目トピックとして、Next.js 16.2のAdapter APIの安定化があります。異なるプラットフォームがビルドプロセスをカスタマイズできるAPIで、Netlify、Cloudflare、AWSのアダプターが年内に登場予定です。また、Dan Abramovが Claude を使ってReactのバグ修正を行った事例も紹介されています。

TanStack DB 0.6の永続化・オフラインサポートも注目に値します。アプリ内にリアクティブなクエリ可能データベースを置き、APIを叩く代わりにローカルでデータの読み取りとフィルタリングを行うアプローチです。Web、モバイル、サーバー環境向けのSQLiteアダプターが揃い、ローカルファーストなアプリケーション開発の実用的な選択肢になっています。
