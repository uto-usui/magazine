### [Splitting atoms & splitting hairs](https://renderghost.leaflet.pub/3mnxjmjjyyc2y)

> **出典**: Sidebar | **公開日**: 2026-06-29 | **カテゴリ**: design

**3行まとめ**
- Atomic Design 誕生から10年、いまや「Atom / Molecule / Organism のどれに分類するか」で消耗するチームが多く、比喩が本来の目的を超えて足枷になっているという指摘です
- 本来の洞察は「コンポーネントはより小さなコンポーネントから合成される」というコンポジションの原則だけで、途中の階層に固有の名前を付ける必要はないと結論づけています
- 入門用の足場として使うのはよいが、そこに居着かず「composability」だけを残せば、命名論争に費やしていた時間を実装に戻せると主張しています

**詳細解説**

Brad Frost が Atomic Design を提唱したのは、コンポーネント指向の考え方を広めるうえで大きな役割を果たしました。ボタンを17個の場所にコピペする文化から、モジュラーで再利用可能なフロントエンドへ移行する際の共通言語として、業界に強く浸透したのは事実です。この記事の著者は Atomic Design 自体を否定しているわけではなく、比喩が独り歩きしすぎている現状に警鐘を鳴らしています。

現場でよく起きるのは、アバターとラベルを持つカードが Molecule なのか Organism なのかを議論して午後がまるごと消える、というたぐいの摩擦です。この議論はよりよいコンポーネントを生まないうえに、Figma と Storybook の両方でセクションを揃える運用コストまで発生させます。著者はこれを「税金」と呼び、実装ではなく分類法に時間が吸い取られる状態を戒めています。

UXエンジニアリングの視点から読むと、この記事はデザインシステム運用における「メタデータの誘惑」への戒めとして機能します。分類階層を厳密に整えるより、最小の再利用可能単位が明確に定義され、組み合わせたときに信頼できる振る舞いをするかを問うほうが本質的です。テストしやすいか、拡張時に壊れないか、他のメンバーが理解して信頼できるか。この観点は組織のスケールとともにますます重くなります。

読み終えて残るのは「composability」という一語です。中間層に molecule / organism というラベルを貼るより、Props の契約と振る舞いの予測可能性を担保するほうがずっと有益で、Atomic Design は入門用のオンランプとして使い切ったら卒業してよい、という提案は多くのチームにとって現実的な処方箋になります。

### [Rethinking Figma in an AI world](https://newsletter.uxdesign.cc/p/rethinking-figma-in-an-ai-world)

> **出典**: UX Collective | **公開日**: 2026-06-29 | **カテゴリ**: design | **著者**: Fabricio Teixeira

**3行まとめ**
- Config 2026 を受けて、Figma がキャンバスを守る側から、コード・モーション・シェーダ・エージェントワークフローへ能動的に拡張する側へ回った転換点を整理しています
- 10年以上にわたって「コラボレーションのデフォルト」だった Figma が、AI 時代にキャンバスを重力の中心に置き続けられるかという問いを立てています
- 併載されている記事群も、AI体験の階層モデル、デザインシステムがひとりの判断に依存する脆さ、AI生成プロトタイプの限界など、いまの論点を横断しています

**詳細解説**

Config 2026 は Figma にとって節目のイベントでした。過去のカンファレンスが「新機能お披露目会」だったのに対し、今回はキャンバスそのものの位置づけを再定義する場になった、という Fabricio Teixeira の観察は的を射ています。キャンバスがコード・モーション・シェーダ・エージェントを飲み込みにいく動きは、Figma が「デザインの中心地であり続けたい」という強い意志の表明でもあります。

AI が製品の設計・試作・出荷の仕方を根底から変えている現在、「デザインファイルが最終成果物」という前提そのものが揺らいでいます。プロトタイプがコードで直接生まれるなら、Figma の役割はどこに残るのか。この問いに対する Figma の答えは、キャンバスを「思考の共有空間」として拡張し続けることでした。Motion、Code on canvas、AI ツール群といった一連の発表は、その延長線にあります。

紹介されている周辺記事も読み応えがあります。Emily Campbell の「The Layers of AI experience」は、AIプロダクトが多次元であり、ひとつの要素の小さな変更が全体に不釣り合いな影響を及ぼすと指摘します。Jim Nielsen の「Consistency of excellence」は「アイコンはこの形、この光源、このストローク」というルール中心の一貫性ではなく、意味と目的に奉仕する「卓越さの一貫性」を掲げます。どちらも AI 時代のデザインシステムを考えるうえで示唆に富みます。

UXエンジニアリングの視点で読むと、Figma の路線変更は「デザインとコードの境界を管理する仕事」に大きな影響を及ぼします。キャンバスが実行可能なコードやシェーダを内包するなら、フロントエンド実装のどこまでをデザインファイルに寄せ、どこからをリポジトリに戻すかの線引きが、今後1〜2年で揺らぎ続けるでしょう。既存のトークンパイプラインや Storybook 中心のワークフローが、Figma 側でどこまで代替されうるのかを、実プロジェクトで少しずつ試しながら見極める姿勢が現実的です。

### [The Goldilocks customizable select height](https://jakearchibald.com/2026/goldilocks-select-height/)

> **出典**: Jake Archibald | **公開日**: 2026-06-29 | **カテゴリ**: web-standards

**3行まとめ**
- Jake Archibald がフルスタイル可能な `<select>` のピッカーで「小さすぎず、大きすぎない、ちょうどよい高さ」を実装する CSS パターンを解説しています
- ビューポート端との余白、最小サイズ、最大サイズをすべて両立させるには `calc-size()` と `flip-block` / `flip-inline` の組み合わせが要点で、`min(fit-content, 12em)` を CSS だけで表現できます
- Firefox / Safari 未対応の場合のフォールバック含め、コピペで使える最終形の CSS もまとまっており、customizable `<select>` の実装リファレンスとして参照価値が高いです

**詳細解説**

Chrome 系ブラウザではフルスタイル可能な `<select>`（customizable select）の実装が進んでいて、popover と anchor positioning というプリミティブの上に組まれています。UA デフォルトは合理的ですが、実運用で気持ちよいピッカーにするには追加の調整が必要です。この記事はその調整を段階を追って詰めていく、実装知の塊です。

とくに興味深いのは、`min(fit-content, 12em)` に相当する挙動を CSS でどう表現するかという課題です。`min()` は intrinsic size を引数に取れないため、そのままでは書けません。ここで登場するのが `calc-size(fit-content, min(size, 12em))` という新しい構文で、intrinsic size を第1引数に、その size を含む計算式を第2引数に置くことで、選択肢が少ないときは fit-content、多いときは 12em で頭打ち、という自然な挙動が実現できます。

もうひとつの見どころは、ピッカーがビューポート端に近づいて反転（flip）したときの挙動です。`position-try-fallbacks` に `flip-block` を指定しておくと、反転時に `margin-block-end` が `margin-block-start` として解釈される、というやや魔術的な仕様に触れています。書き手いわく「Spooky, yet convenient」で、仕様書を読み解かないと出てこない知見です。

UXエンジニアリングの観点だと、この記事は「Web 標準の新機能を実務でどう使いこなすか」の教科書的なサンプルです。UA デフォルトが妥当な出発点であること、Chrome / Firefox / Safari のあいだで支援状況が違うためフォールバックの階段設計が要ること、そして最終的にコピペ可能な短い CSS に集約されること。この3段構えは、View Transitions や Anchor Positioning など他の新機能を触るときにも参考になる型です。

UXエンジニアリングの視点では、AI コーディング支援と a11y の相性は今後の大きな論点になります。生成されたコンポーネントが aria 属性やフォーカス管理を正しく扱えているか、キーボード操作のみで完結するか、生成コードの品質基準をどこに置くか。これらは vibe coding の速度と、a11y の丁寧さのどちらを優先するかというより、両立するための仕組み（linter、CI、a11y スキル定義）を整える設計課題として捉えるほうが健全です。

### [Do websites need to function exactly the same on every platform?](https://www.bram.us/2026/06/21/do-websites-need-to-function-exactly-the-same-on-every-platform/)

> **出典**: Sidebar | **公開日**: 2026-06-29 | **カテゴリ**: design

**3行まとめ**
- 2000年代初頭の「全ブラウザで見た目を揃えるべき」という妄執がようやく解けたのに、いまは「全プラットフォームで機能を揃えるべき」という新しい呪縛に囚われている、という指摘です
- Interest Invokers、Overscroll Actions、Document Picture-in-Picture のような Web プラットフォーム機能の議論が、この呪縛のせいで停滞していると具体例を挙げて示しています
- キーボードショートカットや長押しなど、入力手段固有の機能は「追加の到達手段」であり、プラットフォームごとに異なってよい、という Progressive Enhancement の再解釈です

**詳細解説**

書き手の Bramus は Chrome DevRel でも活動しているブラウザ寄りの人で、この論考は Web プラットフォームの仕様策定の現場で感じている摩擦をそのまま言語化したものです。ピクセルパーフェクション信仰が Progressive Enhancement によって解体されるのに何年もかかったのと同様に、いまは機能パリティ信仰を解体するフェーズに入っている、という時代認識が明確です。

具体例が説得的です。Interest Invokers はホバーで情報カードを出すような UI ですが、タッチデバイスでは「長押し」がすでにシステムのコンテキストメニューを占有しているため、既存の入力ジェスチャーとぶつかります。この衝突を「タッチでも長押しで対応させよう」と押し込もうとすると、`::interest-button` のような擬似要素が必要になり、それが既定で出てしまうと開発者側が抑制する手段を用意しなくてはならない、という悪循環に陥ります。

Overscroll Actions の「デスクトップでは discoverability が低いから必ずボタンを見せるべき」という議論への反論も、Progressive Enhancement の枠組みでスッと理解できます。キーボードショートカットが「あれば嬉しい追加手段」であるのと同じで、Overscroll も追加手段でよく、その機能がなくても UI は完結しているべき、という考え方です。Document PiP に対する WebKit の反対理由（iOS / iPadOS では PiP は動画専用）についても「それは Apple 側の設計判断であって、Web プラットフォーム側で解決すべき問題ではない」と切り込みます。

UXエンジニアリングの視点で読むと、この記事は「機能を差し込む場所を、入力手段の特性に合わせて選ぶ」という設計指針として使えます。モーダルを閉じる方法がタッチではフリック、キーボードでは ESC、マウスでは背景クリック、というのはユーザー体験としてはむしろ自然です。プラットフォームの制約を隠すのではなく、各プラットフォームの強みに寄せて機能を分解する。この考え方はレスポンシブデザインの次のフェーズを言語化しています。

### [Ten years of Terms and Conditions](https://henryach.com/blog/tsandcs/)

> **出典**: Sidebar | **公開日**: 2026-06-29 | **カテゴリ**: design

**3行まとめ**
- 著者が2016年から2026年まで10年間、同意した Terms & Conditions をすべて記録し続けたセルフ実験の結果報告です
- 累計821件の同意で3,066,332語、1日平均約840語で読破するには8.95日相当、日にすると3.53分の負担という定量化がユニークです
- 「4分/日なら現実的では」という一見良心的な結論から、実はドキュメントが他文書を参照する二次負荷や法律読解の遅さを差し引くと現実味が薄れる、という考察に反転していきます

**詳細解説**

同意ボタンを押すときに全文を読む人はいない、という現実を、10年間の実測データで裏付けた研究めいたブログです。3,066,332語という総量は、The Great Gatsby 61冊分、Iliad 20冊分、KJV Bible 3.9冊分に相当します。データセットとして眺めるだけで、いま Web で暮らす人が背負っている「読んだことにする文書」の総量が見えてきます。

もっとも長い契約書のトップ5に Apple Developer TS and CS、Apple Developer Program License Agreement、AWS Service Terms、Grab Terms of Service、TikTok Terms of Service が並んでいるのは、開発者と一般消費者の両方が影響を受けていることの証左です。Apple Developer 関連が2件入っているのは、開発者向けの利用規約がすでに一般契約の域を超えていることを示しています。

さらに面白いのが読解速度の実測です。Virgin Airlines は306.23 words/min、Pizza Hut は210 words/min、Zya は191.34 words/min という結果で、平均語彙の音節数 1.74（対して憲法1.56〜1.62、Gatsby 1.38）から、法律文書がいかに遅読を強いるかがわかります。「他文書への参照が数倍のボリュームを埋め込んでいる」という副次負荷も、実務で契約書を扱った経験があると強く共感します。

UXエンジニアリングの視点だと、これは「消費者が理解できない条件に同意させる UI」を再考する材料になります。デザインシステム上のチェックボックスひとつ、モーダルひとつを設計する担当者にとって、「その同意ボタンを押させることの累積負荷」を数値で把握できるのは大きな価値です。同意 UI に読了時間の目安を添える、要点を先に提示する、参照文書を明示するといった具体策のうち、どこまでを製品側の責務にするかを議論する土台としても機能します。

### [課金基盤のパフォーマンス改善に向けた取り組み](https://tech.smarthr.jp/entry/2026/06/30/100000)

> **出典**: SmartHR Tech Blog | **公開日**: 2026-06-30 | **カテゴリ**: design | **著者**: smarthr_dev

**3行まとめ**
- SmartHR の課金基盤チームが、日次で走る人数計上バッチを親子ワーカー構造に分割し、10万テナント規模でも制約時間内に収まるように再設計した記録です
- 単純な parallel 化ではなく「すべての子ワーカー完了後に送信を1回だけ」という要件を Sidekiq Pro の `Sidekiq::Batch` の `on_success` コールバックで担保しています
- 冪等性を `find_or_initialize_by` で担保しておくことで、並行処理特有のリトライ・再実行時の二重計上リスクを排除しています

**詳細解説**

契約データの移行によって処理対象テナントが数百から数万規模に跳ね上がることが決まっており、既存の直列処理では3時間の SLA に収まらなくなる、という予測から改善プロジェクトが始まっています。所要時間の見積もり（10万テナントで直列は3時間18分、並行化で40分）が具体的で、意思決定の根拠が明快です。

技術選定の議論が読みごたえあります。cron で送信を別起動する方式は、集計が長引いたときに未完了送信のリスクがあり却下。完了数を自前でカウントする方式は、同時完了時の競合と失敗時の整合性が難しく却下。最終的に Sidekiq Pro の `Sidekiq::Batch` を採用し、子ジョブ群を1つのバッチとして起動して `on_success` コールバックで送信ワーカーを起動する構成に落ち着きます。`:complete` ではなく `:success` を選んだ理由（失敗を含めた完了ではなく成功だけを検知したい）も明記されていて、判断過程が透明です。

冪等性への言及も実務的です。`DailyEmployeeCountLog.find_or_initialize_by(...).update!(...)` にすることで、一部の子ワーカーだけを再実行しても二重計上が起きない。並行処理は失敗単位が細かくなるため、冪等性を担保しないと運用が破綻します。ワーカーの引数で対象日付を指定できるようにしてある点も、事後の復旧オペを見据えた設計です。

UXエンジニアリングの視点で読むと、これはバックエンドの並行制御の話に見えて、実は「請求UIの整合性を担保する設計」の話でもあります。集計が中途半端に流れて外部SaaSに反映されると、顧客の請求画面や管理UIに矛盾したデータが表示される可能性があります。バッチ処理層で「成功したときだけ確定送信」という契約を厳密に守ることが、フロントの体験を静かに支えている。表に出ない設計判断が、体験の信頼性を作っている好例です。

### [Inside Bisous: Designing an Editorial Experience for Cinematic CGI](https://tympanus.net/codrops/2026/06/29/inside-bisous-designing-an-editorial-experience-for-cinematic-cgi/)

> **出典**: Vercel | **公開日**: 2026-06-29 | **カテゴリ**: frontend | **著者**: Marc Codina Segura

**3行まとめ**
- Vercel Sandbox のスナップショット期限が「作成日基準」から「最終使用日基準」に変わりました
- 使うたびに期限タイマーがリセットされるため、短めの retention でも「セッションの合間に消える」心配なく長期ワークフローを組めます
- `Sandbox.update({ snapshotExpiration: 7 * 24 * 60 * 60 * 1000 })` のような設定で、7日間未使用のときだけ消える運用ができます

**詳細解説**

Vercel Sandbox はエージェントやコード実行環境を短時間立ち上げるためのプラットフォームで、AI ワークフローの重要な下回りです。従来はスナップショットの期限が作成日基準だったため、「30日で消える」に設定するとどれだけ使い続けていても30日で消える、という運用上の不便がありました。今回の変更で、最終使用日基準に変わり、アクティブに使い続けているスナップショットは維持されるようになります。
