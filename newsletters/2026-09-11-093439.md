## ハイライト

### [AI is making us build too much](https://sjg.io/writing/ai-is-making-us-build-too-much/)

> **出典**: Sidebar | **公開日**: 2026-09-11 | **カテゴリ**: design

**3行まとめ**
- AIが制作コストを下げた結果、コード・テスト・ドキュメント・ポリシー・組織設計まで、あらゆるものを過剰に作るようになるという話です
- Steve Yegge の Wheelhouse（50〜60体のエージェント、60万行、450の「法的成果物」）を題材に、工場が製品より速く育つ現象を読み解いています
- 作るのは安くなったが、所有し続けるコストは下がっていない。「これは存在に値するか」を問う判断こそが希少な仕事になった、という締めです

**詳細解説**

書き出しが率直です。著者は数週間前に「AIはソフトウェアを作るコストを潰した。もう作ることは難しい部分ではない」と書いたが、同じ経済的な変化のもうひとつの帰結を見落としていた、と振り返ります。その帰結とは「私たちはあらゆるものを過剰に設計するようになる」ということ。コードも、テストも、ドキュメントも、ポリシーも、ガバナンスも、組織設計も、です。

やっかいなのは、ひとつひとつの成果物はたいてい妥当で、網羅的で、弁護可能に見えるところでしょう。問題は「もう1個作る」がほぼ無料になった一方で、それを理解し、検証し、保守し、整合を取り、最終的に削除するコストは下がっていないことにあります。

題材になっているのは Steve Yegge の『Fences, not Sandboxes』です。Yegge は Wheelhouse と呼ぶ仕組みで、30年作り続けているゲーム Wyvern を開発しています。エージェントは50〜60体、うち18は名前つきの役職、1日あたり平均270コミット。10週間足らずで Android・iOS・Steam へのリローンチが視野に入り、新クライアントと本番インフラの書き直しも済ませたそうです。デモではなく、実在のプロダクトに対する実際の仕事なのがポイントになります。

数字のほうが強烈でした。Wheelhouse はコードとテストで約60万行、大半が Bash。ゲームコンテンツを除いた Wyvern 本体がその2倍程度なので、工場が製品に追いつきつつあるわけです。エージェントたちは450の「法的成果物」（オフィス、ランブック、判例、権限の範囲、強制機構）を生み出し、100を超える fence を持ち、憲法と判例法と管轄とルールのライフサイクルを備えるに至りました。最後には「Wheelhouse法務局長」という役職が新設されます。古びた判例を刈り取り、ガバナンスをガバナンスするためです。

ここで著者は「笑って切り捨てるのはフェアではない」と一度立ち止まります。Wheelhouse は実際に役立つ仕事をしているし、無状態のエージェントを50体も同じプロダクトに走らせるなら、永続する決定・権限の境界・キュー・デプロイゲート・ロールバックが要るのは当然です。人間のチームはその大部分を人の頭のなかに持っていて、会議や給与やSaaSの費用として隠しているだけ、という見立ても示されます。60万行の工場は、同じ結果を出すために必要な人間の組織より安いかもしれません。だから「大きい＝無駄」ではない。著者の主張は、AIが「その層は元が取れているのか」を確かめさせる経済的圧力を取り払ってしまった、という点にあります。

「安く作れて、持つのが高い」という節が中心です。かつてはポリシーの起草と承認、テストを書く時間、ドキュメントのために手を止めて説明する労力、組織改編のための数週間の議論とスプレッドシートがありました。この摩擦は煩わしいものでしたが、フィルターとしても働いていた。そもそも作るに値するかを、ときどきは誰かに考えさせていたわけです。AIはそのフィルターを外しました。ポリシーも実装もテストも運用手順もRACIもレビューチェックリストも、昼までに出てきます。安くならなかったのは所有のほうです。どのポリシーが現行かを知り、2つの文書の食い違いに気づき、半年後にテストが落ちる理由を理解する人が要る。トークンは安くなっても、認知の負荷は安くならない、と。

過剰化のプロセスの描写も具体的でした。エージェントが判断を誤る → ルールを書く → 大事だからテストを付ける → テストを走らせる場所が要るので強制機構を足す → 例外が生まれるので例外を文書化する → ルール群にオーナーとライフサイクルとレビューが要る → 最後はプロセスを変えるプロセスにも統制が要る。各ステップは全部まともなのに、全体としては不条理になりうる、という構造です。

もうひとつの見立てが「capacity seeks utilisation（能力は稼働先を求める）」でした。大規模なエージェント群を立ち上げると、遊ばせておくのが無駄に感じられる。実際の遊休コストがほぼゼロでもそう感じます。結果として作業はより細かく分解され、バックログは膨らみ、同時に走る変更を吸収するための調整がさらに必要になる。Wheelhouse には完全に設計済みで未実装の作業項目が700件以上たまり、Yegge 自身、Wyvern に対する全作業の20〜25%が Wheelhouse そのものへの作業だと見積もっていて、その比率が下がる気配はないそうです。エージェントがマージ機構の吸収能力より速く変更を出し、キューが無限に伸び、システムはバッチサイズの最適化を続けた——各部分は合理的に振る舞いながら、全体としては前に進まなくなる。この失敗の形は示唆的です。

指標の話も現実的でした。行数、コミット数、作成した文書数、書いたテスト数、クローズしたチケット数、消費トークン数は、どれも活動の量であって価値ではない。[Faros が1万人超の開発者のテレメトリを分析した調査](https://www.faros.ai/blog/ai-software-engineering)では、AI活用度の高いチームはタスク完了が21%増、マージしたプルリクエストが98%増だった一方で、レビュー時間は91%増、平均PRサイズは154%増、開発者あたりのバグは9%増。会社レベルではAI採用と成果のあいだに有意な関係が見られなかったとあります。商用ベンダーによる相関研究なので因果の証明ではありませんが、生産は加速し、吸収は加速しなかった、という形は見て取れます。BetterUpの調査では、米国のデスクワーカーの40%が「もっともらしく見えるが、考える作業と修復を受け手に押しつけるAI生成物」を直近1か月で受け取ったと答えたそうです。送り手は加速を体験し、受け手は新しい仕事を体験する、という対比が効いていました。

著者は fence 自体を否定していません。Yegge が「もっとも強力なモデルでも無人運転中に1日1回はひどい判断をする」と言っている以上、文脈的なルールも強い封じ込めも両方要る、という立場です。問題はガバナンスではなく、その量を質と取り違えることだ、と。100の fence が正解かもしれないし、95個多すぎるのかもしれない。何を守り、正しく保つのにいくらかかるのかが分からないうちは、数字は何も語らない。

提案は地味で、ふつうのエンジニアリング規律への回帰でした。内部機構には予算を持たせる（トークンやインフラだけでなく、プロダクトの余力と人間の注意をどれだけ消費してよいかの上限）。ルールには理由を持たせる（fenceは想像可能なリスクではなく、名前のついた実在の失敗モードに対応させる）。すべてに見直しと引退の経路を用意する（ポリシー、ドキュメント、テスト、エージェント、役職まで）。そして工場の外側を測る（顧客体験は良くなったか、意思決定は速くなったか、信頼性は上がったか、誰かの時間は戻ってきたか）。

UXエンジニアリングの視点で読むと、これはデザインシステムの運用とほぼ同型の話です。トークンが増え、コンポーネントのバリアントが増え、ガイドラインが増え、ガイドラインを守らせるlintルールが増え、lintの例外を記録するドキュメントが増える。どの1歩も妥当で、全体は誰も読めなくなる。この記事の実務的な使いどころは、最後の「引退の経路」でしょう。デザインシステムでもプロンプトでもCLAUDE.mdでも、追加のレビューはあるのに削除のレビューがない、という状態は珍しくありません。「これが消えたら何が悪くなるか」を説明できないものは堆積物として扱う、という基準は、そのまま棚卸しの運用に落とせます。

締めの一文がよく効いています。足場が建物に匹敵しはじめたなら、答えは自動的に「足場部長を置くこと」ではない、と。

### [Building data-driven design systems](https://ky.fyi/posts/data-driven)

> **出典**: Sidebar | **公開日**: 2026-09-11 | **カテゴリ**: design

**3行まとめ**
- Scribe の最初で唯一の Design Engineer として18か月、デザインシステム Stylus を立て直した記録です
- 半年ごとに全エンジニア・デザイナー・PMへ同じサーベイを4回配り、6つの設問の推移と、その裏で打った手をセットで並べています
- ドキュメントの設問が+40%、総合評価が7.6→9.1。Omlet の静的解析ではコンポーネント網羅率が6か月で37%→52%になりました

**詳細解説**

2024年6月、著者は Scribe に最初の（そして唯一の）Design Engineer として入社します。Scribe はブラウザ拡張でクリックとキー入力を記録し、手順書を自動生成するツールで、60万社以上、Fortune 500の94%が使っているとのこと。デザインシステム Stylus は Radix UI と Tailwind という堅い土台の上に建っていましたが、専任のメンテナがいないまま会社が大きくなり、ひびが入りはじめていました。

診断が4つ挙がっています。ドキュメントが散らばっていてシステムに何ができるのか、どう使う想定なのかが分からない。採用率が低く、各チームはシステムに還元するよりその場限りのコンポーネントを作ってしまう。コンポーネントAPIが不統一でトークン戦略もなく、その不整合がユーザー体験と信頼を損なっている。そしてコントラスト不足、フォーカスリング欠落、クリックできないチェックボックスラベルといったアクセシビリティの問題が、一部のユーザーを締め出している。

ここまでは既視感のある話ですが、この記事がおもしろいのはその先です。著者は過去にもデザインシステムを作った経験があり、直し方は分かっていた。そのうえで「どれだけ良くなったかを定量化したい」「定期的に状態を測り、全員からフィードバックと批評を集める習慣を作りたい」と考えます。入社した月に6つの設問を5段階のリッカート尺度で、加えて総合品質を10点満点で聞くサーベイを作り、以後18か月にわたって半年ごとに同じものを配り続けました。低い評価には自由記述を促し、それがそのまま優先順位に流れ込む設計です。

4回分の推移と打ち手の対応が、この記事の本体になります。

「既存のコンポーネントで新機能のほとんどを作れる」は4.0→4.4で10%の改善。効いたのは、更新のチーム全体への周知、ドキュメントの改善、そして新機能を見越した先回りの対応でした。ダークカラーを多用する新機能のローンチを見込んで、事前にシステム全体のダークモード対応を主導した例が挙がっています。

「コンポーネントはだいたい期待どおりに動く」は4.1→4.6で12%の改善。Tailwind の設定を単一の情報源に統合したことと、複雑なコンポーネントで「設定より合成（composition instead of configuration）」を選んだことが挙がっています。前回のサーベイの自由記述から出た変更がそのまま次回のスコアを押し上げた、という循環が回っているのが良いところです。

「コンポーネント名・トークン名・プロパティ名が理解できる」は4.3→4.8で11%の改善。共通のプロップ型を抽出して再利用し、ネイティブのHTMLプロップを再宣言せず拡張し、真偽値のプロップに `is` / `has` / `should` の接頭辞を付けるといったグローバルな命名規則を敷いた、と具体的です。

「Stylus のおかげで時間が節約できている」は4.7→4.7でほぼ横ばい。著者はここを取り繕わず「最初から良かった指標もある」と書いています。全部の線が右肩上がりになっていないところが、むしろこの記録の信頼性を上げていました。

伸び幅が一番大きかったのがドキュメントで、3.2→4.5の40%増。Starlight で公開の読み物としてのドキュメントを書いて公開したことが効いています。副次的な効果として、ドキュメントがコードベース内のMarkdownとして存在するため、LLMを使う開発者からのエージェント経由のアクセスも良くなったとありました。JSDocコメントとTypeScriptの型からAPIリファレンス表を自動生成し、Figma↔コード↔ドキュメントを相互リンクしてドリフトを抑えています。

「デザインとエンジニアリングの協業が進む」は4.1→4.8で20%増。Figmaとコードの乖離を減らしたことと、全チームからの貢献を歓迎する文化が理由に挙がっています。自由記述に出てくる「ライブラリから消費するだけでなく、コンポーネントの中に踏み込んで提案や変更ができて、レビューが速い」という声は、デザインシステムの運用としてかなり健全な状態を示していました。

総合品質は7.6→9.1の20%増。ただし著者はここに自分で留保を付けます。サーベイのフィードバックは開発者体験に偏りやすく、エンドユーザー体験を測れていない、と。だから Lighthouse でのパフォーマンステスト、Playwright と axe-core でのアクセシビリティテスト、Chromatic での視覚回帰テストという、ユーザー側を向いた指標で補っています。さらに Omlet（コードベースを静的解析してコンポーネントやプロップの使用回数、カバレッジの推移を出すツール）で定量データを足し、大量のコード削除と合わせてコンポーネント網羅率を6か月で37%から52%へ引き上げました。

UXエンジニアリングの視点で言うと、この記事の使いどころは「二階建ての測り方」にあります。サーベイで拾えるのは体感と不満の所在で、静的解析で拾えるのは実際の採用状況。前者だけだと声の大きい人の話になり、後者だけだと「使われているが我慢して使われている」状態を見逃します。両方を半年ごとに並べる運用は、専任が1人しかいない規模でも回せるサイズに収まっているのが現実的でした。

もうひとつ、設問そのものが打ち手の設計図になっている点も参考になります。「予測どおりに動くか」「名前が理解できるか」「時間が節約できるか」という切り方は、そのまま改善の対象を指しています。裏を返すと設問に入れなかった軸は改善対象から落ちるので、サーベイを作る段階が一番の設計作業だといえます。

締めは静かでした。デザインシステムを作ることはエントロピーとの終わりのない戦いで、定期的に脈を取ることがチームを大事なことに集中させてくれる。デザインシステムに完成はないけれど、「より良く」へ向かう道をもう少しだけ先へ進めることはいつでもできる、と。

### [Kugiri (区切り)](https://edoardolunardi.github.io/kugiri/)

> **出典**: Sidebar | **公開日**: 2026-09-11 | **カテゴリ**: design

**3行まとめ**
- テキストを行・単語・文字に分割する処理の検証ページで、ブラウザが実際に描画したとおりに分割できているかをケースごとに並べています
- `text-wrap: balance` / `pretty`、`::first-line`、ドロップキャップ、float、multi-column、`pre-line` など、分割が壊れやすい条件を網羅しています
- 3つの対象を1コールでまとめてレイアウトするバッチ処理や、約220語での負荷ケースなど、分割コストの検証も含まれます

**詳細解説**

テキストのリビール演出でおなじみの「分割」——1つの段落を行ごと、単語ごと、文字ごとのDOM要素に切り分けて、順番にアニメーションさせるあの処理——を、どこまで正確にできるかを列挙した検証ページです。Sidebar経由で流れてきたもので、文章というより標本帳（specimen）に近い作りになっています。

なぜこれが難しいのかは、並んでいるケースを見ると分かります。たとえば `text-wrap: balance` の項では「バランスの取れた行はスラックなしで収まっているので、単語を広げる分割処理があれば必ず折り返しが変わる」と書かれています。ブラウザが最適化して決めた行分けは、分割のためにラッパー要素を挿入した瞬間に別物になってしまう。`text-wrap: pretty` の項も同様で、最終行に孤立語を作らないという結果を、分割処理が再び壊してはいけない、と条件が書かれています。

タイポグラフィ寄りのケースも丁寧でした。行送りをグリフの箱より詰めた場合（`line-height: 0.85` で1行1語のディスプレイ書体）、行同士が数ピクセル重なります。ここでマスクが行ボックスぴったりだと、g・y・p のディセンダーが切られてしまう。そこで「クリップを各行ボックスの .25em 外まで伸ばし、尻尾が自分の行と一緒に動くようにする」という対処が示されています。ドロップキャップの項では、グリフが自分の文字ユニットから離れて先頭の行ブロックの前に浮いても、その後ろの書記素（グラフェム）は描画上の範囲を保つ、とあります。絵文字を含む `split=chars` のケースがあるのも、書記素クラスタを単純なコード単位で切ると壊れるからでしょう。

レイアウト側の難所も並びます。`::first-line` は「1行目だけ太字・大文字・字送り付き」で、その幅は元のまま保たれなければならない。`text-indent` は「すべての行がブロックになった以上、2行目以降は字下げしないよう明示しなければならない」。段落先頭の float は「テキストではないのでユニットではなく、リビールは動かさない。1行目のブロックの前に戻され、その後ろの行はもとどおり短縮される」。multi-column では「1列目の最終行と2列目の先頭行は別の行だが、2つ目のほうがページ上では高い位置にある」。どれも、素朴に実装すると必ず踏むところです。

アクセシビリティへの目配りが入っているのも見どころでした。行をまたぐリンクの項に「空のクローンを作らない。リンクは1行につき1つのタブストップのまま」と明記されています。分割処理でリンクを行ごとに複製すると、キーボード操作のタブストップが行数分だけ増えてしまう。演出のためのDOM操作が操作性を壊す典型例で、それをテストケースとして固定しているわけです。

最後の「Scale」の節はコストの話です。3つの段落を配列で1回のコールに渡すと、書き込みの前に3つとも計画されるので、1段落のときと同じ1回のレイアウトで済む。途中の段落がハイフンで折り返す場合も、すべての切断が済んでから一度だけ復元される、とあります。約220語の負荷ケースには「パネルで分割コストを見てください」と添えられていて、ページ上にパフォーマンス計測が載っている構成のようです。祖先要素が `scale(0.5)` されている場合に「矩形はそのスケールで測り、ユニットはスケールなしで書き込む。それでもすべてのボックスが描画をタイルしなければならない」というケースまであって、実装の真面目さがうかがえます。

UXエンジニアリングの視点では、この標本帳そのものが資産として読めます。リビール演出は「見栄えのための一時的なDOM操作」と軽く扱われがちですが、実際にはタイポグラフィ、レイアウト、アクセシビリティ、パフォーマンスの4つを同時に壊しうる処理です。ここに並んだケース一覧は、自前で分割処理を書くときにも、既存ライブラリを選ぶときにも、そのままチェックリストとして使えます。とくに `text-wrap: balance` / `pretty` との相性は、両プロパティの採用が進んだいま踏みやすい落とし穴でしょう。

### [How we cut CDN metadata lookup latency by 91%](https://vercel.com/blog/how-we-cut-cdn-metadata-lookup-latency-by-91-percent)

> **出典**: Vercel | **公開日**: 2026-09-10 | **カテゴリ**: frontend

**3行まとめ**
- パスごとに1オブジェクトだったルーティングメタデータを、約200KBのシャードにまとめてキャッシュ効率を上げた話です
- JSONLに固定幅のBase64ポインタでインデックスを埋め込み、シャード全体をパースせずに二分探索で目的の1件だけ読みます
- P99レイテンシが215.8ms→19.1msで91%減。ビルド側も不要になった処理を削ってデプロイ工程が約10%速くなりました

**詳細解説**

Vercel の CDN は平均して毎秒8,000万を超えるルーティング命令を実行していて、その一部が「どのパスが存在し、どう配信するか」を決めるメタデータの参照です。このメタデータがキャッシュに乗っていないと、応答の前に取りに行く必要があります。

もともとの設計は、パスごとに独立したオブジェクトを保存し、CDNがそれぞれ個別に取得してキャッシュするというものでした。小さめのプロジェクトで、デプロイ頻度が低ければ問題ありません。ところが大きなデプロイには数十万のパスがあり、それぞれがキャッシュエントリを持つ。そして新しいデプロイのたびにキャッシュキーが総入れ替えになるので、各パスの最初の参照は必ずミスする。頻繁にデプロイする大規模サイトにとって、キャッシュミスが繰り返し発生するコストになっていたわけです。

打ち手は「まとめて取る」でした。多数のパスのメタデータをシャードと呼ぶファイルにまとめ、サイズに上限を設ける。1つのシャードを取ればそこに含まれる全パスのメタデータがキャッシュに乗るので、後続の参照が再利用できます。

ただし、まとめて取ることとまとめてパースすることは別の問題です。ここが技術的に面白いところでした。各シャードには、対象パスとメタデータをソート済みの交互のJSONLレコードとして格納し、各エントリの開始位置を記録するインラインのインデックスを持たせています。位置は固定幅のポインタで、1つのポインタは6ビットのBase64文字の整数個ぶんになっている。だからインデックス行をJSONとしてパースしたり、Base64文字列全体をデコードしたりせずに、任意の1ポインタだけをその場でデコードできます。ルーティングプロセスはそのポインタでエンコード済みのパスを二分探索し（O(log n)回のポインタ読みと文字列比較）、見つかったら次の行のメタデータだけをパースする。シャードの残りは手つかずのままです。データレイアウトと、その上の検索構造を分離しておいたので、ワークロードごとに必要な性質だけを選べる、という設計になっていました。Bulk Redirects のソート済みキーバリューJSONLと、Bloom filter のときに作った直接アドレス可能なBase64構造の組み合わせです。

シャードサイズの決め方の話も実践的でした。当初は「ほとんどのデプロイのメタデータが1シャードに収まるといいな」と考え、インデックスと二分探索のおかげでパースが安いことを前提に、数MBのシャードから始めています。大きなシャードが成立するのは、リクエストの近くにキャッシュされ続ける場合だけ。各ルーティングプロセスは直近のシャードを小さなLRUキャッシュにメモリ保持し、その背後にリージョン共有のキャッシュがあります。デプロイあたりのシャードが数個なら、たいていLRUに当たるはずでした。

ところが実測では、リージョンキャッシュのヒット率は高い一方でLRUのヒット率が低かった。リクエストがリージョン内の多数のプロセスに分散するためです。そして数MBの転送は想定より高くついた。逆に小さすぎるとリージョンキャッシュのミスが増える。この綱引きの落とし所が約200KBでした。リージョンキャッシュのヒット率を高く保ちつつ、LRUミスのときの穴埋めが安く済むサイズ、という決め方です。

結果は、P99レイテンシが215.8ms→19.1msで91%減、平均が8.59ms→1.81msで79%減、標準偏差が44.9ms→19.0msで58%減（2026年8月5〜12日の本番トラフィックでの計測）。記事の末尾には、中央値は0.7ms前後のまま変わっていない、とも書かれています。つまりこの改善は速い経路をさらに速くしたのではなく、テールを刈り取ったものだと読めます。自社のマーケティングサイトとドキュメントサイトでは、P99のメタデータ参照が203ms→31msになったそうです。

さらに縮められる余地の検討もあって、ソート済みパスのフロントコーディング、メタデータを重複排除するJSONL分割、より密なカスタムシリアライズ形式の3つを試しています。オフラインのシミュレーションでは、どれもシャードは大幅に小さくなるものの、レイテンシの改善は控えめだった。だからエンコード・互換性・ロールアウトの追加作業に見合わないと判断し、共有ライブラリ側に寝かせた、という記述があります。やらなかった判断を理由つきで書いてあるのが良いところでした。

移行の進め方の節もそのまま参考になります。この参照はすべてのデプロイへのリクエストで走るので、シャード側と旧来のパスごとメタデータが食い違えば、古いルートを返したり、誤ったステータスを返したり、存在するパスに404を出したりすることになる。そこでまずオフラインでテスト用デプロイを作り、全パスを両方の方法で引いて答えを比較するハーネスを走らせています。次に本番で、フィーチャーフラグの下、ランダムなサンプルのリクエストに対して両方の参照を実行し、返すのは旧来の結果のまま。新しい結果は背後で比較し、数週間にわたって不一致を監視する。これを「シャドウモード」と呼んでいました。本番のリクエストを遅くせずに検証できるのがポイントです。

シャドウモードで見つかった差異は極めてまれで、そのうち1つは旧来のエンコーディング側のバグでした。非ASCIIのテキストをASCII専用フィールドに収めるためRFC 2047のencoded wordにパスを詰めていたのですが、絵文字が2つのwordにまたがったときだけ壊れる、というもの。新形式はパスをプレーンなUTF-8で保存するので、このバグは起こりえません。このエッジケースを捕まえたことで比較への信頼が増し、シャードで本番トラフィックを捌きはじめた、という流れです。

最後にビルド側の掃除があります。シャードが本番で動きはじめたあと、不要になった処理を消しました。パスごとメタデータのアップロードをやめて約9.7秒、ルートグループのメタデータをマニフェストに書くのをやめて約4.5秒、空になったファイルのアップロードをやめて約2.4秒。合計で約16.6秒、全デプロイでデプロイ工程が約10%、メタデータの多いデプロイでは25%近く速くなったと見積もられています。

UXエンジニアリングの視点では2つ持ち帰れるものがありました。1つはシャドウモードという移行の型です。ルーティングのように全リクエストが通る経路を差し替えるとき、「新旧を両方走らせて、返すのは旧、比較は背後で」という形は、フロントエンドのデータ取得層やフィーチャーフラグ運用にもそのまま移植できます。もう1つは数値の読み方でした。中央値が動かずP99だけが1/10になったという事実は、体感としては「たまにすごく遅い」がなくなったことを意味します。平均で語ると小さく見える改善が、ユーザーの体感では大きいという典型例です。なお、2026年7月17日以降にビルドされたデプロイはすでに新形式なので、それ以前のものは再デプロイが必要とのことでした。

```ts

});
```

内部では `@ai-sdk/harness-acp` を使い、Agent Client Protocol（ACP）経由で GitHub Copilot につないでいるとのこと。ACP対応のharnessならこの経路に乗れる、という構造が見えます。

### [FastAPI frontends and static files served from the CDN](https://vercel.com/changelog/fastapi-frontends-and-static-files-served-from-the-cdn)

> **出典**: Vercel | **公開日**: 2026-09-10 | **カテゴリ**: frontend

**3行まとめ**
- `app.frontend()` や `StaticFiles` で配信していたFastAPIのフロントエンドと静的ファイルが、ビルド時に Vercel CDN へ昇格されるようになりました
- それらのパスへのリクエストは Vercel Function を起動せずCDNから直接返ります
- FastAPIの宣言順による優先度は保たれ、依存関係やミドルウェアで守られているものは自動ではCDNに上げません

**詳細解説**

FastAPIでフロントエンドを配信している場合、これまでは静的ファイルのリクエストでも関数が起動していました。今回の変更で、ビルド時にCDNへ昇格されるようになります。

```python
app = FastAPI()
app.frontend("/", directory="dist")
app.mount("/assets", StaticFiles(directory="assets"), name="assets")
```

挙動の説明が丁寧でした。FastAPIはルートを宣言順に評価するので、`StaticFiles` のマウントより前に宣言したルートが、同じパスのCDNファイルより優先されます。この優先度はそのまま保たれる、と。

```python
@app.get("/static/manifest.json")  # Vercel Function が返す
def manifest(): ...

app.mount("/static", StaticFiles(directory="static"), name="static")
```

昇格されたソースディレクトリは、アプリが実行時に読めるように関数バンドルにも残ります。除外してCDNからのみ配信したい場合は `pyproject.toml` で `tool.vercel.fastapi.static.exclude = true` を設定します。

安全側に倒してある点も見ておきたいところです。FastAPIの dependencies で守られているフロントエンドは、CDNが依存関係のチェックを実行できないため関数側に残ります。同様に、ミドルウェアの背後にある静的ファイルも関数側に残る。これを上書きして常にCDNへ上げたい場合は `tool.vercel.fastapi.static.cdn = true`、CDNを完全に使わない場合は `false` を設定します。

認証付きの静的ファイルが意図せず公開されてしまう事故を、既定値で防いでいる設計です。逆に言えば、ミドルウェアを噛ませているだけで実際には公開してよいアセットは、明示的にオプトインしないと関数経由のままになります。デプロイ後にキャッシュが効いていないと感じたら、まずここを疑うとよさそうです。

### [The Pulse #191: a new trend of CPU shortages](https://newsletter.pragmaticengineer.com/p/the-pulse-191-a-new-trend-of-cpu)

> **出典**: The Pragmatic Engineer | **公開日**: 2026-09-10 | **カテゴリ**: engineering

**3行まとめ**
- GPU不足、メモリ不足に続いて、いまCPU不足が起きているという話題です
- 原因として挙げられているのは、AIエージェントがツール利用でCPUを大量に使うようになったこと
- 計算資源を今後必要とするなら、いま確保しておくとよい、という提言が付いています

**詳細解説**

Pragmatic Engineer の The Pulse は、大手テック企業とスタートアップの出来事・洞察・トレンドを扱う連載です。今回取得できたのは有料記事の冒頭部分なので、扱っているトピックの一覧と導入までになります。

主題は計算資源の逼迫が次の段階に入ったこと。AI企業が牽引したGPU不足、そしてメモリ不足に続いて、いまCPU不足が起きている、と。理由として名指しされているのが「AIエージェントがツールを使う際に、従来よりずっと多くのCPUを消費している」ことです。将来的により多くのコンピュートが必要になるなら、いまのうちに確保しておくとよい、という示唆が導入に置かれています。

この因果関係は少し考えると腑に落ちます。エージェントがコードを書き、テストを走らせ、ビルドし、ブラウザを操作し、ファイルを検索する——これらはどれもGPUではなくCPUの仕事です。推論そのものはGPUで走りますが、その周りで発生する「ツール実行」は普通のサーバーワークロードで、しかもエージェントは人間より圧倒的に多くの回数それを走らせます。この日のニュースレターの1本目で紹介した「1日270コミット」のような世界が広がれば、CI・テスト・ビルドのCPU需要が跳ね上がるのは自然な帰結でしょう。同じ号の Vercel Sandbox の一連の更新（全リージョン対応、ストレージ増量）も、需要側の同じ流れの上にあります。

ほかに予告されているトピックは、COVID期のユニコーン企業でさらに成長の夢が終わりつつあること、そしてAIがインシデント対応を担うことでエンジニアがシステムへの肌感覚を失っていくこと。最後の論点は、本文を読む価値がありそうです。障害対応は、システムの実際の姿を学ぶ数少ない機会でもあるからです。

なお、本文は有料購読者向けなので、ここで紹介できるのは導入までになります。
