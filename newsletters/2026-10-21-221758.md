### [38 things we’ve learned about building AI products](https://newsletter.posthog.com/p/38-things-weve-learned-about-building)

> **出典**: Sidebar | **公開日**: 2026-10-20 | **カテゴリ**: design

**3行まとめ**
- PostHog が10個の AI プロダクトを作ってきたなかで得た学びを、38項目にまとめた記事です
- 「AI を足すとプロダクトが悪くなることもある」「アシスタントではなくシステムを作る」など、作る前の判断に関する項目が多く含まれています
- UI は不要になるのではなく、エージェントがしたことを「承認・確認・取り消し」する場に役割が変わる、と述べています

**詳細解説**

PostHog は、AI アシスタントの PostHog AI、導入を自動化するウィザード、セッション録画を解析する Replay Vision などを提供していて、月に約10万人が使っています。記事はその経験を、選ぶ・作る・測る・見せるの順に短くまとめたものです。各項目からは、より詳しい過去記事へのリンクが張られています。

前半では「作るかどうか」の判断が続きます。ドキュメントと会話する機能のように、どの AI でもできることを作っても意味は薄いといいます。むしろ MCP サーバーのように「AI のために作る」ほうが先で、実際に PostHog では MCP サーバーの日次利用者が PostHog AI の5倍いるそうです。狙い目は、30秒以上かかる作業、SQL のようにユーザーが慣れない言語を使う作業、20回以上くり返す作業です。導入ウィザードは2時間の作業を約8分に縮め、使った人は有料化が5倍、定着が2倍速かったと紹介されています。

中盤はエージェント向けの設計です。「skill はエージェントのための機能」という項目では、`docs-search` が呼ばれるたびに skill かツールが足りていない証拠だと書いています（月に約2.8万回呼ばれている、もっとも多いツールだそうです）。`experiment-create` はあるのに `experiment-start` がないと、エージェントは最後に人へ UI でのクリックを頼むことになる、という例もわかりやすいです。足りないツールは「ロボットが書いた機能要望」だという言い方も、エージェントを利用者として扱う姿勢をよく表しています。

UXエンジニアリングの視点では、後半の UI に関する項目が参考になります。空のテキストボックスを出すと、ユーザーはそのプロダクトについて知っていることを忘れてしまうので、候補や手がかりを添えるとよいそうです。推論や失敗したツール呼び出しを「見た目が散らかる」と隠したら、過程が見えず信頼しにくいと言われ、今はすべてストリーム表示にしているといいます。テキストだけでは足りない場面では、エージェントの作業を確認する画面や、人の判断が必要なことを並べる受信箱のような画面を用意する、という指摘もあります。最後の項目は「1年後にはこの半分は間違っているだろう」です。ユーザーと話す、早く出す、実験するという、AI 以前からある進め方は古くならない、と締めています。

### [What’s the ROI of software engineers’ spending on AI?](https://newsletter.pragmaticengineer.com/p/whats-the-roi-of-software-engineers)

> **出典**: The Pragmatic Engineer | **公開日**: 2026-10-20 | **カテゴリ**: engineering

**3行まとめ**
- 27の職場のエンジニアリングリーダーやシニアエンジニアに、AI ツールへの1人あたり支出と PR の数の変化を聞いた調査記事です
- CodeRabbit のデータでは、同じ2万人の開発者を1年追ったところ週あたりの PR が128%増えていました
- 一方で「PR の数は横ばいでサイズが3倍」「品質を保とうとすると速度はそれほど上がらない」といった声もあり、ROI をはっきり答えられる会社は少数でした

**詳細解説**

きっかけは、読者から届いた「他社は1人あたり AI にいくら使っているのか、PR の数はどう変わったのか」という質問です。PR の数はほとんどの会社ですぐ取れる指標で、まだ開発者に意識されて数字を操作されていないため、AI 前後の比較に使いやすい、というのが著者の考えです。

支出の傾向として、会社の規模と支出額には関係がないことが挙げられています。2人の .NET の会社は1人月 $3,000 を使い、エンジニア1,500人の上場企業は上限を1人月 $150 にしています。6〜7月に支出のピークを迎え、API 課金の会社では今はおよそ半分に下がっているそうです。あるクオンツ系の会社は、9月の月間支出が $8M と1月の16倍になっていて、いちばん使っているのはエンジニアではなくトレーダーだといいます。

数字の変化は会社によってまちまちです。2人の .NET の会社では PR が5〜10倍になり、「以前なら5〜7人でやっていた量を2人でこなしている」と話しています。一方、PR の数は変わらずサイズが3倍になった会社や、「人のレビューは、そもそも不要な変更や10倍大きすぎる変更など、エージェントが見逃すものを多く拾う」と話す会社もあります。スクラムとカンバンを5年続けているチームが「完了したユーザーストーリーが3倍になった」と答えているのは、PR の数より事業上の価値に近い指標として興味深いところです。

UXエンジニアリングの視点では、「PR の数」を成果の指標にすることの危うさが見えてきます。PR が増えてもサイズが膨らんでいたり、レビューする人の負担に移っているだけだったりすることもあるからです。ユーザーに届いた価値をどう測るかは、AI 以前からの課題がそのまま残っています。なお、取得できた本文は Big Tech の事例に入る手前で途切れていて、表題の ROI についての結論部分は読めていません。全体は元記事で確認してください。

### [AI が書き、レビューし、QA する開発で、私は「監督」の役割を考え始めた](https://tech.layerx.co.jp/entry/engineer-as-director)

> **出典**: LayerX エンジニアブログ | **公開日**: 2026-10-21 | **カテゴリ**: engineering

**3行まとめ**
- チケットからマージ、開発環境での QA までをほぼ AI に任せ、16営業日で211本の PR をマージしたエンジニアの記録です
- コードは1行ずつ読まない代わりに、AI が何を読んで何を commit したか、できあがったものがどう動くかを見ています
- AI のレビュアー6体が、変更の入っていないコードをもっともらしくレビューしていた失敗と、そのあと変えたことが書かれています

**詳細解説**

流れは4つの Claude Code の skill でできています。チケットから実装、PR、CI 対応、マージまでを走らせる ship、難しいチケットで先に方針を立ててレビューする plan-checker、観点ごとに並列でレビューし指摘を別のエージェントに疑わせてから直す pr-checker、マージ後に QA 手順書のシナリオを開発環境で流す devqa です。仕様だけは勝手に決めさせず、「PdM がこの PR を見て『そう決めたつもりはない』と言いそうか」を判断の基準にしています。PR の9割ほどは同僚が approve し、本番の前には QA チームの確認が入ります。

印象に残るのは失敗の話です。並列で走らせていた別のセッションがメインの作業ツリーのブランチを切り替えてしまい、レビュアー3体と検証役3体が、変更が1行も入っていないコードを読んで結果を返してきました。その1週間前にも、worktree で編集したはずのファイルがメインの作業ツリーに書き込まれ、そのファイルが抜けた commit の上にさらに4本が積まれていたそうです。それからは、長い作業は最初から専用の worktree に入れ、commit のたびに `git show --stat` でファイル名と行数を見るようにしています。

後半では、Addy Osmani の「dark factory（人がコードを読まない工場）」と、Dex Horthy の「Read the dang code（いいからコードを読め）」が紹介されます。著者は自分の手元だけ電気を消していて、その先に同僚と QA チームという明かりがある、と立ち位置を整理しています。そして自分の役割を、小島秀夫監督が語った料理長のたとえに重ねます。作るのは AI で、自分は味見をする役だということです。

UXエンジニアリングの視点では、初期設定を案内するエージェントの例が示唆に富んでいます。AI に任せた最初の案はテストもすべて通ったのに、「あれもこれも」が入りすぎて何をしてくれるのかわからないものになっていました。最終的に PdM が触りながら作り直したそうです。テストが通ることと、使って気持ちいいことは別の話です。その差を見つける「味見」が、人に残る仕事としてはっきり書かれています。ただし、著者自身も断っているとおり、チームのレビューと QA があって成り立っているやり方で、どの現場にもそのまま当てはまるものではありません。

### [Making every harness durable](https://vercel.com/blog/making-every-harness-durable)

> **出典**: Vercel | **公開日**: 2026-10-19 | **カテゴリ**: frontend

**3行まとめ**
- Pi、OpenCode、Codex、Claude Code といった既存のエージェントハーネスを、クラウド上でクラッシュに強くする `durable-harness` が公開されました
- モデル呼び出しやツール呼び出しの前に「意図」、終わったら「結果」をログに記録し、途中で落ちても新しい関数がログを読んで続きから再開します
- ツールごとに、クラッシュ後に再実行してよいか（`'safe'`）、二度と実行しないか（`'never'`）を宣言できます

**詳細解説**

ローカルでコーディングエージェントを動かすと、PC を起こしたままにしておく必要があります。クラウドの VM に移しても、どのモデル呼び出しやツール呼び出しが完了したかは自動では記録されず、障害で中断すると作業が失われます。`durable-harness` は、Vercel の Workflow SDK と同じ仕組みを使って、この問題をハーネスの外側から解決するオープンソースのパッケージです。

仕組みは、ターンの各ステップを永続的なログに書き込み、ターン自体をキューのメッセージで支えるというものです。関数が落ちるとキューが新しい関数にターンを渡し、ログを読んで再開します。完了済みの呼び出しは結果をログから読むので二重に課金されません。中断したツールのうち `replay: 'safe'` のもの（ファイルの読み込みや CI の状態確認など）は再実行されます。それ以外は「実行されたかもしれない」とモデルに伝わり、確認するかどうかをモデルが判断します。返金処理や PR へのコメント投稿のように、二重に実行すると困るものは `'never'` にします。

保存先は World というインタフェースで抽象化されています。Vercel 上では Vercel World、開発中はローカルのファイル、自前のサーバーでは Postgres・MongoDB・Redis・Turso を使えます。ファイル操作には、ログ上に仮想のファイルツリーを持つ `virtual()` と、セッション専用の Vercel Sandbox を使う `sandbox()` が用意されています。Claude Code と Codex は本物のシェルとファイルシステムを前提にしているので、常に Sandbox で動きます。

UXエンジニアリングの視点では、To-Do リストや計画、フォームのような状態を「ドキュメント」として型付きの JSON でログに置ける点が気になります。ツールの結果と同じタイミングで記録されるので、エージェントの作業と画面に出す状態がずれにくくなります。チャットのルートから変更をそのまま UI にストリームすることもできます。中断と再開をはさんでも、ユーザーが見ている進捗が巻き戻ったり二重になったりしない設計は、長時間動くエージェントの体験を作るうえで大事な土台です。

### [The Future of CSS ✨](https://www.joshwcomeau.com/css/interop-2027/)

> **出典**: Josh W Comeau | **公開日**: 2026-10-20 | **カテゴリ**: frontend

**3行まとめ**
- ブラウザ間の互換性を高める取り組み Interop 2027 の候補から、Josh W. Comeau が投票した10の CSS 機能を紹介しています
- `@function` による CSS 関数、`corner-shape`、`border-shape`、`reading-flow`、`interpolate-size`、ギャップの装飾などが並びます
- 多くは現在 Chrome と Edge だけの対応ですが、プログレッシブエンハンスメントとして今から使えるものもあります

**詳細解説**

Interop は Google、Apple、Microsoft、Mozilla などが協力して、特定の機能の対応状況をそろえるプロジェクトです。たとえば CSS Subgrid は2019年に Firefox で実装されたあと何年も広がりませんでしたが、Interop 2023 に入るとその年のうちに主要ブラウザでほぼ使えるようになりました。2027年の対象は、Mozilla が用意したランキングサイトでの投票を参考に決まる予定です。

紹介されている機能のなかでも、`@function` で CSS に関数を定義できる提案は使いどころが広そうです。記事では、角度と距離から `translate()` を返す関数を作り、極座標で要素を動かす例が出てきます。`corner-shape` は角を `squircle` や `bevel` などの形にでき、`clip-path` と違ってボーダーや影も新しい形に沿います。`interpolate-size` は `height: 0` から `height: auto` へのアニメーションを可能にするもので、アコーディオンの実装でずっと困ってきた部分です。

アクセシビリティに関わるのが `reading-flow` です。CSS Grid でデスクトップとモバイルの並びを大きく変えると、タブの移動順は DOM の順番のままなので、どちらかの画面では見た目とずれてしまいます。`reading-flow: grid-rows` を指定すると、見た目の並びに沿ってフォーカスが移動します。ほかにも、`position: sticky` の要素が貼り付いているかどうかや、スクロールできる方向が残っているかを判定するコンテナクエリが紹介されています。

UXエンジニアリングの視点では、結びの主張が大事です。LLM の学習データは数年前のものが多いので、新しい CSS 機能を自分から使ってくれることはあまり期待できません。だからこそ人のほうが知っていて、エージェントに使うよう指示する必要がある、と著者は書いています。エージェントに実装を任せる場面が増えるほど、どの機能を選ぶかという判断の重みは増していきそうです。

### [Embracing Playful Imperfection With The CSS `random()` Function](https://smashingmagazine.com/2026/10/embracing-playful-imperfection-css-random-function/)

> **出典**: Smashing Magazine | **公開日**: 2026-10-20 | **カテゴリ**: design

**3行まとめ**
- Safari で使えるようになり、Chrome 156 で展開中の CSS `random()` 関数を、デザインシステムのなかでどう使うかを考える記事です
- 文字の傾き、跳ねる文字、手で配ったようなカードの広がり、ボケ表現など、6つのデモで「ほどよい不揃い」を作っています
- スクリーンリーダーへの配慮や `prefers-reduced-motion`、使ってはいけない場所についてもはっきり書かれています

**詳細解説**

`random()` は CSS Values and Units Level 5 で定義されている関数で、JavaScript や Sass のループなしに CSS のなかで乱数を扱えます。`random(-3deg, 3deg)` のように最小値と最大値を書き、3つ目の引数でステップを指定すると決まった刻みの値だけが出ます。最小値と最大値は同じ単位でそろえる必要があります。キャッシュキーを使うと、`inline-size` と `block-size` に同じ乱数を使って正方形を保つ、といったことができます。

デモのなかでは、扇形に広がるカードの例がよくできています。`sibling-index()` と `sibling-count()` で中心のカードを基準にした角度と位置を計算し、そこに `random()` で小さなずれを足しています。「構造は計算で、人の手の揺らぎは乱数で」という考え方で、枚数が変わっても同じ形に広がります。跳ねる文字のデモでは、`animation-delay` に負の乱数を入れることで、ページを開いた瞬間から各文字がばらばらのリズムで動いている状態を作っています。

アクセシビリティについての注意も具体的です。1文字ずつ `<span>` で囲むとスクリーンリーダーが文字単位で読み上げてしまうので、見出しに `aria-label` で単語全体を渡し、中の `span` は `aria-hidden="true"` で隠します。動きを減らす設定の人には、アニメーションを止めるだけでなく傾きもなくすとよい、という提案もあります。

UXエンジニアリングの視点では、「どこで使わないか」の線引きがそのままデザインシステムのルールとして使えそうです。レイアウトの余白や入力欄の幅、本文の文字サイズ、ボタンやリンクの位置には使わず、装飾やエディトリアルな表現、背景、ループするアニメーションのずらしに限定します。押す対象を傾けるなら、ホバーやフォーカスで必ずまっすぐに戻すこと、という条件も添えられています。一貫性を作り込んできたからこそ、少しの不揃いを意図して入れられる、という見方は前向きで参考になります。

### [State of Ecommerce Accessibility 2026](https://davedavies.dev/state-of-ecommerce-accessibility/)

> **出典**: Sidebar | **公開日**: 2026-10-20 | **カテゴリ**: design

**3行まとめ**
- Shopify と WooCommerce の商品ページ59,400件を自動でチェックし、64%に「もっとも影響の大きい」レベルの問題が1つ以上あったという調査です
- もっとも多かったのは文字と背景のコントラスト不足で、80%のページで見つかりました
- アクセシビリティのオーバーレイ（自動修正をうたうウィジェット）を入れたページでも、62%に重大な問題が残っていました

**詳細解説**

対象は、世界の上位100万サイトに入る Shopify のストア39,976件と WooCommerce のストア19,424件で、1ストアにつき1つの商品ページを選んでいます。チェックは Google PageSpeed Insights 経由のモバイル版 Lighthouse で、中身は axe-core のルールです。96%のページが何らかの自動チェックに引っかかり、1ページあたりの問題は平均21件でした。アクセスの多いストアほど良いわけではなく、上位10万サイトでは69%と、むしろ少し悪い結果になっています。

多かった問題は、コントラスト不足（80%）、読み上げられる名前のないリンク（53%）、見出しレベルの飛び（49%）、小さすぎるタップ領域（32%）、見た目のラベルと支援技術向けの名前のずれ（28%）、代替テキストのない画像（27%）の順です。ピンチズームを無効にしているページも20.5%ありました。ラベルと名前のずれは、音声操作で見えている言葉を言っても反応しない原因になります。

オーバーレイについての分析は慎重です。オーバーレイありのページは重大な問題の割合が2.20ポイント低かったものの、信頼区間を見ると明確な差とはいえず、そもそもストアが自分で導入を選んでいるので因果関係も示せない、と書いています。初回表示の時点だけを測っていて、ウィジェットを開いたあとの変化は測っていない点も明記されています。

UXエンジニアリングの視点では、「商品ページはプラットフォーム、テーマ、アプリやプラグイン、制作会社の実装、ストア自身のコンテンツの重なりでできていて、どの層でも問題が入りうる」という指摘が大事です。チェックアウトのようにプラットフォームが管理する部分が改善されても、ほかの層で崩れてしまいます。だから社内に担当者を置いて、問題がどの層にあるかを切り分ける必要があるという話は、デザインシステムを運用するときにもそのまま当てはまります。なお、自動チェックで見つかるのはアクセシビリティの問題の一部だけです。レポートは自社ページの診断の申し込みにもつながっているので、その点も踏まえて読むとよいでしょう。

### [CPOとDirectorが語る、これからのプロダクト組織 —「AIの登場で、デザイナーの重要性はむしろ高まっている」—](https://tech.smarthr.jp/entry/2026/10/21/112027)

> **出典**: SmartHR Tech Blog | **公開日**: 2026-10-21 | **カテゴリ**: design

**3行まとめ**
- SmartHR の CPO 安達さんと、プロダクトデザイン組織を統括する佐々木さんの対談です
- AI が何をできて何をできないかを、どこまでユーザーに見せるかという「透明性のレベル」を決めるのがデザイナーの仕事だと語られています
- 業務用ソフトウェアの UI は凡庸であるべきで、凡庸な UI の組み合わせで業務を変えるのがデザイナーの本領だ、という話も出てきます

**詳細解説**

### [データベースとコードの長期的なリファクタリングを安全に進めるための取り組み —— 従業員データの複雑さを解きほぐす](https://tech.smarthr.jp/entry/2026/10/21/123725)

> **出典**: SmartHR Tech Blog | **公開日**: 2026-10-21 | **カテゴリ**: design

**3行まとめ**
- SmartHR の従業員データのうち、親子関係にある2つのバイテンポラル履歴テーブルを1つに統合するリファクタリングの進め方を紹介しています
- ダブルライトとバックフィルで新旧のデータを保ち、Branch by Abstraction で新旧の実装を隠して切り替えられるようにしています
- データ移行用のコードもアプリケーションと同じように設計してテストを書き、日次と全件の整合性チェックで未知のパターンを早く見つけています

**詳細解説**

バイテンポラル履歴は、「いつ有効だったか」と「いつシステムに記録されたか」という2つの時間軸で履歴を持つ設計です。このテーブルが2つ親子の形で関係しているため、過去のある時点のデータを取るにも、両方のテーブルに正しい時点を指定する必要がありました。挿入や更新のたびに両テーブルの履歴期間をそろえる特別な処理が必要で、多くの箇所から使われるモデルの品質を下げ、不具合の原因にもなっていました。親テーブルは1,000万件規模で、半年以上かかる作業になる見込みでした。

進め方の1つめは、新旧のデータを両方保つことです。現行の書き込みに合わせて統合後のテーブルにも書き込み（ダブルライト）、過去のデータは後から移します（バックフィル）。新しいデータは現行の実装から参照しないので、書き込みに失敗しても今の動作には影響しません。新実装に切り替えたあとも旧テーブルへの書き込みを続け、切り戻しもできるようにしています。

2つめは、新旧の実装を使う側から隠すことです。`ConsolidatedData` というクラスを挟み、その中でフィーチャーフラグを使って新旧を切り替えます。`parent.child` という呼び出し方は変わらないので、使う側にリファクタリング中だという知識が漏れず、変更が広がりません。3つめは、移行用のコードを書き捨てにせず、アプリケーションと同じディレクトリ構成でモジュールを分け、テストも書くことです。そのロジックを使って、前日以降に変わったレコードを見る日次チェックと、全件を並列で確かめる CLI ツールを運用しています。

UXエンジニアリングの視点では、外から見た振る舞いを変えずに中身を入れ替える進め方は、デザインシステムのコンポーネントを作り直すときにもそのまま応用できます。古いコンポーネントと新しいコンポーネントを同じインタフェースの裏に置き、フラグで切り替えながら差分を確かめる、という形です。「事前にすべてのパターンを把握するのは現実的でない」と認めたうえで、チェックのループを短くして不確実性を減らす、という姿勢も参考になります。まだ移行の途中なので、切り替え後の結果は今後の続報を待ちたいところです。

> **出典**: SmartHR Tech Blog | **公開日**: 2026-10-20 | **カテゴリ**: design

- 企画そのものも、時間や部屋の広さ、人数といった制約を AI に伝えながら組み立てています

**詳細解説**

フルリモートで働くチームが、たまに集まる機会を「ちゃんと盛り上がるか」という不安なく過ごすための工夫です。紹介されているのは2つのレクリエーションです。1つめの「共通点探し」は、3人1組で10分間、全員に共通する意外な点を探して2分で発表し、チームを入れ替えてもう1ラウンドします。仕事以外のレアな共通点ほど高評価、というルールです。2つめの「メンバー配置ワーク」は、「魔王城から全員で帰るまでが遠足です」のようなお題ごとに9つの役割を用意し、9人を1人1役で割り当てながら、その人の良さを話していきます。

UXエンジニアリングの視点では、AI の出力が「正しさ」ではなく「会話のきっかけ」として使われている点がおもしろいところです。精度が多少ぶれても価値が下がらず、むしろツッコミどころが盛り上がりにつながる。AI をどこに置くと失敗が許されるか、という設計の例として読むこともできます。人を役割に当てはめるワークで「その人の良さが伝わる理由づけ」をルールにしているのも、細かいけれど大事な配慮です。
