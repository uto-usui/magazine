### 1. **Humanity as differentiator**
[記事を読む](https://staticmade.com/2026/01/14/humanity-as-differentiator/)

**3行まとめ:**
- NRF 2026ではAIが全てのセッションと製品を支配していたが、その飽和状態こそがチャンスを生む
- 全企業がAIに走る中、人間性と自然世界に注力する企業は意味のある差別化を実現できる
- AI最適化で競争優位性が消失する中、人間性を選ぶ決断が顧客に無視できないシグナルとなる

**詳細解説:**

NRF 2026（全米小売業協会の年次カンファレンス）で目撃されたAI一色の状況は、UXエンジニアにとって重要な示唆を含んでいます。全ての企業が同じAI戦略を追求することで、逆説的に競争優位性が失われるという現象です。

UXエンジニアリングの観点から見ると、この状況は技術的な実装だけでなく、戦略的なポジショニングの問題として捉える必要があります。AIを使った効率化や自動化は確かに価値がありますが、それが全ての企業の標準戦略になった瞬間、差別化要因ではなくなります。

むしろ、人間中心のデザインプロセス、手作業でのユーザーリサーチ、人間同士のインタラクションを重視したインターフェース設計など、意図的に「人間性」を選択することが、新しい形の競争優位性を生む可能性があります。これは単なる懐古主義ではなく、ユーザーが機械的なインタラクションに疲弊している現代において、戦略的な差別化手段となり得ます。

UXエンジニアは、AIツールを使いながらも、最終的な意思決定や創造的なプロセスにおいて人間の判断を中心に据えることで、このバランスを取ることができます。技術の選択は常に目的に従うべきであり、「AIを使うこと」自体が目的化してはならないという教訓です。

### 2. **What I'm seeing for UX as we move into 2026**
[記事を読む](https://boagworld.com/emails/2026/)

**3行まとめ:**
- UXは再び企業のコスト削減対象となっているが、AIで代替できる浅いUXと人間的判断が必要な深いUXに二極化している
- テンプレート駆動型のUXはAIが担えるが、複雑な組織力学を navigate する能力や taste（センス）などの人間的スキルの価値が上昇している
- AI実装フェーズに移行する今こそ、UXプロフェッショナルが「何を解決するか」に焦点を当てて価値を示すチャンス

**詳細解説:**

Paul Boagの分析は、2026年のUX業界の現実を率直に描いています。特にUXエンジニアにとって重要なのは、技術スキルだけでは不十分になりつつあるという点です。

記事が指摘する「浅いUXと深いUXの分離」は、エンジニアリングスキルとデザインスキルの両方を持つUXエンジニアのポジションを強化します。なぜなら、単なるワイヤーフレーム作成やプロトタイピングはAIでも可能になっていますが、技術的制約を理解しながら組織内で合意形成を図り、実装可能なソリューションを設計するには、両方のドメイン知識が必要だからです。

特に注目すべきは「複数の帽子をかぶる」というアドバイスです。UXエンジニアは既にデザインとエンジニアリングという二つの帽子をかぶっていますが、さらにシステム思考、データモデリング、ビジネス戦略などの知識を加えることで、AIツールを効果的に活用しながら、人間にしかできない統合的な判断を下せる専門家になれます。

AIが開発の高速化を実現する今、UXエンジニアは「早く失敗して学ぶ」アプローチをより積極的に取れます。プロトタイプの作成スピードが上がれば、クリエイティブなリスクを取る余地が生まれ、より革新的なユーザー体験の探索が可能になります。ただし、そのためには明確な判断基準とセンス（taste）が必要で、これこそが人間のUXエンジニアが提供できる価値です。

### 3. **Building a Scroll-Driven Dual-Wave Text Animation with GSAP**
[記事を読む](https://tympanus.net/codrops/2026/01/15/building-a-scroll-driven-dual-wave-text-animation-with-gsap/)

**3行まとめ:**
- GSAPのScrollTriggerとquickToを使い、2カラムのテキストが波のように対称的に動くスクロール駆動アニメーションを実装
- 数学的な位相計算（sin波）とビューポート中心からの距離測定で、滑らかな動きとフォーカス状態を制御
- 767行に及ぶ詳細なチュートリアルで、Vite + GSAP環境でのモダンなアニメーション実装を体系的に解説

**詳細解説:**

この記事は、UXエンジニアが実装レベルで理解すべきスクロールアニメーションの完全なケーススタディです。単なるライブラリの使い方ではなく、数学的な基礎（sin関数による波の生成）から、パフォーマンス最適化（`quickTo`の活用）、レスポンシブ対応まで、プロダクションレベルの実装に必要な全要素をカバーしています。

特にUXエンジニアリングの視点で重要なのは、デザインの意図を技術で実現するプロセスです。「二つのカラムが逆方向に波打つ」というデザインコンセプトを、multiplier（1と-1）というシンプルなパラメータで実装する設計判断は、保守性と拡張性を考えた優れたエンジニアリングです。

また、`quickTo`を使ったパフォーマンス最適化は、60fpsのスクロールアニメーションを実現するために不可欠です。毎フレーム新しいtweenを作成するのではなく、事前に作成した関数を再利用することで、ガベージコレクションの負荷を減らしています。これは、ユーザー体験を損なわない高品質なアニメーション実装の好例です。

さらに、`ScrollSmoother`の必要性を明示している点も重要です。多くのチュートリアルがアニメーションコードのみに焦点を当てる中、この記事はスムーススクロールの基盤がなければ全体の体験が台無しになることを理解しています。UXエンジニアは、個別の機能だけでなく、それを支えるインフラストラクチャーの重要性を認識する必要があります。

### 4. **Live Region Support**
[記事を読む](https://adrianroselli.com/2026/01/live-region-support.html)

**3行まとめ:**
- 主要スクリーンリーダー（NVDA, JAWS, Narrator, VoiceOver, Orca, TalkBack）でのlive region実装を詳細にテスト、ブラウザとの組み合わせで結果が大きく異なる
- polite/assertive/alert/outputの各種live regionと、Braille表示の両方で動作を検証、多くの実装にバグや非標準動作が存在
- hidden属性やaria-hiddenで非表示にしたlive regionは全てのスクリーンリーダーで正しくアナウンスされない

**詳細解説:**

Adrian Roselliのこの詳細なテストレポートは、アクセシビリティ実装における「理論と現実のギャップ」を如実に示しています。UXエンジニアにとって、これは仕様通りに実装すれば完璧に動作するという楽観的な前提が通用しないことを教えてくれます。

特に重要な発見は、同じ`aria-live="polite"`でも、スクリーンリーダーによって「assertive」として扱われたり、全く異なるタイミングでアナウンスされたりする点です。JAWSでは全てのlive regionがpoliteとして扱われ、VoiceOver macOSではpoliteが音声ではアナウンスされないがBraille表示では assertive として動作するなど、予測不可能な動作が多数報告されています。

UXエンジニアリングの実践として、この記事から学ぶべきは：

1. **テスト環境の多様性が必須**: 一つのスクリーンリーダー+ブラウザの組み合わせでテストするだけでは不十分。主要な組み合わせ（NVDA+Firefox, JAWS+Chrome, VoiceOver+Safari等）での検証が必要。

2. **フォールバック戦略の重要性**: `aria-describedby`を使った動的な説明更新など、live region以外のアプローチも検討すべき。ただしこれも完全な互換性はない。

3. **「隠れたlive region」は機能しない**: 全てのテストで、hidden/aria-hidden/display:noneで非表示にしたlive regionは正しく動作しません。これは重要な制約です。

実装時には、仕様準拠だけでなく、実際のユーザー環境での動作確認と、必要に応じた代替手段の用意が不可欠です。

### 5. **How to write a good spec for AI agents**
[記事を読む](https://addyosmani.com/blog/good-spec/)

**3行まとめ:**
- AI agentには一つの巨大なpromptではなく、構造化されたPRD/SRS形式の仕様書を提供し、タスクを段階的に分解して渡すべき
- Commands, Testing, Project structure, Code style, Git workflow, Boundariesの6要素を含む仕様が効果的
- Plan Modeでコード生成前に仕様を固め、3段階境界（Always/Ask first/Never）で安全性を担保する

**詳細解説:**

Addy Osmaniによるこの包括的なガイドは、AI時代のソフトウェアエンジニアリングにおける「仕様書の役割の再定義」を示しています。UXエンジニアにとって特に重要なのは、AIツールを使う際の「設計先行アプローチ」の価値です。

記事が強調する「Plan Mode」の概念は、UXエンジニアリングのワークフローに自然にフィットします。ユーザー体験を設計する際、いきなりコードを書き始めるのではなく、まずユーザージャーニー、インタラクションパターン、技術的制約を整理する必要があります。AI agentも同様で、読み取り専用モードで仕様を固めてから実装フェーズに移行することで、手戻りを防げます。

「6つのコア要素」は、UXエンジニアリングプロジェクトに直接適用できます：

1. **Commands**: `npm run storybook`, `npm test`, `npm run lint`など、プロジェクト固有のコマンドを明示
2. **Testing**: Jestなのかvitestなのか、E2EはPlaywrightなのかCypressなのか
3. **Project structure**: コンポーネントは`src/components`か、storiesは隣接配置か別ディレクトリか
4. **Code style**: Functional component、TypeScript、CSS Modulesなど、実例を含めて明示
5. **Git workflow**: Conventional Commits、feature branchの命名規則
6. **Boundaries**: `node_modules/`は触らない、APIキーをコミットしない、など

特に「3段階境界」（Always/Ask first/Never）は、AI agentの自律性と安全性のバランスを取る優れた設計です。UXエンジニアは、デザインシステムのコンポーネント更新やアクセシビリティ修正など、常に安全な変更と、スキーマ変更やパフォーマンス最適化など、レビューが必要な変更を区別して定義できます。

**3行まとめ:**
- 3Dプリント設計の課題（バージョン管理、コラボレーション、カスタマイズ、自動化の欠如）をソフトウェア工学の手法で解決するMakerRepoを構築

- セミカスタム製品市場の拡大に対応し、製造知識をオープンソースコードとして保存・共有することで知識の消失を防ぐ

**詳細解説:**

この記事は、UXエンジニアリングの概念を物理世界に拡張する興味深い試みです。デジタルプロダクトで当たり前の実践（バージョン管理、自動化、コラボレーション）が、製造業ではまだ確立されていないという指摘は、私たちが普段使っているツールの価値を再認識させます。

UXエンジニアリングの視点で特に注目すべきは、「Code as a single source of truth」という思想です。FusionやSolidWorksのようなGUIベースのCADソフトは、デザインツール（Photoshop, Sketch）からコードベースのデザインシステム（React components）へのシフトと似た課題を抱えています。

MakerRepoのアプローチは、以下の点でソフトウェアエンジニアリングのベストプラクティスを適用しています：

1. **宣言的な定義**: Build123Dを使ったPythonコードで3Dモデルを記述
2. **Git統合**: 変更履歴、diff、ブランチ戦略をモデル設計に適用
3. **CI/CD**: コミット時に自動的にartifact（STL, 3MF）を生成
4. **コラボレーション**: Fork, Pull Request, Code Reviewを製造プロセスに導入

UXエンジニアにとって、これはデザインシステムの将来像を示唆しています。現在のデザインツールとコードの分離は、製造業のCADソフトと同じ課題を抱えています。FigmaのDev Modeやtoken managementの方向性は、MakerRepoと似た「design as code」の実現を目指しているとも言えます。

また、「セミカスタム製品」の概念は、コンポーネントベースのUI設計と通じるものがあります。完全にカスタムな一点物ではなく、パラメータ化された設計から個別ニーズに合わせてバリエーションを生成するアプローチは、props経由でカスタマイズ可能なReactコンポーネントと同じ設計思想です。

### 7. **A Site for Sore Eyes: Combining GSAP and Webflow to Showcase Flim**
[記事を読む](https://tympanus.net/codrops/2026/01/14/a-site-for-sore-eyes-combining-gsap-and-webflow-to-showcase-flim/)

**3行まとめ:**
- WebflowとGSAPを組み合わせ、Lottie、Rapier物理エンジンを統合した複雑なインタラクティブサイトを構築
- ページ遷移、スクロール駆動アニメーション、視線追従、物理シミュレーションなど多様な技術を統合
- 各機能を独立したモジュールとして実装し、ScrollTriggerで制御することで保守性と性能を両立

**詳細解説:**

ToyFightによるFlimプロジェクトは、UXエンジニアリングにおける「複数技術の統合」の優れた実例です。Webflow（ノーコードツール）、GSAP（アニメーションライブラリ）、Lottie（ベクターアニメーション）、Rapier（物理エンジン）という異なる性質のツールを、一貫したユーザー体験として統合しています。

技術的に特筆すべきは、物理シミュレーションの実装です。DOMレンダリングと物理計算を分離し、Rapierの物理ワールドとCSSトランスフォームの同期を`requestAnimationFrame`で行う設計は、パフォーマンスとメンテナンス性を両立させています。

```javascript
const updateShape = (rigidBody, domElem) => {
  const position = rigidBody.translation();
  const rotation = rigidBody.rotation();
  domElem.style.transform = `translate3d(
    ${position.x * SIZE_RATIO}px,
    ${(-position.y) * SIZE_RATIO}px, 0
  ) rotate(${-rotation}rad)`;
}
```

このパターンは、ゲーム開発の「Entity-Component-System」に似た設計で、状態管理とレンダリングを分離する考え方です。

また、Lottieアニメーションの制御戦略も参考になります。スクロール位置に応じて`playSegments()`で再生範囲を制御し、`hasEnterPlayed`などのフラグで状態を管理することで、複雑なスクロール連動アニメーションを実現しています。

UXエンジニアとして学ぶべきは、「適切なツールを適切な場所で使う」という判断力です。ページ遷移にはシンプルなGSAPタイムライン、複雑なベクターアニメーションにはLottie、物理挙動にはRapierと、それぞれの強みを活かした設計が、最終的な体験の質を高めています。

### 9. **Detail - A collection of small details that make big difference**

**詳細解説:**

例えば、「インラインの単位変換」は、ユーザーが異なる単位系で考えている場合の摩擦を減らす配慮です。実装は比較的シンプルですが、そのニーズに気づき、適切なタイミングで表示する判断が重要です。

UXエンジニアリングの実践として、これらのディテールは以下の段階で統合されるべきです：

1. **設計フェーズ**: デザインシステムのガイドラインとして文書化
2. **実装フェーズ**: 再利用可能なコンポーネントやユーティリティとして実装
3. **品質管理**: レビューチェックリストやLinterルールとして標準化

小さなディテールの積み重ねが、「洗練されたプロダクト」と「そこそこのプロダクト」を分ける要因になります。
