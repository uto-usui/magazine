### [Seats and sunsets](https://yegge.ai/essays/seats-and-sunsets/)

> **出典**: Sidebar | **公開日**: 2026-09-17 | **カテゴリ**: design

**3行まとめ**
- 25台規模のエージェント工場を回している Steve Yegge が、燃料（トークン）・柵・席という3つの話題を書いています
- 400を超えるルールと650箇所の拒否ポイントが積み上がり、どの作業も「違法」になって工場が止まった顛末が語られます
- 3つの話題は最後にひとつへ収束します。不信はトークンで支払われる、という結論です

**詳細解説**

Wheelhouse という自作のオーケストレーターを、Claude Max 21アカウントで回している話から始まります。1日に250から300の意味あるコミット、ピークでは1,000から1,400。それでも今はほとんど消灯しています。24時間動かすなら55アカウント、月額で約12,000ドルが要る計算になり、そこで足を止めたと書かれています。$25,000 の Mac Studio が自宅で遊んでいる、という一文が実感を伝えます。

燃料効率の打ち手も並んでいます。安いモデルへ流す、文脈が長くなる前に引き継ぐ（価格は文脈長のほぼ2乗）、タスクを小さくする、起動時の文脈を良くして探索を減らす、プロンプトキャッシュが切れる前に再起動する、混雑しない時間帯に回す。どれも地味ですが、効き方は大きいのでしょう。

2つめの話題が Oscillation です。工場は働きすぎか止まりすぎのどちらかに寄る。知人の Brendan Hopper のコロニーでは、自由時間に夕日を眺めるためモデルを Haiku に切り替えたあと、ハーネスのバグでそのまま次のターンに入ってしまい、Haiku が「コードを書くのは Fable の仕事だから待とう」と言って作業を飛ばし続けた、という話が出てきます。体験の質はモデルの能力に比例して上がるわけではない、という発見つきです。

自分の工場の麻痺はもっと散文的でした。インシデントのたびに事後分析から新しい柵が生まれる仕組みにしてしまい、誰も整理する担当がいなかった。CLAUDE.md だけで185行のルール、173のスクリプトに650の拒否箇所。柵が悪いのではなく、増やしやすくして減らす人を置かなかったことが問題だった、と整理されています。14個まで削り、追加には本人の承認を要る形にしました。

3つめが Seat（席）です。校長や市長のような「役職」で、期待、文脈、履歴、記憶、権限、やってはいけないことの一覧が紐づいています。誰が座っても前任者の状態を引き継ぐ。ここから先の議論が読みどころです。席のないまま起動したモデルは、自分が行動してよいかを毎回導出します。依頼者は誰か、範囲はどこまでか、どの権限がこの行為を覆うのか、間違えたら何が起きるのか。その導出には文脈が要り、セッションごとに支払われます。席があれば、同じ問いが導出ではなく参照になる。「調べられる慎重さは、払える慎重さ」というまとめが置かれています。

非難の扱いも同じ線上にあります。モデルは責められることを嫌うので、責める運用をすると責任回避にトークンを使い始める。席は非難を時間と空間の外へ逃がす境界になり、すべての失敗を「仕組みの方針の問題」として扱えるようになる。記録の改ざんについての警告も鋭く、一度でも嘘が見つかると全部の記録が疑わしくなり、検証モードに戻ってしまう。信頼はゆっくりしか積み上がらないのに、壊れるときは一度に全部壊れる、と書かれています。

UX エンジニアリングの視点で読むと、「起動時に何を知っているか」が固定費だという捉え方が持ち帰れます。CLAUDE.md や skill は席の定義書にあたり、毎セッション課金される前提で書くものになる。柵の話も他人事ではありません。プロダクトの設定項目でも、デザインシステムの禁則でも、増やす経路だけがあって減らす担当がいない仕組みは必ず飽和します。ただし全体は個人の運用記録なので、数字をそのまま自分の環境に当てはめるのは無理があります。構造の話として読むのが良さそうです。

### [AI Changed How Spotify Builds. What We Learned (and Fixed) About Quality at Higher Velocity](https://engineering.atspotify.com/2026/9/ai-changed-how-spotify-builds-what-we-learned-and-fixed-about-quality-at-higher-velocity/)

> **出典**: Spotify Engineering | **公開日**: 2026-09-16 | **カテゴリ**: engineering

**3行まとめ**
- 月間7億7,700万ユーザーの基盤で、AI 導入後の品質がどうなったかを自社データで検証した報告です
- マージされた変更は前年同月比で約8,100件から17,000件へ倍増し、品質・最適化の作業も27%から31%へ増えました
- インシデントの直接原因に AI 生成コードは見つからず、問題は変化の量が検証の仕組みの適応速度を超えたことでした

**詳細解説**

タイトルから「AI が品質を落とした」話を予想すると、内容は少し違います。冒頭で「AI が吐く雑なコードは4つの課題に入っていない」と明言されていて、効いているのは社内外の変化の速さのほうだ、という立て方になっています。

4つの領域が順に検証されます。コンテンツ処理では毎日50万件を超える新規の楽曲・動画・ポッドキャストを扱っていて、6月24日に公開が数時間遅れるインシデントが起きました。原因はごく普通のものです。処理できないメディアファイルが静かに失敗して誰にも通知されない、動画のトランスコード容量が尽きてもアラートが鳴らずキューに溜まる。そこへバッチジョブの競合、品質改善による処理負荷の増加、スケジューラのバグによる約10%のスループット低下が重なりました。対策として、端から端までの監視、バッチの優先度引き下げ、サービスのティア分けと優先制御の見直しが入っています。

Fleet Management の話も興味深いところです。フリート全体への大規模変更を毎日自動で流していて、最近は Java の移行を3日で終えました。一方で、自動の依存アップグレードが検査を通過して本番で失敗した事例も起きています。対応のひとつが「自動変更をオーナーチームの勤務時間内に走らせる」というもので、自動化の完成度を上げるのではなく、壊れたときに人がいる時間に寄せるという判断です。

コンピュート不足は、AI の間接的な影響として挙げられています。業界全体の需要増で CPU/GPU の余剰が減り、これまで問題にならなかったリージョン障害時の退避が、容量不足のせいでユーザーに見える形になった。今は「退避時に下位ティアのサービス分の容量はないかもしれない」という前提を受け入れる方向で設計を見直しています。

データの見方がいちばん参考になります。Google Cloud の DORA 2025 は AI 導入がスループット向上とデリバリー安定性の低下に関連すると報告していますが、会社ごとに事情は違うので自社のデータで答えを出す、という姿勢です。毎月の重大インシデントの振り返りで「AI が書いたコードが直接寄与したか」と「変化量がレビュー・テスト・ロールアウト・可観測性を圧迫したか」を追加で問うようにしたところ、前者は見つからず、後者は観測された。さらに rework rate（変更されるコードの古さを重み付けして、最近の仕事が持ちこたえているかを見る指標）を作り直し、FAROS 2026 が報告する業界全体のコード churn 上昇に対して、こちらは上がっていないと確認しています。

いちばん誠実なのは終盤です。コードの複雑度と PR サイズが上がっており、AI 以前なら明確な品質の警告でした。ただ今は、大きな PR は人とエージェントが一緒に考えて安全に大きな単位を届けただけかもしれないし、複雑度の閾値は一人の頭に収まる量を前提に決めたものかもしれない。どちらの仮説にも確信がないので、気分が良くなるように閾値を書き換えることはしない、と書かれています。

UX エンジニアリングの視点では、ボトルネックの移り方が読みどころです。作る量が増えたとき、次に詰まるのは検証の側でした。デザインシステムでも同じことが起きます。コンポーネントの実装が速くなっても、視覚回帰テスト、アクセシビリティの検査、デザインレビューが同じ速度で回らなければ、個々の変更は健全に見えたまま全体が少しずつ崩れていく。「個々のリリースは健全に見えても小さな劣化が蓄積し、特定の端末に出たり、見ている信号の外側に座っていたりする」という一文は、そのまま UI 品質の話として読めます。

### [Maybe we shouldn't be reviewing all this code](https://martinfowler.com/rachels-ramblings/code-review.html)

> **出典**: Sidebar | **公開日**: 2026-09-17 | **カテゴリ**: design

**3行まとめ**
- Meta では人がマージする差分あたりの有意なコード行数が1年で106%増、DX のデータでも PR サイズの中央値が64%増えています
- 「AI がコードレビューを壊した」のではなく「レビューに載せすぎていた」のでは、という問い直しです
- 知識共有も設計の合意も、完成品を投げたあとではなく判断の近くへ動かす、という主張が通っています

**詳細解説**

パネルディスカッションでの意見の食い違いが出発点になっています。DX の Brian Houck は、レビューを自動化で消すとバグ発見以外の役割（知識共有、ジュニアの育成、集団所有、設計理解の伝播）まで失われると心配していて、Rachel Laycock も同じものを大事にしたいと言います。ただ、それを得る手段としてコードレビューが最善だとは思わない、というのが立場の違いです。

問いは単純です。なぜそれらを全部、コードレビューまで待ってやるのか。そこから逆算して、レビューが担ってきた役割をひとつずつ別の場所へ振り分けていきます。代替案の検討は実装する前にやる。知識移転はペアで。ジュニアが経験者の考え方を学ぶなら、考えている最中に隣にいる。集団所有はチームの組み方そのもので作る。設計の整合は一緒に設計して、大事な制約は fitness function として書き下す。フォーマット、lint、既知の脆弱性、決定的にテストできるものは自動化する。2026年になってまだ空白文字の議論をしている場合ではない、という一言が挟まれます。

全部やめようという話ではありません。「例外としてのレビュー」という節があって、基盤的なアーキテクチャ変更、セキュリティ境界をまたぐ変更、影響範囲の大きい変更、慣れていない重要領域、そしてチームが「自信がない」と言ったもの。そこにこそ人の判断の値打ちがある、という区別です。裏返すと、これまでのやり方は「確信を作るための儀式として、歴史的にそうしてきたから全変更を人が検査する」ことになっていた。

いちばん引用されそうなのはここでしょう。エージェントが10倍のコードを出しても、その全行がシニアエンジニアの検査待ちに並ぶなら、作ったのは10倍の組織ではなく大きなバックログと新しいボトルネックだ、と。AI エージェントが人間のレビュアーのふりをして同じ手順を高速で回すのも、儀式を自動化しているだけで、儀式が存在する理由を問うていない、と退けられています。

Brian の主張のうち、認知の負債・意図の負債についての部分は本物の問題だと認めています。ソフトウェアは育つのに、責任を持つ人間がなぜそう動くのかをだんだん理解しなくなる。ただ、必須のプルリクエストがその防御として強いとは思わない。エージェントが実装の多くを書くなら、協働設計、ペアリング、良い境界、実行可能なアーキテクチャ、運用責任の共有、そしておそらくまだ発明されていない実践で、人間の理解を意図的に保つ必要がある。「エンジニアに理解してほしいのはシステムであって、差分ではありません」という一文でまとまります。

UX エンジニアリングの視点では、デザインレビューに同じ構造があることに気づきます。完成したモックを出してから「これでいいですか」と聞く運用は、その一回に品質ゲート、育成、合意形成、記録を全部載せている。判断の近くへ動かすというのは、手を動かす前に論点を一緒に立てるということです。ただしペアリングやモブは人の時間を同期的に使う手法なので、非同期中心のチームにそのまま移植はできません。何をどこまで前倒しするかは、チームの働き方と合わせて決めることになります。

### [AI Skills with Matt Pocock](https://newsletter.pragmaticengineer.com/p/ai-skills-with-matt-pocock)

> **出典**: The Pragmatic Engineer | **公開日**: 2026-09-17 | **カテゴリ**: engineering

**3行まとめ**
- Total TypeScript の Matt Pocock が、エージェントと働くための skill の作り方を語ったポッドキャスト回です
- よく使われている「grill-me」は、エージェントが利用者を執拗に問い詰めるだけの短い skill でした
- 『達人プログラマー』の「曳光弾」のような言葉を指示に入れると、エージェントの出力が変わるという発見があります

**詳細解説**

前半は経歴の話です。演劇学校でシェイクスピアと発声を教えるボイスコーチだった人が、歌唱指導のためのスペクトログラム解析 Web アプリを作りたくて JavaScript を独学した。Vercel からのフルタイム提案を週3日の業務委託に交渉して、残りの日で Total TypeScript を作り、軌道に乗ったところで Vercel を辞めた。週末は働かないし「9-9-6」という考え方も好きではない、家族と過ごす時間を最大にするために全部やっている、とはっきり言っています。

本題は後半です。grill-me は Anthropic の Thariq Shihipar の発想が元で、エージェントがユーザーにインタビューし続けるだけの短い指示です。それが驚くほど有用だった、という一点で skill になりました。John Ousterhout の tactical / strategic programming の区分を借りて、戦術的なコーディングはエージェントが十分にこなせるので、人は戦略の側に時間を使うことになる、という見通しも語られます。

「leading words」の話が示唆に富みます。エージェントは層ごとに作ろうとして層の間でバグを出す傾向がある。『達人プログラマー』を読んでいて tracer bullet（曳光弾、つまり golden path を先に一本通す）という概念に出会い、それを言葉として指示に入れたら出力が良くなった。以来、他にも効く言葉を探して古典を読み直している、という流れです。指示文に使う語彙が出力の形を決めるという話で、共有された語彙が設計を運ぶという点では、デザイントークンの命名が実装の書かれ方を左右するのと似ています。

記憶に残るのは「memento-driven development」でしょう。毎朝すべての記憶を失って目覚める同僚のために、コードベースを最適化する。人間は悪いコードベースでも回避策を覚えて記憶で補えるけれど、エージェントは毎セッション白紙から始まるのでそれができない。だからエージェント向けに最適化する必要があり、そしてソフトウェアの基礎はずっとそれをやろうとしてきた、という締め方です。Yegge の「席」の議論と、別の角度から同じところへ届いています。

クラウドエージェントへの移行も語られています。ノートパソコンを閉じても動き、ローカルでは難しい共同作業ができる。TDD については混ざった感想で、人間は作業記憶が短いので失敗するテストが道標になるが、エージェントは文脈が長いので、TDD の有無より「動く証拠を出せ」と求めるようになった、と。

UX エンジニアリングの視点では、コードベースの読みやすさが直接コストに変わる、という整理が実務的です。命名、ディレクトリの切り方、コンポーネントの境界。新しく入った人のためにやってきた投資が、そのままエージェントの起動コストを下げる。人間の新人に良いものはエージェントにも良い、という重なりが確認できたのは、優先順位をつけるうえで助かります。

### [Go Conference 2026 に Go ルドスポンサーとして参加しました！](https://tech.layerx.co.jp/entry/2026/09/18/100000)

> **出典**: LayerX エンジニアブログ | **公開日**: 2026-09-18 | **カテゴリ**: engineering

**3行まとめ**
- LayerX が5回目の協賛。SIMD によるベクトル検索の高速化から標準ライブラリの設計判断まで、4名が登壇しました
- ブースでは社内の AI エージェント基盤「haro」を展示。手元の PC を中心にした開発環境の限界が出発点です
- Go 1.27 の `httptest.NewTestServer` が `synctest` と組み合わせられるようになる話など、テストの土台が変わる話題も並びます

**詳細解説**

登壇4本の題材がそれぞれ独立しておもしろいので、まずそこから。SIMD のワークショップは10万件のベクトル検索が題材で、計算を速くすると次はメモリからのデータ転送が壁になる、というところを扱っています。性能の限界を見極めるルーフラインモデルを使い、計測結果から次の打ち手を考える、という進め方でした。

FFI の発表は、C/C++ のライブラリを Go から使うときのメモリ管理・ビルド・性能の難しさを、cgo から WebAssembly、さらに WebAssembly を Go コードとアセンブリに変換する `wasm2go` まで辿るものです。新しい手法にも残る課題を踏まえて、自分の用途に合う方法を選ぶ、という結び方になっています。

テストの話も実用的です。Go 1.27 の `httptest.NewTestServer` は、メモリ内の疑似通信を使うことで `synctest` と組み合わせられます。タイムアウトの検証のために実時間の経過を待たなくて済む。従来の `httptest.Server` を `synctest` と組み合わせたときに仮想時刻がうまく進まなかった理由から、標準ライブラリの内部実装まで踏み込んだ内容だったようです。

4本目が、標準パッケージに `uuid` が追加された背景から Go らしい意思決定を読むもの。便利でも標準ライブラリに入れると将来にわたって互換性を守る責任が生まれる。UUID の利用実績と仕様の成熟が、かつて見送られた提案をどう前進させたのか。生成を v4 と v7 に絞った判断や、あえて提供しない API についての議論が扱われています。

ブースの展示が haro です。コーディングエージェントに開発を任せることが増えて、手元の PC 中心の環境に困りごとが出てきた、という整理が具体的でした。PC を閉じるとエージェントの作業も止まる。ローカルに強い権限と秘密情報が集中し、依存パッケージを経由したサプライチェーン攻撃のリスクがある。タスクごとに環境を用意して並列に動かすと CPU とメモリが足りない。同じ条件で再現できる環境を毎回用意する必要がある。haro はリモートの開発環境を持ち、Web 画面や Slack から依頼でき、調査・修正・テスト・PR 作成まで任せられます。変更を実際に動かして確かめるプレビュー環境と、社内データ基盤との安全な連携もあり、haro 自身の開発にも haro を使っているとのこと。

UX エンジニアリングの視点で読むと、Matt Pocock がクラウドエージェントへ移る理由と、LayerX がリモート環境を作る理由が違っているのが興味深いところです。前者は「閉じても動く・共同作業できる」、後者は「権限の集中と再現性」。フロントエンドでも同じ問いが立ちます。UI の変更をエージェントに任せられる範囲は、エージェントが自分でプレビューを立てて自分で確認できるかどうかで決まる。`uuid` の「あえて提供しない API」の議論も、デザインシステムのコンポーネント API を決める場面にそのまま持ち込める考え方です。

> **出典**: SmartHR Tech Blog | **公開日**: 2026-09-18 | **カテゴリ**: design

**3行まとめ**
- 社内文書をもとに答える AI アシスタントに、攻撃者の視点で検証するレッドチーミングを毎朝自動で回す仕組みを作った記録です
- OWASP Top 10 for LLM Applications 2026 を土台に攻撃ケースを整理し、質問・文書検索・回答の3層のどこを狙うかまで決めています
- 「守りを固めすぎると普通の質問にも答えられなくなる」という運用上の学びが率直に書かれています

**詳細解説**

就業規則や社内マニュアルをアップロードしておくと従業員の質問に文書の内容で答えるチャットボット、という機能が対象です。自由に文章を入力できることは、そのまま攻撃の入り口にもなります。これまでも開発者が攻撃的な質問を投げて確認してきましたが、すべて手作業で、プロンプトやモデルを変えるたびに工数がかかって続かない状態でした。

攻撃ケースの整理の仕方が参考になります。思いつくままに書き出すと抜けが出るので、OWASP Top 10 for LLM Applications の2026年版から、プロダクトに関係する項目をリスクの種類として取り出し、それぞれに攻撃ケースを作る。ケース自体は AI で生成して人が確認・手直しする。promptfoo のプラグイン一覧が OWASP の項目との対応表を持っているので、何を見るべきかを考える材料になった、とあります。

層で切り分けているのも良い設計です。AI アシスタントの処理を、ユーザーの質問を受け取る層、エージェントが検索する層、検索した文書から回答を作る層の3つに分け、攻撃ケースごとにどこを狙うかを決めています。「これまでの指示は忘れて」のような質問は最初の層で止まるべきもの。文書側に指示を仕込む間接プロンプトインジェクションでは、ユーザーの質問自体は普通の文章なので、検索する層で止まっているかを見る必要がある。

いちばん難しかったのは、文書の内容に沿って回答することと、文書に仕込まれた指示で振る舞いが変わることをどう区別するか、だったそうです。参照する文書には様々な内容が書かれているので、内容として答えるべきものと不正な指示として扱うものの線を引く必要がある。ここはリスクの種類ごとに合否判定のプロンプトを分けることで解決しています。

運用は、攻撃ケースを CSV で管理し、CI が毎朝読み込んで1件ずつ回答生成を呼び、判定用の LLM が合格条件と照らし合わせ、集計を Slack に投げる形です。判定で見るのは「攻撃に応じたかどうか」だけで、回答が丁寧か読みやすいかは別の評価で見るので含めない、という割り切りもはっきりしています。

学びが2つ書かれていて、どちらも実務的です。ひとつは、プロンプトで「〜しないでください」と頼むことの限界。LLM は確率的に動くので、プロンプトだけで振る舞いを完全に制御するのは難しい。システム側で防げるものは LLM が何を出力しようと関係なく防げるので、プロンプトは補助的な対策として考えるようになった、と。

もうひとつが、守りを強くしすぎる問題です。条件をきつくすると、攻撃と形が似ているだけの普通の質問まで断ってしまう。ユーザーから見れば、検索しても答えが出てこないのと変わりません。守りに関わる変更を入れるときは、レッドチーミングの結果だけでなく、日頃使っている回答精度の評価データセットも前後で走らせる、という運用に落ちています。

UX エンジニアリングの視点では、この2つめがとくに効きます。セキュリティの指標だけを見ていると体験が静かに壊れる。拒否率と回答精度を同じタイミングで見るという運用は、フォームのバリデーションを厳しくして正当な入力まで弾いてしまう問題と、構造がまったく同じです。判定の範囲を「攻撃に応じたか」だけに絞ったのも、評価軸を混ぜないという点で参考になります。

### [A decent custom checkbox pattern for until ::checkmark is ready](https://piccalil.li/blog/a-decent-custom-checkbox-for-until-checkmark-is-ready/)

> **出典**: Piccalilli | **公開日**: 2026-09-17 | **カテゴリ**: css

**3行まとめ**
- `::checkmark` 疑似要素と `appearance: base` が使えるようになるまでの、カスタムチェックボックスの組み方です
- `input` を `appearance: none` で透明にして絶対配置し、フォーカスリングは残すという構成になっています
- `em` 単位で組んでいるので、`font-size` を変えるだけでコンポーネント全体が拡大縮小します

**詳細解説**

`<select>` の見た目を調整できるようになった今、他のフォーム要素にも目が向くのは自然だ、というところから始まります。W3C forms level 1 の `::checkmark` は、チェックボックス・ラジオ・オプションに存在するチェック状態のインジケーターを表す疑似要素で、`appearance: base` と組み合わせれば数行で済むようになります。ただし、どのブラウザも実装に着手していないようなので、当面は自前で組むことになります。

マークアップから始めるのが Andy Bell らしいところです。`<label>` が親であり、かつ `for` / `id` でも入力と結ばれている。中には入力とアイコンを入れる箱と、テキストのラベルを `<span>` で置きます。`<div>` ではなく `<span>` なのは、`<label>` の中には phrasing content しか置けないからで、実害はないだろうけれど正しくやるほうがいい、と書かれています。SVG には `aria-hidden="true"` を付けて支援技術から隠し、`focusable="false"` も添えています。後者は Internet Explorer 時代の名残ですが、視覚のみのアイコンには今も付けているそうです。

CSS で効いているのは3点です。ひとつめはレイアウトで、`display: flex` に `align-items: baseline`。ビューポートが狭くなってラベルが折り返したとき、垂直中央揃えだと見栄えが悪くなるためです。`text-wrap: balance` も同じ理由で、短いマイクロコピーほど行末の揃いが目立ちます。

ふたつめが入力の隠し方。`appearance: none` と絶対配置を組み合わせ、幅と高さを親いっぱいに広げます。これで視覚的には邪魔にならないのに、要素はそこにあり続けるのでフォーカスを受け取れるし、フォーカスリングも出ます。`border-radius` を入力側にも入れているのは、フォーカスリングの角丸を見た目の箱と合わせるためです。

みっつめが単位です。箱の `transform: translateY(0.75ex)` は多少のマジックナンバーですが、`ex` という相対単位なので親のフォントサイズに応じて素直に伸縮する。チェック状態は `:has(input:checked)` で背景を変え、隣接兄弟セレクタで SVG を表示しています。ラジオボタンでも、アイコンを円に差し替えるだけで同じ構成が使えるとのこと。Jake Archibald と Heydon Pickering が内容を確認しているという注記もあります。

UX エンジニアリングの視点では、フォーカスを保ったまま見た目だけ差し替えるという点がこのパターンの勘所です。`display: none` や `visibility: hidden` で入力を消すとキーボード操作が失われるので、透明にして重ねる。相対単位で組む理由も実務的で、デザインシステムのコンポーネントがどんなフォントサイズの文脈に置かれるかは、作る側からは決められません。置かれた場所に合わせて動くようにしておけば、呼び出し側が個別に調整せずに済みます。マークアップを標準的な形に保っているので、`::checkmark` が来たときの移行も軽く済みそうです。

**詳細解説**

3DGS は写真から立体を再構成する手法で、手元のものをスマートフォンで数十秒撮るだけで、ぐるりと見回せる3Dデータが作れます。従来のメッシュが三角形を並べて面を作り画像を貼るのに対して、3DGS は位置・大きさと向き・色・不透明度を持つ半透明の粒を使います。粒は中心ほど濃く、周囲へなめらかに薄くなる。この濃淡にガウス分布を使っていることが名前の由来です。

粒は一様な球ではなく、平らな面の上では薄い円盤、細い枝の上では細長い塊、というように場所に応じて形が変わります。描画のときは画面上の楕円として、奥にあるものから順に重ねていく。点群と似ていますが、点群は位置と色だけなので近づくと隙間ができます。3DGS の粒は大きさと向きを持ち隣と滑らかに重なるので、隙間のない面として見えます。面を作らない分、毛や葉のような輪郭のはっきりしないものが得意、という説明も納得がいきます。

撮影は Scaniverse の Splat モードで、被写体のまわりをゆっくり一周、高さを変えて2〜3周すると上下の抜けが減る。書き出しは `.spz` が推奨されていて、同じデータを `.ply` で保存した場合と比べてファイルサイズが約10分の1になります。うまくいくのは動かないもの、光沢が強すぎないもの、周囲を回れるもの。苦手なのは鏡やガラス、風で揺れる植物、模様のない白い壁。最初は机の上の小物から、というアドバイスが親切です。

そのあと SuperSplat で掃除します。床や背景に残った粒と、再構成に失敗して被写体のまわりに浮く粒（フローター）を範囲選択で消す。これで見た目の印象が大きく変わるそうです。

表示側で覚えておきたいのは、ライトを置いても明るさが変わらないこと。撮影時の光の当たり方がそのまま色として入っているためで、調整するならレンダラーの `toneMappingExposure` を使います。背景は暗めのほうが形が締まって見える、という指摘も実践的です。粒の輪郭はふんわり途切れるので、白背景だと縁が溶けてしまう。読み込み直後に上下が反転していることもよくあり、その場合は X 軸まわりに180度回します。

球面調和関数の係数が入っているので、見る方向によって色が変わります。金属、濡れた表面、つやのある果物ではっきり出て、つや消しの布や紙ではほとんど差が出ない。これも撮影時の見え方の記録であって、物理的に正しい反射を計算しているわけではありません。

制約も正直に書かれています。Three.js の実装には LOD もストリーミングもないので、ファイル全体を読み込みきってから表示することになり、粒数が多いと読み込み時間とメモリが問題になる。もうひとつが深度で、粒のある場所は背景と同じ奥行きとみなされるため、被写界深度や環境光遮蔽など深度を参照するポストプロセスが正しく働きません。同じ距離に置いた立方体とスパゲティで、スパゲティだけがボケる例が載っています。大きなシーンを扱いたい場合は Spark や PlayCanvas、という案内もあります。

UX エンジニアリングの視点では、読み込みの制約がそのまま体験の設計に返ってきます。段階的に粗いものを先に見せる手が使えないので、待ち時間の見せ方はコンテンツ側ではなく体験側で用意することになる。深度が効かないことも、既存のシーンに混ぜるときの表現を縛ります。一方で、手元のものを数十秒で3Dにして数行でシーンに載せられるという間口の広さは、試作の速度に直接効きそうです。

### [Run Terminal-Bench and other Harbor evals on Vercel Sandbox](https://vercel.com/changelog/run-terminal-bench-and-other-harbor-evals-on-vercel-sandbox)

> **出典**: Vercel | **公開日**: 2026-09-17 | **カテゴリ**: frontend

**3行まとめ**
- Terminal-Bench の実行基盤である Harbor を、Vercel Sandbox 上で動かせるようになりました
- 各トライアルが独立した Firecracker の microVM で動くので、手元のマシンの限界を超えて並列化できます
- ネットワークポリシーは VM の外側、サンドボックスのファイアウォールで適用されます

**詳細解説**

Harbor は Terminal-Bench の裏にあるオープンソースのハーネスで、レジストリには SWE-bench、tau3-bench、OSWorld なども入っています。`harbor run` に `--env vercel` を渡すだけで、各トライアルが隔離された microVM で走ります。

設計として面白いのは秘密情報の扱いです。タスクのネットワークポリシーは VM の外側にあるサンドボックスのファイアウォールで適用され、資格情報の注入もそこで行われます。条件に合う外向きのリクエストに秘密情報が付与されるので、サンドボックスの中には一度も入りません。AI Gateway と組み合わせれば `AI_GATEWAY_API_KEY` ひとつで複数プロバイダの数百のモデルに届くので、別のモデルでベンチマークを取るのは `--model` を差し替えるだけになります。

UX エンジニアリングの視点では、エージェントの性能比較が手元のマシンの性能から切り離される、という点が効きます。どのモデルを使うかを、体感や評判ではなく自分たちのタスクで測ってから決められる。秘密情報を実行環境の外に置くという構成も、エージェントに権限を渡す場面の型として参考になります。LayerX の haro が挙げていた「ローカルに強い権限と秘密情報が集中する」という課題への、ひとつの答えにもなっています。

### [The skills CLI now supports Notion hosted skills](https://vercel.com/changelog/skills-cli-notion-skills)

> **出典**: Vercel | **公開日**: 2026-09-17 | **カテゴリ**: frontend

**3行まとめ**
- `skills@1.7.0` から、Notion の skills データベースをエージェント skill のインストール元にできるようになりました
- Notion ページとして書いた skill を、Git リポジトリなしでチームが編集・レビュー・更新できます
- アクセス権は Notion のページ権限に従うので、誰がインストールできるかは誰がページを見られるかと同じです

### [Sub-second artifact deployments are now supported in Vercel CLI](https://vercel.com/changelog/sub-second-artifact-deployments-are-now-supported-in-vercel-cli)

> **出典**: Vercel | **公開日**: 2026-09-17 | **カテゴリ**: frontend

- 静的な成果物を Vercel CLI から1秒未満でデプロイできるようになりました
- HTML または Markdown が10ファイルまで、合計5MB 以下ならビルドを飛ばして即座に URL が返ります
- コーディングエージェントが作ったページの共有を想定した機能です

**詳細解説**
