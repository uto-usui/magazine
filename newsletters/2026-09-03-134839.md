### [The best dark mode toggle is probably none](https://lea.verou.me/blog/2026/dark-mode-toggles-2/)

> **出典**: Lea Verou | **公開日**: 2026-09-02 | **カテゴリ**: css

**3行まとめ**
- 常時表示のダークモード切り替えは、ほとんどのサイトでそもそも要らないのではないか、という結論にたどり着いた続編です
- 前回の「2状態トグル」提案への反論に一つずつ答えながら、頻度×影響×持続性で使いやすさの問題を優先づけする原則を確認しています
- 決め手は「消費者向けの有名サイトに常設トグルが一つも見当たらない」という観察と、HCI 専攻の同僚がそのUIを見たこともなかったという経験でした

**詳細解説**

Lea Verou さんが1か月前に書いた「ダークモードの切り替えを常時置くなら、system・light・dark の3状態ではなく、system と『いまの system の反対』を行き来する2状態にするほうがいい」という記事は、かなり広く読まれました。今回はその続編です。前回は「そもそも置くべきかどうか」には踏み込んでいなかったのですが、今回は「ほとんどのサイトでは置かないほうがいい」とはっきり書いています。

前半は Bramus さんからの反論への応答です。中心にあるのは「OSが時刻でライト・ダークを自動切り替えする人が、日中にダークを試してライトに戻したあと、夜にまた訪れるとダークになってしまう」という筋書きでした。これに対する反論の組み立てがおもしろいところです。まず、Bramus さんが開発者に対して「あなたはどちらを実装しますか」と聞いた投票を、「どちらが使いやすいか」の根拠として使っている点を指摘します。この2つは別の問いで、開発者の好みには慣習と実装のしやすさが混ざっている。もし開発者に聞くことで使いやすさがわかるなら、ユーザーテストは要らないはずだ、と。

次に「3状態でも選択中の項目は変わるので、局所的なフィードバックはある」という擁護に対して、ボタンは手段であって目的ではない、と返します。ユーザーはボタンを変えたくて押したのではなく、ページを変えたくて押した。コントロールだけが変わってページが変わらないのは、Norman のいう評価の淵（gulf of evaluation）そのもので、緩和策ではなく失敗のほうだ、という整理です。そして、使いやすさの問題は頻度×影響×持続性で優先度を決めるのが定石で、Bramus さんの筋書きは3つとも低い。一方で3状態は、ほとんどの人が使わない状態のぶんの負担を毎回の操作にかけている、と続きます。

大きな転換点は後半でした。Verou さん自身が、HCI の博士号を持つ同僚に記事を読んでもらったところ、その同僚は記事が何のUIの話をしているのかわからなかった。ダークモードの切り替えを見たことがなかったのです。そこで気づいたのは、自分が見てきた常設トグルはすべて開発者向けのサイトにあったということでした。Gmail も Facebook も Bluesky も、1日に何時間も使われるサービスですら、これを設定パネルの奥に置いています。まれな意図は段階的開示（progressive disclosure）の向こう側に置くもので、全訪問者が見る唯一のコントロールに置くものではない、というのが結論です。

UXエンジニアリングの視点でとくに使えるのは、「実装の状態機械についての明快さは、結果についての明快さではない」という一文でしょう。「明快さ」や「シンプルさ」は誰もが賛成する言葉なので、まったく反対の立場を支えるためにも使われます。だからこそ「何について明快なのか」を一段掘る、という手つきがそのまま真似できます。加えて、記事の誠実さも見どころです。使いやすさはユーザーの結果に宿る性質なのに、ここまでの議論では誰一人ユーザーを観察していない、と自分で釘を刺しています。しかも、こういう頻度の低い微小な操作は、少人数を呼んで観察する定性テストとは相性が良くない。テスト対象だと知られた時点で、その人は普段よりずっと注意を払ってしまうからです。

最後は「そもそもこの問題は解く価値があるのか」を先に問おう、という話で締められます。標準化の議論でも、機能を入れるかどうかを決める前に細部の議論が始まってしまうことがよくある。エンジニアリングの背景を持つ人ほど、難しい問題に抗いにくい。答えが「いいえ」であることの多さに驚くはずだ、という締め方でした。

### [How AI-ready is your design system?](https://christophhellmuth.com/open-design-system-bench/)

> **出典**: Sidebar | **公開日**: 2026-09-02 | **カテゴリ**: design

**3行まとめ**
- デザインシステムがAIエージェントにとってどれだけ読めるかを測る、オープンなベンチマーク open-design-system-bench の紹介です
- 静的監査7項目と、実際にエージェントにUIを書かせて6軸で採点する生成ベンチマークの2段構えになっています
- 4つのシステムを測った結果、全部が中間層どまりで、しかもすべてに未知の実バグ（公開されていないつもりが到達できないコンポーネントなど）が見つかりました

**詳細解説**

「エージェントが生成したUIは、うちのデザインシステムに本当に従っているのか」という会話は、いまどのデザインシステムチームでもされています。ただ、それを数字で裏づけられる人はいませんでした。この記事は、その空白を埋めるためのベンチマークを作って4つの実在システムに当て、結果とハーネスの両方を公開した報告です。Nord Security の本番デザインシステム Aurora から始まり、React と TypeScript のコンポーネントライブラリ全般に一般化されています。

静的監査のほうはAPIキーも不要で数秒で終わります。見ているのは、AGENTS.md があるか、コンポーネントカタログが抽出できて説明がついているか、公開しているつもりのコンポーネントがパッケージのエントリポイントから本当に到達できるか、命名がモデルの期待と合っているか、トークンが機械可読か、非推奨をエージェントが読めるか、ドキュメントが grep できるテキストか、の7点です。ここで見つかったのが Finding 1 でした。公開APIをソースから計算する（ルートのバレルとpackage.jsonのexportsマップの和集合）というルールひとつで、監査したすべての本番システムから出荷済みの不具合が出てきます。ある本番キットでは Toggle を含む3コンポーネントがディレクトリごとのエントリポイントは持っていたのに再エクスポートされておらず、チームは公開済みだと思っていたのに利用側からインポートできませんでした。

採点モデルの設計もよく考えられています。同じ平均点が正反対の失敗を隠すことがあるからです。システムをよく使ったうえでAPIを微妙に間違えるもの、システムに一切触らず全部手で書いてAPIチェックを全通過するもの、野心的な構造を組んだがコンパイルが通らないもの。平均はこの3つを同じに扱ってしまうので、ゲートは最悪の軸で切り、「デザインシステムを無視した」を一級の指標として扱う、という判断です。実際、GPT 5.6 の2構成はコンパイル成功率が83%と94%と高く、存在しない名前も出さないのに、それは55%と63%のケースで Aurora を無視していたからでした。混ぜた1つのスコアなら、この2つが勝者に見えてしまいます。

Finding 4 も実務に効きます。898件の生成のなかでモデルが読まずに推測したときに発明した名前を集めた語彙集が、リポジトリに入っています。モデルは Switch、Box、TextField、spacing、as を期待する。その事前分布に近い命名のシステムは、追加の準備なしに従ってもらえる。独特の語彙を持つシステムは、生成のたびに幻覚のぶんの税金を払う。測定できた最高の一致度（97.2）はオープンソースのシステムのひとつで、これはインフラ費用がゼロで得られる、AGENTS.md を1行も書く前から持てる数少ない優位だ、と書かれています。

もうひとつ、ガイダンスの効果を測ったグラフの読み方が誠実でした。ガイダンスなし、指示ファイルあり、指示ファイル＋スキル＋カタログ、の3段階で比べると、指示ファイルを追加した段の伸びが大きく、それを磨いた段の伸びは小さい。つまり、まず指示ファイルをエージェントの目の前に置くことが効くのであって、その洗練は二次的な利得だ、という結論です。しかも、ガイダンスなしで最高だった GPT 5.6 Luna（69.0）は、ガイダンスが入るとほぼ反応せず最下位タイに落ちます。予算の会話に耐えるのは水準ではなく差分（Lift）だ、という主張がここから出てきます。

UXエンジニアリングの視点では、Finding 5 の自己申告がいちばん示唆的かもしれません。オープンソースの3システムに抽出器を向けた日、そのツール自身の前提が3つ壊れました。バレルは `export * from` を使うはずだったのに88文中87文が名前指定の再エクスポートだった、バレルの参照先は素の再エクスポートファイルのはずだったのに JSX の実装ファイルを直接指していた、ディレクトリのインデックスは `index.ts` のはずだったのに3分の1が `index.tsx` だった。デザインシステムは、機械の利用者が依存する機械的な細部でこそ食い違う。それはソースにツールを当てて初めて見えてくる、という話です。ドキュメントのページを増やしても、エクスポートも命名も changelog も何ひとつ変わりません。デザインシステムを「新しい種類の利用者に向けたAPI表面」として扱い、そのように測る、という視点の転換がこのベンチマークの提案でした。

### [How Coinbase used Code Connect to guide agents and shrink token costs](https://www.figma.com/blog/how-coinbase-used-code-connect-to-shrink-token-costs/)

> **出典**: Figma Blog | **公開日**: 2026-09-02 | **カテゴリ**: design

**3行まとめ**
- Coinbase のデザインシステムチームが Code Connect を全コンポーネントに行き渡らせ、その効果を実測した事例です
- 同じデザイン・同じプロンプト・同じモデルで3回走らせ、トークン11.5%減、実装時間22.3%減、コスト22.5%減という結果でした
- エージェントスキルは「どう実装するか」を形づくり、Code Connect は「デザインから始めるときの初期文脈」を渡す、と役割が分かれています

**詳細解説**

Coinbase Design System（CDS）チームは、すでにいくつかのエージェントスキルを持っていました。適切なコンポーネントを選ぶ、非推奨のパターンを避ける、CDS のデザイントークンを使う。社内のプロトタイピング環境もそのスキルの上に載っていて、そこで作られたものは既定で CDS に沿います。ただ、どちらもゼロからコードを書く前提でした。「Figma のデザインを本番品質の CDS コードにする」という、もうひとつのよくある流れは手つかずのままで、プロダクトエンジニアからは遅い・不正確・普段の仕事に持ち込むには予測が立たない、と言われていたそうです。

Code Connect は明らかな打ち手でしたが、CDS のマッピングは Figma MCP サーバーが出る前から更新されていませんでした。あるものは古く、新しいコンポーネントの多くにはテンプレートすらない。モバイルとウェブで数百のコンポーネントを直す必要があります。ここで Technical Lead の Erich Kuerschner さんは、Claude Code で Figma コンポーネントの一覧を受け取って並列に処理していくワークフローを組み、テンプレートの記述は `figma-code-connect` スキルに任せました。約4時間で、数個しか移行できていなかった状態から、デザインシステム全体をカバーする状態まで到達しています。

評価のセットアップは、この記事のいちばん見どころです。同じデザイン、同じプロンプト、同じモデル（Sonnet 4.6）で、空のコードベースに対して3回。毎回リセットして「次のエージェントがつまめる手がかり」を残さないようにし、さらにプロンプトキャッシュの影響も制御しています。キャッシュが効いてしまうと、Code Connect とは無関係な理由で好結果が出てしまうからです。プロンプトは意図的に素っ気なく、`Implement this design from Figma` とデザインファイルへのリンクだけ。デザインは単純すぎず（ボタンと入力欄だけ）複雑すぎず（アプリのホーム画面まるごと）、その中間を狙って選ばれました。わざと罠も仕込まれていて、ヘッダーには数十のプロパティを持ちコード上もかなり複雑な Stepper が置かれています。

結果として、トークン使用量が平均11.5%減、実装までの時間が22.3%減、コストが22.5%減。3回とも改善しています。ただ、この記事でおもしろいのは数字よりも定性的な観察のほうかもしれません。Code Connect なしのときによく見られた失敗は、Stepper をプログレスバー2つとラベルで手作りしてしまうことでした。そして「エージェントがイラストやアイコンの名前を幻覚することで有名だったが、Code Connect の導入を終えたら一晩でその問題が消えた」という一文が、実務の手触りをよく伝えています。

役割の切り分けも明快でした。CDS のエージェントスキルは、パターンの選び方から非推奨の回避まで、エージェントが解を実装する過程を形づくる。Code Connect は、デザインから出発するときにいちばん良い初期文脈を渡すので、探索と推測に使うトークンが減り、スキルの有無にかかわらず時間とコストが下がる。CDS チームは、新しい世代のモデルが出るたびにスキルなしでも CDS をうまく使えるようになっていることに気づいていて、いつかスキルが不要になる日に備えて評価を回している、とのことです。ただし文脈の質はいつまでも効く。「その未来で Code Connect を持っていない状態にはなりたくない。エージェントがデザインの解釈で暴走するのを見てきたから」という言葉で締められています。

UXエンジニアリングの視点で気をつけたいのは、これが3回の実行、1つのデザイン、1社の自己報告だという点です。数字をそのまま自分の環境に持ち込む根拠にはなりません。ただ、実験の組み方（キャッシュを制御する、プロンプトを意図的に曖昧にする、毎回リセットする）は、自分のチームで同じ問いを立てるときにそのまま使える手順になっています。

### [The critical design engineering manifesto](https://www.pipshea.net/manifesto)

> **出典**: Sidebar | **公開日**: 2026-09-02 | **カテゴリ**: design

**3行まとめ**
- 2011年の Critical Engineering Manifesto を、デザインエンジニア向けに書き直した11の宣言です
- 「コードは設計の材料である」から始まり、生成物への依存、シームの設計、なぜをリポジトリに書くこと、押した責任までを扱います
- 本文はバージョン管理下の公開 Gist にあり、コミット履歴と署名つきで、フォークへの誘いが添えられています

**詳細解説**

2011年、Julian Oliver、Gordan Savičić、Danja Vasiliev の3人が Critical Engineering Manifesto を発表し、私たちが依存している技術を研究と疑いと介入の対象として扱おうと呼びかけました。それから15年、Pip Shea さんがそれを「批評的デザインエンジニア」向けに remix したのがこの文章です。ソフトウェアのデザインとエンジニアリングのあいだの空間に、批評的に住もうとする人。エージェント的な開発能力をデザイナーとして使いこなしていくにあたって、自分のためのガードレールとして作った、と説明されています。

宣言0は「コードを設計の材料と考え、直接それを扱う」。ここから始まるのが特徴的です。宣言1は「自分の代わりに生成するあらゆるツールを、能力であると同時に脅威であると考える。生成されたコードへの依存が大きいほど、その働きを読み、問い、露出させる必要も大きくなる」。宣言2はもう一段踏み込んで、「コードとの近さは透明性ではない。ソースそれ自体が一つの表現であって、近いことを理解と取り違えてはならない」と言います。Wendy Hui Kyong Chun の「sourcery」（ソースコードが透明性と取り違えられること）が下敷きです。

個人的にいちばん効くと思ったのは宣言3と5でした。3は「シームレスさではなくシーム（継ぎ目）を設計する。ユーザーが理解し、設定し、異議を唱えられるように」。影響元として Weiser の「美しいシーム」、Chalmers の seamful design と並んで、Krug の『Don't Make Me Think』が「押し返す対象としてのシームレス体験の正統」として挙げられているのが率直です。5は「コードは何が決まったかを記録するが、なぜかは記録しない。だから、なぜをリポジトリに書き込む」。Nygard の Architecture Decision Record と、Lisanne Bainbridge の「Ironies of Automation」（作ることが自動化されるほど判断の重みが増すという逆説）が並べられています。

後半の3つは責任の話です。宣言9は「意図だけでなく帰結の著者性を引き受ける。プッシュすることは署名することだ」。Langdon Winner の「Do Artifacts Have Politics?」と Lessig の『Code』が下敷きになっています。宣言10は「マージを、もっとも望ましく、もっとも危険な露出の形式と考える」。宣言8は、批評的デザイン・スペキュラティブデザイン・アドバーサリアルデザインの戦略をギャラリーからリポジトリへ持ち出す、というもので、批評が実際の利用との接触を生き延びなければならない場所として repository が置かれています。

UXエンジニアリングの視点で気に入ったのは、宣言そのものよりも、その置き場所かもしれません。本文は GNU Free Documentation License のもと公開 Gist にあり、コミット履歴と著者の署名を持ち、フォークへの誘いがついています。宣言5が「なぜをリポジトリに書け」と言っているものを、宣言自体がそのやり方で公開されている。影響レジスターとして、どの思想がどの宣言に効いたかが1行ずつ明記されているのも、主張と根拠を分けて置く実践になっています。エージェントに任せる範囲が広がるほど、自分たちが何を手放さないかを言語化しておく価値は上がっていくので、そのまま真似せずとも、自分のチーム版を書き出す出発点として読めます。

### [You have to beat the models at something](https://www.seangoedecke.com/you-have-to-beat-the-models-at-something/)

> **出典**: Sidebar | **公開日**: 2026-09-01 | **カテゴリ**: design

**3行まとめ**
- 「置き換えられる人との差分（value over replacement）」で自分を測るなら、いまその差分は何か、を正面から考えた記事です
- モデルが時間をかけても伸びていない領域として、コードベースへの深い馴染みと、技術的な文章によるコミュニケーションの2つを挙げます
- モデルの間違いは「無知」と「過剰な用心」に集約され、それを捕まえるには自信を持って異を唱える度胸が要る、という話でした

**詳細解説**

Sean Goedecke さんは2025年に「エンジニアは会社にいくら稼がせたかではなく、同じ役職の平均的なエンジニアと比べてどれだけ多く稼がせたかで評価されるべきだ」と書きました。今回はその続きです。2010年代なら、置き換え水準のエンジニアでも十分に給料を払う価値がありました。コードを書くこと自体に高い固定費がかかっていたからです。いまその固定費は月100ドル程度になった。あなたの立場で、モデルがやらないことを何をしているのか。2桁も3桁も多く払う理由は何か、という問いから始まります。

まず釘を刺されるのが、逃げ道の潰し方です。LLMは実はコードを書けないとか、生成されたコードは本質的にひどいので使っている会社は来年潰れるとか、そういう話に逃げても自分のためにはならない。2027年に目覚めたらAI狂騒が終わっていて全員が手でコードを書いている、ということにはならない、と。そして、深い専門性を要する「硬い」領域に退避する作戦にも懐疑的です。2026年初頭には「大きなコードベースに動く変更を入れる」がその領域に入っていたのに、いまはもう入っていない。的が動き続けるからです。

### [How we make AI coding more cost efficient without sacrificing task quality](https://github.blog/ai-and-ml/github-copilot/how-we-make-ai-coding-more-cost-efficient-without-sacrificing-task-quality/)

> **出典**: GitHub Engineering | **公開日**: 2026-09-02 | **カテゴリ**: engineering

**3行まとめ**
- ツール呼び出し1回のトークンではなく、完了したタスク全体で効率を測る、という原則を4つの実例で示した記事です
- 出力を短くする既製ツールを評価したら、欠けた情報を取り戻すためにターンが増えてタスク全体では高くついた、という失敗から始まります

**詳細解説**

出力の質は大事だけれど、本当の効率は「速く、無駄なく、適切な文脈で」仕事が終わることから来る。だからツール呼び出し単体のトークン数は意味のある指標ではない、という前提から始まります。簡潔なツール応答が、エージェントの必要とする情報を落としていたら、追加の呼び出しや作業を招いて、結果としてタスクは遅く高くなる。最適化するのはツール呼び出しではなく結果のほうだ、という原則です。

その具体例が RTK（Rust Token Killer）の評価でした。エージェントが読む前にシェル出力を短くするユーティリティです。GitHub のハーネスとベンチマーク構成で試したところ、たしかにいくつかの応答は短くなったのですが、省かれたテキストが重要だったとき、モデルは元の出力を開き直したりコマンドを再実行したりして取り戻そうとしました。その回復のぶんターンが増え、文脈が持ち越され、平均するとタスクはトークンも時間も増えた。局所的に節約して、全体で余計に払った、という結果です。

そこから出てきたのが、選択的な出力圧縮でした。ベンチマークの分析から、install・build・test・lint の出力は繰り返しのノイズが多く、ソースらしい出力や任意のコマンド結果はエージェントが必要とする情報を含みやすい、とわかった。初期版は攻めすぎて、モデルに作業を繰り返させたり保存済みの全文を読ませたりして、かえって高くなり成功率も下がりました。たとえば最初は `git diff` を圧縮していたのですが、エージェントが元の出力を開き直すのを見てその対象から外しています。結果として3部構成の方針に落ち着きました。ソースらしい出力と任意の出力はそのまま返す、検索結果は内容を落とさずまとめ方だけ変える、繰り返しのノイズは節約が大きいときだけ圧縮する。しかも圧縮したときは元の全文への復旧経路を残し、その経路が使われた頻度を評価の信号として追跡しています。

いちばんきれいな変更として紹介されているのが `view` ツールの話です。ファイル内容をモデルに見せるとき、各行に行番号を付けていました。かつてのファイル編集ツールはその番号で変更箇所を指定していたのですが、いまのツールは周囲のコードと照合するので番号を使っていません。使われないまま残っていた書式が、すべての行、すべてのファイル読み込みで積み上がっていた。消したところ、オフラインのベンチマークで推論コストが約5%下がり、成功率は実行ごとのばらつきの範囲に収まり、編集の失敗も増えませんでした。CLIの利用者で試したオンライン実験では、1人あたりの1日の推論コストが約3%下がっています。モデルへの新しい指示もなく、取り戻す必要のある情報もなく、判断も増えない。ファイルの中身は変わらずモデルに届く、という点で理想的な変更でした。

プロンプト圧縮の節には、そのまま教訓として使える失敗が書かれています。並列作業のために専門エージェントを起動する task ツールのガイダンスが、ツール説明・スキーマ・エージェント定義・システム指示・関連ツールに散らばって膨らんでいた。Copilot に自分自身のプロンプトを反復的に書かせるループで、およそ半分に縮めました。ところが最初のオンライン実験で、オフライン評価が見逃していた退行が見つかります。そのループが、慎重な並列化のガイダンスを固い スケジューリング方針に書き換えてしまい、独立したカスタムエージェントが直列に走るようになっていた。実験を止め、プロンプトを触る前に、利用者が露呈させたその振る舞いに対する退行テストを書いた。最終的な修正は、明示的な許可リストと禁止リストを1文に置き換えるものでした。「独立したエージェントは並列に実行できる。副作用は考慮すること」。短く、制約も緩く、並列にするかどうかの判断をモデルに委ねる形です。プロンプトの振る舞いにはテストが要る。テストされていない振る舞いは、短いプロンプトが誰にも気づかれずに消してしまう、という一文が結論でした。

UXエンジニアリングの視点で持ち帰れるのは、最後の5つの教訓のうち3つ目と5つ目でしょう。「出力が何を表しているかで圧縮を決める。正確な内容は保ち、可逆な変換を優先し、復旧経路がどれだけ使われたかを測る」。そして「証拠はワークロードに固有である」。実際、コードレビューで良い結果を出したファイルツールの指示の締め直しを CLI で試したらコストが増えたので出荷していない、という例まで挙げられています。どの変更も、それが動く流れのなかで測る。モデルを賢くした変更はひとつもなく、モデルがそもそもやる必要のなかった仕事を取り除いただけだ、という締め方でした。

### [An Organizational Second Brain: Building an AI That Learns From Experts](https://engineering.fb.com/2026/09/02/ml-applications/organizational-second-brain-ai-learns-from-experts/)

> **出典**: Meta Engineering | **公開日**: 2026-09-02 | **カテゴリ**: engineering

**3行まとめ**
- 専門家の頭のなかにある知識を構造化されたファイル群に外出しし、その保守を「コンパイル問題」として自動化した設計の話です
- 知っていること（宣言的な知識ファイル）と、どう推論するか（手続き的なレシピ）を分けることで、失敗の原因をどちらか一方に帰属できます
- 専門家の指摘を、診断・コンパイル・検証・レビューの4段階で最小の差分に変え、通ったものは退行テストに組み込んで恒久化します

**詳細解説**

大きな組織の専門知識には共通の問題があります。一部はモデルやプレイブックやチェックリストとして書かれているけれど、いちばん価値のある部分は人の頭のなかにあり、耐久性のある形ではどこにも残らない。コンプライアンス領域なら、同じ種類の質問が何百もの製品レビューで繰り返され、専門家の判断には何日もの調査が要り、判断のばらつきそのものが組織のリスクになる。専門家が、判断が本当に要る新しく曖昧な仕事よりも、定型的な質問への回答に時間を使ってしまうことも珍しくない、という現状認識から始まります。

知識の置き方が独特です。大量のドキュメントを組織の知識と見なしたくなるけれど、本当の知識は暗黙的で、専門家がどう推論し、何を優先し、曖昧さをどう解消するかにある。推論時にドキュメントの断片を取ってくるだけのエージェントは、その推論を毎回ゼロから導き直すことになる。そこで、長時間走るオフライン処理でソース文書を推論し、構造化された知識ファイルに蒸留しておきます。200以上のファイルが厳密な分類で整理されていて、組織としての立場を記録する position ファイル、用語の唯一の出典となる taxonomy と vocabulary、入力の特徴からどのファイルが効くかを決める routing index、そして専門領域に入る前に通す必要のある閾値テストを定義する gateway ファイル、という構成です。すべてのファイルが YAML frontmatter に依存先（depends_on）と被参照（referenced_by）を書き、双方向の依存グラフを作ります。

wiki と RAG の分け方も明快でした。情報密度が高く頻繁に参照されるもの（立場、意思決定の枠組み、境界事例、戦略的な解釈）は wiki に置く。エージェントはほぼ毎ターンこれを参照するし、組織の考えが変わるものなので、更新しやすく版管理でき検証できる形にしておく必要がある。まばらで状況依存のもの（詳細な参考資料、個別の製品仕様、過去の意思決定記録、ニッチな外部知識）は検索で出す。全部を wiki に入れると肥大化して注意が薄まるから、という理屈です。

そして「知っていること」と「どう推論するか」を分けます。知識ファイルは宣言的で、レシピは命令的。レシピは知識ファイルを参照するけれどドメインの事実は含まず、知識ファイルは立場を述べるけれど手順は規定しない。この分離があると、立場を追加するのは知識ファイルの追加と routing index の更新だけで済み、手法の欠陥を直すのはレシピの編集だけで済む。そして失敗がどちらか一方にきれいに帰属します。初期版は1枚の平たい指示ファイルとセマンティック検索で、毎回いろいろな関連度のファイルをコンテキストに引き込んでいましたが、レシピ駆動の段階に再構成したところ1ターンあたりのトークンが約80%減ったそうです。

自己改善のループがこの記事のいちばんおもしろいところでした。専門家の指摘を精密なファイル編集に翻訳する作業は、依存グラフ全体を理解し、他が壊れないことを確認し、修正が効くことを検証する必要があるので、何週間もかかる。それをコンパイル問題として自動化します。診断の段では、最初のやり方（会話の形で分類する。情報を提供したら知識の欠落、方向を修正したら手順の問題）が失敗しました。会話の形は根本原因の代理としては貧弱だからです。うまくいったやり方は、抽出と分類を分けたうえで、実際の知識ファイルを読んで1つの帰属テストを当てるものでした。エージェントは手元の材料から正しい結論に到達できたか。到達できたはずなのに誤ったならレシピの問題、材料に答えがなかったなら知識の欠落、専門家同士で答えが割れるなら曖昧さとして人間の議論に上げる。

検証の設計も参考になります。提案された差分だけを、改善の理由を何も知らない新しい文脈のエージェントに渡して、矛盾や壊れた境界事例を探させる敵対的レビュー。文脈を共有していないので盲点を引き継げない、という理屈です。加えて、宙ぶらりんの相互参照、ファイルサイズ超過、識別子の衝突、依存の循環を機械的に落とす lint。そして、指摘のきっかけになった元のシナリオでエージェントを走らせる再生テストでは、エージェントはテストされていることを知らず、判定役は何が変わったかを知らない。この盲検の設計は確証バイアスを避けるためです。通ったものはプルリクエストとして人間の専門家に渡り、承認されると、元の失敗シナリオと正解が自動的に退行テストに追加されます。

### [Breaking the Frame: Building a Real-Time Datamosh Effect with Three.js](https://tympanus.net/codrops/2026/09/02/breaking-the-frame-building-a-real-time-datamosh-effect-with-three-js/)

> **出典**: Codrops | **公開日**: 2026-09-02 | **カテゴリ**: design

**3行まとめ**
- 映像コーデックのキーフレーム更新をわざと抑える「データモッシュ」を、フラグメントシェーダーでリアルタイムに再現した解説です
- 実装は `new frame = warp(previous frame, motion vectors) + residual` の一行に集約され、そこから各段が積み上がります
- 補正（residual）をあえて不完全にしておかないと、ずれが打ち消されて効果そのものが消えてしまう、という設計の勘所が説明されています

**詳細解説**

映像コーデックは、周期的に「前のピクチャを参照せずに再構成できる」イントラピクチャを符号化します。そのあいだのピクチャは、すでに再構成された参照ピクチャから予測される。連続するピクチャは似ていることが多いので、予測は大量のデータを節約できます。シーンの切り替わりでイントラ更新を抑えると、デコーダーは出ていくショットに属する参照から再構成を続けながら、入ってくるショット向けのデータを処理してしまう。古いシーンのピクセルが引きずり回され、後の更新でようやくきれいな画に戻る。映像作家は昔からこの仕掛けを実ファイルに対して使ってきましたが、この記事はフラグメントシェーダーを Three.js シーンのデコーダーに見立てて、リアルタイムでやります。

最小構成はフィードバックループです。ポストプロセスのパスは普通、レンダラーが今描いた画をサンプリングしますが、このパスは自分の前回の出力をオフセットつきでサンプリングし、新しいレンダリングを少しだけ混ぜます。ここで WebGL の制約が1つ効いてきます。いま描き込んでいるフレームバッファに紐づいたテクスチャはサンプリングできないので、履歴バッファを1つその場で更新するのは無理。だからバッファを2つ持ち、片方から読んでもう片方に書き、毎フレーム末尾で入れ替えます。

定数ベクトルではすべてのピクセルに同じ変位が当たるので人工的に見えます。そこで、可視ジオメトリがスクリーン空間でどう動いたかをレンダラーから導き出す velocity パスを追加します。各頂点を現在のモデル行列とカメラ行列で1回、1フレーム前に保存しておいた行列でもう1回投影し、その差を変位に使う。ここで間違えやすい細部が明示されています。両方のクリップ座標は割り算せずにフラグメントシェーダーまで届ける必要があり、透視除算はフラグメントごとに行う。頂点シェーダーでやるほうが安くて等価に見えるのに、正しくない値が出る。スクリーン位置は比であって、比を補間することと、補間された2つの量を割ることは違うからだ、という説明です。

ここまでは手の込んだモーションブラーで、データモッシュに変えるのは4行ほどのスケジューリングでした。ポインタ、スペースキー、タッチで新しいジオメトリ・パレット・カメラのショットに切り替わる。デコーダーには何も通知されないので、出ていくショットの最後の出力を読みながら、入ってくるショットから測った動きベクトルを当ててしまう。順序が重要で、切り替えを `composer.render` の後に置くことで意図的に1フレーム遅らせる。そして切り替え直後に前フレームの状態を取り直すことで、カメラの飛びそのものが動きベクトルに混ざらないようにします。

いちばん設計的におもしろいのが residual の扱いです。本物のエンコーダーは、再構成された参照から作った動き補償つきの予測に対して残差を計算します。もしここで、現在のレンダリングと「わざと間違えた予測」の完全な差分を使ってしまうと、残差がずれを打ち消してデータモッシュを修復してしまう。だから補正は意図的に不完全でなければならない。この実装では、入ってくるレンダリングの高周波成分と、前フレームをワープして作った予測にすでにある高周波成分を比べ、入ってくる側のほうが強い部分だけを送ります。予測が十分強いエッジを持った時点で残差はゼロに落ちるので、同じ輪郭がフィードバックループに二度足されない。残差は色を持たない輝度に近い信号にしてあり、RGB の残差だと新しいショットのパレットが古い画に乗って半透明に見えてしまうから、という理由まで書かれています。

仕上げの「圧縮っぽさ」も分解されています。ブロック（8pxのタイル中心で1つのベクトルを読んで全体に当てる）、精度（サブピクセルの格子にスナップさせ、滑りを段差に変える）、スキップ（閾値以下の動きをゼロにして履歴サンプルを止める）、そして間違ったベクトル（一部のブロック中心を斜めにずらして隣のベクトルを読ませ、ブロックマッチングが違う対象に食いつくのを真似る）。さらに、複数の粗さのグリッドを重ね、セルごとにハッシュで位相をずらした時計を回して矩形を凍らせるパケットロス風のマスクが載ります。著者は「これらの定数はどれも導出したものではない。ブロックサイズも閾値もミスマッチ率も、壊れたファイルらしく見えるまでスライダーを動かして決めた」と正直に書いていて、そこも好印象でした。UXエンジニアリングの観点では、「壊れて見える」を成立させるには、まずコーデックの仕組みを正しく再現してから、その一部だけを意図的に外す、という順序そのものが持ち帰れる作法だと思います。

Long Animation Frames（LoAF）はこれまで、長く走るスクリプトとそれに続く描画の仕事を組み合わせて、メインスレッドの詰まった瞬間を説明するのに役立ってきました。Worker には自分の描画フレームがないので名前としては少し奇妙になりますが、実用上は有用です。専用 Worker のイベントループを塞ぐ長いタスクが `long-animation-frame` のエントリを生み、その Worker のなかから `PerformanceObserver` で観測でき、いつものスクリプト単位の帰属情報も持つ。

なぜこれが効くのか、という説明が的確でした。仕事をメインスレッドから外せば描画や入力処理からは遠ざかりますが、仕事が無料になるわけではない。データのデコード、大きなカタログの絞り込み、画像処理、クライアント側のモデル実行に時間をかけすぎる Worker は、インターフェイスが待っている結果を遅らせられる。メインスレッドの INP はまったく問題なさそうに見えるのに、有用な答えが別の場所でまだ並んでいるせいで製品は遅く感じる。Worker 側の LoAF は、その欠けていた区間に対するブラウザ由来の信号を RUM の設計に与えてくれる、というわけです。

ただ、最初の実装は意図的に狭い、と釘が刺されます。専用 Worker から始まり、Worker のイベントループを塞ぐ1つの長いタスクを報告するだけ。小さなタスクの洪水による混雑を特定するという Chrome の広い構想は今後の作業です。ページ側のオブザーバーが Worker のエントリを拾ってくれることもないので、オブザーバーは Worker のなかで走らせ、アプリ側でその証拠をユーザーの操作や完了させたかったタスクに結びつける必要がある。実践的な手順として、すでに遅延を体験しているWorker経由の経路を1つ選び、Worker のなかで対応を機能検出し、スクリプトの帰属と継続時間を保持し、メインスレッドが結果を起点の操作に結びつけられるようにアプリケーションのマークやタスクIDを添える。Early Stable は母集団が小さくこの信号は当面 Chrome だけなので、ブラウザのバージョンと計測の版も一緒に残しておく、と。

エントリを全部集めるのは洞察よりずっと多いデータを生むだけなので、最悪のケースをサンプリングし、製品の操作に見合った閾値を設け、原因を決めつける前にトレースと突き合わせる。目指すのは、忙しい線がたまたま Worker のものだった新しいグラフではなく、非同期の道のりが実際にどこで待ったのかが見える状態だ、という締め方でした。

そのほかでは、Chrome 153 が Related Website Sets と `document.requestStorageAccessFor()` を削除し、Attribution Reporting API もほかの Privacy Sandbox API と一緒に消えます。サードパーティクッキーの方針を維持したからといって、クッキーレスなブラウザ向けに設計されたAPIがすべて残ったわけではない、という指摘です。埋め込みサインインやクロスサイトの導線、コンバージョン計測にこれらを使っているなら、本番の利用状況を棚卸しして、ブラウザがそれなしで何をするか試す時期になります。Firefox 155 では、モジュールの読み込み失敗が恒久的な失敗としてキャッシュされなくなり、ネットワークエラーや誤った MIME タイプが直れば同じ指定子の再インポートが成功するようになりました。失敗のテストは、応答を戻し、インポートを再試行し、リロードなしでUIとテレメトリが回復することまで確認する経路全体で見る、という助言が添えられています。

### [Evaluating a Success Criterion](https://adrianroselli.com/2026/09/evaluating-a-success-criterion.html)

> **出典**: Adrian Roselli | **公開日**: 2026-09-01 | **カテゴリ**: accessibility

**3行まとめ**
- WCAG の達成基準をどう解釈するか、W3C のいまの立場にたどり着くための7段階の手順です
- 規範テキストから始めて、Understanding、Techniques、GitHub の issue・PR・discussion、信頼できる個人ブログの順に降りていきます
- どの結論が出ても必ず自分でテストする。W3C の答えに従うと体験が悪化する場合もある、という前提が置かれています

**詳細解説**

WCAG の評価（レビューでも監査でも）をしていると、ある達成基準の意図と文言のあいだで迷うことがよくあります。とくに、いま突いているインターフェイスのパターンが考案される前に書かれた基準ではなおさらです。自分たちのローカルな参照を作り上げるまで、そして作ったあとも、解釈しようのないものを解釈するための計画を持っておくといい、という前置きから始まる、短いけれど密度の高い記事です。

手順は7段階です。まず WCAG 仕様の規範テキスト（公式な要件）を読む。つねに最新版を見る。そして、w3.org のサイトにいることを確かめる。wcag.info のような紛らわしいサイトや、仕様の名前を借りた企業所有のドメイン（wcag.com など）ではなく、という注意が最初に来るのが実務的でした。次に、その基準の Understanding 文書（補足資料）を読む。そこからリンクされていることが多いのが Techniques 文書で、既知の失敗例と、合格する方法・追加で望ましい方法が集まっています。ただし古いものや、置き換えられた技術・期待どおりに動かなかった技術を指しているものもあるので慎重に。1つの Techniques 文書が複数の基準に効くこともあります。

ここから先が、この記事の値打ちのある部分です。4段目は WCAG の GitHub issue を見る。日付、リンクされた issue と PR、埋め込まれた議事録、決定に注意を払う。そして閉じた issue を探す。決着済みの答えであることが多いからです（スパムボットのものは除く）。5段目はプルリクエスト。マージされなかったものであっても見る。むしろ、マージされなかった PR にこそ良い議論があることが多い、と。6段目は数少ない discussions で、自分の疑問に合う未回答のものを見つけたらコメントしてみてもいい、という誘いつきです。

7段目が個人ブログですが、ここにもいちばん長い注意書きがついています。信頼できる専門家、しばしば仕様そのものに関わっていて自分の洞察を書いてくれる人のブログを見る。ただし、何かの立場を推していたり、根拠を示さずに解釈を主張したりするブログには慎重に。これは、抜け穴やすき間を使って基準を最低限だけ通す正当化をしている人にも当てはまる、として、敵対的・悪意ある適合についての自身の記事群が挙げられています。

そして結び。どんな結論にたどり着いても、とにかくすべてテストする。新しいリリースは絶えず出るし、退行はよくあるし、新しいサポートも生まれるし、ユーザーの期待も動く。さらに、W3C が示す失敗条件への答えに従って直したら、かえって体験が悪くなることもありうる。そのときは、ここまで調べたすべての内容が、W3C の立場から離れる判断を正当化しやすくしてくれる、という締め方でした。

UXエンジニアリングの視点では、これはアクセシビリティの記事であると同時に、仕様の読み方そのものの記事として読めます。二次情報から入らず一次ソースを積み上げる。決着は「閉じた issue」と「マージされなかった PR」にある。そして、権威の答えが手元の状況で最良とは限らないので、離れるときのために根拠を積んでおく。この型は WCAG に限らず、ブラウザの仕様やフレームワークのAPIの解釈でもそのまま使えます。

### [Compression is prediction](https://ngrok.com/blog/compression-is-prediction)

> **出典**: Sidebar | **公開日**: 2026-09-02 | **カテゴリ**: design

**3行まとめ**
- 圧縮器と大規模言語モデルは、根っこでまったく同じ問題を解いている、という話をゼロから積み上げた解説です
- エントロピーコーダーは決定的で調整の余地がなく、圧縮率を上げたいなら予測器（モデル）を良くするしかありません
- LLMは最高の予測器だけれど、モデル本体を配る費用と計算量のせいで、実際の圧縮には割に合わない、と現実的に締めています

**詳細解説**

圧縮について読んでいて、圧縮器とLLMが根っこでまったく同じ問題を解いていることに気づいた、という書き出しから始まります。まず、なぜミニフィケーションがデータ圧縮の分野でほぼ語られないのかを説明するところが親切でした。ミニフィケーションは機械が要らない構文を捨てているだけで、「本物の」圧縮は冗長性に依拠しているからです。9個のA、4個のB…という文字列を A9B4C2D1A3D9 に置き換えるランレングス符号化が、いちばん素朴な例として置かれます。

現代の圧縮ツールには、変換（transforms）・モデル・エントロピーコーダーという3つの器官があります。変換は前処理で、必ずしも縮めるわけではなく、あとで縮めやすいように冗長性を増やすこともある。モデルは各シンボルの頻度からデータの形を記述するもので、いまはシンボルと確率の対応表だと思っておけばいい。エントロピーコーダーは最後の段で、圧縮された生のビットストリームを吐く。確率が入って、圧縮されたビット列が出てくる。

ここから算術符号化の説明に入ります。データセット全体を1つの数で表せる、という約束です。A B A B A A C という文字列の各シンボルの確率を0から1の範囲に並べ、シンボルごとにその区画のなかへ範囲を狭めていく。同じ確率で分割し続けるので、範囲はどんどん小さくなり、最後に残った極小の範囲に入る任意の数、それもいちばん少ないビットで書ける数を選ぶ。8ビットASCIIで56ビット必要だった文字列が10ビットになります。この最終的な数は浮動小数点ではなく2進小数で、浮動小数点なら必要でも不要でも32ビットか64ビット払うところを、10ビットで済む、という補足も気が利いています。

そして確率の偏りが効くことが示されます。Aが支配的な文字列にすると、1シンボルあたり1.38ビットだったものが0.82ビットになる。この平均ビット数がエントロピー（シャノンエントロピー）で、圧縮の土台です。動物あてクイズの決定木で、ありそうな動物ほど少ない質問で当たり、yes/no を 1/0 に置き換えると質問回数がそのままビット数になる、という説明はハフマン符号の導入も兼ねています。確率がきれいに半分ずつでないときは丸めが必要になり、要らないビットを払うことになる。その最小値は -log2(p) で計算できる。エントロピーはこの床であって、これ以上は縮まない。

ここが転回点です。それなら1つの万能圧縮器を全部に使えばいいはずなのに、そうならないのは、エントロピーが特定の確率分布に固有だからでした。分布をもっと偏らせられれば、もっと縮む。そのやり方が文脈です。英語全体で U の確率は約0.028ですが、Q の直後なら約0.999になる。ビットに直すと約5.158ビットが約0.001ビットになります。直前の1文字を文脈にするのが order-1 モデルで、"TO BE OR NOT TO BE" は文脈なしの47ビットから order-1 の21ビットへ半分以下になりました。文脈を足すと予測が良くなる。ところで、予測が本当に得意なものが他にありますよね、という運びです。

LLM を圧縮に使うのは、テキスト生成とほとんど同じで、違うのは次の語を選ばないことだけです。新しいテキストを作りたいのではなく、次に来る語はもう分かっている。モデルが実際の次のシンボルに割り当てた確率が、そのままビット単位の費用を決める。訓練の足りないモデルは、文脈が「The rain in」のときに Bermuda に0.82を与え、実際の Spain には0.02しか与えなければ、-log2(0.02) で5.64ビット払う羽目になる。ディケンズの一節を、order-1 モデルが434ビット（元の24%）に縮めるのに対し、GPT-2 なら176ビット（10%）まで縮む、という比較も載っています。

では、なぜ実用にならないのか。圧縮ツールの目標は、ただ縮めることではなく、一定の資源制約のもとで縮めることだからです。HTTP のレスポンスなら、ブラウザは gzip の小さな内蔵モデルでデコードしていて、オーバーヘッドはごくわずか。LLM でやるとブラウザとサーバーの双方に数ギガバイトのモデルが必要になり、実行前からすでに割が合わない。すべてのスタイルシート、すべてのスクリプト、すべての JSON ペイロードのために LLM を回す絵を想像すればわかります。結びも簡潔でした。エントロピーまで縮めることは1970年代後半の算術符号化ですでに解決済みで、いまのエントロピーコーダーは比率ではなく速度とメモリで競っている。開いているのは「エントロピーをどこまで小さくできるか」という問いのほうで、それは予測器を良くする話であり、LLM が最小化しようとしている交差エントロピーは同じ式だ、と。UXエンジニアリングの現場でプロンプトやコンテキストの設計をしている人にとって、「文脈を増やすと予測が良くなる」という直感の数学的な裏側を見ておくのは、それなりに効く読書だと思います。

### [Creepy crawlies](https://people.kernel.org/monsieuricon/creepy-crawlies)

> **出典**: Sidebar | **公開日**: 2026-09-02 | **カテゴリ**: design

**3行まとめ**
- git.kernel.org が AI クローラーに受けている負荷を、実測値つきで報告した記事です
- 5拠点90コアのうち14〜16コアが、つねにスクレイパー向けにコミットをHTMLへ描画するためだけに回っています
- git clone すれば全部手に入るのに、1コミットずつHTMLを取りに来る。正当なリクエストは全体の約2%と見積もられています

**詳細解説**

Linux の開発は公開の場で行われます。クローンできる git リポジトリから、リアルタイムで追える議論のアーカイブまで。大規模言語モデルにとってこれは学習データの金鉱です。すぐ手に入るだけでなく、AI以前のコンテンツだけを確実に選り分けられるから。LLMが作ったものでLLMを訓練するのはデジタル版のプリオン病にあたるので、カーネルのコミット履歴のようにLLM由来でないと保証できる出典は、重さのぶんだけ金の値打ちがある、という説明から始まります。

だから、いちばん効率のいい取り方をするだろうと思うわけです。リポジトリをクローンして全コミットを歩けば終わり。ところが実際には、いちばん愚かなやり方が選ばれている。1コミットずつHTMLとして描画させ、それをパースしているのです。linux.git は執筆時点で約148万コミットあり、git.kernel.org にはそのフォークが約922個ある。バックエンドではほとんど同じオブジェクトなので極めて効率的なのですが、スクレイパーにとっては数十億の有効なURLがあり、そこから同じ148万コミットの922個の重複を得ている。しかもコミットだけでなく、パッチも、プレーンな描画も、任意のコミット間の差分も要求できる。cgit は喜んで返します。インターネットが人間と robots.txt に従うクローラーのためのものだった時代には完璧でしたが、いまは最悪です。

対処の変遷が生々しいところです。最初はログを見て明らかなボットのIPを fail2ban に入れるだけで済みました。ボットが user-agent で親切に名乗っていたからです。それが普通のブラウザのふりを始めたので、IPで遮断するようになる。8年放置されたフォークの全コミットを取りに来ているIPが、画面に出るリンクを片端からクリックしている Windows の Chrome ユーザーではないと判断するのは簡単だからです。ボットがサブネット全体に散り始めても、Google Compute から来る Firefox 名乗りは偽装だと分かるので、ASN ごと遮断するのは正当でした。

本当にひどくなったのはその次でした。数百万のランダムな住宅用IPやモバイルIPから、それぞれが最新のブラウザを名乗って来るようになる。そういうIPは4〜5リクエストして二度とログに現れない。ボットだと判別できたときにはもう終わっているので、遮断しても意味がなく、二度と来ないIPでファイアウォールの規則を膨らませるだけです。イナゴの群れのように降りてきて、システムが倒れるまで速く強く叩き、次の標的へ移り、また戻ってくる。この背景にあるのが「プロキシSDKの収益化」という大きなビジネスで、あなたのテレビもたぶんそれをやっている、と書かれています。

経済を逆さにする試みもありました。ボットに使い捨ての計算をさせる Anubis を全面に置く。自分のIPと提供された秘密を組み合わせて、先頭に0が4つ並ぶ sha256 を作る文字列を探させる、という類のものです。効果はすぐに現れ、ボットは諦めました。数か月の平穏のあと、難易度4を解いて戻ってくる。難易度を5に上げる。正当な利用者はより苛立ちます。モバイル端末で数秒かかり、端末が不快なほど熱くなる。それでもさらに数か月の平穏を買えました。そして、ボットは難易度5も解き始めます。

いまの数字が締めです。git.kernel.org は1日約600万件のランダムなコミット要求を受け、そのうち66%は Anubis の課題で即座に払われ、33%は計算を解いて本体まで届いている。差し出しているものが、それだけの計算資源を使う価値があると判断されているわけです。寛大な仮定を重ねても、正当なリクエストはトラフィックの約2%。90コアのうち14〜16コアが、つねにスクレイパー向けのコミット描画だけをしている。平均で全容量の20%ですが、波で来るので実際のグラフはもっと尖っています。ちなみに、実際にサービスを落とすのはスクレイパーではなく、20ノードから同時に stable.git を shallow clone しようとするような雑に設計されたCIのほうだ、という一言も添えられていました。

対応として、クロール可能なURLの数を減らすために機能を切り、実行費用の高い操作を閉じていく。匿名でのアクセスでは機能が減ることを覚悟してほしい、私たちも同じくらい嫌なのだが必要なのだ、と。UXエンジニアリングの視点では、公開データを保ち続けることと、利用者の体験を守るために機能を削ることのトレードオフが、ここまで具体的な数字で語られている例はなかなかありません。それでも「求める人には全データのダウンロードを提供し続けると約束する。ただ、通す輪が増えるかもしれない」と結ばれているのが、この文書のいちばん良いところだと思います。
