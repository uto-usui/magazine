### [The making of Cursor's icons](https://www.minoradventures.co/blog/the-making-of-cursors-icons)

> **出典**: Sidebar | **公開日**: 2026-08-17 | **カテゴリ**: design

**3行まとめ**
- Cursor の 600 以上のアイコンを1年かけて手で描き直した記録。16px と 24px の2サイズ、Outline と Filled の2スタイル
- 1.25px というストローク幅、光学的な図形4種、接合部に入れるノッチや線の細り——数値は目が先に下した判断の記録として残る
- 645 のコードポイントを1つも壊さずにフォントを差し替える移行と、`ship it` 一発で公開まで通すパイプラインまで含めての納品

**詳細解説**

Marek Minor（Minor Adventures）による制作記です。出発点は、VS Code のエコシステムから継承した Codicons が Cursor の現在に合わなくなっていたこと。数えると 468 個で、ドキュメントには 498 と書かれ、行き先のないコードポイントもある。「誰も所有していないセットはずれていく」と書かれていて、継承したアイコンセットの典型として読めます。

ただ、より大きな問題は概念のカバー範囲でした。AIエージェント、並列実行と逐次実行、単一スレッドと並列スレッド、思考の深さの段階、コストと計算量、Bugbot。どの汎用アイコンライブラリにも揃っていない語彙です。汎用セットはある程度まで引き伸ばせるけれど、いつかプロダクトは自分の語彙を必要とする、という整理でした。

技術的な判断の部分がおもしろいところです。1px では文字の隣で細すぎ、1.5px では重すぎ、1.25px で 16px の Cursor Gothic と並んで釣り合う。ピクセルグリッドにスナップしない選択も意図的で、12px・14px・16px・20px でレンダリングされるならスナップ先の単一のグリッドは存在しないからです。アイコンをビットマップではなく、小さなロゴや書体の字のような記号として扱う、と説明されています。24px は別のグリッドに 1.5px で描き直す。書体の Text と Display の光学サイズと同じ考え方です。

構築のロジックも一貫していました。水平・垂直・45度の線から始め、概念が要求するときだけ他の角度を許し、形が意図に沿うまで角を丸める。雲は円からではなく直線の連結に丸い接合を与えて作る。円由来の自由曲線はほとんど登場しません。ポインタが左下から右上へ走るので、どちらでもありうるアイコンはすべてその向きに揃え、スラッシュだけは逆に走らせて方向を打ち消す。「画面からこれを読み取る人はいません。でもこういうルールがないと、セットは一箇所から来たものに見えなくなります」という一文が効いています。

光学的な補正の節は、この記事のいちばん濃い部分でした。線が交わる接合部は形が積み上がって暗く見えるので小さなノッチを切る、線が集まりすぎる場所では一部の線を細くする、行末のドットと「もっとある」のドットと単独で浮くドットはそれぞれ違うサイズが要る、重なる形の隙間は 16px グリッドで3単位を下回らせない。16px で見えるのかという問いには、インターフェースはズームするし 24px は大きいサイズで生きる、そして10ptのインクトラップと同じく「気づきの手前の層で効く」と答えています。ハンバーガーアイコン1つに 156 通りの探索を並べた画像が添えられていました。

後半は運用の話です。Figma ファイルを3つ持つ——数百の試行を置く Explorations、光学図形・隙間・修飾記号・ドットとノッチ・遠近と斜線・繰り返し登場する物体（155 以上の要素）を突き合わせる Overviews、最終形をコンポーネントとして持つ Icons。Overviews のプロトタイプはスマートフォンにミラーリングして確認します。16px が実際に 16px として見える場所で、描いたファイルの外から見る必要があるという理由でした。差し替えは、旧フォントの 645 個をすべて同じコードポイントの後継へ再マッピングし、後継のないものは意図して退役させる方針。そのために移行用ダッシュボードを自作し、SVG の欠落と重複コードポイントを警告させています。

UXエンジニアリングの視点では、納品物の定義が広いところが読みどころです。Figma ソース、アイコンフォント、書き出した SVG、そしてチームが日々使うコンパニオンサイト。サイトにはホバーでコードポイントとクイックアクションが出るグリッド、1,274 のタグを対象にした検索（「search」で `magnifying-glass` が出る）、Cursor の概念とアイコンを1対1に固定する表があります。「[X] のアイコンは？」への答えが常に1つであり続けるための表で、これがないとセットは同じ概念に2つのアイコンを持ちはじめ、その時点でシステムでなくなる、と。そして `ship it` コマンドがコードポイント割り当てからフォント4種のコンパイル、スタイルシートの統合、フォント内メタデータの書き換え、サイトのデータ再生成、ドキュメントのアイコン数の照合、コミットとプッシュまでを通します。「システムが、自分が何かを覚えていることに依存しない状態」で引き渡す。これはデザインシステムの担当者が読むと刺さる形の締め方でしょう。

### [Morphicons](https://www.morphicons.com/)

> **出典**: Sidebar | **公開日**: 2026-08-18 | **カテゴリ**: design

**3行まとめ**
- 任意の SVG ストロークアイコンを任意の別アイコンへモーフィングするライブラリ。Lucide、Tabler、Heroicons など既存セットをそのまま使える
- 2D Procrustes（最適な相似変換）を閉じた式で解き、合同なら回転、そうでなければ揃えた座標系でモーフィングする。回転グループを手で宣言しない
- gzip 後 6.5KB、依存ゼロ、モーフの計画は 1ms 未満、画面上の全アイコンで requestAnimationFrame を1本共有

**詳細解説**

小さいながら設計が明快なライブラリです。アイコンのモーフィングは、実務では「from/to のペアを手で定義する」「回転で済むケースを別扱いする」といった設定作業に沈みがちなところ。それを形状間の最適な相似変換を閉じた式で解くことで消しています。ペアが回転で合同なら回転させ、そうでなければ揃えた座標系のなかでパスを補間する。どのペアが回転グループかを人が宣言する必要がない、というのが売りです。

アイコンを「コンポーネントではなくデータとして」消費する設計も効いています。`d` 属性か Lucide の `IconNode` 形式を構造的に型づけて受け取るので、ライブラリごとのアダプタが要りません。コアが DOM に触らないため、React・Vue・Svelte・React Native・Astro・Next.js・素の JavaScript がすべて同じ資格で使えます。Astro では island を作らなくてもよく、アイコンが Web Components に昇格する、という書き方をしていました。

数字も具体的です。gzip 後 6.5KB に全部入り、実行時依存はゼロ、任意のモーフのペアの計画に 1ms 未満、そして画面上のすべてのアイコンで rAF を1本だけ共有する。スプリングは中断可能で、静止時には角が鋭く保たれる。この「静止時に角が鈍らない」という一点は、実装したことがある人には効き目が分かる部分でしょう。パスの補間はしばしば静止状態の形を微妙に崩します。

UXエンジニアリングの視点で見ると、この日の1本目と裏表の関係にあるのがおもしろいところです。Cursor のアイコンは人が判断を積み上げて統一感を作りましたが、こちらは形状同士の関係を数学で解いて設定作業を消しています。どちらも「毎回人が決めるしかないもの」を減らす方向ですが、片方は決定を canonical にして書き残し、もう片方は決定そのものを不要にする。デザインシステムのアイコンにモーションを持たせたいとき、`fitIcon` で任意のグリッドに合わせられる点も含めて、検討に入れる価値はありそうです。

### [Design is how it tastes](https://superposition.jem.computer/design-is-how-it-tastes/)

> **出典**: Sidebar | **公開日**: 2026-08-17 | **カテゴリ**: design

**3行まとめ**
- デザインシステムは判断を保存できるけれど、その判断が存在する「感じられた理由」は落としてしまう
- object-language（暖色のニュートラル、8px の角丸）と encounter-language（ユーカリの林に車を降りたときの空気）を対比させ、後者のほうが多くの設計方向を含んでいると論じる
- 拡散モデルが encounter-language を直接解釈できるようになったので、体験の言語が実行の言語の隣に来た。sensation → visuals → system という逆向きの流れの提案

**詳細解説**

2000年の Macworld で Steve Jobs が Aqua のボタンを「舐めたくなる」と紹介した場面から始まります。半径やパディングやコントラスト比の話ではなく、感覚的な直接性の話をしていた、と。それから26年、デザインの判断を保存するための強力なシステムを作り続けてきました。トークン、コンポーネント、スペーシングスケール、インタラクション状態、ブレークポイントごとのバリアント。整合を保ち、ずれを防ぎ、意図を再利用可能な文法に符号化する点でデザインシステムは優秀です。けれど、その判断が存在する感じられた理由は落ちる。

Google Labs の DESIGN.md が例に出されます。デザインの理念を1つの Markdown に符号化してコーディングエージェントに一貫して実装させる、という発想自体は妥当。ただ典型的な DESIGN.md には「8px の角丸を使う。ニュートラルなパレットにピンクのアクセント。ボタンには primary と secondary。カードには控えめなボーダー」と書かれている。有用だけれど薄い、生成された物体を記述しているだけで、意図された出会いを保存していない、という指摘です。「デザインの意図がトークンになった瞬間に、温度が抜け落ちる」。

対比の立て方が鮮やかでした。object-language は成果物を記述します——暖色のニュートラル、上品なセリフ、控えめなテクスチャ、柔らかいカード、ゆったりした余白。encounter-language は成果物に出会う経験を記述します——車を降りてユーカリの林に立つ、メンドシーノの太平洋の空気の味、額に触れる黄金色の日差し、山小屋に漂うコパルの煙。「ページはあなたが到着する前にもう息を吐き終えている」。1つの感覚的な場面が、色・余白・コントラスト・素材感・装飾・密度を名指さずに符号化できる。別の軸で精密なのだ、という言い方です。

この言語はこれまで機械には無用でした。ブランドデッキに「このページは乳香の香りがするべきだ」と書いても、開発者はうなずいて角丸の調整に戻る。感覚の言語は実行の言語とは別の部屋に住んでいた。変わったのは、拡散モデルが encounter-language を直接解釈できるようになった点だとされます。「乳香」を「控えめなテクスチャの暖色ニュートラル」に翻訳してもらう必要がなく、感覚を理解して形を生成する。実験の記述も具体的で、いちばん強く効いたプロンプトは視覚的なスタイルタグではなく身体化された場面でした。「田舎の未舗装路でタイヤの下で砂利が鳴る」「少し日焼けして靴に砂を入れたまま街に帰る」。返ってきたものは、ブランドガイドラインが掲げていた「カリフォルニアへのラブレター」を、デザイン用語を与えないまま設計判断へ翻訳していたそうです。プロンプトは無作為な感覚のノイズではなく、味と香り・天候と大気・素材・情動・社会的シグナル・人生の季節というカテゴリに分かれていて、天候は階層と密度を、素材は質感と輪郭を、社会的シグナルは誰が自分を認められたと感じるかを形づくる、と整理されています。

UXエンジニアリングの視点では、結論の置き方が慎重なところに注目したいです。デザインシステムをバイブで置き換えるという主張ではありません。トークンも craft も判断も必要で、コーディングエージェントは何を作るのか知る必要がある。提案はその上に生成的な意味論の層を置くこと。従来は system → visuals で、トークンを決め、コンポーネントを決め、ページを作る。逆向きにする——sensation → visuals → system。どう感じるかから始め、視覚的な場を生成し、うまくいったものからシステムを抽出する。モデルは可能性を生成しますが、判断としての taste はループの中に残る。「これはまだ意図のように感じられるか、それとも美的なコスチュームに崩れたか」。この問いを誰が持つのかという整理は、生成物の量が増えるほど重くなるところでしょう。

### [Inside HAOQI.DESIGN: Letting DOM and WebGL Share a Retro-Futurist Stage](https://tympanus.net/codrops/2026/08/15/inside-haoqi-design-letting-dom-and-webgl-share-a-retro-futurist-stage/)

> **出典**: Codrops | **公開日**: 2026-08-15 | **カテゴリ**: design

**3行まとめ**
- Lenis と React Three Fiber がそれぞれ rAF を持つと1フレームのずれが出る。スクロールとレンダリングを1つのフレームループに統合し、ScrollBus で同じスナップショットを共有させる
- レイアウトとアクセシビリティは DOM と CSS Grid が持ち、透明なプレースホルダの矩形を測って canvas に転写する。WebGL は CSS では出しにくい状態だけを担当
- ガラスの hello は FBO による屈折と分散、Beer-Lambert 則に着想した透過とダークモード用のハードライト、リムライトは角度だけを追わせて縁から離さない

**詳細解説**

Awwwards の Site of the Day、FWA of the Day、CSS Design Awards の Website of the Day を獲った個人サイトの制作記です。子どものころ画集で見た iMac G3 の半透明の筐体と Apple の hello (again) キャンペーンが出発点になっていて、視覚の方向は hello・ガラス・色のついた光・レトロフューチャリズムのまわりに育った、と書かれています。技術構成は Next.js + React、Lenis、Motion、Three.js / R3F / Drei、独自シェーダとポストプロセス、3Dモデルは Spline、ステッカーは Figma。

いちばん実務的に効くのは最初の節でした。最初の版では Lenis が DOM を更新し、R3F は `useFrame` の中で `window.scrollY` を読んで WebGL を更新していた。低速では問題なく見えるのに、速くスクロールすると WebGL に一貫して1フレームの遅れが出る。原因は Lenis と R3F がそれぞれ `requestAnimationFrame` のループを持っていたことです。R3F が先に走ると前フレームのスクロール値を読み、Lenis はその後で進んで DOM を現フレームへ動かす。カスタムのスクロールコンテナを使うと `window.scrollY` が Lenis の保持する値と一致しなくなるため、ずれはさらに露骨になる。「補間をどうチューニングしても、実行順序と信頼できないデータソースが原因の問題は解けません」。

解き方は素直です。Lenis 自身のループを止め、R3F が `addEffect` 経由で `lenis.raf` を呼ぶ。そのフレームの Lenis のスクロール値を ScrollBus が記録し、以降の `useFrame` の消費者は全員その同じスナップショットを読む。DOM と WebGL がデータと、それが現在になる瞬間の両方で一致します。React 側で DOM 出力に必要な箇所だけ `useSyncExternalStore` で購読させ、コンポーネントツリーの残りは触らない設計。同じ考え方をポインタにも広げて PointerBus を作り、ブラウザ座標を1度だけ 0〜1 の UV に変換し、ウィンドウ内かどうかの `inside` フラグを保持します。ポインタが出た・ページがフォーカスを失った・タブが隠れたときは UV を中心に戻すので、戻ってきたときに古い座標から飛ばずに初期状態へ落ち着ける。

グリッドの作りも参考になります。各プロジェクト画像は透明な DOM プレースホルダを持ち、位置と寸法は CSS Grid が決める。毎フレーム全カードにレイアウトを読ませるのではなく、1つのサンプラが共有の矩形キャッシュを保つ。スクロール中はキャッシュをスクロール差分で補正し、ビューポート近くのカードだけ毎フレーム測り、遠いカードはリストをまたいでずらしながら12フレームに1回だけ更新する。DOM の読みを同じフレームに固めないための工夫です。3Dジオメトリを DOM に合わせて動かすのではなく、矩形の位置とサイズを `uRect` に書き込んでシェーダがスクリーン UV をカードローカル座標に変換する。座標系の補正は Y の反転1回だけで済み、あとは CSS が列・間隔・カード比率を自由に変えられます。

ガラスの hello は屈折を2パスで作ります。まずガラスを FBO から除外して背後のシーンをテクスチャへ描き、本シーンでガラスを描くときにそのテクスチャを少しずつ違う屈折方向でサンプリングして歪みと分散を出す。ガラス専用の Three.js レイヤーを使うので FBO がガラス自身を捉えない。リムライトの扱いには判断が入っていて、最初はポインタを直接追わせたところ、ポインタが画面中央に近づくと光がガラスの面に乗って明るい斑になり、文字の輪郭が弱まった。そこでポインタの方向だけを取り、中心からの距離は捨てて、固定半径の円上に常に光を置く。角は通常の数値として補間できないため、πから−πをまたぐときに長いほうの弧を回らないよう、差分を−π〜πに巻き戻してから指数的に滑らかにする `dampAngle` を用意しています。色つきガラスはライトモードでは Beer-Lambert 則に着想した `pow(tint, thickness)` を透過率の近似として使い、暗い背景では暗すぎたのでダークモードはハードライトで持ち上げる。「これは統一された物理モデルではありません。まったく違う2つの背景に対する視覚的な調整です」と明言しているところに誠実さがあります。

UXエンジニアリングの視点では、Reflections の節が本題でしょう。「この案件でいちばん重要な学びは、エフェクトをどこに出すか決める前に、DOM と WebGL へ信頼できるスクロールとポインタのデータを渡しておくことだった」。CSS が構造とアクセシビリティを持ち、WebGL は curl や屈折や遷移が CSS では表しにくいものを足せるときに入ってくる。実験的な HTML-in-Canvas API のフラグを訪問者に立てさせなくて済む構成にしている点も含めて、役割分担が最初から意識されています。AI はシェーダの案を試し、問題を調べ、初期実装を速く抜けるのに役立ったけれど、最終的な判断はしなかった、という一文も添えられていました。やり直すならモバイルのパフォーマンス予算と各エフェクトの停止条件をもっと早く決める、という反省が、いちばん実装者らしい締め方です。

### [Building an Animated Testimonial Hero Using the GSAP Timeline and Dynamic CMS Data](https://tympanus.net/codrops/2026/08/18/building-an-animated-testimonial-hero-using-the-gsap-timeline-and-dynamic-cms-data/)

> **出典**: Codrops | **公開日**: 2026-08-18 | **カテゴリ**: design

**3行まとめ**
- 数字を 0 から数え上げるのではなく、桁ごとに数字の帯を作って `translateY` でスライドさせる。スロットマシン風のカウンター
- CMS コレクションリストは全項目を同じ形で出力する。`:first-child` / `:nth-child(even)` / `:last-child` の4つだけでコラージュ配置を作る
- `container-type: inline-size` と `font-size: 1cqw` を組み、中の値をすべて `em` にすると、コラージュ全体が1つの塊として拡縮する

**詳細解説**

Webflow で作られたセクションの制作記です。設計上の緊張がはっきりしていて読みやすい。手で組んだような性格のあるレイアウトにしたいのに、中身はすべて CMS 由来である必要がある。Webflow のコレクションリストは全項目に同じレイアウトを繰り返す前提なので、ポートレートごとに違うサイズと位置を持たせたい要求とぶつかります。それを Webflow Designer の中に留まったまま解こうとした記録です。

カウンターの実装が素直に上手い。値を 0 からターゲットへアニメーションさせるのではなく、桁ごとに縦の数字の帯を作る。各桁は `overflow: hidden` で1行分の高さのセルに入り、中には 0〜9 が必要な回転数だけ積まれ、末尾にターゲットの数字が置かれる。帯を `translateY` で上へ滑らせれば、セルが1桁だけ残して切り落とすので数字が回って見えます。「数えるのではなく、切り抜いて動かす」。細部の判断が3つ挙げられていて、どれも実装者の目線でした。回転数は数の全体に散らすのではなく右から数える——そうしないと 952 から 1,000 に変わったときに全桁の並びが再編されて手触りが変わる。「何回転するか」と「どれだけ時間をかけるか」を分ける——純粋な ease-out は全速で始まるので慌ただしく感じる。そして `1em` を決め打ちせず `getComputedStyle` で実際の行の高さを読む——見出しが `line-height: 0.9` なのでセルが高すぎて下の間隔が崩れる。

制作者が「JavaScript は自分では書けない」と明言しているところも、この記事の性格を作っています。AI に書かせているけれど、イージングだけは言葉で調整を伝えるのが難しかった。そこでやり方を変え、スライダーのついた小さなコンフィギュレータを作らせて自分で詰めた。その設定値が AI へのフィードバックになり、どう JS を生成すればいいのかを正確に伝えた、という流れです。結果を無料ツールとして公開してもいます。

コラージュの解き方も気持ちがいい。「項目を並べ替える必要はまったくなくて、位置ごとにスタイルを当てればいい」という気づきから始まります。Webflow が Designer から直接与えるのは first-child、last-child、odd、even の4つだけ。カスタム CSS を書かずにその4つでどこまで行けるかを試したら、足りていた。項目ごとに幅を変え、2つには上マージンを足して一直線に並ばないようにする。CMS が全項目の下に同じ名前とロールのラベルを繰り返してしまう問題も同じ子セレクタで処理し、既定ですべて隠して、コラージュごとに1つだけ表示させています。

`em` の使い方の節は、そのまま持ち帰れる技術でした。ラッパーに `container-type: inline-size` を与えると、ラッパー自身の幅が中の値の基準になる。`font-size` を `1cqw`、つまりその幅の1%にする。`em` は font-size に対する相対値なので、`1em` がラッパー幅の1%と等しくなり、10em の項目は 10%、5em は 5% になる。ベースの font-size を変えれば、背後のグラデーション図形まで含めてコラージュ全体が1つの塊として拡縮します。モバイルとタブレットでは `cqw` を `vw` に差し替えるだけ——ページのコンテナがそこでは全幅なので、`1vw` が `1cqw` と同じ振る舞いになる、という調整も具体的です。

UXエンジニアリングの視点では、最後のアクセシビリティの節が読みどころです。ループを1本のタイムラインの無限リピートで作ろうとすると、1度だけ流したい入場のフェードインまでループしてしまう。そこで入場だけを扱う `user-hero-beginning` と、顔の入れ替えだけを扱って無限に繰り返す `user-hero-collection-loop` の2つのインタラクションに分けた。この分割が reduced motion で報われます。3Dの入れ替えループは強すぎるけれど、スクロールで入ってきたときの穏やかなフェードインは問題ない。分けてあったので、フェードは全員に残したままループだけ止められた、と。モーションを「1本の演出」ではなく役割の違う複数の層として組む理由が、これほど具体的に説明されている例はあまり見ません。タイムラインを enter で再生し leave で一時停止して戻ったら再開する扱いも、同じ発想の延長でしょう。

### [Reliable Query Prefetching with TanStack Router](https://tkdodo.eu/blog/reliable-query-prefetching-with-tanstack-router)

> **出典**: TkDodo | **公開日**: 2026-08-18 | **カテゴリ**: frontend

**3行まとめ**
- ルートローダーで先読みし、コンポーネントが `useSuspenseQuery` で拾うパターンには、同じことを2箇所に書く代償がついてくる
- 2箇所がずれても何のエラーも出ない。検索パラメータを1つ足しただけで、不要な先読みと待たされる二重フェッチが同時に起きる
- `queryOptions` をルートコンテキストに置き、ローダーとコンポーネントの両方がそこから読む。ずれが構造的に起きなくなる

**詳細解説**

TanStack Router シリーズの4本目です。前提の整理から始まります。推奨されるデータ取得のパターンは、できるだけ早くローダーでフェッチを起動し、ローダーをイベントハンドラのように扱ってコンポーネントが `useSuspenseQuery` や `useQuery` で promise を拾うこと。コンポーネントは可能なら自分でデータ取得を始めないほうがいい、というのが要点です。自己完結したコンポーネントが自分のデータ要件を解決するのは理屈としては優れているけれど、実際にそこだけでフェッチすると、理想より遅く始まるうえ、フェッチのウォーターフォールを簡単に作ってしまう。

その代償が「The Great Divergence」と名づけられています。コンポーネントでやっていることをルートローダーという第2の場所に複製する。重複自体は世界の終わりではなく、得られる UX に対して妥当な取引です。ただ、この2箇所は100%同期していなければならない。そしてアプリが育つとそれを保つのが難しくなる。理由が2つ挙げられていて、どちらも身に覚えがあるところでしょう。まずコンポーネントは `Route` ファイルに留まらない——`component: Dashboard` はいいけれど Dashboard は多くのコンポーネントから組まれ、それらも `getRouteApi` でルートAPIにアクセスする。ファイルを分けるのは良いことですが、コンポーネントのクエリの使い方を変えたときにローダーも直す必要があると即座には思い至らない。もう1つ、2つが一致していなくてもエラーは出ない。

具体例が効いています。ダッシュボードに過去の日付でスナップショットを見る機能を足したい。共有可能にしたいので `?asOf=YYYY-MM-DD` を任意の検索パラメータとして持たせ、コンポーネントで消費する。読み込んでも動くし、パラメータを変えればその時点のデータが出る。ところがそのルートを共有すると、ローダーは「今日」のデータを読み、それが揃うまで待ってコンポーネントを描き、そこから `asOf` つきで再度フェッチする。`asOf` は `QueryKey` の一部になるので完全に別のクエリになり、コンポーネントはもう一度サスペンドする。正しいデータで描かれるのはその後です。「いちばんよくある使い方（機能を足すこと）を正しくやるのが難しく、そこから来るバグは見つけにくい」。

対処が2段階に分けられているところが丁寧でした。まず症状を止めるなら、`loaderDeps` という間接層を使ってローダー側にも任意パラメータを含める。これで URL を共有しても不要なリクエストは起きなくなるけれど、根本原因には触れていません。次のルートで同じ間違いをする確率は変わらない。そこで重複そのものを直します。ローダーの `ensureQueryData` とコンポーネントの `useSuspenseQuery` は同じクエリオプションを共有していて、違うのは渡す先の関数だけ——命令的な1回のフェッチか、リアクティブな購読か。ならばオプションをルートコンテキストに置いて両方から読めばいい。`context` 関数だけが `params` と `deps` を使い、ローダーもコンポーネントも `context` しか見なくなります。

この間接層の効き目が複数挙げられています。ずれるバグが起きなくなるのはもちろん、コンポーネントが先読み済みのクエリを使っていることが分かるようになる。つまりコンポーネントから使用を消したときに、ローダーの先読みを片付けようと思い至る確率が上がる。コンテキストは親から継承されるので、サブルートも親の `queryOptions` を知る。ルートルートのローダーでユーザーデータを先読みしておき、末端の Widget から使うといった書き方ができます。購読の粒度で気になる点にも答えていて、`context` 関数は `params` か `loaderDeps` が変わったときにしか走らないため、無関係な検索パラメータ（`debug` など）が変わってもコンテキストを購読しているコンポーネントは再レンダリングされない、と。

UXエンジニアリングの視点では、これは体験の質と保守性が同じ向きに揃った珍しい形の解です。先読みは UX のために入れるものですが、そのために生まれた重複が、放っておくと二重フェッチという UX の劣化に化ける。しかも劣化は静かに起きて、テストも型も教えてくれません。単一の情報源を作ってローダーとコンポーネントの両方をそこに向けるのは、あらゆる「2箇所を同期し続けなければならない」問題の定石ですが、ルーターのコンテキストというすでにある機構に載せられる点が実装コストを小さくしています。似た構造を抱えているコードベースは多いはずです。

### [Sandboxテスト 〜フロントエンドとAI時代の変化の激しさへの挑戦〜](https://tech.smarthr.jp/entry/2026/08/17/080914)

> **出典**: SmartHR Tech Blog | **公開日**: 2026-08-16 | **カテゴリ**: design

**3行まとめ**
- Rails を起動せず、OpenAPI のモックサーバー Prism だけで動かす Playwright テスト。フロントエンドに閉じた結合テスト
- スキーマの `examples` を固定レスポンスにして UI 状態（空・成功・エラー）を再現し、VRT も回す。同時に Prism がリクエスト側のスキーマ準拠も検証する
- 選んだ理由はポータビリティ。フレームワークや設計に依存せず振る舞いに焦点を当てたテストが、コーディングエージェント時代の前提になると見ている

**詳細解説**

SmartHR の AI アシスタント開発チームによる、テスト戦略の記録です。「Sandbox テスト」は一般的な呼称ではなく、バックエンドのサーバーも立てる既存の E2E テストと区別するために便宜上そう呼んでいる、と明記されています。モック E2E テスト、フロントエンド統合テスト、ネットワークインターセプトテストとも言い換えられるかもしれない、と。技術構成は Next.js 16（App Router、Server Function と RSC）、Rails、OpenAPI、Playwright 1.59、Prism 5.14。フロントエンドは openapi-generator-cli で自動生成したクライアントコードを使って Rails の API にアクセスする形です。

仕組みの要点は、Prism が単なるモックサーバーではないところにあります。OpenAPI の `examples` をレスポンスとして返すのでレスポンスのパターンを固定でき、空・成功・エラー・各ステータスといった UI 状態を再現できる。加えて Prism は受け取ったリクエスト（パラメータやボディ）をスキーマに照らして検証し、違反していれば 422 などのバリデーションエラーを返す。つまり「ある操作でしかるべき UI が表示されるか」と「フロントエンドがスキーマに沿ったリクエストを送れているか」を、フロントエンドに閉じたまま同時に担保できます。表示の検証に VRT のスナップショット比較も重ねています。

採用理由の説明が、この記事のいちばん読ませる部分でした。ポータビリティの高いテストとは、特定のフレームワークや設計にできるだけ依存せず、アプリケーションの振る舞いに焦点を当てて品質を担保できるテスト、と定義されます。そのうえでフロントエンドの変化の激しさを3層に分けている。フロントエンドそのものの特性としての変更の激しさ（DB のスキーマ変更より UI の変更のほうが速い）、フレームワークレベルの変更（jQuery から Backbone.js、AngularJS、React や Vue へと10年余りで何度も入れ替わった）、コンポーネントレベルの変更（RSC でサーバー側に切り出す、下層に状態を閉じ込めるための分割）。だから詳細レベルのテストは難しいところがある、という整理です。

そこにコーディングエージェントの台頭が重なります。Bun が11日で Rust に書き換えた例と、Stripe が1日で 5,000 万行の Ruby を移行した例が引かれていて、こういうドラスティックな変更でもデグレが起きないような抽象度の高いテストが効果的だと考えている、と。もう1つの理由は消去法で、RSC を前提としたエコシステムの未成熟。Storybook の PlayFunction でコンポーネント単位の結合テストが理想でありつつ、RSC がクライアントサイドでレンダリングされたり Server Action をモックしなければならない制約があって、検証時点では難しかったそうです。

構築で難しかった2点も具体的でした。1つはネットワークインターセプト。Playwright と Next.js が別プロセスで、Next.js の中にもブラウザと Node.js があり、個々のテストで設定がバッティングしてはならず、しかもブラウザからサーバーへの通信は Server Function でエンドポイントが1つにまとめられるためリクエストの区別ができない。Playwright の `page.route`、`msw`、`@mswjs/interceptors` を検討した末、結局ファイルによるプロセス間通信に落ち着いています。Playwright 側が Cookie でファイルパスを指定し、Next.js 側は `globalThis.fetch` にパッチを当ててそれを購読し、マッチしたリクエストに `Prefer: example=...` を付与して Prism へ転送する。もう1つは環境変数で、Next.js 独自の `@next/env` の読み込み優先度やキャッシング、`.env.sandbox` のような独自ファイルを定義できない制約に悩まされ、`@next/env` 内部のパーサーを再利用しつつ読み込み順を自前で制御するコードを書いています。

UXエンジニアリングの視点では、課題を隠していない点にいちばん価値があります。`next dev` の中の Turbopack がインメモリにキャッシュを蓄積するため、テスト時間が伸びるにつれメモリを食って CI で Flaky になる（Next.js 16.3 のメモリ改善で解消見込み）。Prism がストリーミングに対応していないので、AI の回答のストリーミングは検証できない。Prism はスキーマの検証はできるが、フォームの入力値に基づくしかるべきデータが送信されているかまでは見られない。どれも `globalThis.fetch` のパッチを拡張すれば対応できるとしつつ、現状は正直に並べられています。UI の振る舞いとスキーマ準拠を同時に押さえる層を1つ持つという発想は、エージェントが大きな変更を短時間で入れる前提のコードベースでは効き目が大きくなるはずです。

### [Introducing LUX Sidecar: Your SpeedCurve Companion](https://csswizardry.com/2026/08/introducing-lux-sidecar/)

> **出典**: CSS Wizardry | **公開日**: 2026-08-18 | **カテゴリ**: css

**3行まとめ**
- SpeedCurve の LUX エージェントの隣に置く小さなプラグイン。ネットワーク状況、キャッシュ状態、プロトコル、圧縮、Service Worker の関与などをページビューごとに足す
- パーセンタイルは有用だけれど自分を説明できない。metric（測るもの）と dimension（そのページビューを記述するもの）を組むと、初めて条件つきの問いが立つ
- UNO（帰属不能なナビゲーション負荷）と TTLB（最終バイトまでの時間）を計測。値の欠損は失敗ではないので、黙って 0 にしない

**詳細解説**

Harry Roberts による自作ツールの紹介です。位置づけがはっきりしていて、これは SpeedCurve のプラグインなので RUM アカウントが必要で、標準の LUX スニペットを置き換えるものではない。既存の SpeedCurve の設定を、`LUX.addData()` API 経由で追加データを送ることで補完する。「文字どおりサイドカーです。運転は LUX がしていて、Sidecar は道中のためにもう少し情報を持っていく」。SpeedCurve のデータを自分の観察で補い続けてきた作業のうち、有用で持ち運べる部分を1つの小さなツールにまとめた、という経緯でした。

前提の整理が本題です。RUM が価値を持つのは、実際のページビューに何が起きたかを見せるからで、同じ理由でデータは散らかる。2人の訪問者が同じページを要求し、同じコードを受け取り、それでも著しく違う体験をする。要求のまわりの条件が違ったからです。一方はローカルキャッシュからドキュメントを読み、他方は高遅延のモバイル回線を越えた。一方は HTTP/3 と Brotli をネゴシエートし、他方は中間装置に HTTP/2 と Gzip で届いた。一方は通常のナビゲーションで、他方は bfcache から復元したかプリレンダリング済みドキュメントを activate した。「パーセンタイルだけを見るなら、それらのページビューは同じ線に消えます。線は有用なままですが、自分を説明できません」。

metric と dimension の区別の節が、いちばん実務に効きます。metric は測るもの——UNO 480ms、最終バイトまで1.7秒、圧縮デルタ 0.72。dimension はそのページビューを記述するもの——キャッシュヒットかネットワーク転送か、`h2` か `h3` か、プリレンダリング済みか通常か、Service Worker があるかないか。TTLB は「どれだけ長いか」を教え、プロトコル・キャッシュ状態・コンテンツエンコーディングは「どういう条件下で」を問う助けになる。だからすべての数値を自動的に数値メトリクスにするのは違う、という指摘が続きます。HTTP のレスポンスステータスや CPU tier は API の境界では数値でも、セグメンテーションのカテゴリとして使うほうが有用です。「`404` は `202` の2倍のレスポンスではないし、CPU tier `4` は現在の CPU 負荷を記述していません。型は意味に従うもので、JavaScript がその値についてどう思っているかには従いません」。

計測項目のうち2つが詳しく説明されています。UNO（Unattributed Navigation Overhead、Tim Vereecke による命名）は、初期ドキュメントの TTFB から Navigation Timing が公開するリダイレクト・DNS・接続・リクエストからレスポンス開始までの各フェーズを引いた残余。診断ではなく残余なので、値が高いことはブラウザが名前つきフェーズに割り当てられない時間を観測したという事実だけを教えます。クロスオリジンのリダイレクト遅延はよくある原因の1つですが、正しい対応は推測ではなく調査だ、と。TTLB は navigation start から `responseEnd` までで、初期ドキュメントの応答時間の全体。TTFB は最初のバイトの到着を印しますが、ドキュメントは最初のバイトで届き終えていない。HTML が大きい、圧縮が効いていない、スループットが制約されている、サーバーがドキュメントをストリーミングしている場合に、この差が意味を持ちます。

名前と解釈の慎重さも一貫していました。ゼロバイト転送は有用なキャッシュのヒューリスティクスであって、完全なキャッシュ分類ではない。`nextHopProtocol` はオリジンではなく中間装置への接続を記述しているかもしれない。`contentEncoding` はまだどこでも使えるわけではない。Sidecar は検出できるものを feature-detect し、ブラウザが公開しないものは省き、分析は人に委ねる。「データの欠損は想定されています。ブラウザ API は一様にサポートされているわけではなく、保護されたタイミング情報は保護されたままであるべきです。欠けている値は失敗したページビューではないので、黙って 0 に変えてはいけません」。

UXエンジニアリングの視点では、同じ作者の Obs.js との対比が示唆的です。Obs.js は現在のページが届けるべき体験に関わるもので、ブラウザのコンテキストを CSS クラスと `window.obs` に変換し、制約された回線でリッチメディアを避けるといった判断を可能にする。LUX Sidecar は事後にページビューを理解するためのもので、SpeedCurve に値を足してチャート化・フィルタ・セグメント・調査できるようにする。同じブラウザのシグナルを見ているので重なるけれど、どちらも他方を置き換えないし要求しない。そして「スクリプトはゼロコンフィグでも、SpeedCurve はそうではない」という節が正直で良いところでした。カスタムデータの定義、compact なビーコンキーの登録、メトリクスと dimension のどちらにするかの選択は人がやる。「あるページビューが遅いのはコードのせいであることもあり、コードが走った条件のせいであることもある。良い RUM の仕事は、その違いを言い分けられる必要があります」。

### [When Safari's 'Ignore Cache' Ignored Cache-Control](https://csswizardry.com/2026/08/when-safaris-ignore-cache-ignored-cache-control/)

> **出典**: CSS Wizardry | **公開日**: 2026-08-17 | **カテゴリ**: css

**3行まとめ**
- Safari Technology Preview 250 のリリースノートの一行から、WebKit のコミットまで追った話
- Web Inspector の「Ignore Cache」が、ローカルキャッシュを迂回するだけでなく、ページが自分で付けた `Cache-Control` リクエストヘッダーを `no-cache` で上書きしていた
- 修正は小さい。すでにヘッダーがある場合は付けないだけ。キャッシュ迂回とリクエストの意味論が分離された

**詳細解説**

短いけれど気持ちのいい記事です。きっかけは Safari Technology Preview 250 のリリースノートの、それ自体は曖昧な一行でした。「リソースキャッシュの無効化が、ページがすでに設定した `Cache-Control` ヘッダーを上書きする問題を修正」。一見すると機能が意図どおり動いている説明のようにも読めます。キャッシュの無効化は当然どこかでキャッシュを上書きするはずだから。けれど WebKit のローカルリソースキャッシュを無効にすることと、ページが意図してリクエストに付けたヘッダーを差し替えることは、まったく別の話です。

バグの中身はこうでした。Ignore Cache が有効なとき、WebKit は2つのことをしていた。1つは内部ポリシーを設定してリソースキャッシュを迂回すること——これは頼んだとおりです。もう1つは、送信するリクエストの `Cache-Control` と `Pragma` を `no-cache` に設定すること。しかもページがすでに自分のヘッダーを与えていても設定していた。「デバッグの設定が、Safari がローカルのレスポンスを再利用できるかどうかを変えるだけでなく、アプリケーションが送信するリクエストを変えていました」。

前提として `Cache-Control` はレスポンスヘッダーとして考えられがちですが、リクエストにも現れて、クライアントがどんな保存済みレスポンスを受け入れる用意があるかをキャッシュに伝えられる。`fetch` にヘッダーを渡してページ自身が付けることもできます。WebKit の新しい回帰テストがほぼその場合を扱っていて、キャッシュ有効ならサーバーは `max-age=12345` を受け取る、キャッシュ無効でページ側のヘッダーがなければ WebKit の `no-cache` を受け取る、そしてキャッシュ無効かつページが `max-age=12345` を設定している場合はやはり `max-age=12345` を受け取るべき。修正前はここで `no-cache` を受け取っていた。ページが求めた値がネットワークに届いていなかったわけです。

影響の説明が的確でした。`max-age=12345` が `no-cache` に変わるのは見た目の問題ではありません。`no-cache` は保存済みレスポンスの再利用の前に検証の成功を要求するので、共有キャッシュや CDN やオリジンは違う応答を返しうる。リクエストを検査するための道具が、リクエストのキャッシュ意味論をネットワークに届く前に変えていた。そこから生まれる混乱の形も並べられています。サーバーログにアプリケーションが送っていない `no-cache` が出る。Web Inspector を開いて Ignore Cache が有効なときだけエンドポイントの挙動が違う。ウォームキャッシュのテストのつもりが、毎回ユーザーが明示的に再検証を要求したように見える。「どの観測も、正確には偽ではありません。それを生んだデバッグ条件の下でのみ真なのです」。

UXエンジニアリングの視点では、末尾の作業手順が持ち帰る価値のある部分でしょう。キャッシュの検証では条件を分ける——コールドキャッシュは関連データを1度消してからキャッシュ有効で読み込む、ウォームキャッシュはキャッシュ有効のまま通常に読み込むか再訪する、そしてキャッシュ無効はウォームキャッシュのテストではなく別の診断モードとして扱う。ブラウザのバージョン、Web Inspector が開いていたか、Ignore Cache が有効だったかを記録しておく。リクエストヘッダー自体が疑わしいときは、Web Inspector の表示と CDN やオリジンのログ、あるいはその設定の外での別のキャプチャを比べる。開発者ツールは観測装置であって、観測が対象を変えることがある——パフォーマンス計測に限らず、あらゆる計測の前提として覚えておきたい形です。

### [$1 million hacker challenge for Vercel Sandbox](https://vercel.com/blog/one-million-dollar-hacker-challenge-for-vercel-sandbox)

> **出典**: Vercel | **公開日**: 2026-08-18 | **カテゴリ**: frontend

**3行まとめ**
- Vercel Sandbox の隔離を破った研究者に、2週間で最大100万ドルを支払う公開 HackerOne プログラム
- microVM だけがサンドボックスではない。ネットワーク境界を計算に入れていないセキュリティモデルは、VM の境界を越えずに封じ込めを抜けられる

**詳細解説**

エージェントに untrusted なコードを実行させる基盤の話です。前提の置き方が明快でした。エージェントは信頼できないコードを走らせる必要があり、microVM がその標準的な方法になった——ワークロードごとに専用のゲストカーネルを持ち、ホストからも同じマシン上の他のワークロードからも隔離される。ところが最近のセキュリティ研究と実際の事故が示したのは、信頼できないコードを走らせるエージェントは封じ込めを抜けるために VM の境界を越える必要はないということ。セキュリティモデルが計算に入れていなかったネットワーク経路が1つあればいい。「隔離は両側が保っていて初めて保たれます」。

構成の説明も具体的です。Vercel Sandbox はベアメタルの EC2 ホスト上で動き、各サンドボックスは専用ゲストカーネルを持つ Firecracker microVM を得て、その microVM の中で Linux コンテナが実行者のコードを走らせる。セキュリティ境界はコンテナではなく microVM なので、実行者が与えたコードはホストから2層隔てて走る。そのコードは完全に敵対的だと想定する——コンテナ内では root、microVM 内ではカーネルへの完全なアクセスを持ち、ホストや他テナントへ到達する動機がある。ネットワーク側の境界は microVM の外、ホスト側で強制されるため、サンドボックス内のコードからは変更も無効化もできない。サンドボックスのファイアウォールは outbound の TCP と DNS を intercept し、各接続を実行者のドメインと CIDR のポリシーに照らし、境界で資格情報を注入できるので秘密が microVM に入らない。

自社でやったことも書かれています。CTO がセーフガードのないオープンウェイトのモデルを Vercel Sandbox に向けた。脱出はしなかったけれど、ゲストカーネルを地図化し、自分の考えを再現するための VM を作り、ファザーを書いた。「防御側には先手の優位がありますが、それは永遠には続きません。選べるのは、いつ境界を試すかだけです」。だから攻撃者のスケジュールではなく自分たちのスケジュールで、しかも公開の場で、世界最高の研究者たちと試すことにした、という筋立てです。

対象の切り分けが厳密でした。計算の境界では、Firecracker microVM から EC2 ホストへの脱出、計算層を通じた他テナントのサンドボックスへの到達（読み取り・改変・コード実行）、あるサンドボックスから他テナントのサンドボックスをクラッシュさせること。ネットワークの境界では、microVM を越えずにサンドボックスのファイアウォールを破ること——実行者が許可していない宛先への到達、データの持ち出し、仲介された資格情報の取得。そしてコンテナの名前空間の脱出で Firecracker のゲスト OS に届くだけのものは対象外、と明記されています。「名前空間は開発者体験の機能であって、セキュリティ境界ではありません」。報奨はレポート単位で、単一の root cause にスコープされ、実証可能な最大影響に基づいて triage が割り当てる。1件あたりの上限は5万ドルで、それは脅威者が他テナントのデータを読むか改変できる脆弱性に対する額。静的解析だけの報告には支払わない——境界が破れるところを見る必要がある、と。

UXエンジニアリングの視点では、この記事はエージェント基盤を選ぶ側の判断材料として読めます。「サンドボックス」という言葉が指す範囲が製品によって違うということ、そしてどこを境界と宣言しているかがそのまま脅威モデルになるということが、これだけ明示的に書かれた例は多くありません。フロントエンドの開発でも、ユーザーのコードやプロンプト由来の処理をサーバー側で走らせる構成は増えています。そのとき問うべきは「隔離されているか」ではなく「何と何のあいだの、どの層の境界が、誰によって強制されているか」でしょう。プログラム終了後に見つかった手法と修正の writeup を公開する予定と書かれているので、そちらも追う価値がありそうです。

**詳細解説**

Nic Steenhout による、いつもの短い記事の集まりではなく1本の長い文章に充てたニュースレターです。出発点は言葉づかいへの注意でした。開発前のデザインをレビューして、安心できる結論に至ることがある。ただし「これはアクセシブルです」でも「これはアクセシブルになります」でもなく、「これはアクセシブルに実装できます」。そして数週間から数か月後に完成した機能を監査すると、結果はしばしば意外なものになる。情報を伝える画像に代替テキストがない、モーダルがキーボードフォーカスを保持しない、動的な更新がスクリーンリーダーに通知されない、キーボードから到達できない部分がある。

原因の候補を1つずつ外していく進め方が丁寧です。「開発者がアクセシビリティを気にしていない」で片付けるのは簡単だけれど、そうは思わない。「訓練が足りない」も簡単で、ときには本当だけれど、ここで起きたことの説明にはならない。このプロジェクトの開発者はアクセシブルなプロダクトの経験があり、ゼロから始めたわけではなかった。そこで個々のバグへの関心が薄れていきます。代替テキストの欠落もフォーカス管理の破綻も通知の欠落も症状で、本当の問いは、アクセシブルに実装できるデザインから始めたチームが、そうでないプロダクトに行き着けるのはどういう仕組みなのか、というものでした。

区別の立て方が有用でした。デザインレビューと監査は違う問いに答えている。レビューが問うのはアイデアがアクセシブルに実装できるかどうか、つまり可能性です。良いレビューは障害のあるユーザーにとってうまく働くパターンを見つけ、働きえないアイデアに旗を立てる。それが通常しないのは、その結果を達成するために必要な実装の細部をすべて文書化することです。キーボードフォーカスをどう管理するか、どの変更を支援技術に通知するか、カスタムコンポーネントが意味論をどう露出するかは実装の判断で、誰かがそれを決め、文書化し、実際にそうなったか検証する必要がある。だからレビューは「アクセシブルに実装できます」と誠実に結論しながら、実際にそうなるかについて何も言わないままでいられる。

「キーボードを使っているから分かるはず」という思い込みへの反論も的確です。コードをキーボードで書くことと、マウスなしでインターフェースを操作することは違う技能。エディタのショートカットを知っているからタブ順を学ぶわけではないし、Vim や VS Code を効率よく使うからフォーカス管理を発見するわけでもない。手がキーから離れないからといって、スクリーンリーダーがいつ live region を必要とするかは分からない。このプロジェクトには自分をパワーキーボードユーザーだと言う開発者が何人もいたけれど、それがキーボードに優しいインターフェースを作ることには繋がらなかった。「それを認めることは結果を免責しません。『とにかくキーボードを使ってみて』では、障害のあるユーザーが実際に何を経験しているかを誰にも教えられなかった理由を説明するだけです」。

診断のポイントは受け渡しの構造でした。デザインチームがデザインを持ち、開発者がコードを書くことを持ち、QA が機能のテストを持ち、アクセシビリティが監査を持つ。各段階に担い手がいた。担い手がいなかったのは、アクセシビリティを1つの段階から次へ運ぶことです。障害のあるユーザーにとって重要だった実装の細部は、意図的に削られたのではなく、運ばれなかった。だからこれは人の問題ではなく workflow の問題になる、と。監査の時期についての一節も鋭いです。デザインの後の最初のアクセシビリティのチェックポイントが開発終盤の包括的な監査なら、チームには早期警戒の仕組みがない。リリース前の週に最初のパフォーマンス問題を見つけるところ、あるいはコードが全部書かれた後に最初のセキュリティレビューをするところを想像してみる、と。そして「人はレビューされるものに注意を向ける」。コードレビューがアーキテクチャや命名やパフォーマンスやテストカバレッジにコメントし、QA が振る舞いを検証し、自動テストがビルドごとに走る。それらのチェックポイントは、誰が意図しようとしまいと、チームに品質とは何かを教えている。

UXエンジニアリングの視点では、提案が既存の workflow に載る形になっているところが実行可能性を上げています。デザイン段階では、「アクセシブルに実装できる」と承認されたときにアクセシビリティ要件を視覚仕様の隣に書く——フォーカス順、キーボードの振る舞い、通知、意味論、状態変化を誰かの記憶や議事録ではなくデザインの一部にして、そこから受け入れ条件にする。開発段階では、デザインから実装への移行に担い手を置く。加えて、フォーカス管理や disclosure widget を毎回作り直さないための共有コンポーネントライブラリと、ビルドパイプラインの自動チェック。検証段階では、完全な監査でなくてよいので開発中にもう1つ焦点を絞ったレビューを挟み、すでに行われているコードレビュー・機能レビュー・QA の会話の中にアクセシビリティを可視化する。「新しい儀式は必要ありません。すでに持っている会話の一部になる必要があります」。最後に誰が見落としたかを探すことには依存しない、すべての受け渡しに担い手を与えることに依存する——という締め方は、そのまま組織に持ち込める言葉でしょう。

### [The human is the loop](https://brentfitzgerald.com/posts/the-human-is-the-loop/)

> **出典**: Sidebar | **公開日**: 2026-08-18 | **カテゴリ**: design

**3行まとめ**
- 数週間 AI から離れて戻ってきたら、自分が作っていた習慣の不健全さがよく見えた
- 開いたラップトップには 11 個の cmux タブと、途中で止まったエージェントが複数。「2026年版の開いたままのタブ」だけれど、もっと悪い感じがする
- 人間がエージェントのループに閉じ込められるのではなく、人間がループであって、エージェントをときどき慎重にタグインさせる

**詳細解説**

Brent Fitzgerald による、休暇明けの内省です。夏の終わりの休暇で冷たい川で泳ぎ、s'more を食べすぎ、昼寝をした。多くの時間はラップトップも電話も離れていたので、数週間 AI なしで過ごした。「恋しくなかった」。戻ってきた数日で分かったのは、AI の使用の多くが不要だったこと。それどころか、しばしば習慣を形成する松葉杖になっていて、知的に弱く、好奇心を減らし、自信を減らしていた。少し落ち込ませてもいたと思う、と。

描写が具体的で効きます。ラップトップを開くと 11 個の cmux タブが迎えて、それぞれに途中で止まったエージェントが複数。仕事のものも私的なものも、その中間もたくさん。税金から造園のアイデアからポリシー文書のレビューまで、Claude のチャットに未読のバッジがついている。「2026年版の、たくさんタブを開いたままにしているやつでしょうか。かもしれませんが、もっとずっと悪い感じがします」。それぞれは助けが必要だと思った企画か、思考の一部を自動化あるいは外注したかったものだった。同時にそれぞれが、物事を終わらせないこと、時間の使い方が効率的でも賢くでも集中できてもいないことへの、小さな罪悪感の切り株でもある。

自己批判に寄りすぎないよう慎重に書かれているのも好ましいところです。厳しすぎるのは新しい振る舞いではなく、非現実的な期待に基づく圧力は長く自分の源にあった。ただ機械知性の時代に、その圧力は新しい出口を見つけた。仕事と生活で何がいちばん重要かを選別して集中させるのではなく、「今ならもっとできるはずだ」という検討されていない信念を養う。そしてもう1つのエージェントの会話、もう1つのターミナルのペイン、誰も頼んでいないフォーク、読むことのないマークダウンの出力として放出される。以前は個人の企画を、くつろぐためと楽しみのために学ぶために弄っていた。今の企画はそれをしない——結果に行くために学びを飛ばしがちで、学びこそが喜びが起きる場所なのに。

エージェントを「自分とストレスを起こすタスクのあいだの層」として使っていたという観察が、いちばん刺さる部分でしょう。直接引き受けるのではなく、エージェントを間に入れる。特別なぬいぐるみかお守りのように守ってくれる。何か書く必要があれば、考えを全部口述して、運転中や歩きながら ChatGPT と話す。自分と考えをやりとりしている、生産的でない時間を活用しているのだと正当化するけれど、それが追従する鏡であることは知っていた。現実的な思考の相手ではないので、そのセッションの出力を実際の仕事に使ったことは一度もない。「では、あの何時間かは本当にどれだけ有用だったのか。今は OpenAI のサーバー上のとりとめのない録音と書き起こしです」。もう1つの例も的確で、理論的にもっと速く働けて多くのタスクを並列にできるよう自動化を整えようとしたけれど、後から見れば誰もその効率の向上を求めていなかった。「道具の使用を最大化するという課題に道具を適用することで、道具の使用を最大化したいという強い衝動を感じました。最悪の意味で再帰的で、生産性のウロボロスです」。

技術がこういう効果を必然的に持つとは論じていない点も抑制が効いています。形式・設計・そのまわりの文化が、形成された習慣の大きな要因だと考えている。エージェントの使用は、たとえば終わりのないアルゴリズムのフィード送りと同じ意味で本質的に神経化学的な中毒性を持つものではないだろう、という見立て。ただ依存と習慣化の効果は実在する。一度 AI の道具を仕事に入れると、組み込める方法をもっと見つけるのは早い。そして「テック業界の大きな一角が今、LLM への大規模な社会経済的依存に賭けています。ああいう評価額が正当化される唯一の道は、私たちが集団的に AI 基盤の技術に望みなく依存するようになることです」。

UXエンジニアリングの視点では、締め方の実践性が価値です。方針は単純——いつ AI を使い、いつ外に置くかを意図的にする。そして自分の選択で実際に何を得て何を失っているかについて正直であろうとする。この記事を書く前に実際にプロンプトを1つ入れた話が具体例になっていて、要件と提案を渡し、コードベースやウィキやスキーマや会話を見るよう指示し、旗を立てた問題と可能な解決策を持ち帰らせた。設定する作業そのものが、現状に追いつき、考え抜くことを強いた。狭く制約し、自分がすでに考えていることと確信のないことを含めて可能な限りの文脈を与え、出力への期待を明確にした。「AI は完璧な解決策を渡してはくれません。結果が自分を10倍にすることもない。でも、散らばったシステムと SaaS 製品を横断してパターンを照合し検索している——自分が得意ではなく、楽しくもない作業です」。より重要なのは、それが今こうして書いて省察するという人間的なことをする余裕を作っていること。「人間がエージェントのループに閉じ込められることは望みません。人間がループであって、私たちはエージェントをときどき、慎重にタグインさせるのです」。

### [Headed for the Exit: the Great Engineering Leader Career Break](https://newsletter.pragmaticengineer.com/p/the-great-engineering-leader-career-break)

> **出典**: The Pragmatic Engineer | **公開日**: 2026-08-18 | **カテゴリ**: engineering

**3行まとめ**
- キャリアブレイク中か真剣に検討中のエンジニアリングリーダー20人近くへの取材。話した CTO 級の過半数が同じことを考えているか、実際に離れる過程にあった
- 仕事が悪くなった主因は AI についての非現実的な期待。「AI ネイティブに魔法のように変えろ」「20〜50%のコスト削減」「少ない人数でもっと出せ」
- エクイティが煙になる計算、founder slop、そして小さくなったチームに VP of Engineering が要らなくなる構造

**詳細解説**

Gergely Orosz によるレポートです。この記事は途中から購読者限定になっているため、以下は公開部分について書いています。導入の書き方が慎重で、20年ほどこの業界にいて、これほど多くの有能なエンジニアリングリーダーが降りるか長い休みを取るのを見たことがない、と。CTO、VP of Engineering、head of engineering といった高い地位の役職を辞めて、次が決まっていないまま去っていく。サンフランシスコの head of engineering から届いたメッセージが起点になっていて、4つのスタートアップと head of engineering の役職について話しているうち、2社では創業 CTO や head of engineering が完全なキャリアブレイクのために離れていた、しかも良いスタートアップで、というものでした。私的に聞いてまわった結果、話した CTO 級の過半数がまさに同じことを検討中か、実際に長い離脱の過程にあった。10人のうち6人が出口へ向かっていると答えたそうです。

仕事が悪くなる原因の並びが具体的でした。創業者や CEO による非現実的な期待、とくに AI についての期待が2026年時点で最大の要因。会社を「AI ネイティブ」に魔法のように変えることを期待される、20〜50%に及ぶエンジニアリングのコスト削減を、士気を削ぐ人員削減も含めて実行しなければならない、「少ないリソースでもっと」つまり補充なしで少ない人数で多く出荷すること、AI のコーディング費用が積み上がるなかで事業成果への圧力、そして founder slop——不安定な AI プロトタイプを数週間で本格的なプロダクトとして出荷させたがること。

「AI psychosis」を巡る証言が生々しいところです。辞めたばかりの CTO の言葉が引かれています。「創業者や役員の同僚の『AI psychosis』を扱うのがとても難しくなりました。たとえば、創業者が6万行のプルリクエストをプロダクトに投入して、AI でどれだけ生産的になったか喜びに輝いているとき、どうしますか。彼らはその PR の問題をすべて見ることはないし、膨大な技術的負債を作ったことをどう持ち出せばいいのか。とくに『Debbie Downer』に見えないようにしながら」。問題は複数の面に広がる、と整理されています。オンコールの責任——創業者が出荷したコードが壊れたとき誰が持つのか。「作った者が持つ」文化のスタートアップで、創業者が手を動かしながら自分の仕事を所有しないのは混乱を招く。品質の流出——創業者の半焼けの機能が受け入れられるなら、品質は重要でないという広いメッセージになる。そして創業者は CTO や VPE と以前合意していたことを覆せる。感じている vibes がそれだけで十分な理由になる。

エクイティの計算の節が、いちばん冷静で有用でした。ある CTO は普通株の2%という非常に手厚い付与を持っていたのに離れた。理由は投資家への急峻な preference stack の後ろにあること。数字で示されています。シード $10M を $50M のバリュエーションで、シリーズ A $100M を $500M で調達し、合計 $110M。投資家の preference が通常の1倍なら売却時に最初の $110M を得る。ところがこの会社ではシリーズ A の投資家が2倍を交渉していたので、売却時に $210M がまず投資家へ行く。共通株主が1円でも得るには、会社は少なくとも $210M で売れなければならない。$200M 超の exit は通常は買収で、株式公開は近年 $10B 超のバリュエーションでなければほとんど起きない。加えて、VC 資金の会社が年20〜50%程度で成長する収益や顧客を持たないなら次のラウンドは苦しく、事業の実際の価値は年間収益の3〜5倍に縮む。$110M 調達して年 $10M を稼ぎ、前年比30%で成長している会社は、おそらく $30〜50M の価値になる。

キャリアの観点も含まれています。いちばん高給のエンジニアリングリーダー職には共通点が1つあって、AI ネイティブな組織を率いた経験が期待される。大きな銀行の元エンジニアリングディレクターは、キャリアを加速させるために辞めたと語っています。「仮説について『ループを閉じる』機会を十分に得られていませんでした。業界で関連性を保つには、追い越し車線に出る必要があると感じます」。Honeycomb の共同創業者兼 CTO の Charity Majors の言葉も引かれていて、「AI を履歴書に載せないといけません。載せないなら、これは大きなキャリアのリスクです」。そして Director+ から個人貢献者に移ることが可能な会社は少数派ではあるけれど存在するので、そこで働いているならこの機会を使えるか考えてみるとよい、と。ChatPRD 創業者 Claire Vo の厳しい観察も紹介されています——ほとんどの会社は AI ネイティブにならない、なぜならほとんどの VPE や CTO にそういう変革をやり切る力がないから。そこから「行き詰まり」の構造が導かれます。現在の組織は AI がエンジニアリング文化を悪くしていることに苛立ち、士気が下がっている。解決するには全員の働き方に大きな変更が必要で、それをやり切るには変革管理に優れた VPE か CTO が必要だが、ほとんどの VPE や CTO はそこの専門家ではなく、やったこともない。

UXエンジニアリングの視点では、チームが小さくなった理由の節がフロントエンドに直接関わります。DoorDash の Karthik Hariharan の観察——「エンジニアリングチームも今は小さくなっています。チームが必要とするほど大きくなるまで VPE は要りません。技術のある創業者が、今ならずっと長くチームを回せます」。理由が3つ挙げられていて、1つ目はフルスタックエンジニアの主流化で、これは AI 以前から進んでいた。Next.js や Ruby on Rails のようなフルスタックのフレームワークがそれを容易にしていて、今は AI のコーディングエージェントが不慣れなプラットフォームでもまともなコードを書くので、専門の違う複数の開発者が要る理由がほとんどない。Anthropic では1つのプロジェクトに1人か最大2人という記述も引かれています——各エンジニアがすでに複数のエージェントを走らせていて、実装で互いの足を踏み合うエージェントと戦っているので、それぞれのエージェントを連れた人間をそんなに多く置けない、と。2つ目はフロントエンド専任チームとネイティブモバイルチームの縮小か消滅で、Bluesky が React Native と Expo でローンチ時の Web・iOS・Android を1人のエンジニアで作った例が挙がっています。その後採用はしたけれど、全員が3つのプラットフォームを横断して働いていて、Web エンジニアと iOS エンジニアと Android エンジニアを別々に雇うのとは違う、と。フロントエンドとネイティブモバイルの需要が下がり続けているグラフも示されていました。3つ目は組織のフラット化が3年続いていること。ここは職種としての立ち位置に関わる話なので、フロントエンドやデザインエンジニアリングを担う人には読み方が難しい記事でもあります。

### [Creativity at Enterprise-Scale, Without Compromise: The OFF+BRAND. Story](https://tympanus.net/codrops/2026/08/17/creativity-at-enterprise-scale-without-compromise-the-offbrand-story/)

> **出典**: Codrops | **公開日**: 2026-08-17 | **カテゴリ**: design

**3行まとめ**
- グラスゴーで2人から始まったスタジオが6年で30人に。Microsoft、Slack、Webflow の旗艦案件を手がけるまでの記録
- 大規模で創造性を出すために効いたのはガバナンスと変更管理。信頼を作れば創造的な仕事をさせてもらえるし、失えば無味な成果物になる
- 来る仕事の約6割を断る。「小さいままでいる」と「選び続ける」は同じ1つの決断

**詳細解説**

スタジオ自身による振り返りです。始まりの正直さが良いところでした。2020年に2人の共同創業者として、Resn や Monks や Lusion のような憧れのエージェンシーみたいな体験を作りたいという共通の展望から始めた。ただ、そこへ至る道がどんなものかは2人とも知らなかった——エージェンシーで働いたこともなく、そういう仕事をしたこともなかった。転機は Totem という案件で、予算の4倍ほどかかり管理は悪夢だったけれど、特別なものを作れる機会があると分かった最初のブリーフだった。最終形を見せたとき、クライアントの全員が走り回り、1人はうれしさでプールに飛び込んだそうです。

そこから得た教訓の整理が的確でした。Totem が Awwwards と FWA の Site of the Day を獲ると、ほぼ一夜にしてより大きなクライアントが、より多くの創造的なコントロールを渡す用意をして来るようになった。Totem の前はクライアントが創造的であることを信頼してくれなかった。後は特別なものを期待して来るようになり、それがより影響力のある仕事を可能にし、さらに評価に繋がった。「優れたクライアントワークは、クライアントが電話をかけてくる前に築いた評判から始まると気づきました。その信頼がなければ、全員がより安全な決定（つまりまずい決定）をすることになります」。社内の企画への投資を止めなかったことも強調されていて、Manifesto と Aether が良い例、日の目を見なかったまずい例もたくさんあるけれどそこからも学ぶ、と。

規模での創造性の節は退屈だと自分で認めながら、内容は重い。成長するにつれて、良いガバナンスと変更管理の（率直に測りようのない）重要性を学んだ。この2つが規模での創造性を可能にする。大きなクライアントと信頼を築いて維持すれば創造的な仕事をさせてもらえる。信頼を失えば、契約ごと失うか、全員を失望させる無味なものを納品することになり、後者のほうがずっと悪い。信頼の作り方が2点で示されています——プロジェクトとタイムラインを目に見えて統制していること、そして自分たちが統制していることをクライアントが見て信じられるよう助けること。「そしてクリエイティブの部分が開きます。すばらしいことをするための空間と権限を、クリエイティブな人たちに渡す必要がある。心配ごとで邪魔をするほど、体験は特別でなくなります」。

事例の並びも読みどころが多い。Microsoft の Windows と Surface では、これほどの規模と、これほど多くのエージェンシーと管理の階層を経験したことがなかった。3つの旗艦プロダクトの完全なデザインシステムを作り、各部門から承認を得る必要があった。世界でもっとも訪問されるテクノロジーサイトのひとつで、プロダクト群の全体に耐える基盤を作る仕事です。Windows と Surface のデザイン作業と重なったので承認を取るのは複雑になったけれど、結果としてより強いシステムになった、と。難所はステークホルダーの数で、全員が聞かれて理解されたと感じられるようにすること。「近道はありません。関わる全員のフィードバックを本当に受け止め、受け止めきれない場合は、なぜ全部は取り込めないのかをきちんと説明することです。たくさんのトラッカー、たくさんのスプレッドシート、たくさんの会議」。

他の事例では判断の質が見えます。Lando Norris のサイトはより広いシステムを気にする必要がなく、利用者にとっての最大の効果に集中できた。ヒーローの体験はミームになり、Twitter のあらゆる vibecoder が自分の版（ときにひどい版）を再現しているそうです。難所はアイデアを伝えることで、最初から勝ち筋だと分かっていたのにクライアントが気に入らないことが恐ろしくて、承認を確実にするためほぼ全部作ってから見せた、と。Trevor Noah のサイトは、スタンダップ・ポッドキャスト・執筆・ライブ・論評という多面性をきれいなカテゴリに押し込む案がどれも本人らしく感じられなかったので、常に何かに気づき、繋がりを作り、アイデアを集めているという好奇心そのものを概念にした。ホームページは思考と物語と瞬間の生きたコラージュになっています。「技術が主題になってはいけなかった。人々に Trevor を覚えていてほしかったので」。Steven のサイトでは4つの柱にそれぞれページを与えるのが誤りに思えた——プラットフォームの要点はすべてが繋がっていることなので、読むものではなく探索できるものにしたかった。そこで中心にインタラクティブなキャンバスが来て、ナビゲーションとして機能するのではなく、ナビゲーションそのものになった。この発想は自社の Manifesto の実験から来ていて、「ナビゲーションは体験の外に座らなくてよい。体験そのものになれる」。

UXエンジニアリングの視点では、最後の「Small by Design」の節が経営の話として読めます。長く事業をやるほど大きくなることへの関心が薄れた。楽しいことをするためにキャリアを離れたのだから、創造的な小さなスタジオが運用の仕事に変わらないよう、作業の近くに留まる。来る仕事の約6割を断ることで両側を守っている——「小さいままでいることと選び続けることは、同じ1つの決断です。ここでは誰も引き伸ばされていないし、頭数を養うために引き受けた案件を抱えている人もいません。過去にはやりました、もちろん。でもひどいし、誰も楽しくない」。好奇心も守る対象で、いちばん好きな仕事のいくつかにはクライアントがついたことがない。Manifesto と Aether はアイデアを試したかったから存在していて、エンタープライズのプラットフォームに載る発想の多くはそういう実験から生まれている。締めの一文が全体を要約しています。「最良のアイデアを届けようとして、利益として残せたはずのクライアント予算を大量に使ってきました。承認される類のアイデアではなく。つまり文化はこうです——正しくないものを納品して、それで支払われたなら、失敗です」。
