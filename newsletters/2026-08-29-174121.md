### [The AI-native SDLC playbook](https://claude.com/blog/the-ai-native-sdlc-playbook)

> **出典**: Sidebar | **公開日**: 2026-08-28 | **カテゴリ**: design

**3行まとめ**
- コードが制約でなくなったあと、開発プロセスの詰まりどころが計画・レビュー・デプロイへ移ったという整理から始まります
- 6つのステージそれぞれに「何を捨て、何をコミットされた成果物に置き換えるか」を対応表と手順で書き下ろしています
- 各ステージが `intent.md` / `spec.md` / `plan.md` といったファイルを書いて終わり、次のステージがそれを読んで始まる、という設計が全体を貫いています

**詳細解説**

Anthropic の Applied AI チームが顧客支援で積み上げてきた実践を、SDLC（ソフトウェア開発ライフサイクル）の全ステージ分まとめたガイドです。分量はかなりのもので、Plan / Design / Build / Test / Deploy / Maintain の6ステージに「プレイ」と呼ばれる単位が並び、それぞれに前提条件・実行手順・ガバナンス上の論点・測定方法が付いています。

出発点の観察はシンプルです。多くの組織はコード生成の速度だけを1年前と別物にした一方、その周囲にある承認ゲート、レビュー、引き継ぎ、ポリシーは何も変えていません。結果として3つのことが起きます。詰まりどころがビルドの左右（計画とレビュー・デプロイ）へ移動すること。人が1行ずつ読む前提の統制が、エージェントが差分の大半を書く現実に追いつかなくなること。例外処理が週次や月次の委員会を経由するため、ガバナンスのコストが上がること。セキュリティチームは人間の出力量に合わせて人員が組まれているので、エージェントが出力を増やすとレビュー待ちが積み上がるか、レビュー不足のままリリースされるかのどちらかになる、という具体例が挙がっています。

もっとも実装に近い部分は、ステージをつなぐ成果物の設計でしょう。企画は `intent.md` として発案者自身の言葉で書かれます。従来なら誰かが要件定義に翻訳してくれるのを待つところが、Claude とのブレストの結果をそのままバージョン管理下のファイルとして置く形になります。以降も同じ考え方で、承認された `spec.md` がプラン作成を起動し、マージされた PR がパイプラインを起動し、本番で制御帯域を割ったことが次の `intent.md` を書く。コミットの連なりがそのまま監査証跡（誰が何を依頼し、エージェントが何を出し、誰が承認したか）になるという主張です。

UXエンジニアリングの視点で拾えるのは、スキルとフックの役割分担の説明です。スキルは「組織の知識を運用可能にするもの」で、あくまで助言的な統制にとどまります。API セキュリティ標準を `SKILL.md` に書けば、コードを書いている最中にポリシーが適用される可能性は高くなりますが、セッションが従うことを強制はしません。例外なく守らせたいポリシーには、その背後に決定論的なもの、つまり操作をブロックするフックか、PR で再チェックするレビューパスが必要になります。「スキルが違反を稀にし、フックが違反をほぼ不可能にする」という切り分けは、デザインシステムのガイドラインと lint の関係にそのまま置き換えられます。毎回レビューで同じ指摘をしているルールがあるなら、それはスキルに書き出す候補で、絶対に崩せないものは検出側に落とすところまでやる、という判断軸になります。

測定の置き方も参考になります。各プレイに先行指標と遅行指標が対で用意されていて、たとえばスキルなら「ポリシー変更の承認からスキルのマージまでの時間」が先行指標、「そのポリシーを指摘する PR レビューの件数」が遅行指標です。後者がゼロに向かわない場合は、スキルが発火していないか、文面が公式ポリシーからずれているかのどちらか、と原因の切り分けまで書かれています。ここまで具体的に指標を設計している資料はあまり見かけません。

気になる点も正直に書いておくと、これは Anthropic 自身の製品ガイドでもあるので、Claude Code、Claude Security、Claude Tag といった固有機能への言及が全体に織り込まれています。ただ、`intent.md` から始まる成果物の連鎖、スキルとフックの二層構造、決定論的な検知と model 起動の分離といった骨格は、ツールの選択と関係なく持ち帰れる部分です。とくに Maintain のステージで「検知は完全に決定論的なまま、しきい値を割ったときだけモデルを呼ぶ」「1σ はログのみ、2σ は読み取り専用で診断、3σ で PR を開くところまで」と権限を段階化している設計は、自律的に動く仕組みを入れるときの現実的な型として使えそうです。

### [The Custodial Era of UX: Cleaning Up After AI](https://www.nngroup.com/articles/ai-ux-debt/)

> **出典**: Nielsen Norman Group | **公開日**: 2026-08-28 | **カテゴリ**: design

**3行まとめ**
- 生産が UX 評価より安くなった結果、UX の仕事が「白紙から設計する」から「AIの出力の何を残すか決める」に寄ってきたという整理です
- 新しいアイデア → 高速な実装 → 評価の遅れ → 体験の問題 → UX による後始末、という循環を「管理人（custodial）パターン」と名づけています
- 抜け出す道は3つ。何を作るかの判断を共有すること、評価を生産の速度に追いつかせること、そして生成のプロセス自体に UX の知識を入れることです

**詳細解説**

NN/g の Anna Kaley さんと Raluca Budiu さんによる、AI 時代の UX の立ち位置を扱った論考です。前の記事（Anthropic の SDLC プレイブック）が「速くなった生産に統制を合わせる」側から書かれているとすれば、こちらは「速くなった生産に評価が追いつかない」側から見た景色になります。並べて読むと、同じ現象の裏表がよく見えます。

中心にある一文が明快です。「AI で作られたものが本質的に悪いわけではない。問題は、生産が UX 評価より安くなったことにある」。体験を作る時間より、その体験が有用か・使えるか・信頼できるか・一貫しているかを判断する時間のほうが長くなってしまった、という状況の説明です。動くプロトタイプが目の前にあると、議論は「これは必要か」から「いつ出せるか」へ一瞬で移ります。

管理人パターンとして5段階が示されます。チームが機会を見つける、あるいは市場の勢いや「AIを使わなければ」という圧力に反応する。AI ツールで一気にプロトタイプや実装ができる。見た目が良いので調査も「そもそもこれは要るのか」の検討も飛ばして、リリース時期の話に移る。ユーザーの混乱、サポート依頼、伸びない利用率といった、プロトタイプ段階では見えなかった信号が出る。そして UX が評価・簡素化・修復を依頼される。UX を重視している組織でも起こりうる、という指摘が現実的です。

実務に効くのは、渡された機能をすぐ磨き始めないという助言でしょう。まずトリアージして費用対効果を見る。この機能はどんな問題を扱っていて、それが実在するニーズだという証拠はあるか。ユーザーの既存のメンタルモデルやワークフローにどう収まるか（既存の経路を重複させるのか、置き換えるのか、新しく覚えることを増やすのか）。追加される複雑さ、サポートや保守のコスト、そしてこの機能の周辺を作り直す機会費用まで含めるとどうか。トリアージの結果は「作り直す」だけではなく、残す・簡素化する・別のフローに統合する・リリースを延期する・削除する、のいずれもありえます。

3つ目の処方箋、「生成のプロセスに UX を入れる」がもっとも実装寄りです。同じ UX の問題が AI の出力に繰り返し現れるなら、毎回作り直すより、最初から起きないよう指示するほうが効率的だという理屈で、Design.md や UX.md のような UX コンテキストファイル、承認済みのインタラクションパターンを含むデザインシステム、コンテンツと書式の基準、アクセシビリティ要件、避けるべき欺瞞的パターンの一覧が候補に挙がっています。これは前の記事の「スキル」とほぼ同じ発想で、デザイン側から独立に同じ結論に到達しているのが興味深いところです。

締めくくりの言葉の使い方が効いています。custodian には「後始末をする人」と「大切なものを託された人」という2つの意味があり、UX が管理人であり続けるのは前者ではなく後者の意味においてだ、という着地です。古いプロセスそのものを守る必要はないけれど、そのプロセスが果たそうとしていたこと（人間のニーズを中心に技術を置くこと）は守る必要がある。掃除に追われている実感がある人にとっては、その時間を次の予防に変換する視点として読めます。

### [AI Gateway「Bifrost」の本番導入で、Technical Project Manager が担ったこと](https://tech.layerx.co.jp/entry/2026/08/28/180027)

> **出典**: LayerX エンジニアブログ | **公開日**: 2026-08-28 | **カテゴリ**: engineering

**3行まとめ**
- テナントごとに異なるデータレジデンシー要件を、アプリケーションではなくゲートウェイ側の Virtual Key で解決した事例です
- 4つの選択肢（アプリ内制御 / Azure API Management / LiteLLM / Bifrost）を ADR として比較し、採らなかった理由まで文書に残しています
- TPM の仕事を「課題の構造化・意思決定の文書化・分担の設計・コストの見積もり・リリース前の社内共有」として具体的に描いています

**詳細解説**

LayerX の Ai Workforce 事業部で TPM（Technical Project Manager）をしている urapico さんによる、AI Gateway の本番導入記です。技術選定の中身とプロジェクトの進め方が同じ密度で書かれていて、どちらか片方だけを読んでも成立するのに、通して読むといっそう納得できる構成になっています。

出発点の課題整理が丁寧です。3つに分けられています。1つ目はテナント単位のデータレジデンシー制御。あるテナントはリージョンを限定しないグローバル推論を使えるが、別のテナントは特定リージョン内で処理を完結させなければならない、というケースが実際にあります。契約で処理地域が指定されている業務、製造業の未公開設計情報、M&A・法務文書の処理などが例として挙がっています。2つ目は LLM プロバイダー障害への対応で、リトライやフェイルオーバーを各アプリに実装すると、再試行回数や切り替え先のルールがサービスごとに散らばり、複数サービスが同時にリトライしてレート制限中のプロバイダーへさらに負荷をかける可能性まで出てきます。3つ目は利用状況の可視化です。

設計上いちばん見どころがあるのは、データレジデンシーの制御を Virtual Key に寄せた部分でしょう。アプリケーション側は「US のテナントなので US の Virtual Key を使う」という責務だけを持ち、具体的なモデルエンドポイントや認証情報はゲートウェイが管理します。そのうえで、US 用のキーがグローバル用のプロバイダーへ紐付かない対応関係を config.json で作っているため、今後フェイルオーバー先を複数プロバイダーに広げても、要件を守ったまま可用性を上げられる形になっています。制御を1か所に集約すると抜け漏れが起きにくくなる、という設計判断が具体的なコードと設定で示されているのがいいところです。

技術選定の記述も参考になります。Azure 上で動いているサービスなので Azure API Management は親和性が高い選択肢でしたが、マルチクラウド対応やベンダーロックインを抑える方針、追加の利用料を考えて見送っています。LiteLLM については、対応プロバイダーの多さと機能の豊富さを認めたうえで、本番構成では Redis や PostgreSQL などの外部コンポーネントが必要になる点と、パッケージ公開経路の侵害インシデントが報告されていた点を挙げています。後者を「特定プロダクトの問題というより、認証情報を集約する AI Gateway 全般に共通するリスク」として評価軸に加えた判断は、フェアで応用が効きます。Bifrost を選んだ最大の決め手は、コア機能だけなら外部ミドルウェアなしで動き、依存コンポーネントを1つに抑えられることでした。

観測の設計で好感が持てるのは、「何を送らないか」に気をつけたと明記している点です。すべての LLM 通信がゲートウェイを通るので計装を1か所に集約できる一方、プロンプトや応答の本文には個人情報やセンシティブな内容が含まれます。Collector でマスクして監視 SaaS へ送らず、メトリクスも値の種類が少ない属性だけに絞る。可視化と情報保護を同時に成立させる、地味ですが重要な線引きです。OpenTelemetry の GenAI セマンティック規約（`gen_ai.*` 属性）に沿わせているため、どのアプリケーション経由でも同じ軸で分析できるようになっています。

UXエンジニアリングの視点で持ち帰りたいのは、進め方の記述のほうかもしれません。本番と同等のネットワーク制限を持つ環境で事前にリハーサルしたこと、リリース前にカスタマーサクセスへ動画とドキュメントで共有し、会議だけに頼らず非同期で理解できる形にしたこと。そして最後の一文、「振り返ると、このプロジェクトで私自身が書いたコードはごく一部です」。書いたコードの量ではなく、通した意思決定の量で仕事を測る、という職能の説明として読めます。デザイン側でも似た構造の仕事はあるはずで、その見えにくさをどう言語化するかのお手本になりそうです。

### [Workflow lab: Moving between design and code with agents](https://www.figma.com/blog/workflow-lab-moving-between-design-and-code-with-agents/)

> **出典**: Figma Blog | **公開日**: 2026-08-26 | **カテゴリ**: design

**3行まとめ**
- スクリーンショットとチケットだけを渡すと AI の出力がデザイン仕様からずれる、という前提から始まる架空チームのワークフロー実演です
- FigJam の図、Figma MCP サーバー、Code Connect、`search_design_system`、`get_variable_defs` を順に使い、エージェントに「システム」を渡していきます
- 最後は `use_figma` でコードだけに存在していたトーストを Figma のレイヤーとして書き戻し、両方向をつないで終わります

**詳細解説**

Figma の Workflow Lab シリーズの1本で、Radicle という架空の STEM 学習アプリのチームが受信箱の一括操作フローを作る話です。設定が具体的なので、どのツールをどの順で使うかが追いやすくなっています。

最初の失敗の描写に見覚えのある人は多いはずです。デザイナーが各画面を Figma で作り、開発者がそれをコーディングエージェントに渡す。コードはすぐ返ってくるものの、UI がずれている。アイコンが違い、モーダルの余白が不揃いで、トーストには失敗状態がない。午後いっぱいを手直しに使うこともできますが、この記事の開発者は一度立ち止まって、Figma の開発者向けツールからやり直します。

段取りが良いのは、プロンプトの前に計画を置いている点です。画面・状態・遷移の意図を書き出し、PRD と現在のコンポーネントのコードと一緒にエージェントへ渡したうえで、`generate_diagram` で FigJam に編集可能な図を作ります。この図はエージェントの材料になると同時に、開発が始まる前にチームが反応できるものにもなります。デザイナーとデザインシステムのリードが Slack のスレッドではなく図の上に直接フィードバックを残す、という書き方が具体的です。

その後の各ツールの役割分担が整理されています。Figma MCP サーバーがコンポーネント・トークン・レイアウトへのアクセスを与え、Code Connect が「どのコンポーネントか」から「それがどう実装されているか」へ橋を架けます。一括操作の選択状態だけは Code Connect で対応づけられていない新しい部品でしたが、ゼロから作る前に `search_design_system` でチーム全体のライブラリを検索し、数か月前に出荷した機能から似たコンポーネントを見つけてコードベース内の実装を流用しています。「チームがすでに作ったパターンをエージェントに発明させない」という一文が、この節の要点でしょう。

もっとも実務的なのは、ドリフト（ずれ）を検知する部分です。開発者が確認モーダルを実装している最中に、デザイン側でブランドカラーを暗くし、ボタンの角丸を変更してライブラリに公開しました。手で直す代わりに `get_variable_defs` を呼ぶと、モーダルで使われている変数が更新後の値で返ってくるので、エージェントがコード側のトークンと突き合わせて2か所の不一致をその場で直します。デザイン変更の伝達がチケットの文面ではなく変数の照合になるので、伝え漏れの余地が減るという話です。

そして締めが逆方向です。トーストはビルド中に作られたのでコードにしか存在せず、失敗状態が足りていませんでした。`use_figma` でトーストを編集可能なレイヤーとしてキャンバスへ置き、デザイナーが「再試行」アクションのある状態を足し、デザインシステムのリードが新しいコンポーネントとして公開して Code Connect でコードへマッピングする。実装から生まれた部品が正式にシステムへ戻る経路まで含めて描かれているのが、この記事のいちばんの価値だと思います。

UXエンジニアリングの視点でいうと、ここで実演されているのは「エージェントの出力品質を上げる方法」というより「デザインシステムの投資が何に効くか」の話です。Code Connect のテンプレート整備も、ライブラリの検索性も、変数として定義されたトークンも、人間だけが読む前提では後回しにされがちでした。エージェントが同じ資産を読むようになると、その整備の見返りが直接コードの精度に出ます。逆にいえば、システムが整っていない状態でエージェントに文脈を渡そうとしても、この記事の手順はそのままは効きません。何から手をつけるかの優先順位を考える材料として読むのが良さそうです。

### [How do you actually measure the impact of AI on design?](https://www.figma.com/blog/measuring-the-impact-of-ai/)

> **出典**: Figma Blog | **公開日**: 2026-08-28 | **カテゴリ**: design

**3行まとめ**
- AI の影響を測るために、消費者信頼感指数のような「センチメント指数」を6つの次元で設計した話です
- 639件の AI モデレーターによるインタビューを、自作の主題分析パイプラインで200万語・40,701コードまで処理しています
- 出来合いの分析ツールが不透明だったので、どのテーマがどの発言に遡れるかを追跡できる仕組みを自分たちで作った、という判断が中心にあります

**詳細解説**

Figma のリサーチチームが、複数年にわたる AI インパクト調査をどう組み立てているかを明かした記事です。調査結果そのものではなく、調査の作り方の話なので、リサーチの運用に関わる人にとって読みどころが多くなっています。

指数の設計思想がおもしろいところです。参照しているのはミシガン大学の消費者信頼感指数で、これは経済が実際にどうなっているかを測るものではなく、人々がどれだけ楽観的か悲観的かを捉えるものです。同じ読み取り方を AI に対して行いたかった、と説明されています。質問は「過去12か月、AI はあなたの生産性やワークフローにどの程度影響しましたか」と「次の12か月、どの程度影響すると予想しますか」の対になっていて、予想と実測を比べることで、AI が期待に追いついているのか、追い越しているのか、届いていないのかが分かる設計です。

6つの次元は、組織の目標、個人の生産性とワークフロー、他者との協働、取り組むプロジェクトの種類、会社の製品とサービス、使うツール。3年間同じ質問を使っているので推移が追えます。2026年はすべての次元が前年の予想を10ポイント以上上回り、協働は32から58へほぼ倍増、生産性・プロジェクト・製品は40台から60台後半〜70台へ上がっています。個人の生産性がチーム全体より先に動く、といった不均一さを見るために次元を分けた、という説明も筋が通っています。

インタビュー側の規模が目を引きます。AI モデレーターが実際に会話をリードし、文脈に応じて掘り下げの質問をする形で639件。結果として200万語の書き起こし、40,701のコード、11,846のテーマ、参加者をまたいで繰り返し現れたテーマが553件。人間のチームだけでは同じ時間でここまで集められなかった、と率直に書かれています。

自作した理由の説明がいちばん実務的です。試した出来合いのリサーチ分析ツールは不透明で、ツールがデータをどう解釈しているか見えなければ検算のしようがない。そこで、主題分析（すべての書き起こしを読み、各インタビュー内のアイデアに「コード」というラベルを付け、より広いテーマへ統合する標準的な手法）を、各ステップが見える形で組み直しました。たとえば「AI は反復速度を上げたが品質の課題を生んだ」というテーマを開くと、それに言及した47人が並び、実際の発言を読み、元の書き起こしまで遡れます。

品質面の指摘も納得できます。人間が数百件を手作業でコーディングすると、50件目は1件目と違う基準でラベル付けされてしまう。疲労が溜まり、解釈がずれ、早い段階で気づいたパターンが後半の読み方に影響します。ツールは同じ分析レンズをすべてのインタビューに毎回適用できる、という利点です。ただし記事は「AI に丸投げできる」とは言っていません。どの手法を使うか、どの粒度が欲しいか、対立するテーマをどう扱うか、テーマをどう書き起こしまで遡らせるか。明確な文脈を与える設計が必要だったと書かれていて、MIT の David Autor さんによる「expertise re-intermediation（専門性の再仲介）」という言葉が引かれています。AI は専門的な判断を不要にするのではなく、その判断をスケールさせる、という整理です。

UXエンジニアリングの視点で持ち帰れるのは、最後のダッシュボードの話でしょう。分析結果は数万のデータ点になり、ノートブックとテキストファイルの中では研究者以外に扱えません。3年分の調査結果とインタビュー分析と対話的なグラフをまとめた社内ダッシュボードを作った理由は、「レポートはチームスポーツだから」。ライター、マーケター、アナリストがそれぞれ散らばったメールやスライドから独立にメンタルモデルを作るのではなく、全員が同じソースから見る状態にする。ちなみにこのダッシュボード自体も、生データを自己完結した HTML に変換してから Figma MCP サーバーで数回反復して作られています。調査の道具を作るのもデザインエンジニアリングの仕事だと考えると、この作り方はそのまま真似できます。

### [AI Can't Replace Real Research in Empathy Mapping](https://www.nngroup.com/articles/ai-empathy-mapping/)

> **出典**: Nielsen Norman Group | **公開日**: 2026-08-28 | **カテゴリ**: design

**3行まとめ**
- 共感マップの付箋を AI に生成させることと、集めた調査結果を AI に整理させることの間には決定的な差があるという整理です
- AI が生成した発言と実調査から出てきた発言を製品ごとに並べた対比表が、その差をとても分かりやすく示しています
- 「これは組織できるデータか、それとも持っていないデータの生成か」という自問が、判断の分かれ目として提示されます

**詳細解説**

NN/g の Rachel Krause さんによる、共感マップと AI の関係を扱った短めの記事です。ワークショップの日程は決まっているのにデータが揃っていない、という状況で AI に手が伸びる気持ちを認めたうえで、「付箋がどれだけ速くできたかより、何から作られたかのほうが重要です」と切り出します。

対比表が秀逸なので、そのまま紹介します。食料品デリバリーアプリで AI が生成する発言は「商品を入れ替える前に確認してほしい」。実調査で出てくる発言は「オーツミルクが牛乳1ガロンに入れ替えられて、通知を見る前に課金されていた」。スケジュール管理ツールでは「カレンダーがうまく同期しないと困る」に対して「同僚が動かした後の新しい版があると知らずに古い版を見ていたので、14時が二重予約になっていた」。オンラインバンキングでは「お金が安全だと安心したい」に対して「まず1ドルだけ送金して口座番号を打ち間違えていないか確かめてから、残りを送る」。履修登録では「登録は緊張するしシステムが遅い」に対して「4人でグループ通話をつないで6時59分に一斉にリロードして、空きが出たら誰かが取れるようにする」。

AI 側の発言はどれも安全で、そのカテゴリのどんな製品にも当てはまってしまいます。だからこそ、誰のことも指していない。実調査側の発言は具体的で、そこにこそ共感マップの有用性が宿る、という論の運びです。

反論への答え方もフェアです。「もっと具体的な発言を書けとプロンプトすればいいのでは」という問いに対して、そのとおりだと認めたうえで、実ユーザーの発言が価値を持つ理由は具体性だけではないと返します。それは、その人が実際に言った・した・経験したことの証拠であるということ。作り出された観察は、どれだけもっともらしくても仮説にすぎません。

実務向けの切り分けも整理されています。正当な使い方は、すでに集めた調査から付箋を整理・クラスタリングすること、根拠が揃ったあとで言い回しを整えること、大量の発言からパターンを要約すること、あとで自分がレビューして直す前提の一次案を作ること。マップを損なう使い方は、存在しないユーザーに帰属させた発言・行動・感情を生成すること、薄い調査の隙間をもっともらしい文で埋めること、実施しなかった調査の代わりに「典型的なユーザー」を発明すること、誰もデータを持っていない象限を丸ごと生成すること。

締めに置かれた3つの自問がそのまま使えます。自分は AI に実データを整理させているのか、それとも持っていないデータを生成させているのか。この付箋は実際の調査の証拠まで遡れるか。もし AI なしで自分が思いついたとしたら、これを「発見」と呼ぶか「仮説」と呼ぶか。答えが居心地悪いなら、それは有益な情報で、たいていはマップにもっと調査が必要だという意味です、と書かれています。

前掲の Figma の記事と並べると、線の引き方が一致しているのが分かります。どちらも AI に処理させているのは実際に集まったデータのほうで、データそのものを作らせてはいません。速さの誘惑がもっとも強いのはデータが足りないときなので、この線を先に引いておくのが実際的だと思います。

### [The best workflow engine is a programming language](https://vercel.com/blog/the-best-workflow-engine-is-a-programming-language)

> **出典**: Vercel | **公開日**: 2026-08-27 | **カテゴリ**: frontend

**3行まとめ**
- ワークフローは DAG であり、DAG を書く道具はすでにある（プログラミング言語がそれだ）という主張から出発します
- Temporal を実運用して感じた3つの痛み（インフラ、実行中ワークフローのバージョニング、signal / query / update の分かりにくさ）に、それぞれ設計で答えています
- 「プラットフォームではなくライブラリ」という方針で、ストレージ・キュー・認証・ストリーミングを World という単一インターフェースの背後に隠しています

**詳細解説**

Vercel の Pranay Prakash さんが、Workflow SDK を作るに至った経緯と設計判断を書いた記事です。半年ほど週末に Temporal のフォークをいじって「Vercel らしい DX のサーバーレス版」を作ろうとした末に、それを届けるには実行環境そのものを持つ必要があると気づいてフォークを捨てた、という導入から始まります。

主張の骨格は明快です。ワークフローは有向非巡回グラフで、Apache Airflow に代表される多くのフレームワークはその DAG を手で描かせ、実際のロジックをノードの中に埋めてきました。しかし「これをやって、次にあれをやって、これらは並列で、ここで分岐する」を表現する道具はすでにあります。それがプログラミング言語で、抽象構文木は DAG そのものです。Temporal を見て、普通の逐次コードに見えるものを裏で耐久化してくれる形が「ずっと求めていた夢だった」と書かれています。

Temporal を実際に立ち上げて分かった痛みの列挙が具体的です。Temporal Cloud を用意するか、Frontend / History / Matching / Worker の各サービスと Cassandra や PostgreSQL などのバックエンドとシャーディングを自前で運用するか。ワーカー群を自分で持つこと（Temporal は自分のコードを実行しないので、実質的には自前の Kubernetes クラスタになります）。タスクキュー、アクティビティ登録、クライアント設定の配線。スケーリング、稼働、再起動、ワーカープロセスのビルドとデプロイの面倒。ワーカーが制御プレーンとインターネット越しに通信するための相互 TLS とペイロード暗号化の設定。

より根の深い問題として挙がるのがバージョニングです。実行中のワークフローがあるのにコードを変えると、古いバージョンを動かすワーカーはもういません。リプレイが古いイベント履歴で新しいコードを叩き、非決定性エラーで壊れます。公式の答えはパッチング API（`patched()` / `GetVersion`）で変更 ID による分岐を書き、古い実行が保持期間を過ぎるまで多段階の非推奨ライフサイクルを進めるというもの。動きはするけれど、変更を重ねるうちにワークフローのコードがバージョンフラグの藪になっていくと書かれています。

Workflow SDK の答えは、実行を「開始したデプロイメント」にピン留めすることです。実行は開始時のコードのコピーに対して動き続けるので、ワークフローを変えても進行中の実行が壊れません。ただしこの解決策は、Vercel が不変なデプロイメントを長期間保持しているから簡単に作れたものだ、と正直に書かれています。そのうえで「これは正しいトレードだと思う」と続きます。バージョニングの複雑さを、ワークフローを書く開発者から、World の作者・インフラ提供者・フレームワークの作者へ移す。フレームワークを使う全員が同じ難問に当たり、同じ苦しみ方で各自解決しているなら、そのフレームワークは失敗している、という一文が印象に残ります。

DX の話としてもう1つ良いのが、signal / query / update を hook 1つに置き換えた判断です。この3つは実行中のワークフローに出入りするための別々のプリミティブで、query はブロックできない、signal は投げっぱなしでバッファされる、どれを使うか知っている必要がある、と説明が必要でした。「ホワイトボードなしで human-in-the-loop のプリミティブを説明できないなら、それは複雑すぎる」という判断で、1つに統合しています。`createWebhook()` が実行中のワークフローの内部で本物の呼び出し可能な URL を1行で作り、誰かが POST するまで実行がそこで停まる、という例が示されています。承認フローが数秒でも数週間でも待てて、追加でデプロイするものは何もありません。

UXエンジニアリングの視点でおもしろいのは、最後の「ステップは無料であるべきだ」という節です。ステップの呼び出しにはネットワークとキューの往復があり、正しさのためにはそれが正解なのですが、オーバーヘッドが重いと抽象化が漏れ始めます。ステップを節約するようになり、粒度を考えるようになり、小さな関数をチェックポイントにするのは「ステップに見合わない」と判断してしまう。普通のコードを書くとき関数呼び出しのコストを二度考えないのと同じ状態にしたい、という目標の立て方は、UI の抽象化を設計するときの感覚にも通じます。使うたびにコストを見積もらせる部品は、結局使われなくなります。

### [Moving a 400-route app from Next.js to TanStack Start](https://react.statuscode.com/issues/488)

> **出典**: React Status | **公開日**: 2026-08-28 | **カテゴリ**: frontend

**3行まとめ**
- Lovable が約400ルート・85万行超を Next.js から TanStack Start へ移した事例が巻頭に置かれています
- 両フレームワークをプロキシの背後で並走させ、コードを共有フォルダで持つという移行の作り方が中心です
- Next.js に未認証の重大な RCE が2件パッチされたので、16.3.3 または 15.5.24 への更新が必要という注意も入っています

**詳細解説**

React Status の第488号です。単一記事ではなくニュースレターなので、拾える話題が広いのが利点になります。

巻頭は Lovable の移行記です。Vercel 上で動いていた Next.js アプリ、約400ルート・85万行以上のコードを、自社プラットフォーム上の TanStack Start へ移しました。この規模の移行で気になるのは「どう切り替えたか」ですが、答えは両方のフレームワークをプロキシの背後で並走させ、共有フォルダにコードを置くというものです。一括の切り替えを避けて段階的に移す、という定番の手法ですが、85万行規模で実際にやりきった記録は貴重でしょう。

もう1つの比較記事も紹介されています。SVAR は同じデータグリッドを React、Vue、Svelte で出しているのでフレームワークの差をよく知っている立場ですが、その差が性能に効くのかを検証したところ、ほとんど効かないという結論でした。勝者は宣言されず、「速いデータグリッドの高価な部分は、ほぼ完全にフレームワーク非依存だった」という引用が置かれています。フレームワーク選定の議論で性能を前面に出しがちな場面では、この観察が効きます。

React 本体の動きも2つ拾われています。Canary チャンネルに `browser()` API が入り、サーバーでレンダリングできないコンポーネントに対して `use(browser())` を書くと、そのコンポーネントのサーバーレンダリングを止めて直近の `<Suspense>` のフォールバックをそこに置き、ブラウザで通常どおりレンダリングします。もう1つは parallel transitions が Canary ビルドで既定オンになったこと。React Native も含み、すでに Meta の本番で動いていて、React 19.3 に入る可能性があるとのことです。

アセットの話も見逃せません。Three.js で GLB にきれいにテクスチャを当てられるので Cinema4D 側でのテクスチャリングが不要になり、各メッシュにロード時に独自のマテリアルが割り当てられるため、エクスポーターが書いた PBR マップは全部が無駄でした。それを剥がして weld と quantize をかけると、メイン CD の GLB が 9.7MB から 182KB になり、見た目の差はまったくありません。50分の1です。

UXエンジニアリングの視点で拾いたいのは、外部の専門性を早めに入れている点でしょうか。音は友人の Lane Fujita さんに依頼していて、返ってきたのは音源だけでなく、タイミングと「いつ鳴らし、いつ鳴らさないか」を明記した詳細な仕様書でした。演出を作るときに音が後付けになりがちなのに対して、最初の「Insert Disc」画面が音を前面に置くための仕掛けとして設計されている。Claude Code を使って自分の快適圏の外に出た、と冒頭で書いていることも含め、制作の進め方の記録としても読めます。

### [Futurism is always extreme](https://borretti.me/article/futurism-is-always-extreme)

> **出典**: Sidebar | **公開日**: 2026-08-28 | **カテゴリ**: design

**3行まとめ**
- 長期の未来について厳密に考えると、その帰結は構造上、必ず極端になるという議論です
- 「厳密に考える」とは、世界の状態を表す形式と、状態を進める遷移関数を持つことだと定義されます

**詳細解説**

Fernando Borretti さんによる短い論考です。分量は少ないのですが、議論の運びがきれいなので紹介します。

主張は冒頭の一文に集約されています。「長期の未来についての厳密な思考は、どれも極端な帰結に至る。構造上、平凡でありふれた未来を生み出すことはできない」。

「厳密な思考」の定義が明確です。モデルを持つこと、つまり世界の状態を表現する形式と、状態を先へ進める遷移関数を持つこと。世界をその形式に入れ、クランクを回して次々と状態を得ます。モデルには定性的なものと定量的なものがあり、未来についての思考の大半は定性的で非形式的です。「知性」のような曖昧な性質についての傾向として考えることになります。

例として挙がるモデルは2行だけです。現在、人間はコンピュータより賢い。コンピュータは、人間が賢くなるより速く賢くなっている。ここから導けるのは、将来のどこかでコンピュータが人間の知性に並び、その後は超えるということ。そして情報処理の物理について妥当な仮定を置けば、極限においてコンピュータは人間の知性を大きく上回るということ。ただし、それがいつ起きるかは言えません。定性的なモデルは世界が通過する離散的な状態の列を教えてくれますが、時刻は教えてくれない、という整理です。

定量的なモデルは時間の解像度が上がる代わりに、細かい予測が効くのは近い未来だけになります。そこで著者は、実存的な意味で本当に問題なのは「究極の未来」だけだと言います。ここでの「究極」は「長期」ではなく、書き換え規則がもうこれ以上適用できない状態、つまり正規形という意味です。だからモデルが安定するまでクランクを回し続けることになる。そして安定状態は2つしかない、というのが結論です。天国か地獄か。特異点、自己増殖する宇宙探査機、主観時間で毎秒100万年を生きるアップロードされた精神、マトリョーシカ脳のために赤外線まで暗くなった銀河、オメガポイント。あるいは、崩壊してゼロになる。

UXエンジニアリングの視点で持ち帰るなら、これは未来予測そのものより「モデルの性質が結論を決めてしまう」という指摘として読めます。正規形まで回し切る前提を置いた時点で、極端な帰結しか出てこない構造になっている。AI について「10年後どうなるか」を語る文章を読むとき、その論者がどんな遷移関数を暗黙に置いているかを見る癖がつきます。極端な結論が出てきたら、それは世界についての発見ではなくモデルの構造の反映かもしれない、と一度疑えるようになるのが、この短い文章の実用的な価値だと思います。

na2kera さんの発表も具体的でした。内定者インターン中、自分ではコントロールできない問題に悩んで手が止まってしまった経験から、一人で悩み続けるのではなく、自分ができる範囲を見極めて「悩む」から「根拠を探して迷う」状態へ切り替えることの大切さを語っています。この言い換えは良いと思います。悩むには出口がないけれど、根拠を探して迷うには次の行動があります。

teruya さんの「極力登壇したくないあなたへ、極力登壇したくないわたしより」というタイトルも良く、内容は締め切り駆動での小さな進捗、思考の外部化、物理的な緊張ほぐしという3つのハックでした。課題を細かく砕いて不確実性を減らす考え方はプロダクトエンジニアの仕事にも通じる、というまとめ方に納得感があります。
