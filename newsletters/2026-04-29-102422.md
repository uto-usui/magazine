### [Scroll-Driven Animations](https://www.joshwcomeau.com/animation/scroll-driven-animations/)

> **出典**: Josh W Comeau | **公開日**: 2026-04-28 | **カテゴリ**: frontend

**3行まとめ**
- スクロール量に応じてキーフレームアニメーションを進行させる Animation Timeline API の解説。
- `animation-timeline: view()` と `animation-range` の組み合わせで、要素のビューポート進行度に紐づけた表現が CSS だけで書ける。
- `view-timeline` と `timeline-scope` を使えば、別要素のスクロール位置で離れた要素のアニメーションを駆動できる。

**詳細解説**

これまでスクロール連動アニメーションは IntersectionObserver や `scroll` イベントで JavaScript 制御するのが定番でしたが、Animation Timeline API はキーフレームの進行軸を「時間」から「スクロール距離」に置き換えるシンプルな発想で、既存の `@keyframes` をそのまま流用できます。Josh W. Comeau は、`view()` と `scroll()` の使い分け、`cover` / `contain` / `entry` / `exit` で範囲を切り替えられる点、`linear()` のスプリングカーブまで併用できる柔軟さを実例で示しています。

UX エンジニアリングの観点で興味深いのは、JavaScript 主導のスクロールアニメーションに比べてメインスレッドの負荷が小さく、設計上の責務分離もしやすいところでしょう。レイアウトに紐づく演出を CSS のレイヤーに戻すことで、状態管理コードと演出コードが分離し、デザインシステム側で再利用可能なトークンとして組み込みやすくなります。

一方で、スプリング演出を `linear()` の長大な値で表現する例には著者自身も「ちょっと呪いっぽい」と書いている通り、可読性とパフォーマンスのバランスは設計者の判断が問われる領域です。動きを過剰にすればアクセシビリティの面で `prefers-reduced-motion` を必ず併用するなど、配慮も欠かせません。

### [CSSカスタムハイライトAPI - DOM操作なしでテキストをハイライト](https://ics.media/entry/260427/)

> **出典**: ICS MEDIA | **公開日**: 2026-04-26 | **カテゴリ**: frontend

**3行まとめ**
- `Range` と `Highlight` オブジェクト、`::highlight()` 疑似要素を組み合わせ、DOM を書きかえずにテキストの一部をハイライトできる API の入門記事。
- 検索語のリアルタイムハイライト、入力校正、AI による感情ヒートマップなど、実用的なデモを 3 つ紹介。
- Chrome / Edge / Safari / Firefox の主要ブラウザで利用可能になり、いまから採用しても問題ない段階に入った。

**詳細解説**

検索ハイライトや構文チェックの可視化のような UI を作るとき、これまでは `<span>` 挿入や Mark.js のようなライブラリでテキストノードを切り刻む必要がありました。CSS Custom Highlight API は DOM を一切いじらず、JS 側では `Range` の範囲指定だけ、CSS 側では `::highlight(name)` の疑似要素だけで完結させる仕組みです。マークアップとスタイルが綺麗に分離されるので、サーバーから取得したテキストの即時ハイライトや、ユーザー入力に応じた動的ハイライトが、フレームワークの仮想 DOM と衝突せずに実装できます。

UX エンジニアリングの視点では、テキストエディタ、ドキュメント検索、コードビューア、AI 出力のソース根拠提示など、表示テキストの構造を変更したくない局面で大きな利点があります。`<span>` を差し込まずに済むということは、`copy` や `selection` の挙動が壊れにくく、スクリーンリーダーへの読み上げ順序も維持されやすいということです。

注意点としては、`Range.setStart()` の引数にテキストノードではなく要素ノードを渡すと意図しない範囲を指すこと、そしてビルドツールで空白がミニファイされる場合に範囲が変わる可能性が挙げられています。複数のキーワードを別々のスタイルで重ね合わせられる柔軟性もあるので、UI 内でレイヤー化された注釈表現を考えるときの選択肢として頭に入れておきたい API です。

### [Long-running Agents](https://addyosmani.com/blog/long-running-agents/)

> **出典**: Addy Osmani | **公開日**: 2026-04-28 | **カテゴリ**: performance

**3行まとめ**
- 数時間〜数週間にわたって作業を継続する「長時間稼働エージェント」の現状と設計パターンを、Anthropic / Cursor / Google の事例を横断的にまとめた長編記事。
- 共通の課題は「有限のコンテキスト」「永続状態の欠如」「自己検証ができない」の 3 点で、いずれも brain / hands / session の分離設計で対処する流れ。
- 開発者目線では Ralph ループのようなシェルスクリプト＋外部ファイルでの状態管理から始めるのが現実的で、`AGENTS.md` や進捗ファイルなど「外部に状態を置く」設計が鍵。

**詳細解説**

「AI エージェント」の主流イメージはチャット欄でループするものでしたが、コンテキストウィンドウが満たされる前にタスクが終わるか、自分で「完了」と宣言してしまう問題が露呈してきました。Addy Osmani はこれを乗り越えるための長時間稼働エージェントを「長期推論」「長時間実行」「永続的なエージェンシー」の 3 つに分けて整理しています。METR の time horizon メトリクスでは、1 タスクの完了時間が 7 ヶ月ごとに倍増しており、2028 年には日単位、2034 年には年単位のタスクをこなす予測が出ています。

技術的な要点は明快で、ステートをモデルの外に置くこと、生成と評価を分離すること、そしてセッションをイベントログとして再構成可能にすることです。Anthropic は initializer / coding の二段構成と planner / generator / evaluator の三役分離を打ち出し、Cursor は planner / worker / judge という近い構成にたどり着いています。Google の Agent Platform はこれをマネージドサービスとして提供し、Memory Bank と Agent Sessions、Sandbox、Identity を組み合わせる形です。

UX エンジニアの実務に引き寄せると、`CLAUDE.md` のような外部の計画書と `progress.txt` のような外部のログを組み合わせる Ralph ループが、すぐ試せる入口になります。重要なのは、コードを書くスキルよりも「自律実行に耐える仕様を書くスキル」が価値を増しているという指摘で、デザインドックや受け入れ条件をエージェント前提で書き直す力が次の差別化要因になりそうです。コスト管理、認証情報の隔離、アライメントドリフト、検証のためのオブザーバビリティといった運用上の課題は依然として残っており、安易にプロダクションへ持ち込まないだけの慎重さも必要です。

### [How will AI change operating systems? Part 1: Ubuntu and Linux](https://newsletter.pragmaticengineer.com/p/ubuntu-and-ai)

> **出典**: The Pragmatic Engineer | **公開日**: 2026-04-28 | **カテゴリ**: engineering

**3行まとめ**

- ハードウェアエネーブルメント（GPU / NPU / DPU）と CUDA ツールチェーンの統合、x86_64 アーキテクチャバリアントの最適化など、OS が AI に向けて踏み込んでいる領域を整理。
- ローカルファースト戦略やエージェンティックワークフローへの構想、各 Linux ディストリの動きまで俯瞰できる。

**詳細解説**

OS ベンダーの視点で AI 対応とは何か、というテーマは普段 UI 寄りの開発者にはやや遠い話題ですが、ローカル LLM や NPU を活用した端末側推論が広がるにつれて、フロントエンド開発者にとっても無関係ではなくなってきました。Canonical の Jon Seager は「アプリの機能と OS の境界を曖昧にしない。OS にできる最も強力なことはハードウェアエネーブルメントだ」とし、NVIDIA / AMD / Intel との直接連携、CUDA ツールキットの apt 一発インストール、x86_64 v3 への対応などをひとつずつ進めている経緯を語っています。

技術的にとくに目を引くのは、x86_64 のアーキテクチャバリアントごとに別バイナリを配布する取り組みです。これまで Ubuntu は最古の v1 を基準にしていましたが、ビルドパイプラインを刷新して v3 向けのバイナリを提供できるようになり、AVX-512 のような新命令を活かせるようになりました。NPU を使ったローカル推論や ARM64 ラップトップ対応も同じ流れの一部で、開発者の手元で AI を動かす環境がどんどん整っていくことを示しています。

UX エンジニアリングへの含意としては、ローカルで完結する AI 機能（オンデバイス文字起こし、AI 補助の入力、画像補正など）が現実的になることで、オンライン前提の API 設計やレイテンシモデルが見直される可能性がある、ということです。WSL の普及や ARM64 ラップトップへの最適化も、開発体験そのものを底上げする話で、フロントエンド側のビルド・配布戦略にも波及していきます。記事は Part 1 で、Windows 編は次回予告として残されている点も踏まえ、続報を追っておくとよいでしょう。

### [ETCカードに対応するため、クレジットカードの決済を無停止でDBマイグレーションするときに考えたこと](https://tech.layerx.co.jp/entry/migrate-card-db-for-etc-card-support)

> **出典**: LayerX エンジニアブログ | **公開日**: 2026-04-28 | **カテゴリ**: engineering

**3行まとめ**
- バクラクビジネスカードに ETC カードの決済データを乗せるため、3 年分のレコードを抱えた本番 DB を無停止でマイグレーションした事例。
- テーブルを「決済処理 API に紐づく系統 A」と「Webhook 経由の非同期処理に紐づく系統 B」に分け、それぞれに合った変更戦略を選択した。
- 本番クローン環境で実データ量による DDL の所要時間を事前計測し、自信を持って本番投入できた。

**詳細解説**

決済領域は止められない上にレコード量も巨大、というハードな制約のもとで、テーブル設計の考え方をユースケース別に切り分けるアプローチが特徴的です。系統 A の API 側テーブルは応答時間制約がきついので、親テーブルに種別カラムを 1 つ加え、ETC 固有の付随情報を新規テーブルに切り出す最小限の変更にとどめています。一方、系統 B の Webhook 受信テーブルは多少時間がかかってもキューで再処理できるため、共通テーブル＋種別ごとのサブテーブルという踏み込んだ整理に踏み切っています。

UX エンジニアリングの目線で参考になるのは、設計判断を「全テーブルで同じやり方」に揃えないこと、本番のユースケースを先に観察してから戦略を決めることの重要性です。ECサイトの注文テーブルへの配送種別追加や、SaaS の課金プラン拡張など、SLA の厳しい経路と緩い経路が混在する場面は他の業界にも普遍的に存在します。フロントエンド側でも、同じ API リソースに対して種別カラムが増える運用が始まると、クライアント側のコンポーネント分岐戦略にも影響します。

実データ量での DDL 計測、Bytebase をフロントに置いた本番クローンでの事前検証、`ALGORITHM=INSTANT` で完了するか・テーブルコピーになるかの確認といった具体プラクティスもよく整理されており、サービス無停止のスキーマ変更を考えるときの実務的なテンプレートとして読めます。

### [AI エージェントをチームで導入していくまでの道のり](https://tech.smarthr.jp/entry/2026/04/28/165243)

> **出典**: SmartHR Tech Blog | **公開日**: 2026-04-28 | **カテゴリ**: design

**3行まとめ**
- SmartHR の労務領域チームが、1 年かけて AI エージェントをチーム開発の標準にしていった試行錯誤の記録。
- 「AI 縛り週間 → ツラミ・知見共有会 → Skills 勉強会 → モブ作業」という段階的な施策で、個人差をならしながらチームの底上げを進めた。

**詳細解説**

「個人最適はスケールしない」「コンテキスト投入が属人化する」「ツール乱立で運用コストが爆発する」という、多くのチームが直面する現実的な課題からスタートしている点が共感しやすい記事です。1 週間の AI 縛りで全員がいったん詰まる体験を作り、その後の打ち手の必然性を引き出したのは、現場の納得感をつくるうえで巧妙な設計といえるでしょう。

UX エンジニアリングの観点では、Skills 勉強会とモブ作業を組み合わせる流れに注目できます。Skills はドキュメントだけ読んでもピンと来にくく、`/skill-creator` を使って自分で作ってみる体験を用意したことで、「コーディング以外の業務にも AI を使う」発想が広がったとあります。さらに、画面共有しながら 2 人で 1 セッションを操作するモブ作業によって、レビュー観点や指示の勘所が暗黙知のまま共有される構造を作っています。

導入に唯一の正解はなく、施策ごとに新しい課題が顔を出すという観察も率直で、Harness Engineering まで含めた長期的な視座を持つチームの姿勢が伝わってきます。「個人では使えるけれどチームに広がらない」と悩むエンジニアリングマネージャーやテックリードにとって、自分たちの現在地を測る材料になる記事です。

### [How I built an AI tool that does real content design](https://uxcontent.com/ai-content-design-tool/)

**3行まとめ**

実装で参考になるのは、コンテンツスキルが製品スペックや調査結果を読みに行く設計です。文字列を見る前に状態と利用可能なアクションを把握することで、「この問題はコピーではなく構造の問題」と切り分けられるようになっています。AI で UX ライティングを底上げしたい、という以前に「コンテンツデザインがインフラだ」という基本姿勢を、AI ツール設計に落とし込んだ良いケーススタディです。

ナッジは強力な道具ですが、文化や年齢層、プライバシー意識によって受け取られ方が異なる点も指摘されています。集団主義文化では社会的証明が効きやすい一方、プライバシーに敏感な社会ではデフォルトのオプトインが侵害的に映る、という観察は、グローバル展開するプロダクトでは無視できません。記事末尾の監査フレームワークは、デザインレビューや A/B テストの設計時にチェックリストとして転用しやすい構成になっています。

### [New to the web platform in April](https://web.dev/blog/web-platform-04-2026?hl=en)

> **出典**: web.dev | **公開日**: 2026-04-24 | **カテゴリ**: web-standards

**3行まとめ**
- 2026 年 4 月の Chrome 147 / Firefox 150 で安定版に降りてきた Web プラットフォーム機能のまとめ。
- `contrast-color()` がベースラインに、スクロール駆動アニメーションの `animation-range-*` プロパティもベースライン入り。
- `ariaNotify()`、`<img sizes="auto">`、要素スコープの View Transitions、`border-shape`、SVG `<textPath>` の path 属性なども追加。

**詳細解説**

UX エンジニアリングの視点では、`<img sizes="auto">` が遅延読み込み画像のレスポンシブ対応を簡素化してくれること、`border-shape` で矩形以外のボーダーが扱えるようになること、`Math.sumPrecise` で誤差なしの合計が標準で使えるようになることなど、地味だが実装の選択肢を増やす変化が並んでいます。Safari は今月安定版がない一方、Beta では `:open` 疑似クラスのサポートなど準備が進んでおり、来月以降の流れも気になるところです。

### [AI reads my meetings. I take more notes than ever.](https://crixu.blog/2026/04/09/ai-reads-my-meetings-i-take-more-notes-than-ever/)

> **出典**: Sidebar | **公開日**: 2026-04-28 | **カテゴリ**: design

**3行まとめ**
- AI ミーティングツールに会議の議事録を任せたら、書き起こしの精度は高いのに「重要さ」を取り逃がしていることに気づいた、という PM の体験記。
- AI は「何が話されたか」、手書きノートは「なぜそうなったか・違和感の正体」を担当する、二系統の併用が機能する。
- ノートは記録ではなく自分の解釈の場であり、リアルタイムで「何が大事か」を判断する筋肉を鍛え直す装置として再定義する。

**詳細解説**

UX エンジニアリングへの含意としては、AI を入れることで省ける動作と、あえて省かないほうがよい動作がある、ということです。会議ノートを取る行為は、書き留めること自体が目的ではなく、聞きながら判断する練習になっている。AI に書き起こしを任せた途端、その判断の練習が抜け落ちてしまいます。プロダクト設計でも、ユーザーがやっている小さな儀式を AI が肩代わりすることで、別の能力が知らず知らず萎えてしまう可能性に気を配る必要があります。

「AI は recall が得意で judgment が苦手」「自分の手書きノートは recall は最悪だが、その場で判断を強いる」という対比は、ツール選定のメンタルモデルとして覚えておきたいフレームです。AI 議事録を導入したものの何かが薄まったと感じている人にとって、運用を立て直すヒントになります。
