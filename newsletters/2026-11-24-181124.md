### [On drawing icons](https://pierre.computer/writing/on-drawing-icons)

> **出典**: Sidebar | **公開日**: 2026-11-24 | **カテゴリ**: design

**3行まとめ**
- Pierre が、自社のプロダクトで使うアイコン 1,200 以上を 12・16・24px の3サイズで描き直しました。線の太さはサイズごとに 1px・1.25px・2px と決め、Figma の変数に入れています
- Figma では、ファイルやフォルダの形、プラスやバッジを部品にして組み合わせています。元の形を1か所直すと、関連する20ほどのアイコンが一緒に変わります
- Figma から React のコンポーネントを直接書き出す試みはやめ、Figma とリポジトリのあいだは SVG と manifest.json で受け渡すことにしました

**詳細解説**

確認は2段に分けています。書き出しのたびに、足りないバリエーション・重複・位置のずれを Figma のノード ID 付きで REPORT.md に書き出し、直すときは Figma から探せるようにしています。そのあと、生成した静的な HTML のプレビューで見た目を確かめます。プレビューには、アイコンを 13px の文字と並べたナビゲーションの一覧もあります。数値のうえでは中央にあっても、文字の横では高く見えたり重く見えたりするアイコンがあり、アイコンだけを並べた一覧ではそれに気づけないためです。既存のアイコンセットを選ぶときも、候補をラベルと同じ大きさの文字と並べて比べておけば、入れてから重さや位置のずれに気づく手戻りが減ります。

Figma で部品を組み合わせる作り方は、React には持ち込んでいません。React の側でもバッジを組み合わせる案（`<IconFile badge="clock" />`）を試すと、ファイルにバッジを1つ付けたアイコンは、組み合わせた場合 gzip で 2.81KB、1つのアイコンとして書き出した場合 1.40KB で、組み合わせたほうが倍ほど重くなりました。Figma で図形をフラット化すると、1px ずれることもありました。`size` は、そのサイズ用に描いた絵を選ぶ指定です。1 枚の SVG を拡大しているわけではなく、描いていないサイズは型の段階で選べないようにしています（`12 | 16` など）。

### [The Compacting Sidebar Blues](https://blog.master.dev/the-compacting-sidebar-blues/)

> **出典**: Frontend Masters Blog | **公開日**: 2026-11-24 | **カテゴリ**: css

**3行まとめ**
- 縦に短い画面でアプリのサイドバーがスクロールしないよう、ナビゲーションのラベルを隠してアイコンだけにする切り替えを、CSS だけで作っています
- `scroll-state(scrollable: y)` の container query で「スクロールが出たらラベルを隠す」と書くと、隠した途端にスクロールが消えてラベルが戻り、またスクロールが出ます
- 項目1つの高さに `sibling-count()` を掛けて上限を出し、style query で `--sidebar-h < --limit` と比べると、この繰り返しを起こさずに切り替えられます

**詳細解説**

項目の数、フォントの描画、アイコンの大きさのどれかが変わると、画面で測った 500px のような固定値は合わなくなります。計算で出そうにも、container query や media query の条件には `var()` を書けません。style query ならカスタムプロパティどうしを比べられるので、`--sidebar-h` と `--limit` を `@property` で `<length>` として登録してから比べています。

残る固定値は、文字の高さの 14px だけです。項目のあいだに `<hr>` などを入れると、`sibling-count()` の数がずれて計算が合わなくなります。ラベルは `display: none` にせず、`clip-path: inset(50%)` などで見えなくしているだけなので、スクリーンリーダーには読まれます。

Chrome 142 以降と Firefox 154 以降で動きます。Safari は style query の範囲の書き方にまだ対応していませんが、ラベルが出たままになるだけで、サイドバーが使えなくなることはありません。これまで ResizeObserver で高さを見てクラスを付け替えていた処理を、CSS に移せるかもしれません。

### [Claude Projectsを使って、複数のリポジトリにまたがるtextlintとルールのパフォーマンスを改善した](https://efcl.info/2026/11/24/textlint-performance/)

> **出典**: Web Scratch | **公開日**: 2026-11-24 | **カテゴリ**: frontend

**3行まとめ**
- textlint と、よく使われるルールやライブラリを2週間かけて直し、実行時間を約10分の1にしました。設定は変えずに、textlint とルールを更新するだけで速くなります（textlint v16 は Node.js 22.12.0 以降が必要です）
- 本体・ルール・ルールが使うライブラリは別々のリポジトリにあるので、Claude Projects の1つのプロジェクトにまとめて進めました。Pull Request を出したリポジトリは30以上あります
- 「既存のルールと設定がそのまま動き、同じ結果を返す」を条件にし、変更の前と後で同じ文書を lint して、結果が変わらないことを確かめながら直しています

**詳細解説**

最初に `textlint --profile` を足し、設定の読み込み、ファイルの検索、パース、AST の走査、ルールの実行にかかる時間を、ルールごと・ファイルごとに出せるようにしました。Pull Request ごとに、変更前と変更後の lint の結果と実行時間を比べる CI も入れています。互換性の確認には、約1万ファイルある MDN の日本語版を使いました。ドキュメントの lint が遅いなら、textlint とルールを更新したうえで、`--profile` の出力から重いルールを探せます。

どこで時間がかかっていたかは、ルールによって違いました。preset-jtf-style はノードごとに正規表現を作り直していたので、1回だけ作るように直しています。preset-ja-technical-writing は実行時間の約70%が形態素解析だったので、形態素解析をしていた kuromojin を自前の解析器に置き換えました。その結果、jtf-style で MDN を lint する時間は 75.5秒から 7.17秒に、ja-technical-writing で js-primer を lint する時間は 40.6秒から 4.10秒になっています。

どこまで速くなるか見通しが立たない改善は、別のスレッドで先に試しています。kuromojin では、最初の試作で60%ほど削れました。形態素解析の時間を0にした場合も測って削れる上限を出し、そのうえで80%減を目標にしています。方向が決まったものは、仕様を書いてから実装しています。辞書に単語を足すと lint の結果も変わるので、メジャーバージョンのなかでは辞書を変えず、`dictionaryVersion` で日付を指定したときだけ新しい辞書を使うことも、仕様の段階で決めています。

### [Computing with CSS Layout](https://noscript.ing/compute)

> **出典**: Sidebar | **公開日**: 2026-11-23 | **カテゴリ**: design

**3行まとめ**
- グリッドやフレックスボックスが要素を並べるときに計算した幅を、CSS から数として読み出し、最大値・合計・並べ替えに使う手法です。記事では、折れ線グラフの縦軸の上限もこれで決めています
- `container-type: inline-size` の要素のなかで `round(100cqw / 1px)` を計算し、`@property` で `<integer>` として登録したカスタムプロパティに入れると、幅が数になります
- この手法を集めたライブラリ dCSS も公開されています。`<figure>` に class を付けて数を `<li>` に並べると、合計・平均・中央値などを出せます

**詳細解説**

`auto` の列はいちばん幅の広い要素に合わせて広がるので、その列の幅がそのまま最大値になります。フレックスボックスの行の幅は子の幅の合計で、`order` に値を入れれば小さい順に並びます。

記事の計測（Chrome、300個の数）では、順位を出す処理を `calc()` だけで書くと 95ms かかり、CSS も 5.0MB 要りました。レイアウトに計算させると 6ms です。並べ替えも 36.8ms から 3.2ms に縮んでいます。累積和だけは、`calc()` だけで 0.7ms、レイアウトを使って 0.8ms と、ほとんど変わりません。

読み出した数を使う要素は、読み出した要素のなかに置く必要があり、マークアップは3段になります。`order` は整数しか受け付けません。使う機能の多くはこの3年で Baseline に入りましたが、長さを長さで割る書き方（`100cqw / 1px`）は Baseline の項目がなく、Chrome 140、Safari 26、Firefox 158 以降で動きます。仕組みは細かい仕様の組み合わせで、チームのほかの人が読んで直すのは難しそうです。使うなら dCSS の class を呼び出すだけにして、仕組みには手を入れないほうが扱いやすいでしょう。dCSS では、数を並べたリストをスクリーンリーダーから隠し、図のキャプションで同じ数を言葉にしています。

### [Reactはここまで変わった！ メモ化・Effect・アニメーションの最新事情](https://ics.media/entry/261119/)

> **出典**: ICS MEDIA | **公開日**: 2026-11-23 | **カテゴリ**: frontend

**3行まとめ**
- React 19.3（2026年9月）で `<ViewTransition>` が安定版になりました。並べ替えなどの state の更新を `startTransition` で包むと、`<ViewTransition>` で囲んだ要素がアニメーションで動きます
- React Compiler を入れると、`useMemo`・`useCallback`・`memo` による手動のメモ化は、ほとんど書かなくてよくなります
- `useEffectEvent` は、Effect のなかで最新の state を読みたいけれど、その state が変わるたびに Effect をやり直したくはないときに使います

**詳細解説**

5秒ごとに入力を自動で保存するメモアプリで、入力の値を `useEffect` の依存配列に入れると、1文字打つたびにタイマーがやり直しになり、いつまでも保存されません。保存の処理を `useEffectEvent` に移すと、依存配列から入力の値を外せます。ただし、再実行を避けるためだけに使うと、どの値が変わったときに処理が走るのかをコードから読み取りにくくなる、と注意しています。そもそも `useEffect` は本当に必要なときだけ使うよう勧めています。

React 19.2 からは、Chrome DevTools の「パフォーマンス」タブに React のトラックが出ます。「Scheduler」トラックでは、ユーザー操作に伴う更新（Blocking）と、`startTransition` で優先度を下げた更新（Transition）が分かれて表示されます。開発用のコマンドで立ち上げれば出ますが、本番用のビルドでは出ないので、本番に近い状態で見るにはプロファイリングビルドを使います。入力が重いと言われた画面で、どの更新を Transition に回せばよいかを見分けるのに使えそうです。

### [The answer to slop is accountability](https://naildrivin5.com/blog/2026/11/18/the-answer-to-slop-is-accountability.html)

> **出典**: Sidebar | **公開日**: 2026-11-23 | **カテゴリ**: design

**3行まとめ**
- 製品に組み込んだ LLM の質の低い出力（slop）の責任は、それを機能として出すと決めた人、おもにプロダクトマネージャーにある、という主張です
- 機能を「AI」「LLM」という言葉を使わずに説明してみると、挙動の責任が誰にあるかがはっきりする、という確かめ方を勧めています
- 機能の成果をプロダクトマネージャーの評価につなげる仕組みがあれば、slop は減ると見ています

**詳細解説**

New York Times Cooking が計画しているレシピの書き換え機能を、AI という言葉を使わずに書くと「ユーザーが変えたいことを文章で入力すると、システムが材料と変更点を文章で返す。返す内容はある割合で間違うが、その割合は測れない。そこでベータの表示と『間違いを含むことがあります』の注記を付ける」となります。こう書くと、間違うとわかっている道具をなぜ料理中の人に渡すのか、という問いが出てきます。間違いの責任が New York Times の側にあることもはっきりします。

間違いを測って減らす手段がないまま出すことはしない、と書いています。デザインレビューで AI を使った機能を見るときも、注記の文言を詰める前に、間違いをどう測ってどう減らすかが仕様にあるかを先に見られます。

### [Using Fallbacks for a Robust Front-End](https://css-tricks.com/using-frontend-fallbacks/)

> **出典**: css-tricks | **公開日**: 2026-11-23 | **カテゴリ**: css

**3行まとめ**
- プログレッシブエンハンスメントは使える環境で新しい機能を足すもの、フォールバックは「使えないときに何を出すか」を決めるもの、と分けています
- HTML では `<noscript>` を使って部品ごとに説明・再読み込みのボタン・問い合わせのリンクを出し、CSS では `@supports` に、使う機能を `and` ですべて並べます
- JavaScript では `if (window.navigation)` のように機能があるかを確かめ、データが届かないときは、代わりの表示を出すか何も出さないかを選びます

**詳細解説**

問い合わせのリンク（`mailto:`）の件名に部品ごとのエラーコードを入れておくと、サポートの担当者が聞き返さずに済みます。`@supports` は、機能が広まったあとにコードを検索して、要らなくなったフォールバックを消すときの目印にもなります。Baseline はアクセシビリティの機能の対応状況を追っていない、とも注意しています。

ただし、例の再読み込みボタンは `type="button"` なので、JavaScript が動かない状態では押しても何も起きません。この例を使うなら、リンクにするか、フォームから送信する形にしておく必要があります。部品のデザインで読み込み中や空の状態を描くときに、「スクリプトが動かない」「データが届かない」ときの表示も並べておくと、実装の段階で文言をその場で考えなくてよくなります。

### [The era of personal software](https://jakub.kr/writing/the-era-of-personal-software)

> **出典**: Sidebar | **公開日**: 2026-11-23 | **カテゴリ**: design

**3行まとめ**
- デザインエンジニアの Jakub Krehel さんが、毎日使う自分専用の健康記録の Web アプリを、AI のエージェントと作った過程を書いています
- iPhone の健康データは Health Auto Export で1時間ごとに JSON で送り、データベース（PlanetScale）の準備はエージェントが MCP サーバー経由で済ませました。最初のバージョンは約30分で公開しています
- 食事の記録は、アプリに組み込んだ AI エージェントをやめ、手持ちのエージェント（Grok Bot など）が書き込める API を足しました

**詳細解説**

Jakub さんのアプリでは、組み込んだ Claude Haiku 5.5 にカロリーを推定させると、正確な値が出にくく、すでに払っているサブスクリプションとは別に費用もかかりました。記録のたびにアプリを開くのも手間でした。そこで `POST /api/meals` を用意し、チャットで食べたものを送ると、エージェントが値を調べて書き込む形に変えています。新しい道具を使い始めるときに、画面を触らずにエージェントが MCP で設定を済ませることが増えている、とも書いています。

結びでは、自分のためだけに作るなら全員に合う判断をしなくてよく、コントラストの基準を満たさない配色でもそのまま使える、としています。一方で、健康データの書き出しのように、ほかの人が長く考えてきた部分は自分で作らず、Health Auto Export に任せています。
