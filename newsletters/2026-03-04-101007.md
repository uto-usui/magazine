### [Design-first collaboration](https://martinfowler.com/articles/reduce-friction-ai/design-first-collaboration.html)

> **出典**: Sidebar | **公開日**: 2026-03-03 | **カテゴリ**: design

**3行まとめ**
- AIコーディングアシスタントは設計と実装を一体化してしまい、設計判断が暗黙のまま進む「Implementation Trap」を引き起こす
- 5段階の設計レベル（Capabilities → Components → Interactions → Contracts → Implementation）で段階的に合意を取る手法を提案
- 「コードを書く前に設計に合意する」という1つの制約がAIとの協働を根本的に変える

**詳細解説**

Martin Fowlerのサイトに掲載されたこの記事は、AIとのペアプログラミングにおける構造的な問題を的確に言語化しています。人間同士のペアプロでは、まずホワイトボードでコンポーネントの境界やデータフローを議論してから実装に移ります。しかしAIはプロンプトを受けると即座にコードを生成し、スコープ、アーキテクチャ、インターフェースに関する判断をすべて暗黙のうちに下してしまいます。

この記事がとくに鋭いのは、AIが生成したコードのレビューが同僚のコードレビューより疲れる理由を説明している点です。同僚のコードは事前に合意した設計の実装なので、レビューの次元が限られます。一方AIのコードでは、スコープ、アーキテクチャ、インテグレーション、契約、品質のすべてを同時に評価しなければなりません。

提案されている「Design-First」アプローチは、AIとの対話を5つのレベルに分け、各段階で合意を取ってから次に進むものです。実例として通知サービスの構築では、Components段階でAIが提案したBullMQのラッパー抽象化を「不要」と却下し、よりシンプルな設計に導けたことが紹介されています。この手法はTDDとも相性がよく、Contracts段階で合意した型やインターフェースからテストを先に書ける点も魅力です。

### [Expose your design system to LLMs](https://hvpandya.com/llm-design-systems)

> **出典**: Sidebar | **公開日**: 2026-03-03 | **カテゴリ**: design

**3行まとめ**
- LLMはデザインシステムのトークンを「推測」するため、セッションを重ねるほどUIの一貫性が崩れていく
- 構造化されたスペックファイル、閉じたトークンレイヤー、監査スクリプト、ドリフト検出の4層で解決できる
- Atlassianのデザインシステムで検証し、28ファイルの418件のハードコード値をゼロにした実績がある

**詳細解説**

「バイブコーディング」でUIを作ると、最初のセッションでは良い見た目になるものの、5回目、10回目と重ねるうちにまるで3つの別チームが作ったような不統一なUIになっていく。この記事は、その構造的な原因と解決策を明確に示しています。

LLMがデザインに関して抱える問題は3つあります。値を「捏造」すること、セッション間で記憶がないこと、ソースコードからデザイン意図を読み取れないことです。たとえば、リンクの色を`#2563EB`にしたセッションの翌日には`#1D4ED8`になるかもしれません。どちらも妥当な青色ですが、デザインシステムの一貫性は失われます。

解決のアプローチは「Infrastructure as Code」の考え方に近く、スペックファイルでLLMに毎セッションの記憶を与え、トークンレイヤーで閉じた値の集合から選ばせ、監査スクリプトで漏れを検知します。とくに3層のCSS変数構造（上流トークン → プロジェクトエイリアス → コンポーネント）は実践的で、ダークモード対応やテーマ変更にも自動で追従できます。UXエンジニアにとって、AIとの協働時代にデザインシステムをどう進化させるかという問いへの具体的な回答になっています。

> **出典**: Sidebar | **公開日**: 2026-03-03 | **カテゴリ**: design

**3行まとめ**

- ツールを選ぶときは明確で、GitHub Actions 94%、Stripe 91%、shadcn/ui 90%と高い一致率を示す
- 新しいモデルほど新しいツールを選ぶ「Recency Gradient」が存在し、Prisma → Drizzle、Celery → FastAPI BackgroundTasksへのシフトが顕著

**詳細解説**

この研究は、Claude Codeが実際のリポジトリに対してどんなツールを選ぶかを大規模に調査したものです。プロンプトにツール名を含めず、純粋にオープンな質問だけで2,430回の応答を収集しています。

デプロイ先の選択も象徴的で、JSプロジェクトではVercelが86/86件で選ばれ、AWS・GCP・Azureはプライマリ推薦ゼロです。「Recency Gradient」も見逃せないポイントで、Sonnet 4.5ではPrismaが79%だったORMの選択が、Opus 4.6ではDrizzle 100%に完全にシフトしています。AIコーディングエージェントが事実上のツール選定ガイドになりつつある現在、この研究はエコシステム全体に影響を与える知見を提供しています。

### [Navigation API - a better way to navigate, is now Baseline Newly Available](https://web.dev/blog/baseline-navigation-api?hl=en)

> **出典**: web.dev | **公開日**: 2026-02-17 | **カテゴリ**: web-standards

**3行まとめ**
- 10年以上使われてきたHistory APIの構造的な問題を解決するNavigation APIが、全主要ブラウザでBaseline Newly Availableに
- `navigate`イベント1つで、リンククリック・フォーム送信・ブラウザバック・プログラマティック遷移すべてを一元管理できる
- View Transitions APIとの組み合わせで、アプリライクなページ遷移がネイティブに実現可能に

**詳細解説**

SPAのルーティングを支えてきたHistory APIは、本来SPAのために設計されたものではありませんでした。`<a>`タグのクリックをグローバルに監視し、`preventDefault()`で止め、`pushState()`を呼び、DOMを更新し、さらに`popstate`イベントを別途監視する…という煩雑な手順が必要でした。

Navigation APIはこれを根本から解決します。`navigation.addEventListener('navigate', ...)`という単一のリスナーで、あらゆる種類のナビゲーションをインターセプトできます。`event.intercept()`がURLの更新、ヒストリースタックの管理、フォーカス管理までを自動で行うため、開発者はUIの更新ロジックだけに集中できます。

フォーム送信の処理、スクロール位置の復元制御（`scroll: 'manual'`オプション）、View Transitions APIとの統合など、実用的なコード例も豊富です。React RouterやNext.jsを使っている場合は即座に書き換える必要はありませんが、フレームワークの内部実装が今後このAPIに移行していく流れは確実でしょう。Web標準の進化として注目しておくべき仕様です。

### [How we rebuilt the search architecture for high availability in GitHub Enterprise Server](https://github.blog/engineering/architecture-optimization/how-we-rebuilt-the-search-architecture-for-high-availability-in-github-enterprise-server/)

> **出典**: GitHub Engineering | **公開日**: 2026-03-03 | **カテゴリ**: engineering

**3行まとめ**
- GitHub Enterprise ServerのElasticsearch HA構成が抱えていた構造的問題を、Cross Cluster Replication（CCR）で解決
- 従来のクラスタ方式ではプライマリシャードがレプリカに移動してロック状態に陥るリスクがあった
- 各ノードを独立した単一ノードクラスタとして運用し、CCRでインデックスデータを安全に複製する新アーキテクチャに移行

**詳細解説**

GitHubのIssuesページ、リリースページ、Projectsページなど、多くの機能が検索に依存しています。この記事では、GitHub Enterprise ServerのHA（高可用性）構成における検索基盤の再構築について解説しています。

従来の方式では、プライマリノードとレプリカノードをまたいでElasticsearchクラスタを構成していましたが、Elasticsearchがプライマリシャードをレプリカノードに移動させてしまうことがありました。メンテナンスのためにレプリカを停止すると、Elasticsearchはレプリカの復帰を待ち、しかしレプリカはElasticsearchの正常化を待つという循環的なデッドロックに陥る問題です。

新しいアーキテクチャでは、各ノードを独立したElasticsearchクラスタとして扱い、Cross Cluster Replication（CCR）でインデックスデータを複製します。CCRはLuceneセグメントに永続化されたデータを複製するため、データの耐久性が保証されます。既存インデックスのブートストラップ処理や、フェイルオーバー、インデックス削除、アップグレードといったライフサイクル管理の工夫も紹介されており、分散システムの設計に興味があるエンジニアにとって参考になります。

### [Supporting additional payment methods for agentic commerce](https://stripe.com/blog/supporting-additional-payment-methods-for-agentic-commerce)

> **出典**: Stripe Blog | **公開日**: 2026-03-03 | **カテゴリ**: engineering

**3行まとめ**
- StripeがShared Payment Tokens（SPTs）を拡張し、Mastercard Agent PayとVisa Intelligent Commerceに対応
- BNPL（Affirm・Klarna）もエージェント経由の決済で利用可能に
- 売り手はSPTsのみを扱い、ネットワークトークンやBNPLの複雑さはStripeが吸収する

**詳細解説**

AIエージェントが人間の代わりに購買行動を行う「エージェンティックコマース」の基盤が着実に整備されています。StripeのShared Payment Tokens（SPTs）は、エージェントがユーザーの許可と希望する決済手段を使って支払いを開始できるしくみで、すでにEtsyやURBN（Anthropologie、Free People、Urban Outfitters）で採用されています。

今回の拡張で、MastercardとVisaのネットワーク主導のエージェント決済トークンに対応しました。ユーザーがエージェントに購買を許可すると、StripeがMastercardやVisaからスコープ付きのトークンをプロビジョニングし、エージェントはそのトークンを複数の加盟店で使えます。BNPLの対応もおもしろく、エージェントのUI上でBNPLの確認画面を表示するしくみです。

UXエンジニアの視点では、エージェントが決済フローをどう進めるかという新しいインタラクションデザインの課題が生まれています。人間のチェックアウト体験を前提としたUIから、エージェントが仲介する体験へ。これはフロントエンド開発のあり方にも影響を与える変化です。

### [Design systems checklist](https://tylercoderre.com/projects/design-systems-checklist.html)

> **出典**: Sidebar | **公開日**: 2026-03-03 | **カテゴリ**: design

**3行まとめ**
- デザインシステムの構築・運用に必要な要素を網羅的にチェックリスト化
- ブランド、ガイドライン、ファウンデーション（色・タイポグラフィ・スペーシング等）、コアコンポーネント、メンテナンスの4セクション構成
- 各項目にWCAGの該当基準を紐づけ、アクセシビリティとの対応関係を明示

**詳細解説**

デザインシステムの立ち上げや見直しの際に「何が足りているか・足りていないか」を確認するための実用的なチェックリストです。ブランド（ビジョン、デザイン原則、トーンオブボイス）からファウンデーション（色、タイポグラフィ、スペーシング、アイコノグラフィ）、コアコンポーネント、メンテナンス体制まで、幅広い領域をカバーしています。

とくに有用なのは、各チェック項目にWCAGの該当基準（たとえばTone of VoiceにはWCAG 3.1系）が紐づけられている点です。デザインシステムの設計判断とアクセシビリティ要件を自然に結びつけることで、「アクセシビリティは後回し」になるのを防ぎます。既存のデザインシステムを持つチームにとっても、棚卸しの観点として参考になるでしょう。

### [The Lookback: A Digital Capsule for Better Off Studio's Creative Past](https://tympanus.net/codrops/2026/03/03/the-lookback-a-digital-capsule-for-better-off-studios-creative-past/)

> **出典**: Codrops | **公開日**: 2026-03-03 | **カテゴリ**: design

**3行まとめ**
- コンバージョンを気にしない「カルチャーピース」として制作されたインタラクティブなデジタルアーカイブ
- タイムライン、サーフ（波）、インデックスの3つのビューでコンテンツを探索でき、FLIP技法を使った文脈的なページ遷移が特徴
- Nuxt 3 + GSAP + DatoCMS + Tailwindで構築し、モバイルではオーディオ機能を除外してパフォーマンスを確保

**詳細解説**

Better Off Studioのインスピレーションと制作物をアーカイブするこのプロジェクトは、コンバージョンやビジネスKPIから解放された純粋なクリエイティブ体験として制作されています。

技術的にもっとも見どころのあるのは、ページ遷移のFLIPアニメーションです。ルート変更前に各画像のバウンディングボックスを記録し、新しいページでIDによるマッチングを行い、位置とスケールの差分をGSAPでアニメーションさせます。ビューポート内の要素のみを対象とすることで、パフォーマンスも確保しています。サーフビューではCSS 3Dの変換状態を考慮したFLIP処理が必要になるなど、高度な実装課題にも対応しています。

パフォーマンス面の判断も参考になります。サーフビューのホバーエフェクトでは、スクロール中にエフェクトが毎秒何度もトリガーされる問題を「本のように画像が棚から覗き出る」というクリエイティブなソリューションで解決しています。制約のなかから生まれる創造的な解法は、UXエンジニアの日常業務にも通じるものがあります。

### [Who owns this book?](https://www.itsnicethat.com/articles/michele-hratko-who-owns-this-book-publication-graphic-design-project-170226)

> **出典**: Sidebar | **公開日**: 2026-03-03 | **カテゴリ**: design

**3行まとめ**
- デザイン学生向けの著作権ガイドブックで、法的・倫理的な考慮事項を親しみやすいデザインで解説
- 「Googleの画像をポスターに使える？」「フォントの試用版を買わずにプロジェクトで使える？」といった実際の疑問に応える内容
- 7種類の異なる紙を使い、紙の重さでセクションの切り替えを触覚的に伝えるブックデザイン

**詳細解説**

AI時代において「画像の著作権」は避けて通れないテーマです。Michele Hratkoが制作したこの書籍は、デザイン学生がよく抱く「ネットで見つけた画像をどのくらい編集すれば使える？」「試用フォントをプロジェクトで使っていい？」といった疑問に、ファウンドアーティクル、オリジナルの文章、著名な著作権訴訟の事例をコラージュする形で応えています。

デザイン面の工夫もおもしろく、著作権法の「怖さ」を和らげるために、フレンドリーな書体を使い、カラフルで現代的な見た目と、アーカイブ的で歴史的な美学のバランスを取っています。物理的にも7種類の紙を使い分け、紙の重みの変化でセクションの切り替えを触覚的に伝えるデザインは、デジタルのUXデザイナーにとっても学びのある触覚インタラクションの設計です。
