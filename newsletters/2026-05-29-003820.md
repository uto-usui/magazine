### [You are no longer the user. You are the principal.](https://uxdesign.cc/you-are-no-longer-the-user-you-are-the-principal-3a6222e0780a)

> **出典**: Sidebar | **公開日**: 2026-05-28 | **カテゴリ**: design

**3行まとめ**
- Google I/O 2026は「人間がシステムの操作者である」という35年来の前提を崩し、人間が principal（委任者）、エージェントが operator（操作者）になる初の消費者向けスタックを出荷した
- affordanceやmental modelといった既存のUX語彙は「present（その場にいる）ユーザー」のためのもので、「represented（代理される）principal」のための設計言語はまだ存在しない
- Android Haloの光る点に象徴される「省略の設計」が、これからの10年のデザイン課題になる

**詳細解説**

著者のAdrian Levyは、Sundar Pichaiの「もうラップトップを開いておく必要はありません」という一言を起点に、デザインの足場が静かに移動したことを論じます。Gemini Sparkは専用の仮想マシン上で24時間稼働し、ユーザーが画面の前にいなくても仕事を進めます。これまでコンピューティングは「座って、開いて、操作して、閉じる」という行為でした。それが、別のどこかで進行するプロセスを覗く窓へと変わっていきます。

ここで提示される三つの語彙が要点です。ユーザーは「操作する」存在ですが、principalは「authorize（authorize＝権限を委ねる）」する存在です。ユーザーはインターフェースに混乱させられると失敗しますが、principalはエージェントが「指示どおりに動いたとしても、本来許可しなかったはずの振る舞いをしたとき」に失敗します。この違いは小さく見えて、設計対象を根本から変えます。

記事はI/O 2026の6つの発表（Spark、Antigravity 2.0、WebMCP、Android Halo、Information Agents、Gemini Omni）を、それぞれ別のレイヤーで同じメッセージを反復するものとして読み解きます。とくにUXエンジニアリングの視点で興味深いのはWebMCPでしょう。Webサイトが「自分が何を依頼されうるか」を機械可読な形で宣言し、エージェントはビジュアルを1ピクセルも描画せずにサイトを直接呼び出します。レスポンシブデザインがWebを「スマートフォンに話せる」ようにした瞬間だとすれば、WebMCPは「エージェントに話せる」ようにする瞬間だ、という対比は鋭い指摘です。30年かけて磨いてきたビジュアル層が、この読み手にとっては任意のものになります。

著者が「省略のアーキテクチャ」と呼ぶAndroid Haloの議論も読みごたえがあります。エージェントが代理で動いていることを示す18ピクセルほどの光る点には、操作ログもタイムライン化も取り消しジェスチャーもありません。すべてを見せればダッシュボードの監視が新たなフルタイム業務になり委任が崩れ、何も見せなければブラックボックス化して疎外に変わる。だから設計すべきは透明と省略のどちらかではなく、その勾配（gradient）だ、という整理は実務的です。既定で省略されたものを「要求に応じて取り出せ、点検すれば読み解け、疑わしければ取り消せる」状態に保つ。これは現在のエージェント機能を実装する人にとって、そのまま設計指針になります。

一方で記事は、自らの破綻も誠実に名指しします。Jared Spoolの「世界はAIを全能のゲームチェンジャーとしてロマン化するが、実際にはかろうじて動いているだけだ」という批判を引きながら、デモは綺麗でも本番は汚いと認めます。エージェントが9%の確率で信頼できないなら、次の5年の専門性はその9%に宿る——失敗をどう可視化し、principalがどう制御を取り戻し、誤作動後にどう信頼を再構築するか。長編ですが、AI時代のUXを考える人には一読の価値があります。

### [SilverTorch: Index as Model — A New Retrieval Paradigm for Recommendation Systems](https://engineering.fb.com/2026/05/26/ml-applications/silvertorch-index-as-model-new-retrieval-paradigm-recommendation-systems/)

> **出典**: Meta Engineering | **公開日**: 2026-05-26 | **カテゴリ**: engineering

**3行まとめ**
- Metaは推薦システムの検索（retrieval）コンポーネントを、複数のマイクロサービスから単一のニューラルネットへ統合する「Index as Model」というパラダイムを発表した
- 従来のマイクロサービス構成に対しスループットは最大23.7倍、計算コスト効率はCPU比で20.9倍に向上した
- インデックスやフィルタもPyTorchのテンソル・モジュールとして表現することで、ML基盤と推論基盤の境界が消える

**詳細解説**

推薦システムの検索処理は、数百万件のコンテンツから100ミリ秒未満で数千件に絞り込む、極めて厳しいレイテンシ予算のなかで動いています。従来はオーケストレータがユーザータワー、検索サービス、スコアリングサービスへとファンアウトする「マイクロサービスのメッシュ」でした。CPU時代にはうまく機能した構成ですが、サービス間のホップごとにネットワーク往復とシリアライズのコストがかかり、本来計算に使うべき予算を食いつぶしていました。さらにユーザーモデルがv2、アイテムインデックスがv1のままといったバージョン不整合や、PyTorchを書くMLエンジニアとC++を書く基盤エンジニアの分断も構造的な限界を作っていました。

SilverTorchの発想の転換は「マイクロサービスを設計してそこにニューラルネットを差し込む」のではなく「ニューラルネットから始めて外側へ設計する」点にあります。アイテムインデックス、適格性フィルタ、スコアリング層、ユーザータワーのすべてが、単一のPyTorchモデル内のテンソルあるいは演算子になります。実行時にはANN検索もBloomインデックスフィルタも訓練済みのMLリランカーも、すべて `nn.Module` として区別がつきません。デプロイする成果物は一つ、実行するforward passも一つ、システムの真実の源も一つになります。

技術的なハイライトは、CPU時代のコンポーネントを単に `nn.Module` で包んだのではなく、GPU実行に合わせて検索プリミティブそのものを再設計した点です。フィルタリングを従来の転置インデックスからBloomインデックスへ置き換え、ビット演算でGPUが得意な密な並列処理に変えています。ANN検索もInt8形式で埋め込みを保持しメモリを約半分に削減、融合GPUカーネルで実行することで、より多くの候補を後段に渡せるようにしています。Bloomインデックスはバッチでの転置インデックス比291〜523倍という数字が示すとおり、再設計の効果は大きいものでした。

UXエンジニアリングの視点で見ると、この記事の含意は「基盤の効率化が、ユーザー体験の天井を引き上げる」という関係性にあります。マイクロサービス時代はレイテンシ予算の制約から、検索段階は単純な埋め込み類似度に絞らざるを得ませんでした。SilverTorchはニューラルリランキングとマルチタスクスコアリングを検索段階で実行可能にし、結果として推薦の質そのものを底上げします。当日投稿のコンテンツが推薦に占める割合が増えた、というフレッシュネスの改善も体験に直結します。エンジニアリングの速度も「数週間から数日へ」と短縮されており、アーキテクチャの選択が組織のアウトプットに与える影響を考えるうえで示唆に富む事例です。

### [Algorithmic Theming Engines: Building Self-Correcting Color Systems With `contrast-color()`](https://smashingmagazine.com/2026/05/building-self-correcting-color-systems-contrast-color/)

> **出典**: Smashing Magazine | **公開日**: 2026-05-28 | **カテゴリ**: design

**3行まとめ**
- CSSの `contrast-color()` は背景色を渡すと黒か白の最適なコントラスト色を返す関数で、Chrome・Firefox・Safariの3エンジンすべてで安定版に到達した
- 70%以上のサイトがWCAGのコントラスト基準を満たせていない現状は、ライブラリ不足ではなくCSSの不在が原因だった
- 数学的なAA準拠は保証するが知覚的なアクセシビリティとは限らず、トランジションのスナップなど注意点もある

**詳細解説**

著者Durgesh Pawarは、半世紀近い設計システムツールやアクセシビリティリンター、JavaScriptライブラリの蓄積にもかかわらず、コントラスト不足のサイトが減らない現実から話を始めます。WebAIM Millionでは2026年に83.9%のホームページが低コントラストとして検出され、前年より悪化しています。これは開発者が気にしていないからではなく、「気にすること」と「実際に出荷すること」の距離——ライブラリ、ビルドステップ、実行時計算、ハイドレーションのちらつき、配線を忘れた一つのコンポーネント——のどこかでアクセシビリティが静かに脱落していたからだ、という診断が説得力を持ちます。

`contrast-color()` の使い方は拍子抜けするほど単純で、`color: contrast-color(var(--brand-color))` と書けば、ブラウザがスタイル計算の段階でコントラスト計算を済ませ、適切な文字色を返します。ライブラリもビルドステップもハイドレーションのちらつきもありません。記事は仕様がLevel 5（黒か白を返す現行版）とLevel 6（候補色リストと目標比率を扱う将来版）に分かれている事情や、アルゴリズムが「UA-defined」とされている理由——将来WCAG 2.xからAPCAなど別のアルゴリズムへ、既存コードを壊さずに移行できる逃げ道として意図的に残されている——まで丁寧に解説します。

実装者にとって価値が高いのは「落とし穴」の節です。`contrast-color()` が返すのは数学的なAA準拠であって知覚的なアクセシビリティとは限らない、という指摘は重要です。`#2277d3` のような中間色は黒文字でも数学的にはAAを通過しますが、人間の目には読みにくいことがあります。また背景色を白から黒へアニメーションさせると、出力が離散値（黒か白）であるためトランジションが補間されずスナップします。しかもWCAGの相対輝度は非線形なので、スナップは中間ではなく約18%の輝度地点で起こり、見た目には終盤で急に切り替わる不自然な挙動になります。`transition-behavior: allow-discrete` でも解決しないため、滑らかにしたい場合は `color-mix()` を重ねる必要があります。

UXエンジニアリングの観点では、この関数が「メインスレッドからブラウザのネイティブなスタイル計算フェーズへ計算を移す」点が見逃せません。JavaScriptライブラリは色のパース、輝度計算、黒白の判定、DOMへの書き戻しをメインスレッドで行い、レイアウトやイベントハンドラと競合します。chroma-js（約14kB）やpolished、tinycolor2をコントラスト用途だけで使っているなら、ランタイムから外せます。バンドルサイズとパフォーマンス、そしてSSRアプリのハイドレーションフラッシュの解消という、複数の便益が一度に得られる好例です。`@supports` による段階的拡張の書き方も示されており、すぐ実務に持ち込める内容です。

### [Navigating the age-old problem of checkmarks in UI with progressive enhancement](https://piccalil.li/blog/navigating-the-age-old-problem-of-checkmarks-in-ui-with-progressive-enhancement/?ref=main-rss-feed)

> **出典**: Piccalilli | **公開日**: 2026-05-28 | **カテゴリ**: css

**3行まとめ**
- カスタムドロップダウンのチェックマークを従来手法で作ると、大量のJavaScriptとARIA属性が必要になり、JSが失敗すると全体が機能しなくなる
- CSSの `::checkmark` 擬似要素と `appearance: base-select` を使えば、ネイティブの `<select>` のまま少量のCSSでチェックマークを自由にスタイルできる
- ただし `::checkmark` はSafari・Firefoxで未対応、対応ブラウザでも `<select>` の `<option>` のみという制約がある

**詳細解説**

著者Sunkanmi Fafoworaは、UIにおけるチェックマークの表現という古くからの課題を、従来手法とモダン手法を対比しながら解説します。まず非セマンティックな `<div>` でカスタムドロップダウンを作る場合、ボックスの開閉、選択時の値更新、外側クリックでの閉じる動作、キーボードナビゲーションなど、ブラウザが本来提供する振る舞いをすべて自前で実装する必要があります。記事はそのHTML、CSS、そして「これだけのJavaScript」を実際に並べて見せ、その量に圧倒される感覚を共有させます。

この手法の問題は二点に整理されます。第一に、JavaScriptが失敗すると解決策全体が「死ぬ」こと。追加したマークアップはむしろ支援技術の利用者にとって問題を増やしかねません。第二に、すべてのブラウザ標準の振る舞いを不必要にゼロから実装しなければならないこと。フォーカス管理、開閉、外側クリックでの閉じる動作まで自前で書く必要があり、解決策は脆く信頼性を欠きます。そもそもドロップダウンが開けなければチェックマークのスタイルは存在すらしません。

対するモダン手法はシンプルです。ネイティブの `<select>` と `<option>` を使い、`appearance: base-select` を指定したうえで `::checkmark` 擬似要素の `content` を変えるだけ。アクセシビリティ、キーボードナビゲーション、標準的な振る舞いはすべてブラウザが処理し、JavaScriptは不要です。JSが失敗してもネイティブ要素なので機能し続け、支援技術にも正しくアナウンスされます。これは段階的拡張（progressive enhancement）の勝利だ、と著者は言います。

UXエンジニアリングの視点で見ると、この記事は「セマンティックな要素に立ち返ることが、結果としてアクセシビリティと保守性の両方を底上げする」という原則を具体的なコードで示しています。前述の `contrast-color()` の記事や、後述するBaselineダイジェストとも通底するテーマです。注意点として、`::checkmark` は執筆時点で3大ブラウザのうち一部のみの対応で、仕様上はチェックボックスやラジオボタンも対象のはずが実際には `<select>` の `<option>` だけ、という制約があります。著者はブラウザベンダーへの完全対応を「お願い」として結んでおり、今すぐ全面採用というよりは、対応状況を見ながら段階的拡張で取り入れる前提で読むとよいでしょう。

### [An Extension is Not an Excuse](https://webaim.org/blog/an-extension-is-not-an-excuse/)

> **出典**: WebAIM Blog | **公開日**: 2026-05-28 | **カテゴリ**: accessibility

**3行まとめ**
- 米HHSがSection 504に基づくWebとモバイルアプリのアクセシビリティ準拠期限を1年延長したが、要件（WCAG 2.1 AA準拠）自体は変わっていない
- 延長は「パニックからの猶予」であって「アクセシビリティからの猶予」ではない
- 期限は動いても、ポータルを使えない患者が医療を受けられないという人間のニーズは変わらない

**詳細解説**

著者John Northupは、コンプライアンス期限の延長という一見事務的なニュースを、アクセシビリティの本質的な問いへと引き上げます。15人以上の組織は2027年5月11日まで、それ未満は2028年5月10日まで猶予されました。しかしWCAG 2.0は2008年から、HHS規則が採用するWCAG 2.1は2018年から存在します。Webは何度も再設計・再構築されてきたにもかかわらず、です。WebAIM Million 2026では検出されたアクセシビリティエラーが前年比で約10%増加しており、Webはむしろ後退している、という指摘が延長への苛立ちを鋭くします。

同時に著者は、組織が単に怠けているわけではない現実にも目を向けます。デジタルアクセシビリティの要件を最近知ったばかりの組織、低コストツールで急いで作ったサイト、アクセシビリティが後で障壁になると気づかずにスケジューリングシステムやポータルを購入した組織、数千の非アクセシブルなPDFを引き継いだ組織。Webサイト担当者が一人で、しかもコミュニケーションやIT、コピー機の紙詰まり対応まで兼任している場合もあります。これは「言い訳」にはならないが「なぜ時間がかかるのか」を説明する、という両面を誠実に提示します。

HHSの通知に引用された、ある遠隔メンタルヘルス提供者のコメント——2024年の規則は「いかなる実質的便益も提供せず」医療提供者に多大な財政負担を課す——を、著者は「立ち止まらせるべき」言葉として取り上げます。HHSは明確に反論し、遠隔医療において障害のある人がコンテンツやアプリにアクセスできなければ、それは技術的な問題ではなく連邦資金の受給者による医療の拒否だ、と述べています。「実質的便益がない」という言い方は、排除される人々が見えない存在として扱われているときだけ成立する、という指摘が核心を突きます。

UXエンジニアリングの観点では、後半の実践的な提言が役立ちます。第一に最も重要なサービス（予約、問診フォーム、給付申請、決済、緊急情報）を優先する。第二に新たな非アクセシブルなコンテンツの生成を止める——古いPDFを修正しながら新しい非アクセシブルなPDFを公開し続けるのは「蛇口を開けたまま水をかき出す」ようなものだ、という比喩が印象的です。第三に調達を真剣に扱いVPATなど信頼できる文書を要求する。第四にコンテンツを作る人を訓練する。第五に進捗を正直に測る。期限は動いても市民権の義務は動かない、という締めくくりは、アクセシビリティに関わるすべての実務者に響く内容です。

### [April 2026 Baseline monthly digest](https://web.dev/blog/baseline-digest-apr-2026?hl=en)

> **出典**: web.dev | **公開日**: 2026-05-27 | **カテゴリ**: web-standards

**3行まとめ**
- 2026年4月に `contrast-color()` と `Math.sumPrecise()` がBaseline newly availableに到達した
- `<search>` 要素、WebAuthnの公開鍵アクセス、`String.prototype.isWellFormed()`、ARIA属性のリフレクションがwidely availableになった
- Web標準に頼ることが、アクセシビリティを考慮した開発をより効果的にする

**詳細解説**

web.devのBaselineダイジェストは、Webプラットフォームの成熟度を「いつそのフィーチャーを評価・採用してよいか」のシグナルとして毎月伝えてくれます。今回の冒頭では、A11y Upの記事を引きながら「アクセシビリティはWeb標準に頼るほうが効果的だ」という論点が示されます。長年エンジニアは、いまやプラットフォームの一部となったアクセシブルなパターンを、独自の重いJavaScriptで再現してきました。そうした自前の実装は脆く、支援技術の下で壊れやすく、保守も難しい。これは前述のチェックマークの記事とまさに同じ主張です。

newly availableの目玉は二つです。`contrast-color()` は本号のハイライトでも取り上げたとおり、動的テーマやカスタマイズ可能なコンポーネントのために複数のカラーシステムを維持する負担を、ブラウザ側へ移します。`Math.sumPrecise()` は、数値列の合計で起こりうる浮動小数点の精度損失に対処する関数です。`Array.prototype.reduce()` での合計は金融計算やテレメトリの集計で誤差を生みますが、この関数は反復可能な数値を受け取り精度安全な合計を返します。

widely availableになったフィーチャーは、いずれもアクセシビリティとセマンティクスに関わるものが目立ちます。`<search>` 要素は検索体験を表すフォーム群の明示的なラッパーで、ブラウザが暗黙的に `search` のARIAランドマークロールを割り当てるため、`role="search"` を書く必要がなくなります。WebAuthnの `getPublicKey()` などはパスワードレス化の実装からバイナリ操作の煩雑さを取り除きます。`isWellFormed()` / `toWellFormed()` はUTF-16のサロゲートペアが壊れた文字列を検出・修復し、`encodeURI()` などが `URIError` を投げる前に対処できます。

UXエンジニアリングの視点で見ると、ARIA属性のリフレクションが実務的にうれしい追加です。これまで `element.setAttribute('aria-expanded', 'true')` とDOM属性メソッドを経由していたものが、`element.ariaExpanded` のようにドット記法で扱えるようになります。ARIAターゲットをJavaScriptのプロパティとして扱えることで、UIフレームワークや状態管理ツールが支援技術のコンテキストをより確実に同期でき、スクリーンリーダーの状態とアプリの実状態がずれにくくなります。Baselineを定点観測する習慣は、こうした「自前実装を減らせるタイミング」を逃さないために有効です。

アーキテクチャの核心は「ループを不可視にする」点にあります。フルスクリーンのセクションを作り、最初のセクションを末尾に複製し、Lenisで無限スクロールを有効化し、各セクションにスナップさせ、GSAP ScrollTriggerでメディアをアニメーションさせる。ユーザーには滑らかで連続したページが見え、ブラウザには「とてもよくできた変装をまとった、丁寧に演出されたループ」が見える、という対比が分かりやすい。複製したセクションは `aria-hidden` で支援技術から隠し、スクリーンリーダーが二重に読み上げないようにする配慮も盛り込まれています。

技術的なポイントも実務的です。CSSでは `100vh` ではなく `100svh` を使ってモバイルSafariのツールバー問題を避けます。Lenisのセットアップでは `infinite: true` の一行がマジックの大半を担い、残りは制御と仕上げ。パララックスは `picture` 要素を `-50%` から `50%` へ動かすだけで、スクロールとメディアの間のわずかな遅延が奥行きを生みます。後半では、iOS Safariのツールバーの伸縮がループの継ぎ目を露出させる問題を、独自のスクロールコンテナと `ScrollTrigger.scrollerProxy` を使ったネストされたLenisセットアップで「きちんと」解決する方法まで示されます。

UXエンジニアリングの視点では、この記事の締めくくりが本質を突いています。「重厚なアーキテクチャや過剰な設計はなく、いくつかのよく考えられたアイデアが正しく組み合わさっているだけ。たいていは、より多くを足すことではなく、何が重要かを理解しそれを意図を持って実行すること」。前述のVanderpotteの記事とも響き合う、モーションの「感触」を技術的なロジックに落とし込む実践例として、コピペで終わらせず設計判断ごと学べる良質なチュートリアルです。

### [Why I don't use icon fonts in Figma](https://www.alicepackarddesign.com/blog/why-i-don-t-use-icon-fonts)

> **出典**: Sidebar | **公開日**: 2026-05-28 | **カテゴリ**: design

**3行まとめ**
- Figmaでアイコンフォントを使わず、SVGパスをメインコンポーネントとして保存すべき7つの理由
- グリフの挿入の煩雑さ、視覚プレビューの不在、名前の暗記、編集や共有の難しさ、多色非対応など
- 唯一の利点は他フォントとのインライン配置だが、それも設計システムとの相性が悪い

**詳細解説**

著者Alice Packardが、Figmaでアイコンフォントを使うことのデメリットを7つ挙げ、SVGパスをメインコンポーネントとして管理するアプローチを推奨します。2014年のCSS-Tricksの記事「Icon Fonts vs SVG」のFigma版だ、と自ら位置づけています。第一の理由は、グリフをテキストレイヤーに入れる作業の煩雑さ。Figma公式ドキュメントが7ステップのプロセスとして説明するこの作業は、Figmaを離れてFont AwesomeのサイトでグリフをコピーしてFigmaに戻る、という文脈切り替えを強います。皮肉なことに、FAやMaterialの公式プラグインですら、選んだアイコンをSVGパスとしてキャンバスに置きます。

第二・第三の理由は、視覚プレビューの不在とグリフ名の暗記です。Materialのアイコンフォントなら名前を手入力してレンダリングできますが、正確な名前を覚えなければならず、覚えていないアイコンは結局ギャラリーで探すことになります。SVGをメインコンポーネントとして保存していれば、視覚プレビューが得られ、キーワードによる「あいまい検索」が使え、しかもそのキーワードは自分（や設計システム)が制御できます。グリフのアートワークを横に並べて比較するのも、正確な名前が必要なアイコンフォントでは「創造性の罠」になり、可能性の世界が縮む、という指摘も鋭い。

第四以降は、編集・共有・多色の難しさです。アイコンをフォントとして編集するにはFontLabやFontForgeのような学習コストの高いツールが要ります。フォントファイルの共有も、転職や新メンバー参加のたびに再インストールが必要になり煩わしい。Figmaの組織プランならフォントを組織内にインストールできますが、権限がなければ管理者頼みになります。そしてFigma内ではアイコンフォントで多色アートワークが実現できません。これらはいずれもSVGをメインコンポーネントとして管理すれば、より多くの制御を持てる領域です。

UXエンジニアリングの視点では、第七の「私の開発者はアイコンフォントを使わない」という理由が示唆的です。開発側がしばらく前からSVGに移行しているなら、デザインデータも同じ前提に揃えるほうがデザインとコードの距離が縮まります。著者はアイコンフォント唯一の利点として「他のフォントファミリーとインラインで配置できる」ことを認めつつ、それは2つのフォントファミリーが同一レイヤーに混在することを意味し、変数やテキストスタイルに接続できないため設計システムとの相性が悪い、と冷静に評価します。Figmaに `span` 相当の機能が来てほしい、という願いも添えられた、実務に根ざした主張です。

### [The Part of Agile Designers Fear the Most: Imperfect Work](https://uxmag.com/articles/the-part-of-agile-designers-fear-the-most-imperfect-work)

> **出典**: UX Magazine | **公開日**: 2026-05-28 | **カテゴリ**: ux-research

**3行まとめ**
- アジャイルはデザイナーに「完成と感じる前のもの」をリリースするよう求め、深い恐れを引き起こす
- MVPで忘れられがちな言葉は「minimum」ではなく「viable（実用可能）」である
- デザイナーが躊躇する本当の理由は完璧主義ではなく「チームが改善に戻ってこない」ことへの不安

**詳細解説**

著者Paivi Salminenは、アジャイル製品開発が想像以上に心理的なものだと気づいた経験から書き起こします。スプリント、バックログ、スタンドアップといった手続きの裏に、デザイナーにとってより居心地の悪いものがある——完成と感じる前の仕事をリリースすることへの恐れです。Laura Kleinの講座から得た中心的な洞察は、MVPで最も重要な言葉が「minimum」ではなく「viable」だ、というものです。最初のバージョンは小さくてよいが、使えないものであってはならない。混乱させ、壊れ、苛立たせるものをリリースしても、意味のある学びは得られません。

著者が掘り下げるのは「デザイナーが躊躇する本当の理由」です。インタビューでは、多くのデザイナーが「チームが改善に戻ってくると信じられれば、不完全な仕事をリリースすることに抵抗はない」と答えたといいます。問題は、多くのチームが戻ってこないこと。機能が出荷され、祝福され、静かに放棄される。チームは次のバックログ項目へ移り、不完全なバージョンが恒久的なものになる。デザイナーの視点では、それはユーザーを裏切ることのように感じられます。反復こそが早期リリースを意味あるものにする、という指摘が核心です。

記事は「反復は機能を足すことではない」という重要な区別も示します。エンジニアリングのリファクタリング——ユーザーへの振る舞いを変えずに内部構造を変える——に倣い、デザインにも同種の作業が必要だ、と。最初は数セクションでトップナビゲーションが機能していた製品が、機能追加で手狭になったとき、機能は変えずにナビゲーション構造を再編する。これがデザインのリファクタリングです。リファクタリングが可能だと知ることが、早期の意思決定への向き合い方を変える、という論理は実務的です。

UXエンジニアリングの視点では、この記事は「完璧な解は、ユーザーが触れる前は理論にすぎない」という現実を、デザイナーとエンジニアの共通言語で語っている点に価値があります。すべての設計判断が将来のあらゆるシナリオを支える必要があるなら、何もリリースできません。現在に責任を持って設計しつつ、将来に適応する余地を残す。アジャイルチームはすべてを予測しようとせず、有用なものを作り、現実世界での振る舞いを観察し、継続的に改善する。前述の「7 things」が説く文書化や反復の重要性とも通じる、地に足のついた一篇です。

### [Microsoft Foundry Hosted Agent と Claude Agent SDK を使ったサンドボックス検証](https://tech.layerx.co.jp/entry/hosted-agent-claude-agent-sandbox)

> **出典**: LayerX エンジニアブログ | **公開日**: 2026-05-27 | **カテゴリ**: engineering

**3行まとめ**
- 不特定多数が触る環境でAIエージェントを安全に動かすためのサンドボックス構成を、Azure内に閉じて検証した記事
- 個別のdeny ruleの積み上げは漏れやすく、OS/VM境界での構造的・多層的な防御が筋
- Hosted AgentのセッションごとのmicroVMと、Claude Code Bash sandboxのnamespace jailの二層構成が効果的

**詳細解説**

LayerXのosukeさんによる、AIエージェントのサンドボックス技術の実地検証記事です。Webサービスの裏側など不特定多数のユーザーが操作する環境でエージェントを動かすには、各ユーザーのデータが他ユーザーから見えないこと、LLMが触ったコマンドがホストや他テナントに到達しないこと、副作用を用途に応じて制限できることが同時に求められます。記事の基本姿勢は明快で、個別の攻撃パターンを一つずつdeny ruleで塞ぐアプローチは、新しいバリエーションが出るたびに穴が開く——だからセキュリティは「包括的に、構造的に、多層に」組まないと持たない、というものです。

検証の出発点はMicrosoft Foundry Hosted Agentです。これはセッション単位でmicroVMを立て、Azure VM同士と同じ強度の境界で隔離する仕組み。2つのセッションで `/proc/sys/kernel/random/boot_id` を比較すると完全に異なる値が返り、セッションごとに別のmicroVMが立っていることが実機で確認できた、という検証の丁寧さが好印象です。Claude Agent SDKのRead/Write/GlobなどのビルトインツールはmicroVMのファイルシステムに閉じているため、`cwd` を制限すれば別セッションのファイルは構造的に見えません。問題はBashで、これをallowにした瞬間にmicroVM境界だけでは塞げない経路が多数現れます。

記事の核心は「アドホック対応は漏れる」という構造的な議論です。たとえば `permissions.deny` のRead ruleはcatやheadには適用されますが、`python3 -c "print(open('/run/secrets/example-token').read())"` のようにファイルを間接的に開ける任意のサブプロセスには適用されず、構造的に素通りできます。新しい脅威カテゴリが見つかるたびに穴が開くイタチごっこになり、監査説明性も低い。「OS層のnamespaceで構造的に切ってある」と言えるほうが説明性も再現性も高い、という指摘は、顧客のセキュリティレビューに向き合う実務者にとって説得力があります。

UXエンジニアリングの直接の対象ではありませんが、エージェントを製品に組み込むうえで避けて通れないテーマです。記事は4つの実装パターン（素のBash＋個別対応、Vercelのjust-bash、Azure Container Apps Dynamic Sessions、Claude Code公式sandbox）を比較し、最終的にHosted AgentのmicroVMとClaude Code Bash sandboxのnamespace jailを組み合わせた二層構成を推奨します。後者はbubblewrapでmount/net/pid/user namespaceを一括して構造的に切り、トークン読み出しもネットワーク通信もnamespaceの段階で詰む様子を実機ログで示しています。前述の「You are no longer the user」がエージェント時代のデザインを論じたのに対し、本記事はその基盤を安全に支える技術の一次情報として価値があります。
