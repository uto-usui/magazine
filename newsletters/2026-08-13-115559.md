### [Building a software factory for AI SDK](https://vercel.com/blog/building-a-software-factory-for-ai-sdk)

> **出典**: Vercel | **公開日**: 2026-08-12 | **カテゴリ**: frontend

**3行まとめ**
- AI SDK のリポジトリには月100件を超える issue が積み上がり、6月末には open issue が1,022件、PRが約800件に達していた
- エージェントを増やすのではなく、分類・再現・実装・レビュー・バックポートを1タスク1エージェントに分けた「工場」を構築した
- 稼働4週間で、マージするPRの25〜35%を工場が書き、7月にクローズされた issue の75%超を処理している

**詳細解説**

AI SDK は週2,000万ダウンロード、26,000スターという規模のプロジェクトです。メンテナンスは4つの動く標的を同時に追いかけることを意味します。モデルプロバイダ、UIフレームワークのバインディング、サンドボックス、そして各種ハーネスのアダプタ。そこに Opus 4.6 のリリースでPRが変曲点を迎えました。

冒頭の整理が誠実です。「このバックログは規律の問題ではない。どれだけ優秀なメンテナでも働き方でギャップを埋めることはできないし、コード生成が安い以上ギャップは広がる一方だ」。そのうえで、既存のアプローチがなぜ足りないかを説明します。Mitchell Hashimoto のように常にエージェントを動かす運用も、Simon Willison のように4つ並列で回すやり方も、レビューボットも、結局すべての変更が一人の人間の注意を通ります。だからレビュアーの効率を第一原理に据えた、と。

設計上の判断は3つあります。1つ目は1エージェント1タスク。1つのエージェントに複数の skill を持たせる案も試したうえで、それぞれ独自のプロンプト・コンテキスト・eval を持つ形に分けました。個別にテストでき、デバッグしやすいからです。2つ目はセキュリティを2番目のエージェントの時点から実装したこと。公開リポジトリでは issue もPRもコメントもリンクも攻撃者が制御しうる入力として扱う、という前提から出発しています。各エージェントは Vercel Sandbox のなかで、そのタスクに必要な秘密情報だけを持って動きます。3つ目はローカルCLIで価値を作ってからクラウドに移したこと。

実際の流れが1つの issue で追えるようになっています。分析エージェントが機能の有無を推測ではなく確認するために、失敗するプローブを書いて実行する。その失敗が「main にこの機能がない」という証拠になり、仕様の根拠として issue に貼られる。実装エージェントは実際にウェブ検索を走らせて、ブロックしたドメインに到達しないことを確認します。

UXエンジニアリングの視点で読むと、これは人間向けの情報設計の話でもあります。工場の出力は動くコードだけでなく「証拠の連鎖」で、レビュアーはそれを見てどれだけの労力を割くかを決めます。ドキュメント修正はざっと確認、プロバイダ変更は焦点を絞った検証、新しい public API は深いレビュー。リスクに応じて注意の配分を変えられるように出力を組み立てる、というのは、まさにレビュー画面のUI設計です。

失敗の扱い方も参考になります。実行結果は success / flawed / blocked / manual の4つに分類され、成功以外はすべてフィードバックとして系に戻ります。flawed ならプロンプトかコンテキストか eval の追加、blocked なら環境の不足を埋める、manual は意図的に引いた境界線で、それを外せるかを毎回問い直す。「工場を改善することが仕事になる」という結びは、テストスイートやパイプラインに向けてきた規律を、作業する側のシステムに向け直すという意味です。

### [Stop being skeptical about AI for development with Charity Majors](https://newsletter.pragmaticengineer.com/p/stop-being-skeptical-about-ai-for)

> **出典**: The Pragmatic Engineer | **公開日**: 2026-08-12 | **カテゴリ**: engineering

**3行まとめ**
- 2025年にAIへ懐疑的だったのは合理的だったが、2026年にはもう懐疑の居場所が少ない、と Charity Majors が語る
- 転機は2025年11月。モデル（Opus 4.5）よりも、Claude Code のようなハーネスがシェルスクリプトから本格的なインフラになったことが大きい
- 「読んでいないコードを本番に出せる状態にするには何が要るか」が、これからエンジニアが答えるべき問い

**詳細解説**

Honeycomb の CTO で『Observability Engineering』の共著者である Charity Majors へのインタビューを、Gergely Orosz が13の論点にまとめた回です。2025年3月の SREcon で「懐疑的な人こそ vibe coding を試すべきだ、学んだほうが上手に文句を言える」と言ったときは会場がざわついた、というところから話が始まります。

対比として持ち出されるのが2010年のクラウドです。あの年、クラウドが主流になってインフラ層を変えることが明らかになった。2025年のAIはそれと同じ位置にある、と。同時に、それまでの懐疑には理由があったことも認めています。COBOL、ニューラルネット、ノーコード。「プログラマは要らなくなる」と言われた技術はいくつもありました。

いちばん引っかかるのは「pets から cattle へ」という比喩でしょう。これまでソフトウェアはゼロから書くほうが既存を編集するよりずっと高くつきました。ところが今は、関数の変種を数百作るほうが1つ手書きするより速い。2010年代にサーバーが「直すもの」から「作り直すもの」に変わったのと同じことが、コードにも起きるかもしれない、という見立てです。

逆張りの主張も入っています。コードレビューは過大評価されていて、人間が加える価値のなかでもっとも低い部分だ、と。人間が得意なのは会話と「何を作るか決めること」であって、正しさや構文やバグを読み取ることではない。DevOps 20年についての総括も厳しく、「ops はコードを学べ」の側は機能したが「エンジニアは本番の自分のコードを理解しろ」の側は今日まで失敗している、と切り捨てます。

非決定的なシステムには、以前より多くの規律が要るという指摘が全体を貫いています。自分で書いていない以上コードへの信頼は下がる。だから開発プロセスの別の場所、つまりテストや eval や適合性テストといった検証の側で信頼を上げるしかない。前項の software factory が「証拠の連鎖」でやろうとしていることを、組織と職能の側から言い直したものと読めます。

AI疲れへの対処が具体的なのもいいところです。Honeycomb では水曜日は誰もAIを使わない。小さく主導権を取り戻す行為が効く、と。最後の頼みも印象に残ります。「勝ちを見ている人たちは、それをコストに結びつけていない。だから同僚が自動化を恐れているだけに見えてしまう。全体の物語を話してほしい」。

### [How we stopped outsourcing decision-making to AI](https://uxcontent.com/how-we-stopped-outsourcing-decision-making-to-ai/)

> **出典**: UX Content Collective | **公開日**: 2026-08-12 | **カテゴリ**: ux-writing

**3行まとめ**
- Intuit でコンテンツシステムを担当する2人が、AIツールで skill を量産するうちに自分たちの決定を説明できなくなった話
- 我に返るきっかけは、skill ファイルの一行の意味を、二人とも説明できなかった瞬間
- 立て直せたのは、着手前のリサーチで「デザイナーはコンテンツを意識していない」と知っていたから

**詳細解説**

置かれていた状況が、今の多くのチームと重なります。以前はコンテンツデザイナー向けの標準を作れば、あとは各人がスキルを使って製品に適用してくれました。今は、コンテンツデザイナーがその場にいないAIの文脈でも標準が効いてほしい。PMもエンジニアもプロダクトデザイナーも顧客向けの文言を書くようになったからです。vibe coding が全員のワークフローに入ったのなら、AIツール向けの skill を束ねたプラグインを作るのが答えに思えた、と。

10個の skill ができた頃には勢いに乗っていました。ところが、お互いに「なぜこの構造にしたんだっけ」と聞くと、答えが「Claudeがそう言ったから」になっていた。追いきれていない変更を追跡し、検証していない提案に従い、どちらも選んだ覚えのない方向に進んでいた。著者は嵐の海に放り込まれた比喩でこれを書いています。泳ぎ方を聞けばいいと言われるが、AIは泳ぐ前に飛び込み方を教えてくる、そして自分はもう水面下にいる、と。

Sarah という同僚の反応が本題です。彼女は「自分で完全に擁護できない推奨はしない」ことでキャリアを積んできました。説明できない一行を前にして気づいたのは、いまデザインレビューの場にいたらこの仕事を自信を持って擁護できない、ということでした。Claudeはすべてに自信満々で、その確信が自分たちの確信の代わりになっていた。

そこから先の立て直しは地味です。markdown を開いて読む。skill 間でテキストを比較し、各説明文、各ワークフロー節、各出力仕様を突き合わせるアーキテクチャ監査をする。それが機能したのは、何を探せばいいかを知っていたからでした。着手前に、デザイナーとPMがAIツールを実際にどう使っているかリサーチしていたのです。分かったのは、構造とレイアウトとインタラクションをプロンプトしていて、コンテンツは眼中にないということ。

この発見が設計を決めました。デザイナーが「コンテンツを見てほしい」と思っていないなら、頼まれるまで待つ skill は永遠に発火しない。だから、顧客向けの何かに取りかかった瞬間を捕まえるトップレベルのハブ skill を置き、そこから専門 skill に振り分ける形にした。トリガーの言葉も「content review」ではだめで、デザイナーが実際に使う言葉でなければならなかった。

UXエンジニアリングの視点では、これはトリガー設計というインタラクション設計の話です。利用者が使う語彙でトリガーを書く、というのはコマンドパレットや検索の設計でずっと言われてきたこと。skill をプロダクトとして見ると、発見可能性の問題として同じ道具立てで扱えます。そして最後に詰まったプラグイン化を解いたのは Claude ではなく、Slack で答えてくれた同僚のエンジニアたちでした。「忙しさを保ったまま制御を失うのは簡単すぎる。作っているもののなかの決定を説明できないなら、あなたは仕事をリードしていない。従っている」。

### [What vibe coding a Figma plugin taught me about content design](https://uxcontent.com/what-vibe-coding-a-figma-plugin-taught-me-about-content-design/)

> **出典**: UX Content Collective | **公開日**: 2026-08-12 | **カテゴリ**: ux-writing

**3行まとめ**
- Coinbase のコンテンツデザイナーが、LibreChat 上のエージェントを Figma プラグインに移植しようとした顛末
- Cursor は「接続できた」と報告したが、eval を書いて確かめたらガイドラインをまったく参照していなかった
- 文字列を1つずつ採点する設計では画面全体の破綻を検出できず、フレームを1つの体験として扱う形にプロンプトを書き直した

**詳細解説**

出発点は実績のあるツールでした。40人以上のプロダクトデザイナーが毎日使っている、LibreChat 上のコンテンツデザインエージェント。唯一の難点は、スクリーンショットをアップロードするために Figma を離れる必要があることでした。中身は30ページのシステムプロンプトをモジュールに分けたもので、その外側に何年もかけて作られた何百ページものコンテンツ戦略ガイドラインが Glean MCP 経由でぶら下がっています。価値があるのは、この分厚い外側のほうです。

最初の教訓は手品でした。Cursor が「LibreChat のエージェントを Figma に接続しました」と報告し、著者は自分のプロンプト力に感心します。ところが疑り深さが勝って eval を書いてみると、「大きな数字はどう省略するか」「この製品で避けるべき語は何か」に答えられない。ガイドラインを一切見ていなかったわけです。原因もはっきりしていて、LibreChat のエージェントはプログラムではなく、システムプロンプトとMCPとモデルの組み合わせを固めた「容器」でしかない。容器を Figma に持ち込む方法は最初から存在しませんでした。作り直したのは17個の SKILL.md と、それを呼び分ける system.md です。同じ eval を通したら、今度は合格しました。

本題は次の問題です。プラグインは見出し、本文、CTAを1つずつ独立に採点していました。記事に出てくる例が分かりやすい。見出し「Leave without saving?」、本文は本人確認書類のアップロードの話、CTAは Continue と Cancel。1行ずつ読めばどれも問題ないのに、画面として読むと意味が通りません。見出しは保存の話をしているのに本文が別の話をしていて、CTAは見出しの問いに答えていない。全部が「合格」して、画面は混乱の塊になる。

書き直したあとの出力は、見出し「Save before you go?」、本文「You can pick up right where you left off.」、CTAは Save と Leave without saving。著者の言葉では「ルールに対して単一の文字列を採点するのは戦いの半分でしかなく、いちばん大事なのはすべての文字列を協調させることだった」。

もう1つの事件が source folder です。エンジニアに渡そうとしたら「ソースフォルダはどこですか」と聞かれ、渡せるものが dist/ui.html しかないことに気づきます。Figma はプラグインの実行に dist と manifest.json しか要求しないので、Cursor はソースを不要と判断して捨てていました。人間のエンジニアなら絶対にやらない判断です。読むことも保守することもデバッグすることもできなくなるからです。

UXエンジニアリングの視点で見ると、この記事の2つの失敗は同じ形をしています。「1つずつ見ると正しいが、全体としては壊れている」。コンポーネント単位の lint が全部通るのに画面が破綻する、という現象とまったく同じ構造です。評価の単位を上げないと検出できない種類の欠陥があり、それを知っているのが職能の中身だ、という話でもあります。アクセシビリティリードの言葉も残しておきたいところです。「vibe coding は強力な増幅器だが、コードはAIに与えた指示の分しかアクセシブルにならない。手動チェックを飛ばさないこと。キーボードでタブして回り、スクリーンリーダーを立ち上げること」。

### [Let your designs fail for the right reasons](https://blog.mozilla.org/ux/2026/08/let-your-designs-fail-for-the-right-reasons/)

> **出典**: Sidebar | **公開日**: 2026-08-12 | **カテゴリ**: design

**3行まとめ**
- プロトタイプの制約がユーザビリティテストの失敗理由を曖昧にしている、という Mozilla の UX デザイナーからの問題提起
- Firefox Android の実アプリに Claude で機能を組み込み、ネイティブ忠実度のプロトタイプでテストした
- 分岐ロジック、メタデータの取得、入力バリデーションは、作り込んだ画面遷移では表現しきれない

**詳細解説**

「walled prototype（壁に囲まれたプロトタイプ）」という命名が効いています。walled garden になぞらえたもので、参加者は動けるけれど、あらかじめ用意された道の上だけを動ける空間のことです。Figma でプロトタイプを作ると、起こりうるインタラクションをすべて先回りして明示的に定義する必要があります。複雑さが増すほど画面が増え、接続は壊れやすくなり、アニメーションの保守が面倒になる。「ある時点から、体験を設計しているのではなくプロトタイプを管理している」。

そのしわ寄せは参加者に届きます。テスト参加者はプロトタイプだと気づくと行動が変わる。探索をためらったり、タスクの意図を汲もうとしたり、詰まったらあちこちタップしたりする。issue type を数種類しか選べるようにしていなければ、参加者は「何をしたいか」と「プロトタイプが何を許してくれるか」を同時に考えることになります。初期のコンセプト検証なら道を狭めるのは有効ですが、体験全体の挙動を知りたいときには足かせになる。

題材の Report Broken Site という機能が、この差を際立たせます。タブに応じたURL・スクリーンショット・ブラウザ情報・トラッキングデータの取得。実際のテキスト入力とカーソル移動とオートコレクト。「サイトが読み込めない」を選ぶと詳細は任意だが「その他」を選ぶと必須になる分岐。「その他」のときの文字数バリデーションとエラー表示。どれも画面遷移の連鎖では再現しづらいものばかりです。

環境そのものが体験の一部だ、という指摘も実感があります。平均的な端末サイズを想定して作ったUIが大きい端末で間延びする。遅い回線でプロトタイプがもたつく。プロトタイピング環境の制約でレイアウトが期待どおりに適応しない。これらは全部「デザインの問題」と誤認されるリスクを持っています。

トレードオフも正直に書かれています。初回セットアップは複雑で、ターミナル、ビルド環境、IDEへの慣れが要る。バックエンドにはまだ繋いでいないし、クロスデバイスの検証もこれから。参加者の行動が実際に変わるかどうかも、まだ検証していないと明言しています。

UXエンジニアリングの視点では、この記事はこの職能の存在理由そのものです。デザイナーが実コードに手を伸ばすときの障壁は、コードを書く能力というよりビルド環境のほうにあります。逆に言えば「初回セットアップが複雑」という難点は、環境を整える人がチームにいれば消える種類の障壁です。もうひとつ拾っておきたいのは「要件が対話のなかから立ち上がってくる」という観察でしょう。エッジケース、欠けている状態、曖昧な挙動は、作りながらだと見つかります。

### [State of AI in Design Systems](https://state-of-ai-in-design-systems.netlify.app/)

> **出典**: Sidebar | **公開日**: 2026-08-12 | **カテゴリ**: design

**3行まとめ**
- 主要デザインシステムのAI対応状況を、MCP・llms.txt・Agent Skills・AGENTS.md といった軸で1件ずつ実地調査したサイト
- AI-native 14件、Invested 5件という階層で、Ant Design、Carbon、Chakra UI、shadcn/ui、Material UI、Polaris などを収録
- 「Confirmed absent（不在を確認）」を根拠付きで書いているのが特徴で、Figma Code Connect はほとんどのシステムで不在

**詳細解説**

調査の軸は10以上あります。MCPサーバー、llms.txt、Agent Skills、エディタのルールファイル（.cursorrules や copilot-instructions）、AGENTS.md / CLAUDE.md、AI向けドキュメントページ、エージェント発見レイヤー、CLI、Figma Code Connect、Storybook、その他の取り組み。デザインシステムがAIエージェントから使われる前提で、どの接点を用意しているかを一覧にしたものです。

いちばん際立つのは「ない」ことの書き方です。たとえば Ant Design の Code Connect の欄には「12522b38 時点のツリーに `*.figma.tsx` も `figma.config.json` も code-connect パスも存在しない」と書かれ、Storybook の欄には「master の完全な再帰リスト（4,973ファイル、truncateなし）に .storybook ディレクトリもストーリーモジュールも storybook を含むパスも存在しない」と書かれています。「見つからなかった」と「調べて存在しないことを確認した」を区別している、ということです。この粒度で書かれた調査はなかなかありません。

読み取れる傾向がいくつかあります。MCPサーバーと llms.txt と Agent Skills の3点セットは、AI-native と分類された層ではほぼ標準装備になりました。一方で Figma Code Connect は Primer と Carbon を除いてほぼ全滅です。デザインとコードを機械的に結ぶ部分だけが、まだ誰も解けていない。Storybook を持たないシステムも目立ちます。shadcn/ui、daisyUI、Nuxt UI、PatternFly、Cloudscape、Material UI は、いずれも独自のドキュメントサイトにライブデモを寄せています。

個別におもしろい項目もあります。Shopify Polaris の「AI-crawler blocklist + noai メタ」は anti-affordance と注記されていて、AIに読ませない方向の選択が同じ表のなかに記録されている。Atlassian と Ant Design の design.md は、ポータブルなデザインコンテキストという別方向の試みです。Nuxt UI の「.well-known/api-catalog、MCP の server-card.json、Link ヘッダ、sitemap.md、マークダウンのコンテントネゴシエーション」という発見レイヤーの並びは、エージェントに見つけてもらうための工夫の見本市になっています。

**詳細解説**

warm pool は、ビルドがすぐ始められるように待機しているコンテナ群です。どのコンテナが準備できているか、各コンテナの認証トークン、そして実行中のビルドと課金対象のデプロイを結ぶマッピングを持っています。全部 Redis に置いていました。速かったし、当時は理に適っていた。

ロールアウトは Redis のみ、二重書き込み、シャドウリード、DynamoDB プライマリ、DynamoDB のみ、の5段階です。各段階にフラグとロールバックを用意し、一致率・書き込みエラー・クエリ遅延・期限切れ件数のダッシュボードが段階を進める判断材料になりました。不一致はすべて、実際のバグか、二重書き込みの競合か、想定内の差異のいずれかまで追い切ってから次に進んでいます。

途中の2つの事故が示唆的です。3月、比較機構そのものの負荷で1リージョンのビルドが落ちました。ステータスカウントにインデックスがなくO(n)だったところを、常時カウントしていたからです。同じ月、移行元の Redis が実際にダウンしましたが、warm pool はすでに DynamoDB を参照していたので生き延びました。移行の理由が、移行の完了前に現実になったわけです。

本題は4月です。供給ループが止まり始めました。シャドウのデータは健全で、クエリごとの遅延も許容範囲に見えていたのに、どちらも測っていない挙動が壊れていた。「check → create」をコンテナごとに繰り返すN+1で、Redis が速すぎて隠れていたのです。17個ごとに1回だけチェックするバッチ化も検討しましたが、レイテンシ比という定数を焼き込むことになるので却下し、供給呼び出しの並行化を選びました。最悪ケースは少し古い情報から数台余分に作ることで、それを「受け入れるコスト」としてPRに明記しています。

さらに分かったのは、Redis 時代にも同じループは1分以上止まることがあったという事実でした。証拠はずっとテレメトリのなかにあったのに、warm pool は需要の手前に立つ位置にあってリクエストパスに入らないため、誰も見に行かなかった。UXエンジニアリングの視点で言えば、この形の暗黙の前提はフロントエンドにも山ほどあります。localStorage が同期だから成立している処理、キャッシュヒットを前提にしたレンダリング、即座に返る前提で await を並べた初期化。ストアや依存を差し替えるときに怖いのはデータの移し替えではなく、速さに乗っかっていたコードのほうです。「1msから15msへのP90の劣化が warm pool の管理ロジックを落としうる」という振り返りの一文を、2月には誰も書いていませんでした。

- 上位100社は収益の48%を本国外から得ており、それを支えているのはローカライズ

**詳細解説**

2026年の Forbes AI 50 のうち88%が Stripe を使っていて、収益上位100社は3年目までに平均120市場に到達している。そういう位置から書かれたレポートです。

指標の選び方が読みどころです。単純な市場規模で並べると、AI企業にとっての良い市場ではなく「どんな企業にとっても良い市場」が出てきてしまう。そこで Stripe 上の総支出に対するAI支出の比率という別の軸を足しています。この見方でインド、メキシコ、ポーランド、UAEが上がり、ブラジル、日本、韓国は絶対額でも比率でも高いという結果になりました。

韓国の分析が具体的です。成長率134%で、大きい市場でありながら比率も高い。理由として、安全性のガードレールを設けつつ成長を促す2026年の「基本法」、政府が支援するスタートアップ環境、そしてAIの日常化について「期待より不安が勝る」と答えた人の割合が世界でもっとも低かったという Pew の調査を挙げています。突出しているのはメキシコで、前年比264%。米国からの近さと投資が背景にあり、すでに混み合った高成長国より足がかりを作りやすい、という読みです。

後半はローカライズの効果です。成長の速いAI企業は、平均でローカル決済手段を2倍多く使っている。Gamma はインドのUPIを有効にして国内収益が22%増えた。Adaptive Pricing を使うサブスク事業者は初回コンバージョンが平均4.7%、ライフタイム価値が5.4%改善し、Runway では最大17.7%の伸びが出た。

UXエンジニアリングの視点で見ると、決済手段の選択肢はUIの話です。UPIが並んでいるかどうかで22%動く。i18n をテキストの翻訳だと捉えていると、この部分がまるごと抜け落ちます。通貨の表示、決済手段の並び順、価格の見せ方、そもそもその国で当たり前の支払い方が選べるか。「進出しているだけでは収益にならない」という主旨は、200カ国に対応したところで終わりではない、という実務の話でもあります。

Stripe の営業資料でもあるので、数字はそのつもりで読む必要があります。ただ、市場規模ではなく比率で見るという分析の組み立て方自体は、自分たちのデータを眺め直すときにも使える視点でしょう。

### [2年かけてたどり着いた1on1の形 —— メンバーと一緒に1on1の最適解を探る](https://tech.smarthr.jp/entry/2026/08/13/080000)

> **出典**: SmartHR Tech Blog | **公開日**: 2026-08-12 | **カテゴリ**: design

**3行まとめ**
- SmartHRのチーフ（プレイングマネージャー）が2年かけて作り上げた1on1の進め方
- ゴールは「メンバー自身が気持ちよく働けるようになっていること」で、主語がメンバーである以上、四半期ごとに1on1そのものを評価してもらう
- アイスブレイクは「最近の調子は10点満点中何点ですか？」という定型文から必ず入る

**詳細解説**

出だしが率直です。チーフになりたての頃は1on1に苦手意識があった。何を話せばいいか分からない、メンバーにとって有意義な時間になっているのだろうか。問題を解決しよう、成長してもらおうと、自分でハードルを上げていた、と。

転換点は、ゴールの置き方を変えたところにあります。メンバー一人ひとりがプロフェッショナルで主体的に取り組んでいるなら、教えたりコントロールしたりすることは成果の最大化につながらない。むしろモチベーションの源を一緒に見つけたり、日々の業務を阻害する何かを取り除いたりするほうが効く。一方的な働きかけはメンバーの選択肢を狭め、自主性を損なう、とまで書いています。

設計の具体が細かくて役に立ちます。初回の1on1で場そのものをすり合わせる。どんな時間だと嬉しいか、目的の確認と調整、定例アジェンダの整理、頻度と時間の設定。目的にはたたき台を用意しておくのがポイントで、そのたたき台にはメンバー側の目的（不安が解消できている、成長を実感できている）とチーフ側の目的（無理なく働けているかの把握、目標達成に必要なサポートと障害の把握、期末のサプライズ評価を避ける）が両方書かれています。自分側の目的があることを隠さず、先に伝えたうえですり合わせる。この誠実さが効いているのだと思います。

アイスブレイクの「10点満点中何点ですか」も、うまい定型化です。点が高ければ要因を掘り下げて人となりを知り、低ければ業務負荷やチームの課題として見る。そして著者が書いているとおり、点数をつける行為自体がメンバーにとって自分を振り返る時間になる。「今日は少し早くあがろう」「来週は有給を取ろう」という行動のきっかけが、そこから生まれます。

振り返りの質問も具体的です。「1on1どうでしたか、改善点はありますか」では出てこないので、モチベーションが上がった／下がったタイミングはあったか、もっと話したかったことはあるか、アジェンダで変えたいところは、頻度と時間は適切だったか、と絞って聞く。

UXエンジニアリングの視点で読むと、この記事の構造はプロダクトの改善サイクルそのものです。ゴールを利用者側の状態で定義し、初回にすり合わせ、定期的に評価をもらって適応する。「私がどれだけいい1on1をしたつもりでも、それだけでゴールに近づけたかは分かりません」という一文は、作り手の自己評価と利用者の体験を分けて考える話に、そのまま置き換えられます。締めの「1on1の絶対的な正解はない。ただ二人の間に最適解はある」も、汎用のベストプラクティスと個別の文脈の関係をよく言い当てています。

### [I'm leaving OpenAI to build Jurassic Park](https://taylor.town/leaving-openai)

> **出典**: Sidebar | **公開日**: 2026-08-12 | **カテゴリ**: design

**3行まとめ**
- OpenAIを辞めて「Jurassic Park」を創業する、という体裁の風刺エッセイ
- 「恐竜は1億6500万年間、AIサイバー攻撃を一度も受けていない」といったグラフが真顔で並ぶ
- 末尾の disclosure は「この投稿は爬虫類人世界政府から一部資金提供を受けています」

**詳細解説**

念のため書いておくと、これは実際の転職エントリではありません。AI安全性をめぐる言説、スタートアップの資金調達ピッチ、そして「それらしいグラフを出せば何でも正当化できてしまう」という風潮を、まとめてパロディにした一本です。

いちばんよくできているのがチャートの部分でしょう。セキュリティスコアカードでは、人間が11,000件超のインシデントで評価F、Claudeが3件、OpenAIが1件でどちらもC、ティラノサウルスとトリケラトプスとステゴサウルスは0件でA+。ゼロインシデントを最高評価にすると何が起きるか、という皮肉です。次のグラフでは、恐竜の属数の推移とAIサイバー攻撃件数の推移を軸の切れ目でつなぎ、「恐竜が絶滅したちょうどそこから攻撃が始まっている」ように見せます。エンセファリゼーション指数と体重の散布図、消費電力の対数グラフ、雇用の予測線と、それらしい単位を持つ図が最後まで続きます。

主張のほうも一貫して真顔です。「経済学者はAIが人間の仕事の99%（誤差±5%）を奪うと見ている。だから Jurassic Park こそが究極の雇用対策だ」「AIは牛を育てられないし、糞を拾うには物理的な身体が要る」。ロードマップも Phase 1 の建設が完了済みで、Phase 2b では Boston Dynamics 製の機械恐竜を走らせ、Phase 5 で「安全のために大きなオフスイッチを付けた」データセンターをティラノサウルスの展示場の中に作ることになっています。

締めは映画のマルコム博士の台詞のもじりです。「AI科学者たちはできるかどうかに夢中で、やるべきかどうかを考えなかった。幸い我々の恐竜科学者たちは、やらねばならないことをやっている」。

UXエンジニアリングの視点で拾うなら、やはりチャートでしょう。それらしい軸とそれらしい単位を持つグラフは、中身が無意味でも説得力を持ってしまう。今週このニュースレターに並んだ記事にも、数字とグラフで語るものがいくつもあります。軸の取り方は妥当か、比較対象は揃っているか、その指標を選んだ理由は何かを見る癖は、作る側でも読む側でも持っておきたいところです。この記事は、その練習台としてもよくできています。
