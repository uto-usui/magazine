### [Where the disabled button got its rule](https://www.hipuku.dev/writing/where-the-disabled-button-got-its-rule)

> **出典**: Sidebar | **公開日**: 2026-11-13 | **カテゴリ**: design

**3行まとめ**
- Material、Carbon、Polaris、Primer など8つのデザインシステムでは、無効なボタンの文字のコントラストが 1.36:1 から 3.35:1 で、どれも Tab キーで届きません
- 「無効な項目は選べない」という決まりは、1983年の Apple Lisa のメニューにさかのぼります。1980年の社内規約では、薄く表示した項目も選べることになっていました
- Material の `softDisabled` や Primer の `inactive` のように、無効に見えても Tab で届き、使えない理由を伝えられる状態を足すデザインシステムが出てきています

**詳細解説**

8つのうち、Atlassian、GOV.UK、Primer はガイドラインで無効なボタンを避けるよう書いています。Polaris と Carbon は、まわりの UI で理由を説明することを条件に認めています。Material、Spectrum、shadcn/ui は立場を示していません。コントラストの数字は、各システムが npm で公開している色の値から計算したものです。WCAG は、操作できない部品の文字にコントラストの基準を設けていません。GOV.UK の緑のボタンも、有効なときの 5.35:1 が無効にすると 2.13:1 まで下がります。

Polaris だけは作りが違います。ドキュメントでは無効なボタンと説明していますが、実際には `aria-disabled` に `tabindex="-1"` を付けた要素を出力していて、結局 Tab の順番から外れます。ライブラリのほかの部分はこのボタンをフォーカスできる部品として扱っていたので、ダイアログのなかにフォーカスを閉じ込める処理を、このボタンを飛ばすように直す必要が出ました。

W3C の ARIA Authoring Practices が、使い分けの目安を示しています。表の1ページ目の「前へ」のように、まわりを見れば使えない理由がわかるものは `disabled` で十分です。メニューの項目、タブ、ツールバーのボタンは `aria-disabled` にして Tab で届くようにします。両方を持つデザインシステムも、二重送信の防止のように試すこと自体ができない操作には厳しいほう、権限の不足や入力の不足のように利用者が直せるものには届くほうを使っています。フォームの送信ボタンを無効にしている画面は、足りない入力がボタンの近くで見えるかどうかで分けておくと、どちらの状態に移すかを決めやすくなりそうです。

届く状態は作る手間が増えます。クリックを止めるコード、ほかのキーボード操作を壊さないフォーカスの扱い、スクリーンリーダーが読み上げる位置に置いた理由が要ります。Atlassian は「無効なボタンにツールチップを付けない」と書いています。フォーカスを受けないボタンのツールチップは、キーボードでは開けないからです。

### [Building interfaces that understand what we want to do](https://agustinbarrientos.com/writing/senior-eye/interfaces-that-understand-what-we-want)

> **出典**: Sidebar | **公開日**: 2026-11-13 | **カテゴリ**: design

**3行まとめ**
- 決まった選択肢から1つを選び、選択肢ごとの確率を返す「判断モデル（decision model）」を UI に組み込む方法を、その場で試せるデモとコードで解説しています
- Chrome の Decisions API を使うと、ブラウザのなかのモデルで、無料かつオフラインで判断できます。ただしまだフラグを有効にしないと使えない実験段階で、延長されなければ Chrome 161（2027年1月19日予定）でフラグがなくなります
- 8つのモデルを5種類のテストで比べたうえで、しきい値は間違えたときの損の大きさで決め、正解のわかっているデータで調整するよう勧めています

**詳細解説**

レストランのたとえで説明しています。客（利用者）は好きな言葉で注文し、店員（AI）は何を勧めるか予測できませんが、出せるのはメニューにある料理だけです。メニューを書くのは作り手なので、利用者が目にする文言はすべて事前に書いてレビューし、翻訳しておけます。`if` で書ける判断なら `if` で書き、生成 AI は多くの判断には重すぎる、という立場です。記事の計測では、Claude Haiku 5.5 は判断モデルの Jev に比べて約5倍の時間がかかり、費用は約3倍でした。

デモは3つあります。王に会わせるよう門番を説得するミニゲーム、送り先のチャンネルに合わない投稿を送る前に警告するチャット、選んだ文から「タスクを作る」「カレンダーに保存」などの操作を1つ提案するタスク管理です。しきい値は損の大きさで変えています。操作の提案は、外れても「引用」が残るだけなので50%で出します。チャットの警告は70%から始め、問題のない投稿にも出すぎたので98.5%に上げ、さらにスペイン語の機微な投稿が98.4%だったので98%に下げました。

「用件を答えたか」をはい・いいえで聞くと、Gemma 4 は本当の答えにも「いいえ」と返したので、4択に変えています。選択肢の順番を逆にしただけで、賄賂を差し出した人を含む4人の敵意ある訪問者が門を通りました。Chrome の新しい小さなモデル EmbeddingGemma は Gemma 4 より26〜59倍速い一方、正しい選択肢を選べる割合は Gemma 4 の半分ほどです。

選択肢の数だけ UI の反応を作るので、デザインでは選択肢ごとの画面の状態を描くことになります。門番がしきい値に届かないとき「はっきり言え」と聞き返すように、確信度が足りないときの状態も1つ描いておくと、実装との食い違いが減りそうです。本番では Chrome の API を先に試し、使えなければ Gemini Decision 1 などのクラウドに切り替える組み方を勧めています。Gemini の無料枠は1日10,000回までで、送った内容は Google の製品改善に使われます。

### [The components of agent memory](https://www.anthropic.com/research/components-of-agent-memory)

> **出典**: Sidebar | **公開日**: 2026-11-11 | **カテゴリ**: design

**3行まとめ**
- Anthropic が、AI エージェントの記憶の作り方を、CL-Bench やポケモン赤のプレイなどの評価から整理しています
- 新しいモデルには、何を記録するかを細かく指示せず、記憶が何のためにあるかだけを伝えたほうが成績が上がりました。「失敗だけを記録する」という規則を足すと、記憶による伸びの多くが消えています
- 作業の合間に記録を読み直して記憶を整える「dreaming（夢を見る）」で、誤ったメモの修正、wiki 作り、毎回読み込む層の整理ができると報告しています

**詳細解説**

ポケモン赤のプレイでは、Claude Sonnet 3.7 が戦闘や道具ごとにファイルを作り、225フォルダに413ファイルを書いてバッジ1個でした。Claude Fable 5 は2フォルダに9ファイルと `global.md` だけで、バッジは4個です。所持金や現在地のように画面を見ればわかることは書かず、戦略や確かめた規則のように、書かなければ消えることだけを残していました。

dreaming では、セッションの記録と照らし合わせてメモを直します。ある場所の向きを逆に覚えたメモを直さなかった回では、同じ段差から3回落ちて先に進めませんでした。直した回ではそのまま先の町に着いています。約35万ファイルの社内文書から wiki を作った実験では、検索だけで53%、検索と wiki を合わせると54%から61%まで上がり、1問あたり約2万トークンを節約しました。1つの文書を文字で検索すれば済む課題では差が出ず、wiki がもとの文書より大きくなって何もまとめていない例もあります。

契約書から wiki を作る課題では、複数のエージェントが同じ表を同時に書き換え、条件が抜けていました。契約ごとに1ページを1つのエージェントが書き、条文をそのまま引用する指示に変えると、満たした評価項目は72%から100%になりました。毎回の会話に読み込ませる層は小さく保つ必要があり、Claude Code の自動メモリも `MEMORY.md` の先頭200行か25KBまでしか読み込みません。指示ファイルが長いほど守られにくくなる、と Claude Code のドキュメントでも注意しています。

### [Pew Research Finds the Same Problem We Did with Digital Twins](https://measuringu.com/pew-research-finds-the-same-problem-we-did-with-digital-twins/)

> **出典**: MeasuringU | **公開日**: 2026-11-10 | **カテゴリ**: ux-research

**3行まとめ**
- 実在の人のデータから作った AI の「デジタルツイン」に調査へ答えさせた Pew Research Center の研究を、MeasuringU が自分たちの SUS（使いやすさの標準アンケート）の2つの実験と比べています
- Pew で成績のよかった設定（Claude Opus 4.6 に詳しいプロフィールと専門家の所見を渡したもの）でも、約300問の平均誤差は12ポイントでした。MeasuringU の業務ソフトの実験でも、SUS を約10.5点高く見積もっています
- どちらも誤差が決まった方向にかたよるので、ツインの数を増やしても打ち消し合わず、実在の利用者の代わりにはならないと結論づけています

**詳細解説**

大きく外れた質問もあります。合衆国憲法修正第1条が保障する権利を正しく答えられたアメリカ人は52%でしたが、ツインは98%と見積もりました。ツインが「わからない」を選んだ回数は人の約4分の1で、半数近くの質問に、どのツインも選ばなかった選択肢がありました。モデルによって外れる向きも変わり、GPT-5.1 は世論を実際より極端に、Opus 4.6 は穏やかに描いています。

製品の順位はおおむね合っていても、点数の水準がずれます。MeasuringU の実験では、GitHub の評価が D から B に、ZipRecruiter が C から A に上がりました。人の回答が25〜75%の中間にあるときほど誤差が大きく、端に近いときは小さくなる傾向も両方の研究に出ています。ベンチマークの基準を超えたか、改善したかのように、点数そのもので判断する場面にはそのまま使えません。

同じ人の生の回答をさらに足しても、精度は0.1点しか変わりませんでした。質問に関係の深い態度の項目を足すと誤差が下がった可能性はありますが、得点の上限の影響と区別できないと断っています。Pew は、回答者の代わりに AI を使う予定はない一方、自由回答の分類や集計のコードには AI を使い続けるとしています。

### [Don’t make a human do what AI is amazing at](https://www.johnnunemaker.com/dont-make-a-human-do-what-ai-is-amazing-at/)

> **出典**: Sidebar | **公開日**: 2026-11-11 | **カテゴリ**: design

**3行まとめ**
- John Nunemaker さんが、自分の関わる20のリポジトリに小さな改善の PR を出し続けるプロンプト「Nunebot」の作り方をまとめています。10月18日からの12日間で269件を開き、250件をマージしました
- 1回に1つ、読んですぐマージできる大きさの変更だけを選ばせていて、マージされた PR の変更行数の中央値は43行です
- 作ったあとは `/simplify`、`/qa`、`/codex review` の順に通し、2回目以降のレビューは直した部分だけに絞って、指摘を追いかけて PR が膨らむのを止めています

**詳細解説**

PR には、当てはまる証拠を必ず付けさせます。main では失敗してブランチでは通るテストとその出力、テストとリンターの結果、動いている様子、画面が変わるなら前後のスクリーンショット、速くなったと言うなら前後の数字、削除なら使われていないことを示す検索結果です。PR 本文は「なぜ」「何を変えたか」「証拠」「性能と互換性」「レビュー」「リスクと戻し方」の順で、20件ほどマージしたころから、コードを読まずに本文だけでマージするようになりました。

閉じた PR や「いいえ」と答えた内容は `taste.md` に規則として書き足され、11日で107個になっています。最近ルーティングを外したコードを不要と判断して2,248行を消す PR が来たときは、「ルーティングから外しただけで不要とは限らない」という規則が加わりました。1つのリポジトリで開いたままの PR は Dependabot にならって5件まで、本番や外部サービスは読み取りのみ、マージやデプロイはさせない、という制限も付けています。

マージした250件のうち46件は、足した行より消した行のほうが多い PR です。直前の PR が追加ばかりなら、削除の候補を優先するよう指示しています。見た目が変わる PR に前後のスクリーンショットを付けさせておけば、デザイナーもコードを読まずに PR を確かめられます。

### [There’s no better name for design systems](https://karolinaszczur.com/journal/translation-not-rebranding/)

> **出典**: Sidebar | **公開日**: 2026-11-11 | **カテゴリ**: design

**3行まとめ**
- デザインシステムのよりよい呼び名を探すのをやめ、相手の職種に合わせて言い換える「翻訳」の問題として扱おう、という Karolina Szczur さんのエッセイです
- 「プロダクト」はマネージャーに、「方法論」はデザイナーやエンジニアに、「インフラ」は経営や財務に届きやすく、どの呼び方にも弱いところがあります
- ふだん選んでいる呼び方は「インフラ」で、職種をまたいで通じやすいことと、Deb Chachra『How Infrastructure Works』の考え方を理由にしています

**詳細解説**

プロダクトは後回しにしたり買わなかったりできるので、デザインシステムはずっと予算と注目を取りに行く立場になります。方法論は、経営層に費用と見返りを数字で示しにくい呼び方です。インフラでも、削れる費用として扱われれば同じ予算の争いに戻ります。

デザインシステムの担当者の外の人と話すときに、Figma や Storybook、トークンやアイコンといった中身を並べると、相手の関心が離れていきます。相手が知りたいのは、デザインシステムで何ができるようになるかです。「デザイナーのためのもの」と名前から受け取られ、使われないまま古くなったデザインシステムも多いと書いています。目指すところは、組織がデザインシステムとは何かを理解することより、どのチームも自分たちにとって何の役に立つかをわかっていて、ものを作るときの当たり前のやり方になっていることだとしています。

### [Should You Actually Add AI To That? A Four-Question Audit For Product Teams](https://smashingmagazine.com/2026/11/should-you-add-ai-audit-product-teams/)

> **出典**: Smashing Magazine | **公開日**: 2026-11-12 | **カテゴリ**: design

**3行まとめ**
- AI 機能を足す前に「利用者の手間は減るか」「今のやり方に勝つか」「誤りに気づけるか」「1年後も誤りを見抜けるか」の4つを、実際にその仕事をしている人と一緒に確かめる手順です
- 冒頭の例では、保険の不服申し立ての判定文を AI に書かせると、署名できるほど読み込むのに書くのと同じ時間がかかりました。関係する規定と過去の判断を探す部分だけに絞り直すと、確認の時間が減っています
- 4つの答えは「デザインの条件」としてデザインの指示書に書き込み、誤りが見えにくく影響の大きい機能には、出典の表示と確認の促しがなければ出さないとしています

**詳細解説**

手間は、考える量、クリックの数、AI が加わったあとに利用者が引き受ける確認まで含めて数えます。ローン番号を入力する欄を AI に埋めさせると、数秒で済んでいた入力が、合っているかを確かめる注意の要る作業に変わります。同じ機能でも、パターンの蓄えが少ない若手のアナリストには役立ち、ベテランには読み比べる手間が増えるだけ、ということもあります。そのため、使う人の層を決め、ほかの層には外れる道を用意します。

誤りについては、起こりやすい誤りを3つ挙げ、見えやすさと影響の大きさで評価します。旅行の計画で休館日の美術館を勧められても、出力には何もおかしな点が見えません。2023年の放射線科の実験では、経験の長い読影医でも、AI の提案が正しいときは82.3%、誤っているときは45.5%しか正しく分類できませんでした。経験の浅いグループは79.7%から19.8%まで下がっています。判断する力を保つ仕組みとして、AI の出力を見る前に自分で判断する確認や、一部の案件を AI なしで回す方法を挙げています。

会議の要約の例では、行動項目ごとに元の発言のタイムスタンプへのリンクを付けることが条件になりました。出典と取得日の表示は AI の出力を出す画面のどれにも要るので、デザインシステムに部品として用意しておくと、機能ごとに作り直す手間が減ります。

### [QA チームで Jev 勉強会を開いたら、AI に任せる範囲と人に残したい範囲が見えてきた](https://tech.layerx.co.jp/entry/qa-jev-study)

**3行まとめ**
- LayerX の QA エンジニア16人で、判断に特化した AI「Jev」の勉強会を開き、20分で78枚のアイデアを出して使いどころを整理しています
- 事前に作ったチケットのラベル付けでは、ルールで判定し、Jev が確かめ、食い違うか確信度が低いものだけを Claude に回して、224件で人のラベルとの一致率が94.6%になりました
- AI に任せる範囲は「誤っていたとき気づけるか」「妥当性の判断に理由が要るか」の2つの問いで決めています

**詳細解説**

見た目の回帰テストで出た差分を「意図した変更か崩れか」で仕分ける作業にこの2つの問いを当てると、崩れを意図どおりと判定された差分は誰も見なくなります。人が見る順番を決めるところまでにとどめるのが、この整理に沿った任せ方になりそうです。

### [KMP撤退の意思決定と得られたもの](https://developers.cyberagent.co.jp/blog/archives/67436/)

> **出典**: CyberAgent Developers Blog | **公開日**: 2026-11-13 | **カテゴリ**: frontend

**3行まとめ**
- iOS と Android でロジックを共通化する Kotlin Multiplatform（KMP）から撤退した判断を、導入で受け入れていたトレードオフとあわせて説明しています
- KMP を使っていた間は、Swift 6.0 に上げると KMP 側でクラッシュする問題で約1年対応を進められず、SwiftUI のプレビューもワークアラウンドで動かしていました
- 撤退でインストールサイズは40MB、ダウンロードサイズは4.7MB減り、起動時間は50ms短くなりました

**詳細解説**

KMP の利点は実装の手間だけでなく、「仕様と実装が合っているか」「両 OS の実装が合っているか」を確かめる手間が、サーバーや QA を含む全職種で減ることだと整理しています。一方で、Repository だけのような部分的な導入でもプラットフォームは結びつき、ビルド時間は10〜20%延び、CI の KMP 関連の工程に4〜7分かかっていました。API クライアント、約10画面の Presenter、主要機能のロジック、ログまで共通化していても、アプリ全体から見れば一部で、制約はアプリ全体にかかっていました。

### [Web-Perf Wednesday 017 – Prebid Stops Re-downloading Its Manifest](https://csswizardry.com/2026/11/web-perf-wednesday-017-prebid-stops-redownloading-its-manifest/)

> **出典**: CSS Wizardry | **公開日**: 2026-11-11 | **カテゴリ**: css

**3行まとめ**
- 広告の入札ライブラリ Prebid.js の 11.48 で、jsDelivr の `bundle.js` ローダーが毎回違う URL でマニフェストを取りに行き、ブラウザのキャッシュが効いていなかった問題が直りました
- 11.46 のマニフェストは Brotli で67KBあり、1,642個のチェックサムのうち747個は `storageControl` モジュールを使うサイトでしか要らないものでした
- 11.47 ではユーザー同期用の iframe を既定で15秒後に消すようになり、11.48 では広告の描画に失敗したことをイベントで受け取れるようになっています

**詳細解説**

原因は、マニフェストの URL のクエリ文字列に毎回ランダムなコールバック名が入っていたことです。jsDelivr は1年間キャッシュしてよいと返していたのに、ブラウザは使い回せませんでした。直したあとも初回は取りに行き、Prebid のバージョンを上げれば URL が変わるので、毎回67KBが消えるわけではないと断っています。

対象は 11.40 で入った jsDelivr の `bundle.js` ローダーを使うサイトだけです。ページのソースかウォーターフォールで `/prebid.js@.../dist/bundle.js` を探し、DevTools の「Disable cache」を外して1回目と2回目の表示を比べるよう勧めています。アップデート後は、2回目の `manifest.js` がキャッシュから読まれれば効いています。

iframe の件は、ある同期の仕組みが25秒で約174のホストから450〜1,000個の入れ子の iframe に膨らんでいた計測がきっかけです。描画の失敗は `adRenderFailed` で受け取れ、入札には勝ったのに広告が出ない状態を、需要がない状態と分けて記録できます。クエリにランダムな値を付けてキャッシュが効かなくなることは自前のスクリプトでも起こるので、同じ比べ方で、2回目の表示でも毎回取り直しているファイルを探せます。

### [Creating Diagrams and Graphs Using Modern CSS](https://blog.master.dev/creating-diagrams-and-graphs-using-modern-css/)

**3行まとめ**
- アンカー位置指定、`border-shape`、`shape()`、`if()` を組み合わせ、CSS だけで2つの要素を線でつなぐ連載の3本目です
- 2つの要素が近いときは中心どうし、縦の距離が小さいときは左右の辺どうしをつなぐように、`if()` の条件で線の形を切り替えています
