### [Agent Harness Engineering](https://addyosmani.com/blog/agent-harness-engineering/)

> **出典**: Addy Osmani | **公開日**: 2026-04-19 | **カテゴリ**: performance

**3行まとめ**
- コーディングエージェントは「モデル + ハーネス」であり、モデルを取り巻く足場の設計こそが実用的な挙動を決める
- エージェントの失敗は「モデルが悪い」ではなく「設定が悪い」と捉え、失敗のたびにルールや hook を増やすラチェット運用が肝になる
- ハーネスはモデルの進化とともに縮むのではなく、役割を変えながら動く生きたシステムである

**詳細解説**

Addy Osmani が Viv Trivedy の「harness engineering」という概念を整理した、今のエージェント活用における最良の整理のひとつです。主題はシンプルで、同じモデルでもハーネス次第で挙動は大きく変わる、というもの。Terminal Bench 2.0 でのスコアが、Claude Opus 4.6 を Claude Code のまま動かしたときと専用ハーネスで動かしたときで大きく差がつくという事例が、その主張を裏づけています。

ここで言うハーネスとは、システムプロンプトや `AGENTS.md`、ツール定義、MCP サーバー、サンドボックス、hook、サブエージェントの起動規則、そしてコンテキスト圧縮や継続の仕組みを含めた、モデル以外のすべてのことを指します。Osmani はこれを「振る舞いから逆算する」設計として捉え、フィルタリング、計画、検証、そしてコンテキストロット対策に対して、それぞれどのハーネス部品が対応するかを対応づけていきます。

UX エンジニアリングの視点でおもしろいのは、ここで語られている設計原則が、実は古典的な UX の考え方と地続きなことです。「失敗のたびにルールを足す」は障害対応のポストモーテム文化、「成功は静かに、失敗は雄弁に」は適切なフィードバックの設計、「10 の良いツールは 50 の重複したツールより強い」は情報アーキテクチャの単純化。エージェントを前に座らせた利用者として、こちらが見る景色を設計する営みこそが harness engineering なのだと読み替えると、だいぶ手触りが出てきます。

注意したいのは、良いハーネスは「ダウンロードできない」ことです。自社のコードベースや失敗履歴から蒸留されるものなので、他社の `AGENTS.md` を真似しても機能しません。ここは組織ごとの肌着のようなものだと考えたほうがよさそうです。

### [9 Accessibility Myths and Pushbacks (And How to Answer Them)](https://stephaniewalter.design/blog/9-accessibility-myths-and-pushbacks-and-how-to-answer-them/)

> **出典**: Stephanie Walter | **公開日**: 2026-04-22 | **カテゴリ**: design

**3行まとめ**
- アクセシビリティを気にかけることは簡単で、他者を説得することこそが難しい、という現場感覚から出発した記事
- 9 つのよくある反論（「障害のある利用者はいない」「予算がない」「ブランドが許さない」など）に対して、リフレーム・データ・戦略の 3 点セットで応答する具体策が並ぶ
- 「明日からできる小さな一歩」から始める草の根の変革を推奨している

**詳細解説**

axe-con 2026 での講演をもとにした、Stephanie Walter によるアクセシビリティ普及のプレイブックです。単なる WCAG 解説ではなく、「どう説得するか」という政治的で地味な営みに踏み込んでいるのが特徴。IBM の有名な「設計段階で直すコストを 1 とすると、運用段階での修正は 100 倍になる」という研究や、Deque の「アクセシビリティ問題の 67% は設計段階で生まれる」という数字が、デザイナーの早期介入の意味を数字で後押しします。

ビジネスサイドを動かすための数字もきれいに揃っています。世界の 13 億人が障害を抱え、家族友人を含めると 33 億人の潜在顧客、可処分所得にして 13 兆ドル規模。そして Nucleus Research の「視覚障害者の 23% が EC サイトでの取引を諦めている」という数値。KPI に接続して語るための材料がここに集約されています。

UX エンジニアリング文脈で印象的なのは、「ブランド色が変えられない」という反論への切り返しです。筆者は「ブランドを変えるのではなくデジタル用に拡張する」という捉え直しを提案し、Wise の黄色やパステル配色で作られたアクセシブルなカラーパレットを例に挙げます。デザイントークンをアクセシビリティ込みで設計できれば、これは実装側にもそのまま伝わります。

最後の「草の根運動」のパートは、とても等身大で、予算もマンデートもない状況でのスタート地点を 5 つほど示してくれます。ジャーニーマップにアクセシビリティの壁を乗せる演習など、小さなワークショップに落とし込める粒度の高いアイデアが並びます。

### [Background Coding Agents: Supercharging Downstream Consumer Dataset Migrations (Honk, Part 4)](https://engineering.atspotify.com/2026/4/background-coding-agents-dataset-migrations-honk-part-4/)

> **出典**: Spotify Engineering | **公開日**: 2026-04-22 | **カテゴリ**: engineering

**3行まとめ**
- Spotify の社内エージェント「Honk」で、約 1,800 件のデータセット消費パイプラインの移行タスクに取り組んだ実例報告
- BigQuery Runner と dbt のように標準化されたフレームワーク上では自動 PR を 240 本生成、約 10 人週ぶんの作業を削減できた
- 自由度が高く標準化されていない Scio では歯が立たず、データ基盤の標準化とテストの存在が前提になることが改めて明らかになった

**詳細解説**

Spotify のバックグラウンドコーディングエージェント「Honk」の運用事例シリーズ第 4 回です。今回扱うのは大規模なデータセット移行で、廃止されるふたつの利用者データセットには約 1,800 本の直接的な下流パイプライン、間接的には数千チームが接続されていました。手作業では 10 人週ほどかかると見積もられた作業をどう自動化したか、という話です。

成功の鍵はふたつで、ひとつは Backstage の Codesearch や lineage プラグインで対象リポジトリを迅速に特定できたこと、もうひとつはコンテキストファイルの書き方にあります。最初は「人間向けの移行ガイドを流用」しようとして失敗しており、「Honk はコンテキストファイルに書かれていることしか見えない」という前提に立って、フィールドのマッピングをすべて表形式で明示的に書き出すことで、ようやく安定した性能が出ました。

一方で、この事例は楽観的なだけのストーリーではありません。Scio という柔軟性の高いフレームワークでは、チームごとにスタイルが違いすぎてプロンプトが肥大化し、Skill や MCP が使えない現行の制約下では断念せざるを得なかった。また BigQuery Runner と dbt のリポジトリにはビルド時の単体テストがほとんどなく、Honk が本来得意とする「自分で検証して直す」ループが機能しなかったという課題も正直に書かれています。

UX エンジニアリングの視点で読むと、ここには二重の示唆があります。ひとつは「AI が効く場所ほど、事前の標準化・テスト整備という地道な下ごしらえがものを言う」ということ。もうひとつは、「振る舞いの観察ポイント（Fleetshift の進捗 UI）を整備してあったからこそ、自動化の成果を追いかけられた」という点です。自動化の成否は、しばしば自動化以前の土台で決まる、というよく知られた教訓がそのまま表れています。

### [Designing Data-intensive Applications with Martin Kleppmann](https://newsletter.pragmaticengineer.com/p/designing-data-intensive-applications)

> **出典**: The Pragmatic Engineer | **公開日**: 2026-04-22 | **カテゴリ**: engineering

**3行まとめ**
- 名著 Designing Data-Intensive Applications（DDIA）の第 2 版リリースに合わせた Martin Kleppmann との対談
- クラウド時代にマルチリージョン・マルチクラウドは「ベストプラクティス」ではなく、リスクとコストのトレードオフであると言い切る
- LLM が大量生産するコードを人間がレビューしきれなくなる時代、形式検証（formal verification）が現実的な選択肢に戻ってくる可能性について語られている

**詳細解説**

Gergely Orosz のポッドキャスト Pragmatic Engineer に Martin Kleppmann が登場した回です。Rapportive 時代にデータベース性能で溺れかけた経験から、「後続のアプリケーション開発者が同じ苦しみを味わわないように」と書かれたのが DDIA であるという成り立ちが語られます。印象的なのは、この本の対象読者は「DB を作る人」ではなく、むしろアプリケーション開発者であるという位置づけの明示です。

本書第 2 版で縮小された話題のひとつが MapReduce で、「Spark や Flink が置き換えたので、学習用の参照としてのみ残す」という実務的な判断がとられています。逆に手厚く残るのは複製（replication）で、障害耐性はクラウド時代でもスケールの大小にかかわらず必要だからという理由。シャーディングは一台の性能向上とクラウドの進化で「専門家の領域」に引いた、という診断がわかりやすいです。

UX エンジニアリングの視点で注目したいのは、Kleppmann が「エンジニアの仕事はトレードオフを意思決定者に可視化することだ」と繰り返す点です。そこには技術的リスクだけでなく、評判リスクや社会的リスクも含まれる。AI と形式検証の話題も、LLM が書く膨大なコードを人間レビュアが処理しきれない状況で、「機械が書いたコードを別の機械が形式的に証明する」という分業の可能性として提示されています。

local-first ソフトウェアにおけるアクセスコントロールの難しさ、学術と産業の相互不信など、議論は広範に及びます。距離のある話題のように見えて、「自分たちが作っているプロダクトは、どこに対する責任を負っているのか」という自問への導線になっています。

### [Designing for Dependence: When UX Turns Tools into Traps](https://uxmag.com/articles/designing-for-dependence-when-ux-turns-tools-into-traps-2)

> **出典**: UX Magazine | **公開日**: 2026-04-21 | **カテゴリ**: ux-research

**3行まとめ**
- Nir Eyal の Hook Model に代表される習慣形成の手法が、意図と関係なく「依存」を作り出す設計になっていないかを問い直す論考
- ストリーク機能や「あなたが恋しい」通知のような仕掛けは、楽しさではなく損失回避の感情で利用者を縛りつけがちだと指摘
- エンゲージメントではなく「使わない自由」を計測する、emotional check-in や longitudinal study を取り入れる具体案を示す

**詳細解説**

UX Magazine の Ethical UX シリーズ第 8 回で、Tushar Deshmukh による依存設計（dependency design）への警鐘です。面白いのは、この記事が「ダークパターン」ではなく、ごく普通に歓迎されてきた「スムーズな体験」そのものに批判の矛先を向けている点。YouTube の autoplay、Amazon のワンクリック、TikTok の無限スクロールは、どれも「使いやすさ」の延長にありながら、利用者が立ち止まって判断する余地を奪う構造を持っている、という診断です。

例として挙げられるのが Calm や Headspace といったマインドフルネスアプリ。本来は落ち着きを届けるはずのプロダクトが、ストリーク機能によって「毎日やらないと罪悪感」を生み出してしまう。UX Collective の調査では、3 人に 1 人が瞑想アプリのストリークを途切らせたときに不安や罪悪感を抱えた、という数字も引かれます。「手段が目的を裏切っている」典型的な例です。

UX エンジニアリング視点で刺さるのは、「KPI の再設計」の提案です。エンゲージメントは満足度と等号ではなく、セッション長は心の明晰さを保証しない。「この機能がなかったら、1 週間どう過ごしますか？」と尋ねる emotional check-in や、縦断的な調査で罪悪感・解放感・不安のパターンを追うなど、実装しやすい調査手法が紹介されています。

「マニピュレーションとは、ユーザーの成功ではなくビジネス上の成功へ向けてナッジを最適化した瞬間に始まる」という定義は覚えておきたいところです。プロダクトマネージャや開発者と KPI を議論するとき、この線引きをひとつ持っておくと、意思決定のぶれが減ります。

### [False Earth: From WebGL Limits to a WebGPU-Driven World](https://tympanus.net/codrops/2026/04/21/false-earth-from-webgl-limits-to-a-webgpu-driven-world/)

> **出典**: Codrops | **公開日**: 2026-04-21 | **カテゴリ**: design

**3行まとめ**
- WebGL の制約を WebGPU と TSL（Three.js Shading Language）で超え、百万本の草が揺れるブラウザ上の世界を構築した制作記
- compute shader とストレージバッファで草・花・地形・キャラクターが同じデータを共有し、CPU 読み戻しなしで GPU 側だけでライフサイクルを回す構成
- indirect draw と LOD、frustum culling によって、ブラウザでも大規模シーンが現実的な描画コストに収まる設計を具体的コードつきで解説

**詳細解説**

Ming Jyun Hung による WebGPU 作品 False Earth の技術的な内部公開です。宇宙飛行士が偽の地球に降り立つという物語を下敷きに、無限に広がる草原、成長と枯死を繰り返す花、降り注ぐ宇宙光線の波紋を、すべてブラウザのひとつのタブで動かすまでの工夫が並びます。

中心にあるのは「GPU で完結させる」という思想です。草 1 本あたりのデータは 4 つの `vec4` に詰め込まれ、ストレージバッファで保持されます。法線は 2 成分だけ持って `sqrt(1 − x² − z²)` で残りを再構成する、といったビット単位の最適化が随所に入っていて、まさに WebGPU ならではの自由さを感じます。草の形状は 3 次ベジエで、風は制御点を動かして曲げ、根本では動かず先端で大きくしなる自然な揺れが実現されています。

CPU 側で描画数を決めず、GPU 自身に「何本描画するか」を決めさせる indirect draw の使い方も読みごたえがあります。compute pass で視錐台カリングと LOD 判定を行い、結果を可視インデックスのバッファに書き込んで、頂点シェーダでそれを参照する。カメラの視野が 75° であれば理論上 8 割の草は頂点シェーダにすら到達しない、という計算が気持ちよく効いています。

UX エンジニアリングの文脈では、シェーダコンパイル待ちで画面が固まらないための AsyncCompile の三段階パイプラインが参考になります。Compile → Queue → Upload の状態遷移を明示的に持ち、GPU ドライバを同時に叩きすぎないようにする。ブラウザでの体験を落とさないための、典型的な「待ち時間の設計」の話として読み替えられます。

### [Good taste the only real moat left](https://rajnandan.com/posts/taste-in-the-age-of-ai-and-llms/)

> **出典**: Sidebar | **公開日**: 2026-04-20 | **カテゴリ**: design

**3行まとめ**
- 生成 AI により「そこそこの出力」が安価になったいま、差がつくのは「何を却下できるか」という審美眼（taste）である、という論旨
- ただし taste だけで戦うと人間は「機械の選定者」に縮んでしまう危険があり、建てる・決める・責任を負う側として関わる必要がある
- AI の出力を並べて「なぜこれは駄目か」を言語化することで、自分の taste を鍛える具体的な練習法が提示されている

**詳細解説**

Rajnandan Kashyap による、AI 時代の taste 論。よくある「センスが大事」論と違い、taste を「不確実性の下での判別力」と定義し、感想ではなく診断の言葉として扱う点に価値があります。「これは既視感がある」ではなく、「これは規制上の制約を誤ってマーケティング的な表現に圧縮しており、顧客を混乱させる」と言える解像度です。

AI と LLM は統計的にもっともらしい出力を高速で大量に作れます。結果として「7 点の作品」が無限に湧き、真ん中が溢れかえる。このとき希少になるのは生成ではなく拒否で、何がジェネリックか、何がビジネス上の本質的なトレードオフを隠しているかを見抜く能力が、新しいボトルネックとして浮上します。

記事の後半は、taste だけでは足りないという点に踏み込みます。GAN の判別器のアナロジーが出てきて、生成器が十分に良くなると判別器は出荷には不要になる、と。人間がやるべきことは選別ではなく、方向性を選ぶこと、責任を引き受けること、訓練データにはまだ存在しない「本当に新しいもの」を守り育てることだ、と主張されます。

UX エンジニアリングの現場で特に使えるのは、「AI の出力に対して『fails because...』という一文を 10 本書いてみる」という練習です。文句を言語化する語彙が肥えることが、たぶんこの数年で一番効く差別化になります。個人的には、生成スピードが揃ってしまった世界での差分は「何を出さないか」に集約されるだろうと感じました。

### [If you thought the speed of writing code was your problem, you have a problem](https://andrewmurphy.io/blog/if-you-thought-the-speed-of-writing-code-was-your-problem-you-have-bigger-problems)

> **出典**: Sidebar | **公開日**: 2026-04-21 | **カテゴリ**: design

**3行まとめ**
- AI コーディングで「コードの出力が 40% 増えた」は、たいていの組織ではボトルネック以外を高速化しているだけ
- Goldratt の制約理論（Theory of Constraints）に従えば、ボトルネックでない工程を速くしたシステムは速くならず、むしろ壊れる
- 本当のボトルネックは「何を作るか」「レビュー待ち」「デプロイへの恐怖」「成果測定の欠如」「会議依存」のどこかにあることが多い

**詳細解説**

Andrew Murphy による、やや辛辣でとても実践的なエッセイです。冒頭のシーンは身に覚えのある人が多いでしょう。VP of Engineering が登壇し、「AI で生産性が 40% 上がる」と宣言する。誰もが肝心な問いを尋ねない。「どの方向に速くするのか」。そしてここから、コードを書く速度に最適化しただけではシステム全体の cycle time はむしろ悪化する、という論が静かに展開します。

筆者が列挙するボトルネックの候補は 5 つ。 PM が利用者と話せていない「何を作るか不明」、2 ヶ月動かない PR を生むレビュー・テスト・デプロイの待機列、「木曜デプロイ＝週末が潰れる」という心理からくる巨大バッチ化のスパイラル、リリース後の計測や振り返りがない空虚さ、そして「承認をもらうための会議待ち」。どれも AI コーディングでは 1 ミリも解決しません。

UX エンジニアリングの視点から読むと、自分たちの勝ち筋は「価値ストリームを描ける立場にある」ことだと再確認できます。「アイデアから利用者に届くまで」を自分で追跡し、どこで時間が溶けているかを可視化する作業は、ほとんどのプロダクト組織で空席になっています。この記事は、AI 活用そのものを否定せず、AI を「入れるべき場所」を慎重に選ぶための視点をくれます。

結語の「修正すべきはキーボードではなく、ボトルネックのほうだ」という一文は、個人にも組織にも刺さります。コードを速く書く競争に巻き込まれそうになったら、一度立ち止まってこの記事を開き直す価値があります。

### [Learnings from conducting ~1,000 interviews at Amazon](https://newsletter.pragmaticengineer.com/p/learnings-from-conducting-1000-interviews)

> **出典**: The Pragmatic Engineer | **公開日**: 2026-04-21 | **カテゴリ**: engineering

**3行まとめ**
- Amazon で 17 年、約 1,000 回のインタビュー（うち約 600 回が Bar Raiser）を経験した Steve Huynh による振り返り
- 技術選抜ラウンドを通った候補者が落ちる理由の多くは技術力ではなく、行動面接での語り方にある
- 準備の配分を見直し、80 時間の技術対策の 10 時間をストーリー準備に回すだけでも合否が大きく変わる

**詳細解説**

AI によって技術面接の形式が揺れている一方、行動面接はほとんど変わっていない、という観察から始まる、Gergely Orosz と Steve Huynh の共同記事です。本記事では Huynh の新刊 Technical Behavioral Interview から第 2 章の抜粋もあり、候補者と企業のマッチングがどのように「fit」と「level」という 2 軸で判定されるかが具体例つきで語られます。

本稿の主張は明快です。ファイナルラウンドは「この人と働きたいか」を確認する場であり、そこで決まる。技術はすでに通過条件としてクリアしている。なのに候補者は準備時間の 95% を技術に、5% を行動面接に使ってしまう。逆の配分に近いほうが合格率が上がる、という身も蓋もない指摘です。

level 評価の章は、自分の評価軸を言語化するのに使えます。scope（影響範囲）、contribution（自分の貢献）、impact（変化）、difficulty（難しさ）の 4 軸で Entry から Principal まで段階定義されており、「staff はどこから始まるか」「mid と senior の差は何か」を自分のストーリーで試す材料になります。転職直前でなくても、自己評価や部下のフィードバックに応用できます。

UX エンジニアリング職で働く人間にとっても、他人に語れる「自分の物語」を持っているかは、業務でも評価面談でも効いてきます。「準備したら不誠実」ではなく「準備してこそ本音が伝わる」という筆者の価値観は、引き出しに入れておきたい姿勢です。

> **出典**: Meta Engineering | **公開日**: 2026-04-21 | **カテゴリ**: engineering

**3行まとめ**
- Facebook Groups Search をキーワード検索からハイブリッド検索（lexical + 密ベクトル）に置き換えた事例

- Llama 3 を評価者に据えた自動オフライン評価で、人手ラベルがなくても意味的な適合度の改善を継続的に計測できる

**詳細解説**

「小さな個別ケーキに砂糖衣がかかったもの」を検索したとき、コミュニティが「cupcakes」と呼んでいれば、従来のキーワード検索では何もヒットしない。この明快な例からスタートする Meta の検索刷新レポートです。Groups のような利用者の語彙がゆれる場所では、字面一致だけでは届かない情報が山ほど眠っていた、という問題提起です。

おもしろいのは評価の仕組みです。密ベクトル検索は「なぜ関連性があるのか」を人間が感じ取りづらく、従来の二値ラベルでは伸びが測れません。そこで Llama 3 を判定者にしたオフライン評価を BVT（ビルド検証テスト）に組み込み、「完全一致」ではなく「同じドメイン・テーマで中程度に関連」というカテゴリを明示的に定義しました。

UX エンジニアリング文脈で読みごたえがあるのは、検索体験のフリクションを「発見・消費・検証」の 3 つに分解している点です。ただの検索改善ではなく、「そこにある共同体の知を取り出すための導線設計」に問題を読み替えているので、検索以外の UI 設計にも応用が効きます。

### [The UX Designer's Nightmare: When "Production-Ready" Becomes A Design Deliverable](https://smashingmagazine.com/2026/04/production-ready-becomes-design-deliverable-ux/)

> **出典**: Smashing Magazine | **公開日**: 2026-04-22 | **カテゴリ**: design

- 解決策はひとりフルスタックではなく、デザイナー・AI・エンジニアの 3 者ループでの役割分担

**詳細解説**

Carrie Webster による、現役シニアデザイナー目線の悲鳴混じりの論考です。グラフィックデザイン職が 3% 増に留まる一方で、UX・UI・プロダクトデザイン職は 16% 増と予測され、その多くが AI プロダクト開発の文脈で求められている。そして求人票が「production-ready prototyping」や「technical orchestration」を前提にし始めたことで、デザイナーがコードでも評価される時代に突入した、という観察から話が始まります。

UX エンジニアリングの立場から読むと、ここにあるのは「境界を消す」ことの危うさです。デザインとエンジニアリングの重なる中間地帯で仕事をすること自体は面白いのですが、AI があるからといって両方を深く持てるわけではない。記事が提案する「デザイナーは意図・アクセシビリティ・フロー、エンジニアはアーキテクチャ・性能のプロンプトを担う」という分担は、現実的な落とし所のひとつだと感じます。

### [Expansion artifacts](https://mattstromawn.com/writing/expansion-artifacts/)

> **出典**: Sidebar | **公開日**: 2026-04-21 | **カテゴリ**: design

**3行まとめ**
- 圧縮（compression）がブレイク世界の設計原理だったなら、LLM 時代の設計原理は「展開（expansion）」であるという主題
- JPEG や MP3 の圧縮アーティファクトと同じく、AI 生成物には「expansion artifact」と呼ぶべき痕跡が残る
- これらの痕跡が次世代モデルの学習データに混入し続けるとき、モデルの長尾（独特な声や珍しい言い回し）が静かに痩せていく

**詳細解説**

Matt Strom による、情報時代と AI 時代の設計原理の相違を「圧縮 vs. 展開」という軸で整理した論考です。2013 年に David Kriesel が発見した Xerox の JBIG2 バグ（スキャンした建物図面の「21.11m²」が「14.13m²」に置換されていた）を導入として、圧縮アーティファクトが単なるノイズではなく「文書の来歴を教えてくれるメタ情報」になっている点を丁寧に描きます。

そこから Ted Chiang の「ChatGPT は Web のぼやけた JPEG だ」という有名な比喩を引き継ぎつつ、筆者は「アーティファクトがあるのは圧縮ではなく、むしろ展開の側だ」と言い換えます。LLM の生成物は、訓練データという圧縮済みの塊から、プロンプトに向けて確率的に膨らませた結果であり、そこに「ヘッジを多用する言い回し」「必要のないエラーハンドリング」「6 本指」「連続性の破綻した動画」など、展開固有のアーティファクトが残る、というのが核心です。

特に危ういのは、これらの痕跡が新しいモデルの訓練データに入り込み、さらにぼやけた JPEG が生産されていくループ。CEO の音声メモ → Claude → Notion AI → Cursor → Devin → ChatGPT → Intercom の Fin エージェント、という実務の連鎖が例示されており、見覚えがある人は多いはずです。Gell-Mann Amnesia（他分野では警戒するのに、自分の関心領域でだけ AI 出力を信じる傾向）も言及されます。

UX エンジニアリングの現場で気になるのは、「紫のグラデーション」や「`bg-indigo-500`」のような視覚的な expansion artifact です。Tailwind の初期設定が AI 生成 UI の画面を一色に染めた、という Adam Wathan のツイートが引かれ、デザイナーとしては「どう痕跡を消すか」「どうあえて残すか」を意識する必要が出てきた、と感じさせます。
