### [AI SDK 7](https://vercel.com/blog/ai-sdk-7)

> **出典**: Vercel | **公開日**: 2026-06-25 | **カテゴリ**: frontend

**3行まとめ**
- AI SDK 7 は「エージェント開発・実行・統合・観測・テキスト以外」の5領域を軸にしたメジャーリリースで、TypeScriptでの本番エージェント基盤としての位置づけを鮮明にしました
- reasoning オプションの標準化、ツール文脈と実行時文脈の型付け、ファイル・スキルの provider 側アップロード、MCP Apps サポートなど「本番で困る細部」に手が入っています
- WorkflowAgent による耐障害性、ツール承認フロー、Codex/Claude Code/Deep Agents などのハーネス連携、音声・映像対応まで一気に射程が広がりました

**詳細解説**

AI SDK は週次1,600万ダウンロードのレイヤーで、Vercelの `eve` エージェントフレームワークもこの上に載っています。バージョン7の主眼は、チャット原始要素の域を超えた「エージェント運用基盤」への転換です。単なる機能列挙に見えて、実は本番で困っていた摩擦をひとつずつ潰してきた印象を受けます。

たとえば reasoning。フロンティアモデルの多くが推論深度を制御できるようになりましたが、プロバイダーごとにAPIが違います。SDK 7 では `reasoning: 'high'` のような単一オプションに正規化しつつ、必要ならプロバイダー固有オプションにフォールバックできます。細かい話に見えますが、複数モデルを切り替えて評価するチームにとってはコード分岐が減る意味が大きいです。ツール文脈も型付きスキーマで定義でき、APIキーのような秘匿情報を「そのツールだけ」に閉じ込められるようになっています。3rd party ツールが不要な文脈を覗けない設計は、エージェントの権限最小化を実装レベルで保証する仕組みです。

もうひとつの目玉は WorkflowAgent です。長時間実行や人間の承認待ちで生じるプロセス再起動・デプロイ跨ぎに耐える、resumable なエージェント実行を提供します。ツール承認は user-approval のシンプル指定に加え、HMAC 署名によるリプレイ防止まで用意されており、監査可能性まで含めて設計されています。UXエンジニアリングの観点だと、こうした承認・耐障害性は「エージェントを本番導入するときにUI側で何を見せるべきか」の議論と直結します。ユーザーが承認を差し戻せる粒度、途中経過を可視化する範囲、失敗時の再開ボタンの設計、いずれもSDK側の抽象がそのまま画面のアフォーダンスに現れる領域です。

ハーネス連携は特筆に値します。Codex、Claude Code、Deep Agents、OpenCode、Pi といった既存の実装済みエージェントランタイムを同一インターフェースで扱えるので、コードを書き換えずにランタイムを切り替えられます。実運用では「特定タスクだけ Claude Code に流す」といった細かい使い分けが可能になります。音声・映像への拡張、TUI パッケージ同梱を含め、SDK 6 から乗り換える価値は明確です。移行は `npx @ai-sdk/codemod v7` で自動化されており、破壊的変更は思ったより穏やかです。

### [Privacy-Aware Infrastructure in the AI-Native Era: An Asset Classification Case Study](https://engineering.fb.com/2026/06/25/security/privacy-aware-infrastructure-in-the-ai-native-era-an-asset-classification-case-study/)

> **出典**: Meta Engineering | **公開日**: 2026-06-25 | **カテゴリ**: engineering

**3行まとめ**
- Meta のプライバシー基盤における資産分類（データが人に関するものかシステム由来かの判別）を、決定論ルール優先＋LLMをフォールバックにする「決定漏斗」で運用している事例です
- プロンプト最適化より先に「証拠ブリーフ」を組み立てる文脈設計が精度に寄与し、マスクした信号がルールに逆流しない不変条件を厳守しています
- 学習ループと評価ループを分離し、多視点ジャッジで自己採点を防ぎつつ、安定したパターンは決定論ルールに蒸留して LLM 呼び出しを段階的に減らしています

**詳細解説**

`age` というフィールド名が、人の年齢を指すこともあればキャッシュTTLの数値でもあるという例から始まる、実務にひどく共感できる話です。プライバシー制御は保持・アクセス・目的・共有・匿名化の各ポリシーを執行しますが、そのすべてが「このデータは何なのか」の理解を前提にしています。AI ネイティブな製品はデータのモダリティが増え、派生特徴量や埋め込みが増えるので、人手レビューだけでは分類が追いつきません。

Meta のアプローチは3原則にまとまっています。ひとつめは「文脈がプロンプトを超える」。分類失敗の多くはプロンプトではなく証拠不足に由来していて、支持信号・反証信号・出所・マスク済みフィールドを整理した evidence brief に切り替えたら精度が明確に上がった、というくだりは非常に示唆的です。プロンプトエンジニアリングの前に、モデルに何を渡すかの設計をやり尽くすべきという主張は、コーディングエージェントのスキル設計にも同じことがいえます。ふたつめは評価と最適化の分離。分類器が自己の予測を教師データに戻すと、ドリフトを進歩と誤認するので、レビュー済み参照ラベルを独立に維持する必要があります。みっつめが「安定したふるまいは決定論ルールに蒸留する」。約85%のトラフィックはミリ秒台の決定論ルールで処理し、残り15%だけをLLMに回す運用は、コストと監査可能性の両面で理にかなっています。

システム不変条件として印象的なのが「マスクしたフィールドは学習済みルール蒸留からもブロックする」規約です。マスクは単なるプロンプト衛生ではなく、システム全体で保つ invariant として扱われています。ある本番デプロイでは、この扱いにバグがあってルール適用が静かにフォールバックし、カバレッジが伸びない現象があったそうです。「ルールが増えているのに LLM 呼び出しが減らない」という観測できる兆候から拾えたのは、監査可能性を設計に組み込んでいた成果でしょう。

UXエンジニアリング目線で読むと、これは「AIを使った判断を製品に載せる際のパターン集」として応用が効きます。ユーザーが目にする分類結果には、必ず decision trace とバージョン情報が付いていて、再現可能で説明可能な状態を保つ、という発想は、AI 機能をUIに載せる際の「なぜこう判定したか」表示の設計指針としても参考になります。

### [Teaching agents product design at Vercel](https://vercel.com/blog/teaching-agents-product-design-at-vercel)

> **出典**: Vercel | **公開日**: 2026-06-25 | **カテゴリ**: frontend

**3行まとめ**
- Vercel は受け入れた製品判断を「コードと同じ扱い」でリポジトリに置き、`product-design` スキルとしてエージェントに読み込ませています
- スキル・リンター・レビューループの3層構造で、判断が要る部分はスキル、決定論的に検査できる部分はリンター、標準を作る部分は人間、と役割を明確に分けています
- 「clear」「polished」のような形容詞ではなく「Destructive CTA は Verb + Noun」のような観測可能な決定に落とすこと、そして各ルールに安定ID・出典・例外を持たせることが要点です

**詳細解説**

コーディングエージェントは動くUIを速く出せるけれど、「なぜそのパターンが標準になったのか」を理解できません。その判断はデザインレビュー・PRコメント・Slack・会議の中に散っています。Vercel は「エージェントネイティブなチーム」を自認し、その判断を明示的にリポジトリに書き込むことで、あらゆるエージェントから参照可能にしました。

構造がおもしろいです。`.agents/skills/product-design/` の下に SKILL.md がルーティングを担い、`references/` は product-judgment.md、interface-quality.md、copy.md、surfaces.md といった観点ごとに分割され、`exemplars/` に「良い判断・悪い判断の実例」が置かれています。SKILL.md はまず request モードを解決します。shape（設計）・implement（実装）・review（監査）・copy（文言）・harden（仕上げ）のどれで来たのかを識別し、監査がいきなり編集に化けたり、文言修正が再デザインに膨らんだりしないよう境界を引く、という設計は非常に実務的です。

各ルールには安定IDと出典が紐づいています。たとえば `rule/destructive-names-action` は「破壊的なCTAは Verb + Noun に従い、Confirm / OK / 動詞単体は使わない」といった具合です。判断がぶれない粒度まで書き下してあるのが特徴で、Vercel Agent が変更提案を出すときは、Vercel Sandbox でビルド・テスト・リンターを走らせてから投稿します。

リンター側の割り切りも参考になります。「2〜3個の静的オプションを持つ Select はラジオを勧める」「モーダルのネストを止める」「アイコンボタンにアクセシブルネームを要求」など、コードだけで判定できるものはリンター、そうでないものはスキル、という切り分けです。ここに載っている決定木は他チームでもそのまま使えます。UXエンジニアリングの観点だと、これは「デザインシステムのドキュメントをエージェント向けに書き直す」というより、「同じ判断をコード検査・エージェント読解・人手レビューの3層で反復可能にする」設計に近く、判断のスケーラビリティに真正面から取り組んでいる好例です。

### [The layers of AI experience](https://emilycampbell.co/writing/layers-of-ai-experience)

> **出典**: Sidebar | **公開日**: 2026-06-25 | **カテゴリ**: design

**3行まとめ**
- Jesse James Garrett の Elements of UX と Jamie Mill の Elements of Product Design を継ぐ形で、AI体験を6層（UI・Context・Harness・Model・Governance・Emergence）でモデル化した論考です
- UIは「指示」から「監督」へ役割が変化し、Context はセッションを越えて育つエンジンとして機能する、という段階遷移が丁寧に描かれています
- デザイナーが「フルスタック」になる必要はないが、各層を語れる多言語性が求められる、という結論が明確に提示されています

**詳細解説**

Elements of UX（2000）は、Web を可視化できる5層で捉える古典でした。Emily Campbell の議論は、それを生成AI時代に拡張する試みです。従来モデルは決定論的な世界を前提にしていましたが、AI 製品は確率的で、モデルの学習データやツール、外部文脈、そして emergence（想定外挙動）まで巻き込みます。デザインは「あらゆる状態を仕様化する」から「介入点を設計する」方向に移る、という指摘は説得力があります。

各層の説明も丁寧です。UI層では、初期はユーザーの direction が中心でも、時間とともに oversight（監督）に役割が移る、という「progressive autonomy」の観点が印象的です。オンボーディングも「ユーザーが製品を学ぶ」から「システムがユーザーを学ぶ」へ反転します。Context層は徐々に開示されるゲームのマップに例えられていて、context rot を避けるために「何を保持し、何を捨てるか」の制御が要る、と釘を刺しています。

Harness層の記述は、UXエンジニアリングにとってとくに核心的です。Connectors・Tools・Skills・Agents の4要素で構成される「モデルの働くための操作面」を、単なる DevX ではなく UX の一部として捉え直す視点が示されています。connectors のパーミッションを可視化するUI、tool の自律度を状況に合わせて調整するアフォーダンス、skills の有効・無効をユーザーが理解できる粒度で提示する仕組みなど、実装課題としてもデザイン課題としても濃密です。

Model 層・Governance 層・Emergence 層はさらにサブサーフェスに踏み込みます。特に emergence は「予期しなかった挙動」に対して観測可能性・解釈可能性・出所（provenance）で対応せよ、というスタンスです。デザイナーが機械学習エンジニアになる必要はないが、各層の下流影響を語れる語彙は要る、という結論は、実務で「デザインエンジニア」を名乗る人にも共通の宿題を提示しています。

### [退職者を在籍者で割るだけ……じゃない。「離職率」の奥深さとチームの意思決定](https://tech.smarthr.jp/entry/2026/06/26/142109)

> **出典**: SmartHR Tech Blog | **公開日**: 2026-06-26 | **カテゴリ**: design

**3行まとめ**
- HRアナリティクスのグラフ分析機能で「離職率」を扱うにあたり、統一定義のない指標をチームで定義していったプロセスの詳細な事例です
- エンジニアが「仕様待ち」ではなく「何を作るか」に踏み込み、方式ごとのトレードオフを整理して PdM・デザイナーと議論した動き方が中心テーマになっています
- 意思決定を支えるための「調べる時間の確保」「Notion による一元管理とカスタムエージェント」「相談しやすい関係性」の3点が具体的に紹介されています

**詳細解説**

離職率は「退職者を在籍者で割るだけ」ではありません。分母を期首の在籍者だけにするか、期中入社者も含めるか、期間を相対日付にするか暦月にするか、休職者を含めるか——分母と期間の選び方だけで、同じデータでも数値が2ポイント以上ブレます。厚労省の雇用動向調査が採る式をそのまま持ち込むと、中途採用が活発な組織では実態を捉えづらくなる、という指摘は指標設計の難しさをよく表しています。

HRアナリティクスチームは「在籍＋入社ベース」「暦月方式」を採用しました。おもしろいのは決めた理由です。分母は対象期間中にその組織に属したすべての人を対象にしたいこと、期間は同じSmartHR内の「人事労務レポート」との整合性を優先したこと。プロダクト間で数値が食い違うとお客さんが混乱するから、という判断は、単一プロダクトだけを見ていたら出てこない視点です。しかも「なぜそう決めたか」を却下案の理由まで含めてADRに残しているところに、意思決定の再現可能性への意識が表れています。

UXエンジニアリング的に読むと、これは「実装解像度を持ったエンジニアが指標定義に踏み込むと、後工程の手戻りを入り口で潰せる」という話です。仕様が降ってくるのを待つのではなく、選択肢と技術トレードオフをセットで整理する動き方は、AIによって「どう作るか」のコストが下がっている今こそ相対的に価値が上がるはずです。

チームの工夫として紹介されている「調べる時間をタスクとして積む」「PRD・仕様書・ADRを読み込ませたカスタムエージェントをNotionに置いて質問できるようにする」「デイリースクラムに相談時間を確保する」は、AI前提の意思決定基盤としても示唆に富んでいます。ドキュメントは置いておくだけでは読まれない、という現実に、エージェントを窓口にすることで応じる発想はほかのチームにも展開できそうです。

### [Less is more, more or less](https://jakub.kr/writing/less-is-more)

> **出典**: Sidebar | **公開日**: 2026-06-25 | **カテゴリ**: design

**3行まとめ**
- AIで「量」は誰でも出せるようになったが、良いものを作るには理解・判断・テイストが不可欠、という主張です
- コンテキストメニューを1日200回開くとアニメーション時間だけで年6時間になる、という具体例が「意図なくアニメを足すこと」への警鐘として提示されています
- Interfere では `/codebase-standards` スキルと `/interfere-review` コマンドで判断を仕組み化し、エージェントにもレビューを反復させています

**詳細解説**

AIで「追加は簡単、削除は難しい」時代になったからこそ、削るために深い理解と判断が必要になる、という論旨です。Antoine de Saint-Exupéry と Jony Ive の引用を並べ、simplicity は「clutter がない状態」ではなく「複雑さに秩序をもたらすほど深く理解している状態」だ、と再定義しています。読み返して手が止まる文章です。

具体例として、macOS の右クリックメニュー相当のコンテキストメニューが取り上げられています。開閉両方をアニメーションするか、閉じる時だけアニメーションするか。1日200回、300msのアニメーションが挟まると年6時間以上を「アニメが終わるのを待つ時間」に費やす計算になります。「頻繁に使うUIは動かさない」を、コスト計算で言い換えている点が地に足ついています。判断は「使い方を理解して初めて自明になる」——これはエージェントが持ちにくい能力です。

エンジニアリング面での主張も刺さります。「PRの行数ではなく、目的をどれだけ少ないコードで達成したかで評価する」というInterfereのポリシー、「コードを書く能力より、良いコードと悪いコードを見分けて批判的に考える能力の希少性が上がっている」という指摘。UXエンジニアリング視点だと、これは「判断を仕組み化したスキル」の話でもあります。Interfere が用意している `/codebase-standards` と `/interfere-review` は、Vercel の product-design スキルと同じ発想で、判断をチーム内外で反復可能にする装置です。

締めくくりの「AI時代でもっとも重要なスキルは、何を作らないかを知ることかもしれない」は、少し目を引く言い回しですが、記事全体の流れとして納得できます。エージェントとの付き合い方リスト（思考を外注しない、書かれた内容を疑う、追加が最終成果を良くするか自問する）は素朴ですが実践的です。

### [セールスのオンボーディング期間を3分の1に短縮した内製の「AIロープレ」](https://tech.layerx.co.jp/entry/2026/06/25/162902)

> **出典**: LayerX エンジニアブログ | **公開日**: 2026-06-25 | **カテゴリ**: engineering

**3行まとめ**
- バクラク事業部でセールスのランチングチェック（実技テスト）前の練習を、内製の音声AIロープレで置き換え、対人ロープレを10回以上から約3回まで削減できた事例です
- 画面共有付きのデモを含む「実戦さながらの打席」を再現するため、既製SaaSではなく SalesPortal 上への統合を選択しています
- STT・LLM・TTS の組み合わせで自然な音声対話を実現しつつ、フィードバックから学習コンテンツへの動線までひとつのエコシステムに閉じ込めているのが特徴です

**詳細解説**

バクラクの13プロダクトすべてをキャッチアップする必要があるセールスのオンボーディングは、既存社員の負担・「先輩待ち」・新メンバーの心理的ハードルという3つの課題を抱えていました。ここに内製AIロープレを差し込んで、量をこなすフェーズを人間から剥がすというアプローチです。

技術構成はシンプルで、Next.js の裏で STT（音声認識）→ LLM（会話生成）→ TTS（音声合成）→ 商談終了後に別のLLMで評価、という直列パイプラインです。音声モデルは Azure ベースで現在も検討を続けているとのこと。UXエンジニアリング的に注目したいのは、「画面共有をしてデモを見せる」というバクラクの商談で最重要のプロセスを、そのまま体験に組み込んでいる点です。使い慣れたオンライン会議ツールと同じUIで画面共有ボタンを押し、自分のPCでバクラクのデモ環境を動かしながら音声でAIに話しかけられる、という設計は、実戦に極端に寄せた練習環境を再現しています。

「バクラクでよくある商談シナリオ」を自動生成する機能も光ります。プロダクト数が多いと商談シチュエーションの組み合わせは無限になり、手動で維持するのは破綻します。この課題を運用コスト側から潰しているのが賢いところで、既製SaaSでは自社ユースケースに合わせた手作業がボトルネックになる、という現実的な指摘があります。

- Bluesky スレッド経由で Dan Abramov が Next.js チームに part-time でジョインすることが発表されています
- Vite 8.1 の bundled dev mode、Rsbuild 2.1 の Rust 版 React Compiler、Linear の styled-components → StyleX 移行など、周辺エコシステムでも大きな動きが並んでいます

**詳細解説**

Next.js 16.3 の instant navigations は、Server Components を選んだときに感じる「遷移が重い」という積年の苦情に直接応える機能です。既存のプロジェクトが乗り換えやすいよう、Vercel は adoption skill（`next-cache-components-adoption`）まで用意しています。エージェントに移行を任せる前提でリリースを組み立てているのは、AI SDK 7 の migration skill と同じ発想で、Vercel のリリース設計に一貫性を感じます。

そしてなにより Dan Abramov が Next.js チームに part-time で加わることが Bluesky で明かされました。Dan は近年 React コアから距離を取って書き物や外側の思索に軸を移していましたが、それが Next.js の中に還ってくる意味は大きいです。同じニュースレターに Dan の「AT Protocol の中には instance が存在しない」という Bluesky 論も出てきていて、React コミュニティと atproto コミュニティの重なりが増えてきている雰囲気があります。

周辺ニュースも密度が高いです。Vite 8.1 の bundled dev mode は、大規模プロジェクト（1万コンポーネントで15倍という測定値）を意識した設計です。一方で Rolldown / Vite は初期の Rust 版 React Compiler 統合を「バイナリサイズが17%増えたので」外した、というのは、フロントエンドツールチェーンが Rust 化していく途中の生々しい現場感です。Linear の styled-components → StyleX 移行は、エージェントが10万行規模のcodemodを書いて自動化し、それでも人手で仕上げる部分が残った、という事例で、AIコード改修の到達点と限界が具体的に見えます。Takumi 2.0（Rust製 JSX→画像レンダラ）、TanStack Table v9 のメモリ削減、Waku の Slices など、記事末尾までカタログ的に濃い号です。
