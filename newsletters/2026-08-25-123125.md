### [Your alt text passes automated checks. That doesn't mean it's any good.](https://github.blog/engineering/user-experience/your-alt-text-passes-automated-checks-that-doesnt-mean-its-any-good/)

> **出典**: GitHub Engineering | **公開日**: 2026-08-24 | **カテゴリ**: engineering

**3行まとめ**
- WebAIM Million 2026 では、alt が欠けている画像が16.2%、内容を説明しない alt がさらに10.8%という数字が出ています
- GitHub がアクセシビリティスキャナ向けの alt text プラグインを、決定的な5つのルールとオプトインのモデル呼び出し1つに分けて作った記録です
- 「証明できること」と「疑えるだけのこと」を分けて既定値を変える、という自動チェック設計の指針が読みどころになっています

**詳細解説**

出発点は、既存のチェッカーがほとんど「アクセシブルな名前が存在するか」だけを見ている、という指摘です。しかもそれは手抜きではなく設計判断で、品質を見るルールは誤検知を出した時点でチームに切られてしまう、という理由があります。だから `alt="IMG_2847.png"` は通ってしまうし、5つの星アイコンに同じ `alt="3/5 stars"` が付いていても通ります。ここを埋めるために作られたのが、GitHub Accessibility Scanner 向けの [alt text プラグイン](https://github.com/github/accessibility-scanner-alt-text-plugin)です。

決定的に判定できるルールは5つに絞られました。属性そのものがない（空ではない）か空白だけ、ファイル名になっている、`TODO` のような置き換え忘れのプレースホルダ、`image` や `logo` のように中身ではなく媒体を指す一語、隣り合う画像で同じ alt が繰り返される。どれも「文字列についての主張」で、そこが線引きになっています。判定対象を集めるところでは `querySelectorAll('img')` ではなく Playwright のロール指定ロケータを使い、アクセシビリティツリーに載らないものを落とします。`alt=""` が外れるのが効いていて、空の alt は「これは装飾です」という作者の明示なので、そこを指摘すると促したい振る舞いを罰することになるからです。

厳しさの調整も割り切っています。曖昧な alt のルールは正規化したあと、単語の閉じたリストと完全一致したときだけ発火します。`alt="image"` は引っかかり、`alt="image of the login screen with the SSO button highlighted"` は引っかかりません。見逃しは増えますが、切られないチェッカーのほうが価値がある、という判断です。反復の検出でつまずいた話もおもしろく、最初は DOM の順に見て同じ alt の連続を指摘していたところ、フッターとヘッダーの GitHub ロゴのように、抽出リストでは隣なのに画面上は離れているものを拾ってしまいました。そこでバウンディングボックスの隙間が箱の大きさに比べて小さいときだけ連続とみなす形に変えています。乗数は仕様から導いた数字ではなく実際のページで調整する値、箱が測れないときは連続を切らずに素通りさせる（見逃しは見えないが誤検知は見える）という注記が添えられます。

モデルを入れた部分の失敗は、画像の読み間違いではなく「モデルが意見を持つこと」でした。良い alt を渡しても別案を出してくる。「もっと良くできるか」という問いに言語モデルは常に yes と答えるので、全画像が指摘になって信号が消えます。効いた対策が3つ挙がっていて、指示ではなく4段階の決定手続きにして最初に当たった段階で止める、細かい指摘の禁止を明文化する（作者の枠組みを信じる、`Image of…` のような冗長な接頭辞と `Photograph of…` のような意味のある接頭辞を分ける、周辺の文章がすでに画像を説明しているなら短い alt を正しいと扱う）、構造化出力のフィールド順を固定して `reasoning` を `verdict` より先に生成させる、というものです。プライバシーとコストの扱いも具体的で、既定オフ、URL のクエリとフラグメントの除去、`src` と `srcset` を `(omitted)` に置換。そのうえで「指摘には実際のページ URL と元の HTML が乗るので、除去で狭まるのはモデルとログに届く範囲だけ」と、読み過ぎを止める注意まで書かれています。

UXエンジニアリングの視点でいちばん持ち帰れるのは、締めの一文です。DOM が何と言っているかではなく、利用者が何を経験するかを問う。反復をレイアウトで判定したのはまさにそれで、残っている限界（リンクの中にあることは記録するが、リンクの唯一の内容かは見ていない。属性を読むので `aria-label` で直しても指摘が止まらない）はどれも同じ形をしています。決定的なチェックはゲートに置き、疑いにとどまるものは提案として人に回す。この仕分けはビジュアルリグレッションやパフォーマンス予算にもそのまま持ち込めます。

### [Keeping type consistent in changing conditions](https://elliotjaystocks.com/blog/keeping-type-consistent)

> **出典**: Sidebar | **公開日**: 2026-08-24 | **カテゴリ**: design

**3行まとめ**
- weight が差をつけるための軸なのに対して、grade は揃えるための軸だという整理から始まります
- 紙のインクの滲みと、画面の halation（明るい文字が暗い背景で膨らんで見える現象）を、字送りや行分割を変えずに補正できます
- 変数フォントの `GRAD` 軸を持つ書体が増えていて、SF Pro、Roboto Flex、Roboto Serif などが挙げられています

**詳細解説**

Elliot Jay Stocks さんが Config のトークをもとに書いた一本で、Adobe Design のブログに載ったものの再掲です。grade は一見 weight に似ていますが、目的が逆だと言います。weight は強調やコントラストをつけて「区別する」ためのもの、grade は本来同じに見えるべき文字が違って見えてしまうときに「揃える」ためのもの。しかもスペーシングや行分割、レイアウトを変えずに濃さだけ動かせます。この問題に一度気づくと、あちこちで見えるようになるという書き方が的を射ています。

由来は印刷でした。新聞のマット紙は同じ書体・同じウェイトでもインクが滲んで柔らかく見えるので、光沢紙に刷った同じ文字とは印象が変わります。記事では Bennet の例が引かれていて、軽いはずの Bennet Text One を吸い込みやすい紙に刷ると、光沢紙の Bennet Text Four と同じ濃さになる、という写真が並びます。Stocks さん自身が grade に出会ったのは、2014年から2019年まで運営していた雑誌 Lagom の制作中だったそうです。白抜きの文字は紙が見えている部分なので、インクが文字の内側に滲んでいく。それを黒文字のページと揃えるために、Tabac というスーパーファミリーの異なる grade を使い分けました。

画面でも同じことが起きます。暗い背景に明るい文字を置くと膨らんで見える現象は halation と呼ばれ、夜間の照明付き道路標識の可読性を落としたり、ライトモードとダークモードを切り替えたときに現れたりします。ここで grade の性質が効いてきて、uniwidth や multiplexed の書体（ウェイトが変わっても字幅が変わらないもの）と同じように、grade を切り替えても文字が動きません。InDesign での一括置換で行が崩れないし、画面では UI の要素が箱から押し出されない。変数フォントの `GRAD` 軸を使えば、定義済みの段階に縛られず連続的に調整できます。記事に添えられた例では、暗いボックスアウトの中の文字を `GRAD` で -92 まで下げて、本文と釣り合わせています。

UXエンジニアリングの立場で読むと、これはダークモード実装の実務的な答えのひとつです。よくやる回避策は、ダークモードで `font-weight` を一段下げることですが、多くの書体ではそれで字幅が変わり、行分割やボタン幅、タブの並びまで動きます。`GRAD` なら幅が変わらないので、`prefers-color-scheme` に応じて `font-variation-settings` の `GRAD` だけを CSS カスタムプロパティで差し替える、という形に収まります。ただし `GRAD` 軸を持つ書体はまだ限られるので、採用の段階で軸の有無を確認しておく必要があります。手元の書体に軸がないなら、色のコントラストを少し落として調整するほうが現実的でしょう。

### [How complex systems fail](https://how.complexsystems.fail/)

> **出典**: Sidebar | **公開日**: 2026-08-24 | **カテゴリ**: design

**3行まとめ**
- Richard Cook による古典的な18項目の短い論考が、読みやすい形で公開されているものです
- 破局には複数の失敗の重なりが必要で、単一障害点だけでは足りない、という前提から議論が組まれます
- 「root cause の特定は技術的に間違っている」「安全はシステムの創発的性質である」といった主張が並びます

**詳細解説**

Sidebar 経由で回ってきましたが、内容は1998年から知られている Cook の論考です。医療の事故研究から出てきたもので、いま読んでも古びていません。前半の議論の土台になるのが3番目の項目で、破局には複数の失敗が必要であり、単一の失敗では足りないと述べます。防御層はふだんうまく機能していて、失敗の芽の多くは設計された安全機構か、現場の実務者によって止められている。だから表に出る事故の数より、失敗の機会のほうが圧倒的に多いわけです。

続く4〜6番の流れが、実務にいちばん刺さります。複雑なシステムは複数の欠陥を抱えたままでしか動かせず、つまり壊れた状態で走っている。冗長性があり、人がなんとか動かしているから機能している。事故後のレビューはほぼ必ず、破局に近づいた過去の出来事の履歴を見つけますが、「事前に気づけたはずだ」という議論はシステムの動きを素朴に捉えすぎだと切り捨てます。組織も人も技術も、絶えず壊れて置き換わりながら動いているからです。

7番と8番はポストモーテムの作法に直接関わります。表に出る失敗が複数の要因を必要とするなら、孤立した「原因」は取り出せません。それらが結びついてはじめて十分になるので、root cause の特定という発想は失敗の性質を技術的に理解したものではなく、特定の誰かや何かを責めたいという社会的・文化的な要求のあらわれだと述べます。さらに hindsight bias、つまり結果を知ったあとでは当時の当事者にもそれが目立って見えたはずだと感じてしまう偏りが、人の行動の評価をいちばん歪めるとも指摘されます。実務者の行動はすべて不確実性のもとでの賭けであり、事故後は悪い賭けだったと見えるけれど、うまくいった結果も同じく賭けの結果だという対称性は、あまり評価されません。

後半は、では何が安全を作っているのかという話に移ります。安全は人やデバイスや部署に宿るものではなく、システムの創発的性質である。買うことも作り置きすることもできない。無事故の運転は、許容範囲の内側にシステムを留めておくための、人の日々の適応の結果として生まれている。そして最後の項目が「無事故の運転には失敗の経験が必要」で、境界がどこにあるかを分かっている人がいるシステムのほうが頑健になる、と締めます。フロントエンドの現場に引き寄せると、既知の不具合を抱えたままリリースしている状態はまさに degraded mode ですし、事故後に増やした手続きが結合と複雑さを増やして潜在的な失敗を増やす、という15番の指摘はインシデント対応の振り返りで思い出しておきたいところです。カナリアリリースやフィーチャーフラグは、この論考の言い方だと「境界の手前で気づくための道具」として整理できます。

### [Perfection is not over-engineering](https://var0.xyz/posts/perfection-is-not-over-engineering.html)

> **出典**: Sidebar | **公開日**: 2026-08-24 | **カテゴリ**: design

**3行まとめ**
- 「完璧を目指さない」という言い方が over-engineering への警戒と混ざってしまった、という問題提起です
- over-engineering の定義を「間違った問題を解いている」だけに絞り、丁寧さや品質の高さとは別物だと切り分けます
- 制約を全部そろえて要件を締めていくと解が1つに収束し、それが唯一だからこそ完璧なのだと述べます

**詳細解説**

「完璧な解は作らない」という言い方を、あたかも perfect が汚い言葉であるかのように使う場面をよく見る、という書き出しです。警戒の理由は分かる、と一度受け止めたうえで、業界がこの2つを静かに混同してきたと指摘します。over-engineering は間違った問題を解いていることであって、それが定義のすべて。気にしすぎることでも、良く作りすぎることでもない。たいてい善意から始まり、ほぼいつも付随的な複雑さの山が積み上がっていく、という補足が現実的です。

完璧な解は存在する、という主張には大きな条件がつきます。要件が非常にはっきりしていて、制約が全部テーブルに載っていること。そこまで締めると選択肢が1つになり、その1つは「唯一だから」完璧なのだと。例として、新規プロジェクトで言語もツールもホスティングも自由に選べる状況が挙げられます。serverless を選び、コンパイル工程がなくファイルを上げるだけで済む Python を選ぶ。別の人には間違った選択で、Python を知らないか、性能を優先する制約があるかもしれない。同じ問題空間でも制約が違えば「完璧」の中身が変わります。Django か Flask かも同じ構造で、どちらでも似た結果に届くけれど哲学は違う。要件を明確にすれば解が従ってくる、という順序です。

もう一段おもしろいのが「システムはプロダクトである」という節です。ライブラリ、API、社内ツールを、あたかもプロダクトの外側にある純粋に技術的なものとして扱いたくなるけれど、そこには利用者がいて、ニーズがある。必要なのはサービスかもしれないし、HTTP 呼び出しよりライブラリのほうが合っているかもしれない。API を渡すのではなくパッケージを渡す、という選択が見えてくるのは、システムをプロダクトとして扱い、要件を正直に定義したあとだと言います。見分け方も具体的で、「なぜこう作られているのか」と問いはじめて答えが持たないときが、いちばんはっきりした兆候だと。

例に出るのは、3人のチームが5つのマイクロサービスを維持し、サービス間でデータを共有している構成です。データベースが強制してくれていた外部キーは緩い文字列 ID になり、整合性の保証が消える。片方のサービスがレコードを消しても、もう片方は気づかず、参照が浮いたまま後で痛い形で分かる。得たものは独立したデプロイですが、それは本当に抱えていた問題だったのか。3人で1つのドメインなのに、スケールと所有権の問題を解いて、分散した不整合と運用コストを払った。これが署名だ、と言います。診断は要件収集の失敗であって、敵は完璧ではなく曖昧な要件だった、と締めます。フロントエンドでも同型の話は多く、状態管理ライブラリの導入、デザインシステムのコンポーネント抽象化、マイクロフロントエンドの分割は、どれも「誰のどの制約に対して1つに絞れているか」で点検できます。逆に、要件が締まっていない段階で「完璧を目指さない」を理由に手を抜くと、間違った問題を解く速度だけが上がる、という読み方もできそうです。

### [不具合情報の集約基盤を整え、品質改善に活かすまで](https://tech.smarthr.jp/entry/2026/08/24/133642)

> **出典**: SmartHR Tech Blog | **公開日**: 2026-08-24 | **カテゴリ**: design

**3行まとめ**
- JIRA や GitHub から API 経由で不具合情報を取り、Notion に定期的に集約する基盤を整えた話です
- 集めた情報は PR、不具合チケット、インシデント、自動テストの4種で、設定ファイルへの追記だけでデータソースを足せます
- ファイル単位で Risk / Fragility / TestWeakness / Impact / Unexpected の5つのスコアを週次で算出し、バックテストとフォワードテストで精度を検証しています

**詳細解説**

SmartHR の品質保証本部 Director の tarappo さんによる、品質にまつわる定量データの基盤の紹介です。動機の書き方が素直で、組織が小さいうちは周りで起きていることが見えやすく、大きな問題になる前に手を打てる。しかし会社とプロダクトがスケールすると「肌感」という定性データだけでは限界が出てくる。そこで判断材料としての定量データを集めることにした、という流れです。開発で使っているサービスから API で取得し、Notion に定期的に集約する構成で、Notion の sync 機能を使わないのは同期後のデータを加工することがあるから、という注記が付きます。

整備の進め方に工夫があります。データソースは設定ファイルへの追記で足せるようになっていて、AI 活用で基盤自体のカスタマイズもしやすくしてあるため、設定追加はメンバーが自分でやっている。データを集めるためのサポートツールも併走していて、PR の description に不具合チケットを貼ると自動でラベルが付く仕組みが例に挙げられます。これは同期しやすくなるだけでなく、視覚的にも分かりやすくなる、という副次的な効果が書かれています。sync の結果は通知され、2026年前半に QA エンジニアを軸に適用範囲を一気に広げて、多くのプロダクトで収集できる状態になったそうです。残る課題も正直に並べられていて、開発フェーズの情報が中心でライフサイクル全体を覆えていないこと、粒度に差があって具体的な課題までつかみにくいケースがあること、データの充足率に伸びしろがあることが挙がります。

できるようになったことは2つ紹介されます。ひとつは、複数のエリアを横断して品質の状況をまとめ、関係者全体に共有できるようになったこと。不具合の「発見タイミング」の傾向からどこに力を入れるかを決められるようになり、単一のエリアを見ているだけでは気づきにくい共通の課題も見つかるようになりました。もうひとつがファイル単位のスコアで、週次に5種類を算出しています。過去の不具合から見た将来リスクの Risk、次に触ったときの壊れやすさの Fragility、自動テストで防げているかの TestWeakness、変更の影響範囲の Impact、隠れた依存関係の Unexpected。組み合わせることで「どこが危険で、なぜ危険で、次に何をするか」が分かる設計だと説明されます。

いちばん見習いたいのは、スコアを出して終わりにしていないところです。過去に問題が起きたファイルをどれだけ捕捉できているかを見るバックテストと、スコアを記録したあとに実際に問題が増えたかを見るフォワードテストを組み合わせて、週次で精度を確認しています。精度に課題があるリポジトリもあると認めつつ、データが揃っているところではスコアの高いファイルほど問題が起きやすい結果になってきた、という書き方も誠実です。スコアはファイルパス単位で Notion DB に同期され、それを使う skill も用意されているとのこと。UXエンジニアリングの側に持ち込むなら、これはコンポーネントの健全性指標としてほぼそのまま読み替えられます。デザインシステムのどのコンポーネントが壊れやすいか、ビジュアルリグレッションをどこに厚くするか、レビューの時間をどこに寄せるか。そして社内指標が形骸化しないための要点は、指標を作ることではなく、指標が当たっているかを測り続ける仕組みを同時に作ることだと分かります。

### [Blender to Three.js and Back: 10 Tips for a Better Workflow](https://tympanus.net/codrops/2026/08/24/blender-to-three-js-and-back-10-tips-for-a-better-workflow/)

> **出典**: Codrops | **公開日**: 2026-08-24 | **カテゴリ**: design

**3行まとめ**
- Blender MCP と AI エージェントを前提にした、Blender と Three.js を往復するワークフローの実務 tips が10個並びます
- エクスポートごとに自動リフレッシュするアドオンや、ベイクの7工程を1クリックにまとめた自作アドオンの例が紹介されます
- TSL（Three.js Shading Language）によって Blender のシェーダーノードの移し替えが楽になった、という話で締められます

**詳細解説**

### [MetaRoCE: A New RDMA Transport Built for AI-Scale Ethernet](https://engineering.fb.com/2026/08/24/networking-traffic/metaroce-rdma-transport-ai-ethernet/)

> **出典**: Meta Engineering | **公開日**: 2026-08-24 | **カテゴリ**: engineering

**3行まとめ**
- Meta が AI ワークロード向けに一から設計した RDMA トランスポートで、仕様とリファレンス実装、適合テストスイートを OCP から公開します
- 「ファブリックはパケットを見るが、NIC は意図を見る」という発想で、知性をスイッチから端点へ移しています
- 順序外配送と損失を通常の状態として扱う設計で、パケットロス1%でも約86%のスループットを維持したと報告されます

**詳細解説**

背景の説明が分かりやすいです。学習では all-reduce や all-to-all が数千台の加速器を同期させるので、いちばん遅い転送が全体のペースを決めます。推論では分散したモデルシャード間の低遅延通信が、そのまま応答時間になります。だからネットワークのわずかな摩擦が、高価な計算資源を大量に遊ばせることになる。ところが標準的な RoCE はすべてのフレームが順序どおりに届くことを期待し、PFC に頼るので、大規模やマルチプレーンの構成で性能を出すためのパケットスプレーとは相性が悪い、という問題設定です。

中心の発想が「ファブリックはパケットを見るが、NIC は意図を見る」という一文に凝縮されています。従来はスイッチに知性を集め、無損失と順序をファブリックに強制させていた。MetaRoCE は端点に寄せ、ネットワークを細かい論理パスの集まりに分解して、パスごとに RTT、ECN の状態、利用率をリアルタイムで見ます。そこから4つの性質が出てきます。ひとつめは順序外配送を通常の状態として扱うこと。全パケットが自分の宛先を持つので、届いた順にそのまま最終メモリ位置へ書けて、リオーダーバッファも head-of-line blocking もいりません。Send も投稿済みの受信バッファとの対応を持つので、前のメッセージが届いていなくても正しく着地します。

ふたつめがネイティブなマルチパスで、パスごとに別の UDP 送信元ポートを ECMP のエントロピーとして持ち、NIC がいつでも変えて悪い経路から抜けられます。パスごとにウィンドウと RTT 推定を保つので輻輳と故障を区別でき、1本の詰まったリンクが接続全体を止めるのではなく1パスを遅くするだけになります。3つめが損失前提の設計で、PFC も pause frame も使いません。256bit の選択的 ACK のビットベクタに空いた穴は、並べ替えではなく損失の証拠になるので、失った正確なパケットを、失ったパスで即座に再送できます。4つめが双方向の輻輳制御。送信側の ECN ベースの AIMD に加えて、受信側が ACK ごとに「その送信側に割り当てた入力帯域の割り分」を返すので、送信側は適正速度を探索せず直接そこへ向かえます。incast が1〜2 RTT で収束すると述べられます。

運用上の性質もよく考えられています。ファブリックに求めるのは ECN マーキングと ECMP だけで、packet trimming や in-network telemetry、クレジットベースのフロー制御、スイッチ側のスプレーはいりません。fat-tree でもマルチプレーンでも、設定を握れないベンダークラウドでも同じトランスポートが動きます。queue pair の扱いも整理されていて、従来は順序ストリームと帯域の両方を増やすために QP を増やしていた（ノード対あたり数十）ところを、1接続の上に多数の独立した順序ストリーム、下に多数のパスを置き、輻輳制御を1つにまとめました。接続の状態がワークロードの並列度に比例して膨らまなくなります。既存の RDMA Verbs API と既存のソフトウェアスタックはそのまま動くとのこと。実測は AMD Pensando のプログラマブル NIC 上で、64ノードの AMD GPU クラスタで RoCEv2 と比較され、スループットと flow completion time の両方で優位。ロス1%で約86%のスループット、10%でも使える帯域を出し、崩壊せず緩やかに劣化します。

フロントエンドから遠い層ですが、設計の向きは持ち帰れます。順序を保証させる代わりに順序外を前提にする、損失をなくすのではなく損失に強くする、中央ではなく端点に判断を置く。この3つは、オフライン対応やリアルタイム同期の設計とほぼ同型です。どのメッセージも自分の宛先と適用先を持つように作れば、到着順を仮定せずに済み、再送と再接続の処理が単純になります。受信側が自分の処理できるレートを返すという発想も、クライアント側のバックプレッシャーの設計として読み替えられそうです。

推薦モデルの学習が抱える固有の事情から始まります。大規模言語モデルが膨大な浮動小数点スループットを必要とするのに対して、推薦モデルはアクセラレータ間の通信がボトルネックになる。埋め込みテーブルがモデルのパラメータの99%以上を占めることがあり、それを扱うためのハイブリッド並列が、数百台をまたぐ AllReduce、AllToAll、AllGather を頻発させます。GPU ではこれらの通信操作が学習計算と同じ資源を取り合うので、高価なハードが遊んでしまう。ここに手を入れたのが MTIA 300 で、通信ライブラリの HCCL をチップと一緒にゼロから設計したのが特徴です。

ハードウェアの作りが素直に効いています。ネットワークインターフェースがチップのパッケージの中にあり、2つのネットワークチップレットがそれぞれ 800Gbps のカスタム RDMA NIC を6つ持って、合計 1.2TB/s の I/O 帯域を PCIe を跨がずに供給します。ホストと NIC の間を CPU が仲介する構造が消えるわけです。同じ12個の Ethernet ベースの NIC を、ラック内16ノードの scale-up（最大1TB/s）とラック間の scale-out（200GB/s）の両方に使い、モデルの要求が変われば配分をネットワークの設定側で変えられます。遅延を削る工夫として、work request の書き込み自体を doorbell にすることでメモリ読み出しを1回省き、操作あたり約800ns を節約する express doorbell も入っています。

計算と通信の分離がこの記事のいちばんの読みどころでしょう。12×6 の処理要素グリッドとは別に、通信を独立して扱う message engine が16基。各エンジンは調整用の RISC-V コア、NIC インターフェース、128バイト/サイクルで縮約する near-memory compute を持ちます。この縮約ユニットは HBM とキャッシュの隣に置かれ、合計で 2.8TB/s を超える縮約スループット、つまり I/O 帯域の2倍以上を出すので、AllReduce と ReduceScatter を計算グリッドに触れずにラインレートで流せます。結果として、大きな GEMM と集団通信を同時に走らせても計算スループットの劣化は0.5%未満。同じことを従来の GPU でやると20%を超える劣化が出ることがある、という比較です。

ソフトウェア側も呼応しています。HCCL は集団通信を実行時にホストから駆動するのではなく、依存関係を明示した work-queue entry の部分グラフに丸ごとコンパイルして message engine に渡します。デバイスに届いたあとはホストが関与しません。PyTorch の c10d と torchcomms のインターフェースに載るので、`torch.compile` で追跡した集団通信が計算オペレータと同じグラフにコンパイルされます。性能はラック内で最大 940GB/s、1,500億パラメータの本番推薦モデルを40台で回して総通信時間が GPU クラスタの3.9倍速い。216GB の HBM3E でローカルバッチを大きくでき、CPU とアクセラレータが1:1 なので数値計算の重い最適化処理を CPU に逃がせて、帯域に余裕があるぶん高い精度のデータ型を使える、という副次的な設計余地も挙げられます。

引き取れるのは「通信を後付けではなく一級市民として設計する」という言い方です。フロントエンドでも、画面を作ったあとにデータ取得を足すのか、最初から画面の構造に織り込むのかで、待ち時間の見え方はまるで違ってきます。専用のエンジンに逃がして本線を汚さないという形は、重い処理を Worker に出してメインスレッドを空けておく判断とも重なります。記事の終わりで、推論が推論的・エージェント的・長文脈へ寄るとメッセージは小さく頻繁になり遅延に敏感になる、と述べられているのも示唆的です。帯域ではなく遅延とメッセージレートが問題になる、という移り方は、ストリーミング UI の設計で起きていることとよく似ています。

### [Environment variables now use Config and Secret types](https://vercel.com/changelog/environment-variables-now-use-config-and-secret-types)

> **出典**: Vercel | **公開日**: 2026-08-24 | **カテゴリ**: frontend

**3行まとめ**
- 環境変数の Sensitive トグルが、Config と Secret という2つの型に置き換わりました
- Config は保存後もアクセス権のあるメンバーが値を読めて、Secret はデプロイからは使えるがメンバーは閲覧できません
- 既存の Sensitive は自動的に Secret として扱われるので、移行の作業はいりません

**詳細解説**

Vercel で環境変数を追加・編集するときの選択が、Sensitive のオン・オフから Config か Secret かに変わりました。Config は保存後もアクセス権のあるメンバーが値を確認できるので、公開用のフレームワークプレフィックスが付いた変数のように、あとで見返したい非機密の値に向きます。Secret はデプロイからは使えて差し替えもできますが、保存したあとはメンバーが閲覧・取得できません。パスワード、API キー、トークンがこちらです。値ごとに環境や Preview のブランチを選べて、一覧には各変数の型と適用範囲が表示されます。

チームポリシーも整理されました。「Enforce Sensitive Environment Variables」は非推奨になります。これは有効にすると、メンバーが作る環境変数すべてを Sensitive にすることを求めるもので、非機密の設定値まで巻き込んでいました。代わりに「Separate Production Secret Values」が追加され、Secret の Production の値が、同じキーの Preview・Development・カスタム環境の値と異なることを求めます。旧ポリシーは Vercel CLI でも強制されなくなったので、有効にしていたチームは新しいポリシーを入れるかどうかを確認しておくとよいでしょう。CLI では `vercel env add` と `vercel env update` に `--visibility config` または `--visibility secret` を渡します。省略時は `--no-sensitive` が Config、`--sensitive` が Secret に対応します。

小さな変更ですが、設定 UI の作り方としては学べるところがあります。「機密かどうか」の1軸トグルは、状態が2値なのに意味が文脈に依存するので、押した本人以外には意図が伝わりません。名前の付いた型に置き換えると、一覧を見ただけでどれがどういう扱いなのか判断がつきます。旧ポリシーが「全部 Sensitive にする」しかできなかったのも、軸が1本しかなかったことの帰結でした。トグルを型に開く、という置き換えは、権限や公開範囲を扱う画面を設計するときに思い出しておきたい手です。

引用付きの答えを返す UI を考えているなら、そこは先に決めておくとよさそうです。ゲートウェイに任せるならモデルの出力テキストから出典を取り出す設計になり、途中を見せたいなら Marketplace 側の Exa SDK を直接叩いて、検索と生成を自分で分ける形になります。同じ機能でも、待ち時間の見せ方まで含めて考えると選ぶ側が変わってくる、という例として読めます。

**詳細解説**

フロントエンドの体験としては、「押した瞬間に受け付けたと返して、処理は裏で進める」という形が組みやすくなります。ただし裏に回した処理の状態を画面に返す部分は自分で作る必要があります。`messageId` を受け取ったあと、進捗をポーリングするのか、完了を通知で伝えるのか、それとも画面上に楽観的な結果を先に出しておくのか。キューを入れると待ち時間がユーザーから見えなくなるので、その「見えなくなった時間」をどう表現するかが実際の勘所になります。

### [Bun runtime now supports large functions and extended max duration](https://vercel.com/changelog/bun-runtime-now-supports-large-functions-and-extended-max-duration)

> **出典**: Vercel | **公開日**: 2026-08-24 | **カテゴリ**: frontend

**3行まとめ**
- Vercel Functions の Bun ランタイムで、非圧縮で最大5GB のパッケージと最大30分の実行時間が使えるようになりました
- どちらも Fluid compute が必要で、これまで Node.js と Python でだけ動いていた2つのベータです
- 800秒を超える時間はプロジェクトの既定ではなく、`vercel.json` で関数ごとに設定します

**詳細解説**

large functions は標準の250MB というパッケージサイズ上限を5GB に引き上げ、extended max duration は一般提供されている800秒の上限を1800秒に引き上げます。後者は Pro と Enterprise のチーム向けです。新しく作ったプロジェクトは large functions のベータに自動で入りますが、2026年7月より前に作られたプロジェクトは `VERCEL_SUPPORT_LARGE_FUNCTIONS=1` を環境変数に追加して再デプロイする形で参加します。30分の設定は `vercel.json` の `functions` で対象の関数に `maxDuration` を書きます。ベータの期間中は Secure Compute や Static IP を使っているプロジェクトでは利用できません。

数字の意味を考えると、この2つはどちらもエージェント時代の上限緩和です。30分は人が画面の前で待つ長さではないので、ここが要るのはエージェントの実行や重いバッチ処理でしょう。つまり UI 側は最初から「投げて離れる」前提で組むことになります。5GB のほうは、大きな依存を抱えた処理をフロントエンドと同じリポジトリ・同じデプロイに置けるようになる、という意味で効いてきます。ランタイムを揃えられれば、型もツールチェインも共有できます。

もっとも、上限が上がったことは「そこまで使ってよい」という話とは別です。30分の関数を1つ置くたびに、失敗したときの再実行、途中でデプロイが入ったときの扱い、進捗をどう見せるかが付いてきます。長い処理はキューやワークフローに載せたほうが素直な場面も多いので、上限に頼るのは「載せ替えるコストのほうが高い」と判断できたときにとどめておくのが安全でしょう。
