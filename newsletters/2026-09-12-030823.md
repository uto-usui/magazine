### [Why Shopify is moving off React Native](https://react.statuscode.com/issues/490)

> **出典**: React Status | **公開日**: 2026-09-11 | **カテゴリ**: frontend

**3行まとめ**
- React 19.3 がリリースされ、Fragment Refs と View Transitions が実験段階を抜けました
- Shopify が React Native への全面移行から6年で、Swift と Kotlin によるネイティブ再構築に舵を切っています
- 理由は「コーディングエージェントが、同じ機能を2回作るコストを下げた」から。クロスプラットフォームの前提そのものが揺れています

**詳細解説**

React Status の第490号です。ニュースレターなので複数の話題が並びますが、この号は2つの大きな出来事で構成されています。

ひとつめが React 19.3 です。とくに大きいのが Fragment Refs と View Transitions で、どちらも長く実験扱いだったものが正式な API になりました。Fragment Refs は、レイアウトを壊しかねないラッパー要素を追加せずに、複数の DOM ノードをまとめてフォーカス・イベント・計測の対象にできる仕組みです。「ref を通すためだけに div を1枚挟む」という、UI 実装でよくある妥協がひとつ消えることになります。`<ViewTransition>` のほうは、要素の出入りや変化を CSS でカスタマイズできる形でアニメーションさせるもので、Suspense の解決にも対応しています。

ほかにも Trusted Types のサポート（`innerHTML` などに値を渡す際に trusted オブジェクトを保持するようになり、文字列に変換されてブラウザに拒否される問題が解消）、`use(browser())` によるサーバーレンダリングのオプトアウト、`<Activity>` の Server Component 対応、そして遅いトランジションが無関係なトランジションをブロックしなくなる変更が入っています。最後のものは、体感としてかなり効く類の改善でしょう。

ふたつめが Shopify の話です。React Native に全面的に賭けてから6年、Swift と Kotlin でアプリを作り直すという判断をしています。論拠として挙げられているのが「コーディングエージェントによって、同じ機能を2回作るコストが下がった」こと。React Native Skia、FlashList、Restyle といった Shopify 発の OSS がどうなるのかにも言及があります。

この論法は、UX エンジニアリングの視点から見るとかなり重い意味を持っています。クロスプラットフォーム技術の存在理由は、おおむね「実装を1回で済ませたい」という一点にありました。ネイティブのほうが体験は良いと分かっていても、2回作るコストが割に合わないから共通化する、という取引です。エージェントがその取引の片側を安くしたなら、判断の天秤は当然ネイティブ側に傾きます。ただし注意したいのは、2回作るのが安くなっても、2つを一貫させ続けるコストは別だという点です。プラットフォーム間で体験がじわじわずれていく問題は、コード生成の速さでは解けません。ここは今後の観察ポイントになりそうです。

同じ号の短信も濃い内容でした。Tailwind CSS の Tailwind Labs が Shopify に加わること（OSS は MIT ライセンスのまま、同じチームが継続）、React DevTools 8.0 で Suspense タブが既定になり Timeline profiler が廃止されてブラウザの Performance パネルに引き継がれたこと、そして `chrome-devtools-mcp` 経由で React DevTools をコーディングエージェントに開く実験的パッケージが出ていることなどです。デバッグツールをエージェントに向けて開く動きは、しばらく続きそうな流れでしょう。

技術的におもしろかったのは、oxc による React Compiler の Rust 移植を1000ファイル超の React Router アプリに適用した記録です。コンパイル時間が14.3秒から0.81秒になり、しかも Babel ベースの 1.0 が飛ばしていたパターンまで扱えているとのこと。Discord の New Architecture 移行の記事も現実的で、移行そのものに関わるチケットは全体の14%しかなく、残りはすべてロングテールだったと報告されています。移行プロジェクトの見積もりをする立場なら、この比率は覚えておくと役に立ちます。

### [Building A UX ROI Case That Survives The Boardroom](https://smashingmagazine.com/2026/09/building-ux-roi-case-survives-boardroom/)

> **出典**: Smashing Magazine | **公開日**: 2026-09-11 | **カテゴリ**: design

**3行まとめ**
- UX 施策の投資対効果を、役員会で詰められても崩れない形で組み立てる手順を、架空企業 Meridian の数字で一気通貫に追っています
- 分母（コスト）にステークホルダーの時間まで含めること、因果を A/B テストで検証すること、寄与率を控えめに置くことが柱です
- 最終的に ROI 約5:1。ただし前提となる3つの仮定をスライドに明記する、という誠実さの部分がこの記事の要点でしょう

**詳細解説**

書き出しがいきなり刺さります。いずれ CFO がワイヤーフレームを見て「これは結局、収益に何をするのか」と聞いてくる。ストーリーボードはその問いに答えないし、5分のピッチで答えられた時代はとっくに終わった、と。3D のパーティクル表現の力で100万ドルの改修を通した元同僚のエピソードが引かれていて、いま同じピッチを財務チームの前でやってみろ、と続きます。

この記事の良いところは、ヒントを散らすのではなく、Meridian という架空の B2B SaaS 企業のオンボーディング改修ひとつを、目標設定からコスト計上、因果検証、最終的な ROI まで同じ数字で追い切っているところです。しかも「架空である」というラベルが要所で繰り返されます。

最初の論点は、そもそも会社に測れる目標が存在しない場合の話です。多くの UX ROI の記事は「組織にはすでにきれいな事業目標と KPI がある」と都合よく仮定しますが、現実は「もっと速く成長する」「顧客体験を改善する」といった、誰も測れる形に分解していない野心で動いていることが多い。Meridian の当初の目標も「新規ユーザーのプラットフォーム定着率を改善する」で、これは設計もできなければ測定もできません。部門横断のインタビューで分かった実際の形は、トライアルユーザーが最初の価値に到達するまで中央値14日かかり、その前にほとんどが離脱し、オンボーディングの質問がサポートのキューを埋めている、というものでした。そこから「ガイド付きセットアップで初回価値到達までの中央値を14日から7日へ」「トライアルから有料への転換を8%から9.5%へ」という、輪郭のある OKR が出てきます。

KPI を UX チームの内側から押しつけると、経営層は「自分たちに有利な土俵を作った」と疑う。だから成果の責任を持つ人と一緒に作る、という指摘も実務的でした。ただし、自チームが苦しくなる目標を受け入れてまで妥協はしない、というただし書きも付いています。すでに誰かがダッシュボードで見ている指標に着地する KPI の梯子は、デザイン作業を始める前から信頼を稼いでくれる、と。

コストの節がこの記事でもっとも有用な部分でしょう。ROI には分母があり、UX チームはたいていここで間違える。デザイナーの人件費とコンサル費だけを数えて、残りは数えない。しかし財務チームは、こちらが数えようが数えまいが残りを見つけ出します。だから先に全部数えておく。Meridian の内訳は、デザインとリサーチの人件費4万5,000ドル、ツールと被験者謝礼8,000ドル、エンジニアリング3万8,000ドル（フロントエンド2スプリント + QA）、調整コスト4,000ドル、そして——ほとんどの人が落とす項目である——ステークホルダーの時間2万2,000ドルです。

このステークホルダーの時間という項目が良い指摘でした。ワークショップ、デザインレビュー、フィードバックセッションは、いずれも上位職を本来の仕事から引き剥がします。週に4時間 UX レビューに出ている VP of Product は、その4時間をロードマップ計画やパートナー交渉に使っていない VP です。誰がどれだけ、どの職位で参加したかを記録し、給与と福利厚生を稼働時間で割った「フルロードコスト」で値段をつける。合計11万7,000ドルを口に出すほうが「デザインに4万5,000ドル使いました」と言うより強いのは、財務が自力で掘り出すはずのものをすでに含んでいるからです。

因果の節も現実的です。改修後にコンバージョンが上がったとして、CFO が知りたいのは「新しい価格設定、季節的なトラフィックの増加、同じ週に走ったマーケティング施策をどう排除したのか」でしょう。Meridian は8週間、新規トライアル登録の半分に新しいガイド付きセットアップを出し、半分は従来のフローのままにしました。コントロール群8.0%、バリアント群9.4%、期間内のトライアル約6,100件で統計的に有意。それでも「1回のテストでの1.4ポイント差は、予算を組む前にもう一度見るに値する結果だ」と釘を刺しています。

そのうえで、5週目から8週目にマーケティングチームの価格ページテストが重なっていたことを記録し、両群に均等に当たっていることを確認したうえで、なお改修への寄与を70%に留めています。この70%という数字を出す公式はなく、あくまで例として置かれた仮定だと明言されている。大事なのは、結果が出る前に書き留めて論拠を示すことであって、後から結果に合わせて当てはめることではない、という規律です。「観測された上昇のおよそ70%をオンボーディング改修に帰属させ、残りは並行して走った価格施策の影響と見ています」は反対尋問に耐えるが、全部が自分の成果だと主張するほうは耐えない、と。

先行指標と遅行指標を同じスライドに置く、という助言も効いています。Meridian では先行指標が先に動き（セットアップ完了率62%→89%、初回価値到達までの中央値14日→6.5日）、遅行指標のトライアル転換率が後から追随しました。メカニズムが先、事業成果が後。この順で並べると、どちらか一方より崩しにくい因果の鎖になります。

最終計算はこうなります。年間トライアル登録4万件、転換率8.0%→9.4%で有料顧客が年間約560件増加、1件あたり年間経常収益1,800ドルで約100万8,000ドル。寄与率70%を適用して擁護可能な数字は約70万6,000ドル。投資11万7,000ドルに対して初年度 ROI は約5:1、回収期間は約2か月。サポートチケットが約30%（年間3,600件）減った分は、1件15ドルとして年間5万4,000ドルを別行に立てています。ひとつの膨らんだ見出し数字に畳み込まない、というのがここでの判断です。

そして結果を支える3つの仮定を、結果の隣に明記する。4万件の登録と1,800ドルの平均 ARR は前年実績を横置きしたもの、70%の寄与率は例示のための仮定で測定値ではない、2か月の回収期間は解約を差し引いた認識収益ではなく入ってきた ARR で数えているので楽観的（純額ベースなら約四半期に伸びる）。この3つを率直に述べれば財務チームは自社の数字に置き換えられるし、隠せば、どれだけ実験が丁寧でも全体がマーケティング算術に見えはじめる、と。

UX エンジニアリングの視点で読むと、この記事の使いどころはデザインシステムや基盤系の投資の説明にあります。この種の仕事は成果が間接的で、「作った人以外には効果が見えない」状態になりがちです。この記事の型をそのまま当てると、分母にはコンポーネント実装の工数だけでなく、移行の会議や各チームのレビュー時間まで入れることになる。分子には実装リードタイムの短縮や不具合率だけでなく、その値が本当に基盤のおかげなのかを問う工程が必要になります。数字を盛る技術ではなく、削って残ったものだけで戦う技術の話だと読めます。

### [Test Complex Interactions Earlier with AI Prototyping](https://www.nngroup.com/articles/test-earlier-with-ai/)

> **出典**: Nielsen Norman Group | **公開日**: 2026-09-11 | **カテゴリ**: design

**3行まとめ**
- 状態の多い複雑な UI を AI ツールで作り込み、開発前にユーザーテストへ回せるようになった、という報告です
- Ramp のポリシーエディタと会話型 AI、Purdue 大学の交通データフィルタという3つの事例で、静的プロトタイプでは出なかった問題が見つかっています
- 一方で「忠実度の罠」——見た目が完成しているせいで改善の手が止まる現象への注意が置かれています

**詳細解説**

フィルタ、ダッシュボード、会話型 AI のような UI は、取りうる状態が多すぎて手作業のプロトタイピングが割に合いません。AI ツールが登場する前は、ハッピーパスをいくつか押さえた簡単なプロトタイプでテストし、実際の操作感は開発が終わるまで分からない、というのが一般的でした。その前提が変わった、という記事です。

導入部のただし書きが丁寧でした。複雑ではない UI なら静的プロトタイプで答えられるリサーチクエスチョンはまだ多い。AI プロトタイピングが効くのは、UI が複雑なときに限られる、と範囲を切っています。

最初の事例は Ramp の経費ポリシーエディタです。シニアプロダクトデザイナーの Pavan Garidipuri が Cursor を使って再設計のプロトタイプを作りました。このツールは管理者が支出ルールを管理するもので、以前からナビゲーションが難しいと言われていた領域です。再設計の主眼は AI チャット経由でポリシーを編集する体験にあり、会話ベースの編集は UI 側の応答が動的なので、静止画面ではシミュレートしにくい。ユーザビリティテストでは参加者に、自分の（匿名化された）データを読み込んだ動くプロトタイプへのリンクを渡しています。結果として、編集内容の追跡と表示の仕方が分かりにくいという問題が見つかった。これは実物そっくりの操作できるプロトタイプがなければ発見できなかった、とチームは述べています。構想からデモまで3週間、この案件がその年の残りのロードマップを動かしました。

2つめは同じ Ramp の会話型 AI による経費精算フローです。ここが AI プロトタイピングの本領で、この UI はほぼどんな入力にも妥当な応答を返す必要があり、同じ入力に対して違う出力を返すことすらあります。あらかじめ用意した画面の集合に閉じている従来のデザインツールでは、この非決定的な振る舞いは表現できません。プロダクトデザイナーの Andrew Lucas は Cursor でエージェントに接続したプロトタイプを作り、参加者が決められた経路を辿るのではなく好きなものを入力できるようにしました。エージェントが想定外の依頼をどう扱うかを観察できたわけです。

3つめは Purdue 大学の研究者による、高速道路の交通技術者向けフィルタ UI です。交通イベント1件あたり27の属性があり、入れ子の副属性を持つものもある。フェーズ1では Figma で手作業の低忠実度ワイヤーフレームを作り、視覚デザインへのフィードバックは得られたものの、フィルタの操作に対してシステムがどう応答するかは観察できませんでした。フェーズ2では v0 と Bolt で作り直し、合成データを与えた動くプロトタイプへのリンクを共有しています。参加者の関わり方が違った、という観察が興味深いところです。静止画面では「まだ初期段階すぎて深く批評するものではない」と扱われ、フィードバックが具体性を欠いた。動くプロトタイプでは、チームが対処できる具体的な問題を指摘してきた、と。

ここでも記事は正直です。これは統制実験ではなく単一プロジェクトの逐次的なケーススタディなので、フェーズ1からフェーズ2にかけてチーム自身の問題理解も深まっている。だから「AI プロトタイピングのほうが良いリサーチを生む」証拠としてではなく、「何が作れてテストできるようになったか」の例として読むように、と明記されています。この種の留保を置けるかどうかが、記事の信用を決めます。

手順は6ステップにまとまっています。(1) プロトタイプに何をさせる必要があるかを、ツールを開く前に決める。リサーチクエスチョンに答えるのに必要な相互作用のレベルはどこか。簡単なプロトタイプで足りるなら完全な対話性は要りません。(2) デザインの判断を先に済ませる。レイアウト、階層、インタラクション、そして空状態やエラー状態のようなエッジケースまで書き出す。ステップ4のプロンプトの質は、ここでの思考の質で決まります。(3) データを集める。実データを使うなら組織のデータポリシーに従い、個人を特定できる情報は上げない。ツール側のデータポリシーも確認する。あるいは合成データセットを生成させる。(4) 判断とデータを含んだプロンプトを書く。スケッチやワイヤーフレーム、既存デザインも添付してよく、Markdown 形式が LLM には解釈しやすい。(5) Cursor、v0、Figma Make などに渡す。(6) 出力を編集して反復し、最後に小さなパイロットテストで意図通り動くかを確かめる。

最後の2つの注意が、この記事でもっとも価値のある部分でしょう。ひとつは「デザインの判断は依然としてこちら側にある」こと。AI ツールに判断を委ねれば、ツールは勝手に隙間を埋めますが、人間のような細部への注意は持ちません。コンテンツのレイアウトや視覚的階層を本質的に理解しているわけではないので、詳細な指示が要ります。変わったのは「判断を誰がするか」ではなく「判断をどれだけ速く動くものに変えられるか」だ、と整理されています。

もうひとつが「忠実度の罠」です。磨き上がって見え、実データが載り、完全に操作できる AI プロトタイプを作ったとき、「良さそうだね、これ出荷できない?」と言われた経験はないか、と。作り方を知らない人からすれば妥当な質問ですが、高忠実度の見た目は本番可用性を意味しません。間違ったデザインパターンを使っている、階層が混乱している、要素が不必要に繰り返されているといった問題を抱えたまま、完成して見えることがあります。危ないのは、その磨かれた見た目のせいで改善の手が止まることです。本番に出る前にデザインの知識がある人がレビューする、という歯止めが要ります。

UX エンジニアリングの立場からいうと、この「忠実度の罠」は自分たちが持ち込んだ問題でもあります。動くものを速く出せるのは強みですが、動くものは意思決定の場でつねに絵に勝ってしまう。プロトタイプを共有するときに「これはこの問いに答えるために作ったもので、この部分は検証していません」と明示する習慣が、以前よりずっと重要になっているといえます。

### [AI Can Help Write an Article, but It Can't Stand Behind It](https://www.nngroup.com/articles/ai-editorial-process/)

> **出典**: Nielsen Norman Group | **公開日**: 2026-09-11 | **カテゴリ**: design

**3行まとめ**
- NN/g が自分たちの編集プロセスで AI をどう使っているかを、具体的な用途ごとに開示した記事です
- EU AI Act の透明性規定が「人間によるレビューまたは編集管理を経たコンテンツ」を適用除外にしている点が出発点になっています
- 明確さの改善、厳格な書式への適合、他チャネルへの転用、そして批評パートナー。ただし編集上の判断と責任は外注できない、という線引きです

**詳細解説**

2026年8月に EU AI Act の透明性規定が発効しました。一定の種類の AI 生成・公益的なテキストに開示義務を課す法律ですが、興味深いことに「人間によるレビューまたは編集管理を経た」コンテンツで、かつ個人または組織が編集上の責任（公開されたものに対する説明責任）を負うものは適用を除外しています。この区別から記事は始まります。

NN/g では編集プロセス全体で AI を使っている。AI が言葉を、ときにはアイデアの一部を記事に提供することもある。しかし編集上の判断は人間に残る——つまり、AI ではなく関連する専門知識を持つ人間が、そのコンテンツが伝える知見と実践を評価し、その内容を支持している、という立て付けです。

NN/g の編集プロセス自体の説明も参考になります。2013年以降ほぼすべての記事が同じ手を通っており、書き手がテーマを提案し、そもそも扱うかどうかを判断する。すでに同じテーマの記事がないか、この分野が必要としているものか、ほかの誰にも出せない独自の視点や整理の枠組みがあるか。そこから改稿が始まります。初稿がそのまま公開されることはまれで、通常2人の編集者が論理の一貫性、UX としての正確さ、コピーをレビューする。改稿は2〜3回、それ以上のこともあり、ブログ執筆というより学術出版に近いプロセスだ、と。しかもゲスト寄稿者だろうと組織の上位者だろうと、在籍1日だろうと20年だろうと同じルールが適用されます。

AI の使いどころは4つに整理されています。

ひとつめが文章を明確にすること。書き手の幅が広く、多くはプロのライターではない。英語が第二言語の人もいる（編集者自身を含めて）。以前は段落を簡潔かつ分かりやすく書き直すのに長い時間を使っていたが、いまは Word の Copilot や Grammarly が、同じことをより簡潔に、しばしばより明確に言う手伝いをしてくれる。ただし AI が議論を濁したり、短くする過程で大事なニュアンスを落とすこともあるので、書き直しが本当に良くなっているかを判断するのは編集者の仕事だ、と留保が付きます。

ふたつめが厳格な書式要件への適合です。NN/g の記事は必ず固定長の要約から始まり、現在は160文字。その範囲にぴったり収まる段落を書くのは技芸で、多くの書き手は文字数を忘れる（あるいはスペースを数え忘れる）。AI はこの制約を満たす要約の生成が得意です。スタディガイドや用語集にも厳格な書式があり、たとえばスタディガイドの記事リンクには「能動態の動詞を含む完全な文」といった形式の短い説明が要る。書き手が用意したものを要件に合わせる作業は AI に向いています。

3つめがチャネル間の転用です。NN/g は自習コース、レポート、動画、ポッドキャストと複数のチャネルでコンテンツを作っており、ある形式にあるアイデアを記事向けに作り直す必要が出てきます。AI は関連情報を抽出して新しい形式に適合させる手伝いができる。最終確認は必ず人間が行いますが、転用作業の退屈な部分の多くは任せられる、と。

4つめが判断の補助で、ここがもっとも踏み込んだ部分です。AI は、記事を支える証拠と議論の論理の両方を編集者が問い直す助けになる。事実確認や主張の検証で、研究や法律を引用している箇所について、より詳しく見るべき誇張や過度の一般化を指摘できる。この記事の第一文の表現も、EU AI Act の具体的な内容を正確に反映させるため AI の助けを借りて何度か調整されたそうです。ただし「AI が主張の正しさを保証することはない」と明記されています。AI が問題を指摘したとき、出典に戻って再確認し、誤りがあれば直すのは編集者か書き手の仕事です。

議論のレベルでも同じ役割を果たせる、という例がおもしろい。編集者としてもっとも難しい仕事のひとつが、矛盾や、記事が支えていない・明示していない前提のような論理的な問題を見つけることです。この記事の初期版は「思考を AI に外注してはいけない」という考えを中心に据えていた。ところが同じ草稿の別の箇所では、AI を推論プロセスに参加できる有用な批評パートナーとして描いてもいた。ChatGPT に草稿を批評させたところ、この2つの緊張関係を指摘してきた。それが、最終的な原則をより正確に言語化させることにつながった、と。

使い方の作法も明快です。まず自分の草稿評価を共有し、それに異議を唱えるか、その上に積み上げるように頼む。見落としを見つけることもあれば、評価に異議を唱えることもあり、同意できない推奨をしてくることもある。いずれの場合も答えとして受け取るのではなく、提案として重みづけする。議論を強くし、かつ適用可能だと信じられるものを残し、残りは捨てる。

結びの整理が良い。書くことを AI に委ねるのは考えることを AI に委ねることだ、という警告は多い。書くことの利点のひとつは、思考とともに時間を過ごして整理する機会を持てることで、その過程で議論の弱点や欠陥を発見して良くできる。ただし思考は書くこと以外でも起こりうる——スケッチ、誰かとの議論、AI ツールに向かって構造化されていない考えを口述すること。プロンプトを書くことも思考のプロセスの一部になりうる、と。だから NN/g は書き手に、どう書くか・どう考えるかを規定しない。重要なのは、人間の専門家が、その記事を理解し評価し支持するために必要な知的作業をしたことである、という立場です。AI は執筆プロセスに参加できるが、編集上の責任は委譲しないし、書き手として名前も載せない。

UX エンジニアリングの文脈に引きつけると、これはコードレビューの責任の所在とほぼ同じ話です。エージェントが書いたコードでも、マージした人が説明責任を負う。「AI が書いたので分かりません」は通らない。この記事が良いのは、その原則を掲げるだけでなく、では実際どこまで任せているのかを用途ごとに開示しているところでしょう。最後の一文も皮肉が効いています。NN/g の AI コンテンツポリシーは、この記事を入力として AI が大部分を生成し、人間がレビュー・改稿・承認したものだ、と。

### [How Tailscale built a customer-facing model router on AI Gateway](https://vercel.com/blog/how-tailscale-built-a-customer-facing-model-router-on-ai-gateway)

> **出典**: Vercel | **公開日**: 2026-09-11 | **カテゴリ**: frontend

**3行まとめ**
- Tailscale の Aperture は、AI モデルへのアクセスをプライベートネットワーク（tailnet）の ID で制御するプロダクトです
- インフラ企業でありながら、モデルルーターとサンドボックスは自作せず Vercel の AI Gateway と Sandbox に載せています
- エージェントに API キーを一切渡さない設計と、「lethal trifecta」への対処の仕方が読みどころです

**詳細解説**

Tailscale は、企業のノートPC、サーバー、クラウドインスタンス、個人デバイスをひとつのプライベートネットワーク（tailnet）につなぐ会社です。Aperture のプロダクトを率いる Remy Guercio の説明が簡潔でした。「どのクラウドにも、オンプレにも、自宅にも、スマホにもまたがれる VPC のようなもの」だと。

Aperture はその発想を AI に適用しています。従業員・エージェント・ツールのそれぞれに別々のプロバイダー API キーを配るのではなく、tailnet 自体を通してモデルへのアクセスを制御する。ネットワークに誰かを追加すれば、その人はすぐ承認済みモデルを使える。外せばアクセスは消える。この「ID とネットワークをアクセス制御の単位にする」というアイデアが中心です。

興味深いのは、インフラ企業である Tailscale が、ルーティング層と実行層を自作しなかったことです。当然の第一選択として検討はしたものの、必要な工数を深く調べた結果やめている。「エンドポイントは全部同じだろうと思うでしょう。違います」と Remy は言います。共同創業者で CSO の David Carney の言い方はさらに具体的で、Aperture に移行していない一部顧客向けにいまもその配管を保守しているそうです。「大手プロバイダーがやっていないことがたくさんあって驚きます。レスポンスにコストを入れるだけのことすら、です。最初は自分たちで顧客向けに作りましたが、複雑さは常軌を逸しています」と。

エージェントが話をさらに難しくします。プライベートなデータを読め、読んだテキストに基づいて行動でき、公開インターネットに到達できるエージェントは、いま「lethal trifecta」と呼ばれるセキュリティ問題です。正しい緩和策は、ID とアクセス制御が組み込まれた隔離サンドボックス。「サンドボックスまで自分たちで作ろうとしていたら、このプロダクトは出せなかったと思います」「Vercel の上では、プロトタイプから有料顧客まで数か月で行けました」と David は述べています。

技術的な選定理由も具体的です。AI Gateway が数百のモデルにひとつの API を提供し、リクエストごとにコストと使用量を返すので、Aperture はプロバイダーごとの価格表を保守せずに顧客へ支出を見せられる。顧客のデータ保護の要求から Zero data retention（ZDR）は前提条件でしたが、AI Gateway 自体がデータを保持せず、ZDR をグローバルに設定するか、リクエスト単位の `zeroDataRetention` フラグで ZDR 準拠のプロバイダーにルーティングを限定できる。「どのモデルが ZDR でどれが違うかは常に動く標的ですが、そのロジックを一切書かなくてよい」という言い方が、この種のプロダクトの現実をよく表しています。トークンコストへの上乗せがない点（顧客が自前のキーを持ち込む場合も含めて）も選定理由に挙がっています。

「time to first token」という言葉を David が意図的に二重の意味で使っている、というくだりが良かった。AI インフラの世界では、キャッシュをロードし、応答を生成し、ユーザーに返すまでの時間という明確な定義があります。David の定義は「ユーザーがサインアップしてから最初のモデル呼び出しまでの時間」で、それこそが Aperture が顧客に提供する本当の価値だ、と。これは体験設計としてはまっとうな言い換えです。技術指標としての初回トークン到達時間を最適化しても、サインアップから価値到達までの障壁が残っていれば、ユーザーにとっての「速さ」は変わらないからです。

tailnet の中でエージェントを安全に動かすワークフローも明快でした。サンドボックスが起動して Aperture に接続、Aperture が AI Gateway に接続、Tailscale が ID を検証、エージェントが作業し、サンドボックスが終了する。そして「エージェントにキーが発行されることは一度もない」。サンドボックス層も他社で完全な実装まで作ったうえで Vercel に切り替えたそうで、「ネットワーク ID に集中したかったのであって、サンドボックスのセキュリティ境界に集中したかったわけではない」という理由づけがされています。

社内の AI 利用の移行も現実的な話でした。Tailscale 自身の AI 利用も、多くの会社と同じようにプロバイダー直契約とクラウドエンドポイントがチームごとに積み上がった状態だった。社内リクエストは Aperture を経由していたものの、プロキシの裏では個別プロバイダーを直接呼んでいた。顧客向けに AI Gateway を実装したあと、自分たちも移行しています。Aperture 側に切り替えスイッチを作っただけで、従業員にとっては何も変わらない。呼ぶエンドポイントは Aperture のままで、使っていたモデルはすべて AI Gateway のカタログにあったので、中断ゼロで切り替わりました。「全社を数秒で AI Gateway に切り替えて、誰も気づかなかった。それが興奮した部分です。誰も気づかなかった」というコメントは、移行プロジェクトの理想形を言い当てています。

UX エンジニアリングの視点で拾いたいのは、Aperture が「開発者がコーディングエージェントを向ける先の生のゲートウェイ」として始まり、いまはチャット UI、MCP コネクタ、一時ノードとして起動できるサンドボックスを備えるに至った、という経過です。インフラ的なプリミティブとして出発したものが、使われるにつれて UI を要求してくる。最後に David が言う「みんな自前のルーターを作りたがる。うちも試した。でも、もうひとつルーターを作る必要はない」は、判断の基準としてそのまま持ち帰れます。

### [Turning Names Into Digital Architecture with Three.js](https://tympanus.net/codrops/2026/09/09/turning-names-into-digital-architecture-with-three-js/)

> **出典**: Codrops | **公開日**: 2026-09-09 | **カテゴリ**: design

**3行まとめ**
- パリの Three.js Conference 向けに、入力した名前を金属の3D構造物に変える実験を作った制作記です
- すべての文字を「ちょうど120点の閉じた輪郭」として扱うことで、文字から文字へのモーフィングが成立しています
- 実体のあるチューブではなく、縦線・筋交い・斜材だけを残した構造システムとして描く。発想はエッフェル塔から来ています

**詳細解説**

「ウェブサイトというより、小さなデジタル機械のようなものを作りたかった」という書き出しです。アイデアはシンプルで、名前を打ち込むと、それが金属になる。

技術的な出発点は文字の表現でした。すべての文字を、ちょうど120点からなる閉じた輪郭として表現します。ロゴの文字はあらかじめ点データを持っていますが、ユーザーが入力した名前は少し違う経路をたどる。隠しキャンバスに文字を描き、ピクセルマスクに変換し、輪郭をトレースし、平滑化して、同じ120点の構造に戻す。穴も数に入れる——穴のない「B」はまったく別の「B」になってしまうからです。点の数を固定に保つことが、次の工程を可能にしています。

その次の工程がモーフィングです。ある文字の各点は、次の文字の対応する点を持っている。両者を補間しながら、輪郭を空間内の曲線経路に沿って動かしていく。ただの単純なモーフではなく、移動しながら構造そのものを変形させます。点はねじれ、狭まり、傾いていく。2枚の平らな輪郭から始まったものが、連続した構築物になる。金属のチューブを通して文字を引き抜いたような見た目です。

掲載されているコードは短いのに、変換の大半をここが担っています。ループがやっているのは3つのことで、2つの輪郭のあいだで形状を補間すること、点を曲線に沿って動かすこと、そして遷移に有機的な動きを与える変形を適用することです。ベジエ曲線上の位置と接線を求め、そこに `pinch`（くびれ）と `twist`（ねじれ）を `sin(πu)` のバンプでかけている。区間の中央でもっとも強く変形し、両端では元の形に戻る、という素直な設計です。文字のインデックスが偶数か奇数かでねじれの符号を反転させているところが、単調さを消す小さな工夫でしょう。

見た目のうえでもっとも効いているのが、構造の作り方です。実体のあるチューブをレンダリングする代わりに、選んだ縦方向の線、筋交い、斜めの支持材だけを残す。着想はエッフェル塔と、大きく複雑な形を驚くほど軽く感じさせるそのやり方から来ている、と書かれています。Three.js の line geometry とカスタムシェーダーでレンダリングされています。

もうひとつ、実装者として覚えておきたい判断があります。金属の見た目にレイトレーシングは使っていません。反射の表現はベイク済みのリフレクションマップで、不要なレンダリング負荷を足さずに変化する金属表面を得ている。カンファレンス向けのインタラクティブな体験で、任意の文字列を入れられる以上、フレームレートは体験の一部です。見た目の質を落とさずに計算量を落とす、という判断が明確に効いている例といえます。

UX エンジニアリングの視点で見ると、この制作記の価値は「制約を先に決めたことで表現が広がった」構造にあります。120点という固定の制約は、一見すると表現の自由を縛るものです。しかしその制約があるからこそ、任意の文字から任意の文字への連続変形が単純な補間として書ける。ユーザー入力を受け付ける体験を作るときに、入力の多様性を後から吸収しようとすると破綻しがちですが、ここでは「どんな入力も同じ形式に正規化する」層を最初に置いています。フォームバリデーションからデザイントークンまで、同じ考え方が効く場面は多いはずです。

協賛の背景も率直に書かれています。技術コミュニティから日々知見を得て、OSS として活用させてもらっている以上、一方的に恩恵を受けるだけでなく貢献を続けたい、と。加えて、自社のフロントエンドチームがまだ発展途上で、社外コミュニティとの接続がより求められていると感じている、という認識も明かされています。協賛を通じて社内に知見を持ち帰り、最終的にコミュニティへ還元したい、という流れです。

### [Control who can manage connectors in Vercel Connect](https://vercel.com/changelog/control-who-can-manage-connectors-in-vercel-connect)

> **出典**: Vercel | **公開日**: 2026-09-11 | **カテゴリ**: frontend

**3行まとめ**
- Vercel Connect のコネクタを誰が作成・管理できるかを、Pro と Enterprise チームで制限できるようになりました
- Team Settings の Connector Permissions で有効にすると、Owner ロールか Connector Manager 権限を持つ人だけが操作できます
- コネクタはアプリケーションとエージェントが、チームが管理する認証情報で外部サービスにアクセスするための仕組みです

**詳細解説**

Vercel の changelog なので短い更新ですが、位置づけを押さえておくと意味が見えてきます。

Vercel Connect のコネクタは、アプリケーションとエージェントが、チームが管理する認証情報を使って外部サービスにアクセスするための仕組みです。今回の更新で、Pro と Enterprise のチームは、誰がコネクタを作成・管理できるかを制御できるようになりました。Owner が Team Settings の Connector Permissions からこの制限を有効にすると、それ以降は Owner ロールを持つ人か、Connector Manager という拡張権限を持つ人だけがコネクタを作成・管理できます。

エージェントが外部サービスに触れる経路が増えるほど、認証情報の管理は「誰がその経路を開けるか」の問題になります。同じ日の Tailscale の記事で出てきた「lethal trifecta」——プライベートデータを読め、読んだ内容に基づいて行動でき、公開インターネットに到達できるエージェントの危険性——を思い出すと、この changelog が何に対処しているかが分かりやすいでしょう。アクセスできる先を増やす機能と、それを誰が増やせるかを絞る機能は、セットで進む必要があります。

チーム規模が大きくなると、コネクタの追加は「便利だから誰でもできる」状態から「影響範囲が読めないので統制が要る」状態に変わります。その移行を、ロールの分離という素直な形で用意した更新です。
