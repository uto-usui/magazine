### [Rendering huge pull requests in the GitHub Copilot app](https://github.blog/engineering/user-experience/rendering-huge-pull-requests-in-the-github-copilot-app/)

> **出典**: GitHub Engineering | **公開日**: 2026-09-23 | **カテゴリ**: engineering

**3行まとめ**
- 2,200ファイル・100万行超の変更・400件超のレビューコメントを持つ PR でも、普通の PR と同じようにスクロールや操作ができるよう、GitHub Copilot アプリの PR 画面を作り直した記録です
- 高さが事前に決まるコード行と、描画してみないと高さが分からないコメントを別々の「ジオメトリ」で管理し、測定は1回のまとまった処理に寄せています
- バグ探しは目視ではなく、アプリ自身に健康状態を答えさせる計測と、無人で回る「変更→計測→改善」のループで進めています

**詳細解説**

出発点は、巨大な差分を描画すること自体はもう解けた問題だ、という整理です。画面に見えている行だけを DOM にマウントして使い回す仮想化を使えば、100万行あっても実際に存在する行は100程度で済みます。コード行はフォントサイズが決まっているので、全行の高さを最初に計算しておけば、スクロールバーの長さも「N行目へジャンプ」もただの足し算になります。記事はこれを「描画前にすべての高さが分かっている」という約束と呼んでいます。

難しいのはコメントです。Markdown の折り返し、`<details>` の開閉、返信欄への入力、画像の読み込みなど、高さは描画してみるまで分からず、描画後も変わり続けます。見積もりの高さで枠を取っておくと、多くのコメントでは余白が空き、長いコメントでは切れたり入れ子のスクロールバーが出たりします。あとから実測値を書き戻すと、その下にあるものがユーザーのスクロール中にすべて動いてしまいます。

そこで高さを2つの領域に分けました。コード部分は従来どおり正確に計算し、コメントがリサイズしても作り直しません。コメントや返信欄は「動的ブロック」として別のインデックスで持ち、ピクセル座標ではなく「ファイル・行・左右のどちらか」で位置を固定します。内容や `<details>` の開閉状態から作った指紋と、測定時の幅（一定の刻みに丸めたもの）も記録しておくので、ウィンドウを少しリサイズしただけで全部の測定が無効になることはありません。

測定の設計で最初に失敗した話がとても参考になります。ブロックごとに `ResizeObserver` を付けて高さを書き戻す方法は、書き戻しが自分自身をもう一度呼び出すフィードバックループになるため、却下しました。採用したのは、スクロールが止まったときだけ動き、ビューポートの前後約2,400pxに限定した1回の測定パスです。オブザーバーは「再測定して」と印を付けるだけで、高さは書きません。ただし、自分で `<details>` を開いたときのように、ユーザー自身が起こした変化だけは同じフレーム内で反映し、1フレームのずれが見えないようにしています。

スクロール位置の補正も、ピクセルではなく「今見ているもの」を基準にしています。補正の前にアンカーとなる行やブロックを記録し、高さを反映したあとで同じアンカーの新しい位置へスクロールし直す流れです。おもしろいのは、「ユーザーがスクロール中なら補正しない」というガードが、サイドバーの開閉にともなう画面自身のスクロールまでユーザー操作と誤認していたバグです。「ユーザーは操作中か？」という判定は、自分の副作用で満たせてはいけない、という一文は、UI の状態判定全般に通じる教訓です。

UXエンジニアリングの視点では、後半の計測の話がいちばん持ち帰りやすいと感じます。「今マウントされている行とブロックの数」「測定の反映が1フレームにまとまっているか」「補正量はどれくらいか」といった問いに、アプリが常に自分で答えられるようにしておき、E2E テストで予算として検証しています。さらに、実アプリを無人で操作し続ける autopilot と、JSON で操作手順を渡せるヘッドレスのプローブを用意し、エージェントがログを読んで原因を追えるようにしました。巨大な PR という極端な題材ですが、フィードやチャットなど、高さが変わる項目が並ぶ画面ならどこでも同じ問題が起きます。後述の CSS Wizardry の記事にある、Safari 27 のスクロールアンカリング対応とあわせて読むと、ブラウザに任せられる範囲と自前で持つ範囲の境目が見えてきます。

### [New Event Ticketing UX Research: 3 Key Takeaways](https://feeds.baymard.com/link/9825/17472042/event-ticketing-ux-research-launch)

> **出典**: Baymard Institute | **公開日**: 2026-09-24 | **カテゴリ**: ux-research

**3行まとめ**
- Baymard が米英のチケット販売サイト（Ticketmaster、StubHub、劇場やホールなど）を対象に463セッションのユーザビリティテストを実施し、370件超のガイドラインにまとめた新しい調査の概要です
- 問題の中心は、総額・空席状況・座席からの見え方といった判断材料が、購入フローの深い段階まで隠されていることでした
- 返品できない「未来の体験」を買うチケット購入は、比較で決める物販とは違い、確信が持てるかどうかで決まる買い物だと位置づけています

**詳細解説**

この調査の前提になっているのが、チケットは返品できる商品ではなく、取り消せない未来の体験だという見方です。行ってみてだめだった場合、失うのはお金だけでなく、時間と気持ちも戻りません。そのためユーザーは信頼が低く不安が高い状態でサイトに来て、決める前にできるだけ多くの確証を求めます。物販がスペック比較で決まる「コンバージョン駆動」なら、体験の購入は「確信駆動」で、ためらいを前提に設計する必要がある、という整理です。

1つめの問題は価格の不透明さです。公演日の一覧に価格がなく、座席選択の画面まで進まないと値段が分からないサイトでは、「値段も分からないのに Buy Now を押すわけがない」という声が出ています。Fox Theatre の事例では、2席で360ドルを選んだあと、カートでチケット手数料75ドル、駐車料金、注文手数料5ドルが一気に加算され、参加者はその場で離脱しました。「手数料を足したいなら最初から価格に含めて」という発言は、そのまま設計の指針として読めます。

2つめは、条件による絞り込みの遅さと、売り切れ表示の欠如です。一覧では売り切れが分からないまま詳細まで進み、そこで「チケットはありません」と言われる。並んで座りたいグループに枚数を先に聞かないので、座席表を開くたびに、ばらばらの1席しか残っていないことを知る。Barbican の事例では、2つの公演でこれを繰り返して約4分かかり、参加者は別の公演を探し始めました。

3つめは、座席の位置と見え方を確かめるための操作コストです。セクションをクリックしても一覧が絞り込まれない静的な座席図や、選んだチケットの物理的な位置が示されない画面が、ユーザーを迷わせています。座席からの眺めの写真がないと、ユーザーはサイトを離れて外部で会場の写真を探しに行きます。逆に Gametime のように、会場マップ上の価格ピンにホバーすると座席からの眺めが出る設計は、「ページを離れずに全部判断できる」と高く評価されていました。

UXエンジニアリングの視点でおもしろいのは、3つの問題がどれも「情報を出す順番」の問題だという点です。価格、枚数、売り切れ、視界は、どれもサイトがすでに持っているデータです。それを早い段階で出せるかどうかは、API の設計やデータを取ってくるタイミングで決まることが多いでしょう。一覧画面で在庫や最低価格を返すにはバックエンドの負荷や在庫の鮮度の問題があり、それを避けた結果が「深い階層まで行かないと分からない」UI になっている可能性もあります。なお、この記事は有料の調査レポートの告知で、ガイドラインの詳細は購読者向けです。チケット販売に限らず、予約や旅行のように「取り消しにくい体験」を売るサービスには、同じ原則がそのまま当てはまりそうです。

### [When Should You Disclose AI Use? The PACED Framework](https://www.nngroup.com/articles/disclose-ai-paced/)

> **出典**: Nielsen Norman Group | **公開日**: 2026-09-25 | **カテゴリ**: design

**3行まとめ**
- AI を使って作った文章に「AI を使いました」と開示したとき、読み手の反応がどう変わるかを、複数の研究からまとめた記事です
- 開示がいつも信頼を下げるわけではなく、AI の役割と関与の度合い、人間らしさが求められる文脈かどうか、読み手の態度によって反応は変わります
- 開示するかどうかを判断するための5つの観点を、PACED（Policy、Audience、Context、Expectations、Degree）としてまとめています

**詳細解説**

背景には、EU の AI 法による透明性の義務が2026年8月に始まったことがあります。開示が法的に求められる場面が増える一方で、開示すると読み手の信頼や評価が下がるのでは、という心配は多くの現場にあるでしょう。記事は、その心配が半分当たっていて半分外れていることを、研究を引きながら示しています。

まず、開示の効果は一貫していません。ニュースに関する47本の研究をまとめたレビューでは、ニュースの種類や媒体の信頼性、読者によって結果はばらばらでした。実際のお金がかかる信頼ゲームの実験では、メッセージに「AI 支援」と付けても、相手に送る金額にも信頼の評価にも変化はありませんでした。一方で、AI が「生成した」と伝えると評価が下がり、「編集しただけ」だと影響が小さくなる、AI が関与した割合が大きいほど著者の評価が下がる、という結果も出ています。

反応が厳しくなるのは、人間の貢献が価値の中心にある文脈です。お礼状や個人的な手紙のような対人的な文章、創作、ブランドの SNS 投稿などでは、開示によって信頼性や本物らしさの評価が下がりました。読み手の側の要因もあり、テクノロジーに好意的な人ほど減点は小さく、自分の文章に自信がある人ほど厳しくなる傾向があります。

おもしろいのが「開示のパラドックス」です。読み手は開示してほしいと言いながら、開示された文章を低く評価します。さらに、人は他人の AI 利用は知らされたいけれど、自分の利用は開示したくない、という非対称もありました。ただし、黙っていればいいわけではありません。何も言わなかった場合は開示した場合より信頼がやや高かったものの、第三者に AI の利用を指摘された場合がもっとも信頼を失いました。あとで露見する可能性があるなら、先に自分から開示するほうが安全だ、という結論です。

UXエンジニアリングの視点では、この記事は「開示の UI をどう作るか」の手前にある判断材料として役立ちます。記事の冒頭では、SNS のピル型ラベル、記事末尾のカード、Google Docs が自動で付ける「この部分は AI の文章に似ています」という表示など、開示の形がいくつか紹介されています。機械が読み取る透かしと、人の目やスクリーンリーダーで読める開示は別のものだ、という区別も、実装のときに押さえておきたいところです。一方で、ここで扱われているのは文章だけで、評価の多くはアンケートによる態度指標です。画像や音声、UI の中の AI 機能そのものについては、別に考える必要があるでしょう。

### [Improving site performance by shipping more CSS](https://github.blog/engineering/architecture-optimization/improving-site-performance-by-shipping-more-css/)

> **出典**: GitHub Engineering | **公開日**: 2026-09-25 | **カテゴリ**: engineering

**3行まとめ**
- GitHub のデザインシステム Primer と GitHub 本体が、CSS-in-JS（styled-components）から CSS Modules へ移行した約3年間の記録です
- Primer のコンポーネントの移行で、サーバーサイドレンダリングの時間が55%、コンポーネントの初期化時間が25%短くなりました
- 最大で約7,760個あった `sx` prop の移行は、後半に Copilot のコーディングエージェントを使い、2人で3週間のうちに残り895個をゼロにしています

**詳細解説**

2023年ごろ、1ページあたりのコンポーネント数が急に増え、CSS-in-JS のコストが目立ってきました。クライアントでスタイルを初期化するための初回表示の遅れ、サーバー側でスタイルを集めるための SSR の劣化、コンポーネント数に比例して重くなるスタイルの更新、の3つです。Primer チームは、ランタイムを持たず、ネイティブの CSS を書けて、クラス名がローカルに閉じる CSS Modules を選びました。

移行の進め方は、壊さないことを最優先にした堅実なものです。コンポーネントごとに CSS Modules 版のファイルを追加し、フィーチャーフラグで新旧を切り替え、既存のビジュアルリグレッションテストでスナップショットが一致することを確かめ、チーム、社員、全ユーザーの順に段階的に展開しました。2024年12月に、Primer の全コンポーネントの移行が終わっています。

難しかったのは、GitHub 本体に大量にあった `sx` prop です。インラインのオブジェクトでなんでも上書きできる `sx` は、デザイントークンと連携した型補完が効く便利なものでしたが、動的な性質のせいで実行時のコストが大きく、使う箇所が増えるほど重くなりました。移行のあいだは `@primer/styled-react` というラッパーの層を用意し、`sx` を使い続けている箇所はそちらから、使っていない箇所は新しい `@primer/react` から読み込めるようにしています。

`sx` の移行は2025年4月に始まり、VS Code の拡張機能と社内の codemod で大半を機械的に変換しながら、8人のローテーションで6か月かけて6,419個を移しました。ページによっては SSR の時間が1%から最大22%改善しています。2026年4月に作業を再開したときには状況が変わっていて、残りの895個を、2人のエンジニアと多数の Copilot コーディングエージェントで3週間のうちにゼロにしました。そのあとも7種類のテーマとハイコントラストモードの切り替えが styled-components に依存していたので、同じ手順で切り離し、2026年6月に100% CSS Modules になっています。

UXエンジニアリングの視点では、デザインシステムが「大規模な変更を安全に配る仕組み」として働いた事例として読めます。コンポーネントの内部実装を差し替えれば、利用側のコードに触れずに多くの画面が速くなるのは、デザインシステムならではの強みです。一方で、`sx` のような「なんでも上書きできる逃げ道」は、便利さと引き換えに数年分の移行コストを生みました。今週の React Status で紹介されている「Props Are Not a Design System」ともつながる話で、任意のスタイル props をどこまで許すかは、デザインシステムの設計でいちど立ち止まって考えたいところです。タイトルの「CSS を多く送る」は、JS のランタイムを減らし、そのぶん静的な CSS に寄せた、という意味です。

### [Design Engineering with Maggie Appleton](https://newsletter.pragmaticengineer.com/p/design-engineering-with-maggie-appleton)

> **出典**: The Pragmatic Engineer | **公開日**: 2026-09-23 | **カテゴリ**: engineering

**3行まとめ**
- GitHub Next のスタッフリサーチエンジニアで、デザインエンジニアとして知られる Maggie Appleton が、Pragmatic Engineer のポッドキャストで仕事の進め方を語った回の要約です
- 手描きのノートから始めることや、スライダーやカラーピッカー付きのプロトタイプ「ジグ（jig）」をエージェントに作らせ、自分専用の Figma のように使っていることが紹介されています
- 質問攻めの計画づくりで判断が鈍ることや、前日にできたことが翌日できない「capability gaslighting」など、AI と働くときの落とし穴にも触れています

**詳細解説**

Maggie Appleton は文化人類学を学び、開発者教育サービスの Egghead でイラストレーターとして React のチュートリアルを描くなかで、フロントエンドを身につけたという経歴の持ち主です。AI スタートアップ Elicit の最初のデザイナーを経て、今は GitHub Next で、エンジニアと AI の新しい協働の形をプロトタイプで探っています。記事は、約1時間半の対談から11のポイントを抜き出したものです。

最初に印象に残るのは、ChatGPT の公開前、2021年の失敗談です。LLM で科学研究を速くする新しい UI として、無限キャンバスにカードを並べる形や、Notion のように組み立てられるドキュメントを数か月かけて作ったものの、研究者が求めていたのは慣れ親しんだシンプルな表でした。新しいことに挑むときでも、なじみのある基本の要素から始めるのが賢い、という教訓です。

仕事の道具としては、まず紙のノートがあります。アイデアはスケッチするほうが Claude Code に説明するより速く、翌日もそこに残っている、というのが理由です。そして「ジグ」です。木工で特定の作業を助ける治具にちなんだ名前で、色やサイズ、アニメーションの速度をスライダーで調整できるプロトタイプをコーディングエージェントに作らせ、その場でいじりながら決めていきます。プロトタイプの段階では生成されたコードを読まなくなり、何を作るか決まったら、エージェントが自分の作業をどう検証するかまで書いた詳しい仕様を渡しているそうです。

AI との協働の課題として挙げられているのが、計画づくりの体験の悪さです。エージェントが A・B・C の選択肢を何十回も聞いてくると、20問目あたりで疲れて考えられなくなり、推奨された A をそのまま選ぶようになってしまう。もう1つが「capability gaslighting」という造語で、最先端のモデルが専門家のように振る舞ったかと思えば、翌日には同じタスクで大きく失敗し、それでもユーザーは「このモデルはできるはず」と信じ続けてしまう現象を指しています。

UXエンジニアリングの視点では、ジグの考え方がすぐに試せて効果も大きいと感じます。値を言葉で伝えてやり直してもらうより、つまみを用意してもらって自分で触るほうが速い場面は多く、後述の Three.js Conf で Bruno Simon が挙げた「画面上で数値を調整してすぐ試す」という鉄則とも重なります。エージェントがいる重みやスキルや MCP の世界と、人間の手触りや光や素材の世界をつなぐ「中間の成果物」が必要だ、という問題提起は、デザインツールの次の形を考えるヒントになります。ただし、記事は対談の要約なので、それぞれの論点を深く知りたい場合はポッドキャスト本編を聞く必要があります。

### [I gave my website a boss fight](https://www.paulbakaus.com/i-gave-my-website-a-boss-fight/)

> **出典**: Sidebar | **公開日**: 2026-09-24 | **カテゴリ**: design

**3行まとめ**
- Impeccable の作者 Paul Bakaus が、個人サイトを Claude Code と10日間で作り直し、ボス戦まであるピクセルアートの世界にした制作記です
- Amiga の4,096色パレット、整数倍の拡大、ディザリングといった具体的な制約を決めたことで、AI とやり取りを重ねても見た目がぶれにくくなりました
- 派手な演出をしながらも、テキストは本物の HTML のまま、reduced motion に対応、音はユーザーが選ぶまでオフ、とウェブサイトとして使えることを守っています

**詳細解説**

UXエンジニアリングの視点では、今週の Kent C. Dodds の「良いプリミティブを用意する」や、LukeW の「道具より結果を」と同じ流れにある記事だと感じます。ユーザーごとに体験が変わる製品では、「意図したとおりに使われる」という前提を手放し、使われ方を観察し続ける仕組みまで含めて設計することになります。記事は考え方を示すところまでで、どう観察するかの具体策には踏み込んでいません。それでも、良い初期値を選び、それを時間とともに見直す、という指針は多くのプロダクトに当てはまるでしょう。

### [Skip the tools, make the outcomes](https://www.lukew.com/ff/entry.asp?2163)

> **出典**: Sidebar | **公開日**: 2026-09-25 | **カテゴリ**: design

**3行まとめ**
- ソフトウェア業界は長く「道具」を作ってきましたが、AI があれば道具を飛ばして、その道具が生み出すはずだった「結果」を直接届けられる、という提案です

**詳細解説**

Luke Wroblewski は、モバイルファーストやフォーム設計で知られるデザイナーです。この短い記事の問いはシンプルです。今の AI 活用の多くは、見慣れた道具を速く作ることに向いている。けれど道具はもともと目的のための手段で、AI が目的地まで直接連れていけるなら、なぜ道具で止まるのか、というものです。

例として挙げられているのが、2年前に作った AI のニュースルーム Exposit です。裏側では AI エージェントがニュースの収集、執筆、編集をしていましたが、表側は見出しや記事やカテゴリが並ぶ、普通のニュースサイトの形でした。つまり、運営が AI になっただけの「ニュースの道具」を作っていたことになります。

あとから、特定のトピックについて質問すると、最新のニュースや関連する出来事、人物、場所をもとに個別のレポートをまとめる機能を加えたところ、それがすぐに主な使われ方になりました。筆者はこれを「ジャストインタイム・コンテンツ」と呼んでいます。一度書いたものが誰にでも合うことを願うのではなく、組み替えられる素材を用意しておき、その人のその瞬間の必要に合わせて答えを作る、という考え方です。レポートから記事や話題へ深く入っていくこともでき、結果から始めて、必要なら道具に進む流れになっています。

Ask LukeW でも、以前は質問しないと何も得られなかったものを、毎日最新のツイートや記事から「Luke が今考えていること」を自動でまとめ、質問しなくても読めるようにしました。答えから始めて、質問を求めない形です。

UXエンジニアリングの視点では、空の入力欄だけを置いたチャット UI を見直すきっかけとして読めます。ユーザーに「何を聞けばいいか」を考えさせる負担は小さくなく、先に何か役立つものを出しておくのは、空の状態の設計として効果的です。一方で、結果を直接出すことは、ユーザーが自分で探して比べる過程を省くことでもあります。AI チャットはエラーチェックを遠ざける、という NN/g の以前からの指摘と表裏一体の話です。結果を先に出しつつ、元の記事や話題にたどれる道を残しておく Exposit の作り方は、そのバランスをとる1つの答えになっています。

### [State of agent skills](https://vercel.com/blog/state-of-agent-skills)

> **出典**: Vercel | **公開日**: 2026-09-25 | **カテゴリ**: frontend

**3行まとめ**
- Vercel が運営するスキルのレジストリ skills.sh の集計データから、エージェントスキルの市場を分析したレポートです
- 7か月で100万件のスキルが登録され、インストールは約2億8,000万回に達しました（GitHub が100万リポジトリに届くまでは27か月でした）
- 供給は技術系に偏る一方、需要は業務運用や文書作成などに広く分散しており、今後は「誰もが知ること」より「自社だけが知ること」を教えるスキルに価値が移ると見ています

**詳細解説**

スキルは、エージェントに特定の仕事のやり方を教える再利用可能な指示で、ふつうの言葉で書いたファイル1つでも作れます。Anthropic が2025年10月に Agent Skills を発表し、その3か月後に Vercel が skills.sh を立ち上げました。スキルを書くには、手順や「良い」の基準、結果の評価方法といった、仕事の背後にある判断を言葉にする必要があります。このレポートは、それを「専門知識をソフトウェアに変える」と表現しています。

成長の速さは、ほかの登録サービスとの比較で示されています。100万件に届くまで、skills.sh は7か月、GitHub のリポジトリは27か月、App Store のアプリは5年あまり、npm のパッケージは9年以上かかりました。プログラムを書ける人よりも、仕事のやり方を説明できる人のほうがはるかに多いことが、この速さの理由だとしています。

供給と需要のずれもおもしろいところです。登録されているスキルの半分以上は、ソフトウェア開発、エージェントのワークフロー、データ、インフラ、セキュリティといった技術系で、ソフトウェア開発だけで約4分の1を占めます。一方でインストールはもっと分散していて、ソフトウェア開発が18%、エージェントのワークフローが15%、業務運用と文書作成がそれぞれ約11%です。1件あたりのインストール数で見ると、業務運用は平均より74%、文書作成は50%多く、逆にソフトウェア開発は約30%少なくなっています。

分布の偏りも大きく、半数近くのスキルは1回しかインストールされておらず、上位375件（全体の0.04%）がインストールの62%を占めます。それでも、もっとも多いスキルでも全体の1%未満で、1つの勝者が独占しているわけではありません。仕事ごとに勝者が決まり、それらを組み合わせて使う構造です。業界をまたいで使えるスキルは、業界固有のものより1件あたり3.6倍多くインストールされています。

UXエンジニアリングの視点では、「次の100万件は、あなたのエージェントにあなただけが知ることを教える」という予測が、実務にいちばん近い話です。デザインシステムの使い方、アクセシビリティの社内基準、レビューの観点など、チームごとの判断をスキルとして書き出し、コードと同じように保守していく流れは、すでに多くの現場で始まっています。スキルの価値を測る基準が人気から効果へ移り、使った場合と使わない場合の差をテストで測るようになる、という見通しにも納得感があります。ただし、これは skills.sh を運営する Vercel 自身のレポートで、インストール数は重複を含む集計値だと本文にも注記されています。

### [I don’t want the details](https://michaelheap.com/i-dont-want-the-details/)

> **出典**: Sidebar | **公開日**: 2026-09-25 | **カテゴリ**: design

**3行まとめ**
- 障害のあと、経緯を説明しようとした筆者に、SVP が「詳細はいらない。何を変えるのかを知りたい」と返したエピソードから始まる、ポストモーテムについての短いエッセイです
- 良い説明は修正ではなく、全員の判断が妥当だったと納得した時点で、変えようとする動機が消えてしまうことがある、と指摘しています
- 「なぜ起きたか」ではなく「同じ種類の失敗を起こりにくくするために何を変えるか」を問うよう、すすめています

**詳細解説**

筆者は、重大ではないものの起きてはいけない問題のあと、SVP との通話に呼ばれました。経緯を話し始めたところで遮られ、「詳細を聞けば理由はきっと妥当で、私はみんなの判断を理解して共感する。そしてまた同じことが起きる」と言われます。最初は突き放されたように感じたものの、あとで、それは「あなたたちが有能なことはもう信じている。次の話をしよう」という信頼の表明だったと気づいた、という話です。

多くの組織は、障害のあとに「なぜ起きたか」を問い、タイムラインを書き、判断を再構成し、依存関係を説明します。全員がうなずき、「それなら仕方ない」と納得して終わる。筆者は、理解することと直すことは違い、良い説明がかえって状況を悪くすることもある、と書いています。誰も悪くない不運な出来事の連鎖として片づけられると何も変わらず、半年後に同じことが起きます。

記事では、言い訳を問いに言い換える例が挙げられています。「Alice が休暇中で、Bob は Widgets チームの担当だと思っていた」なら、担当者が不在のときに持ち主をはっきりさせるには？「要件が公開の3日前に変わった」なら、公開直前に要件が変わったときにどうする？「アラートは鳴ったが、担当者はその晩すでに20件の価値の低いアラートに対応していた」なら、アラートの信号と雑音の比をどう改善する？という具合です。変えるのは人ではなく仕組みだ、という立場が一貫しています。

ポストモーテムに「サポートをもっと早く巻き込む」「コミュニケーションを良くする」「次からもっと気をつける」が並んでいたら、それは進歩のふりをした願望の集まりだ、という一文は耳が痛いところです。関係者が明日全員いなくなっても修正は効くか、同じ状況が明日起きたら何が結果を変えるか、と問うようすすめています。ただし、すべての失敗に新しいプロセスを足すと誰も働きたくない職場になるので、防ぐコストのほうが高いなら、承知のうえで失敗を受け入れる選択もある、と釣り合いもとっています。

UXエンジニアリングの視点では、障害対応だけでなく、ユーザビリティテストやデザインレビューで見つかった問題の扱いにもそのまま使える考え方です。「ユーザーが見落とした理由」は説明できても、次のリリースで同じ種類のつまずきが起きにくくなる変更がなければ、調査は記録で終わってしまいます。デザインシステムのコンポーネントや lint、チェックリストのように、人の記憶に頼らない形で学びを残すことが、この記事のいう「仕組みを変える」にあたるのでしょう。なお、「詳細はいらない」は信頼関係がある場での言葉で、原因の分析そのものが不要だという意味ではない点には気をつけたいところです。
