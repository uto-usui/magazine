### [Beyond Generative: The Rise of Agentic AI and User-Centric Design](https://uxdesign.cc/beyond-generative-the-rise-of-agentic-ai-and-user-centric-design-b9ef3a0c8d23)

> **出典**: UX Collective | **公開日**: 2026-01-22 | **カテゴリ**: AI

**3行まとめ**
- AIが「生成」から「自律行動」へと進化し、デザイナーの役割は「体験の設計者」から「意図の翻訳者」へ変化している
- エージェント型AIでは、ユーザーが何を望んでいるかを正確に伝える必要があり、曖昧さを許容するUIが重要になる
- 倫理的な境界線の設定やプライバシー保護が、AIエージェント設計における最重要課題となっている

**詳細解説**

この記事は、AIの次なる進化フェーズである「エージェント型AI」がUXデザインにもたらす影響を包括的に論じています。これまでのAIは主にコンテンツ生成（テキスト、画像、コード）が中心でしたが、エージェント型AIは自律的に判断し、タスクを実行できる点が根本的に異なります。

UXエンジニアリングの観点で注目すべきは、「意図の明確化」という新たな設計課題です。従来のUIはユーザーの操作を受け取り結果を返すものでしたが、エージェント型AIでは「何を達成したいか」という意図を正確に伝える仕組みが必要になります。これはプロンプトエンジニアリングとUIデザインの融合領域といえるでしょう。

記事では、エージェントが自律的に行動する際の「信頼性の可視化」も重要なテーマとして挙げています。AIがどのような判断でどのような行動を取ったのかを、ユーザーが理解・監視できるインターフェースの設計が求められます。これは単なるログ表示ではなく、人間が自然に理解できる形式での透明性確保が課題となります。

- Simon Willisonは映画を観ている間にAIエージェントに9,200件のテストをパスするHTML5パーサーを構築させた
- 成功の鍵は「明確な成功基準」であり、テストスイートが充実している問題ほどAI自動化に適している

**詳細解説**

Drupalの創設者であるDries Buytaertによるこの記事は、AIを活用したソフトウェア開発の新しいパラダイムを「陶芸のろくろ」に例えて説明しています。人間がプロンプトを与え、AIが実装し、テストを実行し、また人間がフィードバックを与える…このサイクルは、まさに粘土を形作る陶芸家の動きに似ているという洞察です。

Geoffrey Huntleyの「Ralph Wiggum Loop」は、各反復で新しいコンテキストから始めることで、長時間の作業でもノイズが蓄積しない仕組みを実現しています。これはLLMのコンテキスト制限を逆手に取った設計であり、状態をファイルシステムに保存することでセッション間の連続性を保っています。

UXエンジニアリングへの示唆として重要なのは、「成功基準の定義」が人間の最も価値ある役割になるという点です。「このページをもっとブランドらしくして」といった曖昧な要求は自動テストできませんが、ブランドガイドラインに基づいた評価をAIに行わせることは可能かもしれません。検証可能な基準をどう設計するかが、今後のUXエンジニアの重要なスキルになりそうです。

### [I Learned the First Rule of ARIA the Hard Way](https://www.youtube.com/watch?v=P3IWVHD6xnk)

> **出典**: Sidebar | **公開日**: 2026-01-22 | **カテゴリ**: design

**3行まとめ**
- ARIAの第一原則は「ネイティブHTML要素で済むなら、ARIAを使うな」である
- 過剰なARIA属性の追加は、スクリーンリーダーユーザーの体験を悪化させることがある
- アクセシビリティ改善は「足し算」ではなく、適切なセマンティックHTMLの選択から始まる

**詳細解説**

アクセシビリティに取り組む開発者が陥りがちな「ARIAの誤用」について解説した動画です。ARIAはアクセシビリティを向上させるためのツールですが、不適切に使用すると逆効果になることがあります。

ARIAの第一原則「No ARIA is better than bad ARIA」は、ネイティブのHTML要素が持つ暗黙のセマンティクスを活用することの重要性を説いています。たとえば、`<button>`要素は自動的にボタンとしての役割（role）とキーボードインタラクションを持っていますが、`<div role="button">`では追加のキーボードイベント処理が必要になります。

UXエンジニアとして重要なのは、アクセシビリティを「追加機能」ではなく「基盤」として捉える視点です。最初から適切なHTML要素を選択し、セマンティックな構造を設計することで、ARIAによる補強が最小限で済みます。

また、アクセシビリティテストでは自動ツールだけでなく、実際のスクリーンリーダーでの確認が重要です。ツールはARIA属性の存在は検出できますが、その属性が実際のユーザー体験を向上させているかは判断できません。

- 長年議論されてきたCSSのMasonryレイアウトが「Grid Lanes」として正式に仕様化された
- `grid-template-rows: masonry`という構文で、PinterestスタイルのレイアウトがネイティブCSSで実現可能に
- Safari 26.2でサポートが開始され、他ブラウザも順次対応予定

**詳細解説**

Pinterestで有名になった「Masonryレイアウト」が、ついにCSS標準として策定されました。これまではJavaScriptライブラリ（Masonry.js、Isotope等）に頼るしかなかったこのレイアウトパターンが、CSSだけで実現できるようになります。

技術的には、CSS Gridの拡張として実装されています。`grid-template-rows: masonry`を指定することで、列方向は固定グリッドを維持しつつ、行方向では要素が自動的に空きスペースを埋めていく動作になります。これにより、異なる高さのコンテンツを美しく配置できます。

UXエンジニアにとって重要な点は、パフォーマンスの向上です。JavaScriptベースのMasonryライブラリは、リサイズやコンテンツ追加のたびに再計算が必要でしたが、ネイティブ実装ではブラウザのレイアウトエンジンが最適化された処理を行います。

ただし、現時点ではブラウザサポートが限定的（Safari 26.2のみ）なため、プロダクション環境での採用には`@supports`によるフォールバック実装が必須です。CSSの進化を追いながら、段階的に導入を検討するのが現実的でしょう。

### [text-decoration-inset is Like Padding for Text Decorations](https://css-tricks.com/text-decoration-inset-is-like-padding-for-text-decorations/)

> **出典**: css-tricks | **公開日**: 2025-12-22 | **カテゴリ**: css

**3行まとめ**
- テキスト装飾（下線など）がテキストの端まで伸びてしまう問題を解決する`text-decoration-inset`プロパティ
- 左右で異なるインセット値を設定可能で、em単位を使えばフォントサイズに連動する
- アニメーションにも対応し、ホバー時に下線が縮む演出などがネイティブCSSで実現可能

**詳細解説**

`text-decoration-inset`は、テキスト装飾の開始・終了位置を制御できる新しいCSSプロパティです。これまでリンクの下線がテキストの端を超えて伸びてしまう問題は、疑似要素でカスタム下線を作るしか解決策がありませんでした。

構文は`text-decoration-inset: <left-inset> <right-inset>`で、左右に異なる値を設定できます。em単位を使用すれば、フォントサイズの変更に自動追従するレスポンシブな実装が可能です。ただし、最初の文字の形状によっては完璧なアライメントにならない場合もあり、内容が分かっている状況での使用が適しています。

UXエンジニアとして注目すべきは、このプロパティがアニメーション対応である点です。ホバー時に`text-decoration-inset`を変化させることで、下線が端から中央に向かって縮むような演出がネイティブCSSだけで実現できます。従来は疑似要素の幅をアニメーションさせる必要があった表現が、より意味的なプロパティで実装できるようになります。

現時点ではFirefox 146以上でのみサポートされていますが、今後の普及が期待される機能です。

### [Future CSS: :drag (and Maybe ::dragged-image?)](https://css-tricks.com/future-css-drag-and-maybe-dragged-image/)

> **出典**: css-tricks | **公開日**: 2026-01-07 | **カテゴリ**: css

**3行まとめ**
- HTML Drag and Drop APIを補完する`:drag`疑似クラスがCSS仕様に提案されている
- 現在はJavaScriptでのクラス切り替えが必要なドラッグ中スタイルが、CSSだけで実現可能に
- ドラッグプレビュー画像をスタイリングする`::drag-image`疑似要素も提案されている

**詳細解説**

現在、要素がドラッグされている状態を検知してスタイルを適用するには、JavaScriptで`dragstart`/`dragend`イベントを監視してクラスを切り替える必要があります。提案されている`:drag`疑似クラスは、この処理をCSSだけで実現することを目指しています。

```css
.menu-bar:drag {
  cursor: grabbing;
  opacity: 0.2;
  scale: 1.2;
}
```

このシンプルな構文で、ドラッグ中のスタイルが定義できます。パフォーマンス向上（JSのイベント処理が不要）、保守性向上（スタイルとロジックの分離）というメリットがあります。

さらに記事の著者は、`::drag-image`疑似要素も提案しています。現在、ドラッグ中に表示されるプレビュー画像をカスタマイズするには`dataTransfer.setDragImage()`を使う必要がありますが、これもCSSで定義できれば実装が簡素化されます。

CSSWGでは`:drag`の議論が予定されており、採用されれば将来のWeb標準となる可能性があります。UXエンジニアとしては、このような提案の動向を追い、フィードバックを通じてWeb標準の発展に貢献することも重要です。

### [Postcard From Web Directions Dev Summit, 2025](https://css-tricks.com/postcard-from-web-directions-dev-summit-2025/)

> **出典**: css-tricks | **公開日**: 2026-01-12 | **カテゴリ**: css

**3行まとめ**
- Web Directions Dev Summit 2025のカンファレンスレポートが、登壇者の視点からエッセイ形式で綴られている
- 「ブラウザのネイティブ機能を活用し、フレームワーク依存を減らすべき」というメッセージが複数の登壇者から発信された
- アクセシビリティの自動テストツールには限界があり、実際のユーザーテストが不可欠という指摘

**詳細解説**

Lee Meyerによるこの記事は、通常のカンファレンスレポートとは異なり、登壇者自身の視点から「意識の流れ」スタイルで書かれたユニークなエッセイです。ステージフライトやインポスター症候群との葛藤も率直に綴られており、技術カンファレンスの人間的な側面が伝わってきます。

技術的な内容としては、Jono Aldersonによる「ブラウザネイティブ機能の再評価」が印象的です。ReactなどのフレームワークをRube Goldberg machine（複雑すぎる装置）に例え、もはや存在しない制約のために複雑さを維持していると指摘しています。LLMがReactのコードで大量に訓練されているため、AIがネイティブ機能よりもフレームワークを推奨しがちという問題も提起されています。

Beau Vassによるアクセシビリティの講演も重要な視点を提供しています。自動テストツールは「問題でないものをフラグ付けし、重要な問題を見逃す」ことがあり、Lighthouseのスコアを目標にすること自体が問題だと指摘しています。AIはアクセシビリティを「解決」しませんが、スクリーンリーダーユーザーがどのようにタスクを完了しようとするかをシミュレートする用途では有用かもしれません。
