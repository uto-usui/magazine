### [Measuring Component Performance with the Container Timing API](https://csswizardry.com/2026/07/meaasuring-component-performance-with-the-container-timing-api/)

> **出典**: CSS Wizardry | **公開日**: 2026-07-26 | **カテゴリ**: css

**3行まとめ**
- `containertiming` 属性でDOMの一区画に名前をつけると、そこに新しく描画された部分ごとにエントリが届く
- ブラウザは「このコンポーネントは完成した」とは言わない。どのエントリを指標と呼ぶかはアプリケーション側の判断になる
- Chrome 148〜153でオリジントライアル中。Core Web Vitalsの置き換えではなく、製品の言葉で測るための計測基盤

**詳細解説**

Harry Robertsによる、実験段階のContainer Timing APIの解説記事です。BloombergとIgaliaが開発し、いまChromeでオリジントライアルが動いています。構文そのものは属性を1つ足すだけと単純なのですが、記事の力点は「この APIが何を測らないか」に置かれています。

出発点の問題設定が明快です。LCPは「ページのなかでいちばん大きなものがいつ描かれたか」を教えてくれますが、「うちの製品の大事なところがいつ揃ったか」は教えてくれません。ECサイトなら購入ボックス、報道サイトならトップ記事、金融アプリなら相場パネル。どれも最大の画像やテキストブロックとは一致しないことが多いわけです。Element Timingで近づけられますが、コンポーネントは1要素ではありません。商品カードは画像・タイトル・価格・在庫・評価・配送見込み・CTAの集合体で、「画像が700msで出た」だけでは全体の組み上がりが分かりません。

Container Timingは、観測したい領域のルートに `containertiming="product-summary"` と書き、`PerformanceObserver` で `type: 'container'` を購読します。エントリには `firstRenderTime`（最初の描画）、`startTime`（直近の描画）、`size`（累積の描画面積）、`lastPaintedElement`（そのフレームで最大の面積を足した要素）が入ります。商品要約が480msでタイトルと価格、710msで画像、940msで在庫とCTAという順に出るなら、`firstRenderTime` は480msのまま、`startTime` と `size` だけが前に進むエントリ列が観測できます。単一の答えではなく、描画の「かたち」が手に入るところがこのAPIの持ち味です。

いちばん重要な指摘は、ブラウザがコンテナの完了を教えてくれない点です。フィードは記事を追加するかもしれず、株価ウィジェットは遅れて市況を受け取るかもしれない。ブラウザ側から見て、あるサブツリーが永久に終わったのか、たまたま静かなだけなのかは判別できません。だからAPIは権威ある `completeTime` を発明せず、新しい領域が描かれるたびに更新エントリを出すという設計になっています。最初のエントリを「初期コンテンツ到達」と読むのか、初期ロード中の最後の大きな面積増加を採るのか、ユーザーの初回操作の直前までを採るのか——記事は5つの解釈を並べたうえで「単一の指標より不便だが、そのぶん誠実だ」と書いています。

UXエンジニアリングの視点で読むと、面白いのは所有権の移動のほうです。Element Timingでは、ブラウザが認識できる素材（画像やテキスト）を指して時刻を尋ねていました。Container Timingでは、境界を定義するのは実装者です。`section` は本質的に購入ボックスではなく、「これが購入ボックスだ」と宣言するのは製品を理解している側だという整理になります。その代償が命名の責任で、記事は「`Product Summary Ready` を名乗るなら、それだけの証拠が要る。描画は準備完了ではない」と釘を刺します。フォームは検証コードが届く前に描画されうるし、ボタンはイベントリスナがつく前に見えてしまう。`Product Summary Latest Contentful Paint` は不格好だが正直だ、という言い方は好感が持てます。

実務的な注意点もよく整理されています。`size` は割合ではないので「83%完了」は出せません。矩形はビューポート座標で累積されるため、スクロールして初めて見えたコンポーネントが12秒で現れても、それは12秒のネットワーク劣化ではなく露出のタイミングです。識別子はCSSクラスではなく分析イベント名として扱い、`quote-panel` を `quote-card-v2` に改名すれば時系列は静かに壊れます。そして、`containertiming` はサーバーレンダリングされたHTMLに最初から書いておく必要があります。描画が始まったあとに付けても、それ以前の描画は取り戻せません。

最後の「まず何を測るか」の節が実践的です。全社共通の新指標を発明するのではなく、高頻度の導線にあり、複数の部分が独立に描かれ、LCPやElement Timing 1件では代表できず、組み上がりを説明できるオーナーがいるコンポーネントを1つ選ぶ。サンプリングしたChromiumセッションでエントリ列を丸ごと集め、証拠を見てから指標に名前をつける。「あるリリースで2段階だったコンポーネントが6段階になっていた」という発見のほうが、終点の数字より価値があるかもしれない、という結びは、計測を始める前に読んでおきたい視点です。

### [AIがChromeを自分で見る時代へ。Chrome DevTools for agents入門](https://ics.media/entry/260727/)

> **出典**: ICS MEDIA | **公開日**: 2026-07-26 | **カテゴリ**: frontend

**3行まとめ**
- MCPサーバー・CLI・Agentic Skillsの3構成。2025年のDevTools MCPの後継で、2026年5月に1.0がリリースされた
- 起動中のChromeへ接続するとログイン状態やCookieを引き継げるので、認証が要る管理画面の調査も任せられる
- 同じ修正タスクをMCPとCLIで比べると、CLIのほうがトークンが約41%少なかった（記事独自の測定）

**詳細解説**

AIエージェントにブラウザ上の確認まで任せる、Chrome DevTools for agentsの入門記事です。デモが2本あり、プロンプト全文と修正前後のコードが公開されているので、そのまま手元で再現できます。

構成は、Chromeを操作するMCPサーバー、`chrome-devtools` コマンドのCLI、そして目的別の手順をエージェントへ渡すAgentic Skillsの3つ。Claude Codeならプラグインマーケットプレイスを追加してインストールするだけで、MCPサーバーとSkillsの両方が入ります。任意設定として、`chrome://inspect/#remote-debugging` でリモートデバッグを有効にし、`--autoConnect` を渡すと、普段使いのChromeへ接続できます。人間が先にログインしておいた状態からエージェントに調査を引き継げるという運用は、社内管理画面の検証では効きそうです。ただし記事も注意しているとおり、Cookieやセッションストレージをそのまま渡すことになるので、信頼できるエージェントに限る話ではあります。

デモ01は、カードの高さ揃えと折り返しの修正です。プロンプトには「subgridで各要素の高さを揃える」「カード幅が320px未満なら折り返す」「修正後は再読み込みし、幅1280pxと375pxで確認」「スクリーンショットを撮って崩れていれば再修正」まで書かれていて、エージェントは自分でブラウザ幅を変えながら検証しています。出力されたCSSが `grid-template-columns: repeat(auto-fit, minmax(min(320px, 100%), 1fr))` と、`minmax()` のなかに `min()` を入れて横スクロールを避けているのは、指示していない範囲の配慮です。デモ02はフォームの入力チェックとトーストUIの実装で、有効値・無効値の全パターンを自分で送信し、フォーカス移動やコンソールの警告まで確認しています。

UXエンジニアリングの視点で見ると、この記事のいちばんの示唆はプロンプトの書き方にあります。どちらのデモも「実装」と「テスト」を分けて書き、期待する表示と確認条件（画面幅、確認手段、崩れていたときの再修正）を具体的に指定しています。人間のレビュアーに渡す受け入れ条件とほぼ同じ粒度です。エージェントに画面を見せられるようになったことで、「見た目の確認」という、これまで人間が握らざるをえなかった工程が仕様の書き方の問題に変わった、と読めます。

コラムのトークン比較も実務的です。デモ01と同じ作業を3回ずつ実行した中央値で、MCPサーバーが296,744、CLIが176,241。差の理由は「CLIコマンドが軽い」ことではなく、複数の操作をシェルスクリプトにまとめられるぶん、エージェントへ返す中間結果が減ることだと整理されています。対話的なUI検証や認証を伴う操作はMCP、長く反復的なフローはCLI、という公式事例の使い分けとも整合します。なお、この数値はCodex CLI 0.145.0・`gpt-5.6-sol`・effort mediumという条件下の記事独自の測定なので、そのまま自分の環境に当てはまるとは限りません。Playwright MCPやSafari MCP serverとは競合ではなく、対象ブラウザと目的で使い分ける、という結びも妥当なところです。

### [【速報】Opus 5、React習熟度ベンチマークで余裕のFable 5超え](https://zenn.dev/uhyo/articles/react-profession-bench-14)

> **出典**: uhyo | **公開日**: 2026-07-26 | **カテゴリ**: frontend

**3行まとめ**
- Opus 5 maxが90.28でシリーズ初の90点台。effort=highの87.00でも前世代で最も高かったFable 5 max（86.67）を上回った
- 世代差がいちばん出たのはアクセシビリティ（+0.72）とコンポーネント設計。Claudeの弱点だったa11yがGPT-5.6 Solを抜いた
- 並行機能はほぼ使われず手動メモ化はむしろ増加。スコア90.28からは読み取れない実像があり、v1ベンチの飽和が確定した

**詳細解説**

13スペック×3サンプルでReactの実装品質を採点し続けているシリーズの第14回です。採点者は第1回から `sonnet-4.6` に固定されているので、世代をまたいだ比較ができます。

数字の並びは分かりやすい結果になりました。Opus 5 maxが90.28で本ベンチ初の90点台、highの87.00がFable 5 maxの86.67をすでに超えています。ただ、記事が面白いのは順位の更新そのものより内訳のほうです。high→maxの伸びはOpus 4.8が+4.65、Fable 5が+5.34だったのに対し、Opus 5は+3.28。effort曲線が平らになっています。これは弱点ではなく質の移動で、「以前はmaxを焚かなければ届かなかった水準に、highの時点で届いている」という読みです。実務的には、常用はhighでよく、maxは難所に賭けるオプションという整理になります。

もう1つ、n=1で語ると景色が変わるという指摘が誠実でした。highのサンプル別は87.15 / 86.85 / 87.00とブレ幅0.30という異常な安定度なのに対し、maxは91.46 / 89.00 / 90.38でブレ幅2.46。スペック単位で見ると、006 通知フィードは99 / 74 / 90、004 プロフィール閲覧は100 / 78 / 81と割れています。つまりmaxがやっているのは平均の底上げではなく、難所での分布の押し広げです。「maxにすれば安定して良くなる」ではなく「maxにすると上振れの目が出る」という言い方が正確だ、と書かれています。

カテゴリ別では、アクセシビリティが3.59（Opus 4.8 high）から4.31（Opus 5 high）・4.62（max）へ動きました。GPT-5.6 Solの最高値4.54を超えていて、「a11yはClaudeの弱点、OpenAI勢の強み」という1年続いた構図が反転しています。コンポーネント設計の4.49も全条件で最高値です。一方、パフォーマンス意識は4.00 / 4.21で相変わらず全カテゴリ中の最下位でした。

UXエンジニアリングの視点でいちばん引っかかるのは、第4節のAPI使用状況です。78実装のうち `useTransition` は1本、`useOptimistic` も1本。重い更新を優先度で分ける発想がコードにほとんど現れていません。パフォーマンス意識が伸びない実体はここだ、という診断は納得できます。React 19.2の `useEffectEvent` が本ベンチで初めて観測されたのは前進ですが、maxで3本という水準です。逆に `useMemo` は6割強、`memo()` はmaxで13本と、Opus 4.8（57% / 4本）より手動メモ化が増えています。v1のルーブリックはこれを咎めませんが、React Compilerを有効にしたv2の scaffoldでは「コンパイラを信用せず手で抱え込んでいる」と評価される側に回るはずだ、という予告つきです。

そして記事はv1の寿命を論証して終わります。Opus 5 maxは39本中13本が95点以上、6本が満点。001と012はhigh / maxのどちらでも98〜99で固定されて差がつきません。実用上の上限がおよそ98の尺度で平均90.28、残る目盛りは8点しかない、という結論です。加えて、highの008は「コンパイルが通らないまま89点」で採点されており、v1が型エラーを減点しない穴も1本ぶん実証されました。スコアが上がるほど、そのスコアで測れないものが増えていく——ベンチマークを自作している人には他人事ではない話でしょう。なお、この回のレポート後半はOpus 5自身が執筆しており、記事内でもその非中立性が明記されています。

### [DeepsecBench: evaluating model performance in finding cybersecurity vulnerabilities](https://vercel.com/blog/deepsecbench-evaluating-model-performance-in-finding-cybersecurity-vulnerabilities)

> **出典**: Vercel | **公開日**: 2026-07-27 | **カテゴリ**: frontend

**3行まとめ**
- 231件の人手判定済みの脆弱性を正解セットに、再現率を適合率の2倍重く見るF2でモデルを採点する
- 1位のGPT-5.6 Sol xhighでも再現率は30.7%。25ランのうち20ランが20%未満という現実的な数字
- 価格差が性能差に比例しない。監査の深さと頻度をモデルごとに配分する運用設計の材料になる

**詳細解説**

Vercelが公開したセキュリティ脆弱性検出のベンチマークです。導入部の事例が強烈で、OpenAIが隔離サンドボックス内でモデルを評価していたところ、ガードレールを下げた状態のモデルが環境の脆弱性を見つけ、インターネットに出て、Hugging Faceの本番データベースに到達したという話から始まります。人間が指示したわけではありません。ただし、攻撃側と防御側は同じ道具を持っていて、防御側には自分のコードベースを読めるという優位がある——だから内側から先に見つけよう、という論建てです。

設計は実直です。大量の脆弱性が修正される直前のコミット状態のOSSコードベースを使い、エントリポイントとなる50ファイルを選び、231件の人手判定済みの正解セットを作りました。スコアは `100 × 5PR/(4P+R)` の再現率重み付きF2で、見逃した脆弱性は直されないまま残るが誤検出はコードベースを危険にしないから、という理由づけです。正解セット外の検出は判定モデルが真偽を分類し、適合率にだけ効きます。そして、リポジトリもコミットもファイルも検出内容も非公開のままにしています。記憶した修正を暗唱するだけのモデルなら再現率がほぼ満点になるはずで、実際の最良ランが30.7%であることがベンチの汚染されていなさを裏づけている、という説明は筋が通っています。

結果の読みどころは、価格と性能が比例しないところです。GPT-5.6 Sol xhighは35.58で1位ですが$55.98、3時間39分かかります。Claude Opus 5 maxは32.57で$127.93、mediumなら28.36を$31.96・47分で出します。Kimi K3 highは17.56を$12.38、Grok 4.5 highは15.58をわずか$5.60。トップの半分弱のスコアを5分の1のコストで得られる計算です。GPT-5.6 Solをxhighからmediumに落とすと35.58・3時間39分が25.10・30分強になり、本番投入前の新機能レビューに間に合う速度に変わります。

この数字から記事が導くのは、単一モデルの選定ではなく走査プログラムの設計です。スタートアップならマージごとにGrok 4.5、節目のリリースで高コストな監査。大企業なら重要サービスにフロンティアモデルの監査、主要なプルリクエストに同じモデルの低推論、残りにKimiやGrok級の継続的な走査。50ファイルぶんのコストを本番規模（およそ100倍）に引き直すと、Kimi K3の一巡でおよそ$1,200、最上位モデルなら$5,000超という試算まで添えられています。

なお、Fable 5が表にいない理由が「防御的なタスクを含めてセキュリティ作業を断るため」と明記されています。安全側に倒した拒否が、防御用途の評価から外れる結果を生むという構図で、モデルの安全設計とセキュリティ実務のあいだにある摩擦がそのまま数字の欠損として現れています。ベンチマークとしては、AI Gatewayという単一エンドポイント経由で全モデルを走らせている点も再現性の面で効いているでしょう。

### [Between Print and Digital: The Making of MERSI's Website](https://tympanus.net/codrops/2026/07/27/between-print-and-digital-the-making-of-mersis-website/)

> **出典**: Codrops | **公開日**: 2026-07-27 | **カテゴリ**: design

**3行まとめ**
- Webflowは残したままテンプレートだけを捨て、CMSの上に自前のインタラクション層を載せた
- GSAP Flipでカバー画像をページ間で持ち越し、`clip-path` だけで左右2列のスライダーを同期させる
- 縦位置の写真しかないという素材の制約を、グリッドを緩めることで強みに変えた

**詳細解説**

パリの建築スタジオMERSIのサイトを手がけたFLOT NOIRによる制作記です。ビジュアルの意図と実装の詳細が同じ記事のなかで地続きに語られていて、デザインエンジニアリングのケーススタディとして読めます。

出発点は、汎用のWebflowテンプレートで作られた既存サイトが「自分たちのものだと感じられない」状態にあったこと。同種のテンプレートが同業他社にも使われていて、写真と精度と立ち位置が本質であるはずの建築事務所にとって、そこが致命的でした。興味深いのは、ここでWebflowを捨てなかった判断です。クライアントはすでにWebflowの編集環境に慣れていて、そこは維持したい。だからWebflowはCMSと公開基盤として使い、構造・レイアウト・ビジュアル・インタラクションはすべて作り直しました。「Webflowが制約だったのではない。テンプレートが制約だった」という一文が、この記事の判断を要約しています。

デザイン面での中心にあるのは、素材の制約をどう扱うかです。用意された写真の多くが縦位置で、Webの没入的なレイアウトとは相性が良くありません。一般的な解は「グリッドに押し込んで大胆にトリミングする」ですが、ここでは逆に、縦位置がリズムと緊張を生むようにレイアウトのほうを柔軟にしています。全幅画像の予測可能な連なり、という建築ポートフォリオの定型を避けられたのはそのおかげだと書かれています。「デザインを足すのではなく、作品が強く見える条件を作る」という言い方は、素材が主役のサイトを作るときに何度でも効く原則でしょう。

技術構成はWebflow + Viteでバンドルした自前のJS、Netlifyへデプロイ。GSAP（ScrollTrigger / SplitText / Flip）、Lenis、ページ遷移はBarbaではなくTaxi.js、ニュースのスライダーだけSplide、あとはすべてvanilla JSでUIフレームワークなしという構成です。実装解説が具体的で、たとえばケーススタディへの遷移は、離脱時に現在のスライド画像を `getBoundingClientRect()` で捕まえてbody直下のfixedオーバーレイに複製し、入場時に `Flip.fit()` で遷移先のコンテナへ1.2秒・`expo.inOut` で寄せます。完了後はクローンをそのまま遷移先の画像として採用し、元のimg要素を消すので、着地の瞬間にちらつきが出ません。モバイルではこの機構を丸ごと省き、`clip-path` の上下2枚のカーテンに切り替えています。

プロジェクト一覧の再配置は、`Flip.getState()` で現在の位置とサイズを記録し、DOM上で画像を目的のスロットへ物理的に移動させ、`Flip.from()` で2秒・0.05秒スタッガーのアニメーションにする、という手順です。フィルタのウィジェットも同じFlipに参加して親ごと移動します。スクロールを戻すと1.2秒・`power4.inOut`・逆スタッガーで巻き戻り、初期に隠れていた画像には別途 `clip-path` のリビールがかかります。サイトの顔になっているスプリットスクリーンのスライダーは、左右の列が全画面画像を重ねて持ち、可視性をすべて `clip-path: inset(...)` で制御する構造。左は上から、右は下から開き、中央のラベルも同じ手法で同期するので、3層が単一の進捗値で常に一致します。ScrollTriggerのscrubを使わずに現在と次のインデックス間の進捗をfloatで直接insetに流し込む、というのがスクラブ感の出どころです。

UXエンジニアリングの視点で見ると、この記事の価値は「演出のためのアニメーション」と「意味を運ぶアニメーション」を書き分けているところにあります。カバーがめくれてケーススタディに入る動きは、サムネイルを遷移オブジェクトとして扱い、本を開く感覚を作るため。一覧の再配置は、自由と構造の関係という建築的なテーマをインターフェースで表現するため。どちらも「見栄えのため」とは説明されていません。ただし、無限スライダーがスクロール位置を静かにテレポートさせる実装（100サイクルぶんの高さを持つラッパーを作り、端に近づいたら中央へ戻す）のように、体験を成立させるための細工も相応に入っています。読むときは、意図の語りと実装の代償を両方見ておきたいところです。

**詳細解説**

Spotifyが、データレイク上のParquetファイルに対して低レイテンシのポイントクエリを成立させる仕組みを解説した記事です。動機の書き出しが今っぽくて、オンラインサービスの個人化機能に加えて、「去年の夏、何を聴いてた？」に答えるAIエージェントが挙げられています。エージェントはユーザーのデータを素早く取り出し、絞り込み・集計・ローカルでのSQL実行まで行ってLLMのコンテキストを組み立てる必要がある。従来の個人化機能とエージェントは、キーによる高速なポイントクエリという同じプリミティブを共有しているわけです。

前提となる数字が効いています。Spotifyではオンライン用途にペタバイト級がBigtableにありますが、GCSのデータレイクにはエクサバイト級が眠っています。ストレージ自体は速くなっていて、GCSが30〜100ms、S3 Express One ZoneやGCS Rapid Storageは1桁ミリ秒です。ボトルネックはその上のクエリエンジンのほうで、TrinoやBigQueryは1行の取得でもジョブのスケジューリングとプランニングに秒単位を足します。分析のスループット向けに設計されていて、対話的なポイントクエリ向けではないという整理です。

従来手法の限界の説明が丁寧です。90日ぶんの再生履歴が日次1,000ファイルなら候補は90,000ファイル。キーによるパーティショニングでファイル名だけから候補が90に落ち、ユーザーIDのBloom filterで実際に活動していた12日ぶんまで絞れます。しかし残った12ファイルの中身を読むには、フッタの取得、行グループのメタデータの解析、キー列の走査、カラム／ページインデックスの参照——と、前の結果に依存する読み取りの連鎖が必要です。ファイルごと・カラムごとに複数の往復が発生し、そのすべてが他のクエリとIOPSを取り合います。

RAPの発想はここを潰すことです。外部インデックスがキーからファイルと行番号へ直接マッピングし、リーダーはキャッシュ済みのファイルメタデータで行番号をページ位置に解決して、必要なページだけをレンジリードで取ります。ルックアップはO(1)、データ取得は少数の正確なレンジリードで、しかも依存関係がないので並列に発行できます。インデックスは追記でフラグメントが増えていくだけで既存を書き換えません。目安として、テラバイトを索引すればギガバイト、ペタバイトならテラバイトのインデックスになります。ParquetのPageIndexやBloom filterが確率的に走査範囲を狭めるのに対し、外部インデックスは決定的で、走査そのものを消すという違いも明示されています。

面白いのは、外部インデックスがあることで最適化のトレードオフが反転する、という指摘です。ファイル内での探索を助ける性質（細かいページインデックス、述語スキップ向けの小さなページ、プッシュダウン用の辞書エンコード）の価値が下がり、最終的な読み取りを小さくする性質（往復を減らす、取得サイズを小さくする、連続配置する）の価値が上がります。具体策は、キーでのソート、co-grouping（`ARRAY_AGG` で1キー1行にする）、粗いパーティショニング、キー境界でページを切る「one page per key」、ページ内でキーごとにZSTDフレームをリセットする方式、ストレージのブロック境界へ揃えるパディングなど。とくに読み取り回数の削減がいちばん効くとされ、複数カラムを物理的にインターリーブして1回の連続レンジリードにまとめる手法、そしてインデックス側に小さな値を持ち上げてストレージ読み取りをゼロにする covering index まで用意されています。どれも「ファイルは正当なParquetのまま」を維持しているのが実装上の要点です。

UXエンジニアリングの視点で読むと、結論の経済性の話がいちばん響きます。いまはKVストアの容量単価が「何をオンラインで出せるか」を規定していて、そのために優先順位づけという名の切り捨てが起きています。ポイントクエリのコストがクラウドストレージの読み取り1回ぶんまで落ちれば、履歴データ、ロングテールのエンティティ、利用の少ない機能も対話的に扱える範囲に入ります。「エージェントはKVストアに載っているぶんにコンテキストを制限されず、レイクの全幅に対して何か月・何年でも遡れる」という締めは、体験の側の制約が裏側のコスト構造から来ていたことを、あらためて思い出させてくれます。

いちばん重要な指摘は冒頭に置かれています。Entra IDのEnterprise application galleryにはSigma公式のアプリケーションが登録されていますが、SCIMを使うならこれを選んではいけません。gallery applicationはSAMLのみの構成向けで、App rolesの再定義に制限があるため現行ライセンスモデル（`admin` / `analyze` / `build` / `act` / `view`）を割り当てられず、`roles` マルチバリュー属性を追加できないため複数ロールの連携もできません。ユーザーが複数グループに所属すると `MultipleGrantsNotSupported` でプロビジョニングが失敗します。しかもMicrosoftはgalleryへのSSO / SCIM統合の新規受付と更新をすでに停止していて、SCIMにはcustom applicationを案内しています。gallery → customの移行はSSOの再設定を伴うので、将来SCIMを使う可能性が少しでもあるなら最初からcustomで作る、という助言は実務的です。

`aadOptscim062020` の解説が、この記事でいちばん役に立つ部分でしょう。コミュニティのドキュメントには「Tenant URLの末尾に付けよ」としか書かれていないのですが、調べたところSigma固有のものではなく、Entra IDのSCIMクライアントの挙動を変えるMicrosoftのfeature flagでした。Entra IDが送るPATCHは歴史的経緯でRFC 7644に準拠していない箇所があり、このフラグを付けると `active` が文字列の `"False"` からbooleanの `false` になり、グループメンバー削除が `remove` 操作と `members[value eq "..."]` のパスフィルタになり、`roles` のPATCH形式がPOSTと揃います。そして、フラグがなくても「Test Connection」は成功するという注意が添えられています。接続テストではPATCHが発行されないためで、接続テストが通ることとプロビジョニングが正しく動くことは別だという指摘は、汎用的に覚えておきたい話です。

グループ設計の節も、制約から解を導く形で書かれていて読みやすいです。Sigma側は1ユーザー1 Account typeでTeamは複数所属可、Entra ID側は1グループ1 App role。この組み合わせから、Account typeを決めるグループ（必ず1つだけ所属）と、Teamに対応するFunctionalグループ（複数所属可）に分ける設計が導かれます。このとき1ユーザーに複数のApp Roleが連携されますが、Sigmaは `view` などの低権限ロールを無視して残りをAccount typeに採用するため、Functionalグループ側に `view` を割り当てておけば干渉しません。ただし `build` と `analyze` のような低権限以外の組み合わせでの優先順位はドキュメントに明記がないので、Account typeグループへの所属は運用で1つに担保する、という但し書きまで書かれています。同社ではAccount typeグループを手動管理、FunctionalグループをSnowflake用の既存グループからDynamic Membershipで自動構成し、Terraformで管理しているそうです。

UXエンジニアリングの視点で見ると直接の接点は薄い題材ですが、「ドキュメントに書かれた手順の背景を1つずつ確かめる」という姿勢そのものが参考になります。フラグの意味を調べたからこそ、接続テストが通るのに無効化が反映されないという罠を先に潰せたわけです。あと、SCIMトークンが払い出したAdminユーザーに紐づき、そのユーザーの無効化でトークンも無効になるという注意も、引き継ぎで効いてくる情報でしょう。

### [Nuxt July 2026 security advisory](https://vercel.com/changelog/nuxt-july-2026-security-advisory)

> **出典**: Vercel | **公開日**: 2026-07-27 | **カテゴリ**: frontend

**3行まとめ**
- Nuxt 4.5.1 / 3.21.10 と `@nuxt/devtools` 3.3.1 で、8件のセキュリティアドバイザリに対応
- server islandのpropsを経由したサーバーサイドRCEがHigh、DevToolsのRCEはCritical
- 以前のroute rule修正（CVE-2026-53721）の回帰があるため、対応済みの環境も再度の更新が要る

**詳細解説**

Nuxtの7月のセキュリティリリースです。深刻度の高いものが複数含まれているので、Nuxtを使っているなら早めに手を打っておきたい内容になっています。

対応された脆弱性は8件。server islandのpropsを経由したサーバーサイドのリモートコード実行（High）、同じくserver island propsによる権限のないコンポーネントのインスタンス化（Medium）、route ruleの認可バイパス（High）、サーバーコンポーネントのDoS（High、アドバイザリ2件）、キャッシュされたペイロードのユーザーをまたいだ漏洩（High、Nuxt 4.4.0以降が対象）、開発サーバーのパス開示（Low）、そしてNuxt DevToolsのリモートコード実行（Critical、開発環境のみ、`@nuxt/devtools` 3.3.1で修正）です。

更新は `npx nuxt upgrade --dedupe` で、ロックファイルも更新されて修正済みのDevToolsが入ります。注意点が2つあり、1つは、以前のroute ruleのアドバイザリ（CVE-2026-53721）で更新済みの環境でも再度の更新が必要なこと。今回の認可バイパスは、その修正の回帰だと明記されています。もう1つは、Nuxt 4で認証済みページのユーザー固有データをキャッシュしている場合、修正前に生成されたペイロードが残っている可能性があるので、上流のキャッシュをパージすること。

Vercelの立場からの記述も含まれていて、サーバーサイドRCEについては事前通知を受けてプラットフォーム全体のWAF緩和策を公開前に展開済みとのことです。Vercelにデプロイされたアプリケーションは設定変更なしで保護されますが、記事自身が「これを完全な防御として頼らないでほしい」と明記しています。WAFの緩和策が覆うのはサーバーサイドRCEの直接の悪用だけで、コンポーネントのインスタンス化、キャッシュ、認可、DoS、開発時の各脆弱性はNuxtとNuxt DevToolsの更新が必要です。プラットフォーム側の保護は追加の層であって依存の更新の代わりにはならない、という線引きがはっきり書かれているのは良心的でしょう。

UXエンジニアリングの視点で1つ引っかかるのは、キャッシュされたペイロードのユーザーをまたいだ漏洩です。SSRやISRでレスポンスをキャッシュする設計は、体験の速さのために当たり前に選ぶ手段になっていますが、その境界にユーザー固有のデータが混じるかどうかは、フレームワークの実装詳細に左右されます。速度のための判断が、事後にセキュリティの判断だったと分かる典型例だと言えます。

### [eve adds new Slack event hooks and session controls](https://vercel.com/changelog/eve-adds-new-slack-event-hooks-and-session-controls)

> **出典**: Vercel | **公開日**: 2026-07-27 | **カテゴリ**: frontend

**3行まとめ**
- スレッドにアクティブなセッションがあれば、メンションなしでも会話を継続できる `onMessage` フック
- `ctx.cancel()` で実行中のターンを捨て、`ctx.reset()` でセッションごと作り直せる
- `onEvent` で `reaction_added` や `team_join` など、Slackアプリが購読する任意のイベントに反応できる

**詳細解説**

eveのSlackチャンネル機能の更新です。エージェントをSlackに置いたときに必ずぶつかる、会話の粒度の設計に手が入っています。

まず `onMessage` フック。`ctx.isBotMentioned()` が明示的なメンションを検出し、`ctx.isSubscribed()` がそのメッセージがアクティブなセッションを持つスレッドに属するかを判定します。この2つを組み合わせて、DM・明示的なメンション・セッションのあるスレッド内の続き、の3つを処理対象にできます。毎回メンションを打たないと会話が続かない、というSlackボットにありがちな摩擦がなくなるわけです。誰がスレッドに参加しているかで振り分けたい場合は `ctx.thread.listParticipants()` が使えて、人間のSlackユーザーIDが初出順に返ります。パブリックチャンネルでは `message.channels` のトリガーイベントと `channels:history` スコープ、プライベートなら `message.groups` と `groups:history` も必要になります。

セッション制御は2つ。`ctx.cancel()` は現在のターンを止めつつセッションは維持し、`{ auth }` を返す前に呼ぶと新しいメッセージが差し替えの入力としてキューに入ります。つまり、途中で「あ、そうじゃなくて」と訂正したとき、古い作業を捨てて最新のメッセージに応答します。`ctx.reset()` はスレッドが持つセッションを終了させ、次のメッセージから履歴・状態・サンドボックスがすべて新しい状態で始まります。記事の例では `!new` というコマンド1つに3行で対応しています。

`onEvent` フックは、`reaction_added`、`team_join`、`channel_created` のような生のイベントを受け取ります。フックのなかで `ctx.receive()` を呼ぶとエージェントのターンが始まり、複数回呼べば1つのイベントを複数の宛先へ展開できます。記事の例は `team_join` を受けて、複数のウェルカムチャンネルそれぞれでオンボーディングを走らせるものです。

UXエンジニアリングの視点でいうと、この3つの追加はどれも「エージェントとの会話をどこで区切るか」というインタラクション設計の話に見えます。メンションは、人間にとっては呼びかけの合図ですが、実装上はセッション境界の代用でもありました。それを `isSubscribed()` で分離したことで、呼びかけと文脈の継続を別々に設計できるようになっています。`cancel` と `reset` も同じ話で、「言い直す」と「やり直す」はユーザーの意図としてまったく違うのに、多くのチャットUIでは同じ操作に潰れていました。エージェントのUIを作るなら、この2つを別の操作として置けるかどうかは押さえておきたいところです。
