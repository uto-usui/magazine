### [Code, craft, and the making of nested folders](https://www.figma.com/blog/code-craft-and-the-making-of-nested-folders/)

> **出典**: Figma Blog | **公開日**: 2026-08-03 | **カテゴリ**: design

**3行まとめ**
- ネストしたフォルダという地味な改善のために、コンテンツモデルと権限モデルを土台から作り直した
- 要件を Slack で議論する代わりに PR を提案として出し、壊れなければマージする進め方へ切り替えた
- エンジニアがデザインを決め、デザイナーがコードを書き、PM は日々の実行を手放して戦略の問いに回った

**詳細解説**

ネストしたフォルダは長く要望されてきた機能です。使い勝手の改善のように聞こえますが、ファイルブラウザ、管理者向けの制御、共有、権限、基盤のインフラまで、Figma の土台を作り直す必要がありました。着手は1年前。当初は通常のプロセスで進めていました。プロダクトが要件を詰め、デザインが体験を描き、思考が固まったところでエンジニアリングが実装に入る流れです。

途中で状況が変わります。チームは AI ネイティブな機能の開発にリソースを割かれ、いっぽうで Figma Make、MCP サーバー、agent skills、コードベースからのプロトタイピングが、アイデアを形にするまでの時間を短くしていました。記事は、そこから始まった新しい進め方を3つの視点で語ります。

エンジニアの Ethan Adams は、通常の開発プロセスでは間に合わないと気づいた瞬間を「期末試験の途中で顔を上げたら、残り5分だと分かった」と書いています。「誰が X にアクセスできるようにするか」といった要件の議論を、コードによる提案で置き換えました。書くことが高価で時間のかかる時代には議論が有効な前提づくりでしたが、今はエージェントの時代である、と。壊れなければマージする方針にしたので、コピーが甘くても、機能が足りなくても、論理の穴が残っていても進められます。「実際のコードベースで動くデモは、いつでも PRD に勝つ」という一文が置かれています。PM との関係も、要件を決めて実装するウォーターフォールから、提案を出して staging にマージしフィードバックをもらい仕上げる検証ループへ変わりました。

デザイナーの Cai Charniga の告白は率直です。このプロジェクトでの PR は2、3本。エンジニアになったわけではないけれど、全員が誰かの持ち場に踏み込むようになった、と書いています。エンジニア側が構造への直感と企業向け権限モデルへの理解を持っていたので、フローやデザインの調整を持ち込んでくる。強いデザインシステムがガードレールとして働き、判断してよいという信頼があれば、エンジニアがデザイン機能を良い状態まで持っていける。誰かが手一杯でも「適切な人」を待って止まらなくなります。フォルダ共有のフローでは、エンジニアの Jenny Yu がモックを数案作り、そこへ UX ライターの Molly Rosen Marriner と Cai が加わって、キャンバス上で3人で組み上げました。技術的な整合性、権限を説明する言葉、視覚的な階層をそれぞれが担う形です。

逆向きの動きもありました。変更を引き受けてコードに入ってみたら裏側で起きていることが多く、これは自分の仕事ではないと戻した、という話です。「自分の専門がどこで尽きるかを知ることも、それ自体がクラフト」という言い方をしています。それでもデザイナーは PR を出してみるとよい、とも書いていて、環境を立ち上げてプレビューできるまでの待ち時間を体で知ったことが、どんなハンドオフよりも共感を育てた、と続きます。

PM の Sachi Shah が最初に手放したのは、良いプロダクト思考が PM だけから出るという前提でした。仕事は、適切な人を適切な問題に当て、走る余地を渡し、いつ戻るかを判断すること。データサイエンティストが新しい権限モデルのコホート別の影響をマッピングして、前提を検証する役を担いました。実行を手放して得た時間で向かったのは上流の問いです。AI ファーストの世界でファイル整理はまだ重要なのか、AI 検索が良くなればフォルダは時代遅れになるのか。出てきた答えは逆でした。人がより多く作るようになるほど、フォルダは AI 検索が参照する構造と文脈を与えるので、いっそう重要になりうる。Config では happy hour に飛び込んで、作っているファイル整理の仕組みを顧客へ売り込み、その場で早期アクセスプログラムの参加者を獲得しています。

UXエンジニアリングの視点だと、「コードを提案として扱う」はUXエンジニアが以前からやってきたことです。議論の代わりに動くものを置く。それがチーム全体の標準になった形だと読めます。見落としたくないのは、デザインシステムがガードレールとして機能するという指摘のほうでしょう。エンジニアがデザイン判断を持てるのは、システムが決定の幅をあらかじめ狭めているからです。逆に言えば、システムが弱い組織で同じ進め方をすると品質が散ります。

役割を溶かすのは気まずかった、とも正直に書かれています。互いの足を踏み、境界を不器用に越え、やったことのないことを試した。その不快さは新しい常態を見つける過程の一部で、下地にある関係へ投資していたから通り抜けられた。週次のバグバッシュ、部門横断の同期、デザインとエンジニアリングのライブペアリング、節目の祝い。仕組みの話として読める部分です。

### [横断フロントエンドユニットの取り組み — 技術的負債の解消から AI 活用まで](https://tech.smarthr.jp/entry/2026/08/03/112823)

> **出典**: SmartHR Tech Blog | **公開日**: 2026-08-03 | **カテゴリ**: design

**3行まとめ**
- jQuery 1.12.4 のメジャーアップデートは、AI で修正箇所を洗い出し、細かい PR に分け、jquery-migrate の警告を Sentry へ送る形で進めた
- gulp はプラグインが放置され脆弱性を引き込んでいた。生成物のコミット、CLI ツールの組み合わせ、npm scripts へ段階的に置き換えて廃止
- 専任のフロントエンドエンジニアがいないチーム向けに、基本機能の文脈を組み込んだ AI レビュースキルと、Figma から実装するスキルを提供

**詳細解説**

SmartHR の基本機能は従業員情報の管理を担う基盤で、歴史が古く大きなプロダクトです。モジュールのバージョンが全体的に古くセキュリティに問題がある、コードが肥大化して開発速度が低下し続けている、チームごとに書き方がバラバラで手を入れるコストがかさむ。これらを「機能開発を優先するという事業判断をしていたために発生した組織的な課題」と位置づけているところに、この記事の姿勢が出ています。さらに AI の活用が進むなかでこうした課題が増幅されうる、という見立てから横断ユニットが組成されました。

jQuery のメジャーアップデートは、対象が 1.12.4 でサポート終了と脆弱性を抱えた状態でした。動いている画面が多く影響範囲が広いので、AI を使って事前に修正できる箇所の洗い出しとテスト設計をし、レビューと動作確認をしやすいように細かく PR を作っています。アップデート後は一定期間 jquery-migrate を入れました。削除・変更された API の互換性を保ちながら、非推奨の記法が使われたときに警告を出すプラグインです。修正漏れがあっても画面は動いたまま、警告は Sentry へ送って検知する仕組みまで作っています。結果として障害を起こさずに完了しました。

gulp の廃止も進め方が具体的です。プラグインの一部がメンテナンスされておらず、依存パッケージ経由で複数の脆弱性を引き込んでいた。多くのプラグインが gulp 本体のアップデートに追従できず、更新のボトルネックにもなっていた。エコシステム自体の衰退も踏まえて npm scripts へ移行しています。移行は3つの粒度で PR に分割しました。生成結果が変わらない処理は生成済みファイルをリポジトリにコミットしてタスク自体を廃止、CSS のビルドパイプラインは CLI ツールの組み合わせに置き換え、Lint やファイルのコピーはそれぞれ npm script に。最後に gulp 本体を削除しています。

AI スキルの提供は、専任のフロントエンドエンジニアがいないチームがボトルネックになったり、コーディングガイドラインに沿わない実装が生まれたりする課題への対応です。基本機能の文脈を組み込んだ AI レビュースキルの拡充と、Figma を読み込んでデザインを実装するスキル。専任がいなくても一定の品質を担保できる状態を目指しています。

Jira をやめて Notion に統合した話も混ざっています。理由として挙がっているのは、Notion と Jira を行き来する煩雑さ、実装計画と チケット管理の二重管理、そして MCP を複数つなぐことによるトークン量の肥大化です。統合の結果、AI による週次振り返りの精度も上がったと書かれています。

UXエンジニアリングの視点で拾いたいのは、この3つ目の理由でしょう。ツールを1つにまとめた判断の根拠に、エージェントが読む文脈の量が入っています。AI 前提の運用が、そのままツール選定と情報の置き場所の設計に跳ね返る例です。

展望の部分もこのニュースレターの読者に近い話でした。これまで分業されてきたデザイン・コード実装・アクセシビリティ・テストを、AI を使って1人のエンジニアが横断的にカバーするようになると予想している。まさにUXエンジニアの職能像で、それを AI が押し広げるという読みです。あわせて、AI による開発が技術的負債を増幅させないよう、テストや Lint、ハーネスを整えながら既存の負債の解消も続ける、と書いています。増幅を仕組みで止めるという発想が明示されている点は、参考になります。

### [メニューUIの誤操作を減らせ！ CSSで作るヒットエリア「セーフ・トライアングル」](https://ics.media/entry/260803/)

> **出典**: ICS MEDIA | **公開日**: 2026-08-02 | **カテゴリ**: frontend

**3行まとめ**
- 階層メニューで斜めに動かすと途中の項目が反応する問題は、ポインターとサブメニューの上下端を結ぶ三角形をヒットエリアにすると避けられる
- CSS の `clip-path: polygon()` と CSS 変数で実装でき、`::before` は長方形でも切り抜かれた三角形の内側だけが反応する
- 1980年代半ばの Mac の階層メニューに同じ考えがあり、2013年の Amazon メガメニューの分析で Web に広まった

**詳細解説**

問題の立て方が良い記事です。目的のサブメニューへ斜めに進むと、途中の別項目が反応してサブメニューが切り替わる。誤反応を避けるには、いったん右へ進んでから垂直に動かすしかない。つまり格子上の道のり（マンハッタン距離）で動くようユーザーが矯正されている、という捉え方から始まります。

解決策は、マウスポインターとサブメニューの左上・左下を結ぶ三角形をヒットエリアとして置くことです。実装は疑似要素を `position: fixed` で配置し、長方形の位置と大きさを CSS 変数で受け取って `clip-path` で三角形に切り抜きます。`z-index` はトリガーやサブメニューより背面。初期状態は `display: none` にしてホバー中だけ有効にします。`::before` 自体は長方形ですが、切り抜かれた三角形の内側だけがマウスに反応する、というのが仕組みの中心です。

JavaScript 側は `mousemove` のたびに、疑似要素を囲む長方形の位置・幅・高さとマウス側の頂点を CSS 変数へ渡します。始点を少し重ねてポインターが三角形の境界から抜けるのを防ぐ、という細かい配慮まで書かれていました。ホバー操作にだけ役立つ手法なので、`@media (hover: hover) and (pointer: fine)` で囲んでマウスデバイスに限定します。主な入力機器でホバーができ、かつ細かい位置を指せるポインターであるという2つの条件です。

コラムとして Popover API と `interestfor` 属性の組み合わせも紹介されています。`popovertarget` でクリックから、`interestfor` でホバーから、同じ `popover="hint"` 要素を参照すれば、JavaScript を減らして開閉を実装できます。

ライブラリの比較がこの記事のおもしろいところです。Adobe の React Aria は DOM で三角形を作りません。JavaScript でポインターの移動方向とタイムアウトを判定し、サブメニューへ向かっている間は親項目を開いたままにします。記事は、疑似要素の透明なヒットエリアでも誤判定があるため、より高い精度を求める方法が検討されたようだと書いています。Floating UI には `safePolygon()` と `useHover()` があり、こちらも移動方向を考慮して必要なときだけ多角形を作ります。MUI や shadcn/ui も、内部で使っているサブメニューのライブラリ経由で対応済みとのことでした。実装方法はひとつではなく、さまざまな検討がなされている奥深い手法だ、という締め方に説得力があります。

歴史の節も読みどころです。この考えは1980年代半ばの Mac の階層メニューに採用されていて、当時のインターフェイス設計を振り返った1999年の記事に「a buffer zone shaped like a <」という記述があります。Web では2013年に Amazon のメガメニューを分析した記事が話題になりました。誤反応対策のひとつが遅延表示だったのに対し、セーフ・トライアングルなら即座に反応できるので即応性が良い、という説明です。

UXエンジニアリングの視点では、まとめの一文が効いています。HTML と CSS で実装すると矩形でレイアウトを考えがちで、斜め方向にヒットエリアを確保するのは思い至らないことが多い。ヒットエリアは見えるボックスの形に縛られる必要がないのに、実装の語彙が矩形なので思考も矩形になる、という構図です。フォーカスリングの範囲やタップターゲットの拡張でも同じことが起きます。React Aria が DOM で三角形を作らず移動方向で判定しているのも、「ユーザーの意図を推定する」という別のモデルに立っている点で示唆的でした。

気になる点も挙げておきます。`mousemove` ごとに CSS 変数を書き換えるのでコストはかかります。またホバーを前提にした改善なので、キーボード操作の経路は別途担保が必要です。

### [Use Cases for aria-expanded](https://a11yweekly.com/issue/511/)

> **出典**: Accessibility Weekly | **公開日**: 2026-08-03 | **カテゴリ**: accessibility

**3行まとめ**
- Piccalilli の記事を主題にした号。狙いは `aria-expanded` が正しく使われているかを見分けやすくすることで、本番の実装手順書ではないと明示している
- リンク集には自動スキャン連載の総括、スクリーンリーダー向け文章に編集者は必要かという問い、リンクと popover を組み合わせたナビゲーションなどが並ぶ
- 「新しく学ぶ人へ」の枠では、HTML はすでにコントロールの型を知っているので、名前は何をするかを説明する形にする、という指摘が紹介されている

**詳細解説**

Accessibility Weekly 511号の主題は、Piccalilli の「Use cases for aria-expanded」です。引用された狙いの部分が誠実でした。この記事は `aria-expanded` が正しく使われているかどうかをより簡単に判断できるようにするためのもので、ここで扱うすべてのパターンを本番環境でどう実装するかの記事ではない、と。そのうえで各節に深掘り用のリンクを添える構成になっています。

`aria-expanded` は、その要素が制御している対象が展開されているかどうかを支援技術へ伝える属性です。アコーディオン、ディスクロージャー、コンボボックスのように、開閉の状態を伴うパターンで使います。誤用が起きやすいのは、展開される対象を実際には制御していない要素に付ける場合や、状態を持たない要素に付ける場合でしょう。判断の助けになる形で整理されているのは、実装レビューの場面で使いやすいはずです。

スポンサー枠の内容も実務に近い話でした。コントラストのスキャンをかけると、結果の多くが「手動確認が必要」で返ってきます。グラデーション、背景画像、不透明度、重なった要素についてツールが推論できないからです。紹介されているツールは、画面に実際に描画されたものを解析して、そのうち約80%を明確な合否に振り分ける、というアプローチを取っています。人の目が本当に必要な数件まで絞り込む、という位置づけです。

リンク集からいくつか。自動スキャンの連載を総括した4回目、Google ドキュメントでアクセシブルなリンクが作りやすくなった話、スクリーンリーダー向けのコンテンツに編集者は必要かという問い、心の健康を扱うアプリが UI の流行をすべて追うわけにはいかない理由、デザインシステムはもう任意ではないという主張、そして Adrian Roselli のリンクと popover を組み合わせたナビゲーション。「98%では足りない」という記事も並んでいます。

「新しく学ぶ人へ」の枠で紹介されている Erik Kroes の指摘は短くて的確です。HTML はすでにコントロールの「型」を知っているので、名前はそれが何をするかを説明する形にする。

UXエンジニアリングの視点で言えば、`aria-expanded` の誤用は、見た目の状態と支援技術に伝える状態を同じものとして扱ってしまうところから起きやすいです。開閉のアニメーションを書いた側は状態を持っているつもりでも、属性が更新されていなければ伝わりません。Erik Kroes の指摘も同じ層の話で、要素の型を名前で繰り返すと（「〜ボタン」）冗長になり、何をするかが埋もれます。

### [The Story Is in the Interaction: Bonhomme's Digital Experiences for Luxury Brands](https://tympanus.net/codrops/2026/08/03/the-story-is-in-the-interaction-bonhommes-digital-experiences-for-luxury-brands/)

> **出典**: Codrops | **公開日**: 2026-08-03 | **カテゴリ**: design

**3行まとめ**
- パリの Bonhomme は2013年創業。125件を超えるプロジェクト、200を超える国際的な賞、TAG Heuer との長期の協業
- 創業者2人が全案件に最初から最後まで関わる小さな構成。最初の創造的なビジョンを定義した人が最終成果を検証する
- WebGL やシェーダーは見せ場のためではなく物語の道具として使う。ブラウザ互換性・読み込み速度・描画最適化を前提に組む

**詳細解説**

スタジオの成り立ちに、デジタルは伝達の経路ではなくブランド体験が本当に立ち上がる場所だという確信があります。Morgane Urbain がクリエイティブディレクションを担い、ブランドアイデンティティ、視覚的な一貫性、コミュニケーション戦略を形づくる。Emmanuel Cruellas がアートディレクション、体験のアーキテクチャ、インタラクションデザイン、クリエイティブ開発を見る。この2人が全案件に関わります。

大きなエージェンシーとの違いは規模ではなく構造だ、という説明が印象に残ります。最初の創造的なビジョンを定義した人が、最終結果を検証する責任も持つ。この連続性があるので、ラグジュアリー時計の国際的な EC でも、Cartier のパリ本店に置くインタラクティブなインスタレーションでも、同じ水準を出せるという論理です。

### [GEM Training: How Meta Doubled the Efficiency of Its LLM-Scale Ads Foundation Model](https://engineering.fb.com/2026/08/03/ml-applications/training-gem-at-llm-scale-meta-ads-recommendation-foundation-model/)

> **出典**: Meta Engineering | **公開日**: 2026-08-03 | **カテゴリ**: engineering

**3行まとめ**
- 広告推薦の基盤モデル GEM を数千枚の最新世代 GPU で訓練。12か月で訓練 FLOPs を4倍にしながら E2E の効率を2倍（MFU 20〜25%）にした
- LLM 向けに最適化された AI インフラはそのまま転用できない。長さがばらつく入力、非対称な attention、数値への敏感さが推薦特有の壁になる
- E2E MFU = ローカル MFU × スケーリング比 に分解し、カーネル設計と超低精度で前者、5D 並列と SM を使わない通信で後者を攻めた

**詳細解説**

GEM は Instagram と Facebook の広告推薦を支える基盤モデルです。兆単位のスパースな埋め込みパラメータと、十億単位のデンスなパラメータを持つハイブリッド構成。系列特徴（ユーザーの行動履歴）と非系列特徴（位置、広告クリエイティブの表現）にそれぞれ専用の attention を当てながら、特徴を横断した学習もします。このハイブリッドな構造と推薦領域のデータの性質が組み合わさるところが、訓練を難しくしています。

GPU あたりの利用率を上げる側の壁が4つ挙がっています。ひとつはジャグな入力で、ユーザーの行動履歴は数百から数万トークンまで大きくばらつくため、最大長へパディングすると最大50%の計算が無駄になる。次に系列の非対称さで、self-attention は極端に長い系列に対して attention の窓が短く、cross-attention はクエリが長く key/value が短く、履歴を圧縮する PMA は逆になる。この形の違いがカーネル内のパイプライン化を効きにくくします。3つ目はメモリ律速の処理で、MLP の小さい埋め込み次元や、品質と安定性のための各種正規化。4つ目が数値への敏感さで、CTR/CVR の予測は精度の変化に弱く、素朴な低精度は品質の劣化を招きます。

数千 GPU へのスケールについては、E2E のレイテンシがランク横断の最大値（ローカル計算時間と通信時間の大きいほう）で決まるという式から入ります。ほぼ線形にスケールする条件は4つ。計算時間が通信時間を大きく上回る、競合なしに通信を計算の裏へ隠す、メモリ圧による再計算を最小にする、ランク間の負荷を均衡させる。GEM のワークロードはこの4つすべてを脅かします。

枠組みの立て方が読みどころです。E2E MFU をローカル MFU（計算効率）とスケーリング比（スケール効率）の掛け算に分解しました。ローカル MFU は層を1枚の GPU で個別に走らせ、再計算も通信の露出もない状態の重み付き平均として測る。スケーリング比はローカルと E2E の比として導く。こうすると、カーネルと数値精度の問題と、分散システムの問題を別々に扱えます。

計算効率側の打ち手をいくつか。JFA は可変長のジャグテンソルを直接扱う FlashAttention の実装です。ジャグ境界を -inf で埋める従来の2Dマスクは非テンソルコア命令の約28%を消費していたので、Query/Key をゼロでマスクして（TMA が無料でやってくれます）余分な指数を減算する方式に置き換え、数値的に等価な結果を得ました。後退パスは dQ の累積に atomic add を使うのが定石ですが、バッチとヘッドが大きい推薦のワークロードでは、系列並列を使わず dQ を分割する方式が21〜40%速いという結果です。v4 は v2 比で TFLOPS が40〜140%改善しました。

BlockAttention は、長いユーザー系列に対する self-attention のコストを扱います。まず full self-attention をスライディングウィンドウにして計算量を O(L²) から O(L × 窓) へ落とし、レイテンシを最大68%削減（モデル品質の指標は中立）。さらに64トークンの固定ブロックに揃えて、各 Q ブロックが対応する K/V ブロックだけを見る形にしました。64×64の独立した問題になるので、部分的な窓のマスクや複数タイルの反復が消えます。RoPE の後退を attention のエピローグに融合して勾配を FP32 レジスタに保つ工夫も加えて、スライディングウィンドウ比で約44%の改善です。

GDPA は視点が良い統合です。self-attention、PMA、cross-attention は「2回の行列積の間に要素ごとの活性化」という共通構造を持ち、softmax の代わりに GELU や SiLU を使う。これを1つのカーネルにまとめました。ここで報告されている観察が印象に残ります。実際の本番トラフィックと合成ベンチマークの間に、順方向で2.6倍、最悪の場合4倍の性能差があった。短くて非対称な K/V、ジャグな入力、大きなバッチが、パイプラインの占有率の前提を壊すためです。softmax の補正段を消すと4つの warp とレジスタが空く。ジャグテンソル向けにはタイルの有効性を CPU で事前計算して空タイルを飛ばし、ジグザグに SM へ割り当てて偏りを6倍からほぼ均衡まで縮めた。GELU の tanh（SFU 律速）は、正規化で入力範囲が抑えられていることを利用して6次のテイラー展開（ALU のみ）に置き換えました。順方向2倍、逆方向1.6倍、短い K/V の本番設定では FA4 比で最大3.5倍。モデル全体で30%を超えるスループット改善です。

低精度の節も丁寧です。FP8 は FP16 比でピーク FLOPS が2倍、FP4 は4倍になるので低精度は魅力的ですが、データ型を入れ替えるだけでは済みません。スケール係数を各行列積の K 次元に沿って生成する必要があり、FA4 がすでに埋めている TMEM をやりくりしなければならない。一時的に使われていない領域にスケール係数を重ねる、softmax の warp 内で計算済みの行の最大値を再利用して P をその場で MXFP8 化する、[32, 32] の正方量子化で転置に対して不変にしてテンソルごとに1回だけ量子化する。順方向1.3倍超、逆方向1.5倍超です。量子化のオーバーヘッド対策も具体的で、FSDP の all-gather の前にローカルシャードを量子化してコストをランク間で分散し、低精度のペイロードを通信して all-gather の量そのものを減らす。活性化は前段の正規化や射影にカーネル融合する。数値の安定性には、Random Hadamard Transform で外れ値を散らし、確率的な丸めで決定的な偏りを消し、勾配の計算を選択的に高精度へ戻す、という組み合わせでした。

スケール効率側は5D の並列化です。設計原則が明快で、通信量をトポロジ階層で使える帯域に合わせる。ある階層で collective がボトルネックになったら、その階層でのメッセージ量かグループサイズを減らす並列次元を足す。クラスタは3階層で、ホスト内8GPU が NVLink、AI ゾーン内のホスト間が RoCE、ゾーン間はオーバーサブスクライブされた RoCE。だから Expert Parallelism の重い通信は帯域の高いホスト内へ、FSDP はゾーン内へ、DDP の all-reduce はメッセージが小さいのでゾーン跨ぎでも許容する、という割り当てになります。スパース側は3世代の変遷が表で整理されていて、1D から2D で負荷とレイテンシを改善し、そのかわり生じたレプリカごとの兆パラメータの複製を、さらにシャードすることでほぼゼロにしています。

通信が SM を占める問題の指摘もおもしろいところでした。all-gather や reduce-scatter の通信カーネルが約24 SM を占め、最大15%の効率を食う。しかも SM 占有率の低下以上に計算カーネルの性能が落ちる。データ移動を Copy Engine と RDMA に任せて all-gather の SM 使用を24から1へ減らし、約23 SM を計算に返して E2E で約5%の改善を得ています。

負荷均衡の節は、LLM との違いがはっきり出ます。LLM は全系列を固定長にパディングすれば均衡を避けられますが、GEM ではパディングが50%以上の計算を捨てる。ジャグなカーネルはランクごとの無駄を避けるかわりに、反復ごとに変わるデータ由来の偏りを生みます。もっとも重いランクが平均を毎回約15%超えていました。ランク間で全体的に再配分すればほぼ完璧に均衡しますが、毎ステップの collective が効率の利得を打ち消してしまう。採用したのは、128サンプルのサブバッチを系列長でソートし、重いものと軽いものを組にして1000超のバッチへ交互に混ぜる方式です。ランク間の通信をゼロに保ったまま、理論上の最適の大部分を捉えて4%の改善になりました。

UXエンジニアリングの視点で直接の接点はありませんが、持ち帰れるものが2つあります。ひとつは「実際の本番トラフィックと合成ベンチマークで2.6倍の差」という観察で、これはフロントエンドの計測にもそのまま当てはまります。理想化した条件で測ると、現実の分布で崩れる。もうひとつは指標を掛け算の因子へ分解してから、それぞれに固有の打ち手を当てるという思考の型です。結びの「これはソフトウェアだけの問題でもハードウェアだけの問題でもなく、co-design の問題」という一文も、層をまたいで設計する仕事の説明として読めます。

感想の部分に読みどころがあります。10本の発表のどれもキャリアをきれいな成功談として扱っていなかった、という観察です。わからないことをうまく聞けなかった経験、環境を変えても自分の振る舞いを変えなければ状況は変わらなかったこと、仕事や家庭の合間に活動を続けてきたこと。それぞれの試行錯誤が率直に語られていた、と書かれています。

もう一つ残ったのが、これまでの経験は新しい役割へ移るときに捨てるものではなく、別の形で使い直せるという話でした。マネジメントの経験が AI エージェントとの開発に活きたり、幅広い技術経験が「負債解消」という専門性として捉え直されたり。キャリアは一直線ではなく、これまでの経験を持ったまま進んでいくものだと感じた、と続きます。

UXエンジニアリングの視点では、職能の境界をまたぐ人にとって、この「経験は使い直せる」という捉え方は具体的な支えになります。デザインの経験がある人がコードを書くとき、あるいはその逆のとき、前の職能で身についた判断の型がそのまま消えるわけではありません。今回の Figma の記事とも重なる話で、あちらは役割を溶かすチームの側から、こちらは個人のキャリアの側から、同じ現象を見ていると読めます。

「キャリアの正解を持ち帰るのではなく、自分にも試せそうな選択肢を一つ増やして帰る」という締め方も、参加レポートとしての誠実さがありました。
