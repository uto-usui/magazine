### [JPEG XL vs AVIF for web use-cases](https://jakearchibald.com/2026/jpeg-xl-vs-avif/)

> **出典**: Jake Archibald | **公開日**: 2026-10-15 | **カテゴリ**: web-standards

**3行まとめ**
- JPEG XL が主要ブラウザすべてで使えるようになったのを受けて、Jake Archibald さんが AVIF と自前のベンチマークで比べた長編記事です。写真の非可逆圧縮では、既定の設定で JPEG XL のほうが15〜25%大きくなるのがふつうでした
- スクリーンショットやイラストでは差がさらに広がり、JPEG XL は30〜90%大きくなります。透過画像やデコード速度でも AVIF が上回りました
- 一方で、可逆圧縮と既存 JPEG の無劣化変換（9〜20%縮小）では JPEG XL がはっきり勝っています。結論は「AVIF 4:4:4 を既定にして、大きすぎるときだけ JPEG XL（jixel）も試す」です

**詳細解説**

検証には avifenc と、JPEG XL のエンコーダー2種類（参照実装の libjxl と、新しく出てきた jixel）を使っています。F1 の写真、人物、レッサーパンダ、スクリーンショット、イラスト、透過画像、1,800万画素の大きな画像、HDR と、画像の種類ごとにファイルサイズ・エンコード時間・メモリ・3ブラウザでのデコード時間を測っています。画質の指標には SSIMULACRA2 と ColorVideoVDP の2つを使い、両者が食い違う場面もそのまま書いています。データとグラフがすべて公開されているので、結論だけでなく条件ごとの差を確かめられる記事です。

結果のなかで実務に効きそうなのは、エンコーダーの選び方で結果が大きく変わる点です。jixel はたいてい libjxl より小さいファイルを作りますが、透過は常に可逆で保存するため、透過画像では AVIF の2〜3倍になります。libjxl は努力値を上げても、時間とメモリが増えるわりにほとんど小さくならず、かえって大きくなることもありました。AVIF の 4:2:0（色の解像度を半分にする設定）もファイルはあまり小さくならず、高画質に届きにくくなるので、既定は 4:4:4 がよいとしています。「スクリーンショットは可逆形式で」という長年の習慣についても、非可逆の AVIF ならきれいに扱えると述べています。

UXエンジニアリングの視点では、プログレッシブ表示の考察がおもしろいところです。JPEG XL は読み込み途中でも徐々に精細になりますが、80%読み込んだ時点の画像は「ピントの甘い写真」に見えてしまい、読み込み中だと気づかれにくいと指摘しています。AVIF は約11.5kBで「何の写真か判断できるプレビュー」を出せるので、待つかどうかをユーザーが決められます。同じ理由で、BlurHash のようなぼかしは「かわいいけれど役に立たない」とも書いています。読み込み中の表示を「完成品と見分けがつくか」で評価する考え方は、スケルトン UI などにも応用できそうです。

同じ週には、AVIF 側の開発者 Gianni Rosato さんによる「[The case against JPEG XL](https://giannirosato.com/blog/post/case-against-jxl/)」も公開されています。デコード時間の差に加えて、1,918バイトの JPEG XL がデコードに17秒以上かかる例を挙げ、低性能端末への負荷攻撃になりうると指摘する内容です。また CSS Wizardry の記事（このあと紹介します）によると、Firefox 158 は JPEG XL を既定で有効にし、`Accept` ヘッダーに `image/jxl` を加えました。`Accept` を見て形式を切り替えている CDN では、アプリを変えなくても Firefox に返る画像が変わる可能性があります。キャッシュキーや `Vary` の扱いもあわせて確認しておくと安心です。Archibald さんも「AI が誤情報をそのまま返すこともあるので、自分の画像で試してほしい」と書いています。

### [Pure UI in the Agentic Era](https://mattrothenberg.com/notes/pure-ui-agentic-era/)

> **出典**: Sidebar | **公開日**: 2026-10-16 | **カテゴリ**: design

**3行まとめ**
- Guillermo Rauch さんが2015年に書いた「Pure UI」（UI はアプリの状態の純粋な関数であるという考え方）を、コーディングエージェントの時代に読み直した記事です
- エージェントに削除ボタンの追加を頼むと、オーナー権限のアカウントで動作を確かめて「完了」と報告しました。閲覧専用のロールでも削除ボタンが出てしまう不具合は見落とされていました
- 画面に影響する状態をページの境界で明示的な入力にすれば、16通りの組み合わせを並べて描画し、一覧でレビューできると提案しています

**詳細解説**

記事の例はダッシュボード画面です。ロール、プラン、請求の状態、ベータ機能のフラグという4つの入力があり、それぞれ2つの値をとるので16通りの画面になります。ところが実際のコードでは、ロールはクエリから、プランはコンテキストから、請求の状態はレイアウトからと、状態があちこちから届きます。コンポーネントを読んでも、どんな状態がありうるのかはわかりません。著者の図では、ツリーが宣言しているのは7つの props だけで、それ以外に15か所で状態を暗黙に読み込んでいました。

エージェントの報告は、型チェックが通り、ブラウザでも確認したという、それらしいものでした。ただ、確認したのは開発サーバーがたまたまログインしていたオーナーのアカウントだけです。ヘッダーには「View only」のバッジが出ているのに、テーブルの各行には削除ボタンが残っていました。著者は、人も同じ見落としをするとしたうえで、違いを次のように述べています。エージェントは1つの状態しか確かめていなくても、16通りを確かめたときと同じ自信で「完了」と言います。しかも、生成された変更1件あたりにかけられるレビューの時間は減っていきます。

解決策は、画面の表示に関わる状態をページやビューの境界に集めて、引数として渡すことです。そうすれば、その API がそのまま「出力を変えうる条件の一覧」になります。Storybook のストーリーやテスト、画面を並べたグリッドにも変換しやすくなります。Storybook や Playwright を否定するのではなく、どの組み合わせが大事かを書き留めておく場所として Pure UI を位置づけているのがよいところです。

UXエンジニアリングの視点では、「エージェントが実際に何を見たのか」をマージ前に問う習慣として取り入れやすい内容です。デザインでも、ロレム・イプサムで埋めた理想の1画面だけを描く問題は昔から指摘されてきました。状態の組み合わせを明示すると、権限や料金プランの抜け漏れをレビューで見つけやすくなります。ただし、組み合わせは条件が増えるほど急に増えるので、どれを並べるかを決めるのは結局人の仕事です。記事もこの限界を認めています。

### [Synthetic Users vs. Human Respondents: Same Conclusion, Less Variation](https://www.nngroup.com/articles/synthetic-users-vs-human-respondents/)

> **出典**: Nielsen Norman Group | **公開日**: 2026-10-16 | **カテゴリ**: design

**3行まとめ**
- 以前604人の専門職に聞いた「この仕事を何と呼ぶか」という自由回答の質問を、AI が生成した120人の「合成ユーザー」にも聞いて比べた調査です
- どちらも「UX という呼び名が主流」という同じ結論になりましたが、人の回答が50以上の呼び名に分かれたのに対し、合成ユーザーは十数個に集まりました
- 珍しい回答が消えてよくある回答に寄っていく現象を「モード崩壊」と呼び、少数派の意見が大事な調査では人が必要だと結論づけています

**詳細解説**

合成ユーザーには、Synthetic Users というサービスを使っています。調査計画を渡すと、年齢・地域・職種・文化的背景・性格特性などのプロフィールを持った回答者を自動で作ってくれます。ただ、このサービスはインタビュー形式で回答するので回答が長くなり、質問の言い回しも勝手に少し変えていました。研究者が質問の出し方を細かく管理できないこと自体が、結果に影響しうる要因だと指摘しています。

数字の比較が具体的です。UX 関連の言葉を使った割合は、人が約70%、合成ユーザーが84%でした。人のサンプルは NN/g 自身のパネルから集めたので UX 職が67%を占めていました。一方、合成ユーザーは職種の割り当てを決めて作ったので、UX 職は20%しかいません。それでも合成ユーザーのほうが UX という言葉を多く使っていたわけです。プロダクトマネージャーに絞ると、人は44%、合成ユーザーは93%でした。職種による違いは合成データにも出ていますが、全体として多数派の言い方に強く引っぱられています。

「もっと多様に答えて」と指示すればよいという考えにも、記事は答えています。多様さを出せても、それが実際の人の珍しい回答を、実際と同じくらいの頻度で再現しているとは限りません。人のデータがなければ、その多様さが正しいかどうかを確かめる方法もない、ということです。

UXエンジニアリングの視点では、AI ペルソナや合成ユーザーを使う場面が増えるなかで、使いどころをはっきりさせてくれる記事です。仮説づくりや大まかな傾向の確認には使えますが、意外な言葉づかいや新しいテーマを探す調査、ユーザー層ごとの違いを見る調査には向きません。結論が人の調査と一致したことは、合成ユーザーが信頼できる証拠にはならない、という点も覚えておきたいところです。ただし、今回は1つの質問と1つのサービスによる比較なので、ほかのツールや質問形式にもそのまま当てはまるとは限りません。

### [Web-Perf Wednesday 013 – CrUX Adds Soft-Navigation Core Web Vitals](https://csswizardry.com/2026/10/web-perf-wednesday-013-crux-adds-soft-navigation-core-web-vitals/)

> **出典**: CSS Wizardry | **公開日**: 2026-10-14 | **カテゴリ**: css

**3行まとめ**
- 2026年9月の CrUX（Chrome の実ユーザーデータ）に、SPA の画面遷移（ソフトナビゲーション）も含めた LCP・INP・CLS の実験的な指標が加わりました
- 新しい指標では、3つの指標すべてで「良好」と判定されるオリジンの割合が55.9%から59.5%に上がります。測る対象そのものが変わるので、従来の数値とは分けて扱うよう勧めています
- あわせて、Firefox 158 の `deliveryType` 対応と JPEG XL の既定有効化、Safari Technology Preview 254 の性能まわりの修正も紹介しています

**詳細解説**

これまでの CrUX は、SPA のセッション全体を1つの長いページとして扱っていました。最初の読み込みだけを LCP として記録し、そのあとの操作もすべてそのページの INP に数え、レイアウトのずれも積み上げていました。新しい指標では、ルートの切り替えを別の画面表示として扱います。商品一覧、商品詳細、カート、購入手続きがそれぞれ指標を持てるようになります。

注意したいのは、新しい指標が「ソフトナビゲーションだけ」の数値ではなく、従来のページ遷移とソフトナビゲーションを合わせた75パーセンタイルだという点です。数値が良くなるのも、速くなったからとは限りません。2回目以降の表示は最初の読み込みのコードや素材を使い回せますし、INP は画面ごとに評価され、CLS も遷移ごとにリセットされます。約70%のオリジンにはソフトナビゲーションがほとんどない一方で、上位1,000サイトの35〜42%ではページ表示の半分以上がソフトナビゲーションです。影響は大規模な SPA に集中しそうです。

Google はこの指標を2027年5月に正式なものにする予定で、そのときに Search Console も新しいデータに切り替わります。著者は、それまでの期間を比較のための準備期間として使うよう勧めています。新旧の数値がずれているルートや端末を探すこと、使っている RUM ツールの「画面遷移」の定義と照らし合わせることが具体的な作業です。BigQuery を使っていなくても、CrUX Vis で新しい指標を確認できます。

UXエンジニアリングの視点では、SPA の体感とスコアのずれがやっと数字で見えるようになる変化です。とくに、購入手続きのように後ろのほうにある画面の体験を改善しても、これまでは Core Web Vitals に表れにくいものでした。一方で、ダッシュボードや目標値、社内レポートが新旧どちらの指標を使っているかを整理しないと、数値の改善を施策の成果と取り違えてしまうおそれがあります。今のうちに旧指標での記録を残しておくとよいでしょう。

### [Design owns coherence](https://www.petermerholz.com/newsletter/newsletter-design-owns-coherence/)

> **出典**: Sidebar | **公開日**: 2026-10-16 | **カテゴリ**: design

**3行まとめ**
- デザイン組織論で知られる Peter Merholz さんが、デザインという職能が受け持つ責任を「一貫性（consistency）」ではなく「まとまり（coherence）」だと提案するエッセイです
- 財務は資本配分、法務はリスク、営業は売上を受け持つのに対し、デザインが受け持つ「一貫性・使いやすさ・アクセシビリティ」は事業から見て小さく見えている、と問題提起しています
- 複数の製品やチャネルが利用者から見て1つの体験になっているかを「まとまり」と呼び、それを担うための論点を3つ挙げています

**詳細解説**

背景にあるのは、買収などで寄せ集めた製品群がつながっていない企業の悩みです。銀行や医療のように、商品、窓口、社内ツールが入り組んだサービスでは、利用者が同じ情報を何度も入力させられます。部分ごとにはよく設計されていて、それぞれの指標も達成しているのに、つなげると離脱や問い合わせが増えるという状況です。著者は、各チームが自分の機能を期日どおりに出すことで評価されてきたプロダクトマネジメントは「縦割り」になりやすく、この問題を解きにくいと述べています。

説得の材料として、2016年の McKinsey のレポートを引いています。4つの接点がそれぞれ90%、85%、85%、90%の評価でも、通しの体験では約60%になる、という図です。部分ごとには A や B の評価なのに、全体では D になるわけです。ところがそのレポートでは、解決策として顧客体験の責任者や部門横断のジャーニーオーナーといった体制づくりばかりが挙がっていて、デザインという職能には触れていない、と著者は指摘しています。

「まとまり」には、ブランド、実際の行動の観察、サービスデザイン、コンテンツデザインと情報設計が含まれるとしています。そのうえで、職能として認められるための論点を3つ挙げます。どの場面でデザインが決定権を持つのか、まとまりをどんな証拠で示すのか、なぜカスタマーサービスや業務部門ではなくデザインなのか、の3つです。著者自身も答えはまだ持っていないと認めていて、読者に意見を求める形で終わっています。

UXエンジニアリングの視点では、デザインシステムの価値を「見た目をそろえる」から「通しの体験をつなぐ」へ広げる手がかりになります。画面をまたぐ入力の重複や、チャネル間の受け渡しで失われる情報は、エンジニアがデータの流れから見つけやすい問題でもあります。なお、記事の最後は著者のリーダー向けプログラムの告知になっています。主張の多くは問題提起の段階なので、自分の組織の事例に当てはめて考えるための材料として読むとよさそうです。

### [From 2,500 requests to 24: Rebuilding star history without the stargazers](https://github.blog/engineering/architecture-optimization/from-2500-requests-to-24-rebuilding-star-history-without-the-stargazers/)

> **出典**: GitHub Engineering | **公開日**: 2026-10-14 | **カテゴリ**: engineering

**3行まとめ**
- スター数の推移グラフを作るために、ツールはスターを付けた人の一覧を API で全件取得していました。その一覧がスパムやフィッシングに使われ、データベースの負荷も大きくなっていました
- GitHub は一覧の公開を制限したうえで、個人を含まない「日ごとのスター数」を最大30週分まとめて返す新しいエンドポイントを作りました
- `react/react` の履歴を取るのに約2,511回かかっていたリクエストが約24回になりました。返すデータを減らすだけでなく、集計の前に期間で絞り込んだことがポイントです

**詳細解説**

元のエンドポイントは「誰がスターを付けたか」を1ページ100人ずつ返すものでした。スターのデータ自体も現在の状態だけを持っていて、スターが外されると記録が消えます。もともと履歴を取るための仕組みではなかったわけです。さらにページ分割の実装にバグがあり、1ページを返すたびに全スター数を数え直していました。制限の直前の1週間には、遅いクエリとして記録されたものが約37,000件あり、平均で約3秒かかり、1,000件以上が強制終了されていました。

おもしろいのは、最初に考えた案がうまくいかなかった理由です。日や週ごとに集計してから `LIMIT` と `OFFSET` でページを分ける方法では、返す件数は減ってもデータベースは毎回すべてのスターを集計して並べ替えます。`react/react` の履歴をすべて読むと、24回のリクエストでのべ約600万行を処理することになります。そこで、ページ番号を `created_at` の期間に変換し、インデックスで絞り込んでから集計するようにしました。これで各スターが処理されるのは約1回、全体で約25万行になります。

この調査の途中で、GitHub.com のスター一覧ページでも同じように毎回数え直していることが見つかり、キャッシュ済みのスター数を使うようにしたところ、週に数百件あった遅いクエリがゼロになったそうです。一方で、残る制約もはっきり書いています。極端にスターが集中した週は今でも重いクエリになりうること、週の区切りや外されたスターの扱いも API の仕様の一部であることです。

UXエンジニアリングの視点では、「利用者が本当にほしいもの」から API を作り直した例として参考になります。メンテナーが必要としていたのは人の一覧ではなく、リリースや告知の前後で傾向を比べるための曲線でした。古い API が個人とタイムスタンプをセットで返していたせいで、個人情報も必要なものだと思い込まれていたわけです。用途に必要なものだけを返せば、悪用される情報も減らせます。画面のために必要以上のデータを取っている API がないか、見直すきっかけになる記事です。

### [How Meta Built Forum With AI-Native Engineering](https://engineering.fb.com/2026/10/15/ml-applications/how-meta-built-forum-ai-native-engineering/)

> **出典**: Meta Engineering | **公開日**: 2026-10-15 | **カテゴリ**: engineering

**3行まとめ**
- Facebook グループ向けの新アプリ Forum を、小さなチームが AI エージェントを開発プロセスの参加者として扱いながら作った記録です
- 人が毎回手を動かす「human-in-the-loop」から、エージェントが計画・実装・テスト・修正を回し、人は目標設定と承認を受け持つ「human-on-the-loop」へ移ることを目指しました
- 完了の基準をコンパイルではなく検証に置き、ストレステストでメモリの問題を開発中に見つけるなどして、8週間で Facebook グループの主要機能に並びました

**詳細解説**

成功の基準を、コードの量ではなく「ビルドが通り、テストに合格し、レビューを通った変更」に置いています。検証がなければ、AI が出したそれらしいコードを人が読んで直して捨てることになり、ボトルネックが実装からレビューに移るだけだという認識です。そこで、ビルド結果、ユニットテスト、UI 仕様との照合をエージェントのループに組み込み、レビューに出る前に自分の仕事を確かめさせています。プルリクエストには、テスト計画と検証の様子を記録した映像が添えられます。

運用の仕組みは5つの部品でできています。同じ失敗が2回を超えたら書き足す恒久的な指示（Rules）、チームの慣習を手順にした Skills、手作業の確認を自動化する Agents、それらをつなぐ Commands、そしてリンターの実行などを自動で走らせる Hooks です。とくに効いたのは、プロンプトよりもコードと道具を変えることでした。エージェントがアプリのどこを触っているのか見失う問題には、アプリを説明する代わりに、シミュレーターから画面の階層を読み取る道具を渡して解決しています。

プロトタイプを扱う工夫もあります。本番と同じコードベースとデザインシステムを使う別のビルドを用意し、プロトタイプのコードは本番のビルドから物理的に外れるようにしました。デザイナーや他職種がエンジニアを介さずに AI で試作でき、それをそのまま本番に移すこともできます。それでいて、試作のコードが本番アプリを落とすことはありません。ストレステストでは、激しいスクロールや素早い画面遷移を繰り返してメモリの増え方を監視し、見つけた問題で使用量をおよそ半分にしています。

UXエンジニアリングの視点では、試作用のビルドを分ける設計が参考になります。フィーチャーフラグで隠すだけでは、試作のコードは本番に含まれたままです。デザイナーが自由に試せる場を、本番の安全を損なわずに用意できます。また、エージェントの回答の質を上げたのは、新しく入ったエンジニアに初日に渡すような資料（関連コード、クエリの例、設計ドキュメント）だったという話もうなずけます。ただし、公式ブログでの成果報告なので、うまくいかなかった点は図でまとめられている程度です。チームの規模や体制の詳しい条件も書かれていません。

### [A flame needs three sine waves](https://www.carmenansio.com/articles/matchstick-flame-canvas/)

**3行まとめ**

**詳細解説**

最初のメモは「本物のマッチを見る」です。観察して書き留めたのは「少し傾く」「同じ動きを二度しない」「部屋が暖かくなる」の3つで、オレンジ色で光っているといった見た目の特徴はあえて外しています。動きを作るときに必要なのは、どう見えるかではなく、どうふるまうかだという考え方です。3つの観察は、それぞれ「涙形の先端だけが動く」「3つのサイン波」「炎に合わせて明るさが変わる大きな放射グラデーション」というコードになりました。

公開しているコードのバグも隠していません。すべての数値を1フレームあたりで書いていたため、120Hz の画面ではマッチが6.5秒で燃え尽き、火花は2倍の速さで飛んで4倍の重力で落ちていました。直し方は、経過時間 `dt` から60Hz なら何フレーム分かを求め、線形補間を `1 - Math.pow(1 - 0.08, k)` のように書き換えることです。`requestAnimationFrame` でアニメーションを書くときに見落としやすい点なので、そのまま確認リストに入れられます。

UXエンジニアリングの視点では、reduced motion の扱いがいちばんの学びです。動きを減らす設定でも、マッチが点いているかどうかや、部屋が暖かくなることは情報なので残します。やめるのは火花の飛び散りと揺らぎで、炎が育つ表現はフェードに置き換えています。「アニメーションを止める」のではなく「状態と色は残して、動きだけを減らす」という線引きは、UI のトランジションやローディング表示にもそのまま応用できます。

### [Findings from the $1M Vercel Sandbox challenge](https://vercel.com/blog/findings-from-the-1-million-dollar-vercel-sandbox-challenge)

> **出典**: Vercel | **公開日**: 2026-10-14 | **カテゴリ**: frontend

**3行まとめ**
- Vercel Sandbox からの脱出に最大100万ドルの賞金をかけた公開チャレンジの結果報告です。2週間で1,285件の報告が届き、24万2,000ドルが支払われました
- もっとも深刻だったのは Linux カーネルのネットワーク処理のゼロデイ脆弱性でした。特殊なパケットで、ホストのメモリの漏えい、ホストの停止、ホスト上でのコード実行ができてしまうものです
- 顧客データへのアクセスは確認されませんでした。外部監査を受けて「ゲストを一切信用しない」などの3つの構造的な改善を入れています

**詳細解説**

ゼロデイは3日目に、特別な権限のない通常のサンドボックスから見つかりました。ホストのメモリの漏えいは本番環境で実証され、ホストの停止とコード実行は研究者自身の同じ構成の環境で実証されています。主要なクラウド事業者の多くが同じカーネルの層で顧客の処理を分けているため、業界共通のリスクとして AWS などと修正を進めているそうです。パッチと CVE はまだ非公開で、詳細は伏せられています。社内のインターンも、削除したサンドボックスのディスク領域を別のサンドボックスから読めてしまう問題を見つけていました。

セキュリティ企業 Trail of Bits は、エンジニア4週間分の時間をかけてソースコードを調べ、20件の指摘を出しました。そのうえで勧められた改善は3つです。1つ目は、マイクロVMの中から返ってくる値はすべて利用者の入力として扱い、ホスト側で求めるか署名すること。2つ目は、通信制限のポリシーを複数の仕組みがそれぞれ解釈していたのを、1つの判断役にまとめること。3つ目は、次のゼロデイが来る前提で被害を小さくすることです。

とくに印象的なのは、スナップショットの保存先をゲストの中のソフトウェアが報告し、ホストがそれを信じていたという問題です。研究者は自分の2つのアカウントのスナップショットの参照先を入れ替え、相手のファイルシステムを丸ごと復元してみせました。実際に他人を狙うには、外部に出ない96ビットの識別子を知る必要がありました。それでも Vercel は「秘密が守られることに頼る境界は境界ではない」として、1週間で修正しています。

UXエンジニアリングの視点では、この「ゲストを信用しない」原則は、ブラウザから届く値をサーバーが信用しないという Web の基本と同じ形をしています。フロントエンドで計算した値や、クライアントが申告する保存先をそのまま信じていないか、自分たちの設計を見直すきっかけになります。また、1,285件のうち877件が重複で、「研究者が AI の速さで探すようになった」とも書かれています。報告の数が増えるぶん、選り分ける側の体制も問われるようになっていることがうかがえます。

### [React Native 0.88 - Web-Based Event Dispatching, Variable Fonts, SceneDelegate, no breaking changes](https://reactnative.dev/blog/2026/10/19/react-native-0.88)

> **出典**: React Native Blog | **公開日**: 2026-10-19 | **カテゴリ**: frontend

**3行まとめ**
- React Native 0.88 がリリースされ、イベントの伝わり方が W3C の `EventTarget` にもとづく仕組みに切り替わりました
- `Text` と `TextInput` で可変フォントの `fontVariationSettings` が iOS と Android の両方で使えるようになり、iOS 27 SDK で必須になる UIScene のライフサイクルにも対応しました
- 0.83、0.86 に続いて、利用者に影響する破壊的変更のない3回目のリリースです

**詳細解説**

今回もっとも大きいのは、イベントの伝え方の変更です。これまでの独自のプラグイン方式をやめ、Web と同じようにキャプチャーフェーズで目的の要素まで下り、バブリングで上に戻るようになりました。`stopPropagation()` や `preventDefault()` も、DOM をまねた再実装ではなく、同じモデルの上で動きます。Canary チャンネルでは、ネイティブの ref に `addEventListener` を付けることもでき、宣言的な props と両方あるときは props が先に動きます。アプリ側のイベント props の名前や順番は変わりませんが、内部のイベント処理に直接触っていたライブラリは確認が必要です。

iOS の変更は締め切りがある点で重要です。iOS 27 SDK からは UIScene のライフサイクルが必須になり、Xcode 27 でビルドした UIKit アプリは起動できなくなります。0.88 では `AppDelegate` との互換性を保ったまま `SceneDelegate` の入り口が追加されました。対応は単一のシーンまでで、移行にはエントリポイントの移動、URL などのコールバックの転送、`Info.plist` へのキーの追加が必要です。ウィンドウのサイズが変わるようになり、`useWindowDimensions()` もそれに合わせて更新されます。

細かな変更にも、UI に関わるものが含まれています。iOS の RTL 表示で `textAlign` を指定しないときに右寄せになって Android とそろったこと、`Image` で `accessibilityState` と `aria-*` を両方指定したときに `aria-*` が無視されていた問題の修正などです。Android では既定の `User-Agent` にアプリ名とバージョンが入るようになったので、その値で判定しているサーバーがあれば影響します。Swift Package Manager は 0.89 で既定にする予定で、CocoaPods はその後のリリースで外す計画です。

UXエンジニアリングの視点では、Web とモバイルのあいだでイベントや文字組みの考え方がそろってきたことが大きいです。イベントの流れを前提にしたライブラリを Web と共通で書きやすくなり、可変フォントでウェイトや傾きを細かく調整したタイポグラフィも両方のプラットフォームで表現できます。なお、公開日は RSS の記載どおり 10月19日です。古いイベントの仕組みは内部のフラグで残っていますが、次の段階で取り除かれる予定なので、古い方法でしか動かない処理は早めに報告するよう呼びかけています。
