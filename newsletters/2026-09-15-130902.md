### [AI is breaking this thing we call trust](https://terriblesoftware.org/2026/09/10/ai-is-breaking-this-thing-we-call-trust/)

> **出典**: Sidebar | **公開日**: 2026-09-14 | **カテゴリ**: design

**3行まとめ**
- 「何かを作った人は、それを理解している」という職場の暗黙の前提が、AI によって崩れかけているという話です
- レビューの出発点が「これは良い変更か」から「送ってきた人はこれを理解しているか」に変わってしまった、という実感が語られています
- エンジニア向けとリーダー向けに、それぞれ立て直し方が提案されています

**詳細解説**

書き出しは1900年代初頭のアメリカです。人々は一生を馬とともに過ごしてきて、街そのものが馬で移動する前提で作られている。そこにフォードが現れて世界がひっくり返り、その後の数年で習慣のほうを作り直すはめになった。いまがちょうどそこだ、という導入です。

著者が問題にしているのは、生産性でも品質でもなく信頼です。職場の習慣の多くは「何かを生み出したなら、その人はそれを理解している」という前提の上に乗っています。PR が送られてきたら、少なくとも本人はコードを読んだと思う。ブリーフが来たら、調査は済んでいると思う。この前提は完璧ではなくて、Stack Overflow からのコピー＆ペーストは昔からありました。ただそれでも手間はかかったし、レビュアーは穴に気づけました。

AI は、理解しないまま完成して見えるものを出せるようにしてしまった、と著者は書きます。しかも困ったことに、理解していなくても正しいことのほうが多い。その結果、レビューの最初の問いが「これは良い変更か」ではなく「この人は自分が送ってきたものを理解しているか」に変わってしまった、と。

信頼は工程を省略させてくれるものです。同僚を信頼していれば、もう一度同じ調査をやり直さずに、本当に別の目が必要な部分だけを見ればいい。そこが崩れると、レビューのたびに相手の仕事を一度自分でやり直すことになります。文章の癖だけで疑いはじめてしまう（「Yes — and the real unlock is…」のような言い回し）のはフェアではないかもしれない、と自分でも書いているのが誠実なところです。ただ、具体的な質問をしたのに質問に答えていない AI 生成の説明が返ってくれば、疑う理由としては十分でしょう。そして一度そうなると、次に送られてくるものへの目線も厳しくなる。ある日のショートカットが、そのあと長く共同作業を重くする、という指摘です。

著者自身も「自分がその人だった」と告白しています。理解しないまま AI が書いた修正をマージした。修正は正しかったけれど、正しいと知るための仕事はしていなかった、と。

提案は具体的です。エンジニアには、送る前に自分の diff を読むこと、レビュアーに必要な分だけに説明を削ること、なぜそのバグが起きてなぜこの修正で直るのかを説明できる状態にしてから依頼すること。レビューする側も「どのケースをテストしましたか」「その結論に至った理由は」と押し返していい、と。リーダーには、「レビュー準備完了」がレビューできる状態を意味するように揃えること、ただし要求は変更のリスクに比例させること。そして未完成なものを未完成として共有できる場を保つこと。「まだ検証していません」は有用な情報だ、という言い方は良いと思います。最後に、自分が雑なものを送っていればチームも同じことをする、というひとこと。

UX エンジニアリングの視点で読むと、これはコードだけの話ではありません。デザインレビューで「なぜこの余白なのか」に答えられないとき、あるいはコンポーネントの API がなぜこの形なのかを説明できないとき、起きていることは同じです。レビューという場は品質のゲートであると同時に、信頼の口座でもある。そこから引き出してばかりいると、そのうち残高が尽きます。実務にすぐ持ち込めるのは、提出物に「どこまで自分で確かめたか」を1行添える習慣でしょう。AI を使ったかどうかより、何を検証したかのほうが、受け取る側にとってははるかに有用な情報です。

### [GPT-6 AstraのReact習熟度はOpus 4.8並み](https://zenn.dev/uhyo/articles/react-profession-bench-16)

> **出典**: uhyo | **公開日**: 2026-09-14 | **カテゴリ**: frontend

**3行まとめ**
- GPT-6 Astra（effort=high）の React 習熟度ベンチマークは 79.92 で、Claude の1世代前と同じ帯に入りました
- 伸びたのは Effect 衛生。これまで 0 だった `useSyncExternalStore` の採用が 7 件に増えたのが主因と見られます
- 差が残ったのはコンポーネント設計。実装の約6割が `App.tsx` + 1ファイル以下で構成されていました

**詳細解説**

React 習熟度シリーズの16記事目です。13スペック × n=3 で実装させ、`sonnet-4.6` にピン留めした評価者モデルで採点する、という設計が第1回から変わっていません。今回の対象は OpenAI の GPT-6 Astra です。

結果は 79.92。GPT-5.6 Sol の high（76.95）から +2.97 で、Sol の max（80.18）とほぼ同値です。「新しい世代の high が、前の世代の max に並ぶ」という形は Claude 側でも観測されていたので、そこは再現したことになります。ただし到達点は違っていて、Fable 5.1 high が 86.44、Opus 5 high が 87.00。順位表では Opus 4.8 high（79.38）と Sol max のあいだ、つまり1世代前の Claude と同じ帯です。

3サンプルの総合は 79.85 / 79.77 / 80.15 とブレ幅 0.38 で、かなり安定しています。一方でスペック単位では 010 ツリーエクスプローラが 82/64/83 と19点振れていて、総合は信頼できてもスペック個別の値をそのまま受け取るのは早い、という注意書きが添えられています。

カテゴリ別で動いたのは Effect 衛生の +0.29 だけです。GPT-5.6 は3層とも 3.79〜3.95 に貼り付いていて、effort を上げても動かなかった項目でした。Astra の 4.21 は Claude 上位（4.38）に 0.17 差まで詰めています。理由ははっきりしていて、`useSyncExternalStore` の使用が 0 から 7 に増えたこと。ただし中身を見ると、イベントバスの購読には正しく使う一方で、ブラウザ API（online/offline、resize、matchMedia、visibilitychange）には `useEffect + addEventListener` に戻っている。API を知っていて、使いどころを半分だけ当てている状態だと書かれています。

そして動かなかったのがコンポーネント設計の 3.15 です。ここは第11回から一貫して差がついていた項目で、Claude 上位が 4.2 台。6カテゴリのうち唯一、差が1点を超えています。

この記事で良いのは、カテゴリ点が評価者の判断であることを認めたうえで、実装の構造を直接数えているところです。`.tsx` ファイル数は Astra が実装あたり 3.2、Fable 5.1 が 8.3、Opus 5 が 7.7。`App.tsx` の平均行数は Astra 284 行に対して Claude 側は 87〜91 行。`.tsx` が2個以下の実装は Astra が 48本中29本、Claude 側は43本中2本。前世代の 430 行から 284 行に短くはなったけれど、それは分割ではなく圧縮で達成されていて、コンポーネント数はほとんど増えていない、という読み方が提示されます。

評価者の判定文も同じ方向を向いていて、`StatusCard` や `Icon`、カスタムフック `useBrowserStatus` のような「明らかに再利用する部品」は well-extracted と評価されている。つまり能力の問題ではなく、画面の構造をコンポーネント階層として表現する習慣がない、という癖として整理されています。

13スペック中の最下位は 005 ステータス監視の 62.0（66/61/59）。Fable 5.1 が 85.0、Opus 5 が 89.3 なので、この1本だけで23〜27点の差です。005 は「ブラウザ API の購読を `useSyncExternalStore` で書けるか」と「ダッシュボードをコンポーネントに分解できるか」を同時に問うスペックで、Astra の2つの癖がちょうど重なる場所だった、と分析されています。原因の特定として気持ちがいい説明です。

並行レンダリング系（`useTransition`、`useOptimistic`）は全モデル揃ってゼロのまま。`useActionState` は GPT 系が 0 で、`<form action>` を主題にしたスペック 008 でもゼロだったとのこと。`useMemo` は 26 から 17 に減っていますが、React Compiler が入っていないスキャフォールドでは、メモ化しないことは単に最適化していないことでもある、と評価を保留しています。この慎重さは信頼できます。

UX エンジニアリングの視点から見ると、この記事でもっとも実務に効くのは「コンポーネント分割はデフォルトでは出てこない」という結果でしょう。デザインシステムを運用しているチームにとって、コンポーネント境界はコードの整理術ではなく、デザインと実装の共通言語です。生成された 284 行の `App.tsx` は動くけれど、そこには `FilterBar` も `EventRow` も存在しない。次に手を入れる人が、デザイン側の名前と実装側の構造を突き合わせられません。エージェントに UI を書かせるなら、分割の指示を出すか、既存のコンポーネント階層を文脈として渡すかを最初に決めておくのが良さそうです。このベンチマークは意図的に設計の指示をしない条件なので、「指示すれば直る範囲かもしれない」という注記もきちんと置かれています。

### [Fragment Refsのずるい使い方](https://zenn.dev/uhyo/articles/react-fragment-refs-hack)

> **出典**: uhyo | **公開日**: 2026-09-14 | **カテゴリ**: frontend

**3行まとめ**
- React 19.3 の Fragment Refs を使って、`Activity` のように「自分は描画せず子要素に属性を与える」コンポーネントを作る方法です
- `FragmentInstance` の `observeUsing` に、Observer のふりをした独自オブジェクトを渡して子の DOM 要素を受け取ります
- 著者自身が「公式にサポートされた使い方ではない」と書いていて、プロダクトでの利用はすすめていません

**詳細解説**

React 19.3 で `Fragment` が `ref` を受け取れるようになりました。得られるのは `FragmentInstance` というオブジェクトで、`addEventListener` や `focus` などのメソッドを持っています。実体のないラッパーに対して、擬似的に操作しているように振る舞える仕組みです。

この記事が扱うのは、その応用というより抜け道のほうです。出発点は React 19.2 の `Activity` コンポーネントで、`<Activity mode="hidden">` で囲まれた部分は非表示になります。裏でレンダリングしておけるので表示の切り替えが速く、非表示のあいだも状態が保たれる。そして `Activity` 自身は DOM 要素を描画せず、中の要素に `display: none` を与えることで非表示を実現しています。

ここで著者が投げる問いが良いです。「自分では何も描画せず、内部の要素に `display: none` を与える」コンポーネントを、ユーザーランドで実装できるでしょうか。従来はできませんでした。React の内部だけが持つ特権的な振る舞いだったわけです。

`FragmentInstance` のメソッドのうち、子の DOM 要素を取得できそうなものは `observeUsing` だけです。本来は `IntersectionObserver` か `ResizeObserver` のインスタンスを渡して、Fragment の子として存在する各要素を監視させるためのもの。ところがこのメソッドは、内部的には各子要素に対して `observe` を呼んでいるだけです。ということは、`observe` と `unobserve` を持つ独自オブジェクトを渡せば、そこから子の DOM 要素にアクセスできてしまう。

実装は短くまとまっています。`observe(element)` で `element.toggleAttribute('hidden', enabled)`、`unobserve(element)` で属性を外す。`disconnect()` は react-dom からは呼ばれないけれど、`observeUsing` の型を構造的に満たすために置いてある、というコメント付きです。Fragment の中に要素が追加・削除された場合も React が面倒を見てくれるので、後始末まで含めて破綻しません。

注意書きが本文の中で明確なのが、この記事の良いところです。公式ドキュメントは Observer のインスタンスを渡す前提で書かれているので、この方法はサポート外であり、将来動かなくなる保証はない。だからプロダクトで使うのはやめたほうがよい、と。子の DOM 要素がもともと `hidden` 属性を持っていた場合を考慮していない、という単純化の告知もあります。

UX エンジニアリングの視点では、この話の面白さは「ラッパー要素を挟まずに済む」という一点にあります。ref を通すためだけに `div` を1枚追加すると、Flexbox や Grid の直接の子という関係が壊れて、レイアウトが静かにずれることがあります。Fragment Refs はそこを埋めるために入った API で、今回のハックは「その延長にある正当な要求」が、まだ公式には満たされていないことを示しています。結びで著者が「公式にこのユースケースがサポートされると嬉しい」と書いているとおり、この記事はテクニックの紹介であると同時に、機能要望の実演でもあります。

### [Building Depth: Designing and Developing a 3D Renderer Inside Figma](https://tympanus.net/codrops/2026/09/13/building-depth-designing-and-developing-a-3d-renderer-inside-figma/)

> **出典**: Codrops | **公開日**: 2026-09-13 | **カテゴリ**: design

**3行まとめ**
- Figma プラグインとして動く 3D レンダラー「Depth」の、設計から紹介サイト制作までの記録です
- Three.js 側と Figma ドキュメント操作側を分け、レンダー結果は通常の画像レイヤーとしてキャンバスに戻ります
- 紹介サイトのヒーローは完全なリアルタイム 3D をあきらめ、240フレームの生成シーケンスをマウス位置で制御する形に落ち着いています

**詳細解説**

出発点は、3D レンダーに強く依存するプロダクトサイトのデザインでした。完成画像は社内のビジュアライゼーションチームが作っていて、そのチームは全社のデザイナーからの依頼をさばいている。一方で著者は2週間おきに経営層とレビューをして、そのあいだにページを変えていく。モデルには触れるけれど、自分で案を試すには Figma を出て、使い慣れない Blender や Cinema 4D でシーンを組み、画像を書き出して戻ってくる必要がありました。

ここでの要求定義がとても明快です。その段階で必要なのは最終的なマテリアルや本番用のライティングではなく、その画像がページの上で機能するかを判断できるだけの形と光だ、と。ツールの粒度をどこに置くかという判断が、最初にはっきり書かれています。

インターフェース全体に取りかかる前に、ワークフローだけをなぞる小さな実装を作っています。モデルを読み込み、カメラを動かし、ライトを変え、画像を Figma に返す。そこで見ていたのは、プラグインのウィンドウの中でシーンがどれだけ軽快に動くか、そして「一日の大半を Figma で過ごす人」にとって違和感が出ない範囲で、どれくらいの 3D 操作を詰め込めるか、の2点でした。

構成は明確に分かれています。Three.js がモデル・カメラ・マテリアル・ライティングを担当し、別のコントローラーが Figma ドキュメントの読み書きをする。フレームを選択するとコントローラーがそれを PNG として 3D シーンに渡し、レンダーが終わると通常の画像レイヤーとして Figma に戻ります。2x エクスポートは PNG の幅と高さを倍にしつつ、キャンバス上のレイヤーサイズは意図したままに保つので、構図を変えずに解像度だけが上がる。細かいですが、デザイナーの作業を壊さないための配慮です。

インスペクタを右に置く Figma の慣習を保ちつつ、カメラ・ビューポート・タイムラインは Cinema 4D や 3ds Max に近い作法にしている、というのも良い折衷です。カメラ移動中は描画を落とし、Figma に置く画像ではシャドウとエッジを戻す。透明・半透明のマテリアルを含むときは、反射と屈折が破綻しないようにシーンの背景をエクスポートに含める。どれも「レンダラーとして正しいか」より「この画像がキャンバスで使えるか」を基準にした判断です。

後半は紹介サイトの制作記です。構成はレンダーができあがる順序をなぞっていて、素の形に出会い、マテリアルと環境を変え、最後に完成レンダーのカタログにたどり着く。ほぼ真っ暗から始めて情報を一層ずつ足していき、同じオブジェクトが残り続けるので、各決定の効果が読み取りやすくなっています。

いちばん興味深いのはヒーローの判断です。最初はライブの 3D モデルで組んでいて、それは Depth の最も直接的な延長でした。ところがテクスチャと HDRI をいくら変えても、マテリアルとライティングが望む画質に届かない。動作としては正しいのに、頭の中にあった絵ではなく「インタラクティブな 3D の実験」に見えてしまった、と。そこでヒーロー全体をライブでレンダリングするのをやめ、2枚のフレームを生成して Seedance 2.0 で360度の回転を作り、240フレームのシーケンスをマウスの水平位置で制御する形にしています。固定の動画が再生されるのではなく、ページを横切る動きがそのまま島を回す。周囲はリアルタイム 3D のままなので、全体としてはひとつの 3D シーンに見えます。

このハイブリッドにはメディアのコストが伴うので、最初のフレームがシーケンスの準備を待たない設計にしてある、という補足も現実的です。まずポスター画像を描き、横向きと縦向きのメディアを分け、重い部分を後から始める。

マテリアルの遷移も作り込まれています。新しい表面がオブジェクトを渡りきるのに2秒弱かかるけれど、コントロール自体は即座に反応する。遷移は Three.js のひとつの不透明マテリアルの中で、色・粗さ・金属性・表面のディテール・反射をブレンドしてから照明されるので、回転させてもエッジと奥行きが安定する。途中で気が変わって元のマテリアルを選び直すと、そのスイープが現在位置から引き返す。3つめを選べば現在の変化を素早く畳んで次に移る。操作の取り消しがアニメーションの文法として設計されているのが良いところです。

環境の章では、写真的な世界の反射はほしいけれど、その写真を背後に置きたくない、という問題が語られます。雲や雪や地平線が黒い空間を埋めると、サイト全体が普通の 3D ビューポートに見えてしまうから。そこで HDRI は光と反射のためだけに使って見せず、実際に見える山は実地形からサンプリングした点の疎な集まりとして別レイヤーで描いている。形は本物から取りつつ、質感はサイトの視覚言語に合わせる、という分け方です。

UX エンジニアリングの視点で読むと、この記事の主題は 3D ではなく「判断のためのツールと、完成のためのツールは別でいい」という設計判断だと思います。デザイナーが欲しかったのは最終品質ではなく、レビューとレビューのあいだに自分で回せる速度でした。ヒーローの意思決定も同じ構造で、リアルタイムであることより意図した絵であることを優先している。技術的に一貫していることと、見る人にとって良いことは別だ、という割り切りが全体を通して気持ちよく貫かれています。

### [Yestalgia: Bringing Decathlon's '90s Spirit to Life Through a Playful Digital Experience](https://tympanus.net/codrops/2026/09/12/yestalgia-bringing-decathlons-90s-spirit-to-life-through-a-playful-digital-experience/)

> **出典**: Codrops | **公開日**: 2026-09-12 | **カテゴリ**: design

**3行まとめ**
- Decathlon の90年代カプセルコレクションのサイト制作記です。ウォークマン型のメニューが目を引きます
- 見た目より難しかったのは「作り込んだアートディレクションを、クライアントが自分で更新できる形にする」ことでした
- 装飾的なモーションの多くは HTML の data 属性で宣言され、新しい JavaScript を書かずに再利用できます

**詳細解説**

アーカイブのアイテムを現代的に再解釈したコレクションのローンチサイトで、鮮やかなイラストと表情のあるタイポグラフィをそのまま Web に持ち込む、という仕事です。前半はデザイン、後半は実装の話になっていて、後半のほうが読みごたえがあります。

デザイン面での方針は、商品を主役にしたエディトリアルな流れと、タイポグラフィと図形だけが動く純粋にグラフィックな区画を交互に置くこと。後者はキャンペーンのビジュアルを装飾として扱うのではなく、サイトの視覚言語の一部として使うための間奏として機能しています。

ナビゲーションはカセットプレイヤーです。ウォークマンがせり上がってきて、カセットが滑り出し、選ぶとデッキに収まってから本体が落ちて目的のセクションが現れる。この「収まる感じ」を出すために、開発者が最初にデザインどおりの動作版を作り、モーションデザイナーがそこからイージング・ディレイ・デュレーションを大きく作り直し、その設定をコードに戻す、という往復をしています。閉じるときにウォークマンが一度沈んで跳ね返る短いトゥイーンが2つ入っていて、それがカセットのはまる「カチッ」に相当する、という説明が具体的です。ホバーで背景色とそれに対応する夕景レイヤーが入れ替わり、モバイルでは触覚のパルスが返ります。

開発の節の見出しが率直で良いです。「本当の難所は、クライアントが実際に更新できるクリエイティブなサイト」。Yestalgia はフルカスタムテーマの WordPress で、7言語展開。アニメーションは目に見える部分だけれど、より厳しい制約は見えないところにあった、と。そこでサイトの各セクションを Blockstudio のブロック（`json` のスキーマと `twig` のテンプレート）として作り、ページをそれらの組み立てとして構成しています。クライアントは並べ替えも入れ替えもできて、アートディレクションは壊れない。

フロントエンドはネイティブ Web Components の上に作られた piecesjs で、各 `Piece` は自分の JS と CSS だけを遅延読み込みする自律した要素です。プロジェクトをまたいで持ち回っているユーティリティのなかで重要なのが `Scroll` Piece で、Lenis を GSAP ScrollTrigger につなぎ、スクロール関連をすべて data 属性の裏側に集約します。

このアプローチがはっきり出ているのが `c-timeline` です。`data-timeline-from` と `data-timeline-to` に JSON で状態を書き、イージング・デュレーション・縦画面用のバリアント、さらにビューポートのどこで再生を始めてどこで止めるかまでマークアップで宣言できる。コンポーネントがそれをパースして GSAP のタイムラインを組み、`Scroll` Piece が進行度を駆動する。サイト全体で数十のアニメーションがこの方法だけで作られていて、新しい JavaScript は1行も要らない、と書かれています。

もうひとつの「サテライト」は、延々と回転する小さな装飾要素です。それぞれが開始角度と方向をランダムに決めるので同期せず、回転は Tempus というページ全体で共有する単一のアニメーションループの上で動きます。デルタタイムで正規化されているので 60fps でも 120fps でも速度が同じ。ビューポートに入ったら購読し、出たら購読を解除するので、画面外のものはコストゼロになります。

大見出しのリビールも仕掛けが面白いです。疑似的な3Dの厚みが付いているのに、3D はどこにも使われていない。各文字（モバイルでは各単語）が、わずかに後ろを走る複製とペアになっていて、それがエンボスのような奥行きを作ります。文字ごとのスタッガーがリビールを横に歩かせ、文字と複製のあいだのディレイが厚みを生む。フェードインを移動よりずっと速く走らせることで、動きに生気を持たせている、と。

アクセシビリティまわりの扱いに一貫した考え方が見えます。reduced-motion では、見出しのデュレーション・スタッガー・ディレイをすべて 0 にして、組み上がった状態を即座に見せる。Rive のベクターアニメーションのほうは、スキップするのではなく最後のフレームまでスクラブする。つまり「動きを止める」のではなく「デザインされた結果は必ず見せる」という判断です。動きを減らす設定にしている人が、情報や意匠から締め出されない形になっています。Rive のループは IntersectionObserver でゲートされていて、ビューポートを離れた瞬間に停止するので、誰も見ていないモーションに GPU を使わない。

ほかに、GSAP のシームレスループを使った全画面の無限ドラッグカルーセル（1枚おきに逆向きに傾く）、そしてフッターのルックブックがあります。後者は常に1枚だけが開いていて、セクションの総高さが変わらない。ブラウズしても、下にあるコンテンツが飛び跳ねません。画像が開くタイミングを、周囲がすでに押し出されている状態と噛み合わせるのがいちばん難しかった、と正直に書かれています。

技術スタックは、バックエンドが WordPress + Timber + Blockstudio + Polylang、フロントエンドが piecesjs、Tailwind v4、GSAP（ScrollTrigger / Draggable / SplitText）、Lenis、Rive、Tempus、web-haptics、ビルドは vite。

UX エンジニアリングの視点では、この記事の学びは「運用可能性を最初の制約に置く」ことに尽きます。表現の強いサイトは、公開時点を頂点にして、更新のたびに崩れていくのが常です。ブロック単位の構造と、マークアップで宣言されるモーションは、どちらも「編集する人が壊さずに済む範囲」を広げるための投資でした。モーションを data 属性に押し出す設計は、実装者にとっての省力化であると同時に、モーションデザイナーが直接値を触れる場所を作ることでもあります。ウォークマンの往復がまさにそれで、職能の境界を越えて値を渡し合える形になっていたから、あの物理感が出たのだと思います。

### [WCAG 3 Update](https://a11yweekly.com/issue/517/)

> **出典**: Accessibility Weekly | **公開日**: 2026-09-14 | **カテゴリ**: accessibility

**3行まとめ**
- WCAG 3 の新しいドラフトで、適合モデルに「レポーティング階層」が加わりました
- 「すべてを適合の内側で直す」から「柔軟性と調和のバランスを取る」への方向転換です

**詳細解説**

Accessibility Weekly の第517号です。特集は WCAG 3 の適合モデルの更新で、Alastair Campbell のまとめから引用されています。「このドラフトの適合モデルは、すべてを適合の内側で修正しようとするアプローチから、適合と並んでレポーティング階層を設けることで、柔軟性と調和のバランスを取るアプローチへと変わります」。

WCAG 2.x の適合は、ほとんどの場面で二値です。達成基準を満たすか満たさないか。この設計は明快ですが、実務との相性には昔から無理がありました。大規模なサイトで一部のレガシーページが基準を満たせないとき、現行のモデルでは「そのページは非適合」としか言えず、残りの99%で積み上げた改善は表に出てきません。結果として、適合宣言そのものが避けられるか、あるいは実態と乖離した宣言になりがちでした。報告の階層を用意する方向は、その現実に寄せた変更だと読めます。

スポンサー枠として載っている AAArdvark のアクセシビリティスコアの話も、指標設計として読む価値があります。すべてのサイトにスコアが付くけれど、その上限は「実際にどれだけテストしたか」で決まる。自動スキャンだけでは、どれだけ結果がきれいでも B が上限で、そこから上げるには潜在的な問題のレビューと手動テストが必要になる。しかもすべての評価に「自動のみ」「テスト中」「手動テスト済み」のラベルが付き、報告するのは進捗であって適合ではない、と明示されています。「スコアを作ることを何年も拒んできた理由」という記事タイトルも含めて、数値化の副作用に自覚的な設計です。

そのほかに並んでいるもので実務に近いのは、「このメニューはキーボードで動くのか」という記事（大手ブランドの失敗率の話）、Adrian Roselli による 2.1.1 の「specific timings」条項の解説、ブラウザのコンソールを使ったアクセシビリティテストの第2回、4.1.2 の Name, role, value の入門あたりです。Michelle Barker の「Little websites everywhere」と、Matt Rothenberg の「You don't have a design system」も同じ号に載っています。

新しく入った人向けの欄では、Erik Kroes の「アクセシブルな色は存在しない」が紹介されています。ひとつの色だけではアクセシブルになりようがない、という区別の話です。これは実装でよく起きる誤解で、デザイントークンに「アクセシブルなカラーパレット」という名前を付けた瞬間から、組み合わせのコントラストを確認する習慣が抜けていきます。色は単体ではなく、前景と背景の関係としてしか評価できません。

UX エンジニアリングの視点で見ると、WCAG 3 の方向は実装チームにとって歓迎できるものだと思います。ただし報告の階層が入ることで、「進捗を報告している」が「達成した」にすり替わる余地も同時に生まれます。AAArdvark がスコアに上限とラベルを設けているのは、まさにそのすり替えを構造で止める工夫でした。社内のアクセシビリティ指標を作るなら、達成率よりも「どの水準の検証で得た数字か」を一緒に表示する形が参考になります。

**3行まとめ**

操作はキーボード中心です。`t` でタイルが最適なグリッドに自動整列し、`1` から `4` で列数を強制、`n` でサイトを追加、`m` で選択中のタイルを最大化、`f` で全体を収める。

UX エンジニアリングの視点では、これは検証作業のツールとして見るのが良さそうです。地域別の表示、通貨や言語のフォールバック、CDN のエッジごとの差分といったものは、ローカルでは再現しにくく、VPN を切り替えながらの確認はそれ自体が作業になります。同時に並べて見られることの価値は、切り替えの手間が省けることより、違いに気づけることのほうにあります。順番に見ると見落とすものが、並べると目に入る。タブという比喩が担ってきた「同時に開いているが、同時には見えない」という制約に、正面から別解を出している点が面白いところです。

**詳細解説**

求人記事ですが、組織設計の資料として読むと学びがあります。プレイングマネージャーという役割は、たいていの現場で「両方やる人」という形でしか定義されず、結果として個人の頑張りに依存して壊れます。この記事は、それを分担の設計で成立させようとしている点が具体的です。

まず用語から。SmartHR では、2〜5名程度のエンジニアで構成される開発チームをマネジメントするプレイングマネージャーを「チーフ」と呼んでいます。チーフ1名とメンバー2〜4名のエンジニアチームが、プロダクトマネージャー、QA エンジニア、UX ライター、デザイナーと協働してプロダクトを作る、という構成です。UX ライターがチーム構成の前提に入っているのは、この規模の組織としては明快な選択だと思います。

プレイヤー側の期待が「仕様を実装する」で終わっていないのが目を引きます。ユーザーヒアリングや顧客接点を持つ職種との対話を通じて、顧客が達成したいことや業務全体を理解しながら開発する。バックエンドとフロントエンドで担当を分けず、企画・設計・実装・リリース・運用まで職能横断で取り組む。マネジメント側は、担当プロダクトの事業目標を継続的に達成することが目的で、顧客価値や事業インパクトを開発計画に接続する役目と、1on1・目標設定・評価・オンボーディング・チームビルディングが並びます。

両立を支える分担は2つの方向で説明されています。ひとつはマネージャーとの分担で、人員計画・採用・チーム間のリソース調整は部を管掌するマネージャーが責任を持つ。チーフの責任範囲は担当チームの開発成果とメンバーの成長に絞られています。もうひとつはチーム内の分担で、プロジェクトマネジメントやテクノロジーマネジメントはチーフ固有の業務ではなく、最終的にチームで担保できていればよい、という考え方です。チーフ自身が単一障害点になるのを避けるため、メンバーへの移譲を推奨しているとのこと。加えて、チーフ同士が話せる場も用意されています。

担当プロダクトの説明も、技術的な性格がはっきりしています。人事評価は、評価の設計・実施・集計・活用を一元化するプロダクトで、MBO や能力評価、360度評価を自社の制度に合わせて運用できる。開発面では数万人規模のテナントでも安定して動くよう負荷試験と繁忙期対応が要り、現在は3チームで Scrum@Scale を使った並行開発をしています。キャリア台帳は、従業員一人ひとりの人材情報を1ページに集約する機能で、複数のプロダクトで生まれるデータをつなぐため、情報の種類によって開示範囲が変わる閲覧権限の設計が問われる。SLO の運用を通じた非機能品質の向上も挙がっています。

よくある質問の欄も率直です。入社時点でチーフになるわけではなくメンバーとして入ること。チーフの先には部を管掌するマネージャーに進む道と、プレイヤーに軸足を戻す道の両方があること。そしてチーフは役職であって等級とは別の概念なので、役職を降りることがキャリアのマイナスになる構造ではないこと。この最後の点が、この記事でいちばん重要な設計だと思います。役職と等級を結び付けてしまうと、マネジメントを引き受けることが不可逆な選択になり、結果として引き受け手が減ります。

UX エンジニアリングの視点で読むと、「閲覧権限の設計」が開発の難所として名指しされているのが興味深いところです。人材情報のように、同じ画面を見る人によって見えてよい範囲が変わるプロダクトでは、権限は認可の実装であると同時に UI の問題になります。見えないものがあること自体をどう伝えるか、見えない前提で操作を設計できるか。ここは実装とデザインが分かれて考えられない領域で、職能横断のチームを組む理由そのものでもあります。

### [Five eras of UX design and the lessons to keep in the AI era](https://uxdesign.cc/five-eras-of-ux-design-and-the-lessons-to-keep-in-the-ai-era-d76a548747a9/)

> **出典**: UX Collective / Sidebar | **公開日**: 2026-09-14 | **カテゴリ**: design

**3行まとめ**
- Bell Labs 以来、ヒューマンファクターは10年ごとに自分を作り直してきた、という歴史の読み直しです
- 「歴史は繰り返さないが、韻を踏む」ほうの見方を取る、と著者は書いています
- 同じ号には「あなたのプロダクトは悪くなっていない、周りの基準が変わった」など、AI 時代の前提を扱う記事が並んでいます

**詳細解説**

UX Collective の号の巻頭に置かれた Fabricio Teixeira の記事です。本文そのものは取得できていないので、ここでは引用と、同じ号に並んだ記事から読み取れる範囲を紹介します。

引用されているのはこの一節です。「歴史についての有名な言葉が2つあって、UX はどちらにも値する。ジョージ・サンタヤーナは、過去を思い出せない者はそれを繰り返す運命にあると書いた。マーク・トウェインのものとされる版はもっと穏やかで、歴史は繰り返さないがしばしば韻を踏む、という。私はこちらのほうが好きだ」。副題は「ヒューマンファクターは Bell Labs 以来10年ごとに自分を作り直してきた。もっとも古い教訓こそが前に進む道を指している」となっています。

AI の登場を「これまでにない断絶」として語る記事が多いなかで、10年ごとの作り直しの系譜として置き直す構えは落ち着いています。韻を踏むほうを選ぶという表明も、繰り返すのでも無関係でもない、という中間の立ち位置を取るための言い方でしょう。

同じ号で目を引いたのは、Waldek Mastykarz の「Your product didn't get worse」です。「あなたのプロダクトは悪くなっていない。いまも仕事をこなすし、顧客が期待するとおりに動くし、乗り換える理由もない。ところが顧客が別のところでエージェントを使いはじめると、あなたのプロダクトの周りの基準が変わる。旅行を調べてもらう、ファイルを整理してもらう、別のプロダクトで変更を加えてもらう。以前はアプリを開いて複数の画面をまたぐ作業が必要だった仕事が、一文になる」。自分のプロダクトを何も変えていないのに相対的な評価が下がる、という現象を過不足なく言い当てています。

Lightspark の「Limit the number of details」も良い引用でした。「前半は注意を引くが、後半がそれを可能にする。ディテールが少ないほど、ひとつひとつを深く気にかけられる。ディテールというのは小さな視覚的判断だけを指すのではない。すべての機能、コントロール、モード、状態、例外、振る舞いの断片が、チームの誰かが設計し、誰かが理解しなければならないものになる。注意は有限だ。時間も、趣味も、忍耐も同じように」。機能の追加を「作る工数」ではなく「理解の総量」で数える見方で、デザインシステムのバリアントが増え続けるときにも同じ話が当てはまります。

Jenny Wanger の「Burnt out on a three-day week」は、燃え尽きへの一般的な助言（休む、PTO を取る、瞑想する、カレンダーを軽くする、それでだめなら転職する）が必ずしも問題を解決しないことを、コーチングの現場から書いたものです。

そのほかに並んでいるのは、1980年代のコピー機がエージェンティック UX について教えてくれること、2026年の AI がプロダクトチームの協働に与えている影響、下書きにログが付くようになった話（職場の監視が最後の領域に到達した、という論調）、データでできたロゴの小史、テトリスがランダムに感じさせるために不正をしていた話、iPod の終わり、情報アーキテクチャが整っていないときにモデルだけが完璧に振る舞う話、感情を指標にしたときに起きる追従の罠、音声 AI の UX パターン8つ。タイトルの並びだけでも、この号が何を気にしているかが伝わってきます。
