### [design-loop: Claude Codeを使ったブラウザベースのビジュアル編集ツール](https://efcl.info/2026/02/22/design-loop/)

> **出典**: Web Scratch | **公開日**: 2026-02-22 | **カテゴリ**: frontend

**3行まとめ**
- ブラウザ上でサイトをプレビューしながら要素をクリックし、その情報をClaude Codeへ直接渡せるビジュアル編集ツール
- HTTPプロキシ + Bun + ghostty-webという構成で、既存の開発サーバーに手を加えず動作する
- Design Modeではテキスト編集やドラッグ&ドロップの変更をバッチでClaude Codeに送り、ソースコードへ反映できる

**詳細解説**

azuさんが公開したdesign-loopは、「ブラウザでサイトを見ているコンテキスト」と「コードを指示するコンテキスト」の分断を解消するツールです。開発中のサイトを確認しながら「このボタンのスタイルを変えたい」と思ったとき、DevToolsで要素を調べてファイルを特定し、Claude Codeに言葉で説明する…という手間を省きます。

技術的にはHTTPプロキシサーバーが開発サーバーへのリクエストを中継し、HTMLにスクリプトを動的に注入する仕組みです。注入スクリプトがクリックされたDOM要素のCSSセレクタ、React Fiberから取得したコンポーネント情報、計算済みスタイル、ARIAスナップショットなどを収集します。React Fiberの`__reactFiber$`を辿ってコンポーネント名やソースファイルのパスを取得するアプローチは、Claude Code DesktopのPreview機能やFigma連携でも採用されており、同じ課題に対して自然と収束するアーキテクチャといえます。

v1.3.0で追加されたDesign Modeでは、テキストの直接編集や要素のドラッグ&ドロップといったGUI操作を構造化されたコマンドとして蓄積し、「Apply Changes」でまとめてClaude Codeに送信します。同じ要素への複数回の編集は最初のbeforeと最後のafterに圧縮されるなど、正規化処理も入っています。

UXエンジニアリングの観点で注目したいのは、設計思想の違いです。Claude Code DesktopのPreviewが「プロンプト環境が主体」であるのに対し、design-loopは「プレビューが主体でプロンプトは手段」という位置づけです。非エンジニアが複数のウィンドウを行き来すると混乱するという観察から、1つの画面で完結する体験を重視しています。デザイナーとエンジニアの協業ツールとして、こうした統合的なアプローチは今後ますます増えていくでしょう。

### [text-scale によるユーザ指定倍率での文字拡大](https://blog.jxck.io/entries/2026-02-11/text-scale.html)

> **出典**: blog.jxck.io | **公開日**: 2026-02-11 | **カテゴリ**: web-standards

**3行まとめ**
- モバイルOSの文字サイズ設定がWebコンテンツに反映されない問題を解決する新しい標準仕様の解説
- `<meta name="text-scale" content="scale">`で、OSの拡大率をページに反映する意思表示ができる
- `env(preferred-text-scale)`を使えばCSSから拡大率を取得でき、`clamp()`やStyle Queryと組み合わせた細かな制御も可能

**詳細解説**

モバイル端末で文字サイズを大きく設定しても、多くのブラウザはそれをWebページに反映しません。レイアウトが崩れるサイトが多いため、歴史的にブラウザ側が慎重になってきたという背景があります。代わりにフルページズームや拡大鏡を提供してきましたが、アクセシビリティ上の問題は長く認識されていました。

この記事では、問題を解決するためのいくつかのアプローチを整理しています。AppleのDynamic Typeは`font: -apple-system-body`でOS設定に連動しますが、Safari独自の仕組みです。ブラウザ横断で使えるものとして、`env(preferred-text-scale)`が提案され、現在Android Chromeで対応しています。そしてページ単位でオプトインする`<meta name="text-scale" content="scale">`という宣言的な仕組みも策定が進んでいます。

実装面で興味深いのは、非線形スケールの議論です。ユーザが200%に拡大したとき、`medium`サイズの本文は2倍でよくても、`xxx-large`の見出しまで2倍にするとView Portを占有してしまいます。そのため、サイズに応じて拡大係数を変える非線形スケールの導入が検討されています。

UXエンジニアとしては、`rem`/`em`で相対指定していれば安心…というわけではない点に注意が必要です。borderやmarginまで一律に拡大されると余白が無駄に増え、かえって読みづらくなります。文字サイズには`rem`、余白には`vw`/`vh`、線の太さには`px`というように、拡大時の振る舞いを意識した単位の使い分けが求められます。`clamp()`での上限設定やStyle Queryでの拡大率に応じた分岐といった実践的なテクニックも紹介されており、今後の対応指針として参考になります。

> **出典**: css-tricks | **公開日**: 2026-02-17 | **カテゴリ**: css

**3行まとめ**
- Chrome、Safari、Firefoxの3大ブラウザエンジンが協力し、CSS新機能のクロスブラウザ対応を推進するInterop 2026が始動
- Anchor Positioning、Container Style Queries、Scroll-driven Animations、View Transitionsなど注目機能が対象
- `contrast-color()`、`shape()`関数、メディア擬似クラスなど、表現力を大幅に広げる機能も含まれる

**詳細解説**

毎年恒例のInteropプロジェクトですが、2026年版はCSS開発者にとって待望の機能が数多く含まれています。Blink（Chrome/Edge）、WebKit（Safari）、Mozilla（Firefox）の3エンジンが、仕様の一貫した実装に取り組みます。

Anchor Positioningは、要素を別の要素に対して相対配置するためのCSS機能です。ツールチップやポップオーバーの実装が大幅に簡単になります。Container Style Queriesは、サイズだけでなくスタイル値に基づいてコンテナを照会できるようになるもので、たとえば「親がダークモードならこのスタイルを適用」といった指定が可能です。

`contrast-color()`関数は、背景色に対して白か黒かを自動判定して前景色を返す機能です。後述する別記事でも代替実装が紹介されていますが、ネイティブ対応が進めば、動的なカラーテーマの実装がずっと簡潔になります。メディア擬似クラス（`:playing`、`:paused`、`:buffering`など）や`shape()`関数など、UIの表現力を根本から拡張する機能もそろっています。[Interop 2026 Dashboard](https://wpt.fyi/interop-2026)で進捗を追えます。

### [Approximating contrast-color() With Other CSS Features](https://css-tricks.com/approximating-contrast-color-with-other-css-features/)

> **出典**: css-tricks | **公開日**: 2026-02-12 | **カテゴリ**: css

**3行まとめ**
- `contrast-color()`がまだ主要ブラウザで使えないなか、既存のCSS機能だけで代替する方法を解説
- OKLCHの明度値と`round()`関数を組み合わせた1行の式で、背景色に応じた白黒の自動切り替えを実現
- `color-mix()`を応用すれば、白と任意のベースカラーの切り替えにも拡張できる

**詳細解説**

配色が動的に変わるUIで「背景色に応じてテキストを白か黒にする」というニーズはよくあります。CSS Color Level 5で`contrast-color()`が提案されていますが、まだSafariとFirefoxのみの実装です。この記事は、今すぐクロスブラウザで使える代替手法を段階的に解説しています。

まずWCAG 2.2の輝度計算式をCSSの`pow()`と`round()`で再現するアプローチが示されます。動くものの、式が長く保守性に問題があります。そこで著者はOKLCH色空間の明度値（L）に着目します。OKLCHのLは知覚的な明るさを表すため、APCAのコントラスト計算と相性がよいのです。

閾値を0.72と定め、`oklch(from <your color> round(1.21 - L) 0 0)`というたった1行でAPCAに近い白黒判定が実現できます。1.21は「0.72で切り捨て、0.71で切り上げ」になる計算上の調整値です。LCHよりOKLCHのほうが閾値の振れ幅が小さく、APCAとの整合性が高いことも検証されています。

さらに`color-mix()`を組み合わせて、白と任意のベースカラー（たとえば本文のデフォルト色）の切り替えに拡張する手法も示されています。デザインシステムでカスタムカラーのタグやバッジを扱うとき、この手法は重宝するでしょう。ただしWCAGとAPCAで判定が異なるケースがある点は注意が必要です。

> **出典**: css-tricks | **公開日**: 2026-02-21 | **カテゴリ**: css

**3行まとめ**
- ポインタが要素の近くにあるときにマッチする`:near()`擬似クラスの提案を、ユースケースとともに紹介
- 視覚効果の段階的な適用、要素の事前表示、Speculation Rules APIとの連携など、応用可能性は幅広い
- アクセシビリティ上の懸念（hoverやfocusとの混同、ターゲットサイズの扱い）も丁寧に整理されている

**詳細解説**

`:near()`は、ポインタが要素から指定距離以内にあるときにマッチするCSS擬似クラスの提案です。`button:near(3rem)`のように記述し、ホバー前の「近づいた」段階でスタイルを適用できます。Thomas Walichiewiczによる提案で、まだどのブラウザにも実装されていませんが、その可能性は興味深いものです。

アクセシビリティの観点では、`:near()`が`:hover`や`:focus`と混同されないよう、「先取り的（preemptive）か推定的（presumptive）か」を自問する必要があるという指摘が重要です。WCAG 2.5.8のTarget Sizeとの関係も曖昧さが残ります。インタラクションの「予兆」をデザインするという概念は、UXエンジニアリングの視点からも探求の余地がある領域です。

### [Making a Responsive Pyramidal Grid With Modern CSS](https://css-tricks.com/making-a-responsive-pyramidal-grid-with-modern-css/)

> **出典**: css-tricks | **公開日**: 2026-02-12 | **カテゴリ**: css

**3行まとめ**
- CSS Gridと`sibling-index()`、`if()`関数を組み合わせて、メディアクエリなしでレスポンシブなピラミッド型グリッドを実装
- 三角数の数式をCSSの`calc()`/`sqrt()`/`mod()`で表現し、nth-childの列挙を3行に圧縮
- ピラミッドが収まりきらない幅では自動的に通常のグリッドに切り替わる

**詳細解説**

Temani Afifによる、CSSだけで数学的なグリッドレイアウトを実現するシリーズの最新作です。ヘキサゴン（六角形）をピラミッド状に配置し、画面幅が足りなくなると自動的に通常のグリッドに切り替わるレスポンシブな実装を、メディアクエリもJavaScriptも使わずに実現しています。

核心は`grid-column-start`の計算です。ピラミッドの各行の先頭要素（1, 2, 4, 7, 11…）は三角数の公式`j*(j+1)/2 + 1`で表せます。この逆関数`sqrt(2*index - 1.75) - .5`を`sibling-index()`で得たインデックスに適用し、結果が整数かどうかを`mod()`で判定、CSS `if()`で条件付きに`grid-column-start`を設定します。

レスポンシブ対応では、コンテナクエリの`100cqw`を使ってコンテナ幅から収容可能なアイテム数を算出し、ピラミッド部分と通常グリッド部分の2つの条件を`if()`のカスケードで処理します。負の値を`max(0, ...)`で無効値`0`に変換し、ブラウザにデフォルト配置へフォールバックさせるテクニックも巧みです。

`corner-shape`、`sibling-index()`、unit divisionなどChrome限定の機能を使っている点は留意が必要ですが、CSSが「計算と条件分岐の言語」へ進化していることを実感できる記事です。5年前の同等実装と比較するとコードの簡潔さが際立ちます。

### [Spiral Scrollytelling in CSS With sibling-index()](https://css-tricks.com/spiral-scrollytelling-in-css-with-sibling-index/)

> **出典**: css-tricks | **公開日**: 2026-02-18 | **カテゴリ**: css

**3行まとめ**
- `sibling-index()`と`scroll-timeline()`を組み合わせ、テキストが渦巻き状にスクロールするエフェクトをCSSだけで実装
- JavaScriptは文字の分割のみに使用し、アニメーション制御はすべてCSS（scroll-driven animations）で実現
- `sibling-index()/sibling-count()`の比率で各文字のスケール、回転角、フェードインタイミングを段階的に変化させる

**詳細解説**

JavaScriptで作られた印象的なスクロールテリングサイトへのオマージュとして、CSSの新機能で同等の表現を再現する挑戦です。元のサイトでは「文字ごとにエフェクトをかけるとパフォーマンス負荷が天文学的になる」とされていたものを、CSS scroll-driven animationsで滑らかに動かしています。

`sibling-index()`と`sibling-count()`の組み合わせが鍵です。`startValue - (reductionValue/sibling-count() * sibling-index())`という汎用的なパターンで、各文字のスケール、中心からの距離、回転角を段階的に減少させています。三角関数を使わずに渦巻きを表現しているのも興味深い点です。

各文字のフェードインは`animation-range-start`を`sibling-index()`の比率でずらすことで実現しています。スクロールに連動して文字が順にフェードインしていく演出は、コンテンツの読了進捗を視覚化する応用にもつながりそうです。

`sibling-index()`がBaselineになれば、これまでJavaScriptでしか実現できなかった「要素のインデックスに基づくスタイリング」の多くがCSSで代替可能になります。パフォーマンスの観点からも、メインスレッドを占有しないCSS animationsの優位性は大きく、モバイル対応が困難だったリッチなスクロール表現の実用性が高まります。

### [Distinguishing "Components" and "Utilities" in Tailwind](https://css-tricks.com/distinguishing-components-and-utilities-in-tailwind/)

> **出典**: css-tricks | **公開日**: 2026-02-19 | **カテゴリ**: css

**3行まとめ**
- Tailwindにおける「コンポーネント」と「ユーティリティ」の区別は本質的なものではなく、語源的にはどちらも同じ
- `@utility`でコンポーネント的なスタイルグループを定義し、`!important`修飾子で上書きする方が`@layer components`より簡潔
- コンポーネントとユーティリティの唯一の実用的な違いは「上書き可能性」にある

**詳細解説**

Zell Liewによる短くも本質的な記事です。Tailwindでは`@utility card { ... }`と書けばコンポーネント的なスタイルグループを作れるため、「コンポーネント」と「ユーティリティ」の境界が曖昧になっています。

語源に立ち返ると、Componentは「より大きな全体の一部」、Utilityは「役に立つもの」です。つまりユーティリティもコンポーネントの一部であり、コンポーネントも役に立つものです。この区別はフレームワークのマーケティング上の便宜にすぎないと著者は指摘します。

実用上の唯一の違いは、コンポーネントスタイルをユーティリティで上書きしたい場面です。従来は`@layer components`にスタイルを書く必要がありましたが、`@utility`として定義し、HTMLで`!important`修飾子（`!border-blue-500`）を使えば同じことが実現できます。ファイルごとに`@layer components`を書く冗長さや、余分なインデントを避けられます。

TailwindとネイティブCSSの使い分けを考えるうえで、こうした概念の整理は有用です。とくにデザインシステムを構築する際、「何をコンポーネントとし、何をユーティリティとするか」という分類に悩むことがありますが、上書き可能性という観点で判断するのがもっとも実践的でしょう。

**詳細解説**
