### [A properties panel and annotations, now in Figma Make](https://www.figma.com/blog/properties-panel-and-annotations-now-in-figma-make/)

> **出典**: Figma Blog | **公開日**: 2026-07-30 | **カテゴリ**: design

**3行まとめ**
- Figma Make のエディタに、Figma Design と同じ感覚で余白・タイポグラフィ・レイアウトを触れるプロパティパネルが付いた
- 見た目以外の変更（インタラクションやアニメーション）は、キャンバス上に番号つきの注釈を置いてエージェントに文脈を渡す
- 直接操作はプロンプトより対象がはっきりしているぶん、同じ変更でも消費トークンが少なく速い。編集はチャットに積まれ、適用するまでクレジットは減らない

**詳細解説**

Figma Make は、プロンプトからコードを生成して動くプロトタイプを組み立てるエディタです。今回加わったのは、そこに「言葉で頼まずに直接触る」経路を通す2つの機能でした。

プロパティパネルでは、行間や字間から不透明度、z-index、ボーダーのスタイルまで調整できます。DOM ツリー（コードに対するレイヤーパネル、という説明のしかたが的確です）を見ながら作業でき、ある要素のすべてのインスタンスをまとめて選んで一括で更新することもできます。編集内容はコードベースにすでに定義された色とタイポグラフィのトークンを使う、と明記されているのが重要なところでしょう。Code Connect との連携も予告されていて、そちらが入ると Figma Design 側のコンポーネントとも結び付くようになります。

注釈のほうは、位置は正確に指しつつ、変更内容は自分の言葉で説明できる仕組みです。記事に挙がっている例が具体的で、「このサムネイルにホバーしたら少し拡大する」「このボタンを300ミリ秒遅らせてフェードインさせる」「タップしたときに控えめな押し込み効果を足す」といった依頼を、対象を指し示したうえで書けます。エージェントは印を付けた範囲の文脈を読み、選択したすべての要素にコード側の変更を反映します。

UXエンジニアリングの視点で面白いのは、「言葉で言ったほうが速いこと」と「指したほうが速いこと」の境界に、クレジット消費という測れる指標が乗ったことです。記事は「直接操作はエージェントに正確な対象を渡すので、テキストプロンプトが必要とする探索と推測がいらない」と説明しています。設計の意図をどこに書くかという話が、そのままコストの話になっている構図です。編集がプロンプトボックスに積まれ、適用するまでクレジットを消費しない点も、試行の回数を確保するうえで効いてきます。ただし、プロパティパネルは新しく作った Make のデザインでのみ動き、以前に作ったものは従来の編集ツールのままです。両機能ともクレジットを消費する点も押さえておきたいところです。

### [Building an Infinite GSAP Scroll Gallery with Parallax and Flip Transitions](https://tympanus.net/codrops/2026/07/30/building-an-infinite-gsap-scroll-gallery-with-parallax-and-flip-transitions/)

> **出典**: Codrops | **公開日**: 2026-07-30 | **カテゴリ**: design

**3行まとめ**
- 一時停止した GSAP タイムラインのプレイヘッドをスクロール位置として扱い、無限スクロールを組む。100px = プレイヘッド1秒という換算レートを両側で共有する
- パララックスのオフセットを「ラップする瞬間にゼロになる」式にすることで、継ぎ目が見えなくなる
- 詳細ビューへのモーフは Flip の `data-flip-id` を2つの要素で共有させる。ID の付与は `Flip.getState()` より前でないと、エラーも出ずに何も起きない

**詳細解説**

Surya Aditya による、散らばった画像が無限に流れ、クリックすると詳細ビューへ拡大するギャラリーの実装解説です。使うのは GSAP と素の JavaScript だけで、入力に `Observer`、モーフに `Flip`、テキストの表示に `SplitText` という構成になっています。

土台になっているのが、ブラウザのスクロールを使わないという判断です。`overflow: hidden` でネイティブのスクロールを止め、代わりに全スライドが1周する一時停止済みタイムラインを作り、そのプレイヘッドをスクロール位置として扱います。各アイテムには2つのトゥイーンがあり、上端を抜けるまで動くものと、すぐ下端から再入場するものです。位置の指定に `y` ではなく `yPercent` を使うのは、要素自身の高さに対する相対値なのでサイズが揃っていなくても値が保つから。パララックスのほうは `y` を書き、GSAP が両方を同じ transform に合成します。この分担がきれいです。

読んでいていちばん学びが多いのは、失敗の形が全部書いてあるところでしょう。`immediateRender: false` がないと初回フレームで全アイテムが下端へ飛ぶ。`tl.progress(1, true).progress(0, true)` で全トゥイーンを一度描画しておかないと、実フレームで初期化に捕まる。パララックスを単純に `progress * factor` で当てると、ラップの瞬間にオフセットが最大になるので毎回跳ねる。だから「ビューポート上端からスライド下端までの距離」を掛ける式にして、継ぎ目でちょうどゼロになるようにする。`getBoundingClientRect()` は前フレームで当てたオフセット込みの値を返すので、引き算で純粋なループ位置に戻してから計算しないと、オフセットが積み上がって1秒ほどで画面外へ飛んでいく——このあたりは実際に踏まないと気づきにくい話です。

演出の順序についての記述も具体的です。表示アニメーションのスタッガーは、DOM 順ではなく画面上の `top` でソートしてから当てます。無限ループでは DOM の並びと画面の並びが一致しないため、これをしないとカスケードの向きが崩れます。詳細ビューへのモーフは1.2秒の `power4.inOut` で、外側の枠が広がるあいだに内側の画像を `scale: 1.2` から `1` へ戻すことで、枠と中身が別の速さで動いて「収まっていく」ように見せる。テキストは0.8秒地点から入れて、モーフの3分の2あたりに重ねる。ゼロから始めると画面がうるさく、終わるまで待つと遅く感じる、という理由付きです。

UXエンジニアリングの視点では、著者が自分の妥協も書き残している点が信頼できます。`config.speed` は一見つまみに見えるけれど、実際は2つのファイルに散った「100」が1つの数字なので、`speed: 2` にすると速さではなく感度が倍になる。パララックスの速度配列は6枚周期なので、1枚目と7枚目が同じ動きになる。継ぎ目の余白だけ 26vh と広いが、繰り返しに気づく瞬間の間として残した。動くデモを作るだけなら書かなくてよい情報で、ここが読みどころです。

### [10 チーム同時のハッカソンを支えた Kubernetes + Argo CD の GitOps プレビュー環境「3A」の紹介](https://tech.layerx.co.jp/entry/ai-workforce-gitops-for-hackathon2026)

> **出典**: LayerX エンジニアブログ | **公開日**: 2026-07-31 | **カテゴリ**: engineering

**3行まとめ**
- 半日の事業部内ハッカソンのために、Kubernetes + Argo CD の GitOps で10チーム分の独立した環境を立ち上げた記録
- 立ち上げは Argo CD 向けの PR を作ってマージするだけ。筆者自身は `kubectl` もほとんど叩かず、YAML も書いていない
- オンデマンドインスタンスへの配置、ゴールデンイメージからのデータ複製、worker 数の引き上げ——いずれも Custom Resource に数行足すだけで済んだ

**詳細解説**

LayerX の Ai Workforce 事業部で Technical Product Manager を務める riywo さんによる記事です。10年ほど前にコンテナオーケストレーションのサービスを扱っていた頃は運用のハードルの高さから Kubernetes を薦めていなかった、という書き出しから始まります。

プレビュー環境「3A」は、Kubernetes クラスタ上の Argo CD による GitOps で、Ai Workforce のインスタンスを自由に上げ下げできる仕組みです。通常環境は Kubernetes を使っていないものの、3A ではデータベースからドメインまでほぼフルスタックを Kubernetes 上に立ち上げています。管理 UI もあり、そこからの作成・削除も結局は PR とマージになるので、何が行われたかは GitHub の履歴から辿れます。PR に preview ラベルを付けるとそのブランチの環境が自動で立ち上がる、トピックブランチに追従する環境を持てる、main にマージせず PoC 環境を用意できる、といった使われ方に育っているそうです。

ハッカソン向けの調整が3つ紹介されていて、どれも Custom Resource へ数行という粒度で収まっているのが目を引きます。普段はコストを抑えるためスポットインスタンスに載せているところを、半日は安定して動いてほしいのでオンデマンドのプールを別に作って配置する。10環境ぶんの初期設定を手作業でやるとミスが出るので、設定済みの環境をゴールデンイメージにしてデータを複製する。1チーム6〜7名が同時に触るので worker 数を引き上げる。特に2つ目は、設定をやり直すたびに環境ごと作り直すという運用が現実的になっている点が効いています。

後半の主張は、GitOps + Kubernetes とコーディングエージェントの相性についてです。定型的な YAML の作成・変更はエージェントと相性が良い。「なんだかアプリの挙動が変だ」と伝えるだけで `kubectl` でログやリソースを集めて切り分けてくれる。そして Argo CD の GitOps は、今の状態に関係なく「こうしたい」という意図を更新でき、宣言した状態へ継続的に収束させてくれる——この性質がエージェントと噛み合う、という整理です。

UXエンジニアリングの視点で拾いたいのは、この結論が成り立っている前提が明記されていることでしょう。SRE が設計・検証・権限管理まで含めて基盤を作っていて、エージェントの出力は人間がレビューし、変更履歴が残る形で適用されています。`kubectl` を活用するための skill（エージェント向けにまとめた調査手順とツール定義）も配布されていました。エージェントが学習コストの高い領域のハードルを下げるのは確かですが、下がるのは「基盤と安全な変更経路が先にある場合」に限られる、という読み方が正確だと思います。

### [How to research technical topics with AI](https://www.0xkato.xyz/how-to-research-technical-topics-with-ai)

> **出典**: Sidebar | **公開日**: 2026-07-30 | **カテゴリ**: design

**3行まとめ**
- 「LLM はどう動くのか」は広すぎた。プロンプト入力から次トークン予測までに範囲を絞って、はじめて調べる順序が決まった
- ノートには「正確な技術的主張と出典」と「腑に落ちたいちばん簡単な説明」を分けて書く。簡略化を文字どおりの説明として扱わないため
- チャットはソースではない。書き始める前にチャットを閉じ、白紙から再構成できるか試す

**詳細解説**

LLM の仕組みを解説する記事を書くまでに、AI をどう使ったかを段階ごとに書き起こした記事です。手順そのものより、各段階で「何をしないか」を決めているところに読み応えがあります。

出発点は問いの絞り込みです。「LLM はどう動くのか」は学習、ハードウェア、トークナイゼーション、推論、アライメント、スケーリング則……どこへでも行けてしまい、モデルはそれらしいツアーを組めるけれど、どれ一つ理解できない。プロンプト入力から次トークン予測までに区切ると、始まりと終わりが決まり、同時に順序も決まりました。トークナイゼーション、埋め込み、位置情報、アテンション、生成ループという並びです。次に、絞った問いをモデルに渡して「どの概念に依存するか、何を先に理解する必要があるか、どこがまだ曖昧か」を聞き、順序付きの調査リストへ変えます。

用語の見つけ方の記述が実感に合っています。何に混乱しているかは分かっていても、それが何と呼ばれているかは知らないことが多い。「モデルはどの単語が先に来たかをどうやって知るのか」という言い方から positional encoding へ辿り着き、絶対位置、相対位置、RoPE という語彙を手に入れた。そこではじめて論文やドキュメントやコードを検索できるようになる、という順番です。モデルが出典を勧めてきたら、開く前に「そこに何が書いてあるはずか」を聞く。論文は定義を、ドキュメントは現在の実装を、コードはどちらも省いた細部を教えてくれる——という使い分けも書かれています。

批評の頼み方が独特です。自分の説明を渡して「技術的に何が間違いで、何が妥当な簡略化で、どこから誤解を招くか」を聞くが、書き直しは頼まない。すぐに置き換えられると、なぜ自分の説明が失敗したのか分からないまま新しい文言に同意してしまうから。マルチヘッドアテンションの例が挙がっていて、「トークンベクトルを分割して各ヘッドに配る」という説明は覚えやすいけれど誤った像を残す。各ヘッドは学習された射影を持つ別の見え方であって、元のベクトルの意味的な切れ端ではない、という区別です。反証を探す段では、同じ会話に「あなたは自分に同意しますか」と聞かない、というルールも置かれています。検索語を変え、後発の研究を見て、別のモデルや、それまでの議論を見ていない読者に渡す。

UXエンジニアリングの視点で持ち帰りたいのは、ノートを2列に分ける発想です。片方は正確な主張と出典、もう片方は自分に効いた説明と、その説明が効かなくなる境界。この形はそのまま技術ドキュメントの書き方に移せます。「アテンションヘッドは特化する」ではなく「部分的に特化する」に絞ったという例のように、言葉を弱める判断も記録に残る。エージェントの出力を検証する日常の作業とほぼ同じ手順なので、読んで損のない記事だと思います。

### [You don't have to be smart if you can think clearly](https://www.seangoedecke.com/you-dont-have-to-be-smart-if-you-think-clearly/)

> **出典**: Sidebar | **公開日**: 2026-07-30 | **カテゴリ**: design

**3行まとめ**
- 「賢い」エンジニアと「強い」エンジニアの差は、すぐに解けない問題に出会ったときの反応に出る
- 賢いエンジニアははっきり考えられるが、高速でしかそれができない。F1カーは最高速は高いが、街中の速度ではタイヤもブレーキも効かない
- 足がかりは invariant。絶対に偽ではない前提を見つけて、そこに立って怪しい前提のほうを評価する

**詳細解説**

Sean Goedecke による短いエッセイです。調子の良いときは問題が透明になって、重なった層でも積んだガラス板のように見通せる。でも誰もいつもそう働けはしない、という書き出しから始まります。

指摘されているのは、即座に解が見える経験を積んだエンジニアほど、それが効かない場面で崩れやすいという話です。難しい問題である必要すらなく、何かの理由でコツが見えなかっただけでいい。賢いエンジニアは逃した閃きを求めてもがき、強いエンジニアは淡々と進める手順を持っている。そして、粘る筋力がないと、ありうる解のどれでも正解として受け取ってしまう誘惑が強くなる。自分の職業的な自己像が「問題を簡単に解けること」に結び付いているぶん、うろたえやすい、と続きます。

不足している技能は「ゆっくり、はっきり考える力」だという結論に至ります。以前の記事で書いた invariant の話がここで再登場します。行き詰まるのはたいてい、置いた前提のどれかが偽だから。偽ではありえない前提（サービスからエラーメッセージが返っているなら、サービスはリクエストを処理している、といった類）を特定できれば、そこが足場になって、信頼度の低い前提を評価できる。速く考えることは頭にデータを詰め込んで直感に跳ばせることですが、跳ばずに生データと座っているのは満足感がなく、人はそれを嫌う。だからこそ、そこに価値が残っている、という論の運びです。読者から「これは Keats の negative capability のことでは」と指摘があった、という追記も付いています。

UXエンジニアリングの視点で言えば、この文章はエージェントと働く日常にそのまま重なります。もっともらしい解を高速に何通りも出せる相手が横にいる状況は、まさに「ありうる解のどれかを正解として受け取ってしまう」圧が高い状態です。速さが外注できるようになったぶん、残る仕事は不確かさのなかで座っていられるかどうかに寄っていく。短い文章ですが、読み返す価値のある一本でした。

### [Personal website redesign project post: Getting started with implementing my music collection](https://piccalil.li/projects/personal-site/8/)

> **出典**: Piccalilli | **公開日**: 2026-07-30 | **カテゴリ**: css

**3行まとめ**
- 個人サイト改装記の8回目。3つのコンテンツソースが並ぶ状態を、いまは受け入れる妥協だと明言している
- 音楽コレクションは markdown + フロントマター。Astro の Content Collections で zod のスキーマを定義し、後で AT Protocol の PDS へ移すときは一度きりのスクリプトで済む
- ナビゲーションのラベル件数は reducer ではなく switch 文。読みやすいほうを選ぶ、という判断を明示している

**詳細解説**

Andy Bell による個人サイト改装シリーズの一本で、イテレーション1の骨組みづくりも終わりに近づいた回です。本人が「サイト全体のなかでもっとも大事な部分」と呼ぶ音楽コレクションの実装に入ります。

コンテンツソースが3つに分かれていることの説明が率直です。ブログは18年使ってきた WordPress から長期的には離れるつもりで、注目しているのは AT Protocol。いずれブログも音楽コレクションも自分の Personal Data Server（PDS）で管理できるはずだけれど、プロトコルにはもう少し時間と進化がほしい。だから当面のコンテンツ分断は許容する——「クライアントと何度も交わす類の妥協だ」と書いています。markdown とフロントマターを選んだのはその文脈で、Eleventy から Astro への移行は `date` を `pubDate` に置き換えるだけで済み、Content Collections からデータを取り出して PDS へ移すのも一度きりのスクリプトで足りる、という見立てです。

実装は小さな部品の積み上げです。`MusicCollectionLayout.astro` は props から「単一アイテムを描画しているのか、フィードを描画しているのか」を判断し、`<MusicItemDetail>` を出すかどうかを決めます。ナビゲーションはリンクの静的な配列を持ち、`switch` 文で各ラベルに件数を足してから既存の `<Navigation>` に渡す。「reducer か何かで賢く書けるはずだけれど、消化しやすい `switch` のほうをいつでも選ぶ」と本人が書いています。カード領域は見出しの有無で `region` ユーティリティを付け外しし、縦の余白だけ切り替える。骨組みの段階なので、実際の UI ができるまでのセパレータには `<hr />` を置いている、という状態も正直に見せています。

UXエンジニアリングの視点で言えば、音声インターフェースの体験を決めるのは、モデルの賢さよりも「間」の設計だと思います。人は0.5秒の沈黙にも敏感で、そこで相手が考えているのか止まっているのか分からないと会話のリズムが崩れる。発話と推論を並行させる、ツール呼び出しを早めに投げる、というのはどちらもその間を詰めるための工夫です。書き起こしが電話回線の圧縮に耐えるという点も、実際に音声エージェントを電話窓口に載せる場面ではかなり効いてきます。

### [Turborepo and Vercel Remote Cache now support OpenID Connect (OIDC)](https://vercel.com/changelog/turborepo-and-remote-cache-now-support-openid-connect-oidc)

> **出典**: Vercel | **公開日**: 2026-07-30 | **カテゴリ**: frontend

**3行まとめ**
- CI/CD ワークフローの OIDC トークンを、短命の Turborepo アクセストークンと交換できるようになった
- 長命の Personal Access Token より安全。権限が Remote Cache に限られ、個人ではなく Vercel のチームに紐づく
- 設定は Settings → Build and Deployment の OIDC Policies から。GitHub Actions 向けの action も用意されている

**詳細解説**

Turborepo の Remote Cache へのアクセスに、OIDC を使った短命トークンの発行経路が追加されました。すべての利用者に対して PAT からの移行が推奨されています。

実務上のポイントは、トークンが個人ではなくチームに紐づくところだと思います。モノレポの Remote Cache は、誰かの Personal Access Token を CI の Secret に入れたまま動き続けている、という状態になりがちです。その人が退職したりトークンを再発行したりした瞬間にキャッシュが効かなくなり、原因を追うのに時間がかかる。CI が急に遅くなった理由が権限だった、という話は珍しくありません。

権限の範囲が Remote Cache だけに限られる点も効きます。PAT はアカウント全体に対する鍵なので、CI の環境変数から漏れたときの影響範囲が広い。OIDC トークンは短命かつ用途が絞られているので、事故の規模が小さく収まります。

UXエンジニアリングの視点というよりチーム運用の話になりますが、モノレポのビルド時間はフロントエンド開発の体感を直接左右する部分です。キャッシュが効くかどうかで数分単位の差が出るのに、その仕組みが個人のトークン1本にぶら下がっているのは割に合わない。移行そのものは設定画面での OIDC ポリシー追加だけで済むので、Turborepo を使っているなら早めに済ませておきたい変更です。

### [Shopify and Vercel are rebuilding Hydrogen for faster storefronts](https://vercel.com/blog/shopify-and-vercel-are-rebuilding-hydrogen-for-faster-storefronts)

> **出典**: Vercel | **公開日**: 2026-07-30 | **カテゴリ**: frontend

**3行まとめ**
- Shopify がヘッドレスストアフロント向けのフレームワーク Hydrogen を、Vercel と組んで一から作り直している
- 新版はオープンソースかつランタイム非依存。Next.js、Nuxt、Svelte など好きなフレームワークで組める
- 型安全な API クライアントやカートの状態管理が最初から入り、これまで自作していたつなぎのコードが不要になる

**詳細解説**

Shopify のヘッドレスストアフロント向けフレームワーク Hydrogen が、Vercel との協業で作り直されるという発表です。挙げられている柱は3つで、オープンソースかつ JavaScript が動く場所ならどこでも動くこと、Standard Actions によってエージェント経由の商取引をあらゆるストアフロントへ持ち込むこと、そして Global Retail Brands のような小売事業者で機能開発が数ヶ月から1週間に短縮されたことです。

ランタイム非依存という方針が中心にあります。これまでは Hydrogen を選ぶことがフレームワークの選択とほぼ同義でしたが、新版では Next.js でも Nuxt でも Svelte でも構わない。フレームワーク固有の実装から、どこにでも載る部品へ、という動き方です。型安全な API クライアントとカートの状態管理が import 1つで入り、これまでカスタムのつなぎコードが必要だった部分にベストプラクティスが既定で入る、と説明されています。

UXエンジニアリングの視点で見ると、ヘッドレスコマースは「つなぎのコード」がそのまま保守コストになりやすい領域でした。カートの状態、在庫の整合、チェックアウトへの受け渡し——どれもストアごとに微妙に違う実装が生まれ、フレームワークの更新のたびに手が入る。それが標準の部品として提供されるなら、フロントエンド側は体験の作り込みに時間を割けます。

ただし、この記事で公開されているのは方針の告知にあたる部分までです。Standard Actions が具体的にどういうインターフェースになるのか、既存の Hydrogen ストアからの移行経路がどうなるのかは、まだ読み取れません。方向性としては注目しつつ、実際の設計は続報を待つ段階だと思います。
