### [Fact-Checking at Scale: Building a More Accurate and Efficient Synopsis Factuality System](https://netflixtechblog.com/fact-checking-at-scale-building-a-more-accurate-and-efficient-synopsis-factuality-system-d7d85859d808)

> **出典**: Netflix Tech Blog | **公開日**: 2026-11-09 | **カテゴリ**: engineering

**3行まとめ**
- Netflix の作品紹介文（シノプシス）が事実に合っているかを LLM で判定する仕組みを作り直し、1件あたりのコストを52.4%下げています
- 同じ汎用の判定を5回くり返すのをやめ、「文字どおり正しいか」と「見ていない人に誤った印象を与えないか」を別々の判定役に見させています
- 判定役が理由づけのなかで迷った点を取り出し、確かめられる小さな主張に分けて再確認する手順を加えて、誤った紹介文の見逃しを減らしました

**詳細解説**

紹介文の誤りは2種類に分けています。設定が違うといったはっきりした誤りと、書いてあることは全部正しいのに作品の印象がずれる誤りです。後者の例として、『ブリジャートン家』の紹介文が2つ出てきます。ゴシップ紙を書くレディ・ホイッスルダウンが主役のように読める文と、偽の交際から始まる2人がすぐに恋に落ちるように読める文です。LLM に書かせた UI の文言を確かめるときも、「仕様と食い違っていないか」と「読んだ人が誤解しないか」を別々の確認にしておけば、どちらで落ちたかを出力から読み解く手間が減りそうです。

以前の仕組みは、作品の情報を10万トークン以上まとめて推論モデルに渡し、同じ判定を5回くり返して、1回でも不合格なら落とすものでした。調べると、はっきりした文では5回とも同じ結論になり、意見が割れるのは微妙な文だけでした。そこで判定と一緒に確信度を出させ、確信度の低いものだけを追加の確認に回しています。同じ判定役を何度呼んでも、理由づけが同じ方向に間違っていれば結論は変わりません。

追加の確認では、仮定を置いた箇所、渡された資料だけでは決められない疑問、矛盾に気づいたのに「結論は変わらない」と流した箇所を、判定役自身に挙げさせます。それをルーターが確かめられる主張に書き直し、Web を調べる判定役か、資料を見直す判定役に振り分けます。不合格の紹介文を見逃さない率（Recall-Fail）は 0.77 から 0.86 に上がり、判定の理由が人の注釈者の挙げた理由と重なる割合も、約69%から約82%になりました。処理時間の中央値は延びています。

### [My Interop 2027 Picks](https://adrianroselli.com/2026/11/my-interop-2027-picks.html)

> **出典**: Adrian Roselli | **公開日**: 2026-11-10 | **カテゴリ**: accessibility

**3行まとめ**
- ブラウザ間の互換性を上げる Interop 2027 の投票（締め切りは2026年11月19日）に向けて、Adrian Roselli さんが選んだ15項目とその理由をまとめています
- 1位は `ariaNotify()`、2位は HTML の `focusgroup` 属性、3位は Shadow DOM の `referenceTarget` で、どれもスクリーンリーダーやキーボードの利用者がいま困っている問題につながっています
- 票を入れた `headingoffset` や `random-item()` にも、作り手の使い方しだいで利用者が困るおそれを書き添えています

**詳細解説**

理由は1項目につき1〜2文です。ライブリージョンを正しく実装できていない例が多く、ブラウザやスクリーンリーダーの対応状況もわかりにくいので、`ariaNotify()` を1位にしています。`referenceTarget` は、Shadow DOM の境界をまたいだラベルや説明の関連づけが切れて、スクリーンリーダーや音声操作の利用者が先に進めなくなる問題に向けたものです。

デザインシステムに関わる項目もあります。画面サイズが決まっている前提で作られたデザインシステムが、Apple の新しい端末で問題を起こしているとして、Device Posture API と Viewport Segments API を選んでいます。`AccentColor` は、利用者が選んだアクセントカラーを反映できず、コントラストの低いブラウザの既定色のままになっている部品の話です。

`line-clamp` は、カードの文字が見た目だけで切れたり、操作部品がずれた場所に置かれたりして、キーボードやスクリーンリーダーの利用者が迷う問題への手当てとして挙げています。ただ、`line-clamp` で CSS に文字を生成させることには、翻訳で問題が出るおそれがあるとして慎重な姿勢です。`headingoffset` も、外部のコンテンツの見出しレベルを直せる一方で、見出しの構造を気にしなくなる作り手が増えるおそれを挙げています。

### [My Interop 2027 Picks](https://blog.master.dev/my-interop-2027-picks/)

> **出典**: Frontend Masters Blog | **公開日**: 2026-11-10 | **カテゴリ**: css

**3行まとめ**
- 同じ Interop 2027 の投票で、Chris Coyier さんは CSS の3項目に絞って票を入れています
- 1位の `margin-trim` を使うと、パディングのあるコンテナで、最後の子要素の余分なマージンをコンテナの側で切り落とせます
- 2位は `random()`、3位は `reading-flow` と `reading-order` で、3位の2つを使うと、`order` で並べ替えたときに見た目の順とタブの順がずれる問題を直せます

**詳細解説**

`margin-trim` があれば、これまで `> *:last-child { margin-block-end: 0; }` のように子要素の側で打ち消していたところを、`margin-trim: block;` の1行で済ませられます。「パディングを付けた方向には、同じ方向の `margin-trim` も付ける」という覚え方を勧めています。Safari はすでに対応し、Chrome も先月対応したので、残るのは Firefox です。

`random()` については、位置、グラデーションの角度、アニメーションの開始のずらし方など、厳密に決めなくてよい値を問いの形で並べています。カンプで決まった位置に描いた飾りを `random()` でばらけさせる場合、デザイナーと見た目を確かめるときには、位置そのものより、どこまでずらしてよいかをそろえることになりそうです。

`reading-flow` は Grid Lanes では使えないことに疑問を投げています。記事の最後には、ほかの人が投票について書いた記事へのリンクがまとまっています。

**3行まとめ**

- 使っていない JavaScript や古いフォーラムを片づけ、散らばっていた色・フォント・余白をセマンティックなデザイントークンにまとめています
- Lighthouse ではアクセシビリティが86から91に上がり、ページの総量は2.03MBから1.24MBに減りました

**詳細解説**

CSS は180KB（圧縮後31.7KB）から169KB（同24.6KB）になりました。フォームの CSS は別のファイルに分け、WooCommerce などのプラグインを読み込むページだけで配信しています。

リンクのスタイルは数種類にそろえました。既定のスタイルで、色や不透明度の変化だけに頼らずにリンクとわかる見た目になるので、どのページでもアクセシビリティが上がっています。フォームは Gravity Forms、WooCommerce、Restrict Content Pro と出どころが3つあり、それぞれに専用のスタイルシートがあります。それらをリセットして見た目をそろえています。

テーマは、システム・ダーク・ライトの3つを1つのトグルで切り替え、切り替えには View Transition を使っています。記事本文の白い領域はダークでも白のままで、白と黒を入れ替えるだけでよいかは、まだ迷っていると書いています。トップページの blob の形は `border-shape` と `shape()`、`random()` で作り、ホバーやフォーカスのたびに形が変わります。この形が出るのは、今のところ Chrome だけのようです。`prefers-reduced-motion` で動きを止める指定も入っています。

Lighthouse の数字は、参考程度に見ているという前置き付きで載せています。LCP は8.5秒から7.2秒、Time to Interactive は8.6秒から4.0秒に縮み、パフォーマンスのスコアは71から72でほぼ変わっていません。

### [CSS Optimization: Is Using Declarations Just Once (UDJO) Still Effective Today?](https://css-tricks.com/css-using-declarations-just-once/)

> **出典**: css-tricks | **公開日**: 2026-11-10 | **カテゴリ**: css

**3行まとめ**
- 18年前からある CSS の最適化手法 UDJO（Using Declarations Just Once）が今も効くかを、自作のツール CSS Dedup で確かめています。同じ宣言を1つのルールにまとめ、セレクタの側で共有する手法です
- 20サイトすべてで重複は減らせた一方、そのまままとめると18サイトでファイルサイズが増えました（セレクタがくり返し書かれ、削った宣言より長くなるため）
- サイズが減るときだけまとめる設定にすると、すべてのサイトで重複を減らしながらファイルも小さくできました

**詳細解説**

まとめ方は2通り試しています。安全だと証明できるものだけをまとめる設定（`-f`）と、たぶん安全なものも含めて、サイズが減るときだけまとめる設定（`-f -a -s`）です。後者では、たとえば commission.europa.eu で51.9KB（5.1%）減りました。Web 開発者の個人サイト10件では、そのまままとめてサイズが増えたサイトは5件にとどまりました（組織のサイトでは20件中18件）。短いセレクタを書く人ほど効果が出やすいのかもしれない、と見ています。

数字は gzip や Brotli で圧縮する前のもので、CSS の質を示すものでもありません。まとめると宣言の位置が変わり、カスケードの順序にかかわるため、ツールは安全と言えるものと、たぶん安全なものを分けて扱います。まとめた宣言を、本当にすべてのセレクタで一緒に変えてよいかは、ツールでは判断できません。

デザインシステムの部品で、たまたま値が同じだけの宣言をまとめると、あとで片方だけ変えたいときに分け直すことになりそうです。まずは手元のビルド結果に、安全なものだけをまとめる `-f` で CSS Dedup をかけ、重複がどれくらいあるかを数えるところから始めると手軽です。

- プロフィールの生成、登録内容の確認、最後の除外の確認と、役割ごとに LLM を使い分け、出力の良し悪しは別の LLM に採点させています

**詳細解説**

「興味がない」は、埋め込みでの比較による除外、順位の引き下げ、LLM による最後の確認、端末のキャッシュの削除と、何段にも分けて効かせています。最後の確認では、汎用の大きなモデルより、除く項目だけを返すよう微調整した小さなモデルのほうが速く、結果も安定したとしています。

パソコンを起動したままにしておかなくても、外出先から機能の追加を頼めるようにするのがねらいです。速さや操作感は Claude Code や Codex を直接使うのに及ばない、と書いています。Vercel のサンドボックスには GitHub CLI と Claude Code が入っていないので、セットアップのコマンドで入れる必要があります。Railway のほうが設定は少なく済みます。`lifecycle: { reuse: "thread" }` を指定すると、同じスレッドの続きの依頼で同じサンドボックスが使われます。

後片付けには注意が要ります。記事の執筆時点では、Vercel 用のパッケージの `destroy` はサンドボックスを止めるだけで削除せず、ディスクのスナップショットも残ります。使うなら Vercel の API で消すスクリプトを用意するよう勧めています。
