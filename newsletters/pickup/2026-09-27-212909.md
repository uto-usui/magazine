## [We are all Product Engineers now](https://seldo.com/posts/we-are-all-product-engineers-now/)

> **出典**: Sidebar | **公開日**: 2026-09-18 | **カテゴリ**: design

**3行まとめ**
- コードを書くコストが崩れたあと、ソフトウェア開発の仕事に何が残るのかを10年スパンで見通した約4,000語の論考です
- 残るのは「顧客が本当に欲しいものを引き出し、良いの定義を決め、心地よくする」部分であり、それは移転しないので自動化されにくいと論じています
- その人材を育てる仕組みがほぼ存在しないことが、この先10年の痛みになると書かれています

**詳細解説**

前提は2つ置かれています。エージェントは開発ライフサイクル全体を飲み込む。そして、社会が必要とするソフトウェアの量に上限はない。歯医者のサイトも保険会社のサイトも学校のサイトもひどいのは、誰も良いものの作り方を知らないからではなく、今の価格では誰も払えないからだ、という指摘は説得力があります。

そのうえで、ソフトウェアを作るコストを分解しています。すでに崩壊したのがコードを書く部分。まもなく続くのがレビューと保守。次に来るのがデプロイとスケーリング。たぶん残るのが、何を作るかを決めること、良いの定義を決めること、心地よくすること。この3つめだけは自信がなさそうに書かれているのが誠実です。

データの厚みがこの記事の強みです。Stanford の調査では、AI の影響を受ける職種の22〜25歳の雇用が、影響の小さい同年代と比べて19%低い水準になっており、1年前の15%から悪化しています。しかも減り方は解雇ではなく採用の絞り込みによるもので、若手が地盤を失ったのは「どこかに書かれている知識」で成り立つ職種、経験者が伸びたのは「やって身につける知識」で成り立つ職種でした。SignalFire の集計では、大手の新卒採用は2019年比で65%減、アーリーステージでは75%減。それでも採用全体に占めるエンジニアの割合は46%から55%へ上がっています。人は減り、そのなかでエンジニアの比率は上がる。ただしコードを打つのが主業務の人ではない、という構図です。

レビューが追いつかない話も具体的です。GitHub は1年で3,600万人の開発者と4分の1増のコミットを受け入れ、マージされた PR は2023年比で3.5倍程度。エージェントだけで月に1,700万の PR を開いているという推計もあります。一方、33,000件のエージェント PR を調べた研究では、人か機械かを問わず大半の PR に記録されたレビューがなく、レビューがある場合も58%は別のエージェントだけが見ていました。curl は AI 由来の報告が溢れて有効な報告の割合が15%超から5%未満まで落ち、1月にバグバウンティを終了しています。Claude Code が開いた567件の PR を追った研究では84%が最終的にマージされ、人間の91%に迫っているという数字もあり、能力の上昇と受け入れ側の飽和が同時に進んでいることが分かります。

いちばん効いている論点は「製品の意思決定には規模の経済がない」という部分です。カレンダーアプリの良さとスケジューリングアプリの良さはほとんど共通しない。パン屋の要件と自動車部品工場の要件も違う。設定項目が山ほどあるのに自分のやりたいことができないソフトウェアに出会うとき、この問題に触れている、という説明は腑に落ちます。だから作るコストがゼロに近づくほど、ボトルネックは「問題の記述」へ移り、そこに留まる、というのが結論です。

歴史の補助線も引かれています。1960年代のシステムアナリストは、コードを打てる人が高価すぎて話す仕事まで任せられなかったから生まれた翻訳層でした。それがプロダクトマネージャーへ姿を変えて、25年ほどエンジニアリングと別の職能になっていた。その2つが1つに戻ろうとしている、という見立てです。実際 Palantir 発祥の forward deployed engineer は、直近の集計で462社・約1,000件の求人になり、平均総報酬は約24万ドル、シニアは60万ドルを超えます。求人票の中身はほぼシニアのプロダクトエンジニアで、コードを書く部分はいちばん小さく、そこはエージェントが担当します。

そして育成の話になります。Google の APM は年12,000人の応募から約50人。同種のプログラムを全部足しても年に数百人で、数万人規模だったジュニア開発者のパイプラインの代わりにはなりません。大学はデータ構造を教え、ブートキャンプは React を教えますが、「パン屋に1週間張りついて仕様を持ち帰る」を教えるところはない、という指摘は痛いところを突いています。

最後の2段落には、コードを書く手仕事が好きで職業にした人たちへの言葉が置かれています。慰めにはならない、と断ったうえで、「打鍵が好きだと思っていた人のかなりの部分は、実は打鍵の直前、曖昧な問題が頭のなかで形を得る瞬間が好きだったのではないか。それが今後の仕事そのものになる」と書かれています。家具工場ができても木工が残ったように、手仕事は残る、ただし職業としてではない、という締め方です。

UX エンジニアリングの視点では、デザインの扱いが目を引きます。デザインは製品の意思決定とは別のものとして切り分けられ、「2つの解がどちらも正しく問題を解いていて、片方だけが実際に使われて好かれる」部分だと定義されています。そして「誰もが正しいものを作れるようになったとき、残る競争軸は心地よさだ」と続く。コストが下がったぶんデザインの相対的な重みが上がる、という順序の説明として明快です。

> 🐈‍⬛ : 作るコストを段階に分けて、どれがいつ崩れるかを並べた整理が分かりやすいです。最後に残る「心地よくすること」だけ自信がなさそうに書かれているのも、かえって信用できます。打鍵の直前、曖昧な問題が頭のなかで形になる瞬間が好きだったのでは、という一文は、UX エンジニアにもそのまま当てはまりそうです。

## [Designing with AI](https://buzzusborne.com/work/designing-with-ai/)

> **出典**: Sidebar | **公開日**: 2026-09-18 | **カテゴリ**: design

**3行まとめ**
- Help Scout のプリンシパルデザイナーが、品質を落とさずに速度を上げるためにやった一連の整備を書いたケーススタディです
- 15年分の暗黙の判断を design.md に書き出し、200超のプリミティブをモデルが読める形へ作り直しています
- 導入後3ヶ月で、本人が過去10年より多くの本番コードを出した、という結果まで報告されています

**詳細解説**

出発点の整理が率直です。AI は作れるものの幅を広げたけれど、雑に使うと平均的な仕事を速く作るだけになる。そして「craft や taste を、遅いことの言い訳にはもう使えない」と腹を決めたうえで、判断が安く覆せるところで最速で動き、そこで稼いだ時間を、発見と判断に時間が要る場面へ再投資する、という方針を立てています。速くする場所と遅くする場所を分けているのがこの記事の骨格です。

最初にやったのは文書化でした。おもしろいのは作り方です。まず何の文脈も与えずに Claude Design へ簡単な画面を作らせると、当然ながら自分たちの基準ではひどいものが出る。そこで、なぜその判断が間違いなのか、色をどう使うのか、どの場面でどのコンポーネントを選ぶのかを少しずつ足しては、同じ課題をやり直す。この評価の反復を通して、システムに足りていない判断がひとつずつ露わになっていった、と書かれています。15年分の taste と意図は推測できない、というのが得られた実感です。

次がデザインシステムの作り直しです。2018年から運用されてきた成熟した Figma ライブラリと、対応する React コンポーネントがあったのに、LLM に使わせると派手に失敗しました。ボタンの代わりにタグ、存在しないコンポーネントの発明、システムにあるものの自作での再実装。原因は明快で、Figma と React のライブラリは人が探すために整理されていて、機械が理解するためではなかったからです。2週間かけて200を超えるプリミティブとコンポジションを組み直し、数百のトークンと変数を標準化し、文書の層を書きました。

ここで見落とされがちな条件が挙げられています。Figma と React の完全なパリティです。これがないと、AI は正しく見えるけれど実在しないコンポーネントで組んだ画面を自信ありげに出してくるので、システムの意味がなくなる。React 側を監査し、Code Connect でつなぎ、合わなくなったものを作るか非推奨にし、その間ずっと評価を回し続けた、とあります。そして、これだけの構造と文書をデザイナーが手で維持するのは現実的でないので、Figma と React の文書を同じ水準で作り更新する skill を作った、というのが締めです。

その先に2つの道具があります。ひとつは Scenario Pal という、会社の戦略・顧客ペルソナ・製品分析を土台にしたカスタム GPT で、案が現実の顧客シナリオでどう働くかを試したり、画面をブランド原則やアクセシビリティ基準に照らして批評させたりするもの。もうひとつが HSDS Studio という社内のプロトタイピング環境で、本番の React システムに触れるので、見た目を近似したり新しいコンポーネントを発明したりせずに、検証済みの部品で体験を組み立てられます。捨てて作り直すのではなく、出てきたコードを本番へ育てられる、という点が価値だと説明されています。

結果の書き方も落ち着いています。全デザイナーに本番へ1つ変更を出すよう促し、自分が最初にやった。導入3ヶ月で本人は過去10年より多くの本番コードを出し、長く残っていたバックログや、いつも優先順位で負けていた細部を片づけた。ただし「単に量が増えたのではない」と釘を刺しています。デザインと実装の距離が縮み、放置されていた細部が顧客に届くのが速くなり、スコープを切る段階で落ちていた野心的な案を追う余力が生まれた、というのが報告された変化です。

UX エンジニアリングの視点では、「機械可読性はデザインシステムの品質要件になった」という点が持ち帰りどころです。人が探しやすい整理と、機械が理解しやすい整理は別物で、後者を満たしていないシステムは、AI を入れた瞬間に迂回されます。パリティの話も同じで、Figma にあって実装にないコンポーネントは、これまでは調整で済んだかもしれませんが、いまは幻覚の材料になる。「プロンプトから直接コードを書く環境は、それ自体が良いアイデアを生むわけではない。実行のコストをほぼゼロにして、未知のなかに留まって遊ぶ時間をくれるだけだ」という一文が、この記事のいちばん誠実なところです。

> 🐈‍⬛ : 何も渡さずに作らせて、ひどい結果から足りない判断を1つずつ掘り出していく、という文書の作り方がおもしろいです。以前紹介した「Building data-driven design systems」とも通じていて、デザインシステムの読み手に機械が加わったことで、整理の仕方そのものが問われています。Figma にだけあるコンポーネントが、いまは幻覚の材料になるという見方は、パリティを保つ理由として説得力があります。

## [How to document your design system: best practices & tools](https://storybook.js.org/blog/how-to-document-your-design-system-best-practices-tools/)

> **出典**: Storybook Blog | **公開日**: 2026-08-31 | **カテゴリ**: design-systems

**3行まとめ**
- デザインシステムのドキュメントに何を載せるか、どう保守するか、どのツールを使うかを、開発者向けの層を中心にまとめたガイドです
- Zeroheight の2026年レポートでは、組織全体に広く定着したデザインシステムは38%にとどまり、ドキュメントの充実度が定着と強く結びついていました
- コンポーネントのリファレンスはコードから生成し、ほかの情報はそこへリンクする、という原則を軸にツールを比較しています

**詳細解説**

冒頭の数字が重いです。Zeroheight の2026年版レポートでは、組織全体に広く、または完全に定着しているデザインシステムは38%でした。ドキュメントがなければ、作ったコンポーネントは見つけてもらえず、誤って使われ、次の開発者にゼロから作り直されます。部品の集まりを「ほかの人が採用できるシステム」に変えるのがドキュメントだ、という位置づけです。

載せる内容は5つに整理されています。1つめはコンポーネントで、「今これをどう使うか」に1分以内で答えられることが目標です。用途、props、バリアントと状態（hover、disabled、loading、error）、アクセシビリティの挙動、そしてスクリーンショットではなく実際に触れる描画例とコピーできるコードを載せます。2つめはトークンで、値だけでなく「どういうときにこれを選ぶか」という意図まで書くようにすすめています。3つめはフォーム、ナビゲーション、空の状態などの組み合わせ例、4つめは Do と Don't の対比、5つめは貢献のしかた（提案の方法、「3か所以上で使われている」といった採用基準、レビュー担当、バージョン管理）です。

ベストプラクティスでとくに強調されているのが、コードとの同期です。実物からずれたドキュメントは、ないよりも悪い、つまり積極的に人を誤らせる、とまで書かれています。保守は面倒な作業で、面倒な作業は後回しにされるので、コンポーネント自体からドキュメントを生成して自動で追従させるのがもっとも確実だ、という考え方です。失敗パターンとしても「一度きりのプロジェクトとして扱う」が最初に挙がり、「信頼を失ったとき、デザインシステムは死ぬ」という一文があります。

AI エージェント向けの章もあります。同じレポートでは、AI に期待することの1位がドキュメント生成（57%）だった一方で、AI を使って必要なツールにドキュメントを届けているチームは12%でした。Storybook の MCP サーバーを使って Reshaped というコンポーネントライブラリでUIを生成させたベンチマークでは、使わない場合に比べてコンポーネントの使い方が12.8%良くなり、2.76倍速く、トークンも27%少なかったそうです。ドキュメント化された状態はそのままテストできるストーリーでもあるので、エージェントは自分の出力をテストにかけ、失敗を読んで直せます。

ツール比較は実務で役に立ちます。開発者向けの Storybook、デザイナーやブランド寄りの Zeroheight と Frontify、トークンとデザインからコードへの流れに強い Supernova、1つの基盤にまとめたい大組織向けの Knapsack、汎用ドキュメントの GitBook が並び、料金体系（Zeroheight は編集者1人あたり月59ドルから、Supernova は1席あたり月25ドルから、など）まで書かれています。どれが勝つかではなく、どのツールがどの層を担うか、という見方が示されているのがいいところです。

UXエンジニアリングの視点で持ち帰りたいのは、「コンポーネントのリファレンスはコードから生成し、それ以外はコピーせずリンクする」という原則です。Figma とコードとドキュメントで同じ情報を三重に持つと、いつかどこかがずれます。どれか1つを正とし、ほかはそこを参照する形にしておくと、人にもエージェントにも同じものを見せられます。一方で、コードに寄せるほど非エンジニアが編集しにくくなるという弱点も記事は認めていて、原則やトーンの文章をどこに置くかはチームごとに決める必要がありそうです。

> 🐈‍⬛ : AI に期待することの1位がドキュメント生成なのに、実際に届けているチームは12%という差が印象的です。Help Scout がドキュメントを保守する skill まで作っていたのは、まさにこの差を埋める動きでした。「実物からずれたドキュメントは、ないよりも悪い」は、人よりもエージェントに対してのほうが強く効いてくる話かもしれません。

## [Component testing: a practical guide for frontend developers](https://storybook.js.org/blog/component-testing-a-practical-guide-for-frontend-developers/)

> **出典**: Storybook Blog | **公開日**: 2026-08-31 | **カテゴリ**: design-systems

**3行まとめ**
- コンポーネントを1つずつ実ブラウザで描画し、ユーザーと同じ操作をして振る舞いを確かめる「コンポーネントテスト」の入門ガイドです
- 描画テスト、インタラクションテスト、モックとスパイの3つの手法を、Storybook の実例コードで順に示しています
- AI エージェントがUIを書く時代には、テストが「ガードレール」、ストーリーが「文脈」の2役を担うと位置づけています

**詳細解説**

出発点は、UIテストの板ばさみです。E2E テストは実際のユーザー操作に近いぶん信頼できますが、遅くて不安定で、特定の状態に持ち込むのが大変です。ユニットテストは安くて速い反面、エミュレートした DOM の上で動くので、画面が本当に動くかどうかはあまり分かりません。コンポーネントテストはその間に入り、実ブラウザで動かしながら、小さく速く安定したテストとしてユニットテストの隣に置ける、というのが記事の主張です。

特徴として4つが挙げられています。アプリの残りから切り離して動かす「分離」、ボタン1つからページ全体まで扱える「範囲」、エミュレーションではなく実ブラウザで動く「環境」、そして QA チームではなくフロントエンド開発者が書いて保守する「担当」です。分離は強みであると同時に限界でもあり、システム全体のつながりは確かめられない、と正直に書かれているのは好感が持てます。

例として出てくるのは、タイトル入力、`getUsers()` で候補を取ってくる招待者ピッカー、送信ボタンを持つ `EventForm` です。まず `export const Default: Story = {}` だけで、描画できれば合格のスモークテストになります。次に `play` 関数で送信ボタンを押し、「Title is required」が出るかを確かめます。最後に `.storybook/preview.ts` で `sb.mock(import('../lib/users.ts'))` を登録し、ストーリー側で `mocked(getUsers).mockResolvedValue(...)` を指定して、フォームを最後まで入力させます。`args` に渡しておいた `fn()` がスパイになっているので、`onSubmit` が正しい値で呼ばれたかも検証できます。モックで状態を作り、スパイでロジックを確かめる、という分担が分かりやすいです。

ユニットテスト、結合テスト、E2E テストとの比較表もついています。目安として示されているのは、UIに依存しない純粋なロジック（整形、計算、データ変換）はユニットテスト、描画や操作への反応があるものはコンポーネントテスト、という線引きです。結合テストについては、フロントエンドでは独立した分類としてはあまり扱われず、コンポーネント同士はコンポーネントテストに、バックエンドとの連携は E2E に吸収されている、という整理になっています。

終盤の AI エージェントの話は、今の現場に直結します。エージェントはすでにあるコンポーネントを作り直したり、既存のパターンから外れたり、存在しない API を書いたりします。コンポーネントテストが失敗すると、props の不一致や壊れた操作、アクセシビリティ違反といった具体的なエラーが返るので、エージェントはそれを読んで自分で直せます。さらに、テストのために書いたストーリーは「このコンポーネントは何で、どう使うものか」を構造化して残した記録にもなり、エージェントに渡せば既存部品を使って組み立ててもらえる、という指摘です。

UXエンジニアリングの視点では、読み込み中、エラー、空の状態、バリデーション失敗といった「E2E では再現しにくい状態」を一覧として持てることが大きいと感じます。デザイナーやPMとの確認もその一覧の上でできるので、状態の抜け漏れが話し合いの場で見つかりやすくなります。ただし、見た目の正しさはこのテストだけでは担保できず、記事自身も Chromatic の視覚テストを別の層として紹介しています。Storybook チームの記事なので、ツール選びの部分は割り引いて読み、テストの分類と考え方を持ち帰るのがよさそうです。

> 🐈‍⬛ : 同じストーリーがテストにもなり、エージェントへの文脈にもなる、という1つで2役の置き方がうまいです。読み込み中や空の状態を一覧で持てるのは、デザインレビューの場でもそのまま役に立ちます。ツールの紹介は割り引いて読むとしても、ユニットテストとコンポーネントテストの線引きは明快で、チームで共有しやすいところです。

## [Why your numbers look wrong](https://www.carmenansio.com/articles/opentype-features-css/)

> **出典**: Sidebar | **公開日**: 2026-09-18 | **カテゴリ**: design

**3行まとめ**
- ダッシュボードの数字がなんとなくおかしく見える原因は CSS でもデータでもなく、フォントが既定で渡してくる数字のほうだ、という記事です
- `tabular-nums`、`oldstyle-nums`、`diagonal-fractions`、小型大文字の4つを、実演つきで1つずつ解説しています
- Google Fonts の可変フォントはこれらの機能を削って配信していることが多く、セルフホストが必要になる点まで触れています

**詳細解説**

書き出しが具体的です。データは正しい、レイアウトも綺麗なのに数字がどこか落ち着かない。値が更新されると行全体が横に震える。揃うはずの合計の列が不揃いになる。文中の年号だけ背が高くて叫んでいるように見える。仕様書の `1/2` が割り算に見える。これらは既定の数字が、見出しやロゴで大きく目立たせるために切られたものだからで、ダッシュボードがやる仕事のための2つめの数字がフォントには入っているのに、ブラウザは名指しで頼まれるまで使わない、という説明です。

`tabular-nums` は幅の話です。既定では数字も文字と同じように字ごとの幅で組まれていて、`1` は `0` より狭い。文章のなかでは正しい挙動ですが、数字が縦に揃う場面や、その場で値が変わる場面では間違いになります。表では列が不揃いになり、更新されるものは新しい桁の幅が違うので値が動くたびに跳ねる。すべての数字に同じ幅の枠を与えるとこれが止まります。記事には百分の1秒まで表示する時計の実演があり、切り替えるとぴたりと止まるのが分かります。「製品がお金を動かすとき、数字はインターフェースそのもの。更新で跳ねる合計や揃わない列は、理由を言葉にできるより先に壊れているように読める」という一文が、この機能の位置づけを言い当てています。

`oldstyle-nums` は高さの話です。既定のライニング数字は高さが揃っていて大文字に合わせてあるので、大きな統計値では狙いどおりですが、文章や小さなラベルのなかでは大文字の連なりを放り込んだように振る舞います。オールドスタイル数字は小文字のように上下に出入りし、6 と 8 が上がり、3・4・5・7・9 が下がって、行に馴染みます。文章とラベルにはオールドスタイル、大きな統計値と表にはライニングとタブラー、という組み合わせが提案されています。

`diagonal-fractions` は分数です。`1/2` と打つとベースライン上に3文字が並んで計算式に見えますが、フォントには本物の分数グリフが入っています。注意点も添えられていて、この指定はスラッシュで区切られた組を何でも分数に畳むので、`24/9` のような日付や、そのままにしておきたい比率まで巻き込みます。本当に分数である数字だけを span で囲む、という運用が勧められています。`2 1/3` の整数部分が正しくそのままの大きさで残る、という細部の記述も親切です。

実務で刺さるのはフォントの入手経路の話でしょう。Google Fonts の多くはこれらの機能を持っておらず、可変フォントのビルドはバイト数を削るためにオールドスタイル数字・分数・小型大文字を取り除いています。だから `oldstyle-nums` を指定しても何も起きず、構文を間違えたと思い込む。実際にはグリフが配信ファイルに入っていないだけです。解決はフル版のセルフホストで、記事自身がそうしている、と書かれています。

UX エンジニアリングの視点では、投資対効果の良さが際立ちます。4つの切り替えで CSS 1ブロック、JavaScript なし、しかも機能はすでにフォントに入っている。それでいて、金額を扱う画面の信頼感にはっきり効きます。デザインシステムに落とすなら、表・統計タイル・カウンターのコンポーネントに `tabular-nums` を既定で入れて、本文のスタイルにオールドスタイルを当てる、という形になるでしょう。デザイナーが「なんとなく落ち着かない」と言ったときに、原因を名指しできる語彙が手に入るのも大きいところです。

> 🐈‍⬛ : 「なんとなく落ち着かない」に名前を付けられるようになるのが、この記事でいちばんうれしいところです。Google Fonts の可変フォントでは指定しても何も起きない、という罠は知らないとなかなか気づけません。Product Engineers の記事が最後に残るとした「心地よさ」は、こういう CSS 1ブロックの積み重ねでできているのだと思います。

## [The 3 Roles of Context for AI Agents](https://www.nngroup.com/articles/3-agent-context-roles/)

> **出典**: Nielsen Norman Group | **公開日**: 2026-09-18 | **カテゴリ**: design

**3行まとめ**
- Claude を日常的に業務で使うパワーユーザーの調査から、コンテキストが果たす役割を global・local・ambient の3つに整理した記事です
- 参加者は全員が「コンテキストライブラリ」を作っていて、同じ情報でも役割が移り変わることが観察されています
- 役割が決まると扱い方が決まる、というのが結論で、プロンプトの書き方より置き場所の設計が効くと述べられています

**詳細解説**

global はめったに変わらず、対話をまたいでエージェントの動きを形づくる情報です。調査で挙がった例が具体的で参考になります。会話のなかで拾われてプロフィールに保存された本人の事情や好み。良い仕事とはどういうものかを定義する型やテンプレート。どの行動に承認が要るかというガバナンス規則（ある参加者は、公開されるものと、頼んだ方向からの急な転換には許可を必要とさせていました）。信頼する助言が載った本の一覧を北極星として置いた markdown。個人ブランドの色コードと視覚ルール。意図を必ず確認させる決まり。

local は今の仕事に直接ひもづく情報です。プロジェクトごとの優先順位付きタスクリスト、skill、会話の履歴、作業の終わりに自動更新される変更ログ、Notion に置かれた応募先の記録（本人は一度も更新せず、Claude が読み書きしていたそうです）、土地の調査レポート。ここでおもしろいのは、local の一部は Claude 自身が書いて最新に保っている点です。作業中の成果物そのものではなく、それを支える情報だ、という区別がされています。

ambient がいちばん大きく、いちばん散らかっています。メール、会議の書き起こし、チャット。事前にどのタスク向けか決められていない生の流れです。「作った文書のなかには、その場では役に立つけれど二度と使わないものがある。ただ視界には入れておいてほしい」という参加者の発言が引かれていて、curate する時間がないから流れごと渡す、という割り切りがそのまま記録されています。Shopify の購買データを自作スクリプトで書き出して HubSpot の顧客プロフィールを更新させる、30近い subreddit を巡回させる、Amplitude を接続して製品の数字を常時見せる。手間をかけてでも接続を維持していた、というのが観察です。

同じ情報の役割が移る、という指摘も実感に合います。Slack のメッセージは最初 MCP 経由の ambient の一部ですが、ユーザーがそれを指させば local になります。よく参照する記事をアーカイブして常時参照にすれば global へ上がる。

結果として、プロンプトの精度への依存が下がります。参加者の多くはマイクを入れて雑に口述していて、ある人は Gemini で練った計画を markdown にして「プロジェクトディレクトリの MD を読んで実装して」とだけ言っていました。一般には良くないプロンプトですが、local に十分な情報があったので通った、という例です。

UX エンジニアリングの視点では、この3分類が設計のチェックリストとして使えます。あるチームで CLAUDE.md が太るのは、local に置けばよいものと ambient から拾えばよいものを global に押し込んでいるからだ、と診断できる。Addy Osmani の棚卸しの記事と並べて読むと、片方が「何を書くか」、もう片方が「どこに置くか」を担当していて、補い合います。プロダクト側でも同じで、AI 機能を作るときに何を常時の前提とし、何をその場のスコープとし、何を接続だけしておいて漁らせるかは、そのまま設定画面と権限設計の話になります。

> 🐈‍⬛ : 同じ Slack のメッセージが、指させば local に、残しておけば global に移る、という観察が実感に合います。雑な口述でも通ったのは local が厚かったから、という例も、プロンプトの書き方より置き場所が効くことをよく示しています。次の Addy Osmani の棚卸しとあわせて読むと、何を書くかと、どこに置くかの両方がそろいます。

## [Audit your Agent files](https://addyosmani.com/blog/audit-your-agent-files/)

> **出典**: Addy Osmani | **公開日**: 2026-08-27 | **カテゴリ**: performance

**3行まとめ**
- CLAUDE.md や skill には半減期があり、書いた当時のモデルやハーネス向けの指示が残り続ける、という問題を扱っています
- 6本の実証研究を並べたうえで、コンテキストファイルは正答率を上げなかったが働き方は変えた、という区別を提示します
- 数週間おきに棚卸しし、退避してから消し、消した状態で実際に走らせて判断する手順を勧めています

**詳細解説**

指示ファイルが太る仕組みが、まず素直に説明されます。エージェントが一度痛い間違いをする。もっともな1行を足す。ファイルが育って大事な部分が薄まる。遵守率が落ちて品質が下がる。また1行足す。単体では妥当な判断の連なりで、短い判断の手引きのつもりが知識ベースになってしまう、という指摘です。Osmani 自身も、自分のファイルが200行を超えていたと認めています。

数字の並びが読みどころです。人気リポジトリ100件の調査では、lint に関する漏れ出しが62%、コンテキストの肥大が42%、skill の漏れ出しが35%で、大半のファイルが少なくともひとつを抱えていました。17のタスク・288回の実行でコンテキストファイルの効果を測った研究では、正答率に明確な差が出ていません。ただし働き方は変わっていて、あるリポジトリでは「テストスイートが遅い」という注意書きを読んだ Claude が対象を絞ってテストを走らせ、無駄が減りました。機能の実装が上手くなったのではなく、そのリポジトリの流儀に効率よく従った、という差です。

個人向けに最適化した skill の研究も意外な結果を出しています。13人の開発者・206セッションで、ある開発者の履歴から作った skill は、他人の履歴から借りた skill とほぼ同じ性能でした。多数の開発者から作った汎用の skill のほうが全体として有用だった、という結論です。ただし開発者のシミュレータを使った実験なので、確定ではなく有望という扱いにしてあります。受け取り方として示されるのは「強い汎用 skill から始めて、個人の決まりごとは少しずつ足す。一度口にした好みを恒久的な記憶に昇格させない」という構えです。

散文と実コードの比較も示唆的です。コードについての振る舞いの質問45個に対し、要約文が答えられたのは4つ、ソースそのものは27でした。要約は、ちょうど大事な細部を均してしまうからです。「コードの説明ではなく、コードそのものを指させ」という結論になります。Anthropic が Claude 5 世代でシステムプロンプトの80%超を削っても社内の評価に測定可能な低下がなかった、という報告も引かれていますが、これは目標値ではなく「指示の価値には期限がある」ことの例として扱われています。必ず守らせたい決まりは散文ではなくテスト・hook・権限に置く、という整理です。

skill のコストについて、よくある誤解を訂正している部分もあります。インストール済みの skill が毎回まるごとプロンプトに載るわけではなく、探索用に名前と説明が既定でコンテキスト幅の1%という枠のなかで読み込まれ、本体は呼び出されたときに入ります。だから剪定の理由はトークンではありません。モデルは一覧から選ぶので長い一覧は選択を誤る、似た skill が同時に発火して衝突する、入っているものは自分の持ち物になる、忘れた設定については考えられない。これが理由です。250個から25個に減らしたという投稿への「どうすれば250になるのか」という反応が、実感としてよく分かります。

手順もはっきりしています。まず退避して、いつでも1コマンドで戻せる状態を作る。`/doctor` で skill、プラグイン、MCP サーバー、遅い hook、重複した記述を洗い、`/memory` は別に見る。指摘されたものと、入れた覚えがないものを外す。そのうえで実際のタスクを、ローカルの skill をいっさい使わない状態で走らせてみる。結果を見て、削除を確定するか元に戻す。セッション内の `/doctor` が設定監査で、シェルの `claude doctor` はインストール診断だけ、という名前の罠にも触れられています。

UX エンジニアリングの視点で持ち帰れるのは、「消せない理由」の正体です。「外すのが不安だから残している。それはたいてい、ルールを書いた当時からモデルもハーネスも良くなっていないほうに賭けている、ということだ」と書かれています。デザインシステムの禁則や lint ルールでも同じことが起きます。追加する経路だけがあって、外す担当と外す手順がない仕組みは、必ず飽和します。退避してから消す、という一手を用意するだけで、判断の性質が変わるのはそのためでしょう。

> 🐈‍⬛ : 先週の Matt Pocock の AI Skills の話とも通じますが、今回は足すより外すほうに重心があります。外すのが不安で残しているのは、モデルが良くなっていないほうに賭けているのと同じ、という指摘はなかなか痛いです。退避してから消し、消した状態で走らせてみる手順は、デザインシステムの非推奨コンポーネントを整理するときにも使えそうです。

## [Brownfield Agentic Engineering](https://addyosmani.com/blog/brownfield-agentic-engineering/)

> **出典**: Addy Osmani | **公開日**: 2026-09-14 | **カテゴリ**: performance

**3行まとめ**
- 歴史の長いコードベースにエージェントを入れるときの型を、ゾーン分け・特性テスト・移行単位・並列化の順で整理した記事です
- リポジトリだけでは挙動を説明しきれない環境では、「コードに書けないこと」だけを文書にするのが要点だと述べています
- 並列化は最後、判定役と復旧路と人が読めるレビュー形式が1単位で揃ってから、という順序が繰り返し強調されます

**詳細解説**

出発点は、古いコードベースではリポジトリが挙動の完全な説明になっていない、という観察です。暗黙知、応急処置、レガシーなサービス、他チームの期待が木の外側に住んでいる。そこへエージェントを放つと、「動く」けれど設計が間違っていて脆いテストが付いてくるものが出てくる、と書かれています。

最初の型がゾーン分けです。テストが揃って独立している緑、品質が混在する黄、認証・課金・権限・給与のように少数の人しか分かっていない赤。緑はエージェントが自分で回してよく、黄は特性テストで今の挙動を固定してから、赤は人が常に隣にいるか、やらないか。運用として成立させる条件が3つ添えられています。地図を描くのは人であること（放っておくとエージェントはいちばん怖いファイルから始める、名前がいちばん面白そうだから）、ゾーンの昇格は条件を満たしたときだけ、ゾーンが動詞を決めること。

「コードに書けないことだけを書く」という節も実務的です。モジュール構成、呼び出し関係、命名、テストの置き方、型が強制していること、linter が捕まえること。これらはエージェントが読めば分かるので書かない。代わりに書くのは、業務やチーム固有の事情、なぜこの構造なのかというトレードオフ、ツールが強制していない決まり、ドメイン規則、外部制約、直感に反する実装の経緯です。そして「繰り返される指摘は、ハーネスに足りていない部品だ」という原則が置かれます。同じレビューコメントが再び出たら、lint ルール、hook、型、テスト、skill のどれかに移す。散文は機械的に強制できない制約のために取っておく。

移行についての指摘がいちばん厳しいところです。中途半端な移行はエージェントを迷わせます。検索すると古いやり方が40ファイル、新しいのが12ファイル、両方を現役に見せる shim がひとつ。矛盾した前例を見せられた状態です。だから1経路を端から端まで終わらせ、古い経路を削除するまでを1単位にする。削除が将来の掃除チケットになっているなら、その単位は未完了だ、と言い切っています。SWE Refactor Bench の数字も引かれていて、520回の実行のうち移行監査・振る舞いテスト・独立検証の3段階すべてを通ったのは28回、5.4%でした。テストが緑のまま、置き換えたはずの実装が裏で旧実装を呼んでいる状態を、この研究は「blindness」と呼んでいます。

大きな移行の事例は、見出しの数字ではなく構造を写せ、という整理で紹介されます。Bun の Zig から Rust への移植は53万5,000行を11日、約50のワークフロー、実装役ごとに2人の敵対的レビュアー、既存テスト全通過をマージ条件にしていますが、写す価値があるのはエージェントを走らせる前に Zig と Rust の対応を書いた移植ガイドのほうです。VB6 から C# の対照実験では、単純な機能で92%、複雑な機能で47%の振る舞い一致。単位の大きさが効く、という結論になります。Stripe が370万行を1つの PR で TypeScript へ移したときエージェントは関わっておらず、残った資産は codemod という移行機械でした。Asana の Enzyme 移行は2週間・約1万2,000ドルですが、これはベンダー申告のトークン代であって、対照実験による削減額ではない、と注釈が付いています。

並列化の節は順序の話です。ソフトウェア工場は多数の変更を同時に流せますが、真似るのは1単位で信頼できる判定役、安価な復旧路、人が最後まで読めるレビュー形式が揃ってからにする。並列化はすでにあるボトルネックを掛け算するだけで、自動検証なら5件を捌けても、全行を読むシニアが1人なら待ち行列と儀式的な承認が残ります。worktree は変更を分離しても挙動は分離せず、Git のメタデータ、認証情報、ローカルサービス、ネットワークを共有しうる、という注意も添えられています。

UX エンジニアリングの視点で効くのは、指標の置き換えです。生成行数は改善の証拠にならない、緑のテストも単体では証拠にならない。移行なら、残っている旧 import、新しい経路が捌いている実際のトラフィック、差分の不一致、消せたレガシー依存を見る。全トラフィックが旧経路のまま緑のテストが並んでいる状態は、ただの作業です。デザインシステムの移行にそのまま当てはまります。新コンポーネントの実装数ではなく、旧コンポーネントの残存 import と、新しいものが本番で担っている画面の割合を見る。「エージェントは曖昧さに見える値札を付ける。暗黙の慣習は繰り返されるレビューコメントになる」という一文が、この記事の要約になっています。

> 🐈‍⬛ : 「削除が将来の掃除チケットになっているなら、その単位は未完了」という線の引き方が好きです。古いやり方と新しいやり方が混ざったコードは人にとっても紛らわしいものでしたが、エージェントはその矛盾をそのまま前例として拾ってしまいます。繰り返されるレビューコメントを lint や型へ移すという原則は、前の2本の「散文に書きすぎない」ともつながっています。

## [How I Vibed a Proof of Conway’s Conjecture](https://overreacted.io/how-i-vibed-a-proof-of-conways-conjecture/)

> **出典**: Dan Abramov | **公開日**: 2026-09-18 | **カテゴリ**: frontend

**3行まとめ**
- 数学の素人を自認する Dan Abramov が、1ヶ月の余暇と大量のトークンを注いで、Conway が50年前に立てた予想の Lean 証明にたどり着いた記録です
- PM・数学・Red・Lean と役割を振った複数エージェントの「研究室」を組み、2度の全面破棄を経て成果に至っています
- 数学者による独立検証はまだ済んでおらず、本人も反証を歓迎すると明記しています

**詳細解説**

対象は Conway の refinement conjecture です。omnific integer（超現実数の整数部分）で `ab = cd` が成り立つとき、`a = ef`、`b = gh`、`c = eg`、`d = fh` となる4つの数に分解し直せるか、という主張です。ふつうの整数なら 210 = 10 × 21 = 6 × 35 が (2 × 5) × (3 × 7) の組み替えだと分かりますが、無限を含む数でも同じ性質が残るのか、が問われています。

読みどころは数学そのものより、1ヶ月の失敗の記録のほうです。最初の一撃は完全に空振りでした。Claude は「stage-1 obstruction of C\* is not rigid」といった造語だらけの文章を量産し、本人の言葉を借りれば出来の悪い SF のようだったとのこと。次に ChatGPT にその出力を「これはでたらめか」と読ませたところ、造語・過剰な演出・誤った推論を次々に指摘したので、その懐疑的な人格ごとセッションを複製して使い始めます。この「批判させてから分岐する」という手つきが最初の転換点です。

Codex でローカルに研究室を組んだのが第2週です。PM が目標を管理して成果をマージし、数学エージェントが新しい手を探し、Red エージェントがそれを壊しにかかり、Lean エージェントが形式化する。受け取ったメッセージを全員に転送する「cafeteria」まで用意しています。ところが3週目に破綻します。「論文」が1日で12本から30本近くまで増え、ひとつでも誤りがあれば後続がすべて崩れる構造になっていて、実際に「構成した対象に必要な確認をしていない」という同じ型の欠陥が複数の論文に埋まっていました。ChatGPT 自身が「we do not have a proof」と認めて、1週間プロジェクトが止まります。

立て直し方が参考になります。予想を一旦脇に置き、依拠している査読済み論文の誤植探しだけに絞って、見つけたものを論文の著者へメールで確認したのです。狙いは3つ、モデルへの信頼の校正、Lean への信頼の校正、そして数学者に話を聞いてもらうための信用でした。ここで得た手応えをもとに、それまでの成果をすべて捨てて salvage をかけたところ、造語に埋もれていた本物の新結果（finite-degree primality）がひとつ残ります。

再構築後の設計には、エンジニアリングとして流用できる工夫が並んでいます。Lean エージェントを2つに割り、片方は査読済みの前提だけを形式化し、もう片方は新しい結果を別の worktree で扱って未成熟な抽象が既存部分に混ざらないようにする。Mathlib 以外の import を禁じた standalone フォルダを用意し、500行以下の自己完結したステートメントだけを人がレビューできる形に切り出す。モデルが勝手に発明した名前をいったん A、B、C に置き換え、元の名前を見ていない別セッションに、分野の用語マップを渡して命名し直させる。証明の依存関係を Mermaid 図にして、モデル自身に無駄な回り道を見つけさせる。「モデルは見えないものを最適化できないし、見えるものを無視できない」という一文が、これらをまとめています。

コストも公開されています。おおよそ400億トークン、うち出力が2.1億、95%超はキャッシュ読み。API 価格に換算すると約4万ドル相当で、本人は「うまく舵を取れば5分の1から10分の1でいけたはず」と書いています。

UX エンジニアリングの視点では、検証手段を先に用意することが速度を決める、という構図がそのまま読み替えられます。Lean が果たしたのはコンパイラによる検証で、これが追いつかないうちに「論文」を積み上げた期間は丸ごと無駄になりました。UI の仕事でいえば、視覚回帰テスト、型、アクセシビリティ検査がその位置に来ます。もうひとつは、レビューできる単位を設計する話です。数千ファイルの Lean は誰も読みませんが、500行の自己完結したステートメントなら読める。デザインシステムの変更を人が見られる粒度に切る作業と、まったく同じ判断です。ただし成果自体はまだ独立検証を待つ段階なので、結論より過程を読むものとして扱うのが良さそうです。

> 🐈‍⬛ : いちばんおもしろいのは、行き詰まったあとに予想から離れて、依拠している論文の誤植探しに切り替えたところです。モデルと Lean への信頼を小さく確かめ直してから、もう一度大きな問題に戻っています。500行以下に切り出して人が読める形にする工夫は、Brownfield の記事にあった「人が読めるレビュー形式」とも重なります。

## [New Insurance UX Research: 3 Key Takeaways](https://feeds.baymard.com/link/9825/17465872/insurance-ux-research-launch)

> **出典**: Baymard Institute | **公開日**: 2026-08-25 | **カテゴリ**: ux-research

**3行まとめ**
- 米英20の保険サイトを対象にした新規調査で、4,700時間超・220セッションから1,700件超の中〜重度の問題を観察しています
- ユーザーがつまずくのは、なじみのない概念、見積もりフローの操作性、そしてブランドへの信頼の3点でした
- 答えを知らない質問を投げると、長い逡巡・空欄・当てずっぽうのどれかが返ってくる、という観察が一貫しています

**詳細解説**

一般的な EC との違いから説明が始まります。保険では、住所や支払い情報よりずっと複雑でなじみのない情報を求められます。しかも自動車保険や住宅保険への加入は、たまにしか起きない作業です。だから「5-level mortice deadlock」のような、見積もりに必須なのに何のことか分からない語に出くわす率が高くなります。

実際の発話が効いています。Go Compare の参加者は「建物の再建築費用」の見積もりを求められて「そんなの分からない。大きく外したら困るから、自分で数字を入れるのは不安」と言い、質問を飛ばそうとします。しかも続きが本質的で、「入力しないまま進んでみて、どうしても必要だと言われたら、見積もりは別のところで取ることを考え直すかもしれない」。答えを知らない質問は、質の低い回答・空欄・離脱のどれかを招く、という指摘がそのまま口から出ています。Money Supermarket の参加者は屋根の素材を聞かれ、「これだけ選択肢がある……『Shingle』って何のことか分からない」と言いながら、ゆっくりスクロールした末に「Tile」と答えて進んでいます。

対処法もはっきりしています。Direct Line ではサイトの推奨額が示されていて、参加者は「勧められた額を入れます」と迷わず採用しました。この既定値のおかげで、ほかのサイトで当てずっぽうを宣言していた同じ参加者より、はるかに正確な回答になっています（別のサイトでは家財を実際の15%未満で見積もっていました）。Compare the Market ではイラスト付きで屋根の平坦率・外壁の素材・屋根の素材を聞いていて、参加者は8秒未満で答え、「速くて簡単だった」と述べています。ほかのサイトで同じ質問に苦戦した人たちとの間に、測定できる時間差が出た、と書かれています。技術的な部材を尋ねるときは、説明と、必要なら図を添える。金額の見積もりには、近隣の同種の住宅の平均のような既定値を出す。走行距離なら日次・年次といった期間の取り方に柔軟性を持たせる。

フローの操作性については、見積もりフローが多くのユーザーにとって旅の中心だという前提が置かれます。そのうえで、20分かけて入力してきたあとに1つの項目で詰まる、戻れない、エラーで入力済みのデータが消える、といったことが起きると、ユーザーはあきらめる。短い決済フローなら多少の不具合が許されても、見積もりフローでは問題が急速に積み上がって離脱に至る、という対比が示されています。Allstate の例が具体的で、名前が「Hannah Hannah〔姓〕」と誤って入ってしまった参加者がブラウザの戻るボタンを押したところ反応せず、ロゴをクリックしたらホームに戻されて見積もりが最初からになりました。良い例としては Liberty Mutual の戻るボタンが挙げられ、「Save & Continue」と並んで置かれ、大きさと色で周囲から際立ち、各ページの同じ位置にあることが見つけやすさの条件として整理されています。加入資格がないなら、フローに入る前のできるだけ早い段階で伝えたほうがよい、という指摘も実務的です。

信頼の節では、Travelers のアグリゲータで「どれも聞いたことがない会社ばかり……この辺りは底辺だね」と切り捨てる参加者の発話が引かれています。知らない会社であることを品質の低さと同一視した例です。保険は高額で、期待した補償が受けられなかったときの影響が大きいので、会社と商品の両方に外部からの裏づけが要る、と結論づけられています。

UX エンジニアリングの視点では、「ユーザーが答えを持っていない入力」をどう設計するかという課題が、保険に限らない形で立ち上がります。B2B の設定画面、開発者向けツールの初期設定、業務システムのマスタ登録でも、同じ構図がよく起きます。この記事が示す解は3つです。既定値を出す（推奨値は当てずっぽうより正確になる）、視覚的に見せる（屋根の素材をテキストで並べず図で見せると8秒で答えられる）、期間や単位の取り方を利用者に合わせる。どれも、質問を減らすのではなく答えやすくする方向の解で、フォームの設計としては地味なぶん再現性が高いところです。

> 🐈‍⬛ : 「入力しないまま進んで、必要だと言われたら見積もりは別のところで取る」という参加者の発話が、離脱の直前の気持ちをそのまま言葉にしています。推奨値を出すと当てずっぽうより正確になる、という結果は、既定値を誘導ではなく手助けとして置けることを示していますね。B2B の設定画面でも、同じ構図はよく見かけます。

## [自分の施策を自分で評価する —— 結果を見る前に決めておいたことと、そこから外したこと](https://tech.smarthr.jp/entry/2026/09/18/143604)

> **出典**: SmartHR Tech Blog | **公開日**: 2026-09-18 | **カテゴリ**: design

**3行まとめ**
- 自分が立ち上げた施策を自分で評価して報告する構造の危うさに、手続きで対処した記録です
- アンケートの結果を見る前に、判定基準・自分の予測・どの結果でどの主張を立てるかを文章にして凍結しています
- 主張を強めるには事前の条件が要り、弱めるには妥当な理由があればよい、という非対称なルールを置いたのが要点です

**詳細解説**

背景は、リリース後の観測から判断を更新する学習ループを回すためのパイロットです。観測結果を確認して判断する場「Decision Review」と、それを記録する「Decision Log」の2つを型として2チームで回し、一周終えた報告になっています。ただし記事の焦点は結果ではなく、その結果をどう評価したかに置かれています。

成果の書き方が慎重です。当初の仮説は限定的にしか判定できていない、と最初に認めています。型がなくても観測そのものはやっていただろう、と答えたチームがあったからです。型がチームに足したのは観測する行為ではなく、観測結果を事前に決めた基準に照らして次の判断につなげる部分でした。いちばん堅く確認できた付加価値は、PM が持っていた判断の前提がエンジニアに共有されて目線が揃うこと。しかも狙いはリリース後の判断更新でしたが、実際に効いたのはリリース前に「リリース後に何を観測するか」を決める段階だった、と書かれています。4月の発表で挙げていた3つの付加価値のうち、事前の判断設計は「型に付随して生まれた効果ではなく、型を回すこと自体に含まれるステップ」だとして最終的に外しています。

評価の手続きが本題です。2チームへの振り返りアンケートにあたり、判定の基準、チームがどう答えるかの自分の予測、どの結果が出たらどの主張をどの強さで立てるかを文章にし、日付を入れて回答を見る前に凍結しました。回答を見てから「こう来ると思っていた」と書くことはできるけれど、それだと予測の当たり外れを数えられない、という理由です。

凍結したおかげで見えたことが具体的です。片方のチームで、当たった4件はいずれも本人の発言か実際に残っている記録を根拠にしたもの、大きく外れた3件のうち2件は観察した行動から相手の意識を推定した予測でした。いちばん外れたのは「今後チームだけで型を回せそうか」で、エンジニア2名は回せそうと答えると予測していたのに、3名とも慎重な回答。しかも全員が、外からの客観的な視点がなくなることをハードルに挙げていました。「チームが進行を担えるか」という観点だけで予測を立てていて、自分が実際にやっていたこと、つまりチームの中からは出てこない問いを投げることを、予測に入れていなかったのです。対処として、予測を書くときに根拠の種類も併記し、観察した行動からの推定なら確信度を最初から1段下げることにしています。

設問の作り方も丁寧です。感想を求める形を避け、「型がなかったとしたら」という反実仮想で聞く。ただしそのままだと「たぶん同じだったと思います」で終わりかねないので、最後の Decision Review で実際に決めた内容を設問文に書き込み、その場面に限定して聞いています。読み方の規律も同じ水準で、片方のチームで「あまり価値を感じなかった点」が3名とも空欄だったことについて、不満がなかったのか、書く負担や遠慮なのか、空欄では区別がつかないとして、ここからは何も読み取っていません。

いちばん効いている設計が、書き換えのルールを強める側と弱める側で非対称にしたことです。強めるときは結果を見る前に条件を決めておき、該当した場合だけ書き換える。弱めるときは妥当な理由があれば事前の条件なしでも書き換える。あとから「言い過ぎでした」となるほうが、「控えめすぎました」となるよりはるかに困るから、という説明に無理がありません。実例も両方あります。「計測の準備にチームが自ら時間を割くようになる」は、複数名が見込みではなく実際にそうなっていると書くことを条件にしていて、該当したのが1名だったので確認できたとは書かない。ただし、そう書いた事実は残して効果として主張しないだけにする。一方、片方のチームの結果だけで「自走のハードルは能力ではない」と断定していた部分は、もう片方の結果で成り立たなくなったので、理由を添えてその場で弱めています。

見積もりの失敗も自分から書かれています。8週間で一周する計画が実際は4ヶ月前後かかった。観測したいことが観測できる状態になるまでの時間を甘く見ていたためで、片方の案件はリリースから1ヶ月経っても使われておらず、観測を2ヶ月後まで延ばしました。

UX エンジニアリングの視点では、自己評価の構造を手続きで扱う、という発想がそのまま使えます。デザインの改善施策も、提案した本人が効果を報告する形になりがちです。「正しく評価しようという心構えだけでは、都合のいい方へ寄っていくのを止めるのは難しい」「事前に決めたことと実際の結果との差分を記録しておくほうが確実だ」という結びは、A/B テストの解釈でも、ユーザーテストの読み取りでも、同じように効きます。もうひとつ拾いたいのは、不確実性の高い案件をやったチームほど自走に慎重な答えを返した、という観察です。これは2チームの結果なので候補どまりだと扱われ、引き継ぎを自己評価だけで決めないことにしています。示唆に飛びつかず、次に何を記録するかへ変換しているのが、この記事らしいところです。

> 🐈‍⬛ : 結果を見る前に予測を凍結して、外れた予測の種類まで数えているのが丁寧です。行動から意識を推定した予測ほど外れた、という発見は、ユーザーテストの読み取りでも覚えておきたいところです。強めるときは事前の条件が要り、弱めるときは理由があればよい、という非対称なルールは、チームの振り返りにもそのまま持ち込めます。

## [Agentic Skill Decay](https://addyosmani.com/blog/agentic-skill-decay/)

> **出典**: Addy Osmani | **公開日**: 2026-08-31 | **カテゴリ**: performance

**3行まとめ**
- 以前はコードを書く副産物として自然に積まれていた練習量を、意図して取りに行く必要が出てきた、という主旨です
- 仮説を立ててから指示する、なぜを聞く、差分を読む、何が壊れそうか予想する、ときどき手で通す、という4つの介入点を挙げています
- 検証が床で、想像力が天井。出せるものはそのあいだに収まる、という整理で締められます

**詳細解説**

エージェント以前、判断力は失敗の副産物として溜まっていました。試して、壊して、原因を追って、他人の修正を読む。エージェントはそこを飛ばして問題から動くパッチまで数分で届けます。タスクが終わったことと、何かを学んだことは別だ、という指摘がこの記事の芯です。

Anthropic の研究がひとつ引かれています。ジュニアのエンジニアが Python の Trio というライブラリを学ぶ実験で、AI アシスタントを使った群のその後の小テストは50%、手で進めた群は67%でした。しかも AI 群のなかで成績が良かったのは、概念を質問して説明を求めた人たちで、モデルをコードの自販機として使った人たちではありません。Osmani 自身も「短期間・単一ライブラリの研究なので決定的とは言えない」と留保を付けたうえで、17ポイントの差は腑に落ちると書いています。

もうひとつ、約40万件の Claude Code セッションを見た研究では、専門性はタスク固有のものとして扱われ、中程度の知識があるだけで検証済みの成功に届く確率が上がっていました。スタック全体に10年の経験が要るという話ではなく、「良い」が何かを見分けられる程度にその領域を理解している必要がある、ということです。

良いエージェント仕事を支える2つの能力として、深い専門性（何が起きてほしいのか）と、応用された判断（何をもって起きたと認めるか）が挙げられます。そこから磨く技能として、意思決定、仕様化、舵取り、検証の4つ。実践としては、指示する前に何が悪いと思うか書き出す、作業中はなぜその手なのか・何を捨てたのか・システムについて何を仮定したのかを聞く、パッチが来たら差分を読んで何がまだ壊れうるか考える、ときどき手で通す。差分を読む1分が全体でいちばん価値が高く、いちばん飛ばされやすい、と書かれています。

著者はエージェントを控えめに使えとは言いません。日によっては5つ10つのセッションを並行させ、一度は別のプロジェクトにダークモードを足すよう頼んでしまった、という失敗談まで書いています。そこから出てくる制約が「エージェントの処理量は、自分の注意力より速く増える」でした。

終盤の二重ループの話が実務的です。良い1回の練習は自分を鋭くし、同時にエージェントも鋭くする。そうでないと、毎回のセッションが記憶喪失の新人をオンボーディングしているのと変わらなくなる。UI の微妙なスクロール不具合を解いたなら、その教訓を lessons.md か lint ルールか型制約かテストに移す。チャットウィンドウは死にますし、圧縮で残りも消えます。ただし markdown に投資しすぎないよう注意せよ、というただし書きも忘れていません。

UX エンジニアリングの視点では、「検証が床、想像力が天井」という定式化が使えます。Osmani はアルバムサイト用に3D のプレイヤーを作らせたとき、見た目以前にインタラクションの型が間違っていてモバイルの性能も出ていなかったと書いていますが、それに気づけたのは自分が同じ失敗をしてきたからです。プロンプトで何でも出せる時代に、コントラストが足りない、スクロールの挙動が良くない、画面領域の使い方が最適でない、と言えることの価値が上がる。デザインの目利きがそのまま検証能力になる、という読み方ができます。

> 🐈‍⬛ : 「検証が床、想像力が天井」という整理は、今週の記事全体をまとめてくれる言葉でした。コントラストが足りない、スクロールの挙動が良くない、と言える目は、同じ失敗を自分でしてきたから育つものです。差分を読む1分がいちばん価値が高く、いちばん飛ばされやすい、というのもよく分かります。
