## [AI活用で生まれた別のコスト](https://tech.smarthr.jp/entry/2026/09/02/120000)

> **出典**: SmartHR Tech Blog | **公開日**: 2026-09-02 | **カテゴリ**: design

**3行まとめ**
- 書くコストは下がったのに、読むコストとレビューのコストが別の人に移っているだけではないか、という自戒の記事です
- AI生成のPR説明が詳細すぎてレビュワーに優しくない、という具体例から、情報量が多いことと親切は違うと整理しています
- 「個人が楽になったのか、チームの生産性が上がったのか」を、摩擦の減少という観点で見分けよう、という提案でした

**詳細解説**

SmartHR で給与計算機能を開発しているプロダクトエンジニアの方による記事です。社内ではコーディングだけでなく、PRD、チケット、テスト計画書、ヘルプページと、あらゆる成果物の作成でAIを使うのが当たり前になった。書く側の時間は大きく短縮され、もう以前の仕事の仕方には戻れそうにない。そのうえで、読み手やレビュワーの立場から見ると、AIが生成する文章の乱立が別の場所でコストを生んでいるかもしれない、という気づきが出発点になっています。

具体例として挙がるのがプルリクエストの説明文でした。変更ファイルごとに「やったこと」が並んでいるものの、結局どこが本質的な変更なのかを読み解くのに時間がかかる。文章量は多いのに、読み手が知りたいことには答えていない。著者の見立ては、AIはコード差分の要約には強くても、レビューの交通整理を任せるのはまだ難しい、というものです。だから、人間が要点を抽出して自分の言葉で書くか、AIに書かせたうえで読み手の判断に影響しない詳細を人間が削る。それだけでPR上のやりとりは滑らかになる、と。

「情報量が多い」ことと「親切」は違う、という節も具体的です。どの文章もボリュームがある。ただでさえAIでドキュメントが増えているので、AI生成のドキュメントを開いただけで身構えてしまうことがある。それっぽいことは書いてあるが結局何が言いたいのかわからない。重要度の濃淡がなく、詳細すぎて概要や構造がつかめない。文章を増やすのが簡単になったぶん、何を削ると伝わるか、どの情報を際立たせるかという人間の推敲の重要度は、むしろ上がってきている、という結論です。

もうひとつ指摘されているのが、見た目の完成度と中身のずれでした。PRの説明、仕様書、設計メモは、ぱっと見の完成度が高くても、実際には未検証の仮説、AIが補完したそれっぽい説明、人間がまだ合意していない内容が混ざっていることがある。その場合、生成した人の時間は短縮されていても、読む人・確認する人・判断する人の負荷は増えている。だから「個人が楽になったのではなくチームの生産性が上がったか」を見極めるには、レビューする人のコストが増えて相殺していないか、読み手との認識のずれが減らせそうか、という「摩擦の減少」も一緒に見るとよさそうだ、という提案になっています。

UXエンジニアリングの視点では、この記事が今号の GitHub Copilot の記事と同じ構造の指摘をしているのがおもしろいところです。あちらは「ツール呼び出し1回のトークンを減らしても、足りない情報を取り戻すために往復が増えるならタスク全体では高くつく」という局所最適の罠の話でした。こちらは、その罠が組織のなかで人をまたいで起きている。最適化する単位を、自分の作業時間から、成果物が誰かに読まれて判断されるまでの全体に広げる、という点で同じことを言っています。記事の最後にあるチェックの4項目（生成物には必ず自分で目を通す、読み手に不要な情報を削って推敲する、読み手が咀嚼しやすい粒度にまとめる、一歩引いて見る）は、そのまま自分のチームのレビュー規約に置けるくらい具体的でした。

> 🐈‍⬛ : 「情報量が多い」と「親切」は違う、という一行がこの記事の仕事です。書く側の時間だけを見れば改善なのに、読む人・確認する人・判断する人のところで相殺されている。同じ形の負債は文章以外でも起きていて、案が10枚出てくるデザインレビューや、網羅的すぎるテストケースも構造は同じです。生成が安くなったものは、そのぶん誰かの目を余分に使う。最後のチェック4項目が、そのままレビュー規約に置ける粒度なのもいいところ。

## [AI is making development faster. But where did the work go?](https://medium.com/design-bootcamp/ai-is-making-product-development-faster-57a86bc3ffa0)

> **出典**: Sidebar | **公開日**: 2026-09-04 | **カテゴリ**: design

**3行まとめ**
- 局所的に速くなったとき、その周りにあった労力はどこへ行ったのかを問い直す記事です
- コード化されたプロトタイプを本番の出発点にしようとしたら、視覚的な引き継ぎの段差が構造の段差に置き換わっていました
- 「プロトタイプのコードは本番品質でなくてよいが、本番で使える形であってほしい」という基準の言い直しが実用的です

**詳細解説**

リサーチ中心のデザイン業務では、AIによる高速化がはっきり効いていると著者は書きます。ディスカバリーやユーザーテストの書き起こしを整理し、繰り返し出てくるテーマを取り出し、提案の土台まで組む。数日かかっていた統合が1日以内にまとまることもある。ただし出力を読み、疑い、何が重要かを決め、語られる筋がリサーチに支えられているか確かめる責任は消えていません。変わったのは、意味を作る作業に入る前の時間の量でした。その余白が、最初のまともな答えで妥協せずもう一方向を探る、あるいは締め切りで削られがちなユーザーテストをもう1回入れる、といった使い方に回る。ここまでは素直な利得です。

複雑なほうの例が本題です。著者のデザインチームは、コード化されたプロトタイプを本番の出発点として開発が再利用できないか試していました。動機は妥当で、従来の引き継ぎでは余白のずれ、意図と違うレスポンシブ挙動、簡略化された相互作用といった小さな差が積み上がってデザイン負債になる。設計意図がより多く成果物と一緒に旅をすれば、伝言ゲームを減らせるはずでした。

ところが実践で詰まります。デザイナーが作ったコード化プロトタイプを開発が再利用する前提だったのに、チームは下地の構造を一貫して評価できる技術的な深さを必ずしも持っていなかった。見た目と挙動に目が向いているあいだ、コンポーネント構造・コードの整理・レスポンシブ挙動の問題は本来より遠くまで流れていく。開発が受け取った時点で、表面は完成間近に見えるのに出発点として使いにくい。数千行に育ったページ、境界が曖昧なコンポーネント、設計意図と合わない実装。レスポンシブな体験のはずが、別々のアダプティブレイアウトのように作られていたこともあった。視覚的な引き継ぎの段差を減らそうとして、構造の引き継ぎの段差を作ってしまった、という総括です。デザインは速くなったが、労力の一部は下流に移っただけでした。

引かれている研究も効いています。Vella と Blincoe の2026年の縦断研究では、ソフトウェアエンジニアがコードを書く時間を減らし、AIの出力を指示・評価・修正する作業へ比重を移していた。研究者はこれを「監督的なエンジニアリング作業」と呼び、著者は「ベビーシッター」と呼んでいます。DORAの2025年の研究からは、AIは周りのシステムを増幅する、という読み方が引かれます。強いワークフローは速度をより価値あるものにし、弱いワークフローは下流の摩擦に変える。AI採用度が高いほどデリバリーのスループットは改善しつつ、デリバリーの不安定さも増していた。速度にはチームのほうが先に適応し、それを安全に支えるシステムの適応が追いついていない、という解釈です。

いちばん使えるのは「good enough」の言い直しでしょう。**プロトタイプのコードは本番品質である必要はないが、本番で使える形であってほしい (production-useful)**。具体的には、開発が全体をほどかずに取り出せる程度に構造化されていること、コンポーネントの境界が明確なこと、再利用できるはずの部分が実際に再利用できること、レスポンシブ挙動が設計意図と一致していること。そして求める厳密さは、そのプロトタイプが下流に何を及ぼす想定かで決める。来週捨てるかもしれない探索用の画面なら緩いコードでかまわないが、構造・挙動・コンポーネントが本番に運ばれる前提なら話が変わる。

DORAの報告がこの緊張に直接答えているのも紹介されています。速く直せるなら不安定さは許容できるのではないか、という想定は支持されなかった。スループットが改善しても、不安定さは製品パフォーマンスと燃え尽きに意味のある悪影響を残していた。速度を借りているのか、妥当な取引をしているのか、どちらをしているのか知っていることが大事だ、という締め方です。「誰かがAIでチームが速くなったと言うとき、何が速くなり、残りの仕事はどうなり、顧客はより早く価値を受け取ったのかを知りたい」。測る側の語彙として、そのまま使えます。

> 🐈‍⬛ : 「本番品質でなくてよいが、本番で使える形であってほしい」の言い直しが実用的です。プロトタイプに求める厳密さを、下流に何が運ばれる想定かで決める。構造や挙動やコンポーネントが本番まで旅するなら基準は上がり、来週捨てる探索用の画面なら緩くていい。視覚的な引き継ぎの段差を消したら構造の段差ができた、というのは今号の「別のコスト」とまったく同じ形で、労力は消えずに下流へ移っただけでした。DORA の「速度を借りているのか、妥当な取引をしているのか」という問いの立て方も覚えておきたいところ。

## [How we make AI coding more cost efficient without sacrificing task quality](https://github.blog/ai-and-ml/github-copilot/how-we-make-ai-coding-more-cost-efficient-without-sacrificing-task-quality/)

> **出典**: GitHub Engineering | **公開日**: 2026-09-02 | **カテゴリ**: engineering

**3行まとめ**
- ツール呼び出し1回のトークンではなく、完了したタスク全体で効率を測る、という原則を4つの実例で示した記事です
- 出力を短くする既製ツールを評価したら、欠けた情報を取り戻すためにターンが増えてタスク全体では高くついた、という失敗から始まります
- 行番号の接頭辞を消す、プロンプトを圧縮する、完了通知に結果を同梱する、といった変更をそれぞれA/Bで検証しています

**詳細解説**

出力の質は大事だけれど、本当の効率は「速く、無駄なく、適切な文脈で」仕事が終わることから来る。だからツール呼び出し単体のトークン数は意味のある指標ではない、という前提から始まります。簡潔なツール応答が、エージェントの必要とする情報を落としていたら、追加の呼び出しや作業を招いて、結果としてタスクは遅く高くなる。最適化するのはツール呼び出しではなく結果のほうだ、という原則です。

その具体例が RTK（Rust Token Killer）の評価でした。エージェントが読む前にシェル出力を短くするユーティリティです。GitHub のハーネスとベンチマーク構成で試したところ、たしかにいくつかの応答は短くなったのですが、省かれたテキストが重要だったとき、モデルは元の出力を開き直したりコマンドを再実行したりして取り戻そうとしました。その回復のぶんターンが増え、文脈が持ち越され、平均するとタスクはトークンも時間も増えた。局所的に節約して、全体で余計に払った、という結果です。

そこから出てきたのが、選択的な出力圧縮でした。ベンチマークの分析から、install・build・test・lint の出力は繰り返しのノイズが多く、ソースらしい出力や任意のコマンド結果はエージェントが必要とする情報を含みやすい、とわかった。初期版は攻めすぎて、モデルに作業を繰り返させたり保存済みの全文を読ませたりして、かえって高くなり成功率も下がりました。たとえば最初は `git diff` を圧縮していたのですが、エージェントが元の出力を開き直すのを見てその対象から外しています。結果として3部構成の方針に落ち着きました。ソースらしい出力と任意の出力はそのまま返す、検索結果は内容を落とさずまとめ方だけ変える、繰り返しのノイズは節約が大きいときだけ圧縮する。しかも圧縮したときは元の全文への復旧経路を残し、その経路が使われた頻度を評価の信号として追跡しています。

いちばんきれいな変更として紹介されているのが `view` ツールの話です。ファイル内容をモデルに見せるとき、各行に行番号を付けていました。かつてのファイル編集ツールはその番号で変更箇所を指定していたのですが、いまのツールは周囲のコードと照合するので番号を使っていません。使われないまま残っていた書式が、すべての行、すべてのファイル読み込みで積み上がっていた。消したところ、オフラインのベンチマークで推論コストが約5%下がり、成功率は実行ごとのばらつきの範囲に収まり、編集の失敗も増えませんでした。CLIの利用者で試したオンライン実験では、1人あたりの1日の推論コストが約3%下がっています。モデルへの新しい指示もなく、取り戻す必要のある情報もなく、判断も増えない。ファイルの中身は変わらずモデルに届く、という点で理想的な変更でした。

プロンプト圧縮の節には、そのまま教訓として使える失敗が書かれています。並列作業のために専門エージェントを起動する task ツールのガイダンスが、ツール説明・スキーマ・エージェント定義・システム指示・関連ツールに散らばって膨らんでいた。Copilot に自分自身のプロンプトを反復的に書かせるループで、およそ半分に縮めました。ところが最初のオンライン実験で、オフライン評価が見逃していた退行が見つかります。そのループが、慎重な並列化のガイダンスを固い スケジューリング方針に書き換えてしまい、独立したカスタムエージェントが直列に走るようになっていた。実験を止め、プロンプトを触る前に、利用者が露呈させたその振る舞いに対する退行テストを書いた。最終的な修正は、明示的な許可リストと禁止リストを1文に置き換えるものでした。「独立したエージェントは並列に実行できる。副作用は考慮すること」。短く、制約も緩く、並列にするかどうかの判断をモデルに委ねる形です。プロンプトの振る舞いにはテストが要る。テストされていない振る舞いは、短いプロンプトが誰にも気づかれずに消してしまう、という一文が結論でした。

UXエンジニアリングの視点で持ち帰れるのは、最後の5つの教訓のうち3つ目と5つ目でしょう。「出力が何を表しているかで圧縮を決める。正確な内容は保ち、可逆な変換を優先し、復旧経路がどれだけ使われたかを測る」。そして「証拠はワークロードに固有である」。実際、コードレビューで良い結果を出したファイルツールの指示の締め直しを CLI で試したらコストが増えたので出荷していない、という例まで挙げられています。どの変更も、それが動く流れのなかで測る。モデルを賢くした変更はひとつもなく、モデルがそもそもやる必要のなかった仕事を取り除いただけだ、という締め方でした。

> 🐈‍⬛ : 個人的にいちばんおもしろかったのは、`view` の行番号を消したら5%下がった話です。かつて編集ツールが使っていた書式が、使われなくなったあともすべての行・すべての読み込みに乗り続けていた。フロントエンドにも同じ形の残骸はあって、参照されない data 属性や、誰も読まない aria がそれにあたります。もうひとつ、プロンプトを半分に縮めたら並列実行のガイダンスが固いスケジューリング方針に化けていた件は、「プロンプトの振る舞いにも退行テストが要る」の実例として強い。RTK の評価を「効かなかった」まで書いているのも誠実です。

## [Portal by Spotify cut my Claude Code token usage by 90%](https://engineering.atspotify.com/2026/9/portal-by-spotify-cut-my-claude-code-token-usage-by-90/)

> **出典**: Spotify Engineering | **公開日**: 2026-09-03 | **カテゴリ**: engineering

**3行まとめ**
- コーディングエージェントの仕事の大半は思考ではなくI/Oだ、という見立てから始まる記事です
- 大きなファイルの読み込みとボイラープレート生成を安いモデルへ振り分けるだけで、トークン消費が平均90%減りました
- 委譲できないもの（編集・推論）とレイテンシの限界まで書いてあるのが、この記事のいいところです

**詳細解説**

書き出しの一文が効いています。「エージェントがやってくれることのほとんどは、思考ではなくI/Oだ」。ひとつのメソッドについて答えるために5つのファイルを読む、隣に並んだ20個のテストファイルとまったく同じ形のテストを書く、打ち合わせのあとにドキュメントを更新する。ここで消えていくトークンには、推論がほぼ含まれていません。痛いのは席のライセンス料ではなくトークンなのに、そのすべてを、この仕事には過剰なフロンティアモデルに食べさせている、という問題設定です。

背景の数字も置かれています。2028年にはAIコーディングのコストが開発者の平均給与を超えるというGartnerの予測があり、エンジニアリング責任者の4分の1はすでに開発者1人あたり月200〜500ドルをトークンに使っている。2,000ドルを大きく超えている組織もある。ツールは元が取れる、ただしフロンティアのトークンを、それを必要としない仕事に燃やすのをやめた場合に限る、と続きます。

仕組みは3層です。第1層のフックがいちばん効いています。Claude Codeのフックはツール呼び出しの前に発火するので、`Read` が既定350行を超えるファイルに向かったら、フックがその読み込みを止めて `/bulk-reader` スキルへ誘導する。`cat`、`head`、`tail` も同様に捕まえますが、`cat file | grep` のようなパイプは狙いを絞った読み込みなので通す。第2層のスクリプトがPortal CLIを包み、第3層のスキルが「いつ・どう呼ぶか」を教える。この積み方の要点は、Claudeがスキルの説明を読まなかったとしてもフックが高コストの読み込みを止める、という劣化のしかたにあります。

UXエンジニアリングの視点で読み替えると、これはエージェントに対する段階的開示とガードレールの設計そのものです。CLAUDE.mdにルーティング規則を書いた最初の版は「助言であって強制ではなく、Claudeが無視できた。しかもプロジェクトごとに写しが必要だった」と振り返られています。方針を文書として置くだけでは足りず、実行経路のうえに置いて初めて守られる。エージェント向けの指示を書く人が何度も踏む段差が、ここに素直に書かれています。

限界の節が誠実です。編集は委譲できない。ワーカーモデルの要約には信頼できる行番号が入らないので、分析にもとづいて手を入れるなら該当箇所は直接読むしかない。推論も委譲できない。ワーカーは表層のパターンは見つけたのに、スレッド安全性の微妙な不具合を見落とし、適切な文脈を与えられたClaudeは数秒で気づいた。だからデバッグ・アーキテクチャの判断・安全性が要る箇所は、ルーティングから明示的に外してある。そしてレイテンシは、1回の委譲がネットワーク往復なので10〜30秒かかり、Portal側の上限も30秒。小さな読み込みでは委譲のオーバーヘッドが節約を上回るので、行数のしきい値がある。

いちばん持ち帰りやすいのは最後の一段でしょう。プラグインは「いつ委譲するか」を決め、モードは「どう応えるか」を決める。この2つを分けておくと、ワーカーモデルをより安いものに差し替えてもプラグイン側は変わりません。モデルルーティングをシステム設計の問題から設定の問題へ移す、という整理です。

> 🐈‍⬛ : CLAUDE.md に書いたルーティング規則が「助言であって強制ではない」ので無視された、という一段が効いています。方針は文書に置くだけでは守られず、実行経路のうえに置いて初めて守られる。今号の `design.md` が「機械的に判定できる失敗はコードの決定論的なチェックへ」と分けているのと同じ判断です。フックが高コストの読み込みを止めるので、スキルの説明を読まなかったときも安全側に倒れる。委譲できないもの（編集と推論）とレイテンシの限界を先に書いてあるぶん、どこまで真似できるかも見積もれます。

## [useStateとuseEffectだけじゃもったいない！ ユーザー体験を改善するReactの便利機能](https://ics.media/entry/260903/)

> **出典**: ICS MEDIA | **公開日**: 2026-09-02 | **カテゴリ**: frontend

**3行まとめ**
- React 18・19以降で入った機能を「ユーザー体験の改善」という軸だけで並べ直した解説です
- `<Suspense>`、`useTransition`、`useDeferredValue`、`useOptimistic`、`<Activity>` を動くデモ付きで扱っています
- `<Activity>` のプリレンダリングは、表示される可能性が高いコンポーネントに限る、という注意まで書かれています

**詳細解説**

機能の一覧ではなく「ユーザーを待たせない」「ユーザーの入力を消さない」「重い処理は裏側で実行して見せない」という3つの目的で章立てされているのが、この記事の良さです。同じAPIの説明でも、どの体験の問題を解くために使うのかが先に来ると、選ぶときの手が動きます。

待たせない章は4つ。`<Suspense>` は複数のコンポーネントを別々に囲むと準備できたところから表示できるので、待たされている感が軽くなる。JotaiやTanStack Query、Next.jsはサスペンスに対応しているので導入は思ったより軽い、という実務の補足も添えられています。`useTransition` は `startTransition()` のなかの状態更新を優先度の低いものとして扱い、ユーザー入力などより優先度の高い更新に中断させる。料金計算のデモがわかりやすく、使わない側は操作のたびに数値が何度も切り替わり、使う側は計算中に「calculating…」を出して完了後に1度だけ更新します。計算処理がスキップされるのではなく状態更新が中断される、という区別が明記されているのも親切です。

`useDeferredValue` は用途が近いのに効き方が違います。受け取った値を使う画面描画を遅らせるので、最終的な結果を表示するまで古い検索結果が残り、スピナーのチラつきが消える。`searchResource !== deferredResource` で検索中かどうかを判定する書き方も、そのまま使える形で示されています。`useOptimistic` は楽観的更新で、「いいね」のような単純な更新にローディングが出ると遅いアプリだと感じられてしまう、という動機から入ります。確定した状態と楽観的な状態を別に持ち、保存が完了したら確定させる。失敗したら値が元に戻る、という挙動もひとこと押さえてあります。

`<Activity>` の章がいちばん新しい話でしょう。囲まれた子要素は非表示にしても状態が保持されるので、複数ステップのフォームで画面外の入力値を保つために、これまで必要だったグローバルな状態への逃がし方が要らなくなります。そしてもうひとつの使い方がプリレンダリングです。非表示でも優先度を下げたうえでレンダリングされるため、`use()` によるデータ取得が表示前に走る。デモでは2画面目の国リスト取得に1秒かかるのに、`<Activity>` 側は素早く表示されます。ここで「表示される可能性が高いコンポーネントに限るほうがよい」という注意が入るのが誠実で、ほとんど表示されないものを先に描いても無駄な処理が走るだけです。

UXエンジニアリングの視点で補足すると、この記事の並びは、uhyoさんのReact習熟度ベンチマークの結果と裏表になっています。そのベンチマークでは `useTransition` と `useOptimistic` が43実装中ゼロで、代わりに `useMemo`/`useCallback` が広く撒かれていました。つまりここで紹介されている並行レンダリング系は、モデルが自発的に選んでこない領域です。生成に任せる場面が増えるほど、こういう「体験の設計として選ぶAPI」を人間側が把握して指示に落とす価値が上がる、と考えると読み方が変わってきます。次回は開発体験を改善する機能とのことなので、続きも期待できます。

> 🐈‍⬛ : APIの一覧ではなく「待たせない／入力を消さない／重い処理を見せない」という目的で章立てされているのが、この記事の効いているところです。同じ `useTransition` の説明でも、どの体験の問題を解くために使うのかが先に来ると、選ぶときに手が動く。`<Activity>` のプリレンダリングに「表示される可能性が高いものに限る」と注意を添えているのも誠実。並行レンダリング系はモデルが自発的に選んでこない領域なので、生成に任せる場面が増えるほど、人間側がこの並びを覚えておく価値が上がります。

> 🐈‍⬛ : 「なぜ `filter: brightness()` ではないのか」の説明が、この文書のいちばんの収穫かもしれません。ページはSDRで合成されるので、フィルターもブレンドモードもCSSの色を白より先へは押し出せない。ヘッドルームを持てるのはHDRのコンテンツだけ、という一段で、色の話がブラウザの合成まで戻ります。実装メモとしては `@media (dynamic-range: high)` で囲む形が要点で、SDR・Firefox・印刷には本物の `color` が残り、`background-clip` がはみ出した行を切ってしまう落とし穴も同時に避けられる。「正直な限界」という見出しを自分で立てているところにも信用が置けます。

**詳細解説**

Sean Goedecke さんは2025年に「エンジニアは会社にいくら稼がせたかではなく、同じ役職の平均的なエンジニアと比べてどれだけ多く稼がせたかで評価されるべきだ」と書きました。今回はその続きです。2010年代なら、置き換え水準のエンジニアでも十分に給料を払う価値がありました。コードを書くこと自体に高い固定費がかかっていたからです。いまその固定費は月100ドル程度になった。あなたの立場で、モデルがやらないことを何をしているのか。2桁も3桁も多く払う理由は何か、という問いから始まります。

まず釘を刺されるのが、逃げ道の潰し方です。LLMは実はコードを書けないとか、生成されたコードは本質的にひどいので使っている会社は来年潰れるとか、そういう話に逃げても自分のためにはならない。2027年に目覚めたらAI狂騒が終わっていて全員が手でコードを書いている、ということにはならない、と。そして、深い専門性を要する「硬い」領域に退避する作戦にも懐疑的です。2026年初頭には「大きなコードベースに動く変更を入れる」がその領域に入っていたのに、いまはもう入っていない。的が動き続けるからです。

そこで著者が採るのは、「モデルが時間をかけても良くなっていない仕事」「原理的に良くなりにくい仕事」を探すという方針でした。1つ目はコードベースへの深い馴染み。フロンティアのモデルが犯す間違いは、もう素の幻覚やオフバイワンではなく、無知による間違いだと言います。再実装せずに済むモジュールが社内にあるのを知らない、この機能の置き場所として標準なのはシステムXだと知らずに別の場所に入れる、社内の慣習と違うスタイルで書く。あるいは過剰な用心による間違い。設定から一度だけ入って更新されない値に三重の検査を入れる、10ミリ秒の古さを許容できないと決めつけて複雑な同期を設計する、クラッシュしていいCLIツールに丁寧な劣化処理を組み込む。どれも、能力はあるがその場に長くいない賢いエンジニアがやりそうなことです。

ここに心理的な要素が加わります。エージェントは説得力があるので、「これはよくない、XもYも要らないと思う、なぜもっと単純にZでいけないのか」と言い切る度胸が要る、と。そして、これを別のエージェントのレビューで代替できない理由も明快でした。同じモデルなら同じ前提と同じ間違いを再現するし、違うモデルでも構造的な理由から同じ種類の間違い、つまり無知と過剰な用心に寄っていく。しかも現代のモデルは何であれ細かい指摘をひねり出すよう強化学習されているので、批評役と作業役を往復させると、用心深いスロップが1万行できあがるだけになりがちだ、という指摘です。

2つ目のコミュニケーションの議論も、原因の説明がおもしろいところです。良い文章は検証可能な領域ではないので、数学やコードのように問題を生成して自動採点する道が使えない。人間に採点させると、単一段落で読んだときに平均的な人に見栄えのする文章、つまり1文に3つの修辞を詰め込む文体が出てくる。加えて、研究所は能力に一極集中してきた。内部の推論トークンを見ると、奇妙な語選択と切り詰められた文法になっていて、それを半分そのまま英語に直すとあの独特の文体になるのではないか、という仮説が示されます。Peter Watts の『Blindsight』に出てくる synthesist（略語と身振りで話す天才たちと、それ以外の人々のあいだの翻訳層を務める人）の比喩が置かれ、天才の国にも、その洞察を全員に翻訳する普通に賢い人が要るのではないか、と続きます。

UXエンジニアリングの現場に引きつけると、AIが書いた文章を人が反射的に読み飛ばすようになっている、という観察が刺さります。技術戦略の文書をAIが書いたまま回覧すると、同僚の多くは一語ずつ読むよう自分に強いる必要が出てくる。伝えたい相手が人間なら、人間が書くことに大きな利点がある、という話です。結びは「meat proxy（依頼をエージェントに貼りつけて出力を自分の成果物として出すだけの人）にはなるな」。定義からして自分では価値を足していないので、解雇を願い出ているようなものだ、と。複数エージェントの「ソフトウェア工場」を組んでいても、その仕組みが企業向けのAIツールに取り込まれた時点で不要になる、という指摘まで含めて、なかなか容赦がありません。

> 🐈‍⬛ : モデルの間違いを「無知」と「過剰な用心」の2つに整理したのが、今号でいちばん持ち帰れる道具です。そう見ると、ここに並んだ Code Connect も `design.md` も AGENTS.md も、全部が無知を減らすための投資でした。もう片方の過剰な用心——設定から一度だけ入る値に三重の検査を足す、クラッシュしていいCLIに丁寧な劣化処理を組む——を止められるのは、いまのところ「これは要らない」と言い切る人のほうです。別のエージェントにレビューさせても同じ種類の間違いに寄っていく理由を、構造から説明しているのも納得感がありました。
