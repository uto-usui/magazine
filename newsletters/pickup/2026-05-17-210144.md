## [Apps and programming: two accidental tyrannies](https://andymatuschak.org/tat/)

> **出典**: Sidebar | **公開日**: 2026-05-13 | **カテゴリ**: design

**3行まとめ**
- アプリの「サイロ化」とプログラミングの「専門職化」という、パーソナルコンピューティングが意図せず生んだ2つの制約を、コーディングエージェントが解きほぐしつつあるという議論
- CodeMirror の「ファセット（facets）」を例に、プラグイン同士が衝突せず合成可能になる宣言的アーキテクチャと、エージェントがその実装コストを肩代わりする組み合わせの可能性を示す
- 発明のボトルネックがプログラミングからイマジネーションへ移ることで、デザイナーやドメイン専門家が直接プロトタイプを動かす文化が立ち上がりはじめている

Andy Matuschak が、ソフトウェアの未来をめぐる重要な論考を発表しました。テーマは「アプリケーションモデル」と「プログラミングの専門職化」という、ふだん当たり前すぎて疑われない2つの構造です。前者は、開発コストを回収するためにソフトウェアが「one-size-fits-all」になり、ユーザーが自分の道具を本当の意味で持てなくなった状況を指します。後者は、新しいインターフェイスの発明にプログラミングが必須となった結果、デザインやドメインの直感を持つ人々が「壁打ち相手」を待つしかなくなった構造です。

技術的なポイントとして読み応えがあるのは、Obsidian と CodeMirror を題材にした「合成可能性（composability）」の解説です。CodeMirror はテキストエディタを「プラグインの集合」として設計しており、装飾・キーバインド・トランザクションといった関心領域ごとに、プラグインが「やりたいこと」を宣言的に表明し、フレームワークが衝突を解決します。Matuschak はこの仕組みを使い、書籍内の一節を音声で参照する Quote Leap と、トランスクリプトと音声を同期する Audio Transcript という2つの複雑なプラグインを、コーディングエージェントの支援で実装してみせます。

注意したいのは、後半で語られる「scattered, frenetic energy」という副作用です。エージェントと往復している時間が長くなるほど、手で作る喜びや、深く考える時間が損なわれる。著者自身が「考えることを避ける手段としてエージェントと打ち合うようになっていた」と告白する場面は、設計者が今後向き合うべき切実な課題でもあります。

> 🐈‍⬛ : エージェントの登場は単なる「コードの量産」ではなく、宣言的アーキテクチャと組み合わさったときに本当の意味で「拡張可能なソフトウェア」を実現する、という補助線がいい。先週の「Design is the work」が言っていた「意図を定義する仕事」が、なぜ次の十年で価値を持つのかが、構造の側から裏付けられている読み物。

## [The prompt is not an interface](https://uxdesign.cc/the-prompt-is-not-an-interface-41b77277681d)

> **出典**: UX Collective | **公開日**: 2026-05-11 | **カテゴリ**: design

**3行まとめ**
- 「最先端のAIシステムが、点滅するカーソルと空のテキストボックスでコミュニケーションを求めてくる」という違和感の指摘
- 過去40年のインタラクションデザインは、コマンドラインからdirect manipulationへ進んできたのに、AIで巻き戻った
- UX Collectiveの今号は、AI時代のチャットUIと「プロダクトオーナーシップ」を巡る記事を横断紹介

UX Collectiveのニュースレターで、Fabricio Teixeiraがメイン記事に取り上げているのは「The prompt is not an interface」というエッセイです。「最も進んだAIシステムが、史上もっとも貧弱な入力欄を通してコミュニケーションを要求してくる」という導入が痛烈で、過去40年のインタラクションデザインの蓄積がいったんゼロに戻ってしまったような感覚を持ったことがある人には刺さる視点でしょう。

同号で紹介されているほかの記事も興味深いラインアップです。「You skipped the first question. Now you're adding AI.」は、AIを追加することで、もともと飛ばしていた根本的な問いが浮き彫りになる、という指摘です。「The forgotten conversation problem in AI chat」「10 UI patterns that won't survive the AI shift」「How to make Claude follow your design system」など、AIチャットUIとデザインシステムをどう繋ぐかというテーマが集まっています。

UXエンジニアリングの視点でいうと、プロンプトを最終UIにしないための「足場」を考えることが、AI機能を製品化する人の仕事になりつつあります。direct manipulationの伝統を、AI機能の上にもう一度乗せ直す手法を模索するうえで、今号の記事群は手元のブックマーク行きになりそうです。

> 🐈‍⬛ : 「テキストボックスに丸投げ」のUIが量産されている時期だからこそ、direct manipulation の歴史を一度棚卸ししたい。続く「Practical Interface Patterns For AI Transparency」とセットで読むと、空のテキストボックスから次に何を足すか、の見取り図が手に入る。

## [Mockups were never the hard part](https://www.lukew.com/ff/entry.asp?2152)

> **出典**: Sidebar | **公開日**: 2026-05-12 | **カテゴリ**: design

**3行まとめ**
- AIによって誰でも数分でモックアップを作れるようになり、デザイナーの仕事の本質が浮き彫りになった
- 難しいのは常に、プロダクト全体の一貫性と意図を保ち続けることであり、モックの作成自体ではなかった
- 全員がモックを持って打ち合わせに来ることで、議論が「どっちが好き?」から「機能はどう関係するか?」という設計の本筋に移る

Luke Wroblewskiの短いエッセイ。バックエンドエンジニアもプロダクトマネージャーもフロントエンドエンジニアも、それぞれAIで作ったモックを持ち寄って打ち合わせに来た、という最近の体験談から始まります。「これでデザイナーの仕事がなくなる?」と思いきや、議論はむしろ深まったといいます。

参加者全員にベースラインがあるおかげで、「自分のアイデアはこう」「私のはこう」というプレゼンの応酬を飛ばして、いきなり機能どうしの関係、データ構造、ユーザーのメンタルモデルといった本質的な問いに入れた。著者がビジネススクールの教育者から聞いた話とも符合します——学生全員がAIで事前分析を済ませてくるようになって、授業の時間がベースライン到達ではなく、その先の議論に使えるようになった。

注意したいのは、「全員がモックを作れる」状態を活かすには、出てきたモックを材料に深い対話に持ち込めるファシリテーション能力が要ること。誰のモックを採用するかではなく、なぜそう設計するかを問える人が場を動かす、という現実的なメッセージが詰まった一本です。

> 🐈‍⬛ : 「ベースラインの民主化で議論が上に上がる」という構図は、ビジネススクールの例えがとてもわかりやすい。AIで生成された複数のモックを並べる時間そのものが、デザイナーの「司会業」のスキルを底上げする時間になっているのが面白い。

## [Practical Interface Patterns For AI Transparency (Part 2)](https://smashingmagazine.com/2026/05/practical-interface-patterns-ai-transparency/)

> **出典**: Smashing Magazine | **公開日**: 2026-05-13 | **カテゴリ**: design

**3行まとめ**
- AIエージェントの「思考中」を表現するために、従来のスピナーは機能しない。何を、なぜ、どの境界の中で実行しているかを言葉と構造で示す必要がある
- Living Breadcrumb / Dynamic Checklist / Thinking Toggle / Audit Trail という4つのパターンを、リスクとタスクの重要度に対応させて使い分ける
- 失敗時には「ツール側の問題」と「AI 自身の能力」を切り分け、部分的成功を率直に表示するなど、信頼を育てるマイクロコピー設計が鍵

「AIが20秒沈黙しているとき、ユーザーは何を見せられているべきか？」という問いに、Victor Yocco が真正面から答えています。前編の「Decision Node Audit」で透明性を確保すべき瞬間を洗い出したうえで、後編は具体的な UI コンテナの設計に踏み込みます。

中心となるのは「Agentic Update Formula」、すなわち Action Word（動詞）／ Specific Item（対象）／ Limits（制約）という3点で状態更新文を組み立てる定式です。`"Searching for flights…"` ではなく `"Scanning prices on Lufthansa and United under $600"` と書く。ユーザーの依頼を正しく咀嚼していることを毎ステップで伝えることで、「沈黙への不安」を「いまここを処理している」という安心に変換します。

注目したいのは、4つのパターンを Impact/Risk Matrix で使い分ける視点です。低リスクのバックグラウンドタスクには Living Breadcrumb、金融取引のような高リスクには Dynamic Checklist、開発者向けには Thinking Toggle（生ログを開示する）、完了後に確かめたい場面には Audit Trail。それぞれが「ユーザーの不安」と「システムが返すべき信頼シグナル」を1対1で対応させていて、設計の語彙として実務で使いやすい構成になっています。

UXエンジニアリングの視点で重要なのは「Disentangling The Tool」のくだりです。Google Calendar の API がダウンしているとき、「カレンダーを確認できませんでした」とだけ書くと、AI が無能に見える。「Google Calendar との接続が応答していません。30秒後に再試行します」と書けば、AI は健全だが外部依存に問題があると伝わる。エラーの帰責を正しく分解することは、エージェントの信頼を守るための実装責務でもあります。

> 🐈‍⬛ : 「Action Word / Specific Item / Limits」の3点で状態文を組み立てる定式は、エンジニアがログメッセージを設計するときの感覚にも近く、現場ですぐ持ち出せる語彙。AIに「沈黙の不安」を任せず、こちらで構造化してあげる設計責任を引き受けたい。

## [AI Fails Silently: A Systems Perspective on AI Reliability](https://uxmag.com/articles/ai-fails-silently-a-systems-perspective-on-ai-reliability)

> **出典**: UX Magazine | **公開日**: 2026-05-11 | **カテゴリ**: ux-research

**3行まとめ**
- 従来システムは大きく壊れるのに対し、AIシステムは静かに、しかも継続的に壊れていく
- 二値的なしきい値ベースの監視はAIには合わず、振る舞いをパターンとして観測する仕組みが必要
- 「アラートが鳴らないこと=正常」という前提を捨て、継続的フィードバックを組み込んだ設計に転換すべき局面

UX Magazineに掲載された、AI時代のシステム信頼性をオペレーション視点から論じた読み応えのある記事です。決定的システムでは、エラーレスポンス、レイテンシ急増、エラー率のスパイクなど、失敗が明示的な信号として現れます。一方でAIシステムは、出力を返し続け、ダッシュボードは緑のまま、品質だけが少しずつ劣化していく、というのが書き手の問題意識です。

「失敗は離散イベントではなくパターンとして現れる」という表現がとくにわかりやすいところです。モデルがドリフトし、小さな不正確さが何千ものインタラクションで繰り返されるあいだ、ひとつひとつの出力は許容範囲に見えてしまいます。気づいたときには、もう問題は分散して下流のシステムや意思決定プロセスにまで埋め込まれている、というシナリオは、AIプロダクトを運用したことがある人なら身に覚えがあるでしょう。

具体例として、金融サービスのマイクロサービスで、教師なしクラスタリングを使って「baseline activity」「transient spikes」「sustained degradation」「critical anomalies」の4つのパターンに振る舞いを分類した事例が紹介されています。固定しきい値に頼らず、ノイズ、想定内のバラつき、新興の問題、即応が必要なインシデントを継続的に区別できるようになった、というのは実装の指針として参考になります。

> 🐈‍⬛ : Practical Interface Patterns の「Audit Trail」とちょうど対になる話で、UI 側で透明性を担保するなら、裏側でも振る舞いを継続的に観測しておかないと「見せられる事実」が手元にない。AI機能の SLI を考えるときに、availability や latency と並べて「振る舞い分布」を置く語彙が手に入る。

## [Temporalによるナレッジ更新の同時実行制御](https://tech.layerx.co.jp/entry/2026/05/14/173940)

> **出典**: LayerX エンジニアブログ | **公開日**: 2026-05-14 | **カテゴリ**: engineering

**3行まとめ**
- バクラクヘルプデスクエージェントのナレッジ更新で、複数経路から来る同期・削除の競合を解くために、Temporal の Workflow ID 命名規則で同時実行制御を実装
- Entity Workflow と Signal キューによるシリアライズ案を検討したうえで、長寿命ワークフローの運用コストを避け、Workflow ID をパス構造にしてプレフィックス検索で関連処理を一括キャンセルする設計を採用
- 「やるべきことは命名規則どおりに ID を作るだけ」というシンプルな運用に集約しつつ、命名規則違反や階層変更に弱いというトレードオフも明確化

AIエージェントの背骨を支えるのは、実は LLM ではなく「データ整合性」だ——この記事はその主張を実装で示すケーススタディです。社内規程やマニュアルをソースとするナレッジを Notion / Google Drive と同期するとき、複数のユーザーやバッチが同時に同期・削除を走らせると、削除したはずのデータが復活したり、ベクトルインデックスに孤立データが残ったりする。当初は DB の排他ロックで対処していたものの、エントリポイントが増えるほど実装漏れやデッドロックのリスクが膨らんだといいます。

着眼点が見事なのは、「すべての操作を厳密にシリアライズする必要はない」と問題を再定義したところです。同期 × 同期は冪等なのでスキップで十分、同期 × 削除は DB制約で復活は防げるが進行中の同期はキャンセルすべき——と分解したうえで、Temporal の Workflow ID 一意性制約と Visibility API を活用します。

具体的には Workflow ID を `folder/{folderId}/page/{pageId}/sync` のようにファイルパス構造にし、ページ同期は固定 ID で重複排除、フォルダ同期はユニーク ID で並列実行、削除時は親パスをプレフィックスにして関連ワークフローを `STARTS_WITH` クエリで一括キャンセルする設計です。各経路に分散していたガード処理が「命名規則の遵守」一点に集約され、新しいエントリポイントの追加コストも下がります。

> 🐈‍⬛ : 「全部シリアライズしない」の問題再定義が見事。AIエージェントを業務に組み込むほど、即時性と整合性のトレードオフを設計で解く必要が出てくる。`CancellationScope.nonCancellable` で削除後処理を守る粒度まで含めて、エージェント体験の土台として参考にしたい。

## [From latency to instant: Modernizing GitHub Issues navigation performance](https://github.blog/engineering/architecture-optimization/from-latency-to-instant-modernizing-github-issues-navigation-performance/)

> **出典**: GitHub Engineering | **公開日**: 2026-05-14 | **カテゴリ**: engineering

**3行まとめ**
- GitHub Issues のページ遷移を「instant」にするため、IndexedDB によるクライアントキャッシュと preheating、Service Worker を組み合わせた local-first アーキテクチャを導入
- 「HPC（Highest Priority Content）」という Web Vitals LCP に近い指標で、ナビゲーションを Instant（<200ms）・Fast（<1000ms）・Slow（>=1000ms）にバケット分けし、分布の質を改善する戦略に切り替えた
- React ナビゲーションの最大70%が instant に到達。P10 は 600ms→70ms、中央値は 1,200ms→700ms と大幅に改善

「Issues は遅い」と言われていたわけではなく、「フローを切るほどには遅い」という体感差の話を、GitHub のチームが詳細に書き起こしたエンジニアリング記事です。バックエンドの細かな最適化ではなく、ナビゲーション全体のデータフローそのものを再設計したのが特徴です。

最初の打ち手は IndexedDB ベースの client-side cache に stale-while-revalidate を載せること。再アクセスの多い Issues 画面で、まずローカルデータで即描画し、裏でリバリデーションをかける。次に、cache hit ratio を上げるための preheating を導入しますが、ここでの設計判断が興味深い。よくある「全部 prefetch」をやめて「ローカルに使えるデータがすでにある状態を作る」ことに目的を再定義し、preheating をキャッシュ充填ロジックに位置づけました。低優先度ワーカー、レート制限、サーキットブレーカーを組み合わせて noisy neighbor 問題を避けています。

ハードナビゲーション（リロードや直接URL）にも効かせるために、Service Worker が登場します。Service Worker がサーバへのリクエストにヘッダを付与し、サーバはキャッシュ命中時には HTML シェルだけを返す——という分岐で、Turbo ナビゲーションの応答時間が大きく改善しました。p99 を磨く従来のやり方では「全体としての体感」が変わらないため、「分布のどのバケットに入ったか」で評価する設計に切り替えています。

> 🐈‍⬛ : 「prefetch を増やす」ではなく「ローカルに使えるデータがすでにある状態を作る」へ目的を再定義する一手がいい。HPCで分布を語る指標設計は、AI 機能の応答時間の見方にもそのまま応用できる。p99 ばかり磨いて疲れていたところに、別のレイヤーを足す勇気をもらえる。

## [Meet Your Users Where They Are with Obs.js](https://csswizardry.com/2026/05/meet-your-users-where-they-are-with-obs-js/)

> **出典**: CSS Wizardry | **公開日**: 2026-05-12 | **カテゴリ**: css

**3行まとめ**
- ウェブパフォーマンスはサイトとユーザーの「あいだ」で起きる現象で、相手の状況に応じた振る舞いを設計できるかが鍵
- Obs.jsはネットワーク、電池、CPU、メモリなどブラウザが教えてくれるシグナルを `<html>` のクラスと `window.obs` として露出する小さなライブラリ
- 「Status（事実）」と「Stance（意見）」を分けて提供することで、生のシグナルとライブラリの推奨判断を使い分けられる

Harry RobertsによるObs.jsの考え方を綴った記事。著者自身のホームページで、配信モードに応じてマストヘッド画像のリッチネスを切り替えたり、電池が少ないときにナビゲーションのアニメーションを止めたりする実例から始まります。SpeedCurveの計測では、lite モードと rich モードのLCP差はわずか80msしかなく、軽い配信でも体験品質を保てることが示されています。

技術的な肝は「StatusとStanceの分離」です。Statusは「Data Saverが有効である」「レイテンシが高い」といった事実、Stanceは「接続が弱そうだ」「ライトな配信が安全だ」というライブラリの解釈。生のシグナルを使いたい場面と、ライブラリの判断に乗りたい場面を切り替えられるAPIは、適度に意見を持ちつつ強制しない設計として参考になります。

ある顧客で、電池残量の低いユーザーのほうがコンバージョン率が高かったというエピソードも興味深いです。バッテリーが切れる前に決済を済ませようとする「切迫感」の仮説が立てば、チェックアウトを最小フリクションに切り詰める設計判断につながる。シグナルそのものより、シグナルをもとに「問いを立てる」ことが価値になる、というメッセージは普遍的です。

> 🐈‍⬛ : 「Status と Stance」を分けるAPI設計は、意見を持ちつつ強制しない、というツールづくりのお手本。GitHub Issues の HPC バケットと並べると、「ユーザーの体感をどの粒度で測り、どの粒度で介入するか」を考える筋トレになる。電池残量と CV 率の話は単なる小ネタを超えて、計測設計のリフレーミング材料として持っておきたい。

## [Exploring the HTML-in-Canvas Proposal](https://tympanus.net/codrops/2026/05/13/exploring-the-html-in-canvas-proposal/)

> **出典**: Codrops | **公開日**: 2026-05-13 | **カテゴリ**: design

**3行まとめ**
- WICG の HTML-in-Canvas 提案は、`<canvas>` の中で実 DOM を描画しつつ、CSS・レイアウト・アクセシビリティを保てる新 API
- `layoutsubtree` 属性、`drawElementImage()`、`paint` イベントの3つを軸に、ポストプロセス・小さなマイクロインタラクション・遷移演出・3D シーン内 UI などのユースケースを実演
- Three.js は r184 で `HTMLTexture` を導入。`InteractionManager` がポインターイベントを DOM に転送するため、ヒットテストやフォーカスもブラウザ側で扱える

「DOM か Canvas か」という長年の二項対立を解こうとする WICG の提案を、Vittorio Retrivi が実際のデモとともに解説します。Chromium のフラグ（`chrome://flags/#canvas-draw-element`）で試せる実験段階の機能ですが、もし主流ブラウザに広がれば、Web UI の表現可能性が一段拡張される話です。

API は驚くほど素直で、`<canvas layoutsubtree>` の子要素を `drawElementImage()` でテクスチャ化し、変化時に `onpaint` で再描画する、というシンプルな構造です。ここで重要なのは、テクスチャ化された後も DOM そのものは残っているため、SEO・スクリーンリーダー・キーボード操作が壊れない点。`<foreignObject>` や html2canvas ではトレードオフだった部分が、ネイティブ実装によって解消される可能性があります。

ユースケース2「A Small Feature」が示唆的です。フルスクリーンの派手なシェーダーよりも、ボタンを押した瞬間にテキストが粒子状に消えるような小さな wow を、アクセシビリティを保ったまま導入できる。「面で華やかさを足す」のではなく、「微差で印象を整える」設計が現実的になります。さらに、3Dシーン内のUI構築が圧倒的に楽になり、これまで R3F の `<Html>` や uikit を駆使していた領域で、CSS Flexbox・Grid・box-shadow・border をフルに使った UI をテクスチャ化できます。

> 🐈‍⬛ : 「テクスチャ化しても DOM が残るから a11y が壊れない」というのが地味に強い。AI Doesn't Fix Accessible Systems で釘を刺された「壊れた構造を継承する」問題を、Web 標準の側から押し戻してくる提案。実験段階の機能だが、頭の片隅に置いておくと、これからのインタラクション提案の選択肢が広がる。

## [The unreasonable effectiveness of HTML](https://thariqs.github.io/html-effectiveness/)

> **出典**: Sidebar | **公開日**: 2026-05-11 | **カテゴリ**: design

**3行まとめ**
- 大きなマークダウンの壁の代わりに、自己完結した20個の `.html` ファイルをエージェントに生成させた事例集
- Exploration、Code Review、Design、Prototyping、Diagrams、Decks、Research、Reports、Custom Editorsの9カテゴリ
- 「読まれる文書」を作るためのフォーマットとしてのHTMLを、エージェント時代に再評価する視点

タイトル通り、エージェントの出力フォーマットとしてHTMLが持つ底力を改めて見せる試みです。長いマークダウンを読み下すのは認知コストが高く、結局スキミングで終わってしまう、という経験は多くの人が共有していると思います。提案は単純で、ひとつひとつの `.html` ファイルとして書き出し、ブラウザで直接開いて読めるドキュメントにしよう、というものです。

カテゴリの切り分けが具体的で参考になります。Exploration & Planningでは、3つの方向性を並べて指差せるようにする、という使い方が紹介されています。Code Review & Understandingでは、diffやcall-graphは空間情報なのにマークダウンが平らにしてしまう、と指摘し、annotated diff、boxes-and-arrows、レビュアーが読みたくなるPR descriptionをエージェントに作らせる方向性が示されています。

Designでは、HTMLが設計システムの「実装言語」そのものなので、tokens-as-swatches、components-as-contact-sheetsのような出力をそのまま次のプロンプトに食わせられる、という指摘が興味深いところです。Prototypingでは、モーションとインタラクションは記述ではなく感覚で評価するしかない、という割り切りで、本物のイージングとクリックスルーをすぐ試せるページを作る、というアプローチがまとめられています。

> 🐈‍⬛ : 「エージェントの出力はマークダウン一択」をやめてみるだけで、レビューや意思決定の質が変わる、という発想転換が小気味よい。Custom Editing Interfaces の「使い捨てのエディタとして書き出してもらう」発想は、Slack の議論用に1ページの mini-app を出力させる、みたいな運用にすぐ転用できる。

## [AI Doesn't Fix Accessible Systems. It Depends on Them.](https://annaecook.com/writing/2026/ai-doesnt-fix-accessible-systems-it-depends-on-them)

> **出典**: Accessibility Weekly | **公開日**: 2026-05-11 | **カテゴリ**: accessibility

**3行まとめ**
- AIがアクセシビリティを「パーソナライズで解決する」というストーリーは事実ではない
- AIは壊れた構造を修復できず、それを継承しスケールで再生産してしまう
- 決定論的な設計、診断ではなく仕組みの思考、構造的な仕事は引き続き必要

Accessibility Weeklyが取り上げたAnna E. Cookのエッセイで、AIとアクセシビリティの関係を整理する立ち位置が明快な一本です。「ここ数年、業界はこんなストーリーを聞かされてきた——AIがアクセシビリティをパーソナライズで解決する、決定論的な設計は死んだ、診断が仕組みの思考に取って代われる、構造的な仕事はもう必要ない。どれも事実ではない」という冒頭の宣言は、AIを安直なアクセシビリティのレイヤーに使うアプローチへのアンチテーゼになっています。

AIは壊れた構造を修復できず、むしろ継承してスケールで再生産する、という指摘は、生成AIがプロダクトに組み込まれていく今の流れに釘を刺しています。代替テキストの自動生成、コントラストの自動補正、フォーカス順序の自動調整、といった「AIで一発解決」のナラティブが、ベースとなるHTMLの構造的な貧しさを温存したまま、上層の自動化で覆い隠してしまう構図が浮かびます。

UXエンジニアリングの視点でいうと、AIで覆い隠せる部分と、覆い隠してしまうと将来コストが膨らむ部分を見分ける感覚を、設計時点で持っておきたいところです。AIをアクセシビリティのショートカットにするのではなく、AIが効くための土台としてアクセシブルな構造を整える、という順序を改めて確認させてくれます。

> 🐈‍⬛ : 「AIは壊れた構造を継承してスケールで再生産する」という一文がいちばん重い。HTML-in-Canvas の提案が「DOM を残すから a11y が守られる」と言っているのと表裏で、土台の整え方が AI 時代の体験品質を分ける、という主張が一貫している。

## [The Spiral Climbs: Ideas Are Expensive, Systems Are Cheap](https://uxmag.com/articles/the-spiral-climbs-ideas-are-expensive-systems-are-cheap)

> **出典**: UX Magazine | **公開日**: 2026-05-14 | **カテゴリ**: ux-research

**3行まとめ**
- デザインは死んでいない、ただ上流に移った。デザインシステムとコードが結びついた今、「フレーミング・テスト・記録」が価値の中心になるという主張
- Miro→Figma→VS Code+AI→GitHub→Jira→テレメトリ という一本のチェーンを48時間ループで回し、「リンクされていないものは存在しない」という原則で運用
- AI は 0→1 のスキャフォルディングに使い、ハードニング・スケーリング・セキュリティはプロフェッショナルが引き継ぐ役割分担

Pavel Bukengolts が「製品データを全部失った状態から再構築する」という極限のシチュエーションを通じて、現代のプロダクトデザインのワークフローを描き出します。トレンドへの便乗ではなく、ツールとAIエージェントを一本の意思決定の流れにまとめあげる手つきが具体的で、UXエンジニアが現場で参考にできる粒度です。

中核にあるのは「Everything is connected」という原則。Miro のスナップショットは Jira の bet にリンクし、Jira は Figma の clarifier と GitHub の PR に紐づき、PR には decision log とプレビューが残る。デザイントークンの ID は Figma Dev Mode とコードで一致し、スマートコミットが Jira を更新する。ミーティングのアクションは自動でチケットになる——「idea → ship → learn」が一本の鎖で繋がる構造です。

48時間ループ（Observe / Orient / Decide / Act / Review）は、Boyd の OODA を製品開発に再翻訳した形式で、「フィデリティの階段」（スケッチ→プロンプト→runnable プロトタイプ→本番）を毎ループで往復します。それを支えるのが Design Thinking Facilitator・Systems Thinking Coach・Meeting Minutes Facilitator という3つのカスタムアシスタント。エージェントは判断を肩代わりするのではなく、「私を鋭くする」ための補助輪として位置づけられています。

> 🐈‍⬛ : 「AIを使うなら、判断と所有権だけは人間が握る」Agent RACI が、今週の他の記事から見えてくる結論をひとことで束ねている。Apps and programming の「scattered, frenetic energy」と並べると、エージェントを補助輪にするか主役にするか、で見える景色が全然違うことがよくわかる。

冒頭で投げた「AIエージェントが手早く書ける時代に、UXエンジニアの仕事はどこに残るのか」という問いは、12本を通すと意外と素直な輪郭をとります。残るのは表層のモックでもプロンプトでもなく、宣言的アーキテクチャ、AI透明性のUIパターン、振る舞いの観測、整合性、アクセシビリティの土台——つまり「裏側を整えて、表側の即時性を支える」仕事です。Global Accessibility Awareness Day（2026-05-21）も近い週末、いつもより少しだけ土台のほうに目を向けて過ごしてみる、というのも悪くないかもしれません。また来週。
