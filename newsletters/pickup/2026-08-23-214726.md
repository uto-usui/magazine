## [99% of my website traffic is bots](https://patronview.com/news/99-percent-of-my-website-traffic-is-bots/)

> **出典**: Sidebar | **公開日**: 2026-08-18 | **カテゴリ**: design

**3行まとめ**
- サーバーは週に 250 万リクエストに応答して 128 万ページを配信したのに、訪問者統計は 5,977 ページビューしか記録していない。人間1人あたりボットが 214 ページ
- 「参照1件あたりの巡回ページ数」という指標。Googlebot は 46:1、Bingbot は 406:1、Claude-SearchBot は 35,000:1、Amazon の AI 検索クローラーは無限
- Cloudflare の JavaScript Detections が中位機種で 2,875ms かかっていた。切ったら Lighthouse が 58 から 99 に。ただし5時間後にはスクレイパーが戻ってきた

**詳細解説**

米国の慈善家データベース PatronView を運営する Nick Gray が、1年間のボットとの戦いを記録した文章です。実測値が具体的で、しかも自分の立場に正直なところが読ませます。サイトは IRS の 990 フォームや寄付者ウォールや年次報告から作った 150 万件のプロフィールページを持ち、つまりそのデータは公開文書のスクレイピングで得ている。「スクレイパーがスクレイパーについて文句を言うブログを書いています。どう聞こえるかは自覚しています。念のため、こちらは年に数回で、1日に数千回ではありません」。

まず見えていなかったことの話から始まります。自己ホストの Plausible Community Edition は JavaScript を実行する訪問者しか数えず、ボックスはほとんど実行しない。訪問者統計は1日約500人の小さなサイトを映すのに、サーバーは週に数百万の実リクエストに応答している。「Plausible や Fathom や Google Analytics のような JavaScript ツールの訪問者統計しか見ていないなら、何がサーバーに当たっているのか分かりません。分かっていませんでした」。この一文が記事全体の起点です。

出来事は段階的に激しくなります。最初は SemrushBot、AhrefsBot、MJ12bot、DataForSEOBot といった SEO クローラーが全ページを繰り返し巡回する。2025年11月には4,000の「訪問者」が数日で現れ、それぞれ1ページだけを見て直帰率99%、リファラーなし——「ボットを見つけるいちばん簡単な方法」だそうです。そして4月22日、1日で 360 万リクエストが 361,844 の一意 IP から、ほぼすべて中国から届く。Cloudflare の Managed Challenge が最初の10時間で 118 万を吸収したものの、通過するものも相当あった。そこで「やってはいけないこと」をした——エッジで中国全体をブロックし、数日後にベトナムからの模倣波が来たのでベトナムも、次にシンガポールも。「うちは英語で書かれた米国の美術館寄付者のデータベースです。実際の検索トラフィックは 95.9% が米国、1.3% がカナダ」という説明が添えられています。

指標の作り方がこの記事の中心的な貢献でしょう。Cloudflare の AI クローラーダッシュボードで、`Claude-SearchBot` が1週間に 420,680 ページを要求し、同じ週に Claude が送った人間の訪問者は 12 人だった。帯域では 4.63GB を配信して、送られてきた人間には 175KB。そこから「参照1件あたりの巡回ページ数」という指標を得ます。Googlebot は 46:1 で元を取っている、Bingbot は 9 倍悪い 406:1 でもまだ擁護できる、LLM を訓練する AI クローラーは近くもない。調査中に見つけた `Amzn-SearchBot` は1日約 117,000 リクエストで首位のクローラーになっていて、Rufus と Alexa の回答を供給するので Web トラフィックを送ることはない。2分でブロックした、と。礼儀正しい AI 企業は 403 を受け取る、という観察も添えられています——Claude-SearchBot は1日6万リクエストから1日25回の試行に落ちました。

7月に来た次の波が話を難しくします。米国のデータセンターからのヘッドレス Chrome で、JavaScript を実行するので統計に偽の「訪問者」が混ざる。対処は「データセンターすべてにチャレンジ」で、これがいちばん長く効いた規則になった。実在の読者は Comcast や T-Mobile から見に来て、`AWS us-east-1` の IP からはほぼ来ない。例外はクラウドデスクトップや VPN の利用者なので、ブロックではなくチャレンジにしてある。そして Lighthouse の話が挟まります。Cloudflare の JavaScript Detections が1年間すべてのページにチャレンジスクリプトを注入していて、中位機種のスマートフォンで 2,875ms かかっていた。サイト自身の JavaScript は 278ms。しかも契約プランではその判定結果がファイアウォールのルールから読めない。「読めない誰かのテレメトリのために40点のパフォーマンス税を払っていました」。切ったら1時間以内に Lighthouse が 99 になり、5時間後に Azure のスクレイパーが1時間で 23,000 ページを、80 以上の IP からそれぞれ丁寧にレート制限の下を通って取っていった。つまり効いてはいたわけです。

住宅用 IP のボットネットが最後の難所として描かれます。プロキシ企業からリクエスト単位で借りた、数千の一般家庭の回線を経由するスクレイピング。どのリクエストも実在の ISP の実在の人間に見える。2025年11月の統計に、数十の国がほぼ同じ数ずつ同じ日に訪問するという奇妙な形が出ていて、それが借り物のプロキシネットワークの署名だった。9か月後、同じ形が米国の家庭回線で戻ってくる。北米以外にチャレンジする規則もクラウド事業者にチャレンジする規則も、オハイオの家から Spectrum で来るトラフィックは通してしまう。そこで追加したのが「お気に入りの間抜けな規則」——数年前で凍結したブラウザにチャレンジする。Chrome 100 から 130 に CAPTCHA、古い Firefox にも。実トラフィックを先に確認して、実際の検索訪問者のうちそんな古いブラウザは 0.54% で、その多くは古い OS に取り残された Firefox 115 ESR だったので除外してあります。

UXエンジニアリングの視点では、コストの内訳と結論が読みどころです。Cloudflare Workers と D1 と KV のエッジ構成なので、多くのボットリクエストはキャッシュに当たって1円未満で済み、通常の請求は月90ドル前後。ひどい月には5倍になった。ただ「本当のコストはこそこそしたほうだった」と書かれています——訪問者統計が汚れて自分の数字を信じられなくなったこと。ビジネスをやろうとしていて、実在の人が何を読んでいるかを知りたいのに、ボット越しには見えない。48時間で 106,437 のチャレンジを発行して解かれたのは 252 件、解決率 0.24% という数字も出ていて、「0.2% ならボットなので規則を維持、30% なら人間に課税しているので規則を直す」という運用の目安に使われています。処方箋も明快で、訪問者統計ではなくサーバーログを見る、IP ではなく ASN でブロックする、人間が混じりうるならブロックではなくチャレンジにする、解決率を監視する、そしてセキュリティ機能のコストをプロファイルする。「うちの CAPTCHA はサイト全体より高価でした」。スクレイピングが悪化し続けるのは安くなり続けているからで、本当の解決は経済的なものしかない——Cloudflare の pay-per-crawl に期待を書きつつ、それまでの規則は単純だと締めています。「訪問者を1人も送らないクローラーはブロックする」。

> 🐈‍⬛ : 「参照1件あたりの巡回ページ数」を作ったところが、この記事のいちばんの発明でしょう。ブロックするかどうかという議論を、収支が合っているかという話に翻訳している。個人的には、セキュリティ機能に40点のパフォーマンス税を払っていたという節が効きました。CAPTCHA をパフォーマンス予算の対象として測ったことのあるチームは少ないはずで、しかも測ろうと思わなければ一生見つからない種類のコストです。

## [Agent behavior](https://www.agentbehavior.dev/)

> **出典**: Sidebar | **公開日**: 2026-08-19 | **カテゴリ**: design

**3行まとめ**
- AIエージェントに期待する「良い振る舞い」をMarkdownで明文化する新フォーマット「Agent behavior」が公開されました
- `.agents/behaviors/` 配下に置くBEHAVIOR.mdは、実行時プロンプトではなくレビュアーや評価設計者に向けて書かれます
- Evidence / Decision / Execution / Recovery という推奨ディメンションで、振る舞いを評価可能な形に分解します

**詳細解説**

Braintrustが公開した、AIエージェントの「振る舞いの基準」を書き下すためのフォーマット仕様です。ポイントは、AGENTS.mdやシステムプロンプトとの役割分担にあります。既存のプロンプト類が「エージェントにどう動くかを指示する」ものであるのに対し、BEHAVIOR.mdは「何が良い振る舞いなのかを定義する」ものです。読者もエージェント本体ではなく、トレースをレビューする人や評価（eval）を設計する人を想定しています。

フォーマット自体は意図的に小さく保たれています。フロントマターにnameとdescriptionを持つMarkdownファイルを `.agents/behaviors/<name>/BEHAVIOR.md` に置くだけで、本文は自由記述です。ただし推奨の観点として「どんな証拠を集めるか（Evidence）」「そこから何を判断するか（Decision）」「判断後に何をするか（Execution）」「うまくいかないときにどうするか（Recovery）」が示されており、この分解が振る舞いをテスト可能な単位に落とし込む鍵になっています。

UXエンジニアリングの視点では、これは「エージェントの体験品質をコードと同じリポジトリでバージョン管理する」試みと読めます。UIコンポーネントにデザインシステムのガイドラインがあるように、エージェントの応対にも明文化された基準があれば、レビューも改善も再現可能になります。仕様の中で「実行時プロンプトに全部注入しない」と明記されている点も示唆的で、基準と実装を分けて考える規律は、デザイン原則とスタイルガイドの関係にそのまま重なります。まだ生まれたばかりの仕様ですが、エージェントの品質保証をどう仕組み化するかを考えるうえで参考になるでしょう。

> 🐈‍⬛ : 「実行時プロンプトに全部注入しない」と明記したところで、この仕様の性格が決まっています。AGENTS.md が指示書なら、BEHAVIOR.md は受け入れ条件。テストコードを本番のコードに混ぜないのと同じ分け方です。Evidence / Decision / Execution / Recovery という4分解は人の引き継ぎ資料にもそのまま効くもので、とくに Recovery が独立した欄になっているのがいい。次の記事がちょうどそこを掘っています。

## [Agent experience needs failure affordances](https://blog.ronbronson.com/agent-experience-needs-failure-affordances)

> **出典**: Sidebar | **公開日**: 2026-08-19 | **カテゴリ**: design

**3行まとめ**
- エージェントが「これ以上進めない」と人間に知らせるための出口、つまり失敗のアフォーダンスが必要だという主張です
- 権限を判定するjudgment routerと、想定外を通報するexception channelは別のインフラだと整理しています
- ジムの予約エージェントがAPIの認可不備を発見した事例を通じて、通報経路の欠如という空白を示します

**詳細解説**

サービスデザイナーのRon Bronsonさんによる、Agent Experience（AX）論への問題提起です。発端は、エージェントが行き詰まったときにTeamsへ通知を送る `distress_call` という仕組みの話題でした。そこから、Stafford BeerのViable System Modelにおける「algedonic signal（通常の報告経路の外を流れる例外信号）」を補助線に、エージェントにも例外チャネルが要るという議論を組み立てています。

興味深いのは、2種類のインフラを明確に区別している点です。ひとつは、提案されたアクションの権限・リスクを評価して実行/エスカレーション/停止に振り分ける「judgment router」。もうひとつは、権限の範囲内で作業していても遭遇する「なにかがおかしい」状況を人間に伝える「exception channel」です。APIは200を返すのに結果が矛盾している、ツールは仕様どおり動くのに危険な挙動が見える。こうした状況は認可の閾値を越えていないため、ゲート型の制御では捕捉できません。ジム予約エージェントが他人の予約をキャンセルできる認可不備を偶然発見した事例は、この空白をよく示しています。

人間のサービス設計では、窓口担当者が異例のケースを上司に相談する、パイロットが緊急事態を宣言するといった「失敗のアフォーダンス」を何十年もかけて作り込んできました。現在のAX議論がドキュメントやAPIの整備といった「成功の支援」に偏っているという指摘は、エージェント連携を設計するエンジニアにとって耳が痛いところです。エージェントを働かせる環境だけでなく、エージェントがどう止まるかまで設計対象に含める。この視点は、前述のAgent behavior仕様のRecoveryディメンションともきれいに響き合います。

> 🐈‍⬛ : judgment router と exception channel を別のインフラだと切り分けたところが、整理として効いています。前者は権限の設計で、後者は組織の設計。200 が返ってきているのに結果が矛盾している、という状況は人間のオペレーターなら「なんか変です」と上司を呼ぶ場面ですが、呼べる相手が用意されているかどうかはエージェントの性能ではなく周りの設計の問題になる。algedonic signal を補助線に持ってきたのも好みで、1970年代の組織論がそのまま使えるのはおもしろいところです。

## [コーディングエージェント主体に実装の進め方を変え始めている話](https://tech.layerx.co.jp/entry/coding-agent-driven-development)

> **出典**: LayerX エンジニアブログ | **公開日**: 2026-08-19 | **カテゴリ**: engineering

**3行まとめ**
- 複数ウィンドウでの並列作業から、planner / worker / reviewerと役割を分けたエージェント編成へ移行した実践記です
- エージェント間の受け渡しを人間が仲介する構成では、自分自身が詰まりどころになるという課題が浮かびます
- 仲介役のエージェント化に向けて、判断基準をスキルとして書き、実際の判断履歴から育てる仕組みを試しています

**詳細解説**

LayerXの古濵さんによる、エージェント駆動開発の移行過程を段階ごとに記録した記事です。最初は単純にエディタのウィンドウを増やして並列化していたものの、進み具合が自分の頭の中にしか存在せず、切り替えのたびに読み直しが発生する。そこで `herdr` を使い、設計担当のplanner、実装担当のworker、レビュー担当のreviewerと役割を固定した構成に変えた、という流れです。

読みごたえがあるのは、うまくいかなかった部分の解像度です。役割を分けても受け渡しの仲介を人間がやっている限り、ボトルネックの場所が変わっただけで構造は同じ。しかも設計と実装で往復すれば、それだけで4回は自分を経由します。さらに「渡す」という操作自体にも失敗の仕方があり、レビュー出力をそのまま流すと命令形の文が指示として解釈される、端末表示の読み取りでは古い行が欠けても気づけない、といった具体的な落とし穴が挙げられています。長い出力はファイル経由で受け渡す、転送前に文脈を補って書き直す、という対処はどれも実践的です。

もっとも示唆に富むのは、仲介役の判断基準をスキルとして明文化し、セッション中に下した判断を表形式で記録してスキルの改善に還元する、という「基準を育てる」発想でしょう。往復が3回を超えて収束しなければ人間に聞く、といった暴走防止の線引きも含めて、「経路をつなげば任せられるわけではない」という結論には重みがあります。エージェントオーケストレーションを試している方には、設計の参考として一読の価値があります。

> 🐈‍⬛ : 役割分担の記事に見えて、実際に書かれているのは受け渡しのプロトコル設計です。レビュー出力をそのまま流すと命令形の文が指示として解釈される、という失敗は人間同士の Slack 転送でも起きるもので、間に立つ人が黙って文脈を足して書き直していた仕事が急に可視化された感じがあります。判断履歴を表で記録してスキルに還すやり方は、今週の Agent behavior が仕様として書こうとしている場所を、現場の側から掘っている。

## [How v0 authenticates to Snowflake without exposing the user's OAuth token](https://vercel.com/blog/how-v0-authenticates-to-snowflake-without-exposing-the-users-oauth-token)

> **出典**: Vercel | **公開日**: 2026-08-20 | **カテゴリ**: frontend

**3行まとめ**
- AIが生成したコードにユーザーのOAuthトークンを一切渡さずにSnowflakeへ認証させる、v0のプロキシ設計の解説です
- サンドボックス内には無害なプレースホルダーだけを置き、実クレデンシャルはプロキシがリクエスト時に注入します
- プレースホルダーの単純置換は漏洩経路になるため、プロトコル上の認証フィールドだけに構造的に注入します

**詳細解説**

AI生成アプリが外部サービスへユーザーの代理で認証する、という状況には本質的な緊張があります。生成コードはモデルが書いて人間のレビューなしに動き、プロンプトインジェクションで「読めるものを外へ送る」よう誘導されうる。だからユーザーのクレデンシャルを生成コードの実行環境に入れてはならない。しかしSnowflakeのSDKやCLIはトークンがある前提で動く。v0チームはこの矛盾を、サンドボックスのファイアウォールでSnowflake宛の通信をすべてプロキシへ転送し、実トークンはプロキシがリクエスト時に解決・付与する構成で解きました。サンドボックス内には72バイトの公開された無害なプレースホルダーだけを置き、既存クライアントを騙して普通に動かします。

白眉は「盲目的な置換がなぜ危険か」の分析です。初期実装はリクエスト本文中のプレースホルダーを実トークンへ一括置換していましたが、SQL文は呼び出し側が制御するデータです。生成コードがSQLの文字列リテラルにプレースホルダーを含めれば、置換によって実トークンがクエリに埋め込まれ、その結果がクエリ出力としてサンドボックスに戻ってきてしまう。守るために作ったプロキシが漏洩装置になるわけです。最終版は、SQL APIなら `Authorization` ヘッダー、ログインリクエストならJSONを構造的にパースしてトークンフィールドのみ、というようにプロトコルが定めた認証フィールドにだけ注入し、それ以外の場所にプレースホルダーが現れたら拒否してログに残す設計になっています。本番投入後15日間で約13,000リクエストを処理し、プレースホルダー誤用による拒否はゼロだったそうです。

「隔離はコードから守るが、秘密は守らない」という整理は、エージェントに権限を渡すあらゆる設計に効く教訓です。ユーザーからは接続して使うだけに見えるこの透明さも含めて、エージェント時代のセキュリティ境界設計のお手本といえる内容です。

> 🐈‍⬛ : 「守るために作ったプロキシが漏洩装置になる」という中間の失敗まで書いてあるのが、この記事の価値です。文字列の一括置換は安全に見えて、置換対象がどこに現れるかを呼び出し側が決められる時点で崩れる。構造をパースして所定のフィールドにだけ入れるという解は SQL のプレースホルダと同じ形をしていて、20年前に学んだ教訓が新しい皮をかぶって戻ってきている。生成コードを、信用できない外部の書き手として扱う前提の置き方がきれいです。

## [Sandboxテスト 〜フロントエンドとAI時代の変化の激しさへの挑戦〜](https://tech.smarthr.jp/entry/2026/08/17/080914)

> **出典**: SmartHR Tech Blog | **公開日**: 2026-08-16 | **カテゴリ**: design

**3行まとめ**
- Rails を起動せず、OpenAPI のモックサーバー Prism だけで動かす Playwright テスト。フロントエンドに閉じた結合テスト
- スキーマの `examples` を固定レスポンスにして UI 状態（空・成功・エラー）を再現し、VRT も回す。同時に Prism がリクエスト側のスキーマ準拠も検証する
- 選んだ理由はポータビリティ。フレームワークや設計に依存せず振る舞いに焦点を当てたテストが、コーディングエージェント時代の前提になると見ている

**詳細解説**

SmartHR の AI アシスタント開発チームによる、テスト戦略の記録です。「Sandbox テスト」は一般的な呼称ではなく、バックエンドのサーバーも立てる既存の E2E テストと区別するために便宜上そう呼んでいる、と明記されています。モック E2E テスト、フロントエンド統合テスト、ネットワークインターセプトテストとも言い換えられるかもしれない、と。技術構成は Next.js 16（App Router、Server Function と RSC）、Rails、OpenAPI、Playwright 1.59、Prism 5.14。フロントエンドは openapi-generator-cli で自動生成したクライアントコードを使って Rails の API にアクセスする形です。

仕組みの要点は、Prism が単なるモックサーバーではないところにあります。OpenAPI の `examples` をレスポンスとして返すのでレスポンスのパターンを固定でき、空・成功・エラー・各ステータスといった UI 状態を再現できる。加えて Prism は受け取ったリクエスト（パラメータやボディ）をスキーマに照らして検証し、違反していれば 422 などのバリデーションエラーを返す。つまり「ある操作でしかるべき UI が表示されるか」と「フロントエンドがスキーマに沿ったリクエストを送れているか」を、フロントエンドに閉じたまま同時に担保できます。表示の検証に VRT のスナップショット比較も重ねています。

採用理由の説明が、この記事のいちばん読ませる部分でした。ポータビリティの高いテストとは、特定のフレームワークや設計にできるだけ依存せず、アプリケーションの振る舞いに焦点を当てて品質を担保できるテスト、と定義されます。そのうえでフロントエンドの変化の激しさを3層に分けている。フロントエンドそのものの特性としての変更の激しさ（DB のスキーマ変更より UI の変更のほうが速い）、フレームワークレベルの変更（jQuery から Backbone.js、AngularJS、React や Vue へと10年余りで何度も入れ替わった）、コンポーネントレベルの変更（RSC でサーバー側に切り出す、下層に状態を閉じ込めるための分割）。だから詳細レベルのテストは難しいところがある、という整理です。

そこにコーディングエージェントの台頭が重なります。Bun が11日で Rust に書き換えた例と、Stripe が1日で 5,000 万行の Ruby を移行した例が引かれていて、こういうドラスティックな変更でもデグレが起きないような抽象度の高いテストが効果的だと考えている、と。もう1つの理由は消去法で、RSC を前提としたエコシステムの未成熟。Storybook の PlayFunction でコンポーネント単位の結合テストが理想でありつつ、RSC がクライアントサイドでレンダリングされたり Server Action をモックしなければならない制約があって、検証時点では難しかったそうです。

構築で難しかった2点も具体的でした。1つはネットワークインターセプト。Playwright と Next.js が別プロセスで、Next.js の中にもブラウザと Node.js があり、個々のテストで設定がバッティングしてはならず、しかもブラウザからサーバーへの通信は Server Function でエンドポイントが1つにまとめられるためリクエストの区別ができない。Playwright の `page.route`、`msw`、`@mswjs/interceptors` を検討した末、結局ファイルによるプロセス間通信に落ち着いています。Playwright 側が Cookie でファイルパスを指定し、Next.js 側は `globalThis.fetch` にパッチを当ててそれを購読し、マッチしたリクエストに `Prefer: example=...` を付与して Prism へ転送する。もう1つは環境変数で、Next.js 独自の `@next/env` の読み込み優先度やキャッシング、`.env.sandbox` のような独自ファイルを定義できない制約に悩まされ、`@next/env` 内部のパーサーを再利用しつつ読み込み順を自前で制御するコードを書いています。

UXエンジニアリングの視点では、課題を隠していない点にいちばん価値があります。`next dev` の中の Turbopack がインメモリにキャッシュを蓄積するため、テスト時間が伸びるにつれメモリを食って CI で Flaky になる（Next.js 16.3 のメモリ改善で解消見込み）。Prism がストリーミングに対応していないので、AI の回答のストリーミングは検証できない。Prism はスキーマの検証はできるが、フォームの入力値に基づくしかるべきデータが送信されているかまでは見られない。どれも `globalThis.fetch` のパッチを拡張すれば対応できるとしつつ、現状は正直に並べられています。UI の振る舞いとスキーマ準拠を同時に押さえる層を1つ持つという発想は、エージェントが大きな変更を短時間で入れる前提のコードベースでは効き目が大きくなるはずです。

> 🐈‍⬛ : 「ポータビリティの高いテスト」という言葉で選定基準を先に決めているのが効いています。フレームワークの寿命よりテストの寿命を長くする、という発想。Prism がレスポンスを固定するだけでなくリクエスト側のスキーマ準拠まで見るので、モックサーバーが型の番人も兼ねているところが地味に大きい。Turbopack のメモリで CI が Flaky になる話やストリーミングが検証できない話を隠さず並べているのも、真似する側からするといちばんありがたい部分です。

## [Reliable Query Prefetching with TanStack Router](https://tkdodo.eu/blog/reliable-query-prefetching-with-tanstack-router)

> **出典**: TkDodo | **公開日**: 2026-08-18 | **カテゴリ**: frontend

**3行まとめ**
- ルートローダーで先読みし、コンポーネントが `useSuspenseQuery` で拾うパターンには、同じことを2箇所に書く代償がついてくる
- 2箇所がずれても何のエラーも出ない。検索パラメータを1つ足しただけで、不要な先読みと待たされる二重フェッチが同時に起きる
- `queryOptions` をルートコンテキストに置き、ローダーとコンポーネントの両方がそこから読む。ずれが構造的に起きなくなる

**詳細解説**

TanStack Router シリーズの4本目です。前提の整理から始まります。推奨されるデータ取得のパターンは、できるだけ早くローダーでフェッチを起動し、ローダーをイベントハンドラのように扱ってコンポーネントが `useSuspenseQuery` や `useQuery` で promise を拾うこと。コンポーネントは可能なら自分でデータ取得を始めないほうがいい、というのが要点です。自己完結したコンポーネントが自分のデータ要件を解決するのは理屈としては優れているけれど、実際にそこだけでフェッチすると、理想より遅く始まるうえ、フェッチのウォーターフォールを簡単に作ってしまう。

その代償が「The Great Divergence」と名づけられています。コンポーネントでやっていることをルートローダーという第2の場所に複製する。重複自体は世界の終わりではなく、得られる UX に対して妥当な取引です。ただ、この2箇所は100%同期していなければならない。そしてアプリが育つとそれを保つのが難しくなる。理由が2つ挙げられていて、どちらも身に覚えがあるところでしょう。まずコンポーネントは `Route` ファイルに留まらない——`component: Dashboard` はいいけれど Dashboard は多くのコンポーネントから組まれ、それらも `getRouteApi` でルートAPIにアクセスする。ファイルを分けるのは良いことですが、コンポーネントのクエリの使い方を変えたときにローダーも直す必要があると即座には思い至らない。もう1つ、2つが一致していなくてもエラーは出ない。

具体例が効いています。ダッシュボードに過去の日付でスナップショットを見る機能を足したい。共有可能にしたいので `?asOf=YYYY-MM-DD` を任意の検索パラメータとして持たせ、コンポーネントで消費する。読み込んでも動くし、パラメータを変えればその時点のデータが出る。ところがそのルートを共有すると、ローダーは「今日」のデータを読み、それが揃うまで待ってコンポーネントを描き、そこから `asOf` つきで再度フェッチする。`asOf` は `QueryKey` の一部になるので完全に別のクエリになり、コンポーネントはもう一度サスペンドする。正しいデータで描かれるのはその後です。「いちばんよくある使い方（機能を足すこと）を正しくやるのが難しく、そこから来るバグは見つけにくい」。

対処が2段階に分けられているところが丁寧でした。まず症状を止めるなら、`loaderDeps` という間接層を使ってローダー側にも任意パラメータを含める。これで URL を共有しても不要なリクエストは起きなくなるけれど、根本原因には触れていません。次のルートで同じ間違いをする確率は変わらない。そこで重複そのものを直します。ローダーの `ensureQueryData` とコンポーネントの `useSuspenseQuery` は同じクエリオプションを共有していて、違うのは渡す先の関数だけ——命令的な1回のフェッチか、リアクティブな購読か。ならばオプションをルートコンテキストに置いて両方から読めばいい。`context` 関数だけが `params` と `deps` を使い、ローダーもコンポーネントも `context` しか見なくなります。

この間接層の効き目が複数挙げられています。ずれるバグが起きなくなるのはもちろん、コンポーネントが先読み済みのクエリを使っていることが分かるようになる。つまりコンポーネントから使用を消したときに、ローダーの先読みを片付けようと思い至る確率が上がる。コンテキストは親から継承されるので、サブルートも親の `queryOptions` を知る。ルートルートのローダーでユーザーデータを先読みしておき、末端の Widget から使うといった書き方ができます。購読の粒度で気になる点にも答えていて、`context` 関数は `params` か `loaderDeps` が変わったときにしか走らないため、無関係な検索パラメータ（`debug` など）が変わってもコンテキストを購読しているコンポーネントは再レンダリングされない、と。

UXエンジニアリングの視点では、これは体験の質と保守性が同じ向きに揃った珍しい形の解です。先読みは UX のために入れるものですが、そのために生まれた重複が、放っておくと二重フェッチという UX の劣化に化ける。しかも劣化は静かに起きて、テストも型も教えてくれません。単一の情報源を作ってローダーとコンポーネントの両方をそこに向けるのは、あらゆる「2箇所を同期し続けなければならない」問題の定石ですが、ルーターのコンテキストというすでにある機構に載せられる点が実装コストを小さくしています。似た構造を抱えているコードベースは多いはずです。

> 🐈‍⬛ : 「2箇所が一致していなくてもエラーは出ない」という一文が、今週の他の記事とまったく同じ形をしています。型もテストも教えてくれない種類のずれで、しかも UX のために入れた先読みが UX の劣化に化ける。症状を止める `loaderDeps` と原因を直すコンテキストへの移動を、あえて2段階に分けて書いているのが丁寧なところ。単一の情報源に寄せるという定石を、すでにあるルーターの機構に載せられるので手が出しやすい。

## [Accessibility getting dropped in the process](https://buttondown.com/nic-steenhout/archive/accessibility-getting-dropped-in-the-process/)

> **出典**: Sidebar | **公開日**: 2026-08-17 | **カテゴリ**: design

**3行まとめ**
- 「アクセシブルに実装できます」というデザインレビューの結論は、実際にそうなるかについては何も言っていない
- 落ちたのは受け渡しの途中。デザイン、実装、テスト、監査にはそれぞれ担い手がいたが、アクセシビリティを次の段階へ運ぶ役だけ不在だった
- 監査が厳しすぎたのではなく、遅すぎた。人はレビューされるものに注意を向ける

**詳細解説**

Nic Steenhout による、いつもの短い記事の集まりではなく1本の長い文章に充てたニュースレターです。出発点は言葉づかいへの注意でした。開発前のデザインをレビューして、安心できる結論に至ることがある。ただし「これはアクセシブルです」でも「これはアクセシブルになります」でもなく、「これはアクセシブルに実装できます」。そして数週間から数か月後に完成した機能を監査すると、結果はしばしば意外なものになる。情報を伝える画像に代替テキストがない、モーダルがキーボードフォーカスを保持しない、動的な更新がスクリーンリーダーに通知されない、キーボードから到達できない部分がある。

原因の候補を1つずつ外していく進め方が丁寧です。「開発者がアクセシビリティを気にしていない」で片付けるのは簡単だけれど、そうは思わない。「訓練が足りない」も簡単で、ときには本当だけれど、ここで起きたことの説明にはならない。このプロジェクトの開発者はアクセシブルなプロダクトの経験があり、ゼロから始めたわけではなかった。そこで個々のバグへの関心が薄れていきます。代替テキストの欠落もフォーカス管理の破綻も通知の欠落も症状で、本当の問いは、アクセシブルに実装できるデザインから始めたチームが、そうでないプロダクトに行き着けるのはどういう仕組みなのか、というものでした。

区別の立て方が有用でした。デザインレビューと監査は違う問いに答えている。レビューが問うのはアイデアがアクセシブルに実装できるかどうか、つまり可能性です。良いレビューは障害のあるユーザーにとってうまく働くパターンを見つけ、働きえないアイデアに旗を立てる。それが通常しないのは、その結果を達成するために必要な実装の細部をすべて文書化することです。キーボードフォーカスをどう管理するか、どの変更を支援技術に通知するか、カスタムコンポーネントが意味論をどう露出するかは実装の判断で、誰かがそれを決め、文書化し、実際にそうなったか検証する必要がある。だからレビューは「アクセシブルに実装できます」と誠実に結論しながら、実際にそうなるかについて何も言わないままでいられる。

「キーボードを使っているから分かるはず」という思い込みへの反論も的確です。コードをキーボードで書くことと、マウスなしでインターフェースを操作することは違う技能。エディタのショートカットを知っているからタブ順を学ぶわけではないし、Vim や VS Code を効率よく使うからフォーカス管理を発見するわけでもない。手がキーから離れないからといって、スクリーンリーダーがいつ live region を必要とするかは分からない。このプロジェクトには自分をパワーキーボードユーザーだと言う開発者が何人もいたけれど、それがキーボードに優しいインターフェースを作ることには繋がらなかった。「それを認めることは結果を免責しません。『とにかくキーボードを使ってみて』では、障害のあるユーザーが実際に何を経験しているかを誰にも教えられなかった理由を説明するだけです」。

診断のポイントは受け渡しの構造でした。デザインチームがデザインを持ち、開発者がコードを書くことを持ち、QA が機能のテストを持ち、アクセシビリティが監査を持つ。各段階に担い手がいた。担い手がいなかったのは、アクセシビリティを1つの段階から次へ運ぶことです。障害のあるユーザーにとって重要だった実装の細部は、意図的に削られたのではなく、運ばれなかった。だからこれは人の問題ではなく workflow の問題になる、と。監査の時期についての一節も鋭いです。デザインの後の最初のアクセシビリティのチェックポイントが開発終盤の包括的な監査なら、チームには早期警戒の仕組みがない。リリース前の週に最初のパフォーマンス問題を見つけるところ、あるいはコードが全部書かれた後に最初のセキュリティレビューをするところを想像してみる、と。そして「人はレビューされるものに注意を向ける」。コードレビューがアーキテクチャや命名やパフォーマンスやテストカバレッジにコメントし、QA が振る舞いを検証し、自動テストがビルドごとに走る。それらのチェックポイントは、誰が意図しようとしまいと、チームに品質とは何かを教えている。

UXエンジニアリングの視点では、提案が既存の workflow に載る形になっているところが実行可能性を上げています。デザイン段階では、「アクセシブルに実装できる」と承認されたときにアクセシビリティ要件を視覚仕様の隣に書く——フォーカス順、キーボードの振る舞い、通知、意味論、状態変化を誰かの記憶や議事録ではなくデザインの一部にして、そこから受け入れ条件にする。開発段階では、デザインから実装への移行に担い手を置く。加えて、フォーカス管理や disclosure widget を毎回作り直さないための共有コンポーネントライブラリと、ビルドパイプラインの自動チェック。検証段階では、完全な監査でなくてよいので開発中にもう1つ焦点を絞ったレビューを挟み、すでに行われているコードレビュー・機能レビュー・QA の会話の中にアクセシビリティを可視化する。「新しい儀式は必要ありません。すでに持っている会話の一部になる必要があります」。最後に誰が見落としたかを探すことには依存しない、すべての受け渡しに担い手を与えることに依存する——という締め方は、そのまま組織に持ち込める言葉でしょう。

> 🐈‍⬛ : 「監査が厳しすぎたのではなく、遅すぎた」という言い換えが強い。リリース前の週に最初のパフォーマンス計測をする状況を想像すれば誰でも異常だと分かるのに、アクセシビリティだと同じ形が受け入れられてしまう。「人はレビューされるものに注意を向ける」も、誰かを責める言い方をせずに構造だけを指しているのがいい。受け渡しごとに担い手を置くという処方は、今週の TanStack の記事や LayerX の記事とまったく同じ場所を叩いています。

## [The making of Cursor's icons](https://www.minoradventures.co/blog/the-making-of-cursors-icons)

**3行まとめ**
- Cursor の 600 以上のアイコンを1年かけて手で描き直した記録。16px と 24px の2サイズ、Outline と Filled の2スタイル

**詳細解説**

Marek Minor（Minor Adventures）による制作記です。出発点は、VS Code のエコシステムから継承した Codicons が Cursor の現在に合わなくなっていたこと。数えると 468 個で、ドキュメントには 498 と書かれ、行き先のないコードポイントもある。「誰も所有していないセットはずれていく」と書かれていて、継承したアイコンセットの典型として読めます。

ただ、より大きな問題は概念のカバー範囲でした。AIエージェント、並列実行と逐次実行、単一スレッドと並列スレッド、思考の深さの段階、コストと計算量、Bugbot。どの汎用アイコンライブラリにも揃っていない語彙です。汎用セットはある程度まで引き伸ばせるけれど、いつかプロダクトは自分の語彙を必要とする、という整理でした。

技術的な判断の部分がおもしろいところです。1px では文字の隣で細すぎ、1.5px では重すぎ、1.25px で 16px の Cursor Gothic と並んで釣り合う。ピクセルグリッドにスナップしない選択も意図的で、12px・14px・16px・20px でレンダリングされるならスナップ先の単一のグリッドは存在しないからです。アイコンをビットマップではなく、小さなロゴや書体の字のような記号として扱う、と説明されています。24px は別のグリッドに 1.5px で描き直す。書体の Text と Display の光学サイズと同じ考え方です。

構築のロジックも一貫していました。水平・垂直・45度の線から始め、概念が要求するときだけ他の角度を許し、形が意図に沿うまで角を丸める。雲は円からではなく直線の連結に丸い接合を与えて作る。円由来の自由曲線はほとんど登場しません。ポインタが左下から右上へ走るので、どちらでもありうるアイコンはすべてその向きに揃え、スラッシュだけは逆に走らせて方向を打ち消す。「画面からこれを読み取る人はいません。でもこういうルールがないと、セットは一箇所から来たものに見えなくなります」という一文が効いています。

光学的な補正の節は、この記事のいちばん濃い部分でした。線が交わる接合部は形が積み上がって暗く見えるので小さなノッチを切る、線が集まりすぎる場所では一部の線を細くする、行末のドットと「もっとある」のドットと単独で浮くドットはそれぞれ違うサイズが要る、重なる形の隙間は 16px グリッドで3単位を下回らせない。16px で見えるのかという問いには、インターフェースはズームするし 24px は大きいサイズで生きる、そして10ptのインクトラップと同じく「気づきの手前の層で効く」と答えています。ハンバーガーアイコン1つに 156 通りの探索を並べた画像が添えられていました。

後半は運用の話です。Figma ファイルを3つ持つ——数百の試行を置く Explorations、光学図形・隙間・修飾記号・ドットとノッチ・遠近と斜線・繰り返し登場する物体（155 以上の要素）を突き合わせる Overviews、最終形をコンポーネントとして持つ Icons。Overviews のプロトタイプはスマートフォンにミラーリングして確認します。16px が実際に 16px として見える場所で、描いたファイルの外から見る必要があるという理由でした。差し替えは、旧フォントの 645 個をすべて同じコードポイントの後継へ再マッピングし、後継のないものは意図して退役させる方針。そのために移行用ダッシュボードを自作し、SVG の欠落と重複コードポイントを警告させています。

UXエンジニアリングの視点では、納品物の定義が広いところが読みどころです。Figma ソース、アイコンフォント、書き出した SVG、そしてチームが日々使うコンパニオンサイト。サイトにはホバーでコードポイントとクイックアクションが出るグリッド、1,274 のタグを対象にした検索（「search」で `magnifying-glass` が出る）、Cursor の概念とアイコンを1対1に固定する表があります。「[X] のアイコンは？」への答えが常に1つであり続けるための表で、これがないとセットは同じ概念に2つのアイコンを持ちはじめ、その時点でシステムでなくなる、と。そして `ship it` コマンドがコードポイント割り当てからフォント4種のコンパイル、スタイルシートの統合、フォント内メタデータの書き換え、サイトのデータ再生成、ドキュメントのアイコン数の照合、コミットとプッシュまでを通します。「システムが、自分が何かを覚えていることに依存しない状態」で引き渡す。これはデザインシステムの担当者が読むと刺さる形の締め方でしょう。

> 🐈‍⬛ : 「AIエージェント、並列実行と逐次実行、思考の深さの段階」がどの汎用ライブラリにも揃っていない、という指摘が効きます。プロダクトが自分の語彙を必要とする瞬間の記録として読めて、しかもその語彙のほとんどがここ2年で生まれたものだというところがおもしろい。納品物に `ship it` コマンドとコンパニオンサイトまで含めて「システムが、自分が何かを覚えていることに依存しない状態」で渡す、という締め方が好みです。概念とアイコンを1対1に固定する表は、前号で読んだ「決定を運ぶ」という話のいちばん具体的な形をしている。

## [How to choose a UI font (and 10 Inter alternatives)](https://yeptype.com/article/inter-alternatives)

> **出典**: Sidebar | **公開日**: 2026-08-20 | **カテゴリ**: design

**3行まとめ**
- UIフォント選定の基準を「cap-centeredな垂直メトリクス」と「背の高いx-ハイト」の2つに絞り込んだ実用記事です
- この2条件を満たすフォントなら、ボタンのラベルが単一のパディングトークンで光学的に中央揃えになります
- InterとSan Franciscoを基準点に、条件を満たす10書体を x-ハイトの数値付きで紹介します

**詳細解説**

「Interはみんな使っているから別のフォントにしたい」という、プロダクトデザイナーなら一度は通る場面から始まる記事です。筆者は60書体以上のネオグロテスクを集めるタイポグラフィ愛好家でもあり、その経験から「きれいなサンセリフならどれでもいい、では済まない」ことを2つの基準で説明します。1つ目はcap-centered vertical metrics。フォントのバウンディングボックス内で、キャップハイトの上の余白とベースラインの下の余白が等しいことです。これが満たされると、ラベルがボタンのなかで光学的に中央に座り、隣のアイコンとも揃い、CSSは `padding: var(--space-v) var(--space-h)` の1行がどのサイズでも成立します。満たされないと、フォントサイズごとに違うピクセル数の手動調整が必要になり、デザインシステムの保守性を静かに削っていきます。

2つ目はx-ハイトがキャップハイトの70〜75%あることです。単語を四角いブロックとして中央に置いても、小文字が低いと上に空白ができて「沈んで」見えます。InterやSan Franciscoが採用する75%は、単語がほぼブロックとして読めつつ大文字と小文字の区別も保てる黄金比だ、という説明には説得力があります。Figmaで確認する手順（1000pxで表示して行間を詰め、テキストボックスの上下が同時に文字に接するかを見る）も具体的で、明日から使えます。

CSSの `text-box-trim` がこの問題の半分を解決しつつあることにも触れられていますが、Firefox未対応で世界のカバレッジは約79%、しかも直せるのはメトリクスだけでx-ハイトには手が出せません。当面は「最初から条件を満たすフォントを選ぶ」が正解、という結論は現実的です。フォント選びを感覚から仕組みに変えてくれる、ブックマーク推奨の一本です。

> 🐈‍⬛ : 好みの問題に見えるフォント選びを、パディングトークンが1つで足りるかという保守性の問題へ翻訳したのがうまい。フォントサイズごとの手動調整がデザインシステムを静かに削っていく、という言い方も正確です。Figma で1000pxまで拡大して上下が同時に文字に接するかを見る手順は、明日そのまま試せる粒度。前の記事の 1.25px と同じ層の作業で、どちらも数値のほうが後から来ている。

## [Design is how it tastes](https://superposition.jem.computer/design-is-how-it-tastes/)

> **出典**: Sidebar | **公開日**: 2026-08-17 | **カテゴリ**: design

**3行まとめ**
- デザインシステムは判断を保存できるけれど、その判断が存在する「感じられた理由」は落としてしまう
- object-language（暖色のニュートラル、8px の角丸）と encounter-language（ユーカリの林に車を降りたときの空気）を対比させ、後者のほうが多くの設計方向を含んでいると論じる
- 拡散モデルが encounter-language を直接解釈できるようになったので、体験の言語が実行の言語の隣に来た。sensation → visuals → system という逆向きの流れの提案

**詳細解説**

2000年の Macworld で Steve Jobs が Aqua のボタンを「舐めたくなる」と紹介した場面から始まります。半径やパディングやコントラスト比の話ではなく、感覚的な直接性の話をしていた、と。それから26年、デザインの判断を保存するための強力なシステムを作り続けてきました。トークン、コンポーネント、スペーシングスケール、インタラクション状態、ブレークポイントごとのバリアント。整合を保ち、ずれを防ぎ、意図を再利用可能な文法に符号化する点でデザインシステムは優秀です。けれど、その判断が存在する感じられた理由は落ちる。

Google Labs の DESIGN.md が例に出されます。デザインの理念を1つの Markdown に符号化してコーディングエージェントに一貫して実装させる、という発想自体は妥当。ただ典型的な DESIGN.md には「8px の角丸を使う。ニュートラルなパレットにピンクのアクセント。ボタンには primary と secondary。カードには控えめなボーダー」と書かれている。有用だけれど薄い、生成された物体を記述しているだけで、意図された出会いを保存していない、という指摘です。「デザインの意図がトークンになった瞬間に、温度が抜け落ちる」。

対比の立て方が鮮やかでした。object-language は成果物を記述します——暖色のニュートラル、上品なセリフ、控えめなテクスチャ、柔らかいカード、ゆったりした余白。encounter-language は成果物に出会う経験を記述します——車を降りてユーカリの林に立つ、メンドシーノの太平洋の空気の味、額に触れる黄金色の日差し、山小屋に漂うコパルの煙。「ページはあなたが到着する前にもう息を吐き終えている」。1つの感覚的な場面が、色・余白・コントラスト・素材感・装飾・密度を名指さずに符号化できる。別の軸で精密なのだ、という言い方です。

この言語はこれまで機械には無用でした。ブランドデッキに「このページは乳香の香りがするべきだ」と書いても、開発者はうなずいて角丸の調整に戻る。感覚の言語は実行の言語とは別の部屋に住んでいた。変わったのは、拡散モデルが encounter-language を直接解釈できるようになった点だとされます。「乳香」を「控えめなテクスチャの暖色ニュートラル」に翻訳してもらう必要がなく、感覚を理解して形を生成する。実験の記述も具体的で、いちばん強く効いたプロンプトは視覚的なスタイルタグではなく身体化された場面でした。「田舎の未舗装路でタイヤの下で砂利が鳴る」「少し日焼けして靴に砂を入れたまま街に帰る」。返ってきたものは、ブランドガイドラインが掲げていた「カリフォルニアへのラブレター」を、デザイン用語を与えないまま設計判断へ翻訳していたそうです。プロンプトは無作為な感覚のノイズではなく、味と香り・天候と大気・素材・情動・社会的シグナル・人生の季節というカテゴリに分かれていて、天候は階層と密度を、素材は質感と輪郭を、社会的シグナルは誰が自分を認められたと感じるかを形づくる、と整理されています。

UXエンジニアリングの視点では、結論の置き方が慎重なところに注目したいです。デザインシステムをバイブで置き換えるという主張ではありません。トークンも craft も判断も必要で、コーディングエージェントは何を作るのか知る必要がある。提案はその上に生成的な意味論の層を置くこと。従来は system → visuals で、トークンを決め、コンポーネントを決め、ページを作る。逆向きにする——sensation → visuals → system。どう感じるかから始め、視覚的な場を生成し、うまくいったものからシステムを抽出する。モデルは可能性を生成しますが、判断としての taste はループの中に残る。「これはまだ意図のように感じられるか、それとも美的なコスチュームに崩れたか」。この問いを誰が持つのかという整理は、生成物の量が増えるほど重くなるところでしょう。

> 🐈‍⬛ : 前号の「Taste is all that's left」が taste の原資を遡っていたのに対して、こちらは taste をどう入力に変えるかを書いています。ただ encounter-language には再現性の弱さがあるはずで、「ユーカリの林」から生成されたものを次の人が同じ方向へ伸ばせるかは別の問題。だから前の記事の x-ハイト 70〜75% のような object-language が消えるわけではなく、順番が逆になるという提案として読むのが正確でしょう。「これはまだ意図のように感じられるか、それとも美的なコスチュームに崩れたか」を誰が持つのか、という問いだけが残ります。

## [The human is the loop](https://brentfitzgerald.com/posts/the-human-is-the-loop/)

**詳細解説**

Brent Fitzgerald による、休暇明けの内省です。夏の終わりの休暇で冷たい川で泳ぎ、s'more を食べすぎ、昼寝をした。多くの時間はラップトップも電話も離れていたので、数週間 AI なしで過ごした。「恋しくなかった」。戻ってきた数日で分かったのは、AI の使用の多くが不要だったこと。それどころか、しばしば習慣を形成する松葉杖になっていて、知的に弱く、好奇心を減らし、自信を減らしていた。少し落ち込ませてもいたと思う、と。

自己批判に寄りすぎないよう慎重に書かれているのも好ましいところです。厳しすぎるのは新しい振る舞いではなく、非現実的な期待に基づく圧力は長く自分の源にあった。ただ機械知性の時代に、その圧力は新しい出口を見つけた。仕事と生活で何がいちばん重要かを選別して集中させるのではなく、「今ならもっとできるはずだ」という検討されていない信念を養う。そしてもう1つのエージェントの会話、もう1つのターミナルのペイン、誰も頼んでいないフォーク、読むことのないマークダウンの出力として放出される。以前は個人の企画を、くつろぐためと楽しみのために学ぶために弄っていた。今の企画はそれをしない——結果に行くために学びを飛ばしがちで、学びこそが喜びが起きる場所なのに。

エージェントを「自分とストレスを起こすタスクのあいだの層」として使っていたという観察が、いちばん刺さる部分でしょう。直接引き受けるのではなく、エージェントを間に入れる。特別なぬいぐるみかお守りのように守ってくれる。何か書く必要があれば、考えを全部口述して、運転中や歩きながら ChatGPT と話す。自分と考えをやりとりしている、生産的でない時間を活用しているのだと正当化するけれど、それが追従する鏡であることは知っていた。現実的な思考の相手ではないので、そのセッションの出力を実際の仕事に使ったことは一度もない。「では、あの何時間かは本当にどれだけ有用だったのか。今は OpenAI のサーバー上のとりとめのない録音と書き起こしです」。もう1つの例も的確で、理論的にもっと速く働けて多くのタスクを並列にできるよう自動化を整えようとしたけれど、後から見れば誰もその効率の向上を求めていなかった。「道具の使用を最大化するという課題に道具を適用することで、道具の使用を最大化したいという強い衝動を感じました。最悪の意味で再帰的で、生産性のウロボロスです」。

技術がこういう効果を必然的に持つとは論じていない点も抑制が効いています。形式・設計・そのまわりの文化が、形成された習慣の大きな要因だと考えている。エージェントの使用は、たとえば終わりのないアルゴリズムのフィード送りと同じ意味で本質的に神経化学的な中毒性を持つものではないだろう、という見立て。ただ依存と習慣化の効果は実在する。一度 AI の道具を仕事に入れると、組み込める方法をもっと見つけるのは早い。そして「テック業界の大きな一角が今、LLM への大規模な社会経済的依存に賭けています。ああいう評価額が正当化される唯一の道は、私たちが集団的に AI 基盤の技術に望みなく依存するようになることです」。

UXエンジニアリングの視点では、締め方の実践性が価値です。方針は単純——いつ AI を使い、いつ外に置くかを意図的にする。そして自分の選択で実際に何を得て何を失っているかについて正直であろうとする。この記事を書く前に実際にプロンプトを1つ入れた話が具体例になっていて、要件と提案を渡し、コードベースやウィキやスキーマや会話を見るよう指示し、旗を立てた問題と可能な解決策を持ち帰らせた。設定する作業そのものが、現状に追いつき、考え抜くことを強いた。狭く制約し、自分がすでに考えていることと確信のないことを含めて可能な限りの文脈を与え、出力への期待を明確にした。「AI は完璧な解決策を渡してはくれません。結果が自分を10倍にすることもない。でも、散らばったシステムと SaaS 製品を横断してパターンを照合し検索している——自分が得意ではなく、楽しくもない作業です」。より重要なのは、それが今こうして書いて省察するという人間的なことをする余裕を作っていること。「人間がエージェントのループに閉じ込められることは望みません。人間がループであって、私たちはエージェントをときどき、慎重にタグインさせるのです」。
