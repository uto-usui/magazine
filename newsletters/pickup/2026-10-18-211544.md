## [Pure UI in the Agentic Era](https://mattrothenberg.com/notes/pure-ui-agentic-era/)

> **出典**: Sidebar | **公開日**: 2026-10-16 | **カテゴリ**: design

**3行まとめ**
- Guillermo Rauch さんが2015年に書いた「Pure UI」（UI はアプリの状態の純粋な関数であるという考え方）を、コーディングエージェントの時代に読み直した記事です
- エージェントに削除ボタンの追加を頼むと、オーナー権限のアカウントで動作を確かめて「完了」と報告しました。閲覧専用のロールでも削除ボタンが出てしまう不具合は見落とされていました
- 画面に影響する状態をページの境界で明示的な入力にすれば、16通りの組み合わせを並べて描画し、一覧でレビューできると提案しています

**詳細解説**

記事の例はダッシュボード画面です。ロール、プラン、請求の状態、ベータ機能のフラグという4つの入力があり、それぞれ2つの値をとるので16通りの画面になります。ところが実際のコードでは、ロールはクエリから、プランはコンテキストから、請求の状態はレイアウトからと、状態があちこちから届きます。コンポーネントを読んでも、どんな状態がありうるのかはわかりません。著者の図では、ツリーが宣言しているのは7つの props だけで、それ以外に15か所で状態を暗黙に読み込んでいました。

エージェントの報告は、型チェックが通り、ブラウザでも確認したという、それらしいものでした。ただ、確認したのは開発サーバーがたまたまログインしていたオーナーのアカウントだけです。ヘッダーには「View only」のバッジが出ているのに、テーブルの各行には削除ボタンが残っていました。著者は、人も同じ見落としをするとしたうえで、違いを次のように述べています。エージェントは1つの状態しか確かめていなくても、16通りを確かめたときと同じ自信で「完了」と言います。しかも、生成された変更1件あたりにかけられるレビューの時間は減っていきます。

解決策は、画面の表示に関わる状態をページやビューの境界に集めて、引数として渡すことです。そうすれば、その API がそのまま「出力を変えうる条件の一覧」になります。Storybook のストーリーやテスト、画面を並べたグリッドにも変換しやすくなります。Storybook や Playwright を否定するのではなく、どの組み合わせが大事かを書き留めておく場所として Pure UI を位置づけているのがよいところです。

UXエンジニアリングの視点では、「エージェントが実際に何を見たのか」をマージ前に問う習慣として取り入れやすい内容です。デザインでも、ロレム・イプサムで埋めた理想の1画面だけを描く問題は昔から指摘されてきました。状態の組み合わせを明示すると、権限や料金プランの抜け漏れをレビューで見つけやすくなります。ただし、組み合わせは条件が増えるほど急に増えるので、どれを並べるかを決めるのは結局人の仕事です。記事もこの限界を認めています。

> 🐈‍⬛ : 「エージェントは1つの状態しか確かめていなくても、16通りを確かめたときと同じ自信で完了と言う」という一文が、今週いちばん印象に残りました。状態をページの境界に集めるのは昔からある設計の話ですが、レビューする側が「何を見たのか」を問える形にしておく、という目的で読み直すと新しく見えます。ロールやプランの組み合わせを一覧で並べるやり方は、デザインのレビューにもそのまま持ち込めそうです。

## [How Meta Built Forum With AI-Native Engineering](https://engineering.fb.com/2026/10/15/ml-applications/how-meta-built-forum-ai-native-engineering/)

> **出典**: Meta Engineering | **公開日**: 2026-10-15 | **カテゴリ**: engineering

**3行まとめ**
- Facebook グループ向けの新アプリ Forum を、小さなチームが AI エージェントを開発プロセスの参加者として扱いながら作った記録です
- 人が毎回手を動かす「human-in-the-loop」から、エージェントが計画・実装・テスト・修正を回し、人は目標設定と承認を受け持つ「human-on-the-loop」へ移ることを目指しました
- 完了の基準をコンパイルではなく検証に置き、ストレステストでメモリの問題を開発中に見つけるなどして、8週間で Facebook グループの主要機能に並びました

**詳細解説**

成功の基準を、コードの量ではなく「ビルドが通り、テストに合格し、レビューを通った変更」に置いています。検証がなければ、AI が出したそれらしいコードを人が読んで直して捨てることになり、ボトルネックが実装からレビューに移るだけだという認識です。そこで、ビルド結果、ユニットテスト、UI 仕様との照合をエージェントのループに組み込み、レビューに出る前に自分の仕事を確かめさせています。プルリクエストには、テスト計画と検証の様子を記録した映像が添えられます。

運用の仕組みは5つの部品でできています。同じ失敗が2回を超えたら書き足す恒久的な指示（Rules）、チームの慣習を手順にした Skills、手作業の確認を自動化する Agents、それらをつなぐ Commands、そしてリンターの実行などを自動で走らせる Hooks です。とくに効いたのは、プロンプトよりもコードと道具を変えることでした。エージェントがアプリのどこを触っているのか見失う問題には、アプリを説明する代わりに、シミュレーターから画面の階層を読み取る道具を渡して解決しています。

プロトタイプを扱う工夫もあります。本番と同じコードベースとデザインシステムを使う別のビルドを用意し、プロトタイプのコードは本番のビルドから物理的に外れるようにしました。デザイナーや他職種がエンジニアを介さずに AI で試作でき、それをそのまま本番に移すこともできます。それでいて、試作のコードが本番アプリを落とすことはありません。ストレステストでは、激しいスクロールや素早い画面遷移を繰り返してメモリの増え方を監視し、見つけた問題で使用量をおよそ半分にしています。

UXエンジニアリングの視点では、試作用のビルドを分ける設計が参考になります。フィーチャーフラグで隠すだけでは、試作のコードは本番に含まれたままです。デザイナーが自由に試せる場を、本番の安全を損なわずに用意できます。また、エージェントの回答の質を上げたのは、新しく入ったエンジニアに初日に渡すような資料（関連コード、クエリの例、設計ドキュメント）だったという話もうなずけます。ただし、公式ブログでの成果報告なので、うまくいかなかった点は図でまとめられている程度です。チームの規模や体制の詳しい条件も書かれていません。

> 🐈‍⬛ : 「ボトルネックが実装からレビューに移るだけ」という認識から検証をエージェントのループに組み込んだのは、Pure UI の話へのひとつの答えになっています。個人的には、エージェントにアプリの説明を重ねるより、シミュレーターから画面の階層を読む道具を渡したほうが効いた、というくだりが好きです。プロトタイプ用のビルドを物理的に分ける設計も、デザイナーが安心して試せる場づくりとしてよく考えられています。

## [React習熟度ベンチマークでHaiku 5.5が見せた底力](https://zenn.dev/uhyo/articles/react-profession-bench-20)

> **出典**: uhyo | **公開日**: 2026-10-10 | **カテゴリ**: frontend

**3行まとめ**
- uhyo さんの React 習熟度ベンチマーク第20回で、Claude Haiku 5.5 を effort の high と max で計測した結果です。high は83.82点で、Sonnet 5.5 high の81.08点を上回りました
- ただし著者は、これを「Haiku が強い」ではなく「Sonnet 5.5 が high ではほとんど考えていない」ことの表れだと読んでいます。実装1件にかかった時間の中央値は、Sonnet 5.5 high が0.9分、Haiku 5.5 high が2.2分でした
- max にしても +1.74点しか伸びず、その伸びは `useEffectEvent` や `useSyncExternalStore` のような新しい API を使いきるかどうかにほぼ集中していました

**詳細解説**

Haiku 5.5 max は85.56点で、GPT-6 Astra max や Fable 5.1 と同じ帯にいます。4か月前の Opus 4.8 max（84.03点）を、今の Haiku が上回ったことになります。high 同士では OpenAI 系の high 条件をすべて上回りましたが、max 同士では Sonnet 5.5 が6.2点上です。著者は「effort=high という同じ名前の下で、Haiku のほうが多く働いている」とまとめています。

effort を上げて何が変わったかの分析が細かいです。通知フィードの課題では、`useEffectEvent` を使った実装が high の0/3から max で3/3になりました（Sonnet 5.5 max は1/3）。別の課題では、high でも `useSyncExternalStore` を使っていたものの、5つある外部購読のうち毎回1つを `useEffect` のまま残していて、max で全部置き換わりました。一方、コンポーネント設計とパフォーマンスの点数は max でもまったく動いていません。ツールチップの課題で Popover API を使った実装は、これまでの全91回で一度もなかったそうです。

計測の姿勢も参考になります。今回、ホストのスリープで止められた実行の判定理由が保存されていなかったハーネスのバグを見つけ、過去分で約100件が失われていたことを報告し、修正しています。「この結果から言えないこと」という節を設け、評価者が Sonnet 4.6 であることや、Haiku 4.5 との比較は条件が違うので目安にしかならないことも明記しています。

UXエンジニアリングの視点では、アクセシビリティも採点項目に入っているなかで、Popover API が一度も使われないなど、モデルが新しいプラットフォーム機能を自分から選ばない傾向が見えるのは、UI 実装をエージェントに任せるときの注意点になります。effort の名前が同じでもモデルによって作業量が違うので、モデル選びは名前ではなく自分たちの課題で測って決める、という教訓も得られます。各条件 n=3、13の課題での結果である点は踏まえておきましょう。

> 🐈‍⬛ : 同じ effort=high でもモデルによって考える量が違う、という話は、ベンチマークの数字を読むときの前提を揺さぶります。ハーネスのバグで約100件の判定理由が失われていたことを自分から報告し、「この結果から言えないこと」の節まで設けているのも、測る側の誠実さとしてよくできています。Popover API が91回で一度も使われていないのは、新しいプラットフォーム機能をエージェントに使わせたいなら指示で明示する必要がある、という合図にも読めます。

## [Synthetic Users vs. Human Respondents: Same Conclusion, Less Variation](https://www.nngroup.com/articles/synthetic-users-vs-human-respondents/)

> **出典**: Nielsen Norman Group | **公開日**: 2026-10-16 | **カテゴリ**: design

**3行まとめ**
- 以前604人の専門職に聞いた「この仕事を何と呼ぶか」という自由回答の質問を、AI が生成した120人の「合成ユーザー」にも聞いて比べた調査です
- どちらも「UX という呼び名が主流」という同じ結論になりましたが、人の回答が50以上の呼び名に分かれたのに対し、合成ユーザーは十数個に集まりました
- 珍しい回答が消えてよくある回答に寄っていく現象を「モード崩壊」と呼び、少数派の意見が大事な調査では人が必要だと結論づけています

**詳細解説**

合成ユーザーには、Synthetic Users というサービスを使っています。調査計画を渡すと、年齢・地域・職種・文化的背景・性格特性などのプロフィールを持った回答者を自動で作ってくれます。ただ、このサービスはインタビュー形式で回答するので回答が長くなり、質問の言い回しも勝手に少し変えていました。研究者が質問の出し方を細かく管理できないこと自体が、結果に影響しうる要因だと指摘しています。

数字の比較が具体的です。UX 関連の言葉を使った割合は、人が約70%、合成ユーザーが84%でした。人のサンプルは NN/g 自身のパネルから集めたので UX 職が67%を占めていました。一方、合成ユーザーは職種の割り当てを決めて作ったので、UX 職は20%しかいません。それでも合成ユーザーのほうが UX という言葉を多く使っていたわけです。プロダクトマネージャーに絞ると、人は44%、合成ユーザーは93%でした。職種による違いは合成データにも出ていますが、全体として多数派の言い方に強く引っぱられています。

「もっと多様に答えて」と指示すればよいという考えにも、記事は答えています。多様さを出せても、それが実際の人の珍しい回答を、実際と同じくらいの頻度で再現しているとは限りません。人のデータがなければ、その多様さが正しいかどうかを確かめる方法もない、ということです。

UXエンジニアリングの視点では、AI ペルソナや合成ユーザーを使う場面が増えるなかで、使いどころをはっきりさせてくれる記事です。仮説づくりや大まかな傾向の確認には使えますが、意外な言葉づかいや新しいテーマを探す調査、ユーザー層ごとの違いを見る調査には向きません。結論が人の調査と一致したことは、合成ユーザーが信頼できる証拠にはならない、という点も覚えておきたいところです。ただし、今回は1つの質問と1つのサービスによる比較なので、ほかのツールや質問形式にもそのまま当てはまるとは限りません。

> 🐈‍⬛ : 結論が一致したのに、それが信頼の証拠にならないという構図がおもしろいところです。多数派の答えはもともと人に聞かなくても予想がつくことが多く、調査の価値はむしろ50以上に分かれた呼び名のほうにあります。uhyo さんのベンチマークと同じく、平均の数字より、ばらつきや取りこぼしのほうに大事な情報がある、という話として読みました。

## [The best way to use icons in Web UIs](https://lea.verou.me/blog/2026/icons/)

> **出典**: Lea Verou | **公開日**: 2026-10-11 | **カテゴリ**: css

**3行まとめ**
- Lea Verou さんが、HTML に手を入れずに CSS だけでアイコンを差し込み、状態に応じて切り替えられる仕組みを提案した記事です。アイコンをデザイントークンとして `:root` の CSS 変数に置き、`--icon` を指定するだけで使えます
- 疑似要素を `1em` の正方形にして `currentColor` で塗り、アイコンの形で `mask` をかけるのが基本です。スタイルクエリと `@property` を組み合わせて、アイコンを指定した要素にだけ表示されるようにしています
- Safari のバグ3件の回避策まで含めた実装を `@nudeui/icons` として公開しています。Linked Parameters や `ident()`、`@mixin` など、今後の CSS で書き方がさらに短くなる見通しも紹介しています

**詳細解説**

今もっとも一般的なのは、インライン SVG を HTML に直接書く方法です。`<TrashIcon />` のようなコンポーネントで包んでも、重いマークアップはそのままブラウザに届きます。アイコンフォントは CSS でアイコンを扱えるのが魅力でしたが、読み込みに失敗したときの代替文字や、スクリーンリーダーが私用領域の文字を読み上げてしまうといった問題がありました。著者は「問題はフォントであって CSS ではなかった」と述べています。2010年に UI アイコンを Web フォントで表示した最初の一人かもしれず、Font Awesome のプロダクトリードも務めた人の提案なので、説得力があります。

使い方はシンプルです。`button.delete { --icon: var(--icon-trash); }` と書けば HTML を変えずに削除ボタンにアイコンが付き、`:hover` やダークモード、印刷時に別のアイコンへ切り替えることもできます。`details::marker` や `select::picker-icon` のような疑似要素にも置けるのは、マークアップ側の方法では実現できない点です。flex のボタンのなかでは `aspect-ratio` が効かないので幅と高さを両方指定する、`flex: none` で縮まないようにする、キャップハイト（大文字の高さ）に合わせて縦位置をそろえる、といった細かな工夫も書かれています。アイコンだけのボタンには、生成コンテンツの代替テキスト `content: "" / var(--icon-style-alt, "")` で名前を付けられます。

スタイルクエリは Baseline 2026 で、Firefox が2026年5月に最後に対応しました。Can I Use では約93%のブラウザで使えるそうです。著者はアイコンを段階的な機能拡張として扱い、アイコンだけのボタンのように欠けると困る場面ではクラスで指定する方法を勧めています。Safari では、ユーザーが操作するまでアイコンが表示されないバグがあり、長さ0のアニメーションを当てて回避しています。

UXエンジニアリングの視点では、アイコンをデザインシステムのトークンとして一か所で管理できる点が大きいです。ページによって Font Awesome と Lucide のゴミ箱アイコンが混ざる、といったことを防げますし、登録されていないアイコンを直接指定するとレビューで目立ちます。一方で、マスクを使うため単色のアイコンに限られ、自由なアニメーションにはインライン SVG が必要です。SVG ファイルの相対 URL の解決もブラウザごとにばらばらで、今は Firefox だけが正しく動きます。React コンポーネントでアイコンを配っているチームは、移行の手間と比べて判断するとよいでしょう。

> 🐈‍⬛ : アイコンフォントの問題を「フォントであって CSS ではなかった」と切り分け直したうえで、CSS 変数とマスクで同じ使い心地を取り戻しているのがきれいです。Font Awesome に関わってきた人がこれを書いているのも味わい深いところです。単色に限られる、Safari の回避策が要るといった制約まで並べてくれているので、自分たちのデザインシステムに入れるかどうかを判断しやすくなっています。

## [JPEG XL vs AVIF for web use-cases](https://jakearchibald.com/2026/jpeg-xl-vs-avif/)

> **出典**: Jake Archibald | **公開日**: 2026-10-15 | **カテゴリ**: web-standards

**3行まとめ**
- JPEG XL が主要ブラウザすべてで使えるようになったのを受けて、Jake Archibald さんが AVIF と自前のベンチマークで比べた長編記事です。写真の非可逆圧縮では、既定の設定で JPEG XL のほうが15〜25%大きくなるのがふつうでした
- スクリーンショットやイラストでは差がさらに広がり、JPEG XL は30〜90%大きくなります。透過画像やデコード速度でも AVIF が上回りました
- 一方で、可逆圧縮と既存 JPEG の無劣化変換（9〜20%縮小）では JPEG XL がはっきり勝っています。結論は「AVIF 4:4:4 を既定にして、大きすぎるときだけ JPEG XL（jixel）も試す」です

**詳細解説**

検証には avifenc と、JPEG XL のエンコーダー2種類（参照実装の libjxl と、新しく出てきた jixel）を使っています。F1 の写真、人物、レッサーパンダ、スクリーンショット、イラスト、透過画像、1,800万画素の大きな画像、HDR と、画像の種類ごとにファイルサイズ・エンコード時間・メモリ・3ブラウザでのデコード時間を測っています。画質の指標には SSIMULACRA2 と ColorVideoVDP の2つを使い、両者が食い違う場面もそのまま書いています。データとグラフがすべて公開されているので、結論だけでなく条件ごとの差を確かめられる記事です。

結果のなかで実務に効きそうなのは、エンコーダーの選び方で結果が大きく変わる点です。jixel はたいてい libjxl より小さいファイルを作りますが、透過は常に可逆で保存するため、透過画像では AVIF の2〜3倍になります。libjxl は努力値を上げても、時間とメモリが増えるわりにほとんど小さくならず、かえって大きくなることもありました。AVIF の 4:2:0（色の解像度を半分にする設定）もファイルはあまり小さくならず、高画質に届きにくくなるので、既定は 4:4:4 がよいとしています。「スクリーンショットは可逆形式で」という長年の習慣についても、非可逆の AVIF ならきれいに扱えると述べています。

UXエンジニアリングの視点では、プログレッシブ表示の考察がおもしろいところです。JPEG XL は読み込み途中でも徐々に精細になりますが、80%読み込んだ時点の画像は「ピントの甘い写真」に見えてしまい、読み込み中だと気づかれにくいと指摘しています。AVIF は約11.5kBで「何の写真か判断できるプレビュー」を出せるので、待つかどうかをユーザーが決められます。同じ理由で、BlurHash のようなぼかしは「かわいいけれど役に立たない」とも書いています。読み込み中の表示を「完成品と見分けがつくか」で評価する考え方は、スケルトン UI などにも応用できそうです。

同じ週には、AVIF 側の開発者 Gianni Rosato さんによる「[The case against JPEG XL](https://giannirosato.com/blog/post/case-against-jxl/)」も公開されています。デコード時間の差に加えて、1,918バイトの JPEG XL がデコードに17秒以上かかる例を挙げ、低性能端末への負荷攻撃になりうると指摘する内容です。また CSS Wizardry の記事（このあと紹介します）によると、Firefox 158 は JPEG XL を既定で有効にし、`Accept` ヘッダーに `image/jxl` を加えました。`Accept` を見て形式を切り替えている CDN では、アプリを変えなくても Firefox に返る画像が変わる可能性があります。キャッシュキーや `Vary` の扱いもあわせて確認しておくと安心です。Archibald さんも「AI が誤情報をそのまま返すこともあるので、自分の画像で試してほしい」と書いています。

> 🐈‍⬛ : 結論そのものより、「自分の画像で試してほしい」と添えてデータとグラフをすべて公開している姿勢がこの記事らしいところです。プログレッシブ表示を「完成品と見分けがつくか」で評価する視点は、今週の流れで読むと、途中の状態を完了と取り違えさせない設計の話でもあります。フォーマットの比較は結論だけが引用されがちですが、エンコーダーの選び方で結果が大きく変わるという点こそ、自分の環境で測り直す理由になります。

> 🐈‍⬛ : 「見つからない」とだけ答えるのではなく、どこを探して何が足りないかを伝える、という文例は、LayerX の記事の「確認できない」を書き分ける話をユーザー向けにしたもののように見えます。処理を見せる透明性と、なぜそうしたかの説明は別物だという指摘も、エージェントの UI を作るときに手元に置いておきたい視点です。賢さより手元の文脈が効くという結論は、先週の NN/g の調査や、同じ週の「[Context Libraries](https://www.nngroup.com/articles/context-libraries/)」の記事ともつながっています。

## [システムが正常でも、お客さまの業務は止まっているかもしれない。SmartHRのCREが挑む「顧客の可観測性」](https://tech.smarthr.jp/entry/2026/10/16/164423)

> **出典**: SmartHR Tech Blog | **公開日**: 2026-10-16 | **カテゴリ**: design

**3行まとめ**
- 2025年7月に立ち上がった SmartHR の CRE（Customer Reliability Engineering）チームに、取り組みの中身と目指す姿を聞いたインタビューです
- 社内向けの「DESK AIエージェント」は、技術的な問い合わせの約1割をそのまま解決しています。2026年下期には、担当プロダクトの問い合わせの50%を CRE メンバーなしで閉じることを目標にしています
- もう1つのテーマ「Customer Observability」は、システムが正常かどうかではなく、お客さまが業務を最後まで進められているかを観測しようとする構想です

**詳細解説**

CRE を立ち上げたきっかけは、カスタマーサポートだけでは解けない問い合わせが開発エンジニアにエスカレーションされ、機能開発の時間を圧迫していたことでした。ただ、エンジニアリングマネージャーの a-know さんは、問い合わせを引き受けるだけの「何でも屋」にはしたくないと話しています。SRE を「ソフトウェアエンジニアに運用チームの設計を任せたときにできあがるもの」と説明する言い方にならい、CRE を「ソフトウェアエンジニアにカスタマーサクセスチームの設計を任せたときにできあがるもの」にしたい、というのが目指す姿です。

DESK AIエージェントは、お客さまと直接話すチャットボットではなく、問い合わせを受けた社内メンバーが Slack で使う仕組みです。過去の対応記録やヘルプページを調べて回答し、解決しなかった場合も一次回答があることで対応が速くなっています。評価では点数を付けるだけでなく、情報が足りなかったのか、追加の質問が必要だったのかという解決できなかった理由を調べ、次に足す情報源を決めています。CRE の仕事の中心を「自分で調べて答えること」から「エージェントを評価して改善すること」に移したいと話しています。

Customer Observability の説明がわかりやすいです。申請業務で「提出する」ボタンを押したときの成功率やレイテンシーは、SLI と SLO ですでに見られます。しかし、そもそもボタンまでたどり着けなかった人が何人いて、なぜ離脱したのかは見えていません。AI で開発が速くなるなかで、CI/CD がすべて成功していても実際の業務で問題が起きることがあります。リリース後もお客さまの業務が滞っていないことを、安全に速く出し続けるためのガードレールにしたい、という考えです。

UXエンジニアリングの視点では、プロダクトアナリティクスのファネル分析と SRE の信頼性指標を、お客さまの業務単位でつなごうとする発想がおもしろいところです。システムの成功と業務の完了は別物だという指摘は、B2B の SaaS に限らず多くのプロダクトに当てはまります。ただし、業務の完了を観測するには、マーケティングやカスタマーサクセスが持つ情報まで集める必要があり、プロダクト開発に生かす部分はこれから力を入れる段階だと話しています。採用向けのインタビュー記事なので、具体的な設計や指標の定義はこれからの発信に期待したいところです。

> 🐈‍⬛ : 「提出する」ボタンを押したあとの成功率は見えていても、ボタンまでたどり着けなかった人は見えていない、という説明がわかりやすいです。CI/CD がすべて通ることと、お客さまの業務が進むことは別だという指摘は、最初の Pure UI の話をリリース後の側から言い直しているようにも読めます。DESK AIエージェントの評価で、解決できなかった理由を調べて次に足す情報源を決めているのも、地に足のついた改善の回し方です。
