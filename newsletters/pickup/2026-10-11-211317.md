## [The New Big Ball of Mud: Why Agentic AI Systems Turn Fragile](https://www.nngroup.com/articles/big-ball-of-mud-ai/)

> **出典**: Nielsen Norman Group | **公開日**: 2026-10-02 | **カテゴリ**: design

**3行まとめ**
- エンジニアではない人が AI エージェント向けのコンテキストやワークフローを自分で組み上げると、昔のソフトウェアと同じ「big ball of mud（つぎはぎで育った泥団子のようなシステム）」になる、というユーザー調査の報告です
- 使い捨てのつもりのコード、継ぎ足しの成長、その場しのぎの修正、ゴミ箱フォルダへの押し込み、作り直し、という5つのパターンを実例つきで整理しています
- 作り直しを避けることではなく、作り直すときに自分で方向を決められる状態でいることが大事で、そのためにコンテキストをグローバル・ローカル・アンビエントの3種類に分けて管理するよう勧めています

**詳細解説**

「big ball of mud」は、Brian Foote と Joseph Yoder が1990年代後半に書いた論文の言葉です。時間もお金も専門知識も足りないなかで、とにかく動くものを作った結果できあがる、場当たり的なシステムを指します。NN/g は、技術的な背景が少ないまま AI と一緒に仕組みを作る人たちを「vibe architects」と呼んで調査しました。その結果、AI のおかげで作る手間がほぼなくなった分、優先順位をつける理由もなくなり、むしろ作りすぎてしまう様子が見えてきたといいます。

実例が具体的で、読んでいて耳が痛くなります。Asana の進捗を見せる小さなウィジェットが、ダッシュボードを足し、完了日の予測や経理向けの時間記録まで抱えた部署横断ツールに育った例。AI のデスクトップアプリが落ちてチャット履歴が消えたので、ゴミ箱からファイルを拾って Downloads フォルダに置き、以後そこで作業を続けている例。「to be synthesized」という名前のフォルダに記事をため込み、AI が違う記事を拾ってきたせいで45分を指示の修正に使った例もあります。重要なファイルの場所を本人が答えられず、AI に探してもらう場面も何度もあったそうです。

作り直しのきっかけは3つにまとめられています。システムが用途に合わなくなったとき、作った本人でさえ全体を把握できなくなったとき、もっと良いやり方が見つかったときです。そのうえで、「仕組みの動きを変えたいとき、コンテキストのどこを直せばいいか分かるか」という問いを判断の目安にしています。分かるなら小さな改修で足ります。分からないなら、AI だけが道案内できる状態になっているということです。

UXエンジニアリングの視点では、CLAUDE.md やスキル、ルールファイルを育てている人にとって、そのまま点検リストとして使える内容です。「全体に効くグローバルなコンテキストは、一度に通して読める長さに保つ」「変更を頼むときは、どの種類のコンテキストを直すのかを指定する」といった習慣は、明日からでも試せます。調査対象はおもに個人で使う仕組みなので、チームで共有するコンテキストの運用まではまだ踏み込んでいません。その点は、後述する LayerX の LLM Wiki の記事と合わせて読むと補えます。

> 🐈‍⬛ : 「仕組みの動きを変えたいとき、コンテキストのどこを直せばいいか分かるか」という問いは、CLAUDE.md を育てている人なら一度は自分に向けてみたくなります。以前紹介した、CLAUDE.md には半減期があるという棚卸しの記事とも同じ方向の話です。作り直すこと自体を失敗として扱っていないところも、読んでいて気が楽になります。

## [Do frameworks matter anymore?](https://brookslybrand.com/posts/do-frameworks-matter-anymore/)

> **出典**: Sidebar | **公開日**: 2026-10-02 | **カテゴリ**: design

**3行まとめ**
- Remix チームで3年間フレームワーク開発に関わってきた Brooks Lybrand さんが、エージェントがコードを書く時代にフレームワークはまだ意味があるのかを考えたエッセイです
- 「フロントエンドのコードはもう気にしなくていい、だから React でいい」という意見の矛盾を突き、フレームワークを使わなくてもエージェントが勝手に「暗黙のフレームワーク」を作るだけだと指摘しています
- フレームワークの価値を「抽象・構造・制約」と定義し、エージェントと一緒に作るときこそ、その3つが効くと結論づけています

**詳細解説**

最近よく聞く意見に、こんなものがあります。「モデルが十分に賢くなったのでコードの中身は気にしなくていい。React は学習データが多いのでモデルも得意だ。だから React 以外を試す理由はない」。著者は、コードを気にしないのなら React すら要らないのでは、と問い返します。フレームワークが意味を持たないなら React を使う理由もないし、React が有利なのならフレームワークには意味がある、という二択の整理がわかりやすいです。

おもしろいのは「フレームワークを使っていない人も、実はフレームワークを使っている」という指摘です。React Conf 2024 で Ricky Hanlon さんが言った「フレームワークを使うか、自分で作るかのどちらかだ」を引きつつ、いまは作るほうが簡単になったと述べています。フレームワークなしで LLM にサイトを作らせると、LLM は関数やクラスを組み立てるのと同じ調子で、自前のフレームワークを作ってしまいます。著者はこれを「片付けをしないまま機能を足していくこと」と呼び、昔から人間がやってきたことで、速くなっただけだと見ています。

開発体験（DX）の個別の評価も実感がこもっています。HMR（ホットモジュールリプレースメント）は、エージェントと作業するようになってからむしろ役立っているそうです。TypeScript は、補完で自分がメソッドを探す用途としてはもう要らないけれど、型の制約が LLM の修正を安定させるので引き続き価値があるといいます。一方で `useEffect` は、自分では使いこなせていたけれど LLM に扱わせるのは不安だとしています。同じ道具でも「人間にとっての価値」と「エージェントにとっての価値」が分かれる、という見方が参考になります。

UXエンジニアリングの視点では、「正しいやり方が明らかで、抜け道は使えるけれど普段は要らず、使ったら人にも機械にも分かる」という制約の考え方が、そのままデザインシステムにも当てはまります。著者が求めているのは、Web 標準に沿ったフルスタックのフレームワークで、ドキュメントが `node_modules` の中にあってエージェントがすぐ読めるものです。エージェント向けのフレームワークを客観的に評価する方法はまだない、と認めている点も誠実です。

> 🐈‍⬛ : NN/g の泥団子の話を、フレームワークの側から見るとこうなる、という記事です。「片付けをしないまま機能を足していく」という言い方が、そのまま重なります。TypeScript は人間には要らなくなっても LLM には効く、という分け方は、ほかの道具を見直すときにも使えそうです。

## [LLM Wikiの組織運用に向けて ── 陳腐化を防ぐ更新の仕組み](https://tech.layerx.co.jp/entry/enterprise-llm-wiki-ops)

> **出典**: LayerX エンジニアブログ | **公開日**: 2026-10-05 | **カテゴリ**: engineering

**3行まとめ**
- 設計仕様書・ヘルプ記事・コードの3つに分かれたプロダクト仕様を突き合わせ、LLM が書き育てる「LLM Wiki」に1か所でまとめた事例です
- 毎日の差分ごとに「利用者が訊きそうな質問」を1つ書かせ、質問を書けない変更は捨てることで、LLM が読む量をしぼっています
- 出典のハッシュで古いページを機械的に検出して lint で止める仕組みと、回答の書き戻しを一時置き場に通す仕組みで、正しさと一貫性を保っています

**詳細解説**

LLM Wiki は Andrej Karpathy さんが提唱した知識管理のパターンです。人ではなく LLM が一次情報を読んで wiki を書き、質問に答えるたびに wiki を育てます。バクラクでは、仕様の答えを探す先が Notion の設計仕様書、Zendesk のヘルプ記事、GitHub のコードの3つに分かれ、しかも食い違うことがよくありました。そのまま LLM に渡してもどれが正しいか判断できないので、渡す前に整理しておこうという発想です。1プロダクトあたり100ページ前後、全体では1,000ページを超える見込みだそうです。

いちばんの工夫は、差分の選び方です。直近のリリースには2,000件を超える Pull Request が含まれていて、1件ずつ LLM に読ませると費用がかさみます。そこで判断の起点を「出典の何が変わったか」から「利用者の質問への答えが変わるか」に移しました。差分ごとに想定質問を書かせ、書けないもの（内部の整理や誤字の修正など）はその場で捨てます。書けたものは今の wiki で答えさせ、更新後の出典と食い違ったときだけ直します。

ただし、この選別は LLM の判断に頼っているので、根拠が変わったのに「答えは変わらない」と見逃される可能性が残ります。そこで各ページに根拠とした出典とそのハッシュを記録し、出典が変わったページを機械的に「古い」と判定します。ページ A を直すと A を根拠にしたページ B も古いと判定される、というように上流から順に伝わっていきます。この照合は lint として実装し、古いページが1件でも残っていれば push できないようにしました。LLM の判断と機械的な検出を二重にかけているところが、組織で使う仕組みらしい設計です。

UXエンジニアリングの視点では、書き戻しの扱いが参考になります。利用者がそれぞれのエージェントから直接 wiki を書き換えると、人やエージェントの癖でだんだん書き方がばらばらになります。そこで回答は一時置き場にだけ残し、別のエージェントが出典と突き合わせてから本体に昇格させます。確認前の回答は次の回答の根拠に使わない、というルールも、誤りが広がるのを防ぐうえで大事な点です。今後は Slack の議論や問い合わせも取り込みたいものの、閲覧権限の違いをどう扱うかが課題として残っています。

> 🐈‍⬛ : 「質問を書けない変更は捨てる」という選び方がよくできていると思います。変更を利用者の言葉に置き換えられるかどうかで価値を測っていて、リリースノートを書くときの考え方にも近いです。LLM の判断の後ろに、ハッシュによる機械的な検出をもう一段置いているところも、組織で回すための現実的な落としどころですね。

## [cognee CEOの講演で聞いたナレッジグラフの話 ── エージェントの記憶は「増える」から「良くなる」へ](https://tech.layerx.co.jp/entry/cognee-kg)

> **出典**: LayerX エンジニアブログ | **公開日**: 2026-10-05 | **カテゴリ**: engineering

**3行まとめ**
- AI エージェントの記憶をナレッジグラフ（KG）として提供する cognee の CEO の講演内容と、実際に cognee を試した結果をまとめた記事です
- 講演の要点は「厳密なオントロジーではなくゆるいスキーマで始める」「記憶をエージェント・会社・個人に分けて権限で制御する」「訂正してもデータは消さず、つながりの重みを変える」の3つです
- LayerX のブログ50記事で試したところ、スキーマを決めるとエンティティの種類が43から3に、関係名が214から4にまとまり、検索の答えも正確になりました

**詳細解説**

講演は、Neo4j が主催した「Context Graph」がテーマのミートアップで行われました。ログには「何が起きたか」しか残りませんが、判断の理由や因果関係までグラフで残せば「なぜ起きたか」もたどれる、という問題意識です。cognee はエージェントの実行履歴も、RDB や Google Drive、Notion、Slack のデータも、埋め込みを持つ1つのグラフにまとめます。API は `remember()`、`recall()`、`improve()`、`forget()` の4つです。

講演でもっとも強調されたのは「記憶は増えるだけでなく良くなるべき」という点です。たとえば「A さんは3月にベルリン、7月からサンフランシスコ」という記憶があるのに、8月に「今どこ？」と聞かれてベルリンと答えてしまったとします。訂正を受けると、今の居場所はサンフランシスコと答えるようになりますが、ベルリンの記憶は消えず、「3月はどこ？」には正しく答えます。不確かなエージェントの判断でデータを消さず、消すのは人が明示的に指示したときだけ、という役割分担がわかりやすいです。

後半の検証が具体的で参考になります。タイトル・公開日・概要だけの50記事を、スキーマなしで取り込むと47秒かかり、エンティティは404個、関係名は214種類（うち151種類は1回しか使われない）にふくらみました。「ai agent」と「aiエージェント」が別のノードになるような表記ゆれも起きています。「記事・技術・イベント」の3種類だけのスキーマを Python のクラスで書き、関係名を `Literal` で固定すると、29秒でエンティティ100個、関係名4種類にまとまりました。「Snowflake の記事のうち、イベントのレポートではないものは？」という質問にも、スキーマありでは4本すべてを挙げ、なしでは1本だけでした。

UXエンジニアリングの視点では、「数えたい・まとめたい単位をスキーマにする」というコツが、コンテンツの情報設計そのものだと感じます。プロンプトでイベント名を「略称 年」にそろえるよう指示したのも、1回目の結果で表記ゆれを見つけてから足したものです。小さく始めて結果を見ながら直す、という進め方は KG に限らず使えます。なお、`improve()` による「良くなる」記憶の効果はこの記事では試されていないので、講演の主張としての紹介にとどまる点は注意して読むとよいでしょう。

> 🐈‍⬛ : スキーマなしでは関係名が214種類にふくらみ、型を3つ決めるだけで4種類にまとまる、という結果がわかりやすいです。LLM Wiki の記事と同じく、LLM に任せる前に構造を少しだけ決めておくと、あとの片付けがずっと楽になります。ベルリンの記憶を消さずに重みを変える、という訂正の扱い方も個人的に好きです。

## [Blume](https://useblume.dev/)

> **出典**: Sidebar | **公開日**: 2026-10-02 | **カテゴリ**: design

**3行まとめ**
- Hayden Bleasel さんが作った、オープンソースのドキュメントサイト用フレームワークで、「エージェントも読者として扱う」ことを前面に出しています
- すべてのページに Markdown 版を用意し、`.md` の URL や `Accept: text/markdown` での取得、`llms.txt` と `llms-full.txt` の自動生成、オプトインの MCP サーバーなどを標準で備えています
- ローカルの Markdown や MDX に加え、別の GitHub リポジトリ、Notion や Sanity などのヘッドレス CMS、Obsidian の保管庫からも内容を取り込めます

**詳細解説**

「1つのページに、2種類の読者」という見出しが、このフレームワークの考え方をよく表しています。人間向けの HTML とは別に、エージェント向けの Markdown を同じ URL 体系で返すので、コーディングエージェントがドキュメントを読むときに HTML から本文を抜き出す手間がかかりません。Vercel や Cloudflare のサーバービルドでは、`Accept` ヘッダーで Markdown を返し分けられます。エージェント向けのスキルを、エージェントが探しにいく場所に公開する機能もあります。

書き手向けの機能もそろっています。`:::tip` や `:::warning` のような記法がそのまま注意書きのブロックになり、`package-install` のコードブロックは npm、pnpm、yarn、bun などのインストールコマンドをタブで切り替えて表示します。コードのハイライトは Shiki でビルド時に処理し、KaTeX の数式もビルド時にレンダリングするのでクライアントの JavaScript が要りません。Mermaid の図は、図を使うページでだけ読み込まれます。

エージェント対応の度合いを測る外部サービス2つで、Mintlify や Fumadocs より高い点数が出たことも紹介されています（2026/09/20時点、is-agentic.com と isitagentready.com による）。Mintlify から移行するガイドも用意されていて、リポジトリをコーディングエージェントに渡し、変更内容を確認しながら URL を保ったまま移す流れが書かれています。

UXエンジニアリングの視点では、ドキュメントの「読者」にエージェントが加わったことで、情報設計の考え方が変わりつつあることがよくわかる例です。社内のデザインシステムのドキュメントでも、Markdown 版や `llms.txt` を用意しておくと、エージェントに正しい使い方を伝えやすくなります。ただし紹介ページは製品自身のサイトで、点数の比較も自己申告なので、実際の使い勝手は試して判断するのがよいでしょう。

> 🐈‍⬛ : 同じ URL で人には HTML を、エージェントには Markdown を返すのは、フレームワークの記事が求めていた「エージェントがすぐ読めるドキュメント」を、ドキュメントの側から用意する発想です。社内のデザインシステムのドキュメントでも、まずは `llms.txt` を置くところから試せそうです。

## [Modern web types](https://philipwalton.com/articles/modern-web-types/)

> **出典**: Sidebar | **公開日**: 2026-10-02 | **カテゴリ**: design

**3行まとめ**
- TypeScript 標準の DOM 型は「2つ以上のブラウザエンジンで実装された API」しか含まないため、要素スコープの View Transition や Long Animation Frame、`fetchLater()` などで型エラーが出ます
- Philip Walton さんが作った `modern-web-types` は、同じ公式の生成ツールを使いつつ基準を「1エンジン」に下げた、DOM と WebWorker の型の置き換え用ライブラリです
- 既存のインターフェースに足りなかったメンバーだけでも DOM で311個あり、`Document` や `Element` のような毎日使う型にも抜けがあったことがわかります

**詳細解説**

Chrome で使えて、プログレッシブエンハンスメントとして安全に使える API なのに、TypeScript ではエラー扱いになる。この不満は、新しい Web 機能を試したことがある人なら覚えがあるはずです。原因は TypeScript-DOM-lib-generator の方針で、2つ以上のエンジンで実装された API しか型に含めないと決めています。著者は長年、型を手で書いてプロジェクトごとにコピーしてきましたが、それに疲れてこのライブラリを作りました。

使い方は短く、`npm install --save-dev @typescript/lib-dom@npm:modern-web-types` で TypeScript が DOM ライブラリとして探す名前に別名でインストールします。TypeScript 6 以降では `tsconfig.json` で `libReplacement: true` を設定する必要があります。生成には TypeScript 本体と同じ生成ツールと w3c/webref のデータを使い、GitHub Actions で毎週更新を確認して差分があれば PR を作る仕組みになっています。手作業で保守するライブラリではないので、置いていかれにくいのが安心できる点です。

「2エンジン基準は、まだ使えない機能から守ってくれているのでは」という疑問にも答えています。著者の考えでは、2エンジンで動いても無条件には使えない API もあれば、1エンジンでも段階的に使って問題ない API もあります。`LargestContentfulPaint` や `LayoutShift`、`fetchpriority` も最初は Chrome だけでしたが、多くのサイトが使ったことで Web 全体が速くなりました。型がないと `@ts-ignore` や `as any` で済ませる人が増え、かえって危ない、という指摘には説得力があります。

> 🐈‍⬛ : 型がないと `as any` で済ませる人が増えてかえって危ない、という指摘はその通りだと思います。手で保守せず、公式と同じ生成ツールで毎週追いかける作りになっているのも安心できます。型が通ることと動くことは分けて考え、機能検出や Baseline の lint と組み合わせて使いたいライブラリです。

UXエンジニアリングの視点では、パフォーマンス改善のような地味な作業が「とても大事で、とても退屈」で、自分ひとりではそこが限界になる、という気づきが現実的です。たくさん作れるようになったことで、かえって他の人の専門性が必要な場所がはっきり見えてきた、という話は、AI 時代のチームの組み方を考えるヒントになります。最後の「アイデアを放っておいても、午後を無駄にしたと感じない自分でいたい」という一文も、多くの人に響くはずです。

> 🐈‍⬛ : 「以前なら喜んで止めていた地点が、今は足りないものに気づく地点になっている」という話が、今週の最初の泥団子の記事に戻ってきます。品質が上がっているのか、できるから広げているだけなのか、作っている最中には区別がつきにくいと正直に書いているのがいいです。エージェントに作ったものを説明させて、自分が責任を持つコードを理解しておく習慣は、真似しやすそうです。
