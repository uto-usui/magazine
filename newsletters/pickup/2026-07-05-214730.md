## [The problem is prompt debt](https://www.dbreunig.com/2026/06/22/the-problem-is-prompt-debt.html)

> **出典**: Sidebar | **公開日**: 2026-06-30 | **カテゴリ**: design

**3行まとめ**
- 自然言語プロンプトは工学的な仕様言語ではなく、信頼できるシステムを組む土台としては弱いという指摘です
- プロトタイプは1日でできても「prompt debt（プロンプトの負債）」が通常の進捗に紛れてゆっくり積み上がり、やがてアプリが動かなくなると論じています
- 対策は挙動を散文でなく評価で規定すること、そしてプロンプトを手書きせず探索・生成するものへ移すことの2点です

プロンプトを書き足して振る舞いを整えていく作業は、最初のうちは順調に見えます。この記事はそこに潜む負債を「prompt debt」と名づけ、症状を3つに整理しています。エッジケースに対応するたびに指示を足し、その修正が過去の指示を退行させてイテレーションが鈍る。プロンプトが同僚には解読できなくなりチームが機能しなくなる。特定モデルへのロックインが起き、GPT-4oで直した挙動がGPT-5.4-miniで新たに壊れる。どれも実務で覚えのある痛みです。

具体例が生々しく、Fableのシステムプロンプトは著作権ガイダンスを最大6回、Claude Codeは「1レスポンスで複数ツールを返せ」を7回、ChatGPTの画像プロンプトは「画像返却時に返信するな」を8回繰り返しているといいます。著者はこれを「fighting the weights（重みと戦う）」と表現し、欲しい挙動がモデルの訓練内容と食い違うほど、同じことを言い換えて何度も指示する必要が出てくる構図を描きます。

UXエンジニアリングの視点で読むと、この記事はAI機能づくりの投資先を問い直す材料になります。UIコピーを詰めるように言葉のニュアンスを職人的に調整するのではなく、望ましい振る舞いを測定可能に定義するほうへ軸足を移す、という提案です。アセンブラからコンパイラへ、手書きクエリからプランナへ、と同じ流れがプロンプトにも来る、という見立ても腑に落ちます。

> 🐈‍⬛ : 「散文ではなく評価で規定せよ」という処方は、前回の「Access is not mastery」で語られた「基準を持つ側の価値」と直結する。プロンプトを職人的に磨く時間を、そのままevalを設計する時間に振り替えられるか、という個人単位の投資判断にも読める。

## [The Prompt Is the New Brief](https://uxmag.com/articles/the-prompt-is-the-new-brief)

> **出典**: UX Magazine | **公開日**: 2026-06-30 | **カテゴリ**: ux-research

**3行まとめ**
- プロンプティングは新しいスキルではなく、デザイナーが長年培ってきた「ブリーフを書く力」を新しい表面に応用したものだという主張です
- 良いプロンプトは Role / Situation / Task / Constraints / Evaluation criteria の5要素で構成でき、なかでも成功基準の定義がもっとも重要で見落とされやすいと説きます
- 「prompt engineering」という技術的な呼び名が主導権を技術職に渡し、本来UXが担うべき領域を過小活用させる危険を指摘しています

UX×AIシリーズのPart 2で、中心の命題は「プロンプトは新しいブリーフである」というものです。良いブリーフと良いプロンプトの共通点を、goal（作るものではなく達成したい成果）、audience（具体的な対象像）、constraints（形式・長さ・トーンなどの制約）、context（AIは記憶を持たないため毎回の文脈設定が必要）の4要素で整理します。デザイナーが日常的にやってきた「明確で具体的で文脈豊かなコミュニケーション」がそのまま通用する、という見立てです。

実践的な型として提示されるのが5要素です。具体的な専門役割を与えるRole、AIが持たない文脈を渡すSituation、形式や構造まで指定するTask、境界を明示するConstraints、そして「良い」の定義を与えるEvaluation criteria。最後の評価基準はもっとも使われていないのにもっとも効く、と強調されています。前記事の「prompt debt」が「評価で挙動を規定せよ」と説いていたことと、この記事の「評価基準がもっとも重要」という指摘は、きれいに重なります。

UXエンジニアリングの視点で読むと、システムプロンプトやAIワークフローの設計を「実装後の見た目調整」ではなく上流の設計課題として捉え直す根拠になります。Role / Situation / Task / Constraints / Evaluation という型は、日々のプロンプト設計にそのまま持ち込めます。

> 🐈‍⬛ : 「prompt engineering」を技術用語にすると主導権が技術職に渡る、という指摘は職能の境界に関わる重要な観察。ブリーフの5要素は、いま自分がAIに投げている一行に足りない項目を炙り出すチェックリストとしても使える。

## [39 principles for designing human-AI interaction](https://uxdesign.cc/39-principles-for-designing-human-ai-interaction-87be5fabdbbe)

> **出典**: Sidebar | **公開日**: 2026-07-02 | **カテゴリ**: design

**3行まとめ**
- Microsoft の18ガイドラインや Google PAIR、OpenAI Model Spec、Anthropic の Constitution など、人間とAIのインタラクション研究を39の実践的なデザイン原則に統合した応用フレームワークです
- 「確率的基盤」「期待値の設定」「較正された信頼」「透明性」「コントロールと主体性」など9つのカテゴリで、AIへの適切な依存を支える設計を体系化しています
- 信頼スコアより出典の提示を優先する、追従（sycophancy）ではなく誠実な反論を設計する、といった直感に反する原則も研究の裏付きで示されます

従来のインターフェイスは予測可能な振る舞いを前提に作られてきましたが、AIシステムは同じ入力から異なる出力を返す確率的な性質を持ちます。この記事は「ユーザーがAIに適切に依存できるようにするには」という問いを中心に、散在する研究や仕様書を製品レベルで使える39原則にまとめたものです。Horvitz の mixed-initiative 研究のような古典から、OpenAI Model Spec や Anthropic の Constitution といった最新のモデル仕様まで参照範囲が広く、リファレンスとしての密度が高い内容になっています。

興味深いのは、確信度スコアより出典（provenance)を優先する原則です。研究によれば、意味のない数値であっても確信度の表示は誤答への信頼を高めてしまうため、スコアの代わりにソースの引用や変更差分など「検証できる証拠」を見せるほうがよいとされます。また sycophancy（追従）を設計で防ぐ原則では、モデルは異議を唱えられると最大98%のケースで正答を誤答に変えてしまうという研究を引き、誠実な反論をインターフェイスの機能として組み込む必要性を説きます。

UXエンジニアリングの視点では、これらの原則の多くが実装の設計判断に直結する点が重要です。「検証を一瞥で済むコストにする」には差分表示やインライン引用のUIが必要ですし、「マルチステップの作業には計画とトレースを見せる」はエージェント型UIの進捗設計そのものです。Copilot の Tab/Esc のように受け入れより拒否を軽くするインタラクション設計など、フロントエンド実装者が今日から使える指針が多く含まれます。

> 🐈‍⬛ : 「信頼スコアより出典」「追従より誠実な反論」といった直感に反する原則が、研究の裏付きで並んでいるのが良い。手元のAI機能に対して「うちの製品はどう選んでいるか」と当ててみると、無意識に採用しているデフォルトの偏りが浮き出てくる。

## [Matching AI Modality To User Intent: Designing The Right Interface](https://smashingmagazine.com/2026/07/matching-ai-modality-user-intent-designing-right-interface/)

> **出典**: Smashing Magazine | **公開日**: 2026-07-02 | **カテゴリ**: design

**3行まとめ**
- LLMが対話データで訓練されているからといって、あらゆるAI機能をチャットUIにする「会話型トンネルビジョン」に警鐘を鳴らす記事です
- 入力・出力それぞれのモダリティ（ボタン、音声、フォーム、ダッシュボード、キャンバスなど）を、ユーザーの文脈・意図・認知負荷に合わせて選ぶ方法を提示します
- Task Audit と Input/Output Alignment Matrix という2つの実務ツールで、モダリティ選定を推測ではなく証拠ベースにする手順を解説しています

空港を走りながらゲート変更を調べる旅行者に、長いチャット入力と密度の高いテキスト回答を強いるAIアシスタントの例から記事は始まります。入力面では、空白のチャットボックスは機能の発見可能性を奪い、ユーザーに「曖昧な思考を具体的な命令文へ翻訳する」という言語的コストを課します。出力面では、テキストは逐次的にしか読めないため、チャートなら1秒で把握できるパターン認識を読解作業に変えてしまいます。

記事の中核は、入力7種・出力6種のモダリティ分類表と、それを選定に落とし込む Task Audit の手順です。「手は使えるか」「画面を見られるか」「音を出せる環境か」「すでにどれだけ認知負荷がかかっているか」という4つの制約を、コンテキスチュアルインクワイアリーやインタビューで確かめ、ユーザーの意図ごとに最適な入出力の組み合わせをマトリクスで決めていきます。

UXエンジニアリングの視点で読むと、これはAI機能の実装アーキテクチャに直接響く話です。チャットを前提にすると会話履歴やストリーミング表示の実装に工数が向かいますが、意図が「ステータス確認」ならプッシュ通知とバッジで済み、「複雑な分析」ならフィルタUIとダッシュボードが正解かもしれません。どのモダリティを選ぶかでコンポーネント設計もAPI設計も変わるため、実装前の監査プロセスとして取り入れる価値があります。

> 🐈‍⬛ : 「AI機能＝チャット窓」を疑うところから始めるだけで、要件定義の入り口がひとつ増える。前記事「39 principles」の原則3を、実装者が使える手順に翻訳したガイドとして読むと相性がいい。

## [You can't unit test for taste](https://dev.karltryggvason.com/you-cant-unit-test-for-taste/)

> **出典**: Sidebar | **公開日**: 2026-06-30 | **カテゴリ**: design

**3行まとめ**
- ランニングアプリに「見どころ」を追加する開発で、当初はAIを機能の中核に据えたが最終的に脇役に落ち着いた記録です
- ハルシネーションが多発し、要約テキスト生成はWikipedia要約に戻すなど、決定論的なデータ処理へ役割を戻しています
- 一方でLLMは「重み付けに潜む主観的なtaste」を提供する評価者としては採用し、役割分担を明確にしています

Strava の走行距離を世界の有名ルート踏破に見立てるアプリに、地図上の見どころ（POI）を追加する開発記です。当初は「AIが機能の中核」と考えていたものの、最終的にAIは他のデータ処理を補助する脇役に落ち着いた、という発想の転換がこの記事の読みどころです。データ源はGeoNamesで、PythonでParquetに保存しDuckDBをクエリ層に使い、約1,300万行を約72.5万行まで絞り込んでいます。

ハルシネーションの具体例が教訓的です。Decatur, Illinois の Central Park をマンハッタンの同名公園と誤認したり、都市の人口や山の高さを改変したり。位置や行政メタデータでグラウンディングしても残ったため、要約テキストの生成はWikipedia要約に戻したといいます。「正確さのほうが読みやすさより大事」という判断です。使ったのは Anthropic の Haiku で、tool use とバッチ処理により大きなルートで約$10、数時間かかったとのこと。

ではLLMをどこで活かしたか。Wikidataの言語版数だけを知名度シグナルにすると、自動翻訳で150言語に記事がある小さな町が過大評価されてしまう。そこでLLMの主観スコアで「面白い」POIを持ち上げる評価者として採用しました。決定論的なデータ処理とLLMの主観的なスコアリングを役割分担させる、という設計判断が鮮やかです。

> 🐈‍⬛ : 「LLMを中核から脇役へ」という設計判断の後退が、そのまま製品品質の前進になっている構図がいい。tasteのように red / green を書けない対象にこそLLMを寄せる、という切り分けは、次回AI機能を組むときの初手として使える。

## [The organizational cost of low taste](https://uxdesign.cc/the-organizational-cost-of-low-taste-135cb8b10c34)

> **出典**: Sidebar | **公開日**: 2026-07-01 | **カテゴリ**: design

**3行まとめ**
- 組織は戦略ではなく意思決定で失敗する、tasteが弱いと機能不全に陥る、という骨太な組織論です
- 「Taste is the standard. Judgment is the act of applying it.（tasteは基準、judgmentはそれを適用する行為）」という定義を軸にします
- AIで生産がボトルネックでなくなるほど、選ぶ力・捨てる力の価値が上がると論じます

組織の機能不全は従来「スケーリング問題」と説明されてきました。しかし50人のスタートアップが50倍規模の組織と同じ意思決定の麻痺を示す以上、スケールでは説明がつかない、と著者は指摘します。真の変数は「品質を認識する安定した方法を失うこと」だという見立てです。基準が共有されていれば、多くの選択肢は議論に到達する前に静かに除外されます。

Dieter Rams の功績を「視覚的な一貫性」ではなく「組織横断で共有された判断」に見出す読み解きが鋭いです。Herbert Simon の限定合理性を引き、意思決定の質は評価能力の拡大ではなく評価する選択肢の削減で上がると説きます。基準が弱いと選択肢が長く残り、関係者が増え、ボトルネックが「実行」から「選択」へ移る。やがて「何が良いか」が「何が支持されるか」に静かに置き換わり、政治が根本原因ではなく適応として現れる、という描写が生々しいです。

Christopher Alexander の都市論を引いた複雑性の議論も納得感があります。除去は追加より難しいため「これは存在してよいか」が「これは正当化できるか」に変わり、常に追加が勝つ。複雑性は野心の産物ではなく、時間をかけた弱いフィルタリングの結果だといいます。前掲の「You can't unit test for taste」が個人の設計判断としてtasteを論じたのに対し、この記事は組織のスケールでtasteを論じます。デザインシステムやガイドラインを「圧縮装置」として捉え直すと、その意味がよく見えてきます。

> 🐈‍⬛ : 「tasteは基準、judgmentはそれを適用する行為」という切り分けが効いている。デザインシステムのレビュー会議で議論が長引くとき、実は基準がぶれているのか、適用の判断がずれているのか、を分けて話すだけでも会話の質が上がる。

## [Legibility of effort](https://eieio.games/blog/legibility-of-effort/)

> **出典**: Sidebar | **公開日**: 2026-07-03 | **カテゴリ**: design

**3行まとめ**
- LLMによって「かけた労力を他者に伝える」ことが難しくなった——この現象を「努力の可読性（legibility of effort）」の喪失として論じるエッセイです
- tldraw が外部からのPRを自動クローズし始めた例など、労力を一瞥で見分けるヒューリスティックの崩壊がオープンソースの仕組みを揺らしています
- レコード収集ブームと同じように、あえて摩擦を再導入して人間らしさを伝える文化が生まれつつあると観察します

「誰かがこれに時間をかけた」は「これは読む価値がある」の代理指標でした。もっともらしいテキストやWebサイトの生成が自明になった今、この代理指標は壊れています。筆者は Flappy Bird を macOS の Finder 内で動かした自作プロジェクトを引き合いに、その喜びが「無用さ」だけでなく「明らかに手間がかかっていること」に由来していたと振り返り、労力を可視化できなくなった今、創作の動機自体が揺らいでいると率直に書きます。

一方で、vibecoding された Web サイトに共通する「デフォルト Claude スタイル」——クリーム色の背景、サンセリフのヒーローテキスト、アクセント色の一語——が新しい低努力のシグナルとして読まれている、という観察は鋭いところです。良い作品を作るには依然として大量の意思決定が必要で、それは今も難しい。しかし努力の証明が難しくなったことで、ハードウェアや筋トレやスポーツのような「今もごまかせない領域」へ人々の関心が移っている、と筆者は自らの変化も含めて記します。

UXエンジニアリングの視点では、これは「作ったものの見た目から込めた意図が読み取れるか」という問題です。AIの支援でUIの初期生成が容易になるほど、細部のタイポグラフィ、状態遷移の丁寧さ、エッジケースの扱いといった「意思決定の痕跡」こそが品質のシグナルになります。メールにあえてタイポを残す冗談や、意図的に不格好なサイトのほうが面白いという逆説は、デザインにおける「人間の署名」をどう設計するかという新しい問いを開いています。

> 🐈‍⬛ : 「organizational cost of low taste」が組織側の基準の話だったのに対し、こちらは受け手側の読み取り能力の話。tasteは作り手・受け手の両側で摩耗しうる、という前提でデザインシステムを眺めると、「圧縮装置」の設計がまた違って見えてくる。

## [On the semantic web](https://karlkoch.me/writing/on-the-semantic-web)

> **出典**: Sidebar | **公開日**: 2026-07-02 | **カテゴリ**: design

**3行まとめ**
- 「インターフェイスを保守しづらくする最短の方法は、ブラウザを下手に再実装すること」——セマンティックHTMLをインターフェイスの基盤として捉え直す記事です
- `div` にrole・tabIndex・キーハンドラを継ぎ足した「偽ボタン」と、ネイティブの `button` が持つ挙動の契約を対比して示します
- スタイルは流行で変わってもセマンティクスは長持ちするため、大規模開発ほどネイティブ要素から始める価値があると説きます

クリックハンドラ付きの `div` は、CSSが当たれば見た目はボタンになります。しかしフォーカスできず、Enter も Space も効かず、フォームも送信できず、支援技術にも伝わりません。そこで role、tabIndex、aria-disabled、キーダウンリスナーと修繕が始まりますが、筆者はこれを「より良いボタンを設計したのではなく、より悪いボタンに家賃を払い始めた」と表現します。ネイティブの `button` なら、タブ順序、キーボード操作、無効化、フォーム参加のすべてをブラウザが引き受けてくれます。

記事はボタンにとどまらず、`details`/`summary` による開閉UI、`label` と `input` の関連づけ、`type`・`autocomplete`・`required` が担う挙動まで、同じ構図を丁寧に展開します。重要なのは「ネイティブ＝ブラウザのデフォルトの見た目」ではない点です。スタイリングは完全にカスタムでよく、受け入れるのはブラウザの「インタラクションの契約」だけ。「どのネイティブ挙動をスタイリング後も生き残らせるか」がデザインエンジニアリングの問いだと述べます。

UXエンジニアリングの視点では、「セマンティクスはスタイリングより長持ちする」という指摘がデザインシステム運用の実感と重なります。角丸やグラデーションは流行で入れ替わりますが、ナビゲーションのランドマークやフォームコントロールの意味は再設計後も変わりません。カスタムコンポーネントを否定するのではなく「ネイティブの契約を使い尽くしてから作る」という優先順位は、コンポーネントライブラリのレビュー基準としてそのまま使えます。

> 🐈‍⬛ : 前回の「壊れにくいテストコード」でも、セマンティクスが支援技術・テスト・AIの3方向に効くという話があった。今回の「契約」という言葉で見直すと、`button` を選ぶことは実装をブラウザに委任する契約書に署名しているのと同じで、その委任先の重みが伝わってくる。

## [Building accessibility into a canvas-based product](https://www.figma.com/blog/building-accessibility-into-a-canvas-based-product/)

> **出典**: Figma Blog | **公開日**: 2026-07-01 | **カテゴリ**: design

**3行まとめ**
- Figmaのcanvasはビデオゲーム同様レンダリングを引き取るため、ブラウザ標準のアクセシビリティが一切効かないという課題から始まります
- 解決策として「Mirror DOM」と内部アクセシビリティツリー、選択とフォーカスの双方向同期、通知の4システムを構築しています
- 非DOMレンダリングでアクセシビリティを担保するための、実装リファレンスとして極めて実践的です

Figmaのcanvasは無限ズームやリアルタイムのマルチプレイヤーを実現する代わりに、HTML/DOMを使いません。そのためブラウザが無償で提供するアクセシビリティ機能が効かず、canvasはレイヤー数に関わらずフォーカスを持つ`<input>`が1つだけ、ブラウザのアクセシビリティツリーが実質空という状態でした。この課題に、Figmaは「ブラウザが無償で提供するものを自前で再構築する」という重い選択で応えています。

中核が「Mirror DOM」です。4つの協調するシステムで構成されます。全レイヤーのアクセシビリティ詳細をキャッシュし差分更新する内部アクセシビリティツリー、実際にDOM要素を挿入するMirror DOM の Reactコンポーネント、選択とフォーカスの双方向同期、そして編集など非ナビゲーションの変更を伝える通知システム。内部ツリーは「ブラウザが何を知るべきか」から逆算して構築され、初回はフル構築、以降は編集を監視して差分更新でリビルドを避けます。

実装判断で興味深いのは、通常のvisually-hidden手法を使わず、要素を実際にレイアウトする点です。Figmaでは空間的な配置が意味に直結するため、スクリーンマグニファイアのパンや音声制御の画面キューに位置情報が要る。各レイヤーのaffine transformを連結し、CSSで回転やスキューまで含めて配置しています。編集通知はARIAのlive regionを使い、1px×5回のnudgeを「Moved five pixels」1回にまとめるcoalescingで冗長さを抑えています。

> 🐈‍⬛ : 前記事「On the semantic web」がネイティブの契約を使い尽くす話だったのに対し、こちらは契約の外側でどう建て直すかの話。canvas製品でここまでの実装体力を投下している事実そのものが、アクセシビリティを機能ではなく能力として扱う姿勢を裏付けている。

## [プロダクトエンジニアによるSLO運用改善 —— 半年間の取り組みと学び](https://tech.smarthr.jp/entry/2026/07/02/100931)

> **出典**: SmartHR Tech Blog | **公開日**: 2026-07-02 | **カテゴリ**: design

**3行まとめ**
- SREの専門チームではなく、フィーチャーチームのプロダクトエンジニアがSLO運用改善を半年間担当した記録です
- 緩すぎて違反が出ないSLOを見直し、しきい値調整・新規CUJの追加・改善後の目標引き上げというサイクルを2周回しています
- New Relic のデータを Notion DB に蓄積する仕組みを Agent Skill 化し、SLOを個人芸からチームの週次議論の材料へ昇華させました

SmartHR のポータル開発ユニットでは、CUJ（Critical User Journey）に関わるAPIエンドポイントへ実測ベースのしきい値を設定してSLO運用を始めたものの、しきい値が緩すぎて違反がほとんど発生せず、改善につながらない状態が続いていました。担当となった筆者に期待されたのは違反を自分で直すことではなく「運用の仕組み化・体制づくり」でしたが、まず一度、違反の検知から原因特定、PMとの合意形成、実装・リリースまでをやり切ることから始めた、という順序が示唆的です。

改善の中身も具体的です。p85とp99の乖離が解消されたためp85の目標を廃止し、p99が9.3秒から2.2秒へ改善したのを受けて目標値を3.0秒に引き締める。別件の開発で気づいたパフォーマンス課題を新しいCUJとしてSLOに追加する。「SLOは一度設定したら固定するものではなく、プロダクトや実装の変化に合わせて見直し続けるもの」という学びが、実際のサイクルを2周した経験から語られます。エラーバジェットの推移をチームで眺め、「安定しているからしきい値を引き下げよう」「ボラティリティが大きいから調査しよう」という会話ができるようになったのは大きな前進です。

UXエンジニアリングの視点では、SLOは「体験の質を組織の共通言語にする装置」だと読めます。レイテンシのしきい値はユーザー体験の代理指標であり、CUJの選定はまさにUX上のクリティカルパスの特定です。信頼性改善を専門チームの仕事にせず、ユーザーにもっとも近いフィーチャーチームが担う意義——「ユーザーに近いからこそ気づける課題がある」——は、UXエンジニアという職能の存在意義とも重なります。

> 🐈‍⬛ : 「organizational cost of low taste」が基準の話だったのに対し、こちらは基準を数値で持ち込む実践編。CUJとしきい値をチームの共有語彙にできるかどうかで、体験改善が個人芸から仕組みへ移る境目が見える。

## [From Years of Client Work to a Next.js + Sanity Starter Kit](https://tympanus.net/codrops/2026/07/02/from-years-of-client-work-to-a-next-js-sanity-starter-kit/)

> **出典**: Codrops | **公開日**: 2026-07-02 | **カテゴリ**: design

**3行まとめ**
- ヘッドレスCMS案件の最初の3日を消費する「配管工事」を、年月をかけて1つのボイラープレートに畳み込んだ開発者のストーリーです
- キャッシュ境界やリンクフィールドの設計など「一度決めて二度と再交渉しない」判断の集合が、機能の山より価値があると論じます
- AGENTS.md とスコープ化されたスキルで規約をコーディングエージェントに渡し、実行のたびに設計が漂流するのを防ぐ構成が興味深い点です

CMS案件の初週はいつも同じ——ページビルダーのモデリング、SEO層の再構築、Webhook再検証の配線、4回目のコンタクトフォームのスタイリング。しかも「同じバグ」が案件をまたいで再発する。この繰り返しへの答えとして筆者が育ててきたのが、全クライアント案件の土台となるスターターキット「The Content Architecture」です。ステイルコンテンツ問題を引き起こしがちなフェッチ層は、本番ではCDNを切って Next.js の Data Cache とタグベースの再検証に載せ、開発時はCDNを使う——という判断が、理由のコメントごと単一のヘルパーに焼き込まれています。

この記事でもっとも今日的なのは、「決定済みの基盤」とコーディングエージェントの関係です。Claude Code や Cursor にゼロからヘッドレス構成を作らせると、実行のたびにもっともらしくも異なるアーキテクチャが出てきて、その漂流（drift）を人間が引き継ぐことになります。エージェントが間違っているのではなく「保持する意見を持たない」のが原因で、AGENTS.md とスキルで規約を渡せば、エージェントは毎回発明する代わりにアーキテクチャの内側で作業する。「構造は人間が持ち、タイピングはエージェントが担う」という分担です。

UXエンジニアリングの視点では、「アーキテクチャの一貫性はひとりの頭がそれを最初から最後まで保持していたから成立している」という主張が考えさせられます。委員会的な意思決定が設計の一貫性を削ることは経験的に知られていますが、AI協働時代にはこの「意見の一貫性」の価値がさらに上がるのかもしれません。エディタが迷わないStudio設計、レイアウトシフトを防ぐためにすべてのメディアが寸法を返す設計など、編集体験（editor experience）への目配りも、コンテンツサイトのUXを支える見えない仕事として参考になります。

> 🐈‍⬛ : 「構造は人間が持ち、タイピングはエージェントが担う」は、今週の通奏低音への実装解答になっている。prompt debtも、low tasteも、legibility of effortも、原因は「意見が薄いまま量を出せてしまうこと」に集約される。AGENTS.mdは、その意見を明文化しておく置き場所として機能する。
