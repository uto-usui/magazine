## [What happens when you can't hide behind craft](https://microsoft.design/articles/the-naked-designer-what-happens-when-you-cant-hide-behind-craft/)

> **出典**: Sidebar | **公開日**: 2026-08-07 | **カテゴリ**: design

**3行まとめ**
- 制作物の完成度が「この人は分かっている」を代弁してくれていた。その完成度が安くなったとき、代弁するものがなくなった
- AIが奪ったのではなく、AIが安くしたものによって露わになった。作ることが本気の証拠でなくなると、隠れる場所がなくなる
- 安くならなかったのは「選ぶこと」のほう。モデルは千の方向を生成できるが、どれが正しいかを気にかけることはできない

Microsoft Design に載った Matthew Santone のエッセイです。長いあいだ craft は身を隠す場所だった、という告白から始まります。皮肉ではありません。ピクセルは整い、タイポは締まっていた。その制作物が語ってくれるから、自分が語らなくて済んだ。「この人は分かっているのか」という問いに、成果物のほうが先に答えてくれていたのです。

そして実行のコストが落ちました。インターフェースを言葉で説明すれば現れ、会議と会議のあいだにアプリが1つ作れる。隠れていた部分がほぼ無料になったとき、残る問いは1つだけになります。自分には本当に言いたいことがあるのか。完成度が高かった時代、finish はシグナルでした。いまは磨きが無料で、無料のシグナルはシグナルではありません。

罠の描写が鋭いところです。露出を感じる前に覆いへ手が伸びる、というのです。覆いとは流暢さのことで、AIの答えを、それが間違っていても受け取り、より確信を持ってしまう。心理学でいう cognitive surrender です。何も言っていないのに、うまくやったと感じられてしまう。そこからの逃走は一方向に走ります。もっと作る。指揮者になれ、判断で信号と雑音を分けろ——それは知恵に聞こえるが、言いたいことがあるのかを問わずに済ませる許可証でもある、と。

中盤の軸は Poe の『構成の哲学』です。『大鴉』を後ろから設計したという有名なエッセイは、実際にはほとんど演技で、詩は他のすべてと同じように混沌のなかから生まれ、整然とした機械はあとから組み立てられたものでした。ただし、制御が嘘だったのであって、選択は本物だった。長い o の音の物悲しさのために「Nevermore」を選んだのは彼の耳です。安くならなかったのはこの部分だ、と結ばれます。

UXエンジニアリングの視点では、後半の「私的な焚き火」の節がもっとも刺さります。セラピストがくれた共有のワークシートを Claude Code に投げ、1時間で自分の不安の語り口に合わせたアプリにした。役に立った。それがずっと引っかかっているといいます。完成を無料で手渡されるということは、愛着も無料で手渡されるということで、本当に役立ったのか判定する能力を失う瞬間でもあるからです。全員が何でも自分専用に生成できるようになったとき、共有していたものはどうなるのか。無数の私的な焚き火が灯り、その熱は誰にも届かない。

> 🐈‍⬛ : 前号が「実装が速くなったあとに何が残るのか」だったとすれば、こちらは同じ問いを個人の側から書いたもの。速さを外注したあとに残るのは我慢だという話が先週で、完成度を外注したあとに残るのは選択だという話が今週。最後の一文——最後に、自分以外の誰かにとって意味のあるものを作ったのはいつですか——は、自分の道具箱をきれいにする作業に何時間も使ったあとに読むと効きすぎる。

## [Code, craft, and the making of nested folders](https://www.figma.com/blog/code-craft-and-the-making-of-nested-folders/)

> **出典**: Figma Blog | **公開日**: 2026-08-03 | **カテゴリ**: design

**3行まとめ**
- ネストしたフォルダという地味な改善のために、コンテンツモデルと権限モデルを土台から作り直した
- 要件を Slack で議論する代わりに PR を提案として出し、壊れなければマージする進め方へ切り替えた
- エンジニアがデザインを決め、デザイナーがコードを書き、PM は日々の実行を手放して戦略の問いに回った

着手は1年前。当初は通常のプロセスで進めていました。プロダクトが要件を詰め、デザインが体験を描き、思考が固まったところでエンジニアリングが実装に入る流れです。途中で状況が変わります。チームは AI ネイティブな機能の開発にリソースを割かれ、いっぽうで Figma Make、MCP サーバー、agent skills、コードベースからのプロトタイピングが、アイデアを形にするまでの時間を短くしていました。

エンジニアの Ethan Adams は、通常の開発プロセスでは間に合わないと気づいた瞬間を「期末試験の途中で顔を上げたら、残り5分だと分かった」と書いています。「誰が X にアクセスできるようにするか」といった要件の議論を、コードによる提案で置き換えました。書くことが高価で時間のかかる時代には議論が有効な前提づくりでしたが、いまはエージェントの時代である、と。壊れなければマージする方針にしたので、コピーが甘くても、機能が足りなくても、論理の穴が残っていても進められます。「実際のコードベースで動くデモは、いつでも PRD に勝つ」という一文が置かれています。

デザイナーの Cai Charniga の告白は率直です。このプロジェクトでの PR は2、3本。エンジニアになったわけではないけれど、全員が誰かの持ち場に踏み込むようになった、と書いています。エンジニア側が構造への直感と企業向け権限モデルへの理解を持っているので、フローやデザインの調整を持ち込んでくる。強いデザインシステムがガードレールとして働き、判断してよいという信頼があれば、エンジニアがデザイン機能を良い状態まで持っていける。フォルダ共有のフローでは、エンジニアの Jenny Yu がモックを数案作り、そこへ UX ライターの Molly Rosen Marriner と Cai が加わって、キャンバス上で3人で組み上げました。

逆向きの動きもありました。変更を引き受けてコードに入ってみたら裏側で起きていることが多く、これは自分の仕事ではないと戻した、という話です。「自分の専門がどこで尽きるかを知ることも、それ自体がクラフト」という言い方をしています。それでもデザイナーは PR を出してみるとよい、とも書いていて、環境を立ち上げてプレビューできるまでの待ち時間を体で知ったことが、どんなハンドオフよりも共感を育てた、と続きます。

PM の Sachi Shah が最初に手放したのは、良いプロダクト思考が PM だけから出るという前提でした。実行を手放して得た時間で向かったのは上流の問いです。AI ファーストの世界でファイル整理はまだ重要なのか、AI 検索が良くなればフォルダは時代遅れになるのか。出てきた答えは逆でした。人がより多く作るようになるほど、フォルダは AI 検索が参照する構造と文脈を与えるので、いっそう重要になりうる。

UXエンジニアリングの視点だと、「コードを提案として扱う」はUXエンジニアが以前からやってきたことです。議論の代わりに動くものを置く。それがチーム全体の標準になった形だと読めます。見落としたくないのは、デザインシステムがガードレールとして機能するという指摘のほうでしょう。エンジニアがデザイン判断を持てるのは、システムが決定の幅をあらかじめ狭めているからです。逆に言えば、システムが弱い組織で同じ進め方をすると品質が散ります。

> 🐈‍⬛ : 役割を溶かすのは気まずかった、と正直に書いてあるのがいい。互いの足を踏み、境界を不器用に越えた。その不快さを通り抜けられたのは、週次のバグバッシュや部門横断の同期といった下地に投資していたからだと続く。信頼を仕組みの話として書いているところが、この記事を精神論から遠ざけている。「自分の専門がどこで尽きるかを知ることもクラフト」という一文は、越境の話が出るたびに引用したくなる。

## [The last product design tool](https://writing.mariusz.cc/ultimate-product-design-tool/)

> **出典**: Sidebar | **公開日**: 2026-08-06 | **カテゴリ**: design

**3行まとめ**
- デザインシステムがコードとして確立していれば、四角と矢印のワイヤーからAIが実装可能なインターフェースを組み立てられる
- そのため、インターフェース設計の道具として tldraw が Figma より出番の多い場面が出てきている
- エージェントに任せるのはインターフェースの発明ではなく、ホワイトボードとコードベースという2つの語彙のあいだの翻訳

「ワイヤーフレームなんて誰が必要とするのか」から「tldraw が第一の道具になった」への転向を書いた短い記事です。磨かれた画面、丁寧なタイポグラフィ、細かく調整された余白を製品デザインツールの条件とするなら、四角と矢印と落書きしか出せない tldraw は物足りなく見えます。それが機能なのだ、というのが主張です。

理屈は明快です。デザインシステムがコードとして確立していれば、ボタンにはサイズも状態も強弱もすでに定義されています。ダイアログには構造があり、コンポーネントの契約とスロットが、渡せるプロパティと組み合わせ方を決めています。だから「Dialog」と書かれた四角を置いた時点で、それがどう見えてどう動くかは確定しています。決めているのは、フローのこの地点にダイアログが要るかどうかだけです。

エージェントに与えている仕事の切り取り方も参考になります。スクリーンショットやプロンプトからインターフェースを発明させるのではなく、ホワイトボード側の語彙（画面・ラベル・関係・メモ）とコードベース側の語彙（名前のついたコンポーネントと明示的な契約）を対応づけるだけ。契約が明確なほどエージェントが間違える余地は減り、もっともらしい誤りを直す時間も減ります。

UXエンジニアリングの視点では、この記事はデザインシステム投資の回収先が1つ増えたことを示しています。従来はコードの再利用性や一貫性が主な効能でしたが、ここでは「エージェントに渡せる語彙」として機能しています。裏を返せば、デザインシステムがコード側に確立していないチームがこのループを真似ても、エージェントは毎回インターフェースを発明することになり、レビューの手間が増えるだけになりそうです。

いっぽうで、この方法が効く範囲は限定的だという点も押さえておきたいところ。既存コンポーネントの組み合わせで表現できる画面には強い反面、新しいインタラクションそのものを設計する場面では、四角と矢印は解像度が足りません。記事も最終的なインターフェースはブラウザに宿ると書いていて、判断と実験の場をコードへ移す話として読むのが妥当でしょう。

> 🐈‍⬛ : 道具が粗いことを長所として書いているのがおもしろい。四角と矢印しか描けないから、決めるべきことだけに集中できる。ただしこれは、決まっていることが本当に決まっている環境でしか成り立たない話でもある。今回の Figma の記事にあった「デザインシステムがガードレールとして働く」と、まったく同じ前提の上に乗っている。前提が薄い組織で真似ると、白板の粗さがそのまま出力の粗さになる。

## [Better code, fewer tokens: The benefits of Code Connect in MCP](https://www.figma.com/blog/the-benefits-of-code-connect-in-mcp/)

> **出典**: Figma Blog | **公開日**: 2026-08-05 | **カテゴリ**: design

**3行まとめ**
- Code Connect を設定した状態で Figma MCP を使うと、コーディングエージェントの出力品質が 1〜4 の Likert 尺度で 1 段階上がった
- トークン使用量は中央値で 29.5% 減、所要時間は 19.6% 減。27 のテストケースで検証している
- 効果の大きさを決めるのは Code Connect のカバレッジ。デザインのうちどれだけがデザインシステムのコンポーネントで、そのうちどれだけが接続済みかで結果が変わる

Figma MCP の `get_design_context` が返すのは、キャンバス上の見た目を React で記述したものです。視覚的には正しいのですが、それが自社コードベースのどのコンポーネントに対応するのかをエージェントは知りません。結果として、自前でコンポーネントを作る、デザインシステムから違うものを選ぶ、正しいものを見つけるまで探し回ってトークンを消費する、といったことが起きます。

Code Connect のテンプレートがあると、生成される React の一部が本番コードのスニペットに置き換わります。記事の例では、`div` と `button` を並べた tablist が `<SegmentedControl value="design" options={["Design", "Code"]} />` の一行になります。どのコンポーネントを import し、どのプロパティに何を渡すかまで指定された状態でエージェントに届くわけです。

評価の作り方も参考になります。Figma の例示用デザインシステム SDS（MCP 応答の 20% が Code Connect スニペット）と、社内の大きめなデザインシステム FPL（同 6%）の2つを用意し、correctness / code quality / maintainability / completeness / best practices の観点で LLM を判定役に据えました。品質の中身がとくにおもしろいところです。Code Connect なしのランでは、見た目は近いのにタブが動きません。選択状態がハードコードされていて、インタラクションが存在しないのです。エージェントは `node_modules` を漁り、アイコン名を広く grep し、300 行ほどの CSS を書いていました。ありの場合は本物の Tabs と Button に直接手を伸ばし、77% の時間・62% のトークンで終わっています。

UXエンジニアリングの視点では、「見た目は合っているのに動かないタブ」はデザインとコードの対応関係が失われたときに出る典型的な劣化で、スクリーンショットのレビューでは見落としやすい種類のものです。Code Connect はエージェント向けの投資というより、デザインシステムの意味をコード側に書き戻す作業といえます。カバレッジが効くという結果は、部分的な整備でも比例して効くことを示す一方、デザインシステムのコンポーネント比率が低い画面では効果が薄いことも意味します。数字は Figma 自身の評価なので、自分たちのデザインシステムで測り直す前提で読むのがよいでしょう。

> 🐈‍⬛ : ひとつ前の記事が「デザインシステムがコードにあればエージェントに渡せる」と書いていて、こちらはその効果を数字で出している。トークン29.5%減より、動かないタブが動くタブになったという品質側の差のほうが本題だと思う。カバレッジが効くという結果は、整備を全部終えてから使うのではなく、接続した分だけ返ってくるという意味でもあって、着手のハードルとしてはかなり低い。

## [Claude Skills for content design: inside Intuit's AI build](https://uxcontent.com/claude-skills-for-content-design-inside-intuits-ai-build/)

> **出典**: UX Content Collective | **公開日**: 2026-08-05 | **カテゴリ**: ux-writing | **著者**: Sarah Mohs

**3行まとめ**
- 社内調査では、デザイナーが1つのフローをAIで設計するのに 30〜50 回プロンプトを繰り返し、文言は最後に回されていた
- コンテンツ標準を Claude の skill 群として束ね、共有リファレンスを1つ持つ「ハブ」型のプラグインに再設計した
- 社内AIマーケットプレイスで公開 24 時間後にインストール数2位。PRレビュー用のエージェントに組み込む使い方も出ている

問いの立て方が鋭い記事です。Intuit のコンテンツシステムチームは、AI支援のデザインワークフローを観察して、デザイナーが構造・インタラクション・トークンを何十回も直したあと、最後に「このカードには何と書く?」と考えていることを見つけました。そこから「コンテンツが生成される層に標準が置かれていないなら、それはまだシステムの一部なのか」という問いに至ります。

すでにサイトを Markdown 化し、Cursor や Claude 向けの skill も試していましたが、見つけてもらえない・バージョン管理ができないという壁がありました。転機になったのは、社内で検証済みの skill を登録・検索・インストールできるディレクトリが作られていたことです。更新が自動で配布される仕組みがあるなら、プラグインにする価値があります。

アーキテクチャの検討過程が読みどころです。当初は skill ごとにリファレンスのフォルダを持たせていましたが、それでは source of truth が分裂し、標準が変わるたびに重複ファイルを更新することになります。FigJam で複数のモデルを比較し、共有リファレンスを持つ1つの「ハブ」から専門 skill に自動ルーティングする形に落ち着きました。retrieval の精度、トークン消費、保守の手間の3点でこれが有利だったといいます。

ロジック側は人の手で棚卸ししました。skill 同士の重複や、同じ条件を取り合っている箇所を洗い出し、skill の description も書き直しています。トリガーとなる表現を、コンテンツデザイナーが自分の仕事を語るときの語彙ではなく、デザイナーが実際に使う言い方に合わせた、という判断が効いています。skill の description は実質的に検索インターフェースなので、ここは使う人の言葉で書くのが理にかなっています。

効果の実例も具体的です。プラグインなしのモデルは、あるトースト表示を「すべての標準を満たしている」と誤って判定しました。プラグインを有効にすると toast-writer skill が走り、必要なリファレンスを読み込んで、確認系のガイドラインに沿った指摘を返します。「Claude が style guide に反することを本当にやりたいのか聞いてくるようになった」というフィードバックが微笑ましいところ。

> 🐈‍⬛ : skill の description を「コンテンツデザイナーの語彙」ではなく「デザイナーが実際に使う言い方」で書き直した、という判断がいちばん実用的だった。description は検索インターフェースなので、使う人の言葉で書く。これはドキュメントの見出しにもそのまま当てはまる。著者自身が「このプラグインはシステムをスケールさせるが、craft はスケールさせない」と添えているのも誠実で、配布経路を整えることと、良いものを書けることは別だと分けている。

## [Designing for the proxy](https://uxdesign.cc/designing-for-the-proxy-2606ffac2335)

> **出典**: Sidebar | **公開日**: 2026-08-04 | **カテゴリ**: design

**3行まとめ**
- 記事もドキュメントもポートフォリオも、人より先に言語モデルが読んで解釈するようになった
- 検索は発見しやすさ、SNSはエンゲージメント、LLMは解釈しやすさを報酬にする
- 機械のために最適化するのは仕事の一部になった。機械のために設計するのは仕事ではない

長いあいだ、デザイナーの相手は人ひとつでした。その土台は消えていないけれど、周りが変わった、というのが出発点です。いま多くの体験には、人に届く前に別の読者がいます。誰かの疑問に答えるために書いた記事は、まず言語モデルに理解され引用される必要がある。APIを知りたい開発者は公式ドキュメントを開く前にAIアシスタントに聞く。「AIは働き方を変えた」とよく言われるけれど、起きているのはもっと手前のことで、誰が最初に自分の仕事に出会うかが変わった、と著者は書きます。

## [メニューUIの誤操作を減らせ！ CSSで作るヒットエリア「セーフ・トライアングル」](https://ics.media/entry/260803/)

> **出典**: ICS MEDIA | **公開日**: 2026-08-02 | **カテゴリ**: frontend

**3行まとめ**
- 階層メニューで斜めに動かすと途中の項目が反応する問題は、ポインターとサブメニューの上下端を結ぶ三角形をヒットエリアにすると避けられる
- CSS の `clip-path: polygon()` と CSS 変数で実装でき、`::before` は長方形でも切り抜かれた三角形の内側だけが反応する
- 1980年代半ばの Mac の階層メニューに同じ考えがあり、2013年の Amazon メガメニューの分析で Web に広まった

問題の立て方が良い記事です。目的のサブメニューへ斜めに進むと、途中の別項目が反応してサブメニューが切り替わる。誤反応を避けるには、いったん右へ進んでから垂直に動かすしかない。つまり格子上の道のり（マンハッタン距離）で動くようユーザーが矯正されている、という捉え方から始まります。

解決策は、マウスポインターとサブメニューの左上・左下を結ぶ三角形をヒットエリアとして置くことです。実装は疑似要素を `position: fixed` で配置し、長方形の位置と大きさを CSS 変数で受け取って `clip-path` で三角形に切り抜きます。`::before` 自体は長方形ですが、切り抜かれた三角形の内側だけがマウスに反応する、というのが仕組みの中心です。ホバー操作にだけ役立つ手法なので、`@media (hover: hover) and (pointer: fine)` で囲んでマウスデバイスに限定します。

ライブラリの比較がこの記事のおもしろいところです。Adobe の React Aria は DOM で三角形を作りません。JavaScript でポインターの移動方向とタイムアウトを判定し、サブメニューへ向かっている間は親項目を開いたままにします。Floating UI には `safePolygon()` と `useHover()` があり、こちらも移動方向を考慮して必要なときだけ多角形を作ります。実装方法はひとつではなく、さまざまな検討がなされている奥深い手法だ、という締め方に説得力があります。

歴史の節も読みどころです。この考えは1980年代半ばの Mac の階層メニューに採用されていて、当時のインターフェイス設計を振り返った1999年の記事に「a buffer zone shaped like a <」という記述があります。Web では2013年に Amazon のメガメニューを分析した記事が話題になりました。誤反応対策のひとつが遅延表示だったのに対し、セーフ・トライアングルなら即座に反応できる、という説明です。

UXエンジニアリングの視点では、まとめの一文が効いています。HTML と CSS で実装すると矩形でレイアウトを考えがちで、斜め方向にヒットエリアを確保するのは思い至らないことが多い。ヒットエリアは見えるボックスの形に縛られる必要がないのに、実装の語彙が矩形なので思考も矩形になる、という構図です。気になる点も挙げておくと、`mousemove` ごとに CSS 変数を書き換えるのでコストはかかりますし、ホバーを前提にした改善なのでキーボード操作の経路は別途担保が必要です。

> 🐈‍⬛ : 実装の語彙が矩形だから思考も矩形になる、という指摘が今週いちばん静かに刺さった。フォーカスリングの範囲やタップターゲットの拡張でも同じことが起きている。React Aria が DOM に三角形を置かず移動方向で判定しているのも、「ユーザーの意図を推定する」という別のモデルに立っている点で示唆的。40年前の Mac に同じ考えがあったという事実は、UIの発明はだいたい再発見なのだと思わせてくれる。

## [How Baseline Can Help You Ship Less JavaScript](https://smashingmagazine.com/2026/08/how-baseline-can-help-ship-less-javascript/)

> **出典**: Smashing Magazine | **公開日**: 2026-08-07 | **カテゴリ**: design | **著者**: Jad Joubran

**3行まとめ**

- 判断は3つの問いで行う。自分の利用者にとってBaseline安全か、置き換えの費用はいくらか、実際の使い方をカバーできるか

`npm audit` はセキュリティのために回すのに、「このライブラリはまだブラウザにできないことをしているか」は誰も聞かない。だから残り続ける。この記事の出発点はその観察です。Baseline の3段階（Limited / Newly available / Widely available）を土台に、置き換えの安全度を判定していきます。Widely available は全エンジンに載って30か月経った状態で、ここに達していれば今日置き換えられる目安になります。

いちばん取りやすいのは国際化の塊です。`timeago.js` は `Intl.RelativeTimeFormat`、`pluralize` は `Intl.PluralRules`、`numeral` は `Intl.NumberFormat`、配列を文章に繋ぐヘルパーは `Intl.ListFormat` に置き換わります。合わせて gzip で 14KB ほど。ただし `Intl.DurationFormat` は Newly available どまりなので、広い読者を相手にするなら機能検出を挟むか、もう1年待つ判断になります。

UIプリミティブの節がとくにおもしろいところ。`<dialog>` の `showModal()` は、フォーカスの閉じ込め、背景の inert 化、Escape での閉じ、開いた要素へのフォーカス復帰までを引き受けます。つまりモーダルライブラリと `focus-trap` が1要素に畳まれます。残る背景スクロールの固定は `body:has(dialog:modal) { overflow: hidden; }` の1行。`dialog[open]` ではなく `:modal` を使う理由（`show()` の時点で `open` は立つが、まだモーダルではない）まで説明されていて、こうした細部が実務では効いてきます。

逆に「まだ置き換えない」判断の例として Temporal が挙げられているのが誠実です。Safari の安定版が未対応でBaselineに達しておらず、公式ポリフィルは gzip で 44KB。`dayjs` の 3KB と入れ替えると、条件付き読み込みをしない限りバンドルは 41KB ほど増えます。待てと言う側の事例を1つ置くことで、3つの問いが単なる削除の口実になっていないことが示されます。

UXエンジニアリングの視点では、置き換えの副産物としてアクセシビリティの既定値が上がる点が見逃せません。手書きのモーダルやツールチップが抱えがちなフォーカス管理やキーボード操作の不備は、プラットフォーム機能に寄せるだけで解消されることが多いからです。バンドルサイズの話として始まって、実装品質の話に着地します。

> 🐈‍⬛ : 依存を1つずつではなく塊で棚卸しする、という単位の切り方が実際的。国際化の4つを一度に見れば、判断も一度で済む。四半期に一度 `npm ls --omit=dev --depth=0` を眺める習慣として持てる軽さがいい。プラットフォームへ寄せるとアクセシビリティの既定値が上がるという副産物のほうは、削減の提案が通りにくいときの二枚目の理由としても使える。

## [Building an Endless Interactive Glass Xylophone with Three.js](https://tympanus.net/codrops/2026/08/04/building-an-endless-interactive-glass-xylophone-with-three-js/)

> **出典**: Codrops | **公開日**: 2026-08-04 | **カテゴリ**: design

**3行まとめ**
- 64本のバーを1つの位相値でヘリカルに並べ、スクロールしても構図が動かない無限スクロール
- 流体シミュレーションを色のマスクとして使い、バーが持つ固有色を波が通った分だけ見せる
- `MeshPhysicalMaterial` が使えないインスタンス描画で、すりガラスを複数パスで組み立てる

カーソルで演奏する木琴です。バーを横切ると音が鳴り、打たれたチャイムのように揺れ、波が通った部分に色が満ちる。列は終わらず、64本のバーがすりガラスの螺旋を永遠に巡ります。グループもカメラも動きません。スクロールはバーのインデックス単位で測った1つの位相値に積算され、イージングを通って `wrap()` に入る。位相がインデックスではなくレイアウトを駆動するので、各バーは螺旋を連続的に登り、頂点を越えた瞬間に下から現れる。高さも幅もフレーム内の位置も固定なので、10分スクロールしても構図は置いた場所から動きません。

色の設計がこの作品の要でしょう。流体シミュレーションを使いたい、でも本物の木琴のように各バーが自分の色を持っていてほしい。最初はホバーでバー全体を光らせて、動くけれど退屈だった。落ち着いた形はこうです。各バーは列のなかの位置を0から1の数値ひとつで持ち、それがグラデーションテクスチャ上の永久の席になる。そして流体の速度場が、その色をどれだけ見せるかを決めます。静止時のバーはほぼ白で、横切ると波が各バー固有の色を開き、カーソルの色ではない。

揺れの実装も同じ思想です。素直に作るならバーごとにトゥイーンを持ってCPUで毎フレーム進めますが、減衰振り子の式をシェーダーで1行に書き下しています。打たれてからの時間を渡すと角度が返り、最初は大きく1秒ほどで消えていく。CPUがやるのは各バーがいつ打たれたかを記録することだけなので、64本が独立に揺れていてもCPUは知りません。素材の節も密度があります。`MeshPhysicalMaterial` に transmission を付ける方法は、意図的に避けたのではなく本当に使えなかった。64本が1回のインスタンス描画なので、Three.js はインスタンス同士を深度ソートできず、バーは完全に不透明のままになる。そこで背景を別ターゲットへ描いてぼかし、シーン側からそれを読む複数パスの構成にしています。

アクセシビリティの節が、この記事でいちばん引用したい部分です。揺れの角度に0を掛ければ動きは消える。他は何も変わらない。バーは光り、音は鳴り、色は現れる。「インタラクション全体をブール値ひとつで塞ぐのは誘惑だけれど、それは穏やかな楽器を渡すのではなく、楽器を取り上げることになる。動きを減らす設定は、めまいの問題を取り除くのであって、機能を取り除くのではない」。いっぽうで、キーボードで演奏する経路はないと正直に書いています。打鍵はポインタのレイキャストを必要とするので、キーボードのユーザーはページと音のトグルは使えても音を鳴らせない。自分なら矢印キーでフォーカスのインデックスをバー間で歩かせ、同じ打撃の経路を呼ぶ、という直し方まで示しています。

UXエンジニアリングの視点では、reduced motion の扱いが持ち帰る価値のいちばん高い部分でしょう。`prefers-reduced-motion` に反応してアニメーション全体を止める実装はよく見ますが、それが体験の中身まで落としていないかは別の問いです。ここでは揺れという前庭系に効く要素だけを0にして、光・音・色という他の手応えを残しています。同じ考え方は、ページ遷移のアニメーションを消すときに遷移そのものが分からなくなっていないか、という点検にも使えます。

> 🐈‍⬛ : 動きを減らす設定は、めまいの問題を取り除くのであって、機能を取り除くのではない——この一文だけでも読む価値がある。ブール値ひとつで全部を塞ぐのは楽だけれど、それは配慮の顔をした剥奪になりうる。締めの「認めたくなかった学びは、何かを簡単そうに見せるためにどれだけの労力がかかるかということだ」も効いていて、今週の craft の記事が言っていた「安くならなかった部分」が、ここでは実装の細部として並んでいる。
