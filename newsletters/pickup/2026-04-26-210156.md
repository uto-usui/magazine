## [Headless everything for personal AI](https://interconnected.org/home/2026/04/18/headless)

> **出典**: Sidebar 経由（interconnected.org） | **公開日**: 2026-04-23 | **カテゴリ**: design

**3行まとめ**
- アプリやサービスはこれから「ヘッドレス化」を強いられる、というのが Matt Webb の主張です。パーソナル AI が直接叩ける CLI や API を持つ必要があります。
- ユーザージャーニーをデザインで囲い込む発想は崩れ、Unix 哲学的に「組み合わせ可能な小さなツール群」が中心になります。
- フロントエンドは犠牲財ではなく、ブランドや雰囲気を伝える役割が一層重要になる、という見立てです。

MCP に加えて、Google Workspace CLI、Obsidian CLI、Salesforce CLI、コードベースから自動で CLI を生成する CLI-Anything など、AI に渡す前提のコマンドラインツールが急増しています。Webb の主張は、「AI が叩くなら API より CLI のほうが向く」というシンプルな事実認識から始まります。CLI はユーザーの PC 上で他ツールと組み合わせやすく、UI を持たないぶん攻撃面が狭い、というメリットが整理されています。

UXエンジニアリングの観点で響くのは、「ユーザージャーニー設計の限界」をはっきり言語化している点です。ユーザーは「ホテル検索→予約→滞在→レビュー」という直線では生きていません。家族グループに送り、2日後に戻ってきて、別アプリで補足を取る、という非線形な動きをします。ではフロントエンドはどうなるか。Webb は「使い勝手の最適化」という従来の主軸から「ブランドと vibe を伝える」役割へ重心が移る、と予想します。トップページは「AI に伝えるための名刺」になる、という見立てです。

> 🐈‍⬛ : 「ヘッドレス化」と「名刺としてのフロントエンド」の対比がおもしろい。3月のピックアップで触れた Comprehension Debt の議論とも地続きで、AI が触る層と人間が触る層の分業が静かに進んでいる印象がある。今週はこの記事を起点に並べると、ほかの記事の景色も繋がって見えてくる。

## [Thoughts and feelings around Claude Design](https://samhenri.gold/blog/20260418-claude-design/)

> **出典**: Sidebar | **公開日**: 2026-04-22 | **カテゴリ**: design

**3行まとめ**
- Anthropic の Claude Design に触れた Sam Henri Gold による、デザインツールの今後に関する仮説です。
- Figma はプロプライエタリな原語で武装しすぎて、コードを中心にした学習データから自分を締め出してしまった、という診断です。
- ここからデザインツールは「コードに素直なもの」と「純粋な探索環境」の2つに分岐し、Claude Design は前者の先駆けになるという見立てです。

Figma 自身が運用するデザインシステムファイルのスクリーンショットを引き、ダークモードや DevMode など8つのモードに分かれた946の color variable、12種類のバリアントを持つモーダルフッター、「light/elevation-300-tooltip」という奇怪な名前の0.5px ドロップシャドウ、といった重量級の内部を淡々と並べていきます。論点は2つ。Figma が独自プリミティブを発明し続けたことで他ツールでは再現しづらい「学習データの谷」に落ちたこと。そして LLM はコードで訓練されるため、エージェント時代にはデザインの source of truth がコード側に移っていくだろう、という予測です。

Claude Design に対する評価は、機能そのものよりも「HTML と JS のまま正直にいる」という姿勢に向かっています。Arts and Crafts の "truth to materials"（素材への誠実さ）を引いて、Figma が厳格なスキーマの上にふんわりした雰囲気を纏う様子と対比するのは比喩として強いです。Claude Code と兄弟であることが構造的な優位、という見立ても、UXエンジニアの実感に近いはずです。

> 🐈‍⬛ : Figma のプリミティブが「学習データの谷」になる、という指摘の解像度が高い。デザインツールが「コードに寄るもの」と「純粋な探索環境」に分岐する見立ては、自分の足元のツール選びにも関わる。後者の席が空いている、という話のほうも実は気になる。

## [Mouth Coding](https://bradfrost.com/blog/post/mouth-coding/)

> **出典**: Brad Frost | **公開日**: 2026-04-20 | **カテゴリ**: design-systems

**3行まとめ**
- Brad Frost が、会話しながらリアルタイムで Web サイトが立ち上がっていく体験を「マウスコーディング」と呼んでいます。
- 必要なのは会話、文字起こし、堅牢な Web インフラ、ライブプレビュー、共有された文脈、そして人間の判断という6つの材料です。
- AI は人間の創造性を「置き換える」のではなく「促進する」ものであるべきだ、というメッセージが中心にあります。

Brad は妻の Melissa と一緒に、地元のカウンセリングルームの Web サイトを1時間で「話して作る」セッションを行いました。ブラウザーで音声を文字起こししながら LLM が解釈し、ライブプレビューが更新されていく。その過程で会話・既存サイト・デザイン探索・ベストプラクティスといった文脈が自然に流れ込み、最終的にサイトの土台ができあがります。

この記事の本質は、テクニックよりも「コラボレーションの再発明」にあります。プロダクト開発はサイロ化と Jira チケットの壁で疲弊しがちですが、「みんなで話しながらリアルタイムに作る」体験は、デザイナーとエンジニアの境界を一時的に溶かします。マウスコーディングが成立する前提として、堅牢なデザインシステムや UI インフラが要ることにも注目したいところです。会話に応じて即座に高品質な UI が出るためには、コンポーネントの語彙やトークンが整っている必要があります。

> 🐈‍⬛ : AI が速くなるほど、その速さを引き受ける土台の質が問われる、という構造がきれいに見える。デザインシステムがあるからこそ「会話で立ち上がる」体験が成立する話は、デザインシステム投資の意味を更新してくれる。「AI should facilitate human creativity, not replace it.」を10回繰り返す Brad の演出も含めて好きな記事。

## [The UX Designer's Nightmare: When "Production-Ready" Becomes A Design Deliverable](https://smashingmagazine.com/2026/04/production-ready-becomes-design-deliverable-ux/)

> **出典**: Smashing Magazine | **公開日**: 2026-04-22 | **カテゴリ**: design

**3行まとめ**
- 2026年の UX 求人は「production-ready なコード」を成果物として要求する方向に急変しており、デザインとエンジニアリングの境界が溶けつつあります。
- AI 経由で出荷されるコードの品質問題（セキュリティ、アクセシビリティ、性能）がレビューされずにたまり、「Rework Tax」としてエンジニアの時間を食い潰します。
- 解決策はひとりフルスタックではなく、デザイナー・AI・エンジニアの3者ループでの役割分担です。

Carrie Webster による現役シニアデザイナー目線の論考です。グラフィックデザイン職が3%増に留まる一方で、UX・UI・プロダクトデザイン職は16%増と予測され、その多くが AI プロダクト開発の文脈で求められている、という観察から始まります。求人票が "production-ready prototyping" や "technical orchestration" を前提にし始めたことで、デザイナーがコードでも評価される時代に入った、という指摘です。

Anthropic 等の研究を引きつつ「AI で高速化された人ほど理解が浅くなる」というデータも並びます。AI 支援で書いたコードは理解度テストで17%低いスコアを示し、とくにデバッグの局面で差が広がる。結果、本番で壊れたとき「誰も読めないコード」が残る。もうひとつの軸が「Rework Tax」で、AI 生成コードを含む PR では incidents が23.5%増えているというデータを引きつつ、デザイナーが気づかないままセキュリティ脆弱性、アクセシビリティ欠落、性能問題を流し込み、後工程でエンジニアがまとめて尻拭いする現状を描き出します。

> 🐈‍⬛ : Rework Tax という言葉が痛い。AI 生成コードの理解度が17%下がるというデータは、3月のピックアップで紹介した Comprehension Debt の議論をデザイン側から見た景色そのもの。境界を消すこと自体が目的化しないよう、「デザイナーは意図とフロー、エンジニアはアーキテクチャと性能」という分担を引き直す提案には現実味がある。

## [I love AI, but it still can't design for shit](https://jonnyburch.com/i-love-ai-but-it-still-cant-design-for-shit/)

> **出典**: Sidebar 経由（Jonny Burch） | **公開日**: 2026-04-24 | **カテゴリ**: design

**3行まとめ**
- AI を毎日使うコンサルタントが、「AI は自分の出力を批判的に見る目を持たない」と率直に書いています。
- AI が作ったプレゼン・コード・画像・UI は、人間がレビューせず素のまま出すと一瞬でバレる、という指摘です。
- 「ヒューマン・イン・ザ・ループであり続けることのシグナリング価値」は今後も残る、というのが結論です。

著者は AI コンサルタントとして候補者面接を行うなかで「AI を使ったプレゼンを準備してください」と依頼するそうです。優秀な候補者は AI を使いつつも自分が編集者の立場に立ち、1スライド1分・50語以下のシンプルなプレゼンを自信を持って語ります。残り大多数は、3〜4スライド／分の冗長な箇条書きを、自分でも読んでいないまま提示してきます。「あなたが提出物の責任者であって、AI のせいにはできない」という、当たり前だが軽視されがちな原則が中心にあります。

著者は同じ現象が、文章（GPT-3 時代の Jasper による LinkedIn 風スパムから始まり）、コード、画像、そしていま UI に到達した、と整理します。「Anthropic 風グレージュの薄い UI スロップ」が量産され、最初は良く見えても、深掘りするほど壁に塗ったゼリーのように崩れる、という比喩が秀逸です。AI 補助のワークフロー設計を考えるうえで核心の指摘で、AI に最終出力を作らせるのではなく「自分の意図を増幅し、最後の判断を人が握る」レイヤーを作る必要があります。

> 🐈‍⬛ : 「Anthropic 風グレージュの UI スロップ」という言い回しは解像度が高い。AI を増幅器として置き、最終判断を人が握るというワークフロー設計の話は、いまどんな小さな機能を作るときにも効いてくる。「全員がクオリティバーを下げる時代に、自分のバーを保てる人は希少資源になる」という締めの一文も覚えておきたい。

## [Good taste the only real moat left](https://rajnandan.com/posts/taste-in-the-age-of-ai-and-llms/)

> **出典**: Sidebar | **公開日**: 2026-04-20 | **カテゴリ**: design

**3行まとめ**
- 生成 AI により「そこそこの出力」が安価になったいま、差がつくのは「何を却下できるか」という審美眼（taste）である、という論旨です。
- ただし taste だけで戦うと人間は「機械の選定者」に縮んでしまう危険があり、建てる・決める・責任を負う側として関わる必要があります。
- AI の出力を並べて「なぜこれは駄目か」を言語化することで、自分の taste を鍛える具体的な練習法が提示されています。

Rajnandan Kashyap による AI 時代の taste 論。よくある「センスが大事」論と違い、taste を「不確実性の下での判別力」と定義し、感想ではなく診断の言葉として扱う点に価値があります。「これは既視感がある」ではなく、「これは規制上の制約を誤ってマーケティング的な表現に圧縮しており、顧客を混乱させる」と言える解像度です。

AI と LLM は統計的にもっともらしい出力を高速で大量に作れます。結果として「7点の作品」が無限に湧き、真ん中が溢れかえる。このとき希少になるのは生成ではなく拒否で、何がジェネリックか、何がビジネス上の本質的なトレードオフを隠しているかを見抜く能力が、新しいボトルネックとして浮上します。記事の後半では taste だけでは足りないという点に踏み込み、人間がやるべきことは選別ではなく、方向性を選ぶこと、責任を引き受けること、訓練データにはまだ存在しない「本当に新しいもの」を守り育てることだ、と主張されます。

> 🐈‍⬛ : "fails because..." を10本書く練習はすぐ取り入れられる。3月のピックアップでも触れた Osmani の「テイストが希少になる」という話とも並走していて、tasteを「不確実性の下での判別力」と再定義する切り口が今回はとくに腑に落ちる。

## [Expansion artifacts](https://mattstromawn.com/writing/expansion-artifacts/)

> **出典**: Sidebar | **公開日**: 2026-04-21 | **カテゴリ**: design

**3行まとめ**
- 圧縮（compression）がブレイク世界の設計原理だったなら、LLM 時代の設計原理は「展開（expansion）」であるという主題です。
- JPEG や MP3 の圧縮アーティファクトと同じく、AI 生成物には "expansion artifact" と呼ぶべき痕跡が残ります。
- これらの痕跡が次世代モデルの学習データに混入し続けるとき、モデルの長尾（独特な声や珍しい言い回し）が静かに痩せていきます。

Matt Strom による、情報時代と AI 時代の設計原理の相違を「圧縮 vs. 展開」という軸で整理した論考です。2013年に David Kriesel が発見した Xerox の JBIG2 バグ（スキャンした建物図面の "21.11m²" が "14.13m²" に置換されていた）を導入として、圧縮アーティファクトが単なるノイズではなく「文書の来歴を教えてくれるメタ情報」になっている点を丁寧に描きます。

そこから Ted Chiang の「ChatGPT は Web のぼやけた JPEG だ」という有名な比喩を引き継ぎつつ、筆者は「アーティファクトがあるのは圧縮ではなく、むしろ展開の側だ」と言い換えます。LLM の生成物は、訓練データという圧縮済みの塊から、プロンプトに向けて確率的に膨らませた結果であり、そこに「ヘッジを多用する言い回し」「必要のないエラーハンドリング」「6本指」「連続性の破綻した動画」など、展開固有のアーティファクトが残る、というのが核心です。とくに危ういのは、これらの痕跡が新しいモデルの訓練データに入り込み、さらにぼやけた JPEG が生産されていくループです。

> 🐈‍⬛ : "compression artifact" を "expansion artifact" に裏返すだけで議論の射程が一気に広がる。Tailwind の初期設定が AI 生成 UI を一色に染めたという Adam Wathan のツイートが引かれているくだりは、自分のプロジェクトでも見覚えがある人が多いはず。「どう痕跡を消すか」「どうあえて残すか」という問いは、デザイントークン設計にもそのまま効く。

## [Agent Harness Engineering](https://addyosmani.com/blog/agent-harness-engineering/)

> **出典**: Addy Osmani | **公開日**: 2026-04-19 | **カテゴリ**: performance

**3行まとめ**
- コーディングエージェントは「モデル + ハーネス」であり、モデルを取り巻く足場の設計こそが実用的な挙動を決めます。
- エージェントの失敗は「モデルが悪い」ではなく「設定が悪い」と捉え、失敗のたびにルールや hook を増やすラチェット運用が肝になります。
- ハーネスはモデルの進化とともに縮むのではなく、役割を変えながら動く生きたシステムです。

Addy Osmani が Viv Trivedy の "harness engineering" という概念を整理した、いまのエージェント活用における最良の整理のひとつです。主題はシンプルで、同じモデルでもハーネス次第で挙動は大きく変わる、というもの。Terminal Bench 2.0 でのスコアが、Claude Opus 4.6 を Claude Code のまま動かしたときと専用ハーネスで動かしたときで大きく差がつくという事例が、その主張を裏づけています。

ここで言うハーネスとは、システムプロンプトや AGENTS.md、ツール定義、MCP サーバー、サンドボックス、hook、サブエージェントの起動規則、そしてコンテキスト圧縮や継続の仕組みを含めた、モデル以外のすべてを指します。Osmani はこれを「振る舞いから逆算する」設計として捉え、フィルタリング、計画、検証、コンテキストロット対策に対して、それぞれどのハーネス部品が対応するかを対応づけていきます。

> 🐈‍⬛ : 「振る舞いから逆算して足場を組む」という整理は、UX の情報設計と地続きに読める。「成功は静かに、失敗は雄弁に」というフィードバック設計の話、「10の良いツールは50の重複したツールより強い」という情報アーキテクチャの単純化の話。良いハーネスは「ダウンロードできない」、自社の失敗履歴から蒸留される、という観察も実感に合う。

## [Attention Engineering: Why Users Ignore Even the Most Important Elements](https://uxmag.com/articles/attention-engineering-why-users-ignore-even-the-most-important-elements)

> **出典**: UX Magazine | **公開日**: 2026-04-23 | **カテゴリ**: ux-research

**3行まとめ**
- ユーザーが大切な要素を見落とすのは怠慢ではなく、脳が情報の95%を意識前にフィルタリングしているからだ、という前提から議論が始まります。
- 注意は認知・視覚・行動・感情の4つの層から成り、ひとつでも設計とずれると注意は崩壊する、という見立てです。
- 大切なのはコントラストやサイズではなく、ユーザーの目的・メンタルモデル・習慣・感情と整合させる設計、という結論です。

著者の Tushar Deshmukh はこれを Attention Engineering（注意工学）と呼び、注意を「スポットライト」ではなく「ゲートキーパー」として捉え直すよう主張します。脳は意味・安全・期待・関連性を瞬時に判定し、それに合わないものは意識に上る前に弾く、という構造です。

実例も示唆に富んでいます。健康診断ポータルで "Confirm Appointment" ボタンが画面上部にあったのに、ユーザーがスクロールして「確認ボタンが無い」と言い張るケースは、メンタルモデル（最終操作はページ下部にある）が視覚情報を打ち消した典型です。E コマースの "Size Guide" を完全にスルーするのも、その位置のテキストは些末なものという過去の習慣が働いた結果だと整理しています。本当に効くのは、ユーザーが認知的に進みたい流れに沿った構造を作ること、不安を抱えている瞬間に余計な情報を増やさないこと、そして習慣を上書きしようとせず尊重することだ、という結論です。

> 🐈‍⬛ : コントラスト調整やコピー書き直しは症状対処にすぎない、という指摘が刺さる。A/B テストの変数を「色やサイズ」だけでなく「文脈との整合性」「タイミング」「直前の感情負荷」まで広げる発想は、すぐ取り入れられる。3月のピックアップで触れた「Designing for people with anxiety」とも地続きで、注意と不安は同じ層で扱う問題に見えてくる。

## [10 Guidelines for Designing Your Site's AI Chatbots](https://www.nngroup.com/articles/ai-chatbots-design-guidelines/)

> **出典**: Nielsen Norman Group | **公開日**: 2026-04-24 | **カテゴリ**: design

**3行まとめ**
- NN/g がサイト固有の AI チャットボットを実ユーザー観察し、10個の実践的ガイドラインに整理しました。
- 「複数のチャットを並列させない」「全ページで使えるようにする」「できることを冒頭で示す」「サジェスト質問はテキストではなくボタンで出す」など、設計判断のチェックリストとして直接使えます。
- ストリーミング応答の自動スクロール、画像なしの推薦、共有・保存できない会話など、よく見る悪手も具体例で批判されています。

Home Depot の Magic Apron と Live Chat が併存して混乱を生んでいる例、Williams Sonoma の AI Sous Chef がページを横断して追従する好例、Amazon の Rufus が見ているページを認識して提案を変える例など、実プロダクトのスクリーンショット付きで議論されています。第1ガイドライン「複数のチャットを統合する」は、社内のシステム構成をユーザーに理解させてはいけない、というシンプルな原則の再確認として効きます。

第3ガイドラインの「できることを示す」も、AIプロダクトでよく抜け落ちる視点です。「Ask me anything」は一見親切ですが、実際にはチャットボットの能力を超えた期待を生み、失敗体験を量産します。Magic Apron が閲覧履歴を記憶できるのに、UI 上はその能力を一切示していなかったため、ユーザーが商品名をコピペしてしまう例は印象的です。「能力を持っているだけでは不十分で、その能力を使えると気づかせる UI が必要」という、UXエンジニアリング的な原則の好例です。

## [The end of responsive images](https://piccalil.li/blog/the-end-of-responsive-images/?ref=main-rss-feed)

> **出典**: Piccalilli | **公開日**: 2026-04-23 | **カテゴリ**: css

**3行まとめ**
- 14年間悩まされてきた `sizes` 属性の手書き問題が、ようやく決着しつつあります。
- Gecko・WebKit・Blink すべてで `sizes="auto"` がサポートされ、`loading="lazy"` と組み合わせれば描画後のレイアウト情報を使ってブラウザーが自動でソース選択できるようになりました。
- 著者の Mat Marquis は元 RICG（レスポンシブ画像コミュニティグループ）のチェアで、自ら推進した仕様の負債を、自身の手で解消しに来た格好です。

`sizes` がつらいのは、ビルド時点ではレイアウトが分からないという根本制約のせいでした。レイアウトを実測しないと値が決まらないのに、HTML 属性として手書きする必要があった、というねじれ構造です。今回追加された `auto` 値は、この前提を `loading="lazy"` の存在で覆します。遅延読み込みされる画像はビューポートに入る瞬間にリクエストが走るので、その時点ではレンダリング後のサイズが分かっており、ブラウザーが自前で最適なソースを選べる、というシンプルな発想です。

UXエンジニアリングの観点で重要なのは、ここで「制御を諦めた方が良い」という判断が改めて肯定されたことだと思います。一方で LCP 候補となるヒーロー画像など、`loading="lazy"` を付けたくないケースでは引き続き手書きの `sizes` が必要なので、完全な置き換えではない点には注意が必要です。WordPress はすでに `auto` への移行を進めており、サポート外のブラウザーは `auto,` の部分を黙って捨ててくれるので、リスクなく今日から導入できます。

> 🐈‍⬛ : 14年もの伏線回収という重量級の話を、Piccalilli らしい乾いた筆致で語っているのがいい。今週のもうひとつの裏テーマである「制御を手放す」とそのまま重なる記事で、デバイスやネットワークが多様化するほどブラウザに丸投げするほうが体験は揃う、という構造はチームへの説明にも使える。

## [fetchのキャンセルだけじゃない！　AbortSignalで実現するクリーンなJS非同期処理](https://ics.media/entry/260423/)

> **出典**: ICS MEDIA | **公開日**: 2026-04-22 | **カテゴリ**: frontend

**3行まとめ**
- `AbortSignal` は `fetch` のキャンセル専用ではなく、非同期処理全般のクリーンアップを統一的に扱うための仕組みです。
- `addEventListener` の `signal` オプションや `AbortSignal.any()`・`AbortSignal.timeout()` を組み合わせると、レースコンディション対策やタイムアウトを宣言的に書けます。
- 自作の非同期関数も `signal` を受け付ける形にしておくと、標準 API と同じ片付け方法に乗せられて運用が楽になります。

`AbortController` は知っていても、その応用範囲を最大限に活かしているチームは意外と少ない印象です。記事では `fetch` のキャンセルから始めて、インクリメンタルサーチでよくあるレースコンディションをひとつの `signal` で解消するパターン、`AbortSignal.any()` で「ユーザー操作・タイムアウト・コンポーネントのアンマウント」を1つにまとめるパターンまで、実務にそのまま使える書き方が紹介されています。

とくに価値が高いのは、React の `useEffect` でのクリーンアップを `controller.abort()` 一発に統一する例です。複数の `addEventListener` と `fetch` をすべて同じ `signal` に紐付けておけば、コンポーネントのライフサイクルと `AbortSignal` のライフサイクルを1対1で対応させられます。`removeEventListener` への参照ズレや解除漏れといった、地味だが厄介なバグの温床を構造的に消せる設計です。

> 🐈‍⬛ : `useEffect` を `controller.abort()` 一発に統一する例がきれいで、見るたびに気持ちいい。AI エージェントとの連携が増えると「外から長時間処理を止められる設計」がますます効いてくるので、自作ライブラリでも `signal` を受ける前提に揃えておくとよさそう。`AbortSignal.any()` の Baseline 2024 Newly available（Safari 17.4 以降）という条件だけ覚えておくと安心。
