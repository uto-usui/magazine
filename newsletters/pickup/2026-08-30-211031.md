## [When code is abundant](https://about.gitlab.com/blog/when-code-is-abundant/)

> **出典**: Sidebar | **公開日**: 2026-08-26 | **カテゴリ**: design

**3行まとめ**
- コードの生成が安くなったとき、次に希少になるのは「そのコードを信頼できること」だという整理です
- 指標を「1行あたりのコスト」から「受け入れられた変更1件あたりのコスト」に置き換えることを提案しています
- Stripe・Spotify・Amplitude の実測値を並べ、詰まりどころが CI とレビューへ移った様子を具体的に示しています

**詳細解説**

GitLab が1月の取締役会向けメモから育ててきた論考を、8か月分の観測を足して公開したものです。出発点はシンプルで、Anthropic が8月21日に出した「The AI-Native SDLC Playbook」の一文「Code is no longer the bottleneck」に同意するところから始まります。ただし関心はその一歩先にあります。コードが制約でなくなったとき、代わりに何が希少になるのか。

歴史の整理が読みやすいです。ソフトウェア工学は60年間、「コードは高価で壊れやすい」という一つの事実のまわりに組み上がってきました。レガシーを保存するのも、技術的負債を何年も抱えるのも、レビューや承認や各種ゲートの儀式も、高価な資産を守るための合理的な反応だったという見方です。抽象化のたびに次の制約が見えてきたのは、機械語からアセンブリ、高級言語へと移ったときと同じで、誰も手書きのアセンブリを懐かしんではいません。

新しい制約の名前は「信頼」です。モデルは実装を人間より速く出せますが、それが正しく、安全で、性能が出て、コンプライアンスを満たし、保守可能で、そもそも事業が意図したものかどうかは別の話になります。ここで提案される単位が「cost per accepted change（受け入れられた変更1件あたりのコスト）」です。生成・環境構築・コンテキスト・検証・レビュー・修正・ガバナンスをすべて含めた合計のうち、AI が縮めたのは生成の項だけ。ほかを手つかずのまま10倍速くしても、待ち行列が移動するだけだと書かれています。

実例の数字が効いています。Stripe は minions と呼ぶ内製エージェントで、週に1,000件超のマージ済み PR がエージェント生成になっています。Amplitude は6か月でパイプラインを組み直し、PR のサイクルタイムを5.2時間から44分へ、フロントエンドの CI を約30分から3〜4分へ短縮。同期間に PR 数は3倍になった一方、月次のバグ報告は715件から319件に減っています。Spotify は Honk というバックグラウンドエージェントで1,500件以上のマージを記録しています。そして、この作業の大半は AI ではなくインフラ整備でした。「30分の CI パイプラインは、どのモデルを当てても負ける」という一文が象徴的です。

もう一つ興味深いのが、成熟度の一本道を否定している点です。人間が制御するレガシー（Mode 1）、エージェントが支援する開発（Mode 2）、自律的な開発（Mode 3）は長く共存すると見ています。境界線はグリーンフィールドかどうかではなく、「人が全行読まずに検証できるか」「間違ったときシステムが気づくか」。すべてを早々に Mode 3 へ押し込もうとするのが、この移行期でもっとも高くつく判断になりそうだと釘を刺しています。

UXエンジニアリングの視点で持ち帰れるのは、「学びがコードになる」という部分でしょう。どのサービスが脆いか、3年前になぜデプロイが失敗したか、前回のインシデントを生んだミスの型は何か。こうした知識は今まで人の頭の中にありました。実装が安くなれば、本番障害はリグレッションテストに、性能要件は自動化された制約に、セキュリティインシデントはポリシーに変換できます。デザインの領域でも同じことが言えるはずで、レビューで毎回同じ指摘をしているなら、それは実行可能な制約に落とせる候補です。ただし記事自身が断っているとおり、ポリシーは間違うこともあるし、テストは昨日の前提を固定してしまうこともあります。判断そのものが不要になるわけではありません。

GitLab 自身の製品の話がやや長いのは、事業上の主張が混じっているためです。それでも、90日でやることとして挙がっている5項目（受け入れ変更あたりのコストを測る、CI が5分を大きく超えるなら先にそこを直す、承認ではなく基準を書き出す、コンテキストを可搬な形式で置く、どの事業シグナルを開発ループに直結させるか決める）は、プラットフォームの選択と関係なく試せる内容になっています。

> 🐈‍⬛ : 「cost per accepted change」という単位の置き方が、この記事のいちばんの仕事です。生成・環境構築・コンテキスト・検証・レビュー・修正・ガバナンスの合計のうち、AI が縮めたのは1項だけ。待ち行列が移動しただけかどうかは、この分母で測らないと見えません。Amplitude の「CI を30分から3〜4分にしたらバグ報告が715件から319件に減った」が象徴的で、モデルの選定より前に効いた投資がインフラだったという順序は覚えておきたいところ。Mode 1/2/3 が長く共存すると言い切って、境界を「人が全行読まずに検証できるか」に置いたのも良心的です。

## [Human judgment doesn't leave the software factory. It relocates.](https://addyosmani.com/blog/human-judgment-doesnt-leave-the-software/)

> **出典**: Addy Osmani | **公開日**: 2026-08-21 | **カテゴリ**: performance

**3行まとめ**
- ソフトウェアファクトリー（開発を回す反復可能なループ）のなかで、人間の判断がどこへ移るのかを整理した長編です
- ファクトリーが要るのはイベント駆動のキューを隔離環境で回したくなったときで、多くの場合は手元のハーネスで足りると述べます
- 82分かかったサンプル実行、緑のテストが嘘をつく場面、理解が追いつかなくなる comprehension debt など、実体験の失敗談が豊富です

**詳細解説**

Addy Osmaniさんが今週公開した一本で、エージェント運用について書いてきた一連の記事のなかでもいちばん射程が広い内容です。まず「ファクトリーは要るのか」から入るのがいいところで、Claude CodeやCodexを複数セッション立ち上げ、検証を織り込んだ仕様と制約を用意するだけでかなり遠くまで行ける、と最初に釘を刺します。ファクトリーが効いてくるのは、Slackの通知やGitHub issue、Linearのバックログのようなイベント駆動のキューを、クラウドの隔離環境で継続的に回したくなったときだと整理します。

実装として紹介されるものは意外と地味です。Warpの例では、入ってきたissueを ready-to-implement / ready-to-spec / needs-info / wait-to-implement の4状態にトリアージし、そのラベルが次のエージェントを起動します。このラベルがキューであり、同じissueを複数セッションが取り合わないためのロックであり、人間が「今はやらない」と一時的に置いておく駐車場でもある、という三役をこなしている説明はわかりやすいです。人間の関わり方も、最後に差分を承認するだけではなく、shape（上流で形を決める）、steer（途中で軌道修正する）、handoff（状態と文脈ごと引き渡す）、approve（本番に出すかを決める）の4つに分けられます。

読み応えがあるのは失敗談のほうです。テストが通ったので信用してマージした「お気に入り」機能を、数日後に手を入れようとして開いたら、自分のリポジトリなのに動作を説明できなかった、という話。承認したのは自分なのに、理解がコードの増加に追いついていなかったわけです。並行するセッションを5つ、10と増やしていくと、冷えた頭のなかのモデルがその数だけできあがります。コードは決定を保存しますが、なぜその決定をしたかは保存しません。エージェントに判断の経緯やつまずきを書き残させて、あとから参照できるようにしておくとよい、という提案が添えられています。

もうひとつ実務的なのは「検証予算」という考え方です。パフォーマンス予算と同じ発想で、lintや型チェックのような速いチェックは早い段階に、ミューテーションテストやブラウザテスト、セキュリティチェックのような重いものはドラフトPRの前後に置く。検証を要約で置き換えず、置き場所で調整します。実際のサンプル実行では、指摘なしで通った検索機能が7分、2回の差し戻しと人間の判断を挟んだお気に入り機能が56分。同じファクトリーでこの差なので、実行結果の分類（Vercelの success / flawed / blocked / manual に倣ったもの）だけでなく、工程ごとの所要時間も見ないと、何にコストがかかったのかが分からないと述べます。

UXエンジニアリングの視点で読むと、自動的な押し戻しがいちばん弱くなるのはフロントエンドだと言えそうです。タップしたときの反応の質感、アニメーションの落ち着きどころ、読み上げたときの語順といったものは、決定的なチェックに落としきれません。だからこそ人間のレビューをそこに集める、という配分の話として受け取れます。手を動かした量ではなく、判断をどこに置いたかで責任を語る、という締めくくりも印象に残ります。

> 🐈‍⬛ : shape / steer / handoff / approve という4分類は、レビューの粒度を決める語彙としてそのまま借りられます。効くのは失敗談のほうで、テストが通ったので信用してマージした機能を数日後に開いたら自分のリポジトリなのに動作を説明できなかった、という話。承認の署名だけが残って理解が残らない状態に名前を付けたのが comprehension debt でしょう。フロントエンドは自動的な押し戻しがいちばん弱い領域なので、その分だけ人間の判断がここに集まるという配分の話として読むと納得しやすい。GitLab の記事と並べると、片方は組織の指標の話、こちらは机の上の話をしています。

## [The Custodial Era of UX: Cleaning Up After AI](https://www.nngroup.com/articles/ai-ux-debt/)

> **出典**: Nielsen Norman Group | **公開日**: 2026-08-28 | **カテゴリ**: design

**3行まとめ**
- 生産が UX 評価より安くなった結果、UX の仕事が「白紙から設計する」から「AIの出力の何を残すか決める」に寄ってきたという整理です
- 新しいアイデア → 高速な実装 → 評価の遅れ → 体験の問題 → UX による後始末、という循環を「管理人（custodial）パターン」と名づけています
- 抜け出す道は3つ。何を作るかの判断を共有すること、評価を生産の速度に追いつかせること、そして生成のプロセス自体に UX の知識を入れることです

**詳細解説**

NN/g の Anna Kaley さんと Raluca Budiu さんによる、AI 時代の UX の立ち位置を扱った論考です。前の記事（Anthropic の SDLC プレイブック）が「速くなった生産に統制を合わせる」側から書かれているとすれば、こちらは「速くなった生産に評価が追いつかない」側から見た景色になります。並べて読むと、同じ現象の裏表がよく見えます。

中心にある一文が明快です。「AI で作られたものが本質的に悪いわけではない。問題は、生産が UX 評価より安くなったことにある」。体験を作る時間より、その体験が有用か・使えるか・信頼できるか・一貫しているかを判断する時間のほうが長くなってしまった、という状況の説明です。動くプロトタイプが目の前にあると、議論は「これは必要か」から「いつ出せるか」へ一瞬で移ります。

管理人パターンとして5段階が示されます。チームが機会を見つける、あるいは市場の勢いや「AIを使わなければ」という圧力に反応する。AI ツールで一気にプロトタイプや実装ができる。見た目が良いので調査も「そもそもこれは要るのか」の検討も飛ばして、リリース時期の話に移る。ユーザーの混乱、サポート依頼、伸びない利用率といった、プロトタイプ段階では見えなかった信号が出る。そして UX が評価・簡素化・修復を依頼される。UX を重視している組織でも起こりうる、という指摘が現実的です。

実務に効くのは、渡された機能をすぐ磨き始めないという助言でしょう。まずトリアージして費用対効果を見る。この機能はどんな問題を扱っていて、それが実在するニーズだという証拠はあるか。ユーザーの既存のメンタルモデルやワークフローにどう収まるか（既存の経路を重複させるのか、置き換えるのか、新しく覚えることを増やすのか）。追加される複雑さ、サポートや保守のコスト、そしてこの機能の周辺を作り直す機会費用まで含めるとどうか。トリアージの結果は「作り直す」だけではなく、残す・簡素化する・別のフローに統合する・リリースを延期する・削除する、のいずれもありえます。

3つ目の処方箋、「生成のプロセスに UX を入れる」がもっとも実装寄りです。同じ UX の問題が AI の出力に繰り返し現れるなら、毎回作り直すより、最初から起きないよう指示するほうが効率的だという理屈で、Design.md や UX.md のような UX コンテキストファイル、承認済みのインタラクションパターンを含むデザインシステム、コンテンツと書式の基準、アクセシビリティ要件、避けるべき欺瞞的パターンの一覧が候補に挙がっています。これは前の記事の「スキル」とほぼ同じ発想で、デザイン側から独立に同じ結論に到達しているのが興味深いところです。

締めくくりの言葉の使い方が効いています。custodian には「後始末をする人」と「大切なものを託された人」という2つの意味があり、UX が管理人であり続けるのは前者ではなく後者の意味においてだ、という着地です。古いプロセスそのものを守る必要はないけれど、そのプロセスが果たそうとしていたこと（人間のニーズを中心に技術を置くこと）は守る必要がある。掃除に追われている実感がある人にとっては、その時間を次の予防に変換する視点として読めます。

> 🐈‍⬛ : custodian に「後始末をする人」と「大切なものを託された人」の2つの意味があると気づいて着地させるのがうまい。トリアージの選択肢に「削除する」が入っているのが実際的で、渡された機能をすぐ磨き始めない、というのがこの循環を切る最初の一手になります。生成のプロセスに UX の知識を入れる、という3つ目の処方箋が Design.md や UX.md に落ちているのは、Anthropic のプレイブックの「スキル」と同じ発想にデザイン側から独立に到達しているということで、そこがいちばんおもしろいところ。

## [The task isn't the job](https://sunilpai.dev/posts/the-task-isnt-the-job/)

> **出典**: Sidebar | **公開日**: 2026-08-21 | **カテゴリ**: design

**3行まとめ**
- コーディングエージェントのおかげで「昼までに間違ったものを3つ作れる」ようになった、という書き出しのエッセイです
- Clayton Christensenのジョブ理論を引き、タスクを完璧にこなしても本来のジョブを外すことがあると指摘します
- 自律性は能力であって製品の方向性ではなく、「代わりにやって」「一緒にやって」「やり方を見せて」のどれが要るかはジョブが決めると述べます

**詳細解説**

Sunil Paiさんによる、しみじみと読ませる文章です。週に数万行、以前なら数日の覚悟が要ったアイデアを午後のうちに試せる。それ自体はいいことだけれど、ロードマップが10分の1に縮んだわけでもなければ、何を作る価値があるかを決める腕が10倍になったわけでもない。実装が押し潰されて消えた結果、難しい決断に早く到達するようになっただけかもしれない、と。

そこで持ち出されるのがジョブ理論です。人はプロダクトが欲しくて買うのではなく、生活のなかで前に進むために「雇う」。プレゼン用に30秒のBGMが要るだけなら、20秒黙って使えるものを返してくる機械は完璧な仕事をしています。ここで音楽家になりたかったわけではないので。けれど音楽を作りたくて座ったのなら、完成した曲を手渡されるのはかなりの読み違いです。コードを動かして、聴いて、悪くして、気が変わって、探していたと知らなかったものに行き当たる。その過程は結果に至るまでの摩擦ではなく、それ自体が目的でした。同じ成果物でも、ジョブがまるで違います。

もうひとつ効いているのが逆側の指摘です。保険会社と交渉して、返金を追いかけて、6人分のカレンダーで再調整して、フォームを埋めてほしい。そこに「神なるコンピュータとの楽しい共同作業」へ招待してこないでくれ、と。agency という言葉は関与できることを指すこともあれば、まるごと消せることを指すこともある。エージェントの進歩は自律できる時間の長さで語られがちですが、自律性は能力であって製品の方向性ではない、というのが主張の中心です。どれを選ぶかはジョブが決めます。

締めくくりは個人的な話です。南インドの小さな町で、安いインターネットとオープンソースと無料の学習素材によって人生が変わった。ただしそこには相当大きな入学試験があった。のめり込むような時間、運、国と街を移る選択。プログラミングは大きなてこを与えてくれたが、まずプログラマーにならなければならなかった。だから「知性をはしごにする」——知性を安くすることと、agency の前提条件を下げることは別の問題だ、という問いの立て方に着地します。エージェントをどこに置けるかから始めず、その人がすでにやろうとしていることから始める。どこが退屈で、どこで専門知識に詰まっていて、どこがそもそもやりたかった理由なのか。AI機能の要否を検討するときの順序として、そのまま使える問いだと思います。

> 🐈‍⬛ : 「代わりにやって／一緒にやって／やり方を見せて」の3択は、AI機能の仕様を書くときの最初の分岐に置ける形をしています。同じ30秒のBGMでも、プレゼンの素材が欲しい人と音楽を作りたくて座った人ではジョブが違う、という並べ方が効いていて、agency という語が「関与できること」と「まるごと消せること」の両方を指す、という指摘で腑に落ちます。保険会社との交渉に「神なるコンピュータとの楽しい共同作業」を持ち込まないでくれ、という一節が個人的には好き。エージェントをどこに置けるかから始めない、という順序は、今週の Custodial Era が言う「作る前に必要かを問う」とほぼ同じ場所を指しています。

## [Design's legibility gap](https://www.petermerholz.com/newsletter/designs-legibility-gap/)

> **出典**: Sidebar | **公開日**: 2026-08-27 | **カテゴリ**: design

**3行まとめ**
- UX/デザインが組織で苦戦する理由を、コミュニケーションではなく「見えなさ（legibility）」の問題として説明しています
- 事業は予測可能性を求め、そのために確定性を求め、確定的な仕事だけが評価対象になるという連鎖が背景にあります
- デザインリーダーの仕事は翻訳ではなく、事業が「見える」と認める範囲そのものを広げることだと結論づけています

**詳細解説**

Peter Merholz さんが「人間的な組織を成り立たせる条件は何か」という個人的な問いを掘るなかで出てきた概念を、UX/デザインの状況に当てはめた一本です。冒頭に並ぶ台詞に覚えのある方は多いはずです。「デザインは遅い」「デザインの ROI は」。予算を求めれば「10人も話を聞く? 顧客のことはもう分かっている」と言われ、調査結果を出せば「たった10人? それで信頼できるのか」と言われる。

土台にあるのは James C. Scott の『Seeing Like a State』です。18世紀のプロイセンとザクセンの科学的林業が例に引かれます。国家は木材収入を求めたので、森を「板材の材積」という指標でしか見ませんでした。下生えも倒木も無数の生物も、行政上は存在しないものとして扱われ、森はその指標に合わせて作り替えられます。無関係な種は伐られ、木は整然と列に植えられました。第一世代は見事に育ち、第二世代は崩壊しました。見えないものとして切り捨てた部分こそが、森を生かしていたからです。

対応関係が鮮やかです。森にとっての「板材の材積」が、UX/デザインにとっての「エンジニアが実装する画面」にあたります。その画面を最良のものにするための作業、つまり定性調査、スケッチ、発想、反復、構造化、マッピング、概念モデルの構築は、組織から見えていません。そしてこれはデザイン側の落ち度ではなく、事業運営の価値観の反映だという整理になります。組織は予測可能性を求め、予測可能性は確定性を必要とし、確定性が「見えるもの」の範囲を決めます。

見えない仕事の例が具体的です。4つのコンセプトを検討して1つを選ぶと、捨てた3つは存在しなかったことになり、なぜ最初から使えるやつから始めなかったのかと聞かれる。調査で要件の前提が崩れて顧客の実需に沿って組み直しても、ロードマップ上の名前が同じなら何も変わっていないように見える。下流の何百もの判断を規定する体験原則を書いても、どの判断もそこに遡って語られることはない。

歴史的な説明も納得感があります。エンジニアリング、マーケティング、営業、財務、オペレーションは、事業合理化の関門を並走して通り抜けてきました。MBA のカリキュラムに入り、測定によって標準化され、実務が体系化され、モデル・パイプライン・ファネルという共通言語を持つに至りました。デザインだけがその過程を通っていません。情報デザインとコミュニケーションデザインのスタジオ的伝統、HCI、情報科学、社会科学、人間工学。それぞれに固有の厳密さがあるのに、事業の文脈では読み取られないままです。

20世紀は、この仕事の大半がエージェンシーやコンサルティングという「不確定な仕事が見える場所」で行われていたので問題になりませんでした。21世紀に入って多くの事業がソフトウェア事業になり、UX/デザインが社内に移ったところで噛み合わせが悪くなります。事業が「デザインが必要だ」と言ったとき求めていたのは、人間中心の問題設定と問題解決ではなく、画面の制作と、せいぜいユーザビリティテストの実施でした。ROI の議論が徒労に終わるのも、採用や等級制度が噛み合わないのも、ここに理由があるという説明です。

UXエンジニアリングの視点では、この構図がそのまま自分たちにも刺さります。デザインシステムの整備、アクセシビリティ対応、リファクタリング、パフォーマンス改善。どれも「作られた画面」としては見えず、やらなかった場合の損失としてしか説明できません。記事の結論は、事業の言葉に翻訳し続けることではなく、事業が「見える」と認める範囲そのものを広げること。第二世代の森の運命を避けたいなら、開かれていて、探索的で、感情的で、意味があり、美しくもある不確定な仕事の価値を、組織が評価できるようにしていく必要がある、という締めくくりです。

> 🐈‍⬛ : 前号の「見えにくい仕事の価値が上がる」とも重なりますが、こちらは原因をデザイン側の説明不足ではなく組織の可視性に置いているのが違いです。18世紀の科学的林業で、板材の材積という指標に合わせて森を作り替えたら第二世代が崩壊した、という例が強い。翻訳し続けるのではなく、事業が「見える」と認める範囲そのものを広げる、という結論はデザインシステムの整備やアクセシビリティ対応にもそのまま当てはまります。捨てた3つのコンセプトが存在しなかったことになる、という例が具体的で、記録に残す価値がここにありそうです。

## [Every fork looks like adoption](https://blog.murphytrueman.com/every-fork-looks-like-adoption/)

> **出典**: Sidebar | **公開日**: 2026-08-25 | **カテゴリ**: design

**3行まとめ**
- GitClear の調査では、2023年比で他ファイルの関数呼び出しが35%減、リファクタリングが70%減、重複ブロックが81%増
- import 数ベースの adoption 指標は、使われていること（use）と再利用（reuse）を区別できません
- prop の形の変化、ラッパーの数、構造的類似の3つを見よう、という提案です

**詳細解説**

デザインシステムの採用率をどう測るか、という話です。出発点は GitClear のレポートで、4年間・6億2,300万件のコード変更を分析したところ、再利用が減って重複が増えていました。ただし、と著者は続けます。その数字の多くは、そもそも誰も再利用を約束していない一般的なコードベースのものです。デザインシステムの中では逆であるはずで、再利用こそが目的なのだから、と。

問題の形はシンプルです。あるチームが `Card` を持ってきて、自分たちの用途に少し合わせたい。`ProductCard` というローカルコンポーネントで包み、prop を3つ足して padding を調整する。以後そのチームは `Card` の代わりに `ProductCard` を使います。ラッパーは技術的には `Card` を import しているので、ダッシュボードはこれを採用としてカウントします。実際にコードベースにあるのは、プロダクトとデザインシステムのあいだに挟まった局所的な抽象です。健全な合成かもしれないし、フォークの始まりかもしれない。import 数はどちらかを教えてくれません。

以前はこれが人間の速度で起きていました。火曜日にあるチームがラッパーを作り、木曜日に別のチームが少し違うものを作る。ドリフトの蓄積が遅かったので、いくらかは捕まえられたわけです。「なんで同じコンポーネントが3種類あるの」と誰かが聞くか、デザインシステムのチームが「みんな同じプロパティを上書きしている」と気づくか。AI がコードを書くと、そこに至るコストが大きく下がります。「うちの `Card` みたいな感じで、料金プラン用に」と頼めば、import して包む・ほかと合成する・構造を再現して必要なところだけ変える、どれもそれらしい答えになります。同じデザイントークンを使っていれば、結果はプロダクトに完全に馴染んで見えます。

提案されている3つの指標が具体的です。ひとつ目は prop の形の変化。組み合わせの数そのものより、使われ方の形が変わっているかを見る。3つか4つの見慣れたパターンだったものが、一度きりの設定の長い尾を伸ばしはじめたら、理由を知りたい。API を使いこなしているのではなく、API を迂回している兆候かもしれません。2つ目はラッパーの数。ラッパー自体は悪ではなく、合成はコンポーネントシステムが機能する理由のひとつです。問うべきは次に何が起きるか。薄いままか、それとも独自の prop・スタイル・バリアント・振る舞いを溜めはじめるか。みんなが `Card` ではなく `ProductCard` を覚えることになっていないか。バグをラッパー側で直して、機能をシステムに還元しなくなっていないか。3つ目、著者がいちばん重視するのが構造的類似です。デザインシステムのコンポーネントに似ているのに、そこから import していないコード。`Button` を import しない Button、`Card` にそっくりなローカルの Card、同じ状態と間隔とインタラクションを独自に再発明した Modal。jscpd のような重複検出は昔からありますが、デザインシステム向けには「新しいコンポーネントがシステムの既存物に不審なほど似ていないか」という具体的な問いになります。

レビューの話が現実的でした。以前は UI コンポーネントを新しく書くこと自体が高くついたので、「もう似たようなものがあるんじゃないか」と誰かが聞く程度の摩擦がありました。いまはその会話が起きる前にコードが存在します。レビュアーの前にあるのは完成した PR で、動くし、テストは通るし、正しいトークンを使っている。「これ、もうあるんじゃないか」に答えるには、コードベースを検索してドキュメントを読んで既存コンポーネントで足りるか確認して、20分かかります。毎回やる人はいません。だから、レビュアーの手前でシステム側が捕まえる。「このコンポーネントは design-system/Card と構造的に似ています」と出すだけでいい。マージをブロックしなくても、会話が起きればそれで十分だ、という着地です。

締めの一文が効いています。フォークはずっと adoption に見えていた。ただ、以前はそれなりに高くついたので、誰かが気づいていただけだ、と。

> 🐈‍⬛ : import 数は「使われている」ことしか言わず、再利用かフォークかは区別しない。この切り分けが効くのは、採用率ダッシュボードを持っているチームほどでしょう。3つの指標のうち、著者がいちばん重視する構造的類似——`Button` を import しない Button——は、jscpd 的な重複検出をデザインシステム向けに問い直したもので、実装の手が届く範囲にあります。「これ、もうあるんじゃないか」に答えるには20分かかるから誰もやらない、という観察が正確で、だからマージをブロックせず会話だけ起こす、という落としどころが現実的。

## [Workflow lab: Moving between design and code with agents](https://www.figma.com/blog/workflow-lab-moving-between-design-and-code-with-agents/)

> **出典**: Figma Blog | **公開日**: 2026-08-26 | **カテゴリ**: design

**3行まとめ**
- スクリーンショットとチケットだけを渡すと AI の出力がデザイン仕様からずれる、という前提から始まる架空チームのワークフロー実演です

- 最後は `use_figma` でコードだけに存在していたトーストを Figma のレイヤーとして書き戻し、両方向をつないで終わります

**詳細解説**

Figma の Workflow Lab シリーズの1本で、Radicle という架空の STEM 学習アプリのチームが受信箱の一括操作フローを作る話です。設定が具体的なので、どのツールをどの順で使うかが追いやすくなっています。

最初の失敗の描写に見覚えのある人は多いはずです。デザイナーが各画面を Figma で作り、開発者がそれをコーディングエージェントに渡す。コードはすぐ返ってくるものの、UI がずれている。アイコンが違い、モーダルの余白が不揃いで、トーストには失敗状態がない。午後いっぱいを手直しに使うこともできますが、この記事の開発者は一度立ち止まって、Figma の開発者向けツールからやり直します。

段取りが良いのは、プロンプトの前に計画を置いている点です。画面・状態・遷移の意図を書き出し、PRD と現在のコンポーネントのコードと一緒にエージェントへ渡したうえで、`generate_diagram` で FigJam に編集可能な図を作ります。この図はエージェントの材料になると同時に、開発が始まる前にチームが反応できるものにもなります。デザイナーとデザインシステムのリードが Slack のスレッドではなく図の上に直接フィードバックを残す、という書き方が具体的です。

その後の各ツールの役割分担が整理されています。Figma MCP サーバーがコンポーネント・トークン・レイアウトへのアクセスを与え、Code Connect が「どのコンポーネントか」から「それがどう実装されているか」へ橋を架けます。一括操作の選択状態だけは Code Connect で対応づけられていない新しい部品でしたが、ゼロから作る前に `search_design_system` でチーム全体のライブラリを検索し、数か月前に出荷した機能から似たコンポーネントを見つけてコードベース内の実装を流用しています。「チームがすでに作ったパターンをエージェントに発明させない」という一文が、この節の要点でしょう。

もっとも実務的なのは、ドリフト（ずれ）を検知する部分です。開発者が確認モーダルを実装している最中に、デザイン側でブランドカラーを暗くし、ボタンの角丸を変更してライブラリに公開しました。手で直す代わりに `get_variable_defs` を呼ぶと、モーダルで使われている変数が更新後の値で返ってくるので、エージェントがコード側のトークンと突き合わせて2か所の不一致をその場で直します。デザイン変更の伝達がチケットの文面ではなく変数の照合になるので、伝え漏れの余地が減るという話です。

そして締めが逆方向です。トーストはビルド中に作られたのでコードにしか存在せず、失敗状態が足りていませんでした。`use_figma` でトーストを編集可能なレイヤーとしてキャンバスへ置き、デザイナーが「再試行」アクションのある状態を足し、デザインシステムのリードが新しいコンポーネントとして公開して Code Connect でコードへマッピングする。実装から生まれた部品が正式にシステムへ戻る経路まで含めて描かれているのが、この記事のいちばんの価値だと思います。

UXエンジニアリングの視点でいうと、ここで実演されているのは「エージェントの出力品質を上げる方法」というより「デザインシステムの投資が何に効くか」の話です。Code Connect のテンプレート整備も、ライブラリの検索性も、変数として定義されたトークンも、人間だけが読む前提では後回しにされがちでした。エージェントが同じ資産を読むようになると、その整備の見返りが直接コードの精度に出ます。逆にいえば、システムが整っていない状態でエージェントに文脈を渡そうとしても、この記事の手順はそのままは効きません。何から手をつけるかの優先順位を考える材料として読むのが良さそうです。

> 🐈‍⬛ : 実装中に生まれたトーストが Figma のレイヤーとして書き戻り、コンポーネントとして公開されて Code Connect でコードに戻る。その往復まで描いているのが、この記事の値打ちだと思います。`search_design_system` で既存パターンを探してから作る、という一手が入っているのも良くて、エージェントに発明させないための最短の対策になっている。前の「Every fork looks like adoption」と裏表の関係で、あちらがフォークを検知する話なら、こちらはフォークが要らない状態を先に作る話です。整っていない DS に文脈だけ渡してもこの手順は効かない、という前提は正直に受け止めておきたい。

## [Your alt text passes automated checks. That doesn't mean it's any good.](https://github.blog/engineering/user-experience/your-alt-text-passes-automated-checks-that-doesnt-mean-its-any-good/)

> **出典**: GitHub Engineering | **公開日**: 2026-08-24 | **カテゴリ**: engineering

**3行まとめ**
- WebAIM Million 2026 では、alt が欠けている画像が16.2%、内容を説明しない alt がさらに10.8%という数字が出ています
- GitHub がアクセシビリティスキャナ向けの alt text プラグインを、決定的な5つのルールとオプトインのモデル呼び出し1つに分けて作った記録です
- 「証明できること」と「疑えるだけのこと」を分けて既定値を変える、という自動チェック設計の指針が読みどころになっています

**詳細解説**

出発点は、既存のチェッカーがほとんど「アクセシブルな名前が存在するか」だけを見ている、という指摘です。しかもそれは手抜きではなく設計判断で、品質を見るルールは誤検知を出した時点でチームに切られてしまう、という理由があります。だから `alt="IMG_2847.png"` は通ってしまうし、5つの星アイコンに同じ `alt="3/5 stars"` が付いていても通ります。ここを埋めるために作られたのが、GitHub Accessibility Scanner 向けの [alt text プラグイン](https://github.com/github/accessibility-scanner-alt-text-plugin)です。

決定的に判定できるルールは5つに絞られました。属性そのものがない（空ではない）か空白だけ、ファイル名になっている、`TODO` のような置き換え忘れのプレースホルダ、`image` や `logo` のように中身ではなく媒体を指す一語、隣り合う画像で同じ alt が繰り返される。どれも「文字列についての主張」で、そこが線引きになっています。判定対象を集めるところでは `querySelectorAll('img')` ではなく Playwright のロール指定ロケータを使い、アクセシビリティツリーに載らないものを落とします。`alt=""` が外れるのが効いていて、空の alt は「これは装飾です」という作者の明示なので、そこを指摘すると促したい振る舞いを罰することになるからです。

厳しさの調整も割り切っています。曖昧な alt のルールは正規化したあと、単語の閉じたリストと完全一致したときだけ発火します。`alt="image"` は引っかかり、`alt="image of the login screen with the SSO button highlighted"` は引っかかりません。見逃しは増えますが、切られないチェッカーのほうが価値がある、という判断です。反復の検出でつまずいた話もおもしろく、最初は DOM の順に見て同じ alt の連続を指摘していたところ、フッターとヘッダーの GitHub ロゴのように、抽出リストでは隣なのに画面上は離れているものを拾ってしまいました。そこでバウンディングボックスの隙間が箱の大きさに比べて小さいときだけ連続とみなす形に変えています。乗数は仕様から導いた数字ではなく実際のページで調整する値、箱が測れないときは連続を切らずに素通りさせる（見逃しは見えないが誤検知は見える）という注記が添えられます。

モデルを入れた部分の失敗は、画像の読み間違いではなく「モデルが意見を持つこと」でした。良い alt を渡しても別案を出してくる。「もっと良くできるか」という問いに言語モデルは常に yes と答えるので、全画像が指摘になって信号が消えます。効いた対策が3つ挙がっていて、指示ではなく4段階の決定手続きにして最初に当たった段階で止める、細かい指摘の禁止を明文化する（作者の枠組みを信じる、`Image of…` のような冗長な接頭辞と `Photograph of…` のような意味のある接頭辞を分ける、周辺の文章がすでに画像を説明しているなら短い alt を正しいと扱う）、構造化出力のフィールド順を固定して `reasoning` を `verdict` より先に生成させる、というものです。プライバシーとコストの扱いも具体的で、既定オフ、URL のクエリとフラグメントの除去、`src` と `srcset` を `(omitted)` に置換。そのうえで「指摘には実際のページ URL と元の HTML が乗るので、除去で狭まるのはモデルとログに届く範囲だけ」と、読み過ぎを止める注意まで書かれています。

UXエンジニアリングの視点でいちばん持ち帰れるのは、締めの一文です。DOM が何と言っているかではなく、利用者が何を経験するかを問う。反復をレイアウトで判定したのはまさにそれで、残っている限界（リンクの中にあることは記録するが、リンクの唯一の内容かは見ていない。属性を読むので `aria-label` で直しても指摘が止まらない）はどれも同じ形をしています。決定的なチェックはゲートに置き、疑いにとどまるものは提案として人に回す。この仕分けはビジュアルリグレッションやパフォーマンス予算にもそのまま持ち込めます。

> 🐈‍⬛ : 「証明できること」と「疑えるだけのこと」で既定値を分ける、という設計の指針が、alt text の話を超えて使えます。決定的なルールを5つに絞ったのも、曖昧な alt を閉じたリストとの完全一致に限ったのも、見逃しを増やしてでも切られないほうを取るという判断。反復の検出を DOM 順からバウンディングボックスの距離に変えた話がいちばん好きなところで、「DOM が何と言っているかではなく、利用者が何を経験するか」を実装のレベルで一度やってみせています。モデルの失敗が読み間違いではなく「意見を持つこと」だった、というのも示唆的。

## [新API「HTML-in-Canvas」を紹介 - CanvasにHTMLを描くAPIは何を解決するのか？](https://ics.media/entry/260825/)

> **出典**: ICS MEDIA | **公開日**: 2026-08-24 | **カテゴリ**: frontend

**3行まとめ**
- 派手なエフェクトの話題が先行していますが、このAPIが解こうとしているのは Canvas のテキスト描画と UI 自作の課題です
- `layoutsubtree` 属性と `drawElementImage()` メソッドの3ステップで、HTML をそのまま Canvas に描けます
- アクセシビリティーは改善しますが、プライバシー対策で IME やスペルチェックの表示は描画から除外されます

**詳細解説**

matsumoto さんによる、いま提案段階にある HTML-in-Canvas の解説です。冒頭で VFX-JS のデモや、普通のフォームにブラウン管風の表現や雨粒を乗せた作例が紹介されますが、そこで終わらないのがこの記事の良いところで、「このAPIの本質はそこではありません」とはっきり書いたうえで、地味な課題のほうに話を進めます。

Canvas の課題は2つに整理されています。ひとつはテキスト描画です。`fillText()` は指定座標に1行書くだけで、はみ出しても折り返さないし、一部だけ太字にもできません。末尾を「…」で省略したければ `measureText()` で幅を測りながら自分で切り詰めます。OGP 画像の生成、チャートの軸ラベル、ゲーム内 UI。どれも「ちょっとテキストを載せたいだけ」なのに、気がつけばテキストレイアウトエンジンを自作している、という指摘には覚えのある方も多いはずです。さらに多言語が厄介で、アラビア語の連結処理、タイ語やヒンディー語の複雑な字形整形、日本語の縦書き・ルビ・禁則。ブラウザーの HTML レンダラーが長年かけて育ててきた処理に、Canvas はほとんど追従できていませんでした。

もうひとつが UI パーツの自作です。Canvas 上に「きちんと押せるボタン」を作ると、矩形の描画に加えてクリック判定、ホバー時のカーソル変化、Tab によるフォーカス移動、Enter での実行、スクリーンリーダーへの通知まで全部自前になります。HTML なら `<button>` と書くだけのものです。

使い方は3ステップと簡潔です。`<canvas>` に `layoutsubtree` 属性を付け、描きたい HTML を `<canvas>` の直接の子要素として置き、`drawElementImage()` で描く。記事では3段階のデモでこれを見せています。ワンショットで転写するだけなら1行で、ルビも折り返しも CSS のフォントもそのまま画像になります。リアルタイムに動かしたい場合は `paint` イベントと `requestPaint()` を使うだけ。ここで「なぜボタンが押せるのか」という疑問が出ますが、答えは、子要素として置いた HTML は見えていないだけでその場所に存在しているからです。イベントは本物の要素が受け取り、表示が変われば `paint` が発火して Canvas が描き直されます。3つ目は座標系の一致で、`drawElementImage()` の戻り値である `DOMMatrix` をそのまま HTML 側の `style.transform` に設定すると、移動・拡大・回転したあとのフォームも操作できます。

アクセシビリティーについての書き方が慎重で、参考になります。よくなる面は明確で、`fillText()` で描いた文字はただの絵なのでアクセシビリティーツリーに載らず、選択もコピーもページ内検索も翻訳も効きませんでした。HTML-in-Canvas で描いたものは裏にある本物の要素なので、それらが自動的に動きます。支援技術を使っていない人にも効く話です。ただし「これで Canvas のアクセシビリティー問題が解決する」と受け取ると話が変わってきます。従来もフォールバックコンテンツは置けたのに使われなかった理由は、仕組みではなく描画内容との二重管理が難しかったからでした。HTML-in-Canvas はその二重管理をある程度自動化しますが、円グラフを描くなら、ラベルは読み上げられても円弧は依然として `ctx.arc()` のピクセルです。`<img>` に適切な `alt` を付けるのと同じで、必要な対応は設計する側の仕事として残ります。

プライバシーの部分がいちばん考えさせられます。HTML の描画結果には OS のテーマカラー、訪問済みリンクの色、IME の変換候補、字幕の表示設定といった、JavaScript から直接読めないユーザー固有の情報が大量に含まれています。まるごと画像化できると筒抜けになるので、Chrome の答えは「機微な情報をリスト化して最初から描画しない」でした。除外されるのは IME の未確定文字列の下線、スペルチェックや文法チェックの波線、OS のテーマカラー、訪問済みリンクの色の変化、未確定のオートフィル内容、クロスオリジンのコンテンツ、字幕・キャプションの設定など。記事はここに2つの課題を挙げます。リスト方式は OS やブラウザーに新しい UI が入るたびに追加が必要になること。そして、本来必要だから提供されている表示を削るのは利便性やアクセシビリティーを損なう行為であること。単にカッコいいエフェクトのためにページ全体を HTML-in-Canvas で描いてよいかは、慎重な判断が要ります。

各社の状況は2026年8月時点で、Chrome がオリジントライアルを Chrome 154 まで延長（WebGL・WebGPU 向け API とプライバシー面に大きな変更を入れたため）、WebKit は公式なポジション未表明ながら7月から試験的実装が始まっていて、Firefox は「Needs proposed position」のまま。課題感は共有されているが解決手段としての受け入れは未決着、という整理でした。

> 🐈‍⬛ : 派手なデモから入って「このAPIの本質はそこではありません」と切り返す構成が良いです。テキストを載せたいだけなのに気がつけばレイアウトエンジンを自作している、という指摘には覚えがあるはず。アクセシビリティーについての書き方が慎重で、二重管理が自動化されるだけで、円グラフのラベルが読めても円弧はやはり `ctx.arc()` のピクセルのまま、と釘を刺しています。プライバシーの除外リストが OS に新しい UI が入るたび追加を要する、という構造上の弱さまで書いてあるのが誠実なところ。

## [Controlling when CSS custom properties are computed](https://jakearchibald.com/2026/css-custom-property-compute-time/)

> **出典**: Jake Archibald | **公開日**: 2026-08-26 | **カテゴリ**: web-standards

**3行まとめ**
- 未登録のカスタムプロパティは値がトークン列のまま保持され、使われた場所で評価されます
- `@property` で `syntax` を指定すると計算のタイミングが早まり、宣言した場所の文脈で確定します
- `var()` は「任意置換関数」なので、syntax の指定に関係なく即座に置き換えられます

**詳細解説**

Jake Archibald さんによる、短いながら効きどころを突いた解説です。題材は `sibling-index()`。Firefox 154 で Baseline 入りしたばかりの関数で、要素が兄弟の何番目かを1始まりで返します。

問題設定が巧みです。`.second-item` で `--index: sibling-index()` と定義し、その子要素で `scale: var(--index)` と使ったとき、拾われるのは定義側の div の順番なのか、使用側の子要素の順番なのか。答えは「場合による」。登録していないカスタムプロパティは `syntax: '*'`（何でも）として扱われ、値はトークン列のまま保持されます。つまり `var()` が `sibling-index()` そのものに置き換わり、それが使われた文脈で評価されます。子要素は親の最初の子なので `scale: 1` になります。`getComputedStyle()` で `--index` を読むと文字列 `"sibling-index()"` が返ってくる、というのが証拠として示されています。

ここで `@property --index { syntax: '<number>'; inherits: true; initial-value: 0; }` と登録すると挙動が変わります。`<number>` と指定した時点で、値は宣言された場所で数値として計算されます。`.second-item` は2番目なので `--index: 2` が確定し、子要素は `scale: 2` になります。同じ CSS が、登録の有無だけで別の結果を出す。`getComputedStyle()` も `"2"` を返すようになります。

影響を受けるのは `sibling-index()` だけではありません。相対的なフォント単位（`em`、`ex`、`ch`、`cap`、`lh` など）、コンテナクエリ単位（`cqw`、`cqi`、`cqb` など）も同じ話になります。少し性質が違うものとして URL の例が挙がっていて、CSS の URL は計算値の時点でスタイルシートの基準 URL に対して解決されます。トークン列のカスタムプロパティを別のスタイルシートから `var()` すると、消費した側のスタイルシートを基準に解決されてしまう。`syntax: '<url>'` で登録しておくと、宣言したスタイルシートに固定されます。

さらに一段ややこしい例が最後にあります。`--multiplier: 1` と `--index: calc(sibling-index() * var(--multiplier))` を定義し、子要素で `--multiplier: 3` を上書きしてから `var(--index)` を使う場合です。`var()` は `if()`、`attr()`、`ident()` などと同じ「任意置換関数（arbitrary substitution function）」に分類され、カスタムプロパティの syntax に関係なく即座に置き換わります。したがって `--index` は定義された時点で `calc(sibling-index() * 1)` になっており、子側の `--multiplier: 3` は無視されます。そのあと `sibling-index()` がどこで評価されるかだけが、syntax によって変わります。

UXエンジニアリングの視点では、デザイントークンを `@property` で登録するかどうかの判断材料としてそのまま使えます。登録するとアニメーション可能になり、型による安全性が得られ、値の計算が早まります。逆に、コンテナクエリ単位や相対フォント単位をトークンに含めていて「使われた場所の文脈で解決してほしい」なら、登録しないほうが意図どおりに動くケースがあります。どちらが正しいという話ではなく、どちらの挙動が欲しいかを意識して選ぶ、という整理が持ち帰りどころです。Jake さん自身も「`@property` が計算のタイミングを変えることは何となく知っていたが、いつ、どう変わるかは調べるまで分かっていなかった」と書いていて、正直で好感が持てます。

> 🐈‍⬛ : `@property` で登録すると計算のタイミングが早まる、という副作用は知らずに踏みそうです。同じ CSS が登録の有無だけで別の結果を出す、というのが `getComputedStyle()` の戻り値で示されるので、疑いようがない。デザイントークンにコンテナクエリ単位や相対フォント単位を入れているなら、あえて登録しないほうが意図どおりというケースがあるわけで、`@property` を付けるかどうかがトークン設計の判断項目に一つ増えた感じがあります。「何となく知っていたが、いつどう変わるかは調べるまで分かっていなかった」と書いているのが良い。

UXエンジニアリングの視点で興味深いのは、この仕事が徹底的に制約下で行われた点でしょう。数十ピクセル四方の白黒という条件で、しかもゴミ箱やフォルダのように毎日何千回も見られるものを設計していました。制約は選択肢を狭める一方で、判断の数を減らして反復を速くもします。いまの高解像度・多色・アニメーション可能な環境では、同じアイコンに何時間でもかけられるぶん、どこで止めるかが自分で決められません。「アイデアが即座に伝わるだけのちょうどよい量のディテール」という基準は、その止めどころを言葉にしたものとして読めます。アイコンセットに限らず、空状態のイラスト、ローディングの表現、ステータスの記号など、意味を最小の形に落とす場面ならどこでも同じ問いになります。

> 🐈‍⬛ : 数十ピクセル四方の白黒という条件が、選択肢を狭める代わりに判断の数を減らして反復を速くしていた。今週の並びのなかで読むと、この見方がいちばん効いてきます。「アイデアが即座に伝わるだけのちょうどよい量のディテール」は、止めどころを言葉にした数少ない基準で、アイコンに限らず空状態のイラストにもローディングの表現にも持ち込めるもの。制約が消えた環境では止めどころを外から決めてもらえないぶん、この種の基準を自分で持つ必要が出てきます。Vibe coding の記事が「反復の回数が品質を決める」と言っていたのに対して、こちらは「その反復をどこで打ち切るか」を扱っていて、2本でちょうど対になっています。
