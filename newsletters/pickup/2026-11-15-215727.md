## [What does design system AI readiness mean, anyway?](https://seanvoisen.com/writing/design-system-ai-readiness/)

> **出典**: Sidebar | **公開日**: 2026-11-09 | **カテゴリ**: design

**3行まとめ**
- デザインシステムの AI 対応として、ドキュメントを機械で読める形にする、MCP サーバーを用意する、といった対策は広がっていますが、何ができれば「対応できた」といえるのかは決まっていない、と問いを立てています
- 人の代わりに AI がデザインシステムを使うと「もっともらしいずれ」が大量に生まれ、ルールをすべて守った設定画面でも、デザイナーが見るとどこかずれています
- 品質の下限を保ったまま、上限のどの部分を人が支え続けるかをチームが意図して決めている状態を、AI に対応できた状態と定義しています

**詳細解説**

前提として、デザインシステムはもともと品質の下限しか保証しておらず、上限は使う人の判断が支えてきた、と整理しています。AI 向けの対策は2つに分けられます。AI に渡す文脈とルールで生成の幅を絞る方法と、評価や批評のループで出力を確かめる方法です。多くのチームは下限を守るほうに力を入れていて、上限のどこを手放せるかはあまり問われていない、という見方です。

AI に部品を使わせる検証のやり方として、PJ Onori さんの実験も紹介しています。決まったプロンプトでは結果がよすぎたので、予測できない実際の使われ方に近づけるために、ランダムなプロンプトを混ぜています。

書き出せない暗黙の知識については、David Hoang さんの「デザインの台帳」の考えを借りて、作業のなかで記録を残すことを提案しています。レイアウトの決定、意図してシステムから外した場面、アクセシビリティと情報密度がぶつかったときの選択を記録していけば、生成を絞る材料にも、出力を評価する材料にもなるとしています。まだ試していないと断ったうえで、監視の道具に使われうること、過去の決定をなぞりやすいことも欠点として挙げています。

> 🐈‍⬛ : 先週のDESIGN.mdの検証で見えた「書いたことは守られるが、書いていないことは出てこない」は、この記事の言葉でいえば、下限は守れても上限は守れないということになります。デザインの台帳の案は、書き出せない判断を作業のついでに少しずつ残していく方法で、このあと紹介するNunebotの `taste.md` が実際にやっていることにかなり近い形です。

## [Agent Harness: Definition](https://www.nngroup.com/articles/agent-harness/)

> **出典**: Nielsen Norman Group | **公開日**: 2026-11-06 | **カテゴリ**: design

**3行まとめ**
- 同じ AI モデルを使っていても、できることはモデルを囲むソフトウェア「ハーネス」で決まる、という考え方を NN/g が UX の側から整理しています
- ハーネスは、モデルが求めたツールの呼び出しを権限に照らして実行するループを回し、モデルに渡す文脈と、時間・費用・手順数の上限も管理します
- UX の担当者には、画面と一緒に振る舞いを仕様に書くこと、AI の評価では文脈やツール、権限まで本番に近い形でタスク全体を試すことを勧めています

**詳細解説**

「金曜は会議を入れない」と設定を保存していても、ハーネスがそれをモデルに渡さなければ、日程調整アシスタントは金曜を提案し、利用者は同じ希望を言い直すことになります。PDF を渡したときに、テキストだけを抜き出すか、ページを画像にもするかで、レイアウトで示された関係をモデルが読み取れるかどうかも変わります。

全員の都合が合う時間がなかったとき、探し続けるのか、任意参加の人がいないかを聞くのか、ほかの週を提案するのかは、ハーネスの指示と上限で決まります。モデルは指示にいつも従うとは限らないので、ハーネス側で応答を検査して出し直させる方法もあります。権限については、ハーネスとアプリを分けて説明しています。ハーネスで承認しても、接続先のアプリ側の制限はそのまま効きます。

評価のテストには、カレンダーの接続が切れた、設定が変わった、誰の都合も合わない、といった場面を入れるよう勧めています。タスクを取り消せるなら、何が止まり、送信済みの招待のような済んだ操作がどうなるかも決めておくよう求めています。読み込み中やエラーと同じく、画面の状態の一覧に載せる項目になりそうです。

> 🐈‍⬛ : 「金曜は会議を入れない」が伝わらない例は、モデルの賢さより、まわりのソフトウェアが何を渡すかの問題として書かれています。UXエンジニアが手を入れられるのはこの部分で、接続が切れた、誰の都合も合わない、取り消した、といった場面を画面の状態の一覧に足しておくと、デザインと実装の話がかみ合いやすくなります。

## [Building interfaces that understand what we want to do](https://agustinbarrientos.com/writing/senior-eye/interfaces-that-understand-what-we-want)

> **出典**: Sidebar | **公開日**: 2026-11-13 | **カテゴリ**: design

**3行まとめ**
- 決まった選択肢から1つを選び、選択肢ごとの確率を返す「判断モデル（decision model）」を UI に組み込む方法を、その場で試せるデモとコードで解説しています
- Chrome の Decisions API を使うと、ブラウザのなかのモデルで、無料かつオフラインで判断できます。ただしまだフラグを有効にしないと使えない実験段階で、延長されなければ Chrome 161（2027年1月19日予定）でフラグがなくなります
- 8つのモデルを5種類のテストで比べたうえで、しきい値は間違えたときの損の大きさで決め、正解のわかっているデータで調整するよう勧めています

**詳細解説**

レストランのたとえでは、客（利用者）は好きな言葉で注文し、店員（AI）は何を勧めるか予測できませんが、出せるのはメニューにある料理だけです。メニューは作り手が書くので、利用者が目にする文言はすべて事前に書いてレビューし、翻訳しておけます。`if` で書ける判断なら `if` で書き、生成 AI は多くの判断には重すぎる、という立場です。記事の計測では、Claude Haiku 5.5 は判断モデルの Jev に比べて約5倍の時間がかかり、費用は約3倍でした。

デモは3つあります。王に会わせるよう門番を説得するミニゲーム、送り先のチャンネルに合わない投稿を送る前に警告するチャット、選んだ文から「タスクを作る」「カレンダーに保存」などの操作を1つ提案するタスク管理です。しきい値は損の大きさで変えています。操作の提案は、外れても「引用」が残るだけなので50%で出します。チャットの警告は70%から始め、問題のない投稿にも出すぎたので98.5%に上げ、さらにスペイン語の機微な投稿が98.4%だったので98%に下げました。

「用件を答えたか」をはい・いいえで聞くと、Gemma 4 は本当の答えにも「いいえ」と返したので、4択に変えています。選択肢の順番を逆にしただけで、賄賂を差し出した人を含む4人の敵意のある訪問者が門を通りました。Chrome の新しい小さなモデル EmbeddingGemma は Gemma 4 より26〜59倍速い一方、正しい選択肢を選べる割合は Gemma 4 の半分ほどです。

選択肢の数だけ UI の反応を作るので、デザインでは選択肢ごとの画面の状態を描くことになります。確信度がしきい値に届かないとき、門番が「はっきり言え」と聞き返すように、確信度が足りないときの状態も1つ描いておくと、実装との食い違いが減りそうです。本番では Chrome の API を先に試し、使えなければ Gemini Decision 1 などのクラウドに切り替える組み方を勧めています。Gemini の無料枠は1日10,000回までで、送った内容は Google の製品改善に使われます。

> 🐈‍⬛ : 利用者が目にする文言をすべて事前に書いてレビューできる、という点に安心感があります。生成AIを使う画面では文言の確認がどうしても後追いになりますが、判断モデルならそれを選択肢の設計の段階に戻せます。チャットの警告のしきい値を70%から98.5%、98%と動かした経緯を見ると、外れたときの困り方を見ながら数字を詰めていく様子がよくわかります。

## [Fact-Checking at Scale: Building a More Accurate and Efficient Synopsis Factuality System](https://netflixtechblog.com/fact-checking-at-scale-building-a-more-accurate-and-efficient-synopsis-factuality-system-d7d85859d808)

> **出典**: Netflix Tech Blog | **公開日**: 2026-11-09 | **カテゴリ**: engineering

**3行まとめ**
- Netflix の作品紹介文（シノプシス）が事実に合っているかを LLM で判定する仕組みを作り直し、1件あたりのコストを52.4%下げています
- 同じ汎用の判定を5回くり返すのをやめ、「文字どおり正しいか」と「見ていない人に誤った印象を与えないか」を別々の判定役に見させています
- 判定役が理由づけのなかで迷った点を取り出し、確かめられる小さな主張に分けて再確認する手順を加えて、誤った紹介文の見逃しを減らしました

**詳細解説**

紹介文の誤りは2種類に分けています。設定が違うといったはっきりした誤りと、書いてあることは全部正しいのに作品の印象がずれる誤りです。後者の例として、『ブリジャートン家』の紹介文が2つ出てきます。ゴシップ紙を書くレディ・ホイッスルダウンが主役のように読める文と、偽の交際から始まる2人がすぐに恋に落ちるように読める文です。LLM に書かせた UI の文言を確かめるときも、「仕様と食い違っていないか」と「読んだ人が誤解しないか」を別々の確認にしておけば、どちらで落ちたかを出力から読み解く手間が減りそうです。

以前の仕組みは、作品の情報を10万トークン以上まとめて推論モデルに渡し、同じ判定を5回くり返して、1回でも不合格なら落とすものでした。調べると、はっきりした文では5回とも同じ結論になり、意見が割れるのは微妙な文だけでした。そこで判定と一緒に確信度を出させ、確信度の低いものだけを追加の確認に回しています。同じ判定役を何度呼んでも、理由づけが同じ方向に間違っていれば結論は変わりません。

追加の確認では、仮定を置いた箇所、渡された資料だけでは決められない疑問、矛盾に気づいたのに「結論は変わらない」と流した箇所を、判定役自身に挙げさせます。それをルーターが確かめられる主張に書き直し、Web を調べる判定役か、資料を見直す判定役に振り分けます。不合格の紹介文を見逃さない率（Recall-Fail）は 0.77 から 0.86 に上がり、判定の理由が人の注釈者の挙げた理由と重なる割合も、約69%から約82%になりました。処理時間の中央値は延びています。

> 🐈‍⬛ : NN/gのハーネスの記事にあった、応答を検査して出し直させる仕組みを、本番の規模で組んだ例として読めます。確信度の低いものだけを追加の確認に回す組み方は、ひとつ前のしきい値の話とも通じていて、どちらも全部を同じ重さで確かめないことでコストを下げています。

## [LDRライクなRSSリーダのIrodrをReact 19 + Vite+で書き直して、iPhone Duoにも対応した](https://efcl.info/2026/11/07/irodr-2/)

> **出典**: Web Scratch | **公開日**: 2026-11-07 | **カテゴリ**: frontend

**3行まとめ**
- 9年使い続けてきた LDR 風の RSS リーダー Irodr を、見た目とキー操作はそのままに、React 19 と Vite+ で書き直した azu さんの記録です
- JS は gzip 後で 397kB から 150kB に、本番ビルドは27秒から0.5秒に縮み、ブラウザで動く依存は48個から4個になりました
- 書き直しは Claude Code に任せ、書き方のルールを Lint で強制し、外部 API を再現した Fake Server に対してテストしながら進めています

**詳細解説**

2.0 では、Inoreader のフィードと GitHub Notifications を同じ画面・同じキー操作で読めるようにしています。Inoreader の Pro プランで購読数が上限の2,500に近づいたので、購読の大半を占めていたリポジトリのリリース通知を GitHub に移しました。どちらも同じ `Source` インターフェースで扱うので、UI の側ではどのソースのフィードかを区別しなくて済みます。

AI に書かせたコードの書き方は、レビューで指摘するのをやめて Lint で守っています。`let` やクラスを禁止するルールを Oxlint の JavaScript プラグインとして自作し、Oxlint に入っている React Compiler 向けのルール（`react/purity`、`react/refs` など）も有効にしました。React Compiler は扱えないコンポーネントを警告なしにスキップするので、そうしたコードがあれば `vp check` が失敗するようにしています。クラスから関数への書き換えでは、新旧の Reader に同じ操作を流し、記録した30のシナリオと約8,800回のランダムな操作で、差分が出ないことを確かめています。

操作感の数字は、Fake Server に40フィード×20記事を入れた同じ条件で、CI 上で新旧を比べたものです。`s` を押して次のフィードの記事が出るまでの時間は 66ms から 23ms に、CPU を4倍遅くした条件では 215ms から 111ms になりました。一方で、`s` で移動したフィードが見出しの下に隠れる、blockquote の見た目が 1.x と違う、といった問題は自動テストでは見つかりませんでした。これらは実際に使うなかで見つけ、スクリーンショットや画面収録を添えて AI に直してもらっています。

iPhone Duo への対応では、Viewport Segments API の CSS メディア特性 `horizontal-viewport-segments` と `vertical-viewport-segments` だけを使い、左右に開いたときと上下に開いたときでレイアウトを変えています。Safari 27.1 では、この API は機能フラグを有効にしたときだけ使える開発者プレビューです。また、`env(viewport-segment-height 0 1)` は実際の画面よりかなり大きな値を返していました。そのため、下に置くボタンの高さはビューポートの高さの4分の1で決めています。

> 🐈‍⬛ : AIに書かせたコードの書き方をレビューで指摘するのをやめてLintで守る、という分け方は、Voisenさんの言う下限の守り方をそのまま形にしたものです。それでも、フィードが見出しの下に隠れる問題は自動テストでは見つからず、9年使い続けてきた本人が使いながら見つけています。iPhone Duoで使ったViewport Segments APIは、次のRoselliさんの記事でもInterop 2027の候補に挙がっています。

## [My Interop 2027 Picks](https://adrianroselli.com/2026/11/my-interop-2027-picks.html)

> **出典**: Adrian Roselli | **公開日**: 2026-11-10 | **カテゴリ**: accessibility

**3行まとめ**
- ブラウザ間の互換性を上げる Interop 2027 の投票（締め切りは2026年11月19日）に向けて、Adrian Roselli さんが選んだ15項目とその理由をまとめています
- 1位は `ariaNotify()`、2位は HTML の `focusgroup` 属性、3位は Shadow DOM の `referenceTarget` で、どれもスクリーンリーダーやキーボードの利用者がいま困っている問題につながっています
- 票を入れた `headingoffset` や `random-item()` にも、作り手の使い方しだいで利用者が困るおそれを書き添えています

**詳細解説**

理由は1項目につき1〜2文です。ライブリージョンを正しく実装できていない例が多く、ブラウザやスクリーンリーダーの対応状況もわかりにくいので、`ariaNotify()` を1位にしています。`referenceTarget` は、Shadow DOM の境界をまたいだラベルや説明の関連づけが切れて、スクリーンリーダーや音声操作の利用者が先に進めなくなる問題に向けたものです。

デザインシステムに関わる項目もあります。画面サイズが決まっている前提で作られたデザインシステムが、Apple の新しい端末で問題を起こしているとして、Device Posture API と Viewport Segments API を選んでいます。`AccentColor` は、利用者が選んだアクセントカラーを反映できず、コントラストの低いブラウザの既定色のままになっている部品の話です。

`line-clamp` は、カードの文字が見た目だけで切れたり、操作部品がずれた場所に置かれたりして、キーボードやスクリーンリーダーの利用者が迷う問題への手当てとして挙げています。ただ、`line-clamp` で CSS に文字を生成させることには、翻訳で問題が出るおそれがあるとして慎重な姿勢です。`headingoffset` も、外部のコンテンツの見出しレベルを直せる一方で、見出しの構造を気にしなくなる作り手が増えるおそれを挙げています。

> 🐈‍⬛ : Irodrの記事では開発者プレビューとして出てきたViewport Segments APIが、ここではデザインシステムが新しい端末で崩れる問題として挙がっています。票を入れた項目にも、使い方しだいで困る人が出ると書き添えているところに、Roselliさんの見方がよく出ています。投票の締め切りは11月19日です。

## [Where the disabled button got its rule](https://www.hipuku.dev/writing/where-the-disabled-button-got-its-rule)

> **出典**: Sidebar | **公開日**: 2026-11-13 | **カテゴリ**: design

**3行まとめ**
- Material、Carbon、Polaris、Primer など8つのデザインシステムでは、無効なボタンの文字のコントラストが 1.36:1 から 3.35:1 で、どれも Tab キーで届きません
- 「無効な項目は選べない」という決まりは、1983年の Apple Lisa のメニューにさかのぼります。1980年の社内規約では、薄く表示した項目も選べることになっていました
- Material の `softDisabled` や Primer の `inactive` のように、無効に見えても Tab で届き、使えない理由を伝えられる状態を足すデザインシステムが出てきています

**詳細解説**

8つのうち、Atlassian、GOV.UK、Primer はガイドラインで無効なボタンを避けるよう書いています。Polaris と Carbon は、まわりの UI で理由を説明することを条件に認めています。Material、Spectrum、shadcn/ui は、使ってよいとも避けるとも書いていません。コントラストの数字は、各システムが npm で公開している色の値から計算したものです。WCAG は、操作できない部品の文字にコントラストの基準を設けていません。GOV.UK の緑のボタンも、有効なときの 5.35:1 が無効にすると 2.13:1 まで下がります。

Polaris だけは作りが違います。ドキュメントでは無効なボタンと説明していますが、実際には `aria-disabled` に `tabindex="-1"` を付けた要素を出力していて、結局 Tab の順番から外れます。ライブラリのほかの部分はこのボタンをフォーカスできる部品として扱っていたので、ダイアログのなかにフォーカスを閉じ込める処理を、このボタンを飛ばすように直す必要が出ました。

W3C の ARIA Authoring Practices が、使い分けの目安を示しています。表の1ページ目の「前へ」のように、まわりを見れば使えない理由がわかるものは `disabled` で十分です。メニューの項目、タブ、ツールバーのボタンは `aria-disabled` にして Tab で届くようにします。両方の状態を用意しているデザインシステムも、同じように使い分けています。1回目の送信中に押す2回目の送信のように、そもそも試せない操作には Tab で届かない状態を使います。権限や入力が足りないときのように利用者が直せるものには、Tab で届く状態を使います。まず、フォームの送信ボタンを無効にしている画面で、足りない入力がボタンの近くに見えているかを確かめると、`disabled` のままでよい画面と `aria-disabled` に移す画面を分けられます。

Tab で届く状態は、作る手間が増えます。クリックを止めるコード、ほかのキーボード操作を壊さないフォーカスの扱い、スクリーンリーダーが読み上げる位置に置いた理由が要ります。Atlassian は「無効なボタンにツールチップを付けない」と書いています。フォーカスを受けないボタンのツールチップは、キーボードでは開けないからです。

> 🐈‍⬛ : 1983年のLisaで決まった「無効な項目は選べない」が、40年以上たった今も8つのデザインシステムにほぼそのまま残っている、という経緯がおもしろいところです。しかもその3年前の社内規約では逆の決まりでした。手元のデザインシステムでも、まずフォームの送信ボタンから `disabled` と `aria-disabled` を分けてみると、Polarisのようにフォーカスの扱いでつまずく箇所が早めに見つかりそうです。
