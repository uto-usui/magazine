### [When code is abundant](https://about.gitlab.com/blog/when-code-is-abundant/)

> **出典**: Sidebar | **公開日**: 2026-08-26 | **カテゴリ**: design

**3行まとめ**
- コードの生成が安くなったとき、次に希少になるのは「そのコードを信頼できること」だという整理です
- 指標を「1行あたりのコスト」から「受け入れられた変更1件あたりのコスト」に置き換えることを提案しています
- Stripe・Spotify・Amplitude の実測値を並べ、詰まりどころが CI とレビューへ移った様子を具体的に示しています

**詳細解説**

GitLab が1月の取締役会向けメモから育ててきた論考を、8か月分の観測を足して公開したものです。出発点はシンプルで、Anthropic が8月21日に出した「The AI-Native SDLC Playbook」の一文「Code is no longer the bottleneck」に同意するところから始まります。ただし関心はその一歩先にあります。コードが制約でなくなったとき、代わりに何が希少になるのか。

歴史の整理が読みやすいです。ソフトウェア工学は60年間、「コードは高価で壊れやすい」という一つの事実のまわりに組み上がってきました。レガシーを保存するのも、技術的負債を何年も抱えるのも、レビューや承認や各種ゲートの儀式も、高価な資産を守るための合理的な反応だったという見方です。抽象化のたびに次の制約が見えてきたのは、機械語からアセンブリ、高級言語へと移ったときと同じで、誰も手書きのアセンブリを懐かしんではいません。

新しい制約の名前は「信頼」です。モデルは実装を人間より速く出せますが、それが正しく、安全で、性能が出て、コンプライアンスを満たし、保守可能で、そもそも事業が意図したものかどうかは別の話になります。ここで提案される単位が「cost per accepted change（受け入れられた変更1件あたりのコスト）」です。生成・環境構築・コンテキスト・検証・レビュー・修正・ガバナンスをすべて含めた合計のうち、AI が縮めたのは生成の項だけ。ほかを手つかずのまま10倍速くしても、待ち行列が移動するだけだと書かれています。

実例の数字が効いています。Stripe は minions と呼ぶ内製エージェントで、週に1,000件超のマージ済み PR がエージェント生成になっています。Amplitude は6か月でパイプラインを組み直し、PR のサイクルタイムを5.2時間から44分へ、フロントエンドの CI を約30分から3〜4分へ短縮。同期間に PR 数は3倍になった一方、月次のバグ報告は715件から319件に減っています。Spotify は Honk というバックグラウンドエージェントで1,500件以上のマージを記録しています。そして、この作業の大半は AI ではなくインフラ整備でした。「30分の CI パイプラインは、どのモデルを当てても負ける」という一文が象徴的です。

もう一つ興味深いのが、成熟度の一本道を否定している点です。人間が制御するレガシー（Mode 1）、エージェントが支援する開発（Mode 2）、自律的な開発（Mode 3）は長く共存すると見ています。境界線はグリーンフィールドかどうかではなく、「人が全行読まずに検証できるか」「間違ったときシステムが気づくか」。すべてを早々に Mode 3 へ押し込もうとするのが、この移行期でもっとも高くつく判断になりそうだと釘を刺しています。

UXエンジニアリングの視点で持ち帰れるのは、「学びがコードになる」という部分でしょう。どのサービスが脆いか、3年前になぜデプロイが失敗したか、前回のインシデントを生んだミスの型は何か。こうした知識は今まで人の頭の中にありました。実装が安くなれば、本番障害はリグレッションテストに、性能要件は自動化された制約に、セキュリティインシデントはポリシーに変換できます。デザインの領域でも同じことが言えるはずで、レビューで毎回同じ指摘をしているなら、それは実行可能な制約に落とせる候補です。ただし記事自身が断っているとおり、ポリシーは間違うこともあるし、テストは昨日の前提を固定してしまうこともあります。判断そのものが不要になるわけではありません。

GitLab 自身の製品の話がやや長いのは、事業上の主張が混じっているためです。それでも、90日でやることとして挙がっている5項目（受け入れ変更あたりのコストを測る、CI が5分を大きく超えるなら先にそこを直す、承認ではなく基準を書き出す、コンテキストを可搬な形式で置く、どの事業シグナルを開発ループに直結させるか決める）は、プラットフォームの選択と関係なく試せる内容になっています。

### [Why performant code matters (but gets widely ignored), with Casey Muratori](https://newsletter.pragmaticengineer.com/p/why-performant-code-matters-but-gets)

> **出典**: The Pragmatic Engineer | **公開日**: 2026-08-26 | **カテゴリ**: engineering

**3行まとめ**
- プロファイラ起点の最適化は局所解にしか届かない、という主張が中心にあります
- ハードウェアの理論値を先に出し、そことの差を詰めきるのが優れた最適化担当者の共通点だそうです
- 「早すぎる最適化は諸悪の根源」を鵜呑みにすると、あとから直せない設計上の性能問題が残ります

**詳細解説**

Gergely Orosz さんが Casey Muratori さんを招いた回です。Casey さんは Handmade Hero の作者で、Substack「Computer, Enhance」でひたすら性能の話を書いている人。冒頭に引用されている3年前のメッセージが、この回の問題意識をそのまま表しています。性能が事業に効く証拠は揃っているのに、業界の空気はなぜ性能を軽んじるのか。そして反論が返ってこないのに、態度だけは変わらない。

最初に効くのが、プロファイラ駆動の最適化への批判です。アプリを計測してホットスポットをいじり、数字が改善したか見る。この手順は広く共有されていますが、それで見つかるのは局所的な最小値でしかないという指摘です。Casey さんが一緒に働いてきた「本当に最適化がうまい人」は例外なく、まずそのハードウェアが理論上どこまで出せるかを確定させ、実測との差が埋まるまで止めなかったそうです。目標値が「今より速い」なのか「あと3倍出るはず」なのかで、打ち手の候補がまるで変わってきます。

CPU の理解についても割り切りが明快です。押さえるのは3点だけ。データがどう出入りするか（ロード／ストアユニットと L1〜L3 キャッシュ）、命令がどうパイプを流れるか（分岐予測と命令キャッシュ）、実行ユニットのスケジューリング（演算種別ごとの素の処理量）。これが分かっていれば、新しい CPU の発表を見ただいたいの性能の見当がつくという話です。アセンブリも、書けるようになる必要はなく、読めればいい。覚える命令は20〜30個程度と具体的な数字が出ています。

「早すぎる最適化は諸悪の根源」への異議は、もっとも実務に近い部分でしょう。この言葉が最適化を後回しにする言い訳として使われた結果、あとから直せるのはホットスポットだけになり、性能を悪くしている設計そのものには手が入らなくなる。最初から性能が出る形に設計しておかないと、書き直し以外の道が残らないという警告です。テスト駆動開発への態度も同じ筋で、テストは費用対効果の判断であって既定値ではない、と切り分けています。

事業側の温度についても正直です。エンタープライズのソフトウェア購買が見ているのはコスト・コンプライアンス・機能であって、性能ではない。それでも File Pilot（次世代のファイルエクスプローラ）や Blick（動画エディタ）のように、速さそのものでシェアを取り始めた製品が出てきていて、潮目が変わりつつあるのかもしれない、という置き方をしています。

UXエンジニアリングの視点でおもしろいのは、ゲーム業界がすでに「AI の瞬間」を通過しているという整理です。ゲームエンジンがライセンス可能になり、誰でも Steam に出せるようになった結果、最初は新しい作り手が力を得ました。ところが年に何万本も出るようになると、自然な発見が壊れました。マーケティング戦略なしに認知を得る確率はほぼゼロ、というのが現在地です。生成の敷居が下がったときに何が起きるかの先例として読めます。あわせて「グラフィックスが進歩の指標だった時代は終わり、9年前のゲームと今のゲームが見た目でほとんど変わらない」という観察も出てきます。品質の伸びしろが可視化されなくなると、新作が旧作と競合し続けるという話で、Web の UI にもそのまま置き換えられそうな指摘です。

### [Design's legibility gap](https://www.petermerholz.com/newsletter/designs-legibility-gap/)

> **出典**: Sidebar | **公開日**: 2026-08-27 | **カテゴリ**: design

**3行まとめ**
- UX/デザインが組織で苦戦する理由を、コミュニケーションではなく「見えなさ（legibility）」の問題として説明しています
- 事業は予測可能性を求め、そのために確定性を求め、確定的な仕事だけが評価対象になるという連鎖が背景にあります
- デザインリーダーの仕事は翻訳ではなく、事業が「見える」と認める範囲そのものを広げることだと結論づけています

**詳細解説**

Peter Merholz さんが「人間的な組織を成り立たせる条件は何か」という個人的な問いを掘るなかで出てきた概念を、UX/デザインの状況に当てはめた一本です。冒頭に並ぶ台詞に覚えのある方は多いはずです。「デザインは遅い」「デザインの ROI は」。予算を求めれば「10人も話を聞く? 顧客のことはもう分かっている」と言われ、調査結果を出せば「たった10人? それで信頼できるのか」と言われる。

土台にあるのは James C. Scott の『Seeing Like a State』です。18世紀のプロイセンとザクセンの科学的林業が例に引かれます。国家は木材収入を求めたので、森を「板材の材積」という指標でしか見ませんでした。下生えも倒木も無数の生物も、行政上は存在しないものとして扱われ、森はその指標に合わせて作り替えられます。無関係な種は伐られ、木は整然と列に植えられました。第一世代は見事に育ち、第二世代は崩壊しました。見えないものとして切り捨てた部分こそが、森を生かしていたからです。

対応関係が鮮やかです。森にとっての「板材の材積」が、UX/デザインにとっての「エンジニアが実装する画面」にあたります。その画面を最良のものにするための作業、つまり定性調査、スケッチ、発想、反復、構造化、マッピング、概念モデルの構築は、組織から見えていません。そしてこれはデザイン側の落ち度ではなく、事業運営の価値観の反映だという整理になります。組織は予測可能性を求め、予測可能性は確定性を必要とし、確定性が「見えるもの」の範囲を決めます。

見えない仕事の例が具体的です。4つのコンセプトを検討して1つを選ぶと、捨てた3つは存在しなかったことになり、なぜ最初から使えるやつから始めなかったのかと聞かれる。調査で要件の前提が崩れて顧客の実需に沿って組み直しても、ロードマップ上の名前が同じなら何も変わっていないように見える。下流の何百もの判断を規定する体験原則を書いても、どの判断もそこに遡って語られることはない。

歴史的な説明も納得感があります。エンジニアリング、マーケティング、営業、財務、オペレーションは、事業合理化の関門を並走して通り抜けてきました。MBA のカリキュラムに入り、測定によって標準化され、実務が体系化され、モデル・パイプライン・ファネルという共通言語を持つに至りました。デザインだけがその過程を通っていません。情報デザインとコミュニケーションデザインのスタジオ的伝統、HCI、情報科学、社会科学、人間工学。それぞれに固有の厳密さがあるのに、事業の文脈では読み取られないままです。

20世紀は、この仕事の大半がエージェンシーやコンサルティングという「不確定な仕事が見える場所」で行われていたので問題になりませんでした。21世紀に入って多くの事業がソフトウェア事業になり、UX/デザインが社内に移ったところで噛み合わせが悪くなります。事業が「デザインが必要だ」と言ったとき求めていたのは、人間中心の問題設定と問題解決ではなく、画面の制作と、せいぜいユーザビリティテストの実施でした。ROI の議論が徒労に終わるのも、採用や等級制度が噛み合わないのも、ここに理由があるという説明です。

UXエンジニアリングの視点では、この構図がそのまま自分たちにも刺さります。デザインシステムの整備、アクセシビリティ対応、リファクタリング、パフォーマンス改善。どれも「作られた画面」としては見えず、やらなかった場合の損失としてしか説明できません。記事の結論は、事業の言葉に翻訳し続けることではなく、事業が「見える」と認める範囲そのものを広げること。第二世代の森の運命を避けたいなら、開かれていて、探索的で、感情的で、意味があり、美しくもある不確定な仕事の価値を、組織が評価できるようにしていく必要がある、という締めくくりです。

### [Rethinking Data Visualisation: A UX Approach To Dashboards That Actually Drives Decisions](https://smashingmagazine.com/2026/08/rethinking-data-visualisation-ux-approach-dashboards/)

> **出典**: Smashing Magazine | **公開日**: 2026-08-26 | **カテゴリ**: design

**3行まとめ**
- ダッシュボードの成否を決める8割は、チャートを描く前の上流で決まっているという整理です
- 文脈・読み手・インサイトの3つの問いを先に置くと、載せる要素と落とす要素が確定します
- Tufte のデータインク比は正しいが、単純さ自体は目的ではなく「適切な複雑さ」が目標だと言い換えています

**詳細解説**

Meriem Benhabiles さんによる16分の読み物です。書き出しの状況描写が的確で、週次のスタンドアップや四半期レビューで誰かが数字を共有し、部屋がうなずき、決定も方向づけもないまま会議が終わる。そしてたいていデータのせいにされます。粒度が足りない、データセットが不完全だ、もっと情報が要る。実際にはデータが問題であることはほとんどなく、インサイトを届けるように設計されていないだけだという指摘です。

導入で引かれるのが1973年の Francis Anscombe です。平均も分散も相関係数も回帰直線もまったく同じなのに、プロットするとまるで違う4つのデータセット。統計家に向けた教訓は診断についてのものでした。可視化は、生の数字が隠している実態を明らかにします。ただし可視化には伝達の側面もあって、そこで選ぶ形式が、理解が生まれるか雑音に消えるかを分けます。Visual Capitalist の「History of Pandemics」が例に挙がっていて、死者数を巨大な表にする代わりに比例した円で一本のタイムライン上に並べると、ラベルを1つも読む前に黒死病の規模が視覚系に届きます。

Tufte のデータインク比への扱いが慎重で参考になります。すべての印はデータのためにあり装飾のためにあるのではない、という原則は、チャート単体では成り立ちます。しかしチャートは単体で読まれることがなく、特定の文脈で、特定の圧力のもとにいる人が読みます。もっとも清潔な形まで削ぎ落としたとき、意思決定者に必要な文脈の層まで削っているかもしれません。単純さは目的ではなく、目指すのは「適切な複雑さ」だという言い換えになります。

上流の3つの問いが本論です。文脈は「このデータで何を示そうとしているのか」。「プロダクトの調子を見せて」は目標ではなく、「Q1に登録したユーザーのうち、どの機能が継続に効いているかを特定する」が目標です。後者には指標と母集団と含意された行動が入っています。読み手は「これは誰のためで、その人はどう考えるか」。ここは慣れ（データリテラシー）と責任（その数字の責任を負っているか）の2軸で整理されます。12%の下落を示すチャートは、その数字の責任者と、報告するだけのアナリストとではまったく重みが違う。インサイトは「このデータが届いたあと、何が変わるはずか」。情報とインサイトは別の状態で、後者は決定や理解の転換や軌道修正のことです。

事例の説明が具体的で、B2B SaaS の人材・スキル管理プラットフォームの案件が詳しく書かれています。素直な候補だった「プロダクト別の利用時間」を主指標から外した判断が良いです。時間は代理指標であって、そこにいたことは示せても何かを得たかは示せない。代わりに領域別のコンピテンシースコア、認定の完了率、履歴上の推移を主軸に置き、利用時間は「使われていないモジュールとスコアの遅れに相関があるか」を読み解くための補助シグナルに降格させました。8つの領域の強み弱みを一目で見せるためにレーダーチャートを選んだ理由も、見た目の目新しさではなく、全次元が同じ尺度と採点方式を共有しているという条件から導かれています。

UXエンジニアリングの視点では、色の扱いが示唆的です。ブランディングの段階で3つのプロダクトそれぞれに色を割り当て、その色はブランドガイドラインに留まらず、最初からデータモデルに組み込まれました。すべてのチャート、すべてのフィルタ、すべての内訳で一貫して走る。ユーザーが初めてダッシュボードを開いたときには、すでにメンタルモデルができていた、という書き方をしています。トークンをデザインの都合ではなくデータの意味に紐づけると、学習コストがゼロに近づくという話で、実装側でも再現できる考え方です。効果の記述も抑制が効いていて、売上とユーザー成長も動いたが、単一プロジェクトの寄与を切り分けるのは難しいと自分で断っています。

### [Let me click](https://ilyabirman.net/meanwhile/all/let-me-click/)

> **出典**: Sidebar | **公開日**: 2026-08-27 | **カテゴリ**: design

**3行まとめ**
- 不正な状態を防ぐために操作を禁止するのではなく、押させたうえで状態のほうを直す、という原則です
- チェックボックス群・チェックボックスと入力欄・日付選択の3例で、禁止の代わりになる設計を示しています
- 押せなくする設計は操作の順序を強制し、しかも「必須項目だ」という誤ったメッセージを送ります

**詳細解説**

Ilya Birman さんが「Let me click」と呼んでいる UI 設計の原則です。3つの例で説明されていて、どれも実装で一度は迷う場面ばかりです。

1つ目は、独立した複数のチェックボックスのうち最低1つが必須というケース。通知の受け取り方をどれか1つは選ばせたい、という状況です。よくある解法は、残り1つになったチェックボックスをオフにできなくすること。これが良くない理由が2つ挙げられています。まず操作の順序を強制します。気に入らない選択肢を先に外してから、欲しいものを入れたいことがあるはずです。もう一つは意味が濁ること。「チャットで受け取る」だけが残ってそれが無効化されていると、チャット通知が必須のように見えます。実際には必須ではないのに、外そうとしても押させてもらえません。代案は明快で、最後の1つがオフになった瞬間に、既定の選択肢（メールなど）を自動でオンにする。それも外されたら次の優先候補（電話など）をオンにする。押す行為は妨げず、不正な状態だけを防ぎます。

2つ目は、チェックボックスと、それに紐づく入力欄の組み合わせ。コメントの「メールで受け取る」チェックとメールアドレス欄です。チェックが外れていれば欄を埋める意味はないので、論理的には入力欄を無効化できます。しかしそれは煩わしい。先にアドレスを入れてからチェックを付けたいこともあります。逆に、アドレスが埋まっているからチェックを外せない、というのはもっと良くない。代案は、チェックが外れていても入力させ、何か入力された時点でチェックを自動的にオンにすること。逆方向はもっと慎重にして、チェックを外してもアドレスは消さない。何に使うか分からないからです。

3つ目は生年月日の選択です。6月31日は存在せず、2月29日は年によって存在します。不正な日付を選べないように、31日が選ばれていたら月の候補から6月を消す実装があります。しかし誕生日が6月10日の人は、先に6月を選びたいかもしれません。逆に、選ばせておいてあとからエラーを出すのも良くない。良いフォームは利用者にエラーを浴びせるのではなく、そもそも誤りを避けられるよう静かに助けます。代案は、現在選ばれている日と矛盾する月が選ばれたら日の選択をクリアし、逆も同様にする。2月29日を選んで年に29日がなければ、年の選択をクリアします。

UXエンジニアリングの視点で言えば、これは実装上の楽さと利用者の自由のトレードオフの話でもあります。`disabled` を付けるのは1行で済み、不正な状態が絶対に作れないので検証も楽です。一方で提案されている「押させて、あとで直す」方式は、状態遷移を自分で書くことになり、意図しないループを作らないよう気をつける必要があります。それでも、押せない理由が画面から読み取れない `disabled` は、利用者にとってはただの行き止まりです。「押せなくする」を検討したときに、代わりに何を自動で整えられるかを一度考えてみる価値はありそうです。記事の末尾では、同じ発想の別記事として「『購入』ボタンは常に効くべし」が挙げられています。

### [Controlling when CSS custom properties are computed](https://jakearchibald.com/2026/css-custom-property-compute-time/)

> **出典**: Jake Archibald | **公開日**: 2026-08-26 | **カテゴリ**: web-standards

**3行まとめ**
- 未登録のカスタムプロパティは値がトークン列のまま保持され、使われた場所で評価されます
- `@property` で `syntax` を指定すると計算のタイミングが早まり、宣言した場所の文脈で確定します
- `var()` は「任意置換関数」なので、syntax の指定に関係なく即座に置き換えられます

**詳細解説**

Jake Archibald さんによる、短いながら効きどころを突いた解説です。題材は `sibling-index()`。Firefox 154 で Baseline 入りしたばかりの関数で、要素が兄弟の何番目かを1始まりで返します。

問題設定が巧みです。`.second-item` で `--index: sibling-index()` と定義し、その子要素で `scale: var(--index)` と使ったとき、拾われるのは定義側の div の順番なのか、使用側の子要素の順番なのか。答えは「場合による」。登録していないカスタムプロパティは `syntax: '*'`（何でも）として扱われ、値はトークン列のまま保持されます。つまり `var()` が `sibling-index()` そのものに置き換わり、それが使われた文脈で評価されます。子要素は親の最初の子なので `scale: 1` になります。`getComputedStyle()` で `--index` を読むと文字列 `"sibling-index()"` が返ってくる、というのが証拠として示されています。

ここで `@property --index { syntax: '<number>'; inherits: true; initial-value: 0; }` と登録すると挙動が変わります。`<number>` と指定した時点で、値は宣言された場所で数値として計算されます。`.second-item` は2番目なので `--index: 2` が確定し、子要素は `scale: 2` になります。同じ CSS が、登録の有無だけで別の結果を出す。`getComputedStyle()` も `"2"` を返すようになります。

影響を受けるのは `sibling-index()` だけではありません。相対的なフォント単位（`em`、`ex`、`ch`、`cap`、`lh` など）、コンテナクエリ単位（`cqw`、`cqi`、`cqb` など）も同じ話になります。少し性質が違うものとして URL の例が挙がっていて、CSS の URL は計算値の時点でスタイルシートの基準 URL に対して解決されます。トークン列のカスタムプロパティを別のスタイルシートから `var()` すると、消費した側のスタイルシートを基準に解決されてしまう。`syntax: '<url>'` で登録しておくと、宣言したスタイルシートに固定されます。

さらに一段ややこしい例が最後にあります。`--multiplier: 1` と `--index: calc(sibling-index() * var(--multiplier))` を定義し、子要素で `--multiplier: 3` を上書きしてから `var(--index)` を使う場合です。`var()` は `if()`、`attr()`、`ident()` などと同じ「任意置換関数（arbitrary substitution function）」に分類され、カスタムプロパティの syntax に関係なく即座に置き換わります。したがって `--index` は定義された時点で `calc(sibling-index() * 1)` になっており、子側の `--multiplier: 3` は無視されます。そのあと `sibling-index()` がどこで評価されるかだけが、syntax によって変わります。

UXエンジニアリングの視点では、デザイントークンを `@property` で登録するかどうかの判断材料としてそのまま使えます。登録するとアニメーション可能になり、型による安全性が得られ、値の計算が早まります。逆に、コンテナクエリ単位や相対フォント単位をトークンに含めていて「使われた場所の文脈で解決してほしい」なら、登録しないほうが意図どおりに動くケースがあります。どちらが正しいという話ではなく、どちらの挙動が欲しいかを意識して選ぶ、という整理が持ち帰りどころです。Jake さん自身も「`@property` が計算のタイミングを変えることは何となく知っていたが、いつ、どう変わるかは調べるまで分かっていなかった」と書いていて、正直で好感が持てます。

公開されたのは `kemiljk/skills` の11個。うち2つは以前から単独のリポジトリとしてあった `fluid-design` と `modern-css-html` で、統合版では引き金の条件が明確になり、読み込まれるファイルが小さくなり、例は references に移され、モーションの好みとプラットフォームネイティブな CSS が衝突したときの優先順位が明文化されました。残る8つは、AI の出力をレビューするたびに繰り返し出てきた指摘を固めたものです。`semantic-html-first`（ネイティブ要素とプラットフォームの契約を優先する）、`interface-affordances`（可能な操作を入力手段を問わず知覚できるようにする）、`write-first-design`（ピクセルやコードの前に散文で決める）、`design-engineering`（デザインの意図と本番コードの受け渡し）、`product-delight`（装飾的な目新しさより予期と信頼性）、`subtractive-design`（目的を示せないものは消す）、`ai-output-judgement`（生成物は下書きとして扱い最後に人が見る）、`prototype-to-production`（ハッピーパスを現実のエッジケースに耐えるよう固める）。

11個目の `dxe` は、それ自体の判断基準を持たず、ほかの10個を走らせる役です。ここに至った経緯の告白が正直で、最初は手で組み合わせるつもりだったのに、実際には一度もやらなかったといいます。1つ呼び出して狭い答えをもらい、削ぎ落としのパスや本番向けの堅牢化があることを忘れたまま、まずいものが出てしまう。だから `dxe` を作った、という流れです。返ってくるのは10個の意見ではなく1つのレポートで、このパスが何を良くしようとしているかの仮説、深刻度別の指摘とそれを検出した skill、明示された削ぎ落とし、そして残作業の優先順です。

構成の順番が設計として参考になります。まず Intent（`write-first-design` と `subtractive-design` で、そもそもこの仕事が必要かどうかを決める）、次に Platform（`semantic-html-first` と `modern-css-html` でネイティブな材料を選ぶ）、Feel（`fluid-design`、`interface-affordances`、`product-delight` で相互作用の質を作る）、Bridge（`design-engineering` でデザイン構造をコード構造に写し、趣味をハンドオフ文書ではなくトークンとレンダリングに結びつける）、最後に Shipping（`ai-output-judgement` と `prototype-to-production` で凡庸な下書きが逃げ出す前に捕まえる）。モーションの好みと CSS の純度が対立したときは、望ましい挙動は fluid design が決め、それを実現できるもっともネイティブな実装は modern CSS が決める、と役割が分けられています。

UXエンジニアリングの視点で持ち帰りたいのは、「重なり合う skill には優先順位が要る、なければ雑音になる」という一文です。これはデザインシステムのガイドラインにもそのまま当てはまります。アクセシビリティのルールとブランドのルールとパフォーマンスのルールが同じ重みで並んでいると、衝突したときに現場が判断できません。どちらが上位かを先に書いておく作業は、ルールを増やす作業より地味ですが効きます。記事の締めも実践的で、AI の下書きに同じレビューコメントを繰り返している、エッセイの抜粋をプロンプトに貼っている、重複する指示ファイルを複数保守している、同じ趣味を別々のツールに教え直している。そう気づいたら、自分の skill 集を作る頃合いだ、という提案です。すでに信頼している自分の文章から始め、引き金・ルール・チェックに圧縮し、例は references に置く。

### [The asteroid hitting frontend development](https://frontendfoc.us/issues/755)

> **出典**: Frontend Focus | **公開日**: 2026-08-26 | **カテゴリ**: frontend

**3行まとめ**

**詳細解説**

Frontend Focus の第755号です。編集は Chris Brandrick さん。表題に取られている Nolan Lawson さんの「The Asteroid Currently Hitting Frontend Web Development」は、長年かけて築いてきた知識の多くが AI の回答によってほぼ陳腐化したという実感から出発して、フロントエンド開発と教育の現在地を考え、いくつかの進み方に着地する内容だと紹介されています。恐竜を絶滅させた隕石になぞらえたタイトルですが、紹介文を読むかぎり悲観一色ではなく、どう泳ぐかの話に向かっているようです。

レイアウト面では Ahmad Shadeed さんの `flex-wrap: balance` の解説が筆頭に置かれています。折り返したときに行ごとのアイテム数が不揃いになる問題に対して、`flex-wrap: balance` と新しい `flex-line-count` プロパティであらゆる幅で意図どおりに振る舞わせる、という内容。どちらも今のところ Chrome のみですが、対話的なデモとフォールバックとコードが揃っているとのことです。孤立した1個だけが次の行に落ちる、あの見た目を CSS 側で解けるようになるのは実務的に大きい話でしょう。

HTML まわりも充実しています。Manuel Matuzović さんの「My HTML Boilerplate in 2026」は5年ぶりの更新で、`<head>` を中心に使っている要素をすべて解説したもの。Chris Burnell さんの「HTML Can Do That」は、HTML が JavaScript の担当領域を次々と取り込んできたという主張のもと、`popover`、invoker commands、`hidden="until-found"` など8つの例をコードと注意点つきで示しています。「できるようになった」だけでなく、それぞれの足りない部分にも触れているのが良さそうです。

ブラウザ側の動きも整理されています。Firefox 154 で `text-box` の一括指定と `sibling-index()` / `sibling-count()` が入り、このリリースで `sibling-index()` が Baseline に到達しました。ちょうど Jake Archibald さんの記事が扱っていた関数で、同じ日のニュースとして並んでいるのがおもしろいところです。Jake さんは Firefox の JPEG XL 対応予定についても記事を出していて、Chrome も対応を計画しています。Chrome 153 beta には `scroll-axis-lock` プロパティが入りました。

そのほか、CSS-Tricks には `@location` でページに名前を付けて `@navigation` で遷移をアニメーションさせる提案の紹介（実装はまだなく、あくまで草案）、Carmen Ansio さんによる2Dの擬似的な奥行きから本物の3Dへ進む CSS の対話的ガイド、ブラウザ上で任意の画像にディザリングをかけて SVG か PNG で書き出せる Dither などが並んでいます。UXエンジニアリングの視点でいうと、この号は「JavaScript でやっていたことが CSS と HTML に降りてくる」流れと「その知識自体が AI で代替される」流れが同じ紙面に載っている構成で、そこがいちばん読みどころかもしれません。

### [Survivor's guilt and other joys of not getting laid off](https://uxcontent.com/survivors-guilt-and-tech-layoffs/)

> **出典**: UX Content Collective | **公開日**: 2026-08-26 | **カテゴリ**: ux-writing

**3行まとめ**
- レイオフで残った側の感情について、2年前に書き始めて出せずにいた原稿を公開したものです
- コンテンツデザイン組織の50%が「AI による効率化」を理由に削減された現場の記録でもあります
- 感情の処理、つながり直し、自我と仕事の切り分け、構想、前向きさ、という5つの段階で整理されています

**詳細解説**

James West さんによる、テック業界のレイオフを「残った側」から書いた文章です。書き出しの断り方が誠実で、レイオフされた人向けの助言やリソースは山ほどあるけれど、平静を装って働き続けなければならない側の感情については話しにくい、というところから始まります。この原稿を2年前に書き始めて公開しなかったのは、職を失った人から注目を奪いたくなかったからでした。そして最近、書き手自身がキャリア17年で初めてレイオフされたことをきっかけに公開しています。生き延びるほうが感情的にはむしろきつかった、という述懐が添えられています。

状況の描写が具体的です。2024年6月、コンテンツデザインのリーダーシップに移って3年目。6人のチームをゼロから作り、メンタリングとコーチングをしながら新任マネージャーとしての自分を育てていました。フィンテック SaaS で、顧客が実際に使いたくなる AI 機能を作っていた時期です。そこにレイオフが来て、マネージャーとしての最後の仕事はチーム全員に通告を伝えることでした。そのうえで、その全員分の仕事を引き継ぎます。給与等級は変わらないまま IC に戻ることが、見え方としては降格か、逃れようのない気まずさに感じられたといいます。自分が過去に持ったマネージャーは全員いなくなり、評価の高かったコンテンツデザイン組織は解体されました。

5つの段階のうち、3つ目の「自我が傷ついているのか、仕事が傷ついているのかを切り分ける」がもっとも実務的です。レイオフの判断はさまざまな観点で不公平だったかもしれない。それでも、いま何をするか。今やらなくてよくなったことに救いはないか。実際に生じたカバー範囲の穴は何で、働き方のどこを変える必要があるか。AI は本当にその穴を埋めるのか、それともサービスモデルを見直してもっとも重要な仕事に絞る必要があるのか。残されたコンテンツ担当者たちは、支援の度合いを低・中・高に分ける枠組みを作り、どのトラックに全面的に付き、どれはツールで自己解決してもらい、どれは構造上の問題だけ見るかを決めました。

2つ目の「つながる」も、書き方が具体的で良いです。レイオフされた人には LinkedIn の推薦を書くと申し出る、求人を見つけたら知らせる、ネットワークにつなぐ。そして、ひとこと添えるときの温度についての助言があります。何年も一緒に働いた相手から「寂しくなるね、良い人だった」程度のメッセージが来るのは、実のところ堪えるものです。去る側が聞きたいのは「あなたが切られたなんて正気じゃない、会社は確実に困ることになる」に近い言葉で、それに満たないものは、決定への暗黙の同意のように響いてしまう。

UXエンジニアリングの視点で言えば、これは組織の知識が失われる場面の当事者記録として読めます。前の記事「Design's legibility gap」が指摘していた「見えない仕事」の担い手が消えたとき、残った側が最初に直面するのがカバー範囲の穴です。低・中・高の支援モデルは、その穴を埋める代わりに、埋められない範囲を明示的に決めるやり方でした。最後の指摘も鋭くて、レイオフが心理に与えるいちばんの打撃は、自分に決定権がなかったという感覚そのものだと書かれています。

### [Tegaki](https://gkurt.com/tegaki/)

> **出典**: Sidebar | **公開日**: 2026-08-26 | **カテゴリ**: design

**3行まとめ**

- React・Svelte・Vue・SolidJS・Astro・Web Components・素の JavaScript 向けのコンポーネントが用意されています
- API からテキストが流れてくるのに合わせて手書きアニメーションを再生する使い方が想定されています

**詳細解説**

手書き風のアニメーションを実現するライブラリです。紹介文が4段階に分かれていて、処理の流れがそのまま説明になっています。Generate では、CLI が Google Fonts から任意のフォントを取得し、字形のアウトラインを抽出して骨格を計算し、線幅とタイミングのデータを持つストロークのパスを引きます。Bundle では、そのストロークデータを字形のメトリクスとタイミング情報とともに小さなバンドルにまとめます。Render では、各フレームワーク向けのコンポーネントを置くだけで、テキストのレイアウトと行の折り返し、アニメーションの再生を引き受けてくれます。Stream では、API からテキストがストリーミングされてくるのに合わせて手書きを描いていきます。

紹介文以上の詳細はサイト側にあたる必要がありますが、任意の Google Fonts から骨格を機械的に導いているという点は押さえておく価値があります。フォントごとに手作業でストローク順を定義しているわけではないので、対応できる字形の幅は広い一方、書き順として自然かどうかは元の字形とアルゴリズム次第になるはずです。日本語のように書き順が意味を持つ文字体系でどう振る舞うかは、実際に試して確かめたいところです。
