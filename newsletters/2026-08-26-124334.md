### [Why Ramp built its own in-house coding agent, Inspect](https://newsletter.pragmaticengineer.com/p/why-ramp-built-inspect)

> **出典**: The Pragmatic Engineer | **公開日**: 2026-08-25 | **カテゴリ**: engineering

**3行まとめ**
- Ramp ではマージされた PR の75%が、自社製コーディングエージェント Inspect のセッションから生まれています
- ローカルマシンでは並列セッション数が頭打ちになるという不満が、リモートサンドボックス型の内製に向かわせました
- 社内データソースへの接続と、変更を自分で検証するループが、市販ハーネスとの差になっています

**詳細解説**

Gergely Orosz さんが Ramp の CTO・エンジニアリング責任者・Inspect の創設エンジニアに取材した一本です。前提として、Block の Goose、Stripe の Minions、Shopify の River のように、自前のコーディングエージェントを持つ会社がいくつか出てきています。Claude Code や Cursor がすでにあるのに、なぜ時間をかけて作るのか。その問いに具体的な数字と経緯で答えています。

Inspect の出発点は失敗でした。v1 はデザイナー向けの Chrome 拡張で、画面の一部を選んで「この文言を変えて」「ボタンの位置をずらして」と AI に頼めるものでした。評判は悪くなかったのに使われなかった理由が2つ挙がっています。エンジニアはファイルを開いて1行直せるので使う理由がない。非開発者にはローカル開発環境の構築が重すぎる。ここから v2 でリモート開発環境そのものに舵を切り、その上にコーディングエージェントを載せる形になりました。ハーネスにはオープンソースの OpenCode を選んでいて、理由は HTTP API が露出していて組み込みやすかったこと、そしてモデル非依存であることです。

方向転換の後の伸びが速く、2026年1月に PR の約60%、5月には75%。7月には累計100万セッションを超えています。ほかの数字も具体的で、完全にプロビジョニングされたリモート環境の起動が5秒未満、チームは4人のエンジニアと1人のディレクターと兼任 PM の5.5人、Inspect のコードベースには150人以上のエンジニアが貢献しています。Inspect 自身の8割以上が Inspect のセッションで書かれていて、Inspect リポジトリへマージされる PR の約90%が Inspect 由来だそうです。

技術的にいちばん効いているのは検証のループです。バックエンドの変更ならテストを走らせ、テレメトリを見て、フィーチャーフラグを問い合わせる。フロントエンドならスクリーンショットとライブプレビューを出して自分で見た目を確かめる。市販のハーネスがこれをそのままできないのは、モデルの賢さではなく、テレメトリやフィーチャーフラグといった社内システムへの接続を持っていないからだ、という整理です。実際 Ramp はスクリーンショット検証をベンダーより1年近く先に作っていました。スタックは React/Vite、Cloudflare Durable Objects と SQLite、Cloudflare Agents SDK、サンドボックスは Modal。サンドボックスの中には Postgres・Redis・RabbitMQ・Temporal といった開発用サービス、Chromium、VS Code Server が入っています。

もうひとつおもしろいのが、Inspect がプラットフォームになっていることです。社内には200を超えるエージェントが載っていて、チームごとにカスタマイズできるコードレビューの ReviewBuddy（1人が1週間で作った）、観測系につながって障害の文脈を集める Oncall Assistant、ユーザーのようにクリックして回って Playwright テストを作る Testo、Looker や Snowflake につながる Ramp Research、チャット・メール・App Store レビューから90日分の声を集める Voice of the Customer などが挙がっています。エンジニアがクラウドのバックエンドを気にせずエージェントを作れる、という土台になっているわけです。

UXエンジニアリングの視点で持ち帰れるのは、v1 が失敗した理由のほうかもしれません。「デザイナーが UI をちょっと直せる」という価値提案そのものは間違っていなかったのに、ローカル環境という前提が非開発者を締め出していました。同じ機能を、環境を用意しなくていい場所に置き直しただけで採用率が跳ねています。ツールの効き目を決めているのがモデルではなく、どこに置くかと何につながっているかだった、という読み方ができます。あわせて、全セッションが公開でオプトアウトなし、という運用も特徴的です。他人の試行錯誤が読める状態が、150人の貢献につながっているのでしょう。

### [新API「HTML-in-Canvas」を紹介 - CanvasにHTMLを描くAPIは何を解決するのか？](https://ics.media/entry/260825/)

> **出典**: ICS MEDIA | **公開日**: 2026-08-24 | **カテゴリ**: frontend

**3行まとめ**
- 派手なエフェクトの話題が先行していますが、このAPIが解こうとしているのは Canvas のテキスト描画と UI 自作の課題です
- `layoutsubtree` 属性と `drawElementImage()` メソッドの3ステップで、HTML をそのまま Canvas に描けます
- アクセシビリティーは改善しますが、プライバシー対策で IME やスペルチェックの表示は描画から除外されます

**詳細解説**

matsumoto さんによる、いま提案段階にある HTML-in-Canvas の解説です。冒頭で VFX-JS のデモや、普通のフォームにブラウン管風の表現や雨粒を乗せた作例が紹介されますが、そこで終わらないのがこの記事の良いところで、「このAPIの本質はそこではありません」とはっきり書いたうえで、地味な課題のほうに話を進めます。

Canvas の課題は2つに整理されています。ひとつはテキスト描画です。`fillText()` は指定座標に1行書くだけで、はみ出しても折り返さないし、一部だけ太字にもできません。末尾を「…」で省略したければ `measureText()` で幅を測りながら自分で切り詰めます。OGP 画像の生成、チャートの軸ラベル、ゲーム内 UI。どれも「ちょっとテキストを載せたいだけ」なのに、気がつけばテキストレイアウトエンジンを自作している、という指摘には覚えのある方も多いはずです。さらに多言語が厄介で、アラビア語の連結処理、タイ語やヒンディー語の複雑な字形整形、日本語の縦書き・ルビ・禁則。ブラウザーの HTML レンダラーが長年かけて育ててきた処理に、Canvas はほとんど追従できていませんでした。

もうひとつが UI パーツの自作です。Canvas 上に「きちんと押せるボタン」を作ると、矩形の描画に加えてクリック判定、ホバー時のカーソル変化、Tab によるフォーカス移動、Enter での実行、スクリーンリーダーへの通知まで全部自前になります。HTML なら `<button>` と書くだけのものです。

使い方は3ステップと簡潔です。`<canvas>` に `layoutsubtree` 属性を付け、描きたい HTML を `<canvas>` の直接の子要素として置き、`drawElementImage()` で描く。記事では3段階のデモでこれを見せています。ワンショットで転写するだけなら1行で、ルビも折り返しも CSS のフォントもそのまま画像になります。リアルタイムに動かしたい場合は `paint` イベントと `requestPaint()` を使うだけ。ここで「なぜボタンが押せるのか」という疑問が出ますが、答えは、子要素として置いた HTML は見えていないだけでその場所に存在しているからです。イベントは本物の要素が受け取り、表示が変われば `paint` が発火して Canvas が描き直されます。3つ目は座標系の一致で、`drawElementImage()` の戻り値である `DOMMatrix` をそのまま HTML 側の `style.transform` に設定すると、移動・拡大・回転したあとのフォームも操作できます。

アクセシビリティーについての書き方が慎重で、参考になります。よくなる面は明確で、`fillText()` で描いた文字はただの絵なのでアクセシビリティーツリーに載らず、選択もコピーもページ内検索も翻訳も効きませんでした。HTML-in-Canvas で描いたものは裏にある本物の要素なので、それらが自動的に動きます。支援技術を使っていない人にも効く話です。ただし「これで Canvas のアクセシビリティー問題が解決する」と受け取ると話が変わってきます。従来もフォールバックコンテンツは置けたのに使われなかった理由は、仕組みではなく描画内容との二重管理が難しかったからでした。HTML-in-Canvas はその二重管理をある程度自動化しますが、円グラフを描くなら、ラベルは読み上げられても円弧は依然として `ctx.arc()` のピクセルです。`<img>` に適切な `alt` を付けるのと同じで、必要な対応は設計する側の仕事として残ります。

プライバシーの部分がいちばん考えさせられます。HTML の描画結果には OS のテーマカラー、訪問済みリンクの色、IME の変換候補、字幕の表示設定といった、JavaScript から直接読めないユーザー固有の情報が大量に含まれています。まるごと画像化できると筒抜けになるので、Chrome の答えは「機微な情報をリスト化して最初から描画しない」でした。除外されるのは IME の未確定文字列の下線、スペルチェックや文法チェックの波線、OS のテーマカラー、訪問済みリンクの色の変化、未確定のオートフィル内容、クロスオリジンのコンテンツ、字幕・キャプションの設定など。記事はここに2つの課題を挙げます。リスト方式は OS やブラウザーに新しい UI が入るたびに追加が必要になること。そして、本来必要だから提供されている表示を削るのは利便性やアクセシビリティーを損なう行為であること。単にカッコいいエフェクトのためにページ全体を HTML-in-Canvas で描いてよいかは、慎重な判断が要ります。

各社の状況は2026年8月時点で、Chrome がオリジントライアルを Chrome 154 まで延長（WebGL・WebGPU 向け API とプライバシー面に大きな変更を入れたため）、WebKit は公式なポジション未表明ながら7月から試験的実装が始まっていて、Firefox は「Needs proposed position」のまま。課題感は共有されているが解決手段としての受け入れは未決着、という整理でした。

### [New Insurance UX Research: 3 Key Takeaways](https://feeds.baymard.com/link/9825/17428024/insurance-ux-research-launch)

> **出典**: Baymard Institute | **公開日**: 2026-08-25 | **カテゴリ**: ux-research

**3行まとめ**
- 米英20サイト・220セッションのユーザビリティテストから、1,700件以上の中〜重度の問題と190以上のガイドラインが出ました
- 保険は「たまにしかやらない」タスクなので、屋根の素材や再建築費用のような設問で利用者が止まります
- 見積フローでのつまずきは一般的なECより深刻で、戻るボタンが効かないだけで20分の入力が捨てられます

**詳細解説**

Baymard が保険サイトの UX リサーチを公開しました。規模は4,700時間以上の調査、Think Aloud プロトコルによる220セッション。対象は英国9サイトと3つのアグリゲータ（Compare the Market、MoneySuperMarket、Go Compare）、米国8サイト（Liberty Mutual、Travelers、Progressive、GEICO、Amica Mutual、Lemonade、Root Insurance、Allstate）です。

1つ目の観察は、保険特有の概念のわからなさです。一般的な EC が住所と支払い情報を聞くのに対して、保険は「物件の再建築費用」や「5レバーのモーティスデッドロック」を聞いてきます。しかも自動車保険や住宅保険は数年に一度のタスクなので、慣れる機会がありません。Go Compare で再建築費用を聞かれた参加者は「見当もつかない。大きく外したら困るから自分の数字を入れるのは不安」と言って、そのまま空欄で進もうとしました。しかも「必須だと言われたら、別のところで見積もりを取ることを考え直すかもしれない」とまで言っています。MoneySuperMarket で屋根の素材を聞かれた参加者は選択肢を延々スクロールして「Shingle って何かわからない」とつぶやき、結局「Tile」と答えて先に進みました。

対して、うまくいっている例が対照的です。Direct Line で推奨額を提示された参加者は、迷わずその数字を採用しました。この参加者は別のサイトでは自分の家財を実際の15%未満で見積もっていたので、デフォルト値のほうが正確な答えを引き出したことになります。Compare the Market のモバイルでは、屋根の平坦度・外壁の素材・屋根の素材を図解付きで示していて、参加者は8秒以下で3問に答えました。同じ質問に他サイトでは詰まっていた人たちです。つまり、わからない値を聞くときは、説明と図解を添え、地域の平均のような妥当なデフォルトを置くとよい、ということになります。走行距離のように「日あたり」「年あたり」を選ばせる柔軟さも同じ方向の工夫です。

2つ目は見積フローそのものの操作性です。ここでの失敗が一般的な EC より重いのは、投じた時間の長さが理由になっています。20分入力したあとで、ある項目で詰まる、戻れない、エラーで入力済みデータが消える。どれか一度でも起きれば人は諦めます。Allstate では、名前が「Hannah Hannah 姓」と誤って埋まったのを直そうとした参加者がブラウザの戻るボタンを押し、ページが反応しなかったのでロゴをクリックし、ホームに戻って見積もりが最初からになりました。逆に Liberty Mutual の戻るボタンは見つけやすいと評価されています。「Save & Continue」と並んで置かれ、周囲とサイズと色でコントラストがあり、全ページで同じ位置にある。カバレッジごとの「Add」「Edit」リンクも右マージンに大きく置かれていて、押せば変更できることが即座にわかりました。あわせて、その保険を買えない条件に当てはまる人には、フローに入る前に知らせるとよい、という指摘もあります。

3つ目が信頼です。Travelers の Insuramatch で見積もり一覧を見た参加者は「どれも聞いたことがない会社ばかり。こんなところには電話しない」と、知名度の低さをそのまま品質の低さと結びつけました。外部の評価や認証を出すことが、保険では特に効くわけです。もうひとつ、価格の透明性の例が痛烈でした。Insure and Go で「Hazardous Activities」の追加補償を無料だと思って選んだ参加者は、次のステップで £56 前後だった見積もりが £115 になっているのに気づきます。追加から更新後の金額に到達するまで54秒、そこから外せるページに戻るまでにさらに3分。一般的な EC でも40%が想定外の追加費用でカートを放棄しますが、保険でも同じことが起きます。

UXエンジニアリングの立場で見ると、ここで挙がっている修正はどれも実装側の話です。ブラウザの戻るボタンをフローの状態と正しく同期させる、選択が価格に与える影響をその場で見せる、エラー時に入力を保持する、選択肢に図版を添える。長いフォームをステップに割ったときに、履歴とスクロール位置と入力状態をどう保つかは、フレームワークに任せきりにするとよく壊れる部分でもあります。20分ぶんの入力を守るコードは、コンバージョンを守るコードでもある、と読めます。

### [Every fork looks like adoption](https://blog.murphytrueman.com/every-fork-looks-like-adoption/)

> **出典**: Sidebar | **公開日**: 2026-08-25 | **カテゴリ**: design

**3行まとめ**
- GitClear の調査では、2023年比で他ファイルの関数呼び出しが35%減、リファクタリングが70%減、重複ブロックが81%増
- import 数ベースの adoption 指標は、使われていること（use）と再利用（reuse）を区別できません
- prop の形の変化、ラッパーの数、構造的類似の3つを見よう、という提案です

**詳細解説**

デザインシステムの採用率をどう測るか、という話です。出発点は GitClear のレポートで、4年間・6億2,300万件のコード変更を分析したところ、再利用が減って重複が増えていました。ただし、と著者は続けます。その数字の多くは、そもそも誰も再利用を約束していない一般的なコードベースのものです。デザインシステムの中では逆であるはずで、再利用こそが目的なのだから、と。

問題の形はシンプルです。あるチームが `Card` を持ってきて、自分たちの用途に少し合わせたい。`ProductCard` というローカルコンポーネントで包み、prop を3つ足して padding を調整する。以後そのチームは `Card` の代わりに `ProductCard` を使います。ラッパーは技術的には `Card` を import しているので、ダッシュボードはこれを採用としてカウントします。実際にコードベースにあるのは、プロダクトとデザインシステムのあいだに挟まった局所的な抽象です。健全な合成かもしれないし、フォークの始まりかもしれない。import 数はどちらかを教えてくれません。

以前はこれが人間の速度で起きていました。火曜日にあるチームがラッパーを作り、木曜日に別のチームが少し違うものを作る。ドリフトの蓄積が遅かったので、いくらかは捕まえられたわけです。「なんで同じコンポーネントが3種類あるの」と誰かが聞くか、デザインシステムのチームが「みんな同じプロパティを上書きしている」と気づくか。AI がコードを書くと、そこに至るコストが大きく下がります。「うちの `Card` みたいな感じで、料金プラン用に」と頼めば、import して包む・ほかと合成する・構造を再現して必要なところだけ変える、どれもそれらしい答えになります。同じデザイントークンを使っていれば、結果はプロダクトに完全に馴染んで見えます。

提案されている3つの指標が具体的です。ひとつ目は prop の形の変化。組み合わせの数そのものより、使われ方の形が変わっているかを見る。3つか4つの見慣れたパターンだったものが、一度きりの設定の長い尾を伸ばしはじめたら、理由を知りたい。API を使いこなしているのではなく、API を迂回している兆候かもしれません。2つ目はラッパーの数。ラッパー自体は悪ではなく、合成はコンポーネントシステムが機能する理由のひとつです。問うべきは次に何が起きるか。薄いままか、それとも独自の prop・スタイル・バリアント・振る舞いを溜めはじめるか。みんなが `Card` ではなく `ProductCard` を覚えることになっていないか。バグをラッパー側で直して、機能をシステムに還元しなくなっていないか。3つ目、著者がいちばん重視するのが構造的類似です。デザインシステムのコンポーネントに似ているのに、そこから import していないコード。`Button` を import しない Button、`Card` にそっくりなローカルの Card、同じ状態と間隔とインタラクションを独自に再発明した Modal。jscpd のような重複検出は昔からありますが、デザインシステム向けには「新しいコンポーネントがシステムの既存物に不審なほど似ていないか」という具体的な問いになります。

レビューの話が現実的でした。以前は UI コンポーネントを新しく書くこと自体が高くついたので、「もう似たようなものがあるんじゃないか」と誰かが聞く程度の摩擦がありました。いまはその会話が起きる前にコードが存在します。レビュアーの前にあるのは完成した PR で、動くし、テストは通るし、正しいトークンを使っている。「これ、もうあるんじゃないか」に答えるには、コードベースを検索してドキュメントを読んで既存コンポーネントで足りるか確認して、20分かかります。毎回やる人はいません。だから、レビュアーの手前でシステム側が捕まえる。「このコンポーネントは design-system/Card と構造的に似ています」と出すだけでいい。マージをブロックしなくても、会話が起きればそれで十分だ、という着地です。

締めの一文が効いています。フォークはずっと adoption に見えていた。ただ、以前はそれなりに高くついたので、誰かが気づいていただけだ、と。

### [Why Your Website Should Never Stop Changing](https://smashingmagazine.com/2026/08/why-website-should-never-stop-changing/)

> **出典**: Smashing Magazine | **公開日**: 2026-08-25 | **カテゴリ**: design

**3行まとめ**
- サイトは公開日が最高で、壊れないまま少しずつ会社と合わなくなっていく、という前提から始まります
- 完全自律のプラットフォームを作ってみたら、誰もそれを望んでいなかった、という観察が中心です
- 線をどこに引くかは人によって違うので、制御の単位は設定ではなくエージェントそのものになります

**詳細解説**

自律型ウェブサイトのプラットフォーム Fimo を作っている Pierre Burgy さんの記事です。導入がうまい。最後のブランチがマージされてサイトが公開された日、それは設計どおりの姿で、束の間、完璧です。二度とこれほど良くはなりません。壊れるからではなく、市場が動き、メッセージが変わり、競合が何かを出して、丁寧に作ったものが少しずつそれが表すはずの会社と合わなくなるから。1年後には時代物になっている。誰もが知っている劣化で、ほとんどの人が自然法則として扱っています。

そこで「エージェントに全部渡せばいい」となるのが素直な発想で、実際この人たちは完全自律をゴールだと仮定して作りました。そして観察されたのは、ためらいでした。エージェントを信用していないからではありません。ウェブサイトには単一の持ち主がいないからです。部分ごとに持ち主が違い、それぞれが望む自律の量が違う。問うべきはエージェントを信じるかどうかではなく、どこに線を引くか、そして誰にとっての線か、でした。

そう問い直すと、仕事は3つにきれいに分かれます。いちばん大きい山は、ルールで決まる、繰り返しの、まったく楽しくない作業です。ページが変わるたびアクセシビリティを保つ。トークンが動いたらデザインシステムの更新を伝播させる。壊れた meta タグ、急ぎのリリースで未圧縮のまま出た画像、3スプリント前の URL 変更で腐ったリンクを拾う。誰もこれが得意だから採用されたわけではありません。渡せてほっとする側の仕事で、しかも味覚ではなくルールで定義されているのでエージェントが得意な領域です。この山がどれだけ大きいかを言葉にすることが、自律という話を飛躍でなくする、と書かれています。判断を渡すのではなく、雑用を渡している。

反対の端には、いくらでも金を積まれても渡さない仕事があります。小さな山ですが、自分が存在する理由でもある。エージェントは新しいページをルールに照らして全部チェックできます。コントラストが通っているか、見出しの順序が正しいか、トークンが合っているか、コピーがスタイルガイドどおりか。できないのは、そのページがどう感じられるべきかを決めること、そして出そうとしているものが、味覚の意味で良いかを判断することです。人が自律に抵抗するときに最初に守りにいくのがここで、守るのは正しい。間違いは、サイト全部がこの種の仕事でできていると思うことだ、という書き方でした。

そして真ん中に、人によって位置が変わる部分があります。例が良くて、「サイトに来た人にダークモードをデフォルトで見せる」という変更です。エージェントは数秒でやれます。問題は、そもそもそれをやると誰が決めるか。サイトのアイデンティティを持つデザイナーにとって、デフォルトのテーマは設定ではなく、ブランドが最初にどう見られたいかの表明なので、自分で決めたい。変更を出す開発者にとっては、理由の明確な1行のデフォルト値で、エージェントに任せて次に進みたい類のものです。同じ変更、同じサイトで、2人は正反対の場所に線を引きます。片方が慎重でもう片方が無謀なのではなく、同じタスクに含まれる判断の量が人によって違う。「正しい」はタスクの性質ではなく、その人の価値がどこにあるかの関数だ、というまとめです。

だから制御はタスクごと・人ごとになり、トグル1つでは足りなくなります。Fimo が取った形は、エージェントそのものを組み立てさせることでした。固定メニューから選ぶのではなく、それぞれが何に触れてよいかを決める。無人で走らせて構わないアクセシビリティエージェント、ブランドに関わる文言には近づけておきたいコンテンツエージェント。そして線は固定されません。実行履歴もログも変更前後の差分も見られるので、信頼は「慣れたから」ではなく「見て比べられるから」育ちます。エージェントが自分では見逃していたものを静かに直し、その中身を確認できた瞬間、次の委任が楽になる。締切を設けておけば、自分が承認のボトルネックにもなりません。

最後の反転が効いています。人が最初に口にする心配は「自分の知らないところでエージェントがサイトを変えてしまう」ですが、ひっくり返すと、本当のリスクは何も変わらないサイトのほうです。凍結したサイトは安全なのではなく、誰も気づかないうちに、もう存在しない会社を表すようになっていく。自律の目的はあなたをサイトから取り除くことではなく、劣化を取り除くことだった、という一文で締められます。

### [The end of credential sprawl for agents](https://vercel.com/blog/the-end-of-credential-sprawl-for-agents)

> **出典**: Vercel | **公開日**: 2026-08-25 | **カテゴリ**: frontend

**3行まとめ**
- 長寿命トークンをやめ、実行時に要求する短命でスコープ付きのトークンに置き換える、という提案です
- Vault は盗みにくくするだけで、盗まれた後の危険度は変わらない、という指摘から入ります
- Vercel Connect が GA になり、100以上のコネクタと RBAC・監査ログ・可観測性が付きました

**詳細解説**

役に立つエージェントは必ずコードベースの外に手を伸ばします。Slack に投稿し、PR を開き、Snowflake に問い合わせ、社内 API を叩く。その到達範囲こそが価値で、同時にリスクのある場所でもある。長らくそれを許可するとは、長寿命のトークンを発行して漏れないことを祈ることでした。この導入から始まる Vercel Connect の GA 発表です。

議論の骨格が明快です。認証情報の管理はそれ自体がひとつの仕事になっていて、ローテーションのスクリプトを書き、環境をまたいで秘密をコピーし、ユーザー間でトークンを共有します。Vault に入れれば盗みにくくはなりますが、盗まれた後は変わりません。期限が来ないし、漏れた認証情報にできることを Vault は制限しないからです。エージェントはより多くのシステムに、より自律的に、より頻繁に触るので問題を増幅させたのに、封じ込める道具は変わっていない。

Connect のモデルは、コネクタをプロバイダごとに一度登録して、必要なプロジェクトと環境に紐付け、コードは実行時にトークンを要求する、という形です。ポイントは、トークンを取るための秘密が要らないところにあります。Vercel 上のすべてのデプロイは OIDC アイデンティティを持っているので、SDK はそれで「誰が要求しているか」を証明します。記事の表がわかりやすく、寿命（期限なし → 短命で自動更新）、到達範囲（エージェントが必要としうるすべて → 要求ごとにタスク単位）、アイデンティティ（全ユーザー共通の1つの bot → アプリまたは指名されたユーザー）、ローテーション（発行してコピーを更新して再デプロイ → 不要）、失効（ローテートして再デプロイ → コマンド1つ）と並びます。

スコープの粒度はサービスによりますが、GitHub がいちばんわかりやすい例として挙がっています。組織全体の常設の権限を信頼する代わりに、単一リポジトリの読み取り専用にトークンを絞れる。オープンソースの GitHub Tools SDK は `code-review` のようなプリセットを選ぶと必要なスコープだけのトークンを発行します。`subject` に名前付きユーザーを渡せば、そのユーザーが一度きりの同意フローで許可した範囲で、本人として動きます。

イベントの受け取り側も同じ考え方でした。Triggers では、ユーザーが Slack に投稿するとプロバイダは Vercel Connect にイベントを送り、Connect がサーバー側で署名を検証し、OIDC アイデンティティで再証明してからプロジェクトに転送します。アプリ側には振る舞うための bot トークンも、webhook を検証するための署名シークレットも残らないのに、ループ全体は回る。Deployment Protection が有効でも転送されたイベントは届きます。eve と Chat SDK 向けのアダプタを使うと、Slack 連携で環境変数に置きがちな `SLACK_BOT_TOKEN` と `SLACK_SIGNING_SECRET` の2つがアプリから消えます。

GA で加わったのがガバナンスの3点で、コネクタを作れる人を絞る RBAC、認可とコネクタ活動を記録する監査ログ、プロジェクト横断でトークンとトリガーの使われ方を見せる可観測性です。監査で「いつ誰がどのシステムにアクセスできたか」を聞かれたとき、答えがプロジェクトと Slack スレッドを掘る調査ではなく、監査ログへのクエリになる、という説明が実感に近いところでしょう。価格は全プランで利用でき、トークンリクエストとトリガーイベントに基づきます。Hobby は月500リクエストと1,000トリガーまで無料、Pro は1,000リクエストあたり$3・1,000トリガーあたり$0.95。ベータ期間中の利用者は 2026年9月25日 まで現行の条件が続きます。

UXエンジニアリングの視点だと、`subject` にユーザーを渡すと本人として動く、という部分が効いてきます。エージェントが何かをしたとき、それが「アプリの bot がやった」のか「あなたの権限でやった」のかは、UI 上で見せ分けたい情報です。共有 bot 1つで全員ぶんを代行する構成だと、ログにも通知にも本人が現れません。認証の設計が、そのまま「誰の行為として画面に出すか」の設計になっています。

### [Introducing Run SDK: secure eval for your agents](https://vercel.com/blog/introducing-run)

> **出典**: Vercel | **公開日**: 2026-08-25 | **カテゴリ**: frontend

**3行まとめ**
- エージェントが書いた TypeScript を、アプリの権限を渡さずに実行するためのパッケージです
- worker thread 内の新しい QuickJS コンテキストで評価し、アプリ側は host function だけを露出します
- 認証や人間の承認のために実行を中断でき、再開時に済んだ呼び出しはやり直しません

**詳細解説**

エージェントはツールを組み合わせて結果を処理するために TypeScript を書くようになりました。そのプログラムが実際のアプリケーションに触れはじめると、認証が要るステップや人間の承認が要るステップが出てきます。`eval` で実行すると周囲のアプリと同じ権限になり、秘密にも内部サービスにも届いてしまう。しかも境界で止まって待つ手段がない。Run SDK はそこを埋めるライブラリです。

設計の中心が host function です。アプリは公開したい操作だけを `hostFunctions` として渡し、それがサンドボックス内でグローバルとして呼べるようになります。例では `store.listOrders(customerId)` だけを見せていて、データベースクライアントとその認証情報はアプリ側に残ります。呼び出しはシリアライズを介して境界を越え、host function は Promise を返してよいので、既存のサービスクライアントをサンドボックスに渡さずにインターフェースの裏に置けます。

「code mode」と呼ばれる使い方の説明が良いところで、エージェントにプログラムを渡すと仕事の単位が変わる、と書かれています。1回のモデル応答で、CRM のアカウント取得と請求書一覧の取得を `Promise.all` で並列に投げ、期限切れだけ絞り込んで、必要な結果だけ返せる。2つのリクエストが同時に走り、フィルタはプログラム内で完結し、アプリに返るのは有用な結果だけです。サポートエージェントが請求 API の巨大なレスポンス全体をコンテキストに戻さずにアカウントを調べられる、という例が挙がっています。API 設計の助言も添えられていて、host function は製品の操作に対応させるのが良く、`orders.refund(id)` なら「このユーザーとこの注文でよいか」を確認する場所が明確になる。汎用のリクエスト関数にすると権限の見通しが一気に悪くなります。

human-in-the-loop の扱いが実装として参考になります。請求書を読むのと返金を実行するのは違うので、機微な操作に到達したら host function 側が `context.interrupt()` で実行を止められます。中断されると署名付きトークンが返るので、アプリはそれを承認リクエストと一緒に保存し、決定が届いたら再開します。再開はプログラムを再生する形ですが、確定済みの host function 呼び出しは記録された結果を使うので、中断前に完了した処理は走り直しません。中断された関数が承認を受け取って、そこから続きます。待っているあいだアプリが時間を持つので、worker を生かしておく必要がないのも実務的です。

制限まわりも書かれていて、`createRunner()` で `timeoutMs` と `memoryLimitBytes` を共通設定でき、実行ごとにも指定できます。呼び出しごとに新しい QuickJS コンテキストが割り当てられ、動的評価は無効、組み込みプロトタイプは硬化されます。ただし、この境界が守るのは生成されたプログラムに対してであって、host function は信頼されたアプリのコードなので通常の認可チェックは自分でやる必要がある、と釘が刺されています。OS やパッケージインストール、プロセスレベルの分離が要るワークロードは Vercel Sandbox のほうへ、という住み分けです。

出自の説明も短く載っていて、最初は `just-bash` の中の `js-exec` として QuickJS 上に存在し、それを抽出して Node 形の環境をアプリ定義の host function に置き換えたもの。`eve` で実ツールに対して検証し、いまは AI SDK の code mode を動かしています。既存の AI SDK のツールが host function にマップされ、実行のサンドボックス化を Run SDK が担う構造です。Node.js 22.13 以上と Bun に対応。

**詳細解説**

baqemono のクリエイティブデベロッパー Tomoyuki Nakata さんによる Three.js のチュートリアルです。パリで開かれる最初の Three.js カンファレンスに合わせた Codrops のシリーズの一本で、きっかけは Pinterest で見つけた1枚の画像でした。グレースケール画像の一部が、レンズ効果のかかったカラーの四角で切り抜かれているデザイン。それを WebGL で再現しつつ、四角がマウスを追い、背景側にも別のエフェクトを載せたらもっとおもしろくなるだろう、と考えて作ったものだそうです。

作り方の順序がそのまま学びになっています。まず2枚のテクスチャを全画面に出すところから。`getCoverUv` という関数で、CSS の `background-size: cover` と同じように、アスペクト比を保って中央から切り取る UV を作ります。次に `v_uv` を -1.0〜1.0 の範囲に変換して画面中央を原点にした座標系を用意し、`u_squareSize` を辺の半分として4辺の境界を定義し、`step` で内外を判定した4つの結果を掛け合わせます。すべての条件を満たす内側が 1.0、外側が 0.0 になるマスクの完成です。ビューポートをリサイズしても正方形が伸びないよう、メッシュの寸法からアスペクト比の補正係数を作って、判定に使う座標をそれで割ります。

いちばん読みごたえがあるのが CC Lens の適用です。`getCCLensUv` に正方形内のローカル UV を渡すと歪んだ UV が返りますが、それをそのままカラー画像の UV に使うと画像全体が正方形に押し込まれてしまいます。狙いは2枚の位置とサイズを揃えたまま、カラー画像だけを歪ませることなので、歪む前と後の差分を `squareLensOffset` として取り出します。ただしこれは正方形を基準にした移動量なので、全画面の `v_uv` にそのまま足すと歪みが大きくなりすぎる。正方形サイズとアスペクト比補正を掛けて `viewportLensOffset` に変換してから足す、という段取りです。座標系の変換ごとに名前を付け替えているので、どの空間の値を扱っているのかが追いやすくなっています。

RGB シフトも同じ発想でした。一定量を足すと正方形のどこでも同じ方向に同じだけずれてしまうので、中心を基準にします。`squareUv` から 0.5 を引いて 2.0 倍し、-1.0〜1.0 のサイズ非依存な方向ベクトル `rgbShiftDirection` を作る。中心では 0、端で ±1 になるので、チャンネルごとのユニフォームがそのまま「端での最大ずれ量」になります。既定値は R が 0.01、G が 0.0、B が -0.01 なので、中心では3チャンネルが重なり、端に向かって R と B が反対方向に分かれます。

マウス追従は `uvSquare -= u_mouse` の1行です。DOM の座標は左上原点のピクセルなので、TypeScript 側で -1.0〜1.0 に変換し、シェーダーは上が正なので Y を反転します。滑らかさは `Vector2.lerp` による線形補間で、補間後の値を毎フレーム `u_mouse` にコピーするだけ。背景のグレースケール画像には `sin` による波と、Shadertoy 由来の `random3` によるノイズを `u_time` とともに加えています。最後に、正方形サイズ、レンズの強さ、RGB シフト量、波とノイズのパラメータを GUI に出して終わりです。

UXエンジニアリングの視点で持ち帰るなら、進め方そのものでしょう。完成品は複雑に見えますが、著者が言うとおり小さな部品の組み合わせで、しかも各段階のシェーダーが GitHub にステップごとのファイルとして置かれています。効果を最初から通しで書くのではなく、マスクだけ、歪みだけ、と分けて画面に出しながら足していく。同じやり方は、プロダクションの表現を実装するときの分解にもそのまま使えます。あわせて、調整したい値を全部ユニフォームに逃がして GUI に並べる習慣は、デザイナーと一緒に詰める場面で効いてきます。数値の議論を口頭でやらずに、その場でスライダーを動かして決められるからです。

「エージェントから見たときにこのサイトは使えるか」を点数にするサービスです。採点の設計に気配りがあって、まず配点の大半を占める Essential チェックが、サーバーでレンダリングされたコンテンツ、正しい HTTP の振る舞い、明確な文書構造、回復できるエラー、操作できるコントロールという、ごく基本的なところを見ます。Recommended チェックはスキャンの証拠から API・OAuth フロー・GraphQL エンドポイント・MCP サーバー・開発者ポータル・コマース面のいずれかがあるとわかったときだけ有効になり、当てはまらないチェックは失敗ではなく除外されます。提供していないインターフェースを持たないことで公開サイトが減点されない、という考え方です。新しいフォーマットは限定的なボーナスにはなりますが、ないことで点は下がりません。

レポートの読み方も示されていて、まず失敗した Essential から見る（それが普通のエージェントに必要な最低ラインを記述しているから）、次にプロダクトの実際の機能と一致する Recommended のギャップを見る。各指摘にはスキャン中に観測された証拠と、可能なら実装ワークフローにコピーできる具体的な推奨が付きます。レポートには「観測されたエージェントの旅程」も含まれていて、1体のエージェントがどうサイトを回り、どこで摩擦にぶつかったかが記録されます。ただしこれは補足的な証拠であってスコアには入りません。1回の実行では、あらゆるエージェント・ユーザーの目的・本番の条件を代表できないから、という理由が明記されています。

自分自身が説くことを実践している部分がおもしろいところです。レポートの公開 URL は安定していて、最新の完了スコアが最初の HTML レスポンスに含まれます。クローラーが JavaScript を実行したりクライアント側の fetch を待ったりしなくていいわけです。`text/markdown` を要求したエージェントには、同じ正規 URL でコンパクトな Markdown 表現が返り、ソフトウェア連携にはレポート API から構造化 JSON が返る。共有キャッシュで HTML と Markdown の表現が混ざらないよう HTTP の Vary ヘッダーで分けています。MCP サーバーは完了済みレポートを読み取り専用のツールとして公開し、入力スキーマと構造化出力、MCP Apps 対応ホスト向けのスコアカードを持ちます。これらの機械向けインターフェースはどれもスキャンを開始せず、対象サイトを変更せず、認証情報も要求しません。

限界の書き方も誠実でした。レポートはある時点のひとつの公開 URL から得られた証拠を記述したもので、ステータスコード、クローラーポリシー、レンダリング結果、ドキュメント、公開されている API、新興のエージェントプロトコルは、スナップショットの後に変わりえます。優先順位付きの技術レビューとして使うもので、あらゆるモデルやブラウザ自動化がすべてのタスクを完了する保証ではない。認証済みのページやワークフロー、地域差、bot 対策、一時的な障害、ユーザー固有の状態は公開スキャンでは観測できません。セキュリティ、アクセシビリティ、プライバシー、法令順守、ビジネス品質は、それぞれ専用のレビューが必要だ、とも書かれています。

UXエンジニアリングの立場で読むと、Essential として並んでいる項目が、エージェント時代のために新しく生まれた要求ではないところが目を引きます。サーバーレンダリング、正しいステータスコード、意味のある見出し構造、回復できるエラー。どれもアクセシビリティと SEO と堅牢性の文脈で以前から言われてきたことの言い直しです。エージェント向けの表層を人間向けとは別に用意するのではなく、既存の基礎が効いている、という読み方ができます。逆に言えば、クライアント側でしかレンダリングされない画面や、エラー時に何が起きたかを返さない API は、人にとってもエージェントにとっても同じように使いにくかった、ということでもあります。

### [Vibe coding and quality](https://ilyabirman.net/meanwhile/all/vibe-coding-and-quality/)

> **出典**: Sidebar | **公開日**: 2026-08-25 | **カテゴリ**: design

**3行まとめ**

この記事の価値は、品質の上限を決めていたものを言い当てたところにあります。技術力でも設計力でもなく、反復の回数と、それを頼める相手がいるかどうかだった。ただし前提は明示しておくとよいでしょう。この結論が成り立つのは、作者自身が「何が良いか」の基準をコマ送りで判別できる水準で持っているからです。基準を持たないまま同じ方法を取れば、速く快適に動くものではなく、速く大量に作られたものが出てきます。品質を決めているのは書き手が人間かどうかではなく、判断する人が細部を見ているかどうかだ、と読むのが公平なところでしょう。

### [Vercel applications are protected from Next.js August 2026 security vulnerabilities](https://vercel.com/changelog/nextjs-august-2026-security-release)

> **出典**: Vercel | **公開日**: 2026-08-25 | **カテゴリ**: frontend

**3行まとめ**
- Next.js の2026年8月セキュリティリリースで、critical が2件公開されました
- 1件は libheif 由来で、細工した AVIF を Image Optimization が処理すると未認証のリモートコード実行につながります
- もう1件は Windows でホストしている Next.js サーバーが対象です

**詳細解説**

1件目は GHSA-2xp9-vwfh-vxw4 で、上流の libheif に起因します。Image Optimization が細工された AVIF 入力を処理したときに、認証なしのリモートコード実行に至りうるものです。2件目は CVE-2026-75604（GHSA-p293-qw3h-jr36）で、Windows ホストの Next.js サーバーが対象。Pages Router を使っているアプリと、Cache Components を使わない App Router のアプリが該当します。

Vercel 上のアプリは対応が不要です。AVIF の脆弱性が特定された時点でマネージドの Image Optimization サービスで AVIF 最適化を無効にし、AVIF 入力は加工されずそのまま配信されるようになりました。影響を受ける処理経路を通らない、ということです。2件目は Windows ファイルシステムを使うサーバーだけの問題で、Vercel の Next.js ランタイムは Linux なので該当しません。

セルフホストの場合は、15.x 以前なら `next@15.5.24`、16.x なら `next@16.3.3` に上げます。ここで注意しておきたいのは、パッチ版でも AVIF 画像はリサイズも最適化もされず、修正された libheif が出るまでそのまま配信されるという点です。Windows 側の脆弱性には回避策がないので、該当するサーバーは即座にアップグレードします。

UXエンジニアリングの観点で気にしたいのは、この「AVIF が最適化を通らなくなる」という副作用のほうかもしれません。AVIF を主フォーマットにして配信サイズを詰めていたサイトでは、当面その分の効果が消えます。元画像の大きさによっては転送量が増え、LCP に出ることもあるでしょう。パッチを当てて終わりにせず、しばらくは実際の配信結果を見ておくとよさそうです。前述の Speed Insights のような実ユーザー計測を入れていれば、影響が出ているかどうかはそこで確認できます。
