### [The CSS caret-* properties and custom caret accessibility](https://www.sarasoueidan.com/blog/caret-styling-accessibility/)

> **出典**: Sara Soueidan | **公開日**: 2026-11-16 | **カテゴリ**: accessibility

**3行まとめ**
- 入力欄で点滅する縦線（キャレット）も、フォーカスの位置を示すしるしの1つです。CSS の `caret-color`・`caret-shape`・`caret-animation` で見た目を変えるときの注意を、WCAG と各ブラウザの挙動からまとめています
- `caret-color` は入力欄のキャレットだけでなく、F7 キーで使えるキャレットブラウズ（矢印キーで本文を移動する機能）のキャレットにも効くので、ページ上のすべての背景に対して 3:1 のコントラストが要ります
- macOS の「点滅しないカーソルを優先」はブラウザも守りますが、Windows のカーソルの太さや点滅の速さの設定は、現在どのブラウザも Web ページに反映しません

**詳細解説**

`caret-shape`（bar・block・underscore）は Chromium でフラグを有効にしたときだけ動き、`caret-animation` も Chromium だけが対応しています。`caret-animation: manual` にすると標準の点滅が止まり、`@keyframes` で色や形を動かせます。ただ、ユーザーが OS でキャレットの点滅だけを止めているかどうかを、CSS で知る手段はありません。`prefers-reduced-motion` で囲むだけでは足りないので、独自のアニメーションを付けるなら、サイトのなかに止めるスイッチを用意するよう勧めています。

WCAG では、入力欄のキャレットはフォーカスの表示の1つに数えられます。枠線のコントラストが足りなくても、キャレットの色が背景と 3:1 あれば 1.4.11 を満たす例が、Understanding 文書に載っています。逆に、`caret-color` を薄い色にして、ほかに十分なフォーカスの表示もなければ、1.4.11 を満たせません。AAA の 2.4.13 の基準には、キャレットは面積が小さすぎて、block にしても届きません。満たすには別のフォーカスの表示が必要です。

2026年9月に改訂された欧州の規格 EN 301 549 v4.1.1 は、テキストカーソルを含む OS のアクセシビリティ設定を Web ページが上書きしないよう求めています。入力欄のセレクタだけに `caret-color` を当て、キャレットブラウズのキャレットには本文の色を引き継がせる書き方も紹介しています。ブランド色を `caret-color` に入れているなら、ダークテーマの背景とも 3:1 を保てる色を、テーマの変数として別に持たせておくと手軽です。

### [Declarative dragging](https://declarative-dragging.github.io/)

> **出典**: Sidebar | **公開日**: 2026-11-17 | **カテゴリ**: design

**3行まとめ**
- UIST 2026 で最優秀論文賞を受けた、ドラッグ操作の作り方の研究です。要素ごとに「ドラッグするとどの状態に移れるか」を宣言するだけで、ドラッグ・アンド・ドロップの操作ができあがります
- エンジンが移り先の状態を先に描画してみて、それぞれで要素がどこに来るかを取り出し、その位置をもとに、なめらかに動くドラッグの操作を組み立てます
- Web の SVG 向けのライブラリ「Dragology」として npm で公開されていて、数式の木、トランプの山、ベジェ曲線などのデモが試せます

**詳細解説**

これまでドラッグの操作を作るには、座標の計算、落とせる場所の判定、つかんでいる間の見た目、離したあとのアニメーションを1つずつ書く必要がありました。Dragology では、単純なドラッグを組み合わせれば、複雑な操作も作れます。浮かせる、吸い付かせる、遷移させるといった振る舞いは、モディファイアとして重ねます。

論文を出したあとは、1つのものを複数の表し方で並べる画面に使っています。置換（permutation）を学ぶデモでは、どれか1つの表し方をドラッグしている途中でも、ほかの表し方が一緒に変わります。編集のたびにコードの意味が保たれるプログラミング環境 Hazel では、リファクタリングをドラッグでできるようにしました。

### [AI Sped Up The Build: How Can Accessibility Testing Keep Up?](https://smashingmagazine.com/2026/11/ai-sped-up-build-how-can-accessibility-testing-keep-up/)

> **出典**: Smashing Magazine | **公開日**: 2026-11-17 | **カテゴリ**: design

**3行まとめ**
- 人の判断を「見つける」「直す」「証拠を残す」の3か所に置き、受け渡しやプルリクエストのような、もとからある手順に組み込むよう提案しています
- Level Access が2,500人以上に聞いた調査では、AI で速くなった工程は設計61%、計画58%、開発51%で、QA とテストは30%にとどまりました
- アクセシビリティの指標がどれも良くなっている組織と、ほかの組織とで、AI を使う割合はほとんど変わりません。差が出たのは、研修、チーム内のやり取り、文化といった周りの取り組みです

**詳細解説**

Level Access とは別に、WebAIM の調べでは、上位100万サイトのトップページで自動検出されるエラーが、1年で1ページあたり51件から56.1件に10.1%増えました。WebAIM は理由の候補の1つに、AI の支援を受けたコーディングを挙げています。Level Access の組織どうしの比較のほうは、アンケートの結果なので相関までしか言えないとしています。

「見つける」では、フォーカスの順番、アクセシブルな名前、状態、見出しの構造、変化やエラーのときに読み上げる内容を、受け渡しの時点で決めておきます。決めておかないと、AI が自分の既定値で埋めてしまいます。決めた内容は仕様書だけでなく、デザインシステムの部品、AGENTS.md などのルールファイル、プロンプトのテンプレートのように、AI が読む場所にも置くよう勧めています。Figma では GitHub の Annotation Toolkit を使うと、見出しやフォーカスの順番をキャンバスに書き込めます。プルリクエストでは eslint-plugin-jsx-a11y、Pa11y、Lighthouse CI で、基準からの差分だけを確かめます。

「直す」では、AI の修正案を下書きとして扱います。`div` に `role="button"` を付ける、余計な ARIA を足す、alt を作り話で埋める、のように、チェックは通っても正しくない直し方があるからです。「証拠を残す」では、修正と一緒に回帰テストを書き、どの支援技術で何を確かめたかをプルリクエストに短く残します。証拠がそろっていたおかげで、VPAT/ACR（アクセシビリティの適合報告書）を書く時間を70%以上減らせた、という Level Access 自身の例も載っています。

### [Do AI and Human Moderators Uncover the Same Facts?](https://measuringu.com/do-ai-and-human-moderators-uncover-the-same-facts/)

> **出典**: MeasuringU | **公開日**: 2026-11-17 | **カテゴリ**: ux-research

**3行まとめ**
- 睡眠についてのインタビューで、20人を人の司会と AI の司会（Gemini 3 Flash と、同じ研究者の姿と声のアバター）にランダムに分け、スクリーナーで先に聞いておいた事実がどれだけ会話に出てくるかを比べました
- 参加者ごとに出てきた割合の平均は、人の司会で35%、AI の司会で21%でした（p = .003）。調査の目的に近い事実（寝室の環境や機器、ペットなど）に絞っても、52%と34%の差があります
- 司会が聞き出した事実の数はほとんど変わらず、差の多くは、聞かれていないのに参加者が自分から話した事実の数（1セッションあたり2.5件と1.0件）で開いています

**詳細解説**

スクリーナーには、使っている機器、ペット、子ども、睡眠のための道具などを選ぶ質問があり、合わせて256件の事実がわかっていました。この回答は、人の司会にも AI の司会にも見せていません。耳栓やアイマスクのような寝るときの道具は、人の司会が「ほかに眠りをよくするためにしていることはありますか」と聞いて出てきました。AI の司会はこの話題を聞いていません。人の司会は3セッションでガイドにない質問をし、そこから5件の事実が出ました。AI がガイドの外で聞いたのは1回だけです。

AI のセッションは短く、参加者が話した言葉も半分ほど（1セッション平均2,028語と988語）でした。ただ、言葉の数の違いを統計で補正しても、15ポイントの差が残ります。

1条件10人の小さな調査です。事実の照合には Claude を使っていて、照合のときにどちらの条件かを伏せていません。目的との近さによる分け方も結果を見てから決めているので、探索的な結果として読むよう書かれています。AI の司会を自社の調査に入れるかを決めるときも、同じようにスクリーナーの回答を司会に伏せておき、あとで照らし合わせれば、聞き漏らしを数字で比べられます。

### [Staggering Scroll-Driven Animations with animation-range-start](https://css-tricks.com/staggering-scroll-driven-animations-with-animation-range-start/)

> **出典**: css-tricks | **公開日**: 2026-11-16 | **カテゴリ**: css

**3行まとめ**
- スクロールに合わせて文字を1つずつずらして出すアニメーションを、Frontend Masters の記事では独自の CSS 関数と長い数式で作っていました。それを `animation-range-start` の1行で書き直しています
- `animation-delay` は時間で進むアニメーションにしか効きませんが、スクロールで進むアニメーションでは `animation-range-start` が開始を遅らせる役を受け持ちます
- `animation-timing-function` もスクロールで進むアニメーションに効くので、イージングを自前で作り直す必要もありません

**詳細解説**

書き直しの中心は `animation-range-start: contain calc(10% + 2.5% * sibling-index());` です。8文字を2.5%ずつずらし、最後の文字が包含範囲の30%（10% + 20%）で出てくるように割り振っています。元の作り方では、すべての文字のアニメーションを1本の進み具合にまとめているので、イージングも文字ごとでなく全体にかかってしまいます。

React、Pretext、CSSTree のように、ブラウザの機能を作り直して得をしてきた例も表にして、何が手に入り何を払ったかを比べています。元の記事の数式には、時間でもスクロールでもない値（入力の進み具合やクイズの回答状況など）でアニメーションを動かせる、という使い道が残るとも認めています。書き直したデモは Chromium 系のブラウザで見られます。

### [おい、 Mutation Test をやれ。テスト品質を、測るために](https://zenn.dev/mizchi/articles/mutation-test-quality)

> **出典**: mizchi | **公開日**: 2026-11-17 | **カテゴリ**: testing

**3行まとめ**
- AI でテストカバレッジは簡単に上げられるようになりましたが、そのテストが振る舞いの変化を本当に見つけられるかは、カバレッジではわかりません
- ミューテーションテストは、比較演算子や戻り値をわざと書き換えたコード（ミュータント）でテストを回し、テストが落ちずに生き残ったものから、検査の足りないところやデッドコードの候補を見つけます
- Vitest 向けに作られた `@mizchi/mutator` は、型チェックが通らないミュータントを先に除き、Git の差分と結果のキャッシュで回す量を減らしています

**詳細解説**

`n > 3` を確かめるテストで 0 だけを渡していると、`>` を `<` に変えたミュータントは落ちますが、`>=` に変えたものは生き残ります。3 ちょうどで `false` になるかを確かめていないからです。どんな入力でも振る舞いが変わらない「等価ミュータント」もあるので、ミュータントが生き残っても、テストが悪いとは限りません。

書き手の経験では、単純な分岐カバレッジは85%を超えたあたりから費用に見合わなくなり、95%を超えると「テストのためのテスト」になりやすいと見ています。ミューテーションテストも、CI で毎回全件を回すものとしては扱わず、リファクタリングのときに使う指標と位置づけています。`cookie-es` での計測では、全体の初回の実行が12.2秒、1か所変えたあとの `--since HEAD` による差分の実行が0.71秒でした。

Playwright のテストに当てはめると、10秒かかるテストをミュータントの数だけ繰り返すことになり、割に合いません。IO のない速いユニットテストに向いた道具です。UI のコードで試すなら、日付や金額の表示を整える関数や、デザイントークンを変換するスクリプトのような、純粋な関数から始めると手軽です。Node.js 24 以上と Vitest 5 が前提で、`pnpm add -D @mizchi/mutator` で入れ、`.gitignore` に `.mutator/` を足せば動きます。

### [Introducing spatial CSS: A developer preview](https://webkit.org/blog/18621/introducing-spatial-css-a-developer-preview/)

> **出典**: WebKit Blog | **公開日**: 2026-11-16 | **カテゴリ**: web-standards

**3行まとめ**
- visionOS 27.3 の Safari で、提案中の spatial CSS を試せる開発者向けのプレビューが始まりました。まずは `<model>` 要素の3Dオブジェクトを扱う機能が中心です
- `spatial: portal` を付けた要素のなかのモデルは1つの空間を共有し、いつもの `transform` で、それぞれを本当の3Dとして動かせます
- 新しい構文の多くは、`position-anchor` や `@keyframes` にならった、今ある CSS の書き方の延長です

**詳細解説**

3Dのモデルどうしをはめ合わせるには `position-anchor` を使います。例では、Blender で作った盤に、ブロックがはまる位置を「空のオブジェクト（null object、empty）」として置いておき、CSS からその名前を指定してブロックを正しい位置に置いています。照明は `@environment-map` で360度の HDR 画像を名前付きで定義し、複数の要素で使い回せます。`portal-action: orbit` を付けるとユーザーがシーンをその場で回して見られ、`requestVolumetricScene()` を呼ぶとシーンをブラウザの窓の外に出して部屋のなかに置けます。

`<model>` 要素は、Safari 27 のすべてのプラットフォームで使えるようになっています。spatial CSS も宣言的な CSS なので、画面の比率、カラーテーマ、動きを減らす設定に合わせたメディアクエリで、3Dの表示も切り替えられるとしています。

位置は3Dの制作ツールの側で決め、コードは名前で参照するだけなので、モデルを作る人とページを作る人のあいだで座標の数値をやり取りせずに済みそうです。試すには、Vision Pro か Xcode に入っている visionOS のシミュレータで「CSS Portals」のフラグを有効にします。

### [Engineering AI Discover](https://netflixtechblog.com/engineering-ai-discover-e244944cdc38)

> **出典**: Netflix Tech Blog | **公開日**: 2026-11-17 | **カテゴリ**: engineering

**3行まとめ**
- Netflix は TV アプリに、テーマを選んで見たい作品を探す「AI Discover」のタブを一部の会員向けに出しました。その裏で、LLM と既存の推薦の仕組みをどう組み合わせるかを決める層を作っています
- リクエストごとに先に計画を立て、検証してから実行します。LLM が計画を作ることもありますが、実行してよいかはコードが決め、計画が遅いときや検証に落ちたときは試験済みの計画に戻ります
- 年齢制限や、会員が「勧めないで」と伝えた内容のように、どんなときも守るルールはプロンプトに書かず、コードで守っています

**詳細解説**

TV では文字を打ちにくいので、会員はリモコンでテーマを選ぶだけで、自由入力やチャットはありません。生成には数秒かかるため、ボタンを押すとサーバーがすぐに受け付けを返し、TV は何を準備しているかを説明する「考え中」の画面に切り替わります。結果ができるとサーバーが TV に知らせ、TV が取りに行きます。会員がどのくらいの時間なら待ってくれるかは、まだわかっていないとしています。LLM の呼び出しが失敗しても、会員にはどんなときも画面を返します。

TV アプリの更新には時間がかかるので、振る舞いの多くはサーバー側のプロンプトと設定に置き、モデルや部品をアプリのリリースなしで入れ替えられるようにしました。入れ替える前には、自動のチェックと LLM による採点で同じタスクを比べます。計画のなかの値は LLM に直接書かせずにプレースホルダーにしておき、検証のあとでコードが埋めます。これはプロンプトインジェクションへの対策にもなっています。

Web のアプリに生成 AI の機能を入れるなら、待ちの画面を「受け付けた」「準備中」「届いた」「失敗したので試験済みの結果を出す」の4つに分け、デザインの段階で4つとも画面を用意しておくと、失敗したときの画面を作り忘れずに済みます。

- 名詞は名詞、動詞は動詞と品詞をそろえて入れ替えるので、文法は崩れません。1,500の文章で試すと、全体の約25%の単語を替えただけで、半分の文章で元の主張が読み取れなくなりました
- React では `<Shield>` で囲むとビルドのときに置き換わります。`"use client"` のファイルに入れると元の文が漏れ、しかもエラーにならない点に注意が要ります

**詳細解説**

検索エンジンも置き換えた単語を読むので、検索で見つけてほしいページには使えません。フォントから置き換えの表を取り出せることも、作り手自身が確かめて公開しています。そのため、暗号で隠すことより、大量に集めるコストを上げることで守る、という考え方をとっています。対応している言語は英語だけです。

### [Agents are users, so your software needs evals](https://vercel.com/blog/agent-evals)

> **出典**: Vercel | **公開日**: 2026-11-16 | **カテゴリ**: frontend

**3行まとめ**
- エージェントも人の代わりにソフトウェアを使う利用者だとして、API や CLI、MCP サーバーを作る側が、エージェントがタスクをやり遂げられるかを測る eval（何度も回して採点するテスト）の作り方を解説しています
- テストを LLM の呼び出し回数で、決定的なテスト（0回）、1ターンの eval（1回）、E2E の eval（2回以上）の3段に分け、捕まえたい問題を捕まえられる、いちばん下の段を選ぶよう勧めています
- 例はサンフランシスコでコーヒーを注文する架空の CLI `sfbeans` で、オープンソースの Harbor を使い、タスク・環境・検証・正解例の作り方を順に示しています

**詳細解説**

5回のうち3回成功するエージェントなら、5回のうち少なくとも1回成功する確率（pass@5）は約99%ですが、5回続けて成功する確率（pass^5）は約8%です。どちらを見るかは、失敗したときにユーザーがどれだけ困るかで決めるよう勧めています。やり直しのきかない毎朝のコーヒーの注文なら pass^k、テストを見ながら直せるコーディングエージェントなら pass@k、ユーザーが送る前に読むメールの下書きなら単純な成功率です。

検証のスクリプトは、注文が1件か、飲み物が合っているか、時間に間に合うか、予算内かを別々に採点します。予算オーバーの失敗は、記録を読んで初めて原因がわかりました。エージェントがメニューの値段を見て、税とチップ込みの見積もりを取らずに注文していたのです。直す場所は CLI の側で、見積もりの合計を目立たせるか、上限を超える注文を断る `--max-total` を足す、という結論です。

記録を読むと、eval そのものの不具合も見つかります。「何もしないのが正解」のタスクで Codex はほぼ毎回合格しましたが、10回のうち9回は、探しもせずにあきらめていただけでした。そこで、検索してからあきらめたかも検証に加えています。結果の表の数字は、説明のために置いた例です。
