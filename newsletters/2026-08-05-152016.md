## ハイライト

### [Turn one giant AI-generated pull request to a reviewable stack](https://github.blog/engineering/turn-one-giant-ai-generated-pull-request-to-a-reviewable-stack/)

> **出典**: GitHub Engineering | **公開日**: 2026-08-04 | **カテゴリ**: engineering

**3行まとめ**
- エージェントが出す1,000行超のPRを、依存関係で層に分けた小さなPRの連なりへ組み替える
- データ、API、配線、UXの4層に分ければ、層ごとに違うレビュアーを割り当てられる
- 読むのは上から、レビューは下から。下層に修正が入っても `gh stack sync` で上へ伝播する

**詳細解説**

冒頭の問いかけが率直です。最後に出した大きな機能を、1つの巨大なPRに詰め込みましたか。それとも小さなPRの連鎖に分けて、手作業で同期し、下に変更が入るたびにコンフリクトを解きましたか。前者はレビューが難しく、後者は維持が難しい。その日の判断は痛みの少ないほうへ傾いた、と書かれています。

ここにコーディングエージェントが加わります。エージェントはPRの構造をどうするかという選択を代わりに決めてはくれません。むしろ選択の必要性を大きくします。例として挙がるのは、ショッピングアシスタントに商品検索を足すプロンプト。数分後に戻ってくると、新しいデータモデルとシード、APIルートとバリデーション、クライアントの配線とUIと空・フォールバック・エラー状態が、1,721行の1つの差分に載っている。「これは後で見ます」とレビュアーが言って、そのまま置かれる流れです。

GitHub の stacked pull requests が提案するのは分解です。機能を論理的な層に割り、依存の連なりを見つけて、下から積む。記事の例では4層になっています。L1が型付きカタログとシードデータとデータアクセスモジュール、L2が検証済みの `/api/products/search`、L3がチャットからAPIを呼んで実データで答える配線、L4が引用カードと状態表示。この分け方の効果として挙がっているのが、レビュアーの割り当てです。データはデータのオーナーが見て、UXはUIのオーナーが見る。層ごとに読む人を変えられます。

段取りとして先に決めるのは stack base です。CI とマージルールがスタック管理の全期間にわたってこのベースに対して評価されるので、ここが起点になります。CLI は `gh extension install github/gh-stack`。おもしろいのはそのあとで、`gh skill install github/gh-stack` でエージェント側にもスタックの扱い方を教える手順が入っていることです。層ごとに担当エージェントを決めていて、L1はデータモデラー、L2はバックエンド、L3とL4はフロントエンド。L3とL4を同じ作者にしながら層を分けているのは意図的で、UIのオーナーが裏側のデータフローを確認しなくてよい状態を作るためだと説明されています。

レビュー側の記述が読みどころです。スタックマップは方位磁石で、動きには向きがある。文脈のために上から読み、レビューは下から積む。上から読めば「チャット画面に商品カードを出したいのか」と最初にゴールが分かり、下から見ればそれぞれの層が前の層を理解したうえで意味を持つ。1,720行を1回で見る作業が、自己完結した小さな的の集まりに変わります。

実運用の細かい注意も1つ書かれています。L1にレビュー指摘が入って修正を押すと、スタック全体がずれて「Unable to merge as a stack」になります。PR画面には1クリックの Rebase stack ボタンが出ますが、これはGitHubのサーバー上で走るので、コミッターがボタンを押した人にリセットされ、できたコミットは署名されません。ブランチ保護が署名を要求していると、その1クリックで静かに壊れる。ターミナルから `gh stack rebase` で手元のGit設定を使い、`gh stack push`、そして `gh stack sync` で上の層へ伝播させるほうが安全だとしています。

UXエンジニアリングの視点だと、これは「レビュー可能性」を成果物の設計対象として扱う話です。UIを4層目に切り出すという判断は、フロントエンドの変更が常にデータ層の議論に巻き込まれる状況を構造で解いています。デザインシステムのコンポーネント追加やインタラクションの調整をレビューしてほしいとき、同じPRにマイグレーションが入っていれば見る人は減ります。エージェントが1回で全部書けるようになったぶん、どこで切るかを人が決める価値が上がった、という読み方ができます。

### [Designing for the proxy](https://uxdesign.cc/designing-for-the-proxy-2606ffac2335)

> **出典**: Sidebar | **公開日**: 2026-08-04 | **カテゴリ**: design

**3行まとめ**
- 記事もドキュメントもポートフォリオも、人より先に言語モデルが読んで解釈するようになった
- 検索は発見しやすさ、SNSはエンゲージメント、LLMは解釈しやすさを報酬にする
- 機械のために最適化するのは仕事の一部になった。機械のために設計するのは仕事ではない

**詳細解説**

長いあいだ、デザイナーの相手は人ひとつでした。手法もフレームワークも原則も、人の必要を理解して、人が辿れて信頼できて楽しめる体験を作ることを軸に回っていた。その土台は消えていないけれど、周りが変わった、というのが出発点です。

いま多くの体験には、人に届く前に別の読者がいます。誰かの疑問に答えるために書いた記事は、まず言語モデルに理解され引用される必要がある。APIを知りたい開発者は公式ドキュメントを開く前にAIアシスタントに聞く。情報を探すユーザーは、元のソースを訪れる前にAIが生成した答えを受け取る。「AIは働き方を変えた」とよく言われるけれど、起きているのはもっと手前のことで、**誰が最初に自分の仕事に出会うかが変わった**、と著者は書きます。

ここから危うさの話に入ります。デジタルプロダクトは昔から仲介者に形を変えられてきました。検索エンジンは情報の整理のしかたを変え、SNSのアルゴリズムは何が注目に値するかを決めた。セマンティックHTML、構造化メタデータ、見つけやすい情報アーキテクチャ。どれも人間中心設計と衝突しませんでした。行き先が同じだったからです。

LLMが違うのは、情報へ人を導くのではなく、解釈し、要約し、ユーザーの代理として振る舞う点です。マクルーハンを引きながら、新しいメディアは流通のしかただけでなく作られ方も変えると確認したうえで、検索は発見しやすさに、SNSはエンゲージメントに、LLMは解釈しやすさに報酬を与えると整理します。問題が始まるのは、代理指標が本来表していたものを置き換えたときです。SNSは関連する内容を見つけてもらうために設計されたのに、測れるという理由でエンゲージメントが支配的な指標になった。何を見続けるかの予測はうまくなったけれど、意味のあるつながりが作られたわけではない。システムは代理指標に最適化し、人の体験は二次的なものになった、と。

具体例が2つ挙がります。1つはヘルスケアの記事で、LLMの引用に完璧な構造でも、患者が理解できなければ失敗している。機械の理解に最適化することが問題ではなく、機械の理解が成功の定義になったときに問題が始まる。もう1つは採用です。応募者追跡システムとAIスクリーニングが増え、候補者が履歴書とポートフォリオをアルゴリズム向けに最適化していくと、採用は機械同士の会話に近づく。候補者は評価するシステム向けに書き、採用担当は二番目の読者になり、その後ろにいる人が見えにくくなる。

作る側の変化にも同じ構図を見ています。生成AIで制作の経済が変わり、それらしいインターフェースは数秒で出てくる。ただスクリーンショットは、プロダクトを成り立たせているものをほとんど隠します。著者はデザインの指示なしでスキンケアブランドのランディングページを vibe coding させ、それを実際のワークフローへ移しました。一貫したグリッドを入れるとレイアウトが崩れ、コンポーネントはシステムとして振る舞わず、インタラクション状態が欠け、タイポグラフィはブレークポイントを超えてスケールせず、アクセシビリティは考慮されていない。ハンドオフはピクセルの集まりで、エンジニアが作れるプロダクトではなかった。生成させたUIキットも、ボタンサイズが不必要にばらつき、セマンティックな階層が一貫せず、Figmaに移すと恣意的な小数がデザインスケールを置き換えていた。

「ピクセルはある。プロダクトはない」という一文が置かれています。良いデザインはスクリーンショットに映らない判断のなかにある。階層を作る余白の体系、プロダクトが変化していけるコンポーネント設計、認知負荷を下げるインタラクションのパターン、複雑さを分かるようにする情報アーキテクチャ、誰もが使えるようにするアクセシビリティの決定。建築家がレンダリングだけで評価されないのと同じで、建物は立ち、適応し、なかで暮らす人を支える必要がある。AIが目に見える層を作るコストを大きく下げたぶん、見えない層の価値が上がる。インターフェースが生成しやすくなるほどデザインが重要になるのは、デザインがもともとピクセルではなかったからだ、と。

結びは両立の話です。言語モデルは一貫性と明示的な構造と意味の明確さから利益を得て、人は個性・曖昧さ・驚き・感情に反応する。どちらも間違っていない。ドキュメントはAIアシスタントが正確に解釈できる構造を持ちながら、読むエンジニアに分かる必要がある。デザインシステムは機械可読でありながら、創造性を消すほど硬直しないほうがいい。GoogleのPeople + AI Guidebook を引いて、目的は人を過程から外すことではなく、人が意味を持って制御し続けられるシステムを設計することだとまとめています。「機械のために最適化するのは仕事の一部になりつつある。機械のために設計するのは仕事ではない」という区別が、この記事のいちばん持ち帰りやすい形でしょう。

UXエンジニアリングの視点では、この記事の主張は日々の実装判断にそのまま落ちます。構造化データを足す、見出しの階層を整える、alt を書く、ARIA を正しく当てる。どれも機械の理解と人の理解の両方に効く作業で、両立できる領域はかなり広い。分かれ道が出るのは、たとえば読みやすさを削って引用されやすい定型文に寄せるかどうか、といった選択のときです。今回の指摘は、その分かれ道が来たと気づくための語彙をくれています。

### [人と人の「認識のずれ」をAIが埋めるチケット管理 ── Notion Custom Agents + External Agents の実践](https://tech.layerx.co.jp/entry/2026/08/04/160016)

> **出典**: LayerX エンジニアブログ | **公開日**: 2026-08-04 | **カテゴリ**: engineering

**3行まとめ**
- 開発チケット管理を Notion の Custom Agents / External Agents で組み直した運用事例
- 起票直後にAIがプロダクトマネージャーの役割でヒアリングを始め、「起票からマージまでのあいだ」が埋まった
- 副作用として起票者の心理的ハードルが下がり、これまで取りこぼしていた要望まで拾えるようになった

**詳細解説**

まず用語の整理から入る構成が親切です。Notion AI はワークスペース内のドキュメントを検索・参照しながら答えるチャット型のAI。Custom Agents は2026年2月に始まった、トリガーを設定して自律的に動く目的別のAIで、最大の違いは「勝手に動く」ことだとされています。トリガーはメンション、スケジュール、データベースのプロパティが特定の値に変わったとき。External Agents は2026年7月からで、Notion の外のエージェント（現状はClaude、Cursorなど）をNotionに持ち込む機能。Notion Workers は2026年5月にリリースされたサーバーレスランタイムで、エージェントから呼ぶツールを自分で書けます。全体像は、Workers などでNotion側にコンテキストを集めておき、その上でNotion AIやCustom Agentsを動かし、必要ならExternal Agentsを使うという設計思想だと読み解いています。

背景にLinearからNotionへ戻ってきた経緯があります。合わなかった点が3つ挙げられていて、いずれも具体的です。1つはシート課金。たまにしか起票しない人とヘビーに使う人が混在する構造では、たまに起票したいだけの人のためにアカウントを用意するコストが割に合わなかった。2つ目はチケットの一覧性で、API経由の管理はとても使いやすいけれど、スプリントで棚卸しをするときのように、みんなで集まって画面を見ながら議論する場面では見づらさを感じた。ここは慣れや好みの問題も大きいと自分で断っているのが誠実です。3つ目は新しいツールを増やすこと自体のコストで、全社でNotionを導入済みなら、みんなが毎日開いている場所で完結させたほうがいい。

チームの構造の説明が、この選択の理由を支えています。AI-BPOの事業ではお客様から業務を預かり、AIとオペレーターが社内システムで遂行する。だから機能要望を起票する人が多様で、社内オペレーター、営業、エンジニア、QA担当が並びます。とくに社内オペレーターは実際のプロダクトを触るユーザーなので要望の解像度が高く、起票数も多い。「たまに起票する人が多い」という条件が、シート課金と噛み合わなかったわけです。

いちばんの主張は「あいだ」を埋めたことです。起票からデリバリーまでのサイクルは、エンジニアやプロダクトマネージャーの手が空いているときにしか進みません。忙しければヒアリングは後回しになり、そのあいだに起票者の記憶は薄れていく。Custom Agents を入れて変わったのはここでした。

具体例が2つ載っています。「一覧ビューにソート機能が欲しい」に対しては、どこの一覧ビューか、何のためにソートしたいかを確認しにいく。Whyが分かれば、そもそもソート以外の解が良いこともある。もう1つは「zipを解凍してPDFにするのが手間なので自動で解凍したい」で、実装するとパスワード付きzipをどうするか、zipの中にPDF以外が入っていたらどうするかという論点が出てくる。エージェントが先に潰しにいく。External Agents で Claude を繋げると実装観点まで踏み込んだ質問が来たり、バグのチケットでは原因まで特定してくれるそうです。

Instruction の抜粋が公開されているのが、この記事の実用的な部分でしょう。要求定義・要件定義のプロフェッショナルとして位置づけ、言葉通りの意味ではなく何を意図しているかを捉えること、アクター・目的・文脈・ルールの4観点が明確になるまで深掘りすること。そして対話ルールが3つ。質問は1回につき1つだけのワンクエスチョン制、前置きや挨拶や理由の説明を省いた100文字程度の超簡潔、そして「〇〇という目的でしょうか？」と推測を添えてYes/Noや短い言葉で返せるようにする。何度もやり取りさせると起票者にストレスを与えるので、数秒で返答できるようあえて短文で仮説を持って話す、という設計意図が明記されています。

手応えを感じているのは別のところだ、と続く節が個人的にいちばん残りました。実装には手間がかかると知っているから、起票する側は「これは細かすぎるから言わなくていいか」と遠慮する。この遠慮で失われている改善案はかなり多いはずだ、と。AIが仕様検討から実装の一歩手前まで伴走すると分かれば、心理的ハードルは下がる。そしておもしろい線として、オペレーターにとって「実装まで依頼する」のは億劫だけれど「自分の要望をチケットとして言語化する」のは億劫ではない、むしろ言語化を手伝ってくれると助かると感じてもらえる、という観察が置かれています。

ここで一度立ち止まる節が入るのも良かった点です。社内では「機能を作るな。楽して作るな。」という資料が共通認識になっていて、AIによって作るコストが大きく下がっても、アウトプットをたくさん作れば良いプロダクトになるわけではない。本当に必要なものを見極めて、なるべく少ない機能で実現する。だから言われた通りに作ることはせず、「本当に必要か」の議論は必ずやる。いっぽうでオペレーターやエンジニアは業務の解像度が高くWhyを理解した要望を出すので、結果としてそのまま作ることも少なくない、とも書かれています。

改善してほしい点として挙がっているのが2つ。モデル選択の「Auto」が体感では比較的カジュアルに高性能モデルを選ぶので、性能とコストの両立を安心して任せられる状態が理想だという話。もう1つは数値集計のような決定的であるべき処理をLLMに任せるのは適切ではないので Notion Workers に寄せたいけれど、設定の難易度が高くまだ誰でも気軽に使える機能ではない、という評価です。

UXエンジニアリングの視点では、Instruction の設計そのものがUIの設計です。ワンクエスチョン制、100文字、仮説を添える。この3つは、Slackという入力欄しかないインターフェースで「答えるコスト」を下げるための具体的な手段になっています。フォームの項目数を減らすのと同じ発想を、エージェントの発話に当てている。もう1つ効いているのは、起票のハードルという体験上の摩擦を、機能追加ではなく「AIが伴走すると分かること」で下げた点でしょう。摩擦の正体が入力の手間ではなく、依頼する側の遠慮だったという見立てが当たっています。

### [Are AI labs pelicanmaxxing?](https://dylancastillo.co/posts/pelicanmaxxing.html)

> **出典**: Sidebar | **公開日**: 2026-08-04 | **カテゴリ**: design

**3行まとめ**
- 動物8種×乗り物6種の48通りで1,008枚のSVGを生成し、7つのフロンティアモデルを比較した
- ペリカンは8種のうち6位、自転車は6種のうち5位、ペリカン×自転車は48通りで42位だった
- 難易度を吸収する固定効果回帰でも、ベンチマーク狙い撃ちを示す有意な効果は出なかった

**詳細解説**

Simon Willison がここ数年、主要なLLMのリリースごとに同じプロンプトを投げてきました。「自転車に乗るペリカンのSVGを生成して」。冗談まじりに始まった検証が、AIの世界でもっとも有名な非公式ベンチマークのひとつになり、新モデル発表のHacker Newsスレッドで最上位のコメントに並ぶようになった。ここまで有名になると、AIラボがこれに合わせて調整しているのではないかという議論も出てきます。数十億から数兆ドルが動く場で、良い結果がユーザーの説得に効くなら、少しくらい「ペリカンマックス」したくなるのではないか。

検証の設計が丁寧です。動物8種（ペリカン、フラミンゴ、サギ、カワウソ、アライグマ、アンテロープ、クジラ、ネコ）と乗り物6種（自転車、一輪車、スケートボード、キックボード、飛行機、ボート）で48通りのグリッドを作り、有名なプロンプトはそのうち1マスになる。表現はSimonのものとほぼ同じで、動物と乗り物だけ差し替える。フラミンゴとサギはペリカンに近く、ネコ・アライグマ・カワウソは易しく、アンテロープは難しく、クジラはもっとも遠い。OpenRouter 経由で7モデルを使い、温度1.0、同じ reasoning effort で1プロンプトあたり3サンプル。合計1,008枚です。

パイプラインは3段。SVGをPNGにレンダリングし（描画に失敗したら再生成して試行回数を記録。1,008件でリトライは11件だけ）、GPT-5.6 Luna が動物・乗り物・動作の整合性を1〜5で採点し、Gemini 3.1 Flash-Lite が認識した動物と乗り物、向き、シーン要素の自由記述リストを抽出する。仮説は明確で、もしラボがベンチマークを学習していたなら、ペリカンの行が動物としての実力より高い、自転車の列が乗り物としての実力より高い、あるいはペリカン×自転車のマスが両方を上回る、のいずれかが出るはずだ、と。

証拠が5つ並びます。まず目で見て、ペリカン×自転車が明らかに他より良い例は見つからなかった。次に動物ごとの平均点で、ペリカンは8種の6位。ネコ、クジラ、アライグマ、サギ、アンテロープの後ろで、7つのラボすべてがネコ・クジラ・アライグマをペリカンより上手に描く。自転車はもっと悪く、6種のうち5位で最下位の飛行機とほぼ同着でした。ただ、ペリカンはネコより描くのが難しいかもしれないという留保をきちんと置いています。自転車も、2つの揃った車輪、両方の車軸に届くフレーム、ハンドル、サドル、ペダルが必要で、審査モデルは自転車画像の3分の2でどれかの欠落や断絶を指摘していました。

そこで難易度を吸収する回帰に進みます。1,008枚に対して `score ~ lab + animal × vehicle` の固定効果モデルを当て、ペリカン、自転車、ペリカン×自転車のマスについてラボごとの交互作用項を入れ、ロバスト標準誤差を使う。動物×乗り物の項が48通り固有の難しさを吸収するので、交互作用項が平均的なラボに対するベンチマーク固有の上乗せを測ります。結果、ペリカン効果はどのラボも -0.11 から +0.14 の範囲で、最小のp値でも0.25。自転車効果は Grok 4.5 の -0.18 から Gemini 3.5 Flash の +0.27 まで散らばり、p<0.05を超えたのはGeminiだけで、符号は両方向に向いている。ペリカン×自転車のマス固有の効果は、どれもp<0.05に届かなかった。最大の正はGLM-5.2の+0.35（p=0.12）で、著者が目で見て気になったのと同じモデルでした。

多重比較の扱いが誠実です。21回の検定をp<0.05でやれば偶然の偽陽性が約1件（21×0.05≒1.05）出るはずで、実際に出たのがちょうど1件。Bonferroni の閾値は 0.05/21≒0.002 なので、p=0.022 は通らない。ただし区間の幅は平均で±0.6点ほどあり、それより小さい上乗せはこの検定では捉えられない、とも書いています。

5つ目の証拠は「記憶した構図」の検証です。ペリカンが必ず右を向く、太陽やスカーフが繰り返し出るという指摘に対して、21枚すべてが右向きだったのは事実で、48通りのなかでこれだけが全一致でした。ただ右向きは全体の60%で、自転車は81%が右向き、ペリカンも78%が右向き。ペリカンや自転車を正面から描くのは難しいので、モデルはほぼ横から描く。だから曖昧な画像が少ない。他にもアンテロープ×キックボードとペリカン×キックボードが21分の20、サギ×自転車が21分の19まで来ているので、21分の21は外れ値には見えない、という判断です。シーン要素では、フラミンゴ×ボートは全部に太陽が入り、カワウソ×飛行機は38%がスカーフをしていて、ネコ×自転車は38%にカゴが付く。ペリカン×自転車にとくに違うところはなく、他と同じようにいくつかの要素が出やすいだけだった。

限界の節も具体的です。採点が単一の審査モデルで、整合性の検証も再現性の確認もしていない。その審査モデルは出場モデルの1つと同じファミリーだけれど、どのラボも48通り全部を描くので、あるラボの作風を好む審査はそのラボのグリッド全体を持ち上げるだけで、この分析が見ている「ラボ内の差」は変わらない。もう1つは「SVGmaxxing」で、SVG生成そのものを全体的に最適化したラボは全マスが同時に上がるので、単に上手いラボと区別できない。GoogleやDeepMindは公然とやっている、と付記されています。予算は約80ドルで、それがサンプル数3、審査1つ、7モデルという規模と、「plane」を「airplane」にしなかった反省を含むプロンプトの詰め切れなさに繋がっている。

その「plane」の話がいい教材です。モデルは plane を幾何的な平面として読むことが多く、動物が平らな面の上に立っている絵になった。特徴抽出が乗り物をまったく見つけられなかったのは飛行機だけで（168枚中25枚。他の5つはゼロ）、飛行機は20%が乗り物の評点で1か2を取った。自転車は5%、ボート・キックボード・スケートボードは0%。単語1つの選び方が結果の質を左右しています。

結論は控えめです。ペリカンが他の動物より上手く描かれているわけではなく、自転車が他の乗り物より上手いわけでもなく、どのラボもペリカンと自転車の実力から予測される以上にその組み合わせを上手く描いていない。もっともありそうな話はGoogleたちがやっているようなSVG全体の最適化で、他のラボが静かにやっている可能性もあるけれど、この実験では誰がやっているかは言えない。「少なくとも、Simon Willison を騙すためだけにテラバイト級の自転車ペリカンを作っているわけではないと分かって眠れる」という締め方でした。

UXエンジニアリングの視点では、これは評価の設計をどう組むかの実例として読めます。1マスの結果を疑うために、そのマスを含む48マスのグリッドを作り、難易度を吸収する項を入れて、ラボ内の相対差だけを見る。UIの比較検証で「この画面のスコアが高い」と言いたいときに、他の画面も同条件で測っておかないと難易度と実力を分けられない、という話と構造が同じです。それと単語1つの読み違いで20%の画像が壊れた例は、プロンプトを書く仕事がインターフェースを書く仕事に近いことの分かりやすい証拠でしょう。

### [Building an Endless Interactive Glass Xylophone with Three.js](https://tympanus.net/codrops/2026/08/04/building-an-endless-interactive-glass-xylophone-with-three-js/)

> **出典**: Codrops | **公開日**: 2026-08-04 | **カテゴリ**: design

**3行まとめ**
- 64本のバーを1つの位相値でヘリカルに並べ、スクロールしても構図が動かない無限スクロール
- 流体シミュレーションを色のマスクとして使い、バーが持つ固有色を波が通った分だけ見せる
- `MeshPhysicalMaterial` が使えないインスタンス描画で、すりガラスを複数パスで組み立てる

**詳細解説**

カーソルで演奏する木琴です。バーを横切ると音が鳴り、打たれたチャイムのように揺れ、波が通った部分に色が満ちる。列は終わらず、64本のバーがすりガラスの螺旋を永遠に巡ります。Three.js と Vite、パス管理は postprocessing。Three.js に慣れていてシェーダーを書いたことがある人向けだと明記されています。

形はxylophoneの鍵盤を思わせるカプセル状のモデルで、光を受ける奥行きを持たせるために角を丸めてある。`.glb` の1本を `InstancedBufferGeometry` で64回インスタンス化し、位置・回転・色のオフセットをインスタンス属性として渡します。螺旋に並べる処理は概ね想像どおりですが、明らかでないのが3つ目の回転です。

```js
const tiltX = Math.atan2(geometryHeight, cfg.radius * cfg.tiltFalloff)
```

この `tiltX` が、バーを水平に置かずに登りへ傾ける役です。螺旋階段の比喩がうまい。傾けなければ段板が積み重なった状態になり、傾ければ斜面に沿って走る手すりになる。角度自体は rise over run で、rise はバー1本の高さ（1本進むぶん上がる量）、run は同じ1歩で横へ進む距離で半径に比例する。広い螺旋は緩やかに登り、狭い螺旋は急に登る。Euler の順序を `YXZ` にしているのは、グローバルな回転を先に当ててからローカルX軸の傾きを足すためです。垂直方向の間隔はバウンディングボックスの高さそのままで、隙間なく積む。角度方向は64本で2回転弱になります。

スクロールの実装が気持ちいいところです。グループもカメラも動きません。スクロールはバーのインデックス単位で測った1つの位相値に積算され、イージングを通って `wrap()` に入る。位相がインデックスではなくレイアウトを駆動するので、各バーは螺旋を連続的に登り、頂点を越えた瞬間に下から現れる。高さも幅もフレーム内の位置も固定なので、10分スクロールしても構図は置いた場所から動きません。安く保つ工夫が2つ。イージングは lerp ではなく `MathUtils.damp` なので60Hzでも120Hzでも同じ速さで収束し、インスタンスバッファはイージング後の位相が実際に動いたときだけ書き換えます。

色の設計がこの作品の要でしょう。流体シミュレーションを使いたい、でも本物の木琴のように各バーが自分の色を持っていてほしい。最初はホバーでバー全体を光らせて、動くけれど退屈だった。落ち着いた形はこうです。各バーは列のなかの位置を0から1の数値ひとつで持ち、それがグラデーションテクスチャ上の永久の席になる。グラデーションは実行時にcanvasで作った赤→マゼンタ→紫→青→シアンのプリズムランプ。そして流体の速度場が、その色をどれだけ見せるかを決めます。

```glsl
float velocity = smoothstep(0.0, 0.2, length(texture2D(u_tFluid, vScreenUv).xy));
float reveal = clamp(velocity * u_fluidStrength, 0.0, 1.0);
vec3 tint = texture2D(u_tGradient, vec2(fract(vTintOffset * u_tintWrap), 0.5)).rgb;
```

各フラグメントが自分のスクリーン上の位置で流体の速度を読むので、露出は渦が漂って減衰する形をそのまま追う。静止時のバーはほぼ白で、横切ると波が各バー固有の色を開き、カーソルの色ではない。`u_tintWrap` でランプを64本にわたって10回巡回させていて、似たものを作るならこの数値をいじるといいと書かれています。

流体そのものは Stable Fluids ソルバーをかなり簡略化したもので、128×128で動き、本来なら数十回やる圧力反復を1回だけにし、渦度もほとんどない。手を抜かなかったのは点ではなく線分に沿って splat する部分で、前フレームの位置から現在の位置までの線に沿って撒くことで滑らかな筆致になります。どのバーをホバーしているかの判定は意図的に素朴で、64本を全部ループしてバウンディングボックスにレイキャストする。工夫はボックスを変換するのではなくレイを各バーのローカル空間へ押し込むことで、こちらのほうが安い。一時オブジェクトはすべて事前に1回だけ確保するので、1フレームの判定でアロケーションはゼロです。

揺れの実装も同じ思想です。素直に作るならバーごとにトゥイーンを持ってCPUで毎フレーム進めますが、シェーダーでアニメーションさせています。

```glsl
float dt  = u_time - aStrikeTime;
float env = step(0.0, dt) * exp(-dt * SWING_DECAY);
float ang = env * SWING_AMP * sin(dt * SWING_FREQ) * u_swingScale;
```

減衰振り子の式を、フレームごとに刻む代わりに1行で書き下したもの。打たれてからの時間を渡すと角度が返り、最初は大きく1秒ほどで消えていく。CPUがやるのは各バーがいつ打たれたかを記録することだけなので、64本が独立に揺れていてもCPUは知りません。`aStrikeTime` の初期値をはるか過去にして減衰を0に潰す、`qmul` の順序を間違えるとバーが螺旋の中心を公転してしまう、という細部も添えられています。音は1つのサンプルをペンタトニックにピッチシフトしたもので、C5から3オクターブの15音を64本に配ると隣り合う4本ほどが同じ音を共有する。これは意図的で、64音を全部散らすと端がサンプルの元の速度から離れすぎて漫画みたいな音になるから。音が鳴るのはカーソルがバーに入った瞬間で、留まっているあいだではない。本物の木琴に近い挙動です。

素材の節が技術的にいちばん密です。`MeshPhysicalMaterial` に transmission を付ける方法は、意図的に避けたのではなく本当に使えなかった。64本が1回のインスタンス描画なので、Three.js はインスタンス同士を深度ソートできず、バーは完全に不透明のままになる。そこでパスを並べます。背景だけを自分のターゲットへ描き、それをぼかして2つ目のターゲットへ、シーンを描くときにバーがそのぼけた背景を読み、法線バッファを描き、SSAO、アンチエイリアス。背景の分離はシーンを2つ作るのではなくレイヤーマスクでやっていて、`GaussianBlurPass` は画面解像度の4分の1で数回まわすので、大きなカーネルの代金を払わずに広くミルキーな霜が得られます。

そこまで用意すれば、透過はテクスチャの読み取り1回です。

```glsl
vec2 buv = vScreenUv + N.xy * u_refractStrength; // screen-space refraction
vec3 trans = texture2D(u_tBackdrop, buv).rgb;
trans = mix(trans, tint, reveal);
vec3 frosted = mix(body, trans, u_transmission * (1.0 - 0.6 * reveal));
```

読み取り位置を法線でずらすことが縁で背景を曲げ、厚みを感じさせる。`(1.0 - 0.6 * reveal)` は著者が気に入っている小技で、波が色を出しているところではミルキーな背景を通す量を減らし、色が霜で洗われずに鮮やかに残ります。Fresnel はかすめる角度で空色へ寄せて縁に輪郭を与える役で、環境マップは持たずフラグメントシェーダーで作った地面・地平線・空の3段ランプで済ませている。かすめる角度でしか読まないところでは本物のHDRと見分けがつかないので、1メガバイト払う価値がない、という判断です。それでも鈍く見えたので薄膜干渉の代わりにコサインパレットの虹色を足し、法線に応じて位相が変わる項を入れて偽の厚みのばらつきを作った。接地影は床がないので、バー同士の遮蔽をSSAOで影の代わりにしています。

ここに1つ非自明な処理が入ります。SSAOは法線バッファを欲しがるけれど、Threeの組み込み法線パスはバーごとの回転や打撃の揺れを知らない汎用マテリアルで描く。そこで表示用マテリアルと同じ頂点シェーダーで法線を描き、uniform オブジェクトを値のコピーではなく参照で共有しています。参照を共有していればずれようがないので、法線バッファが見えているものと物理的に食い違えない。最後にSMAAで縁を整えます。

パスが多いのに性能を出すために、パスを削るのではなく1つずつ安くしたと書かれています。流体の解法は入力が数秒ないと丸ごとスキップされ、スクロールのコンベアは位相が実際に動いたときだけバッファを書き換えるので、落ち着いていれば書き換えもアップロードもゼロ。デバイスピクセル比はどこでも上限を掛け、粗いポインタで小さいビューポートならさらに下げ、フル解像度の2つのバッファ（法線と遮蔽）を半分に落とす。この3つがスマートフォンのGPUが60fpsで持てない部分で、他はもともと十分安かった。リサイズはwindowではなくサイザー要素から測り、同じサイズでレンダーターゲットが無駄に作り替えられないようガードしています。

アクセシビリティの節が、この記事でいちばん引用したい部分です。

```js
this.uniforms.u_swingScale.value = reduceMotion ? 0 : 1
```

揺れの角度に0を掛ければ動きは消える。他は何も変わらない。バーは光り、音は鳴り、色は現れる。「インタラクション全体をブール値ひとつで塞ぐのは誘惑だけれど、それは穏やかな楽器を渡すのではなく、楽器を取り上げることになる。動きを減らす設定は、めまいの問題を取り除くのであって、機能を取り除くのではない」。いっぽうで、キーボードで演奏する経路はないと正直に書いています。打鍵はポインタのレイキャストを必要とするので、キーボードのユーザーはページと音のトグルは使えても音を鳴らせない。自分なら矢印キーでフォーカスのインデックスをバー間で歩かせ、同じ打撃の経路を呼ぶ、という直し方まで示しています。

まとめの一文が効いています。「認めたくなかった学びは、何かを簡単そうに見せるためにどれだけの労力がかかるかということだ」。

UXエンジニアリングの視点では、reduced motion の扱いが持ち帰る価値のいちばん高い部分でしょう。`prefers-reduced-motion` に反応してアニメーション全体を止める実装はよく見ますが、それが体験の中身まで落としていないかは別の問いです。ここでは揺れという前庭系に効く要素だけを0にして、光・音・色という他の手応えを残しています。同じ考え方は、ページ遷移のアニメーションを消すときに遷移そのものが分からなくなっていないか、という点検にも使えます。もう1つ、CPUに状態を持たせず時刻ひとつからシェーダーで復元する設計は、フレームレートに依存しない再現性という意味でも読み直せます。

### [Ecommerce Quantitative UX: 3 High-Level Trends & Takeaways from 20+ Charts](https://feeds.baymard.com/link/9825/17403157/ecommerce-quantitative-ux-insights-2026)

**詳細解説**

Baymard の定量インサイトが更新されました。大規模なUXリサーチの知見を補い深めるための、調査ベースのデータ可視化という位置づけです。対象は商品発見、クロスセルの好み、セール探索の行動、チェックアウトの摩擦、返品行動、アカウント機能への期待、ニュースレター管理まで。基礎データの大部分は年ごとに安定しているけれど、経年で追うといくつかの微妙な変化が見える、という前置きから3つの発見を紹介しています。

1つ目は返品の頻度です。過去1年に1度でもオンライン返品をしたのは52%（1回だけが24%、複数回が28%）。ここで経年の動きが出ます。複数回返品する層は2024年の44%から2025年に34%、今年28%まで下がり続けている。いっぽうで1度も返品しなかった層は26%から44%へ上がりました。この解釈が2通り併記されているのが誠実です。小売側の最適化ツールと買い物客の賢くなった習慣が誤った購入を減らしているのかもしれないし、返品期限の厳しさや手数料への苛立ちを避けて、間違った品をそのまま持っているだけかもしれない。どちらであれ、返品ポリシーがチェックアウトに到達する前に見えていて理解しやすいことが重要だと結んでいます。

2つ目はニュースレターの解除理由の入れ替わりです。48%が「特定の小売業者からのメールが多すぎる」を挙げて首位になり、46%の「フォローしているブランド全体でメールが多すぎる」を上回った。3位は44%の「内容に興味を失った」。上位2つが逆転したことは、個々のブランドの高頻度な配信に対する許容度が下がり、全体の量よりも1社ごとの配信頻度の管理が優先度の高い課題になったことを示しています。打ち手として挙がるのは、全部止めるか受け取るかの二択から離れて、専用のプリファレンスセンターで細かい頻度調整をユーザーに渡すこと。

3つ目はアカウント機能の優先度です。注文状況と配送追跡が51%で変わらず首位。チェックアウトの外で保存済みクレジットカードを管理したいが30%、過去の注文履歴の確認が26%。前年からのいちばんの変化は、ロイヤリティプログラムを重要な機能と答えた人が24%で全体4位に上がったことでした。購入後のダッシュボードが、ブランドのインセンティブと報酬の状況を管理する中心的な入口として、副次的な役割を強めていると読んでいます。整備するなら、ポイント残高、獲得履歴、利用できる報酬を、二次的なサブメニューに埋めずアカウントのダッシュボード本体に組み込むこと。

読むうえで押さえておきたいのは、これが自己申告のアンケートだということです。Baymard の看板である観察ベースのユーザビリティ調査とは性質が違い、記事自身も行動リサーチの知見と組み合わせて使う前提で書いています。返品頻度の低下も、実際の返品率のデータではなく「返品したと答えた人の割合」の変化なので、そのまま在庫や物流の計画に持っていく数字ではありません。

UXエンジニアリングの視点では、3つのうち2つが実装の話に直結します。プリファレンスセンターの粒度をどう切るかは、購読テーブルの設計とメール送信側のセグメント定義の問題です。「全部止める」しか作られていないのは、たいていUIの怠慢ではなくデータモデルが持っていないからでしょう。ロイヤリティの残高をダッシュボード本体に出すのも、別システムのAPIをアカウント画面の初期表示に載せられるかという性能の話になります。どちらも「二次的なサブメニューに置く」判断が、実装のしやすさから生まれやすい場所です。

### [Vercel supports Next.js 16.3](https://vercel.com/blog/vercel-supports-next-js-16-3)

> **出典**: Vercel | **公開日**: 2026-08-04 | **カテゴリ**: frontend

**3行まとめ**
- 16.2から16.3へ上げたアプリで prefetch リクエストが平均45%減、70%超減った例もある
- immutable な静的アセットで CDN リクエストが17%減、転送バイト数が24%減った
- ルートメタデータを JSONL のシャードにまとめ、p99 のルート解決が約2倍速くなった

**詳細解説**

Next.js 16.3 のリリースに合わせて、Vercel 側でも支える仕組みを変えたという報告です。挙がっている数字は3つ。prefetch リクエストが平均45%減（70%超の削減も）、静的コンテンツのCDNリクエストが17%減で転送バイト数が24%減、頻繁にデプロイするプロジェクトでは世界規模のTTFBが最大60%減、大規模サイトのp99ルート解決が約2倍速く。

immutable な静的アセットの話が分かりやすいところです。16.3では既定で有効になり、`/_next/static/immutable/*` の下にコンテンツアドレス指定の静的アセットを出力します。Vercel の CDN はこのプレフィックスで通常の静的アセットと区別する。デプロイをまたいで再利用できるので、Skew Protection を有効にしていないプロジェクトでもバージョンのずれが起きず、再デプロイしてもブラウザのキャッシュが生き残る。Next.js はクエリパラメータ方式の Skew Protection を使っているため、この変更でCDNリクエストが17%、転送バイト数が24%減りました。変わらないアセットは再アップロードを飛ばせるので、デプロイ自体も平均で最大30%速い。他のツールチェーンで同じことをやりたいフレームワーク作者向けに Build Output API のドキュメントも案内されています。

ルーティングの節は、性能改善の背景説明として読み応えがあります。Next.js 16 は、アプリの共通部分を1回 prefetch して遷移をまたいで再利用する最適化を入れました。再利用を成立させるには共有セグメントが単体で取得できる必要があり、結果として同じアプリに対して生成されるパスがずっと増える。そのパスがプラットフォーム側で積み上がります。フレームワークは Build Output API を通してVercelへデプロイし、パスごとに提供方法を記述したメタデータファイルを生成する。CDNはリクエストごとにそのメタデータを読むので、参照はミリ秒未満で終える必要があり、そのためにキャッシュしている。全世界で毎秒500万回の参照です。Next.js 16 のアプリがより多くのパスを出すようになるとキャッシュのエントリ数が増え、ヒット率が落ち、大きめのアプリでp99のTTFBが上がった。

直し方は、セグメントごとのメタデータを個別のキャッシュエントリにするのをやめ、JSONL 形式のシャードにまとめることでした。エントリを少なく大きくすればヒット率が上がり、JSONL ならシャードのなかから該当エントリを速く見つけられる。プロセス内キャッシュとリモートキャッシュも合わせて最適化して、約2倍速く、キャッシュミスが約10分の1に。これはプラットフォーム側の実装なので全デプロイですでに有効で、Build Output API 経由でデプロイする他のフレームワークも自動で恩恵を受けます。

可観測性の追加も並びます。リクエストが prefetch だったかどうかを Vercel Observability と Runtime Logs で問い合わせられるようになった。ISR の再検証については、時間ベースとオンデマンドの再検証がページ上で目立つ形になり、キャッシュ理由と書き込み使用率も見えるようになって、再検証を減らすガイドも公開されています。そして Partial Prerendering の可観測性が新しく追加されました。PPRはページの静的な部分を即座に返してから動的な内容をストリームする仕組みで、内部ではISRとVercel Functions を1つのシステムに組み合わせています。Cache Components を使う Next.js 16 のアプリは、Vercel にデプロイすると自動でPPRになる。ダッシュボードのPPR Observability では、どのリクエストが静的・動的・その組み合わせを返しているかが見えるので、静的シェルが効いているかの確認や、完全に動的へ戻ってしまったルートの発見に使えます。

UXエンジニアリングの視点では、prefetch の削減と「完全に動的へ戻ったルートを見つける」がとくに近い話です。前者は体感速度そのもので、prefetch を減らして遷移が速くなるという組み合わせは直感に反しますが、共有セグメントを1回取って使い回すという設計変更なので筋が通っています。後者は、キャッシュ境界の設計が実装のなかで壊れることを前提にした道具です。`cookies()` を1つ足しただけでページ全体が動的に落ちる、という事故は見つけにくい。それを画面で確認できるのは、パフォーマンス予算をチームで守るときの支えになります。

### [The computer that helped win World War II](https://spectrum.ieee.org/colossus-computer-ieee-milestone)

> **出典**: Sidebar | **公開日**: 2026-08-04 | **カテゴリ**: design

**3行まとめ**
- ローレンツ暗号機「Tunny」を破るため、Tommy Flowers が約2,000本の真空管で Colossus を作った
- 真空管は点けたままにすればリレーより信頼できる、という発見が大規模化を可能にした
- IEEE Milestone に認定され、9月29日に Bletchley Park で記念式典が開かれる

**詳細解説**

1941年の夏、ドイツ軍の周波数を監視していた英国の無線通信士が、ヘッドフォンから予期しない音を聞きます。後の報告書は「奇妙な新しい音楽」と呼びました。エニグマで暗号化された通信のモールス信号とは違う、高速で送られる2進テレタイプ符号のリズミカルな震え。ドイツの技術者が、1920年に特許を取ったエニグマよりずっと進んだ暗号化と伝送の仕組みを作っていたのです。

英国の暗号解読者たちはすぐに飛びつきました。暗号化されたテレタイプ符号だと特定するのは易しかった。難しいのは、その暗号機がどう動くかを解き明かすことでした。製造元がベルリンの C. Lorenz だと分かったのは戦争が終わってから。1941年の時点ではただの黒箱で、「Tunny」というコードネームを付けます。エニグマの解読者たちが Dolphin、Lumpsucker、Porpoise のように魚の名前を使う前例を作っていたからです。

エニグマは3枚か4枚の暗号ホイールを持っていたので、Tunny も回転するホイールの仕組みだろうと推測しました。手がかりは、傍受した全メッセージが共通して持っていた奇妙な特徴です。どれも Anton、Bertha、Conrad、Dora といった12個のよくあるドイツ人名の平文リストで始まっていた。ホイールが12枚あり、12の名前とその順序が、受信側の通信士に復号前にどう回すかを伝えているのだろう、と。

そこで並外れた幸運が訪れます。研究部門長の John Tiltman が、それぞれ1,200文字ほどの傍受メッセージ2通を分析していました。異例なことに両方が同じ名前の並びで始まっていて、2通目は1通目の打ち直しだと判明したのです。句読点が少し違い、いくつか略語があり、細かい相違がある。Tiltman は根拠のある推測と直観の混合で2つの暗号文を解読し、得られた1,200組ほどの暗号文と平文の対応が、Tunny の動作を推定するのに十分な情報になりました。それを成し遂げたのは Bill Tutte という物静かな若い解読者で、何週間も対応を睨んだあと、ある日おずおずと上司にTunnyの仕組みを説明しました。その記述は不気味なほど正確でした。

ただ、仕組みを知るだけでは復号できません。送信側のホイールがどう設定されていたかの詳細も必要でした。各ホイールの円周にはピンが並び、2つの位置のうち一方なら1、他方なら0を暗号化に寄与する。ピンは時々リセットされる。ホイールの開始位置は、ドイツの通信士が12の名前で漏らしていました。エニグマでの成功を経た Turing が「Turingery」という厄介な手法を発明し、傍受した暗号文だけからピンの位置を推定できるようにします。その基礎になったのが「delta-ing」（差分化）と呼ぶ手続きで、横方向の加算を使います。ABCDという4文字をdeltaするには、ビットレベルでAとB、BとC、CとDを足す。Turing はこれでホイールの情報を引き出しました。

Tunny のメッセージはヒトラー自身の署名入りのものも多く、連合国にとって純金でした。ベルリンの国防軍最高司令部が東西の戦線を指揮する将軍と通信するために使っていたのですから。破られたあと、連合国はドイツの作戦を立てる者たちの長いやり取りを盗み聞きできるようになりました。Turingery は1年間、唯一の武器として150万文字の暗号文を解読します。

しかし冒頭の名前のリストが消え、同時に Turingery の有効性も落ちていきました。この手法は、送信者が異なる2つのメッセージに同じホイール設定を使うという誤りに依存していて、Tunny 網全体でセキュリティが締められるにつれてその失敗は稀になっていったのです。幸い Tutte が別の復号法を考えていました。Turing の delta-ing に基づきながら、名前のリストもドイツ側の失敗も要らない、Tunny 機自身の統計的性質を使う方法です。

ただ、適用のしかたがすぐには見えませんでした。解読者は手作業で、Turingery をメッセージに当てるのは巨大な数独やクロスワードを解くようなもの。Tutte の統計的手法は大量の単調な2進演算と、長い2進列の膨大な数え上げを必要とします。手でやれば1通に数か月。自動化する機械が要りました。

最初の計画は電磁リレーで組み、数え上げを速くするために真空管を数十本足すというものでしたが、回路設計の問題がリレーベースの論理部を悩ませます。Turing の推薦で Flowers がトラブルシューティングに呼ばれました。彼はロンドンの郵政省研究所からの出向で、戦前の数年を数千本の真空管を使う実験的な交換機の設計に費やしていました。当時は、真空管はそれぞれ熱いフィラメントを持つので大量には使えないと広く信じられていました。突然死しやすく、大規模な設備では1本が飛んで正しく動かなくなるまで長くはかからない、と。

Flowers が発見したのは、真空管をオンオフすることがストレスになる一方で、点けたままにしておけばリレーよりも信頼できるということでした。彼は約2,000本の真空管を含む高速の全電子式マシンを作ると申し出ます。Bletchley Park の助言者たちは、そんな機械が信頼して動くはずはないと確信して却下しました。Flowers は自分の設計に自信を持っていたので、ロンドンの研究室に戻り、解読者が必要だと信じた電子式マシンを静かに作りました。小さな技術者チームと10か月、昼夜働いて Colossus を作り上げた。

1944年1月、技術者の何人かがトラックの荷台に世界初の大規模プログラム可能な電子式デジタルコンピューターを積んで Bletchley Park に現れます。2週間ほどで再組立てされて動き、1944年2月5日に最初のドイツ語メッセージを記録しました。入力の Tunny 暗号文は大きな穿孔紙テープのループから光電的に読み、出力のホイール情報は、手動タイプライターにリレーを付けてキーを自動化した原始的なプリンターへ出す。「実際に機械を手にするまで、私が何を提案しているのかはっきり理解していなかったと思う。彼らは信じられなかったんだ」と Flowers は1977年のインタビューで語っています。

その後2台目が1944年6月、Dデイの数日前に完成します。2,400本の真空管で、Colossus I より800本ほど多く、毎秒25,000文字で Tunny を処理した。そのタイミングパルスの最大レートは、30年以上あとの最初のIntelマイクロプロセッサの性能から遠くなかったそうです。Flowers 自身は「Colossus が現代のコンピューターに似ている程度は、1829年のロケット号が Royal Scot に似ている程度だ」と認めながら、それでも「現代のコンピューターの基本的な特徴をすべて備えていた」と強調しました。クロックパルス、ビットストリーム生成、制御回路、ループ、カウンタ、シフトレジスタ、割り込み、並列処理。

終戦時には10台の Colossi が防爆構造の巨大な建物2棟で昼夜稼働していました。厚い秘密の帳に隠されていたけれど、Bletchley Park は世界初の電子計算施設だった。戦闘が終わると、極秘は維持されなくてはならないと決まり、Colossi を解体する命令が出ます。残されたのは2台だけ。「機械が立っていた床の深い穴だけが残った」と操作員の Dorothy Du Boisson は回想しています。Flowers の技術者の1人 Norman Thurlow は、もし秘密が解かれたら孫に Colossus と「銀の車輪で回ったテープ」の話をできるかもしれない、というスタッフ向けメモを覚えていた。1945年に書かれ、のちに機密解除された報告書の一節が引用されていて、稼働中の Colossus の魅力を語る文章としてかなり詩的です。輝く滑車を回る薄い紙テープの幻想的な速さ、待ちわびたスコアが突然現れる期待の高まり、走行の種類ごとに違う奇妙なリズム。

UXエンジニアリングの視点で残るのは、Flowers の発見の性質です。真空管が使えないという当時の常識は、部品の仕様の話として語られていました。彼が見つけたのは、部品をどう運用するかで信頼性が変わるという、条件側の事実でした。同じ部品でも、点けたままにするか切り替えるかで結論が反転する。設計の成否が「何で作るか」ではなく「どう動かすか」で決まる場面は、いまも珍しくありません。もう1つは、助言者に却下されたあと議論を続けずに10か月で動くものを作った、という経緯です。今日の「動くデモはPRDに勝つ」という言い方の、かなり極端な先例として読めます。

### [ShaderPad](https://misery.co/shaderpad/)

> **出典**: Sidebar | **公開日**: 2026-08-04 | **カテゴリ**: design

**3行まとめ**
- WebGL2 の足場作りを引き受ける、gzip で5.9kBのフラグメントシェーダーライブラリ
- uniform とテクスチャの同期、リサイズ、履歴バッファといった定型処理を任せられる

**詳細解説**

ブラウザでフラグメントシェーダーを描くために毎回必要になる反復作業を引き受けるライブラリです。WebGL2 の足場、uniform とテクスチャの同期、リサイズ、履歴バッファ、その他のランタイムの配管。既定で性能が出る状態にして、グラフィックスプログラミングの創造的な部分に集中させる、という位置づけです。gzip で5.9kBという小ささが売りで、効果が速く読み込まれてどのデバイスでもよく動く。

できることとして挙がっているのが4つ。10行未満のJSでフルスクリーンのインタラクティブなシェーダーを作る、既存の `canvas`・`img`・`video` 要素にポストプロセスの効果を足す、最小のオーバーヘッドでマルチパスのパイプラインを組む、顔フィルターや姿勢検出のアプリを作る。ドキュメントには「AIエントリポイント」の節もあって、最初のシェーダーを vibe coding で書くこともできると案内されています。

他のライブラリとの比較が率直で助かります。Three.js はすばらしいフレームワークだけれど ShaderPad の30倍近いサイズなので、完全な3Dライブラリなしに GPU を使いたいなら ShaderPad が良い選択になる。ShaderToy のようなホスト型のプレイグラウンドはスケッチには最適だけれど、作ったものがそのプラットフォームに閉じ込められる。ShaderPad は同じくらいの反復速度を持ちながら、どのプロジェクトにも落とし込めるものを渡すことを狙っている。ShaderToy、Three.js、TWGL、ShaderBooth をインスピレーション元として名前を挙げているのも好感が持てます。WebGL2 が必要です。

UXエンジニアリングの視点では、選択の基準がサイズであるところが実務的です。プロダクトの一部にシェーダーの効果を1つ入れたいだけのとき、Three.js を積むのはバンドルの予算に響きます。今回同時に読んだ Codrops の木琴の記事は、64本のインスタンス描画とマルチパスの後処理という要件があったので Three.js と postprocessing が必要でした。逆に、フルスクリーンの背景アニメーションや動画へのポストエフェクトなら、こちら側で足ります。この2本を並べて読むと、境界線がどこにあるかが見えてきます。既存の `img` や `video` に後付けできる点も、すでに組まれた画面へ手を入れるときの現実的な入口でしょう。

### [Give your eve agent a browser](https://vercel.com/changelog/give-your-eve-agent-a-browser)

> **出典**: Vercel | **公開日**: 2026-08-04 | **カテゴリ**: frontend

**3行まとめ**
- eve エージェントに agent-browser を載せ、ページ移動・クリック・フォーム入力・スクショを渡せる
- Chromium は eve の sandbox 内で動き、`allowedDomains` でナビゲーション先を制限できる
- Cookie・ストレージ・保存済み認証状態を扱うコマンドはモデルに公開されない

**詳細解説**

`@agent-browser/eve` を入れて `agent/extensions/` の下にマウントすると、eve エージェントがブラウザの道具立てを一式持てるようになります。ページ移動、内容の読み取り、クリック、フォーム入力、スクリーンショット、コンソールとネットワークの検査。すべてエージェントの sandbox のなかで動きます。

道具は名前空間付きで渡されます。`browser__navigate`、`browser__snapshot`、`browser__click`、`browser__fill`、`browser__screenshot`。設計としておもしろいのは、snapshot が返す `[ref=e12]` のような参照が `@e12` というセレクタになる点です。エージェントはページを調べたあと、まさに自分が見たものに対して操作できる。座標やCSSセレクタを推測する経路を挟まないので、見たものと触るものがずれません。

安全側の作りが3つ挙がっています。1つはサンドボックスの分離で、Chromium と agent-browser はアプリではなく eve の sandbox で動く。sandbox テンプレートに事前インストールしておけばセッションが温かい状態で始まり、そうしなければ初回利用時に拡張が入れる。2つ目はドメインの許可リストで、`allowedDomains` でナビゲーションとサブリソースを制限し、出力サイズ、スクリーンショットの扱い、プロキシの使用、セッション名も拡張のオプションで制御できる。例では `maxOutputChars: 50000` が指定されています。3つ目が資格情報の保護で、Cookie・ストレージ・保存済み認証状態のコマンドはモデルに公開されません。eve の拡張オーバーライドで道具を無効にしたり、承認を必須にしたり、アプリ固有のガード付き道具を足すこともできる。

UXエンジニアリングの視点では、この3つの境界の引き方がそのまま参考になります。とくに「Cookieと認証状態のコマンドをモデルに見せない」は、エージェントに権限を渡すときの基本形として使い回せる考え方でしょう。プロンプトで「触らないで」と伝えるのではなく、道具の一覧から外す。それと `[ref=e12]` → `@e12` の往復は、アクセシビリティツリーのスナップショットが自動化の共通言語になりつつあることの現れです。セマンティックなマークアップを整えることが、スクリーンリーダーだけでなくエージェントの操作精度にも効く、という筋が通ってきています。
