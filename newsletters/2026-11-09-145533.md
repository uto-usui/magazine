### [LDRライクなRSSリーダのIrodrをReact 19 + Vite+で書き直して、iPhone Duoにも対応した](https://efcl.info/2026/11/07/irodr-2/)

> **出典**: Web Scratch | **公開日**: 2026-11-07 | **カテゴリ**: frontend

**3行まとめ**
- 9年使い続けてきた LDR 風の RSS リーダー Irodr を、見た目とキー操作はそのままに、React 19 と Vite+ で書き直した azu さんの記録です
- JS は gzip 後で 397kB から 150kB に、本番ビルドは27秒から0.5秒に縮み、ブラウザで動く依存は48個から4個になりました
- 書き直しは Claude Code に任せ、書き方のルールを Lint で強制し、外部 API を再現した Fake Server に対してテストしながら進めています

**詳細解説**

2.0 では、Inoreader のフィードと GitHub Notifications を同じ画面・同じキー操作で読めるようにしています。Inoreader の Pro プランで購読数が上限の2,500に近づいたので、購読の大半を占めていたリポジトリのリリース通知を GitHub に移しました。どちらも同じ `Source` インターフェースで扱うので、UI の側ではどのソースのフィードかを区別しなくて済みます。

AI に書かせたコードの書き方は、レビューで指摘するのをやめて Lint で守っています。`let` やクラスを禁止するルールを Oxlint の JavaScript プラグインとして自作し、Oxlint に入っている React Compiler 向けのルール（`react/purity`、`react/refs` など）も有効にしました。React Compiler は扱えないコンポーネントを警告なしにスキップするので、そうしたコードがあれば `vp check` が失敗するようにしています。クラスから関数への書き換えでは、新旧の Reader に同じ操作を流し、記録した30のシナリオと約8,800回のランダムな操作で、差分が出ないことを確かめています。

操作感の数字は、Fake Server に40フィード×20記事を入れた同じ条件で、CI 上で新旧を比べたものです。`s` を押して次のフィードの記事が出るまでの時間は 66ms から 23ms に、CPU を4倍遅くした条件では 215ms から 111ms になりました。一方で、`s` で移動したフィードが見出しの下に隠れる、blockquote の見た目が 1.x と違う、といった問題は自動テストでは見つかりませんでした。これらは実際に使うなかで見つけ、スクリーンショットや画面収録を添えて AI に直してもらっています。

iPhone Duo への対応では、Viewport Segments API の CSS メディア特性 `horizontal-viewport-segments` と `vertical-viewport-segments` だけを使い、左右に開いたときと上下に開いたときでレイアウトを変えています。Safari 27.1 では、この API は機能フラグを有効にしたときだけ使える開発者プレビューです。また、`env(viewport-segment-height 0 1)` は実際の画面よりかなり大きな値を返していました。そのため、下に置くボタンの高さはビューポートの高さの4分の1で決めています。

### [What does design system AI readiness mean, anyway?](https://seanvoisen.com/writing/design-system-ai-readiness/)

> **出典**: Sidebar | **公開日**: 2026-11-09 | **カテゴリ**: design

**3行まとめ**
- デザインシステムの AI 対応として、ドキュメントを機械で読める形にする、MCP サーバーを用意する、といった対策は広がっていますが、何ができれば「対応できた」といえるのかは決まっていない、と問いを立てています
- 人の代わりに AI がデザインシステムを使うと「もっともらしいずれ」が大量に生まれ、ルールをすべて守った設定画面でも、デザイナーが見るとどこかずれています
- 品質の下限を保ったまま、上限のどの部分を人が支え続けるかをチームが意図して決めている状態を、AI に対応できた状態と定義しています

**詳細解説**

前提として、デザインシステムはもともと品質の下限しか保証しておらず、上限は使う人の判断が支えてきた、と整理しています。AI 向けの対策は2つに分けられます。AI に渡す文脈とルールで生成の幅を絞る方法と、評価や批評のループで出力を確かめる方法です。多くのチームは下限を守るほうに力を入れていて、上限のどこを手放せるかはあまり問われていない、という見方です。

AI に部品を使わせる検証のやり方として、PJ Onori さんの実験も紹介しています。決まったプロンプトでは結果がよすぎたので、予測できない実際の使われ方に近づけるために、ランダムなプロンプトを混ぜています。

書き出せない暗黙の知識については、David Hoang さんの「デザインの台帳」の考えを借りて、作業のなかで記録を残すことを提案しています。レイアウトの決定、意図してシステムから外した場面、アクセシビリティと情報密度がぶつかったときの選択を記録していけば、生成を絞る材料にも、出力を評価する材料にもなるとしています。まだ試していないと断ったうえで、監視の道具に使われうること、過去の決定をなぞりやすいことも欠点として挙げています。

### [Agent Harness: Definition](https://www.nngroup.com/articles/agent-harness/)

> **出典**: Nielsen Norman Group | **公開日**: 2026-11-06 | **カテゴリ**: design

**3行まとめ**
- 同じ AI モデルを使っていても、できることはモデルを囲むソフトウェア「ハーネス」で決まる、という考え方を NN/g が UX の側から整理しています
- ハーネスは、モデルが求めたツールの呼び出しを権限に照らして実行するループを回し、モデルに渡す文脈と、時間・費用・手順数の上限も管理します
- UX の担当者には、画面と一緒に振る舞いを仕様に書くこと、AI の評価では文脈やツール、権限まで本番に近い形でタスク全体を試すことを勧めています

**詳細解説**

「金曜は会議を入れない」と設定を保存していても、ハーネスがそれをモデルに渡さなければ、日程調整アシスタントは金曜を提案し、利用者は同じ希望を言い直すことになります。PDF を渡したときに、テキストだけを抜き出すか、ページを画像にもするかで、レイアウトで示された関係をモデルが読み取れるかどうかも変わります。

全員の都合が合う時間がなかったとき、探し続けるのか、任意参加の人がいないかを聞くのか、ほかの週を提案するのかは、ハーネスの指示と上限で決まります。モデルは指示にいつも従うとは限らないので、ハーネス側で応答を検査して出し直させる方法もあります。権限については、ハーネスとアプリを分けて説明しています。ハーネスで承認しても、接続先のアプリ側の制限はそのまま効きます。

評価のテストには、カレンダーの接続が切れた、設定が変わった、誰の都合も合わない、といった場面を入れるよう勧めています。タスクを取り消せるなら、何が止まり、送信済みの招待のような済んだ操作がどうなるかも決めておくよう求めています。読み込み中やエラーと同じく、画面の状態の一覧に載せる項目になりそうです。

### [true or false in CSS](https://blog.master.dev/true-or-false-in-css/)

> **出典**: Frontend Masters Blog | **公開日**: 2026-11-06 | **カテゴリ**: css

**3行まとめ**
- `@property` で `syntax: "true | false"` を指定すると、`true` か `false` の値しかとらないカスタムプロパティを作れます
- チェックボックスの状態を `:root` の `:has()` でそのプロパティに移し、`@container style()` で読み取れば、商品の絞り込みを CSS だけで切り替えられます
- 状態の組み合わせを `style(--isBackpack: true) and style(--isDuffel: false)` のように書けるので、`:checked` と `:not(:checked)` を並べるより条件が読みやすくなります

**詳細解説**

リュックとダッフルバッグの絞り込みの例では、`:root` にコンテナ名を付けています。継承しないプロパティを、深い階層の子孫の style query から参照するためです。プロパティを直接の親に置くか、継承するようにすれば、名前は要りません。登録したカスタムプロパティを勧める理由には、型の安全さ、パフォーマンス、継承を避けられることを挙げています。

Figma のコンポーネントプロパティにも真偽値があるので、デザイン側で `isSelected` のように付けた名前を、そのまま CSS のプロパティ名にも使えそうです。対応ブラウザの状況は、記事には書かれていません。

### [Branded Phone Type](https://glebbahmutov.com/blog/branded-phone-type/)

> **出典**: Gleb Bahmutov | **公開日**: 2026-11-06 | **カテゴリ**: testing

**3行まとめ**
- 電話番号をただの文字列ではなく TypeScript のブランド型で表し、テスト用の番号と本物の番号を型で区別する方法を、Cypress のテストコードで紹介しています
- `string & { __brand: 'phone' }` を土台に `TestPhoneNumber` と `RealPhoneNumber` に分け、共通の型は `.d.ts` に置いてテストのリポジトリ全体で使えるようにしています
- `asserts phone is TestPhoneNumber` の形のアサーション関数で、実行時に形式を確かめると同時に型も絞り込むので、API から受け取った値もその場で検証できます

**詳細解説**

Mercari のテストでは、`000` で始まる10桁を開発用の番号、それ以外の10桁を本物の番号として使い分けています。アサーション関数は、テスト用なら `^000\d{7}$` に合うか、本物なら10桁で `0` や `555` で始まらないかを確かめます。ブランド型の値も文字列なので、`cy.get('#phone').type(phone)` のようにそのまま入力欄へ渡せます。

本物の番号を渡したテストは、テスト用の番号しか受け取らないヘルパーの型チェックで止まります。どの番号を使っているかをレビューで一つずつ確かめる手間が減ります。

### [Otherwise you're just a machine](https://uxdesign.cc/otherwise-youre-just-a-machine-a9d3b21179b5)

> **出典**: Sidebar | **公開日**: 2026-11-09 | **カテゴリ**: design

**3行まとめ**
- 「見栄えのいいバイブコーディングのプロトタイプより、紙に描いたよい案を見たい」と考えた書き手が、AI の時代にデザイナーが鍛えるものを8つ挙げています
- 技能、審美眼、直感、創造性、全体を見る力、方法の選び方、行き詰まりを抜ける工夫、ビジネスの理解を、映画や料理、陸上の逸話と、デザイン組織を率いる書き手の経験で説明しています
- AI がこうした力を身につけるかどうかより、人が指示を待ち、最初の答えを受け入れる機械のようになることのほうが危うい、と締めくくっています

**詳細解説**

「方法」の節では、ポートフォリオの審査で、会社も解く問題も違うのに、ペルソナ、困りごと、カスタマージャーニーマップ、ワイヤーフレームと同じ順に並ぶケーススタディが多いことを挙げています。道具そのものに問題はないとしたうえで、なぜその道具を使ったのかが見えないことを問題にしています。各工程を AI で速くこなせても、そのジャーニーマップがそもそも必要だったかどうかはわかりません。プロトタイプをレビューに出すときは、何を確かめるために作ったのかを先に1行で書いておくのが手軽です。見る側も、出来ばえより何を確かめたいのかに目を向けやすくなります。

「全体を見る力」の節では、アイコンを頼まれたデザイナーが、作る前に「このアイコンはそもそも要るのか」と問えるかを例にしています。既存のものと重なっていないか、アイコンの体系のほうを見直す必要はないか、と一段引いて全体を見る話です。

### [Usability 101: Introduction to Usability](https://www.nngroup.com/articles/usability-101-introduction-to-usability/)

> **出典**: Nielsen Norman Group | **公開日**: 2026-11-06 | **カテゴリ**: design

**3行まとめ**
- Jakob Nielsen さんが2012年に書いた定番の入門記事を、NN/g が書き直しました
- ユーザビリティを学習しやすさ・効率・覚えやすさ・エラー・満足度の5つで定義し、使いやすさは「誰が、どのタスクで、どんな条件で使うか」によって変わる、と説明しています
- 代表的な利用者に実際に近いタスクをしてもらって観察することを改善の基本とし、問題を見つけるなら5人、数値で測るなら約40人を目安にしています

**詳細解説**

新しく加わった「ユーザビリティと AI」の節では、生成 AI は同じ依頼にも違う出力を返すので、同じ利用者が同じタスクをしても使いやすさが毎回変わりうることを挙げています。合成ユーザーやデジタルツインは、本物の利用者の代わりにならないとしています。使いやすさは人とエージェントでも別物で、人には低コントラストで読みにくい電話番号でも、エージェントは HTML から読み取れる、という例を出しています。

### [In conversation: Dylan Field and David Friedberg on the human role in creating with AI](https://www.figma.com/blog/in-conversation-dylan-field-and-david-friedberg/)

> **出典**: Figma Blog | **公開日**: 2026-11-06 | **カテゴリ**: design

**3行まとめ**
- Figma の Dylan Field さんと All-In Podcast の David Friedberg さんの対談から、AI でものを作るときの人の役割を話した部分を抜き出しています
- AI でものを作る敷居は下がったものの、上限を引き上げるのは AI ではなく人だと考えを改めた、と Dylan Field さんは話しています
- 誰でもコードを書けるようになったので、差はデザインでつくとしたうえで、AI に考えてもらうか、AI で自分の理解を広げるかを選ぶことになる、と語っています

**詳細解説**

Dylan Field さんの話では、自分の構想をそのまま AI に実装させると、AI の目を通したものになり、思いどおりにはならないそうです。まず AI で作ってみて気に入らない点を直していく往復を勧め、Figma でコードをキャンバス上の素材として扱えるようにしているのもそのためだと説明しています。具体的な作り方や事例は出てこず、Figma Weave などの製品の紹介も途中に入ります。
