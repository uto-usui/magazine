### [Agent Skills](https://addyosmani.com/blog/agent-skills/)

> **出典**: Addy Osmani | **公開日**: 2026-05-03 | **カテゴリ**: performance

**3行まとめ**
- AIコーディングエージェントが省略しがちな「diffに残らない仕事」（仕様策定、テスト、レビュー、スコープ管理）を、必ず通る workflow として強制する仕組み
- アンチ合理化テーブル、進行的開示、検証を出口条件にする、5つのデザイン原則で運用する
- Google の SDLC 慣行（Hyrum's Law、テストピラミッド、約100行PR、Chesterton's Fence）を skill ファイルに落とし込んだ実装

**詳細解説**

Addy Osmani が GitHub で 26K star を集めた agent-skills プロジェクトの設計思想を解説した記事です。シニアエンジニアの仕事の大半は、仮定のあぶり出し、仕様の作成、レビュー可能なサイズへの分割、退屈な設計の選択といった「diffに残らない作業」だが、AIエージェントはこれらをデフォルトで全部スキップする、という問題提起から始まります。

skill とは Markdown + frontmatter で書かれた「workflow」であり、reference documentation ではない、という区別が中心軸になります。「テストのベストプラクティス2,000語のエッセイ」を context に入れても、エージェントはそれっぽい文章を生成してテストを書かないが、「失敗するテストを先に書け、走らせて失敗を確認しろ、最小限の実装で通せ」と手順化すれば実行可能になる。Process over prose、Workflows over reference、Steps with exit criteria over essays without them、というスローガンに集約されます。

なかでもおもしろいのが anti-rationalization tables という発明です。「このタスクは仕様を要するほど複雑じゃない」「テストはあとで書く」「テストが通ったから出荷していい」といった、エージェント（や疲れた人間）が口にしがちな言い訳に対して、あらかじめ反論を書いて貼り付けておく仕組みです。LLM は合理化が得意なので、まだ言われていない嘘への反論を先回りで用意しておくのがミソです。Google の SDLC 慣行（テストピラミッド 80/15/5、DAMP over DRY、約100行PR、Hyrum's Law、Chesterton's Fence）を 1 個ずつ skill ファイルに落としているのも示唆的です。

UXエンジニアリングの観点で読むと、これは「コード生成における senior-engineer scaffolding を文書ではなく workflow として強制する」という設計パターンに尽きます。デザインシステムの運用、アクセシビリティチェック、レビュー基準なども、プロセスの形にしないと実行されないという認識は、エージェント時代の組織知のあり方に関わる議論です。

### [Claude Opus 4.7のReact習熟度をeffort=maxで測る、ついでにOpus 4.6の劣化説も検証](https://zenn.dev/uhyo/articles/react-profession-bench-5)

> **出典**: uhyo | **公開日**: 2026-05-04 | **カテゴリ**: frontend

**3行まとめ**
- Opus 4.7 を effort=max で実行すると、React 習熟度ベンチマークで全モデル中最高の 78.2 点を記録（default の 75.4 から +2.8）
- 噂の Opus 4.6 劣化説は、3月と4月で同条件再走した結果 +1.2 点と確率的揺れの範囲内で否定
- 4.6 はカテゴリ別に「TypeScript 品質+0.39 / 状態設計-0.31 / コンポーネント設計-0.23」と方向が振れているだけで、平均は安定

**詳細解説**

uhyo さんによる React 習熟度ベンチマークの第5回。13スペックを用意し、評価者を Sonnet 4.6 に固定して各モデルにフロントエンド実装を書かせ、客観的に採点する継続的な取り組みです。今回の論点はふたつ、Opus 4.7 を effort=max で走らせて性能向上が見られるかと、4.6 の劣化説の検証です。

まず性能。Opus 4.7 max は 78.2 点でベンチマーク首位、default の 75.4 点から +2.8 点の改善です。GPT-5.4 (71.5) との差は +6.7 まで広がり、Claude が明確にトップグループを形成しているのが見て取れます。スペック単位では「クイズビルダー」「フォームアクション」など、設計判断が必要な複雑系で max の効果が大きく、シンプルなタスクでは default と差が出にくいという妥当な傾向です。

劣化説の検証は記事のもうひとつの読みどころです。同一スペック・同一評価者で 3 月と 4 月の Opus 4.6 を再走させた結果、平均 +1.2 点で「劣化していない」が結論。ただしスペック単位では ±10 程度の確率的揺れが自然に発生しており、ユーザーが「劣化した」と感じるとき、それは特定のタスクで悪いサンプルを引いた可能性が高い、と冷静に分析しています。一方で 4.6 のアクセシビリティ低位（2.54）は不変で、4.7（3.54）との差として残っている、という観察も外せません。

UXエンジニアリングの観点で読むと、モデル更新ごとに「劣化」の主観が SNS で飛び交うなか、再現可能なベンチマークで定量的に検証する作法は学ぶところが多いです。とくに 4.7 のアクセシビリティスコアが 4.6 を一貫して上回るのは、a11y 配慮を AI 任せにしてよいかを考える材料として直接効きます。

- OpenAPI Links を使って campaign → ad set → ad の依存グラフを spec 内で機械可読にし、エージェントが多段 API 呼び出しの順序を spec から学習

**詳細解説**

Spotify Engineering による、広告 API への自然言語インタフェース実装の事例記事です。「Connecticut の 25-44 歳に $100/日で audio キャンペーンを打って」と話しかけると、geo-targeting ID 検索、ドル → micro-unit 変換、オーディエンスサイズ検証、campaign / ad set / ad の3段作成を順に実行してくれる、という仕様です。

おもしろいのが OpenAPI Links の活用です。campaign 作成の 201 response に「次は ad set を作れ、ID は $response.body#/id を使え」という遷移情報を spec 内で宣言しておくことで、エージェントは多段ワークフローを spec の中から学習できます。人間にとって暗黙の API 階層構造を、機械可読に書き出してエージェントへ手渡すという設計判断は、AI フレンドリーな API ドキュメンテーションの将来像として参考になります。

UXエンジニアリングの観点では、curl コマンドをユーザーに見せて確認を取るという「透明性のある実行」が示唆的です。広告予算という金銭的影響のある操作で、agent の判断を全部隠さず、コピー・修正・再実行できる形で提示する設計は、エージェント時代のあらゆるツールに応用できる UX パターンと言えるでしょう。

### [PGKeeper: Building the bouncer we needed for Postgres](https://www.figma.com/blog/pgkeeper-building-the-bouncer-we-needed-for-postgres/)

> **出典**: Figma Blog | **公開日**: 2026-05-04 | **カテゴリ**: design

**3行まとめ**
- Figma がスケール限界に達した PgBouncer を置き換える独自の Postgres コネクションプーラ PGKeeper（Go 製）を構築
- 優先度付きセマフォ、CoDel + 適応的 LIFO、weighted min-max fair share の多次元配分で過負荷時の admission control を実装
- 完全 rollout 後、コア体験 SLO が 99.99% 以上を維持、Q4 2025 だけで20件以上のユーザー影響インシデントを未然防止

**詳細解説**

Figma が PgBouncer を Go 製の自作コネクションプーラ PGKeeper で置き換えた事例。理由は、PgBouncer のシングルスレッド構造の縦スケール限界、優先度制御や backpressure の不在、connection churn 保護の弱さ、observability や feature flag を載せる拡張性の限界、というありがちな成熟期の課題群です。

技術的な見どころは admission control の二段構成です。V1 として、各リクエストにトラフィック priority タグを付け、優先度付きセマフォで「debt」機構と組み合わせて高優先度を優先する仕組みを実装。CoDel（待ち時間ベースの load shedding）と適応的 LIFO（過負荷時にキューを LIFO に切り替えて古いリクエストを早く落とす）の組み合わせは、Adrian Cockcroft 系の議論を読んだことのある人にはなじみ深い実装です。V2 で、認証状態 × ルートのような多次元の fair share を木構造で配分する weighted min-max を追加し、同優先度のなかで単一ワークロードがリソースを独占するのを防いでいます。

connection 管理側もしっかりしていて、pool warming、トークンバケットによる接続作成 / 廃棄レート制限、bounded exhaust、auto rollback、context cancellation の Postgres 側への翻訳まで丁寧に実装されています。Postgres 13.21 から 13.22 への upgrade で大量接続クローズが CPU を飽和させた経験から teardown 側もレート制限している、という運用知見の塊が読めます。

UXエンジニアリングの観点では、「過負荷時にどのリクエストを生かすか」という設計判断がそのままプロダクト体験に直結する、という事実が改めて浮き彫りになります。Figma を使う側にとって「ファイルを開く / ドキュメントを読む / 編集を保存する」が高優先度として常に優先される、という挙動が裏でどう実装されているかを覗き見できる稀少な記事です。安全な rollout 戦略（disaster readiness testing、自動 fallback、replica → primary の段階移行）も、本番運用の参考事例として価値が高いです。

### [Designing Stable Interfaces For Streaming Content](https://smashingmagazine.com/2026/05/designing-stable-interfaces-streaming-content/)

> **出典**: Smashing Magazine | **公開日**: 2026-05-01 | **カテゴリ**: design

**3行まとめ**
- AIチャット、ログビューア、リアルタイムダッシュボードといったストリーミングUIの3大課題（スクロール、レイアウトシフト、レンダー頻度）を実装で解決
- ユーザーが上方向にスクロールしたときの追従停止、60fps を超える更新の rAF バッチング、aria-live と prefers-reduced-motion 対応を実装サンプル付きで解説
- aria-atomic="false"、role="log"、Stop / Retry ボタンの aria-label 動的更新まで、アクセシビリティの実装ディテールを丁寧に網羅

**詳細解説**

Smashing Magazine の Joas Pambou による、ストリーミングUI設計の決定版的な記事です。AIチャットやログビューア、リアルタイムダッシュボードのデモを通じて、3つの本質的な問題を順に解決していきます。

ひとつ目は scroll の問題。多くのストリーミングUIは新しいコンテンツが来るたびにビューを最下部に固定しますが、ユーザーが上にスクロールすると勝手に最下部へ引き戻され、読みたい内容を見られなくなります。解決策は、ユーザーのスクロール位置と最下部の差分が60px以上なら「意図的にスクロールした」と判定し、自動追従を止める。再度最下部に戻ったら追従を再開する、という挙動の実装です。

ふたつ目は layout shift。ストリーミングはコンテナを常に成長させるので、その下にあるボタンや読んでいた行が動いてしまう。三つ目は render frequency で、ブラウザは60fpsでしか描画しないのに、ストリームはそれより速く来ることがあり、見えないフレームに対する DOM 更新がコストとして積み上がる。requestAnimationFrame でバッチして1フレームに1回だけ書き込む、というパターンで解決します。

アクセシビリティの章がとくに充実していて、`role="log"` + `aria-live="polite"` + `aria-atomic="false"` の組み合わせ、`prefers-reduced-motion` 対応で typewriter エフェクトを止める、停止後の Retry ボタンに元の質問を含む aria-label を動的に付与する、focus を Retry ボタンに飛ばすことでキーボードユーザーが Tab で探さずに済むようにする、といった実装ディテールが詳しく書かれています。

UXエンジニアリングの観点では、「ストリーミング自体は解決済みで、問題はその上に載るUI」という著者の指摘が刺さります。SSE や Streams API でデータが来るのは簡単になったが、それを安定したインタフェースに乗せるかどうかは、いまも設計と実装の craft が問われる領域です。AIチャット系プロダクトの実装者には必読といえます。

### [Users own the present. You own the future.](https://www.dir14.com/articles/users-own-the-present-you-own-the-future)

> **出典**: Sidebar | **公開日**: 2026-05-01 | **カテゴリ**: design

**3行まとめ**
- ユーザーリサーチで賢い経営層ほど自信たっぷりに間違った答えを返す、という観察と「want と need の区別」
- ユーザーは現在を所有する（自分の日常の専門家）、研究者は未来を所有する（パターンと飛躍）、という役割分担の提案

want と need の区別は Jared Spool の有名な論で、「ユーザーがアイスクリームを欲しいと言っても、本当の need は涼みたいこと」。want は選択肢を閉じ、need は選択肢を開く。ほとんどのユーザー研究は want で止まり、faster horse を作ることになる、と著者は主張します。Bain などのコンサルティング出身者は「answer-first」アプローチで訓練されているので、リサーチ session でその本能が裏目に出る、というのも鋭い指摘です。

「ユーザーは現在を所有する、あなたは未来を所有する」という構図がエッセイの背骨です。ユーザーは自分の毎日がどう動くか、何が壊れたとき何をするか、これまで何にお金を使って解決を試みたかの専門家。あなた（研究者・デザイナー）は、まだ存在しない pattern と product を統合する側。両者の責任が混ざるとき、リサーチは「決定の回避」や「アウトソース」に堕する、という警告が続きます。

Snapchat のナビゲーションを引き合いに出した learnability trap の議論も実用的で、新しいデザインは初回テストでは悪く出るのが普通。それを first-session feedback だけで判断するチームは、学習が必要なものを永遠に出荷できない。本当に問うべきは「自分で図解できるか」「次回も覚えているか」「不慣れさが消えるか」だ、と書かれています。Teresa Torres の product trio idea が現場では「3つのバイアスを平均してコンセンサスを作り、誰も責任を取らない」状態に堕しがち、という観察も忘れがたいです。

UXエンジニアリングの観点では、AI が自然言語インタフェースを作りやすくなったいま、ユーザーの「want」を機能化することはより簡単になっています。だからこそ「need」へ降りていく judgement と、その判断に責任を取る覚悟が、エンジニアやデザイナーの側により強く要求される、と読めます。
