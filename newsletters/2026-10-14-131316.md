### [The best way to use icons in Web UIs](https://lea.verou.me/blog/2026/icons/)

> **出典**: Lea Verou | **公開日**: 2026-10-11 | **カテゴリ**: css

**3行まとめ**
- Lea Verou さんが、HTML に手を入れずに CSS だけでアイコンを差し込み、状態に応じて切り替えられる仕組みを提案した記事です。アイコンをデザイントークンとして `:root` の CSS 変数に置き、`--icon` を指定するだけで使えます
- 疑似要素を `1em` の正方形にして `currentColor` で塗り、アイコンの形で `mask` をかけるのが基本です。スタイルクエリと `@property` を組み合わせて、アイコンを指定した要素にだけ表示されるようにしています
- Safari のバグ3件の回避策まで含めた実装を `@nudeui/icons` として公開しています。Linked Parameters や `ident()`、`@mixin` など、今後の CSS で書き方がさらに短くなる見通しも紹介しています

**詳細解説**

今もっとも一般的なのは、インライン SVG を HTML に直接書く方法です。`<TrashIcon />` のようなコンポーネントで包んでも、重いマークアップはそのままブラウザに届きます。アイコンフォントは CSS でアイコンを扱えるのが魅力でしたが、読み込みに失敗したときの代替文字や、スクリーンリーダーが私用領域の文字を読み上げてしまうといった問題がありました。著者は「問題はフォントであって CSS ではなかった」と述べています。2010年に UI アイコンを Web フォントで表示した最初の一人かもしれず、Font Awesome のプロダクトリードも務めた人の提案なので、説得力があります。

使い方はシンプルです。`button.delete { --icon: var(--icon-trash); }` と書けば HTML を変えずに削除ボタンにアイコンが付き、`:hover` やダークモード、印刷時に別のアイコンへ切り替えることもできます。`details::marker` や `select::picker-icon` のような疑似要素にも置けるのは、マークアップ側の方法では実現できない点です。flex のボタンのなかでは `aspect-ratio` が効かないので幅と高さを両方指定する、`flex: none` で縮まないようにする、キャップハイト（大文字の高さ）に合わせて縦位置をそろえる、といった細かな工夫も書かれています。アイコンだけのボタンには、生成コンテンツの代替テキスト `content: "" / var(--icon-style-alt, "")` で名前を付けられます。

スタイルクエリは Baseline 2026 で、Firefox が2026年5月に最後に対応しました。Can I Use では約93%のブラウザで使えるそうです。著者はアイコンを段階的な機能拡張として扱い、アイコンだけのボタンのように欠けると困る場面ではクラスで指定する方法を勧めています。Safari では、ユーザーが操作するまでアイコンが表示されないバグがあり、長さ0のアニメーションを当てて回避しています。

UXエンジニアリングの視点では、アイコンをデザインシステムのトークンとして一か所で管理できる点が大きいです。ページによって Font Awesome と Lucide のゴミ箱アイコンが混ざる、といったことを防げますし、登録されていないアイコンを直接指定するとレビューで目立ちます。一方で、マスクを使うため単色のアイコンに限られ、自由なアニメーションにはインライン SVG が必要です。SVG ファイルの相対 URL の解決もブラウザごとにばらばらで、今は Firefox だけが正しく動きます。React コンポーネントでアイコンを配っているチームは、移行の手間と比べて判断するとよいでしょう。

### [A design system is what it does](https://matthenry.fyi/posts/a-system-is-what-it-does/)

> **出典**: Sidebar | **公開日**: 2026-10-09 | **カテゴリ**: design

**3行まとめ**
- 米国政府のデザインシステム USWDS が大きく作り直されることになり、`shadcn/ui` への移行がうわさされていることを受けて、元 USWDS チームの著者が両者を比べた記事です
- 本文1行の文字数は USWDS が約68字、shadcn は約83字です。この既定値の違いが「何のための、誰のためのシステムか」の違いを表していると指摘しています
- ドキュメントでも、USWDS は既定値の理由まで説明しているのに対し、shadcn は設定の変え方は詳しいものの、なぜその値を選ぶのかは書いていないと比べています

**詳細解説**

タイトルは「システムの目的は、それが実際にしていることだ」という格言をデザインシステムに当てはめたものです。著者は、文字が小さく1行が長い組版には暗黙の前提があると言います。小さな文字を苦労せず読めること、1行分の情報を頭に保っておけること、情報が詰まったページから目当てのものを探す時間があること、の3つです。スタートアップの SaaS ならそれでよいかもしれませんが、政府のサイトを使う人すべてに当てはまるわけではありません。

ドキュメントの比較も具体的です。USWDS の `usa-prose` は、Markdown や CMS から出てくる本文のための部品です。ドキュメントには、見出しの階層やリスト、表までそろえた見本と、縦のリズムを示す図が前面に置かれています。タイポグラフィのページを読むと、既定値の変え方だけでなく、なぜ変えないほうがよいかまでわかります。shadcn の `typeset` は柔軟で、調整の方法は丁寧に書かれています。ただ、アクセシビリティのために文字を大きくする方法は載っていても、既定値自体は大きくしていません。

政府サイトを作る人の多くは、Web 制作とは別に本来の仕事を抱えていて、既定値のまま使います。著者はこれを批判ではなく前提として扱っていて、だからこそ既定値がそのまま品質になると述べています。

UXエンジニアリングの視点では、社内のデザインシステムにも同じ問いを向けられます。既定値とドキュメントは「どんな体験を作ってほしいか」を表明するものです。AI で UI を生成する場面が増えると、エージェントも既定値に流されやすいので、既定値の重みはさらに増すでしょう。なお、移行先はまだ決まっておらず、仮定にもとづく議論です。著者が元チームメンバーという立場であることも踏まえて読むとよさそうです。

### [Decorative Images…](https://adrianroselli.com/2026/10/decorative-images.html)

> **出典**: Adrian Roselli | **公開日**: 2026-10-09 | **カテゴリ**: accessibility

**3行まとめ**
- 「装飾的な画像」というものは、人にとっては存在しない、とあえて言い切ったアクセシビリティの記事です
- 判断のための問いは2つです。画像をまるごと消したら読者は気にするか、画像をうんちの絵に差し替えたら作者は気にするか。気にするなら装飾ではなく、気にしないなら画像を消せばよい、としています
- W3C WAI の代替テキストの決定木を広げ、空の `alt` で済ませる前に画像の役割を考え直す手順を加えています

**詳細解説**

この記事は、最近続いている議論の流れのなかにあります。Nicolas Steenhout さんの「装飾画像という概念を引退させよう」（2026年9月28日）や、WCAG 3 で装飾画像の定義を見直す issue #878 などです。2021年に Eric Bailey さんが書いた「Your Image Is Probably Not Decorative」もあわせて紹介されています。

著者の考えでは、画像を置くのには必ず理由があります。雰囲気を伝えたいのなら、見えない人にもその雰囲気が伝わったほうがよいはずです。余白を埋めたいだけなら、それはレイアウトで解決する問題で、見える人には意図しないメッセージを送ってしまっています。対象は本文中の画像で、アイコンや操作部品のなかの画像は含みません。

決定木は、文字を含むか、操作部品のなかにあるか、意味を持つか、と順にたどります。近くの本文と同じ内容を示す画像には空の `alt` を使う、という従来の扱いも残しています。そのうえで、意味がないと判断しても、消えたらユーザーが気にするなら最初からやり直し、という段を足しています。

UXエンジニアリングの視点では、`alt=""` は lint を通すための逃げ道になりがちです。画像を置く段階でデザイナーが目的を言葉にしておけば、代替テキストも書きやすくなり、不要な画像も減ります。CMS の画像入力に「装飾画像」のチェックボックスがあるなら、その UI 自体を見直すきっかけにもなるでしょう。著者自身が「わざと極端な立場を取っている」と書いているとおり、相手に自分の判断を説明させるための問いかけとして読むのがよさそうです。

### [New to the web platform in September](https://web.dev/blog/web-platform-09-2026?hl=en)

> **出典**: web.dev | **公開日**: 2026-10-02 | **カテゴリ**: web-standards

**3行まとめ**
- 2026年9月に安定版になったブラウザの新機能のまとめです。Chrome と Firefox が2週間ごとのリリースに移った最初の月で、Chrome 153/154、Firefox 155〜157、Safari 27 が出ました
- `progress()`、`alpha()`、`revert-rule`、`light-dark()` での画像の指定、`overflow-anchor` によるスクロールアンカー、`sizes="auto"` などが Baseline Newly available になりました
- Safari 27 が Chrome に続いてカスタマイズ可能な `<select>` に対応し、Chrome 153 では宣言的に使える `<camera>` と `<microphone>` 要素が入りました

**詳細解説**

CSS の追加が目立つ月です。`progress(100vw, 320px, 1200px)` のように書くと、画面幅に応じて0〜1の値が返り、不透明度や色を滑らかに変えられます。`alpha(var(--brand-color) / 50%)` を使えば、ブランドカラーの変数から半透明の色を作れます。`revert-rule` は、そのスタイルルールがなかった場合の値に戻すキーワードです。`light-dark()` は色だけでなく画像やグラデーションも切り替えられるようになり、`font-stretch` の正式名である `font-width` もそろいました。

体験に直接効くものもあります。スクロールアンカーは、読んでいる位置より上で DOM が変わっても、画面が飛ばないようにする仕組みで、Safari でも使えるようになりました。`sizes="auto"` は、遅延読み込みの画像で実際の表示幅から適切な画像を選んでくれます。`<camera>` と `<microphone>` は、ページを開いた途端にスクリプトから許可ダイアログを出すのではなく、ユーザーの操作をきっかけに許可を求めるための要素です。Safari 27 には Service Worker の Static Routing API も入りました。

ベータ版では、Chrome 155 の `margin-trim` や JPEG XL のデコード、Chrome 156 の `random()` 関数、`:playing` や `:paused` などのメディア要素の状態を表す疑似クラス、`<install>` 要素が予告されています。Safari 27.2 では、`display: grid-lanes` の `flow-tolerance` が `fit-tolerance` に名前を変えます。

UXエンジニアリングの視点では、主要ブラウザでそろう機能が増えたことで、これまで JavaScript や独自の部品で作っていた UI をプラットフォームに任せられる場面が広がっています。とくにカスタマイズ可能な `<select>` は、デザインシステムの独自ドロップダウンを見直すきっかけになります。ただし Firefox はまだ対応しておらず、Newly available の機能も古いブラウザでは動かないので、冒頭の Lea Verou さんの記事のように段階的な機能拡張として扱うのが無難です。

### [Context Libraries: How AI Power Users Manage Context Engineering](https://www.nngroup.com/articles/context-libraries/)

> **出典**: Nielsen Norman Group | **公開日**: 2026-10-09 | **カテゴリ**: design

**3行まとめ**
- Claude を毎日使うパワーユーザーの調査から、エージェントに渡す文脈をまとめた「コンテキストライブラリ」の管理で、専門家でもつまずいている様子を報告した記事です
- 参加者はプロンプトより文脈の整備に手間をかけていましたが、ファイルは古くなり、大事だと言っていたファイルを自分で見つけられない人も多くいました
- 教訓として、継続的に手入れする、更新はエージェントに任せる、見つけやすい構造にする、必要な文脈だけを渡す、の4つを挙げています

**詳細解説**

記事は文脈を3つの役割に分けています。めったに変わらず全体に効く「グローバル」、特定のタスクやプロジェクト用の「ローカル」、メールや会議の文字起こしのような未整理の情報の流れである「アンビエント」です。参加者が文脈の扱い方を学んだのは、おもに X や Reddit の投稿と自分の試行錯誤でした。記事は「Anthropic の開発者向けページを読み込まないと作れないのはおかしい」と指摘しています。

観察の内容はとても具体的です。Todoist との接続が何度も切れ、それを「システムの劣化」と呼んだ人がいました。ほとんどの人はファイルを直接編集せず、目の前にファイルを開いていても Claude に変更を頼みます。変更内容もあまり確かめず、その後の出力の質で判断していました。自分が知らなかったグローバルの指示ファイルが見つかった人や、ポッドキャスト用のデザインガイドラインが本の管理アプリに適用されてしまった人もいます。

もっとも作り込まれたライブラリは、読み込む量をできるだけ減らすように設計されていました。持ち主は2,700以上のファイルを階層にまとめ、各フォルダに CLAUDE.md という「索引カード」を置いています。ルールは「横に移る前に、いったん上か下に移動する」というものです。プロジェクトのフォルダで始めたセッションは、ほかのフォルダの中身を読み込まずに済みます。ファイルは数百行以内に収めている人が多かったそうです。

UXエンジニアリングの視点では、文脈の管理がユーザーに丸投げされていること自体が UX の課題です。どの文脈を読み込んだかを見せる、古くなった文脈を知らせる、保存場所をわかりやすくするなど、プロダクト側でできることは多そうです。次に紹介する「Agents don't need memory」と同じ結論に別の方向からたどり着いているので、あわせて読むとおもしろいです。参加者は Claude の上級ユーザーに限られた定性調査である点には注意が必要です。

### [Agents don't need memory. They need documentation.](https://liao.gg/blog/agents-dont-need-memory)

> **出典**: Sidebar | **公開日**: 2026-10-08 | **カテゴリ**: design

**3行まとめ**
- エージェント向けの「メモリ」プラグインは、会話から切り出した断片をベクトル DB に入れ、似ているものを毎回差し込んでいるだけの RAG だと批判し、必要なのはドキュメントだと主張する記事です
- 類似度で選ばれるだけで正しさや新しさはわからない、文脈が抜け落ちる、エージェントは知らないことを検索できない、中身を監査できない、といった問題を挙げています
- 代わりに、要件や判断の理由、制約をエージェント自身が Markdown で書き、作業前に読んで作業後に更新する仕組みを提案し、自作の OSS「Operator Memory」を紹介しています

**詳細解説**

著者のたとえはわかりやすいです。チームの制約を思い出すために、3年前の会議の録画を見直す人はいません。人は書き残し、その記録を使います。コードは「何をするか」は教えてくれますが、要件や判断、方針までは教えてくれません。それを書いておかないと、毎回8万トークン分の探索をして、元の意図を不完全に推測し直すことになるといいます。

役に立つドキュメントの条件として、4つが挙げられています。ひとつめは、コードからわからないことだけを書くことです。ふたつめは見つけやすさで、セッションの最初には目録だけを読み込み、必要になったら詳しい資料を開きます。みっつめは鮮度で、作業したエージェントが文脈を持っているうちに書き、事実が変わったら追記ではなく書き換えます。最後は肥大化させない規律です。ただの Markdown なので、Git で差分を見たり、レビューしたり、元に戻したりできる点も利点として挙げています。

UXエンジニアリングの視点では、NN/g の調査と同じく「索引を置いて、必要な分だけ読む」というやり方に落ち着いているのが興味深いところです。人間の開発チームが育ててきたドキュメントの文化が、そのままエージェントにも効くということでしょう。デザインシステムのドキュメントも、エージェントが読み書きする前提で構成を考えておく価値がありそうです。自作ツールの紹介を兼ねた記事で、エージェントが書く文書は膨らみやすく、著者自身もよく手で直していると認めています。

### [The New Siri's Biggest Strength Is Not Intelligence](https://www.nngroup.com/articles/ai-assistant-context/)

> **出典**: Nielsen Norman Group | **公開日**: 2026-10-09 | **カテゴリ**: design

**3行まとめ**
- 2026年9月14日に英語でベータ公開された Apple の新しい Siri AI を、旧 Siri と ChatGPT と比べ、AI アシスタントの使いやすさを決めるのは賢さよりも手元の個人的な文脈だと論じた記事です
- 兄が勧めたレストランを聞く、旅行の写真を探すといった作業では、メッセージや写真を参照できる Siri AI がもっともうまくこなしました
- 一方で、確認したはずの出発地が地図アプリに引き継がれない、Signal のメッセージを探せないのに「見つからない」とだけ答える、といった失敗から設計上の教訓を引き出しています

**詳細解説**

「先週末のニューヨークの写真を見せて」と頼むと、旧 Siri は Web 上の一般的な画像を、ChatGPT はニュース写真へのリンクを返し、Siri AI だけが本人の旅行写真を見つけました。ChatGPT は仕事用の Gmail と Slack に接続していましたが、そこに必要な情報はありませんでした。記事は「接続先を増やしても、必要な情報がそこになければ役に立たない」とまとめています。

失敗例からの教訓が実務に役立ちます。「Peter は土曜について何て言ってた？」という質問では、答えが初期状態では Siri から読めない Signal にあったため、見つかりませんでした。記事は、どこを探して何が足りないかを伝える必要があるとして、「メッセージとメールを探しましたが、Peter さんの土曜の予定は見つかりませんでした。ほかで共有されていたら、ここに貼り付けてください」という文例を示しています。レストランの「Dimes」と地区の「Dimes Square」を取り違えた例からは、結果が変わる候補があるなら実行前に聞くこと、を導いています。さらに、確認した出発地が Google Maps では現在地に置き換わっていました。途中で確認した内容は、最後の操作まで引き継がれる必要があります。

メンタルモデルの話もあります。提案する質問例は、実際に検索できるデータを指すものにしないと誤解を招きます。メッセージの下書き中に「Web サイトを検索中」と説明なく表示されると、かえって不信につながります。処理を見せる透明性と、なぜそうしたかを伝える説明可能性は別物だ、という指摘です。

UXエンジニアリングの視点では、エージェントの体験を評価するとき、遷移先のアプリで何が表示されるかまで含めてタスク全体を見る、という点がすぐに使えます。探した範囲と次の手を示すエラーメッセージの書き方も、そのまま参考になります。各操作は1〜2回の試行で、統制された比較ではないと著者自身が断っています。

### [AI invasive design](https://jovo.design/writing/ai-invasive-design)

> **出典**: Sidebar | **公開日**: 2026-10-09 | **カテゴリ**: design

**3行まとめ**
- 「AI ネイティブ」という言葉が、AI をどれだけ使ったかという量の競争になり、価値のある既存の仕組みまで AI に置き換えてしまう危うさを指摘した記事です
- 製品を AI に合わせるのではなく、人の行動という生態系のなかで AI が在来種のようになじむように作る、という捉え直しを提案しています。なじまない AI は、手間をかけて生かす観賞用の外来植物か、ほかの価値を締め出す侵略的外来種になるといいます
- そのための条件として、意図を反映する、足場になる、共通の言葉で動く、影響範囲を抑える、ユーザーのスキルを奪わない、の5つを挙げています

手法も丁寧に公開されています。2025年10月7日から2026年10月7日までの変更で、10件以上変更した人を数えています。Android 16 のシステムライブラリをなかまで読み、Android の liblzma は xz ではなく 7-Zip のコードだったことも見つけています。データとスクリプトも公開されていて、HarfBuzz による文字の整形の有無を実際に見比べられるなど、見せ方にも工夫があります。

UXエンジニアリングの視点では、xkcd の「Dependency」の漫画がどこまで本当かをデータで確かめる、という問いの立て方がうまい記事です。データと手法、限界（端末数は下限の値であること）まで明示する姿勢は、データビジュアライゼーションの手本にもなります。自分たちのプロダクトがどんな部品に支えられているかを見直すきっかけにもなるでしょう。変更の作者が保守者とは限らないこと、「公的な助成なし」は特定の基金を調べた範囲であることは、記事自身が断っています。
