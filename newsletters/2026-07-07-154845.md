### [Agentic Autonomy Levels](https://addyosmani.com/blog/agentic-autonomy-levels/)

> **出典**: Addy Osmani | **公開日**: 2026-07-02 | **カテゴリ**: performance

**3行まとめ**
- Steve Yegge の一軸ラダーではもう測れない、AIエージェントの自律性を「エージェンシー（1体をどこまで任せるか）」と「オーケストレーション（何体をどう協調させるか）」の二軸で捉え直す整理です
- Assist / Supervised / Scoped / Goal / Parallel / Managed-by-exception の6段階を、リスクと反証可能性で選ぶ「Calibrated Autonomy」という姿勢を提唱しています
- 「Autonomy as status」「Permission laundering」「Summary substitution」「Fleet cosplay」という4つのアンチパターンを名指しし、それぞれの回避策も示します

**詳細解説**

エージェント開発の議論はしばしば「どのくらい任せるか」の一次元で語られがちですが、実際には「1体のエージェントをどこまで自走させるか」と「複数エージェントをどう束ねるか」という別軸の話が混ざっています。Addy Osmani はこの2つを分けたうえで、Level 0（Assist）から Level 5（Managed-by-exception）までの6段階を、Claude Code や Codex の具体的な機能（/plan、/goal、/loop、/batch、worktrees、Auto-review など）に紐づけて記述します。エージェントを日常的に使うエンジニアが自分の運用を位置づけるための、実務的な地図として機能する内容です。

とくに示唆的なのは「Verification will always be the bottleneck（検証は常にボトルネックである）」という主張です。Anthropic の分析によると、人間は計画の意思決定の70%を担い、実行の80%はAIが担っている——つまり高い自律性とは「人間を輪から外すこと」ではなく「毎ステップに関わるのをやめて方向決定に集中すること」を意味します。判断の基準として提示されるのは、「間違いにどれだけ早く気づけるか」「どれだけきれいに元に戻せるか」「正しいと証明できるものは何か」の3問。この3つの答えがどれも弱いなら、それは高自律ではなく、単に検証を放棄しているだけだと切って捨てます。

UXエンジニアリングの視点では、後述の Geoffrey Litt「Understanding is the new bottleneck」と対になって読むと理解が深まります。Osmani がガバナンス側から「タスクごとの契約と証拠設計」を説くなら、Litt は成果物側から「理解を維持し続けるための道具」を説く関係です。「Every run of an agent should be preceded by a contract（すべての実行の前に目的・スコープ・非目標・ツール・停止条件・証拠・エスカレーション・予算を定めよ）」という枠組みは、これから増えていくエージェント運用の設計書として、そのまま社内ガイドラインの下敷きに使えるレベルの完成度があります。

### [The Agent-Era Career](https://addyosmani.com/blog/career-advice-age-of-agents/)

> **出典**: Addy Osmani | **公開日**: 2026-07-06 | **カテゴリ**: performance

**3行まとめ**
- 「AIは答えのある問題を全て速く安く解けるようになる。あなたのキャリアは答えのない部分すべてだ」という一文から始まる、エージェント時代のエンジニアキャリア論です
- 「問題を解く」より「問題を選ぶ」、「実装する」より「仕上げる」——最初の下書きが無料になった今、finish（最後の30%）こそが差別化要因になると論じます
- 判断力（taste）は反復から生まれる筋肉であり、エージェントに委ねすぎるとそれが萎縮する。deliberate practice を意図的に残せという提言が具体的です

**詳細解説**

Chrome や Gemini を率いた Addy Osmani が、AIエージェントの時代にキャリアをどう築くかを、自身の来歴を交えて書いたエッセイです。「LeetCode がスキルの物差しだった時代」から「エージェントが解いたコードを見て正しいか判断できることのほうが希少になった時代」への転換を、実感を込めて描きます。給与を最大化する選択より、レピュテーションと関係性に投資したほうが長期リターンが大きい——「金は数週で調達できるが、評判は数週では作れない」という言葉は身に沁みます。

技術的に興味深いのは、判断力（taste）の獲得法についての整理です。Osmani は「taste は pattern-matching であり、その pattern-matching は自分の手で仕事をやることでしか蓄積されない」と断言し、良い実践者はエージェントの前に立つ問題を「意図的に選ぶ」といいます。Deliberate Practice（意図的な反復）の対象として推奨されるのは、重要な問題を数個ハードな方法でやる／エージェントが書いた1000倍のコードを読む／エージェントの提案で怪しいものを日々ログに残す——という3点。「エージェントの提案を人間のレビューのつもりで丁寧に正当化する」という一言に、成熟したエンジニアの姿勢がよく表れています。

UXエンジニアリングの視点で刺さるのは「Sprint the last mile」の話です。エージェントは機能の70%を高速に出しますが、残る30%——エッジケースのデバッグ、正しいアーキテクチャの選定、細部の作り込み——が実質的な勝負どころになる。「最初の下書きが無料になった世界では、仕上げ（finish）こそがプロダクトだ」という定式は、AIコーディングの体感と一致します。エージェントに任せた分の余白を、粗い出力を仕上げる能力の獲得に投資するという時間配分は、これからのエンジニアの日々の指針になりそうです。

### [Understanding is the new bottleneck](https://www.geoffreylitt.com/2026/07/02/understanding-is-the-new-bottleneck.html)

> **出典**: Sidebar | **公開日**: 2026-07-06 | **カテゴリ**: design

**3行まとめ**
- Notion の Design Engineer Geoffrey Litt が、「エージェントの書いたコードを我々はまだ理解する必要があるのか」という問いに正面から向き合った講演の書き起こしです
- 理解の目的は「検証（verify）」ではなく「参加（participate）」——プロジェクトは何度もループを回すもので、次のアイデアを出せるかどうかが理解の深さで決まると論じます
- Explainer docs、Micro-worlds（自作デバッガや操作可能な小さな世界）、Shared spaces（チームの共通理解）という3つの実践的テクニックを具体例で紹介します

**詳細解説**

エージェントに書かせたコードを人間はどれだけ理解しておくべきか——という問いに、「検証のため」という答えでは実は不十分だと Litt は指摘します。エージェント自身が検証精度を上げている以上、この目的だけならいずれ人間は外れられるはずです。だが実際のプロジェクトはワンショットのタスクではなく、何十回・何百回とループを回して育てるもの。「次に何を作るか」を発想するには、システムに関する概念の網の目が頭の中になくてはならず、それを失うのは Margaret Storey のいう「認知的負債（cognitive debt）」を積むことに等しい、という論理です。

具体的な手法は3つ提示されます。第一は Explainer docs——`/explain-diff` というスキルで、背景知識→意図→直観→prose形式の literate diff→理解度クイズという構造の説明資料を毎回生成し、コードを読む前に必ず目を通す。クイズに答えられなければコードを他人に送らないという規律が印象的です。第二は Micro-worlds——Prolog インタプリタを理解するためのデバッガや、フレームワーク移行を自分でボタン操作で進められる「コマンドセンター」など、エージェントに自作の学習環境を作らせて、そこに「住み込んで」直観を得るアプローチです。第三は Shared spaces——チームで同じメンタルモデルを持つための場を、Notion のような共同編集空間の上に作るという発想です。

UXエンジニアリングの視点で読むと、Litt が「Alan Kay の augment（拡張）の思想を再訪する」と結んでいる点が響きます。エージェントを単なる自動化装置として使えばコードは増えるが、生成AIには「人間の理解を助けるための小さな道具を作る」使い道もある。Explainer 生成、対話的シミュレーション、視覚化ダッシュボード——ここに書かれた例は、UXエンジニアが社内向けツールとして即日プロトタイプできる領域そのものです。前述の Addy Osmani の「Autonomy Levels」と対にすれば、「エージェントに任せる」と「エージェントに理解を助けさせる」の両輪が見えてきます。

### [Code is the easy part](https://swizec.com/blog/code-is-the-easy-part-or-how-we-refactored-half-the-business-to-fix-a-janky-script/)

> **出典**: Sidebar | **公開日**: 2026-07-06 | **カテゴリ**: design

**3行まとめ**
- 年商20mから100mへ5倍成長したスタートアップで、月末請求を支える壊れかけの Python スクリプトを起点に、事業側の半分をリファクタするまでの6か月の記録です
- 「まず問題をシンプルにしてから解け」——大きく厄介な問題の多くは、データモデルがドメインモデルと合っていないことが原因だと喝破します
- Cessna を飛ばしながらエンジンを交換するように、dual-mode 運用・段階的ロードアウト・最後に大きなUI更新という change management の順序が具体的に語られます

**詳細解説**

Plasmidsaurus という DNA シーケンシング企業で、Swizec が経験した「月末になると徹夜が必要になる請求業務」を automation まで持っていった話です。オペレータは動かし方は知っているが仕組みを知らない、3年前のバグの回避策が今も公式ワークフローになっている、顧客ごとに例外ルールが積み重なっている——という典型的な「ball of mud」を、まず1つの本質的なデータモデルの問題として捉え直します。Torvalds の「悪いプログラマはコードに、良いプログラマはデータ構造と関係性に悩む」という言葉を軸に、「Billing Entity」という新しい抽象を導入するに至ります。

現場の重みが伝わるのは、change management の記述です。「software has to keep working the whole time」——古い方式と新方式を dual-mode で数か月併走させ、経理チームには混乱を強いる代わりに、月に一度しか出ないエッジケースを地道に発見していく。UI の大変更は最後にまとめて投入し、「ユーザーはUI更新なしには変更を実感できない」という洞察も交えられます。最初は経理チームとの6時間のミーティングから始まり、購買部の PO 形式は「AIで作った正規表現地獄」より「ユーザーの作業を watch する」ほうが5分で解決するという実話は、AIとフィールドリサーチの相補性を象徴的に示しています。

UXエンジニアリングの視点で読むと、「1つの共有された概念を3種類のユーザーが違う視点で見るとき初めて複雑なアプリになる」という主張が本質的です。ラボ／機関／個人という組織構造の上に、営業・経理・顧客がそれぞれ別の目的でぶら下がっている状況は、SaaSプロダクトの権限モデルの永遠の難所です。データモデルの再設計と change management は分けて考えがちですが、この記事は「新モデルを走らせながら旧モデルの整合性も維持する足場」（フォールバック・監査ツール・段階的UI移行）を作る仕事こそが、本番の core だと教えてくれます。

### [Design systems are no longer optional](https://mandy.dev/posts/design-systems-ai/)

> **出典**: Sidebar | **公開日**: 2026-07-06 | **カテゴリ**: design

**3行まとめ**
- AIがUIの相当部分を生成する時代、デザインシステムはもはや「一貫性のための努力」ではなく「AIが参照する source of truth」だと位置づけ直します
- 弱いシステムに向けたAIの生成は、ドリフトを一度きりの失敗で終わらせず「次の生成の参照点」にしてしまう——ドリフトが機械速度で伝播することへの警鐘です
- Federated（連邦制）ではなく Central（中央集権）の所有権が必要で、その運営には Constraints と Feedback loops の両輪が要ると論じます

**詳細解説**

以前は「デザインシステムは budget が厳しくなると後回しにされるもの」でした。しかし AIが継続的にUIを生成する体制になると、その参照点の質はコンプライアンスに近い位置に格上げされます。AIは「意図された状態」ではなく「現時点のコードベース」に対して生成するため、少し崩れたカードのコードが残っていれば、次にカードを作るときそれが「正解の例」として参照される。人間なら遅くて限界のあった drift が、機械速度で自己増殖する——という構造の指摘が本記事の肝です。

もうひとつの重要な論点は所有権です。Nathan Curtis の「Federated design systems の詭弁」を引き、feature チームに責任を分散した「連邦制」は、締切と品質が対立したとき常に feature が勝ってしまうため機能しないと指摘します。中央チームに必要なのは「NOを言える権限と責任」で、成功指標は「システムの正確さと使いやすさ」であって feature velocity ではない。「デザインシステムチームを持てる余裕があるか」ではなく「誰もメンテしていない reference にAIを何千回も向ける余裕があるか」という問いの立て直しが、経営層への説得材料としてよく効きそうです。

UXエンジニアリングの視点では、Constraints（トークン・APIの厳密さ・コード横のドキュメント）と Feedback loops（トークン外の値を弾く lint・system をすり抜けるコンポーネントを検出するチェック・visual regression）の両輪という枠組みが実装に直結します。とくに「ドキュメントは Figma や別サイトではなく repo に置く」という指針は、Claude Code や Cursor が読む場所と一致します。次の Fabricio Teixeira の記事とセットで、「デザインシステム負債はもう1人ではなく組織全員で払うことになる」という同じ現象を、供給側（作り手）と需要側（コストを負担する人）の両面から読むと立体的に理解できます。

### [Figma just made your design system debt everyone's problem](https://newsletter.uxdesign.cc/p/figma-just-made-your-design-system)

> **出典**: UX Collective | **公開日**: 2026-07-06 | **カテゴリ**: design

**3行まとめ**
- 「デザインシステム負債は昔、誰も開かないファイルの中で1人が静かに払うものだった。いまはコンポーネントの生成が壊れるエンジニア、引き渡しが破綻するPM、ブランドから外れたバナーで困るマーケが払う」——構造の変化を鮮やかに切り取る Fabricio Teixeira のコラムです
- デザイナーが長年言ってきた「デザインシステムは deliverable ではなく product。ガバナンス・資金・オーナーが要る」という主張が、いま予算を握る側にとっても他人事でなくなったという指摘です
- Figma のプラットフォーム拡大により、システムのズレが下流の全職種に直接可視化される時代を捉えたコンパクトな記事です

**詳細解説**

前述の Mandy の記事が「なぜデザインシステムが AI時代に重要か」を体系的に論じるのに対し、こちらは「その痛みが誰に届くようになったか」という配分の変化を短い文で切り出します。Figma AI や Make によってデザインシステムの参照は上流の生成の入り口になり、そこがズレていれば下流のあらゆる自動生成がズレる。エンジニアはコンパイルの通らないコンポーネントを受け取り、PMは引き渡しの破綻でスケジュールを崩し、マーケはブランドから外れた広告物を出してしまう。かつて「ボタンが少しズレていても大局には関係ない」と却下していた予算保持者が、いま自分の指標の悪化として受け取るようになる、という構図です。

紹介記事なのでボリュームは小さいですが、引用されている「デザインシステムは deliverable（納品物）ではなく product（プロダクト）」というフレーズは、Mandy の主張と併せて社内説得の材料として強力です。「1人が静かに払う」から「全員が払う」への移動、これはコスト構造の変化ではなく可視化の変化——コストは元々そこにあったが、いま計上されるようになっただけ、という読み方もできます。デザインシステムを守るためにこれまで足りなかったのは、コスト自体ではなく「誰が支払いに気づくか」だったのだと。

UXエンジニアリングの視点では、Mandy の記事の「Constraints と Feedback loops」の Feedback を、組織レベルで見た記事だとも読めます。デザインシステムの品質は、生成結果を消費する側の職種にどれだけ痛みが可視化されるかで維持される。開発者向けの visual regression テストや token lint はもちろん重要ですが、それに加えて「ブランドが崩れたことをマーケが気づける仕組み」「引き渡しが壊れたことを PM が数値で見られる仕組み」を作るのも、これからのデザインシステム運営に含まれてくる仕事なのかもしれません。

### [Claude Fable 5のReact習熟度ベンチマークをeffort=maxで回したぞ！！！！！](https://zenn.dev/uhyo/articles/react-profession-bench-10)

> **出典**: uhyo | **公開日**: 2026-07-06 | **カテゴリ**: frontend

**3行まとめ**
- uhyo さんの React 習熟度ベンチマーク第10回。Claude Fable 5 を effort=max で回し、86.67 という歴代最高スコアを記録したという報告です
- 「世代を1つ上げる（+1.9〜+2.6）」より「effort を max に上げる（+4.6〜+5.3）」ほうが効くという、世代×effort の2×2 が完成しました
- Fable の弱点だったコンポーネント設計が effort=max で解消され、地力のアクセシビリティ（+0.52）が決定打として残り Opus 4.8 max を +2.64 上回るという分析が明快です

**詳細解説**

シリーズを継続してきた著者ならではの、2×2 の完全な対照実験になっている点がこの回のいちばん価値ある部分です。Claude Max のサブスクを2週間 Fable につぎ込み、さらに $40 追い課金してベンチを完遂させたコストのかけ方も凄まじいですが、その結果として「default 対 max の不公平な比較」から「同一 effort での世代比較」へと分析の粒度が上がりました。effort の効果（縦方向）が世代の効果（横方向）より大きく、しかも Fable のほうが effort の恩恵を強く受ける（+5.3 対 Opus の +4.6）——これは「モデルを新しくする」より「思考量を増やす」ほうが実務的に効くケースがあることを示唆します。

技術的に興味深いのはカテゴリ別の内訳です。Fable max は状態設計・Effect・型・パフォーマンスで Opus 4.8 max と横並び（+0.03〜+0.08）に達し、コンポーネント設計は 3.77→4.23 に伸びて Opus max（4.21）に追いつきました。第8回で「Fable に足りないのは能力ではなく思考量だ」と立てた仮説がそのまま実証された格好です。そして5カテゴリが並んだあと、Fable default 時点で既に Opus 4.8 max と同値だったアクセシビリティ（3.74）が max で 4.26 まで伸び、+0.52 の差として残った。「effort で弱点を消し、世代の強みで勝つ」という勝ち方の説明が、単なる総合スコアではなく分解できているのが本記事の読み応えです。

UXエンジニアリングの視点では、実運用のモデル選定にそのまま使える教訓が2つあります。第一に、アクセシビリティが Fable の世代由来の地力になっている——ミドルティア／ハイティアを問わず、AIによるReact実装で a11y が担保されやすいなら、レビュー観点の配分を再設計できます。第二に、Fable 5 max は最高スコアであると同時に最も高コスト（Opus の約2倍の使用量 × max effort）。品質最大化と品質/コスト最適化は同じ答えにならず、Opus 4.8 max や Fable 5 default も現時点で合理的な選択肢だと明記される点は、コスト配分の意思決定において誠実な整理です。

### [Getting Started with Anchor Positioning](https://www.joshwcomeau.com/css/anchor-positioning/)

- ツールチップやドロップダウンを別要素に「引っかける」ための CSS Anchor Positioning API を、8割の実務ユースケースをカバーする2割の機能に絞って解説する入門記事です
- `anchor-name` と `position-anchor`、`position-area`、`position-try-fallbacks` の基本を、実装例とインタラクティブなプレイグラウンドで理解できる構成になっています
- Anchor Positioning Level 2 の「anchored container query」で、フォールバック位置を検知して caret の向きを切り替える設計も紹介されます

**詳細解説**

ツールチップやポップオーバーは「ボタンの上に浮かせたいが、上端近くだと下に回りたい」というシンプルな要件の裏に、レイアウト、オーバーフロー検出、方向切り替えという厄介な問題が並びます。従来は Floating UI などのJSライブラリでケアされてきたこの領域が、Anchor Positioning API によって宣言的なCSSで書けるようになりました。Josh Comeau は「20%のAPIで80%のユースケースを覆う」という80/20の視点で、`anchor-name`（アンカー命名）→ `position-anchor`（ターゲット指定）→ `position-area`（相対位置）→ `position-try-fallbacks`（オーバーフロー時の代替位置）という4段の学習経路を提示します。

とくに実務で嬉しいのは `flip-block` キーワードです。ターゲットが画面外に近づいたとき自動で反対側にフリップし、しかも `margin-bottom` のような方向依存プロパティも一緒に反転してくれる。副次的に対応したい caret（吹き出しの尻尾）の向きを Level 2 の anchored container query で切り替えるパターンも紹介され、`@container anchored(fallback: bottom)` で自然にスタイル分岐できるようになっています。Level 2 は現時点で Chromium のみですが、Interop 2026 に含まれているので他ブラウザにも近いうちに来る見込みです。

UXエンジニアリングの視点では、これはUIコンポーネントライブラリのデザインを見直す機会になります。Floating UI 相当のロジックをJSで抱える必要が減ると、コンポーネントのバンドルサイズもロジック複雑度も小さくなり、SSR時のちらつきも減る。当面はプログレッシブエンハンスメントとして扱う必要がありますが、記事末尾の `@supports (position-area: top)` / `@supports (container-type: anchored)` を使った3段階のフォールバック実装は、既存のツールチップUIを非破壊的に置き換えるひな型としてそのまま使えます。当ニュースレターの前号（07/04）で触れた `scrollTo() Promise` と同じく、「ハックで補っていたものをブラウザが宣言的に引き受け始めた」流れの一つです。

**詳細解説**

LessWrong に投稿された短いエッセイで、直感に反する角度から目的意識を扱った文章です。プロジェクトを手伝ってほしいと頼んできた人が、そもそもプロジェクトの目的を知らない——それは非難すべきことに聞こえるが、本当にそうか？と著者は問います。大学進学の理由を「学びのため」「signaling のため」「エリートとつながるため」「今の状況から逃げるため」のどれか一つに明確化していない人は、実は多くいる。そして目的を明確化しすぎた10代のほうが、漠然と「よさそうだから」で動く10代より選択が悪化することもある、というリアリズムがあります。

一方で、「パーティを開くのに『目的』は要らない」けれど「特殊なことをやりたいのに『なんとなく良さそう』しか言えない人を手伝う気にはならない」という対比も示されます。目的を明示すべきかどうかは、活動の慣習性と、巻き込まれる他者の負担で決まる——これは製品開発の文脈にもぴったり重なる話です。既存の型に沿った作業なら理由の明文化は薄くてよい。しかし通例から外れた提案には、他人のリソースを使う分の説明責任が発生する、という原則です。

UXエンジニアリングの視点では、これはPRの粒度やRFCの書き方の議論に接続できるエッセイです。「これはなぜ必要なのか」を書くことに追い立てられる文化は健全ですが、あらゆる活動の目的を最初から明示することを求めるのは行き過ぎることがあります。前述の Osmani「Agent-Era Career」の「Selection over solving」——問題を選ぶことがスキルになる時代、目的の明示性がむしろ発散を阻む可能性も含めて、目的意識の使い方の解像度を上げてくれる小品です。連休の朝に、コーヒーとともに読むのがちょうどよい長さです。
