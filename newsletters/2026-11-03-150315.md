### [Improving navigation experience in v0 with Next.js 16.4](https://nextjs.org/blog/improving-navigation-experience-in-v0-with-nextjs-16-4)

> **出典**: Next.js Blog | **公開日**: 2026-10-16 | **カテゴリ**: frontend

**3行まとめ**
- Vercel の AI アプリビルダー v0 で、テンプレート・設定・プロジェクトの各画面を開いたときや戻ったときに出ていた読み込み中のスケルトンを、Partial Prefetching と `navigation()` で減らした事例です
- 「クリックの前に何が見えていてほしいか」を `instant()` という Playwright のテストで書き、それが通るまでエージェントにリファクタリングさせる進め方をとっています
- PR ごとに本番の指標を見ながら調整し、prefetch のリクエストが2.9倍に増えた画面ではホバーやフォーカスまで待つ形に変えています。全体の1日の費用は2.9%下がりました

**詳細解説**

Partial Prefetching は、遷移先のうち使い回せる部分だけを先に読み込み、残りはクリックしたあとに読み込む仕組みです。従来の `prefetch={true}` は動的な中身まで丸ごと取りにいくので、開かれないページの分まで通信が増えていました。かといって prefetch を切ると、クリックしてからすべてを待つことになります。Next.js 16.4 からは `create-next-app` で Cache Components と Partial Prefetching が最初から有効になっていて、この記事はその使い方を v0 の実際の画面で見せたものです。

進め方でおもしろいのは、目標を先にテストとして書いている点です。`instant()` はクリックの前後を固定し、遷移中に届く中身を止めたうえで「クリックの前に見えている UI」を確かめられるヘルパーです。テンプレートの画面なら「ヘッダー・タイトル・プレビューがスケルトンなしで出ている」ことを assert し、まず失敗させてから、通るまでキャッシュと prefetch の設定を直していきます。テストはそのまま CI に残るので、あとから誰かが同じ画面を遅くしても気づけます。

画面ごとの判断も具体的です。誰が見ても同じテンプレートのデータは `'use cache: remote'` でユーザー間で共有し、アカウントごとに中身が違う設定画面は `'use cache: private'` でブラウザ側に置いています。URL に含まれるアカウントやチームのスコープをキャッシュのキーに入れて、中身が混ざらないようにもしています。設定を保存したあとは `updateTag()` で古い値をすぐに捨てるので、ユーザーは同じ往復のなかで新しい値を見られます。プロジェクト画面では、タイトルと本番デプロイの欄を先に読み込み、「Recent Chats」は `navigation()` で開いたあとに回しています。

UXエンジニアの立場から参考になるのは、「何を先に見せて、何を待たせてよいか」を普通の言葉でエージェントに伝え、それをテストに落としているところです。これはデザインで決める読み込み順の話そのもので、スケルトンをどこに出すかという判断がそのまま仕様になっています。大きなグリッドでは、表示されたカードをすべて prefetch したところ通信が2.9倍に増えたため、ホバー・フォーカス・タッチを待つ形に変えました。小さく固定されたリンク群は、表示されたときに prefetch するままにしています。ユーザーが「開きそうだ」という意図をどこで読み取るか、の線引きとして使える基準です。

費用の面では、共有キャッシュの支出が改修前の4.3倍（1日あたり約3.44ドル増）になりました。それでもリクエスト、計算量、転送量が減ったので、追っていた配信の費用は14.4%下がっています。ただし同じ期間に流入や別のデプロイも変わっているので、全体の数字は「高くはならなかった」ことの確認として扱っている、と記事自身が断っています。Vercel 上での数字なので、自前で `next start` する場合は remote のキャッシュがメモリになる点も含めて読み替えが必要です。

### [Ship less JavaScript in Next.js with your AI agent](https://nextjs.org/blog/ship-less-javascript-with-ai)

> **出典**: Next.js Blog | **公開日**: 2026-10-28 | **カテゴリ**: frontend

**3行まとめ**
- Next.js 16.4 に、Turbopack のモジュールのつながりを調べてバンドルを減らす、エージェント向けのスキル `next-bundle-optimizer` が入りました
- 「同じバンドルのどこかで静的に import されていると、dynamic import で遅らせたつもりのコードも最初に読み込まれる」といった見落としを、import の連鎖をたどって見つけます
- v0 と vercel.com で使ったところ、実験中のエディタやダイアログ、使っていないビューアなどが見つかり、圧縮後で合計約2MBの JavaScript を削るか後回しにできたそうです

**詳細解説**

ひとつ前の記事と同じく v0 が題材で、こちらは最初に読み込む JavaScript の量の話です。バンドルが大きくなる原因は、たいてい1つの大きなライブラリではなく、共通のユーティリティ経由で思わぬものがついてくるような import の関係にあります。記事の例では、URL を解析するコードを共通ファイルから読み込んでいたせいで、監視用のクエリエンジンまでデプロイ画面に入っていました（125KB）。

スキルの中身は、`next analyze` のスナップショットを JSON に書き出し、モジュールとチャンクのグラフを組み立て直して調べるものです。つながりの強いモジュールのまとまりを見つけ、どの import を切れば読み込みを後回しにできるかを最小カットで探します。そのうえで、実際のソースや画面での使われ方と照らし合わせます。既定では問題と修正案を報告するだけで、`fix` を付けたときだけ変更を当て、前後のスナップショットを比べて効果を測ります。

見つかったものの一覧は、多くのプロダクトで心当たりがありそうな内容です。実験の対象外のユーザーにも実験用のエディタを読み込ませていた（多くのページで150KB）、ダイアログをまとめて登録する仕組みが重いダイアログを先に読み込んでいた（40〜650KB）、エージェントのパネルを開いていなくても Markdown の描画やシンタックスハイライト、グラフの描画を送っていた（255KB）、などです。どれも機能を足すたびに少しずつ入り込むもので、コードレビューでは気づきにくい種類の問題です。

UXエンジニアの目で見ると、「操作するまで要らないもの」をどこまで後回しにするかは、操作した瞬間に少し待たせることとの引き換えになります。記事でも、修正ごとに PR を出し、プレビュー環境で動きを確かめてから出したと書かれています。人が使う解析画面にも、ルートごとのサイズの一覧、ビルド間の差分、最初の描画に要るモジュールだけに絞る表示が足されたので、エージェントを使わなくても確認の道具になります。

なお、ここに出てくる数字は Vercel 自身のアプリで減らした量で、表示速度や操作感がどう変わったかの計測までは書かれていません。Turbopack が前提なので、webpack のままのプロジェクトではそのまま使えない点にも気をつけたいところです。

### [A select should tell you something](https://alfy.blog/2026/10/27/a-select-should-tell-you-something.html)

> **出典**: Sidebar | **公開日**: 2026-11-02 | **カテゴリ**: design

**3行まとめ**
- `appearance: base-select` で select の見た目を変えられるようになったことより、option のなかに「選ぶための情報」を入れられることのほうが大きい、という記事です
- フォント選び、タイムゾーン、配送方法、同じ名前の人の選び分け、承認が要る共有先の5つの例を、同じ `<select>` の before / after で見せています
- スマホでは OS 標準のピッカーが使えなくなるので、`@media (hover: hover) and (pointer: fine)` でマウス環境だけ有効にする方法と、どの option も文字だけで意味が通るように書くという条件も添えています

**詳細解説**

これまで option は1行の文字列だったので、判断に必要な情報はラベルに押し込むか、あきらめるしかありませんでした。option に見本や数字、役職、注意書きを入れられるようになると、ユーザーは「読んで考える」のではなく「見てわかる」ようになる、と記事は書いています。見た目を整える話ではなく、選択肢の情報設計の話として読める記事です。

例はどれも具体的です。フォント名の一覧は、各 option をそのフォントで表示すれば option がそのまま見本になります。「(GMT+09:00) Tokyo」のようなタイムゾーンは、各都市の現在時刻と昼か夜かを並べれば、頭のなかで時差を足し算しなくて済みます（ここだけ `Intl.DateTimeFormat` のために JavaScript を使います）。配送方法は、ラジオボタンの文章に埋もれていた到着日と料金を option 内の grid で列にそろえ、1つの欄で見比べられるようにしています。

同じ名前の同僚が2人いて、いつも役職で見分けていた、という経験から、名前の下に役職と部署を出す例もあります。別の部署の人の顔は知らないことが多いので写真は思ったほど役に立たない、という指摘は現場の感覚に近いものです。承認が必要なチームにだけバッジを付ける例は、選んだあとで知るはずだった結果を、選ぶ前に伝える工夫になっています。

実装の面では、キーボード操作、文字入力による移動、フォームの送信、`required` やバリデーション、アクセシブルなロールがすべてブラウザの select のまま残ります。自前でコンボボックスを作るよりずっと安全です。一方で、iOS のホイールや Android のシートのように、親指で操作しやすく各 OS のアクセシビリティ機能に合わせたピッカーは使えなくなります。そのため記事では、ポインタを細かく動かせる環境か、ある程度の画面幅のときだけ有効にする書き方を示しています。

対応していないブラウザでは普通の select になり、option の文字だけが表示されます。だからこそ「Ahmed Mostafa, Accountant · Finance」のように、文字だけでも意味が通るように書いておくことが唯一の条件になります。デモでは、装飾版では隠れる区切りの span を入れて、素の表示でも文として読めるようにしています。「ユーザーがいちばん迷っている select を探し、本当に知りたいことを option に入れる」という締めの提案は、すぐにでも試せる内容です。

### [Overriding Heading Levels With the headingoffset HTML Attribute](https://blog.master.dev/overriding-heading-levels-with-the-headingoffset-html-attribute/)

> **出典**: Frontend Masters Blog | **公開日**: 2026-11-02 | **カテゴリ**: css

**3行まとめ**
- Firefox Nightly 153 にフラグ付きで入った `headingoffset` 属性は、配下の見出しレベルに指定した数を足す仕組みで、`<h1>` のまま h3 として扱わせることができます
- 入れ子にすると値が足し合わされ、レベルは9が上限です。`headingreset` を付けると外側の影響を切れるので、dialog や aside のなかの見出しを独立させられます
- 見た目を新しいレベルに合わせるには、要素名ではなく計算後のレベルで選ぶ `:heading()` 擬似クラスを使います

**詳細解説**

コンポーネントのなかに `<h1>` を書いておき、置く場所によっては h2 として扱いたい、という場面はデザインシステムでよくあります。いまは props でレベルを渡すのが普通ですが、`headingoffset` は HTML の側でそれを解決する方法です。HTML 全体を自分で書けない CMS やテンプレートの組み合わせで、見出しの階層が崩れているのを直す手段にもなり得ます。

計算はシンプルで、`<div headingoffset="3">` のなかの `<h1>` は見出し4、`<h2>` は見出し5になります。入れ子にした値はすべて足され、見出し自身に付けた値も加わります。値は0〜8で、結果のレベルは9で頭打ちです。`headingreset` は外側からの足し算を打ち消しますが、同じ要素に付けた `headingoffset` は効いたままになります。

`aria-level` との違いも整理されています。`aria-level` は見出しのレベルを直接上書きし、`headingoffset` は積み重ねで決まります。どちらも上限は9です。結果は DevTools のアクセシビリティパネルで確かめられるので、スクリーンリーダーに伝わるレベルを確認しながら使えます。

スタイルの面では、`h3 { }` のような要素セレクタは `<h1>` のままの要素には当たりません。そこで `:heading(3)` のように計算後のレベルで選ぶ必要があります。見出しのスタイルを要素名で書いているデザインシステムでは、セレクタの書き方から見直すことになるでしょう。

まだ Firefox のフラグ付きで、すべてのブラウザで使えるのは先の話です。記事も、値を使いすぎたり見出しから遠い祖先に付けたりすると階層を追いにくくなるので、控えめに使うとしています。それでも、見出しのレベルを「どこに置かれたか」で決める考え方は、実現しなかった HTML5 のアウトラインアルゴリズムに近いものです。コンポーネントの作り方に関わる仕様として、早めに知っておくと役に立ちます。

### [Useful @custom-media Presets](https://blog.master.dev/useful-custom-media-presets/)

> **出典**: Frontend Masters Blog | **公開日**: 2026-10-29 | **カテゴリ**: css

**3行まとめ**
- メディアクエリに名前を付けて使い回せる `@custom-media` で、入力方式、100px 刻みのブレークポイント、HDR に対応した画面かどうかの判定をまとめた定義集です
- マウス・タッチ・スタイラス・エアマウス・方向キーの5種類を `hover` と `pointer` の組み合わせで定義し、`any-` 系の条件はあとから重ねて使う、という整理をしています
- 対応はまだ Firefox のフラグ付きだけなので、いまのすべてのブラウザで動く container style query で書き換えた版も載っています

**詳細解説**

画面の大きさから端末の操作方法がわかる時代ではなくなった、というのが出発点です。キーボードとマウスをつないだタブレットもあれば、タッチやペンが使えるノートPCもあります。そこで、ブレークポイントとは別に「主な入力手段は何か」を判定するクエリを用意しよう、という提案です。ひとつ前の select の記事でも、マウス環境だけで装飾版を有効にする書き方が出てきました。こうした条件をプロジェクト全体で同じ名前で使えるのが `@custom-media` のよさです。

入力方式の定義は、`(hover: hover) and (pointer: fine)` がマウス、`(hover: none) and (pointer: coarse)` がタッチ、`(hover: none) and (pointer: fine)` がスタイラス、という組み合わせです。間違えやすい点として、`(any-hover: hover) and (any-pointer: fine)` は「マウスがある」という意味にはならない、と説明しています。2つの条件が同じ入力手段を指しているとは限らないからです。そのため主な入力手段を基準にし、`any-` 系は「タッチ端末だがホバーもできる（マウスをつないだ iPad など）」のようにあとから重ねる使い方を勧めています。

ブレークポイントは、statcounter の画面解像度の統計をもとに、360px から 1560px まで 100px 刻みの「以上」で並べています。「以下」と組み合わせれば範囲も指定できますが、範囲ごとに名前を付けると種類が増えすぎる、という柔軟さとの兼ね合いにも触れています。HDR については、`(dynamic-range: high) and (color-gamut: p3)` の両方を満たさないと HDR の画像や動画がくすんで見えるので、2つをまとめた定義を用意しています。

いま使える代わりの書き方として、`:root` でメディアクエリに応じてカスタムプロパティを立て、`@container style(--touch)` で判定する方法が紹介されています。ただし `:root` 自体にはこの方法でスタイルを当てられないことや、container query とメディアクエリを1つの条件にまとめられないことなどの制約があります。PostCSS のプラグインを使って、今のうちから `@custom-media` の書き方にそろえておく方法もあります。

ブレークポイントの刻み方は記事自身も「主観的」と言っていて、好みが入る部分です。それでも、デザインシステムのトークンとしてメディアクエリを持つときに、名前を「スマホ・タブレット・PC」ではなく入力方式や幅で付ける、という考え方は参考になります。

### [What should you put on a dynamic custom social media card image?](https://blog.master.dev/what-should-you-put-on-a-dynamic-custom-social-media-card-image/)

> **出典**: Frontend Masters Blog | **公開日**: 2026-10-27 | **カテゴリ**: css

**3行まとめ**
- ユーザーの投稿や商品ページのように数が多く、手で画像を作れないページの OGP 画像に、何を載せるとよいかを考えた記事です
- Discord、Slack、Bluesky、iMessage、LinkedIn、X など9つのアプリで、URL、サイト名、ファビコン、タイトル、説明、大きな画像のどれが表示されるかを一覧にしています
- タイトルや説明はほとんどのアプリがすでに表示しているので画像に重ねる必要は薄く、ロゴやそのページならではのデータ（GitHub のスター数など）を載せるほうがいい、という結論です

**詳細解説**

CodePen の Chris Coyier さんが、Pen の共有画像をどうするか考えるなかで書いた記事です。リンクを貼ったときにカードとして展開される表示は「unfurl」と呼ばれ、OGP や `twitter:` のメタタグで中身を指定します。ただ、何がどう表示されるかはアプリ次第で、ユーザーの設定や管理者の判断で展開そのものが止められることもあります。

記事の中心は、各アプリの表示を「あるか、ないか」で並べた棚卸しです。たとえば iMessage は URL を隠してカードに置き換え、X はタイトルを画像の上に重ね、Slack は画像を小さな正方形に切り抜きます。サイト名を出すアプリと URL を出すアプリがあり、最近は URL を出すほうに寄っているようです。`<title>` にほかのサービス名を書いてなりすますことはできても、実際の URL はごまかせないからではないか、という推測も添えられています。

そこから出てくる判断は、画像のなかでタイトルや説明を繰り返さない、URL も載せない、という引き算です。代わりに、ファビコンを出さないアプリが多いのでロゴは画像に入れる価値がある、そのページならではのデータを載せるとカードごとに違いが出る、としています。いいねの数、レビューの平均、株価のチャート、曲の波形、割引率などが例に挙がっています。数字が0や小さいときは出さない、といった出し分けができるのも、動的に作る場合の強みです。

UXエンジニアの視点では、OGP 画像は「自分のサイトの外で表示される UI」だと考えると整理しやすくなります。表示する側の仕様は変わりますし、スマホでは 1200×630 の画像もかなり小さく表示されるので、細かい文字はそもそも読めません。Next.js の `opengraph-image` や Cloudinary の URL パラメータなど、作るための道具はそろっています。残る仕事は、何を載せるかを決めることです。

なお、一覧は記事を書いた時点の観察で、各アプリの表示はこれからも変わります。記事も、こだわるならすべてのアプリで実際に試すとよい、としています。結論は「そのページについて見せられるいちばんおもしろいもの、多くの場合は本物の画像を。文字は少なめに」で、CodePen では10年以上、保存のたびに撮る Pen のスクリーンショットをそのまま使ってきたそうです。

### [Modal・Side panel・専用ページの使い分け：8つのデザインシステムとガイドラインを混ぜずに比べる](https://zenn.dev/lilpacy/articles/modal-side-panel-page-design-systems)

> **出典**: Zenn designsystem | **公開日**: 2026-10-31 | **カテゴリ**: design-systems

**3行まとめ**
- Apple HIG、Material、Carbon、Atlassian、USWDS、GOV.UK、NN/g、WAI-ARIA APG の8つの資料から、Modal・Side panel・専用ページの使い分けの条件を、出典を付けて1つずつ比べています
- 背後を覆うかどうかは見た目ではなく「作業中に背後の何を見る必要があるか」で決まる、という点はほぼすべての資料で一致していました

### [Zod の契約で BE と UI のずれをテストし、振る舞いまで守る Schema-Driven UI](https://zenn.dev/dress_code/articles/fe01d8baae2aa8)

サイドバーの問題は、メモ化の落とし穴としてわかりやすい例です。TanStack Router の `useMatchRoute()` は URL が変わると再レンダーを起こしますが、返す関数は `[router]` だけに依存しているので参照が変わりません。しかもその関数は、呼ばれた時点の現在地をルーターの内部から読みます。Compiler は「参照が同じ関数を同じ引数で使っている」と判断して判定関数と子の JSX を使い回し、その結果、子ページに移ってもグループが開かないままになっていました。記事は Compiler の変換後のコードとライブラリのソースまで示して、この流れを1つずつ追っています。

直し方は、`"use no memo"` を付けた数行のラッパーフックで、レンダーのたびに新しい関数を返すものです。サイドバーのコンポーネント自体は最適化されたままにできます。修正済みの TanStack Router に上げればラッパーを外せる、という次の手順まで書かれています。

React Hook Form のほうは、3つの仕組みが重なって起きていました。`register` 関数は常に同じ参照ですが、呼んだ結果に含まれる ref コールバックは毎回新しくなります。オプションなしの `reset()` は登録済みのフィールドの参照を捨て、次のレンダーで `register()` が呼び直されることを前提にしています。ところが Compiler が呼び出しを省くので ref コールバックが呼び直されず、ダイアログが閉じるアニメーションのあいだ、入力欄に古い値が残りました。閉じきれば DOM ごと消えるので影響は小さかったものの、画面に残り続けるフォームなら送信や値の取得ができなくなるところだった、という指摘は見逃せません。

UXエンジニアの目で見ると、テストの失敗を見つけたあと、実際にブラウザで操作して「ユーザーにどう見えるか」まで確かめているのがいいところです。サイドバーは現在地が見えなくなる問題、ダイアログはアニメーション中だけの問題、と影響の大きさを分けて判断しています。TanStack Table には先に `"use no memo"` を付ける、`watch()` を `useWatch()` に置き換える、といった予防策も紹介されているので、Compiler の導入を考えているチームはそのまま確認リストとして使えます。Lint を通っていてもこの種の不具合は見つからなかった、という点も覚えておきたいところです。

### [@mizchi/mutator で vitest の mutation test をする](https://zenn.dev/mizchi/articles/introduce-mutator)

AI との組み合わせを前提にしているところも今らしい点です。`--reporter agent` を付けると、生き残った mutant と、それが属する関数、関連するテスト、穴の種類を JSON で渡せるので、エージェントにテストの補強を任せられます。一方で、どんな入力でも振る舞いが変わらない mutant もあるので、その場合は理由を付けて記録し、スコアを上げるためだけのテストを足すより先に、その変更が仕様として観測できるかを確かめるよう勧めています。

実務への示唆としていちばん重いのは、「本番の調査の前に合成ユーザーで予備調査をする」という使い方への警告です。本物らしく見えるのに評価が2段階も高い結果が出ると、関係者が「もう十分よい」と判断して本番の調査をやめてしまうおそれがある、と書いています。目標値や業界平均との比較、評価のグレードの報告のように、点数の水準で判断する場面では使えない、という線引きがはっきりしています。

一方で、どの製品のほうがよいか、どの人がより満足しているかといった大まかな区別は、ある程度できていました。今後は、補正の方法や、ツインの作り方、元にする質問の違いによる影響を調べる予定だそうです。AI で UX リサーチを速くしたいという要望は強いので、使ってよい場面と使えない場面を数字で示してくれる研究として、続きも追っておきたいところです。

### [Using AI To Find Usability Problems: Examining Task Failure](https://measuringu.com/using-ai-to-find-usability-problems-examining-task-failure/)

> **出典**: MeasuringU | **公開日**: 2026-10-07 | **カテゴリ**: ux-research

**3行まとめ**
- ユーザビリティテストの動画から問題を見つける作業を、経験の長いリサーチャー1人と ChatGPT・Gemini（4回ずつ実行）で比べた連載の3本目で、今回は参加者がタスクに失敗した動画を使っています
- リサーチャーが見つけた11件のうち8件は AI もどこかで見つけましたが、AI だけが挙げた6件はすべて、問題とはいえない出来事か、実際には起きていない出来事でした
- 3本の動画を通すと AI の指摘の約48%が誤りで、人が見落とした本物の問題を AI だけが見つけたのは2%にとどまります

**詳細解説**

題材は、PetSmart のサイトで犬のトリミングの予約を進めるタスクです。参加者は正しい入口から入りましたが、犬か猫かを選ぶボタンの表示が遅れたので先に年齢を選び、そのあと犬を選んだら年齢の選択が消えていたことに気づきませんでした。犬種のプルダウンでは「入力して絞り込めるのか」と迷い、予約ボタンを押すたびに年齢や店舗の選択を求められ、最後はメニューを下までスクロールせずに、1つ上にある高いサービスを選んで失敗しています。

比べ方は「any-2 agreement」という指標で、2つのリストに共通する問題の数を、どちらかに含まれる問題の数で割ったものです。人同士では50%が平均的とされていて、今回は ChatGPT が47%、Gemini が39%でした。ただし AI だけが挙げた問題は、テストという状況のせいで起きただけの出来事（タスクの指示を何度も見返した、など）か、そもそも起きていない出来事でした。Gemini は「表示されていないはずの正解のサービスを通り過ぎた」「存在しない『もっと見る』を押した」と書いています。

一方で、人だけが見つけ、どちらの AI も見落とした問題もあります。ボタンの表示の遅れが一連の失敗の始まりだったことや、プレースホルダーの「breed」の上に入力できることが伝わっていなかったことです。どちらも、画面の変化と参加者のためらいを合わせて読まないとわからない問題で、UI の状態の変化に関わるものは AI には見えにくいようです。

結論は厳しく、半分近くが誤りで、人が見落とした問題を AI が見つけることもまれなら、専門家が確かめる手間を考えると AI を入れる価値は低い、としています。ただしこれは、この2つのモデルとこのプロンプトでの結果で、比べたのは動画1本ずつ、評価者も1人です。AI の結果は実行ごとにばらつくので、何度か回して一致するものだけを残すのが、人が見る前の実用的なふるい分けになる、とも書いています。

UXエンジニアの立場では、セッション動画の要約や分析を AI に任せる仕組みを作るときの目安になります。ひとつ前のデジタルツインの研究と合わせて読むと、AI は「それらしい結果」を出すことは得意でも、その中身を人が確かめる前提はまだ外せない、という同じ結論に行き着きます。次は問題が起きなかった動画で試す予定で、ユーザーを喜ばせるように作られた AI が「問題なし」と言えるかを確かめるそうです。

### [Participant Panels: Why Research Teams Build Them (and When They Should Buy Instead)](https://medium.com/researchops-community/participant-panels-why-research-teams-build-them-and-when-they-should-buy-instead-157b1b8e4060)

### [Making Failure Diagnosis Reliable with Pensive AI](https://netflixtechblog.com/making-failure-diagnosis-reliable-with-pensive-ai-6b0811a1c015)

> **出典**: Netflix Tech Blog | **公開日**: 2026-10-26 | **カテゴリ**: engineering

**3行まとめ**
- Netflix のデータ基盤で、失敗したジョブのログから原因となるエラーを抜き出し、診断と対処を提案する仕組みに LLM を組み込んだ話です
- モデルにはエラーの最初と最後の行番号だけを答えさせ、表示する文はもとのログから切り出すことで、速さと費用を抑え、ありもしない文が出てくることも減らしています
- 時間のかかる診断を画面に流すとき、毎回それまでの全文を送る、接続が切れても生成を続ける、同じ失敗には誰が開いても同じ診断を返す、といった設計をしています

**詳細解説**

Netflix では、多い日には1日に約10万件のジョブが失敗します。もともと正規表現と手書きのルールでエラーを分類する Pensive という仕組みがありましたが、3か月で約700万件の分類のうち半分ほどが「不明」に入っていました。そこで、うまく動いているルールは残したまま、その周りに AI を足して範囲を広げたのが Pensive AI です。AI によるエラーの抜き出しは、今ではすべての失敗をカバーしています。

本題はデータ基盤ですが、AI の機能を画面にどう出すかの部分は、UI を作る人にもそのまま参考になります。診断には数十秒から1分かかるので、生成しながらサーバーからイベントで送り、画面側は WebSocket で受け取ります。各イベントにはそれまでに生成した全文が入っていて、多少重複しても、画面側でつなぎ合わせる処理が要らず、イベントが抜けても次のイベントで表示が直ります。生成は接続と切り離されていて、画面を離れても続き、結果はキャッシュに残ります。SPA のなかでは、ストリームを画面やコンポーネントのライフサイクルから切り離して持っているので、ページを移動しても途中の回答が止まりません。

診断は自動では作らず、ユーザーが開いたときだけ作ります。ほとんどの失敗は誰にも開かれないからです。そして診断の単位を「開いた人」ではなく「失敗した1回の実行」にしているので、同じ失敗を調べる人は全員同じ診断を見ます。画面で作った診断が MCP 経由の問い合わせにもそのまま返るのも、この設計のおかげです。AI の回答を人ごとに変えるか、対象ごとに固定するかは、体験の一貫性と費用の両方に関わる判断で、ここではその選び方の理由が説明されています。

品質の守り方も具体的です。既存のルールが拾えていたエラーを AI も拾えているかを LLM の判定で確かめる、抜き出したエラーがそれだけで意味を持つかを別の判定で見る、データ全体で頻繁に出るだけのノイズの行を探す、レイテンシを記録する、の4つを PR ごとの CI で回し、基準を下回るとマージできません。ログは7〜30日で消えるので、評価に使った入力をそのまま保存しておく工夫もあります。低評価のボタンが押されるたびに Slack に通知が飛び、そのときの入力と出力の記録にすぐたどり着けるようにしています。

効果の数字としては、Pensive AI を使わなかった失敗では、ログを手作業で探す操作が321%多かったとしています。ただしこれは観察による比較で、因果関係を示すものではない、と記事自身が断っています。「AI を使った機能の信頼性は、モデルの周りの仕組みから生まれる」という締めの考え方は、AI の機能を作るチーム全般に当てはまります。
