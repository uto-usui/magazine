### [Component testing: a practical guide for frontend developers](https://storybook.js.org/blog/component-testing-a-practical-guide-for-frontend-developers/)

> **出典**: Storybook Blog | **公開日**: 2026-08-31 | **カテゴリ**: design-systems

**3行まとめ**
- コンポーネントを1つずつ実ブラウザで描画し、ユーザーと同じ操作をして振る舞いを確かめる「コンポーネントテスト」の入門ガイドです
- 描画テスト、インタラクションテスト、モックとスパイの3つの手法を、Storybook の実例コードで順に示しています
- AI エージェントがUIを書く時代には、テストが「ガードレール」、ストーリーが「文脈」の2役を担うと位置づけています

**詳細解説**

出発点は、UIテストの板ばさみです。E2E テストは実際のユーザー操作に近いぶん信頼できますが、遅くて不安定で、特定の状態に持ち込むのが大変です。ユニットテストは安くて速い反面、エミュレートした DOM の上で動くので、画面が本当に動くかどうかはあまり分かりません。コンポーネントテストはその間に入り、実ブラウザで動かしながら、小さく速く安定したテストとしてユニットテストの隣に置ける、というのが記事の主張です。

特徴として4つが挙げられています。アプリの残りから切り離して動かす「分離」、ボタン1つからページ全体まで扱える「範囲」、エミュレーションではなく実ブラウザで動く「環境」、そして QA チームではなくフロントエンド開発者が書いて保守する「担当」です。分離は強みであると同時に限界でもあり、システム全体のつながりは確かめられない、と正直に書かれているのは好感が持てます。

例として出てくるのは、タイトル入力、`getUsers()` で候補を取ってくる招待者ピッカー、送信ボタンを持つ `EventForm` です。まず `export const Default: Story = {}` だけで、描画できれば合格のスモークテストになります。次に `play` 関数で送信ボタンを押し、「Title is required」が出るかを確かめます。最後に `.storybook/preview.ts` で `sb.mock(import('../lib/users.ts'))` を登録し、ストーリー側で `mocked(getUsers).mockResolvedValue(...)` を指定して、フォームを最後まで入力させます。`args` に渡しておいた `fn()` がスパイになっているので、`onSubmit` が正しい値で呼ばれたかも検証できます。モックで状態を作り、スパイでロジックを確かめる、という分担が分かりやすいです。

ユニットテスト、結合テスト、E2E テストとの比較表もついています。目安として示されているのは、UIに依存しない純粋なロジック（整形、計算、データ変換）はユニットテスト、描画や操作への反応があるものはコンポーネントテスト、という線引きです。結合テストについては、フロントエンドでは独立した分類としてはあまり扱われず、コンポーネント同士はコンポーネントテストに、バックエンドとの連携は E2E に吸収されている、という整理になっています。

終盤の AI エージェントの話は、今の現場に直結します。エージェントはすでにあるコンポーネントを作り直したり、既存のパターンから外れたり、存在しない API を書いたりします。コンポーネントテストが失敗すると、props の不一致や壊れた操作、アクセシビリティ違反といった具体的なエラーが返るので、エージェントはそれを読んで自分で直せます。さらに、テストのために書いたストーリーは「このコンポーネントは何で、どう使うものか」を構造化して残した記録にもなり、エージェントに渡せば既存部品を使って組み立ててもらえる、という指摘です。

UXエンジニアリングの視点では、読み込み中、エラー、空の状態、バリデーション失敗といった「E2E では再現しにくい状態」を一覧として持てることが大きいと感じます。デザイナーやPMとの確認もその一覧の上でできるので、状態の抜け漏れが話し合いの場で見つかりやすくなります。ただし、見た目の正しさはこのテストだけでは担保できず、記事自身も Chromatic の視覚テストを別の層として紹介しています。Storybook チームの記事なので、ツール選びの部分は割り引いて読み、テストの分類と考え方を持ち帰るのがよさそうです。

### [How to document your design system: best practices & tools](https://storybook.js.org/blog/how-to-document-your-design-system-best-practices-tools/)

> **出典**: Storybook Blog | **公開日**: 2026-08-31 | **カテゴリ**: design-systems

**3行まとめ**
- デザインシステムのドキュメントに何を載せるか、どう保守するか、どのツールを使うかを、開発者向けの層を中心にまとめたガイドです
- Zeroheight の2026年レポートでは、組織全体に広く定着したデザインシステムは38%にとどまり、ドキュメントの充実度が定着と強く結びついていました
- コンポーネントのリファレンスはコードから生成し、ほかの情報はそこへリンクする、という原則を軸にツールを比較しています

**詳細解説**

冒頭の数字が重いです。Zeroheight の2026年版レポートでは、組織全体に広く、または完全に定着しているデザインシステムは38%でした。ドキュメントがなければ、作ったコンポーネントは見つけてもらえず、誤って使われ、次の開発者にゼロから作り直されます。部品の集まりを「ほかの人が採用できるシステム」に変えるのがドキュメントだ、という位置づけです。

載せる内容は5つに整理されています。1つめはコンポーネントで、「今これをどう使うか」に1分以内で答えられることが目標です。用途、props、バリアントと状態（hover、disabled、loading、error）、アクセシビリティの挙動、そしてスクリーンショットではなく実際に触れる描画例とコピーできるコードを載せます。2つめはトークンで、値だけでなく「どういうときにこれを選ぶか」という意図まで書くようにすすめています。3つめはフォーム、ナビゲーション、空の状態などの組み合わせ例、4つめは Do と Don't の対比、5つめは貢献のしかた（提案の方法、「3か所以上で使われている」といった採用基準、レビュー担当、バージョン管理）です。

ベストプラクティスでとくに強調されているのが、コードとの同期です。実物からずれたドキュメントは、ないよりも悪い、つまり積極的に人を誤らせる、とまで書かれています。保守は面倒な作業で、面倒な作業は後回しにされるので、コンポーネント自体からドキュメントを生成して自動で追従させるのがもっとも確実だ、という考え方です。失敗パターンとしても「一度きりのプロジェクトとして扱う」が最初に挙がり、「信頼を失ったとき、デザインシステムは死ぬ」という一文があります。

AI エージェント向けの章もあります。同じレポートでは、AI に期待することの1位がドキュメント生成（57%）だった一方で、AI を使って必要なツールにドキュメントを届けているチームは12%でした。Storybook の MCP サーバーを使って Reshaped というコンポーネントライブラリでUIを生成させたベンチマークでは、使わない場合に比べてコンポーネントの使い方が12.8%良くなり、2.76倍速く、トークンも27%少なかったそうです。ドキュメント化された状態はそのままテストできるストーリーでもあるので、エージェントは自分の出力をテストにかけ、失敗を読んで直せます。

ツール比較は実務で役に立ちます。開発者向けの Storybook、デザイナーやブランド寄りの Zeroheight と Frontify、トークンとデザインからコードへの流れに強い Supernova、1つの基盤にまとめたい大組織向けの Knapsack、汎用ドキュメントの GitBook が並び、料金体系（Zeroheight は編集者1人あたり月59ドルから、Supernova は1席あたり月25ドルから、など）まで書かれています。どれが勝つかではなく、どのツールがどの層を担うか、という見方が示されているのがいいところです。

UXエンジニアリングの視点で持ち帰りたいのは、「コンポーネントのリファレンスはコードから生成し、それ以外はコピーせずリンクする」という原則です。Figma とコードとドキュメントで同じ情報を三重に持つと、いつかどこかがずれます。どれか1つを正とし、ほかはそこを参照する形にしておくと、人にもエージェントにも同じものを見せられます。一方で、コードに寄せるほど非エンジニアが編集しにくくなるという弱点も記事は認めていて、原則やトーンの文章をどこに置くかはチームごとに決める必要がありそうです。

### [How will AI change operating systems? Part 2: Windows](https://newsletter.pragmaticengineer.com/p/windows-and-ai)

> **出典**: The Pragmatic Engineer | **公開日**: 2026-09-22 | **カテゴリ**: engineering

**3行まとめ**
- Microsoft の Windows チームへの取材をもとに、OS がエージェントをどう受け入れようとしているかをまとめた連載の第2回です
- エージェントを「人と区別できる別ユーザー」として扱う ID の仕組み、MCP サーバーを集める ODR、ツールを隔離する MXC が紹介されています
- ローカルでモデルを動かすための Windows ML や、OS に組み込まれた小さな言語モデルにも力を入れています

**詳細解説**

前置きとして、開発者のあいだで Windows の存在感が下がっているという話があります。デスクトップ全体では約63%のシェアがありますが、Gergely Orosz らが X と LinkedIn でとった約9,937件のアンケートでは、Windows は Linux にも抜かれて3位でした。回答者がスタートアップや大手テック企業に偏っていることは記事でも認めていますが、Microsoft が開発者の信頼を取り戻したいと考えている、という前提はよく伝わります。

いちばんおもしろいのは、エージェントを OS 上の「ユーザー」として扱う設計です。エージェントのセッションは何時間も続き、複数のアプリや UI、クリップボードを使うので、OS から見ると人とほとんど区別がつきません。そこで Entra ID を使ってエージェントに ID を持たせ、タスクマネージャーでも人（kirupach）とエージェント（V9-G4）が別ユーザーとして並ぶようにしています。人向けの監視の仕組みがそのままエージェントにも使えるわけです。自分をエージェントとして登録しない不正なアプリに備えて、Defender もエージェントの活動を検出するようになっています。

ODR（On Device Agent Registry）は、ローカルの MCP サーバーを登録し、エージェントが見つけられるようにする仕組みです。エクスプローラーや設定アプリへのコネクタも用意されています。外部の研究者の解析では、ODR はクライアントとサーバーのあいだにプロキシとして入っているようで、やりとりの中身を検査できる位置にいます。ただし、これは Microsoft が認めた情報ではないと明記されています。

MXC（Microsoft Execution Containers）は、エージェントが使うツールを隔離して動かすための仕組みです。ネットワーク、ファイルシステム、UI、実行の制限を JSON のポリシーで書き、プロセス、セッション、WSL コンテナ、軽量な Hyper-V コンテナ、完全な仮想マシンから隔離の強さを選びます。起動の速さと、事故が起きたときの影響範囲のトレードオフを、操作の重要度に合わせて選べるのがポイントです。MXC 自体は隔離を実装せず、Mac なら seatbelt のように各 OS の仕組みを使うので、Windows だけでなく Linux と macOS でも動きます。企業では Intune でポリシーを一括管理できるようになるそうです。

ローカル推論では、Windows ML が DirectX のようにハードウェアの違いを吸収する層を目指しています。ONNX ランタイムを包み、GPU、NPU、CPU ごとの最適化は各ベンダーの Execution Provider が担います。前身の DirectML では最適化をドライバー更新で届ける必要があり、行き渡るまで半年かかっていた、という事情も説明されています。Edge には Aion-1.0-Instruct というモデルが組み込まれていて、Prompt API から数行で感情分析のような機能を作れます。NVIDIA の GPU を積んだ試作の Surface で Qwen を動かし、GitHub Copilot につないで毎秒約40トークン出ていたというデモの話もあります。

UXエンジニアリングの視点では、MXC のポリシー設定が OpenClaw では普通の Windows の設定画面として用意されている点が気になりました。隔離の強さのような難しい判断を、ユーザーが理解できる言葉と画面にどう落とすかは、これから多くのエージェント製品が向き合うことになる課題です。また、エージェント側は自分がどんな制限の中にいるか知らないので、禁止された操作にぶつかったときの伝え方も設計の対象になります。なお、取得できた本文は Windows ML と SLM のあたりで途切れていて、開発者向けの改善、WSL、ARM 対応の章は読めていません。

### [Email has never been free](https://buttondown.com/blog/metered-email)

> **出典**: Sidebar | **公開日**: 2026-09-21 | **カテゴリ**: design

**3行まとめ**
- 1通50セントだった MCI Mail から今日の無料メールまで、メールに「料金」をつける試みの歴史をたどった読み物です
- スパム対策として何度も提案された有料メールは、スパム業者のほうが資金を持っているという単純な理由でうまくいきませんでした
- 結局いま料金を払っているのは、スパム業者ではなく、確実に届けたいまっとうな送り手のほうだという皮肉な結論です

**詳細解説**

メールの初期は、大学や研究所では無料、会社や家庭では高価、という二重構造でした。1979年の The Source は入会費100ドルで1時間あたり約10ドル。1983年の MCI Mail は「新しい郵便」を名乗り、最初の500文字までが1通50セント、以降500文字ごとに10セント、さらに年35ドルのメールボックス料金がかかりました。一方、最初のスパムは1978年、利用者にとっては無料の ARPANET で送られています。DEC のマーケター Gary Thuerk が約400通を送り、推定1,300万ドルの売上につながったそうです。

インターネットと Hotmail、Gmail の登場でメールは無料になりました。ここで紹介される Steve Wozniak の返しが印象的です。「情報は自由であるべきだ。でも、あなたの時間はそうではない」。送るのはほぼ無料で、運ぶコストは無料の受信箱を提供する事業者が負い、受け取るコストは受信者が時間と注意で払う。メールの問題はこの非対称にある、という整理です。

そこから有料メールの提案が繰り返されます。1992年の Microsoft Research による「pricing via processing」は、送るたびに適度に重い計算を課すもので、ビットコインにかなり近い発想です。2003年の Penny Black は、1通ごとに10秒の計算を求めれば、スパム用のコンピューターは1日8,000通までに制限できると試算しました。1996年には USPS が1通22セントのデジタル消印を始め、2009年まで細々と続いています。受信者が「スパムではない」と判断すれば返金される Bankable Postage、画像やリンクを含むメールにだけ課金する Goodmail も登場しました。

どれも広がらなかった理由は、AOL の担当者の言葉に集約されています。「大きな財布を持っているのはスパム業者のほうだ」。お金を課せばスパム業者は払い、計算を課せば機械を増やします。そのあいだ、まっとうな送り手と一般の利用者が、中央集権化したメールの仕組みのコストを負うことになります。紙のダイレクトメールは今も1通50セントから1ドルかけて送られているし、有料の LinkedIn InMail でも迷惑なメッセージは届く、という例が説得力を持たせています。

現在の落としどころは、SPF、DKIM、DMARC によって「身元を明かさない送り手はスパムとみなす」という本人確認に近い仕組みです。そして料金を払っているのは、ニュースレターやアプリの自動メールを送る側です。Amazon SES で1通0.01セント、SendGrid で0.04セントほど。さらに本人確認を通し、実在のクレジットカードと住所を使うこと自体が、スパム業者にとっては越えにくい壁になっています。

UXエンジニアリングの視点では、通知やメール配信を設計するときに「受信者の時間を使っている」という感覚を持ち直すきっかけになります。送信のコストがほぼゼロだからこそ、頻度や内容の判断は送り手の自制に任されています。書き手はニュースレター配信サービスの Buttondown なので、「本気の送り手は払う」という結論には自社の立場も含まれていますが、歴史の読み物として十分楽しめる記事です。

### [Scenarios for our economic future](https://www.anthropic.com/institute/econ-scenarios)

> **出典**: Sidebar | **公開日**: 2026-09-22 | **カテゴリ**: design

**3行まとめ**
- Anthropic の経済チームが、AI が2030年までに米国の GDP、雇用、賃金にどう影響しうるかを3つのシナリオで示したインタラクティブな解説です
- 成長率が通常の2倍程度までなら失業率は過去の範囲に収まりますが、極端なシナリオでは知識労働者の賃金と雇用に大きな影響が出ます
- 読者が自分の予想を入力すると、その予想が導く2030年の経済と、ほかの回答者との比較が表示されます

**詳細解説**

ベースになっているのは、Korinek らによる技術レポート「Economic Scenarios for Transformative AI」（2026年）です。2030年の米国 GDP は、控えめなシナリオで AI がない場合より1.6%増（34.1兆ドル）、大きな変化のシナリオで8.3%増（36.3兆ドル）、極端なシナリオで32.4%増（44.4兆ドル）と見積もられています。どのシナリオでも経済は成長しますが、その成長を誰が受け取るかで景色が変わる、というのが全体を通した論点です。

8月に1万人以上の米国人に聞いた調査もついています。AI の能力、普及、自律性、生産性、転職のしやすさの5問に答えてもらったところ、典型的な回答者の見立ては「大きな変化」に近く、2030年に GDP が約10%増、失業率が約5%という水準でした。約10%の人は、極端なシナリオに近い見方をしていたそうです。

雇用については、知識労働で自動化が進むシナリオほど、職業を変える必要のある人が増えます。記事の例では、プログラマーやコールセンターの担当者が、電気工事士や看護師のような AI の影響が小さい仕事へ移ることになります。職業を丸ごと変えるのは難しく時間もかかるので、移る人が多いほど職探し中の人も増えます。賃金は全体の平均では上がりますが、その上昇は知識労働以外に集中し、大きな変化のシナリオでは知識労働者の賃金はほぼ横ばい、極端なシナリオでは2030年までに10%以上下がります。

もう1つの軸が、労働と資本の取り分です。今は経済が生む1ドルのうち約60セントが労働者に、約40セントが資本に回っています。AI が自動化するタスクが増えると資本の需要が上がり、全員の賃金が上がる場合でも資本側の取り分が増えることがあります。極端なシナリオでは、経済は大きくなるのに労働所得の総額は2030年時点でほとんど変わらない、という結果です。

限界もきちんと書かれています。高性能なロボットが実現する場合、政策対応、景気循環、データセンター建設による需要の効果などは含まれていません。レビューした経済学者からは、個々の労働者を追っていないので失業のコストは粗くしか描けない、AI の影響を受ける職業がそもそも縮小するのか疑問だ、極端なシナリオは思考実験として読むほうがいい、といった指摘があり、今後の版で対応するとしています。

UXエンジニアリングの視点では、中身と同じくらい見せ方がおもしろい記事です。モデルの前提を読者自身に入力させ、その結果とほかの人の回答を並べることで、「予測」を一方的に伝えるのではなく、前提を変えると結論がどう動くかを体感させています。数字の多い研究を一般向けに開くやり方として参考になります。なお、AI 企業自身による試算なので、その立場は踏まえて読むのがよさそうです。

### [Open-Sourcing Rebalancer: A Generic, High-Performance Library for Solving Assignment Problems](https://engineering.fb.com/2026/09/21/open-source/rebalancer-generic-high-performance-library-assignment-problems/)

> **出典**: Meta Engineering | **公開日**: 2026-09-21 | **カテゴリ**: engineering

**3行まとめ**
- Meta が9年以上社内で使ってきた割り当て問題のソルバー「Rebalancer」を Apache 2.0 でオープンソース化しました
- 問題の書き方、メモリ上での持ち方、解き方、デバッグのしかたを分けて設計したことが、使いやすさと規模の両立につながっています
- 1日約4,000万件の割り当て問題を解いていて、公開版にはデバッグ用の Web UI「Rebalancer Explorer」も含まれます

**詳細解説**

割り当て問題とは、「いくつかのもの（オブジェクト）をいくつかの入れ物（ビン）に、制約を守りつつ目的が最適になるように入れる」問題です。Meta では、データセンターへのラックの配置、サービスへのサーバーの割り当て、サーバーへのタスクの配置、ユーザーのトラフィックをどのデータセンターに流すか、といったインフラのあらゆる層でこの形の問題が出てきます。難しさは2つあり、現実のルールを数式に落とすのが大変なこと（使いやすさ）と、NP 困難な問題を商用ソルバーでも解けない規模で扱うこと（規模）です。

Rebalancer はこれを、問題の「記述」と「解法」を分けることで解決しています。記述には3段階の抽象化があります。まず、属性を表す dimension、オブジェクトのまとまりである partition、ビンのまとまりである scope、ビンの使用量を表す utilization という基本の部品があります。次に、それらを SUM や MAX でまとめたり、SQUARE で変換したりする式の API があります。そのうえに、よく使う目的と制約を数十種類そろえた spec の API が乗っています。記事の例では、CPU とストレージの容量制限を `CapacitySpec`、ラックごとにジョブの種類を1つに絞る条件を `GroupCountSpec`、サーバーの使用率の偏りを抑える条件を `BalanceSpec` で書いています。

書いた問題は「式グラフ」という有向非巡回グラフに変換され、そこから2種類の解法を選べます。1つは FICO Xpress、Gurobi、オープンソースの HiGHS といった MIP ソルバーに渡す厳密解法です。ただし最悪の場合、モデルの大きさがオブジェクト数とビン数の積になり、Meta の最大規模の問題はどの MIP ソルバーにも載りません。もう1つの局所探索は、今の割り当てからオブジェクトを少し動かした候補を評価して、もっとも良いものを採用する手順を繰り返します。近傍の大きさはオブジェクト数とビン数の和で済み、評価は並列化されて毎秒数百万回に達します。社内では大規模な問題はほぼ局所探索で、厳密解法で試作してから局所探索へ移す使い方もよくあるそうです。

規模の数字も公開されています。30種類以上の問題の形で1日約4,000万件を解き、26.5万オブジェクト、3,200ビンの問題で P99 が12秒。100万オブジェクトと5,000ビンを超える問題でも平均171秒です。インフラ以外にも、移動時間が短くなるような会議室の割り当て、サポートチケットの担当者割り当て、座席配置に使われています。

いちばん興味深いのはデバッグの章です。問題を書いて解くのが楽になった結果、担当者の時間の大半は「ソルバーがなぜこう動いたのか」を調べることに移りました。そこで、どの制約が効いているのか、制約をゆるめたらどうなるのか、なぜこのオブジェクトはあちらではなくこちらに置かれたのか、といった質問に答える UI を作り、それが今回の Rebalancer Explorer です。

UXエンジニアリングの視点では、ここが一番の学びだと感じます。最適化エンジンのような「中身が見えないもの」を使ってもらうには、答えそのものより「なぜその答えなのか」を説明する道具が要ります。AI エージェントの判断や推薦システムの結果を人に見せる場面でも、同じ問いがそのまま当てはまります。詳しい技術的背景は OSDI'24 の論文にまとまっていて、PyPI からも試せます。

6つの手順は、手元の情報を理解する、足りない情報を集める、問題を定義する、明快でシンプルな解き方を決める、目標を決める、目標に向けて急いで動く、です。途中で新しい情報が入れば3から5をやり直し、これを繰り返します。行ったり来たりしているように見えても、それが過程の一部だと分かっていれば健全な揺れだ、という考え方です。筆者はこの手順を、ほとんどの問題とほとんどのプロダクトに、1日に何度も当てはめているそうです。

いちばん多い失敗として挙げられているのが、3（問題を定義しない）と4（シンプルな解き方を決めない）です。どちらかが抜けると、計画が複雑になり、何をもって成功とするかがあいまいになります。しかも計画を立てている本人にはそのあいまいさが見えにくいので、ほかの人からのフィードバックが大事になる、という指摘は実感があります。筆者は相手の手順の抜けにその場でフィードバックを返し、自分にも同じことを求めています。

締めの「間違えるのが好きだ」という一文も、ただの謙遜ではありません。間違いが分かれば問題の定義がはっきりし、正しい解き方が見つかり、学びが速くなるからです。この手順そのものが間違っているなら変える、とまで書いています。

UXエンジニアリングの視点では、AI で手を動かすコストが下がった今こそ、3と4に時間を使う意味が大きくなっていると感じます。実装がすぐにできると、問題の定義があいまいなまま作り始めてしまいやすいからです。短い文章なので、チームの振り返りで「今回はどの手順が抜けていたか」を話すときの共通の言葉として使いやすいでしょう。

### [Inside Petal: Building the World’s First Petabit-Class Transoceanic Subsea Cable](https://engineering.fb.com/2026/09/21/connectivity/petal-petabit-transoceanic-subsea-cable/)

> **出典**: Meta Engineering | **公開日**: 2026-09-21 | **カテゴリ**: engineering

**3行まとめ**
- Meta がフランスと米国を約7,000km で結ぶ海底ケーブル「Petal」を発表し、大洋横断の距離で初めて1Pbps の容量を実現します
- 1本のファイバーに2つのコアを持つマルチコアファイバーを、初めて大規模に使う海底ケーブルになります
- 2029年の運用開始を予定していて、NEC、住友電気工業、Orange と共同で進めています

**詳細解説**

大陸間のデータ通信の約99%は、海底に敷かれたガラスの繊維を通っています。1Pbps は、世界人口の75%が同時に音楽をストリーミングできるくらいの容量だそうです。Meta はこれまで、ファイバーを8ペア持つ Marea、16ペアの Amitié、24ペアで初めて0.5Pbps に達した Anjana と、ケーブル内のファイバー数を増やす方向で容量を伸ばしてきました。Petal は Marea の5.5倍の容量になります。

容量をさらに倍にする選択肢は3つありました。ファイバーを48ペアまで増やす、L バンドまで伝送帯域を広げる、そして2コアのファイバーを使う、の3つです。Petal は24ペアのまま2コアのファイバーを使い、48ペア相当を実現する道を選びました。2本の0.5Pbps のケーブルを敷くのに比べて、材料や資源、二酸化炭素の排出を大きく減らせるのが利点です。

課題は2つありました。1つは、ファイバーの外径を髪の毛ほどの125µm に保ったまま、減衰を小さくすることです。これは超高純度の合成シリカを使うことで解決しています。もう1つは、コア同士の信号の漏れ（クロストーク）を抑えることで、コアの屈折率を周囲より高く保ち、2つのコアで逆向きに信号を流すことで、ほとんど測れないほど小さくしています。

7,000km のケーブルには、信号を増幅する中継器が約100台必要です。Petal の中継器は、2コアのファイバーをいったん1コア2本に分けて増幅し、また2コアに戻す Fan-In/Fan-Out という仕組みを使い、1つの筐体で96の増幅器を動かします。これにより、消費電力を比例して増やさずに容量を倍にでき、既存の給電設備の上限（18kV）の範囲に収まるので、より高い電圧にした場合に必要になる設備全体の再認定を避けられるそうです。

UXエンジニアリングの視点からは遠い話ですが、ふだん当たり前に使っている「速いネットワーク」がどんな物理的な工夫の上に成り立っているかを知るには、ちょうどいい記事です。とくに「既存の給電設備の制約の内側に収める」という判断は、新しい技術を入れるときに周辺の仕組みを作り直さずに済ませる設計として、ソフトウェアにも通じる考え方です。日本企業2社が中心的な役割を担っている点も興味深いところです。

### [For the Designless](https://newsletter.uxdesign.cc/p/for-the-designless)

> **出典**: UX Collective | **公開日**: 2026-09-21 | **カテゴリ**: design

**3行まとめ**
- デザイナーはアーティストではなく、依頼者のぼんやりした意図に形を与える「商業的な問題解決者」だ、という定義から始まる論考の紹介です
- AI が変えたのはデザイナーの仕事の中身ではなく、「誰が自分でデザインを試みられるか」だと述べています
- 自分でデザインを試みる人を、依頼する手段がない、何を頼めばいいか分からない、手段があってもやる気がない、の3つに分けて考えています

**詳細解説**

UX Collective のニュースレターが冒頭で紹介している論考です。デザイナーの仕事は、依頼者の「なんとなくの雰囲気」や「プロっぽく見せたい」という半端な意図を受け取り、形にすることであり、それは鉛筆でも Photoshop でもプロンプト入力欄でも変わらない、と書かれています。AI によって変わったのは、その仕事を自分で試みられる人の範囲です。

おもしろいのは、その人たちを「the designless（デザインを持たない人）」と呼び、3つの種類に分けている点です。デザイナーに頼むお金や手段がない人、何を頼めばいいかを知らない人、そして手段はあるのにわざわざデザインに手間をかけようと思わない人です。今の AI をめぐる議論は、この3つを区別していないせいで弱くなっている、というのが筆者の主張です。

UXエンジニアリングの視点では、この分け方はデザインツールや生成機能を作る側にとって役に立ちます。手段がない人には安く速く作れることが、何を頼めばいいか分からない人には良い選択肢を示して導くことが、やる気がない人には何もしなくても最低限の品質が出る初期値が効くはずで、それぞれ求める機能が違います。なお、ニュースレターに載っているのは冒頭の抜粋だけなので、3つの種類それぞれへの具体的な提言は元の記事で確かめる必要があります。同じ号には「The death of the deliverable」や、LLM が書くコードの「雑さ」を測る試みなども紹介されています。

### [How Rob Farmer turns half-baked sketches into New York Times covers](https://www.creativeboom.com/work/how-rob-farmer-turns-half-baked-sketches-into-new-york-times-covers/)

> **出典**: Sidebar | **公開日**: 2026-09-21 | **カテゴリ**: design

**3行まとめ**
- New York Times などのイラストを手がけるデザイナー Rob Farmer に、アイデアの育て方を聞いたインタビューです
- 思いついたら5分のラフでも描き留め、Instagram の投稿計画アプリに「未完成のアイデアの列」として並べておくのが習慣です
- 完璧主義のせいで世に出ない良い作品がたくさんある、と作品を共有することの大切さを語っています

**詳細解説**

Rob Farmer はオーストラリアのジーロング出身で、大学に入ったのは27歳のときでした。卒業後すぐにブルックリンのブランドエージェンシーでインターンを始めて3年働き、クライアントワークで思うようにできないもどかしさから、自分の実験的な作品を Instagram に投稿し始めます。クライアントや社内の上下関係、フィードバックの外に自分の作品の場所を作ったことで、「趣味としてのデザイン」と「仕事としてのデザイン」の違いが分かるようになった、と話しています。

制作の流れはゆるく、プレッシャーの少ないものです。アイデアが浮かんだらノートパソコンかメモアプリでラフを描き、スクリーンショットを Instagram の投稿計画アプリに入れておきます。5分の走り書きのこともあれば、1時間でほぼ完成することもあります。この未完成の列がなければアイデアを忘れてしまうし、依頼が来たときにその雰囲気に合うものがすでに列の中にあることも多い、というのが実用的です。制作には、ノイズや乱数といったパラメーターで自然のパターンを表現できる Cavalry というモーションツールを使っています。

最近の気に入っている仕事として挙げているのが、AI とエムダッシュ（—）をテーマにした New York Times Book Review の記事のためのイラストです。元は「エムダッシュのタトゥー」というかなり生煮えのラフでしたが、アートディレクターの Matt Dorfman がその可能性を見抜き、何度も磨かせてくれたそうです。

UXエンジニアリングの視点では、「未完成のアイデアを見える場所に並べておく」という仕組みがおもしろいと感じました。プロトタイプや検証中の UI のアイデアも、形にしきれないまま消えていくことが多いものです。小さなラフを捨てずに一覧で持っておくと、別の案件で急に役立つことがあります。完璧になるまで出さないより、途中のものを共有してほかの人の力で磨いてもらうほうが、良い結果につながるという話でもあります。
