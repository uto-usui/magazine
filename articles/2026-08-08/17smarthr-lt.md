## SmartHR LT大会とは

SmartHR LT大会は、有志のプロダクトエンジニアがDevRelとともに隔月で企画・運営している社内イベントです。プロダクトエンジニアの中から11名の登壇者を募り、5分間の[Lightning Talks（LT）](https://shibuya.pm.org/blosxom/common/lightning_talks.html)を行います。

プロダクトエンジニアの企画ですが、当日は職種によらず社員であれば聴講可能です。配信もしており、現地参加が難しい社員もリモートで楽しめるイベントとなっています。

## 参加者情報

今回の参加者数です。

-   現地参加者：89名（うち登壇者：11名）
-   オンライン参加者：25名
-   懇親会参加者：77名

現地参加者数は、[昨年末の忘年会も兼ねたLT大会](https://tech.smarthr.jp/entry/2026/01/22/100000)に次いで、LT大会の歴史上2番目に多い回となりました！

## 発表レポート

第17回も個性豊かな11名の登壇者が揃いました。失敗からの学びや社内ツールの自作、カンファレンス参加レポートまで、現場の知見が詰まった発表内容をレポート形式でお届けします。

### ドメエキの話をちゃんと聞こう！（qwyng さん）

最初の登壇者は qwyng さんで、「ドメエキの話をちゃんと聞こう！」という発表でした。

詳細は社外秘なのでここには記せませんが、CSVでアップロードできる列数の制限をすり抜けてしまったケースへのふりかえりでした。ドメインエキスパート（ドメエキ）は関連する情報を事前に伝えていたものの、開発チームがそれを検証する必要性に気づけなかったことが原因で、ドメイン知識を持つ人の話を丁寧に聞くことの大切さが共有されました。

失敗の経緯を率直に振り返ったうえで、ドメインエキスパートとは用語を正確にそろえて会話しようという教訓まで示してくれた、学びの多い発表でした。

### bloghrの“真実”（osyoyu さん）

2人目は osyoyu さんの「bloghrの“真実”」という発表でした。

社内向けブログプラットフォーム「bloghr」の紹介と、その裏側にあるデプロイ基盤が語られました。bloghrはリリースから10日間で568人が利用し、131本の記事と2,887件の「いいね」が集まっているとのこと。Reactで構築されており、Slackの #random への通知連携や、何度でも押せる「いいね」機能などを備えています。Notionなどの既存ツールを使わず自社で構築した理由として、書き上がったタイミングで通知できることや、社内専用ならではの「俺たちのもの」という所有感を挙げていました。さらに、デプロイ基盤として Cloud Run で Flux CD 的な体験をめざす  kufu/fleet という仕組みを自作しており、GitHub への push を起点にアプリを手軽にデプロイできる環境を目指していることが紹介されました。

利用データの伸びとともに、内製だからこそ実現できる体験づくりへのこだわりが伝わる発表でした。

### Google Slideをやめたい（nori さん）

4人目は nori さんの「Google Slideをやめたい」という発表でした。

登壇先でネットワークが不安定になり、Googleスライドの画像やフォントが読み込めず困った経験から、オフラインでも崩れないプレゼンテーションツール「SlideHR」を自作した経緯が語られました。当初はPowerPoint形式（pptx）のXMLを生成する方針を試したものの、ファイルの復元時に崩れてしまい断念。最終的にHTML・CSS・JavaScriptと、スライドをRubyで記述するDSLで作り上げ、スライドと同期するプレゼンタービューまで実装したとのことです。一方で、Rubyのコードの中に複数行のテキストを書く記法には書きづらさが残っており、今後さらに改良していきたいと締めくくりました。

身近な不便を自作で解決する行動力が印象的で、ツールの今後の進化も楽しみになる発表でした。

### RubyistがLaravel Live Japan行ってきましたレポ（mktakuya さん）

5人目は mktakuya さんの「RubyistがLaravel Live Japan行ってきましたレポ」という発表でした。

5月26日から27日にかけて開催された、PHPのWebアプリケーションフレームワーク Laravel の国際カンファレンス「Laravel Live Japan」への参加レポートでした。スライドやトークはほぼ英語で進行されるなか、Laravel作者の Taylor Otwell さんによる基調講演ではLaravel専用PaaSの「Laravel Cloud」などが紹介され、「この時代にフレームワーク特化のPaaSを出す覚悟よ」と印象に残ったそうです。

トークと同じくらい熱がこもっていたのが「廊下」（Hallway Track）と懇親会の話です。異なるフレームワークの開発者と会話するには「ActiveRecordではなくRDBMSのレイヤで、SidekiqではなくRedisの言葉で話す」というように一段レイヤを下げる必要があり、それが頭の体操としてもオススメとのこと。5分では語り尽くせなかったぶんは、Laravel Live JapanのLTでご登壇された大倉さん（Kaigi on Rails発起人）との感想戦として[ポッドキャスト](https://yuru28.com/350)で公開されています。

英語とPHPという「二重の意味で知らない言語」のカンファレンスでも意外と理解でき、対比によってRailsへの理解も深まるという、異文化交流の楽しさが伝わる発表でした。

### はじめまして、入社改善チームです（yasuda さん）

6人目は yasuda さんの「はじめまして、入社改善チームです」という発表でした。

2026年6月1日に「横断改善チーム」から改称したばかりの「入社改善チーム」の自己紹介LTでした。チームのミッションは「入社まわりをシームレスにする」こと。入社時にはアカウント招待・雇用契約書の配付・資格情報の回収などやることが多く、この体験を担当者にも従業員にも迷わないものにするのがチームの仕事です。ポイントは「機能カットではなく業務カット」で設計するところだと語られました。

その中核となるのが、複数画面に分かれていた招待まわりの操作を1つの画面で一気通貫にした「招待管理」機能です。発表の2日前には資格情報の連携機能をリリースしたばかりで、今後は従業員の属性に応じた招待テンプレートの自動選択など、「ミスを減らして現場に運用を任せられる状態」を目指した開発が続きます。

目指すのは「リテラシーが高くなくても、誰でも迷わず入社手続きができる」状態とのこと。SmartHRの入口となる領域を業務フロー全体から捉え直していく、今後の展開が楽しみな発表でした。

### 年末調整を乗り越えるぞ！（HIGUCHI.Takashi さん）

8人目は HIGUCHI.Takashi さんの「年末調整を乗り越えるぞ！」という発表でした。

年末調整の繁忙期に向けて、SREと年末調整機能の開発チームが協力して取り組んでいる負荷試験プロジェクトの報告でした。k6を用いた負荷試験基盤を整備し、数千人規模でユーザーが重複しないシナリオ設計（年調アンケートはユーザーが被るとエラーになるというドメイン特性への対応）や、Critical User Journey（CUJ）ベースのシナリオ作成を、feature開発と並行して計画的に進めたそうです。

目標は2250rpsに対して、初回の結果は500rps。しかしその場でAIに投げて試験→改善→再実施のサイクルを2時間以内に回し、同日中に1000rpsまで改善できたとのこと。500rps時点でデータベースのCPU使用率が100%に達して性能限界が判明するなど、「10月になってから気づいたら遅かった」問題を今の時期に発掘できたのは大きな成果です。

年末の高負荷を見据えて計画から実行まで1か月で走り切ったスピード感と、負荷試験基盤を社内に広げていこうという姿勢が印象的な発表でした。

### プロジェクト投資分析を利用してチームの意思決定を最適化する（ykyuki21さん）

9人目はykyuki21さんによる「プロジェクト投資分析を利用してチームの意思決定を最適化する」という発表でした。

内容は、Findy Team+ のプロジェクト投資分析を利用して開発チームがどのような活動にどれだけのリソースを割いているのかを可視化するというものでした。 実際にデータを計測してみると、8割弱を新機能、1割強を品質保証に割いている反面、機能改善にはほとんどリソースを割けていないことがわかりました。 チームでは、この定量的なデータを今後の意思決定の支えとして活用していくとのことでした。

開発生産性にリソースを投資した後に、開発タスクの生産性が向上しているかといった時系列変化を可視化しても面白そうだと感じました。 また、AI登場前後での変化や異なる開発フェーズのプロジェクト間で比較してみるなど、さまざまな切り口で分析してみるとさらに面白い知見が得られそうだと感じました。

### 音の次は「画像」がくる（udzuraさん）

10人目はudzuraさんによる「音の次は「画像」がくる」という発表でした。

RubyKaigiなどで「音が鳴る」発表が増えてきたという背景が語られ、あえてここでは「画像」に注目する旨が話されました。具体的には「画像の波（空間周波数）」を分析してみたという内容でした。 実際に、自然画像、美術写真、AI生成画像の3つに関し周波数からスペクトラム画像を生成し、比較したところ、自然画像は低周波成分が多く、AI生成画像は中周波成分も満遍なく含んでいる傾向にあるのでは？　という分析結果になったそうです。 美術品の画像は自然画像に近い低周波成分を主としつつ、作家により特徴的な分布が見られることもわかりました。

なかでも、点描画法で有名なジョルジュ・スーラの「グランド・ジャット島の日曜日の午後」が低周波に集中した分布を示したという結果は非常に興味深いものでした。 また、AI生成された画像の周波数成分が中帯域にまで満遍なく分布しているという事実は、「AI生成画像は細部まで細かく描き込まれすぎていて、どこに目を向ければ良いか注意が散漫になりがち」という、普段私（mashi6n）が抱く主観的な印象と一致しており納得感のあるものでした。

### 「成果、出た？」に答えるための2つの備え（shooenさん）

11人目はshooenさんによる「「成果、出た？」に答えるための2つの備え」という発表でした。

プロダクト開発において、リリース後に成果を正しく計測するための「2つの備え」について語られました。 具体的には (1) 成功条件（成果の指標）を設定する、と (2) リリース後の観測（指標の測定期間とその後の判断分岐）を決めておく、というものでした。 事前にこれらを定義しておくことで、「良かれと思って作った機能が実際にターゲットユーザに喜ばれているか」を継続的に把握できるようになり、次の機能開発へ適切に繋げていくことができるという実践的な内容でした。

「成果、出た？」という頻出でありながら答えるのが難しい問いに対して、さまざまな開発プロジェクトで活用できる汎用性の高さが印象的でした。 特に、成功条件を満たせなかった理由までヒアリングに含めることで、「機能自体に問題があるのか、別の要因があるのか」を判断することができるという視点は非常に勉強になりました。
