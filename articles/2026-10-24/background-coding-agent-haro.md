バクラク事業部 Platform Engineering 部では、社内のプロダクト開発を支援する、クラウド上で動作する Coding Agent “haro” を開発しています。 [Ramp 社の Inspect](https://builders.ramp.com/post/why-we-built-our-background-agent) などと同じく Web UI や Slack 上から呼び出すことができ、バクラクを開発するために必要なものが揃った環境が立ち上がって、そこで Claude Code など Coding Agent が動作します。

## モチベーション

クラウド型の Coding Agent をわざわざ内製したモチベーションですが、大きくは「ローカル開発の限界」と「自社コードベースを動かすには既製品だと足りない」の2つです。

バクラクシリーズはありがたいことに多くのお客様に使っていただき、新規プロダクトも順調にリリースを重ねています。 これらプロダクトのほとんどが1つの monorepo 上で開発されており、コードベースも勢いよく成長しています。

コードが多いことでシンプルにビルドなどが重くなるのもそうですが、例えば Language Server を起動するようなエディタや Coding Agent のプラグインなどを利用していると、びっくりするくらいのメモリを持っていかれます。 Coding Agent 時代なので git worktree を利用した並列開発もするのですが、人間の認知よりも先にメモリが限界を迎えている状況です。 [ローカル開発用のプロセスマネージャーを内製](https://speakerdeck.com/izumin5210/layerx-go-5)したり[高速な gopls を自作したり](https://docs.google.com/presentation/d/1ljMuOUvsg4IAzqFyGWUHCDZ1geA5dqjOTeu72G3I6-c/edit?usp=sharing)と工夫はしていますが、ローカルマシンのリソースに上限がある以上は限界があります。

-   [コンパウンドプロダクト開発のためのローカルプロセスマネージャー再発明](https://speakerdeck.com/izumin5210/layerx-go-5)
-   [速いgoplsの作り方](https://docs.google.com/presentation/d/1ljMuOUvsg4IAzqFyGWUHCDZ1geA5dqjOTeu72G3I6-c/edit?usp=sharing)

また、この規模の monorepo をリモートで快適に動かすであるとか、従来のローカルでのプロダクト開発と同じように内製ツールや環境をリモートで利用しようとすると、既製品だと足りないところも出てきます。 もし機能的に足りたとしても、開発者体験として最適なものになるかはまた別の話です。

少なくとも私たちの規模・コードベースでは、汎用の既製品だけで最高の開発体験を得るのは難しいと感じています。 逆に、自前の仕組みを作ることで自社のプロダクトラインナップ・コードベース・開発文化にフィットさせたものにすることができるはずです。 Agent も人間もともに普段から認知負荷が高い状態にある現代において、仕組み側で負荷を軽減できる価値は高いでしょう。 幸いにして、 現代では Coding Agent によってこのような仕組みを作る負担は劇的に小さくなっています。

## 構成

Agent を制御するアプリケーションは TypeScript で実装されており、 Temporal Workflow から AI SDK の `HarnessAgent` 経由でクラウド上の環境内にある Coding Agent Harness （Claude Code等）を操作しています。 環境は EKS 上で動作し、 Custom Resource Definition（CRD） と Custom Controller でライフサイクルを管理しています。 Agent Loop を TypeScript（Temporal Workflow）, 環境を Go（Kubernetes）でそれぞれ管理するイメージです。

![](https://cdn-ak.f.st-hatena.com/images/fotolife/i/izumin5210/20261021/20261021224435.webp)

haro の簡易アーキテクチャ図

haro 上の Agent には Slack, Notion, Linear, Datadog, Snowflake など社内で利用している様々なサービスの MCP（Model Context Protocol） が接続されており、利用者は面倒な鍵管理・接続先管理をすることなく、普段の自分のアカウントでこれらサービスの情報を Coding Agent から安全に利用することができます。

他にも内製している社内サービスの MCP も繋がっています。 例えば「Coding Agent からアップロードされた HTML アーティファクトを表示でき、かつそれの任意箇所にコメントをつけることができる」という謎の社内プロダクトがあります。 haro からそれに接続することで、複雑な設計タスクの結果を図解豊富な HTML に起こし、そこにコメントしたものをさらに AI に読ませることで、効率的な設計ループを回すことができるようになっています。

![](https://cdn-ak.f.st-hatena.com/images/fotolife/i/izumin5210/20261021/20261021224532.png)

AI Agent で生成した HTML 上にコメントできる謎の社内プロダクト

他にも Service Console という 内製のInternal Developer Platform の MCP なども繋がっており、プロダクト開発・運用の自動化にも活用できるようになっています。

## 利用状況

haro の開発チームでは最初の KPI として「リポジトリ全体の Pull Request(PR) のうち haro 経由で作られたもの」の数を、普及率を表す間接的な指標として追っています。 現行バージョンの開発開始が2026年7月半ばですが、10月時点で1日の PR のうち55〜60%程度、数にして200件弱の PR が haro 上で作成されています。 利用者も増えてきており、10月時点で58名と、バクラク事業部エンジニアの半数を超えました。

![](https://cdn-ak.f.st-hatena.com/images/fotolife/i/izumin5210/20261021/20261021224646.png)

利用者数・セッション数・PR数の推移

チームによっては PR のうち 87% を haro で作成しているところもあります。

![](https://cdn-ak.f.st-hatena.com/images/fotolife/i/izumin5210/20261021/20261021224725.png)

haro 活用が最も激しいチームでの利用状況

早い段階から使い始めたチームの1つがモバイルアプリチームで、こちらは PR の75%ほどが haro で実装されています。モバイル開発は実機あるいはエミュレーターの数が開発並列数のボトルネックとなります。 しかし、haro 環境上では Android エミュレーターが動作するためボトルネックにはならなくなります。 ちょっとした UI 変更なら haro に投げておけば、実装 → AI が動作確認 → スクリーンショット撮影 → PR 作成までを一気通貫にでき、 PR マージ直前まで手放しで走ってくれます。

![](https://cdn-ak.f.st-hatena.com/images/fotolife/i/izumin5210/20261021/20261021224757.png)

動いた瞬間とビビるモバイルエンジニアの様子

![](https://cdn-ak.f.st-hatena.com/images/fotolife/i/izumin5210/20261021/20261021224819.png)

モバイルエンジニアの開発が加速し若返っている様子

また、クラウド型により環境構築が不要になったことで、エンジニア以外での利用も拡大しています。 デザイナ自身によるモバイルアプリの UI 実装修正や QA エンジニアによる PR 差分からの観点出しや自動での動作確認などにも使われています。 **「コードを読み書きでき動作確認も可能な環境」がカジュアルに払い出せる**ことで、プロダクト開発フローの各所で今までにない変化が起きているようです。

![](https://cdn-ak.f.st-hatena.com/images/fotolife/i/izumin5210/20261021/20261021224943.png)

QAやデザイナの仕事が変わっている様子

プロダクト開発におけるエンジニアの仕事は、「機能開発のためのコーディング」だけではありません。 レビュー, バグ修正, アラート対応, リファクタ等の継続開発のための足場固め, … 挙げるとキリがありません。 また、プロダクトを届けるまでの仕事はエンジニアだけでは完結しません。 デザイナや PdM はもちろん、お客様と対面するサポートや営業メンバーとうまく連携していく必要があります。

こうしたコーディング以外の業務も扱えるように haro は設計されています。 実際、ローカルの Claude Code や Codex で開発以外の作業を自動化してる方も多いのではないでしょうか。 haro でも同様で、ベースは Coding Agent ですがそれ以外にも様々なタスクを処理することができます。

-   コードベースを見つつタスク管理システムの状態更新
-   Slack 上の議論で出た仕様や実装の不明点をそのまま haro に聞き、コードベースや仕様 Notion を見て実挙動を教えてもらう
-   Slack でのバグ・インシデント報告から haro を起動し、コードやログ, DWH を見つつ原因調査・対応

これ以外も含め多様なユースケースを扱えるよう、haro には利用者が独自の Agent を定義できる仕組みがあります。 ここでいう “Agent” とはざっくり「system prompt」「利用する MCP tools」「起動する環境」などのパラメタの集まりです。 あるタスクをうまく遂行するための専用のパラメタを事前に定義しておき、利用者はそれを様々な経路で呼び出すことができます。

また、haro は Web や Slack 等のチャットインタフェース以外にも、 Scheduler や HTTP(Connect RPC) の API からの起動にも対応しています。 これによりローカルだけでは実現しづらい自動化も進んでいます。

-   定期でのコードのバグスキャン・セキュリティスキャン
-   daily や weekly でなんらかの指標を集計し所感とともに Slack に投稿
-   flaky test 収集ダッシュボード上のボタンを押し、 API 経由で flaky 修正セッションを起動

これらの機能を使い、haro 自体の開発・運用も haro を利用しています。 開発・動作確認はもちろん、デプロイ作業および直後のログ等の異常検知、問題発生時の原因調査から修正、日々の要望の収集・集約など、さまざまなタスクを自動化し、少人数での開発・運用を実現しています。

![](https://cdn-ak.f.st-hatena.com/images/fotolife/i/izumin5210/20261022/20261022102949.png)

haro がデプロイ後の監視で異常を報告している様子

![](https://cdn-ak.f.st-hatena.com/images/fotolife/i/izumin5210/20261022/20261022101727.png)

haro が haro のバグ調査をしている様子。 問題が起きたセッションの URL を渡すとよしなに調べてくれる。

haro は「カスタム Agent」「Slack, Scheduler, API など多様な起動経路」「MCPによる様々なリソースアクセス」に加え「クラウド上で動作する（ラップトップの状態に左右されない）」という特性を持つことで、単なる “コードを書く Agent” にとどまらず、プロダクト開発に関わる多様なタスクの高度な自動化の基盤となりつつあります。

## haro はループを勝手に閉じる基盤になる（はず）

haro 上のセッション（Agentとのやり取り）は原則公開であり、ほかの社員からもそのやり取りが見えるようになります（顧客データや機密情報に触れるセッションは、権限に応じて閲覧が制限されます）。 なのでチーム内の「うまい人」のセッションを参考にすることができます。 カスタム Agent や Scheduler などの設定も同様に原則公開なので、隣のチームの Slack channel を見て、良さげな使い方を取り入れるということもやりやすくなっています。

また、そもそも haro 上には開発上の試行錯誤のやり取りがデータとして残ります。 そのログを分析し prompt や skill にフィードバックすることができれば、「haro を使ってるだけで勝手に生産性が上がっていく」という世界になるはずです。 開発以外も同じで、 AI が日々タスクを処理してるセッションを定期的に振り返りフィードバックすることで、精度やトークン効率を改善するループが勝手に回るようになるでしょう。 まさに「haro を使うことで勝手にループが閉じている」状態です。 LayerX のイベント Bet AI Day 2026 での CTO 松本の資料を引用すると、haro を使うことで Outer Loop, Harness Optimization Loop が勝手に閉じていくような世界を目指しています。

## haro のこれから - Software Factory のその先へ

最近は世の中で “Software Factory” というものについてよく議論されています。 公開されてる記事や議論を見ると、 Software Factory とは概ね 「AI Agent による計画・実装・検証・リリースと、そこで得た学びによる継続的な改善をつなぐ仕組み」のようなものとして説明されています。ただ、こうした仕組みが整ったとしても、そこに何を流すべきかが自動的に決まるわけではありません。 最初に投入されるのがある程度自明な issue やアラートあるいは作るものが明確な仕様であれば、それは Factory 的に処理していくのが効率が良いでしょう。 しかし、現実のプロダクト開発はそうとは限りません。 バクラクのようなお客様の課題に Deep Dive し問題の解き方から考えていくタイプのプロダクト開発では、むしろこの「仕様を決める」ところが不確実であり、何度もここに戻ってくるタイプのループとなることも多いです。

答えや目指す方向が明確になってる開発では Factory 化して型にはめることで生産性は極めて高くなるでしょう。 しかし、バクラクが向き合っている開発はそれだけではありません。 バクラクらしさを保ちつつ高速に・最大の価値をお客様に届けていくためには、「速く作る」だけでなく「価値を速く作る」ことを達成していくことが求められます。

どうすればええんやという感じではありますが、（おそらく）世界の誰もまだ答えを持ってない領域でもあります。巨大な未解決問題が目の前にあり、かつそれを解く基盤を作ることで事業が大きく加速するであろう状態というのは、技術を愛するソフトウェアエンジニアとしてはかなりアツいのではないでしょうか。

「ソフトウェア開発」だけでなく「プロダクト開発」、あるいは事業全体を加速させるような、AI Agent 時代の新しい開発基盤・新しい開発の常識を作ることを haro は目指していきます。 一緒に目指してくれる方をお待ちしております。
