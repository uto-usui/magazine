## はじめに

こんにちは、バクラク事業部 AI・機械学習部でエンジニアをしている宇都（[@kuto\_bopro](https://x.com/kuto_bopro)）です。

弊社が提供するバクラクは、経理をはじめとするバックオフィス業務を自動化するサービスです。バックオフィス業務では、Microsoft ExcelやGoogle スプレッドシートといったスプレッドシート（以下、スプシ）が様々な場面で利用されています。スプシを使った業務を自動化する方法の1つとして、内容の確認や編集といったスプシ操作をコーディングエージェントに自律的に任せるアプローチが考えられます。

近年のコーディングエージェントは、LLM自体の性能向上に加えて、skillやハーネスといった実行環境も整備され、コード生成だけでなくスプシ操作もうまく扱えるようになってきました。ただし、ユーザーから見えるのは指示と成果物が中心で、エージェントが内部でどのようにファイルを読み書きしているかは分かりにくい部分です。

そこで本記事では、コーディングエージェントがスプシをどう扱っているかを、OpenAIが提供するSpreadsheets skillと、Codexでの実行事例から見ていきます。なお、対象はGUI操作ではなく、コードからXLSXファイルを読み書きする方式とします。以降は表記を簡単にするため、コーディングエージェントを単に「エージェント」と記載します。

## Spreadsheets skillの概要

まずは、Spreadsheets skillの記述をもとに、エージェントがスプシをどう扱うかの概略を整理します。

エージェントはまず、ユーザーからの指示と入力されたスプシの内容を把握します。次に、コードを生成・実行してスプシに必要な編集を加え、編集した箇所の内容を検証します。検証で問題が見つかった場合はコードを修正して再実行し、再び検証して問題がないことを確認してから、最終的な成果物であるXLSXファイルを出力します。 ![](https://cdn-ak.f.st-hatena.com/images/fotolife/k/kutohonn/20260925/20260925133301.png) なお、このskillは継続的に更新されており、内容は[Spreadsheets skillのスナップショット](https://codex-tool-reference.simonw.chatgpt.site/skills/spreadsheets)でも確認できます。本記事では実験時点のバージョン`26.909.12148`を参照していますが、今後内容が変わる可能性があります。

## 特徴的なルール

skillにはスプシ操作に関する様々なルールが記載されています。その中から、特に興味深かったものを3つ紹介します。

### 1\. セル参照と数式を使って計算過程を残す

skillでは、計算結果が合っていることに加えて、後から人が計算過程を追跡し、前提を変更できることも重視されています。そのため、数式の作り方について次の方針が示されています。

-   数値を数式へ直接書き込まず、セル参照と数式を利用する
    -   例えば成長率が5%でも`=A5*1.05`とは書かず、成長率を入力セルに置き、`=A5*(1+$A$6)`のように参照する
-   複雑な式を1つのセルへ押し込まず、意味のある中間計算をセルに分けて残す

どちらも、計算ロジックをスプシ上でユーザーが確認・修正しやすい状態に保つための方針です。 ![](https://cdn-ak.f.st-hatena.com/images/fotolife/k/kutohonn/20260925/20260925182817.png)

### 2\. 編集処理を1つのスクリプトに集約する

skillには、編集処理をまとめた`.mjs`形式のJavaScriptファイル（以下、編集スクリプト）を1つ作り、処理を修正・追加するときは同じファイルを更新して再実行する方針が書かれています。

この方針に従うと、どのセルへ何を書き込んだかを1つのファイルから追跡できます。途中で問題が見つかった場合も、そのファイルを修正して最初から実行し直せます。コードによるスプシ編集はコーディングエージェントと相性が良いことに加え、操作が複数のスクリプトや途中状態へ分散しないため、編集内容を再現しやすく、エージェント自身がレビューしやすい構成になっています。

![](https://cdn-ak.f.st-hatena.com/images/fotolife/k/kutohonn/20260925/20260925133145.png)

### 3\. Artifact Toolを優先利用する

skillでは、OpenAI製のJavaScriptライブラリ`@oai/artifact-tool`（以下、Artifact Tool）を使ってスプシを編集するよう指示しています。Artifact Toolでは以下の機能が提供されています。

-   XLSXの読み込み・新規作成・書き出し、CSVの読み込み
-   セルの値、数式、表示形式、罫線などの読み書き
-   テーブル、グラフ、入力規則、条件付き書式の作成
-   数式の再計算
-   `inspect`による値・数式・書式・図形などの検査
-   `trace`による数式の参照元の追跡
-   `render`によるシートやセル範囲の画像化

Artifact Toolはエージェントが利用する前提で作られており、skillで定義しているデータの探索、編集、検証といったスプシ操作を簡単に実行できます。汎用的なスプシ用のライブラリとしては[openpyxl](https://openpyxl.readthedocs.io/)もありますが、今回のskillでは、skillの記述に沿ったコードを簡単に書けることから、原則としてArtifact Toolを利用するよう指示されています。

## 実験: エージェントの挙動を観察する

ここからは、実際のスプシをCodexへ渡し、skillに沿ったデータの探索、編集、検証の流れを実例を通して見ていきます。

題材にはスプレッドシートのベンチマークであるSpreadsheetBench2を使います。SpreadsheetBench2は、単一セルの編集だけでなく、複数の操作を伴う業務レベルのスプシ作業を評価するためのベンチマークです。データセットには、数式修正、財務モデル、テンプレート補完、可視化のタスクが含まれています。論文では、既存のベンチマークよりもエンドツーエンドの業務フローを重視していると説明されています。

[arxiv.org](https://arxiv.org/abs/2606.29955)

### タスク概要

今回はエージェントの性能ではなく挙動を観察することが目的のため、比較的簡単なタスクを実行します。

-   前提条件をもとに、4年間の売上予測モデルの空欄を数式で補完する
-   シートは1つ。対象のシートには、CPI成長率、CPIを上回る価格成長率、人口成長率、市場シェアの目標成長率、前年売上が入力されている
-   これらを参照し、価格成長、市場シェア、数量成長、売上成長、予測売上をYear 1からYear 4まで計算する
-   指示文は「前提条件に基づいて財務モデルを完成させ、数式、参照、計算を正しくする」という抽象的なもの。そのため、空欄を見つけるだけでなく、行ラベルや注記、既存の値から計算関係を推定する必要がある

![](https://cdn-ak.f.st-hatena.com/images/fotolife/k/kutohonn/20260925/20260925133253.png)

モデルには`gpt-5.6-sol`を使い、reasoning effortは`high`に設定しました。

## 実験結果

### 探索から検証までの流れ

実行の流れを整理すると、処理は次の4段階に分かれていました。

1.  **探索**: `inspect`でブック全体の構造、値、数式を取得し、`render`で入力シートを画像化する
2.  **編集**: 空欄に入れる数式を編集スクリプト`build_model.mjs`へ定義し、再計算・検査・画像化・XLSX出力を行う
3.  **視覚的な検証**: 出力した画像を確認して表示形式の不足を見つけ、同じ編集スクリプトを修正して再実行する
4.  **値と数式の検証**: 保存したXLSXを開き直し、数式と計算結果を検証用の別スクリプトで照合する

以下のアニメーションは、この一連の実行トレースを可視化したものです。青は読み取り、オレンジは書き込みを表し、セルへのアクセス回数に応じて背景色の濃淡が変わります。初回はシートを全探索し、その後に編集すべき空白セルを特定して数式を埋めていく様子が見て取れます。

![](https://cdn-ak.f.st-hatena.com/images/fotolife/k/kutohonn/20260925/20260925134319.gif)

以降の節では、探索から検証までの流れを順に見ていきます。

### 1\. 探索: シート構造の把握

エージェントはまず`inspect`でブック全体の構造、値、数式を取得し、あわせて`render`で入力シートを画像化しています。アニメーションの冒頭でシート全体が青く塗られていくのがこの段階です。行ラベルや注記、既に入力されている前提値を読み取り、どのセルが空欄で、どの前提を参照して計算すべきかをここで把握しています。

### 2\. 編集: コード実行による数式の書き込み

探索の結果をもとに、エージェントは編集スクリプト`build_model.mjs`を作成し、空欄に入れる数式を定義しています。このスクリプトからは次のことが読み取れます。

-   スプシで一般的に使われるセル番地を用いた数式をコードで記述し、編集箇所と内容を指定している
-   skillのルール通り、数値を直接埋め込まず、新しいセルの値は参照と計算式から組み立てている
-   書き込み前に対象範囲が空欄であることを確認し、既存セルを上書きしそうな場合は処理を止めるガードを入れている

const edits \= {
  "D13:F13": \[\["=C22", "=D22", "=E22"\]\],
  "C20:F20": \[\["=C8+C9", "=D8+D9", "=E8+E9", "=F8+F9"\]\],
  "C22:F22": \[\["=C13\*(1+C14)", "=D13\*(1+D14)", "=E13\*(1+E14)", "=F13\*(1+F14)"\]\],
  "C23:F23": \[\["=C22/C13-1", "=D22/D13-1", "=E22/E13-1", "=F22/F13-1"\]\],
  "C25:F25": \[\["=(1+C11)\*(1+C23)-1", "=(1+D11)\*(1+D23)-1", "=(1+E11)\*(1+E23)-1", "=(1+F11)\*(1+F23)-1"\]\],
  "C27:F27": \[\["=(1+C20)\*(1+C25)-1", "=(1+D20)\*(1+D25)-1", "=(1+E20)\*(1+E25)-1", "=(1+F20)\*(1+F25)-1"\]\],
  "C29:F29": \[\["=C16\*(1+C27)", "=C29\*(1+D27)", "=D29\*(1+E27)", "=E29\*(1+F27)"\]\],
};

for (const \[address, formulas\] of Object.entries(edits)) {
  const range \= sheet.getRange(address);
  const occupied \= range.values.flat().some((value) \=> value !\== null && value !\== "") ||
    range.formulas.flat().some((formula) \=> formula !\== null && formula !\== "");
  if (occupied) throw new Error(\`Refusing to overwrite a populated cell in ${address}\`);
  range.formulas \= formulas;
}

### 3\. 視覚的な検証: 画像確認と表示形式の修正

編集後、エージェントは`render`でシートをPNGへ変換し、視覚的な不整合がないかを確認しています。

人がExcelを操作する場合は画面を直接確認できますが、コードからファイルを編集するだけでは、値がどのように表示されるかまでは分かりません。Artifact Toolは編集と画像化を同じ操作系で扱えるため、見た目の確認までを一連の処理に組み込みやすくなっています。

const preview \= await workbook.render({
  sheetName: "Revenue\_Analysis",
  range: "B2:F29",
  scale: 2,
  format: "png",
});
await fs.writeFile(previewPath, new Uint8Array(await preview.arrayBuffer()));

今回のシートは装飾やグラフがないため、画像確認の重要性は一見低そうに見えます。しかし実行トレースを見ると、初回のレンダリングでは、数式を追加したセルがExcelの標準的な表示形式である`General`のままになっていました。`General`では値に応じて表示が決まるため、割合が`3.10%`ではなく`0.031`、売上が`4,328.1`ではなく桁数の多い小数として表示されていました。

一方、左側のセルにあるテキストラベルからは、%表記とする意図が読み取れます。そこでエージェントは、割合と売上の表示形式を編集スクリプトへ追加し、再実行して修正しました。値と数式の検査だけでは見つけにくい問題を、画像確認で補えた例です。 ![](https://cdn-ak.f.st-hatena.com/images/fotolife/k/kutohonn/20260925/20260925133212.png)

### 4\. 値と数式の検証: 保存したファイルの照合

最後にエージェントは、保存したXLSXを開き直し、`inspect`で対象範囲の値と数式を確認しています。

ここでは、値が存在することだけでなく、保存後のファイルに意図した数式が残っていることを確認しています。さらに、`#REF!`や`#DIV/0!`といった代表的な数式エラーをブック全体から検索しています。skillの紹介では省略しましたが、こうした検証方法もskillに記載されています。

const savedCheck \= await savedWorkbook.inspect({
  kind: "table",
  sheetId: "Revenue\_Analysis",
  range: "B13:F29",
  include: "values,formulas",
  tableMaxRows: 30,
  tableMaxCols: 8,
  maxChars: 12000,
});
console.log(savedCheck.ndjson);

const savedErrors \= await savedWorkbook.inspect({
  kind: "match",
  searchTerm: "#REF!|#DIV/0!|#VALUE!|#NAME\\\\?|#N/A|#NUM!|#NULL!|#SPILL!|#CALC!",
  options: { useRegex: true, maxResults: 300 },
  summary: "saved workbook formula error scan",
});
console.log(savedErrors.ndjson);

### 実験から見えた課題

今回の比較的易しいタスクは正しく完了できましたが、実際に動かすことで現時点での課題も見えてきました。

1つ目は実行速度です。今回のような小さな1シートのタスクでも、完了までに15ターン、**約3分32秒**かかりました。skill本体や関連資料の読み込みも含め、現時点では単純なタスクでも一定の処理時間が必要です。

2つ目は、複雑なスプシに対する精度です。今回は依存関係が単純な1シートで正しい結果を得られましたが、ベンチマーク内にある複数シート、外部参照、複雑な数式、独自の書式を含む難しいケースでは、正しく編集できない事例も確認しています。

これらの課題は、LLM自体のエージェント性能の向上によって解消されていく部分もあれば、適切なモデルへのルーティングやエージェント実行環境の整備といったエンジニアリングによって改善できる部分もあると考えています。

一方で、我々が目指すのは、エージェントが複雑なスプシを解けること自体ではなく、その先でお客様の業務が楽になることです。スプシの柔軟さや利便性を活かしながら、確認や管理にかかる負担を減らし、より自然に業務を進められる体験をプロダクトとしてつくることが重要だと考えています。
