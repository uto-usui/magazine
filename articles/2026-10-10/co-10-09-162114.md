こんにちは、LayerX Fintech事業部から三井物産デジタル・アセットマネジメント（以下、MDM）に出向しているs.masです。

皆さん、AI を活用されていますか。非常に便利な反面、昨今は AI によってセキュリティの前提も変化してきていると認識しています。

たとえば 2026年5月には、npm で広く使われているライブラリ群の正規バージョンが改ざんされ、インストールしただけで開発者の認証情報が盗まれるワーム型の攻撃が公開されました。 この検体は、盗んだ認証情報で別のパッケージを次々と再公開して広がるだけでなく、Claude Code や VS Code の設定ファイルに自分自身を書き込んで端末に居座る作りになっていました（[Socket の報告](https://socket.dev/blog/tanstack-npm-packages-compromised-mini-shai-hulud-supply-chain-attack)）。 さらに、AI ツールの設定ファイルからも認証情報を抜き出していたことが報告されています（[Upwind の解析](https://www.upwind.io/feed/shai-hulud-tanstack-supply-chain-worm)）。 7月には別の OSS プロジェクトの npm パッケージも侵害されており（[Socket の報告](https://socket.dev/blog/asyncapi-supply-chain-attack)）、こうした一報が短期間に届く状況が続いています。

脆弱性を見つけて悪用するまでの時間も短くなり、公開されているソフトウェアであれば、どれが次の標的になっても不思議ではなくなりました。 金融機関に対しても、フロンティア AI による脅威の変化を踏まえた対応が求められるようになっています。

そんな折、GMO Flatt Security さんから「[ソフトウェアサプライチェーン攻撃演習](https://flatt.tech/assessment/ssc/exercise)」の集合研修の案内をいただきました。 ちょうど備えておきたいと考えていたテーマだったこともあり、MDM から参加することになりました。演習は、実在の侵害事例をもとに、CI/CD のログや監査ログを読みながらインシデント対応を体験する内容でした。

当日の様子は、GMO Flatt Security さんの[開催レポート](https://flatt.tech/magazine/entry/ssc-exercise-report)にもまとめられています。なお、この記事では演習固有のシナリオや調査手順には触れません。

以下では、演習で得た5つの視点を紹介します。あわせて、これらの視点から MDM の取り組みを振り返ります。

## なぜこの演習に参加したのか

MDM のコーポレートシステム部は、いわゆる情シスの業務に加え、金融機関における第2線（リスク管理側）の役割、監査対応、社内向けシステムの開発、GitHub や AWS を含むインフラ基盤の運用などを担っています。

そのため、サードパーティのツールが侵害されたかもしれないという一報を受けたとき、開発チームに確認を依頼するだけでは終われません。自分たちでログを調べて影響を特定し、経営層や、必要に応じて顧客へ説明する必要があります。

冒頭で触れたような一報は、今後も届き続けるはずです。そのとき自分たちがどう動けるのかを演習を通じて確かめておきたいと考え、参加しました。

### 1\. バージョンを書いても、固定したことにはならない

GitHub Actions では、外部のツールを uses: some-action@v1.2.3 のように書いて呼び出します。CI が動くたびに、GitHub が配布元のリポジトリへ行き、v1.2.3 というタグが今どのコミットを指しているかを調べて、そのコミットの中身をダウンロードして実行するという仕組みになっています。

つまり @v1.2.3 は「バージョン 1.2.3」を指定して取得しているのではなく、「v1.2.3 という名前のタグ」が指す先を取得しています。 そのため、タグを悪意あるコミットに向け直されると、自社のワークフロー定義には何の変更もないにもかかわらず、次の CI 実行からは別のコードがダウンロードされて実行されます。

この状況では自社側に差分が生まれないので、PR レビューにも引っかかりません。

対策は、タグではなくコミットそのものを指す ID（コミット SHA という40桁の英数字）で指定することです。SHA はコミットの中身から計算される値なので、別の中身に付け直すことができません。

uses: actions/checkout@v7

uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1

MDM でもこの点は問題視しており、GitHub Actions の参照を full-length の SHA に固定することを対策方針として決め、各リポジトリを置き換えてきました。 今回の演習で、実際にどのような被害につながるのかを体験できたのは良い機会でした。現在のサプライチェーンリスクの高まりを考えると、一度置き換えて終わりではなく、新しいリポジトリやワークフローが増えるたびに同じ水準を保てているかを確認し続けなければなりません。

### 2\. 問題なしと確認できないは違う

利用している外部ツールの侵害が公開されたとき、まず気になるのは自分たちは問題ない状態なのかということです。社内説明が必要になることもあります。

その際には、確認できた事実と可能性として残っていることを分けて報告する必要があります。 これをいきなり書こうとすると、意外と難しい。書くことに慣れていないというのもありますが、初動の時点では、手元の材料で言い切れることが思いのほか少ないからです。

たとえば、侵害されたパッケージについて、社内の全リポジトリを検索して利用が見つからなかったが、開発者が直接端末にパッケージを入れているかどうかを追える記録が手元になかった場合。 リポジトリで使われていないことは確認できたので問題なしですが、端末については、調べた上で問題がなかったのではなく、調べる手段がなかっただけです。

この二つを「該当なし」の一行で報告してしまうと、受け取る側の判断を誤らせかねません。

### 3\. 封じ込めは、個別の作業ではなく順序で考える

侵害の疑いが出たとき、まず手をつけたくなるのは認証情報の入れ替えです。漏れたかもしれないキーを無効にして、新しいものに差し替える。分かりやすく、効果もはっきりしています。

ただ、侵害されたコードがまだ動いている状態でこれをやると、新しいキーも同じ経路で持っていかれます。CI が回るたびに悪意あるコードが実行されているなら、そこに新しいキーを置いた時点で、また読み取られるだけです。タグを正規のコミットに戻す対応も同じで、書き換えられる権限が攻撃者に残っていれば、また向け直されます。

そのため、「実行停止→認証情報の無効化・再発行の順序を守る」「証拠保全はこの流れと並行して、ログやランナーの状態が失われる前に行う」どれも当たり前の作業ですが、順番を間違えると、対応が不十分なため侵害が続きます。

MDM では、CI から AWS へのアクセスを OIDC の短命な認証情報に寄せています。人が本番環境を操作する場合も、常設の管理者権限ではなく、申請して数時間だけ有効になる JIT（Just-in-Time）の権限を使うようにしています。盗まれても短時間で失効するため、仮に順序を間違えたときの被害も小さくなるようにはしています。ただ、JIT も最近ようやく実現したばかりで、まだまだ対応しなければならないことは多いと感じています。

### 4\. 時刻と証跡が、後からの判断を支える

インシデントの報告では、いつ起きたのかが必ず問われます。ただ、その時刻をどの記録から判断したのかによって、信頼できる度合いが変わります。

信頼できるのは、自社側に残っている記録です。自社の CI がいつ実行され、そのとき何を取得したのか。外部からの一報をいつ受け取ったのか。自分たちがいつ調査を始めたのか。どの記録に基づく時刻なのかを分けて書くことで、報告を受ける側も、どこまで確かな情報なのかを判断できます。

MDM では、AWS の権限の付与や変更を IaC のリポジトリへの PR で行っているので、誰がいつどの権限を得たのかは、PR の履歴として残ります。JIT 権限の申請や失効も Slack に通知されます。材料としては、それなりに揃っている状態です。

ただ、それらをインシデントの時にどう時系列で並べ、報告に使うのかまでは決めていません。記録が残っていることと、いざという時に使えることは別物です。一報を受けてから慌てて履歴を探すのではなく、何をどこから拾えば時系列が組めるのかは、平時のうちに把握しておきたいところです。

### 5\. ログは「あるか」ではなく「何が分かるか」で見る

CI の実行ログが残っていても、そこから分かることは、CI をどこで動かしているかによって変わります。GitHub が提供する標準のランナーでは、ジョブのログに残るのは各ステップが出力した内容までで、裏で動いたプロセスや外部への通信は記録されません。何も出力せずに動くコードがあれば、ログを見ても確認できないで止まります。

MDM の CI も、ランナーの構成はリポジトリによってまちまちで、どこで何が記録されているかを横断して把握しきれているとは言えません。ログがあることに安心せず、インシデントの時にどの問いに答えられるのかを、リポジトリ単位で押さえておく必要があります。

## おわりに

5つの視点に沿って MDM の取り組みを振り返ってみると、SHA での固定や OIDC、JIT のように、対策として入れてきたものはそれなりにあります。一方で、いざ一報が来たときに、それらをどの順番で使い、何を見て、何は見られないのかを説明できるかというと、まだ自信を持ってできるとは言えません。

演習で体験したのは、その「説明する側」の難しさでした。対策を入れて終わりではなく、何が起きたのかを、どこまで後から説明できるのか。まずは、確認すべき情報と対応の流れを MDM に合った形で整理するところから始めていきたいと思います。
