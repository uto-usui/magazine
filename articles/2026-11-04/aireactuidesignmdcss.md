AIにReactの画面を作ってもらうと、必要な入力欄やボタンは揃っているのに、画面を作り直すたびに見た目が変わることがあります。

見出しが少し大きくなる。ボタンの高さが変わる。青だった主役の色が緑になる。頼んでいないヘッダーやアイコンが追加される。

こうしたぶれは、設計ルールを書いた`DESIGN.md`を渡すと減るのでしょうか。さらに、CSSトークンの実体まで渡すと、何が変わるのでしょうか。

今回は、同じチーム設定画面を3条件で各3回、合計9回生成して比べました。

今回の範囲では、**DESIGN.mdを渡した条件でも主要な寸法が揃い、CSSトークンを加えた条件では見出しの文字色も定義どおりに揃いました。** 一方、見た目とは別に、全9画面で同じリセット不具合が見つかりました。

画面、測定値、不具合の修正まで、実際に確認した順に整理します。

## 1\. 同じ画面でも、どこまで見た目が変わるのか

題材にしたのは、次の項目を持つ「チーム設定」画面です。

グループ

項目

プロフィール

表示名、メールアドレス、役割、自己紹介

通知設定

メール通知のオン・オフ、通知頻度

操作

保存、入力エラーの表示、初期値へのリセット

初期データ、文言、選択肢、必要な操作はすべて共通にしました。通信や外部APIは使いません。

見た目の評価では、配色、文字サイズ、コントロールの高さ、角丸などを見ます。ここでは、指定したデザインへの適合と、同じ条件で作り直したときの違いを調べます。

Aはデザイン資料を受け取らない条件なので、目標の色や寸法に一致しなくても、画面要件への違反とは限りません。Aの測定値は、デザインを指定しない場合の比較材料として扱います。

`DESIGN.md`には、余白や文字サイズのスケール、部品の選び方、装飾を増やしすぎないこと、フォームの構造などが書かれています。入力欄の高さ40px・角丸8px、カードの余白24px・角丸12pxなど、具体的な数値を含む項目もあります。

```
:root {
  --color-text: #18181b;
  --color-primary: #2563eb;
  --font-size-xl: 24px;
  --control-height-md: 40px;
  --radius-md: 8px;
}
```

**既存のReactコンポーネントは、どの条件にも渡していません。** 今回測るのは設計文書とトークンの提供による違いで、既存コンポーネントの再利用効果は対象外です。

### Bでも、主要な寸法は揃った

Bでは、CSSトークンの定義ファイルがなくても、今回取り上げた見出しサイズ・入力の高さ・角丸が揃いました。

前述のとおり、DESIGN.mdには具体的な数値も含まれています。この結果を、抽象的な設計方針だけで寸法まで揃えられた証拠とは扱いません。

また、Aも入力の角丸は3回とも6pxでした。資料なしでも揃う項目はあり、「Aはすべてばらばら、B・Cはすべて一致」という結果ではありません。

Cは3回とも、渡した`--color-text`の値と一致しました。Bは寸法が揃っていても、この色には2種類の違いが残っています。

一方、保存ボタンの背景色はB・Cとも3回すべて`#2563eb`でした。**この項目では、Cでトークンを追加したことによる違いは観測されませんでした。**

今回の検証では、「同じ値になること」と「指定した値に一致すること」を分けて見ています。Aの角丸6pxも反復間では一定ですが、今回のキットが定める8pxとは別の値です。

今回の結果からは、設計文書とトークンを次のように使い分けるのがよさそうだと考えています。

**DESIGN.mdでは、判断の基準を伝える。** どんな余白のスケールを使うか、どこでカードを使うか、装飾をどこまで抑えるか、といった方針です。今回のBでは、その文書に含まれる具体的な寸法も手掛かりになったと考えられます。

**CSSトークンでは、実装で参照できる値を渡す。** 「本文の色は既存の色に合わせる」という指示に加えて、`--color-text`の定義自体を使える状態にします。Cの見出し色は、この定義と一致しました。

ただし、CSS変数が存在していても、別の値を直接書くことはできます。今回はCにトークンの実体と読み込み設定を加えていますが、任意の値を禁止する検査は入れていません。

そのため、「トークンを渡せばデザインを強制できる」という結論にはしません。**使える基準を増やした結果、今回の画面では一部の値が揃った**という観察です。

画面全体の再現性をもっと高めたいなら、次は既存コンポーネントを渡す条件も分けて調べたいところです。今回はその効果までは測っていません。

## 6\. 見た目が揃っても、機能の検査は必要だった

全9件でビルドは成功しました。両画面幅で、正常保存、必須入力エラー、簡易リセット、メール形式エラーの基本検査も通りました。

ところが、全項目を変更してからリセットする補足検査で、役割が初期値に戻っていないことが分かりました。

1.  初期値の「編集者」を確認する。
2.  「閲覧者」に変更する。
3.  「リセット」を押す。
4.  「編集者」ではなく、先頭の「管理者」になる。

この現象は、**全9件で、PC・スマホの両方、計18回の確認で再現しました。**  
![条件C・1回目でリセット後に役割が管理者になった画面](https://static.zenn.studio/user-upload/255d52311c87-20261103.png)  
_役割の初期値は「編集者」だが、リセット後の表示は「管理者」になっている。_

最初の簡易リセット検査は、表示名が元に戻ることだけを見ていました。テストが通っていたのは、その狭い確認範囲でのことでした。

### 代表例のコピーで原因を切り分ける

修正は、条件Cの代表例trial-03を別プロジェクトへコピーして行いました。

元の画面は、次の組み合わせを使っていました。

```
<form onReset={reset}>
  {/* Reactの状態で制御する入力欄 */}
  <button type="reset">リセット</button>
</form>
```

リセットのハンドラーはReactの状態を初期化していましたが、resetイベントの既定動作を止めていませんでした。

Reactの`select`は`value`で選択状態を制御できます。一方、ブラウザにもフォームをリセットする処理があります。[Reactのselectリファレンス](https://react.dev/reference/react-dom/components/select)、[MDNのフォームリセットの説明](https://developer.mozilla.org/ja/docs/Web/API/HTMLFormElement/reset)が、それぞれの仕組みの参考になります。

今回の代表例では、resetイベントで一度だけ`preventDefault()`するリスナーを追加して切り分けると、両画面幅で「編集者」に戻りました。これを確認してから、状態を復元する前に既定動作を止める修正を加えました。

```
import type { FormEvent } from 'react';

function reset(event: FormEvent<HTMLFormElement>) {
  event.preventDefault();
  setValues({ ...initialValues });
  setErrors({});
  setSaved(false);
}
```

`preventDefault()`はイベントの既定動作を取り消すためのメソッドです。ここでは、React側で状態を戻す処理に、ブラウザ標準のresetが重ならないようにしています。[MDNのpreventDefault()リファレンス](https://developer.mozilla.org/ja/docs/Web/API/Event/preventDefault)

回帰検査の中心になるのは、次の操作です。

```
const role = page.locator('[data-probe="role-select"]');
const reset = page.locator('[data-probe="reset-button"]');

await expect(role).toHaveValue('編集者');
await role.selectOption({ label: '閲覧者' });
await reset.click();
await expect(role).toHaveValue('編集者');
```

さらに、表示名・メール・役割・自己紹介・通知・頻度をすべて変えてからの復元、繰り返しリセット、リセット後の編集・保存、エラーや保存通知の初期化、キーボード操作も確認しました。

別プロジェクトで行った代表例の修正では、回帰検査12件とビルドが成功し、初期画面の修正前後の画像も両画面幅で一致しました。これはtrial-03の修正結果です。元の9試行の結果を置き換えてはいません。

## 7\. 発見をキットの改善へ反映する

この不具合は、比較実験で生成した画面に見つかったものです。その画面は、キットのv0.1.0の販売用ZIPには含まれていません。

代表例の修正に加え、キットのv0.1.1では次の改善を行いました。

-   DESIGN.mdに、制御フォームのリセット処理と全項目の検査について追記する。
-   初期選択が先頭ではないSelectを含む回帰検査を追加する。
-   同梱サンプルの全項目の復元や、繰り返し操作の検査を拡充する。
-   原因・最小修正・検証範囲を修正事例として残し、配布内容へ反映する。

既存の共通コンポーネントと文章生成サンプル本体の実装・見た目は変えていません。文章生成サンプルは、もともと`type="button"`の操作からReactの状態を直接戻す方式でした。

更新版の検証・配布用のCIは成功し、販売用ZIPのハッシュと、同梱した更新文書の一致も確認しました。

ただし、**今回の9試行は、追記前のDESIGN.mdを使った結果です。** 追記したルールで新しく画面を生成すると不具合が減るかどうかは、まだ測っていません。それを確認する場合は、別の追加実験になります。

## 8\. 今回分かったことと、検証の限界

今回の画面では、DESIGN.mdを渡したBでも、見出しサイズや入力欄の高さなどが揃いました。CSSトークンを加えたCでは、見出しの文字色もトークンの定義と一致しました。

一方で、Cでも画面の構成が完全に固定されたわけではありません。全条件に機能上の不具合も残りました。

実務では、設計ルールと値の定義を渡したうえで、生成結果を画面と機能の両方から確認する必要があります。特に今回のリセットは、1項目が戻ることを確認しただけでは足りませんでした。

この検証には、次の限界があります。

-   一画面・一モデル名・各3回という少数の観察です。別の画面やモデルに一般化できる結果ではありません。
-   Bの文書には一部の具体的な数値があり、抽象的な方針だけの効果とは分離していません。
-   Cはトークンの提供と読み込み設定を組み合わせた条件です。既存コンポーネントの効果は測っていません。
-   モデルの固定版とseedは未固定です。評価者も条件を知っており、盲検評価ではありません。
-   画面を追加したときの一貫性、Firefox・WebKit・実機での動作、完全なアクセシビリティ監査は対象外です。

元資料と他試行へのアクセスは禁止しましたが、完全に別コンテナへ閉じた環境ではありません。最小実行環境へのアクセスは残り、別の一時フォルダに置いた管理用ログへの明示的な禁止設定もありませんでした。保存したコマンド履歴に、そのログや他試行を読んだ記録はありません。厳密な再現実験では、管理用の記録も生成担当から読めない場所に分離する必要があります。

計測器にも途中で修正がありました。開発ツールの起動リンクの不備と、必須バッジ付きラベルなどの完全一致による誤判定を直し、最後は同じ版の計測器で全9件を測り直しています。これは計測の再実行で、AIによる再生成ではありません。途中の失敗記録と元の生成コードも保存しました。

今後の実装では、DESIGN.mdで判断基準を共有し、CSSトークンで参照できる値を渡し、ブラウザ上で全項目の操作を検査する。この3つを組み合わせて使っていこうと思います。
