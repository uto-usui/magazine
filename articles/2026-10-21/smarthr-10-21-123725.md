こんにちは、プロダクトエンジニアの山本（[@kymmt90](https://x.com/kymmt90)）です。SmartHRの[人給基幹プロダクト](https://tech.smarthr.jp/entry/2026/06/03/161126)の技術基盤部門に所属しています。

技術基盤部門において私が所属するユニットでは、SmartHRの従業員データに関する機能を開発しやすくするための改善を進めています。具体的には、従業員データの一部を保存するデータベースのテーブルと、そのテーブルを扱うコードの複雑さを減らすためのリファクタリングを進めています。また、この改善には長期の作業が必要になるという特徴があります。

本記事では、こういったデータベースとコードの長期的なリファクタリングを安全に進めるための方法について紹介します。ポイントは次の3点です。

-   新旧のデータと実装を維持したまま、インクリメンタルかつ安全に作業を進める
-   データ移行用コードの再利用性を高めることで、移行方法について一貫性を保つ
-   データ整合性チェックのループを短く保ち、未知の問題を早めに把握することで不確実性を下げる

## SmartHRの従業員データとは

本記事では、SmartHRの「従業員データ」は、サービスを利用するテナント所属の従業員・職員についてのデータのこととします。この従業員データは、SmartHR内のさまざまな機能が利用しており、サービスの価値を提供するための基盤といえます。

![SmartHRの従業員詳細画面に表示されている従業員データ](https://cdn-ak.f.st-hatena.com/images/fotolife/s/smarthr/20261019/20261019125054.png)

SmartHRの従業員データ

ユーザーがテナントの従業員データを管理する機能は、SmartHRの基本的な機能を提供するRailsアプリケーションに実装しています。また、従業員データ自体は、PostgreSQL相当のデータベースに保存しています。

## 開発における従業員データの課題

従業員データはSmartHRというサービスの要であり、2015年のサービス開始当初から存在します。また、これまでの技術的な意思決定に伴い、内部のデータ構造が何度か変更されてきた経緯があります。

サービス提供開始から10年以上が経った現在、過去の判断に起因して、一部の従業員データと関連コードの両方が複雑化しているという課題があります。この課題について、具体的に説明します。

### 一部の従業員データの構造が複雑である

従業員データを構成するテーブル群のうち、特定の2テーブルが複雑な構造になっているという課題があります。この2テーブルは関連付いており、さらにそれぞれのテーブルがバイテンポラル履歴[1](#fn:1)になっています。ここで、バイテンポラル履歴とは、履歴を有効性・システムへの記録という2次元の時間軸で考えるモデリング方法です。つまり、2次元の時間軸からなる履歴データを持つ2つのテーブルが親子の形で関係しているということです。

![バイテンポラル履歴である2つのテーブルが親子の形で関係しているER図](https://cdn-ak.f.st-hatena.com/images/fotolife/s/smarthr/20261019/20261019125102.jpg)

2つのバイテンポラル履歴からなるテーブル構成

こういったデータを適切に扱うには、複雑な手順が必要になることが少なくありません。たとえば、過去のある時点での履歴データを参照するには、これら2テーブルそれぞれについて適切にバイテンポラルな時点を指定したうえでデータを取得するようなクエリを書く必要があります。

### 複雑なデータを扱うためのコードが複雑である

従業員データについては、上述した2テーブルだけがこういった特殊な構造を持っています。つまり、これら2テーブルだけが、従業員データを構成する他のデータとは異なる構造になっています。

この構造が原因で、アプリケーションで従業員データをまとめて扱う際に、該当の2テーブルに対してだけ種々の特別対応が必要になります。そして、この特別対応によって、コードが複雑化しています。

その一例がレコードの挿入・更新です。特定時点で履歴エントリの作成や更新をするには、該当時点での履歴を表すレコードを2テーブルそれぞれに挿入する必要があります。また、それら2テーブル間の親子関係にあたるレコード同士で、履歴の期間について整合性が常に保たれるような調整が必要になります。

こういった特別対応によってコードの複雑さが増すことで、コードの品質にも悪影響が出てきています。

従業員データを表すActive Recordのモデル群は、アプリケーション内の各所から依存されています。こういった依存元が多いモジュールの内部品質（可読性や保守性）が低下すると、変更の影響を調べるのが難しくなります。その結果、コードを理解するのにも、複雑さを抑えながら変更するのにも時間がかかっています。

また、特別対応のコードは複雑なので、それだけ不具合も紛れ込みやすくなっています。その結果、従業員データを利用する機能についての不具合がしばしば報告されるという、外部品質に関する課題も出てきています。

## 課題の解決に向けた手段としてのテーブル統合

従業員データの一部における複雑さの課題は、重要度自体は高かったものの、事前に別の改修が必要であったりと、さまざまな事情で長らく手付かずのままでした。

しかし、2025年末〜2026年初頭ごろに課題に着手できる環境が整い、私たちのユニットでこの課題に取り組み始めました。ここでは、その方針を説明します。

### 2つのテーブルを統合する

いま問題としている2つのテーブルが複雑な構造をとっているのは、あくまでも過去時点の技術的な判断に基づく歴史的経緯でした。現在の要件では、1つのテーブルにまとめても問題ないという認識がメンバーの間で共有されていました。

その2テーブルの複雑さに対処するために、コードが複雑になっています。現状では、そのコードの複雑さが許容できなくなっているといえます。この点については、PoCを作成して確認したところ、テーブルを1つにまとめると、外部的な機能の変化なく特別対応のためのコードを最終的には削除できそうであることがわかりました。

以上の2点から、該当の2テーブルを1つにまとめると、データベースもコードも簡単に扱えるようになることが見込めました。そこで、2テーブルのうち、親にあたるテーブルにデータをまとめることにしました。本プロジェクトではこれを「統合（consolidation）」と呼んでいます。統合後は次のようなテーブル構成になるイメージです。

![統合によってバイテンポラル履歴であるテーブルが1つになったER図](https://cdn-ak.f.st-hatena.com/images/fotolife/s/smarthr/20261019/20261019125108.jpg)

統合後のテーブル構成

注意点として、統合前後の両方で、プログラム的には`parent.child`のようなインタフェースで子のデータを取得できることとします。

こういった統合にあたっては、アプリケーションの外部的なふるまいを変えずにデータとコードを改善していく必要があります。つまり、データベースとコードのリファクタリングの両方が必要であるといえます。

### テーブル統合に伴う課題

「2つのテーブルを統合する」方針で進める場合でも、別の課題がいくつか出てきます。ここではそういった課題を2つ紹介します。

まず、統合先の親にあたるテーブルの規模が大きいことです。運用が10年以上にわたり、レコードをイミュータブルに扱う形でバイテンポラル履歴を実装していることから、執筆時点で1,000万オーダーの件数のレコードが存在しています。

他にも、情報を失うことなく統合できているかという観点での検証も必要です。これまで生成されてきたデータには、後述のとおり、そのままでは統合に差し障るようなパターンのデータが存在していました。情報を失わずに正しく統合するには、そういったパターンを考慮してデータ移行しなければなりませんが、事前にすべて把握するのは現実的ではありませんでした。

以上のように、テーブルを統合するには、複雑化したデータやコードを解きほぐしながらの変更が必要です。また、SmartHRの各所から依存されている箇所でもあるので、慎重に変更を進めたいところです。試行錯誤する時間を取りつつ、安全に作業を進めるとなると、半年以上の作業が見込まれました。

## テーブル統合に向けた長期にわたるリファクタリング

テーブルの統合に向けた課題を解消するために、作業が長期的になることを前提として、安全にデータベースとコードのリファクタリングを進めるための仕組みを作りました。これは、一般に「Long-Term Refactoring」と呼ばれている考えかた[2](#fn:2)に近いものです。この考えかたを取り入れることで、データの段階的な移行やリファクタリング前後両方のコードでのテストが実施できます。

本記事の執筆時点では、まだ新実装への移行に向けての作業途中です。ここからは、長期にわたるリファクタリングにあたって、いま実際に取り組んでいるポイントを具体的に紹介していきます。

### 安全な切り替えのために変更前後のデータを維持する

リファクタリング後のデータで動くアプリケーションをリリースし終えるまでは、リファクタリング前後両方のデータを保っておくことで、正しく移行できるかの事前チェックや切り戻しが可能になります。これを実現するために、現行のデータ書き込みに合わせて統合後のテーブルにも書き込むダブルライト、統合後のテーブルへのバックフィル（過去のデータの移行）の両方を実行しています。

統合後の新しいデータは現行の実装からは参照していないので、仮に新しいデータの書き込みに失敗しても現在のアプリケーションの挙動には影響しないようになっています。また、新実装に切り替えたあとも従来のテーブルにデータを書き込むようにしているので、旧実装への切り戻しも可能です。

### インクリメンタルな開発のために変更前後のコードを維持する

リファクタリング対象のモジュールには新旧両方の実装が存在しています。そういった事実は、そのモジュールを使う箇所からは隠す必要があります。そうしないと、モジュール利用箇所にリファクタリング中であるという知識が漏れることで、リファクタリング前後どちらの実装を使うかなどの選択を委ねることになり、変更が広範囲に波及してしまうからです。

そこで、リファクタリングするモジュールを抽象化して、その中に変更前後の実装を隠蔽します。この方法を「[Branch by Abstraction（抽象化によるブランチ）](https://bliki-ja.github.io/BranchByAbstraction)」といいます。

単純化したサンプルコードで説明します。まず、次のように抽象化したモジュール（ここでは`ConsolidatedData`クラス）を導入し、そのなかでフィーチャーフラグなどを用いて新旧実装を切り替えます。

class ConsolidatedData
  def initialize(parent, child)
    
  end

  def some\_method
    if feature\_flag.enabled?
      
    else
      
    end
  end
end

そして、親モデルから子モデルにアクセスするとき、この抽象を返すようにします。

module ReaderMethods
  def child
    ConsolidatedData.new(self, child)
  end
end

class Parent < ActiveRecord::Base
  has\_one :child

  
  alias\_method :child\_association, :child

  prepend ReaderMethods
end

parent.child 
parent.child.some\_method 

この方法を使うことで、旧実装で本番を動かしつつ、新実装を徐々に追加できるようになります。つまり、長期にわたる作業でも安全に進めやすくなるということです。

### データ移行用ロジックの再利用性が向上するようにコードを整理する

今回のテーブル統合では、アプリケーションの実装も踏まえつつデータの移行や整合性の確認をする必要があり、考慮すべきことが多数ある状況でした。つまり、移行のために複雑なロジックが必要になります。また、作業自体が長期にわたるので、データ移行用とはいえ、書き捨てのコードを無秩序に増やしていくわけにもいきません。

これについては、データ移行用のコード群も通常のアプリケーションと同じように開発するのがよいと考えました。つまり、アプリケーションと同じディレクトリ構造の中で管理し、適切にモジュールを分けて、ある程度明快なインタフェースを設けて、テストも書かれた状態にするということです。

このように開発を進めたおかげで、データ移行用ツールや後述のデータ整合性の監視ジョブなど、さまざまな箇所から同じロジックを一貫性を持って使うことができています。また、実装箇所によって意図しない判断基準のずれが発生してしまうような事故の防止にも寄与しています。

### 整合性をチェックし続けることで未知の問題を減らして不確実性を下げる

作業を進めるなかで、現行の実装が複雑であるという問題に起因して、データ統合に差し障るようなデータが生成されている可能性があることもわかってきました。具体的には、統合したい2つのバイテンポラル履歴テーブルの間のレコードの対応付けが難しいことがまれにある、というものです。

そのような問題がどの程度潜んでいるかは、レコードの作成・更新状況を日々見ながら把握するしかないという状況なのが現実です。また、対象のテーブルには1,000万オーダーの件数のレコードが存在しており、相対的に規模が大きいほうでもあります。

ここで、先ほど紹介した再利用可能なロジックを活かして、一貫した整合性の確認方法に基づき、チェックの範囲や実行方式が異なる2つの仕組みを作成し、運用しています。

-   日次チェック
    -   前日以降に作成・更新されたレコードについて、ダブルライトが正しくできているか、統合が可能な状態になっているかチェックする
    -   調査対象を絞って毎日実行することで、新たな問題が起きていないかを日々検知し、すぐに把握とデータ・コードの修正ができるようにする
-   全件チェック用のCLIツール
    -   対象テーブルの全レコードについて、並行処理によって速度を担保しつつ整合性をチェックする
    -   古いデータも対象に入れて、問題が発生していないかを洗い出すのに使う

こういった仕組みで、問題の検知から修正までのループを短く保って繰り返し実行し、把握できていないパターンを減らしやすくすることで、早めに不確実性を下げられるようにしています。

## おわりに

本記事では、SmartHRの従業員データとコードの複雑さを解きほぐして開発しやすくするために、どうやって長期にわたるリファクタリングを進めているかについて紹介してきました。

現在は、紹介したような方法に基づいて半年程度作業を進めてきた段階です。日々のデータの状況を見ながら、問題なく移行を進められるように準備を進めています。引き続き、安全に切り替えを実施し、最終的に旧実装を削除できるようにユニット全体で取り組んでいきたいと思います。
