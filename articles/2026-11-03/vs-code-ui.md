## 参照:

-   VS Code 公式ブログ: [Modernizing the VS Code UI](https://code.visualstudio.com/blogs/2026/10/15/modern-ui)（2026-10-15 公開）
-   対象はモダンUIの設計方針とフィードバック。実機での比較検証ではなく、公式記事を読んだ考察

## 背景:

VS Code の [Modernizing the VS Code UI](https://code.visualstudio.com/blogs/2026/10/15/modern-ui) を読んだ。

モダンUIと聞くと、角丸・余白・浮いたカード・淡い配色あたりを想像する。ただ、これらは見た目の傾向であって、何がモダンなのかを説明しているわけではない。

今回の VS Code は、その「モダンらしい見た目」を一度採用してから、使い勝手を理由に一部を戻している。この過程が面白かったので、UIのモダン化をどう捉えるか整理する。

## 結論:

**モダンUIは、角を丸くしたUIではなく、複雑な機能を共通のルールで整理し、必要な情報と操作を迷わず見つけられるようにしたUI**だと考えた。

要素

モダン化でやりたいこと

やりすぎると

色・階層

重要な情報と状態を見つけやすくする

目立つ要素だらけになる

余白

領域や操作の区切りを分かりやすくする

作業領域が減る

一貫性

画面が変わっても操作を予測できる

用途の違う画面まで同じ形にする

情報密度

必要な情報を読み取りやすくする

スクロールや切り替えが増える

応答性

操作への反応を維持する

見た目の処理が操作を邪魔する

個々の要素は昔からある。新しいのは、これらをコンポーネント単位の調整ではなく、アプリ全体の設計として扱おうとしているところだと思う。

## 旅路:

### VS Code が揃えようとしたもの

VS Code は 2015 年から機能を追加し続けてきた。Activity Bar、サイドバー、エディター、パネルなどは、それぞれの都合で進化してきたので、余白や文字、境界線の扱いに一貫しない部分があったという。

そこで色から見直し、Agent のセッション管理画面で共通の設計ルールを作り、それを従来のエディターにも持ち込んだ。

-   色とコントラスト: コードや選択状態を読み取りやすくする
-   余白・文字・角丸: 画面ごとのばらつきを減らす
-   デザイントークン: サイズや色をコンポーネントごとに直書きしない
-   画面構成: Agent とエディターは同じ設計体系を使いつつ、同じレイアウトにはしない

ここは見た目だけの話ではない。トークンが共通なら、密度やテーマを変更するときも各画面で同じ調整をしやすい。新機能を足すたびにデザインを考え直す必要も減るはずだ。

### 余白を増やしたら、コードが見えなくなった

初期のモダンUIでは、1920×1080・拡大率100%の条件で、従来より横に約20px、縦に12〜18px多く領域を使っていたという。

余白で領域の境目は分かりやすくなっても、その分コード・ファイルツリー・ターミナルの表示量は減る。特に小さい画面やエディターを分割していると無視できない。

フィードバックを受けて、VS Code は `Layout Density` の `Compact` を追加した。

```
{
  "window.density.layout": "compact"
}
```

余白が多い = 優れている、ではなかった。エディターにとっては、1行でも多く見えること自体に価値がある。

### Pill 型タブは見た目が新しくても、関係性が分かりにくかった

もう1つがタブ。初期案では、各タブが独立した Pill 型（丸いカプセル状）になっていた。

ただ、選択中のタブと下に表示されるエディターが視覚的に離れて見えた。タブの役割はファイル名を並べるだけではなく、**今見ている内容がどのファイルかを示すこと**でもある。

そこで、選択中のタブとエディターの面をつなぐ Connected 型に変更された。Pill 型も設定で選べるようにしている。

角丸の有無ではなく、タブとコンテンツの関係が伝わるかどうかを優先したわけだ。

個人的には、この変更がいちばん分かりやすい。見た目を更新しても、既存のUIが持っていた手がかりまで消してはいけない。

### 一貫性と画一化は違う

Agent のセッション管理とコード編集では、必要な情報が違う。

Agent 側はセッションの状態・次の操作・レビュー対象を追いやすくする。一方、エディター側は密度の高いファイル操作や複数ペインが必要になる。

両方の画面を同じレイアウトにするのではなく、余白・文字・色・操作部品のルールを共通化する。ここは区別しておきたい。

**共通のルールを持つことと、すべての画面を同じ見た目にすることは別**だ。

### 見た目のコストは描画性能にも出る

公式記事では、CSS セレクターの見直しにも触れていた。広い DOM を探索するセレクターを、コンポーネントがすでに持っている状態クラスに置き換えたという。

一連の操作を使ったベンチマークでは、スタイル再計算時間が 8.2%、全体の経過時間が 3.3% 減った。一方でレイアウト時間は 6.6% 増えている。VS Code 自身も、全面的に高速化したとは説明していない。

UIの改善は描画の負担も含めて考える必要がある。統一されたデザインシステムがあっても、反応が悪ければ普段使う道具としては困る。

### 自分なら何を「モダン化」の条件にするか

今回の話を普段のアプリ開発に持ち込むなら、次を確認したい。

-   重要な情報や選択状態が、説明なしで分かるか
-   新しい画面を足しても、操作ルールが増えすぎないか
-   余白や装飾によって、表示量とクリック数が悪化していないか
-   小さい画面・高コントラスト・キーボード操作でも使えるか
-   実際の操作で、描画や切り替えが重くなっていないか

これは推測だが、今後は AI Agent のように性質の違う画面が同じアプリに増えるほど、個々の画面を綺麗にするより、共通の設計体系をどう維持するかが重要になりそうだ。

## 備考:

-   記事公開時点のモダンUIは Preview。設定で Classic UI に戻せるが、将来的には廃止する方針とされている。廃止日は未定
-   `workbench.experimental.modernUIEditorTabStyle` など、`experimental` を含む設定は変更・削除される可能性がある
-   本記事は公式記事からの考察であり、操作時間や視認性を実測して比較したものではない

見た目が古くても、迷わず操作できて情報を多く扱えるUIは合理的だと思う。逆に新しく見えても、余計なスクロールやクリックが増えたら困る。

**モダン化は装飾を足すことではなく、複雑になったUIをもう一度整理すること**。VS Code の試行錯誤は、その例として分かりやすかった。
