## この記事で学ぶこと

#17 の最後に「同じクラスの並びを何度も書くことになったら、それはコンポーネントに切り出すサイン」と書きました。今回はその「切り出し方」そのものを掘り下げます。ボタンやカードのような、どの画面でも使う部品をどう作り、どう揃えるか。これを設計の目線で考えるのが今回のテーマです。

-   共通部品に切り出す判断基準（いつ切る、いつ切らない）を説明できる
-   `variant` や `size` を props で受けて、見た目のバリエーションを1つの部品に閉じ込められる
-   デザイントークンという「見た目の目盛り」が、なぜページ全体の統一感につながるかを説明できる

迷ったら🔴だけ確実に（🔴 覚える、🟡 理屈、⚪ 流す）。

## 🔴 「同じものが3回出てきたら部品にする」

まず素朴なところから始めます。ある画面に、青いボタンがこう書いてあったとします。

```
<button class="btn btn-primary btn-md">保存</button>
```

次の画面にも、その次の画面にも、同じ `class` のボタンが出てきます。このまま放っておくと何が困るか。たとえば「ボタンの角丸をもう少し大きくしよう」と決まったとき、全画面のボタンを探して1つずつ直す羽目になります。1か所でも直し忘れると、そこだけ古い見た目のボタンが残ります。

そこで、ボタンを `BaseButton.vue` という1つの部品にします。見た目の定義はこの部品の中だけに書き、各画面は `<BaseButton>` と呼ぶだけにします。こうすれば、角丸を変えたいときに直す場所は `BaseButton.vue` の1か所です。これが共通部品の最大の利点で、**見た目の決定を1か所に集める**ということです。

判断の目安はシンプルです。**同じ見た目・同じ振る舞いのものが3回出てきたら、部品にするサインです。** 1回しか使わないものを先回りして部品にすると、かえって読みづらくなります（使う場所と定義する場所が分かれるため）。「3回ルール」はあくまで目安ですが、迷ったときの入口として覚えておくと判断が速くなります。

## 🔴 見た目のバリエーションは props で受ける

ここで初心者がやりがちな失敗があります。ボタンの色違いが欲しくなったとき、`BaseButton.vue` を丸ごとコピーして `DangerButton.vue`、`SecondaryButton.vue` を作ってしまうことです。これをやると部品が増え続け、結局「全部のボタンを直す」問題に逆戻りします。

正しくは、1つの `BaseButton.vue` に **どう見せたいかを props で渡します。** #9 で学んだ props がここで効きます。色の種類を `variant`、大きさを `size` という props で受け取り、部品の中でそれに応じた `class` を組み立てます。

```
<script setup>
import { computed } from "vue";

const props = defineProps({
  variant: { type: String, default: "primary" }, // primary / secondary / danger
  size: { type: String, default: "md" },         // sm / md / lg
});

// props の値から、当てる class を組み立てる
const classes = computed(() => [
  "btn",
  `btn-${props.variant}`,
  `btn-${props.size}`,
]);
</script>

<template>
  <button :class="classes"><slot /></button>
</template>
```

`computed`（#7）で `variant` と `size` から `class` の配列を作っているのがポイントです。`<slot />`（#9）はボタンの中に表示する文字を親から差し込むための穴です。使う側はこう書きます。

```
<BaseButton>保存</BaseButton>
<BaseButton variant="danger" size="lg">削除</BaseButton>
<BaseButton variant="secondary">キャンセル</BaseButton>
```

これを実際に Vue でレンダリングすると、次のHTMLになりました。

```
<button class="btn btn-primary btn-md">保存</button>
<button class="btn btn-danger btn-lg">削除</button>
<button class="btn btn-secondary btn-md">キャンセル</button>
```

props を省いた1つ目は、`default` に書いた `primary` と `md` が当たっています。デフォルト値を決めておくと、「とりあえず普通のボタンが欲しい」ときに何も指定しなくて済みます。色違いのために部品を増やさず、1つの部品で `variant` の数だけの見た目をまかなえます。これが「見た目のバリエーションは props で受ける」の意味です。

## 🟡 部品には「見た目」だけを持たせ、「意味」は持たせない

もう一歩進んだ設計の勘所です。`BaseButton` は「押せる青い四角」という見た目と振る舞いだけを知っていればよく、「これは削除ボタンだ」「押したら商品を消す」といった**その画面固有の事情を知るべきではありません。**

なぜか。もし `BaseButton` の中に「押したら商品を削除する」処理を書いてしまうと、このボタンは商品削除専用になり、他の画面で使い回せなくなります。共通部品の価値は使い回せることなので、固有の事情を持ち込むと価値が消えます。

ではボタンが押されたときの処理はどこに書くか。#9 でやった emit で、押されたという**出来事だけ**を親に伝えます。「押されたら何をするか」は、その部品を使う画面の側が決めます。

```
<!-- 画面側。「削除したら何をするか」はこの画面が知っている -->
<BaseButton variant="danger" @click="deleteProduct">削除</BaseButton>
```

この切り分けを一言でいうと、**部品は「どう見えるか・何が起きたか」までを持ち、「何をするか」は使う側に委ねる**です。バックエンド編で「層ごとに関心を分ける」と学んだのと同じ考え方が、フロントの部品設計にもそのまま出てきます。

## 🔴 共通部品を支える「デザイントークン」

部品を揃えても、まだ揃っていないものがあります。色と余白と文字サイズです。ある部品の青が `#2E6DA4`、別の部品の青が `#2F70A8` だと、並べたときに微妙にちぐはぐになります。人によって選ぶ値が違うからです。

そこで、**使ってよい値をあらかじめ決めておきます。** 「このアプリの主要な青は `#2E6DA4`」「余白の基本は 1rem」のように、見た目の最小単位に名前を付けて1か所にまとめたものを**デザイントークン**と呼びます。#17 で Tailwind の「`p-4` は 0.25rem 刻みの目盛り」という話をしましたが、あれはトークンの一例です。料理で「塩少々」ではなく計量スプーンで計るのと同じで、全員が同じ目盛りを使うので、誰が作った部品でも色や余白がそろいます。

CSSなら、カスタムプロパティ（CSS変数）で書くのが素直です。

```
:root {
  --color-primary: #2E6DA4;
  --space-4: 1rem;
  --radius-lg: 8px;
}
```

各部品はこの名前を参照します（`background: var(--color-primary)` のように）。すると、ブランドの青を変えたくなったとき、直すのは `--color-primary` の1行だけで、その色を使う全部品に反映されます。トークン → 基本部品 → 画面、という3つの階層で見ると、関係がはっきりします。

![デザインシステムの3つの階層を示す図。最下段がデザイントークンで、色（--color-primary: #2E6DA4）、余白（--space-4: 1rem）、角丸（--radius-lg: 8px）、文字（--font-size-md: 16px）という見た目の最小単位・全画面共通の目盛りを定義する。中段が基本部品で、BaseButton.vue・BaseCard.vue・BaseInput.vue・BaseBadge.vue という、トークンを組み合わせた1つの役割だけを持つ共通コンポーネントが並び、variant や size を props で受ける。最上段が画面・機能で、商品一覧ページ・ログインフォーム・注文確認ダイアログという、基本部品を並べて作るその画面にしかない組み合わせが並ぶ。上の階層が下の階層を使うという関係で、下ほど共通、上ほど個別になる](https://raw.githubusercontent.com/kanata-iketani/article-assets/main/f35/18-design-system.png)

下の階層ほど共通で変わりにくく、上の階層ほどその画面固有で変わりやすい、という向きがあります。このまとまり全体、つまり「トークンと共通部品の決めごと一式」を**デザインシステム**と呼びます。大げさな専用ツールが要るわけではなく、`BaseButton.vue` と数個のトークンから始まる、地続きの考え方です。

## 🟡 「切りすぎ」もまた失敗

ここまで「部品に切り出そう」と言ってきましたが、逆方向の失敗もあります。何でもかんでも細かく部品にすると、今度は部品が多すぎて「どれを使えばいいか分からない」状態になります。見出し1つ、余白1つにまで部品を作ると、画面を1枚組むのに十数個の部品をたどる必要が出て、かえって読めなくなります。

判断の軸は「再利用されるか」と「中に意味のあるまとまりがあるか」です。

切り出す

切り出さない

ボタン・カードなど複数画面で使い回す部品

その画面に1回しか出てこない並び

中にロジックや状態を抱える意味のまとまり

`<div>` で囲って余白を付けただけの箱

名前を付けると意図が伝わるもの（`SearchBox`）

名前が `Wrapper` や `Container` になりそうなもの

右側は、無理に部品にせず画面の中に直接書いたほうが読みやすいことが多いです。「1か所でしか使わず、名前がうまく付けられない」ものは、切り出しの見送りを検討してください。部品化は目的ではなく、再利用と見通しのための手段です。

## 【手を動かす】BaseButton と BaseCard を作って組み合わせる

共通部品を2つ作り、片方の中にもう片方を差し込んでみます。#6 の Vite + Vue プロジェクトの `src/components/` に2つのファイルを作ります。

まず `BaseButton.vue`。さきほどの props 版です。

```
<script setup>
import { computed } from "vue";

const props = defineProps({
  variant: { type: String, default: "primary" },
  size: { type: String, default: "md" },
});
defineEmits(["click"]);

const classes = computed(() => ["btn", `btn-${props.variant}`, `btn-${props.size}`]);
</script>

<template>
  <button :class="classes" @click="$emit('click')"><slot /></button>
</template>
```

次に `BaseCard.vue`。これは「枠」だけを提供する入れ物で、中身は3つの穴（slot）で受け取ります。#9 で1つだけ使った `<slot />` に、`name` を付けると穴を複数持てます。

```
<template>
  <div class="card">
    <div class="card-header" v-if="$slots.header"><slot name="header" /></div>
    <div class="card-body"><slot /></div>
    <div class="card-footer" v-if="$slots.footer"><slot name="footer" /></div>
  </div>
</template>
```

`v-if="$slots.header"`（#8）は「header の穴に何か差し込まれたときだけヘッダーを描く」という指定です。差し込まれなければヘッダーの `<div>` ごと出ません。使う側の画面では、カードの中にボタンを差し込みます。

```
<script setup>
import BaseCard from "./components/BaseCard.vue";
import BaseButton from "./components/BaseButton.vue";
</script>

<template>
  <BaseCard>
    <template #header><h3>商品A</h3></template>
    在庫あり
    <template #footer>
      <BaseButton variant="primary">カートに入れる</BaseButton>
    </template>
  </BaseCard>
</template>
```

`<template #header>` の `#header` は、名前付き slot に差し込むときの書き方です（`#` は `v-slot:` の省略形）。名前を付けないものは `<slot />`（本文）に入ります。これをレンダリングすると、次のHTMLになりました。

```
<div class="card">
  <div class="card-header"><h3>商品A</h3></div>
  <div class="card-body">在庫あり</div>
  <div class="card-footer"><button class="btn btn-primary btn-md">カートに入れる</button></div>
</div>
```

`BaseCard` は「商品A」も「カートに入れる」も知りません。枠だけを提供し、中身は使う側が差し込む。`BaseButton` も「カートに入れる」という文字を知りません。この「知らない」の積み重ねが、部品を使い回せる状態に保ちます。同じ `BaseCard` に、別の画面ではフォームを差し込んでもよいわけです。

## 確認テスト

### 知識問題

**Q1.** 同じ見た目のボタンが複数の画面に出てきたとき、共通部品の `BaseButton.vue` に切り出すと、どんな利点がありますか。切り出さずにコピーで済ませた場合に何が困るかと対比して説明してください。

解答を見る

**見た目の決定が1か所に集まるのが利点です。** ボタンの見た目を変えたくなったとき、直すのは `BaseButton.vue` だけで、それを使う全画面に反映されます。

コピーで済ませると、同じボタンがあちこちに重複します。見た目を1つ変えるだけでも全箇所を探して直す必要があり、1か所でも直し忘れると、そこだけ古い見た目が残ります。画面が増えるほどこの手間とズレのリスクが膨らみます。共通部品は「変更を1か所に閉じ込める」ための仕組みです。

**Q2.** ボタンの色違い（通常・危険・補助）が欲しくなりました。`DangerButton.vue` のように部品をコピーして増やすのは、なぜ良くないのですか。代わりにどうしますか。

解答を見る

部品をコピーして増やすと、色の種類だけ部品が増え、見た目を変えるときに全部を直すことになります。Q1 で避けたかった「コピーの重複」を、部品の単位で再発させてしまいます。

代わりに、1つの `BaseButton.vue` に `variant` という props を持たせ、`primary` / `danger` / `secondary` のような値を受け取って、部品の中で当てる `class` を切り替えます。見た目のバリエーションは「新しい部品」ではなく「同じ部品への props」で表すのが基本です。デフォルト値を決めておけば、普通のボタンは何も指定せずに使えます。

**Q3.** デザイントークンとは何ですか。色を直接 `#2E6DA4` と各部品に書くのではなく、`--color-primary` のようなトークンを経由させると、どんな良いことがありますか。

解答を見る

**デザイントークンは、色・余白・文字サイズといった見た目の最小単位に名前を付けて1か所にまとめたものです。** 「使ってよい値」を事前に決めておく仕組みで、全員がその目盛りから選ぶため、誰が作った部品でも色や余白がそろいます。

各部品が `#2E6DA4` を直接書くと、同じ青のつもりでも人によって微妙に違う値が混ざり、並べたときにちぐはぐになります。さらにブランドの青を変えたくなったとき、全部品を直す必要があります。`--color-primary` を経由させれば、使う値が1つに固定され、変えるときも定義の1行を直すだけで全体に反映されます。

**Q4.** 共通部品の `BaseButton` の中に「押したら商品を削除する処理」を書くのは良くない設計とされます。理由と、代わりにどう書くかを説明してください。

解答を見る

**理由は、その部品が「商品削除専用」になり、使い回せなくなるからです。** 共通部品の価値は複数の場所で使えることなので、特定の画面固有の処理を中に持ち込むと、その価値が失われます。

代わりに、`BaseButton` は「押された」という出来事を emit で親に伝えるだけにします。「押されたら何をするか」は、その部品を使う画面の側が `@click="deleteProduct"` のように決めます。部品は「どう見えるか・何が起きたか」までを持ち、「何をするか」は使う側に委ねる、という切り分けです。

### 実技問題

**Q5.** `BaseBadge.vue` という、状態を表す小さなラベルの共通部品を作ってください。`variant`（`success` / `warning` / `danger`）を props で受け取り、`class` に `badge` と `badge-{variant}` を当てて、中の文字は親から差し込めるようにします。`variant` を省いたときは `success` を既定にしてください。

解答を見る

```
<script setup>
import { computed } from "vue";

const props = defineProps({
  variant: { type: String, default: "success" },
});

const classes = computed(() => ["badge", `badge-${props.variant}`]);
</script>

<template>
  <span :class="classes"><slot /></span>
</template>
```

使う側はこう書きます。

```
<BaseBadge>公開中</BaseBadge>
<BaseBadge variant="warning">下書き</BaseBadge>
```

ポイントは3つです。1つ目は、色の種類を別部品ではなく `variant` props で表していること（Q2 と同じ考え方）。2つ目は、`default: "success"` を置いて、何も指定しないときの既定を決めていること。3つ目は、中の文字を `<slot />` で親から受け取り、バッジを「公開中」にも「下書き」にも使い回せるようにしていることです。`BaseBadge` 自身は「公開中」という意味を知らず、見た目だけを担当します。

## まとめ

-   同じ見た目・振る舞いが3回出てきたら、共通部品に切り出すサイン。狙いは**見た目の決定を1か所に集める**こと
-   色違い・大きさ違いは部品を増やさず、`variant` や `size` の **props で受けて部品の中で `class` を切り替える**
-   共通部品は「どう見えるか・何が起きたか」までを持ち、「何をするか」は emit で使う側に委ねる
-   **デザイントークン**（`--color-primary` など見た目の目盛り）を経由させると、全画面の色・余白がそろい、変更も1か所で済む
-   切りすぎも失敗。再利用されない・名前がうまく付かないものは、無理に部品にしない

次回は **#19 Storybook（カタログ駆動の部品開発）** です。今回作った `BaseButton` や `BaseCard` のような共通部品を、アプリ本体を立ち上げずに1つずつ一覧して確認できる「部品のカタログ」を作る道具を扱います。
