## 取り組んだタスクの概要

この度のインターンシップでは、 CyberAgent が OSS として公開している [Intelligent HPA](https://github.com/CyberAgent/intelligent-hpa) (以下、 IHPA) を [KEDA](https://keda.sh/) に対応させるタスクに取り組みました。

### 背景

Kubernetes には Horizontal Pod Autoscaling (HPA) という機能が組み込まれており、 CPU やメモリの負荷に合わせてコンテナの数を増減させることができます。しかし、これには以下のような課題があります。

-   CPU やメモリのメトリクスのみを使う HPA では、Pod 数を 0 にできない
    -   この構成では、長期間利用がない場合でも最低 1 つの Pod を起動しておく必要がある。なお、HPA にも Object／External メトリクスと HPAScaleToZero によるゼロスケーリング機能があり、Kubernetes v1.37 ではベータとしてデフォルトで有効化されている
-   突発的な負荷上昇に対して、スケーリングが遅れてしまう
    -   負荷上昇を観測してからでないと動けないため

このような課題に対応するため、今回扱った IHPA や KEDA ではそれぞれ以下のような機能拡張を行っています。

-   IHPA (CyberAgent 製 OSS)
    -   Python を用いて過去のメトリクスから負荷の傾向を予測し、負荷が上昇する前に Pod を増やす機能
        -   過去 24 時間の実績値をもとに、次の 15 分の負荷を予測する
-   KEDA (CNCF Project)
    -   メッセージキューや DB の状態などを用いた、イベント駆動型のスケーリング
    -   Pod 数の下限を 0 にする機能

そこで、IHPA の負荷予測機能と KEDA によるイベント駆動型スケーリングを組み合わせるため、IHPA を HPA に加えて KEDA の拡張としても利用できるように機能を追加しました。

### 改善の流れ

ここからは、私が取り組んだ作業をより具体的にご紹介します。

#### 設計の検討

このプロダクトを以前から扱われていた社員さんが事前に用意してくださっていた [Issue](https://github.com/CyberAgent/intelligent-hpa/issues/39) では、あらかじめどのような形式で入力を受け付けるか、またそれによりどのような結果を望むかがある程度定義されていました。そのため、私はこの条件を満たすためにどのような処理を定義すれば良いかを中心に考えました。

Kubernetes では、現在の状態を入力から期待される状態に近づける操作を繰り返し行うことで、最終的な整合性を目指します。そのため、単に手続き的な処理を書くだけでなく、繰り返し行われることが前提の仕様を考える必要がありました。例えば一部の処理で非同期に待たないといけない場合に、それを繰り返す処理を一旦止めて待たせるのではなく、一度ループを終えて次の処理のタイミングで回収するようにする、などです。一度に全てやり切ることを目標とするのではなく、徐々に目標とする状態に近づけるという意味で、他の処理を不用意にブロックしない処理にできているかと思います。

大まかな Design Doc がまとまった段階で、メンターさんやトレーナーさんなどを含めたミーティングを行い、そこで意見も伺いました。それまでに考えたことを説明する中で気づいたこともありましたし、有意義な会にできたかと思います。

#### 実装を行う

ここまでで設計が完了したので、ここからは実装です。この度のインターンシップでは Claude Code を利用することができたので、こちらを用いて手早く実装を行いました。なお、実装の過程では手元の環境で minikube を起動し、そちらでテスト用クラスタを起動して検証を行いました。

この過程で、 Go 言語の利用バージョンを最新に引き上げたり、 Kubernetes の最低サポートバージョンを見直したりもしました。

実装後にはレビューをしていただきましたが、そこでも optional な値の Kubernetes での扱われ方など、スキーマにフィールドを追加する機能拡張の際に重要なポイントについてアドバイスをいただきました。

## 取り組んだ感想

これまでに Kubernetes 自体は使ったことがありましたが、custom controller の開発を行うのは初めてだったため、当初はわくわくする気持ちだけでなく少し不安な気持ちもありました。しかし、インターンシップ期間中には、毎回の出社で短時間の 1on1 の機会をいただけたり、他にも業務中に声をかけてくださったりしたおかげで、分からないことをすぐに聞くことができたように思います。途中からはタスクについて広い裁量をいただけるようになり、 Design Doc のミーティングの設定を自分で行うという経験もできました。

技術面においては、今回のインターンシップを通して Kubernetes に対する理解をさらに深められたと思います。 KEDA は HPA にメトリクスデータを渡すために Kubernetes の external metrics という機能を使いますが、これが従来 IHPA が想定していた Datadog Cluster Agent と競合することが分かりました。 Kubernetes API として用意されている external metrics に設定できるリソースがクラスタにつき 1 つであることなどの仕様はこれまで知らなかったので、勉強する機会になりました。

## タスク以外で体験したこと

インターンシップ期間中には、ランチや懇親会の機会で多くの社員の方々と交流することができました。 Kubernetes を扱うインフラの中でも比較的レイヤーの高いチームの方々だけでなく、ハードウェアを購入したり設置したりされるような方々からも話を伺うことができました。

また、社内での勉強会として LWKD (Last Week in Kubernetes Development) を読む会などに参加しました。 この会では参加者のうちの一人がドキュメントを読み進めながら、他の参加者が疑問に思ったことや気になったことを質問して全体で議論するという形式でした。業務で Kubernetes を扱っている方々がどのように最新の情報を取り入れているのかを体験することができました。

さらに、 CyberAgent が管理しているデータセンターにも行ってきました。最も印象的だったのは空調設備で、効率的に計算機を冷やせるよう、いかに冷気を逃さないかが非常に意識されていたのが印象に残っています。 Kubernetes などの仮想化がハードウェア面でどのように実現されているかということを知れた貴重な経験でした。
