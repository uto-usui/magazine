## はじめに

こんにちは。SmartHRでQAエンジニアをしているnotchです。  
私が担当しているプロダクトでは定期的に不具合を振り返っていたのですが、得られた知見を次の仕様やテストケースのレビューに十分生かせていませんでした。  
今回は、その知見をレビュー観点として整理し、3層に分けて蓄積・活用する仕組みと運用を紹介しようと思います。

## 解決したい課題

不具合の振り返りで得た知見をレビューで生かすには、個々の事象を「何を確認すべきか」という観点に整理し、必要な場面で参照できるようにする必要がありました。 しかし、そのための継続的な運用が定まっておらず、せっかく不具合から得た知見を十分に反映できていませんでした。

一方、既存のレビューでは品質に関する観点を集めた「QA観点まとめ」を人やAIが参照していました。ここに不具合由来の観点を追加し続けると、情報が増え続け、AIのコンテキストを圧迫したり、対象と関係のない観点まで参照し精度が下がる懸念がありました。かといって、観点を削ろうとすると、過去の不具合から得た知見を失いかねません。

## 設計方針:量ではなく"質"で階層化する

そこで、**不具合から得た知見を継続的にレビュー観点へ反映し、レビュー対象に応じて必要な観点を参照できる仕組み**を整える方針にしました。 観点を増やすだけでなく、過去の知見を残しながら活用し続けられることを目指しています。

### 3層構造

基本的な観点は毎回確認し、不具合由来の観点は必要な場面で参照したい。また、参照対象から外しても知見は残したいと考えていました。そのため、観点を**常時参照・対象に応じた参照・履歴保持**の3層で管理することにしました。

層

役割

AIの参照

更新頻度

Universal層

普遍的に押さえるべき観点。  
既存の「QA観点まとめ」の内容を反映

毎回・全件を参照

他の層からの昇格時・インシデント発生時

Bug-driven層

不具合分析から得た観点。  
機能ごとのリスクとして管理

レビュー対象に関連するもののみを参照

月次で追加・棚卸し

Archived層

6か月再発がなくなった観点。  
削除せず履歴として保持

参照しない(必要に応じて人間が参照)

アーカイブ時・再発による復活時

### 観点の参照方法

AIによるレビューでは、Universal層を毎回参照し、Bug-driven層からはレビュー対象に関連する観点を取り出します。このとき関連する観点を探すためにBug-driven層の全文を読み込んでは、参照する情報量を抑えられません。そこで、絞り込みに使う軽量なメタデータ表と観点本文に分けています。

まずメタデータ表を読み、次の2種類のタグで絞り込んでから、該当する観点の本文を読み込みます。

-   **機能領域タグ**（プロダクト内のどの機能か）：機能A、機能B、機能C 等
-   **観点タグ**（どのような観点か）：権限・認可、データ同期、エラーハンドリング 等

両軸でフィルタリングすることで、「**機能A**の**権限チェック**で注意すべき観点」のような絞り込みを可能としています。

### 観点例

以下は「項目名が長いとツールチップからはみ出す」「半角英数字の長文でレイアウトが崩れる」といった不具合を、「長いテキストの表示」という共通の観点にまとめた例になります。個別の事象を記録するだけでなく、別の機能のレビューでも使えるチェックポイントとして整理しています。

#### bug-driven-index.json（メタデータ表）

{
  "lastUpdated": "2026-10-05",
  "last\_id": 1,
  "tags": {
    "areas": { "機能A": "機能AAA","機能B": "機能BBB",・・・ },
    "aspects": { "境界値": "境界値・エッジケース","権限": "権限・認証",・・・ }
  },
  "items": \[
    {
      "id": "BD-001",
      "areas": \["機能A","機能B"\],
      "aspects": \["境界値"\],
      "issues": \["BUG-123", "BUG-456"\],
      "first": "2026-05-08",
      "last": "2026-10-01",
      "summary": "長いテキストによる表示崩れ"
    }
  \]
}

#### bug-driven.md（詳細本文）

\### BD-001: 長いテキストによる表示崩れ
\*\*機能領域\*\*: 機能A,機能B

\*\*典型的な事象\*\*
\- 項目名やラベル等のテキストが想定以上に長い場合、tooltip・セル・ダイアログ等のUI要素からはみ出す

\*\*過去の不具合例\*\*
\- BUG-123 (2026-05-08) - 項目名が長い場合、tooltipからテキストがはみ出す
\- BUG-456 (2026-10-01) - 半角英数字で長文を入力した場合にレイアウトが崩れる

\*\*チェックポイント\*\*
\- 表示領域に対して、テキストが長い場合の処理（truncate・折り返し・スクロール等）が定義されているか？
\- tooltip・ポップオーバー等の固定幅UI要素で、可変長テキストの表示方法が考慮されているか？
\- 半角英数字のみの長文でも、正しく折り返しが適用されている

### 運用フロー

観点を継続的に更新するため、月次の不具合振り返りに、次の作業を組み込みました。

1.  **追加**：不具合から得た知見をレビュー観点に整理し、既存観点への統合やBug-driven層への追加を検討する
2.  **更新**：既存観点に該当する不具合が発生した場合は、再発カウントと最終発生日を更新する
3.  **棚卸し**：同種の不具合の再発回数と、最終発生からの経過期間をもとに、観点の扱いを見直す
    -   **Universal層へ昇格**：再発カウントが累計3回以上(特定の機能、観点に限定されないリスクと判断)
    -   **Archived層へ移動**：発生から6か月以上再発なし(一時的なリスクだった可能性)
    -   **継続**：上記に該当しない観点は、Bug-driven層で管理を続ける

インシデントなどで、テストで防げたと判断した観点は、月次の振り返り会を待たず**直接Universal層に追加**します。 また、アーカイブ済みの観点に該当する不具合が再発した場合は、Bug-driven層へ戻します。  
同じ機能で同一の不具合が繰り返される場合は、単に再発回数を加算するだけでなく、観点の記述や参照・活用のされ方を見直し、別の再発防止策も検討します。

## 現時点で確認できたこと

運用はまだ初期段階ですが、確認できている手応えと、見直しを進めている点を紹介します。

### 再発防止の手応え

「長い文字列でのレイアウト崩れ」をBug-driven層に観点として追加したところ、テストケースのレビュー時点でAIが指摘するようになりました。以前は探索的テスト以降で気づくことが多かった問題を、より早い段階で検討するきっかけになっています。

### 肥大化による問題の緩和

Bug-driven層は全文を参照せず、機能領域タグと観点タグで絞り込んでから読み込む構成にしたことで、観点が増えても、コンテキストの圧迫や、レビュー対象と関係のない観点までテストケース化される問題を、ある程度抑えられています。

### アーカイブ基準の見直し

一方で、見直しが必要だと感じている点もあります。  
現在はアーカイブを「一定期間の再発有無」で判定していますが、この基準だと「その観点があるおかげで不具合が起きていない」観点まで、再発がないという理由でアーカイブしてしまい、かえって再発を招くリスクがあります。 そこで、再発頻度ではなく「どれだけ観点が参照されているか」という観点の効果を定量的に計測し、判定基準に取り入れる方向で見直しを検討しています。

## おわりに

今回は、不具合の振り返りで得た知見をレビュー観点として整理し、次のレビューに生かすための仕組みと運用を紹介しました。

運用はまだ初期段階ですが、観点の使われ方や効果を確かめながら、見直しを続けていきます。不具合の知見を次のレビューにつなげたいと考えるチームにとって、一つの参考になればと思います。
