## 探索的テストを AI にまかせたい

AI でコードを書くのが当たり前になり、作る速さはぐっと上がりました。[haro の記事](https://tech.layerx.co.jp/entry/why-we-built-our-background-agent:)にもあるとおり、LayerX ではすでに 1 日の PR の半分以上が haro から作られています。**作る量が増えた分、出来上がったものを確かめる QA の重要度が上がっていると感じています。**

テストケースは、画面や機能ごとに書くことが多いと思います。この書き方だと、1 つずつの機能は確かめられますが、機能をまたいだ組み合わせで起きる不具合は見落としがちです。

そこを補うのが探索的テストです。LayerX にも、リリース前の機能をメンバーが集まって触り、人の手で探索的テストをする文化があります。

[tech.layerx.co.jp](https://tech.layerx.co.jp/entry/2024/12/03/092300)

ただ、集まったメンバーはその場で機能を知るところから始めるので、細かい仕様まで踏み込んで試すところまではなかなか届きません。それに、人がやるとかなり時間がかかります。組み合わせを考え、テスト用のデータを作り、画面を何百回もクリックして、気になった挙動の原因を調べるのを公開前に毎回やるのは大変です。

![](https://cdn-ak.f.st-hatena.com/images/fotolife/a/abctail30/20261113/20261113152549.png)

これを AI にまかせられないか、というのが今回の取り組みの出発点でした。

## テストの観点は「ツアー」で選ぶ

観点の選び方は James A. Whittaker『[探索的テストの考え方 ソフトウェア開発のテスト設計とテクニック](https://book.mynavi.jp/ec/products/detail/id=146407)』（杉浦清博 訳、マイナビ出版）を参考にしています。この本は画面ごとではなく「何を確かめたいか」でテストを分けることを勧めていて、その分け方を「ツアー」と呼んでいます。

![](https://cdn-ak.f.st-hatena.com/images/fotolife/a/abctail30/20261113/20261113152654.png)

今回使ったツアーをいくつか紹介します。

-   **ガイドブックツアー**: 説明書どおりに使う
-   **FedEx ツアー**: 1 件のデータを、登録から最後の出力まで追いかける
-   **反社会的ツアー**: わざと逆のことや、間違った順番の操作をする
-   **強迫観念ツアー**: 同じ操作を何度も繰り返す
-   **雨天中止ツアー**: 途中でやめる、キャンセルする
-   **カウチポテトツアー**: 既定値のまま、空欄のまま進める
-   **タクシー通行止めツアー**: 権限が無い状態で、すべての経路がちゃんと止まるかを見る

1 本のツアーが画面をまたいで動くので、機能どうしが絡む不具合が見つかりやすくなります。ツアーを選んで、ツアーごとにテストのシナリオ（画面で行う操作の手順）を書くのは、探索的テスト AI Agent の仕事です。

## 画面操作を Qwen3.8-27B で動かす

仕組みのポイントは、何を見るかを考える仕事と実際に手を動かす仕事を分けたことです。

![](https://cdn-ak.f.st-hatena.com/images/fotolife/a/abctail30/20261113/20261113152822.png)

Claude には仕様とコードを読んでテストのシナリオを書く仕事と、テストが終わったあとに見つかった問題をまとめて原因を調べる仕事をまかせます。どちらも回数は少ないですが、この 2 つの出来によって見つかる問題が変わります。

社内 GPU の Qwen3.8-27B が受け持つのは、シナリオを読んで次に何を操作するかを決める役と、スクショを見てクリックや入力をする画面操作の 2 つです。画面操作は回数が多く、1 回の実行で Qwen3.8-27B を数百回から千回ほど呼びます。

1 回の流れはこうなります。

![](https://cdn-ak.f.st-hatena.com/images/fotolife/a/abctail30/20261113/20261113152856.png)

人がやるのは、最初に 1 行で頼むことだけです。

XXXの検証環境で、YYYまわりを探索して

どのツアーをどの順で回すかは、Agent が決めます。シナリオはまとめて何本か回し、これを 1 ラウンドと呼んでいます。各ラウンドの最後に「確かめていないこと」を書かせて、次のラウンドのシナリオを書くときに使います。

### Qwen3.8-27B の報告を Claude に確かめさせる

画面を操作するモデルは、見えている画面の外のことが分かりません。そこで、探索結果の裏どりにQwen3.8-27B の報告はそのまま使わず、**画面を操作しない Claude にログやコードという別の手がかりで確かめさせる仕組み**にしています。

たとえば今回、Qwen3.8-27B は見ていた画面の範囲で「値が入らない」というバグを報告しました。ところが Claude が Datadog でサーバーのログを調べると、値は別の画面に別の形で出ていて、報告の誤りに気づけました。

![](https://cdn-ak.f.st-hatena.com/images/fotolife/a/abctail30/20261113/20261113152956.png)

### 確かめた問題をチケット案にまとめる

![](https://cdn-ak.f.st-hatena.com/images/fotolife/a/abctail30/20261113/20261113153051.png) c Claude は確かめた問題のうち原因が同じものを束ねて、チケット案にまとめます。これでチケットの乱立を防ぎつつ、そのまま修正 Coding Agent を起動できます。

## haro を使って探索的テストをバックグラウンドで回す

機能をまたぐ組み合わせを広く試すには、シナリオを何十本も回す必要があります。1 本のシナリオの中でも画面の操作を何度も繰り返すので、全部を回し終えるにはかなり時間がかかります。今回の 47 本では、約 10 時間かかりました。これを人が付きっきりで見ているわけにはいかないので、**バックグラウンドで回しておける形**にしたいと考えました。

実際、最初は手元の Mac で回していました。

![](https://cdn-ak.f.st-hatena.com/images/fotolife/a/abctail30/20261113/20261113153127.png)

手元のローカルマシンでで 10 時間回すと、そのあいだ Google Chrome とマシンが占有されます。スリープやフォーカスの取り合い、閉じ忘れたブラウザの窓など、対策だけでけっこう手間がかかりました。PC を閉じて帰ることもできません。飲み会にも遅れてしまいます。

そこで、同じ仕組みを haro の上で動かすことにしました。haro 自体の構成は下のようになっています。

![](https://cdn-ak.f.st-hatena.com/images/fotolife/a/abctail30/20261113/20261113153151.png)

内製 Background Coding Agent "haro" で拓く未来の開発体験 より引用

探索的テスト AI Agent はこの図の Workspace Pod の中にある Coding Agent Harness の上で、haro の Agent と skill（Agent に読ませる手順書）として動きます。この Agent はラウンドごとに次の 4 つを繰り返します。

1.  テストのシナリオを書く
2.  Qwen3.8-27B に、シナリオどおり画面を並列で操作させる
3.  結果を集めて、Datadog やコードで原因を確かめる
4.  確かめていないことをもとに、次のラウンドのシナリオを書く

この繰り返しを 1 つの Agent が最後まで回せるようにしてあり、その Agent を haro の上でそのまま動かしています。ブラウザも Workspace Pod の中で立ち上げます。haro はクラウド上で動いていますが、Workspace Pod と社内の GPU サーバーを [Twingate](https://www.twingate.com/) でつないでいるので、Qwen3.8-27B を利用できます。原因を確かめるときは、haro につないである Datadog でログも調べます。

haro なら、ブラウザは haro の中で動くので、手元のマシンには何も起きません。依頼して PC を閉じて帰り、翌朝起きて結果を見るという使い方ができます。ログインも画面の遷移も検証環境だけに絞ってあるので、本番を開くこともありません。データを作ったり変えたりするテストを AI にまかせるので、ここは大事なポイントでした。

Skillはリポジトリで共有しているので、社内の誰でも同じように回せます。スクショとレポートがチケットに残るので、チームの誰でもあとから探索的テストの結果が見直せるのも便利です。

## 約 10 時間回してみた結果

公開前の機能を対象に、47 本のシナリオを 9 ラウンドに分けて、約 10 時間回しました。

-   見つかった問題は、重要度が高いものが 3 件、中が 8 件、低が 11 件。原因が同じものを束ねると、根本原因は 5 つ
-   仕様を決めたときの記録にある仕様 13 個のうち、10 個は画面で確かめて仕様どおりに動いていた
-   見つかった 22 件は、Claude が確かめて 5 つのチケット案にまとめた

![](https://cdn-ak.f.st-hatena.com/images/fotolife/a/abctail30/20261113/20261113153316.png)

公開前の機能なので中身は書けませんが、見つかった問題は大きく 3 つの種類でした。複数の機能をまたいで特定の順番で操作したときだけ起きるもの、2 つのサービスをまたいでデータを追うと見つかるもの、権限によって画面の表示とサーバーの判定が食い違うもの、どれも、1 つの画面の中だけのテストでは見えない種類の問題でした。

## 全部 Claude のモデルで回したらいくらかかるか

Qwen3.8-27B は社内で持っている GPU サーバーで動かしているので、電気代はかかりますが、呼び出しごとの料金はかかりません。何時間回しても、追加の費用を気にせずに気軽に回しまくれるのがポイントです。では、同じことを全部 Claude Opus 5.5 でやったらいくらになるのか。手元で回した 2 回の実行で計算してみると、全部 Claude で回すよりも、1 **回目で約 4 割、2 回目で約 7 割安く**済んでいました。Claude の金額と画面操作の呼び出し回数は実測で、ほかは実測のトークン数から計算しています。画像の読み込みも含みます。

今回の 47 本・約 10 時間の実行では、こうなります。

![](https://cdn-ak.f.st-hatena.com/images/fotolife/a/abctail30/20261113/20261113153353.png)

今回の構成でも、シナリオを書く役と結果をまとめる役には Claude Opus 5.5 を使っていて、その分が約 $160 です。次の操作を決める役と画面操作まで Claude にやらせると約 $380 になるので、Qwen3.8-27B にまかせたことで 約 $220 浮いた計算です。

金額のほかに、利用上限の問題もあります。Claude の利用上限に当たると、10 時間の実行が途中で止まってしまいます。社内 GPU なら、上限を気にせずに回せます。

## みんなが回すほど探索的テスト AI Agent が育つ

この仕組みは haro の skill と Agent として展開していて、どのサービスでも、誰でも使えます。そして、**みんなが haro で回せば回すほど探索的テスト AI Agent が育っていくループ**を、haro の上に作っています。

![](https://cdn-ak.f.st-hatena.com/images/fotolife/a/abctail30/20261113/20261113154543.png)

進め方は全サービスで共通にして、画面操作の決まりや回してみて分かったことのような、サービスごとに違う知識は skill の中にサービスごとのディレクトリを切って貯めています。

qwen-exploratory-qa/
├── SKILL.md              # 進め方（全サービス共通）
├── references/
│   ├── lessons.md        # サービスをまたいで使える学び
│   └── apps/
│       ├── clm/          # 契約管理
│       │   ├── rules.md  #   画面操作の決まり
│       │   └── lessons.md #  回して分かったこと
│       ├── workflow/     # 申請
│       └── attendance/   # 勤怠
└── templates/app/        # 新しいサービスを足すときのひな形

探索的テストを回して分かったことは、そのサービスのディレクトリに書き戻していきます。次にそのサービスで回す人は、前の人が貯めた学びを読んだ状態から始められます。サービスをまたいで使える学びは共通の場所に貯めるので、別のサービスで回した結果も活きます。今回も「シナリオを書く前に、仕様を決めたときの記録を読む」という手順を書き戻しました。

## まとめ

探索的テストを、Claude がシナリオを書いて結果を確かめ、社内 GPU の Qwen3.8-27B が画面を操作する形で、haro に一晩まかせられるようになりました。47 本のシナリオで機能やサービスをまたぐ組み合わせの問題が見つかり、全部 Claude で回すより 4 割以上安く、利用上限も気にせずに回せています。

AI で作る量が増えた分、出来上がったものを確かめる QA の重要度は上がっています。探索的テストも AI にまかせ、みんなが haro で回すほど、サービスごとの学びが skill に貯まって探索的テスト AI Agent が育っていく。この形で、確かめる側も作る速さに追いつかせていきたいと考えています。
