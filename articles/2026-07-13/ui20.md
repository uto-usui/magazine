こんにちは！SmartHR で内定者インターンをしている[na2kera](https://x.com/na2kera_0510)です。

私が携わるプロダクトで、UIライブラリSmartHR UIの大幅アップデートに挑戦しました。この記事では、1ヶ月半・13本の PR を経て、バージョンを v75.4.1 から v96 まで一気に引き上げた取り組みと、そこで得た知見を紹介します。

## 1行の CSS を書こうとしたら、20バージョンの遅れが判明した

きっかけは、ある画面のレイアウト修正でした。大きい画面でコンテンツの横幅を制限しようとしたとき、SmartHR UI の最新版には対応用のコンポーネントが用意されているはずでしたが、プロダクトで使用しているバージョンが古く、利用できませんでした。

やむなく自前の CSS を1行書いて対応したところ、メンバーからのコメントで SmartHR UI が約20バージョンもビハインドしていることを教えてもらいました。このまま放置するとライブラリの恩恵を受けられないまま自前実装が積み重なっていくと感じ、自らアップデートしたいと手を挙げました。

## UIライブラリの SmartHR UI とは

SmartHR UI は、SmartHRがOSSとして公開している React 製の UIコンポーネントライブラリです。詳細は以下の記事をご覧ください。

[SmartHR UI の紹介記事](https://tech.smarthr.jp/entry/2022/12/14/170527)

SmartHR UI を使うことで、プロダクト間で UI のデザインや操作感を揃えられるほか、アクセシビリティ対応もコンポーネント側で行われているため、プロダクト側で一から実装する必要がありません。よく使う UI パターンがコンポーネント化されているため、自前で CSS を書く量も減り、開発効率が上がります。ライブラリ側のアップデートでバグ修正や新機能も継続的に追加されるため、SmartHR UI のバージョンを上げておくことは大きなメリットがあります。

## アップデートの規模を数字で振り返る

今回のアップデート規模を数字でまとめると以下のとおりです。

-   バージョン：v75.4.1 → v96（約20バージョン）
-   期間：2026年5月12日〜2026年6月26日（約1ヶ月半）
-   PR の本数：13本
-   総追加行数：約6,500行
-   総削除行数：約6,900行
-   ファイル変更の延べ数：約950ファイル

アップデートの途中では、複数のコンポーネントにまたがる props の変更やコンポーネントの廃止など、破壊的変更が1バージョンに重なるケースもあり、影響範囲の洗い出しや動作確認に時間がかかることがありました。それでも週3稼働で他のタスクと並行しながら進め、1ヶ月半でこの規模の更新を完了できました。

## 最初はうまくいく指示の仕方がわからなかった

約20バージョン分の更新を AI の助けを借りて進めることにしましたが、最初はなかなか思い通りにいきませんでした。たとえば、複数に分かれていた props が1つのオブジェクト prop に統合される変更は、一見単純な置き換えに見えます。

Component label\="操作" iconOnly size\="s" 

Component trigger\={{ children: '操作', iconOnly: true, size: 's' }} 

しかし、プロダクト内では props の組み合わせが箇所ごとに異なっていました。たとえば次のようなパターンが混在していました。

label="追加"  →  trigger={{ children: '追加' }}


label="操作" size="s"  →  trigger={{ children: '操作', size: 's' }}


label="操作" iconOnly size="s"  →  trigger={{ children: '操作', iconOnly: true, size: 's' }}

箇所によって props の組み合わせが異なるため、同じルールですべてをまとめて置き換えることはできません。AI に修正を任せても、組み合わせごとにオブジェクトの組み立て方が変わるので、最初は思いどおりに書き換えてもらえないことがありました。

そこで、抜け漏れや変換ミスを防ごうと、リリースノートの PR を1本ずつ渡して内容を把握させたり、影響範囲を1ステップごとに確認させたりなど、細かく指示を出して進めました。それでも props の組み合わせごとの修正がうまくいかなかったり、変更漏れが残ったりすることもあり、何を・どう伝えればよいか分からないまま、何度かやり直しながら手探りで試行錯誤しました。

## 何度もやるうちに「うまくいく流れ」が見えてきた

試行錯誤を重ねるなかで、安定して機能するワークフローが見えてきました。プロダクトにはすでに Claude Skills が豊富に用意されており、コードレビューや PR 作成などを担う Skills を組み合わせて呼び出すことで、プロダクトのコンテキストを踏まえたフローが組み立てられるようになりました。大まかな流れは次のとおりです。

1.  現在のバージョンを確認し、リリースノートから破壊的変更を影響度付きで整理する
2.  破壊的変更が少ない範囲を提案し、どこまで上げるかを決める
3.  リリースノートとライブラリの型定義から新しい API を把握し、影響箇所を特定する。変更パターンごとに Before → After の修正プランを作成する
4.  依存関係を更新し、破壊的変更をパターンごとに修正する。型チェックで漏れを検出する
5.  コードレビューを実施し、問題があれば修正する
6.  変更パターンごとに、どの画面で何を確認するかの動作確認項目を洗い出す
7.  目視確認の結果を受けて、必要な修正を行う
8.  動作確認結果を含めた PR を作成する

こうして、先ほど挙げたような props の組み合わせごとの変更も、パターン単位で対応できるようになっていきました。

## うまくいく流れを Claude Skill に書き起こした

こうして確立したワークフローを、SmartHR UI のアップデート専用の Claude Skill として書き起こしました。実際の Skill から一部を抜粋・簡略化したものが以下です。

\---
name: update-ui-library
description: UIライブラリのバージョンアップを実施する。リリースノート確認・コード修正・レビュー・PR作成・動作確認項目の洗い出しまで一貫して行う。
argument-hint: "\[target-version\]"
\---

\## 手順

\### 1\. バージョン確認とリリースノート調査

現在のバージョンを確認し、リリースページから各バージョンの破壊的変更を影響度付きテーブルにまとめて提示する。

\### 2\. 対象バージョンの決定

どのバージョンまで上げるかをユーザーに質問する。破壊的変更が小さい範囲を提案する。

\### 3\. 影響範囲の調査とプラン作成

リリースノートとライブラリの型定義から新しい API を把握し、影響箇所を特定する。変更パターン（Before → After）ごとに修正プランを作成する。

破壊的変更が見つからない場合は、依存関係だけ更新して型チェックを通し、「影響がありませんでした。次のバージョンにも進みますか？」とユーザーに提案する。同意が得られたら対象バージョンを拡大し、手順1からやり直す。

\### 4〜8. 実装・レビュー・動作確認・PR作成

破壊的変更をパターンごとに修正し、レビュー用の Skill と PR 作成用の Skill をそれぞれ呼び出す。動作確認は変更パターンごとにテーブル形式でまとめ、目視確認の結果を PR の説明に反映する。

\## 禁止事項

\- 新しい API を推測で対応しない。必ず型定義かリリースノートで確認する
\- 動作確認は個別のコンポーネント名ではなく、変更パターン単位で書く
\- ユーザー確認なしに複数メジャーバージョンを一度に上げない

破壊的変更がないバージョンが続く場合は、影響なしとして次のバージョンへ進むかを確認するループも Skill に組み込みました（上記の手順3にあたる部分です）。これにより、複数バージョンをまとめて上げる判断も Skill 内で完結できます。

動作確認項目を洗い出す手順（上記の「4〜8. 実装・レビュー・動作確認・PR作成」にあたる部分）では、変更パターンごとに以下のような表形式で出力するよう指示しています。

\### label → trigger prop への統合（ボタンの見た目変化）

| 画面             | 確認方法                 | 確認箇所                                                 |
| ---------------- | ------------------------ | -------------------------------------------------------- |
| ユーザー一覧画面 | 「操作」ボタンを表示する | ラベル・アイコン・サイズが変更前と同じ見た目になっている |
| 設定画面         | 「追加」ボタンを表示する | ラベルのみのボタンが正しく表示されている                 |

同じ変更パターンは複数の画面にまたがって登場するため、変更したコンポーネント単位で確認項目を出すと、似たような確認内容が何度も重複してしまいます。そこで、変更パターンごとに表をまとめる形式にしたことで、確認すべき画面と着目点が一目で分かるようになりました。目視確認を依頼する相手にとっても、どのパターンのどこを見ればよいか迷わずに済むようになりました。

この Skill を使いながら以降のバージョンアップを進めるなかで、いくつかのつまずきもありました。リリースノートだけでは変更内容を把握しきれないケースがあり、ライブラリの型定義も合わせて確認する必要がありました。また、破壊的変更の説明が「何を削除するか」だけで終わっており、新しい API でどう書き換えるかまで調べる必要がある場面もありました。

こうした経験をもとに Skill の指示内容を都度見直し、少しずつ改善しました。モブプログラミングの時間をとってチームに Skill の使い方や取り組み内容を共有したところ、フィードバックをもとに Skill を見直すこともありました。Skill を使えば、自分以外のメンバーも同じフローでバージョンアップを進められるようになっています。

## スムーズに進んだ背景にはチームの文化があった

ここまで紹介したワークフローと Skill は、バージョンアップを進めるときの型として使えました。ただ、スムーズに進められた理由はそれだけではなく、Skills の整備からコミュニケーションの仕方まで、チームの文化にも支えられました。

### 開発における Skills が充実していた

私が携わるプロダクトでは、実装パターン、ワークフロー、テスト、調査など、開発のあらゆる場面をカバーする Skills が整備されていました。新しいチームやプロダクトに入ったばかりのときは、フローや暗黙的なルールが分からず、手探りでどうしても作業スピードが落ちがちですが、内定者インターンとして参加したばかりの自分でも、こうした Skills があるおかげで手探り状態が続かずに作業を進められました。

とくに、手元で E2Eテスト を実行したいときにテスト環境を整備してくれる Skill や、複数の評価観点に基づいたレビューをサブエージェントで行ってくれる Skill は、動作確認やコードレビューの待ち時間を短くしてくれました。

### 「やっていること」を宣言する文化が助けをくれた

SmartHRでは、Working Out Loud（WOL）という文化が社内の多くのチームで根付いています。これからやること・今やっていることを周囲に宣言するという考え方です。私たちのチームではリモートのメンバーが多く、基本的なコミュニケーションはチャットで行われるため、この WOL 文化がとくに重要な役割を果たしています。

たとえば、これから着手するチケットを宣言したり、作業中のログを残したりしているほか、質問や提案などもチーム内でたくさん飛び交っています。

今回の SmartHR UI アップデートでも、着手前の共有や作業ログを残していました。そのおかげで、他チームから過去の類似事例を教えてもらえたり、周囲から声をかけてもらえたりすることもありました。詰まったときも、状況がすでに周囲に伝わっているため、サポートを受けやすい状態でいられました。

### 詰まったらすぐモブプロで確認できた

モブプロを気軽に申し込めることも、チームの特徴のひとつでした。

画面を一緒に見た方がよいときや、口頭で相談した方が早いときなど、チャットだけでは解決しにくい場面では、自分から声をかけることもあれば、メンバーから「モブプロしましょうか」と声をかけてもらうこともありました。

今回のアップデートでも、動作確認で機能を再現できないときや修正の方向性に迷ったときにはモブプロをお願いしました。すぐに相談に乗ってもらえ、認識のズレがあった場面もその場ですり合わせられたため、大きな手戻りなく進められ、安心感を持って作業を続けられました。

最近では、AI 活用を促進する AI モブプロも積極的に行われています。実際のタスクを進めながら使い方を共有する場で、取り入れられそうな点を自分なりにブラッシュアップし、開発に活かしています。

## おわりに

内定者インターンとして参加してから、チームにはどんどんタスクを任せてもらえる環境がありました。小さな画面修正から始まり、経験を積むにつれて担当する範囲も広がっていきました。

今回の SmartHR UI のアップデートは、「自分でやりたい」と手を挙げたところから始まりました。約20バージョン分という更新量や、変更の影響範囲の広さには不安もありましたが、自分から動きたいという意思を尊重してくれる環境があったからこそ、思い切って取り組めました。これからも主体的に動きながら、チームに積極的に貢献していきたいと思います。
