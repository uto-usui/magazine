こんにちは、[Kazu](https://x.com/KazuLayerX) です。今年の 4 月に新卒として LayerX に入社して、現在[バクラク勤怠](https://bakuraku.jp/lp/ad_attendance_v3/)の開発をしています。最近、社内の麻雀部で部長に就任しました。

このところ、バクラク勤怠のアラートの巡回を、社内の Background Coding Agent「haro」のスケジュール実行に任せています。Background Coding Agent とは、PC を閉じていてもクラウド上で動き続け、コードの調査や修正、PR の作成までを非同期にこなす Coding Agent のことです。こちらを平日の 9 時から 21 時まで 1 時間おきに起動して、アラートのチャンネルを読み、調べるべきものは調べ、直し方がはっきりしていれば draft PR まで出します。(なお、お客様に影響がある障害は、今までどおり担当者がすぐに対応しています。「haro」 が受け持つのは、その手前の巡回と振り分けです。)

今回はその仕組みと、約 3 週間半運用してみて分かったこと、そして「**巡回のやり方を、巡回する エージェント が自分で直していく**」仕組みについてお話しします。ここでいう「自分で直す」とは、あらかじめ人が定めた制約の中で、調査手順をまとめた Wiki を更新することです。

「haro」 そのものについてはこちらの記事で紹介しています。

[内製 Background Coding Agent "haro" で拓く未来の開発体験](https://tech.layerx.co.jp/entry/why-we-built-our-background-agent)

## アラートを見る負担

バクラク勤怠は、朝の出勤打刻や月末の締めなど、お客様の業務の時刻に合わせてアクセスと処理が集中するプロダクトです。監視のアラートも、そうした時間帯にまとまって届く傾向にあります。そのアラートを流す Slack のチャンネルは、本番にも検証環境にもいくつもあります。これまで人の目が届いていたのは本番の分だけで、検証環境までは手が回っていませんでした。その本番だけでも 1 日に何十件も通知が流れます。

ただ、通知のほとんどは対応の要らないもので、たとえば次のようなものがあります。

-   定期処理が動く時間に、CPU の使用率が一時的に上がる
-   DB が一瞬遅くなり、遅い SQL の警告が出る
-   想定どおりの動きなのに、エラーとしてログに残る

こうした対応の要らないアラートを**アラートノイズ**と呼びます。本来は直して鳴らないようにすべきですが、影響がないと確認できたアラートについては、目の前の開発を優先して、鳴らないようにする根本対応が後回しになっていました。

困るのは、アラートノイズの中に**直近のリリースで入った本物の不具合が混ざる**こと点です。見落とさないためには、結局すべての通知に目を通すしかありません。

1 件ずつ見ると、やることはだいたい同じです。

1.  通知を開いて、どのサービスの何のエラーかを見る
2.  既出のエラーかを思い出す、または調べる
3.  初めてなら Datadog でログや trace を追い、コードを読む
4.  直すべきなら直す。直し中なら、その PR を探してリンクする

手順は決まっているのに、毎回「既出のエラーか」を思い出すところで時間がかかります。しかも、どれがアラートノイズかは見てきた人の頭の中にしかなく、**人に依存してしまう**問題もありました。そこを エージェント にまかせられないか、というのが出発点でした。

## 巡回の仕組み

「haro」 には、カスタムエージェントを決まった日時に起動する「スケジュール」という機能があります。そこに、バクラク勤怠の調査用のエージェントを 1 時間おきに起動するスケジュールを 1 本置いています。Datadog は当初は本番だけで、検証環境は後で述べる Agent からの提案を受けて追加しました。さらに、このエージェントには 『Coding Agent からアップロードされた HTML アーティファクトを表示でき、かつそれの任意箇所にコメントをつけることができる謎の社内プロダクト』（[haro の記事](https://tech.layerx.co.jp/entry/why-we-built-our-background-agent)でも少し触れているものです。）をつないであります。巡回が作る調査ページも、ここに置いています。

もう 1 つ、同じ社内プロダクトに**巡回用の Wiki**（ナレッジをためておく、Markdown で書いたページ）を置いています。これまでに出たアラートの見分け方と判定をまとめた「既知の事象」と、要対応かどうかの判定基準が書いてあり、巡回は毎回これを読んでから振り分けます。Wiki の中身と育て方は、あとの章で詳しく紹介します。

1 回の巡回でやることは次のとおりです。

1.  アラートのチャンネルをすべて読み、直近 1 時間の通知を集める（本番も検証環境も）
2.  巡回用の Wiki の「既知の事象」と照らして、**要対応 / 要確認 / 対応不要** に振り分ける
3.  要対応・要確認は Datadog のログとコードで原因を調べ、調査ページにまとめる
4.  今まで出たことのないエラーなら、リリース起因の可能性があるので、人にメンションして早めに知らせる
5.  直し方がはっきりしていれば draft PR を作り、Slack に調査ページ・PR・変更の概要を投稿する
6.  最後に、巡回用の Wiki を更新する

haro のスケジュール（平日 9〜21 時、1 時間おき）① アラートを集める本番・検証環境の Slack② 振り分けるWiki の既知の事象と照らす③ 調べるDatadog とコードで対応不要理由を残す④ 人に知らせる初めて出たエラーなら⑤ draft PR を作る直し方がはっきりしたら⑥ 巡回用の Wiki を更新既知の事象・対応中の PR・改善記録次の回は更新した Wikiを読んで振り分ける人間がやることSlack に上がった調査ページと draft PR を読んで、merge するか決める

## 約 3 週間半運用してみて分かったこと

10 月下旬から約 3 週間半、平日に回し続けました。

-   作られた調査ページは **271 件**。そのうち PR まで進んだものが 33 件
-   アラートを起点に作った修正 PR は 29 本で、そのうち **18 本が merge** された
-   巡回用の Wiki の「既知の事象」は 30 個まで育った

この巡回でいちばん効果が大きかったのは、**実はアラートノイズを減らせたことでした**。

人が見ていたころは、アラートノイズは既知のノイズと判断して次へ進むのが精一杯で、原因から直すところまでは手が回りませんでした。巡回は、同じアラートが何度も鳴ると原因を調べ、**そもそも鳴るべきでないものなら、鳴らなくする修正の PR を出します**。

-   想定どおりの動きなのに error ログを出していたものを、warn に下げるか、ログを出さないようにする
-   ユーザーの入力や操作の順番が原因なのに 500 を返していたものを、400 系のエラーで返すようにする
-   監視の検知時間が短すぎて、待っているだけの処理を異常と誤検知していたものを直す

こうした「誤検知やノイズを解消する修正」の PR が 17 本出て、そのうち 9 本が merge されました。

鳴る必要のないアラートが減るほど、残ったアラートは本当に見るべきものになっていきます。直近のリリースで入った不具合が混ざっても、ほかの通知に埋もれにくくなってきました。

## エージェント が巡回のやり方を自分で直す

回し始めてすぐ、同じ失敗が何度も起きました。

-   前の回で調べ終わった事象を、次の回でまたゼロから調べ直す
-   同じ原因で鳴り続けるアラートに対して、**同じ修正の PR を何本も作ってしまう**
-   ログの検索の仕方が少し違うだけで件数が 0 件や 1 桁少なく出て、「初めて出たエラー」と取り違える

スケジュールの指示（prompt）を毎回人が直してもいいのですが、それだと自分がボトルネックになります。そこで、巡回が**毎回の最初に読み、最後に書き戻す** Wiki のページを用意しました。ページは次の 2 つです。１ つ目はアラートについての知識、2 つ目は巡回のやり方そのものをまとめたページです。毎回の巡回では、まず 2 つ目で手順とルールを確かめ、調べる前に 1 つ目を読みます。

1\. 勤怠アラート対応ナレッジ調べる前に読み、調べた後に直す2\. 初期設定と手順改善1の配下に置いている毎回最初に読むページ監視しているチャンネル判定基準既知の事象対応中の PR・調査初期設定（人が決める）同じ PR を作らないための確認有効なルール改善記録要承認の変更提案

図2: 巡回用の Wiki の 2 ページ。緑は巡回ごとに書き足していくところ、黄色は人の承認を待つところ

### 改善記録からルールに格上げする

巡回中に エージェント がミスをしたり、手順どおりに進まなかったりすると、エージェント が「改善記録」に 1 行書きます。形式は「何が起きたか → 次からどうするか」です。

```
- 11/12 16:31 エラーコードで件数を数えたら 0 件だった。このサービスのログでは
  コードが別の属性に入っていた → エラーコードで数えるときはその属性を使う
- 11/12 17:31 ナレッジの件数を同じ数え方で数え直したら、1 桁少なかった
  → 「有効なルール」に格上げ
```

同じ学びが 2 回以上出たら「有効なルール」に格上げし、次の回からはそれに従います。

巡回でつまずく調べ直し・数え間違い・PR の重複改善記録に 1 行起きたこと → 次からどうするか有効なルールに格上げ同じ学びが 2 回以上出たら次の回の最初に読む同じ失敗をしない要承認の変更提案人間が承認して設定を変えるエージェントが変えられないことならそれでも残るつまずきはまた書き残す

図3: つまずきを書き残し、ルールに格上げして、次の回から従う

3 週間半で、こうして格上げされたルールが 5 本、改善記録は 20 行ほどになりました。

「同じ修正の PR を何本も作る」問題は、**PR を作る前に、同じ修正の PR がすでに無いかを確かめる手順**を Wiki に書いてからは起きなくなりました。エージェント はopen の PR と直近 14 日に close された PR を一覧し、RPC 名や関数名で本文も検索します。さらに、同じファイルを触っている open な PR が無いかも確かめます。

### 変えていいことと変えてはいけないことを分ける

エージェント が自分の手順を書き換えられるのは便利ですが、何でも変えられると怖いです。そこで、エージェント が自分で変えてよいことと、変えてはいけないことを Wiki に書いて分けています。

エージェント が自分で変えてよい

エージェント は変えない（提案だけ）

-   調査の進め方・ログの検索の工夫・確認の順序
-   判定のしきい値（既定の安全上の制約を緩めない範囲）
-   調査ページや Slack の文面

-   監視するチャンネル・メンション先・通知先
-   担当範囲

エージェント が変えたほうがよいと考えたときは、「要承認の変更提案」に書いて、Slack で知らせてくれます。たとえば「検証環境のログが読めないので、検証環境の Datadog の MCP を足してほしい」という提案が上がってきて、自分が足しました。その次の回からは検証環境で初めて出た panic の stack をその場で読んで、原因の特定から PR まで進めています。

スケジュールの prompt やエージェントの設定を変えるには人の承認が要ります。だからこそ、**承認が要らない範囲の改善は Wiki で回し、承認が要るものだけが自分のところに来る**、という分担がちょうどよかったです。

## まとめ

アラートの巡回は、手順は決まっているのに「既出のエラーか」を思い出すところに時間がかかる仕事でした。「haro」 のスケジュールで 1 時間おきに回し、振り分け・調査・draft PR までまかせたことで、人がやるのは上がってきた調査と PR を読んで判断することだけになりました。人の手が回っていなかった検証環境のアラートも見られるようになり、鳴り続けていたアラートノイズも、原因から直して減らせています。そして、アラートノイズの見分け方は人の頭の中ではなく Wiki に残るようになりました。

巡回が毎回読んで書き戻す Wiki を置いたことで、**回すほど既知の事象が増え、調べ方のルールが増え、同じ失敗をしなくなっていきます**。巡回を任せるだけでなく、巡回のやり方の改善まで任せられるのが、Background Coding Agent を定期で回すおもしろさだと感じています。**巡回の手順や Wiki の分け方、エージェント が自分で変えてよい範囲の決め方などは、ほかのプロダクトのアラートにも使えるはずです。今後は、自分がいるバクラク勤怠だけでなく、ここで得た知見をほかのプロダクトにも広げていこうと思います。**

自分は今年の 4 月に新卒で入社したばかりですが、プロダクトの開発だけでなくプロダクトの運用の仕組みそのものを AI で作り変えることにも挑戦させてもらえています。新卒でもこうした挑戦ができる環境ですし、AI の活用も間違いなく進んでいる会社だと思います。
