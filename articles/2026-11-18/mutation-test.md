## ユニットテストとカバレッジ

AIが作り散らすものを検査するために、テストカバレッジは有用な指標です。

カバレッジだけを見ると意味がないという意見も分かりつつ、僕はそういう単純カバレッジでも意味があると思っています。

特に Dependabot などで依存ライブラリを更新するためには高いカバレッジがあることで、安心して運用できるようになります。少なくともカバーされてる範囲は実行され、テストが通ってるわけですからね。

ただ、単純な分岐カバレッジは(実装対象によりますが)経験的に 85%+ ぐらいから費用対効果がサチってきます。むしろ 95% からは「テストのためのテスト」になりがちなため、有害だとすら思っています。(純粋な数値計算ライブラリなどなら、この限りではありませんが....)

ユニットテストで本番リソースにアクセスできないとき、ネットワークやFSなどの外部へのIOをモックしてテストを書かざるを得なくなり、そこがどうしてもトートロジーな「テストのためのテスト」が出てしまいます。そのために本物の実装に近い高品質なモックが必要になったり、そもそも Adapter/Driver パターンで腐敗防止層を作ったつもりが分離しすぎ、モックを推奨するロンドン学派としない古典学派に意見の違いがあるわけです。

## MC/DC カバレッジはどうだろう？

テスト品質を高めるためにどうしたらいいか。たとえばより厳密なカバレッジを測るのに、個々の条件が単独で判定結果を変えることを確認する MC/DC カバレッジというものもあります。

たとえば sqlite3 は様々なデバイス環境で運用されることを想定されるので、 MC/DC 100%を実施しています。これが先に書いた、カバレッジ100%が有用な例です。

航空業界のガイドラインでも要求されるらしいですね。

ちなみに、MC/DC カバレッジを計測する基盤が LLVM がサポートしたのですが、Rust だとまだサポートされてません。見たところちょうど今実装中みたいです。

しかし、MC/DC 100% でも前述したモック品質の問題などは解決しません。

## ミューテーションテストをやるぞ

ここで考え方を変えます。デッドコードの候補を見つけながらテストの品質を測ることができれば、100%未満でもその有用性を担保できる、と考えます。

これはある種の「サボる」方法ですが、ミューテーションテストはその手法が非常に巧妙です。詳しく知りたい方は Google の Mutation Test のペーパーをご覧ください。

簡単に言うと、ミューテーションテストは今あるコードに対して、意図的にソースコード側の比較演算子などを書き換えてテストを行います。書き換えたコードをミュータントと呼びます。

-   Killed: ソースコードを書き換えた結果、テストが落ちたミュータントです。テストが変更を検出できた、とみなせます。
-   Survived: ソースコードを書き換えてもテストが落ちなかったミュータントです。テストが変更を見逃している可能性があります。

つまり、実際に振る舞いが変わるようにソースコードを書き換えてもテストが通るなら、その違いを検査できていないわけですね。ただし、どんな入力でも元のコードと振る舞いが変わらない「等価ミュータント」もあります。これはテストを追加しても落とせないので、生き残ったから全部悪いテスト、というわけではありません。

ユニットテストが実装コードに対する品質保証なら、ミューテーションテストはテストコードに対する品質保証です。

```
function isBiggerThanThree(n: number) {
  return n > 3 // ここで > の部分を < や >= に書き換える
}
test("0は3より大きくない", () => {
  // 境界値の検査が足りないテストコード
  expect(isBiggerThanThree(0)).toBe(false);
})
```

このテストだと `>` を `<` に変えたミュータントは落ちますが、`>=` に変えたものは通ります。`3` ちょうどを渡して `false` になることも検査したいわけです。

なぜ `if` の条件や `>` のような比較演算子を書き換えるかというと、CFG(コントロールフローグラフ)で考えるとわかりやすいです。  
プログラム上で実際の分岐を発生させるのはこれらの条件の判定結果であり、そこを書き換えることで、 **分岐を壊したときにテストが落ちるか** を確認します。分岐に限らず、`+` を `-` に変えたり、戻り値を書き換えたりすることもあります。

ただし、対象は当然管理してるソースコードのみで、確率的な乱数やプログラム外の外部IOまでは保証できません。それはインテグレーションテストの責務になります。で、当然インテグレーション側もミューテーションテストは応用できます...が、ミュータントごとに関連するテストを繰り返すので、当然元のコードの遅さに引きずられます。試しに playwright でも試してみたんですが、元が10秒とかかかるテストだとして、16個のミュータントをそれぞれそのテストで検査すると、単純計算で 10秒を16回繰り返します。

## ミューテーションテストの運用方法

基本的に、「ユニットテストの品質」を計測するツールだと考えるのが良いでしょう。特にIOのない数値計算などに有用です。これはミリ秒単位の速いテストを高速に繰り返す用途が向いています。それ以上は、費用対効果が微妙になってきます。

ミューテーションテストは、CIで回すものというより、リファクタリング用のツールと捉えたほうがいいと思います。CIなどで常に全件実行する必要はない、というかおそらく不可能です。対象を絞るか、あとで紹介する mizchi/mutator のように HEADとの差分だけテストするように工夫する必要があります。1日1回裏で回してダッシュボードを作っておく、などなら有用かもしれません。

この点では、決定的な指標というより、循環複雑度などと似たようなリファクタリング指標として扱うことができるでしょう。

また、ミューテーションテストは主にテスト側の品質チェックに使うのですが、結果的にコード側のデッドコードの候補も払い出せます。

```
  if (x > 0) {
    // 前の分岐を満たす以上、常に false
    if (x < -1) {
      // dead code
    } else {
      // ...
    }
    return -1;
  }
```

「テスト多いけど、これ本当に効いてるの？」という疑問を解消するのに非常に有用です。実装の振る舞いを変えても常に通るなら、その違いを検査できていないので、テストを見直す必要があります。これがテストカバレッジの考え方と違う視点になるわけで、ミューテーションテストの観点だと、削除してもテストが落ちないコードは、テストが足りないのか、そもそも不要なのかを考える対象になります。

## @mizchi/mutator の紹介

で、ここまで前置きなんですが、JS用には既存の StrykerJS があるんですが、実行時間が長いので最適化したい、が Vitest 時代の今にはちょっと向いてない作りに思えたので、自分で作り直しました。

静的検査とGitの差分検出によって現時点の変更コードに対してチューニングすることで、AIコーディングのように繰り返しコードを変更する際でも高速に運用できます。型チェックが通らないミュータントをテスト前に除外したり、変更していない実装とテストの結果をキャッシュから再利用したりして、実際にテストを回す量を減らしています。

たとえば、`cookie-es` のベンチマークでは、全体の初回実行が12.2秒、1箇所変更したあとの `--since HEAD` による差分実行は0.71秒でした。Apple M3 Pro / Node.js 24 で、各2回の平均です。今の変更に対して繰り返し回す用途を詰めています。

### 最速で導入する

Node.js 24 以上で、既に Vitest 5 のテストが動いてるプロジェクトなら、まずこれを入れます。既存の `vitest.config.ts` や `vite.config.ts` をそのまま読み込むので、テストを書き直す必要はありません。

```
pnpm add -D @mizchi/mutator
```

設定なしでも `src/` 以下を対象に動きますが、対象を絞ったりレポートを出したりするなら、プロジェクト直下にこれを置きます。

mutator.config.ts

```
import { defineConfig } from '@mizchi/mutator';

export default defineConfig({
  include: ['src/**/*.{ts,tsx,js,jsx}'],
  exclude: ['src/generated/**'],
  reporters: ['text', 'html', 'json'],

  // Vitest の設定を自動検出できないときだけ指定
  // vitestConfig: 'vitest.config.ts',
});
```

`include` は書き換える実装コード、`exclude` はそこから除外するコードです。パスはプロジェクト直下からの相対パスなので、`lib/` に実装があるならそこに合わせてください。`*.test.*` や `*.spec.*`、`__tests__/` 以下は最初から除外されます。

キャッシュとレポートは `.mutator/` に出るので、`.gitignore` に追加しておきます。

.gitignore

```
.mutator/
```

あとは実行するだけです。

```
pnpm exec mutator
```

この設定だと、ターミナルの出力に加えて `.mutator/report/index.html` と `.mutator/report/mutation.json` が出ます。設定ファイルを別の場所に置くなら `--config-file`、Vitest 側の設定を指定するなら `--config` です。ここは別物なので注意してください。

全件実行が重かったら、差分だけに絞ります。

```
# 最後のコミットからの作業中の変更だけ
pnpm exec mutator --since HEAD

# main ブランチからの変更だけ
pnpm exec mutator --since main
```

差分内にミュータントがなければ調べるものもないので、最初に全体を見たいときは `--since` なしで実行してください。2回目以降は結果をキャッシュして、変更された実装やテストに関係するものだけ再実行します。

詳しくは SKILL を同梱してるので、こちらを参照してください。

## とりあえずやってみて考える

AIがある今、手間が必要なツールも導入は非常に簡単です。その分、 Config Slop 的な状態になる可能性もありますが、そこは人間がなんとかしてください。

形式仕様のモデル検査などと比べると、理論的な部分が少なく比較的直感的に扱うことができます。またAIもミューテーションツールの運用が非常にうまく、これを見てテストを修正するのがうまいです。ネットに上がってるものは全部暗記してるみたいなやつですからね。

CIで常駐するものでもないので、適当なブランチでやっておいてテストを修正して後で捨てる、みたいな運用も可能です。

早くて安くてうまい部類のツールなので、ぜひ使いこなしましょう。
