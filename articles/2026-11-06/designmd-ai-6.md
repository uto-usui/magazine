AI に「お問い合わせのセクションを作って」と頼みました。  
渡すものを 3 通りに変えて、それぞれ 2 回ずつ。合計 6 回です。

下の 3 枚は、そのうちの 3 回分です。

![AI が作った 3 つのお問い合わせ画面を縦に並べた比較。上から A、B、C](https://static.zenn.studio/user-upload/346b72c4d92c-20261106.png)

どれが一番いい点だったと思いますか。

私は A だと思いました。  
左右に分かれていて、ボタンの下に影がずれて重なっていて、見出しに罫線つきのラベルがついている。  
手間のかかり方が、ほかの 2 枚と違います。

答えはこうでした。

![同じ 3 画面に条件と点数をつけたもの。A は仕様書なしで 1 点、B は古い仕様書で 3 点、C はいまの仕様書で 7 点](https://static.zenn.studio/user-upload/05bb87345816-20261106.png)

A が 1 点。C が 7 点。7 点満点です。

A は、仕様書を渡さずに作らせたものでした。  
C は、いまの仕様書を渡したものです。

一番ていねいに見えた A が、最下位でした。

この差が、あとで効いてきます。

## 知りたかったのは、仕様書が古いときの話

サイトの色を変えたときに、仕様書を直し忘れていたんです。

「仕様書を書くと AI がちゃんと作る」という話はよく聞きます。  
知りたかったのはその先でした。仕様書が実物とずれていたら、どうなるのか。

## 古い仕様書の結果

B は 2 回とも、出てきた色が 7 個ありました。  
その 7 個すべてが、古い仕様書に書いてある値でした。

![古い仕様書から出た 7 色と、実際のサイトで使っている色の色見本。重なるのは白だけ](https://static.zenn.studio/user-upload/82475cf6b927-20261106.png)

上の段が、古い仕様書を渡して出てきた色です。  
下の段が、実際のサイトで使っている色です。

重なっているのは白だけです。

古い仕様書には、藍色だけが書いてあったわけではありません。  
文字の色も、罫線の色も、カードの背景も、全部書いてありました。  
AI はその全部を、正確に使いました。

正確に、間違えました。

## 揺れないほうが怖い

仕様書を渡さなかった A は、毎回ちがうものになりました。  
色だけではありません。上の表のとおり、ボタンの角丸が

-   1 回目 → `border-radius: 0.25rem`（ほぼ角）
-   2 回目 → `border-radius: 999px`（完全な丸）

と、見た目が別物になるところまで振れています。  
背景の書き方も、1 回目は `#f6f1e8`、2 回目は `oklch(97.5% 0.012 85)` で、色空間の記法そのものが変わりました。

これは想像どおりでした。「仕様書がないと揺れる」のは、誰でも予想がつきます。

厄介なのは B のほうです。  
B は 2 回とも、7 色・背景・行間・角丸まできっちり同じでした。ブレがありません。

揺れていれば気づきます。  
揃っていると気づきません。

しかも B の画面は、壊れていません。色は揃っているし、余白も整っている。  
単体で見れば、きれいにできています。  
ずれているのは実物とだけで、そのずれに気づく手がかりが、出力の中にありません。

## B だけ、レイアウトが素っ気ない

ここからは、実験を始めたときには考えていなかった話です。

もう一度さっきの 3 枚を見ると、B だけ左右に分かれていません。  
A も C も 2 カラムで、B だけ 1 カラムです。これは 2 回とも同じでした。  
B の CSS に出てくる flex は、ボタンの `inline-flex` だけで、レイアウト用の grid はありません。

理由を探して、2 つの仕様書を見比べました。

古い仕様書は 332 行あって、色は 7 色きっちり書いてあります。  
でもレイアウトの話は、ほとんど書いていませんでした。  
あるのは最大幅（`768px` / `1024px`）とブレークポイントの一覧だけで、  
**どのセクションを何カラムにするか**の指定はありません。

いまの仕様書は 581 行で、「このセクションは 2 カラムグリッド」「1024px 以下で 1 カラム化」と  
具体的に書いてあります。C はそのとおりに作っていました。

つまり、こういうことが起きていました。

-   仕様書に**書いてある**項目は、そのとおりになる。古い値でも、そのとおりになる
-   仕様書に**書いていない**項目は、仕様書を渡さなかったときより大人しくなる

書き忘れた項目が自由になるのではなく、縮こまるほうに倒れました。  
なぜそうなるのかは分かりません。6 回ぶんの観察なので、断定もしません。

ただ、これは自分の仕事の順番を変える話でした。  
仕様書を書くときに気にしていたのは「書いた内容が正しいか」でしたが、  
同じくらい「何を書かなかったか」が効いています。

## 測り方のほうが、先にまちがえていました

正直に書いておきます。

この記事を書く途中、一度まちがった結論を出しました。

3 枚の画面を並べるために、ブラウザの幅を 900px にしてスクリーンショットを撮りました。  
そうしたら A だけが 2 カラムで、B も C も 1 カラムに見えました。  
それで「仕様書を渡すと AI はレイアウトの発想をやめる」と考えました。

ちがいました。  
C の CSS には `@media (max-width: 1024px)` で 1 カラムに折り返す指定があって、900px はその内側でした。  
幅を 1280px にして撮り直したら、C はちゃんと 2 カラムでした。

データは最初から正しくて、見る窓のほうが狭かっただけです。

採点のコードでも、同じことが起きていました。  
最初に書いた採点コードには不備があって、結果を見たあとに作り直しています。  
不備は 4 つです。

1.  `var(--x)` を解決していなかった。いまの仕様書は「CSS 変数を使え」と指示するので、**従うほど損をする**採点になっていた
2.  ボタンのクラス名を `btn|button` に決め打ちしていた。C の出力は `.contact__link` だった
3.  色が `:root` に**定義**されているだけでも「使っている」と数えていた
4.  `@media print` の背景（`#fff`）を、ページの背景として数えていた

7 項目の中身は変えずに、読み方だけを直しました。

```
# 直したあと: コメントと @media print を除き、var() を :root の値で解決してから見る
def make_resolver(decls):
    vars_ = {}
    for sel, p, v in decls:
        if p.startswith("--") and re.search(r"(^|[\s,])(:root|html)\b", sel):
            vars_.setdefault(p, v)
    ...
```

直す前と直したあとで点数は変わりました。C が 5 点から 7 点へ、A が 2 点から 1 点へ。  
どれも私のミスです。

仕様書が腐る話を書いているつもりでしたが、  
測る道具のほうが先に腐っていました。2 回とも。

## 仕様書は、ブレを消す道具です

今回のことで、自分の中の位置づけが変わりました。

仕様書は、品質を上げる道具ではなくて、ブレを消す道具です。

揃えたいときには効きます。複数人で作るとき、同じものを何度も作るとき、  
ブランドの色を間違えたくないとき。今回の C がそうです。

広げたいときには効きません。  
最初の案出しや、方向を探している段階では、渡さないほうが広い球が返ってきます。  
今回の A がそうです。

そして、中身が古いときは、黙って事故ります。今回の B です。

だから、渡すかどうかを毎回決めることにしました。  
いつも渡す、でもないし、いつも渡さない、でもない。

## 決めたこと

実験のあとで決めた運用です。難しいことはしていません。

1.  **仕様書は実物から作る。** 今回、採点の正解に使ったのは実際のサイトの CSS でした。頭の中から書くと、書いた瞬間から実物とずれ始めます
2.  **見た目を変えたら、同じ作業の中で仕様書も直す。** 別のタスクにすると、まず忘れます。私は忘れました
3.  **仕様書の冒頭に「いつ時点のものか」を書く。** 古いかもしれない、と読む側が疑えるようになります
4.  **書いていない項目を確認する。** 今回でいえばレイアウトです。書き忘れた項目は自由にならず、縮こまります
5.  **案を広げたいときは、渡さないで 1 回やってみる。** 今回いちばん意外だったのがここでした
6.  **測る側を疑う。** 点数が動いたときも、画面が変わって見えたときも、まず自分の測り方を見ます。今回は 2 回ともそこでした
