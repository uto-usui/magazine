最近、トークンマキシングならぬポケモンマキシングをして、ぽこあポケモンの図鑑コンプしました。（時が過ぎるのははやい）

２年前には「基本機能」と呼ばれる SmartHR 最大の Rails アプリケーションに、コネクションプーラーを導入しました。

この記事では、導入にあたって検討した技術的な背景や選定理由をご紹介します。

## 背景

SmartHR の「基本機能」では Cloud Run を使用しており、リクエスト数や負荷の増加によってオートスケールします。 サービスの成長に伴ってトラフィックが増えると、スケールアウトしたコンテナがそれぞれコネクションを確保するため、データベースのコネクション数が上限に達してエラーになる事象が月に１回程度発生していました。

※ SmartHR では PostgreSQL を利用しており、最大接続数に達すると、データベースへの新しい接続がすべて拒否され、エラーが発生します。

以前データベースの負荷を軽減するために「基本機能」にリードレプリカを導入する事例をご紹介しました。 [tech.smarthr.jp](https://tech.smarthr.jp/entry/2025/07/11/081458)

しかしその後もサービスは成長を続け、あるときから複数の処理で同時多発的にこのエラーが発生するようになり、サービスにアクセスしづらくなる障害がたびたび発生していました。

[support.smarthr.jp](https://support.smarthr.jp/ja/info/status/b-_7cmds73/)

デプロイでトラフィックを切り替える際にも、コンテナ数の増加によってコネクション数が増え、アラートやエラーが発生して安心してデプロイできない状態でした。 障害の頻度が急に増したため、緊急対応チームを組成して対応にあたりました。

メトリクスを確認すると、データベースのコネクションの大半は、クエリを処理していない idle コネクションでした。

![データベースコネクション数のメトリクス](https://cdn-ak.f.st-hatena.com/images/fotolife/s/smarthr/20260804/20260804091906.png)

コネクション数のメトリクス

そこで、大半のコネクションが idle な状態だったことを踏まえ、データベースコネクションをコネクションプーラーに集約させることにしました。 アプリケーションはコネクションプーラーに接続し、コネクションプーラーがデータベースへの少数のコネクションを使い回すことで、データベース側のコネクション数を抑えられます。 常時接続するコネクションが減ることで、データベースのメモリ使用量の削減も期待していました。

## コネクションプーラーの選定

導入した当時はマネージドコネクションプーラーがリリースされていなかったため、コネクションプーラーをセルフホストすることにしました。

[docs.cloud.google.com](https://docs.cloud.google.com/sql/docs/postgres/managed-connection-pooling?hl=ja)

コネクションプーラーには定番の PgBouncer ではなく、PgCat を導入しました。

PgCat は PgBouncer とある程度互換性があり、Instacart 社の導入事例では、本番ワークロードで PgBouncer と遜色ないレイテンシで動作し、ピーク時には約105k QPS（1秒あたりのクエリ処理数）を処理したと報告されています。 [company.instacart.com](https://company.instacart.com/tech-innovation/adopting-pgcat-a-nextgen-postgres-proxy)

それに加えて、レプリカのフェイルオーバーやシャーディング、クエリのミラーリングをサポートしている点が魅力的でした。

とくにクエリのミラーリングは、当時データベースのスケーラビリティ向上のため AlloyDB（Google Cloud が提供する PostgreSQL 互換のマネージドデータベースサービス）への移行を検討しており、新旧データベースへ同じクエリを流して結果を比較検証する用途に使えそうだったため魅力的に見えました。

[github.com](https://github.com/postgresml/pgcat)

なお、PgCat は現在開発が止まっているようなので、これから導入する場合は注意してください。

※ 開発停止やセルフホストの運用コストを理由に、「基本機能」はすでにマネージドコネクションプーラーに移行しています。その話はまた後日

### アーキテクチャ

PgCat は Compute Engine 上のマネージドインスタンスグループ（以下 MIG）として稼働させ、前段に内部ネットワークロードバランサーを配置しました。 アプリケーション（Rails と Sidekiq）は ロードバランサー経由で PgCat に接続します。

![コネクションプーラーアーキテクチャ図](https://cdn-ak.f.st-hatena.com/images/fotolife/s/smarthr/20260804/20260804091902.png)

コネクションプーラーアーキテクチャ図

「基本機能」のリードレプリカは明示的に接続を使い分ける実装にしていたため、Primary と Replica それぞれにロードバランサーを立てる構成にしています。

PgCat の [Load balancing of read queries](https://github.com/postgresml/pgcat#load-balancing-of-read-queries) を使えば Primary と Replica を一つのエンドポイントで扱えそうでしたが、検証する余裕がなかったので、既存の実装に手を入れずに済む、アプリケーション側から見てシンプルな構成を優先しました。

なお、マイグレーションやデータパッチなど一部の処理は、後述する制約のため PgCat を経由せず、Cloud SQL に接続します。

### 実行基盤に Compute Engine を選んだ理由

PgCat の実行基盤には、Compute Engine と Container-Optimized OS を採用しました。

PgCat は PostgreSQL の TCP 接続を待ち受ける必要があります。 App Engine、Cloud Run、Cloud Functions は HTTP ベースのリクエスト処理を前提とした PaaS であり、独立した TCP サーバーを公開する用途に向きません。 Cloud Run のサイドカーとして動かすワークアラウンドはありますが、プールがコンテナ毎に分かれてしまい、コネクションを集約するという今回の目的に合いませんでした。 残る選択肢は GKE と Compute Engine です。

「基本機能」は Cloud Run / App Engine ベースの環境で稼働しているため、GKE を選択すると、クラスタの構築、ネットワーク設計、クラスタ内の権限整理といった作業が新たに発生します。今回の導入は、直近発生している障害の再発防止策として短期間での完了を目標としていたため、これらの作業を行うと目標期日に間に合わないと判断しました。 このため、インフラ構築が比較的短期間で済む Compute Engine を選択しています。 運用の自動化や拡張性では GKE に分がありますが、構築スピードを優先しました。

OS には Container-Optimized OS を採用しています。

[docs.cloud.google.com](https://docs.cloud.google.com/container-optimized-os/docs/concepts/features-and-benefits?hl=ja)

PgCat はコンテナイメージが配布されているため、動かすのに必要十分でした。 一方で、Container-Optimized OS は Ops Agent のインストールに対応しておらず、PgCat が出力する Prometheus 形式のメトリクスを Cloud Monitoring へ送信することが素直にはできませんでした。 こちらの件は社内の OpenTelemetry の有識者に声をかけたところ、数日で解決方法を見つけてくれて、別途 OpenTelemetry Collector ベースのエージェントを用意することで事なきを得ました。 そのとき出してくれた解決方法は以下のブログ記事で詳しく解説されています。 [zenn.dev](https://zenn.dev/ymtdzzz/articles/5d91bcba9b7463)

### Blue / Green デプロイ

PgCat 自体の更新には Blue / Green Deployment を採用しました。 PgCat が中継するクエリにはバッチ処理の長時間トランザクションも含まれ、更新のたびにコネクションが強制切断されるとアプリケーションへの影響が大きいためです。

Compute Engine の標準機能も検討しましたが、以下の面で要件を満たせませんでした。

-   シャットダウンスクリプト
    -   実行時間の上限が90秒程度で、長時間のトランザクションの完了を待てない
-   ロードバランサーのコネクションドレイニング
    -   既存の接続がなくなるのを待ってから切り替えられるが、アプリケーション側はコネクションをプールして繋ぎっぱなしにするため接続は自然には減らず、最終的にタイムアウトで強制切断される
-   MIG のカナリアアップデート
    -   ランダムなインスタンスを新しいテンプレートで起動し直す仕組みのため、終了時にコネクションが切断されないことを保証できない

そこで、active と standby の2つのインスタンスグループをあらかじめ用意し、ロードバランサーの向き先を切り替える方式にしました。 切り替え後も古い系統はコネクションが自然に完了するまで残しておけるため、コネクションを切断せずに、PgCat を更新できます。

## トランザクションプーリングの制約と接続先の使い分け

PgCat には動作モードが２つあります。

-   セッションモード：アプリケーションから直接繋ぐのとほとんど同じ挙動で、切断するまで同じコネクションを占有する
-   トランザクションモード：トランザクションが完了するたびにコネクションをプールに返して使い回す

今回はコネクションを効率的に使い回したいので、トランザクションモードで導入しました。 このモードにはセッションに依存する機能が使えなくなるという大きなトレードオフがあり、次のような制約が生じます。

-   advisory lock
    -   Rails の `db:migrate` はマイグレーションの並列実行を防ぐためにセッションレベルの advisory lock を獲得するが、獲得と解放のセッションが別になりエラーになる可能性がある
-   カーソル機能
    -   クエリの結果をデータベース側に保持して少しずつ取り出すカーソルが、セッションをまたぐと参照できない
-   プリペアドステートメント
    -   セッション内でサーバーサイドオブジェクトを使い回す仕組みのため利用できない
-   `SET` したセッション変数
    -   セッション内で `SET` した値が次のクエリで引き継がれる保証がなく、セッション変数に依存した仕組みが機能しない。「基本機能」では statement\_timeout などが該当した。

この制約を踏まえて、アプリケーションには PgCat 経由の接続と、Cloud SQL に直接繋ぐ接続の2つを用意しました。 コネクション数の増加を防ぐという導入の目的から、制御できないユーザートラフィックは必ず PgCat を経由させ、マイグレーションやデータパッチなどセッション依存の機能が必要な処理だけ Cloud SQL に直接繋いでいます。

また、statement\_timeout などセッション変数に依存していた設定値はロールレベルの設定に移行し、同等の効果を維持しています。

## 負荷試験による検証

本番導入の前に、staging 環境で負荷試験を実施しました。 目的は性能の測定ではなく、「データベース接続数がボトルネックになる問題が解消されるか」の確認です。

実際のリクエストログの分析に基づいたシナリオで次のケースを検証しました。

-   漸進的な負荷
    -   RPS（1秒あたりのリクエスト数）を増やし続け、導入前に接続数の上限でエラーになっていた RPS を超えてリクエストを処理できるか
-   瞬間的な負荷
    -   重いリクエストの多発で Cloud Run のコンテナが一斉にスケールアウトしても、コネクションを確保しすぎてエラーにならないか

この試験で期待どおりの挙動を確認し、本番へ導入しました。

## 導入後のメトリクスの変化

本番環境へは、様子を見ながら段階的にトラフィックを切り替える形でリリースしました。導入後のメトリクスには期待していた変化がはっきりと現れました。

データベースの接続数は導入前の 1/4 以下で安定するようになりました。

数日間のモニタリングを経てコネクション数起因の障害は収束したと判断できました。

## まとめ

「基本機能」にコネクションプーラーを導入し、idle コネクションによるデータベースコネクション枯渇問題に対処しました。

今回の反省は、データベースが単一障害点だと把握していながら、障害の頻度がいつ上がるのか見当がつかないまま、対応を先延ばしにしていたことです。 問題が顕在化してから対応するのはプレッシャーが大きく、焦る気持ちからミスも増えてしまいます。

今回の障害をきっかけに、SLO（Service Level Objective）の導入が進み、サービスの信頼性への考え方を大きく見直すことになりました。

また、コネクションプーラー導入に関しては多くの人に助けてもらいました。

緊急対応チームを始め、関わってくれた皆さんにこの場を借りて感謝します。ありがとうございました！
