こんにちは、SmartHR でプロダクトエンジニアをしている negiandleek と sakata です。 私たちは横断フロントエンドユニットに所属し、SmartHR 基本機能のフロントエンドに関する課題解決に取り組んでいます。 本記事では、横断フロントエンドユニットが組成された経緯とこれまでの取り組み、そして将来的な展望を紹介します。

## 横断フロントエンドユニットが組成された経緯

SmartHR の基本機能は、従業員情報の管理を担う基盤となるプロダクトで、歴史が古く大きなものです。 そのため、以下のような課題を抱えていました。

-   全体的にモジュールバージョンが古く、更新されていないため、セキュリティに問題がある
-   コードが肥大化し、開発速度が低下し続けている
-   各チームで書き方がバラバラなため、手を入れる際に開発コストがかさむ

これらは主に、機能開発を優先するという事業判断をしていたために発生した組織的な課題です。 さらに、AI の活用が進むなかで、このような課題はより増幅される懸念がありました。

これらの課題を解決するために、横断フロントエンドユニットが組成されました。

## フロントエンドの技術的負債の解消

SmartHR 基本機能では、使用している技術スタックに古いものが多く残っています。 これらを保守していくことも横断フロントエンドユニットのミッションの1つです。 ここでは、その取り組みをいくつか紹介します。

### jQuery のメジャーアップデート

基本機能では、比較的新しい画面は React で作られていますが、古い画面は jQuery を使用しています。 今回のメジャーアップデート前は 1.12.4 を使用していました。このバージョンはすでにサポートが終了し、脆弱性も存在している状態でした。

しかし、ひとくちにメジャーアップデートをするといっても、簡単なものではありません。 jQuery を使用して動いている画面が多いため、変更に伴う影響範囲も広く、品質を担保しながらメジャーアップデートを行う必要がありました。 そのため、AI を使いつつ、事前に修正できる箇所の洗い出し・テスト設計を行いました。また、コードレビューや動作確認をしやすくするために細かく Pull Request を作成し、安全なアップデートを目指しました。

さらに、メジャーアップデート後は一定期間 [jquery-migrate](https://github.com/jquery/jquery-migrate) を導入しました。jquery-migrate は、削除・変更された API の互換性を維持しつつ、非推奨の記法が使われた際に警告を出すプラグインです。これにより、修正漏れがあっても画面を動作させたまま、検出した警告を Sentry に送って検知する仕組みも構築しました。

こうした取り組みの結果、障害を起こすことなく、無事にメジャーアップデートを終えることができました。

### gulp の廃止

古い画面のビルドタスクでは gulp を使用していましたが、これも技術的負債の1つでした。 gulp が使用しているプラグインの一部はメンテナンスされておらず、依存パッケージ経由で複数の脆弱性を引き込んでいる状態でした。 また、多くのプラグインが gulp 本体のアップデートに追従できておらず、更新のボトルネックにもなっていました。 gulp のエコシステム自体が衰退していることも踏まえ、gulp を廃止して npm scripts に移行しました。 移行作業は、一度にすべてを置き換えるのではなく、以下のような粒度で複数の Pull Request に分割して段階的に進めました。

-   生成結果が変わらない処理は、生成済みのファイルをリポジトリにコミットしてタスク自体を廃止
-   CSS のビルドパイプラインは、CLI ツールの組み合わせに置き換え
-   Lint やファイルのコピーなど、残りのタスクもそれぞれ npm script として置き換え

段階的な移行が完了した後、最後に gulp 本体を削除し、脆弱性の懸念を解消することができました。

基本機能を開発しているチームの中には、専任のフロントエンドエンジニアがいないチームもあります。 そのため、フロントエンドの開発がボトルネックになったり、コーディングガイドラインに沿わない実装が生まれたりすることがあります。

それらの課題を解決するために、以下のようなAIスキルの開発・提供に取り組んでいます。

-   SmartHR 基本機能のコンテキストを組み込んだ AI レビュースキルの拡充
-   Figma を読み込みデザイン実装するスキル

これらの AI スキルを提供することで、専任のフロントエンドエンジニアがいないチームでも一定の品質を担保できる状態を目指しています。

## Jira をやめて Notion でドキュメント・チケットを管理する

横断フロントエンドユニットではドキュメントを Notion で管理しています。 AI ファーストの開発を進める中で、チーム内でコンテキストを失わないためにドキュメントを整備したり、長期にわたる実装計画を Notion に書いたりすることが増えました。

一方、その実装計画に基づくチケット管理は Jira で行っていましたが、いくつかの課題がありました。

-   Notion と Jira を行き来する煩雑さ
-   実装計画が Notion、チケット管理が Jira という二重管理
-   MCP（Model Context Protocol）を複数つなぐことによるトークン量の肥大化

これらの課題を解消するために、ドキュメントとチケットを Notion に統合しました。 結果として、ドキュメントとチケット管理が容易になり、進捗の確認もしやすくなりました。

また、実施した内容が Notion 上にまとまっているため、AI による週次振り返りの精度も上がりました。

## これからの展望

横断フロントエンドユニットは、AI による開発支援の発展とともに、フロントエンドエンジニアが担う領域が拡大していくと考えています。 これまでは、デザイン・コード実装・アクセシビリティ・テストといった領域がそれぞれ分業されていましたが、今後は AI を活用して1人のエンジニアが複数の領域を横断的にカバーしながら開発するようになると予想しています。

そのため、従来の開発プロセスとは異なる、AI 活用を前提とした開発プロセスや開発方法を提供していきたいと考えています。 あわせて、AI による開発が技術的負債を増幅させないよう、テストや Lint、ハーネス（AI エージェントを制御する仕組み）を整えながら既存の技術的負債の解消にも継続的に取り組んでいきます。
