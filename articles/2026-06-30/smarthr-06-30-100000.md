## 人数計上処理とは

SmartHRでは主に「契約したプラン × 課金対象の従業員数（在籍中もしくは休職中の従業員の数）」に応じて請求金額が決まります。 課金対象の従業員数の集計は、基本機能と呼ばれる従業員情報等を持つモノリシックなRailsアプリケーションにて日次でバッチ処理しています。 このバッチと、外部にある契約管理SaaSとの連携を、SmartHRでは「人数計上処理」と呼んでいます。

以降では、基本機能における日次の集計処理にフォーカスします。この処理を担っているのは2つの Sidekiq ワーカーです。 一つは集計ワーカーで、テナントごとの課金対象人数を集計して記録します。もう一つは送信ワーカーで、集計ワーカーの結果を内製の課金システムに送信します。その後、内製の課金システム内の処理を通して外部の契約管理SaaSへと連携されます。 他の処理との兼ね合いで、3時間以内に一連の処理を終える必要があるという制約があります。

## 現状の課題

現在、SmartHRで契約データの移行作業を予定しています。それに伴い、人数計上処理の日次バッチで扱うテナントの数が一気に増えることになりました。移行前は一部のテナント（数百規模）だけが対象ですが、移行後はほぼ全テナント（数万規模）が対象になります。 既存の集計ワーカーは、1つのジョブが対象のテナントを順番に処理する作りでした。

tenant\_ids.each do |tenant\_id|
  tenant = Tenant.find(tenant\_id)
  tenant.switch do
    
    employee\_count = Employee.billing\_target.count
    
    DailyEmployeeCountLog.find\_or\_initialize\_by(tenant\_id:, target\_datetime:).update!(employee\_count:)
  end
end

この作りは対象が数百であれば問題になりませんが、移行後のテナント数では問題になります。 仮に10万テナントとして予測した所要時間は、以下のとおりです。

合計で約3時間18分という予測になり、制約である3時間以内に収まらず超過するリスクが高いと判断しました。 表を見て分かるとおり、ボトルネックは集計ワーカーにありました。全テナントを1ジョブ・1スレッドで直列処理しているため、テナント数に比例して時間が伸びます。テナントを切り替える処理も、テナントの数（10万回規模）だけ発生します。一方の送信ワーカーは、全テナント分を1回のリクエストでまとめて送るため、テナントが増えても時間はあまり伸びません。

## 並行処理で改善する見込み

調査により、改善すべきは集計ワーカーの直列処理だと分かりました。そこで、集計ワーカーを並行して動かすために、処理を親子の2つのワーカーに分割しました。 親ワーカーはテナントを一定件数ずつのロットに分け、それぞれのロットを子ワーカーに渡します。子ワーカーは渡されたロット分のテナントだけを集計します。ロットを分けて配るため、同じテナントが複数の子ワーカーで重複して処理されることもありません。

子ワーカーは並行して動くため、直列だと数時間かかっていた集計が、十数分まで縮む見込みになりました。

### 「すべての子ワーカーの完了後に送信を1回だけ」をどう保証するか

集計ワーカーの処理が終わった後に、送信ワーカーを起動する必要があります。集計が終わる前や、集計処理が一部失敗した状態で送信が走ると、不完全なデータを外部システムへ送ることになります。

送信を起動するタイミングをどう決めるか、いくつかの方式を検討しました。

-   cron で送信を別起動する方式
    -   送信を集計とは別の時刻の cron で起動する案。集計が想定より長引いたとき、未完了のまま送信が走るリスクがあり、タイミング依存になる
-   完了数を自前でカウントする方式
    -   完了した子ワーカーの数を数え、最後の1件が送信を起動する案。複数の子が同時に完了したときの競合や、失敗時の整合性の担保が難しい

最終的には Sidekiq Pro の `Sidekiq::Batch` の持つ仕組みを採用しました。子ジョブ群を1つのバッチとして起動すると、全ジョブの完了時にコールバックが1回だけ呼ばれます。「すべての子ワーカーの完了後に送信を1回だけ」という要件を、自前のロジックではなくライブラリの仕組みで保証できます。

最終的なワーカーの実装は以下の作りになりました。

class CreateEmployeeCountParentWorker < ApplicationWorker
  TENANTS\_PER\_CHILD = 1\_000

  def perform(start\_at = Time.zone.now, options = {})
    tenant\_ids = target\_tenant\_ids
    target\_datetime = calc\_target\_datetime(start\_at)

    batch = Sidekiq::Batch.new
    
    batch.on(:success, self.class, "target\_datetime" => target\_datetime)
    batch.on(:death, self.class, "target\_datetime" => target\_datetime)

    
    batch.jobs do
      Sidekiq::Client.push\_bulk(
        "class" => CreateEmployeeCountChildWorker,
        "args" => tenant\_ids.each\_slice(TENANTS\_PER\_CHILD).map { |lot| \[lot, target\_datetime\] }
      )
    end
  end

  
  def on\_success(\_status, options)
    SendEmployeeCountWorker.perform\_async(options\["target\_datetime"\])
  end

  
  def on\_death(\_status, options)
    notify\_slack\_error("集計の子ジョブが失敗しました", options\["target\_datetime"\])
  end
end

`on_success` と `on_death` は [Sidekiq::Batch](https://github.com/sidekiq/sidekiq/wiki/Batches) のコールバック用のメソッドです。`batch.on(:success, クラス, オプション)` を登録しておくと、すべての子ジョブが成功した時に Sidekiq が自動的に呼び出します。これにより、子ジョブの完了を待ってから送信ワーカーを起動する流れを、cron による分離や自前のカウンタなしで実現できます。

`Sidekiq::Batch` の[コールバック](https://github.com/sidekiq/sidekiq/wiki/Batches#callbacks)には `:complete` もありますが、今回は使いませんでした。`:complete` は失敗したジョブも含めてすべての子ジョブが処理され終わった時点で呼ばれるのに対し、`:success` はすべての子ジョブが成功した時だけ呼ばれます。集計が一部でも失敗した状態で送信したくないため、`:success` を使っています。

### 冪等性を担保して再実行を安全にする

集計結果の記録に使っている `DailyEmployeeCountLog.find_or_initialize_by` は、何度実行しても結果が変わらない冪等な処理として実装されています。これを使っているので、リトライや手動での再実行を安全に行えます。

並行処理にすると、ジョブ単位での失敗とリトライが起きやすくなります。冪等性を担保しておくことで、一部の子ワーカーだけを再実行しても、二重計上などの問題が起きません。

また、特定の日付の集計処理が失敗して後日復旧する場合に備えて、ワーカーの引数で対象の日付を指定できるようにしています。

## 改善予測

予測では、何もしなければ合計で約3時間18分かかり、制約である3時間以内を超過します。親子分割を適用すると、集計ワーカーを並行して動かせるため約40分まで短縮でき、制約に対して十分な余裕が生まれる見込みです。

対応

合計所要（予測）

何もしない

約3時間18分

親子分割を適用

約40分

これらは移行前の計測値からの予測のため、実際の値は移行を進めていく中で計測していきます。

## さいごに

1ジョブで全件を直列処理していた集計バッチを、親子ワーカーに分割して並行処理にしました。並行処理にするにあたっては、冪等性の担保が重要だと感じました。冪等性を担保しておくことで、ジョブ単位の失敗やリトライが起きても、安全に処理を進められます。
