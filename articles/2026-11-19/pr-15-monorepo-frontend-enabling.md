## バクラクのフロントエンドのこれまでと理想

バクラク事業部は、開発するプロダクトの性質もあり、バックエンドに強いエンジニアが相対的に多い組織です。フロントエンドのコード品質やレガシー技術などを改善すべく、2023年に目指す姿を「バクラクフロントエンド Vision」としてまとめ（[資料](https://speakerdeck.com/kikuchikakeru/bakurakuhurontoendo-vision-1-dot-0)、[ブログ](https://tech.layerx.co.jp/entry/2023/08/02/180000)）、有志が集まって「フロントエンドギルド」を立ち上げました。ここでは各プロダクトのエンジニアが集まって、課題を集め、基盤改善やガイドライン作りを行ってきましたが、これは草の根活動で行われてきたため、リアーキテクチャのように時間の必要な活動を片手間で行うのは難しいという声が出ていました。

フロントエンド技術への投資は、プロダクトが増える速度が上がるほどに、重要性が高まる領域です。ここに腰を据えて向き合う人がいれば、プロダクト開発をもっと速く、もっと安心して進められるようになります。そこで2025年の秋から、ギルドからスピンオフする形で Frontend Enabling を推進する部隊を組成し、monorepoのパフォーマンスと信頼性の改善、テスト基盤の構築、CIの高速化などに取り組んできました。

わたしたちが目指すのは、各チームにフロントエンドのスペシャリストがいなくても、**最良の技術と設計の上で、安全・高速にプロダクトを届けられる状態**です。一方で今は、monorepo の統合や古参アプリのリアーキテクチャはまだ道半ばで、品質の多くを人のレビューに頼っています。マージされるPR数が1年で5倍になったいま、この差を埋める投資の重要性はますます高まっています。

例えば、React の useEffect() の誤用によるバグは、これまでスペシャリストがコードレビューで指摘することの多かった問題の一つです。こうした問題を個々のレビューに頼らず防げるよう、誤用を避けられる設計を仕組みとして整えていくことが望ましいと考えています。単にlintを設定するに留まらず、そのような安全が全プロダクトに整備されていく流れそのものをつくることが、これからの Frontend Enabling の役割の1つといえるでしょう。

安全・高速にプロダクトを届けられる状態に近づくには、全プロダクトに共通する基盤を整え続けること、これから必要になる技術を先回りして検証すること、未来を見据えて技術戦略を考えていくこと、これらが欠かせません。この投資に腰を据えて取り組む専任のメンバーを、わたしたちは探しています。

## なぜいま Frontend Enabling なのか

LayerXではBet AIを標語に、Claude CodeやCodexのようなローカルのCoding Agent の活用に加え、内製のBackground Agent（[登壇資料](https://speakerdeck.com/layerx/built-our-own-background-agent-at-layerx-number-aidevex-findy)）も開発しています。フロントエンドのコードを触った PR は1年で5倍以上になっていて、増えた分の7割以上をフロントエンドを含むPRが占めています。バックエンドを得意とするエンジニアに加え、PdM・デザイナーによる貢献もあります。そのような中で、人間、特にフロントエンドのスペシャリストがコードを1行ずつ読んでレビューすることはもう難しいでしょう。

そのような中、フロントエンドの「基盤に投資する」「安全に維持し続ける」活動がますます重要になっていきます。変更の量が増えるほど、品質と速さを左右するのは一つひとつのコードよりも、全プロダクトに共通する基盤と検証の仕組みになるからです。多くのプロダクトが1つの monorepo に載っているバクラクでは、たった1つの改善や10%の高速化が、すべてのプロダクト、チームメンバー、そして Coding Agent を同時に改善し、お客様に届く価値を高めます。

つまり、フロントエンドスペシャリストの専門性の重心は、事業全体にレバレッジが効くものへと移っていくのだと考えています。

## Frontend Enabling は何をするのか

わたしたちは Frontend Enabling の役割を、大きく2つの柱で考えています。

-   **事業を止めない技術基盤**：ビルド、CI、依存関係、テストなど、開発の速度と信頼性を支える足場をつくる。
-   **事業価値を広げる技術投資**：新しいプロダクトや体験を速く安全に届けるための、共通部品や設計に投資する。

特に、事業の成長スピードを下げない・速くするための足場作りは、喫緊でテコ入れしたい点です。その一例が、フロントエンドに特化したハーネスの整備です。目指すのは、人手ですべてをレビューしなくても、十分な初期品質が保たれ、バクラクとしての非機能要件を満たし、フィードバックによって改善され続ける状態です。そのために、推奨の実装パターン、lint やルールによる制約、正しい仕様へのたどり方、変更を検証する手段、フィードバックを蓄積する方法といった足場を、人にも Coding Agent にも使える形で整えていきます。

フロントエンドで完結しない部分は、Platformチーム、デザインチーム、QAチームとの共同の取り組みをリードすることもあります。どの取り組みも、使ってもらえる形で小さく届け、フロントエンド基盤への信頼を積み重ねながら広げていく必要があります。

## Frontend Enabling のこれまでとこれから

これまでの Frontend Enabling の活動例は、以下の通りです。

-   **monorepo への統合**：2025年末に、React アプリのリポジトリを Go と Nuxt のリポジトリに統合しました。リポジトリと CI を先にまとめ、pnpm workspace の統合は後に分けて段階的に進めています（[リポジトリ統合の LT 資料](https://speakerdeck.com/shibukazu/yue-jing-suruainotameni-jing-jie-woqu-rifu-u-ai-shi-dai-nokai-fa-ti-yan-xiang-shang-nixiang-ketaripozitoritong-he-noqu-rizu-mi)）。
-   **CI と開発環境の高速化**：CI で必要な依存だけを入れるようにして、検査の時間を約3分の1短縮しました。tsgo や oxlint のようなネイティブのツールチェインも取り入れ、型チェックの時間はおよそ半分に、手元やコミット前の lint は数十倍速くなりました。
-   **依存関係の整理**：重複したバージョンや循環する依存を解消し、pnpm の catalog を運用し、バージョンアップを行っています。シンプルに見えることですが、CIの低速化やセキュリティ上のリスク、[npm doppelgangers](https://rushjs.io/pages/advanced/npm_doppelgangers/) の問題を抑制しています（[doppelganger検出ツール](https://github.com/ypresto/pnpm-lock-buddy)）。
-   **共通部品と設計**：コンポーネントライブラリの ui-react、新しいアプリの雛形、複雑なフォームに対応する設計を導入しました（[TSKaigi 2025 の発表](https://speakerdeck.com/izumin5210/number-tskaigi2025)）。
-   **リアーキテクチャ**：古参webappのVue→Reactへの移行により、開発生産性の改善に加えて、バクラクらしい「プロダクト間のシームレスな埋め込み」を実現していきます（[Web Frontend Night の発表](https://speakerdeck.com/ypresto/bakuraku-tech-decisions-and-journey)）。

これまでの活動のさらに先で、Frontend Enabling のロールに期待することとして、大きく2つの軸を定義しています。

-   **エコシステムのスペシャリスト**：ビルド、ランタイム、パッケージマネージャ、CI といった技術面に deep dive し、JavaScript 開発の足場を固めます。
-   **技術戦略を描く人**：フロントエンドに対する専門的な見地と将来の見立てから、全プロダクトをまたいだ技術選定やアーキテクチャ、投資の優先度を決めます。

これらに限らず、「フロントエンド」という側面から事業のスケールを実現してくださる方はこのロールで大きなインパクトを出せるはずです。

（※プロダクト横断の開発基盤を担う [Platform Enabling ロール](https://open.talentio.com/r/1/c/layerx/pages/113198) も募集しています）

わたしたちが一緒に働きたいのは、たとえばこんな方です。

-   **問題の本質まで考え抜く**：「CIを速くする」の一言でも、ランナー、ツールチェイン、アプリケーションコードの様々な箇所に対して仮説検証が必要です。目の前の症状を抑えるだけでなく、真の課題と今後発生しない構造まで考え抜ける方は、この仕事で大きな力を発揮できるはずです。
-   **境界を越えて全体を見る**：1つのプロダクトではなく、すべてのプロダクトと事業の時間軸を見て、何にどの順番で投資するかを考える仕事です。フロントエンドに閉じず、必要なときにソフトウェア開発の全体に踏み込んでいける方を歓迎します。
-   **使う人を中心に考える**：どんなに正しい基盤でも、使われなければ意味がありません。各チームの開発の流れに入り込み、人や Coding Agent が基盤を活用する方法を、組織に実装して育てていける方だと、とても心強いです。

日本、あるいは世界でも有数の規模と思われる monorepo で、人と Coding Agent が事業をスケールさせ続ける。この正解のない問いに挑み、新しい道を切り拓いていくことを楽しめる方と、ぜひ一緒に働きたいです。
