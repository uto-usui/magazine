近年の SaaS 業界では、マルチプロダクト戦略をとる企業が一層増えています。複数のプロダクトを束ねて提供することは大きなシナジーを生みますが、その価値を引き出すには、プロダクト同士がデータを安全にやり取りできること——すなわち連携の土台となる認証の仕組みが欠かせません。

SmartHR でも、社内プロダクト同士の連携に加えて、社外サービスとの連携も少しずつ広がり、その下地が整いつつあります。一方で、システム間の認証方式は多岐にわたります。外部サービス側の制約、社内のセキュリティ要件、技術的な事情などを踏まえると、Basic 認証・API キー・OAuth 2.0 といった複数の方式を個別に作り込むのではなく、クレデンシャルとして共通管理できる基盤が必要になってきました。

本記事の筆者である staakaar が所属するプロダクト基盤開発部の外部サービス連携基盤ユニットでは、こうしたマルチプロダクト戦略を技術面から支える共通基盤の開発を進めています。 本記事では、多様な認証方式のクレデンシャルを共通管理するための設計と、その第一歩を紹介します。

## 認証管理の課題と共通基盤で目指す姿

SmartHR ではこれまで、外部サービスとの連携において、認証をサービスごとに個別実装する形で積み上げてきました。Basic 認証や API キー、OAuth 2.0 と方式が異なるうえ、トークンのリフレッシュや有効期限の管理、失効処理までを各サービスが独自に抱えています。 その結果、連携先が増えるたびに似た実装を繰り返すことになり、開発工数だけでなく運用工数も膨らんでいきました。認証ロジックが各所へ散らばることで、横断的な改善やセキュリティ対応も難しくなっていたのです。

認証をさらに複雑にしているのが、扱う主体が一つではない点です。連携の文脈によって、認証や認可の単位は個人単位だったり、テナント単位だったり、あるいはグループ単位だったりと、複数の概念が絡み合います。 同じ外部サービスへの接続でも、誰の・どの範囲の権限でアクセスするのかが変わるため、クレデンシャルをどの粒度で保持し、どう紐づけるかという設計判断は一筋縄ではいきません。 この多層的な構造をどう共通化するかが、基盤設計の難所となりました。

こうした課題に対して、サービス連携における認証という「定型処理」を基盤に集約することで、各プロダクトが本質的な価値提供に集中できるようになります。あわせて、お客様に統一された UI・UX を提供でき、クレデンシャルの一元管理によってガバナンス強化にもつながります。

## OAuth 2.0 を土台に認可フローを組み立てる

今回の実装では OAuth 2.0[1](#fn:1) による認可フローの共通化を最初のスコープとして取り組みました。 まずは、OAuth 2.0 の認可コードフローと呼ばれる手順をシーケンス図で示します。

AuthServer-->>User: 認可画面表示（ログイン・スコープ確認） User->>AuthServer: 認証・認可 AuthServer-->>Client: リダイレクト redirect\_uri?code={認可コード}&state=... このフローの特徴は、クライアントがユーザーのクレデンシャルを直接保持せず、認可コードとアクセストークンを介してリソースへのアクセス権を取得する点にあります。

大まかな流れは次のとおりです。まずリソースオーナーが認可リクエストを開始すると、クライアントはリソースオーナーを認可サーバーの認可エンドポイントへリダイレクトします。リソースオーナーが認証とスコープの認可を行うと、認可サーバーは redirect\_uri を通じてクライアントへ認可コードを返します。クライアントはこの認可コードを、認可サーバーのトークンエンドポイントでアクセストークンに交換します。以降は、このアクセストークンを Authorization ヘッダーに付与してリソースサーバーの API を呼び出します。アクセストークンには有効期限があるため、期限切れ時はリフレッシュトークンを用いて再発行します。

途中にある state 検証は、CSRF（Cross-Site Request Forgery）への対策です。認可リクエストの開始時に発行した state を、コールバック時に受け取った値と照合することで、第三者によるリクエストの差し込みを検出します。

この構成の中心にあるのは認可フローの共通処理（`Oauth::Base`）で、認可 URL の生成からトークンの保存までの一連のフローを担います。そこに、プロバイダーごとのトークン交換処理を担うプロバイダークラス、認可単位ごとの永続化を担うオーナークラス、CSRF 対策の state を管理するステート管理モジュール（`Oauth::State`）が組み合わさります。どのプロバイダークラスを生成するかは、プロバイダー設定を集約したレジストリ（`Oauth::ProviderRegistry`）が解決します。

このモジュール設計では大きく二つの軸があります。「プロバイダー（どのサービスと認可するか）」と「オーナー（誰の権限で認可するか）」です。この二つを独立させることで、他のサービスとの認可時や認可単位が追加された時の拡張性を高めています。

### プロバイダー軸を分離し、連携先の追加を容易にする

プロバイダー軸は「どの外部サービスと認可するか」を扱う軸です。OAuth 2.0 の認可コードフローには、認可 URL を生成し、CSRF 対策の state を発行し、取得したトークンを保存するという共通の骨格があります。この共通部分を認可フローの共通処理（モジュール図の `Oauth::Base`）に集約し、外部サービスごとに異なる部分だけを個別のプロバイダークラスに閉じ込めています。

外部サービスごとに異なるのは、主にトークンを交換するときの通信の作法です。たとえばある外部サービスでは、コールバックが特定の形式で返る、リフレッシュトークンを発行しない、有効期限を返さないなど固有の事情があります。こうした差異はそのサービス専用のクラスの中だけで吸収され、共通の骨格には影響しません。モジュール図でも、各プロバイダークラスが共通処理を取り込む（include する）形になっており、プロバイダーが増えてもこの関係は変わりません。

この分離の利点は、新しい外部サービスを追加するときに共通処理へ手を入れずに済むことです。今後予定している新たな連携先も、専用のプロバイダークラスを一つ追加するだけで対応できます。

### オーナー軸を分離し、認可単位の追加を容易にする

オーナー軸は「誰の権限でクレデンシャルを保持するか」を扱う軸です。同じ外部サービスへの接続でも、テナント単位でクレデンシャルを持つ場合もあれば、個人単位で持つ場合もあります。基盤ではこの認可単位ごとの違いを共通処理から切り離し、保存先の決定を認可単位ごとのモジュール群（モジュール図の `Oauth::Owner::Base` とその派生クラス）に任せています。

共通処理はトークンを保存するとき、認可単位が何であるかだけを手がかりに、対応する保存処理へ委譲します。共通処理がテナント単位のテーブルといった具体的な保存先を直接知ることはありません。モジュール図でも、共通処理が認可単位の共通処理を利用し、そこからテナント単位や個人単位といった各認可単位が派生する構造で表現されています。

この分離の利点は、認可単位ごとの分岐を共通処理から排除できることです。新しい認可単位が増えても、共通処理に条件分岐を追加する必要がありません。たとえば将来グループ単位が必要になった場合も、グループ用のクラスを一つ追加するだけで対応できます。

### 軸の分離に伴うトレードオフ

軸ごとにモジュールを分ける設計には、相応のコストもあります。共通部分と個別部分を分けたぶん、最初に作るときの構造はどうしても複雑になり、連携先が一つしかない現段階では過剰な作り込みに見えるかもしれません。それでも、今後プロバイダーや認可単位が増えていくことを見据え、初期の複雑さを受け入れてでも拡張しやすい構造を選ぶ価値があると判断しました。

## 共通化における制約と、その乗り越え方

共通基盤として設計を進めるなかで、特に乗り越えが必要だった制約が三つあります。本節では、連携先ごとに増える認可の入り口・iframe による埋め込み制約・既存のお客様への影響、この三つに対する設計判断を順に紹介します。

### 認可の入り口を共通化し、一過性データを安全に扱う

連携先が増えても認可の入り口を増やさずに済むよう、特定の外部サービスに依存しない設計を採用しました。今後は他の外部サービスとの連携も予定しています。仮に外部サービスごとに認可の入り口を用意していくと、連携先が増えるたびに窓口の登録や管理の手間がかさみ、似た処理やテストもそのぶん積み重なっていきます。

そこで、外部サービスからの応答を受け取る入り口は一つに集約し、どの外部サービスからの認可なのかは受け取った情報から判別するようにしました。外部サービスごとに異なる設定は一か所にまとめて管理しています。これにより、新しい連携先を追加するときも、共通の入り口や保存処理には手を入れず、その外部サービスに固有の部分を足すだけで済みます。連携先が増えるほど、この入り口を共通化しておく効果が効いてきます。

この共通の入り口で受け取る情報のうち、認可の途中でしか使わない一過性のデータは Redis で管理しています。代表的なのが、なりすましを防ぐために認可の開始時に発行し、完了時に照合する使い捨ての値（OAuth 2.0 の仕様では state パラメータと呼ばれるもの）です。これは、攻撃者が用意した認可完了の通知をお客様に踏ませて、別のアカウントを勝手に連携させてしまう攻撃を防ぐためのものです。

こうした一時データの置き場所として Redis を選んだ理由は三つあります。

-   state の確認と破棄を一度きりにできる
-   有効期限を自動で扱える
-   メモリ上で動くため高速

一つ目は、state の確認と破棄を確実に一度きりにできることです。一度使った state が二度と通用しないようにすることで、同じ通知を使い回す攻撃を防げます。二つ目は、有効期限を自動で扱えることです。認可の途中データは短時間しか必要としないため、放っておいても期限が来れば自動で消える仕組みは、不要なデータの掃除を考えずに済む点で都合がよいのです。三つ目は速度です。認可フローはお客様を待たせる処理であり、ボタンを押してから次の画面が開くまでの間に一時データの保存が終わっている必要があります。メモリ上で動く Redis は、この速さの要求に十分応えられます。

加えて、認可の完了を画面間で伝えるときの通知先も、この一時データに記録した情報で制御しています。通知を送る相手をあらかじめ記録しておき、その相手だけに送るようにすることで、無関係な画面になりすまされて通知を受け取られることを防いでいます。

### 埋め込み画面の制約をポップアップと中継ページで乗り越える

本基盤の認可画面は、別のプロダクトの画面の中に iframe という仕組みで埋め込まれる形で動作します。お客様は一つの画面を見ているつもりでも、その一部は基盤が提供する別の画面として表示されています。この埋め込み構造には、次の三つの制約があります。

-   多くの外部サービスでは、クリックジャッキング対策として認可画面の埋め込み表示が許可されていない
-   埋め込み枠の中ではサードパーティ Cookie の制限により、ログイン状態を保つための情報がブラウザから送られないことがある
-   お客様の操作に直接ひもづかないポップアップは、ブラウザによって自動的にブロックされる

これらにより、認可フローを埋め込み枠の中だけで完結させるのが難しい状況でした。

そこで、認可フローは独立したポップアップで実行する方式を選びました。代替案として、画面全体を外部サービスへ遷移させる案や、別の埋め込み枠で認可を行う案も検討しました。ただ、これらの案には、入力中の設定が失われたり、埋め込み元のプロダクト側に追加の実装が必要になったり、外部サービス側で埋め込み表示が禁止されていたりといった不都合があり、ポップアップ方式が最も影響の少ない選択肢と判断しました。ポップアップが自動ブロックされる問題に対しては、お客様がボタンを押した操作に直接ひもづける形で先に空のポップアップを開いておき、後から遷移先を設定する手順で回避しています。

ポップアップ方式に残るのは、「認可が終わったあと、その結果をどう埋め込み画面へ伝えるか」という課題です。ポップアップで外部サービスの認可が終わると最後に基盤のバックエンドへ戻ってきますが、この戻り先の画面にはなりすまし対策としてセキュリティヘッダーの一種である Cross-Origin-Opener-Policy（COOP）を設定しています。COOP を設定した画面の出所（オリジン）が埋め込み画面と異なると、ブラウザによって window.opener（ポップアップから見た、開いた元の画面への参照）が失われ、この参照を使って送るはずだった完了の通知が元の画面に届かなくなります。

この問題を避けるため、戻ってきた画面をバックエンドが直接表示するのではなく、いったんバックエンドでクレデンシャルを保存したうえで、フロントエンド側の中継用ページに処理を渡す方式を採用しました。バックエンドはクレデンシャルの保存だけを担い、完了の通知やポップアップを閉じる処理は中継ページが受け持ちます。

sequenceDiagram title 認可結果が中継ページ経由で埋め込み画面に届くまで autonumber participant Parent as 親画面 participant Iframe as 埋め込み画面（iframe） participant Popup as ポップアップ participant Bridge as 中継ページ（埋め込み画面と同一オリジン） participant Backend as バックエンド participant External as 外部サービス Iframe->>Popup: 認可フローを開始（window.open） Popup->>External: 認可画面を表示 Note over Popup,External: お客様がログイン・認可 External-->>Popup: 認可コードを返却 Popup->>Backend: 認可コードを送信（/oauth/callback） Backend->>External: 認可コードをアクセストークンに交換 External-->>Backend: アクセストークン Backend->>Backend: クレデンシャルを保存 Note over Backend,Bridge: バックエンドは画面を返さず中継ページへリダイレクトする Backend-->>Popup: 302 リダイレクト（中継ページへ） Popup->>Bridge: 中継ページを表示 Note over Bridge,Iframe: 同一オリジンなのでCOOPによりwindow.openerが切断されない Bridge->>Iframe: 認可結果を通知（postMessage） Bridge->>Bridge: ポップアップを閉じる Iframe->>Iframe: 認可済みの状態へ画面を更新 Iframe->>Parent: 完了を通知（postMessage）

図のとおり、ポップアップで外部サービスの認可を終えるとバックエンドがクレデンシャルを保存し、その後フロントエンドの中継ページへリダイレクトします。中継ページが埋め込み画面（iframe）へ `postMessage` で結果を伝え、埋め込み画面からさらに親画面へ完了を通知する流れです。

この方式の利点は、中継ページが埋め込み画面と同じ出所で配信されることにあります。COOP は出所が同じ画面同士の window.opener の参照までは切らないため、出所を揃えておけば通知の送信手段そのものを保てます。受け取る側も「自分と同じ出所からの通知かどうか」を確認するだけでよくなり、通知が確実に届きます。あわせて、バックエンドはクレデンシャルの保存に専念し、画面への通知や遷移はフロントエンドが受け持つという責務の分担もはっきりします。

ただし例外として、認可開始時に発行した state の照合に失敗した場合は、戻り先の情報そのものを復元できず、中継ページへ処理を渡せません。このときに限っては、バックエンド側でやり直しを促すエラー画面を表示する形にしています。

### 既存のお客様を止めずに新方式へ移行する

認証の仕組みを新しくするうえでもっとも大きな制約となったのが、すでに連携を使っているお客様への影響を最小限に抑えることでした。これまでの連携では、お客様が外部サービス側で発行したクレデンシャルを連携設定の画面に登録しておくという、シンプルな方式を採用してきました。一度設定すれば長く使い続けられるため、連携先データの同期は安定して動いていました。

この方式から新しい認証方式へ一気に切り替えようとすると、いくつかの懸念が出てきます。

-   業務への影響
-   お客様の手間
-   段階的に確かめながら進めたい

一つ目は業務への影響です。既存の同期が従来のクレデンシャルに依存しているため、切り替えの途中で同期が止まるとお客様の日々の業務に支障が出かねません。二つ目はお客様の手間です。新方式への切り替えには、お客様自身に再設定の操作をしてもらう必要があり、そのための調整が欠かせません。三つ目は段階的に確かめながら進めたいという事情です。新しい認証方式の挙動を、実際の利用環境で少しずつ確認しながら広げていきたいと考えていました。

これらを踏まえて採用したのが、新旧の方式をしばらく併存させる、緩やかな移行の方針です。基盤側では、新方式のクレデンシャルが使える場合はそちらを優先し、まだ無い場合は従来のクレデンシャルをそのまま使います。これにより、切り替えを済ませたお客様はすぐに新方式へ移り、まだのお客様もこれまでどおり同期を続けられます。

この緩やかな移行を実現するために、機能の出し分けにはフィーチャーフラグの仕組みを使いました。フィーチャーフラグとは、コードをリリースしたうえで、その機能を実際に有効にするかどうかを後から切り替えられるようにする仕組みです。今回は、Ruby のフィーチャーフラグ管理ライブラリである Flipper を利用しています。新方式の機能はあらかじめ組み込んでおき、フラグの開閉によって有効範囲をコントロールします。

Flipper を使うことで、新方式をいきなり全体へ公開するのではなく、まず一部のお客様だけに限定して有効にし、問題がないことを確認しながら段階的に対象を広げていけます。万一不具合が見つかった場合も、コードを切り戻すことなくフラグを閉じるだけで素早く元の状態に戻せます。これにより、本番環境で挙動を確認したいという要望と、既存のお客様の業務を止めないという要望を両立させています。

あわせて、画面の表示も連携の状態に応じて切り替えています。新方式への切り替えがまだのお客様には設定を促す案内を出し、これから新しく始めるお客様には新方式だけを案内します。新規のお客様には従来方式を選べないようにしておくことで、新しく始める利用は自然と新方式へ統一されていきます。

## おわりに

本基盤の開発は、現在、最初の連携先の認証を新方式へ移すフェーズにあります。新旧の方式を併存させる緩やかな移行によって、既存のお客様を止めることなく、少しずつ新方式へ寄せている段階です。今後は、他の外部サービスや社内プロダクトとの連携にも本基盤を広げ、認証方式や認証単位の違いを共通の仕組みで吸収していきます。

共通化の難所は予想以上に多く、「どこを共通にし、どこを可変にするか」という設計の境界を引くことが、このフェーズのもっとも重要な仕事でした。長期的には、社内・社外を問わず連携で発生するクレデンシャルを本基盤で一元管理することを目指しています。

クレデンシャル管理のような認証基盤設計や、マルチプロダクト環境での共通基盤開発に関心を持っていただけた方は、カジュアル面談でざっくばらんにお話ししましょう！
